== Use Case: Compact Multiaxis Composition

Compact Multiaxis is a convenience composition for workbook surfaces that need
matrix editing and compact structured cell values at the same time. Sparse
Defaults is a separate capability that a pipeline author may compose explicitly
around Compact Multiaxis when a matrix is dominated by a configured default
value.

It exists to make the pipeline author's configuration and user-facing workflow
smaller and clearer. It does not define independent matrix semantics or
independent cell-code semantics.

=== User Problem

A workbook may need a matrix where each intersection carries one or more short
structured codes.

[source,text]
----
feature_id | Product A | Product B
f1         | E-R       | K
f2         |           | E-K
----

The pipeline author could configure this as separate XRef and Cell Codec steps,
and may add separate Sparse Defaults steps around them when the matrix has a
dominant default value. Compact Multiaxis offers a smoother surface for the
XRef-plus-Cell-Codec case.

=== Functional Boundary

Compact Multiaxis delegates the underlying responsibilities:

* *XRef Crosstable* owns matrix addressing and recomposition: which relation
  tuple a matrix cell represents.
* *Cell Codec* owns compact cell-value interpretation: how one cell represents
  one code or several tokens.
* *Legend Blocks* optionally own allowed-code vocabulary and visible
  explanations.
* *Sparse Defaults* separately owns default-value suppression and restoration
  when the pipeline author configures it around this composition.
* *Compact Multiaxis* owns only the XRef, Cell Codec, and optional Legend
  composition surface.

In short:

[source,text]
----
Compact Multiaxis =
  XRef Crosstable
  + Cell Codec
  + optional Legend support
----

This distinction is required. A compact-multiaxis implementation must not grow
parallel rules for matrix addressing, token parsing, code validation, or legend
meaning. It does not invoke Sparse Defaults or claim sparse-default intent.
Pipelines that need default/blank semantics configure `sparse_collapse` and
`sparse_expand` explicitly around the Compact Multiaxis steps.

=== Step: Expand A Compact Matrix

The forward/read path converts a compact matrix into a generic explicit relation
by applying the delegated matrix and cell-code rules.

==== Information Consumed

* *Compact matrix frame* -- essential; the workbook-like matrix being expanded.
* *XRef projection configuration* -- essential; identifies row keys, value
  columns, and the matrix address shape.
* *Cell Codec configuration* -- essential; defines whether each cell is a whole
  code or a tokenized compact value.
* *Legend identity or code groups* -- optional; used only for code validation or
  generic grouping.
* *Canonical base relation* -- optional (`base_canonical_relation`); the opt-in
  scoped-recomposition input for partial spreadsheet projections. See
  <<scoped-recomposition>>.

==== Information Produced

* *Generic explicit relation* -- rows carrying the row key, column key, compact
  code/token, and optional generic group.
* *Composition trace* -- persistent feature-owned diagnostics that records the
  executed high-level configuration. It is not configuration, inverse intent,
  fallback, or precedence authority and no runtime transformation reads it.

==== Semantic Model Reference

Registry anchors: `compact_multiaxis`, `xref_crosstable`, `legend_blocks`.
Cell Codec is not a metadata registry anchor: it is an
explicit compatibility primitive (`encode_cell_values` /
`decode_cell_values`, historical code-row mode) called internally by this
composite with explicit parameters; it writes no `_meta.cell_codecs` and the
retired family is inert sediment.

=== Step: Contract A Generic Relation To A Compact Matrix

The reverse/write path combines explicit relation rows back into compact matrix
cells by applying the delegated cell-code and matrix rules in the opposite
order.

==== Information Consumed

* *Generic explicit relation* -- essential; the relation to contract.
* *Cell Codec configuration* -- essential; defines how rows become compact cell
  values.
* *XRef projection configuration* -- essential; defines how relation addresses
  become matrix cells.
* *Optional column-key list or fill value* -- optional; controls visible matrix
  shape when explicitly configured.

==== Information Produced

* *Compact matrix frame* -- workbook-facing matrix surface.
* *Composition trace* -- persistent diagnostics and roundtrip explanation;
  never an authority for cell or matrix meaning.

==== Semantic Model Reference

Registry anchors: `compact_multiaxis`, `xref_crosstable`.
Cell Codec is not a metadata registry anchor: it is an explicit compatibility
primitive called internally by this composite with explicit parameters and
writes no `_meta.cell_codecs`.

[[scoped-recomposition]]
=== Scoped Recomposition Of Partial Projections

A workbook surface may intentionally expose only a subset of a larger canonical
relation -- a *partial spreadsheet projection* -- through the matrix frame and
the `value_columns` axis selection. Without extra state, reimporting such a
partial projection and using it to replace the full canonical relation would
lose every row outside the visible matrix scope.

Project directions (local `expand`/`contract` name the data-shape change, not
the overall project direction):

[source,text]
----
forward (canonical -> spreadsheet):
  canonical relation
    -> Cell Codec contract/encode -> compact encoded relation
    -> XRef contract              -> spreadsheet matrix

reverse (spreadsheet -> canonical):
  spreadsheet matrix
    -> XRef expand   -> compact encoded relation
    -> Cell Codec expand/decode -> canonical relation
----

`contract_compact_multiaxis` is the project-level forward direction and
`expand_compact_multiaxis` is the project-level reverse direction.

On the reverse path, the pipeline author may supply an optional
`base_canonical_relation`: the name of a frame holding the *canonical* relation
`[*row_keys, column_key, code (, group)]` (the pre-codec shape this composite
produces on the forward path), not the compact XRef-boundary shape. When it is
supplied, the composite preserves out-of-scope rows purely by composing the
existing primitives:

. Cell Codec encodes the canonical base -- under the *same effective codec
  configuration* used for the matrix result -- to the compact encoded relation
  `[*row_keys, column_key, value]` that XRef consumes at its matrix<->relation
  boundary (a base relation belongs to the representation boundary of the
  transformation that consumes it);
. XRef `base_relation` scoped recomposition replaces exactly the visible matrix
  scope and appends the out-of-scope base rows after it;
. Cell Codec decodes the merged compact relation back to canonical rows.

Behavioral contract:

* *Preservation outside scope* -- base rows whose `(row_id, column_key)` address
  is not covered by the visible matrix survive unchanged.
* *Replacement inside scope* -- a matrix-covered address replaces the matching
  base row; visible content wins over the base for duplicate addresses.
* *Deletion inside scope* -- an emptied/removed in-scope cell removes exactly
  that address and does not resurrect from the base.
* *Ordering* -- in-scope matrix rows first, then out-of-scope base rows in their
  first-occurrence order; this is XRef's ordering contract, not a new
  Compact-specific policy.

The merge is XRef's scoped recomposition and the shape transform is Cell
Codec's: Compact Multiaxis adds no parallel merge, dedup, deletion, or ordering
logic and never inspects row scope itself. The encoded base is a locally created
temporary frame, deleted before returning and never persisted. Omitting
`base_canonical_relation` preserves the pre-existing full-replacement behavior
and returned metadata shape, so existing pipelines that expand a full matrix
are unaffected; the input is opt-in.

Source reference:
`docs/backlog/FTR-COMPACT-MULTIAXIS-SCOPED-RECOMPOSITION-P4A.adoc`. The Cold
Storage composition inquiry
(`docs/cold_storage/working_context/functional_model_inquiry/bijective_frame_transformation_composition.adoc`)
records the maintainer intent this aligns with; it is architectural inquiry, not
an independently accepted universal runtime rule.

=== Sparse And Dense Axis Boundary

The current compact composition treats empty cells as sparse by default:
empty cells do not produce explicit relation rows unless configured otherwise.
This `drop_empty` behavior is Cell Codec row filtering, not Sparse Defaults
composition and does not carry default-value restoration semantics.

Dense-axis reconstruction is not a Compact Multiaxis semantic rule. If a future
workflow needs to recreate a complete matrix from configured row and column
sources, that contract belongs to explicit XRef/axis semantics and must not be
inferred from labels, positions, or naming conventions.

=== Non-Goals

Compact Multiaxis does not:

* interpret the business meaning of codes;
* introduce a second matrix projection model;
* introduce a second cell-code parser;
* introduce a second sparse-default/default-blank model;
* infer dense axes from workbook shape;
* replace XRef Crosstable, Cell Codec, Legend Blocks, or Sparse Defaults as
  concepts.

Its value is ergonomic: one clear user surface for a common composition of
already-defined capabilities.

=== Runtime And Metadata Authority

Both directions derive primitive arguments from explicit Compact Multiaxis
configuration, use a local temporary relation between XRef and the historical
Cell Codec path, and remove that temporary frame before returning. XRef metadata
produced only for that internal leg is restored to the caller's prior state, so
no persisted XRef entry names an internal `__compact_multiaxis_*` frame.

Explicit step configuration remains the Compact Multiaxis authority. Legitimate
caller-supplied XRef metadata remains XRef's authority for its documented
fallbacks, including same-run column ordering. The
`_meta.compact_multiaxis[config_id]` trace only explains what ran; it is never
read back as operative intent.
