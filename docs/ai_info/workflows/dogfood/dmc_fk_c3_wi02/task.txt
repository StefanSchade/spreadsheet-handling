DMC-FK-C3-WI02 / H001 -- Missing TARGET-ID identity assessment
==============================================================

Perform one bounded, read-heavy assessment of Missing TARGET-ID identity
semantics around `check_duplicate_ids`.

This is an ASSESSMENT ONLY. Do not implement or modify runtime/test behavior.

ROLE / GOAL
-----------
The goal is not to choose a preferred design from first principles. Determine
what the current accepted repository/domain authority supports and whether one
safe next Cycle-3 slice can be selected.

CURRENT CONTEXT
---------------
The preceding accepted C3-S1 intentionally left this question unresolved.
`check_duplicate_ids` uses string-backed duplicate detection; multiple Missing
target IDs can currently be reported as duplicates; and its historical `"nan"`
guard is ineffective or vestigial under the current string conversion behavior.
Accepted prior work did not decide whether Missing target IDs are invalid
identity, ignored/non-identity rows, or legitimate duplicate findings.

QUESTIONS TO ANSWER
-------------------
At minimum establish:

1. What does a target ID mean at this boundary? Distinguish ordinary domain
   identity, Missing value carrier, invalid/unusable identity, absence of a
   key, and duplicate identity.
2. What is the exact current behavior of `check_duplicate_ids` for `None`,
   `""`, float/NumPy NaN, `pd.NA`, `NaT`, literal String `"nan"`, and repeated
   ordinary IDs?
3. Is multiple Missing target-ID occurrence invalid independently of
   duplication, something duplicate validation should ignore, or a real
   duplicate-ID condition? Answer only if repository authority supports it.
4. Does another current accepted validation boundary already own the
   "target ID must be usable/non-missing" invariant? If yes, identify it
   exactly. If no, do not silently make `check_duplicate_ids` own it.
5. How do existing FK/helper consumers rely on target IDs? Inspect only enough
   current code/tests to establish whether Missing target IDs can reach the
   relevant validation and what later code assumes.
6. Is the current `"nan"` guard dead or vestigial under the actual string
   carrier, and if so does that fact by itself authorize removal? Dead-looking
   code is not sufficient authority to decide Missing target-ID identity
   semantics.
7. Can one bounded next Cycle-3 slice be selected safely?

     acceptance criteria; and state semantics explicitly unchanged.
   * If no, write `NO SAFE SLICE SELECTED`; identify the unresolved semantic
     authority question; and state what evidence or maintainer decision is
     needed.
