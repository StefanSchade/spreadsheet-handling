[[_bijective_transforms]]
=== Bijective Transforms

These steps come in expand/contract pairs. The expand direction converts a
compact or matrix representation into an explicit relation (long form). The
contract direction reverses it. Losslessness is conditional — see each entry.

==== `expand_xref` / `contract_xref`

*Category*: primitive · *Inverse*: conditionally bijective

Expand a matrix frame (rows × columns of marker cells) into explicit long-form
relation rows, or contract them back. Typical use: a role × permission table
where each cell marks whether the role has the permission.

See also: concept doc `technical_model/ch04_concepts/crosstab_binary_xref.adoc`
and `compact_transforms.adoc`.

*`expand_xref` parameters*

[cols="2,1,4"]
|===
| Parameter | Required | Description

| `matrix`
| yes
| Name of the input matrix frame.

| `output`
| yes
| Name of the output relation frame to produce.

| `row_keys`
| yes
| Column name (string) or list of column names that form the row identifier.

| `value_columns`
| no
| Columns to expand. Defaults to all non-key columns.

| `column_key`
| no
| *Field name* in the output relation that stores the column-axis address value
  (default: `column_key`).  This is a field name, not a list of axis values —
  see `column_keys` on `contract_xref` for that.

| `value`
| no
| Column name in the output holding the cell value (default: `value`).

| `drop_empty`
| no
| If `true`, omit rows where the cell value is empty or blank.  Default: `false`.
  With `base_relation`: a blank in-scope cell removes the matching base tuple.
  Without `base_relation`: a blank cell either produces a tuple with empty value
  (`false`) or is omitted (`true`).

| `base_relation`
| no
| Optional name of an existing relation frame for scoped recomposition.  When
  absent, `expand_xref` converts the matrix to a new relation (standard mode).
  When present, the matrix cells define the update scope and the matching
  base-relation tuples are replaced or removed; relation rows whose addresses
  fall outside the matrix scope are preserved and appended to the output.
  First-run pipelines with no prior relation omit this parameter.

| `drop_source`
| no
| Assert that the expanded relation fully supersedes the matrix and mark the
  matrix for carrier-neutral final domain cleanup
  (`_meta.pipeline_cleanup`).  Rejected when an explicit `value_columns`
  subset would leave unexpanded matrix columns behind.  Default: `false`.
  Workbook helper/technical columns must be removed by their owning
  projection step (or made explicit) before a full expansion.

| `name`
| no
| Override the step name shown in logs.
|===

*Losslessness condition*: lossless when `drop_empty: false`, or when the
original matrix had no empty cells in the expanded columns.  With
`drop_source: true`, the checkable value-loss condition (an unexpanded
`value_columns` subset) fails fast; shape recovery of empty-only columns
under `drop_empty: true` needs dense column intent or a retained matrix.

[source,yaml]
----
- step: expand_xref
  matrix: role_permissions
  output: permission_rows
  row_keys: role_id
  drop_empty: true
----

*`contract_xref` parameters*

[cols="2,1,4"]
|===
| Parameter | Required | Description

| `relation`
| yes
| Name of the input long-form relation frame.

| `output`
| yes
| Name of the output matrix frame to produce.

| `row_keys`
| yes
| Column name(s) forming the row identifier (must match `expand_xref` config).

| `column_key`
| no
| *Field name* in the relation that holds the column-axis address values
  (default: the literal `column_key`; configure it to match the preceding
  `expand_xref`).  This is a field name, not a list of axis values — see
  `column_keys` below.

| `value`
| no
| Column in the relation holding cell values (default: the literal `value`;
  configure it to match the preceding `expand_xref`).

| `column_keys`
| no
| Explicit ordered list of *column-axis values* that become the visible matrix
  columns.  (`column_key` names the field; `column_keys` lists the values in
  that field.)  When supplied together with `dense_axes.columns_from`, both
  must resolve to the same ordered list — a mismatch fails fast.

| `fill_value`
| no
| Value to place in cells with no matching relation row. Default: empty string.

| `dense_axes`
| no
| Map with optional `rows_from` and/or `columns_from` keys.  Each specifies an
  entity frame and key field whose unique values drive the corresponding axis.
  When `columns_from` is supplied, the resolved value list must match any
  explicit `column_keys` exactly (consistency contract, not precedence).

| `drop_source`
| no
| Assert that the contracted matrix fully supersedes the relation and mark
  the relation for carrier-neutral final domain cleanup
  (`_meta.pipeline_cleanup`).  Rejected when the relation carries fields
  beyond `row_keys` + `column_key` + `value` (the matrix represents nothing
  else), or when the matrix columns do not cover every relation column key
  (a matrix that silently drops relation pairs cannot supersede the
  relation).  Default: `false`.

| `name`
| no
| Override the step name shown in logs.
|===

*Losslessness condition*: lossless when relation rows are unique per
(row_keys, column_key) combination.  With `drop_source: true`, uncovered
relation column keys fail fast instead of silently dropping pairs.

.Persisted XRef intent
****
Both steps record one entry under `_meta.xref_crosstable.<id>` holding the
minimal feature-local inverse intent: `relation` and `matrix` frame names,
`row_keys`, and optional `dense_axes.rows_from` / `columns_from`.  The
`relation` / `matrix` names may legitimately reference a frame that final
domain cleanup has removed — a reverse pipeline needs exactly that intent to
recreate the absent side.  Run-local resolution (`column_keys`,
`dense_axes.resolved`) never survives the persistence boundary.  When intent
is looked up by frame name and more than one entry matches, the lookup fails
(in the transformations, in sparse-default targeting, and in column-role
resolution alike); name the intended transform explicitly — or pass explicit
`key_columns` to role-consuming steps — to disambiguate.
****

.Carrier-stable column identities
****
XRef distinguishes *matrix-axis identities* from *physical frame column
labels*, and applies a different rule to each.

*Matrix-axis identities* — the values that participate in the persisted
matrix/relation roundtrip — must be *unique, non-empty strings*.  Spreadsheet
carriers realize matrix headers as strings, so numeric, missing
(`None`/`NaN`/`pd.NA`), mixed-type (`1` vs `"1"`), duplicate, or unhashable
identities would silently change type, collide, or produce non-scalar cells
on readback.  Both steps enforce this on every axis-identity source —
relation `column_key` values, explicit and metadata-derived `column_keys`,
dense-axis-derived identities (live and stored), scoped `base_relation`
column identities, and the full physical *matrix* header row (matrix headers
are themselves axis identities) — and fail with explicit diagnostics before
any `drop_source` cleanup command is recorded.  Explicit `value_columns` are
validated as axis identities *before* they are compared against `row_keys`,
so a missing, numeric, or array-valued selector fails with the same
diagnostic rather than a raw pandas/NumPy error.

*Physical frame column labels* — the labels used to address a column on a
participating relation or `base_relation` frame — carry a weaker, still
strict contract: they must be non-missing, hashable, uniquely and
deterministically comparable, and safe for scalar column selection (so
`row[label]` yields a scalar, never a `Series`).  They are *not* required to
be strings: a unique numeric label, for example, is accepted.  Missing-like
(`None`/`NaN`/`pd.NA`), ambiguous-equality (for example a multi-element
array), unhashable (for example a Python `list`), or duplicate physical
labels are rejected before any output or cleanup.  Hierarchical/tuple
physical labels and the separation of stable
technical identity from visible header labels remain future design work;
they are neither promised nor prohibited by a global string-only rule.

Malformed field declarations fail the same way, before any output or
cleanup: duplicate physical column labels on the relation, matrix, or
`base_relation` frame; duplicate configured `row_keys`; and explicit
`value_columns` that overlap `row_keys`.
****

[source,yaml]
----
- step: contract_xref
  relation: permission_rows
  output: role_permissions
  row_keys: role_id
----

.`column_key` vs `column_keys`
****
`column_key` and `column_keys` look similar but carry different information:

[cols="1,3", options="header"]
|===
| Parameter | Meaning
| `column_key`
| *Field name* — the name of the field in the long/relation frame that holds
  the column-axis address (e.g. `character_name`, `context_id`, `product_id`).
| `column_keys`
| *Value list* — an explicit, ordered list of concrete axis values that become
  the visible matrix columns (e.g. `[Galli, Donzo, Rexi]`).
|===

Example: `character_name` is the field name; `Galli`, `Donzo`, `Rexi` are the values.

[source,yaml]
----
- step: contract_xref
  relation: story_cast_role_named
  output: story_cast_role_matrix
  row_keys: [story_id]
  column_key: character_name      # field name in the relation
  column_keys: [Galli, Donzo, Rexi]   # concrete axis values
  value: value
----

`column_key` does not have to be a technical primary key.  A configured unique
alternate key (such as `character_name`) is valid when it is declared unique.

*Column-axis key sources* (`contract_xref` only):

. `column_keys` only → list used directly.
. `dense_axes.columns_from` only → list resolved from the entity frame at runtime.
. Both supplied → must match exactly; a mismatch fails fast (consistency
  contract, not precedence).
. Neither → falls back to `column_keys` stored in meta from a prior run, then
  to relation column order.
****

.Sparse-default cells and `expand_xref`
****
`expand_xref` does not interpret sparse-default metadata.  If blank cells in
the matrix represent a compressed default (introduced by `sparse_collapse`),
run `sparse_expand` before `expand_xref` to restore explicit default values.
`sparse_collapse` / `sparse_expand` are separate transformations with their own
registered steps.
****

==== `decode_cell_values` / `encode_cell_values`

*Category*: primitive · *Inverse*: conditionally bijective

Decode a compact cell string (e.g. `"A,B,C"`) into one row per code, or encode
code rows back into a compact cell string. Used inside the compact multiaxis
chain or independently for coded single-column cells.

See also: concept doc `technical_model/ch04_concepts/compact_transforms.adoc`.

Both steps require *explicit codec intent*; there is no metadata fallback
and no `_meta.cell_codecs` entries are written. Two contracts exist:

* *Position-based* (`codec_intent`): several participating columns are
  joined into one compact column and split back by position.
* *Historical code-row* (`mode` + codec parameters): rows of codes are
  joined into a delimited cell and split back. Consumed primarily by the
  compact-multiaxis composition; available directly when `mode` is passed
  explicitly.

.Cell Codec is string-oriented and writes no metadata
****
Cell Codec follows the string substrate
(`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE`): position-based participating
values must be non-empty strings or empty; numeric, boolean, or date values
fail with an explicit diagnostic instead of silently changing type through
the compact-cell roundtrip. Empty and missing values encode as the
configured `absent_value` token and decode back to `""`. There is no
escaping or quoting. The position grammar keeps encode unambiguously
decodable with a narrow rule: `codec_intent.separator` must be *exactly one
Unicode character*. Because the separator is a single character, and a real
value containing the separator fails encoding while the absent marker must
not contain it, an accepted encode joins tokens that contain no separator
character, so no separator occurrence can be formed across a token boundary
and decode recovers the same fields. (A multi-character separator does not
have this property and is rejected.) A `split_tokens` historical token
containing its delimiter also fails serialization. Duplicate physical column
labels, duplicate configured columns, and output-column collisions fail
before any output is produced. Codec intent lives entirely in explicit step
configuration; no `_meta.cell_codecs` entries are produced (legacy entries
in old sidecars or workbooks are ignored pass-through sediment).
****

*Position-based `codec_intent`* (same mapping for both steps)

[cols="2,1,4"]
|===
| Key | Required | Description

| `participating_columns`
| yes
| Ordered structured columns joined into (encode) or recreated from
  (decode) the compact cell. Must be unique and must exist on the encode
  source; on decode they must not already exist next to the compact column.

| `compact_column`
| yes
| Name of the compact cell column. Must not be a participating column and
  must not collide with a passthrough column.

| `separator`
| yes
| Token separator inside the compact cell. Must be *exactly one Unicode
  character* (no-escaping grammar). Values containing it fail encoding.

| `absent_value`
| yes
| Token representing an empty/missing attribute. Must differ from the
  separator and must not contain it; a real value equal to it fails
  encoding; decodes to `""`.
|===

[source,yaml]
----
- step: encode_cell_values
  source: profiles
  output: profiles_compact
  codec_intent:
    participating_columns: [delivery, language, auth]
    compact_column: profile
    separator: "/"
    absent_value: "-"
----

*`decode_cell_values` historical code-row parameters*

[cols="2,1,4"]
|===
| Parameter | Required | Description

| `source`
| yes
| Name of the input frame containing encoded cell strings.

| `output`
| yes
| Name of the output frame with one row per decoded token.

| `mode`
| yes (for this contract)
| `whole_cell_code` (the entire cell is one code; punctuation such as `-`
  stays part of the code) or `split_tokens` (split on `delimiter`).

| `value`
| no
| Column in `source` holding the encoded string. Default: `value`.

| `code`
| no
| Column name in `output` for the decoded token. Default: `code`.

| `passthrough_columns`
| no
| Columns from `source` to copy unchanged into every output row.
  Default: every non-`value` column.

| `drop_empty`
| no
| If `true` (default), empty cells produce no output row; if `false`, an
  empty cell produces one row with an empty token.

| `delimiter`
| no
| Token separator for `split_tokens` mode. Default: `-`.

| `allowed_codes` / `allowed_tokens`
| no
| Explicit list of valid code/token strings. Validation fails on unknown
  values.

| `allowed_from_legend`
| no
| Name of a legend block from which to derive the allowed-value set.

| `normalize_case`
| no
| `upper`, `lower`, or omit to leave case unchanged.

| `strip`
| no
| If `true`, strip whitespace from each token. Default: `false`.

| `name`
| no
| Override the step name shown in logs.
|===

*Losslessness condition*: lossless when `drop_empty: false` and token order is
preserved (or `canonical_order` is set on the encode side).

[source,yaml]
----
- step: decode_cell_values
  source: assignments
  output: assignment_codes
  mode: split_tokens
  value: codes
  code: code
  delimiter: ","
  passthrough_columns: [employee_id, project_id]
----

[NOTE]
====
`allowed_from_legend` refers to a legend block authored under
`_meta.legend_blocks`. You may author legend blocks as either a *mapping* keyed
by block name or a *list* of block mappings — for a list, the block name is
taken from `name`, then `id`, then a positional `legend_<n>` fallback:

[source,yaml]
----
# Mapping form (canonical)
_meta:
  legend_blocks:
    status_codes:
      entries:
        - {token: A, label: Active}

# List form (equivalent authoring sugar)
_meta:
  legend_blocks:
    - name: status_codes
      entries:
        - {token: A, label: Active}
----

Both forms are accepted through the CLI/config path and are equivalent: the
library normalizes list form to the canonical mapping automatically, and
persisted output is always mapping form. Authoring the same block name twice
(or a positional name that collides with an explicit one) is rejected.
====

==== `expand_compact_multiaxis` / `contract_compact_multiaxis`

*Category*: composite · *Inverse*: conditionally bijective

Compose `expand_xref` and `decode_cell_values` (or their inverses) to handle
compact multi-axis matrices where each cell encodes multiple coded values.
Parameters are a superset of the two constituent steps.

The steps use explicit configuration. Their persisted
`_meta.compact_multiaxis` entry is a diagnostics-only trace and is never read as
configuration or inverse intent. XRef metadata created for the internal
temporary relation is suppressed before the composite returns. Sparse Defaults
is not part of this composite; configure `sparse_collapse` / `sparse_expand`
separately when needed.

`expand_compact_multiaxis` accepts an optional `base_canonical_relation` for
*scoped recomposition* of partial spreadsheet projections. It names a frame
holding the **canonical** relation `[*row_keys, column_key, code (, group)]`
(the pre-codec shape the composite produces on the forward path) — **not** the
compact XRef-boundary shape that the `expand_xref` `base_relation` parameter
takes. When supplied, the composite Cell-Codec-encodes that canonical base under
the same effective codec configuration to the compact encoded relation, hands it
to the wrapped `expand_xref` as its `base_relation`, and decodes the merged
result. Rows outside the visible matrix scope are preserved; matrix-covered
addresses replace (or, when cleared, delete) exactly the visible scope; no
parallel merge logic exists in the composite. Omitting the parameter reproduces
the pre-existing full-replacement behavior, so full-matrix pipelines are
unaffected. See `functional_model/ch04_use_case_concepts/compact_multiaxis.adoc`
and `FTR-COMPACT-MULTIAXIS-SCOPED-RECOMPOSITION-P4A`.

_Full parameter documentation planned._

==== `project_axis_labels` / `restore_axis_keys`

*Category*: primitive · *Inverse*: conditionally bijective

Swap the *axis-identity vocabulary* of a relation's axis-identity column
(default `column_key`) between stable canonical keys and readable, flat
one-level visible labels, composed *around* unchanged `contract_xref` /
`expand_xref`. `project_axis_labels` (outbound) replaces each canonical key
with its visible label so a following `contract_xref` renders readable matrix
headers; `restore_axis_keys` (inbound) replaces each visible label produced by
`expand_xref` with its canonical key. XRef still owns matrix/relation shape and
cell addressing — only the axis-key vocabulary changes.

The bijection is resolved on every run from a live *source frame* mapping a
canonical key column to a single visible-label column, via the reviewed axis
mapping resolver (`FTR-XREF-AXIS-MAPPINGS-P4A2` Slice 1). Nothing is persisted:
if the source frame is absent, the step fails rather than trusting stale or
visible text. This slice is flat one-level only; hierarchical (tuple) labels
and grouped multi-row headers are later slices.

Typical outbound placement: `project_axis_labels` → `contract_xref`. Typical
inbound placement: `expand_xref` → `restore_axis_keys`.

[cols="2,1,4"]
|===
| Parameter | Required | Description

| `relation`
| yes
| Name of the input relation frame. Outbound: canonical keys in its
  axis-identity column. Inbound: visible labels in its axis-identity column
  (typically the `expand_xref` output).

| `output`
| yes
| Name of the output relation frame to produce (a new frame; the input relation
  is not mutated).

| `source_frame`
| yes
| Name of the live frame holding the key/label mapping. Read on every run and
  never persisted.

| `key_column`
| yes
| Column in `source_frame` holding the canonical axis keys.

| `label_column`
| yes
| Column in `source_frame` holding the single visible label per key (flat
  one-level).

| `order_policy`
| no
| `source_row` (default) or `columns`, forwarded to the resolver. It affects
  only the resolver's internal member order, which value substitution does not
  consume, so a projection roundtrip is identical under both policies.
  `source_row` order is defined relative to the caller-supplied `source_frame`
  row order; this step defines no serialized ordering contract.

| `order_columns`
| no
| Ordered column names used when `order_policy: columns`. Default: empty.

| `column_key`
| no
| Field name in the relation that holds the axis identity (default: the literal
  `column_key`; configure it to match the surrounding XRef steps).

| `drop_source`
| no
| Assert that the projected output supersedes the input relation and mark the
  relation for carrier-neutral final domain cleanup (`_meta.pipeline_cleanup`).
  Requires a distinct `output`. Because this is a one-to-one column
  substitution, no rows or columns are lost, so no value-loss guard applies.
  Default: `false`.
|===

*Losslessness condition*: an exact bijection when the inverse step resolves the
*same* key/label mapping from the same live `source_frame` and configuration. A
canonical key used by the relation but missing from the mapping source
(outbound), or a visible label that does not resolve to a canonical key
(inbound), fails fast before any output or `_meta` mutation is published.
Duplicate source keys or duplicate visible labels fail the bijection. Existing
flat XRef pipelines that already carry readable names as their axis key remain
valid and unaffected; axis projection is opt-in.

[source,yaml]
----
# outbound: canonical keys -> readable labels, then contract to a matrix
- step: project_axis_labels
  relation: story_cast_role
  output: story_cast_role_named
  source_frame: characters
  key_column: char_id
  label_column: char_name
- step: contract_xref
  relation: story_cast_role_named
  output: story_cast_role_matrix
  row_keys: [story_id]

# inbound: expand the edited matrix, then restore canonical keys
- step: expand_xref
  matrix: story_cast_role_matrix
  output: story_cast_role_named
  row_keys: [story_id]
- step: restore_axis_keys
  relation: story_cast_role_named
  output: story_cast_role
  source_frame: characters
  key_column: char_id
  label_column: char_name
----

==== `contract_grouped_xref` / `expand_grouped_xref`

*Category*: composite · *Inverse*: conditionally bijective

Project a canonical relation onto a *grouped* matrix whose dynamic column headers
carry multi-level visible label *tuples* (for example `("Kredit",
"Annuitätendarlehen")`), and restore it exactly. `contract_grouped_xref` runs
unchanged `contract_xref` to build the flat canonical matrix, then attaches the
visible label tuples; `expand_grouped_xref` restores the canonical headers and
runs unchanged `expand_xref`. XRef still owns matrix/relation shape and cell
addressing; the resolver (`FTR-XREF-AXIS-MAPPINGS-P4A2` Slice 1) owns the
key/label bijection.

Unlike the flat `project_axis_labels` / `restore_axis_keys` pair, which swaps a
relation column between a canonical key and a *single* flat label, the grouped
composites carry an arity-N visible *tuple* per dynamic column and keep the flat
canonical matrix and its descriptor together.

*Runtime representation.* `contract_grouped_xref` publishes a `GroupedMatrix`
under `output`: an internal domain carrier bundling the flat canonical-string
matrix DataFrame with a `GroupedHeader` descriptor of the per-column visible
tuples. Since GX-3b/GX-4 it is *also* a workbook carrier: a `GroupedMatrix`
composes into an exact multi-row header grid for both XLSX and ODS, and GX-5
makes that path reachable through the public configuration surface (see
_Configured grouped workbook roundtrip_ below).

`expand_grouped_xref` reads the `GroupedMatrix` from its `matrix` frame. It
exposes no descriptor parameter. Raw `GroupedMatrix(...)` construction is
rejected; `grouped_matrix_from_canonical(frame, header, mapping=...)` is the
public construction seam and proves that the current canonical flat column
schema projects to exactly the supplied descriptor. The inverse repeats that
proof under its live mapping before restoration, so reordered dynamic columns,
moved row keys, stale descriptors, `MultiIndex`, and altered headers fail rather
than silently assigning values to different canonical keys. Matrix cell values
remain intentionally editable; the pairing check concerns column identity and
position, not value immutability.

The axis mapping is resolved on every run from a live *source frame* mapping a
canonical key column to N ordered visible-label columns. Nothing is persisted: if
the source frame is absent, the step fails rather than trusting stale or visible
text. `xref_config_id` is forwarded to the wrapped XRef step and selects its
`_meta.xref_crosstable` identity; metadata ownership stays with XRef. In YAML,
`name` is instead the generic pipeline step/log name and is never an XRef config
ID. The grouped composites add no metadata root and persist no mapping,
resolution, fingerprint, or header depth.

Workbook readback (GX-3b/GX-4) reconstructs exact visible tuples, resolves the
live mapping, restores a canonical flat string header sequence in physical order,
and enters through `grouped_matrix_from_canonical` via the
`reconstruct_grouped_matrix` step. GX-2 itself added no XLSX/ODS read/write; that
carrier support arrived in GX-3b/GX-4 and became publicly configurable in GX-5.

Typical forward placement: `contract_grouped_xref` alone (it wraps
`contract_xref`). Typical inverse placement: `expand_grouped_xref` alone (it wraps
`expand_xref`).

[cols="2,1,4"]
|===
| Parameter | Required | Description

| `relation` / `matrix`
| yes
| Forward `relation`: the input canonical relation frame. Inverse `matrix`: the
  input frame holding a validated `GroupedMatrix` carrier (a bare DataFrame or
  direct raw construction is rejected).

| `output`
| yes
| Name of the output frame to produce (a new frame; the input is not mutated).
  Forward: the `GroupedMatrix`. Inverse: the canonical relation.

| `row_keys`
| yes
| Row-identity column(s), forwarded to XRef and used to classify row-key vs
  dynamic columns. A string, list, tuple, or one-shot iterable is owned once as a
  tuple; XRef retains element/duplicate/existence validation.

| `source_frame`
| yes
| Name of the live frame holding the key/label mapping. Read on every run and
  never persisted.

| `key_column`
| yes
| Column in `source_frame` holding the canonical axis keys.

| `label_columns`
| yes
| Ordered columns in `source_frame` holding the visible label per level (top to
  leaf). Their count is the tuple depth.

| `column_key` / `value`
| no
| Forwarded to XRef (defaults `column_key` / `value`).

| `column_keys` / `dense_axes` / `fill_value`
| no
| Forward only, forwarded to `contract_xref`.

| `value_columns` / `base_relation`
| no
| Inverse only, forwarded to `expand_xref`.

| `level_names`
| no
| Forward only. Descriptor level names (top to leaf); defaults to
  `label_columns`.

| `order_policy` / `order_columns`
| no
| `source_row` (default) or `columns`, forwarded to the resolver. They affect
  only resolver member order, which the header projection does not consume, so a
  roundtrip is identical under both policies.

| `drop_source`
| no
| Assert that the output supersedes the input and mark the input for
  carrier-neutral final domain cleanup (`_meta.pipeline_cleanup`), only on full
  success. Forward marks `relation`; inverse marks `matrix`. Requires a distinct
  `output`. XRef's own value-loss guards remain authoritative. Default: `false`.

| `xref_config_id`
| no
| Exact optional XRef metadata identity. Direct Python and YAML use this same
  spelling; it is forwarded to unchanged XRef. When omitted, XRef keeps its
  relation/output fallback.

| `name` (YAML/config only)
| no
| Generic pipeline step name used for logs. Consumed by the builder and not
  passed to `contract_grouped_xref` / `expand_grouped_xref`; direct Python calls
  have no grouped `name` parameter.
|===

*Losslessness condition*: an exact bijection when the inverse resolves the *same*
key/label mapping from the same live `source_frame` and configuration. A used
canonical key missing from the source (forward), or a visible tuple that no longer
resolves — for example after the source mapping changed between runs (inverse) —
fails fast before any output or `_meta` mutation is published. Duplicate source
keys or duplicate complete visible tuples fail the bijection. As with flat XRef, a
*sparse* relation densifies through `contract_xref`'s `fill_value`; use a dense
relation (or XRef's `drop_empty` on the flat path) when an exact relation
roundtrip is required.

[source,yaml]
----
# forward: canonical relation -> grouped matrix (visible label tuples on headers)
- step: contract_grouped_xref
  name: contract_loan_terms_for_log
  xref_config_id: loan_product_axis
  relation: loan_terms
  output: loan_terms_matrix
  row_keys: [account_id]
  source_frame: products
  key_column: product_id
  label_columns: [category, product]

# inverse: grouped matrix -> canonical relation
- step: expand_grouped_xref
  name: expand_loan_terms_for_log
  xref_config_id: loan_product_axis
  matrix: loan_terms_matrix
  output: loan_terms
  row_keys: [account_id]
  source_frame: products
  key_column: product_id
  label_columns: [category, product]
----

*Configured grouped workbook roundtrip (GX-5).* The grouped carrier reaches a
real XLSX/ODS file through the public configuration path. `configure_workbook_view`
selects the `GroupedMatrix` frame and renames its physical sheet; the router-facing
`save_xlsx` / `save_ods` savers preserve the carrier to the exact multi-row header
grid. On readback, the opt-in `exact_header_depths` backend option (keyed by the
*physical visible sheet name*, value = tuple depth) yields a `core.ExactTable`,
`apply_workbook_view_sheet_mappings` re-keys that visible sheet to the logical
frame, and `reconstruct_grouped_matrix` -> `expand_grouped_xref` restores the
canonical relation. A grouped sheet supports inclusion, order, and rename only:
`helper_columns`, `editable_columns`, protection, and generic per-sheet options
are rejected for a grouped sheet because grouped identity is the full visible
tuple.

[source,yaml]
----
# forward: build the grouped matrix, then declare the renamed visible sheet
- step: contract_grouped_xref
  relation: loan_terms
  output: loan_terms_matrix
  row_keys: [account_id]
  source_frame: products
  key_column: product_id
  label_columns: [category, product]
- step: configure_workbook_view
  sheets:
    - frame: loan_terms_matrix
      sheet: Loan Terms Matrix        # renamed physical sheet
# ... then orchestrate/save through the router saver (save_xlsx / save_ods)

# reverse: load with exact_header_depths[physical sheet], then remap + expand
#   input.options.extra.exact_header_depths: {"Loan Terms Matrix": 2}
- step: apply_workbook_view_sheet_mappings
  logical_frames: [loan_terms_matrix]
- step: reconstruct_grouped_matrix
  table: loan_terms_matrix
  output: loan_terms_matrix_rebuilt
  row_keys: [account_id]
  source_frame: products
  key_column: product_id
  label_columns: [category, product]
- step: expand_grouped_xref
  matrix: loan_terms_matrix_rebuilt
  output: loan_terms
  row_keys: [account_id]
  source_frame: products
  key_column: product_id
  label_columns: [category, product]
----
