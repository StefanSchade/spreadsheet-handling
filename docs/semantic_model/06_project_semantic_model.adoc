[[semantic-model-project-semantic-model]]
== Project Semantic Model

=== Core entities

The semantic model treats the following as first-class entities. Each one
carries semantic obligations beyond its data shape.

* *transformations* -- the primitive and step-level operations that read or
  write frames, metadata, or render state;
* *pipeline steps* -- composed operations the registry and YAML configuration
  describe and orchestrate;
* *metadata attributes* -- fields under `_meta.*` that carry meaning between
  steps and across roundtrips;
* *canonical frame data* -- the project's authoritative dataset
  representation, decoupled from any spreadsheet projection;
* *derived data* -- materialized fields and columns whose authority comes from
  a producer step, not from user edit (for example, FK-helper columns recorded
  under `_meta.derived.sheets.*.helper_columns`);
* *configuration* -- YAML and CLI inputs that select transformations,
  primitives, and named semantic modes;
* *persisted sidecar metadata* -- `_meta`-shaped state that survives between
  runs;
* *render directives* -- metadata that controls workbook presentation and is
  not part of canonical data;
* *workbook-visible cells/columns* -- the public projection a user edits;
* *registry entries* -- `registries/meta_registry.yaml` and
  `registries/pipeline_step_registry.json` records that describe producers,
  consumers, and (in the rule-ready direction) contracts;
* *lifecycle events* -- writes, reads, supersessions, prunings, and
  reimports that change metadata state over time.

[NOTE]
====
Metadata *meaning* is distinct from metadata *shape*. Two fields with the same
JSON shape may carry different semantics if they live in different sets (for
example, a column index in `_meta.derived.sheets.*.helper_columns` is derived
provenance, while the same shape in a configuration block would be input
policy). The semantic model classifies fields by meaning; the schema describes
shape.
====

=== Transformations

A transformation may:

* read frame data;
* write frame data;
* read metadata;
* write metadata;
* derive helper data;
* remove helper data;
* validate data;
* render data;
* prepare data for adapter output.

Questions per transformation (to be answered by the transformation's owning
FTR, registry entry, and -- where stable -- architecture guard):

* What does it read?
* What does it write?
* Does it mutate canonical data, metadata, or only render state?
* Does it consume policy, provenance, config, or inferred structure?
* May it infer semantics, or must it consume explicit metadata? The FK-helper
  primitives, for example, no longer infer relation identity from column
  names and must consume `_meta.helper_policies.fk` (policy) or
  `_meta.derived.sheets.*.helper_columns` (provenance).
* What happens when required metadata is absent? (See the Ambiguity Policy
  for the "must become explicit" criteria.)
* Which registry entry describes it?
* Which tests or guards enforce its contract?

=== Metadata attributes

A metadata attribute is a meaning-bearing field in project metadata. It is
characterized by the semantic sets it belongs to, not by where it lives in
the JSON tree.

Questions per metadata attribute:

* What does it mean (in project terms, not in JSON-schema terms)?
* Who may produce it? Who currently does?
* Who may consume it? Who currently does?
* Is it persistent or transient (in the sense defined under Overlapping
  Semantic Sets)?
* Is it canonical, derived, render-related, operational, or diagnostic?
* Is it user-editable through the workbook surface?
* Is it roundtrip-relevant? Does it survive a canonical-to-workbook-to-
  canonical cycle?
* Does it require provenance, or is the producer obvious from its location?
* Does it have lifecycle/versioning rules (transition bridge, deprecation,
  removal owner)?
* What happens when it conflicts with configuration or newly generated data?
  Which precedence rule applies?

[[semantic-model-domain-scalar-language]]
=== Domain scalar language

[NOTE]
====
*Status: accepted current authority*, promoted from independently accepted
Trusted Ingress evidence (see the Technical Model cross-references below).
This promotion covers only this subsection. The remaining sections of this
chapter, and the rest of the Semantic Model's draft scaffold, keep their
existing draft status and are not stabilized by it.
====

A defined internal Domain language is what lets a generic transformation rely
on the *category* a value belongs to instead of re-interpreting, at every
consumer, whatever external carrier happened to produce it. Concentrating that
interpretation at one boundary -- Trusted Ingress -- *enables* transformations
to be written against a closed set of admitted value categories, and
*provides a basis for* a reusable transformation surface rather than one where
every consumer repeats the same defensive checks against an open set of
possible external objects. This is architectural leverage, not a proof:
admission to the Domain language does not by itself guarantee that a
transformation using it is correct -- see "What successful ingress
establishes" below.

==== The ordinary Domain scalar vocabulary

Ordinary Domain payload is drawn from a positive, closed grammar, not from
"whatever pandas happens to hold." A cell value is admissible Domain state
only if it belongs to one of six scalar categories:

* String
* Boolean
* Number
* Missing
* Date
* DateTime

External representation is not Domain merely because a `pandas.DataFrame` or a
NumPy array holds it: an object-dtype cell holding an arbitrary Python object
is not thereby admitted. The current accepted Domain contract admits zero
ordinary composite variants -- there is no list, mapping, or other
nested-structure Scalar today. A future composite value remains possible in
principle, but only through an explicit, separately accepted contract of its
own; a value is never promoted to a composite by inference from shape or
delimiters.

Carrier representation and semantic category are distinct axes. A
`numpy.int64` classifies as Number while remaining a `numpy.int64`; a
`pandas.Timestamp` classifies as DateTime while remaining a
`pandas.Timestamp`. Classification labels a value's category; it does not
convert, narrow, or rewrap the value into one canonical carrier. Which
concrete Python/NumPy/pandas types populate each category, and the classifier
mechanics that decide category membership, are owned by the Technical Model's
link:../technical_model/ch08_architecture_details/internal_value_model.adoc[Internal
Scalar Value Model] -- this section owns what the categories *mean*, the
Technical Model owns the carrier table and classifier mechanics.

Missing is a recognition over carriers, not a new representation: a bounded
family of carriers (`None`, `""`, and the supported NaN/`pandas.NA`/`NaT`
variants) is recognized as Missing; there is no dedicated `Missing` sentinel
type or wrapper. On the visible spreadsheet surface, the accepted missing
representation stays the ordinary string `""`, consistent with the project's
prior accepted decision that visible spreadsheet payload is a string
substrate
(link:../technical_model/ch03_architecture_decisions/ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE.adoc[ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE]),
which this section does not reopen.

==== Strings that merely look like something else

A value's *shape* never promotes it out of String. A numeric-looking,
boolean-looking, date-looking, formula-looking, SQL-looking, shell-looking, or
HTML-looking string remains an ordinary String unless an explicit,
separately accepted contract says otherwise. The Domain language is defined
positively; it is never derived by guessing intent from content.

==== Framework-authored Intent is not a seventh scalar

`FormulaSpec` and other framework-authored declarative output -- backend-
neutral formula/expression Intent the framework itself constructs -- is not an
ordinary Scalar and not ordinary composite payload. It is not subject to the
ingress scalar grammar above, and its existence does not enlarge the
six-category vocabulary to seven. Where and under what conditions such Intent
may exist inside framework-managed execution state is a controlled-execution-
state concern, owned by the Technical Model
(link:../technical_model/ch06_architectural_layers/architectural_layers.adoc[Architectural
Layers]); this section states only the semantic boundary -- Intent is not
payload.

==== What successful ingress establishes

Successful Trusted Ingress establishes a downstream assumption: ordinary
Domain code operates on admitted Domain state and does not need to defend, at
every consumer, against arbitrary external Python objects. *How* and *where*
that admission is established, and re-established after framework-managed
execution passes through code the framework does not control, is a Technical
Model concern -- see
link:../technical_model/ch06_architectural_layers/architectural_layers.adoc[Architectural
Layers]. This section states only what the resulting assumption *means*: a
value already known to belong to the admitted vocabulary does not need to be
reinterpreted defensively by ordinary transformation code.

That assumption is necessary, not sufficient. Ingress conformance says nothing
about family-specific or transformation-local validity -- whether an FK target
resolves, whether values in a key column are unique, or whether a
transformation's own preconditions hold. A conforming value can still be
semantically wrong for the transformation that receives it; admission to the
Domain language and business/family validity are different questions,
answered at different times, and neither substitutes for the other.
