=== Human Readability Review Guide

A provisional, practical guide for judging *local Human Readability* during
ordinary code review and Domain refactor work. It is the distilled, operational
companion to the archived concept in
link:../../cold_storage/reviews/topic_reviews/human_readability/index.adoc[Topic
Reviews: Human Readability]; that archive remains the evidence base, and current
code, executable contracts, and accepted reviews outrank both wherever they
disagree.

[NOTE]
====
This guide is *provisional, practical, non-binding, and judgment-based*. It is a
review aid, not an implementation authorization. It does not measure anything and
does not enforce anything. Use it to ask better questions, not to score code.
====

==== 1. Status and purpose

*What this guide is.* A subordinate, judgment-based aid for reconstructing the
current meaning of code and deciding whether a change is worth its cost. It is
provisional and non-normative. It ranks *below* architecture, public-API,
persisted-metadata, lifecycle, ownership, and compatibility contracts; a Human
Readability observation never overrides any of those owners.

*What this guide is not.* It is not a static style policy, not implementation
authority, not a new mandatory review stage, not a replacement for architecture
review, not a reason to reopen the completed three-family investigation, and not
a source of universal limits.

*It explicitly rejects automatic enforcement of* any of the following. None of
these is a rule; each is at most a contextual signal:

* a maximum parameter count;
* a maximum function or file length;
* a ban on `Any`;
* a ban on `sheet`;
* one mandatory import spelling;
* mandatory helper extraction;
* mandatory dataclasses or configuration objects;
* comments on every empty or no-op path;
* procedural expansion of idiomatic Python.

*Intended users.* This guide should serve, without requiring the full archive:

* a human maintainer reading unfamiliar code;
* an AI agent performing a Human Readability perspective review;
* an implementer preparing a bounded refactor slice;
* an independent reviewer checking whether readability actually improved.

The archive remains available for deeper questions and for the original evidence
behind every example used here.

==== 2. What Human Readability means

*Local Human Readability is bounded reconstruction.* It is the ability of a
future maintainer to reconstruct the current semantics, lifecycle, ownership,
constraints, validation and side-effect order, and non-local reasons of a piece
of code *without avoidable archaeology* across callers, consumers, tests,
metadata, and history.

*Two independent quality dimensions.* Macroarchitecture (package boundaries,
dependency direction, ownership, contracts) and local Human Readability are
complementary and neither subsumes the other. Sound architecture can still leave
a maintainer paying an avoidable local reconstruction cost; locally tidy code can
still cross a public, persisted, or ownership boundary. The target is *bounded
reconstruction inside sound architecture*, not local prettiness and not
architecture diagrams alone.

*Analytic, not measured, benefit.* The three-family investigation did *not*
measure developer productivity or human comprehension. What it established is
narrower and honest: specific truthful cues -- `target_lookup_index` versus an
authoritative relation, raw-versus-resolved option names, `_ResolvedKeys`,
`dense_config` versus `dense_resolved`, a surfaced `HelperValueProvider`
annotation, replay-safety and validation-precedence comments -- were *identified
as reducing* the number of caller, consumer, and history questions a reader must
answer, and the repository traversal those questions require. Claim that reduced
reconstruction and navigation; do not claim measured comprehension.

*Truthful vocabulary (absorbing the former HR-08).* Names, types, and comments
should state *current* semantics and authority. Version, legacy, and slice labels
are not a separate principle: keep a historical label only when it still
communicates a *current* compatibility, migration, or operational distinction
that someone relies on (for example `schema_version: 2` remaining operational
while a private `v2` internal name is only residue). Remove or keep such labels on
that test alone, never because they merely look old or look tidy.

==== 3. The review sequence

For a normal refactor, walk this short sequence. It is a way of thinking, *not* a
formal program required for every small edit.

. State the concrete reader question the code currently raises.
. Establish the local responsibility and the contract boundary it sits behind.
. Inspect only the callers, consumers, tests, metadata, and history needed to
  answer that question.
. Record the positive structures already present *before* proposing any change.
. Identify the reconstruction cost a reader pays today.
. Compare it against contract, compatibility, architecture, locality, change, and
  review costs (see section 5).
. Classify any gate the change would touch (see section 6).
. Select a disposition: `implement`, `coordinate`, `defer`, `accept`, or
  `stop here` (see section 7).
. If `implement` is selected, define a bounded authorized slice: scope,
  invariants, characterization, non-goals, acceptance.
. Verify the before/after reader question independently (see section 4).

A one-line rename with no gate needs only steps 1, 5, and 10 in your head. Reserve
the full sequence for changes whose cost is non-trivial.

==== 4. Review questions

A small checklist, grouped by concern. These are questions, not thresholds.

*Semantics and names*

* Does the local name state current semantics and authority?
* Does it distinguish raw, authored, resolved, validated, persisted, replayed, or
  derived state where that distinction is real here?
* Is any historical or version vocabulary still operationally meaningful?

*Dependencies and domain values*

* Is the callee receiving broad, irrelevant context?
* Would narrowing preserve one coherent owned domain value?
* Would scalarization scatter invariants or lifecycle across parameters?

*Algorithmic locality*

* Can the operation's phases and validation order be reconstructed locally?
* Would extraction remove an unrelated responsibility, or merely add jumping?
* Is size only a signal, or is there a concrete responsibility or reconstruction
  problem?

*Types and heterogeneous boundaries*

* Is `Any` hiding a stable owned shape?
* Or is it truthfully representing an opaque cell, a pandas value, a carrier, or a
  persisted heterogeneous boundary?
* Would a new type expose real ownership, or only add ceremony?

*Vocabulary and boundaries*

* Does `frame`, `sheet`, `policy`, `registry`, `adapter`, `provider`, or
  `resolution` name the actual object at this boundary?
* Would "normalizing" the vocabulary erase a real workbook or persisted contract?

*Comments and empty paths*

* Does a comment explain a non-local reason, ordering constraint, compatibility
  rule, or side-effect boundary?
* Is an empty or no-op path exceptional, or is it ordinary domain semantics?

*Reuse and abstraction*

* Is there a real shared contract?
* Would extraction preserve diagnostics and validation precedence?
* Is repeated-looking code actually semantically identical?

*Idiomatic language*

* Is the construct genuinely misleading, or merely unfamiliar to the reviewer?
* Would expansion make the code clearer, or only more procedural and Java-shaped?

===== The before/after reader-question test

This is the central acceptance test for any proposed change.

*Before*, state:

* what question a maintainer currently has to answer;
* what files or history they must traverse to answer it;
* which local signal is missing or misleading.

*After*, state:

* what question is now answerable locally;
* what navigation is eliminated;
* what new indirection, API, type, compatibility, or maintenance cost was added.

Reject the change if the only "improvement" is lower LOC, fewer parameters, more
types, more helpers, more comments, greater uniformity, a better static-analysis
score, or personal stylistic preference. A real improvement removes a reader
question or a traversal.

==== 5. Trade-offs and counterexamples

*A change is never judged on reader cost alone.* Every proposal weighs at least
six costs, and the decision turns on the balance among them:

. human reconstruction cost;
. contract and compatibility cost;
. architecture and ownership cost;
. maintenance and change cost;
. algorithmic locality;
. implementation and review cost.

Each of the following legitimate pressures becomes a harmful universal recipe if
applied mechanically. The counterexample shows why.

[cols="2,4", options="header"]
|===
| Tempting cleanup | Concrete counterexample

| Minimize the API / signature
| FK's generic raw-options bag hid real authored inputs; explicit resolved inputs
read better. Minimal surface helps only until it hides inputs or lifecycle.

| Atomize a value into scalars
| The Enrich Lookup resolved policy and XRef dense-axis descriptors are coherent
owned mappings; scalar explosion would scatter their invariants. "Narrow" means
the smallest coherent owned value.

| Shorten every long function or file
| XRef's 516-line operation and 411-line dense-axis owner keep validation order
locally auditable. Extraction by length would hide phase order and error
precedence.

| Eliminate `Any`
| XRef cell values are intentionally opaque; pandas and persisted boundaries are
heterogeneous. Type stable owned states; do not invent a false universal value.

| Replace `sheet` with `frame`
| `lookup_sheet`, workbook targets, and `_meta.derived.sheets` are truthful
boundary vocabulary. Rename only a domain object incorrectly called a sheet.

| Use one import spelling everywhere
| Each family had a coherent local boundary rule. Guard dependency *direction*;
leave relative-versus-absolute spelling to local judgment.

| Extract repeated-looking code
| XRef validation blocks can look alike while protecting different direction,
identity, and diagnostic precedence. Reuse only a real shared contract.

| Comment every empty path
| Ordinary empty/sparse/dense outcomes need no ceremony; over-commenting hides the
genuinely exceptional replay-safety and loss explanations.

| Introduce a configuration object
| Enrich Lookup already had explicit arguments; a config object would invent
lifecycle. Justify one only by a real resolution boundary.

| Expand concise Python procedurally
| Accepted closures, comprehensions, tuple unpacking, `setdefault`, and pandas
idioms were readable. Expansion adds names and state without a reader-facing gain.
|===

==== 6. Contract and ownership gates

A readability finding that touches any of these boundaries must be *transferred to
that owner before any change*. The finding does not authorize the change.

[cols="2,2,2", options="header"]
|===
| Boundary | Who must authorize | Characterization required

| Private local implementation | The reviewing/implementing engineer | Existing
tests; a bounded slice definition
| Public Python API | API owner | Compatibility assessment; deprecation/migration
plan if the surface changes
| YAML / CLI surface | Config/CLI owner | User-facing compatibility and
documentation impact
| Persisted metadata | Persistence owner | Round-trip and read-old/write-new
characterization
| Workbook / carrier behavior | Carrier owner | Behavioral characterization of the
workbook or carrier contract
| Architecture / layer ownership | Architecture reviewer | Dependency-direction and
ownership assessment
| Cross-feature lifecycle | The owning lifecycle authority (e.g. derived
provenance) | Lifecycle-invariant characterization across features
| Compatibility / migration | Release/compatibility owner | Version and migration
impact; guard coverage
|===

==== 7. Findings and dispositions

*Observations are not findings; findings are not tasks.* An observation is
anything that makes a reader pause. It becomes a finding only when evidence
establishes a specific avoidable reconstruction cost. A finding becomes work only
through an explicit authorized slice. Independent acceptance stays distinct from
implementation.

Define five distinct dispositions:

`implement`:: concrete reader cost, safe authority, and a demonstrated gain
justify an authorized bounded slice now.
`coordinate`:: a real issue exists, but another architecture, public, or
persistence owner must decide and own it.
`defer`:: likely useful work, but present value, sequencing, evidence, or capacity
does not justify doing it now.
`accept`:: the current structure is the better known trade-off; the residue is
consciously and knowingly retained.
`stop here`:: this review produces no additional work; it may still include
positive validation and findings transferred elsewhere.

`stop here` describes the *review outcome*; `accept` and `defer` describe *item
dispositions*. A review can legitimately conclude `stop here` with real positive
findings and zero implementation.

*Example dispositions* (explanatory, from the completed investigation; not
reopened):

[cols="3,2", options="header"]
|===
| Item | Disposition

| FK local `target_registry` name overstated an execution index | `implement`
| FK Formula Provider factory/type clarity (surfaced existing callback) | `implement`
| FK `build_v2_target_registry` (load-bearing adapter; broader rename) | `accept`
| Enrich Lookup local helper reshaping | `stop here` / `accept` low-value residue
| Enrich Lookup nested provenance mutation (architecture/lifecycle owned) | `coordinate`
| XRef long operations (cohesive, locally reconstructable) | `accept` positive structure / `stop here`
| XRef stale package docstring and reversed technical-model directions | `implement` (documentation-only correction)
|===

==== 8. Positive patterns to preserve

Record the structures worth keeping *before* suggesting changes; a positive
finding constrains any later implementation. Examples surfaced by the
investigation:

* Enrich Lookup `_ResolvedKeys` as a lifecycle/type boundary;
* one coherent resolved lookup policy, narrower than all frames yet not atomized;
* XRef authored *Intent* versus transient *Resolution* kept distinct;
* XRef validation-sensitive phase locality kept in one place;
* cohesive dense-axis descriptor mappings as domain descriptors;
* legitimate heterogeneous cell boundaries typed as `Any`;
* FK Helper replay-safety explanations as non-local-reason comments;
* the existing `HelperValueProvider` surfaced at its factory rather than redesigned;
* correct `stop here` outcomes recorded as successful reviews.

==== 9. Guidance for AI-assisted reviews

An AI reviewer performing a Human Readability perspective *should*:

* begin from a concrete human reader question;
* distinguish an unfamiliar idiom from a misleading construct;
* search callers, consumers, and history only as far as that question requires;
* report positive patterns even when there is no finding;
* label direct evidence, inference, and hypothesis, and expose uncertainty;
* allow and recommend no-change outcomes;
* transfer architecture findings to their owner;
* avoid generating work from every observation.

It *should not*:

* auto-refactor;
* infer unreadability from file or function length;
* ban a language or pandas idiom;
* demand total typing;
* turn a naming preference into a severity;
* claim measured human benefit;
* create a new mandatory workflow stage.

===== Relationship to static analysis

Static analysis supplies *signals and guards*, not readability verdicts. It can
usefully contribute evidence about import cycles, dependency direction, public
surface drift, duplication, complexity, type coverage, and executable architecture
decisions. It *cannot* by itself decide whether a value is coherent or broad,
whether an extraction is useful or harmful, whether boundary vocabulary is
truthful, whether a type is clarifying or ceremonial, or whether a long operation
preserves valuable locality. Route static signals to a location; let judgment
decide. An accepted contextual decision may later be frozen as a narrow guard (for
example, a forbidden-dependency-direction check), but only after a human
establishes it.

==== 10. Applying the guide in ordinary refactor work

In day-to-day work, this guide is a lightweight lens, not a program:

* Reach for the full section 3 sequence only when a change's cost is non-trivial;
  a gate-free rename needs only the before/after reader-question test.
* Prefer the smallest bounded slice that removes a real reader question, with
  explicit scope, invariants, and non-goals.
* Treat `accept` and `stop here` as normal, successful outcomes -- most
  observations should end there.
* When a finding touches a gate in section 6, stop and transfer it; do not
  disguise an architecture change as readability cleanup.
* Do not reopen the completed three-family investigation; use its examples as
  calibration, not as a backlog.

The point is disciplined perspective and honest evidence, not another source of
work.
