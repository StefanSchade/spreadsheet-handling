=== Extending Trusted Ingress

A practical, maintainer-facing checklist for the recurring extension
questions Trusted Ingress raises: adding a registered step, adding a
controlled role, adding a composite Domain value, and the trust-boundary
discipline that runs through all of them. *This section owns extension and
maintenance practice, not architecture.* It states what a maintainer must
prove and update; it does not re-derive *why* the mechanism works that way
or reproduce the full current census/role-set/composition tables. Those
belong to the Technical Model's
link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc[Architectural
Layers] -- follow the links below for the accepted mechanism, current role
set, and current resource census, rather than trusting a paraphrase here
that could drift out of date.

[[dg-h1-registered-step]]
==== Adding a new registered / resource-sensitive step

Registry membership by itself grants *none* of the following. Do not assume
any of them merely because a step is reachable from YAML:

* description authority -- whether a less-trusted pipeline description may
  name this step at all;
* plugin authority -- whether it may accept dotted plugin targets;
* filesystem/resource authority -- whether it may read or write outside the
  in-memory frame set;
* sink authority -- whether it may receive or terminate controlled-role
  state.

Checklist for every new registered step:

. *Classify description identity.* Decide explicitly whether a less-trusted
  description may name this step. This is a positive, reviewed decision, not
  an inherited default -- see
  link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#description-and-resource-authority[Architectural
  Layers, "Description and Resource Authority"].
. *Classify less-trusted-description availability* the same way -- allowlist
  membership, not omission-implies-allowed.
. *Classify resource-sensitive behavior.* Does the step read or write
  outside the in-memory frame set? If yes, it needs its own resource-
  authority classification. Extending the current resource-sensitive census
  is itself reviewed architectural work, not a config toggle -- see the same
  section's "Resource-sensitive capability" subsection for the current
  census and its exact-root/conjunctive-permission shape. Do not re-derive
  that census here; link to it, because it is exactly the kind of table that
  drifts if duplicated.
. *Preserve authorization ordering.* Authorization must be checked, and
  denial must take effect, before import, acquisition, factory resolution,
  binding, or resource activation. A denied step must never be imported
  first and checked afterward.
. *Update the fail-closed census/guard.* An unclassified registry entry must
  fail closed (deny) -- it must never inherit authority merely from registry
  membership.
. *Add tests proving denial occurs before activation* -- not only that the
  step is eventually rejected, but that no import, factory-resolution,
  binding, read, or write side effect occurred on the denied path.

[[dg-h2-controlled-role]]
==== Adding a new controlled role

A new `ControlledRole` is not a config edit and not merely a dataclass that
looks like an existing role. The closed current role set has exactly three
members (`LookupFormulaSpec`, `GroupedMatrix`,
`ArtifactManifestSourceFrames`) -- see
link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#controlled-execution-state[Architectural
Layers, "Controlled Execution State"]. Adding a fourth requires, at minimum,
an explicit answer to each of the following before any framework-managed
flow may carry it:

* named semantic role;
* exact introducing producer/transition -- the one reviewed function call
  that may establish it, and no other;
* exact permitted location -- cell, column, or top-level frame name, stated
  precisely;
* structural/cell contract -- what shape the role's carrier must have;
* current-state descriptor/certificate relationship -- how a classifier
  proves a bound call actually carries this role (see
  link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#certified-executable-binding[Architectural
  Layers, "Executable Binding Authority"]);
* exact consumers -- which transitions or adapters may read or carry it;
* carry/relocation rules -- what happens to the role when its carrier moves
  (a copy, a projection, a relocation);
* exact termination rule -- the specific transition that ends the role's
  authority, not a generic "cleanup" gesture;
* composition rule with every already-supported role -- a disjoint-product
  footprint proof, or the one admitted nesting, per the "Composition"
  subsection of <<controlled-execution-state,Controlled Execution State>>;
* sink/adaptor implications -- which concrete renderer or adapter may
  terminate the role by consumption; every other sink kind must be rejected
  before the saver runs;
* uncertified-return behavior -- the role ends by rule on any uncertified
  return, exactly like every current role (see "Re-establishment after an
  uncertified return" in the same chapter); this is not itself a design
  choice a new role gets to make differently;
* tests and architecture guards proving all of the above.

State clearly, because these are the two failure modes actually seen during
the controlled-role lifecycle's own correction history:

* matching class, factory, shape, mapping key, or an "it did not touch it"
  observation does *not* establish role authority by itself -- only the
  exact reviewed introducing transition does;
* role composition is never automatic. Coexistence with an existing role
  requires one of the two accepted composition proofs; absence of an
  explicit composition proof means the combination is *unsupported*, not
  merely undocumented -- treat it as forbidden until proven.

Link to canonical: Architectural Layers'
link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#controlled-execution-state[Controlled
Execution State] and
link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#certified-executable-binding[Executable
Binding Authority] own the accepted mechanism, the current role set, and its
lifecycle. Do not reproduce that lifecycle here; it drifts.

[[dg-h3-composite]]
==== Adding a future Domain composite

Today's Domain grammar admits *zero* composite variants -- see the Semantic
Model's
link:../../semantic_model/06_project_semantic_model.adoc#semantic-model-domain-scalar-language[Domain
scalar language]. A future composite value remains possible in principle,
but only through its own separately accepted contract. That contract must
define, at minimum, all eight of the following -- an incomplete-looking-
complete checklist is worse than none, so treat this as a minimum, not a
menu:

. a named composite kind, distinct from arbitrary Python collection
  identity;
. a finite cardinality/depth/resource bound;
. the permitted scalar-leaf grammar and Missing semantics for its leaves;
. an explicit carrier plus ownership/copying (alias-safety) rule;
. a schema/declaration and operator-policy capability;
. ingress classification/normalization and safe-path diagnostics -- bounded,
  never echoing raw hostile content, matching the diagnostics discipline in
  link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#trusted-ingress-establishment[Architectural
  Layers, "Establishing and Re-establishing the Domain Scalar Language"];
. DataFrame/pandas interaction -- how the composite behaves as a cell value
  under existing frame operations;
. codec/representation support for every claimed external surface -- every
  backend that must round-trip it.

Make explicit, when proposing or reviewing such a contract:

* no delimiter/shape inference is ever acceptable -- a value is never
  promoted to a composite because it merely looks like one (a numeric-,
  list-, or JSON-looking string stays String, exactly as the ordinary
  scalar vocabulary already requires for strings that merely look like
  something else);
* a list, mapping, or other nested structure happening to sit in an
  object-dtype cell is not by itself evidence of Domain composite status;
* adding a composite is a contract extension requiring its own accepted
  design and review -- it is not merely defining a new Python type or a new
  codec.

This is guidance for a future reviewed extension. It does not itself design
a composite, and it does not reopen the current zero-composite decision.

[[dg-h4-h5-trust-discipline]]
==== Trust-boundary and extension discipline

Two rules recur across every extension surface above and are worth stating
once, together, rather than re-deriving per checklist:

*Where authority must be established.* Never assume authority from
framework authorship, class identity, registry membership, or a value
merely "looking like" a certificate, role, or authorized target. Authority
is established only by the exact accepted mechanism -- the single
authoritative binding snapshot for executable authority
(link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#certified-executable-binding[Executable
Binding Authority]), or the exact reviewed introducing transition for a
controlled role
(link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#controlled-execution-state[Controlled
Execution State]), or the positive allowlist for description/resource
authority
(link:../../technical_model/ch06_architectural_layers/architectural_layers.adoc#description-and-resource-authority[Description
and Resource Authority]).

*What must fail closed.* Every extension surface above -- description
authorization, resource-sensitive capability, controlled-role
classification -- rejects by default. A new, unclassified case is denied,
never admitted by omission.

*What reviews/tests need updating.* Extending any allowlist (plugin
targets, resource-sensitive steps, controlled roles) is reviewed
architectural work, held to the same review bar as the original mechanism
-- not a follow-on config change slipped in beside an unrelated feature.

*Acceptance and wiring are separate checks.* An independently accepted rule
is not automatically live in production. A new ingress or authorization
rule must be explicitly wired into the relevant macro seam (`orchestrate`,
`run_app`, `run_schema_maintenance`) before relying on it -- confirm actual
reachability, not merely acceptance. (This is the same lesson the accepted
architecture already records about an earlier ingress rule that was
accepted before it was wired in; the general rule, not that specific
episode, is what a maintainer needs to carry forward.)

*Which permanent doc owns the resulting contract.* New authority always
lands in the Technical Model (mechanism); this file supplies maintainer
checklists that link to it, never a competing description of the mechanism
itself. If a checklist item above and the Technical Model ever appear to
disagree, the Technical Model is authoritative and this file needs a
correction.
