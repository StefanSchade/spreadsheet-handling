== 7. Current candidate Trusted Ingress target shape

*REVIEW-RECOMMENDED CANDIDATE -- not authoritative and not implemented.*

[source,text]
----
load
  -> initial ordinary establishment

for each managed step:
  -> declare permitted controlled-exception locations
  -> execute the actual step
  -> validate the actual returned state:
       ordinary everywhere else; role-specific postcondition at declared locations;
       `_meta` validated
  -> derive confirmed ManagedExecutionState from observation

before persistence:
  -> authorize confirmed controlled exceptions for the sink
  -> save
----

The intended simplification is that actual state is authoritative.  Derived
trust/certificate state should not be carried where it can cheaply be re-derived.

== 9. Plugin/product-responsibility boundary

Less-trusted YAML/config must not widen or disable the policy constraining its
own plugin authority; operator-owned deny-all/allowlist policy is the correct
boundary.  Once arbitrary same-process Python plugin execution is intentionally
allowed, Trusted Ingress cannot contain plugin side effects.  Filesystem,
network, credential, subprocess, and process isolation then belong to deployment
or runtime responsibility.  Re-establishment still constrains returned Domain
state only.  This records a boundary, not a sandbox design.

Source: assurance review, sections 5, 12, 13, and 18 (same anchor as section 6).

== 10. Assurance anti-accretion rule

A new assurance mechanism needs an external actor/failure anchor, correct-boundary
ownership, an actual enforcement consumer, a cost statement, and a removal
condition.  "Existing governance says so" is not sufficient justification for
more governance.

Diagnostic question: are we enforcing an invariant on authoritative state, or
building machinery to keep a derived description of that invariant synchronized?

Source: assurance review, sections 6, 7, 16, and 20 (same anchor as section 6).
