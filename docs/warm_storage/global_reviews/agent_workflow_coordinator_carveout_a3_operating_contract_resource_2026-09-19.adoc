=== 2.2 Current loading, digest, and prompt path

`operator._preflight()` currently normalizes and reads five consumer paths at
the pinned Git revision: WorkItem, profile, policy, component manifest, and
task. It then loads every component selected by any profile phase. Every one of
those texts is read with `_pinned_text()` through `git ls-tree` and `git show`.
SHA-256 is calculated over `text.encode("utf-8")`; the resulting path-to-digest
mapping is written as `operator-plan.json` `governing_inputs` and re-read from
Git at inter-Hop continuation.

Selected components become `PromptComponent` values. Their references expose
component ID, repository path, Git revision, digest, byte count, and `git show`
retrieval instruction. `assemble_prompt()` orders generated header, selected
role/modifier/policy components, workflow policy, task, context/diff, and the
result-output footer. The operating contract has no distinct identity,
version, digest, or provenance projection today.

The provider-capable path is:

----
operator._preflight
  -> operator.main / operator-plan.json
  -> run_serial_hops
  -> slice4.run_real_one_hop
  -> vertical.run_one_hop
  -> prompt.assemble_prompt
  -> adapter.execute
----

The proof harness joins at `run_real_one_hop`; direct unit seams also call
`run_one_hop()` and `assemble_prompt()`.

== 3. Current dependency problem

The current failure is semantic ownership, not merely a bad pathname. Agents
learn Coordinator invariants from whichever consumer happened to author a task
or component. A consumer can omit, paraphrase, or contradict those invariants,
and the resulting prompt carries no evidence identifying a Coordinator-owned
contract. The proof harness independently restates part of the same semantics.

Treating a Core file path as the authority would preserve the defect: it would
make the consumer repository the apparent owner and require the operated
repository to contain Coordinator semantics. The Coordinator may remain
physically embedded beneath Core until extraction, but its loader and authority
must already be package-relative and Coordinator-owned.

== 4. A3 boundary

A3 answers one question: how the Workflow Coordinator owns, validates, injects,
and records exactly one current generic agent operating contract. It covers:

* Coordinator ownership of one resource;
* one explicit identity and version;
* strict package-relative loading through `importlib.resources`;
* deterministic exact-byte digest/provenance;
* unconditional prompt injection for every provider-capable Hop;
* pre-provider fail-closed behavior; and
* removal of conflicting generic restatements from current production consumer
  tasks and the proof harness.

A3 does not make the Coordinator generally relocatable or distributable. It
does not alter consumer work authority, profile routing, RepositoryPolicy
schema, structured-result schema, reducer semantics, CLI shape, or provider
selection.

== 5. Resource ownership model

=== 5.1 Exact resource

The A3 implementation shall add exactly one resource:

----
scripts/workflow_coordinator/resources/agent_operating_contract_v1.txt
----

The package anchor is the package containing `prompt.py`, obtained
package-relatively rather than named as a Core filesystem path. At the current
layout this is `scripts.workflow_coordinator`. The resource lookup is equivalent
to:

[source,python]
----
importlib.resources.files(__package__).joinpath(
    "resources", "agent_operating_contract_v1.txt"
)
----

This does not require `resources/` to become a Python subpackage and does not
create a resource framework.

=== 5.2 Authority

The Workflow Coordinator maintainer authors and owns the generic operating
contract as Coordinator source. Consumer maintainers author WorkItems, profiles,
policies, tasks, and selected consumer components. Those consumer inputs may add
work-specific or repository-specific constraints, but they cannot select,
replace, disable, register, or supply the Coordinator operating contract.

RepositoryPolicy, WorkflowProfile, WorkItem, component manifest, CLI, and
environment receive no operating-contract field. No runtime registration,
plugin hook, search path, alternate filename, or environment override exists.

The resource is not a `PromptComponent`: it is mandatory Coordinator authority,
not phase-selected consumer context. It is never subject to component omission
limits and never appears as a consumer component or `git show` retrieval path.

=== 5.3 Content boundary

Version 1 shall communicate only generic Coordinator rules already enforced or
projected by existing mechanics:

* generated WorkItem/Run/Hop/invocation identity and phase authority are the
  current invocation facts;
* the agent must not perform mutating Git ownership operations; read-only Git
  inspection remains allowed where phase/task authority permits it;
* CommitIntent is a proposal for Coordinator-owned mechanical commit handling,
  not proof that a commit occurred or permission to broaden paths/actions;
* the required structured result envelope and correlated identity fields are
  mandatory; prose does not replace routing-critical fields;
* outcome, route, scope-change, human requirement, escalation, Finding,
  evidence-reference, summary, and CommitIntent fields must be truthful;
* missing scope, semantic authority, public-surface authority, trust-boundary
  authority, prerequisite, or operational capability is reported through the
  existing escalation vocabulary rather than concealed by false completion;
* consumer task text and selected components remain the authority for what work
  to perform and which repository engineering rules apply.

The text shall reference the existing schema/phase facts rather than reproduce
validation algorithms. It shall not contain DMC, spreadsheet, Core-path,
provider, model, or consumer-specific instructions.

== 6. Versioning

A3 has one supported identity tuple:

[cols="1,3",options="header"]
|===
|Field |Required value

|Contract ID
|`workflow_coordinator.agent_operating_contract`

|Contract version
|Integer `1`

|Resource name
|`agent_operating_contract_v1.txt`

|Resource package-relative path
|`resources/agent_operating_contract_v1.txt`

|Content digest
|One implementation constant containing the reviewed SHA-256 of the exact v1
resource bytes
|===

The file begins with one exact, small ASCII identity prologue carrying the
contract ID and integer version. The loader validates the prologue, resource
name, supported version, and expected digest as one invariant. It supports no
caller-requested version and performs no negotiation.

A content change that alters semantics requires an explicit reviewed identity
decision. A3 does not add v2, a compatibility reader, migration framework,
deprecation mechanism, or multi-version dispatch. Calling the artifact a
package, contract, schema, or security boundary does not imply enterprise or
mass-market requirements; no product-scale machinery is inferred from those
terms.

== 7. Loading and failure semantics

=== 7.1 Loaded value

`prompt.py` shall own a small immutable value and loader rather than a new
module. The value carries exactly:

* contract ID;
* integer version;
* package-relative resource name;
* exact decoded text;
* exact byte count; and
* SHA-256 over the exact resource bytes.

The loader reads bytes once, rejects empty content, validates the exact identity
prologue and expected digest, and decodes strict UTF-8 without newline,
whitespace, Unicode, or BOM normalization. Prompt text is the validated decoded
text. Digest and byte count always describe the bytes actually read.

=== 7.2 Canonical operator

`operator._preflight()` shall call the loader exactly once before Run ID
allocation, `new_run()`, state-root creation, checkout registration, adapter
construction, or provider invocation. The immutable result is returned with
the existing admission bundle, recorded in `operator-plan.json`, and passed
through `run_serial_hops()`, `run_real_one_hop()`, and `run_one_hop()` to
`assemble_prompt()`. Every Hop in that process receives the same loaded value.

`assemble_prompt()` validates that the supplied internal value still matches
the one supported identity tuple and injects its full text immediately after
the generated identity/authority header and before phase-selected consumer
components. The existing result-output footer remains last. There is no
conditional omission path for the contract.

=== 7.3 Proof harness and direct seams

The proof harness shall call the same loader once before creating its proof
root/repository or registering a checkout, record the same provenance facts in
its summary, and pass the result through the same prompt assembly path. It shall
delete its local sentence that re-authors Coordinator commit ownership.

Focused unit seams may pass the immutable loaded value to exercise prompt and
vertical behavior. That internal parameter is not consumer configuration and
does not authorize alternate content. Tests for missing/corrupt resources may
replace the resource reader at the loader seam; they do not add a production
override.

=== 7.4 Fail closed

Missing resource, unreadable resource, invalid UTF-8, empty content, wrong ID,
unsupported version, resource-name/version inconsistency, expected-digest
mismatch, or a loaded-value inconsistency shall produce a stable Coordinator
resource error. The canonical operator projects it through the existing
preflight error boundary and exits before provider-capable state. The proof
harness refuses before creating its proof root. A direct vertical seam reports
execution not started if it encounters an inconsistent internal value.

There is no fallback to the consumer repository, current working directory,
task text, component manifest, `generic_agent.txt`, the reserved Core path by
filesystem access, an environment variable, or a second built-in copy. A stale
matching repository file cannot rescue a resource failure.

== 8. A1 and governance interaction

The resource has two simultaneous but non-conflicting facts before extraction:

. it is physically tracked at the A1-reserved path in Core; and
. it is semantically loaded as a Coordinator package resource, not as a
  consumer-selected repository input.

Both current real v3 policies already protect that exact tracked path. Therefore
A3 needs no policy path edit, policy schema change, or policy revision bump. The
existing A1 symmetric overlap check continues to prevent every admitted phase
scope from equalling, containing, or descending into that location. This is
truthful pre-split protection of the embedded Coordinator source.

The resource shall not be added to the consumer path-to-digest `governing`
mapping and shall not be passed to `_governing_inputs_unchanged()`: those
structures are explicitly repository-backed consumer inputs and are re-read
from the operated repository at later HEADs. The A3 resource is loaded once from
Coordinator ownership and retained immutably for the Run.

The neutral temporary consumer fixture need not vendor or name the Coordinator
resource. Its A1 governance paths continue to protect only its materialized
consumer inputs. This proves that a consumer repository does not own the
contract.

After extraction, Core will no longer contain the embedded resource path. The
stale Core policy reservation is removed atomically during D, when Core consumes
the standalone Coordinator and the embedded implementation is removed. Removing
it in A3 would weaken protection while the file still physically lives under
Core; removing it in A4' would collapse consumer reconnection into relocatability.

== 9. Provenance and digest

A3 reuses SHA-256 and `operator-plan.json`; it adds no provenance ledger,
signature, IAM, or signing key.

The canonical operator plan gains one bounded object, for example:

[source,json]
----
"agent_operating_contract": {
  "contract_id": "workflow_coordinator.agent_operating_contract",
  "version": 1,
  "resource": "resources/agent_operating_contract_v1.txt",
  "byte_count": 1234,
  "sha256": "<64 lowercase hexadecimal characters>"
}
----

The exact digest is calculated once over the bytes read during preflight and is
compared with the reviewed in-code v1 digest before the value can be used. The
same facts are projected by the proof summary because the proof harness has no
operator plan. `PromptPackage` may expose the same bounded reference for focused
assertions; execution evidence need not duplicate it per Hop.

Existing consumer `governing_inputs` and selected-component provenance retain
their current meanings. The old generic rules were not separately identified:
they were absorbed into task/component digests. After A3, cleaned consumer task
digests still identify consumer task content, while the new object distinctly
identifies the Coordinator contract. The operator-plan schema number need not
move merely for this additive evidence projection, matching current plan
evolution; no plan reader or migrator is introduced.

Post-extraction Coordinator release/code identity is a later B/C decision. A3
does not claim that a resource digest alone identifies an installed Coordinator
release.

== 11. Implementation seams

The likely A3 implementation is deliberately confined to existing seams:

* `scripts/workflow_coordinator/resources/agent_operating_contract_v1.txt` --
  the sole new product resource;
* `scripts/workflow_coordinator/prompt.py` -- identity constants, one immutable
  loaded value, strict `importlib.resources` loader, supported-value assertion,
  mandatory prompt placement, and bounded prompt provenance;
* `scripts/workflow_coordinator/operator.py` -- one pre-Run load, propagation,

  `scripts/workflow_coordinator/slice4.py` -- internal propagation through the

* `tests/unit/workflow_coordinator/test_slice3_vertical.py`,
  `test_operator.py`, `test_proof_harness.py`, and focused affected vertical/

* `tests/integration/workflow_coordinator/test_core_consumer_governance.py` --
  real-bundle coherence plus A3 admission/provenance with zero provider calls;
* `tests/data/workflow_coordinator/slice5b_non_dmc.yaml` and

No new loader module, resource registry, policy field, schema family, or

not need modification in A3.

== 13. Architecture questions

[cols="2,4",options="header"]
|===
|Question |Disposition

|Automatic injection or consumer-selected component?
|Automatic mandatory injection. Selection would leave ownership with consumers.

|Where does the loader live?
|`prompt.py`, which already owns prompt material and digest calculation. One
concrete resource does not justify a module/framework.

|How is version represented?
|One ID, integer `1`, v1 filename, exact prologue, and reviewed digest. No caller
selection or compatibility machinery.

|Digest over text or bytes?
|Exact bytes, calculated once before decoding/injection. Text is strict UTF-8
with no normalization.

|Is it a consumer governing path?
|No. It is a Coordinator-owned resource. While embedded, the already-declared
A1 path remains a physical mutation-protection ceiling, not loader authority.

|Do real policies migrate in A3?
|No. Both already contain the exact target path. Removing the obsolete embedded
path later belongs to D consumer reconnection.

|Must package metadata change now?
|No. Source-package loading is A3; distribution declaration and installed-wheel
proof belong to C.

|May tests inject alternate content?
|They may replace the reader to prove failure or pass the loader-produced
immutable value through internal seams. There is no supported consumer/runtime
override.
|===

There are no unresolved architecture questions requiring maintainer selection.
