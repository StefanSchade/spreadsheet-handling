== S4AC-R1 -- uncertain dispatch after execution

=== Failure and correction mechanisms

The former general exception handler in `run_real_one_hop()` deleted
`dispatch.json` after any exception. An exception after `adapter.execute()`
returned -- including Git observation, evidence, reduction, or checkpoint work --
could therefore erase the durable authority that an agent invocation had been
dispatched after it committed.

`ExecutionNotStartedError` is the narrow provider-neutral proof carrier for the
two local vertical steps that precede the execution port: Git preflight and prompt
assembly. `run_real_one_hop()` deletes the marker only for that carrier or for
`CodexCliError`, whose adapter definition is limited to invalid timeout,
unsupported single-contract request, or executable launch failure before `Popen`
succeeds.

Every other `Exception` after marker creation is routed through the existing
`recover_uncertain_dispatch()` flow. It retains the marker, observes Git where
possible, charges one uncertain Hop, and writes `reconcile_required`
run/checkpoint state. If secondary recovery fails, it cannot reach cleanup; the
retained marker remains the durable no-replay authority. An unclassified
adapter-side exception is deliberately in this class: absence of an outcome does
not prove execution did not start.

Pre-execution cleanup is safe because the explicit carriers prove failure before
`AgentExecutionPort.execute()` can be entered or before a process can launch.
The marker is then removed, the Hop is unconsumed, and no reconcile state exists.

== S4AC-R2 -- offline strict-schema anchor

Disposition:: *single-value enum replacement.* Both transport-envelope
`schema_version` nodes now emit `{"type":"integer","enum":[1]}`; Python
semantic validation still independently requires schema version `1`.

Primary authority consulted:: OpenAI, _Structured model outputs_, current
Structured Outputs guide,
https://developers.openai.com/api/docs/guides/structured-outputs . Its
"Supported schemas" section explicitly lists *Enum* among supported types, and
its required-fields example uses typed `enum` schema properties. The guide states
that unsupported schemas supplied with `strict: true` return an error.

The primary guide did not provide an equally explicit supported-keyword rule for
`const`; its indirect mention in a size limit was not treated as support. The
fixed projection therefore uses documented typed `enum`. The checker removes
`const` from its accepted subset, and the exact emitted schema passes
`test_exact_codex_projection_conforms_to_supported_openai_strict_subset`. A
separate test asserts the same enum form at both envelope nodes, so Level-1
conformance is independently anchored rather than sharing a `const` assumption.
