`InterpretedEnrichLookupProvenance` (`lookup_name`, `payload_keys`,

duplicated parsing across the two slices, and its field set is stable. No
correction required.*

== 6. FK strict-reader verdict (Area 4) [[F-CORR-1]]

=== 6.1 The lenient/strict split itself

Independently confirmed: `derived_helper_columns_by_sheet`
(`fk_helpers/policy.py:159-179`) is lenient — `if not isinstance(sheet_entry,
dict): continue` and a further `if isinstance(entry, dict)` filter silently
drop malformed shapes rather than raising. It has five confirmed call sites
beyond DCP: `domain/transformations/helpers.py:223`,
`fk_helpers/drop.py:52`, `domain/column_roles/resolver.py:260`, and
`domain/validations/fk_helpers.py:302,358,479` (two call sites in one file,
as the artifact states). Retrofitting fail-clear behavior onto this function
would touch reorder/drop/column-role-resolution/validation behavior at once
— correctly rejected. DCP's own fail-clear contract is directly test-pinned
(`test_malformed_helper_columns_entry_raises_clear_value_error`,
`test_derived_column_policy.py:443-448`, asserting
`helper_columns[0] must be a mapping`).

Two owner-local readers for two genuinely distinct contracts (return-partial
vs. raise-on-malformed) is the right choice over a `strict: bool` flag on
the existing function: the two contracts differ in control flow, not merely
in a parameter value, and the existing package already uses named,
single-purpose validator functions rather than mode-flagged ones
(`_validated_symmetric_on`/`_validated_single_key` in
`derived_column_policy.py`, soon to move; `_ResolvedKeys`'s explicit `mode`
discriminant rather than a boolean, in `enrich_lookup/policy.py`). A boolean
flag would also force every one of the five existing lenient callers to
carry dead-branch risk for a code path they never exercise.

*Verdict: two owner-local readers is the correct choice; recommend exactly
this over a strictness flag. No correction required for this half of Area
4.*

=== 6.2 Signature inconsistency — required correction

The artifact's proposed new function is
`validated_helper_columns_by_sheet(frames, *, frame_name) -> tuple[dict,
...]` (Section 4) — taking the *entire* `frames` mapping and (implicitly)
re-deriving `_meta.derived.sheets[frame_name].helper_columns` itself. This
is inconsistent with three things this review independently traced:

* The function it replaces, `_validated_fk_helper_names(raw_helper_columns,
  *, frame_name)` (`derived_column_policy.py:286-303`), takes the
  *already-extracted* sub-value, not `frames`.
* Its own Lookup-side sibling in the same Section 4,
  `interpret_written_enrich_lookup_provenance(record, *, frame_name)`,
  correctly takes the already-extracted `record`, not `frames` — the two
  new facade functions the artifact proposes are internally inconsistent
  with each other on this exact point.
* The shared container-shape validation that currently sits *above* both
  `_validated_fk_helper_names` and `_validated_enrich_spec` —
  `_safe_sheet_meta` (raises `"_meta.derived must be a mapping"` /
  `"_meta.derived.sheets must be a mapping"`) and
  `_resolve_derived_identity`'s own `isinstance(derived_meta, Mapping)`
  check (raises `"_meta.derived.sheets[<frame>] must be a mapping"`,
  directly test-pinned by
  `test_malformed_sheet_level_provenance_raises_clear_value_error` and
  `test_malformed_derived_container_raises_clear_value_error`) — is neither
  named in Section 17's Slice-1 removal list nor otherwise proposed to move.
  It stays in `derived_column_policy.py`, shared for both the FK and Lookup
  sub-keys of the same `_meta.derived.sheets[frame_name]` container.

If `validated_helper_columns_by_sheet` is implemented literally as
`(frames, *, frame_name)`, it must independently re-walk and re-validate
that same shared container, which either (a) duplicates
`_safe_sheet_meta`/`_resolve_derived_identity`'s generic path-validation
logic a second time with a real risk of wording or precedence drift from
the currently test-pinned messages, or (b) skips that validation on the FK
path specifically, turning a clean `ValueError` into an unhandled
`AttributeError`/`TypeError` for a malformed `_meta.derived`/`.sheets`
container reached only through the FK reader. Either outcome breaks the
"byte-identical error paths" / "every `ValueError` message/path" claim
Section 8's table and Section 17 make for Slice 1 specifically. This is
exactly the "mapping validation order" hazard the review brief asks
reviewers to check independently for, and it is concrete, not speculative:
the inconsistency is directly visible by comparing Section 4's own two
proposed signatures against each other and against the retained call site.

*Required correction (localized, does not change file scope or strategy):*
`validated_helper_columns_by_sheet` must take the already-extracted
per-sheet raw value (mirroring `_validated_fk_helper_names`'s current
signature and its own Lookup-side sibling's `record`-taking shape), not the
full `frames` mapping. `_safe_sheet_meta`/`_resolve_derived_identity` remain
the single owners of the shared `_meta.derived`/`_meta.derived.sheets[frame]`
container-shape validation, unchanged, exactly as Section 17's file list
already (correctly) implies by omission.

*Verdict: MATERIAL, narrow, localized. Does not require adding a file to
Slice 1's scope or changing its strategy — only pinning the exact parameter
shape before implementation begins. Recorded here; Slice 1 may proceed on
this corrected basis (option B, "may begin once recorded").*

== 9. Formula-mode semantic verdict (Area 7)

Independently reasoned from first principles about what
`warn_on_mismatch`/`fail_on_mismatch` mean for a formula-mode helper cell.
Confirmed directly: the Domain layer never holds an evaluated scalar for a
formula-mode cell (`_build_formula_enrichment`,
`enrich_lookup/operation.py:451-472`, stores a `LookupFormulaSpec` object,
never a computed value; no backend recalculates during pipeline execution).
Candidate (C) (compare against a cached/evaluated scalar) is therefore
correctly rejected as architecturally unsupportable, not merely
inconvenient — there is no pipeline stage where such a value would exist.
Candidate (B) (skip mismatch checking for formula-mode cells) is correctly
rejected: it would make `fail_on_mismatch` a silent no-op guarantee for
every formula-mode helper column, which is a worse contract than an
explicit structural check. Candidate (D) (reject the combination as
unsupported) is correctly rejected: nothing about the combination is
inherently invalid — `helper_value_mode="formula"` and
`policy="fail_on_mismatch"` are two independently documented, registered
features whose composition should be well-defined, not refused merely
because it was never correctly implemented.

Candidate (A/E), structural-intent comparison — does the cell's declared
`(lookup_sheet, source_key_column, lookup_key_column, lookup_value_column)`
still point at the relationship provenance declares — is the correct
semantic analogue of the values-mode contract for this representation: it
answers "does this cell still faithfully encode the declared lookup
relationship," which is the only question the Domain layer can answer about
a formula cell, and is structurally parallel to what values-mode answers
("does this cell still hold the value the declared relationship would
produce"). This is not a redefinition of "mismatch" into two unrelated
guarantees; it is the same guarantee ("this helper cell still reflects the
declared enrichment"), applied through the two different representations
`enrich_lookup` itself already supports.

*Verdict: structural-intent comparison is the correct semantic analogue,
not an inappropriate overload. No correction required to the general
approach.* (The 4-tuple's completeness and the multi-key interaction are
separate, narrower questions — <<F-CORR-3>>, <<F-CORR-2>>.)

== 10. LookupFormulaSpec sufficiency verdict (Area 8) [[F-CORR-3]]

`core/formulas.py::LookupFormulaSpec` (lines 17-32) declares exactly five
fields: `source_key_column`, `lookup_sheet`, `lookup_key_column`,
`lookup_value_column`, and `missing` (default `""`). The artifact's 4-tuple
omits `missing`. Traced whether this omission is currently exploitable:
`enrich_lookup` (`operation.py:164-168`) raises before formula-building
whenever `helper_value_mode="formula"` is combined with `missing="fail"`
("`missing='fail'` cannot be enforced with `helper_value_mode='formula'`");
`_build_formula_enrichment` (lines 451-472) then hardcodes `missing=""` on
every `LookupFormulaSpec` it constructs, ignoring its own `missing_mode`
parameter. The practical result: today, every formula-mode `LookupFormulaSpec`
ever produced by the one existing producer carries the identical literal
`missing=""`. The 4-tuple's omission therefore has *zero currently reachable
failure case* — there is no live divergent `missing` value for the proposed
comparison to miss.

This does not make the omission a non-issue, only a currently-dormant one.
Section 6.2 of the artifact explicitly dispositions the parallel gap for
values-mode missing-key semantics ("DCP structurally cannot know which
[missing] contract was in force... this is the only sound option given that
gap, and is independently judged correct"); no equivalent explicit
disposition exists for the formula-mode 4-tuple's omission of `missing`.

*Verdict: the 4-tuple is INCOMPLETE relative to `LookupFormulaSpec`'s full
field set, but the gap is currently inert given `_build_formula_enrichment`'s
own hardcoded `missing=""`. Required correction before Slice 2: add one
explicit disposition sentence, symmetric with Section 6.2's discipline —
either state the 4-tuple is deliberately partial because `missing` is
currently a known constant for every reachable formula-mode cell (and note
what happens if that producer invariant ever changes), or extend the
comparison to a 5-tuple against the known-constant expected value. MINOR in
isolation; recorded as a required Slice-2 correction for documentation
completeness, not a blocker for the general approach (<<9>> stands).*

== 11. Multi-key formula-mode verdict (Area 9) [[F-CORR-2]]

Independently and empirically reproduced, through the installed package
(read-only; no source/test file touched), a probe not present in the
artifact or either prior review:

[source,text]
----
enrich_lookup(frames, source="matrix", lookup="stories", output="matrix_view",
              keys=["id", "part"], helpers={"fields": ["title"]},
              helper_value_mode="formula", missing="empty")
  -> succeeds, no ValueError
  -> provenance: {"lookup": "stories", "on": ["id", "part"],
                  "helper_columns": ["title"]}
  -> row (id=s1, part=p1) and row (id=s1, part=p2) BOTH receive the
     IDENTICAL LookupFormulaSpec(source_key_column='id',
     lookup_sheet='stories', lookup_key_column='id',
     lookup_value_column='title', missing='') -- `part` is silently
     dropped from the formula's identity entirely.
----

This independently confirms all four of the review brief's factual
questions: (1) formula mode can currently be invoked with multiple keys;
(2) that combination is accepted by policy validation with no error; (3) it
silently ignores every key after index 0
(`_build_formula_enrichment`, `source_keys[0]`/`lookup_keys[0]`,
`operation.py:461-462`); (4) this is already a live, currently-shippable
defect independent of F-002 — the resulting formula, rendered into a real
workbook, would resolve `id` alone via XLOOKUP, which is ambiguous/wrong
whenever `id` is not independently unique without `part`, silently
misrepresenting the declared two-key relationship.

The fifth, decisive question: does the proposed structural validator
*legitimize* this. Yes, confirmed by direct construction: the design's
comparison is `(lookup_sheet, source_key_column, lookup_key_column,
lookup_value_column)` from the cell against `(lookup_name, payload_keys[0],
lookup_keys[0], helper_col)` from interpreted provenance (Section 5). Both
sides independently truncate to index 0 using the *same* logic
`_build_formula_enrichment` already uses, so for the reproduced case above
the two tuples are equal and the validator would report **no finding**
under `warn_on_mismatch` and **no raise** under `fail_on_mismatch` — for a
cell that does not, in fact, faithfully encode the declared multi-key
relationship. This is materially different from "a pre-existing
characteristic F-002 leaves untouched," which is how the artifact's own
"Open question" paragraph (end of Section 5) frames it: leaving the
production defect alone is fine and correctly out of scope, but *adding a
validator that reports the resulting broken cells as structurally correct*
is a new, Slice-2-introduced false-confidence signal, reachable through two
ordinary registered/YAML surfaces, that does not exist today (today the
combination is simply never checked by any registered validation path).

Confirmed further: Section 12.2's own formula-mode test list has no
multi-key case at all — the gap would ship with zero test coverage
detecting it, the same shape of risk FIND-C1-001 itself was.

*Disposition: (D), a distinct concrete disposition combining elements of A
and C.* Leave `_build_formula_enrichment`'s underlying single-key truncation
out of F-002's scope (disposition A is correct for *that* production
defect — fixing formula generation itself is a different, larger,
`enrich_lookup`-write-path change, not a DCP mismatch-checking concern).
But the new structural validator must not silently apply index-0 comparison
when `len(payload_keys) > 1` (equivalently `len(lookup_keys) > 1`): that
combination must be treated as `unverifiable_enrich_lookup` (or an
equivalent explicit "cannot structurally verify a multi-key formula
relationship" disposition) rather than compared and passed. An explicit
multi-key + formula-mode test (asserting the *new*, corrected disposition,
not zero findings) must be added to Section 12.2.

*Verdict: MATERIAL. Must be corrected in the Slice-2 design record before
Slice 2 implementation is authorized. Does not affect Slice 1 (Slice 1
never reaches cell values or formula comparison) and does not require
reopening the general structural-comparison approach validated in <<9>>.*

== 12. Per-cell mode-detection verdict (Area 10)

`isinstance(cell_value, LookupFormulaSpec)` per cell, rather than a new
`helper_value_mode` provenance field, is sound: it uses information the
cell already unambiguously carries, and it correctly does not add metadata
whose only purpose would be convenience. Considered the "does this hide
malformed representation" risk directly: a formula cell manually replaced
with a plain scalar is, under the proposed rule, evaluated as a values-mode
edit against the canonical scalar — which is the semantically correct
reading (a user who overwrites a live formula with a literal value has made
a content edit, and DCP's job is to check content against canonical, not to
police representation-format purity). DCP has, and needs, no way to know
the cell's *original* mode from provenance alone, and does not need one for
this contract: the design deliberately validates content correctness, not
representation-mode stability, a scope boundary it already states
explicitly and consistently (no `helper_value_mode` field, matching Section
6.2's parallel scope discipline for `missing`).

*Verdict: acceptable, correctly scoped. Runtime-type dispatch does not
change the meaning of an edit here — it correctly re-derives, from the only
information available, what kind of edit occurred. No correction required.*

== 13. Finding-vocabulary verdict (Area 11) [[F-CORR-4]]

=== 13.1 `derived_formula_mismatch` as a new rule type

Compared the four options directly. `derived_column_findings` already
carries multiple distinct, coexisting `rule_type` strings for distinct
situations under one findings-frame contract
(`derived_value_mismatch`, `unverifiable_enrich_lookup`,
`missing_lookup_frame`, `fk_deletion_unauthorized` — the last of these
itself a relatively recent addition, confirmed by the deletion-authority
sequence summary, Slice 5/FIND-S5-01). Adding another distinct string for a
genuinely distinct guarantee (content divergence vs. formula-intent
divergence — different message content, different underlying check, no
shared meaning to conflate) matches this repository's own established
practice for this exact findings surface, rather than widening an
otherwise-closed vocabulary. Option B (reuse `derived_value_mismatch` with a
different message) would conflate two guarantees under one label for no
compatibility benefit, since (per <<13.2>>) no consumer dependency on the

structurally-incorrect formula is not "cannot verify," it *is* verified —
and found wrong. Grep confirms (Section 2 above) no canonical documentation
enumerates `rule_type` strings as a closed registry, so this is not a
registry/schema addition requiring separate authorization.

*Verdict: OPTION A (new `derived_formula_mismatch`) is the correct choice,
matching established local precedent. No correction required to the
choice itself.*

== 14. Duplicate/missing-key verdict (Area 13, 14, 15)

=== 14.1 Duplicate-key semantics

Independently confirmed the asymmetry driving this decision:
`_canonical_value_map` (`derived_column_policy.py:776-790`,
`if key in canonical: continue  # first occurrence wins`) versus
`_check_duplicate_lookup_keys` (`enrich_lookup/operation.py:227-233`,
raises `ValueError` on any duplicate at enrichment time). Reusing the
fail-closed pattern DCP already applies to missing key *columns*
(`_check_enrich_lookup_values`'s `missing_payload`/`missing_lookup` branch)
is the correct extension: a lookup frame that has grown duplicate keys
*since* the enrichment-time gate ran cannot be soundly used to certify any
value as canonical, and "first occurrence wins" is exactly the kind of
DCP-invented tie-break the DMC's composite/primitive contract forbids a
composite from inventing on a dependency's behalf. `unverifiable_enrich_lookup`
is the correct existing category — a duplicate lookup table is neither a
values mismatch nor a malformed record; it is exactly the "cannot certify a
comparison from current data" situation that category already exists for.

*Verdict: correct disposition. No correction required to the decision
itself.*

=== 14.2 Reuse mechanism

`_check_duplicate_lookup_keys` is private to `operation.py`, not exported.
Confirmed the established convention for exactly this situation already
exists in the same package: `operation.py` already imports six
underscore-prefixed private names directly from `.policy`
(`_FORMULA_MODES`, `_ResolvedKeys`, `_resolve_allowed`, `_resolve_fields`,
`_resolve_join_keys`, `_resolve_missing`, `_resolve_order`,
`_resolve_value_mode` — `operation.py:14-24`). Same-package private imports
across `enrich_lookup`'s own submodules are the codebase's own established
idiom, not a boundary violation (the architecture guard only blocks
cross-family imports; `mismatch.py` and `operation.py` are the same
family).

*Recommended smallest form (MINOR, procedural, non-blocking):* extract the
boolean predicate `lookup_df.duplicated(subset=join_keys, keep=False).any()`
into a small shared, non-raising primitive (e.g. in `policy.py`, alongside
the other shared private helpers), with `operation.py`'s existing raising
check and the new `mismatch.py`'s non-raising check both calling it —
rather than duplicating the boolean expression or reaching into
`operation.py`'s raising function directly. This avoids inventing a new
generic validator while keeping one source of truth for the duplicate-key
test. Not required before Slice 1; recommended before Slice 2.

=== 14.3 Missing-key semantics

Independently re-verified: `_write_provenance`
(`enrich_lookup/operation.py:495-565`) never records the `missing` mode
used at enrichment time, so DCP structurally cannot reconstruct which
contract (`"fail"` vs `"empty"`) applied to a given unresolved payload row.
The alternatives the review brief poses (mark as unverifiable; compare
against blank only if cell evidence supports it) were independently
considered: marking every unresolved row as unverifiable would produce a
finding on ordinary, correctly-configured `missing="empty"` pipelines with
no way to distinguish that from a genuine problem, and "compare against
blank only if cell type/formula gives evidence" reintroduces exactly the
kind of undocumented heuristic inference the DMC's configuration guidance
warns against (`05_domain_maintainer_contract.adoc` Section 4, "avoid
payload-shape interpretation heuristics unless an accepted producer owns
them"). Declining to check is the only option that neither guesses nor
manufactures false signal from an information gap that is real and, per
Section 6.2's own reasoning, out of scope to close by adding metadata.

*Verdict: correct, no change. No correction required.*

== 15. Mismatch-report/finding ownership verdict (Areas 16, 17, 18)

`LookupMismatchReport`'s four fields (`missing_lookup_frame`,
`unverifiable_reason`, `value_mismatches`, `formula_mismatches`) were
checked against the composite/primitive boundary directly.

`missing_lookup_frame: bool` is a fact `evaluate_lookup_mismatches` must
determine as an unavoidable first step of using the `lookup_frames`
parameter it is handed (it cannot build a canonical map or compare rows
without first checking whether `interpreted.lookup_name` is present in
`lookup_frames`) — the same class of parameter-presence fact the function
already reports for missing key *columns*. `evaluate_lookup_mismatches`
does not construct or own the `lookup_frames` mapping itself (DCP still
composes it from the pipeline's `Frames`, unchanged); Lookup is only
reporting a presence fact about its own declared identity within input DCP
already assembled. This is coherent, not composite-composition leaking
into Lookup.

`unverifiable_reason: str | None` as a joined string, rather than a
structured reason enum: acceptable given that `_check_enrich_lookup_values`
already assembles an unjoined `reasons: list[str]` and joins it today
(`derived_column_policy.py:594-614`) — the design does not introduce new
message-construction responsibility into Lookup, it relocates an existing
one that already lived at exactly this seam. A structured-reasons proposal
(returning `tuple[str, ...]` unjoined, leaving the join/wrap formatting
fully to DCP) would be marginally cleaner but is optional, not required —
recommended as a light, non-blocking simplification for Slice 2, not a
finding.

Separately keeping `value_mismatches`/`formula_mismatches` as two mappings
(rather than one, tagged) correctly preserves DCP's ability to build two
different `rule_type`s from two different report fields, consistent with
Section 9.1's compatibility promise to keep `derived_value_mismatch` and
`derived_formula_mismatch` distinct.

Confirmed `rule_type` strings themselves (`unverifiable_enrich_lookup`,
`derived_value_mismatch`, `derived_formula_mismatch`) are never proposed to
appear inside `enrich_lookup`'s own code — `evaluate_lookup_mismatches`
returns only structured, Lookup-owned semantic categories; Section 10 keeps
100% of `rule_type` selection, severity assignment, and
raise/collect behavior inside DCP, correctly matching the composite/
primitive split independently confirmed in <<3>>.

*Verdict: acceptable as designed. No correction required for
`missing_lookup_frame` placement or `unverifiable_reason`'s shape. Finding
construction/severity ownership correctly stays 100% with DCP.*
