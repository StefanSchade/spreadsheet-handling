== 5. IMPORTANT-1 delta -- public Core / private WFC access

Disposition:: *Closed.*

The split is now explicit in both artifacts: `make setup` / `deps-dev` stays
ordinary public Core setup and must not require private WFC access; `wfc-setup`
is an opt-in target carrying its own tooling stamp invalidated by a changed pin;
consumer tests skip deterministically and visibly when the distribution is
absent and never substitute a sibling checkout; CI always runs `wfc-setup` and
therefore never skips them; every SSH-based WFC install path sets
`GIT_SSH_COMMAND='ssh -o BatchMode=yes'` and `GIT_TERMINAL_PROMPT=0`; and CI
adds a dedicated read-only deploy key with strict known-host verification.

Consistency with the current Makefile and test architecture was checked
directly:

* The opt-in tooling-stamp shape is precedent-following, not new machinery.
  `memory-setup`/`$(PROJECT_MEMORY_STAMP)` (`Makefile:274-281`) and
  `domain-contracts-setup`/`$(DOMAIN_CONTRACTS_STAMP)` (`Makefile:365-375`) are
  already order-only dependants of `$(DEV_STAMP)` and are deliberately off the
  `deps-dev` path.
* Normal non-WFC commands remain usable. `test`, `test-*`, `lint`, `format`,
  `coverage` and `source-style-guards` depend on `deps-dev` only. Because the
  requirement file now hangs on the WFC stamp rather than on `DEV_INPUTS`, no
  public Core command acquires a private-repository dependency.
* Skip logic cannot hide a broken or mis-pinned WFC while WFC *is* installed.
  The only stated skip condition is absence of the distribution; an editable
  sibling install is present and importable, so the guard runs and fails closed
  on `dir_info` instead of `vcs_info`. The plan states the no-sibling-fallback
  rule explicitly.
* CI can distinguish "missing" from "present but wrong". A missing or
  unresolvable pin fails the `wfc-setup` install step and therefore the job; a
  resolvable but wrong distribution installs and then fails the identity guard.
  Because installation cannot silently succeed without installing, the plan's
  "CI therefore never skips them" is a sound inference rather than a claim
  needing separate enforcement. See INFO-1.
* `BatchMode`/no-terminal-prompt coverage is stated as applying to *every*
  SSH-based WFC install path, and it is applied consistently in the Makefile
  target, the CI job, and the section 13.1 fresh-environment command.

One granularity point is left unstated and is recorded as MINOR-2, not as a
reopening: the plan does not say whether the guard's five structural properties
also skip when the distribution is absent.

=== 11.3 MINOR

*MINOR-1 -- "committed" is ambiguous about how the seed reads Core content.*

Observation:: Readiness section 7 seeds the disposable repository "from the real
committed Core consumer bundle files ... and the committed r3
policies/profiles/WorkItems/tasks", and FTR 13.6 repeats "using the committed r3
policy/profile/WorkItem/task/component content". Read as `git show HEAD:<path>`
against live Core, the r3 content does not exist until the single D commit
exists, so the focused consumer test cannot pass before that commit -- a
content-level instance of the ordering coupling whose stop condition this
correction deleted. Read as an ordinary read-only file read of the tracked work
tree, there is no coupling at all.
Consequence:: An implementer taking the first reading finds the focused
acceptance failing before the D commit with no stop condition to consult, and
may either invert validation order silently or weaken the `r3` assertion.
Smallest bounded correction:: One sentence in readiness section 7 and FTR 13.6:
the seed is built by reading Core's tracked working-tree files read-only, so
consumer acceptance does not depend on whether the D commit already exists.

*MINOR-2 -- Skip granularity for the anti-regression guard is unstated.*

Observation:: Readiness section 4 says "those two consumer tests shall skip
deterministically with a visible reason" when WFC is absent. Two of the guard's
seven section 8 properties need the installed distribution; the other five --
absent `scripts/workflow_coordinator/`, absent removed paths, AST import and
`sys.path` repair checks, no A1 reservation in either policy, no Core-owned
`agent_operating_contract_v1.txt` -- are purely structural.
Consequence:: A file-level skip would silently stop enforcing the five
structural anti-regression properties for any local contributor without WFC.
Because the single CI workflow triggers only on `push` to `main`, a re-coupling
regression would then reach `main` before detection.
Smallest bounded correction:: State that the skip is per assertion, not per
file: only the installed-distribution properties skip when the distribution is
absent; the structural properties always run.

*MINOR-3 -- The `ftrs.json` `summary` field stays stale under a superseded row.*

Observation:: The bounded update changes `status`, `current_relevance` and
`source_path` only. The row's `summary` will still begin "Open V1 authority with
Slices 1-5B implemented and maintainer-accepted", contradicting `superseded` in
the same row. Both precedent wont_do rows rewrite `summary` to carry an explicit
"Superseded: ..." clause, and `summary` is the field the rendered context report
surfaces.
Consequence:: A canonical row that is authoritative in its lifecycle fields but
self-contradictory in the field most likely to be read.
Smallest bounded correction:: Extend the same single-row update by one field,
`summary`, in the registry's existing "Superseded: ..." form. Still one row and
still not a broad Project Memory refresh.

*MINOR-4 -- One atomic D commit versus the documented curation-commit rule.*

Observation:: `docs/ai_info/project_memory_workflow.adoc:205` states "Commit
curated changes separately from feature work." The correction places the
canonical `ftrs.json` row inside the single atomic D commit and lists "update
the one canonical FTR row" in section 12's indivisible ownership boundary,
without acknowledging that rule.
Consequence:: D as specified is defensible -- a `source_path` repair that
accompanies its own `git mv` is not a curation pass, and splitting it would
create a commit whose registry row points at a nonexistent file -- but the plan
asserts indivisibility where a documented rule says otherwise, and leaves the
implementer to rediscover the conflict.
Smallest bounded correction:: One sentence in readiness section 12 recording
that the mechanical lifecycle and `source_path` repair rides with the archive
move precisely because it is not a curation pass, and that the deferred
evidence-backed refresh remains a separate commit.
