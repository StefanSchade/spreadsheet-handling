== Eligibility / Missing review

*Accepted.*

* "Missing is not a value" is the strongest available authority and
  directly implies that a Missing carrier cannot carry identity.
* Most maintained key-set builders already exclude Missing targets
  (reference `foreign_key` target set, graph node key set, FK validator
  target sets for `None`/NaN). The outliers are mechanics: `core/fk.py:_norm_id`
  uses `pd.isna` rather than the Missing predicate, so `""` stays a key;
  pandas `merge`/`duplicated` match NaN/None by dtype mechanics; Lookup
  mismatch builds `(None,)` canonical keys.
* The rule decides *participation*, not row validity. Source-side skipping
  (`allow_empty`, FK validation), `primary_key` presence findings, and graph
  Missing-endpoint findings all remain caller policy. The assessment does not
  convert a role-specific primary-key constraint into a universal row rule.
* Composite: any Missing component makes the key ineligible. This is
  consistent with `foreign_key` ("Foreign key contains empty key part") and
  graph endpoints (any empty component is a finding). It is *not* consistent
  with generic tuple uniqueness over optional qualifier columns -- see F2.
* The assessment answers the accepted Cycle-3 maintainer question ("Missing
  target IDs: invalid, excluded, or duplicate identity?") with "excluded from
  identity; no FK-side invalidity finding; `primary_key` remains the opt-in
  presence surface". That is a legitimate Cycle-0 decision but must cite the
  question it answers (F5).

== Equality / category review

*Rule shape accepted; value basis requires correction (F1).*

Verified:

* Boolean and Number are distinct classifier categories. Python `True == 1`
  and `hash(True) == hash(1)`; category tagging is therefore necessary, not
  cosmetic. Current Lookup merge and pandas `duplicated` collapse `True`/`1`
  (reproduced); FK/reference/graph distinguish them only by accident of
  `str()` (`"True"` vs `"1"`).
* Date and DateTime are distinct categories; `date(2020,1,1) ==
  datetime(2020,1,1)` is already `False` in Python.
* "Number is one category" *does* justify `1 == 1.0 == numpy.int64(1)` as a
  relation-key consequence: the classifier deliberately refuses an
  Integer/Float split and classifies NumPy variants without narrowing, so
  carrier type cannot be identity.
* String `"1"` vs Number `1`: category boundary; no parsing. Accepted.

Not established by authority, and not safe to leave implicit:

[cols="3,2,2,3",options="header"]
|===
| Pair (same category) | Native `==` | `hash` equal | Exact value

| `numpy.float32(0.1)` / `0.1`
| `True` (NumPy 2 weak-scalar promotion)
| `False`
| unequal (`.item()` is `0.10000000149011612`)

| `numpy.int64(2**53+1)` / `numpy.float64(2**53)`
| `True` (int64 promoted to float64)
| `False`
| unequal

| `datetime64[ns]` 2020-01-01 / `datetime(2020,1,1)`
| `False`
| `True`
| equal instant

| `datetime64[ns]` / `pd.Timestamp`; `pd.Timestamp` / `datetime`
| `True`; `True`
| `True`
| equal -- native equality is *non-transitive* across the three carriers

| aware UTC 12:00 / aware +01:00 13:00
| `True`
| `True`
| equal instant -- a timezone semantic, not "no timezone policy"
|===

Consequences:

* "Same value within that category" is new relation-key semantics. For
  Number the minimal, authority-consistent basis is the *exact mathematical
  value of the carrier* (NumPy scalars compared by their exact native value,
  not by NumPy promotion). No broader Scalar algebra is needed.
* Every consumer uses hash-based mechanics (dicts, sets, `Counter`,
  `unique`, `merge`). The owner's equality must therefore be an equivalence
  relation consistent with hashing. In practice that means an owner-provided
  category-tagged hashable identity (the assessment's "opaque relation-key
  value" option); a pairwise-only API would force quadratic consumers or
  invite raw-carrier hashing that reintroduces `True == 1`.
* *DateTime is the one category that needs a stated basis.* Any choice
  (instant equality for aware values, exact wall-clock for naive,
  aware != naive, full precision) is policy-bearing. The assessment's
  statement that DateTime compares "within existing category value semantics
  without a new timezone or precision policy" is not achievable because no
  such semantics exist and native carrier equality is non-transitive.
  Date is unproblematic (`datetime.date` only).

This is not a request for a universal Scalar equality model: the correction
is confined to relation-key identity and two categories.

== Whitespace review

*Accepted.* Exact String equality is the minimal consequence of existing
authority:

* scalar authority: String is native `str`, content never reinterpreted;
  only `""` is Missing;
* XLSX/ODS parsers stringify payload without trimming; their `.strip()` uses
  are table-extent/header detection;
* where the product trims, trimming is explicit opt-in configuration
  (`strip: false` defaults in compact multiaxis and the cell codec), and the
  crosstab importer contract forbids trimming;
* four of five current relation paths (FK producer, reference, graph, Lookup
  merge) are already exact; only the FK validator and Lookup mismatch
  `_norm` trim. `git log -S` traces the trim to the FK validation-layer
  refactor with no recorded rationale, and no test protects trimming.

Changing the validator's `.strip()` is therefore a correction of an
undocumented outlier, not the removal of a product contract. Whitespace-only
non-empty Strings are eligible keys in Domain state (W2 records a sink-side
roundtrip caveat).

== pandas / Lookup review

*Accepted as feasible without a larger rewrite.*

Reproduced current Lookup behavior (values mode, `missing="empty"`):
`1`/`"1"` raises pandas `ValueError` with naturally inferred dtypes but
silently misses with object dtype; `True`/`1`, `""`/`""`, and `None`/`None`
all *resolve*. The boundary proposed by the assessment is sound:

* temporary internal join columns holding owner-derived identities (object
  dtype on both sides) remove dtype errors, preserve original key carriers,
  and allow Missing target rows to be excluded before merging;
* duplicate checking can run over the same identities;
* no DataFrame normalization framework is required.

`_check_unmatched_rows` infers "unmatched" from null helper values and thus
conflates "matched with a Missing payload" with "unmatched" (W4). Slice 3
must not entrench that conflation through its new join path, but fixing it is
outside this work.

== Findings

Counts: BLOCKING 0, IMPORTANT 2, MINOR 4, INFO/WATCH 4.

=== F1 -- IMPORTANT -- Within-category equality basis is new semantics and native equality is non-transitive

Observation:: The assessment says each component compares by "the same value
within that category" and that DateTime uses "existing category value
semantics" with no timezone/precision policy. No authority defines
within-category value equality.
Evidence:: Probe table in the Equality section: NumPy weak-scalar promotion
and int64/float64 promotion make native `==` disagree with `hash`; DateTime
carriers are non-transitive (`datetime64[ns] == Timestamp == datetime` but
`datetime64[ns] != datetime`); aware values compare by instant.
Risk:: A Slice 1 implementation using native `==` or raw-carrier hashing
reproduces a producer/validator disagreement between pairwise comparison and
map/set/merge lookup -- exactly the defect class under correction.
Action:: Amend the contract: (a) relation-key equality is an equivalence
relation consistent with the hashing used by consumers; (b) Number compares
by exact numeric value of the carrier, not by NumPy promotion; (c) state one
explicit DateTime basis (or route every DateTime comparison the basis does not
cover to the explicit incompatible outcome). Add the corresponding owner
tests. Do not generalize beyond relation keys.

=== F2 -- IMPORTANT -- Tuple-uniqueness scope is inconsistent; graph unique-edge delegation drops findings

Observation:: Graph `unique_edges` is delegated to relation-key identity
(`_key_token` DELETE), while reference `unique`/`unique_reference` are
explicitly excluded. `unique_columns` is user-configurable and may include
non-key qualifier columns; the graph FTR models unique edges on
`unique_reference` ("relation tuples are unique").
Evidence:: Edges `(a, b, "")` twice with `unique_columns: [s, t, q]`: today
both `graph_unique_edge` and `unique_reference` report duplicates
(reproduced). Under componentwise Missing-ineligibility the graph findings
disappear while `unique_reference` keeps them.
Risk:: Silent loss of duplicate-edge findings, and a new intra-validator
divergence introduced by the correction itself.
Action:: Give graph unique-edge identity the same disposition as
`unique_reference` (keep current tuple identity; named follow-up for generic
tuple-uniqueness identity), keep graph *endpoint* checks delegated; and
record the post-Slice-3 `foreign_key` vs `unique_reference` divergence on the
same columns as that follow-up's evidence. Alternatively bring both into
scope with an explicit Missing-component uniqueness rule -- but not one in
and one out.

=== F3 -- MINOR -- Release note deferred past the behavior-changing slices

Observation:: Slice 4 carries the release note after Slices 2 and 3 change
registered-step behavior. `docs/ai_info/review_instructions.adoc` makes
release notes owned by the implementing change.
Action:: Slices 2 and 3 each add their release-note bullets under the active
unreleased section; Slice 4 remains canonical documentation (and may
consolidate wording).

=== F4 -- MINOR -- Consumer inventory incomplete

Observation:: The registered `validate` step (`pipeline/steps.py`) consumes
`check_duplicate_ids` and `check_unresolvable_fks`; maintained demo pipelines
use `validate` (five occurrences, including `mode_duplicate_ids: fail` and
`mode_missing_fk: fail`) and `add_fk_helpers` (four). The
policy-independent fallback path of `check_duplicate_ids` is not named as
adopting the rule.
Action:: Name these surfaces in the assessment and add a maintained-consumer
acceptance probe to Slice 2.

=== F5 -- MINOR -- Compatibility evidence precision

Observation:: (a) `True` vs `1` Lookup behavior change is not listed; (b)
the `[1.0, 1]` duplicate claim holds only after float64 coercion; (c) the
Missing decision does not cite the accepted Cycle-3 maintainer question it
answers.
Action:: Add (a) to the compatibility table and release-note list; qualify
(b) by dtype; cite (c) and state that no FK-side invalid-target-ID finding is
introduced.

=== F6 -- MINOR -- Slice 3 spans two review concerns

Observation:: Lookup (transformation; pandas and carrier-preservation
boundary) and reference/graph (findings-only validators; F2 disposition) are
independent semantic review points.
Action:: Split into 3a (Lookup enrichment, duplicate, mismatch) and 3b
(reference/graph). Order between them is free once Slice 2 is accepted.

=== W1 -- INFO -- Existing Core seam suffices

`HelperValueProvider` already lets Domain supply resolved helper values;
Slice 2 needs no new callback abstraction and no Core-to-Domain import.

=== W2 -- WATCH -- Whitespace-only keys and JSON/XML writers

JSON nested and XML writers skip cells where `v.strip() == ""`, so a
whitespace-only key does not roundtrip through those sinks and reloads as
Missing. Sink-capability concern; not a relation-key defect.

=== W3 -- WATCH -- Date versus day-precision `datetime64`

By accepted classifier authority, a `datetime.date` key never equals a
`datetime64` key even at day precision. Correct under the rule; worth one
release-note sentence because pandas commonly coerces date columns.

=== W4 -- WATCH -- Lookup unmatched detection

`_check_unmatched_rows` treats a matched row with a Missing helper payload as
unmatched. Slice 3a should keep unmatched detection keyed on resolution, not
payload nullness, or at least not entrench the conflation.
