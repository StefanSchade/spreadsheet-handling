= Legend Blocks Contract and Composition Assessment

:toc: macro
:sectnums:

Read-only architectural and contract assessment of the Legend Blocks
capability family, focused on its role as a primitive dependency of
`compact_multiaxis`. No production code, tests, registries, or existing
documentation were modified. Only this artifact was created.

toc::[]

== Scope and question

`compact_multiaxis` is a composite transformation that delegates to accepted
primitive families (XRef Crosstable, the historical Cell Codec code-row path)
and reads `_meta.legend_blocks`. Before assessing or refactoring
`compact_multiaxis`, we must decide whether Legend Blocks already has a
sufficiently explicit, minimal, and verified *primitive contract*, or whether
it needs its own correction/acceptance slice first.

The controlling question is narrow: *is the Legend Blocks contract on the
surface that `compact_multiaxis` actually depends on solid enough to proceed
to a `compact_multiaxis` composition assessment?* It is deliberately
separated from the broader question of whether the whole `legend_blocks`
metadata root is internally coherent.

== Executive conclusion

The surface that `compact_multiaxis` actually depends on — the shared domain
reader `_read_legend_block` yielding `(token, group)` records — is explicit,
minimal, and covered by tests. `compact_multiaxis` reads *only* that surface;
it never renders a visible legend, never reads `placement`/`label`/`title`,
never writes `resolved`, and (contrary to the functional model's suggestion)
never composes Sparse Defaults. None of the contract defects found in this
assessment sit on the `compact_multiaxis` dependency path.

However, `legend_blocks` as a whole is *not* a single coherent primitive with
one contract. It is a split metadata root with **four independent consumers
applying divergent validation** over the same `entries` structure, plus a
carrier-`resolved` Resolution facet, and its `meta_registry.yaml` consumer list
is materially incomplete. These are real, verified findings — but they belong
to the *render / validation / persistence* surfaces, not to the
`compact_multiaxis` composition. They do not block proceeding to the
`compact_multiaxis` composition assessment; they warrant a separate,
non-blocking legend-contract correction slice.

Final verdict is at the end of this document.

== Current capability summary

Legend Blocks (`_meta.legend_blocks`) is a workbook-level codebook: a named set
of *entries*, each an `{token, label, group?, description?}` mapping. It serves
four distinct runtime purposes, owned by four different modules:

1. *Allowed-value vocabulary* for Cell Codec — `token` values become the
   allowed code/token set for `allowed_from_legend` validation
   (`cell_codec/scalar.py`).
2. *Generic group projection* for `compact_multiaxis` — `token → group`
   mapping fills the optional `group` output column
   (`compact_multiaxis.py`).
3. *Dropdown / data-validation source* for the render `ValidationPass` —
   `from_legend` rules expand to `token` lists (`rendering/passes/_base.py`).
4. *Visible legend table* rendering — `entries` become a rendered support
   table positioned by `placement`, with a carrier-local `resolved` coordinate
   snapshot (`rendering/composer/layout_composer.py`).

The `legend_blocks` root accepts both a *mapping* form (keyed by block name)
and a *list* form (name resolved from `name`/`id`/positional `legend_{i}`).
Both forms are honoured by the domain reader, the composer, and the validation
pass; the *carrier parsers only honour the mapping form* for legend-surface
recognition (see Persistence).

The functional model (`legend_blocks.adoc`) additionally describes a *long
form* / *code resolution rule* (mapping a code to an explicit structured value)
and *frame-backed* legends. Neither is implemented: entries carry only
`token`/`label`/`group`/`description`, and no resolution-to-long-form consumer
exists. Spec is ahead of code here (observation, not defect).

== Producers and consumers

Only one producer of *content*: callers supplying canonical workbook meta.
Transformations do not synthesise legend entries; they only *read* them. The
Composer is the only writer of a legend sub-field (`resolved`), and only onto a
render-local clone (layout_composer.py:116-127, 245-254).

Consumers and the exact subset each reads:

*The shared `_legend_blocks` helper is a narrow, stable reader for exactly one
slice* (the `(token, group)` records used by Cell Codec and `compact_multiaxis`).
It is not an accidental generic abstraction and not a mixed-responsibility
module: its docstring correctly scopes it, it owns only the schema walk +
non-empty-token validation, and it deliberately does *not* validate `label`,
duplicates, `placement`, or `resolved`. The problem is not this helper; the
problem is that it is *not* the contract owner for the render/validation/carrier
consumers, which each re-implement their own walk with different rules.

== Intent versus resolution lifecycle

The intended split holds on the render path:

[source,text]
----
legend_blocks.{entries,title,placement,target}  = durable Intent
legend_blocks.resolved                           = derived Resolution
----

Lifecycle trace (mapping form, legend anchored to the data sheet — the standard
case, verified by probe):

[source,text]
----
caller config (_meta.legend_blocks)                 Intent
  → compose_workbook clones legend_blocks,
    _add_legend_blocks recomputes resolved fresh     Resolution (always overwritten)
  → render passes → RenderPlan → xlsx/ods carrier     resolved embedded in blob
  → parse_workbook reads blob; _legend_table_hints
    uses resolved to classify the legend surface      Resolution consumed (read-side)
  → workbookir_to_frames returns canonical _meta       resolved PRESENT in canonical
  → persistence_boundary strips legend_blocks.resolved Resolution dropped (sidecar)
----

Verified properties:

* `resolved` is *always recomputed* at render — `_add_legend_blocks`
  unconditionally overwrites `spec["resolved"]` (layout_composer.py:246), so a
  stale `resolved` from a prior readback cannot influence a later render.
  (Confirmed by inspection.)
* `resolved` is stripped from *structured* persistence — **for the mapping form
  only** (persistence_boundary.py:169 guards `isinstance(..., Mapping)`).
* Workbook readback *does* promote carrier `resolved` back into canonical
  `_meta.legend_blocks[*].resolved` (probe: after `save_xlsx`/`load_xlsx` the
  readback legend carries `resolved={'frame_name':'legend_L','top':1,...}`).
  This is a transient leak: it is either overwritten on next render or stripped
  on next structured persist, but between those events canonical meta carries a
  derived facet.
* XLSX and ODS behave consistently on the legend-hint path (both restrict to
  the mapping form; both read `resolved.{sheet,frame_name,top,left}`).
* Legend anchored to the *data* sheet round-trips cleanly (data frame stays
  `[id, v]`, legend not merged). A legend that lands on its *own* sheet
  (default placement, no `target`) is re-emitted as a payload frame on readback
  (probe: frames become `['data','L']`) — see finding LB-4.

== Value and identity semantics

The three identity layers are genuinely distinct here and must not be conflated
with the Cell Codec physical-label contract or the XRef axis-identity contract:

* *Legend block identity* — the mapping key / `name`/`id`. A name, not a frame
  or column. Referenced by `allowed_from_legend`, `from_legend.legend`, and the
  default legend sheet name.
* *Legend entry machine value* (`token`) — a domain code compared against
  *cell values*, never against DataFrame column labels.
* *Legend entry display label* (`label`) — display only, explicitly "not
  referenced by persisted data" (functional model).

Because tokens are cell values, the physical-label / axis-identity contracts do
*not* apply and must not be imposed. `token` is validated only as *non-empty*
(`_is_empty_cell`), which correctly admits numeric-like strings; there is no
hashability/string-only requirement, which is right for a code value.

codec and *invalid* for the visible renderer (empty labels), which is a latent
authoring trap.

== Cell Codec dependency

Cell Codec consumes Legend Blocks through exactly one channel:
`allowed_from_legend` → `_read_legend_block` → `_legend_tokens` → *tokens only*
(scalar.py:251-266). It reads no `group`, `label`, `placement`, or `resolved`.
Duplicate tokens are rejected inside `_allowed_values` via `_duplicates`
(scalar.py:259-261). The Cell Codec functional/registry position is explicit:
Cell Codec writes *no* `_meta.cell_codecs` and is not a metadata anchor; its
legend dependency is purely a read of the token vocabulary. This matches the
accepted Cell Codec projection-slice contract (the code-row `mode` path invoked
internally by `compact_multiaxis`). The Cell Codec ↔ Legend boundary is clean
and minimal.

== Compact Multiaxis dependency

`compact_multiaxis` depends on Legend Blocks in two ways, both narrow:

1. *Forwarding* `allowed_from_legend` verbatim into `decode_/encode_cell_values`
   (compact_multiaxis.py:77, 166). This is pure forwarding — the composite does
   not interpret the legend for validation itself; Cell Codec does.
2. *Group projection* — when `group` is requested, `_with_group_column` builds a
   `token→group` lookup via `_legend_groups` (compact_multiaxis.py:215-277),
   optionally merged with an explicit `code_groups` map. Conflicts between the
   legend-derived group and `code_groups` raise (compact_multiaxis.py:258-267).

Classification of the dependency: **required primitive dependency for the
optional group/validation features, presentation-independent.** Legend Blocks is
*optional* to `compact_multiaxis` overall (both `allowed_from_legend` and
`group` default to `None`); when used, the token/group contract is a genuine
functional dependency, not accidental coupling and not presentation enrichment.
The composite never touches the render/carrier legend surface.

`compact_multiaxis` is registered as two pipeline steps
(`expand_/contract_compact_multiaxis`, registry.py:143-149) and its meta root is
`_meta.compact_multiaxis` (meta_registry.yaml:710). The step registry
(`pipeline_step_registry.json`) correctly records that both steps *read*
`legend_blocks` (registry entries at the `legend_blocks` path). The
`compact_multiaxis` inverse-intent meta records only parameter names (including
the `allowed_from_legend` *string*), never legend content — so there is no
duplicated inverse intent between `legend_blocks` and `compact_multiaxis`.

== Sparse Defaults relationship

*Independent at runtime.* `compact_multiaxis.py` contains zero references to
`sparse` and does not import `sparse_defaults` (verified: `grep -c sparse` = 0;
imports are only `_legend_blocks`, `cell_codec`, `xref_crosstable`). The only
sparsity knob on the composite is `dense_axes`, which is explicitly *rejected*
with `NotImplementedError` (`_reject_dense_axes`, compact_multiaxis.py:313-319).
`sparse_collapse`/`sparse_expand` are separately registered pipeline steps
(registry.py:120-126) operating on their own `_meta.sparse_defaults` root; the
`compact_multiaxis` meta root does not reference `sparse_defaults`.

This contradicts the functional model, which states the convenience surface
"may also compose Sparse Defaults" and lists "Sparse default intent … used only
when configured default values should be restored before cell-code expansion"
(compact_multiaxis.adoc:33, 82-83, 117-118). In the current code, any sparse
behaviour must be composed by the *pipeline author* as separate steps around
`compact_multiaxis`; the composite itself neither invokes nor reads Sparse
Defaults. Answer to objective 7: **only documented as an adjacent capability;
not directly invoked, not consumed through XRef metadata, not an enforced
preceding/following step.** (Finding LB-5, doc-vs-code.)

== Persistence and carrier behavior

Two persistence surfaces:

* *Structured sidecar* (json/yaml/xml/csv dir): orchestrator runs
  `project_meta_to_persistable_contract` before save. `_project_legend_blocks`
  strips `resolved` and preserves Intent — **but only when `legend_blocks` is a
  mapping**. For the *list* form the function returns the value unchanged, so
  `resolved` leaks into the structured sidecar (probe confirmed: list-form
  projection still contains `resolved`). Finding LB-1.
* *Workbook carrier* (xlsx/ods): the whole cloned `workbook_meta` — including
  `resolved` — is serialised into the hidden `_meta` sheet blob
  (layout_composer.py:336-339). Parsers deserialise it and use `resolved` to
  re-recognise the legend surface. On readback `resolved` re-enters canonical
  meta (Finding LB-2). Carrier parsers only recognise legend surfaces for the
  *mapping* form; a list-form legend would render but *not* be re-classified on
  readback and would surface as a payload frame. Finding LB-3.

The meta_registry documents the carrier-dependent behaviour correctly at a high
level (meta_registry.yaml:593), but the *list-form* gaps above are neither
documented nor guarded.

== Schema-maintenance behavior

`legend_blocks` is registered as a *blocked reference root*
(meta_refs.py:60, model.py:42) and scanned by `_handle_blocked_roots`
(meta_update.py:827-857) through the generic `contains_structured_reference`
(meta_refs.py:163-177). That matcher requires, *within one mapping*, both a
FRAME-key match (`frame`, `logical_frame`, `source_frame`, …) and a COLUMN-key
match (`column`, `value`, `row_keys`, …).

Legend blocks use *none* of those key names: identity is a bare mapping key,
placement uses `sheet`/`target`/`top`/`left`, entries use
`token`/`label`/`group`, and `resolved` uses `frame_name` (not `frame`).
Therefore:

* *No false blocking from legend content.* A `token` or `group` value equal to a
  real column name cannot block a rename/drop, because there is no co-located
  FRAME key. Good — the convention-shaped-non-reference risk does not fire here.
* *`resolved` coordinates are correctly ignored* by schema maintenance
  (`frame_name`/`top`/`left` are not recognised keys). Good.
* *The blocked-root registration is effectively inert* for legend content: it
  will essentially never match, because legend blocks carry no
  frame+column reference shape. This is *safe* (defensive, harmless) but means
  the guard provides no real protection specific to legends.
* *`placement.target` is a real frame reference that is not maintained.* If the
  target frame were renamed, `placement.target` would dangle silently. This is
  low severity because `sheets-schema-maintain` operates on *columns*
  (add/rename/drop column), not frame renames, so it is out of the current
  maintenance scope — but it is a genuine unmaintained reference. Finding LB-6
  (minor).

Verdict: schema-maintenance treatment of `legend_blocks` is *safe* (no false
blocking, no silent column dangle) but the blocked-root registration is largely
vacuous. No correction is required for `compact_multiaxis`.

== Architecture and minimality assessment

Against the primer's invariants:

* *Domain ownership of validation* — honoured on the domain slice: token
  validity and group conflict live in the domain layer; the composite delegates.
* *Rendering ownership of layout resolution* — honoured: `resolved` is computed
  only in the composer and recomputed each render.
* *Carrier neutrality of persistable meta* — mostly honoured, but the list-form
  `resolved` leak (LB-1) lets a derived facet escape into a carrier-neutral
  sidecar, violating "Resolution is stripped, Intent is preserved."
* *No generic frame ontology / no hidden metadata fallback* — honoured: the
  composite reads legend content only through the explicit `allowed_from_legend`
  name; there is no implicit legend lookup.
* *No duplicated inverse intent* — honoured: `compact_multiaxis` meta stores the
  legend *name*, not legend content.
* *Narrow feature-local metadata* — partially: the domain reader is narrow, but
  the *root* is shared by four consumers with divergent contracts and no single
  owner. This is the central architectural smell.
* *Deterministic diagnostics / no input mutation on rejection* — honoured on the
  domain slice (readers raise before producing output).

Presentation-vs-domain boundary: `entries[].group` is *dual-purpose* (domain
group projection *and* an optional rendered "Group" column). This is a mild case
of presentation and domain identity sharing a field. It is not currently
harmful (the group value is legitimately both the projected value and a
sensible display), but it means `group` cannot be treated as purely one or the
other.

== Findings by severity

=== Blocking

None. No finding sits on the `compact_multiaxis` dependency path or prevents a
`compact_multiaxis` composition assessment.

=== Important

*LB-1 — list-form `legend_blocks.resolved` leaks into structured persistence.*

* Path: `pipeline/persistence_boundary.py::_project_legend_blocks` (:161-178).
* Current behavior: `resolved` is stripped only when `legend_blocks` is a
  `Mapping`; the list form returns unchanged, so a derived Resolution facet is
  written into json/yaml/xml/csv sidecars.
* Expected contract: "the persistence boundary preserves Intent and drops
  Resolution" for *every* accepted `legend_blocks` shape.
* Evidence: probe — `proj({"legend_blocks":[{"name":"L",…,"resolved":{…}}]})`
  returns a list whose block still contains `resolved`; the mapping-form
  equivalent does not.
* Scope of correction: extend `_project_legend_blocks` (and the analogous
  list-form parser/readback handling if list-form carrier support is intended)
  to handle the list form; add a persistence-boundary test.
* Human decision required: yes — confirm whether the *list form* is a supported
  persisted shape or should be normalised to the mapping form at ingest. If
  list form is unsupported, the correct fix may be to normalise/reject rather
  than patch every consumer.

*LB-7 — `meta_registry.yaml` `legend_blocks` consumer list is materially
incomplete.*

* Path: `registries/meta_registry.yaml:597-601`.
* Current behavior: consumers listed are only `compose_workbook`, the two
  parsers, and `workbookir_to_frames`. The registry omits the *domain* token
  consumers (`cell_codec` via `allowed_from_legend`, `compact_multiaxis`
  group projection) and the `ValidationPass` `from_legend` consumer.
* Expected contract: the registry consumer list is the documented producer/
  consumer contract for a meta root; omitting the domain and validation
  consumers understates the coupling and would mislead any future lifecycle
  or classification work.
* Evidence: `cell_codec/scalar.py:265`, `compact_multiaxis.py:271`,
  `rendering/passes/_base.py:151` all read `legend_blocks`; none appear in the
  registry entry. `meta_registry` architecture tests pass, so this omission is
  *not* caught by any guard.
* Scope of correction: documentation-only edit to the registry entry (plus,
  optionally, a registry-consumer completeness guard). Gated surface — registry
  is a contract artifact; do under an explicit doc slice.
* Human decision required: no (pure accuracy fix), but must be an explicit,
  reviewed edit, not silent.

=== Minor

*LB-2 — workbook readback promotes carrier `resolved` into canonical meta.*
Parsers (openpyxl/odf) deserialise `resolved` from the blob and
`workbookir_to_frames` returns it inside canonical `_meta`; it is only later
overwritten (next render) or stripped (next structured persist). Between events,
canonical meta transiently carries a derived facet, contrary to the functional
model's "not trusted from a prior `_meta`" intent (legend_blocks.adoc:70-72,
177-179). Evidence: `save_xlsx`/`load_xlsx` probe shows `resolved` present on the
readback legend. Low blast radius (recomputed before it can mislead a render).

*LB-3 — list-form legend surfaces are not re-classified on readback.*
`_legend_table_hints` in both parsers handles only the mapping form
(`raw.items()`, openpyxl_parser.py:356 / odf_parser.py:876). A list-form legend
renders fine but is not recognised as a legend surface on readback, risking
its promotion to a payload frame. Same underlying asymmetry as LB-1.

*LB-4 — a legend on its own sheet round-trips as a payload frame.*
With default placement (no `target`), the legend lands on a new sheet named
after the block; `workbookir_to_frames` projects every visible sheet's first
table into a frame regardless of `kind == "legend"`, so the legend surface
returns as payload (probe: frames become `['data','L']`). The realistic
"legend anchored to the data sheet" case is clean. Scope: either forbid the
own-sheet default or skip legend-kind-only sheets in `workbookir_to_frames`.

*LB-6 — `placement.target` is an unmaintained frame reference.* Not rewritten
or blocked by schema maintenance because `target` is not a recognised FRAME
key. Out of current column-maintenance scope, but a genuine silent-dangle on a
frame rename.

=== Observation

* *OB-1 — four divergent validators over one `entries` structure.* `label`
  required by Composer only; duplicate tokens rejected by Cell Codec + Composer,
  deduped by `compact_multiaxis`, tolerated by ValPass; unknown reference raises
  in domain, warns in ValPass. Not a bug for any single consumer, but there is
  no single owner of the `legend_blocks` entry contract. The shared
  `_read_legend_block` is a narrow reader for the token/group slice, not the
  root contract owner.
* *OB-2 — functional-model concepts unimplemented.* "long form" / "code
  resolution rule" and frame-backed legends are described but absent from the
  runtime; entries carry only `token`/`label`/`group`/`description`.
* *OB-3 — `entries[].group` is dual-purpose* (domain group projection value and
  optional rendered column).
* *OB-4 — Sparse Defaults composition is documented but not implemented* in
  `compact_multiaxis` (also captured as LB-5).

=== LB-5 (doc-vs-code, important for the composite assessment)

*Sparse Defaults is not composed by `compact_multiaxis`.* The functional model
implies composition; the code neither imports nor invokes `sparse_defaults`.
This is not a Legend Blocks defect but is recorded here because it will directly
shape the *next* (`compact_multiaxis` composition) assessment: the composite's
real delegation graph is XRef + Cell Codec + optional Legend group/validation
only.
