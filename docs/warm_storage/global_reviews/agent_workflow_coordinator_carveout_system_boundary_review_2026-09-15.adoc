== 2. Verdict

*B -- CARVE-OUT DIRECTION SOUND; SPECIFIC PREREQUISITES SHOULD STABILIZE FIRST.*

The Coordinator is a coherent, small domain: a Git-native, single-WorkItem, serial, bounded-Hop execution operator with its own aggregate (Run with Hop and Finding records), its own invariants (every Hop starts and ends on an observed commit with a clean worktree; one trusted commit per effect; fail-closed identity correlation; gate-only Finding disposition; budget accounting), its own acceptance matrix (replays A--J), and a fail-closed versioned data contract. The executable core contains no spreadsheet, DMC, or Trusted-Ingress symbol; WFC-SYS-03 has held in practice, not only on paper. The candidate boundary is therefore right in direction.

It is wrong or incomplete at six specific places, none of which is a redesign. Three are boundary misplacements the split would freeze: evidence-provider commands are consumer values living in Coordinator code (C1); the Coordinator's own agent-facing contract is authored per WorkItem by the consumer (C2); and the Coordinator's normative authority is an open FTR in the consumer's backlog (C3). Two concern what "history-preserving" can actually preserve (C4) and the never-performed copy-run genericity proof the accepted architecture itself named as the extraction criterion (C5). One is timing: the Coordinator owns no declarative profile of its own today, and Slice 5B is where the first one must appear (C9).

Findings by severity: BLOCKING 0; IMPORTANT 5 (C1--C5); MINOR 5 (C6--C10); INFO/WATCH 4 (CW1--CW4).

Most important newly established consequence: the split hazard is not in `scripts/workflow_coordinator/`, whose extraction is mechanically trivial. It is in the three places where ownership and location currently disagree: consumer values inside core code (C1, C6, C7), Coordinator semantics inside consumer-authored inputs (C2), and Coordinator lifecycle authority inside consumer governance (C3, C4). Carving out before those are corrected exports each misplacement as a permanent contract.

== 3. Findings

Each finding states observation, evidence, risk if ignored, recommended action, and disposition. Actions are conceptual or contractual corrections; none authorizes implementation or a split.

=== C1 -- IMPORTANT -- Evidence-provider commands are consumer policy values owned by Coordinator code

Observation:: WFC-EVID-01 requires "a fixed trusted in-code registry of simple evidence callables". The registry contains exactly `diff_hygiene` (`git diff --check`) and `git_version`. Repository policy `evidence_states` and phase `evidence` may only *name* registry entries; they cannot define one. WFC-EVID-03 nevertheless lists "profile-selected tests, architecture guards, source/style checks" as initial categories.
Evidence:: `evidence.py` `TRUSTED_EVIDENCE`; `serialization.py` (`evidence_states` is a free string list); dogfood `repository_policy.yaml`; the test fixtures name an evidence provider `tests` that no registry defines.
Risk if ignored:: Under every hypothetical consumer the first thing that breaks is the same: `pytest`, `npm test`, `cargo test`, `terraform validate`, or `asciidoctor` cannot become required evidence without a Coordinator code change and release. This is the single concrete place where the "Coordinator owns semantics, consumer owns values" division fails today, and it fails in the direction that would make a carved-out Coordinator a bottleneck for every consumer's quality gates.
Action:: Keep the invariant in the Coordinator (argv originates from pinned trusted policy, never from agent output; fixed observation shape; `fail` versus `error` semantics; no runtime discovery), and move the argv *values* into repository policy as a pinned, drift-checked list (`evidence_states` becomes `evidence_providers: {name: {argv: [...]}}` or equivalent). This is one data field, not a provider framework; the registry then holds only Git-generic providers the Coordinator itself needs.
Disposition:: Open; contract correction before carve-out.

=== C2 -- IMPORTANT -- The Coordinator's own agent-facing contract has no Coordinator-owned home; consumers re-author it per WorkItem

Observation:: The prompt header the Coordinator generates carries identity, scope, permitted routes, evidence names, and one line naming the output contract. Everything else an agent must know about the Coordinator -- that it must not run `git add`/`git commit`, what `commit_intent` means, which escalation kinds exist, that prose cannot replace fields, that a truthful non-completion is a valid success -- is written by the consumer in `task.txt` ("AGENT GIT RULE", "STRUCTURED RESULT CONTRACT", "VALIDATION BEFORE SUCCESS"). All four selected components are consumer documents; the component manifest has no Coordinator-authored entry.
Evidence:: `prompt.py` `_header` and `assemble_prompt`; dogfood `task.txt` and `components.yaml`; Commissioning Diary 2026-09-07 (invocation identity not projected) and 2026-09-11 (`commit` token ambiguity), both of which were failures of contract communication between Coordinator and agent/author rather than reducer defects.
Risk if ignored:: After a split every consumer restates the Coordinator's rules in its own words per WorkItem; drift between that prose and the actual contract is undetectable, and contract changes (a new escalation kind, a changed identity rule) silently invalidate consumer task text. The consumer becomes the de-facto author of Coordinator semantics, which inverts the proposed boundary.
Action:: Give the Coordinator one versioned "agent operating contract" text that it owns and pins like any component (digest recorded in `operator-plan.json`), covering the Git rule, effect-token meaning, result envelope semantics, and escalation vocabulary. Whether the Coordinator injects it automatically or ships it as a reference component the consumer vendors is a secondary choice; the former is smaller. This is not a template engine (WFC-PROMPT-04 stands).
Disposition:: Open; contract correction before carve-out.

=== C3 -- IMPORTANT -- The Coordinator's normative authority is an open FTR in the consumer's backlog; a directory split does not move lifecycle ownership

Observation:: Every `WFC-*` contract ID, every slice acceptance, and the closure obligation WFC-LIFE-01 ("move the FTR and companion material to the repository-standard cold-storage destination") belong to FTR-AGENT-WORKFLOW-COORDINATOR-P5, which is `Lifecycle: Open` in `docs/backlog/` with Slices 5B--5F undisposed. Coordinator tests carry the consumer's `pytest.mark.ftr("FTR-AGENT-WORKFLOW-COORDINATOR-P5")` marker. Consumer Project Memory holds Coordinator authorization events (`SIG-ACT-WFC-*`).
Evidence:: FTR status header and section 8.5; `pyproject.toml` marker registration; `project_memory/canonical/concern_events.json`; `_ftrs_open` include.
Risk if ignored:: A split performed mid-FTR leaves the Coordinator's binding contracts, acceptance history, and future slice authorizations in a repository that no longer contains the code. The prompt's question "does a split create ambiguity over which repository owns old FTR decisions?" has a definite answer: yes, unless the split is placed at a lifecycle boundary.
Action:: Treat the carve-out as a lifecycle event, not a file move. Two admissible boundaries: (a) V1 closure per WFC-LIFE-01/02 (all retained slices disposed), after which the incubator FTR is `Done` and the new repository starts its own lifecycle; or (b) an explicit maintainer decision that closes the incubator FTR as `Superseded` at a named commit and re-homes the undisposed slices in the Coordinator repository with the `WFC-*` IDs carried forward verbatim. Either way, pre-split decisions remain the incubator's records (C4). Nothing here changes the FTR now.
Disposition:: Open; sequencing prerequisite.

=== C4 -- IMPORTANT -- "History-preserving" extraction preserves blame, not citations; normative authority for pre-split decisions cannot travel

Observation:: The Coordinator's provenance is SHA-addressed. The FTR cites 54 distinct commits (all resolve today); the execution evolution cites 13; reviews cite their reviewed commit, the fix commits, and consumer-side anchors (DMC closure `f4698c8`, handoff `c4b844a`; Coordinator-authored consumer commits `0f4d4230`, `2adee468`, `54c708ec`). Retained external roots record the consumer checkout's canonical path. Of the 30 commits touching Coordinator code, 22 also touch FTR, review, evidence, diary, or Project Memory paths.
Evidence:: SHA density count at the reviewed HEAD; `git log --stat` over the Coordinator code commits; `slice4.py` `CheckoutAssociation`; retained proof root paths named in the Diary.
Risk if ignored:: A `git filter-repo` path extraction (1) rewrites the SHA of every kept commit, so every citation inside the extracted documents dangles even for Coordinator commits; (2) drops the consumer commits that Coordinator reviews and the Diary cite, including the three commits the Coordinator itself produced; (3) keeps mixed commits with only their Coordinator-path hunks, so extracted review artifacts describe diffs that partially no longer exist. The story survives as narrative; the audit chain does not.
Action:: Decide now, as a concept clause: the incubator repository remains the citation authority for everything decided before the split and is never rewritten; the Coordinator repository receives the extracted file history for blame plus one provenance document naming the incubator, the split commit on both sides, and the filter-repo commit map; pre-split documents copied into the new repository are marked *imported historical provenance* and carry no normative authority there. This is the only arrangement in which both repositories are truthful without duplicating authority. Do not "move" reviews.
Disposition:: Open; concept clause.

=== C5 -- IMPORTANT -- The accepted architecture's own extraction criterion has never been exercised: the core has no import identity outside the consumer root

Observation:: The proposed architecture (section 3) states: "Extraction to `tools/` waits until a sibling can copy and run a proven dependency-light core unchanged." No such copy-run has been performed. The core imports as `scripts.workflow_coordinator.*`, resolved only because the consumer's pytest root and a `sys.path` hack in `operator.py` (`__file__.rsplit("/scripts/workflow_coordinator/", 1)`) make the consumer directory the package root. There is no `pyproject` for the Coordinator, no entry point, no dependency declaration (`pyyaml`, `git`, provider CLI), and the consumer's source-style guard excludes `scripts/`.
Evidence:: `operator.py` lines 8--12; `proof_harness.py` and `codex_adapter_smoke.py` path insertion; `pyproject.toml` (`pythonpath = ["src"]`, no Coordinator package); `tools/check_source_style.py` roots.
Risk if ignored:: For a non-Python consumer the Coordinator must be installable as its own tool. Until the core has been run from outside the consumer tree against a fixture repository that contains nothing from `spreadsheet-handling`, the genericity claim rests on grep and on unit tests that already use throwaway repositories. That proof is cheap and is the honest substitute for a second real consumer.
Action:: Before any split, perform the copy-run criterion once: package the core with an import identity of its own (a minimal `pyproject`, one console entry point, declared dependencies), run the existing operator tests and one fake-adapter N=2 Run from a directory outside the consumer, against a fixture repository with a non-spreadsheet WorkItem. Record the result as evidence. No consumer change and no live provider is needed.
Disposition:: Open; mechanical prerequisite.

=== C8 -- MINOR -- Governing inputs have three authorship channels; the consumer contract must name which are repository-pinned

Observation:: Governing facts arrive (1) from repository-pinned YAML and components, digest-checked at B; (2) from operator argv: `--expected-head` (the pin itself), `--durable-artifact` (a WorkItem-level requirement that WFC-OUTPUT-04 ties to phase policy, yet it lives on the command line and is not part of the `governing` digest set), `--timeout-seconds`, `--executable`; (3) from the execution harness (known T8). Channel 2 is recorded in `operator-plan.json` but is neither pinned nor drift-checked.
Evidence:: `operator.py` `_preflight` (`durable_artifacts` from args; `governing` covers only paths), `_governing_inputs_unchanged`.
Risk if ignored:: The consumer/Coordinator contract would be ambiguous about whether a required durable artifact is a property of the WorkItem or of the invocation; two operators can launch the same pinned WorkItem with different required artifacts.
Action:: Define the governing-input set in the contract as: repository-pinned (schemas, components, task, and the required durable artifact, which should move into the WorkItem or phase schema) versus invocation-time (expected head, timeout, executable, adapter binding), with the latter always recorded and never able to widen the former. === C10 -- MINOR -- The enforceable action model is repository-effect-only; a generic product must say so

Observation:: `authorized_actions` and `policy.actions` are an open descriptive vocabulary; only `edit` and `commit` carry normative meaning (model.py, FTR 11.4.7). For an infrastructure-as-code consumer, `apply`, `deploy`, or `publish` can be written into policy and mean nothing to the Coordinator; the agent's ability to perform such effects is bounded only by the environment (strategy document section 3; T1/T6).

Disposition:: Open; claim boundary (see section 7).

== 4. Boundary assessment by review question

=== 4.1 Is the Workflow Coordinator a domain?

Yes, and a small one. Its aggregate is `Run` (with compact `HopSummary` and `Finding` records); its value objects are `WorkItem`, `WorkflowProfile`, `RepositoryPolicy`, `RoutingResult`, `CommitIntent`, `GitDelta`, `Observation`; its invariants are those the reducer, `record_hop`, `trusted_commit`, and `validated_result` enforce; its lifecycle is the FTR slice sequence with replays A--J; its release concern is the fail-closed `schema_version == 1` on every human-authored and machine-written artifact. Cohesion is semantic: every element exists to answer "what may this Hop do, what did it actually do, and what may happen next". The concept's own empirical base is two unrelated waves (Trusted Ingress, DMC), so the domain was not generalized from one consumer after the fact.

Hidden consumer assumptions found in the core: evidence argv (C1), commit-subject grammar (C6), binding defaults (C7), Python root layout (C5). No spreadsheet or DMC symbol exists in code. Consumer-looking concerns that are actually Coordinator semantics: the agent operating contract (C2); the review dimensions, Finding lifecycle, `durable_artifact` policy, and escalation kinds, all already generic.

=== 4.3 Git: incidental adapter or product contract?

*Answer: B -- a first-class part of the Coordinator's present domain contract.* Hop identity is a commit range; the only effect is one ordinary commit; governing inputs are pinned by revision and re-read at B; the continuation gate is Git revalidation; provenance and reproducibility are Git by design (concept section 23; WFC-PERSIST-03). Abstracting a "repository/effect port" would leave the central invariant ("every Hop starts and ends on a known commit with a clean worktree") without a definition. There is no evidence of a non-Git consumer, and the prompt correctly warns against generalizing toward arbitrary SCM for elegance. `git_facts.py` is already the seam: observation plus one write surface. The smallest truthful product boundary is "Git-repository-native". T3's exported tree is still a Git-derived object. Do not rename the seam a "repository port"; do rename the product claim accordingly (section 7).

=== 4.4 Repository policy: whose?

The Coordinator must own the *schema* and the *domination semantics*: policy actions bound phase actions; phase scope lies within WorkItem scope; policy must bound WorkItem scope and budget (F2, known); `edit`/`commit` coherence; the evidence-provider *shape* and trust origin. The consumer owns every *value*: paths, action tokens beyond the two normative ones, evidence commands (C1), classification labels and sink audiences (T2/T4, known), environment requirements (T1, known), commit-subject grammar (C6). The Coordinator can remain generic while interpreting exactly that much policy because each check is one set-inclusion or one string comparison; the moment a check needs an expression language the policy has become an engine, and nothing found requires it.

=== 4.5 Governing inputs after carve-out

* *Schemas* -- Coordinator-owned: WorkItem, profile, policy, component manifest, task text envelope, RoutingResult envelope, Run/checkpoint/dispatch/plan/summary/execution-evidence JSON.
* *Governing content values* -- consumer-owned and, under current mechanics, necessarily located in the consumer repository, because "tracked at expected HEAD" is the only admission and drift mechanism (`_pinned_text`, `_governing_inputs_unchanged`). Moving them out would remove the only provenance the Coordinator has.
* *Coordinator-shipped material* (the agent operating contract of C2; reference profiles of C9) becomes governing content only when the consumer pins a copy at its HEAD or the Coordinator injects it with a recorded digest. A vendored copy is the boring option and keeps one admission rule.
* *Host/invocation configuration* is governing content by reader (T8, known) and must be recorded (C8); it must never widen repository-pinned values.
* *Consumer-authored versus agent-produced* -- F1 (known): governing paths excluded from agent scope. Add a third authorship class after a split: Coordinator-authored reference material, distinguished by its recorded source digest.

=== 4.6 Environment boundary as a port

The Coordinator core should own the port *contract* and the *admission comparison* (`provided ⊆ required`, evidence classes, refusal when facts are absent), and should *accept a trusted implementation* verified by an in-boundary probe. It should not construct namespaces, mounts, or network policy in core; that would make it an isolation product and import kernel-level threat modelling that WFC-SEC-01 excludes. The mechanism (bubblewrap or another) belongs in the same tier as provider adapters: a Coordinator-repository integration module, chosen by policy, with a "null boundary" implementation in core that records the provided surface as "host account" so that the T-review's fail-closed egress rule applies honestly. Nothing here requires implementing or selecting a mechanism now.

=== 4.7 Provider adapters and model selection

Core: `AgentExecutionPort`, `validated_result`, the envelope contract, `FakeAdapter`/`SubprocessAdapter` for tests. Integration tier inside the Coordinator repository: `CodexCliAdapter` with its strict-schema projection (CW4), later adapters as sibling modules selected by a policy string. With one adapter today and at most two foreseeable, an `if`/dictionary in the operator is the whole "registry". Binding values move to policy (C7); binding facts are already recorded; compatibility is the one-directional predicate of F5 (known); cost evidence is F6's list (known). Consumer repositories should hold no adapter code.

=== 4.10 Release and lifecycle ownership

Evidence for independent lifecycle already exists: the Coordinator has never appeared in the consumer's release notes (internal tooling), its lifecycle is the FTR slice sequence, and every artifact carries an integer `schema_version` rejected fail-closed on mismatch. That is sufficient for a first independent version; no semantic-versioning regime is needed. Minimum stable public contract before carve-out:

. the five governing-input schemas and their selection rules (WorkItem, profile, policy, component manifest, task), including the evidence-provider values (C1), the required durable artifact (C8), and the subject grammar (C6);
. the structured-result envelope `routing-result-envelope/v1` and `structured_result_v1`;
. the Coordinator-owned agent operating contract text (C2);
. the operator command line, exit codes, and terminal lines;
. the state-root layout and JSON artifact schemas;
. the trusted-commit postcondition (identity tokens, single commit, path set equality).

Test ownership: unit and replay tests travel (CW3); the consumer keeps only tests of its own governing inputs (for example, that its profile and policy parse and cohere).

== 6. Timing and relationship to the slices

*Sequencing judgment:* carve-out after Slice 5B acceptance and before 5C/5D mechanization, once P1--P6 hold. Reasons: 5B exercises Finding convergence, the most Coordinator-specific mechanic, and must yield the first declarative consumer-neutral profile (C9); splitting before it moves the most active development across a repository boundary for no gain. 5C (resume) and 5D (parent/child) change Run-state semantics that are pure Coordinator domain and are natural first work in the new home, consumed by the incubator as dogfood. 5E stays optional and unaffected. 5F (profile application / DMC dogfood) is *consumer* work by definition and is the first genuine consumer-side slice after a split.

F1/F2 (known) remain the semantic gate because a generic Coordinator would otherwise export "committed means authorized" and "policy is not a ceiling". T6 is a concept clause the split must carry, not a mechanism it must wait for. The professional-trust runway (T1--T10) is orthogonal to the split: an environment boundary is equally absent in either repository layout.

*Testimonial consequence.* Independent ownership makes three claims structurally visible instead of grep-provable: consumer semantics never entered the core; governing content lives with the code it governs at a pinned HEAD; and the library's own maintenance is run by a tool that is visibly not the library. Carving out now, with one adapter, one DMC profile, no packaging, and the FTR left behind, would present as speculative platform-building and would contradict the "governance follows repetition" principle the strategy document states. Claims that do not become clearer through a split: any information-governance claim (T-review), which depends on the environment boundary, not on repository layout.

== 7. Durable carve-out / system-boundary conclusions

. The Coordinator is a Git-native governed-execution domain, not a repository abstraction: Git is a product contract, and `git_facts` is its seam.
. The generic core owns schemas and domination semantics; consumers own every value. The division is falsified today only where values sit in code: evidence commands, subject grammar, binding defaults.
. Governing content lives with the code it governs, pinned at the same HEAD; Coordinator-shipped reference material becomes governing only through a consumer-pinned copy or a recorded injected digest.
. Action authority in this product means repository effects (bounded edit, one trusted commit); every other effect is an environment-boundary fact, not a policy token.
. The Coordinator's agent-facing contract is Coordinator semantics and must be Coordinator-authored; task payloads carry work, not rules.
. The consumer/Coordinator public contract is data: five input schemas, one result envelope, one state-root layout, one command line, fail-closed integer versions.
. History-preserving extraction preserves blame, not citations; normative authority for pre-split decisions stays in the incubator by construction.
. Lifecycle ownership splits at an FTR boundary, not a directory boundary.
. The smallest genericity proof is running the packaged core from outside the consumer tree against a non-spreadsheet fixture repository; a second real consumer is confirmation, not a gate.
. Environment isolation is a port the core requires facts from and an integration that provides them, never core mechanics.

== Claims the project should not make

. "The Coordinator is provider-agnostic." One adapter exists; the schema dialect and the isolation it relies on are provider-shaped (T6, known).
. "The Coordinator works with any repository." It works with Git repositories, is runnable today only from a Python project root, and enforces exactly two effect tokens.
. "Policy governs what the agent may do." Policy governs path scope and two repository effects; tools, reads, and network are environment facts.
. "`spreadsheet-handling` is already a consumer." It is the incubator: the Coordinator's normative authority, tests, packaging, and lifecycle currently live in its governance.
. "The Coordinator has been validated on generic workflows." It has been validated on one DMC profile plus test fixtures; no committed consumer-neutral profile exists.
