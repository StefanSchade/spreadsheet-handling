== Incident and required invariant

The first real DMC dogfood Run failed `reconcile_required` even though the
provider succeeded, the agent returned a valid structured result and
`CommitIntent`, and `run_id`/`hop_id` correlated. The single differing field was
`invocation_id`: the exact expected `invocation_id` had never been *projected
into the Hop prompt*, so the agent could not echo it, and strict fail-closed
correlation correctly rejected the result.

Required invariant: exactly ONE Invocation identity per Hop, used identically
for (1) generated prompt identity, (2) `AgentExecutionRequest`, and (3)
structured-result correlation; all of `run_id`, `hop_id`, `invocation_id` must
be visible to the agent; strict correlation must not be weakened.

== What the fix does

* `vertical.run_one_hop` now constructs a single
  `invocation = Invocation(run.run_id, hop_id, invocation_id)`
  (`vertical.py:96`) and threads that one object into prompt assembly, dispatch,
  and validation.
* `prompt._header` gained an `invocation: Invocation` parameter and now emits
  `run_id`, `hop_id`, and a new `invocation_id` line sourced from that object;
  `assemble_prompt` grew a keyword-only `invocation` parameter.
* Tests were updated to pass the invocation and to assert the projected /
  dispatched / validated identity coincide, plus a new `invocation_id` mismatch
  rejection case.

| 3. Prompt exposes all required correlation fields exactly?
| *Yes.* `_header` emits `run_id={invocation.run_id}`,
  `hop_id={invocation.hop_id}`, `invocation_id={invocation.invocation_id}` as
  exact `key=value` lines. `work_item_id` remains sourced from the Run (it is a

| *No, within the Hop path.* `run_one_hop` no longer re-derives identity in the

| *Yes.* `assemble_prompt` is wrapped in `try/except -> ExecutionNotStartedError`

== Deterministic regression evidence

The new tests were run against the *pre-fix* implementation
(`e33fbe7c^`) in an isolated worktree by copying only the post-fix test file
onto the old source. The identity regression test failed with precisely the
incident signature:

[source,text]
----
assert 'invocation_id=INV-1' in adapter.request.prompt
E  AssertionError: assert 'invocation_id=INV-1' in
   '[identity]\nwork_item_id=WI-1\nrun_id=RUN-1\nhop_id=H001\nbase_head=...'
----

Note the pre-fix prompt contains `run_id=RUN-1` and `hop_id=H001` but *no*
`invocation_id` line -- an exact match for the dogfood failure mode (run_id and
hop_id correlated; invocation_id never projected). On the fixed implementation
the same test passes. This is genuine reproduce-then-fix evidence, not a
tautological assertion.

== Architecture check: `prompt.py` importing `Invocation` from `adapter.py`

Import graph (intra-package), confirmed by inspection:

[source,text]
----
model.py    -> (no intra-package imports; leaf)
adapter.py  -> model, serialization
prompt.py   -> adapter (Invocation only), model
vertical.py -> adapter, prompt, model, ...
----

`adapter.py` does *not* import `prompt.py` or `vertical.py`, so the new
`prompt -> adapter` edge introduces *no import cycle* today, and there is no
reuse, testing, or authority problem: tests import `Invocation` cleanly and the
identity type is single-sourced.

*Observation (watch-only, not a blocker):* `Invocation` is a pure frozen
identity value `(run_id, hop_id, invocation_id)` with no execution-port
behavior. Its natural home is `model.py`, the leaf that *both* `prompt` and
`adapter` already depend on. Placing it in `adapter.py` makes the prompt-
assembly layer depend on the execution-port layer solely to *name* an identity,
which is a mild layering inversion and a latent cycle risk *iff* `adapter.py`
were ever to reference a `prompt` type (e.g. typing against `PromptPackage`). It
does not today. Per the review's own guidance, relocation is not demanded for
purity; recorded here as a low-priority maintainability note. Recommended (not
required): move `Invocation` to `model.py` when this area is next touched.
