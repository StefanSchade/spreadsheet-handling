toc::[]

== Scope and controlling question

`compact_multiaxis` is a composite transformation that wraps the accepted XRef
Crosstable and Cell Codec primitive families and reads `_meta.legend_blocks`.
The predecessor Legend Blocks assessment
(`legend_blocks_contract_and_composition_assessment.adoc`) cleared the Legend
dependency and explicitly handed off to this assessment. This document
determines whether `compact_multiaxis` is a thin, explicit composition ready
for an independent acceptance review, or whether a narrow correction slice and
one or more human decisions must land first.

The controlling question, stated normatively:

> Does Compact Multiaxis coordinate its primitives through explicit,
> declarative, feature-owned contracts, or does it require later code to infer
> complex behaviour from generic metadata?

The short answer (evidence throughout): Compact Multiaxis coordinates its
primitives **through direct function arguments and returned frames**, not
through a metadata message bus. No later generic step reconstructs a compact
decision from generic ontology-like attributes. The composition *mechanics* are
sound. The problems are confined to the **persistent metadata contract it
emits** (a write-only descriptive root plus a dangling internal-frame reference
leaked through the wrapped XRef metadata), the **registry/schema-maintenance
descriptions** of that contract, and two **open human decisions** (Sparse
Defaults doc-vs-code; whether the write-only `_meta.compact_multiaxis` root
should be retained). The final verdict is at the end of this document.

== Executive conclusion

Compact Multiaxis is a genuinely thin, explicit composition. Both directions
delegate matrix addressing to XRef and cell-value grammar to the historical Cell
Codec code-row path, derive their substep configuration deterministically from
explicit high-level parameters, and communicate with their substeps through
**direct function arguments and returned frames** — never through a metadata
message bus. Its own `_meta.compact_multiaxis` root is a **write-only trace**:
no runtime code, in either direction, ever reads it. Roundtrips are correct;
temporary-frame naming is collision-safe; failure is atomic against the caller's
input mapping (probed).

The controlling-question test therefore passes on the *coordination* axis: there
is no reconstruction of a complex feature decision from generic metadata. The
one reverse-direction metadata fallback that exists (column ordering) is
**XRef-owned** and part of the accepted XRef contract, not a compact-owned
inference.

The defects are on the **persisted contract**, not the composition:

1. Both directions leave `_meta.xref_crosstable[config_id].relation` pointing at
   a *deleted internal temporary frame* (`__compact_multiaxis_<id>_xref` /
   `__compact_multiaxis_<id>_encoded`). This is a persistent metadata root; the
   dangling field is inert today but leaks the composite's internal temp-frame
   naming into a public, persisted metadata contract (CM-1, important).
2. `registries/meta_registry.yaml`'s `compact_multiaxis` entry mis-states the
   root as roundtrip-relevant consumed intent that "preserves … sparse
   behavior", when nothing reads it and the composite composes no Sparse
   Defaults at all (CM-2, important; carries a human decision).
3. The schema-maintenance blocked-root registration for `compact_multiaxis` is
   vacuous against the real payload shape and is tested only with a fabricated
   shape the producer never emits (CM-3, minor).
4. The pipeline step registry's `parameters` block omits historical-path
   parameters that are accepted and actually used in Worldbuilding
   (`mode`, `drop_empty`, …) (CM-4, minor).

Plus two carried-in dependencies (Cell Codec historical-path retirement;
Legend `EC-5` unhashable-token `TypeError` on the compact group path) and one
open doc-vs-code decision (Sparse Defaults, LB-5).

Because the persisted metadata contract does not match runtime reality and two
human decisions remain open, a narrow correction slice should precede an
independent acceptance review. Verdict at the end.

== Current user-facing capability

Compact Multiaxis is a convenience composition for workbook surfaces that need
matrix editing and compact structured cell values at the same time
(`compact_multiaxis.adoc`). It exposes two registered pipeline steps and two
importable functions:

* `expand_compact_multiaxis` (`expand_compact_multiaxis` step): a compact matrix
  frame (rows keyed by `row_keys`, one physical column per matrix axis value,
  each cell a whole code or a delimited token list) becomes a generic explicit
  long-form relation `[*row_keys, column_key, code (, group)]`. This is the
  read/forward path used when importing an edited workbook matrix into
  canonical rows.
* `contract_compact_multiaxis` (`contract_compact_multiaxis` step): the inverse
  — an explicit relation `[*row_keys, column_key, code]` becomes a compact matrix
  `[*row_keys, <one column per column_key value>]`. This is the write/reverse
  path used when rendering canonical rows back into an editable workbook matrix.

Worked example (`compact_multiaxis.adoc`):

[source,text]
----
feature_id | Product A | Product B      expand→   feature_id | column_key | code
f1         | E-R       | K              ←contract f1         | Product A  | E-R
f2         |           | E-K                      f1         | Product B  | K
                                                  f2         | Product B  | E-K
----

Optional capabilities: an `allowed_from_legend` token vocabulary and/or explicit
`allowed_codes`/`allowed_tokens` for code validation; an optional `group`
output column projected from `_meta.legend_blocks` token→group records and/or an
explicit `code_groups` map; `mode` (`whole_cell_code` vs `split_tokens`),
`delimiter`, `normalize_case`, `strip`, `drop_empty`, `canonical_order`,
`column_keys`, `fill_value`. `dense_axes` is accepted syntactically but
**rejected** with `NotImplementedError` in both directions
(`_reject_dense_axes`).

Real consumers: one Worldbuilding pipeline
(`worldbuilding/pipelines/dino_insel/spreadsheet_to_json.yaml`, an
`expand_compact_multiaxis` step with `mode: whole_cell_code`,
`allowed_from_legend: story_group_codes`, `drop_empty: true`,
`name: story_group_matrix`). No Demo usage. Unit + pipeline-binding tests
exercise both directions.

== Normative composite-step framing

Per the task's normative framing, a composite may legitimately: accept explicit
high-level configuration → validate/normalise it → deterministically derive
primitive configuration → call/coordinate the primitives → record explicit
feature-owned metadata needed by later steps or inversion. Metadata-mediated
coordination is *allowed* when a feature-owned step records an explicit,
declarative, documented decision that a *known later consumer* reads; it is
*problematic* only when a later generic step reconstructs a complex feature
decision from broad ontology-like attributes.

Measured against that frame, Compact Multiaxis is on the safe side of the line:

* It accepts explicit high-level config and normalises it locally
  (`_as_list`, `_ensure_distinct_output_columns`, `_reject_dense_axes`).
* It derives substep configuration deterministically (see Forward/Reverse
  graphs) and passes it by **direct kwargs**, not metadata.
* Its own `_meta.compact_multiaxis` write is **not** a coordination message —
  no later consumer reads it — so it is neither the "valid pattern" (recorded
  decision + known consumer) nor the "problematic pattern" (generic
  reconstruction). It is a third thing: a descriptive trace with no consumer.
* The only *read* of persisted intent on the reverse path is XRef's own
  `_meta.xref_crosstable[config_id].column_keys` fallback, which is a
  feature-owned XRef contract with a known consumer (`contract_xref`), not a
  compact-owned inference.

So the "metadata as an internal message bus is bad" heuristic is *not* the
operative concern here — the composite does not use metadata as a bus at all.
The operative concern is narrower: a persistent metadata root that is written
but never read, and a wrapped-primitive metadata field that references a frame
the composite deletes.

== Composite planning contract

There is **no explicit plan object**. The conceptual plan is distributed across
the two public functions and is *recomputed independently in each direction*:

* Validate high-level parameters: `_reject_dense_axes`, `_as_list`,
  `_ensure_distinct_output_columns` (expand only; contract omits the
  distinct-output check — see below).
* Derive XRef arguments: `row_key_cols`, `column_key`, `value`,
  `value_columns`/`column_keys`, `drop_empty=False` forced on the forward XRef
  leg (the codec applies the caller's `drop_empty`).
* Derive Cell Codec arguments: `passthrough = [*row_key_cols, column_key]`
  (expand) / `group_by = [*row_key_cols, column_key]` (contract), plus the codec
  parameter forwarding.
* Derive Legend group behaviour: only when `group` is requested
  (`_with_group_column` → `_group_lookup`).
* Derive deterministic temporary names: `_temp_frame_name` with a
  collision-avoidance suffix.
* Decide redundant frames: **none** — the source frame is preserved
  (`drop_source` is *not* used); only the composite's own temp frame is removed.

Is the plan explicit in one place, distributed, recomputed, encoded in
`_meta.compact_multiaxis`, duplicated in primitive metadata, or hidden in
fallback? It is **distributed across the two call sites and recomputed in each
direction**. It is *not* encoded in `_meta.compact_multiaxis` (that root is not
read). It is *not* hidden inside fallback logic (the composite's own config
never falls back to metadata). The only place derived plan state is duplicated
is the overlap between `_meta.compact_multiaxis[config_id]` (which restates
`row_keys`, `column_key`, `value`, `code`, `value_columns`/`column_keys`, and
the full codec config) and `_meta.xref_crosstable[config_id]` (`row_keys`,
`column_keys`) — a duplication that matters only because the compact copy is
never read (CM-2).

Recommendation on a plan object: introducing an explicit plan dataclass would be
*stylistic purity, not correctness*. The derivation is already deterministic and
small. The one substantive planning gap worth an explicit decision is the
**minor asymmetry**: expand runs `_ensure_distinct_output_columns` (guarding
`code`/`group` against `passthrough`) while contract has no symmetric
output-name guard beyond what `contract_xref` itself enforces. This is not a
correctness defect (contract's outputs are the matrix columns, validated by
XRef), but a future correction should record the asymmetry rather than a plan
object being introduced for its own sake.

== Primitive delegation boundaries

=== Delegated to XRef Crosstable

* Matrix ↔ relation addressing: which relation tuple a matrix cell represents
  (`expand_xref` / `contract_xref`).
* Row-key and column-key selector validation; physical matrix header
  identity (unique, non-empty string labels — the accepted carrier-stable
  contract); `column_key`/`value` output-name collision checks; duplicate
  `(row, column)` pair rejection; deterministic diagnostics.
* Column ordering on contraction (explicit `column_keys` → dense →
  `_meta.xref_crosstable[config_id].column_keys` → distinct relation values).
* XRef inverse-intent metadata (`_meta.xref_crosstable`). Compact passes
  `drop_source=False` implicitly, so XRef schedules **no** `pipeline_cleanup`
  drop command; the composite manages its own temp lifecycle.

=== Delegated to Cell Codec

* Compact cell-value grammar: `whole_cell_code` (one code per cell,
  punctuation-safe) vs `split_tokens` (delimited multi-token) — the historical
  `mode` code-row path (`cell_codec/scalar.py`, `frame.py::_decode_legacy_code_rows`
  / `_encode_legacy_code_rows`).
* Token/code validation against `allowed_codes` / `allowed_tokens` /
  `allowed_from_legend` (legend token vocabulary); duplicate-allowed-value
  rejection; canonical ordering; `normalize_case` / `strip`.
* Physical source-label guards and scalar-addressability of the generated
  `code`/`value` output labels (shared `domain.tabular` boundary).
* No `_meta.cell_codecs` is produced (the codec `del`s the `name` argument the
  composite passes); intent lives entirely in the explicit call arguments.

=== Delegated to Legend Blocks

* Token vocabulary for `allowed_from_legend` (forwarded verbatim to the codec).
* Optional token→group projection for the `group` column
  (`_legend_groups` → `_read_legend_block`), reading only `entries[].token` and
  `entries[].group`. Presentation-independent; never touches
  `title`/`label`/`placement`/`resolved` (confirmed by the predecessor Legend
  assessment and re-verified here).

== Locally owned semantics

Semantics genuinely owned by Compact Multiaxis (not delegable):

* *Composition order and direction pairing*: expand = XRef→Codec; contract =
  Codec→XRef. The forward XRef leg is forced to `drop_empty=False` so the codec
  owns the single `drop_empty` decision.
* *Config normalisation*: `_as_list` (rejects `None`/empty/tuple labels with a
  first-slice flat-label message), `_ensure_distinct_output_columns` (expand),
  `_reject_dense_axes`.
* *Deterministic temporary-frame naming and lifecycle*: `_temp_frame_name`
  (collision-avoidance suffix) plus `out.pop(temp)`.
* *Group-column projection*: `_with_group_column` / `_group_lookup` /
  `_legend_groups` — merging a legend-derived `token→group` map with an explicit
  `code_groups` map under a `_normalize_key` normalisation, with deterministic
  conflict rejection (`"Conflicting group value for code …"`) when the two
  sources disagree, and a legend-internal conflict rejection when one legend
  block carries two `group` values for one token.
* *The composite trace* `_meta.compact_multiaxis[config_id]` (write-only).

This is the correct minimal surface. None of it re-implements matrix addressing,
token parsing, code validation, or legend meaning — matching the functional
model's non-goals.

== Field-level `_meta.compact_multiaxis` contract

runtime code path: **none** (verified by grep and by probe — see Metadata
precedence). The only "consumers" in `meta_registry.yaml` are the generic
persistence carriers `compose_workbook` and `workbookir_to_frames`, which

root. The persistence boundary does **not** project this root at all (it handles
only `legend_blocks` and `xref_crosstable`), so it is persisted verbatim; the
persistence-boundary and carrier-guard tests assert `out["compact_multiaxis"] ==
fixture["compact_multiaxis"]`.

== Temporary-frame and cleanup lifecycle

Names: `__compact_multiaxis_<config_id>_xref` (expand),
`__compact_multiaxis_<config_id>_encoded` (contract). `config_id = name or
output/relation`.

* *Collision with a caller-owned frame*: `_temp_frame_name` appends `_2`, `_3`, …
  until unused. Probed: a caller-owned `__compact_multiaxis_out_xref` sentinel
  frame is **preserved intact** and the composite still produces its output
  using a suffixed temp name.
* *Collision with a prior failed run / repeated invocation*: safe — the temp is
  always popped on success; a prior failure leaves the caller's input mapping
  untouched (probed), so no stale temp accumulates in the input.
* *Multiple instances / nested composites*: each instance uses its own
  `config_id`-derived name and pops its own temp; the collision suffix handles
  identical `config_id` in one mapping.
* *Failure in primitive A / B / local projection*: probed — an invalid code in
  `decode_cell_values` raises `ValueError`; the caller's input mapping keeps
  exactly its original keys (`['product_matrix','_meta']`), no
  `__compact_multiaxis_*` temp leaks into it, the matrix frame is unchanged, and
  no `_meta.compact_multiaxis` is written to the input. All composite functions
  operate on `dict(frames)` copies and shallow-copy `_meta`, so the caller's
  mapping is never mutated on failure.
* *Cleanup on success*: `out.pop(temp)` removes the temp from the returned dict;
  temp frames are never persisted.
* *Cleanup metadata / persistence of temp*: the composite emits **no**
  `_meta.pipeline_cleanup` command (it does not use `drop_source`); the temp is
  removed directly, not via the cleanup command family. `pipeline_cleanup.py`'s
  preserved-intent list includes `compact_multiaxis` and `xref_crosstable`, so
  those roots survive final cleanup.

Distinguishing the lifecycle options the task calls out:

* Deleting a *locally-created temporary frame*: **yes** — this is what the
  composite does (`out.pop(temp)`), correctly.
* Marking a *source frame* eligible for later deletion: **no** — source frames
  are preserved (frame_contract `preserves: [matrix]`/`[relation]`).
* Immediately deleting a source frame: **no**.
* Carrying an explicit deletion permission through metadata: **no**.
* A later generic step inferring deletion from broad attributes: **no**.

Assessment: the composite neither needs nor emits a "may be deleted" message. A
source frame is legitimately retained (the composite is a projection, not a
consuming transform). The one lifecycle defect is **not** about frame deletion —
it is that the wrapped XRef metadata *references* a temp frame that the composite
deletes (CM-1), i.e. a dangling *reference*, not a dangling frame.

== XRef contract preservation

Assessed against the accepted XRef contract (Review 006):

* *Axis identity / physical-header contract*: preserved — the composite passes
  physical frames straight to `expand_xref`/`contract_xref`; the unique
  non-empty-string matrix-header contract and the physical-label boundary

* *Row/column selector validation*: preserved — `row_keys`, `column_key`,

  flat-label first-slice contract.

* *Inverse metadata ownership*: `_meta.xref_crosstable` remains XRef-owned; the

Does the composite validate later than XRef, weaken/duplicate/bypass/delay XRef
validation, or accept combinations XRef rejects? No — XRef runs first on the

**CM-1 (important) — temp-frame reference leaks into persistent XRef metadata.**
After `expand_compact_multiaxis`, `_meta.xref_crosstable[config_id].relation ==

(`relation` not present in the returned frames). After
`contract_compact_multiaxis`, `_meta.xref_crosstable[config_id].relation ==
"__compact_multiaxis_<id>_encoded"`, likewise deleted (probed). This root is
persistent (survives `pipeline_cleanup` and the persistence boundary except for
`column_keys`). The dangling `relation` is inert today because no consumer
reconstructs from it (`matrix` and `column_keys` are the read facets), but it is
a persisted public reference to a frame that never exists in any output, and it
leaks the composite's internal temp-frame naming convention into the XRef
contract. Expected contract: persistent XRef intent should reference only frames
that exist in the composite's output (the public source/output frames), or the
composite should not persist an XRef entry that describes its internal leg.

== Sparse Defaults relationship

*Independent at runtime.* `compact_multiaxis.py` contains **zero** references to
`sparse` and does not import `sparse_defaults` (`grep -c sparse` = 0; imports are
only `_legend_blocks`, `cell_codec`, `xref_crosstable`). The only sparsity knob
on the composite is `dense_axes`, explicitly rejected with
`NotImplementedError`. `sparse_collapse` / `sparse_expand` are separately
registered steps operating on their own `_meta.sparse_defaults` root; the compact
root does not reference `sparse_defaults`, and `sparse_defaults` reads
`_meta.xref_crosstable` (not `_meta.compact_multiaxis`).

This contradicts the functional model (`compact_multiaxis.adoc`), which states
the convenience surface "may also compose Sparse Defaults" and lists "Sparse
default intent" as optional consumed/produced information in both steps. In the
current code, any sparse behaviour must be composed by the *pipeline author* as
separate steps around Compact Multiaxis.

Decision (choose and justify): **Target A — Sparse Defaults remains a separate,
explicit pipeline composition around Compact Multiaxis; correct the live
documentation that implies internal composition.** Justification: there is no
runtime use case, inverse requirement, or ownership evidence for pulling Sparse
Defaults inside the composite. Sparse Defaults already keys off
`_meta.xref_crosstable` for its column targets, so a pipeline author who wants
sparse behaviour composes `sparse_collapse`/`sparse_expand` adjacent to the
compact steps exactly as they would for a bare XRef. Embedding it would (a)
add a second default/blank model inside a surface whose whole non-goal list
forbids "a second sparse-default/default-blank model", and (b) couple the
composite to a `_meta.sparse_defaults` lifecycle it does not otherwise touch.
Correcting the functional model down to the code is the smaller, safer change and
matches the meta_registry, which lists `sparse_defaults` as a *sibling* anchor,
not an internal one. (This resolves LB-5 / Legend decision 3, as that assessment
requested.)

== Schema-maintenance behavior

`compact_multiaxis` is registered as a **blocked reference root**
(`meta_refs.py:59` `BLOCKED_ROOTS_BY_NAME`, `model.py:40`
`ReferenceRoot.COMPACT_MULTIAXIS`) and scanned by `_handle_blocked_roots`
through the generic `contains_structured_reference`
(`meta_refs.py:163-177`). That matcher blocks only when, *within one mapping*, a
recognised FRAME key (`frame`, `logical_frame`, `output_frame`,
`relation_frame`, `source_frame`, `target_frame`) and a recognised COLUMN /
COLUMN-LIST key co-occur.

The **real** `_meta.compact_multiaxis` payload carries *none* of the recognised
FRAME keys — frame identity lives under `matrix` / `output` / `relation`, which
are not in `FRAME_KEYS`. Therefore `has_frame` is always false and the block
**never fires** against a real payload, even though the payload does carry
recognised COLUMN keys (`column_key`, `value`) and COLUMN-LIST keys (`row_keys`,
`value_columns`, `column_keys`).

**CM-3 (minor) — the blocked-root registration is vacuous against the real
payload and tested only with a fabricated shape.**
`test_metadata_refs.py:450-467` exercises the block with the synthetic entry
`{"story_matrix": {"frame": "characters", "value_column": "name"}}` — a `frame`
+ `value_column` shape the producer (`_write_multiaxis_meta`) never emits. The
test passes and gives false confidence that compact references are protected;
the real payload's `code`/`value`/`column_key` column references are neither
maintained nor blocked. This mirrors the Legend `LB-6` situation: it is *safe*
(no false blocking, and the references are inert because nothing consumes them),
but the guard provides no real protection specific to the composite. Since no
runtime code reads the compact root, an unmaintained/dangling reference there is
harmless — which is itself further evidence the whole root is descriptive
sediment (CM-2). A correction should either make the block match the real shape
(recognise `matrix`/`output`/`relation` as frame keys *if* the root is
retained and its references are ever meant to be maintained) or drop the
blocked-root registration when the root stops being persisted.

== Mutation and failure atomicity

Project contract (from `agent_rules.adoc` and observed convention): the standard
is **not** transactional rollback of arbitrary caller state; it is that a
transformation operates on a copied frames mapping and shallow-copies `_meta`,
so a rejection leaves the *caller's input mapping* unmutated and produces no
partial output, metadata, or cleanup command.

Probed rejections (invalid code during expand; and by construction for the
other legs):

* New frames left behind in the input: **none** (input keys unchanged; no
  `__compact_multiaxis_*` temp leak).
* Changed source frames: **none** (matrix/relation unchanged; every function uses
  `dict(frames)` and never mutates a contained DataFrame in place — codec/xref
  build fresh DataFrames).
* Partial target frames: **none** (primitives raise before
  `pd.DataFrame(records, …)`).
* `_meta.compact_multiaxis` on failure: **not** written to the input (written
  only to the returned copy after all frame work succeeds).
* `_meta.xref_crosstable` / `_meta.cell_codecs` / temporary metadata / cleanup
  commands / deletion eligibility on failure: **none** on the input mapping.
* Altered caller-owned nested dicts/lists: the composite shallow-copies `_meta`
  and rebuilds nested config dicts, so it does not mutate caller-owned nested
  structures; the codec/xref follow the same discipline.

Atomicity is therefore satisfied against the stated project contract, in both
directions and at each rejection stage.

  emits a broad, verbatim-persisted root that no consumer reads, with a registry
  description that over-claims its role (CM-2).
* *Deterministic diagnostics / no input mutation on rejection*: honoured
  (probed).
* *Presentation independence*: honoured (Legend dependency is token/group only).

Central architectural smell: a *thin, correct composition* wrapped in a
*persistent metadata contract that describes work nobody reads*, plus a wrapped
XRef metadata field that references a deleted internal frame. The composition
could be reduced to essentially its current form minus the descriptive root, and
minus the temp-name leak — i.e. the family is already close to minimal on the
compute side; the surplus is on the persisted-contract side.

== Findings by severity

=== Blocking

None. The composition mechanics are correct; no finding prevents the composite
from *functioning* correctly.

=== Important

*CM-1 — persistent XRef metadata references a deleted internal temporary frame.*

* Path: `compact_multiaxis.py:53-64` (expand) and `:154-182` (contract), via
  `xref_crosstable/operation.py::_write_xref_meta`.
* Current behavior: after expand, `_meta.xref_crosstable[config_id].relation ==
  "__compact_multiaxis_<id>_xref"`; after contract, `… .relation ==
  "__compact_multiaxis_<id>_encoded"` — both frames are deleted by the composite
  (`out.pop`) and never appear in output. Persistent root; survives cleanup and
  the persistence boundary (except `column_keys`).
* Expected contract: persisted XRef intent should reference only frames that
  exist in the composite's output, or the composite should not persist an XRef
  entry describing an internal leg it deletes.
* Reproducible evidence: probe (session scratchpad) — `xref relation ->
  '__compact_multiaxis_feature_product_codes_xref' | exists in frames? False`;
  same for `_encoded` after contract.
* Correction scope: decide how the composite persists (or suppresses) the
  wrapped XRef `relation`/`matrix` for its internal legs — e.g. rewrite
  `relation`/`matrix` to the public frames after delegation, or route XRef so it
  does not persist a temp-referencing entry, or drop the internal entry and let
  the composite own the minimal reverse intent explicitly.
* Dependency: interacts with the CM-2 decision (if the compact root is retained
  as the authoritative composite intent, the XRef temp entry may become
  redundant).
* Human decision required: yes — this is coupled to whether the composite or XRef
  owns the persisted reverse intent for a composed run.

*CM-2 — `_meta.compact_multiaxis` is a write-only descriptive root, and the
registry over-states its contract.*

* Path: `compact_multiaxis.py::_write_multiaxis_meta`;
  `registries/meta_registry.yaml:710-727`.
* Current behavior: the root is written by both directions and read by no runtime
  code path (probed: reverse roundtrip succeeds with the root absent and is
  unaffected by a conflicting root). The registry describes it as
  `render_relevance: indirect`, `roundtrip_relevance: preserves composed
  transform mode, row/column key names, codec configuration, sparse behavior,
  and optional group projection` — implying consumed roundtrip intent and even
  "sparse behavior", which the composite does not implement.
* Expected contract: the registry (and functional model) must describe the root
  truthfully — either as an explicit, retained *diagnostics trace* with no
  roundtrip authority and no sparse behaviour, or the root should stop being
  written.
* Reproducible evidence: grep (no consumer); probes P1/P2 (absent/conflicting
  root ignored); functional model already calls it an optional "composition
  trace".
* Correction scope: registry/documentation correction plus a decision to retain
  or stop writing the root; if retained, add a test asserting it is *not*
  consumed on the reverse path so a future silent read is caught.
* Dependency: coupled to CM-1 (persisted reverse intent ownership).
* Human decision required: yes — retain-as-trace vs stop-writing.

=== Minor

*CM-3 — schema-maintenance blocked-root registration for `compact_multiaxis` is
vacuous against the real payload and tested only with a fabricated shape.*
`meta_refs.py:59` registers the block, but the real payload carries no

never fires; `test_metadata_refs.py:450` covers it only with a synthetic
`{frame,value_column}` entry. Safe (no false blocking; references inert) but

CM-2 retain/stop decision.

*CM-4 — pipeline step registry `parameters` block is incomplete.*
`pipeline_step_registry.json` lists for `expand_compact_multiaxis` only
`matrix, output, row_keys, value_columns, column_key, value, code, group,

omitting accepted historical-path parameters that are actually used —
Worldbuilding's `expand_compact_multiaxis` step passes `mode` and `drop_empty`,
and the signature also accepts `delimiter`, `allowed_codes`, `allowed_tokens`,

== Conclusion

Compact Multiaxis is a thin, explicit composition that coordinates XRef and the
historical Cell Codec path through direct arguments and returned frames, derives
its substep configuration deterministically, preserves the accepted primitive
contracts, and is atomic against caller input. It does **not** reconstruct
feature decisions from generic metadata, and it does **not** use metadata as a
coordination bus. On the controlling question, the composition is clean.

However, its **persisted metadata contract does not match runtime reality**: the
wrapped XRef metadata persists a reference to a deleted internal temporary frame
(CM-1), and `_meta.compact_multiaxis` is a write-only descriptive root that the
registry over-claims as roundtrip-relevant intent including a "sparse behavior"
the composite does not implement (CM-2), with a matching vacuous
schema-maintenance guard (CM-3) and an incomplete registry parameter list
(CM-4). Two of these carry genuine human decisions (retain-vs-stop the compact
root; who owns persisted reverse intent), and the Sparse Defaults doc-vs-code
question (CM-6/LB-5) must be resolved. These are narrow, but they are
contract-level and should be corrected before an acceptance review certifies the
family's metadata contract.
