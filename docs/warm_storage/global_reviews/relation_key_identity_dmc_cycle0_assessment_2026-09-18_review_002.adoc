== F1 disposition -- CLOSED

*General contract.* The corrected assessment states, consistently in the
decision table, the "Category and carrier differences" section, the minimum
owner contract, and the Local Human Readability list:

* relation-key equality is new, bounded semantics -- not pre-existing scalar
  authority (the Review 001 overreach is withdrawn explicitly);
* it is reflexive, symmetric, transitive, and agrees with one owner-defined
  hashable identity; equality and hashing derive from the same
  category-tagged basis;
* category is part of identity (Boolean/Number and Number/String cannot
  collapse);
* no fallback to native Python/NumPy/pandas equality where it disagrees with
  hashing, and no `str`/`repr`/parsing/dtype coercion defines identity;
* pairwise-only APIs that could disagree with raw-carrier hashing are
  forbidden.

*Number basis -- accepted.* One Number category; equality by exact
represented mathematical value; no NumPy weak-scalar promotion; signed zeros
equal; infinities only with the same infinity; NaN is Missing. All required
consequences are listed and are carried into the owner test matrix
(`1 == 1.0`, `numpy.int64(1) == 1`, `numpy.float32(0.1) != 0.1`,
`numpy.int64(2**53+1) != numpy.float64(2**53)`, equal hashes for every equal
pair). Re-probed: native `==` is `True` for both non-promotion pairs, exact
values differ. The basis is implementable without a numeric normalization
framework: Python's own `int`/`float`/`Fraction` comparison and hashing are
already exact-value based and mutually consistent, so an owner identity
derived from the exact value (for example an exact integer or rational) meets
the contract directly. The assessment explicitly keeps this as private
relation-key identity material and lists general Number normalization as
out of scope.

*DateTime basis -- accepted.* Date and DateTime remain distinct; naive
DateTime by exact proleptic-Gregorian wall-clock coordinate; aware
`datetime`/`Timestamp` by exact UTC instant; offset/zone name not separate
identity; aware never equals naive; no rounding or truncation, and a unit or
carrier-precision difference alone does not distinguish equal coordinates.
The native non-transitive triple (`datetime64[ns]` / `Timestamp` /
`datetime`: `True`, `True`, `False`) is re-probed and is explicitly bypassed
by owner identity. The rule is scoped to relation keys ("does not convert
stored values, prescribe a general DateTime normalized carrier, or establish a
general timezone policy") and the out-of-scope list is amended accordingly.

*Primary F1 question.* The contract is now sufficiently precise and bounded
to implement deterministically. No single unresolved semantic issue remains;
the residual items are implementation mechanics (W2).

=== W2 -- WATCH -- Owner implementation must not reach for native carrier shortcuts

Implementation notes for Slice 1 review, not design gaps:

* Number: `numpy.floating` admits `numpy.longdouble`; its `.item()` returns a
  `numpy.longdouble` and `float()` is lossy, so exact identity should come
  from the exact value (for example `as_integer_ratio()`), with infinities
  handled separately. `numpy.uint64` above `int64` range must keep its exact
  integer.
* DateTime: native `numpy.datetime64` cross-unit comparison is itself unsafe
  (probe: `datetime64[ps]` vs `datetime64[D]` raises `OverflowError`), and
  `Y`/`M` units are calendar-nonuniform. The coordinate should be derived with
  exact integer/rational arithmetic, not NumPy unit promotion.

The contract already requires exact value and full precision; these are the
concrete traps a Slice 1 reviewer should check the owner tests against.

=== W3 -- INFO -- `1.0`/`1` classification wording

The compatibility row says "bug correction where producer and validator
contradicted one another". For FK, the reproduced table shows producer and
validator currently *agree* (both miss/report); the contradiction for
`1.0`/`1` is across surfaces (FK vs Lookup). For FK users the change is miss
-> resolve and a newly reported object-dtype duplicate. The primary
classification ("previously undefined now defined") remains honest; Slice 2's
release note should state the FK-side behavior change plainly.

=== W4 -- WATCH -- Default `unique_edges` columns are the endpoint columns

When `unique_columns` is not configured, graph `unique_edges` defaults to the
source and target endpoint columns. After Slice 3b, endpoint checks will
distinguish `1`/`"1"` and exclude Missing, while default unique-edge tuples
keep token identity (stringified, blank-participating). This is the
deliberate F2 retention, but it is the strongest evidence for the generic
tuple-uniqueness follow-up and should be part of the Slice 3b
characterization.
