== Formula single-key semantics [[sec-formula-single-key]]

`_column_mismatch_indices` (`mismatch.py:186-225`) computes
`expected_formula = (lookup_name, payload_keys[0], lookup_key, helper_col)`
against `actual_formula = (cell.lookup_sheet, cell.source_key_column,
cell.lookup_key_column, cell.lookup_value_column)` -- field order, direction
(source/payload side vs. lookup side), and helper-column identity all match
the accepted design's tuple exactly. Dispatch is per-cell
(`isinstance(cell, LookupFormulaSpec)`), confirmed to produce no cross-row
leakage both by the new
`test_formula_helper_mixed_scalar_and_formula_rows_evaluated_per_cell` test
and by an independent repro constructing a column where row 0 is a
value-mismatching scalar and row 1 is a structurally-wrong formula: this
correctly yields **two** findings (`derived_value_mismatch` row 0,
`derived_formula_mismatch` row 1), not one merged or dropped result
(<<sec11>>). `missing` is excluded from the 4-tuple, matching F-CORR-3;
confirmed `LookupFormulaSpec` (`core/formulas.py:17-32`) has exactly five
fields and `_build_formula_enrichment` still hardcodes `missing=""`
unconditionally (<<sec-producer-defect>>), so the exclusion remains inert as designed. Each
of the four structural fields is independently pinned by the new
parametrized `test_formula_helper_structural_divergence_*` tests
(`lookup_sheet`, `source_key_column`, `lookup_key_column`,
`lookup_value_column`), all confirmed passing. No comparison against the
canonical scalar occurs for a `LookupFormulaSpec` cell (the `isinstance`
branch never falls through to the `else: _norm(cell)` branch).

*Verdict: FORMULA SINGLE-KEY CORRECT.*

== Formula multi-key carve-out (F-CORR-2) [[sec-formula-multi-key]]

`multi_key = len(payload_keys) != 1 or len(lookup_keys) != 1` is computed
from the full, untruncated `InterpretedEnrichLookupProvenance` tuples
(confirmed at Slice 1 and re-confirmed here to remain untruncated). The guard
runs before `_canonical_value_map`/`_column_mismatch_indices` are ever
called, and before any per-cell `[0]`-indexed comparison. Independently
reproduced end to end through the real production path
(`enrich_lookup(..., keys=["id","part"], helper_value_mode="formula")`):
`_build_formula_enrichment` still writes the identical, `part`-dropping
`LookupFormulaSpec` into both rows (confirmed unchanged, <<sec-producer-defect>>), and
`apply_derived_column_policy` correctly reports exactly one
`unverifiable_enrich_lookup` finding -- never `derived_formula_mismatch`,
never zero findings, never a certified-correct result.

`_column_mismatch_indices` can never receive a multi-key + formula
combination in practice: it is reached only after the
`multi_key and _contains_formula_cell(payload, helper_cols)` guard already
returned early whenever *any* in-scope helper column holds a
`LookupFormulaSpec`; if that guard is false, no formula cell exists in scope
at all, so the `expected_formula`/`isinstance` branch inside
`_column_mismatch_indices` is computed but never actually matched for that
call. Multi-key scalar-only helper columns are independently confirmed still
checked normally (<<sec5>>'s multi-key values-mode repro).

Independently constructed a case the test suite does not cover -- two helper
columns under one multi-key relationship, one values-mode ("note"), one
formula-mode ("title") -- and confirmed the *entire call* reports one
`unverifiable_enrich_lookup` finding naming both columns
(`columns: "note, title"`), not a partial certification of "note" alongside
an unverifiable "title". This matches the accepted design's call-level,
fail-closed semantics (this task's own Area 7, question 5) and is coherent
with Area 12's short-circuit-precedence expectations.

Missing lookup frame / missing key column / duplicate-key precedence ahead of
the multi-key-formula check remains coherent, and is not merely a stylistic
ordering choice: the duplicate-key check needs `lookup_keys` already
confirmed present as columns (<<sec6>>), so it structurally must follow the
missing-key-column check, and both structurally must follow
`missing_lookup_frame` (no `lookup_df` to query key columns from) --
confirmed the implementation's order is not just coherent but the only order
that avoids a raw pandas exception.

No accidental certification of the producer defect was found in any
constructed case.

`_contains_formula_cell(payload, helper_cols)` (`mismatch.py:178-183`) is
called with the already payload-filtered `helper_cols`, so `payload[helper_col]`
never raises `KeyError` for a declared-but-absent column. On an empty payload
(`payload.iterrows()`/column access over zero rows), the generator expression
yields nothing and `any(...)` correctly returns `False` -- no crash, no false
positive. It performs a plain `isinstance` scan, not an equality/hash
operation, so `LookupFormulaSpec`'s frozen-dataclass identity semantics are
irrelevant here. It runs only on the `multi_key` path (the uncommon case),
scans each in-scope helper column's cells once, and is not a performance
concern at this domain's scale; this review does not treat it as one, per
this task's own instruction not to turn this into a performance audit.

*Verdict: F-CORR-2 IMPLEMENTED CORRECTLY.*

== Unresolved/missing payload-key semantics [[sec9]]

`_column_mismatch_indices`'s `canonical_row is None: continue` skip runs
before the per-cell `isinstance` dispatch, so an unresolved payload row (its
join-key value absent from the current canonical map) is skipped uniformly
for both scalar and formula cells -- confirmed by direct read, not merely
accepted from the implementation record's Section 5 claim. This is a direct,
unavoidable structural consequence of moving the unresolved-row skip *above*
the per-cell mode branch rather than duplicating it inside each branch;
nothing in the corrected design or its test plan (<<sec5>> of `34223d4`)
distinguishes the two modes for this case, and inventing an asymmetry here
would have been the undesigned choice, not this. Not a new implementation-
time semantic extension requiring separate authorization -- a reasonable
direct consequence of the accepted per-cell evaluator shape.

No metadata was added; `missing` policy is still not inferred or
reconstructed anywhere (Section 6.2 of the design remains unreopened).

*Verdict: reasonable, undisputed consequence of the accepted design; no
correction required.*

semantic ownership over byte-identical incidental diagnostic prose -- favors
the change made.

*Classification: NOTE.* Not MINOR: no test breaks, no information is lost
(only relocated within the same message), and the wording is not part of any
documented, gated surface (`interfaces_and_gates.adoc` does not enumerate

[[find-1]]
=== FINDING-001 -- MATERIAL -- missing-key-column fail-closed guarantee silently bypassed when every declared helper column is also absent from the payload

*Observation:* `evaluate_lookup_mismatches` (`enrich_lookup/mismatch.py:84-175`)
computes `helper_cols` filtered to columns *currently present in the
payload* (`mismatch.py:100`: `helper_cols = [col for col in
interpreted.helper_columns if col in payload.columns]`), then uses that
filtered value for the early "nothing to check" gate
(`mismatch.py:106-107`: `if not payload_keys or not helper_cols: return
LookupMismatchReport()`) -- *before* the "fail closed when key columns are
absent" check that follows it (`mismatch.py:109-121`). Pre-Slice-2 (and, by
the byte-level equivalence independently confirmed in <<sec5>>, at every
point back through Slice 1), the equivalent gate used the *declared*,
unfiltered `helper_columns` (`interpreted.helper_columns`, not filtered by
payload presence), with the payload-presence filter applied only later,
per-column, *inside* the per-row loop -- structurally *after* the
missing-key-column check had already had its chance to fire.

The consequence: when the payload is missing **both** a declared join-key
column **and every** declared helper column simultaneously, the new gate's
`not helper_cols` (now empty via the payload filter) short-circuits *before*
the missing-key-column check ever runs, silently returning an empty
`LookupMismatchReport()` -- no `unverifiable_enrich_lookup` finding, and (via
DCP's unchanged translation) no failure under `fail_on_mismatch`.

*Evidence (independently reproduced, not inferred from reading alone):* a
minimal `_meta.derived.sheets.matrix.enrich_lookup` record declaring
`source_key="story_id"`, `lookup_key="id"`, `helper_columns=["title"]`
against a `matrix` payload frame containing neither `story_id` nor `title`
(only an unrelated column). Run through `apply_derived_column_policy`
directly (the real public entry point, no internal bypass) at the reviewed
commit (`f4a0ecc`):

[source,text]
----
warn_on_mismatch -> len(findings) == 0
fail_on_mismatch -> NO RAISE
----

The identical script, run unmodified against an isolated `git worktree add
... f4a0ecc^ --detach` (Slice 1's accepted, independently-reviewed state --
`f4a0ecc`'s direct parent, `83885c9`, is docs-only and touches no source):

[source,text]
----
warn_on_mismatch -> 1 finding: rule_type='unverifiable_enrich_lookup',
  message="Cannot verify enrich_lookup helpers: payload key column(s)
  ['story_id'] absent from frame 'matrix'. Provenance
  _meta.derived.sheets['matrix'].enrich_lookup."
fail_on_mismatch -> raises: "Derived column policy failed:
  - unverifiable_enrich_lookup: ..."
----

This is a directly observable, empirically confirmed behavior regression
between the accepted Slice-1 baseline and the commit under review, reachable
through `apply_derived_column_policy`'s ordinary public surface with no
malformed or adversarial input -- only a payload frame that has already lost
both the join-key and the helper column the provenance record still names
(a plausible state: some intervening step or manual edit removed both
columns without also clearing `_meta.derived.sheets[frame].enrich_lookup`).

*Why this is not covered by `make test`:* no existing test combines "missing
payload/lookup key column" with "helper column also absent from payload" --
every existing missing-key-column test
(`test_asymmetric_missing_payload_key_column_*`,
`test_asymmetric_missing_lookup_key_column_*`, read directly at
`test_derived_column_policy.py:628-664`) drops *only* the key column,
leaving the helper column (`title`) present, so the payload-filtered
`helper_cols` stays non-empty and the divergent gate is never exercised by
the current suite.

*Concrete risk if ignored:* `fail_on_mismatch` exists specifically to raise
loudly on exactly this class of "cannot verify" condition rather than pass
silently (the inherited code comment cites `review R002-IMP-002`, a
previously closed finding with this identical purpose). A pipeline that
relies on `fail_on_mismatch` to catch a payload whose declared `enrich_lookup`
relationship has become internally inconsistent (both its key and its value
columns gone) will now pass silently instead of failing, for exactly the
narrow but plausible combination where cleanup has removed more than the
metadata record still expects. This also directly contradicts the
implementation record's own Section 4 ("Values-mode behavior preserved
exactly... the one change is structural, not semantic: `_canonical_value_map`
no longer needs its former 'first occurrence wins' branch...") and Section 14
("No other behavior changed... confirmed by the unmodified assertions") --
both of which are therefore inaccurate as written; a fourth, undisclosed
behavior change exists.

*Recommended action:* decouple the "no helper columns declared at all" gate
from the payload-presence filter. The gate at `mismatch.py:106-107` should
test emptiness against `interpreted.helper_columns` (the declared, unfiltered
tuple -- matching every pre-Slice-2 version of this check), not the
payload-filtered `helper_cols`; the payload-filtered variable should continue
to be used only where it already correctly is (canonical-map construction,
`_contains_formula_cell`, and the per-column iteration), preserving the
existing, independently-confirmed-correct "silently skip a helper column
individually absent from the payload when the key columns are otherwise
fine" behavior (<<sec5>>). Add a regression test pinning the specific
combination this finding demonstrates (key column *and* every declared
helper column absent from the payload -> `unverifiable_enrich_lookup` under
`warn_on_mismatch`, raise under `fail_on_mismatch`) so this exact class of
gate-ordering regression cannot recur silently. Re-verify Section 4/14 of the
implementation record once corrected.

*Disposition:* MATERIAL. Blocks Slice-2 acceptance. Scope of correction is
narrow and localized to `enrich_lookup/mismatch.py::evaluate_lookup_mismatches`'s
gate logic plus one new test; no other file, no design reopening, and no
change to the two authorized intentional behavior corrections is implicated.
