== 1. Verdict

*B -- BOUNDED CORRECTION REQUIRED.* The provider-boundary architecture direction
is correctly realized: an explicit provider-neutral `AgentExecutionPort` exists,
`CodexCliAdapter` is the sole concrete implementation and the only owner of
Codex/OpenAI transport and dialect knowledge, the mutable `adapter.outcome`
side-channel is gone from the type surface, the OpenAI strict-schema projection
has moved out of the domain serializer and derives from canonical contract facts,
the two historical live defects are caught offline, and the coordinator suite is
green (108 passed) with no provider invocation.

However, the refactor introduced one concrete, reproducible weakening of the
uncertain-dispatch / reconcile authority (finding *S4AC-R1*, BLOCKING): removing
the `adapter.outcome` side-channel also removed the *signal* the old
general-exception handler used to decide whether the provider boundary had been
crossed. The new blanket `except Exception: dispatch_path.unlink(); raise` in
`run_real_one_hop` now deletes the dispatch marker for *any* post-acceptance
exception -- after the provider has run and possibly committed -- causing the
coordinator to forget a consumed, repository-mutating Hop. This is exactly the
class of authority regression the slice was required to avoid. It is bounded and
correctable without redesign; hence verdict B, not C.

A second, non-blocking conformance-independence gap (*S4AC-R2*, IMPORTANT) is that
the offline layer treats `const` as a supported OpenAI strict keyword on the
implementer's own authority; that specific rule could not be confirmed against
primary OpenAI documentation and primary-adjacent evidence indicates the
documented single-value idiom is `enum`. This does not block acceptance of the
boundary but must be resolved (cheaply, offline) before Level 3, because it
re-creates the "discover one dialect rule live" failure mode 4A-C exists to end.

== 4. Failure / uncertainty semantics (highest-priority area)

=== S4AC-R1 (BLOCKING) -- post-acceptance exception deletes the dispatch marker

*Invariant violated:* WFC-AUTO-02 ("once the atomic dispatch marker exists,
acceptance that cannot be disproved is conservatively charged as one Hop and
never replayed"; "absence of a dispatch marker proves no Hop consumption"),
WFC-FAIL-01 ("failure/malformed result after adapter acceptance consumes a Hop"),
WFC-FAIL-04 ("uncertain state enters common `reconcile_required`; it never
replays automatically").

*Exact code:* `scripts/workflow_coordinator/slice4.py:187-189`

[source,python]
----
    except Exception:
        dispatch_path.unlink(missing_ok=True)
        raise
----

Compared with the accepted prior behavior at `a9e6d620`
(`slice4.py`, general-exception path):

[source,python]
----
    except Exception:
        if adapter.outcome is None:          # provider boundary NOT crossed
            dispatch_path.unlink(missing_ok=True)
        raise
----

The old handler unlinked the marker *only when the provider had produced no
transport outcome* (`adapter.outcome is None`), i.e. only for genuinely
pre-acceptance failures; when the provider had run it *retained* the marker,
preserving the uncertain dispatch for explicit reconcile. The refactor moved the
transport outcome inside `vertical.run_one_hop`, so `run_real_one_hop` can no
longer observe whether the boundary was crossed for an *arbitrary* exception. The
outcome is now re-exposed to the caller *only* via `ExecutionResultValidationError`
(the two spots in `run_one_hop` that check `candidate_result is None` and
`validated_result`). Every *other* exception raised after `adapter.execute()`
returns -- and there are several, none caught inside `run_one_hop` --
falls through to the blanket `except Exception` and unconditionally deletes the
marker.

*Post-acceptance raise sites in `vertical.run_one_hop` (all uncaught there,
all reached only after the provider has run):*

* `observe_hop(...)` -> `git_facts._git(..., check=True)` raises
  `GitPreflightError` on any failing Git fact command (e.g. a stale
  `.git/index.lock` left by a `--sandbox workspace-write` child killed on
  timeout, or a transient Git error);
* `_subject_anomalies(...)` -> `subprocess.run(("git","show",...), check=True)`
  raises `CalledProcessError`;
* `run_evidence(...)`, `record_hop(...)`, `reduce_result(...)`,
  `checkpoint_projection(...)` -> any unexpected raise.

None of these is `ExecutionResultValidationError` or `CodexCliError`, so each
reaches `slice4.py:187` and removes the dispatch marker.

*Concrete failure mode (deterministically reproduced):* a fake CLI that commits
to the agent workspace and emits a valid, correlated envelope was run through
`run_real_one_hop`; `vertical.observe_hop` was then forced to raise (modelling a
transient post-commit Git failure) *without modifying any committed runtime
code*. Result:

----
raised: RuntimeError: simulated transient git failure after acceptance
observe_hop invoked (post-acceptance):  1
provider ran + mutated workspace:        True
provider created a commit:               True
dispatch.json marker survived:           False      <-- REGRESSION
run.json snapshot present:               True   (stale pre-hop snapshot, hop_used unchanged)
----

The provider consumed a Hop and mutated Git; the marker was deleted and the only
on-disk `run.json` is the pre-dispatch snapshot (`hop_used` unchanged, HEAD
pointing at the old base). On a later resume/reconcile the coordinator sees *no
dispatch marker* -> concludes no Hop was in flight (WFC-AUTO-02) -> the consumed,
committing Hop is forgotten, is not routed through `reconcile_required`, and can
be replayed against a now-mutated repository. This is precisely the
"can the coordinator accidentally forget an uncertain dispatch?" probe -- answer:
yes.

*Why the existing tests do not catch it:* the only test exercising the general
`except Exception` path
(`test_real_driver_cleans_marker_for_local_prompt_failure_before_spawn`) triggers
a *pre-spawn* prompt-assembly failure and asserts the fake never ran
(`not executions.exists()`). No test covers a post-acceptance exception, so the
green suite is consistent with the regression.

*Required correction scope (bounded; do NOT implement here):* restore the
pre/post-acceptance distinction at the failure boundary. Options, smallest first:

. Make `vertical.run_one_hop` fail closed for its *post-acceptance* region by
  attaching the transport `AgentExecutionOutcome` to any exception raised after
  `adapter.execute()` returns (e.g. wrap `observe_hop`/evidence/reduce/checkpoint
  raises in `ExecutionResultValidationError`, or a sibling carrier), so
  `run_real_one_hop` routes them to the existing uncertain-recovery /
  marker-retaining path; and
. In `run_real_one_hop`, treat an *unclassified* exception as *uncertain*
  (retain the marker, enter reconcile) rather than deleting it -- deletion must be
  reserved for exceptions proven to be pre-acceptance (`preflight` ->
  `Slice4Error`, prompt-assembly `ValueError`, `CodexCliError` launch/timeout<=0).

The `CodexCliError` branch (`slice4.py:184-186`) is *safe*: `CodexCliError` is
raised by `CodexCliAdapter.execute` only before `Popen` succeeds (timeout<=0, or
`OSError` on launch), so the process never started and marker removal is correct.
The regression is solely the blanket `except Exception` branch.

*Direct-regression surface:* `run_real_one_hop` (slice4.py), `run_one_hop`
(vertical.py); the reconcile/`recover_uncertain_dispatch` path is unchanged and
should be reused.

=== Other failure paths (verified correct)

* candidate_result absent / malformed / uncorrelated -> `ExecutionResultValidationError`
  -> `observe_hop` + `recover_uncertain_dispatch` + checkpoint, marker retained,
  status `reconcile_required`. Covered by
  `test_real_driver_recovers_post_spawn_uncertainty_with_external_anchors`
  (marker + run + checkpoint all present; HEAD unchanged; single execution). This
  path is correct.
* Unlaunchable executable -> `CodexCliError` -> `Slice4Error`, `hop_used==0`,
  marker removed. Correct (pre-acceptance).
* A raise inside the `ExecutionResultValidationError` recovery block (e.g. the
  re-`observe_hop`) propagates without hitting the sibling `except Exception`,
  so it retains the marker -- fail-closed-to-human. Acceptable.
* `KeyboardInterrupt`/`SystemExit` (BaseException) are not caught by `except
  Exception`, so an operator interrupt mid-Hop retains the marker. Correct.

== 5. Port contract review

`AgentExecutionRequest` (invocation, prompt, repository, `result_contract: str`,
timeout) and `AgentExecutionOutcome` (candidate_result, returncode, timed_out,
stdout, stderr, diagnostics) express exactly the cross-boundary facts the current
path needs and no speculative framework. `capabilities`/`ExecutionPolicy` from the
architecture sketch was correctly *not* added (single-contract V1). Both types are
`frozen`. Good.

*S4AC-R3 (MINOR) -- `result_contract` is an unenforced promise.* The port request
carries `result_contract: str`, but `CodexCliAdapter.execute` never reads it: it
unconditionally emits `structured_result_envelope_openai_schema()`. Under a
single-contract V1 this is acceptable, but the field currently makes a semantic
promise the adapter neither validates nor supports. Additionally the identifier is
passed two ways: `vertical.py` uses the named constant
`ROUTING_RESULT_ENVELOPE_CONTRACT`, while `slice4.invoke_codex` passes the bare
literal `"routing-result-envelope/v1"` (`slice4.py:137`) -- a duplicated
string that can silently drift. Recommendation (non-blocking): have the adapter
assert it supports the requested contract (fail closed on anything else) and use
the shared constant everywhere. This documents the single-contract V1 boundary
without adding a registry.

== 6. Semantic-result authority (transport vs semantic)

`AgentExecutionOutcome` is correctly pre-semantic: `run_one_hop` still parses,
validates, and correlates via `validated_result` before any reduction. Transport
`returncode`/`timed_out`/tails never establish acceptance.

*Nonzero-returncode-with-valid-result disposition (verified):* `CodexCliAdapter`
returns `candidate = result.read_text() or None` *regardless of returncode*; if
the result file holds a valid correlated envelope, `run_one_hop` validates and
reduces it even when `returncode != 0` (transport `diagnostics` are recorded on
the outcome but do not block). This is **pre-existing intended semantics**, not a
refactor artifact: at `a9e6d620`, `invoke_codex` set `acceptance="established"`
from `validated is not None` independent of returncode, and `_CodexAdapter.invoke`
raised only when the result was absent. The behavior is consistent with WFC-GIT-02
/ WFC-SEC-02 (transport claims are hints; result validated and Git observed
independently). No finding.

`test_nonzero_without_result_is_uncertain` (nonzero + no result -> uncertain) and
`test_nonempty_invalid_result_is_not_established` (nonzero/valid transport but
malformed/uncorrelated payload -> not established) confirm the split.

== 7. OpenAI conformance audit

Verified against the emitted projection and primary/primary-adjacent OpenAI
documentation (no provider invoked). The projection's *structural* rules are
correct for OpenAI strict Structured Outputs:

* root is a single `object` (not `anyOf`) -- OK;
* every object: `additionalProperties:false` and `required == properties` --
  encoded and asserted;
* nullability via `type:["string","null"]` (finding_id, successor_ref) and via
  `anyOf:[{"type":"null"}, escalation]` (escalation) -- both are documented strict
  idioms; `anyOf` appears only at non-root nodes -- OK;
* `enum` on `outcome`, `proposed_state`, `kind` -- OK;
* every node carries an explicit `type`, including the `anyOf` branches and the
  `const`-bearing `schema_version` -- the rule 11.4.4 discovered, now enforced.

*S4AC-R2 (IMPORTANT) -- `const` support is assumed, not documented.* The
conformance layer's supported set `_STRICT_KEYS` (`codex_adapter.py:37`) includes
`const`, and the projection emits `schema_version:{"type":"integer","const":1}`.
I could not confirm from primary OpenAI documentation that `const` is in the
supported strict subset; the reachable primary page defers to a
"supported-schemas" section that the fetcher could not render, and
primary-adjacent evidence (OpenAI developer-community threads, and the documented
examples that pin single values with `enum`) indicates the documented single-value
idiom is `enum:[value]`, with `const` frequently reported as unsupported/ignored
in strict mode. Consequences:

* if `const` is not accepted live, `schema_version` is provider-invalid and the
  *offline layer will not catch it* -- reproducing the exact 11.4.4 failure one
  rule deeper, which is what 4A-C exists to prevent;
* the checker and the generator *share* the `const`-is-supported assumption
  (Section 7 of the prompt): `assert_openai_strict_schema` blesses `const` and
  `structured_result_envelope_openai_schema` emits `const`, with no independent
  rule anchoring `const`'s validity. Other rules *are* independently anchored
  (e.g. `test_conformance_rejects_constructs_outside_the_projection_subset`
  rejects `oneOf`), so the layer is partly independent -- but not for `const`.

Mitigating context (why IMPORTANT, not BLOCKING): FTR 11.4.5 acceptance item 5
*explicitly* contemplates "const-bearing nodes" (typed), so the implementer
followed the authorized design; and I could not obtain the verbatim current
(2026) supported-keyword list to *prove* `const` is rejected. This is therefore a
verification/independence gap and a live-compatibility risk, not a proven live
defect. Required correction scope (cheap, offline, before Level 3): either (a)
cite the primary OpenAI rule that lists `const` as supported and record it as the
anchor for `_STRICT_KEYS`, or (b) switch the projection to the documented
`enum:[1]` idiom for `schema_version` and drop `const` from the supported set.
Until one is done, the evidence phrase "FULL DOCUMENTED STRICT SUBSET ... CHECKED
OFFLINE" is not justified for the `const` rule specifically.

*S4AC-R5 (MINOR) -- dead const guard.* `codex_adapter.py:63-64`
(`if "const" in node and "type" not in node: raise ... "const requires explicit
type"`) is unreachable: line 59 already raises when `type` is absent, so by line
63 `type` is always present. Harmless, but it misleads a reader into thinking
`const` gets a dedicated rule; remove it or fold the intent into the generic typed
check.

== 8. Test-quality assessment

The offline suite fails for meaningful mutations, not merely generator/checker
symmetry:

* opaque result object -> "object must be strict" (historical defect 1);
* untyped `schema_version` const -> "explicit type" (historical defect 2);
* nested missing `type` on `findings.items.invariant` -> "invariant: explicit
  type";
* missing `type` on a nullable `anyOf` branch -> "anyOf[0]: explicit type";
* `oneOf` present -> "unsupported keywords" (an independently-stated rule, not
  symmetry);
* `required != properties` and `additionalProperties != false` -> rejected;
* projection-derives-from-contract drift guard: `required` sets equal
  `ROUTING_RESULT_REQUIRED_KEYS` / `FINDING_DELTA_KEYS`.

Independence: most rules are restated independently of the generator; the notable
exception is `const` (S4AC-R2), where checker and generator share one unverified
assumption. Recommendation: anchor `_STRICT_KEYS`'s membership (especially
`const`) to a cited primary rule, or narrow it to the `enum` idiom.
