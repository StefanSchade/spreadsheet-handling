== Trusted-Ingress facts actually relied on

The assessment relies on current, implemented guarantees, rather than on an
earlier FTR or review statement:

* Architectural Layers, “Establishing and Re-establishing the Domain Scalar
  Language”, defines an Ingress-Conformant Domain Payload: every ordinary
  `DataFrame`/`ExactTable` cell is one of the six scalar categories and `_meta`,
  where present, is a bounded acyclic substrate of exact-string-keyed exact
  `dict`/`list` containers and ordinary scalar leaves.
* `domain.ingress.coordinator:INGRESS_RULES` proves the executed order:
  structural admission, the Legend Blocks delegate, then complete metadata
  admission. `structural_admission:admit_ordinary_frames` accepts `DataFrame`
  *and* `ExactTable`, checks physical labels, and visits every ordinary cell.
  `metadata_admission:admit_metadata_substrate` rejects non-grammar metadata
  objects and cycles.
* `application.managed_pipeline:establish_initial_state` calls
  `run_domain_ingress` before configured managed steps; an uncertified step
  return is re-admitted before a later ordinary operation. Thus the guarantee
  is real on framework-managed paths, not merely intended policy.
* `pipeline.execution:run_pipeline` does no establishment or re-establishment,
  while direct transformation calls have local contracts. These are secondary
  execution context only: their caller preconditions include supplying an
  Ingress-Conformant payload, so they do not make a hostile-object guard
  necessary.

The primary retention test is: *does Trusted Ingress actually establish the
condition a guard protects?* For every retained guard below, the answer is no.
Ingress establishes a generic carrier and metadata grammar, not FK relation
schema, Lookup provenance schema, DataFrame carrier capability, configuration
or step-argument validity, required source/target columns, uniqueness, or
formula/output semantics. In particular, a generic-valid metadata value such
as a string where FK expects a relation list passes the generic E3 grammar; it
remains a family contract question.

== Ingress-redundant / historical-unreachable items and tests

*None found.* A whole-family signature sweep for hostile-object defences
(`callable(`, module/generator/function types, binary or file-handle probes,
opaque-object introspection, and exotic-comparison handling) found no such
logic in `fk_helpers`, `enrich_lookup`, or `domain.validations.fk_helpers`.
The remaining checks are all enumerated above and protect conditions Trusted
Ingress does not establish.

Accordingly, no redundant-behaviour test is removed or rewritten in this hop.
Focused tests instead support retained contracts:
`test_fk_helpers_helper_columns_validation.py` tests the strict FK leaf error;
`test_fk_helper_primitives_policy_driven.py` tests missing/malformed policy and
provenance-driven primitive behavior; and
`test_enrich_lookup_provenance_interpretation.py` plus
`test_enrich_lookup_provenance_reconciliation.py` test strict Lookup record
interpretation and the H5 reconciliation disposition.

== Next implementation slice

[.lead]
*NO SAFE SLICE SELECTED.*

The smallest proposed deletion would be the `getattr`/missing-column fallback
in `source_frame_has_column` or FK cleanup. Current evidence rejects that
selection: `ExactTable` is explicitly admitted by E2, while these FK helpers
require DataFrame/header operations, and a configured source header may
legitimately be absent in a replayed snapshot. Removing either fallback would
change a family transformation contract rather than delete a guard for an
ingress-unreachable payload.

No source or test change is authorized by this assessment. A later slice can
be selected only after evidence identifies a concrete local check whose
protected condition is established by Trusted Ingress on every supported
invocation contract and whose removal does not weaken `ExactTable` or family
metadata/schema behavior. Direct and `run_pipeline` caller-precondition
surfaces provide execution context, but do not excuse nonconformant payloads
and are not the primary retention rationale.
