== 2. Review Area 1 -- Reproduce the FK/Lookup defect

*Verdict: CONFIRMED, and materially broader than reported.*

The assessment's exact trace (Section D) was independently reproduced without
any `_meta` mutation, legacy shape, or unsupported internal call -- see
<<repro>> above. Values genuinely differ (`lookup-alpha`/`lookup-beta` vs.
what FK's own join would have produced, `Beta1`/`Beta2`), so this is not a
same-value coincidence that would make the defect cosmetic.

Beyond the reported trace, this review found the defect is *also* reachable:

* with the FK materialization primitive (`add_fk_helpers`/`enrich_helpers`)
  never having executed at all in the session -- deletion happens purely
  through the durable `_meta.helper_policies.fk.relations` fallback that
  `drop_helpers`/`_columns_to_drop_by_sheet` and
  `derived_column_policy.py::_safe_policy_helper_names` both implement
  (<<find-001>>);
* through a second, independent production executor,
  `apply_derived_column_policy(policy="drop")`, not only through
  `fk_helpers/drop.py` (<<find-002>>).

Reachability classification confirmed: this is *supported current runtime*,
using only `configure_fk_helpers`, `enrich_lookup` (the exact registered
`enrich_lookup:enrich_lookup` target), `add_fk_helpers`
(`make_apply_fks_step` delegates directly to `enrich_helpers`), and
`remove_fk_helpers` (`make_drop_helpers_step` delegates directly to
`drop_helpers`) -- confirmed against `pipeline/steps.py` and
`registries/pipeline_step_registry.json`. It is not a synthetic-state,
historical-compatibility, or theoretical-unsupported case.

== 3. Review Area 2 -- Is this really a deletion-authority defect?

*Verdict: G (research's interpretation) is best supported; A, B, E, F are
rejected by direct evidence; C and D are each insufficient/worse, not
disproven-as-worthless.*

* *A (reserved FK namespace).* Rejected. No maintained document reserves the
  `_<target>_<field>` shape (or any shape) to FK. `enrich_lookup` accepts an
  arbitrary caller-chosen helper field name with no namespace check, and this
  review's repro used that name only to reproduce the collision -- nothing in
  `enrich_lookup/operation.py` or `helper_policies.py` special-cases labels
  that look FK-shaped. `docs/ai_info/concepts_fk_helpers.adoc` calls the
  underscore prefix "a naming convention," not an authority claim.
* *B (pipeline-ordering contract forbids overlap).* Rejected. No maintained
  document orders FK relative to Lookup; the FK/Lookup Cycle-0 assessment
  (accepted, `ACCEPT WITH MINOR CORRECTIONS`) explicitly treats them as fully
  independent capabilities with no anti-overlap rule, and
  `docs/semantic_model/12_contract_matrices.adoc`'s FK matrix says nothing
  about Lookup at all.
* *C (skip is merely a bug; fix to reject).* Insufficient alone, not
  worthless. Rejecting the same-run collision inside `enrich_helpers` would
  close the same-run variant this review reproduced, but does *not* close the
  durable-policy-fallback variant (<<find-001>>) or the second-executor
  variant (<<find-002>>), because neither of those ever calls the
  collision-checking code path (`core/fk.py::apply_fk_helpers`) at all.
* *D (FK should overwrite/recompute, becoming the physical producer).*
  Rejected as worse, not merely insufficient. If FK silently overwrote
  Lookup's materialized values, FK would indeed become the true physical
  producer -- but Lookup's *own* provenance record would then be the false
  one (it would still claim to have produced a column FK just overwrote),
  and a live, human-edited/consumed value would be silently destroyed with no
  warning. This trades a wrongful-deletion defect for a silent-corruption
  defect and does not resolve the authority question; it only moves the false
  claim to the other producer.
* *E (provenance means "requested projection shape"; cleanup entitled to
  enforce it).* Rejected. No maintained document authorizes this reading;
  `12_contract_matrices.adoc:94-96`, `fk_helper_metadata.adoc`, and
  `concepts_fk_helpers.adoc` all say the opposite -- provenance records
  *materialized* state, not requested shape (<<find-003>>).
* *F (solely a provenance-wording problem).* Rejected by direct
  reproduction. Repro 2 and repro 3 delete the column with *zero* provenance
  of any kind existing for it under the FK subkey -- there is no wording to
  correct in that path, because no FK provenance entry is ever written in
  that scenario. The defect survives even where the wording claim in
  <<find-003>> does not apply.
* *G (research's interpretation: production/request/reliance/deletion are
  distinct; the missing decision is real).* Best supported, with the
  refinements in <<find-001>>, <<find-002>>, and <<find-007>> (below):
  "reliance" is not the missing concept -- "verified current physical
  producer, as a precondition for deletion" is.

== 4. Review Area 3 -- Does "claimant/current reliance" add real value?

*Verdict: not evidenced as necessary; premature as a named primitive.*

See <<find-007>>. The reproduced defect, in all three variants, is fully
described and would be fully fixed using only: *physical producer* (who
actually wrote the column this run, if anyone), *requested/declared policy*
(what a family's configuration says it wants, transient or durable), and a
*deletion precondition* ("before removing a column identified by a
requested/declared name, verify the requesting family is its current
physical producer"). No case in the reproduced evidence requires modeling
"this capability currently relies on the artifact continuing to exist" as a
concept distinct from "did this capability physically write it." H5 itself is
not a reliance/registration/release protocol -- it is a stateless,
recompute-on-demand truthfulness check
(`reconcile_enrich_lookup_provenance`) with no registration call, no release
call, and no enforcement obligation on any other owner. A "claimant" concept
would become necessary only under a *future* adopt/share design (Section I's
own "Unresolved" question), which is not evidenced as required by any current
supported flow.

== 5. Review Area 4 -- Four-family evidence claim

*Verdict: the assessment's own count is accurate and not inflated; this
review adds a within-family refinement.*

Independently confirmed in code:

* Discriminator split (`framecheck.py:28`) raises
  `ValueError(f"Generated target frame(s) already exist: ...")` -- a hard,
  pre-mutation reject, not a silent skip-and-claim. This is a genuine
  counterexample (proves "reject" is a workable, already-used pattern), not a
  second instance of the FK/Lookup defect.
* XRef (`xref_crosstable/operation.py:80-142`) gates `drop_source` behind
  explicit distinctness and loss-check `ValueError`s *before* contributing a
  deletion command. This is a genuine counterexample (an explicit,
  caller-asserted, guarded deletion authority), not a second defect instance.
* Cell Codec (`cell_codec/frame.py::_reject_helper_participating_columns`)
  reads helper provenance only to *exclude* those labels from participating
  payload; it writes no claim and requires no continued existence. Genuine
  counterexample for "consumer != claimant."

The assessment's own closing sentence in Section E ("Only the FK/Lookup case
currently proves multiple simultaneous owner records over one physical
derived column. The other three establish necessary limits on any
generalization") is independently confirmed accurate. This review's
refinement: within the *one* evidenced defect family, this review found (not
merely one reachable path but) up to four reachable combinations -- two
executors (`drop_helpers`, `apply_derived_column_policy`) times two authority
layers (same-run transient provenance, durable-policy fallback) -- all
reducing to one root cause. This sharpens, but does not change, the
assessment's "one evidenced defect, three constraints" count.

== 6. Review Area 5 -- Framework contract vs. local FK rule

*Verdict: a bounded FK-only patch is evidenced as insufficient; the smallest
sufficient fix already spans two DMC-distinct modules.*

Constructing the smallest candidate local repair -- "FK must reject any
pre-existing requested helper column unless FK can prove it is its own
already-materialized helper" -- and testing it against this review's own
reproductions:

* It would close repro 1 (same-run collision through `enrich_helpers`).
* It would *not* close repro 2, because no call to `enrich_helpers`/
  `apply_fk_helpers` (the code containing the collision check) occurs in that
  scenario at all; the deletion happens entirely inside
  `drop_helpers::_columns_to_drop_by_sheet`'s durable-relation fallback.
* It would *not* close repro 3, because `apply_derived_column_policy` never
  calls `fk_helpers/enrich.py` or `fk_helpers/drop.py`; it has its own
  independent `_safe_policy_helper_names` fallback reading the same durable
  relation list.

Therefore the answer to the assessment's own question ("Could we safely fix
FK locally and stop?") is *no*, more concretely than the assessment itself
demonstrates: not because other materializing families need the same
vocabulary (Discriminator/XRef/Cell Codec do not exhibit the defect), but
because *this one* defect already requires a coordinated precondition across
two modules that the DMC's own family/executor model treats as separately
owned (`fk_helpers` is a family; `derived_column_policy.py` is "a
cross-capability executor with feature-aware contracts, not semantic owner,"
per the accepted FK/Lookup Cycle-0 assessment). A single-function patch
cannot be "local" in the DMC sense once it must be duplicated, consistently,
across an owner and an independent executor that already reimplements that
owner's fallback logic once (Cycle-0 Review 001's FIND-002, previously
characterized only as a readability/duplication concern) -- see <<find-002>>.

== 8. Review Area 7 -- Provenance semantics

*Verdict: confirmed and strengthened, not merely documented imprecisely.*

FK provenance's contract, per three independent maintained sources
(`12_contract_matrices.adoc:94-96`, `fk_helper_metadata.adoc` "Derived helper
provenance records materialized helper-column state," `concepts_fk_helpers.adoc`
"Derived helper-column provenance ... is materialized state, not the
policy"), is unambiguous: one entry per column FK actually wrote. Runtime
(`enrich.py::enrich_helpers` -> `_write_helper_provenance`) writes one entry
per *resolved relation definition*, independent of whether
`core/fk.py::apply_fk_helpers`'s `if helper_col in first_cols: continue`
fired for that specific definition. This is directly confirmed by repro 1:
after `add_fk_helpers` runs and skips (because Lookup's column already
occupies the label), the FK provenance entry for `_B_name` exists anyway.

Lookup provenance is comparatively accurate: it is written only for fields
`enrich_lookup` actually projected into the named output, and the operation
rejects a colliding *source*-frame helper before merging
(`_check_column_conflict`). It does not, however, name a release contract
(the assessment's own observation, confirmed).

== 9. Review Area 8 -- Deletion authority

*Verdict: confirmed empirically, not merely by document reading.* Repro 1
directly demonstrates that H5's post-mutation reconciliation
(`reconcile_enrich_lookup_provenance`) does not, and structurally cannot,
undo the physical loss: after `remove_fk_helpers` runs, Lookup's actual
materialized values (`lookup-alpha`, `lookup-beta`) are irretrievably gone
from frame `A`, and H5 only makes the *metadata* consistent with that loss
(both provenance records disappear together) -- it does not gate, prevent, or
even flag the deletion beforehand. The assessment's claim that "post-deletion
reconciliation cannot substitute for pre-deletion authority" is therefore not
just plausible prose; it is directly observable data loss in this review's
own reproduction.

Comparing cleanup contracts confirms the assessment's framing: XRef's
`drop_source` requires an explicit caller flag plus guarded loss checks
*before* contributing a command (pre-deletion authority, explicit); FK direct
cleanup and `derived_column_policy.py` both delete based on a requested-label
match with no physical-producer check (pre-deletion authority, absent). A
canonical concept is warranted (see <<conclusions>>, conclusion G) but it should be
scoped narrowly -- "verified current physical producer" -- not a general
reference-counted claim system.

== 10. Review Area 9 -- Collision policy vocabulary

*Verdict: only "create" and "reject" are evidenced as required today;
"adopt," "shared reliance," and "release" remain speculative.*

No current supported flow requires FK and Lookup (or any two families) to
legitimately *share* one physical column with both relying on its continued
existence. The reproduced defect is exactly the opposite of a legitimate
sharing case: Lookup never expected or wanted FK to have any claim on
`_B_name`, and FK's request collided by coincidence of label choice, not by
design. The minimum vocabulary the evidence requires is: absent -> create;
present -> reject unless the requester can prove (via a same-run
materialization check, or by direct verification against source/target data,
never via label-match alone) that it is the artifact's own prior output.
"Adopt"/"replace"/"shared reliance"/"release" should remain named as *future*
cases in the Design Phase, not built into the first canonical contract.

== 11. Review Area 10 -- Artifact identity

*Verdict: confirmed as out of scope, and the reproduced defect independently
proves why.* All three reproductions resolve column identity correctly and
without ambiguity throughout -- `_visible_label` and flat-label matching work
exactly as intended in every case; the wrongfully-deleted column is
*correctly identified* as `_B_name` by every consumer. The defect is entirely
about deletion *authorization*, never about misidentifying which physical
column a name refers to. This independently confirms the assessment's own
restraint (Section H) in not proposing a global identity model, and sharpens
it: identity mechanics are not implicated by the evidenced defect at all, so
a Design Phase that spent effort on artifact identity generalization would be
solving a problem this review's evidence does not show exists.

== 12. Review Area 11 -- Persistence and replay

*Verdict: this review's own reproduction reinforces "durable claim ledger
unnecessary," rather than merely failing to contradict it.* Repro 2 and
repro 3 show the defect is reachable *without* any transient claim/provenance
existing at all, purely from durable Intent (`_meta.helper_policies.fk`)
already present. This means the missing precondition ("verify current
physical producer") does not need new durable storage to be evaluated -- it
needs to be evaluated *at cleanup time*, from signals already available then
(has this exact primitive materialized this column in this run; or can it
independently verify, from current source/target data, that its own
projection currently occupies that label). No new persisted claim record
would add information a correctly-scoped runtime check could not already
supply on demand. This directly supports the assessment's own conclusion (not
merely leaves it unrefuted).

== 14. Review Area 13 -- Design-phase scope

*Verdict: AUTHORIZED WITH NARROWED / CORRECTED SCOPE.* The assessment's
Section N scope (FK Helpers + Lookup Enrichment mandatory; XRef, Discriminator,
Cell Codec, Workbook View, persistence, Trusted Ingress, schema maintenance

element this review found necessary: `derived_column_policy.py`'s FK-branch
(`_safe_policy_helper_names`, `_resolve_derived_identity`) must be named as a

Helpers," because it is a DMC-distinct cross-capability executor (not FK's

fixes only `fk_helpers/{enrich,drop}.py` and treats
`derived_column_policy.py` as an unrelated readability/duplication
follow-up (as Cycle-0 Review 001's FIND-002 characterized it) would ship
believing the defect closed while it remains open through the second
executor. No broader scope than the assessment's own Section N is
independently justified by this review's evidence; cells, arbitrary sheets,
rendered/backend artifacts, and a whole-Domain census remain correctly out of
scope.

== 15. Review Area 14 -- DMC feedback

*Verdict: not a DMC defect; a legitimate future specialization point, and
this review narrows the assessment's own proposed wording.* The assessment
proposes a fairly open DMC clarification menu ("create / prove compatible /
adopt / replace / decline?"). Given this review's evidence, the load-bearing
question is narrower and should be preferred if the DMC is ever amended: *"Before
a cleanup executor deletes physical state it identified via a requested or
declared name (transient provenance or durable policy), has it verified that
the requesting owner is that state's current physical producer -- not merely
that the name matches?"* This is consistent with, and a specialization of,

*Only partially.* A same-run FK collision-reject fix

re-discovering and re-implementing it per call site.

*Yes, warranted, narrowly.* Not a general derived-artifact lifecycle

both reproduced executors.

*Not necessary now* (this review narrows the assessment's own Section F

requested/declared policy, deletion precondition. Reserve "claimant/reliance"

=== E. Provenance

*Confirmed overloaded, and confirmed as an outright existing-contract
violation* -- not merely documented imprecisely (<<find-003>>). Three
independent maintained sources agree FK provenance should record only
materialized state; runtime does not. This should be corrected regardless of
the Design Phase, though correcting it alone is insufficient

*One genuinely evidenced defect family* (FK + Lookup), reachable through (at
least) two independent executors times two independent authority layers.

constraints/counterexamples, not additional defect instances -- confirmed
independently in code, matching the assessment's own (accurate,
non-inflated) self-assessment.

*Yes, deserves an explicit canonical concept* -- narrowly scoped to
"verified current physical producer," empirically confirmed necessary by
this review's own reproductions of real, unrecoverable data loss (<<review-area-8>>).

*Unjustified now*, and this review's own evidence actively reinforces that
