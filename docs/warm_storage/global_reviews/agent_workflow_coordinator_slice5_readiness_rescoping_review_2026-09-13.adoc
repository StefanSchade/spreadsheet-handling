== 1. Verdict

*B -- BOUNDED REVISION REQUIRED.*

The assessment's core direction is correct and well-evidenced: the
Run/Hop/reducer/Finding/budget model is genuinely `N>1`-capable without semantic
redesign; the real `N=1 -> N>1` gap is a serial continuation *driver plus
composition* obligations, not a new workflow model; the committed
WorkItem/profile/policy plus an explicit `max_autonomous_hops` and a deliberate
operator launch can carry the preauthorized envelope; no machine-readable
MaintainerGrant, supervisor, child Run, execution selector, continuing context,
or graph engine is required for the first increment; and an `N=2`
deterministic fake/local proof centred on false continuation is the right first
acceptance boundary.

The verdict is *B, not A*, for one precise reason. The assessment's
non-blocking disposition of action-authority WATCH-1 rests on the claim that the
accepted operator preflight *dominates every phase*. That is true for
`authorized_actions` but *not* for `authorized_scope`. Phase scope is currently
self-authorizing from the profile and is never constrained to the
`RepositoryPolicy.scope` or `WorkItem.scope` envelope. At `N>1` a second phase's
`authorized_scope` becomes live trusted-commit authority for H002. The
assessment mentions "prove phase scope across both phases" only as review
advice; it must instead be named as a per-phase preflight-domination invariant
equivalent to the actions check, and the proof matrix must include the
corresponding false case. This is a bounded correction to the authority
reasoning, folded into the 5A contract draft; it does not overturn any core
premise (Finding F1).

Three further WATCH-level refinements (F2--F4) sharpen the pre-dispatch gate
location, the two-write publication wording, and the governing-input
revalidation invariant. None is blocking and none requires code before the
contract is drafted.

== 3. Core-model challenge (Axis 1)

Attempted falsification of *CORE MODEL N>1-CAPABLE: YES*. It survives.

* One stable Run across Hops: `run_id` is immutable through `replace`-based Run
  succession; replays A and J keep it stable across 12 and 5 Hops.
* Monotonic `hop_used`/`hop_limit`: `record_hop()` requires
  `sequence == hop_used + 1`, rejects duplicates and exhaustion
  (`model.py:369-375`).
* H002 derivation: both `run_one_hop()` and `run_real_one_hop()` derive
  `H{hop_used+1:03d}`; nothing pins the literal `H001`.
* Phase transition then another Hop: `_apply_route` GOTO sets a new `phase` and
  `status=ready` (`reducer.py:201-214`); replay J drives four consecutive
  transitions.
* `Run.status` between Hops: `record_hop` moves `ready -> running`; reduction
  restores `ready` on GOTO. The intermediate `running` is exactly what the
  reducer requires to correlate a result (`reducer.py:256`).
* Cumulative Hop summaries and Finding identity across Hops: `hops` accumulates
  compact summaries; `_next_finding_id` yields stable run-local IDs; replay A
  accumulates five evidence refs on one persistent `F001`.
* Budget exhaustion before dispatch: an invocation-needing route at
  `hop_used >= hop_limit` yields `awaiting_human_budget` (`reducer.py:312-325`);
  replay H then proves `record_hop` refuses further charge.
* Checkpoint reconstruction: `checkpoint_projection` recomputes routes from the
  pinned profile and never persists route authority (`persistence.py:125-189`).

No hidden `N=1` assumption was found in dataclass shape, reducer invariants,
serialization, checkpoint projection, Hop identity, Git base/head ownership,
Finding IDs, or status transitions. `Run.current_head` is a first-class field and
the Git seam already accepts it, so nothing in the schema is `H001`-specific.
FTR WFC-AUTO-01 independently states the architecture *shall support empirical
N=1 -> 2 -> 5 -> 10 without model/schema redesign*. No model or schema change is
required to represent a correct H002.

CORE MODEL N>1-CAPABLE WITHOUT SEMANTIC REDESIGN:: *YES.*

== 5. Inter-Hop authority challenge (Axes 3, 4, 5)

=== 5.1 Pre-dispatch eligibility (Axis 3)

Confirmed: `run_one_hop()` calls the adapter before any status/budget check;
`record_hop()` -- the first such check -- runs only after execution. Worse,
`run_real_one_hop()` itself writes the dispatch marker and constructs the adapter
with *no* status/budget guard. Therefore a blind second call on a non-ready or
exhausted Run would consume a provider invocation before the late rejection. The
assessment correctly makes the pre-dispatch gate a Slice-5A BLOCKER and requires
"refusal precedes adapter entry" in the proof.

A driver-level gate placed before `run_real_one_hop()` is *sufficient for
correctness* provided the gated driver is the sole supported dispatch caller. But
because `run_real_one_hop()` is itself a provider-capable boundary that today
dispatches unconditionally, the safest placement is a fail-closed eligibility
assertion *at* that boundary, before the marker write -- defense-in-depth
matching the existing per-phase preflight-domination philosophy the assessment
otherwise relies on (Finding F2).

DRIVER-LEVEL PRE-DISPATCH GATE SUFFICIENT:: *YES* (sole-caller condition; F2
recommends also asserting at `run_real_one_hop`).

=== 5.2 Preauthorized Run authority (Axis 4)

`max_autonomous_hops` is a Run/WorkItem fact (WFC-MODEL-01, WFC-AUTO-01) framed
as a *bounded autonomy ceiling*. The assessment's position -- that a committed
WorkItem + profile + policy + explicit cap + deliberate launch is the whole
envelope, and that the contract must state the cap is *both* a ceiling and the
pre-authorized invocation envelope (up to N *while eligible*, never a retry) --
is sound and does not over-read the ceiling as authority. FTR 11.5 acceptance
item 1 ("stops exactly at the configured outer budget") supports it.

The bounded correction is the *scope* asymmetry (F1): phase `authorized_actions`
is dominated by the once-per-Run policy preflight, but phase `authorized_scope`
is not dominated by anything, and `WorkItem.scope` is dead for enforcement. For a
preauthorized `N=2` envelope to be truthful, phase B's `authorized_scope` must be
proven `subset` of the policy/WorkItem scope in the same once-per-Run preflight.

EXISTING AUTHORITY MODEL SUFFICIENT FOR PREAUTHORIZED N=2:: *WITH BOUNDED
CORRECTION* (add phase-scope domination; make ceiling-as-envelope explicit).

MACHINE-READABLE MAINTAINER GRANT REQUIRED:: *NO.* A grant would duplicate the
authority already carried by the committed inputs and would not supply the
missing continuation gate. FTR treats a machine-readable MaintainerGrant as an
unauthorized future item.

=== 5.3 Agent route vs authority (Axis 5)

The chain holds: an agent supplies only a route *string*; `reduce_result` applies
mechanical/human preemption first (`reducer.py:251-278`), then looks the string
up in the *current pinned* phase; an unknown key stops for human
(`reducer.py:281-288`); a GOTO can target only a phase validated at profile-parse
time (`serialization.py:455-460`); reduction, not the result, changes the phase.
`Reduction.autonomous_route` and `outcome=completed` are never consumed as
dispatch authority anywhere in the tree. Replay I confirms a completed result
carrying an escalation is still preempted to `awaiting_human`. Slice 5A must not
introduce a shortcut that treats any agent-produced field as dispatch authority;
the independent inter-Hop gate must stand between reduction and H002.

AGENT CAN SELF-AUTHORIZE H002:: *NO.*

== 6. Git / checkpoint / governing-input challenge (Axes 7, 8)

=== 6.1 Git / checkpoint ordering (Axis 8)

The per-Hop mechanics already publish the reduced snapshot and checkpoint before
returning and set `current_head` to end HEAD, so a second call independently
re-preflights against HEAD B. No Git transaction redesign is required.

One wording correction (Finding F3): the assessment describes "atomic Run
snapshot + checkpoint publication" as one step. In `run_real_one_hop` it is two
sequential atomic writes (`run.json` then `checkpoint.json`, `slice4.py:203-204`)
followed by marker retirement. This is not a correctness defect: the 5A
continuation gate must derive authority from the authoritative Run (the returned
in-memory Run / `run.json`), not from the projection `checkpoint.json`; and a
crash between the two writes leaves the marker present, so recovery routes through
`recover_uncertain_dispatch` -> `reconcile_required` and never auto-dispatches
H002 (verified `persistence.py:73-122`). The contract should state the
authoritative-source rule and this crash disposition explicitly.

The S4B-R4 ordering (a legitimate in-scope commit B lands, then the reducer
rejects an unknown route / invalid Finding delta and stops `awaiting_human`) is
acceptable as-is: B is factual and observed; the invalid routing/finding produces
no phase authority; the non-ready status forbids H002; no rollback is warranted.
Tests `test_commit_intent_without_phase_edit_authority_never_mutates_git`,
`test_failed_result_with_intent_never_synthesizes_a_commit`, and
`test_wi02_shape_edit_only_required_durable_cannot_reach_a_trusted_commit`
corroborate the commit-permission-before-reduction boundary.

GIT/CHECKPOINT ORDERING BLOCKS N>1:: *NO* (with the F3 wording clarification).

COMMIT-BEFORE-LATER-REDUCTION-STOP MAY REMAIN AS-IS:: *YES* (document and test;
do not reorder or roll back).

=== 6.2 Governing inputs (Axis 7)

The genuinely governing/authority inputs are the pinned WorkItem, WorkflowProfile,
RepositoryPolicy, task payload, and component manifest/components -- all
repository files pinned by the operator via `git show <rev>:<path>` at the
expected HEAD. The seam exists (`observe_hop(pinned_paths=...)`) but is unwired on
the accepted path, so an in-scope H001 commit could mutate a governing file while
H002 continued from stale in-memory objects. Revalidation before H002 is
therefore required.

Finding F4 refines the *minimum sufficient invariant*: path-based
`pinned_paths` anomaly detection only catches mutation *inside the observed
commit range and by exact path match*. The robust invariant is content identity:
before H002, re-read each pinned governing path at HEAD B and require *byte/hash
identity* with the operator-pinned content; any difference (or any pinned path
becoming untracked/moved) must force human/reconcile, not a silent continuation
stop. `pinned_paths` remains a useful cheap in-Hop tripwire but is not by itself
the H002 precondition. No Run field and no generic content-addressed config
system are needed.

GOVERNING-INPUT REVALIDATION REQUIRED BEFORE H002:: *YES* (minimum: byte/hash
re-identity of the five pinned inputs at HEAD B; changed input -> human/reconcile,
no H002).

== 7. Policy / action authority challenge (Axis 6, WATCH-1)

Operator preflight validates *every* phase's `authorized_actions` against
`RepositoryPolicy.actions`, so a route A->B cannot surface a phase-B action that
policy omitted, and the runtime still requires the current phase's `edit`+`commit`
immediately before any trusted commit. WATCH-1 is therefore non-blocking for the
*actions* dimension *iff* the 5A driver stays dominated by that once-per-Run
preflight and does not add a new supported caller that reaches
`new_run()`/`run_one_hop()`/`run_real_one_hop()` around it.

The material gap (Finding F1) is that the *scope* dimension has no equivalent
domination: `phase.authorized_scope` is authored freely in the profile, flows
directly into `trusted_commit(allowed_paths=...)` and `observe_hop`, and is never
required to be a subset of `RepositoryPolicy.scope` or `WorkItem.scope`. At N=1
this is masked because only the initial phase acts and the maintainer inspects it;
at N>1 phase B's scope becomes a *second, independently authored* commit-authority
surface for H002. The assessment's WATCH-1 domination argument (actions) does not
transfer to scope, yet its minimum proof matrix only includes a phase-B *action*
outside policy. A 5A implementer following the assessment literally would enforce
action domination (which exists) and could omit scope domination (which does
not).

WATCH-1 BLOCKS SLICE 5A:: *NO*, on the exact condition that (a) the serial driver
remains dominated by the once-per-Run cross-input preflight (reuse or one
canonically extracted check called before `new_run()`), and (b) that preflight is
*extended* to require every phase's `authorized_scope subset RepositoryPolicy.scope`
(and the WorkItem scope envelope). Without (b), WATCH-1's sibling scope gap
becomes a real supported-path authority bug at N>1. A shared helper is justified
only if reused; moving policy actions/scope into `Run`/`vertical.py` is not
needed.

== 8. Context / execution-binding / observability challenge (Axes 9, 10, 11)

=== 8.1 Context continuity (Axis 9)

Strict parsing accepts only `context: fresh` (`serialization.py:291-292`), Hop
records use `fresh`, and the Codex path is ephemeral; no accepted adapter proves
continuing context. So 5A must remain fresh. "Fresh" is not "stateless": the
minimum H002 context the observation-only proof needs is the changed phase header
(phase B scope/routes/evidence, plus -- see below -- its declared
`authorized_actions`/`human_gates`), current HEAD B, the stable Run ID with fresh
Hop/invocation IDs, and a *compact* prior-Hop summary. `assemble_prompt` already
supports `context: tuple[ContextItem,...]` and diff projection with visible
bounded omissions, but `run_one_hop` passes neither; the smallest explicit
projection must be added. The prompt header omits `authorized_actions` and
`human_gates` today; deterministic commit guards remain authoritative so this is
not a bypass, but a first autonomous phase change must make the current phase's
declared authority/stops visible and must not imply an unused human-gate label is
mechanically enforced.

CONTINUING PROVIDER CONTEXT REQUIRED FOR 5A:: *NO.*
BOUNDED COORDINATOR-OWNED PRIOR CONTEXT REQUIRED:: *YES.*

=== 8.2 Execution binding (Axis 10)

`run_real_one_hop` constructs the adapter per call, and FTR 11.5's
execution-binding readiness invariant both requires a concrete per-invocation
binding and forbids freezing it Run-lifetime. 5A can resolve the same trivial
Codex/Terra/medium/fresh binding each iteration through a small internal
value/helper; no selector, registry, difficulty classifier, quota optimizer,
fallback policy, or Run field is required. A small helper must not masquerade as
selection policy.

NEW EXECUTION-SELECTION API REQUIRED FOR 5A:: *NO.*

=== 8.3 Observability (Axis 11)

The current `_summary()` is `N=1`-shaped: it reports commits from the last Hop
only, reconstructs `changed_paths` as baseline-to-live-HEAD (WATCH-2), and carries
one invocation/provider outcome (`operator.py:159-174`). Truthful `N=2` evidence
must separately expose per-Hop: Hop identity, invocation ID, provider attempt
outcome, concrete execution binding, base/end HEAD and commit range, plus
cumulative budget and final Run state. This must stay operator/evidence
projection and per-invocation binding artifacts; FTR 11.5 forbids storing the
binding in Run, and provider outcomes belong in evidence, not the aggregate.

RUN MODEL MUST STORE EXECUTION BINDINGS/PROVIDER OUTCOMES:: *NO.*

== 9. Slice decomposition challenge (Axes 12, 13)

The split is a genuine set of separable risk boundaries: 5A serial continuation
(the only capability needed to cross `N=1`); 5B integrated Finding/correction
convergence (reducer semantics already proven by replays A/J but not integrated);
5C multi-Hop interruption/resume (distinct recovery/authorization-consumption
risk; correctly ordered *after* 5B because ordinary continuation must exist before
resume of it is meaningful, and 5C reuses the already-modeled reconcile path);
5D prerequisite parent/child (distinct human-activation and stale-route risk); 5E
optional supervisor (may legitimately remain unbuilt absent a profile need); 5F
profile application / DMC dogfood (application evidence, kept generic, with DMC as
domain labels only -- corroborated by replay J's `"dmc" not in generic_source`
assertion).

5A is independently useful and reviewable. Nothing required for 5A is wrongly
pushed to 5B: Finding-delta attribution (empty vertical `finding_delta_ids`),
phase-specific required-artifact declarations, and `fail` vs `error` gate
separation are all only needed once H002 does convergence work, which 5A avoids by
construction. The one item under-specified in the 5A boundary is the phase-scope
domination invariant (F1), which belongs in 5A, not 5B, because 5A activates a
second phase's scope authority.

ORIGINAL SLICE 5 SHOULD BE SPLIT:: *YES.*
PROPOSED DECOMPOSITION SOUND:: *WITH BOUNDED REVISION* (name phase-scope
domination explicitly in the 5A boundary).

== 10. First N>1 proof challenge (Axes 14, 15, 16)

The proposed happy path and the false-continuation matrix are the right shape and
are centred correctly on preventing H002 rather than on a two-call happy path.
The matrix already covers: human/escalation after H001; malformed/uncertain
result (`reconcile_required`, one conservative charge); unknown route / invalid
Finding delta including with a legitimate commit B present; dirty/HEAD/governing-
input change injected *after* the H001 checkpoint (proving the independent
pre-H002 guard, not only H001 post-observation); exact budget exhaustion (no
H003); ineligible Run status refused before adapter entry; and phase-B action
outside policy rejected before H001.

Missing false-continuation cases (WITH ADDITIONAL CASES):

* *Phase-B `authorized_scope` outside the policy/WorkItem envelope is rejected by
  the once-per-Run preflight before H001* -- the scope analogue of the existing
  action case; required to prove F1's invariant.
* *Governing-input content revalidation*: strengthen the injected-change case so
  the pre-H002 guard is a *byte/hash* re-identity of the pinned inputs at HEAD B
  (not only a `pinned_paths` range tripwire), and prove a changed governing input
  forces human/reconcile rather than a bare stop (F4).

No real provider is required: the properties under test are driver, authority,
accounting, and revalidation properties, which a fake adapter and temporary Git
repository exercise deterministically; a real provider would only add
nondeterministic output. The accepted `N=1` evidence base (correlation failure,
uncertain recovery, productive/source WorkItems, review-gate separation,
generic-operator execution, action-authority correction, trusted commit, clean
post-observation, durable reconstruction) already covers the prerequisites for
H002; no additional `N=1` commissioning resolves a concrete H002 blocker.

Overdesign scan: the assessment resists every listed trap (no graph engine,
selector, registry, continuing context, grant, supervisor, parent/child,
concurrency, event store). Underdesign scan: it resists "just loop twice" -- it
requires an explicit pre-dispatch gate, per-Hop revalidation, fresh
IDs/bindings, truthful per-Hop summary, and non-ready-Run refusal. It lands
between the two. The single place it drifts toward *underdesign* is treating
phase-scope domination as review advice rather than a named preflight invariant
(F1), and slightly toward imprecision on the two-write publication (F3).

N=2 FAKE/LOCAL PROOF SUFFICIENT:: *WITH ADDITIONAL CASES* (phase-B scope-outside-
envelope; byte/hash governing-input revalidation).
ADDITIONAL N=1 COMMISSIONING REQUIRED BEFORE 5A:: *NO.*
