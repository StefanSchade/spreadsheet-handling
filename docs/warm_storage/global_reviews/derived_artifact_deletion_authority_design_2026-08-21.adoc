[[A]]
== A. Executive design decision

[.lead]
Close the confirmed FK/Lookup deletion-authority defect with the smallest
rule the accepted research evidences: *a cleanup executor may delete a
column identified through an FK-attributed name only when truthful,
currently-unrevoked, same-run transient FK materialization provenance names
that column.* Durable FK relation policy (`_meta.helper_policies.fk.relations`)
is retained as a *materialization* input (it still tells `add_fk_helpers`
what to build) but is permanently removed as a *deletion-candidate* input
from both `fk_helpers/drop.py` and `derived_column_policy.py`. No
value/formula equivalence check, no claimant/reliance vocabulary, and no new
durable state are introduced anywhere in this design.

Review 001 independently reproduced a fourth defect variant (Repro 4,
<<repro-recap>>) proving that "truthful when written" alone is *not*
sufficient: a same-run `enrich_lookup` call can physically replace an
already FK-enriched column while leaving FK's transient provenance entry for
that sheet untouched, so a cleanup executor deletes Lookup's fresh data on
FK's stale-but-was-truthful record. Closing this required one additional,
narrowly-scoped correction beyond the original two (<<K>>): "currently
present" transient provenance is no longer trusted merely because nothing
has since told the cleanup executor otherwise; instead, the one identified
way that provenance can go stale is closed *at its source*, by making the
transformation that can invalidate it responsible for doing so at write
time.

Three runtime corrections, applied together, close all four reproduced
variants (same-run collision, durable-policy-only with FK never run, the
second `derived_column_policy.py` executor, and the same-run staleness Repro
4 exposes):

. *Truthful FK provenance* (site 1) — `core/fk.py`'s materialization
  primitive reports, per resolved FK definition, whether it actually wrote
  the helper column this call or found the label already occupied.
  `fk_helpers/enrich.py` writes `_meta.derived.sheets.*.helper_columns`
  entries only for definitions it can truthfully claim (see <<E>>). This
  alone closes the same-run collision variant, because FK no longer writes a
  false claim for a column it did not write.
. *Deletion-authority rule* (sites 2 and 3) — `fk_helpers/drop.py` and
  `derived_column_policy.py` both stop treating durable FK relation policy as
  sufficient evidence to delete a physically present column. Each keeps
  reading FK's own transient provenance (already correct data, already
  correctly scoped per caller); each simply stops falling back to durable
  policy when transient provenance is silent. This alone closes both
  durable-policy-only variants, because "declared but never proven
  materialized this run" no longer authorizes deletion.
. *Sibling-provenance invalidation at decoupled rebind* (site 4, new in this
  correction pass) — `enrich_lookup`'s own provenance writer
  (`enrich_lookup/operation.py::_write_provenance`) drops any foreign
  producer's subkey already present under `_meta.derived.sheets.<output>`
  whenever it writes into an `output` that is not its own `source` for that
  call (see <<K>>). This closes Repro 4, because FK's transient record for a
  sheet Lookup has just decoupled-rebound no longer survives to be read by
  either cleanup executor.

All three corrections are independently necessary and jointly sufficient
against the accepted evidence, extended by Review 001, in <<repro-recap>>.
None requires value/formula equivalence machinery, a claimant/reliance
primitive, or new durable state — the third correction reuses the same
owner-local, write-time, per-sub-key pattern `_write_helper_provenance`
already established for FK's own stale-sheet cleanup
(`fk_helpers/provenance.py:69-95`), applied at the one other site this
design's authorized FK/Lookup pairing shows needs it.

== C. Canonical semantic distinctions

This design uses exactly the vocabulary the accepted research converged on
(Section F of the assessment; Review 001 Area 3 and FIND-007). No broader
vocabulary is introduced.

[cols="2,4", options="header"]
|===
| Term | Meaning in this design

| Physical producer
| The operation that actually wrote the currently present column/cell state.

| Requested / declared policy
| A family's transient or durable statement that it *wants* a helper at a
  named identity. Never sufficient deletion authority by itself.

| Truthful materialization provenance
| A same-run transient record written only for a definition the writing
  primitive freshly wrote this call (<<E>>). Necessary but, corrected per
  Review 001 FIND-D1, not by itself sufficient — see "current" below.

| Current (as applied to provenance)
| Corrected term, introduced by this pass: a truthful record that has not
  since been invalidated by a decoupled rebind of the sheet it describes
  (<<K>>). Truthful-and-current together are the *only* thing that can
  authorize FK-attributed deletion in this design; truthful alone is not
  (Repro 4, <<repro-recap>>).

| Deletion authority / precondition
| The verified fact ("truthful, current materialization provenance names
  this column") that must hold before a cleanup executor removes a column
  identified through a requested/declared name.

| Cleanup executor
| The operation that mutates the physical frame to remove a column:
  `fk_helpers/drop.py` and `derived_column_policy.py`, the two mandatory
  sites.

| Decoupled rebind
| Corrected term, introduced by this pass: a write that binds `output` to a
  frame name that already exists in `frames` but was not the write's own
  `source`/input, so the write's physical content has no provable
  relationship to whatever the name previously held (<<K>>). The one
  identified trigger for provenance going stale after being truthfully
  written.
|===

*Explicitly not introduced:* claimant, current reliance, claim
registration/release, reference counting, a central claim ledger, stable
artifact identity, or an adopt/share protocol. <<Q>> restates why each is
unnecessary against the evidence in <<repro-recap>>.

[[D]]
== D. FK collision semantics

*Design Question 1 answer.* The smallest sufficient policy is *A: decline
materialization on collision, no provenance claim* — `core/fk.py`'s
materialization primitive must never overwrite an existing column at the
requested helper label (Candidate D — FK overwrites — was independently
rejected by Review 001 as strictly worse: it trades a wrongful-deletion
defect for silent, unwarned data corruption of whichever producer's column
FK overwrote). On collision, the primitive continues to skip the write,
exactly as today; what changes is that the skip must be *reported*, not
silently absorbed, so provenance can be truthful (<<E>>).

*Naming, corrected per Review 001 FIND-D3:* this design previously labeled
this "reject on collision." That word already has an established, different,
*raising* meaning elsewhere in this same subsystem (Discriminator split's
`framecheck.py:28` hard failure; `apply_v2_relations`'s own durable-policy
collision handling, documented as "cross-producer collisions on the same key
fail"; `enrich_lookup`'s own `_check_column_conflict` /
`_check_key_helper_collision` guards, which do raise). A reader carrying any
of those precedents into this design would wrongly expect `add_fk_helpers`
to raise on a label collision. It does not, by design. "Decline
materialization" is used throughout this corrected artifact instead; "reject"
is reserved for behavior that actually raises.

Policy A alone is *sufficient* to close all four reproduced variants once
paired with the deletion-authority rule in <<F>> and the write-time
invalidation obligation in <<K>> — see <<repro-closure>>. Per the design
brief's own instruction ("If A or B is sufficient, do not design generic
adoption"), *Candidate C (value/semantic-equivalence adoption of a foreign
producer's column) is rejected outright and not designed here* — <<L>> gives
the full disposition.

*Optional self-verified-reuse refinement — removed (Review 001 FIND-D2).*
The original design proposed an optional Domain-layer refinement letting a
collided definition be recognized as FK's own idempotent prior output by
comparing definition *shape* (never cell values) against FK's own
already-present transient provenance entry. Review 001 constructed a direct
disproof: continuing Repro 4 with a second `add_fk_helpers` call after
`enrich_lookup` has already decoupled-rebound the column shows the
refinement re-affirming a foreign, stale claim purely because the shape
still matched a record that had never been invalidated — and in doing so it
defeats the one incidental self-healing property `_write_helper_provenance`'s
existing per-sheet replace-not-merge semantics would otherwise provide
(a re-run over an unmatched collision naturally drops the provenance entry
under Policy A alone). This is not "not required," it is actively unsafe as
specified once combined with Repro 4, so it is *removed from this design
entirely*, not scheduled as a deferred slice. <<K>>'s new write-time
invalidation obligation closes the specific staleness Review 001 used to
construct the disproof, which means the refinement's *original* safety
argument ("compares only FK's own metadata shape, never a foreign
producer's") would, after <<K>> lands, once again be reasoning about a
record that cannot be stale in the one way this design has evidence for. That
is grounds for a *future*, separately authorized reconsideration — not for
reinstating it in this pass; see <<R>>.

*Does not help post-persistence.* Regardless of the refinement's removal,
this point stands for the mandatory mechanism: transient provenance does not
survive persistence (`docs/ai_info/agent_rules.adoc`'s persistence-boundary
rule: Intent survives, Resolution/derived provenance does not). On a freshly
reimported frame there is no surviving transient record at all, so a
physically present FK-shaped column is *always* treated as an unverified
collision after reimport. That is intentional — see <<I>>.

[[E]]
== E. Truthful FK materialization provenance

*Design Question, site 1 concrete answer.*

*Is the existing return contract sufficient?* No. `core/fk.py::apply_fk_helpers`
today returns only the resulting `pd.DataFrame`; the per-definition
materialized/skipped fact is computed (`if helper_col in first_cols:
continue`) and then discarded. `fk_helpers/enrich.py::enrich_helpers` cannot
write truthful provenance without that fact.

*Is a narrow result structure needed?* Yes, but it must not change
`apply_fk_helpers`'s existing signature or return type. `apply_fk_helpers` is
re-exported from `spreadsheet_handling.core.__init__` (`__all__` includes
`"apply_fk_helpers"`) and is exercised directly, as a DataFrame-returning
call, by `tests/unit/domain/transformations/test_fk_helpers_enrich.py` and by
the primitive-package architecture guard
(`tests/architecture/dependency_guards/test_fk_helper_primitives_consume_policy.py`,
which allow-lists `apply_fk_helpers` by name). Changing its return type is a
gated public-surface break for no evidenced benefit.

*Public or internal? Corrected per Review 001 FIND-D8: internal.* The
original design left the new reporting primitive's public-barrel status as
an open question (former <<S>> item, "does `interfaces_and_gates.adoc` gate
adding it to `core/__init__.py`'s `__all__`?"). Review 001 checked whether
that question is even reachable: `fk_helpers/enrich.py` already imports
directly from the `core.fk` *submodule*
(`from ....core.fk import apply_fk_helpers, build_id_value_maps`),
bypassing `core`'s `__all__`-gated barrel entirely, and the architecture
guard that must be updated regardless
(`_ALLOWED_CORE_FK_NAMES` in
`test_fk_helper_primitives_consume_policy.py`) operates on submodule-level
imports via AST inspection, not on `__all__` membership.
`interfaces_and_gates.adoc` itself distinguishes the Python import surface
("keep intentionally small... do not treat every internal module or barrel
export as public API") from the CLI/YAML/plugin surfaces it actually gates.
Nothing about the sole evidenced consumer (`fk_helpers/enrich.py`) requires
public status. The new primitive is therefore designed as a private,
leading-underscore symbol in `core/fk.py`, allow-listed in the existing
architecture guard by name, and *not* added to `core/__init__.py`'s
`__all__`. This makes the former open question moot rather than something
requiring a maintainer decision before Slice 1 (<<S>>).

*Proposed shape (design-level, not final naming):*

[source,python]
----
class _FkHelperMaterializationResult(NamedTuple):
    frame: pd.DataFrame
    materialized: list[FKDef]        # definitions this call actually wrote
    skipped_existing: list[FKDef]    # definitions whose helper_col collided
                                      # with an already-present column

def _materialize_fk_helpers(
    df, fk_defs, id_value_maps, levels, helper_prefix="_",
    helper_value_provider=None,
) -> _FkHelperMaterializationResult: ...

def apply_fk_helpers(df, fk_defs, id_value_maps, levels, helper_prefix="_",
                      helper_value_provider=None) -> pd.DataFrame:
    """Preserved for compatibility; existing callers unaffected."""
    return _materialize_fk_helpers(
        df, fk_defs, id_value_maps, levels, helper_prefix,
        helper_value_provider,
    ).frame
----

`_materialize_fk_helpers` becomes the real implementation (identical
materialization logic to today, plus bucket bookkeeping); `apply_fk_helpers`
becomes a thin compatibility wrapper. No duplicated materialization logic, no
change to any existing caller's observed behavior or type. If a genuine
external need for a public `materialize_fk_helpers` later emerges, promoting
the private symbol is a small, separately evidenced follow-up, not something
this design needs to pre-authorize.

*How `fk_helpers/enrich.py` uses it:* `enrich_helpers` calls
`_materialize_fk_helpers` per frame instead of `apply_fk_helpers`. For each
frame, it builds the *provable* set passed to `_write_helper_provenance` from
exactly `materialized` (definitions freshly written this call). Definitions
in `skipped_existing` are never included — no refinement re-admits them
(<<D>>, FIND-D2). This is simpler than the original design's provable-set
construction, not merely equally safe: there is no second case to reason
about.

Definitions in `skipped_existing` writing *no* provenance entry is the
direct fix for the confirmed contract violation (FK provenance must record
only materialized state; three independent maintained sources —
`docs/semantic_model/12_contract_matrices.adoc`,
`docs/technical_model/ch04_concepts/fk_helper_metadata.adoc`,
`docs/ai_info/concepts_fk_helpers.adoc` — already say this; only the runtime
was wrong).

*Avoiding duplicated physical-materialization decisions in Domain code:*
Core (`core/fk.py`) remains the *sole* place that decides column-level
collision (`helper_col in first_cols`); it only gains a reporting
obligation, not new policy. Domain (`fk_helpers/enrich.py` /
`fk_helpers/provenance.py`) owns the *meaning* of that report — this matches
the existing Core/Domain boundary (Core is a content-free mechanism; Domain
owns metadata lifecycle, per the Domain Maintainer Contract §8).

*Replay/idempotence:* a single call to `enrich_helpers` is unaffected. A
second call in the same session against frames that already carry FK's own
prior output writes no provenance for the re-collided definitions (they
land in `skipped_existing`, never claimed) — an accepted, narrow,
currently-unevidenced-as-relied-on behavior change flagged in <<D>> and
<<P>>. This is deliberately conservative rather than merely convenient:
Review 001's FIND-D2 showed that trying to be more clever here (the
now-removed optional refinement) can be actively unsafe, not just
unnecessary.

*Pre-existing requested label — final rule:* absent → materialize and claim;
present (verified or not; no self-check exists) → no-op, no claim, no
overwrite, no error by default (diagnostic per <<J>>).

[[F]]
== F. Deletion-authority rule

[.lead]
*A cleanup executor may delete a column identified through an FK-attributed
candidate name if and only if that name is currently present in
`_meta.derived.sheets.<sheet>.helper_columns` (truthful, same-run,
materialized-only transient provenance, per <<E>>, that has not since been
invalidated by a decoupled rebind of that sheet, per <<K>>).
`_meta.helper_policies.fk` (durable v2 relation policy) never independently
authorizes deletion — it identifies what FK would request, not what FK
currently produced.*

*Corrected per Review 001 FIND-D1.* The rule's shape is unchanged from the
original design ("presence of truthful transient provenance is required and
sufficient"); what changed is that "presence" is no longer trusted as a
standing fact once written. Review 001 independently reproduced (Repro 4,
<<repro-recap>>) that a same-run `enrich_lookup` call with `source != output`
can physically replace an already-FK-enriched sheet while leaving FK's
transient record for that sheet completely untouched, because
`enrich_lookup`'s own provenance writer *merges into* the existing sheet
entry rather than reasoning about whether its own write invalidates a
sibling's claim. Both cleanup executors then trusted that now-stale record.
Neither of the original two corrections (<<E>>, and the durable-fallback
removal in <<G>>/<<H>>) touches this path: FK's write in Repro 4 genuinely
was fresh and uncollided (so <<E>> reports it as `materialized`, correctly),
and the stale record was never sourced from durable policy at all (so the
durable-fallback removal is irrelevant to it). Closing it required a third,
independent correction, made at the one site that can actually know the
staleness is happening — see <<K>>.

| 2 (durable-policy-only, FK never ran)
| <<F>> alone closes it: no transient provenance exists for the sheet at
  all; durable policy is no longer consulted for deletion candidates; the
  column is left in place.
| None evidenced.

| 3 (second executor, same setup)
| <<F>> applied identically at the `derived_column_policy.py` site (<<H>>);
  its own durable-relation fallback (`_safe_policy_helper_names`) is removed
  as a deletion-candidate source.
| None evidenced.

| 4 (same-run staleness via decoupled `enrich_lookup` rebind, Review 001
  FIND-D1)
| <<K>> closes it: `enrich_lookup`'s provenance writer, on writing its own
  record for an `output` that is not its `source` for this call, drops any
  foreign subkey (here, FK's `helper_columns`) already present under that
  sheet's `_meta.derived.sheets` entry. By the time either cleanup executor
  runs, FK's stale record no longer exists to be read.
| See <<find-d1-bound>> below: the same *shape* of hazard, unevidenced, at
  `derived_column_policy.py`'s own `output` parameter — recorded, not fixed,
  in <<R>>.
|===

The three corrections are independently necessary for their respective
repro(s) and jointly sufficient (removing any one reopens at least the repro
it alone closes, per Review 001 Area 6's own smallest-local-repair test,
extended to the third correction by the same logic against Repro 4).

[[find-d1-bound]]
=== Why the third correction is bounded to one write site

Review 001's own instruction was to search beyond Lookup for the same
staleness shape, not assume it is Lookup-specific. This design did so
against the two other write sites already in its mandatory scope:

* *FK's own writer (`fk_helpers/enrich.py` / `core/fk.py`) is structurally
  immune*, for two independent reasons confirmed by reading it: it is always
  self-referential — `enrich_helpers` iterates `iter_data_frames(frames)`
  and reads and writes the *same* frame name for every sheet it touches;
  there is no `source`/`output` decoupling anywhere in FK's materialization
  path. And even within that self-referential shape, the existing collision
  check (`helper_col in first_cols: continue`, unchanged by <<D>>) already
  prevents FK from ever overwriting a Lookup-produced column's physical
  content in place. FK cannot reproduce Repro 4's shape against Lookup's
  provenance.
* *`derived_column_policy.py`'s own `output` parameter has the identical
  structural shape* (payload sourced from `source`, written to a possibly
  different, possibly pre-existing `output`), and — unlike `enrich_lookup`
  — its replacement path writes *no* new provenance for `output` at all, so
  a foreign sibling record attached to a pre-existing `output` name would
  remain silently stale after such a call. This is a real, theoretically
  reachable analog of Repro 4's shape. It is *not* built as a fix here
  because it is not independently evidenced: every current test and
  documented usage of `output` targets a *new* frame name
  (`test_mixed_editable_helper_sheet_preserves_payload_columns`,
  `test_distinct_output_preserves_original_source_provenance`, both using
  `output="orders_payload"`, a name with no prior provenance to collide
  with). Per the design brief's own instruction to prefer a bounded fix when
  only one path is evidenced, this is recorded as a deferred hardening
  question, not designed, in <<R>>.

No further site was found within this design's authorized FK/Lookup pairing.
A future family exhibiting the same `source`/pre-existing-decoupled-`output`
shape while sharing a `_meta.derived.sheets` entry with FK or Lookup should
apply the same owner-local pattern established in <<K>>; generalizing it
into shared infrastructure ahead of that evidence is explicitly not designed
here (<<Q>>).

=== Design Question 2 — what proves current FK production?

*Same-run transient provenance is necessary but, corrected per Review 001
FIND-D1, not by itself sufficient.* "Truthful when written" (<<E>>) proves
only that FK's record was accurate at the moment it was written; it does not
prove the record is still accurate now. The exact additional condition this
design requires: *no `enrich_lookup` call with `output` equal to that sheet
and `source` different from `output` has run since* — because that is the
one identified, evidenced way a sheet's FK-owned sibling record can go
stale while every other reader observes it as untouched (Review 001 section
4, "Transient-provenance authority review"; confirmed independently against
`enrich_lookup/operation.py`,
`fk_helpers/provenance.py`, and `registries/meta_registry.yaml`'s own
per-sub-key-locality invariant, which documents that each producer owns only
its own subkey but has no mechanism for a sibling's subkey to survive a
wholesale content replacement it did not itself produce).

This condition is enforced *by construction*, not by the cleanup executors
re-verifying anything at read time: <<K>> makes the one transformation that
can create the staleness responsible for closing it at the moment it writes,
so a cleanup executor's simple "is the entry present" read (unchanged from
the original design) is correct again. This is why the rule's *header* in
<<F>> did not need to change shape — only the meaning of "currently present"
did, and that meaning is now something the corrected write-time contract
actually guarantees, not an unproven assumption. The corresponding
Design Question 2 assumption in the original design ("no supported
transformation is known to silently overwrite another family's helper
column... named as an open assumption, not a proven invariant") is
superseded: the one identified path is now closed by construction within
the authorized FK/Lookup pairing; an implementer extending FK/Lookup
interaction beyond that pairing later should still re-verify no new
decoupled-rebind shape has been introduced, per <<find-d1-bound>> and
<<S>>.

*Durable-policy-only path:* does not, and structurally cannot, prove current
physical production, with or without persistence (<<I>>). This design
deliberately does *not* build a value-verification override
(`should cleanup verify the current column against what FK would produce?`
from the design brief) — see <<L>> for why. It does *not* ask the caller to
supply a stronger durable declaration — that would be new durable producer
history, explicitly disallowed (the design brief's own instruction: "Do not
invent durable producer history merely to preserve old cleanup behavior"). The
chosen answer is the brief's own named conservative option: *the existing
persistence/reimport contract intentionally leaves the helper column in
place rather than risk deleting Lookup- or user-owned data* — the safe
migration path for pipelines that need durable, persistence-surviving
cleanup identity is named concretely in <<I>>.

[[G]]
== G. FK direct-cleanup design

`fk_helpers/drop.py::_columns_to_drop_by_sheet` currently builds its result
from `provenance_by_sheet` (transient, preferred) with a *fallback* to
`relations` (durable policy) for any sheet absent from provenance. That
fallback branch is removed entirely for deletion-candidate purposes.

*New behavior:* `columns_to_drop` is built from `provenance_by_sheet` only —
i.e. from `derived_helper_columns_by_sheet(frames)`, which is *already*
truthful once <<E>> lands, and — once <<K>>'s write-time correction lands —
*already current*, because a stale sibling entry can no longer exist by the
time this reader runs (no separate new accessor, freshness check, or
re-verification is required here; see the non-design rationale in <<K>> and
<<9-facade>>). `resolve_v2_fk_relations`
remains called by `drop_helpers` for exactly one *unrelated, unchanged*
purpose: the existing "was FK helper policy ever configured at all" clear
error (`missing_fk_policy_error`) when *neither* provenance nor durable
policy exist for the whole run. That precondition check is not a deletion
decision and is out of scope for this design; it is left as-is.

*Concrete disposition:*

* sheet has truthful transient provenance naming the column → delete
  (unchanged happy path);
* sheet has no transient provenance for that column, durable policy names it
  → leave in place, no error, no exception raised by default (diagnostic per
  <<J>>);
* neither transient provenance nor durable policy exist anywhere in the run
  → `missing_fk_policy_error` (unchanged, pre-existing behavior, not a
  deletion-authority question).

H5 (`_clean_helper_provenance` → `reconcile_enrich_lookup_provenance`) is
unchanged — see <<K>>.

[[H]]
== H. Derived-column-policy integration design

`derived_column_policy.py::_safe_policy_helper_names` exists *solely* to
supply FK-attributed deletion candidates from durable v2 relation policy.
Under <<F>> that source is never authorized, so this function's entire
purpose is removed: `apply_derived_column_policy` stops calling it, and its
result is no longer unioned into `durable_helper_names` in
`apply_derived_column_policy`'s body.

*What remains, and why it is not touched:* `_resolve_derived_identity`'s
reading of `_meta.derived.sheets[source].helper_columns` (FK's transient
provenance) is *already correct* — it reads the same truthful subkey
`fk_helpers/drop.py` reads. `_resolve_derived_identity`
also reads Lookup's own `enrich_lookup` declared names in the same call —
that half is Lookup's own self-declared identity of its own column and is
*not* the defect (a family deleting a column via its own declaration of its
own artifact is not "requested identity borrowed from a different owner");
it is untouched.

*Shape-validation divergence between the two transient-provenance readers —
corrected per Review 001 FIND-D6, made explicit rather than a passing
aside.* `fk_helpers/policy.py::derived_helper_columns_by_sheet` (used by
`drop_helpers`) silently filters out non-mapping `helper_columns` entries;
`derived_column_policy.py::_validated_fk_helper_names` (used here) raises a
clear `ValueError` on the identical malformed shape. This is a genuine,
deliberate operational divergence, not an oversight, and it is *not* a
deletion-authority divergence: both directions are conservative toward "do
not wrongly delete on bad data" — one silently proceeds without the
malformed candidate, the other aborts the whole call rather than guess. Per
this repository's own domain-boundary policy (shared helpers require shared
*accepted/rejected vocabulary*, not merely the same accepted-value read),
this divergence does not by itself justify a shared facade, and none is
designed here. It is recorded, not silently left as a one-clause aside, so a
future reader does not mistake it for an unnoticed inconsistency.

*Workbook-View's durable `helper_columns` declaration — corrected per
Review 001 FIND-D5, "different owner" replaced with the actual distinction.*
`_safe_durable_helper_names` reads `_meta.sheets[source].helper_columns` and
feeds it into `durable_helper_names` with *no* physical-producer check at
all — structurally the same "requested/declared identity, unverified
against current physical production" pattern this design eliminates for
FK's durable relation policy (confirmed by the existing, unchanged,
currently-green test
`test_drop_uses_durable_workbook_helper_columns_when_derived_is_absent`).
Leaving it untouched is correct, but "different owner" alone does not make
it safe by itself; the real, citable distinctions are:

* *producer* — this carrier is written only by `configure_workbook_view`
  (`domain/workbook_views.py:55-165,349-379`), whose entire parameter
  surface is a human pipeline author's *explicit* sheet-shape declaration,
  closer in kind to XRef's guarded, caller-asserted `drop_source` flag (a
  pattern the accepted research already treats as legitimate) than to FK's
  auto-derived "what I would build" intent;
* *canonical content contract* — `fk_helper_metadata.adoc`'s "First
  conservative policy" section states, as maintained authority, that
  "manual edits to helper values are not treated as source truth; helper
  values may be ignored or overwritten on re-enrichment." A column declared
  a helper by workbook-view configuration is canonically defined as
  never-authoritative content, independent of who currently produced it;
* *purpose-built origin* — `BUG-HELPER-CLEANUP-CONTRACT-P4A` built this
  carrier, together with the FK-relation-policy fallback this design now
  removes, specifically as durable cleanup identity surviving the
  persistence boundary; it is the carrier this repository already chose for
  this exact job, not an accidental byproduct being repurposed — see <<I>>,
  where this same carrier is named as the concrete, recommended migration
  path for pipelines the durable-fallback removal affects.

This is a real, defensible distinction that makes the residual risk
*smaller and differently justified*, not a distinction that makes the
residual risk *zero*: nothing prevents a caller from repurposing a
historically-FK-derived label for genuine hand-entered data without also
updating the separately-maintained `configure_workbook_view` declaration.
That residual staleness risk is recorded explicitly, not implied away, in
<<R>>. It remains out of scope for this design (see
<<repository-boundaries>> in <<Q>>) — the accepted research's own
narrowed-scope authorization treats Workbook View as a constraint/boundary,
not a mandatory Design-Phase site, and nothing found by this correction pass
forces that boundary open.

*Net effect on `apply_derived_column_policy`:* `durable_helper_names` in the
function body is fed only by `_safe_durable_helper_names` (Workbook-View,
unchanged, out of scope); `policy_helper_names` (`_safe_policy_helper_names`,
FK durable-relation fallback) is deleted. FK-attributed candidate names come
exclusively from `_resolve_derived_identity`'s transient-provenance read,
unchanged.

[[9-facade]]
=== Design Question 9 — why no new shared facade is designed

The two executors do not, in the corrected design, need a shared *data*
accessor: each already reads FK's transient provenance correctly and
independently, at acceptably low duplication risk (a short,
already-well-validated read of one `_meta.derived.sheets[*].helper_columns`
subkey). The defect-causing logic — the *durable-policy fallback* — is not
consolidated into a shared function; it is *deleted outright* from both call
sites, because the answer both sites need ("durable policy never
authorizes deletion") is a fixed rule, not a computed value. This is the
smallest design that prevents both executors from "independently
reimplementing FK authority semantics" (the concern in the design brief):
after this change, neither module contains *any* FK-authority-adjacent logic
beyond reading FK's own truthful transient record.

A narrow, optional hygiene improvement (not required for correctness, not
part of the mandatory scope): `derived_column_policy.py` could call
`fk_helpers.derived_helper_columns_by_sheet` instead of maintaining its own
parallel reader, purely to reduce the duplicate-implementation surface
Review 001's FIND-002 already flagged as a readability/duplication risk one
cycle earlier. This is left to the implementer's judgment at slice time (see
<<N>>) and is explicitly not mandated here.

[[I]]
== I. Persistence/reimport behavior

*Design Question 3 answer.* No special-casing of "before persistence" versus
"after persistence" is designed or required. <<F>>'s rule is stated once,
uniformly: *truthful same-run transient provenance is required; durable
policy alone is never sufficient — regardless of whether a persistence
boundary was crossed.* Persistence does not change the rule; it only changes
which evidence is available. Transient `_meta.derived` is stripped at the
persistence boundary by existing, unchanged, and out-of-scope machinery
(`pipeline/persistence_boundary.py`; "Persist Intent, discard recomputable
Resolution" — `docs/ai_info/agent_rules.adoc`); durable
`_meta.helper_policies.fk.relations` survives.

*Concrete consequence:* after a reimport with no fresh `add_fk_helpers`
materialization pass in the same session, `remove_fk_helpers` and
`apply_derived_column_policy` can no longer automatically delete a
physically present FK-shaped helper column from durable policy alone. This
is a *deliberate, evidenced* compatibility narrowing, not an oversight — see
<<P>> for its scope. It is consistent with `derived_column_policy.py`'s own
pre-existing docstring, which already hedges that durable fallback
declarations "identify columns only" — the implementation was out of sync
with its own documented contract before this design.

*Does running `add_fk_helpers` first restore automatic post-reimport
cleanup?* No, and this must not be assumed by an implementer. Running
`add_fk_helpers` against a freshly reimported frame treats the physically
present column as an unverified collision (no claim); there is no surviving
transient record from before the current run to compare against. No
mechanism in this design can regenerate trustworthy same-run evidence for a
column that already existed before the current run started, short of FK
genuinely re-materializing it from a state where the label was absent.

*Corrected per Review 001 FIND-D4: the compatibility narrowing is larger
than the original design stated, and the migration path was never named.*
Three maintained, currently green tests exist *specifically* to pin the
capability this design removes, two of them tagged to a historical
`0.2.0`-blocker regression
(`BUG-HELPER-CLEANUP-CONTRACT-P4A.adoc`,
`BUG-REIMPORT-PROMOTION-HELPER-COLUMN-LEAKAGE-P4A.adoc`). Each is named and
individually dispositioned here so an implementer does not discover them
mid-slice:

  after a simulated persistence boundary.
| *Inverted.* Under <<F>>, durable FK policy alone must no longer authorize

a reimport pipeline that needs automatic post-persistence FK-helper cleanup
without a fresh same-run `add_fk_helpers` pass must declare
`helper_columns` for the affected sheet via `configure_workbook_view` in its
*forward* pipeline (the step, carrier, and consuming code path — <<H>>'s
`_safe_durable_helper_names` — all already exist and are unchanged by this
design). A pipeline that does not make this declaration and also has no
fresh transient provenance gets the safe, fail-closed default: the column is
left in place, and the existing `validate_references` rule
`no_helper_columns` (built for exactly this purpose by
`BUG-HELPER-CLEANUP-CONTRACT-P4A`, already exercised by

recommended way to catch that at pipeline-authoring time rather than
discover it in canonical output. Whether `configure_fk_helpers` /
`infer_fk_relations` should *also* populate the Workbook-View carrier
automatically, so pipeline authors are not forced into fragile dual
configuration to keep today's reimport-cleanup guarantee, is evaluated and
deliberately deferred, not designed, in <<R>>.

Diagnostics never inspect or report unrelated frame contents; they name only
the frame, the candidate column label, and (where available) the FK relation
identity that was declined.

*`fail_on_mismatch` decision, corrected per Review 001 FIND-D7.* The
original design proposed routing `fk_deletion_unauthorized` through
`fail_on_mismatch`'s existing raise path, flagging it for maintainer
sign-off because it would give a registered pipeline step a genuinely new
failure trigger unrelated to value mismatch. Review 001 found this
repository already has a purpose-built, separately composable mechanism for
exactly the "fail loudly if cleanup silently no-op'd" need:
`validate_references`'s `no_helper_columns` rule, added by
`BUG-HELPER-CLEANUP-CONTRACT-P4A` for precisely this reason ("Architectural
direction": cleanup stays a safe no-op; strictness is opt-in via a separate
validation rule, deliberately not folded into the cleanup step's own
severity ladder), already exercised today by
`test_no_helper_columns_validation_reports_bypassed_cleanup`. Authorization
refusal ("we cannot prove FK currently produced this column") and value
mismatch ("FK's value differs from what the canonical lookup would produce")
are different failure classes; conflating them in `fail_on_mismatch`'s raise
path would re-conflate at the control-flow level what the findings-frame
separation deliberately keeps apart one step earlier. `fk_deletion_unauthorized`
is therefore designed as *always* a conservative, non-raising diagnostic,
emitted under both `warn_on_mismatch` and `fail_on_mismatch`, never routed
into the `raise` path. Callers wanting fail-fast "deletion definitely
happened" enforcement are pointed at the existing `no_helper_columns` rule
instead of a newly grown `fail_on_mismatch` failure surface. This closes the
sign-off question the original design left open in <<S>> with a concrete
decision, not a re-flag.

[[K]]
== K. Lookup interaction / H5 relationship

*Design Question 5 answer, corrected per Review 001 FIND-D1.* The original
design's answer — "no new Lookup-owned pre-deletion handoff is
introduced... it never reads... any other Lookup-owned shape" — is no
longer accurate and is replaced. Closing Repro 4 requires one narrowly
necessary, Lookup-owned *write-time* correction, permitted explicitly by the
design brief's scope check ("the corrected design may add a narrowly
necessary modification/handoff at Lookup Enrichment if FIND-D1 proves it
necessary"). It is a write-time obligation on Lookup's *own* provenance
write, not a new pre-deletion query FK or a cleanup executor makes of
Lookup, and not a change to what either cleanup executor reads — <<F>>'s
rule is still decided entirely from FK-owned evidence, read exactly as
before.

=== The mechanism: invalidate a foreign sibling subkey at decoupled rebind

`enrich_lookup/operation.py::_write_provenance` currently builds
`sheet_entry = dict(derived_sheets.get(output, {}))` — i.e. it starts from
whatever sibling entry already exists for `output` — and then only ever sets
`sheet_entry["enrich_lookup"] = record`, leaving every other subkey (in
practice, FK's `helper_columns`) untouched. This is exactly right when
`output == source`: `enrich_lookup`'s merge (`source_df.merge(...)`, or
`source_df.copy()` in formula mode) provably preserves every pre-existing
column's physical content unchanged — the existing `_check_column_conflict`
guard, which inspects only `source_df`, is sufficient in this case because
`source_df` *is* the frame being extended, so any sibling's claimed columns
are already visible to that guard. It is exactly wrong when `output !=
source`: the physical content now written to `output` is derived entirely
from `source`, which the pre-existing frame at `output` was never party to;
`_check_column_conflict` never inspects the pre-existing `output` frame at
all, so a sibling family's claimed columns can be silently replaced with no
guard seeing it happen.

The correction: when `_write_provenance` writes its own `enrich_lookup`
record and `output != source`, it drops every subkey in `sheet_entry` other
than `enrich_lookup` itself *before* writing its own record — i.e. any
foreign producer's claim already attached to that sheet is treated as
invalidated by the decoupled rebind, regardless of which family owns it or
what its shape is. This is:

* *mechanical, not value-based* — the trigger is `output != source`, a
  parameter comparison already available at the call site; it never
  inspects cell values, never compares definition shapes, and cannot become
  Candidate C (<<L>>) by construction, because it never reads a foreign
  record's *content*, only its *presence*;
* *generic, not FK-specific* — it invalidates *any* non-`enrich_lookup`
  subkey, not specifically `helper_columns`, so it does not need updating if
  a future producer family adds a third subkey to the same
  `_meta.derived.sheets.<sheet>` entry;
* *owner-local* — implemented entirely inside `enrich_lookup`'s own
  provenance writer, reusing the same write-time, per-sub-key pattern
  `fk_helpers/provenance.py::_write_helper_provenance` already established
  for FK's own stale-sheet cleanup (`_write_helper_provenance:69-95`,
  "Remove stale provenance for sheets without current FK defs"), applied at
  the one other site this design's evidence shows needs it (<<find-d1-bound>>);
  it requires no new `_meta` key, no cross-family read at write time beyond
  the sibling-presence check already implicit in `dict(derived_sheets.get(
  output, {}))`, and no new primitive;
* *a true no-op in the ordinary case* — when `output` is a brand-new sheet
  name (the typical `enrich_lookup` shape, per the accepted research's own
  "Output frame name already exists -> replacing the prior mapping" note
  and the package's own test fixtures), `sheet_entry` starts empty and there
  is nothing to invalidate.

=== Why H5 is unaffected

H5 (`reconcile_enrich_lookup_provenance`) remains exactly as it was: a
stateless, recompute-on-demand, *post*-mutation truthfulness predicate over
Lookup's own declared `helper_columns` and the frame's current columns,
called by `fk_helpers/provenance.py::_clean_helper_provenance` after *FK's*
own column removal. It answers a different question ("is Lookup's own
sibling record still truthful after FK deleted something") than the new
mechanism above ("should Lookup invalidate a foreign sibling record because
Lookup itself just replaced the frame's content"), and the two do not
overlap in the case they each handle: H5 never runs as part of
`enrich_lookup`'s own write, and the new mechanism never runs as part of FK's
cleanup. H5's existing job is still necessary for cases outside this
defect's scope (e.g. a *legitimate* FK deletion of its own helper that
happens to share a sheet entry with an unrelated Lookup record) and is left
untouched.

[[D6]]
[[L]]
== L. Formula/value and foreign-artifact equivalence disposition

*Design Question 6 (user/canonical collisions) answer.* <<F>> and <<D>> are
both stated purely in terms of "does FK have truthful evidence it produced
this column" — neither ever asks "was the current producer Lookup." A
caller-supplied ordinary column that happens to collide with FK's requested
helper label is handled identically to a Lookup-produced collision: skipped
at materialization (<<D>>), never claimed, never deleted by either cleanup
executor without truthful transient evidence (<<F>>). This generality is
structural, not a separately maintained rule — there is no producer-identity
branch anywhere in this design to keep in sync.

*Design Question 7 answer.* Value/semantic-equivalence adoption of a foreign
producer's physically present column (Candidate C) is *rejected outright and
not designed*. Reasons, all evidenced by the accepted research and review:

* Candidate A (decline materialization on collision) is already sufficient
  to close the confirmed defect (<<repro-closure>>); building equivalence
  machinery before it is needed contradicts the design brief's explicit "if
  A or B is sufficient, do not design generic adoption."
* Review 001 names the concrete risk directly: a Lookup-produced formula and
  an FK-produced value can display equal current results while carrying
  different update/lifecycle semantics; current value equality does not
  imply equivalent producer semantics — Review 001's own disproof of the
  original design's optional self-verified-reuse refinement (<<D>>, now
  removed) is a direct instance of this: even a check that inspects nothing
  but a producer's own prior *metadata shape*, not a foreign producer's data
  at all, can affirm a stale claim once the underlying record is no longer
  current. Value/shape equivalence of any kind is not identity.
* The one mechanism this corrected design *does* add that inspects sibling
  state (<<K>>'s write-time invalidation) deliberately checks only
  *presence*, never content, shape, or value, of a foreign subkey — it
  cannot drift into Candidate C because it never reads what a foreign
  record claims, only whether one exists.

No equivalence/adoption machinery is designed for any site in this document.
If a future, separately evidenced need for adopting a foreign producer's
artifact arises, it is out of this design's authorization — see <<R>>.

[[Q]]
== Q. Explicit non-goals

Restated from the design authorization, confirmed absent from every section
above:

* claimant / current-reliance as a required primitive;
* claim registration, claim release, a claim AST, a claim ledger, reference
  counting, a shared-claim protocol;
* a generic artifact registry, stable artifact IDs, global artifact
  identity, or rename-following identity;
* a central producer registry or whole-Domain materialization census;
* Trusted-Ingress redesign, persistence redesign, or schema-maintenance
  redesign;
* promotion, deprecation, removal, or merge of Lookup Enrichment as a
  product concept (<<R>>);
* value/formula equivalence or adoption machinery for a foreign producer's
  artifact (<<L>>);
* any new `_meta` root, sub-key, or schema-version bump — this design adds
  zero new metadata; it only changes which existing, already-registered
  entries are written or consulted, and for what purpose. This holds after
  the correction pass too: <<K>>'s invalidation mechanism *removes* an
  existing subkey under an existing path; it introduces nothing new.

Reconfirmed after this correction pass specifically for the two findings
that could plausibly have reopened scope: <<K>>'s write-time mechanism reads
only subkey *presence*, never a foreign record's shape or content, so it
does not become the "physical-production verification override" the
original design brief explicitly disallowed; and removing the optional
self-verified-reuse refinement (<<D>>, FIND-D2) *narrows* this design
further rather than adding anything.

[[repository-boundaries]]
Also explicitly out of scope: Workbook-View-owned durable sheet helper
declarations (`_meta.sheets[*].helper_columns`). These are not
"untouched because they belong to a different owner" without further
qualification (Review 001 FIND-D5) — the actual, load-bearing distinction is
recorded in <<H>>: explicit human pipeline-author declaration via
`configure_workbook_view`, a canonical "helper values are not source truth"
contract independent of current producer, and a carrier purpose-built by
`BUG-HELPER-CLEANUP-CONTRACT-P4A` for exactly the persistence-surviving
cleanup-identity job this design's own durable-fallback removal now makes
more load-bearing (<<I>>). It remains untouched by <<H>>; its residual
staleness risk is recorded, not treated as zero, in <<R>>.

[[R]]
== R. Deferred follow-ups

* *Restoring automatic post-reimport FK-helper cleanup without a
  Workbook-View declaration* (named gap, <<I>>): if a real maintained or
  credible external consumer is later shown to need automatic deletion from
  durable FK relation policy alone after persistence — despite the
  already-existing, already-documented `configure_workbook_view` migration
  path named concretely in <<I>> — the necessary follow-up is a *new*,
  separately authorized design choosing between (a) a narrow,
  explicitly-scoped, FK-owned physical-production verification performed at
  cleanup time against current source/target data (weighing the
  formula/value risk named in <<L>> honestly, not reflexively), or (b) an
  explicit, opt-in, caller-asserted durable declaration analogous to XRef's
  guarded `drop_source` flag. Neither is designed or authorized here.
* *Whether `configure_fk_helpers`/`infer_fk_relations` should auto-populate
  the Workbook-View `helper_columns` carrier* (Review 001 FIND-D4, evaluated
  but not designed): would remove the dual-configuration burden the
  migration path in <<I>> otherwise imposes on pipeline authors, but crosses
  a family-ownership boundary (FK writing into a Workbook-View-owned
  durable structure) this design's narrowed scope does not authorize
  opening. Recorded as a real, evidenced candidate for a future, separately
  scoped design — not a rhetorical placeholder.
* *Reconsidering the removed optional self-verified-reuse refinement*
  (<<D>>, Review 001 FIND-D2): the refinement's original safety argument
  ("compares only FK's own metadata shape, never a foreign producer's") was
  correct for the question it was built to answer but insufficient against
  Review 001's disproof, because FK's own prior record could itself be
  stale. <<K>>'s write-time invalidation obligation now closes the specific
  staleness Review 001 used to construct that disproof within the
  authorized FK/Lookup pairing. That is grounds for a *future*, separately
  authorized reconsideration of the refinement — establishing affirmatively
  that FK's own prior transient record can be trusted to still describe the
  physical column before re-authorizing shape-based reuse — not for
  reinstating it in this pass.
* *Generalizing the write-time invalidation pattern beyond `enrich_lookup`*
  (<<find-d1-bound>>): `derived_column_policy.py`'s own `output` parameter
  has the identical structural shape (payload from `source`, written to a
  possibly pre-existing, possibly different `output`, with no invalidation
  of any foreign sibling subkey at that `output`) but is not independently
  evidenced as reachable by any current test or documented usage — every
  existing `output` use targets a brand-new frame name. If a future,
  evidenced pipeline shape reaches this path, the same owner-local pattern
  established in <<K>> should be applied there; building it now, ahead of
  that evidence, would be exactly the kind of generic infrastructure this
  design's brief instructs against.
* *Registry and Functional wording* identified in <<M>> but not written.
* *Optional hygiene simplification* in `derived_column_policy.py`
  (<<9-facade>>): reuse `fk_helpers.derived_helper_columns_by_sheet` instead
  of a parallel reader, purely to reduce duplication flagged by an earlier
  review cycle. Not required for correctness.
* *Residual staleness risk of the Workbook-View `helper_columns`
  declaration* (Review 001 FIND-D5, named explicitly rather than implied
  away): nothing prevents a caller from repurposing a historically-FK- or
  Lookup-derived column label for genuine hand-entered data without also
  updating the separately-maintained `configure_workbook_view` declaration,
  and nothing enforces that the declared label is non-editable in the
  rendered workbook. The risk is real, structurally the same shape as the
  defect this design fixes for FK's durable relation policy, and smaller
  only because of the three distinctions named in <<H>> — not absent. Left
  unaddressed here because Workbook View remains a constraint boundary, not
  a mandatory Design-Phase site, per the accepted research's own
  narrowed-scope authorization.
* *Lookup Enrichment user-facing publication posture*: a separate maintainer
  question (not decided here, not decided by this design) is whether Lookup
  Enrichment's independent user-facing product status should be marked, in a
  future DMC/publication-posture convention (e.g.
  `user_facing_documentation: false` with an explicit reason), as
  not-yet-established rather than promoted or merged with FK Helpers. This
  design takes no position and does not touch Lookup's user-facing
  documentation, DMC, or product status. Recorded here only so the intent
  is not lost.
* *Architecture guard* for the boundary in <<9-facade>> (recommended in
  <<O>>, not mandatory; Review 001 recommends promoting it to mandatory
  given it also now guards <<F>>'s corrected sufficiency claim — left to
  implementer/maintainer judgment, not mandated here).
