== 2. Executive verdict

[.lead]
*Final design verdict: NOT READY / MATERIAL CORRECTION REQUIRED.*

The corrected design genuinely closes Review 001's original fields-bearing
Repro 4 by construction and correctly resolves FIND-D2 through FIND-D8. It
does not fully close FIND-D1. A supported `enrich_lookup(..., helpers=None)`

No finding requires a claim ledger, claimant/reliance vocabulary, global
artifact identity, reference counting, adoption machinery, or a generic
rebind framework. The necessary corrections remain bounded and owner-local.

== 4. Corrected-design verification

=== Original Repro 4

The corrected mechanism closes Review 001's exact Repro 4 *when Lookup emits
an `enrich_lookup` record*. The independently reconstructed sequence produced
FK values `['fk-alpha', 'fk-beta']`, then replaced them with Lookup values
`['lookup-alpha', 'lookup-beta']` at `orders._B_name`. Applying the corrected
specified invalidation removes `helper_columns` and leaves only
`enrich_lookup` under `_meta.derived.sheets.orders`. Once the design's
separately required removal of both durable-policy deletion fallbacks is
also applied, neither cleanup executor has an FK deletion candidate.

Result:: *The original fields-bearing Repro 4 closes by construction.* This
scoped result does not close the supported no-provenance variant in
<<find-d9>>.

=== Trigger and ownership

`output != source` is the correct Lookup-local semantic trigger. In both
value and formula modes, `output == source` derives from and preserves the
source columns subject to Lookup's existing collision guards, whereas
`output != source` binds the output name to content derived from a different
frame without consulting the prior output. Triggering on mere DataFrame
object replacement would be too broad because the self-extension path also
publishes a new object while preserving the relevant source-derived
artifact.

The corrected design's stronger phrase “preserves every pre-existing
column's physical content unchanged” should be narrowed. Value mode's final
`where(pd.notnull(...), "")` can normalize a pre-existing missing carrier,
and optional sorting can reorder rows. Neither substitutes an unrelated
artifact under the existing label: source columns remain source-derived and
move with their rows, so the helper artifact and its provenance remain
semantically current. This factual wording correction does not change the
`output != source` trigger.

The registry currently recognizes exactly two producer-owned subkeys under
`_meta.derived.sheets.<frame>`: FK `helper_columns` and Lookup
`enrich_lookup`. Both describe current physical helper-column state. No
registered non-producer state exists inside that sheet entry, and neither
registered record has semantics that survive a decoupled full-frame rebind
independently of the physical state it describes.

Removing a foreign producer subkey at this lifecycle boundary is therefore
a coherent conservative invalidation exception to “each producer updates
only its own subkey,” not an overwrite of another family's semantic content.
A narrower cross-family handoff/API is not currently evidenced as necessary.

The evidence supports a narrow rule for the concrete writers in scope: a
decoupled rebind does not carry forward producer provenance attached to the
old output unless the operation explicitly re-establishes it. It does not
yet justify a framework-wide full-frame-replacement abstraction.

== 5. Repro-4 `helpers=None` variant

`enrich_lookup` explicitly supports `helpers=None`; maintained test
`test_enrich_lookup_no_helpers_returns_source_joined_on_key` pins that
public behavior. The operation still publishes a full output via
`out[output] = enriched`, but `_write_provenance` begins with:

[source,python]
----
if fields is None:
    return
----

The supported sequence was:

[source,text]
----
configure_fk_helpers
  -> add_fk_helpers
  -> enrich_lookup(
       source="orders_supplemental",
       output="orders",
       helpers=None,
     )
  -> remove_fk_helpers

# separately, from the same rebound state:
  -> apply_derived_column_policy(source="orders", policy="drop")
----

Observed runtime facts:

[source,text]
----
before rebind: ['fk-alpha', 'fk-beta']
after no-helper rebind: ['caller-alpha', 'caller-beta']
sheet subkeys after rebind: ['helper_columns']
Lookup provenance written: False
after drop_helpers, column present: False
after derived policy, column present: False
----

The replacement data came from the caller-owned source frame. No `_meta` was
hand-constructed. Truthful-when-written FK provenance survived solely
because no Lookup record was emitted, and both cleanup executors deleted the
replacement column.

This also exposes a same-owner variant: if an old `enrich_lookup` record
already exists at the output, a no-helper decoupled rebind leaves that old
record stale because the corrected “remove foreign, then overwrite own”
sequence has no fresh own record to write.

== 6. Decoupled rebind and `derived_column_policy`

The corrected design records `apply_derived_column_policy(source != output)`
as structurally analogous but defers it because current maintained tests use
a new output name. The runtime, however, imposes no “output must be absent”
precondition and unconditionally assigns:

[source,python]
----
out[output or source] = cleaned
----

The supported sequence was:

[source,text]
----
configure_fk_helpers
  -> add_fk_helpers
  -> apply_derived_column_policy(
       source="payload",
       output="orders",
       policy="drop",
     )
  -> remove_fk_helpers

# separately, from the same rebound state:
  -> apply_derived_column_policy(source="orders", policy="drop")
----

`payload._B_name` contained caller values while `orders` was a pre-existing
FK-enriched output. Observed runtime facts:

[source,text]
----
before rebind: ['fk-alpha', 'fk-beta']
after policy rebind: ['caller-alpha', 'caller-beta']
FK provenance remains: [{'column': '_B_name', 'fk_column': 'id_(B)',
                         'target': 'B', 'target_key': 'id',
                         'value_field': 'name'}]
after drop_helpers, column present: False
after second derived policy, column present: False
----

No `_meta` was hand-constructed. Removing durable FK policy as a deletion
candidate does not close this sequence because the surviving candidate is
truthful-when-written transient provenance. This is a current supported
runtime defect shape, not merely a structural resemblance, so the corrected
design may no longer defer it.

== 8. FIND-D9 -- BLOCKER -- Provenance-free Lookup rebind bypasses invalidation

Design claim:: Corrected design Section K places foreign-sibling
invalidation in `enrich_lookup/operation.py::_write_provenance`: when that
writer writes Lookup's own record and `output != source`, it removes every
other subkey before writing `enrich_lookup`. Its acceptance matrix exercises
only a fields-bearing call that emits that record.

Repository evidence:: The maintained `helpers=None` behavior and current
early return are anchored in
`tests/unit/domain/transformations/test_enrich_lookup.py::test_enrich_lookup_no_helpers_returns_source_joined_on_key`
and `enrich_lookup/operation.py::_write_provenance`. The executable sequence
and exact observed output are preserved in Section 5. It uses supported
calls only and no hand-authored `_meta`.

Consequence:: Lifecycle invalidation remains conditional on provenance
emission instead of on the physical rebind that makes prior provenance
stale. FIND-D1's truthful-and-current sufficiency claim remains false for a
supported Lookup mode, and stale prior Lookup provenance is also possible.

Smallest correction:: Make invalidation an unconditional part of
`output != source` publication, independent of whether this call emits new
Lookup provenance: clear all producer subkeys attached to the replaced
output, including an old `enrich_lookup` record, then write a fresh
`enrich_lookup` record only when this call has helper provenance to record.
Add the Section 5 sequence as a permanent regression ending at each cleanup
executor. This remains owner-local and adds no claim, ledger, identity, or
adoption machinery.

Blocks implementation:: *Yes.* FIND-D1 remains open until this branch is
covered explicitly.

== 9. FIND-D10 -- BLOCKER -- The deferred derived-policy rebind is supported

Design claim:: Corrected design Sections F/R acknowledge
`apply_derived_column_policy(source != output)` as structurally analogous but
defer it because every current test and documented use writes a new output
name and no pre-existing-output case was independently evidenced.

Repository evidence:: The registered public operation has no output-absence
precondition and publishes `out[output or source] = cleaned`. The supported
sequence, transient record, and exact observed results are preserved in
Section 6. No `_meta` was hand-constructed, and both cleanup endings delete
the caller-owned replacement column.

Consequence:: This is the same wrongful-deletion class through current
supported Domain calls at a site already mandatory for the design's FK
cleanup work. Deferral leaves the corrected “truthful and current” rule
false immediately after implementation.

Smallest correction:: Bring `derived_column_policy.py`'s distinct-output
publication branch into the bounded lifecycle design. The Design Phase must
choose and specify family-local safe behavior for a pre-existing output—for
example lifecycle invalidation of provenance attached to the replaced
output, or an explicit raising collision contract—and add the reproduced
sequence as regression coverage. This does not authorize a generic rebind
framework or changes to unrelated transformation families.

Blocks implementation:: *Yes*, for the sufficiency claim and the
`derived_column_policy` slice.

== 10. FIND-D11 -- MINOR -- The seven-slice test order cannot stay green

Repository evidence:: Slice 3's intended invalidation contradicts the
currently green parameterized
`test_enrich_lookup_provenance_write_preserves_nested_caller_ownership`,
which uses `source="src"`, `output="result"`, preloads
`result.helper_columns`, and asserts that subkey survives. The fixture has
no physical `result` frame, so its record is synthetic/stale under the new
lifecycle rule and should be dispositioned, not preserved. Separately,
Slice 5 removes the durable FK fallback while Slice 6, which depends on
Slices 4 and 5, postpones inversion/replacement of the three tests FIND-D4
already proves will fail. This conflicts with the design's full-suite-green
requirement and its claim that Slice 3 can land independently.

Consequence:: The architecture is not invalidated by the slice split, but
following it literally creates red intermediate commits or leaves a
maintained ownership regression asserting the superseded rule.

Smallest correction:: Co-locate each affected regression disposition with
the production slice that changes its contract: the nested-ownership test
with Lookup invalidation, and durable-fallback tests with the executor
change. Alternatively revise the sequence so every landed slice remains
green. The slices need not otherwise be merged.

Blocks implementation:: *No by itself.* It is a required implementation-
preflight/test-plan correction before the affected slices land.

== 11. Persistence, over-invalidation, and final gate

=== Persistence/reimport assessment

*ACCEPT.* Durable FK relation policy alone no longer authorizes deletion.
The corrected design makes an explicit caller-authored Workbook-View
`helper_columns` declaration the supported persistence-surviving cleanup
authorization; omission deliberately leaves the helper in place, and
`no_helper_columns` remains the strict postcondition. The required two-case
roundtrip proves both declared safe cleanup and undeclared fail-closed
survival. The design does not claim that the historical leakage problem
magically disappeared.

=== Over-invalidation assessment

A supported content-equivalence case was constructed: configure FK
relations for frames `A` and `B`, FK-enrich both, then run
`enrich_lookup(source="A", output="B", ...)` for an unrelated helper. The
new `B` carries `A`'s byte-identical FK-produced helper, and the old `B` FK
record has the same shape as `A`'s record.

That does not make the old `B`-local record lifecycle-current: the
replacement copied content from `A`, and no current contract transfers
`A`'s production provenance or cleanup authority to `B`. Dropping the old
record is safe and conservative. It can cause observable helper
classification or automatic-cleanup loss, so it is potentially
compatibility-impacting conservative recomputation/declaration loss, not
unsafe data deletion.

The corrected design's assertion that no legitimate survivor is
“plausible” is stronger than the evidence warrants. The load-bearing rule is
narrower: no current contract authorizes transfer of old-output producer
provenance, even when replacement content is coincidentally equivalent. A
future explicit provenance-transfer/adoption contract could change that
answer, but this design correctly does not invent one.
