== 3. Current FK-helper algorithmic reading

`enrich_helpers(frames, defaults)` (`enrich.py:36`) currently performs:

. legacy `detect_fk` kill switch — early return of the *input* frames
  (`enrich.py:44`);
. resolve durable v2 FK relations from `_meta`
  (`resolve_v2_fk_relations`, `policy.py:32`); raise `missing_fk_policy_error`
  when absent (`enrich.py:47-49`);
. resolve local options: `levels` and `helper_value_mode`
  (`enrich.py:51-52`);
. replay-safety filter: drop relations whose target frame is not loaded in the
  current partial run (`enrich.py:54-66`);
. build the target-side lookup registry + required fields via
  `build_v2_target_registry` (`enrich.py:68`, `policy.py:73`);
. group relations by source frame (`enrich.py:72-75`);
. select strategy: formula-mode installs a `_lookup_formula_provider` closure,
  value-mode leaves the provider `None` (`enrich.py:77-81`);
. derive per-frame `FKDef` work items, skipping frames that do not carry the
  configured FK header (`enrich.py:83-94`);
. build shared id/value maps once via `core.fk.build_id_value_maps`
  (`enrich.py:96-100`);
. process each data frame into a new `out` mapping, materialising helpers via
  `core.fk.apply_fk_helpers` (`enrich.py:102-117`);
. preserve source flatness with `_preserve_source_flatness`
  (`enrich.py:117`, `enrich.py:130`);
. write helper provenance via `_write_helper_provenance`
  (`enrich.py:119`, `provenance.py:13`).

`apply_fk_helpers` is the central materialisation, but the full semantic effect
also includes the flatness postcondition repair and the provenance write. The
phased structure described by `FK-HR-POS-002` is intact.

== 5. Detailed evidence for still-valid findings

=== FK-HR-001 — `detect_fk` kill switch (Disposition 2)

`enrich.py:44` still reads `if not bool(defaults.get("detect_fk", True)): return frames`.
Old evidence matches exactly. New evidence raises this from the source review's
"before-low-touch" to a *public-contract* item:

* `detect_fk: true` appears in bundled public example YAML:
  `examples/pipeline_basic.yml:13`, `examples/pipelines.yml:19`,
  `examples/pipeline_pack.yml:17`.
* The same flag gates the *validation* step, not only enrichment:
  `pipeline/steps.py:120` (`detect_fk = bool(defs.get("detect_fk", True))`)
  toggles `check_unresolvable_fks` (`steps.py:129`).
* Cold-storage `FTR-FK-HELPER-DOCS-DEMO-REALIGNMENT-P5` already debated whether
  `detect_fk: true` is a documented `add_fk_helpers` parameter.

Observable risk: the name still advertises obsolete convention-driven detection;
the switch bypasses the required-policy check and silently no-ops an explicitly
configured step; and it is a *shared* convention flag across enrich and validate.

Recommended next action: treat any rename/removal as a public-contract FTR that
covers both the enrich and validate consumers and the bundled YAML. Required
gate: `test_step_registration`, `test_pipeline_yaml`, `test_bundled_example_pipelines`,
`test_validate_modes`, plus example-YAML review.

=== FK-HR-003 — missing vs unsupported-version collapse (Disposition 2)

`policy.py:48` returns `None` when `schema_version != 2`, and the caller raises
the generic missing-policy error. Old evidence matches. New evidence:
this collapse is *intentional and locked by a test* —
`test_v1_only_policy_is_not_consumed_by_primitives`
(`test_fk_helper_primitives_policy_driven.py:140-160`) asserts a v1-shape policy

boundary*: the producer (`domain/fk_relations.py:216`, `SCHEMA_VERSION`) writes
it; the consumer validates it; the persistence-boundary tests assert `== 2`.

Observable risk is limited to *diagnostics*: a hypothetical future version would
be reported as "no policy" rather than "unsupported version". No future version
exists today. Recommended next action: defer; if a v3 is ever introduced,
distinguish absent / malformed / unsupported states as a diagnostics decision.
Do not weaken the current v1-rejection behavior.

Answer to open Q9: the shared signature genuinely serves both strategies. The

== 11. Configuration-boundary assessment

Problem (FK-HR-005/006/007): `enrich_helpers` receives a raw `defaults` bag and
resolves defaults/normalization/validation inline across several call sites; the
parameter name mis-describes it (it is raw authored config, not resolved
defaults).

Constraints:

* accepted keys are a *public step-config surface* (`detect_fk`, `levels`,
  `helper_value_mode`, plus `id_field`/`label_field`/`helper_prefix`/
  `*_by_target` consumed downstream by `core.fk.build_registry` — note
  `enrich_helpers` itself does not read the latter, but the same bag flows to
  `core.fk` via other steps);
* validation currently raises on unknown `helper_value_mode` (must be
  preserved);
* `detect_fk` semantics are shared with the validate step.

Candidate forms (do *not* presume a dataclass):

* explicit keyword parameters on an internal resolve function;
* an internal resolved value object (`_ResolvedHelperOptions`) built by a single
  boundary parser, distinct in name from the raw bag;
* a narrower `_helper_value_mode(raw_mode: str)` signature (independent, cheap);
* retaining the current shape with a corrected parameter name and a single
  resolution block.

Recommendation: the first slice should take the *cheap, uncontroversial* subset
(narrow `_helper_value_mode` input, single local resolution block, corrected
local naming) and explicitly defer the choice between "resolved value object"
and "explicit parameters" until the public key surface is inventoried against
all steps that share the bag. Naming must distinguish *raw* authored config from
*resolved* runtime options (`HR-03`).
