== Decision summary

[.lead]
The bounded evidence is sufficient to select a first hardening slice, but the
ownership hypothesis remains subject to independent review before implementation.

The current evidence does *not* support one undifferentiated "FK family" that
also absorbs Lookup Enrichment, derived-column cleanup, general reference
validation, Workbook View, rendering, schema maintenance, or Trusted Ingress.
It supports the following working model:

* *FK Relation Helpers* are one coherent Domain family. Relation declaration,
  helper projection, relation-specific layout, FK-helper validation, direct
  helper removal, and the durable/transient metadata joining those operations
  share one semantic and lifecycle problem. Confidence: *high*.
* *Lookup Enrichment* is a separate collaborating Domain capability and a
  plausible small family. It owns an explicit lookup projection into a named
  output, its key/missing/order policy, and its own transient provenance. It
  has no edit inverse and does not share FK relation intent. Confidence in
  separation: *high*; confidence that the current capability needs a formal
  family label rather than remaining a single cohesive capability: *medium*.
* *Derived-column policy* is a cross-capability cleanup executor/operation,
  not established as part of either producer. It owns drop/check execution and
  atomic failure, while the meaning of FK and Lookup artifacts remains with
  their producers. Its current direct knowledge of both metadata shapes is a
  material handoff and partial architectural sediment. Confidence: *high*.
* Workbook View, rendering/adapters, persistence, schema maintenance, and
  Trusted Ingress remain external owners. Generic indexing, formula values,
  and finding/severity mechanisms remain shared mechanics. Shared `_meta`
  storage does not merge these owners.

Nine material handoffs were identified. The recommended first hardening slice
is to make FK provenance cleanup strictly FK-owned and move the conditional
Lookup-provenance reconciliation currently hidden inside FK cleanup behind a
narrow Lookup-owned internal handoff, with no public, metadata-shape, or runtime
behavior change.

== B. Candidate ownership and family boundaries

=== B.1 FK Relation Helpers: coherent family

*Observed current facts.* Both explicit and inferred producers converge on the
same v2 relation shape through `domain/fk_relations.py::apply_v2_relations`.
Every FK primitive consumes that shape and/or the feature's rich derived
provenance. Materialization creates the state that layout, validation, and
cleanup interpret. Tests in
`tests/unit/domain/test_fk_relations_inference.py`,
`test_fk_helper_policies.py`,
`transformations/test_fk_helper_primitives_policy_driven.py`,
`test_fk_helpers_domain.py`, and
`validations/test_fk_check.py` protect that composition.

*Semantic and lifecycle coupling.* The family solves one problem: declare a
relation/display intent, derive non-authoritative helpers, keep and
validate the relation-helper pairing, and remove those artifacts without
losing durable relation intent. Layout and validation are roles within this
capability. Direct drop is the family-owned cleanup transition.

*Metadata coupling.* Durable relation identity and transient rich helper
identity deliberately share `source_frame`, `source_column/fk_column`, target,
target key, and helper mapping. A change in one shape can silently break
materialization, validation, layout, and cleanup. This is internal semantic
and metadata/lifecycle coupling, not mere shared storage.

*Recommendation.* Treat these responsibilities as one FK Relation Helpers
family even while their files remain scattered. Confidence: *high*.

=== B.2 Lookup Enrichment: separate capability

*Observed current facts.* `enrich_lookup` reads explicit source/lookup/output
identity, has symmetric and asymmetric key modes, writes a separate output,
rejects output-name collisions, owns missing/order/allowed-field policy, and
writes its own provenance shape. `_ResolvedKeys` intentionally preserves
asymmetric mode even when the two key names happen to be equal. It does not
write or consume FK relations and does not reconstruct helper edits.

*Why it is not FK Relation Helpers.* The authoritative Intent is a lookup
projection request/policy rather than a durable source-FK relation. Output
identity and helper names differ; asymmetric keys and composite-key rules are
Lookup-local; lifecycle is configure/project/consume/drop rather than
declare/materialize/layout/FK-validate/direct-drop. Shared formula objects,
derived carrier, helper display role, and renderer consumers are mechanics and
relationships, not common ownership proof.

The maintained Dino-Insel consumer demonstrates non-interchangeability:

* `worldbuilding/pipelines/dino_insel/json_to_spreadsheet.yaml` uses
  `configure_fk_helpers` + `add_fk_helpers` in values mode +
  `reorder_fk_helpers` for `places.region_id -> regions` and
  `characters.home_place_id -> places`, requiring relation-specific names such
  as `_regions_name`, `_regions_kind`, and `_places_name`.
* The same pipeline uses five `add_lookup_helpers` steps for matrix outputs,
  each projecting exact `title` by `story_id -> stories.id`.
* `worldbuilding/tests/test_dino_insel_matrix_helper_migration.py` guards those
  five output-specific projections and their inverse cleanup sequence.

*Recommendation.* Keep Lookup Enrichment separate. Treat it as a small family
only if later work adds more owner-local operations; no taxonomy or registry
change is needed now. Confidence in separation: *high*.

=== B.3 Derived cleanup: executor with feature-aware contracts

*Observed current facts.* `apply_derived_column_policy` discovers helpers by
unioning feature transient metadata and durable fallbacks, validates metadata
shape, checks Lookup values when requested, drops columns, and only then
publishes copied output/meta. It knows both provenance subkeys. In contrast,
`remove_fk_helpers` is a narrower FK family operation.

The current FK-private
`fk_helpers/provenance.py::_clean_helper_provenance` conditionally removes an
`enrich_lookup` record when none of that record's declared columns remain.
Tests
`test_fk_cleanup_preserves_input_and_presence_checked_siblings_on_repeat` and
`test_fk_cleanup_conditionally_removes_enrich_and_prunes_empty_containers` in
`tests/unit/domain/transformations/test_derived_provenance_nested_ownership.py`
make this current behavior explicit.

*Inference.* Cleanup execution is shared, but feature artifact meaning is not.
The executor may coordinate feature contracts; it should not become the
authoritative source of FK relation or Lookup projection semantics. Current
direct shape parsing and the Lookup rule hidden in an FK module are sediment to
reduce incrementally, not evidence of one family.

*Recommendation.* Keep derived-column policy as a cross-capability executor.
Give feature-specific provenance interpretation to the feature owner through
narrow internal contracts when hardened. Do not introduce a universal cleanup
protocol or registry without a second concrete need. Confidence: *high*.

=== B.4 Validation boundaries

* FK-helper consistency is owner-local semantics using shared Finding/severity
  mechanics.
* Declarative foreign-key/reference integrity belongs to the general reference
  validation capability; it validates canonical keys, not helper projection
  policy.
* `no_helper_columns` is a generic declaration-bound cleanup postcondition.
* Spreadsheet editing/input constraints are presentation intent and stay
  separate.

The current technical `validations` package is therefore not itself a semantic
owner. Confidence: *high*.

=== B.5 External owners and shared mechanisms

Workbook View owns durable visible presentation identity; rendering owns
backend-neutral-to-physical presentation; adapters execute formulas; schema
maintenance owns safe structural mutation; persistence owns transient pruning;
Trusted Ingress owns controlled-state certification. These relationships are
few enough to state explicitly and do not justify absorbing those owners into
FK or Lookup.

| Do not duplicate Lookup policy semantics in ingress. Public FK formula claims

| H8
| Runtime helper metadata -> orchestrator persistence boundary -> reimport

== D. State, metadata, and lifecycle

=== D.1 Actual FK lifecycle

The evidence supports this bounded lifecycle, with one important correction to
the prompt's provisional wording: helper cells are not an edit-authoritative
surface and are not reconstructed back into the FK.

[source,text]
----
explicit config or bounded inference
    -> merge durable v2 relation Intent
    -> materialize value/formula helper projection
    -> write transient rich provenance
    -> optionally reorder / render / validate / consume
    -> drop derived helper artifacts
    -> persist durable relation Intent and presentation declarations
       while stripping transient provenance
    -> replay projection when requested
----

Owners of the transitions are:

* relation producer and `apply_v2_relations`: declaration and conflicts;
* FK materializer: policy Resolution into helper cells and rich provenance;
* FK layout/validation: relation-local consumption without authority transfer;
* FK direct cleanup or derived cleanup executor: artifact removal;
* orchestrator persistence boundary: transient/durable projection;
* renderer/adapters: physical formula and presentation execution.

=== D.3 Precedence and conflicts

* FK relation collision precedence is explicit and centralized in
  `apply_v2_relations`; no consumer silently chooses between divergent owners.
* FK validation and direct cleanup prefer rich per-sheet provenance where
  present and fall back to durable relation declarations. Derived-column
  policy unions declared identities rather than treating transient state as
  canonical.
* Lookup symmetric inline keys are reconciled against policy and fail on
  conflict. A complete asymmetric inline pair owns key selection while policy
  retains non-key authority.
* Lookup `missing`, allowed/default fields, ordering, duplicate/collision checks,
  and value mode are projection-owner policy, not shared cleanup policy.
* Inbound durable identity is keyed by visible sheet. Therefore cleanup before
  Workbook View re-keying is semantically required, not cosmetic sequencing.

=== D.4 Projection and reconstruction conclusion

Both FK helpers and Lookup Enrichment fit the DMC working Projection concept as
one-way, intentionally redundant derived views. Neither has an edit inverse.
For FK, source FK and target value are authoritative; for Lookup, source key and
lookup frame are authoritative. Helper edits are intended loss on cleanup.

The word "reconstruction" in this pilot therefore has two distinct meanings:

* *artifact identity reconstruction* after persistence, using durable relation
  or Workbook View declarations so derived columns can be removed safely; and
* *projection replay* from canonical sources.

There is no supported helper-cell-to-canonical-data reconstruction. Calling
`remove_fk_helpers` an inverse in registry prose means projection removal, not
a semantic inverse of user edits.

=== E.2 Maintained-consumer impact

Dino-Insel is a material current consumer, not architecture authority.
Its exact dependencies are:

* two explicit FK policies and values-mode projections with relation-specific
  prefixes and reorder steps;
* five asymmetric Lookup projections with exact `title` output;
* five durable Workbook View helper declarations;
* five visible-name cleanup steps before Workbook View mapping, followed by
  `no_helper_columns` guards;
* later FK-derived cleanup on `characters`, `groups`, and `places`.

Consequences:

* FK and Lookup cannot be made aliases without adding a real naming/output
  policy and migrating both directions.
* Removing `reorder_fk_helpers.helper_prefix` needs a small Dino config edit
  even though behavior would not change.
* The recommended first slice has no consumer migration if it preserves the
  current conditional provenance behavior.

=== E.3 Compatibility sediment and documentation drift

* The current runtime is v2-only, but maintained prose still contains remnants
  describing a transitional v1-to-v2 bridge or a v1 write. Examples are the
  simplification/history text in the Functional/Semantic/Technical material
  and the historical lifecycle fields retained in `meta_registry.yaml`. The
  registry's current-state paragraphs and runtime agree that v1 is inert.
  This is documentation sediment, not a live dual authority.
* `core/fk.py` retains convention detection and registry builders used by
  low-level tests, while architecture guards prohibit current Domain FK
  primitives from using them for relation inference.
* Lookup deliberately preserves stale provenance for caller-removed old outputs
  rather than authorizing a global scan. Existing behavior is evidence; whether
  it remains desirable is unresolved and out of the first slice.
* Formula overlap is real but does not prove a shared semantic owner. The
  supported managed-state story is currently asymmetric.

== F. Local Human Readability

=== F.1 Strong structures worth preserving

* `enrich_lookup/policy.py::_ResolvedKeys` gives the equal-name asymmetric case
  an explicit local representation; readers do not have to infer mode from
  string equality.
* `enrich_lookup/operation.py::enrich_lookup` is long but phase-coherent:
  resolve, validate, build, order, publish, write provenance. Its local helpers
  name genuine subproblems. Splitting it mechanically would increase
  reconstruction cost.
* FK `enrich.py::enrich_helpers` keeps relation resolution at the boundary and
  passes deterministic rows to Core mechanics. The comments explaining flat
  column preservation and replay safety carry non-local lifecycle rationale.
* FK and Lookup provenance writers use path-local copy-on-write and preserve
  unrelated producer subkeys. Nested ownership tests make this locally
  verifiable.
* `derived_column_policy.py::apply_derived_column_policy` validates/checks before
  publishing replacement frames/meta, making failure atomicity reconstructable.
* Schema maintenance explicitly deep-copies metadata, ignores transient
  `derived`, and returns original frames on a blocked change.

=== F.2 Avoidable reconstruction hotspots

* FK family semantics span `domain/fk_relations.py`, the FK half of
  `domain/helper_policies.py`, `transformations/fk_helpers/`,
  `transformations/helpers.py`, `validations/fk_helpers.py`, pipeline wrappers,
  and `core/fk.py`. A reader must traverse package kinds before seeing the
  lifecycle.
* `fk_helpers/provenance.py::_clean_helper_provenance` contains an
  `enrich_lookup` predicate. The function name and package imply FK-only
  ownership, so the non-local semantic reason is discoverable only by reading
  the loop and tests. This is the highest-value first hotspot.
* `helper_policies.py` co-locates FK and Lookup producers because they share a
  metadata root, obscuring their separate state models.
* FK `defaults` is a raw option bag containing active mode configuration and
  legacy/no-op hints. Call sites do not expose a small resolved state object.
* `core/fk.py::apply_fk_helpers` still comments that the unresolved-reference
  contract is open, while maintained Technical Model/test behavior now defines
  empty-value handling. The comment increases archaeology and should be checked
  in a later code slice.
* `validate_fk_helpers` combines family-local checks with a generic duplicate-ID
  check controlled by defaults. The reason a non-target sheet participates is
  not obvious from the public name.
* The User Guide describes FK formula mode next to Lookup formula mode without
  showing that only the exact Lookup transition is managed-state certified.

=== F.3 Topology versus algorithmic readability

The FK materializer and Lookup projector are locally coherent algorithms even
though the FK lifecycle is topologically scattered. Conversely, the small
`_clean_helper_provenance` helper is locally compact but semantically crosses
owners. This is exactly why function length/helper count must not substitute for
bounded reconstruction cost.

== I. Recommended first hardening slice

=== Scope

*Name:* feature-own conditional provenance reconciliation at the FK-drop seam.

Implement only the following after independent review:

. Make FK provenance cleanup responsible only for
  `_meta.derived.sheets.*.helper_columns`; prune now-empty shared structural
  containers without treating those containers as FK-owned.
. Move the rule "remove `enrich_lookup` provenance only when none of its
  declared helper columns remains in the affected frame" to a narrow
  Lookup-owned internal function/module.
. Have the FK-drop composition invoke that Lookup-owned reconciliation
  explicitly after its column mutation, preserving current copy-on-write,
  sibling preservation, empty-container pruning, failure, and replay behavior.
. Keep every registered name, YAML parameter, metadata shape, consumer
  sequence, and emitted result unchanged.

The exact internal function name and whether a tiny neutral coordinator calls
both owners are implementation-review details. The slice must not generalize a
universal cleanup protocol from this single seam.

=== Why this is the right first slice

* It has two clear owners and exactly one bounded material handoff (H5).
* It removes the most misleading current `_meta` cross-owner knowledge without
  requiring package migration or public-surface decisions.
* Existing tests already express the compatibility behavior, copy ownership,
  and replay cases.
* It exercises DMC family, relationship, metadata authority, failure/replay,
  and Local Human Readability questions in an independently reviewable change.
* Ordinary Git history gives a direct rollback; no persisted shape or migration
  is involved.

=== Prerequisites

* Independent review accepts at least the FK/Lookup separation and H5
  ownership statement.
* The implementation prompt fixes the current behavior as the compatibility
  baseline rather than opportunistically changing stale-provenance policy.
* Tests explicitly distinguish the FK-owned strip from Lookup-owned
  reconciliation, while retaining the existing composition behavior.

=== Explicit non-goals

No public rename/removal, package-wide move, registry change, metadata schema
change, stale-output global scan, cleanup protocol/registry, Trusted-Ingress
extension, formula-surface decision, schema-maintenance change, consumer
migration, or Core relocation.

=== Completion evidence

The slice is complete when:

* no function under `fk_helpers` contains Lookup key-shape or helper-presence
  semantics except an explicit call to the Lookup-owned boundary;
* FK provenance tests prove only the FK subkey is owned and sibling paths retain
  caller identity where unchanged;
* Lookup tests prove its conditional reconciliation for present, absent,
  malformed-as-currently-specified, and repeated states;
* composition tests prove `remove_fk_helpers` produces semantically and
  structurally equivalent
  public results for overlapping and non-overlapping FK/Lookup helper columns;
* focused FK, Lookup, cleanup, pipeline, persistence, and architecture tests
  pass; and
* maintained docs need at most an internal architecture note, with no public
  contract change.

== Unresolved questions

The following do not block independent review of the first slice:

* Is Lookup Enrichment large enough to name a formal family, or should it remain
  a cohesive capability until a second owner-local operation exists?
* Should the registered FK formula surface eventually be certified, narrowed to
  direct/caller-precondition use, migrated, or removed? A complete maintained
  and external consumer/config search plus managed end-to-end behavior decision
  is missing.
* When may deprecated `on`, ignored prefix parameters, FK mode aliases, and
  `detect_fk` be removed? External migration evidence is incomplete.
* Should stale Lookup provenance for caller-removed output frames be pruned?
  Current tests deliberately preserve it; changing it is not required for H5.
* What installed/external callers rely on historical `core.fk` helpers or the
  unused `core.refs` import path? Repository evidence alone is insufficient for
  removal.
* Should Lookup mismatch interpretation ultimately execute in the Lookup owner
  with derived cleanup only coordinating it? That is plausible but larger than
  the first seam and needs its own bounded cycle.

== J. DMC pilot feedback

=== Questions that materially helped

* Separating owner/family, role/kind, relationship, property, and layer stopped
  projection, validation, configuration, cleanup, and Core placement from
  becoming competing taxonomies.
* The material-handoff test forced the investigation through Workbook View
  ordering, persistence, schema maintenance, and Trusted Ingress without
  turning it into a Domain census.
* Intent versus Resolution and canonical/projected/derived vocabulary exposed
  that helper-cell edits have no inverse and that cleanup reconstruction is
  identity reconstruction, not data reconstruction.
* The prohibition on shared `_meta` as ownership proof was decisive for
  separating FK, Lookup, and cleanup.
* Existing behavior as evidence rather than automatic obligation made the
  compatibility sediment assessable without assuming either preservation or
  removal.
* Local Human Readability exposed a small helper with high semantic
  reconstruction cost while protecting long, coherent operations from
  mechanical splitting.

=== Not applicable or only lightly applicable

* Plugin migration, adapter compatibility shims, architectural-law guards, and
  new machine-readable declarations were not needed for this assessment.
* Complexity Isolation and Cross-layer Neutrality were useful only for the
  bounded `core.fk/indexing/refs` review and did not decide placement alone.
* No true edit inverse exists for these helper projections, so inverse design
  questions reduced to projection removal, replay, and intended loss.

=== Ambiguity/bureaucracy findings

The DMC was workable and did not require a procedural exception. Two wording
points may merit future clarification only after more pilots:

* "reconstruction owner" can be read as requiring an edit inverse; this pilot
  needed an explicit distinction between data reconstruction, artifact-identity
  reconstruction, and projection replay.
* A small cohesive capability with one primary operation (Lookup Enrichment)
  can have clear ownership without yet benefiting from the organizational label
  "family". The DMC already permits bounded ownership models, but an example
  could reduce pressure to name a family prematurely.

These are pilot observations, not findings that require a DMC change.
