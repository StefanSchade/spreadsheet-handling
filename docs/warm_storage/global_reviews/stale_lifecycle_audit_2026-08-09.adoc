== 2. Method

Five parallel read-only research agents, each given the same evidence
standard and the same central question: *"If the Status line and the
`_ftrs_open.adoc` include disappeared, would the repository evidence
independently prove that this workstream still owns unfinished work?"*

For every root: read the FTR/BUG file itself; grep `src/`, `tests/`,
`registries/` for the capability or fix it describes; search git log by
FTR ID, by proposed symbol names, and by test names; check
`project_memory/canonical/ftrs.json` and
`docs_generated/project_memory/current_context.adoc`; check
`docs/warm_storage/` and `docs/cold_storage/backlog/{ftrs_done,wont_do}/`
for review artifacts not sitting as an obvious sibling file; cross-check
whether residual scope was named as reassigned to a successor FTR.

One batch (8 roots) was a deep dive on the highest-probability stale
candidates: the 6 roots that already carry a sibling review/assessment
file, plus the two `FTR-PROJECT-MEMORY-*` AMBIGUOUS carryovers from the
first pass, including the specific question this audit was chartered to
answer for `FTR-PROJECT-MEMORY-TEMPLATE-RENDER-CONTEXT-P1`: does commit
`9f43fbb` resolve every Yellow finding from its review? (Answer: no --
see `#5`.) The other four batches (59 roots, ~13-16 each) covered every
remaining included root with no sibling review file.

Every B/C classification below was independently re-verified by the
synthesizing pass before any lifecycle state was changed (full-file reads
of the FTR, its companions, the originating review, and the fix commit for
the one C; targeted grep/git spot-checks for the three B's). No D
(superseded) candidates were found in any batch.
