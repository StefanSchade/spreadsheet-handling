== A. Executive finding

[.lead]
Spreadsheet-handling has a real cross-capability semantic gap at the point
where a derived artifact already exists, another capability accepts that
physical presence, producer-specific provenance is written, and later cleanup
uses that provenance as deletion authority.

The gap is not hypothetical. A supported current sequence can let Lookup
Enrichment materialize a helper column, let FK Helpers accept it by first-level
label without checking its values or origin, let FK provenance record the
column as if FK had materialized it, and let FK cleanup delete the column while
Lookup provenance still identifies it as part of Lookup's projection. The H5
handoff then truthfully removes stale Lookup provenance *after* deletion, but it
does not decide whether FK was authorized to perform that deletion.

The smallest warranted canonical concept is therefore not yet a central claim
registry. It is a framework-level *derived-artifact lifecycle contract* that
requires an artifact-producing capability to make these decisions explicit:

* which physical artifact identity is requested;
* what happens if that identity is absent or already present;
* whether presence is rejected, proven compatible, adopted, replaced, or left
  unrelated;
* whether metadata means "physically produced", "currently relied upon", or
  another precisely named fact;
* what release of that fact changes; and
* which preconditions authorize physical removal.

Four independent current families evidence or constrain that contract:

. FK Helpers plus Lookup Enrichment expose the reachable shared-column defect.
. Discriminator split/merge uses explicit reject-versus-replace collision
  semantics for derived frames.
. XRef plus final pipeline cleanup uses explicit deletion commands and
  loss/contradiction checks rather than implicit last-claim semantics.
. Cell Codec consumes helper provenance as a participation-exclusion marker,
  demonstrating that not every provenance consumer is a claimant and not every
  provenance record should be reinterpreted as one.

Workbook View re-keying and persistence/replay provide additional identity and
lifecycle constraints but are not counted as separate defect cases.

*Recommendation.* Proceed to bounded canonical Semantic + Technical +
Developer design work. Do not introduce common claim metadata, stable artifact
IDs, a registry, or a generic runtime abstraction in advance of that design.
A central claim structure is plausible as a future derived index, premature as
canonical authority, and not necessary to state or repair the current semantic
problem. Require an independent adversarial review of this assessment before
the Design Phase.

== B. Current derived-artifact model

=== Inventory boundary

This inventory includes physical Domain artifacts for which collision,
reconstruction, inverse processing, or later cleanup is material. It is not a
census of every dataframe transformation. Ordinary extraction, filtering,
sorting, and unrelated rendered carrier objects are excluded. Cells, arbitrary
sheets, external resources, and generic Python objects are not generalized into
the model.

[cols="2,2,2,2,2", options="header"]
|===
| Artifact family | Physical identity | Semantic owner/source state
| Provenance and lifetime | Collision, cleanup, replay

| FK helper column
| Source frame plus first visible/first-level helper label; physical assignment
  uses a padded tuple for MultiIndex frames and flatness is restored for flat
  sources.
| FK Relation Helpers; durable v2 FK relation intent and live target-frame
  values are the source state.
| `_meta.derived.sheets.<frame>.helper_columns` is transient. Durable
  `_meta.helper_policies.fk.relations` can reconstruct the requested helper
  name after persistence.
| Existing first-level label is silently skipped. Direct cleanup drops by
  visible label, preferring transient provenance and falling back to durable
  policy.

| Lookup-enriched output and helper columns
| Named output frame plus flat helper labels inside that output.
| Lookup Enrichment; explicit source/lookup/key/helper step configuration and
  lookup helper policy define the projection.
| `_meta.derived.sheets.<output>.enrich_lookup` is transient and records the
  lookup source and helper labels. The output is a current-run projection.
| Helper collision with the source is rejected. The named output frame is
  assigned/replaced. Generic derived-column policy or FK direct cleanup may
  remove helpers; no durable output-specific reliance record is replayed.

| XRef relation/matrix projection frame
| Configured logical relation and matrix frame names; inside the frame, row
  selectors and matrix-axis identities have distinct validated contracts.
| XRef Crosstable owns the scoped matrix/relation inverse. Durable tuple
  relation and/or edited matrix are physical source state depending on
  direction; XRef Intent defines their relationship.
| `_meta.xref_crosstable` preserves durable inverse Intent while runtime
  Resolution is stripped. Frames are durable only if retained by the pipeline.
| The named output is assigned/replaced. `drop_source=True` contributes an
  explicit transient final-cleanup command after loss checks. Replay resolves
  fresh Resolution from Intent and live frames.

| Discriminator split/merge frame
| Generated target frame name, or configured merge target frame name.
| Discriminator Split owns partition/recomposition meaning. Source rows,
  discriminator values, and durable split metadata are canonical inputs to the
  inverse.
| `_meta.split_by_discriminator` is durable recomposition intent including
  value-to-frame mapping and optional row order.
| Split rejects any existing generated target. Merge assigns/replaces its
  target. No family-local frame deletion occurs.

| Cell Codec output and Compact Multiaxis local intermediates
| Named output frame and configured participating physical columns; Compact
  local temporary names exist only during the composite call.
| Cell Codec owns reversible compact-value representation; explicit runtime
  codec intent and structured/compact payload are source state. Compact owns
  only composition.
| Ordinary Cell Codec writes no durable family metadata. Compact/XRef Intent
  persists where needed; local temporary frames are removed before return.
| Named outputs are assigned/replaced. Decode rejects generated-column
  collisions. Helper provenance excludes helper columns from positional
  participation; it does not establish a Cell Codec claim.

| Workbook-visible sheet identity and durable helper declaration
| Visible sheet name before reverse mapping, then logical frame name after
  `apply_workbook_view_sheet_mappings`; helper identity is the declared visible
  label in the phase where cleanup executes.
| Workbook View owns visible-to-logical frame identity. Feature-local FK/Lookup
  owners still own helper meaning.
| `_meta.workbook_view.sheet_mappings` and sheet-local `helper_columns` survive
  carriers; `_meta.derived` does not.
| Inbound cleanup can occur under visible identity before re-keying. The mapping
  reconstructs frame identity, not producer/claimant history.
|===

*Maintained authority.* The registry classifies `_meta.derived` as transient
producer provenance and explicitly says its subkeys are not authoritative over
workbook structure. It classifies XRef and Workbook View Intent as durable and
pipeline cleanup as transient executable commands.

*Observed runtime fact.* Current FK cleanup nevertheless uses FK's transient
provenance as its first-choice list of physical columns to delete. Provenance
is therefore operational deletion input even though it is not structural
authority in the registry wording.

*Inference.* "Derived artifact" is a useful bounded umbrella for these
lifecycles, but the repository does not have one uniform artifact type. A later
contract must permit family-specific identity, collision, inverse, and cleanup
policies.

== C. Concrete collision and adoption cases

[cols="2,2,3,3", options="header"]
|===
| Current path | Artifact already present | Current behavior | Represented semantics

| FK helper materialization
| Any column whose first-level label equals the requested helper label
| Silently skip; no value, equivalence, origin, or ownership check; then write
  FK provenance for every resolved FK definition.
| Physical presence and FK production are conflated. The behavior is an
  implicit name-only adoption for cleanup purposes, but no adoption fact is
  named.

| Lookup helper projection
| Requested non-key helper already exists in the source
| Reject before merge to prevent shadowing.
| Incompatible until proven otherwise; no adoption path.

| Lookup named output
| Output frame name already exists
| Assign the newly enriched frame to that name, replacing the prior mapping.
| Explicit output replacement by operation semantics; not equivalence-based
  reuse.

| Discriminator split target
| Any generated target frame exists
| Reject all target creation before mutation.
| Existing frame is not adoptable by split.

| Discriminator merge target
| Target exists
| Assign recomposed frame to target.
| Explicit reconstruction replacement.

| XRef matrix/relation output
| Output frame exists
| Assign projected/recomposed frame to output.
| Explicit directional replacement; scoped relation carry-forward remains
  feature-local.

| Cell Codec output / decoded generated columns
| Output exists / generated decoded label conflicts with passthrough
| Output is assigned/replaced; decode-side column collision is rejected.
| Frame replacement and inner-column collision are different policies.

| Final pipeline cleanup declarations
| Multiple producers request the same drop
| Set-union and idempotent reuse of the same deletion command; conflicting
  explicit Workbook View mapping or keep/drop declaration fails.
| Command composition, not artifact adoption or reliance.
|===

*Test evidence.* Lookup source-column rejection, discriminator target rejection,
XRef identity validation, Cell Codec conflict handling, and cleanup command
composition are pinned by current tests.

*Observed runtime fact.* FK's collision path is exactly `if helper_col in
first_cols: continue`; `first_cols` is captured before the loop. No current FK
test names or asserts the authority consequences of a pre-existing helper
collision.

*Inference.* Current Domain behavior already requires the semantic cases
"reject", "replace", and "reuse physical presence by name". It does not yet
have an explicit, truthful "compatible and adopted" case.

== D. FK/Lookup motivating case: reachable versus synthetic states

=== Supported current construction

At the baseline, the following all use supported registered capabilities:

. Configure a durable FK relation from frame `A.id_(B)` to `B.id`, requesting
  helper `_B_name`.
. Run Lookup Enrichment from an independent lookup frame into output `A`, also
  producing `_B_name` with values different from `B.name`.
. Run FK helper enrichment.
. Run FK helper removal.

The observed trace was:

[source,text]
----
after Lookup:        _B_name = [lookup-alpha, lookup-beta]
after FK enrichment: _B_name = [lookup-alpha, lookup-beta]  # FK skipped
derived provenance:  Lookup records helper_columns [_B_name]
                     FK records helper_columns [{column: _B_name, ...}]
after FK cleanup:    _B_name absent; both records absent
----

FK did not compare those values with `[fk-alpha, fk-beta]`. It added its own
provenance despite not performing the physical assignment. FK cleanup then
deleted the label and asked Lookup only whether Lookup provenance remained true
after deletion. Because no declared Lookup helper remained, H5 correctly
removed the stale record.

*Observed runtime fact.* This state is reachable without direct `_meta`
mutation, legacy shape, plugin behavior, carrier corruption, or unsupported
internal calls.

*Maintained authority.* FK and Lookup have separate semantic ownership. H5
correctly places interpretation of Lookup's provenance behind a Lookup-owned
boundary. Nothing in current maintained authority grants FK the right to delete
a physical helper merely because FK later wrote the same label into its own
provenance.

=== Reachability classification

[cols="2,3,3", options="header"]
|===
| State class | Evidence | Disposition

| Supported current runtime
| Lookup creates a colliding helper in the same source/output frame; FK
  configuration and enrichment subsequently request the same helper label.
| Reachable and safety-relevant. This is the primary case.

| Supported user/caller payload
| A caller supplies a pre-existing ordinary column with the requested FK helper
  name; FK skips it, records it, and later removes it.
| Also reachable. No second provenance owner is necessary for the deletion
  authority ambiguity.

| Synthetic regression state
| Nested-provenance tests directly construct `_meta.derived` with FK and Lookup
  sibling records to characterize key-selective cleanup and H5.
| Valuable behavior evidence, but not proof of runtime reachability by itself.

| Historical compatibility/corrupt state
| H5 tests malformed Lookup provenance and legacy/pass-through forms.
| Constrains fail-clear behavior, not the motivating normal-path frequency.

| Maintained consumer state
| No consumer inspected in this assessment.
| Unclaimed; historical reports are navigation only.

| Theoretical unsupported state
| Arbitrary external metadata can invent inconsistent producer records.
| Relevant to validation boundaries only; not needed to establish the primary
  finding.
|===

*Test evidence.* Existing tests establish owner-local merge preservation,
cleanup by provenance, H5 retention/removal, malformed-record behavior, and
durable fallback after transient provenance loss. They do not currently assert
the supported Lookup-then-FK collision sequence or protect a pre-existing
user-owned colliding column.

*Inference.* The H5 implementation is correct within its stated post-mutation
responsibility. The newly evidenced defect is one step earlier: deletion
eligibility was never established.

== E. Independent evidence from other capabilities

=== Discriminator split and merge

`split_by_discriminator` computes every generated frame identity, rejects an
existing target before creating anything, and records durable recomposition
intent. `merge_by_discriminator` reconstructs and replaces its configured
target.

*Test evidence.* Existing-target and duplicate-target rejections are directly
asserted.

*Inference.* Collision policy belongs to operation semantics and direction.
The framework cannot define "existing derived artifact means reuse" as a
universal rule.

=== XRef and final domain cleanup

XRef projection/recomposition may replace a named output. When `drop_source`
is requested, XRef validates source/output distinction, addressability, and
loss conditions before contributing an explicit frame deletion command. The
final executor unions duplicate drop requests, rejects contradictions, executes
only commands, and consumes them. Persisted XRef inverse Intent may still name
a frame that was deliberately removed; that reference is reconstruction intent,
not an active requirement that the physical frame remain.

*Maintained authority.* The Functional Model says source frames remain unless a
feature or builder explicitly declares final cleanup; generic provenance or
classification does not establish precedence. The registry says cleanup
commands are executable instructions, not history.

*Test evidence.* Current XRef and pipeline-cleanup tests pin loss guards,
command production, set-union, keep/drop conflict, Workbook View conflict, and
command consumption.

*Inference.* A universal "referenced by metadata means claimed" rule would
misclassify valid XRef intent. Deletion authority can be an explicit operation
contract without a last-claim ledger.

=== Cell Codec

Position-based Cell Codec gathers helper labels from both durable sheet helper
declarations and transient FK/Lookup provenance, then rejects them when they
are requested as participating payload columns. It does not write a Cell Codec
claim on those helpers and does not require them to remain after the operation.

*Observed current fact.* Producer provenance here functions as a role/exclusion
signal for a third capability, not as evidence that Cell Codec semantically
relies on the artifact's continued existence.

*Inference.* "Consumer" and "claimant" are not synonyms. Recasting every read
of provenance as a claim would distort current semantics.

=== Finding from the independent cases

The four counted families establish a framework-level need for common semantic
questions, not common storage. Only the FK/Lookup case currently proves
multiple simultaneous owner records over one physical derived column. The
other three establish necessary limits on any generalization.

== F. Producer, owner, claimant, executor, and authority distinctions

[cols="2,3,3", options="header"]
|===
| Concept | Required meaning | Current evidence

| Physical producer
| The operation that actually writes/replaces the column or frame state.
| Lookup is the physical producer in the motivating trace; FK is not.

| Semantic owner
| The family that defines meaning, invariants, compatibility, and truthful
  provenance for its projection.
| FK and Lookup remain separate owners even under one frame/label.

| Claimant / current reliance
| A capability whose valid current contract requires the physical artifact to
  continue to exist until release.
| Necessary to describe the motivating shared helper. No generic current
  representation exists. Many consumers, including Cell Codec, are not
  claimants.

| Provenance producer
| The operation that writes metadata describing a derivation or current
  projection.
| FK writes provenance for every resolved definition even when it skipped the
  physical write; Lookup writes output-local projection provenance.

| Cleanup executor
| The operation that mutates the physical frame to remove an artifact.
| FK direct cleanup, derived-column policy, and final pipeline cleanup are
  distinct executors.

| Deletion authority
| The semantic contract whose satisfied preconditions permit the executor to
  remove physical state.
| Explicit and guarded for XRef frame cleanup; ambiguous for an FK helper that
  was merely found by label.
|===

*Inference.* Physical producer, semantic owner, and provenance producer often
collapse in ordinary create-and-clean flows, but cannot collapse in the
motivating collision. Cleanup executor and deletion authority must be distinct:
an executor may know how to mutate without owning the facts that make mutation
safe. "Claimant" is useful only if narrowly defined as continued-existence
reliance, not as any producer, reader, or metadata reference.

== G. Current provenance semantics

=== What `_meta.derived` currently means

The maintained registry calls it current-run helper-column provenance produced
by materialization steps, useful to render, validate, position, and clean
helpers. Technical wording describes what a primitive wrote when it last
enriched a source and describes entries per materialized helper. Runtime FK
behavior is broader: it writes records for resolved FK definitions whether it
materialized the column or skipped it.

Consequently current FK provenance is a mixture of:

* declared projection shape;
* an assertion that a helper label belongs to FK processing;
* operational removal input; and
* usually, but not always, a record of physical production.

Lookup provenance more closely describes the current output projection because
Lookup rejects a colliding source helper and constructs/replaces the output.
Even there, the record is not documented as a formal continued-existence claim.

*Observed runtime fact.* Two producer-specific sibling records can refer to one
physical frame and one physical helper label.

*Observed runtime fact.* There is no named current mechanism for multiple
active claims, claim release, or last-claim deletion. H5 is an owner-to-owner
post-mutation truthfulness handoff, not such a mechanism.

=== Can provenance be treated as claims?

Only with qualification. Owner-local provenance can supply evidence for a
claim when its contract explicitly means current continued-existence reliance.
Current repository-wide provenance does not have that meaning:

* FK provenance overstates physical production on collision.
* Lookup provenance describes a projection, but no release contract is named.
* XRef durable intent may validly reference absent frames.
* Cell Codec reads helper provenance without claiming the helpers.
* pipeline cleanup metadata is a command, not provenance or reliance.

*Inference.* Treating every producer record as an implicit claim would hide the
current ambiguity rather than resolve it. A Design Phase must first refine
owner-local meanings.

== H. Artifact identity constraints

There is no evidence for one globally stable `(frame_name, column_name)`
identity, and no evidence yet requiring UUIDs.

=== Column labels

FK creation, provenance cleanup, and direct deletion use a visible/first-level
label. On a MultiIndex or tuple label, that can identify more physical columns
than a full tuple identity would. Duplicate visible labels are not assigned an
occurrence identity. Lookup operates on flat labels and rejects helper
collisions. XRef separately validates physical labels, durable selector labels,
and carrier-stable axis identities.

*Inference.* The minimum identity is family- and phase-specific. Any common
contract must require an owner to declare its equality/addressing rule; it must
not silently standardize on visible text.

=== Rename and schema mutation

Schema maintenance rejects a rename target that already exists, rewrites or
blocks affected durable FK/Lookup references, and deliberately does not rewrite
transient `_meta.derived`. FK helper rename is documented as unsupported.

*Test evidence.* Current schema-maintenance tests pin durable reference updates
and non-ownership of derived provenance.

*Inference.* A transient name-based claim cannot be assumed to survive schema
mutation. A durable claim identity would create a new schema-maintenance
obligation; current evidence does not authorize that expansion.

=== Workbook View and replay phase

Workbook View persists visible-sheet-to-logical-frame mappings. Inbound helper
cleanup can run under the visible sheet name before mapping re-keys the frame to
its logical name. The mapping is authoritative for frame identity only; it
intentionally does not reconstruct a generic source/projection relationship.

*Test evidence.* The maintained XRef/Lookup inbound integration asserts cleanup
by visible identity before mapping, including the no-op behavior when the
durable helper declaration is omitted.

*Inference.* Artifact identity may be phase-relative. A central index keyed
only by logical runtime frame name would not survive the maintained workbook
roundtrip without duplicating Workbook View authority.

=== Replacement, copy, and derived frames

Transformations commonly shallow-copy the frames mapping and replace the
DataFrame object at an existing logical name. Python object identity is not
semantic identity. Split-generated frames reject collision, while inverse
operations replace targets. This is further evidence against a universal
object-identity or name-only rule.

== I. Cleanup and deletion-authority constraints

Current cleanup mechanisms are intentionally plural:

* FK direct cleanup deletes visible labels from FK provenance or durable FK
  policy and then cleans owner metadata.
* derived-column policy interprets FK and Lookup provenance/policy to remove
  projected columns in an inbound/replacement workflow.
* XRef/other projections contribute explicit frame-drop commands after local
  validation.
* final pipeline cleanup executes explicit frame commands and never infers from
  roles or generic provenance.
* Compact composites remove their own local temporaries before returning.

The following constraints already exist:

. Removing metadata is not equivalent to deleting physical state.
. Producing/requesting metadata is not sufficient evidence of physical
   creation.
. A cleanup executor must preserve sibling owner records unless their owner
   decides they became stale.
. Post-deletion reconciliation cannot substitute for pre-deletion authority.
. A durable inverse reference can remain valid after intentional physical
   deletion.
. User/canonical payload that merely collides by label must not become derived
   and deletable without an explicit collision decision.

*Inference.* "Deletion eligibility" should mean that the owning operation's
collision/release contract and every material cross-owner precondition have
been satisfied. It need not mean a numeric reference count reached zero.

*Unresolved.* Whether FK/Lookup should protect a shared compatible column,
reject the collision, establish owner-local adoption, or reconstruct one owner
after the other is released is a Design Phase question.

== J. Persistence and replay constraints

`_meta.derived` and `_meta.pipeline_cleanup` are stripped at the persistence
boundary. Durable state currently includes FK v2 relations, lookup helper
policies, Workbook View mappings and sheet helper declarations, discriminator
split intent, and XRef Intent. XRef Resolution is recomputed.

=== What can be reconstructed

Durable FK relations can reconstruct which helper label FK would request and
can drive fallback cleanup after transient provenance is lost. They cannot
reconstruct who physically produced an already-present colliding column, what
compatibility check occurred, or whether Lookup/user payload still relies on
it. Lookup policy is keyed by lookup frame and does not itself preserve a
specific source/output materialization claim. Workbook sheet helper declarations
can identify a removable visible helper on reimport, but not its physical
producer history.

*Maintained authority.* Durable Intent should survive; run-local Resolution and
derived provenance should be recomputed. One authority per fact is preferred;
metadata joins should not mirror another owner's contract.

*Inference.* If continued-existence claims remain transient, replay must either
recompute them from authoritative Intent plus live structure or perform cleanup
under a conservative family-specific declaration. A durable central claim tree
would otherwise become a second authority over FK, Lookup, Workbook View, XRef,
and schema references.

=== How current derived-column cleanup handles loss

Current cleanup does not restore historical claims. It uses transient
provenance when available and durable declarations/policy when configured. That
solves name discovery, not shared deletion authority. The maintained inbound
roundtrip can intentionally no-op when the durable helper declaration is
absent.

*Unresolved.* Which minimum collision decision must survive persistence, if
any, versus be re-established on each materialization is decisive for Design.

== K. Trusted-Ingress and schema-maintenance implications

=== Trusted Ingress

Current generic `_meta` admission establishes bounded recursive structure, not
truth of every owner-specific semantic assertion. Helper policy origins include
configuration, persisted meta, plugins, and callers. Plugins can be authorized
to run without making their semantic output correct.

If a future claim structure crossed a carrier or plugin boundary, it could not
be trusted merely because it was structurally admitted. It would need one of
these statuses, to be chosen later:

* internal transient Resolution recomputed by owner operations;
* durable owner Intent validated by that owner;
* a non-authoritative derived index regenerated from owner facts; or
* a new authoritative contract with explicit family-level semantic validation.

*Inference.* A durable central authoritative ledger would materially enlarge
Trusted-Ingress obligations. This research neither authorizes nor designs that
change.

=== Schema maintenance

Current schema maintenance owns rewriting durable references and protecting
configured relations from invalid drop/rename. It intentionally ignores
transient derived provenance. A durable artifact/claim identity that follows
column renames would therefore add a new reference family; a transient identity
may instead expire and be recomputed.

*Inference.* The hidden current contract is not "all metadata follows rename".
It is "schema maintenance follows registered durable references it owns".
Design must not make claim metadata durable without explicitly accounting for
that boundary.

== L. Documentation gap analysis

=== Concepts already covered

Current maintained authority already covers:

* family-local semantic ownership and material handoffs (DMC);
* one authority per fact and Intent/Resolution separation;
* transient helper provenance and durable helper policy;
* explicit final cleanup commands rather than generic lifecycle inference;
* Workbook View frame-only reverse identity;
* XRef's distinct logical, physical-label, selector, and axis identities;
* schema-maintenance ownership of durable references; and
* conflict handling at the writer/operation boundary.

=== Ambiguous or incompatible wording

. The registry calls `_meta.derived` non-authoritative over structure while
   current cleanup uses it as first-choice physical deletion input.
. Technical and contract-matrix wording says FK provenance records each
   *materialized* helper; runtime records every requested FK definition even
   when materialization skipped an existing label.
. "Producer provenance" does not distinguish physical production, projection
   declaration, current reliance, adoption, or deletion authorization.
. The Functional meta-lifecycle chapter contains older boundary assumptions
   such as meta not entering externally, while current Trusted Ingress and
   registry contracts admit caller/plugin/persisted meta under controlled
   rules.
. Some older Semantic mechanism prose around pruning configured FK relations is
   superseded by the current Technical persistence contract, which makes v2 FK
   relations durable.

*Maintained authority.* These documents remain authoritative in their owned
areas; the issue is a missing join between them, not license to rewrite one
owner's model from another chapter.

=== Missing concept

No maintained document currently states the lifecycle obligation that connects:

[source,text]
----
materialization request
  -> collision decision
  -> truthful production/adoption/reliance fact
  -> release
  -> physical deletion eligibility
----

*Inference.* That join is the genuinely missing canonical concept. It should be
defined without declaring all derived artifacts identical.

== M. Candidate architecture families

This comparison is non-binding research. It deliberately does not select a
runtime architecture.

=== A. Owner-local provenance plus explicit handoffs

Description: each family keeps authoritative provenance/reliance facts in its
own shape. Cross-owner mutations use narrow owner-to-owner checks such as H5.

Strengths:

* fits current DMC locality and one-authority-per-fact rules;
* preserves family-specific identities and collision policies;
* avoids a second durable authority and broad migration; and
* can repair the known FK/Lookup composition with a bounded handoff.

Risks/limits:

* every new overlap must be discovered and wired explicitly;
* an executor may not know which owners must be consulted;
* owner-local records still need truthful produced/adopted/reliance semantics;
  and
* many pairwise handoffs could become implicit architecture.

Evidence that would favor it: overlaps remain rare and statically known;
families can determine compatibility and deletion authority locally.

=== B. Central authoritative claim ledger

Description: a common `_meta` structure is canonical authority for artifact
identity, claimant registration/release, and final deletion eligibility.

Strengths:

* one discovery point for concurrent claims;
* common last-release checks; and
* potentially consistent diagnostics across executors.

Risks/limits:

* must encode heterogeneous column/frame and phase-relative identity;
* duplicates producer Intent/provenance unless owners delegate authority;
* becomes a schema-maintenance, persistence, replay, and Trusted-Ingress
  contract;
* risks a semantic dumping ground and generic runtime coupling; and
* would misclassify XRef references and provenance consumers unless claim
  creation is highly explicit.

Evidence that would justify it: several independent supported compositions
need dynamic claimant discovery, pairwise handoffs become unsafe/unbounded, and
owner Intent cannot deterministically answer deletion eligibility without a
shared durable transaction record. That evidence is absent today.

=== C. Owner-local authoritative claims plus a shared derived index

Description: owners retain meaning; a common transient index joins physical
artifact identities to owner-local claim references for discovery. The index is
recomputed and is not source truth.

Strengths:

* centralizes discovery without centralizing family semantics;
* could support executors asking all indexed owners; and
* can remain transient Resolution.

Risks/limits:

* identity normalization remains difficult;
* index staleness can itself authorize a bad deletion unless treated
  conservatively;
* every producer must participate in common mechanics; and
* current evidence has only one supported multi-owner collision.

Evidence that would favor it: a second or third independent shared-artifact
case with discoverability needs, plus a proven deterministic rebuild from
owner-local facts.

=== D. Common lifecycle protocol with family-local representation

Description: canonical docs define required outcomes and invariants for
collision, adoption/reliance, release, and deletion eligibility, while each
family represents them locally. Shared helpers may later emerge only for
identical mechanics.

Strengths:

* addresses the semantic gap before choosing storage;
* makes FK's name-only skip and provenance wording reviewable;
* accommodates reject, replace, explicit cleanup-command, and local-temp
  families; and
* creates evidence for or against later common helpers.

Risks/limits:

* consistency depends on reviews and tests until repeated mechanics justify
  code reuse;
* cross-owner discovery remains explicit; and
* the protocol must be concrete enough not to become aspirational prose.

*Inference.* Current evidence makes D the smallest plausible Design Phase
starting point and A the closest existing runtime family. This is not a final
selection. B is premature; C is plausible only after more independent
shared-artifact evidence.

=== Is common claim metadata necessary?

No current evidence makes it necessary. It is architecturally plausible, but
premature. The current defect can be stated, tested, and later repaired without
choosing ledger storage. Common helper functions would be justified only after
two or more owner families demonstrate genuinely identical registration,
compatibility, release, and identity mechanics; common vocabulary alone is not
such evidence.

== N. Smallest problem statement for Design Phase

[.lead]
For Domain-derived columns or frames that have a later cleanup or inverse path,
define how an operation distinguishes creation, collision, compatible adoption,
replacement, and non-ownership; how its metadata truthfully records the
result; and what owner-local and cross-owner conditions must hold before
physical deletion. Apply the first concrete design to the reachable FK/Lookup
same-frame/same-visible-label case without creating a repository-wide artifact
registry.

The bounded scope is:

* derived columns and derived/projected frames produced by registered Domain
  capabilities;
* only artifacts with collision plus cleanup/reconstruction consequences;
* FK Helpers and Lookup Enrichment as the mandatory concrete case;
* XRef/final cleanup, discriminator split/merge, Cell Codec, Workbook View,
  persistence, Trusted Ingress, and schema maintenance as constraints and
  counterexamples, not redesign targets; and
* canonical Semantic + Technical + Developer wording with testable obligations.

Out of scope:

* cells, arbitrary sheets/resources, renderer/backend artifacts, or generic
  object ownership;
* UUID/stable-ID design;
* a central ledger or reference counter by assumption;
* metadata migration;
* Trusted-Ingress or schema-maintenance redesign;
* changing persistence or current runtime behavior during the Design Phase;
  and
* a whole-Domain producer census.

== O. Questions a Design Phase must answer

. What exact compatibility predicate, if any, permits FK to accept an existing
  helper label: full value equivalence, declared semantic equivalence, common
  source relation, or never?
. Does compatible reuse establish continued-existence reliance, or is it merely
  opportunistic reuse with no cleanup rights?
. How must FK provenance distinguish "assigned by FK" from "found and
  adopted" and from "requested but not owned"?
. What pre-deletion question must FK direct cleanup and derived-column policy
  ask before removing a helper another owner produced or relies upon?
. Is the proper FK/Lookup outcome reject, protect, adopt, replace, or a
  pipeline-order constraint, and what user-visible diagnostic follows?
. Can Lookup's existing owner-local record answer that question, or is a new
  owner-local fact required?
. Which collision/reliance facts are transient Resolution, which are durable
  Intent, and which can be recomputed after persistence?
. How does cleanup under visible Workbook View identity bind to the later
  logical frame without duplicating the mapping authority?
. Which artifact identity rules are needed for flat labels, first-level labels,
  duplicate labels, MultiIndex labels, replaced frames, and inverse operations?
. Should schema mutation invalidate transient reliance, rewrite a durable owner
  reference, or reject the mutation?
. If owner-local handoffs are retained, how does an executor discover every
  material owner without importing sibling internals or growing pairwise shape
  knowledge?
. What failure policy applies to malformed or externally supplied
  adoption/claim metadata at Trusted Ingress?
. What second independent supported shared-artifact case would be required
  before considering a derived index or authoritative central ledger?
. Which tests prove physical producer, semantic owner, continued reliance,
  release, and deletion authority separately?

== P. DMC and methodology feedback

The DMC successfully prevented this research from treating shared `_meta`
storage as shared ownership and directed attention to H5 as a material
handoff. Its one-authority-per-fact, lifecycle, reconstruction, and bounded
scope rules are directly useful.

One future clarification is warranted if an independent review confirms this
assessment. The DMC's state/provenance/reconstruction checklist should ask, for
every materializing family with cleanup:

* What happens when the physical target already exists?
* Did the producer create, prove compatible, adopt, replace, or decline it?
* Does provenance distinguish those outcomes truthfully?
* Which fact grants deletion authority, and can another owner still require the
  artifact?

This is Developer Guide clarification pressure, not a proposed edit in this
task. The Human Readability guidance needs no change: the problematic FK
`continue` is locally readable; the defect is cross-capability semantics, not
line-level clarity.

=== Final research disposition

*Recommended disposition:* canonical Semantic + Technical + Developer design
work, bounded exactly as stated in section N.

*Not recommended:* no action, FK/Lookup-only documentation, or Developer Guide
clarification alone. A local FK/Lookup repair will likely be the first later
implementation slice, but the collision/provenance/deletion obligations are
cross-cutting enough to name canonically before that repair.

Require an independent adversarial review before Design Phase. The review
should attempt to disprove runtime reachability, challenge the four-family
count, test whether the concept can remain entirely FK/Lookup-local, and look
for any current authority that already assigns deletion rights more narrowly
than this assessment found.
