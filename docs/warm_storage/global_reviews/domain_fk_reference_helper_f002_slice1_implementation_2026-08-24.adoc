== 6. Design deviation recorded for independent review: two Lookup entry points, not one [[sec6]]

The readiness design (Section 4) and the review's own F-CORR-1 discussion
describe exactly *one* new Lookup function performing shape validation and
key-form resolution together. Implementing it that way and calling it from
`derived_column_policy.py::_resolve_derived_identity` -- the function that
resolves helper *identity* for the drop step, run unconditionally for every
policy including `drop` -- would have eagerly triggered join-key-form
validation for every policy, not only the value-checking ones.

This is a real, concrete, currently test-pinned behavior conflict, not a
hypothetical one: `test_malformed_key_form_drop_is_value_blind`
(`test_derived_column_policy.py:823-828`) asserts that `policy="drop"` never
invokes key-form validation, even for a record with no join-key form at all
(`{}`) or an explicitly null one (`{"on": None}`, `{"source_key": None}`).
Today this laziness exists because DCP's `_resolve_derived_identity` only
ever called the *shape*-only `_validated_enrich_spec` unconditionally;
`_validated_mismatch_keys` (key-form resolution) was called lazily, only
from `_check_enrich_lookup_values`, itself only reached under
`warn_on_mismatch`/`fail_on_mismatch`.

Folding shape validation and key-form resolution into one function, and
calling that one function from `_resolve_derived_identity`, would have
collapsed this laziness and broken the pinned test above -- an
unauthorized, unintended behavior change, explicitly against Slice 1's own
"zero intended behavior change" contract and against this task's explicit
instruction to stop rather than fold in a behavior change discovered during
implementation.

*Resolution applied:* keep the full interpretation
(`interpret_written_enrich_lookup_provenance`) at exactly the call site
where key-form resolution already ran lazily today
(`_check_enrich_lookup_values`), and add a second, narrower, still
Lookup-owned entry point, `validated_enrich_lookup_helper_columns`, that
performs only the shape-validation half (mirroring the former
`_validated_enrich_spec`) for `_resolve_derived_identity`'s unconditional
identity-resolution use. Both share the same internal shape-validation step
(`_validated_enrich_record_shape`), so the record is never re-validated
twice from scratch in one call. No new metadata, no new inference, no
change to which policy triggers which raise -- only where the parsing
*that already existed* now lives.

This mirrors the review's own F-CORR-1 correction in spirit: a function's
signature (here, which of two ownership boundaries it belongs behind) must
match its actual call site's timing requirements, not a literal design
sketch that did not fully trace every call site. Flagged explicitly here,
as instructed, rather than resolved silently.
