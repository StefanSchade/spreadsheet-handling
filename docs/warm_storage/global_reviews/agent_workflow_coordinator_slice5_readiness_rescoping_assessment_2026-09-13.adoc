== 1. Executive conclusion

The original Slice 5 is no longer one sensible implementation slice. Most of its
domain vocabulary and deterministic state transitions already exist, but only the
one-Hop path is integrated through the supported declarative operator. The
smallest additional capability is not a new workflow model and is not merely
"call the provider twice." It is a *serial continuation driver* that, after one
fully reduced and durably checkpointed Hop, decides from trusted state whether
another invocation is eligible, re-establishes the per-Hop Git and governing-input
preconditions, creates a fresh invocation identity and concrete execution binding,
projects the changed phase plus bounded prior state into a fresh prompt, and then
executes at most one next Hop.

`N=2` is the minimum useful first proof because it is the first value that crosses
the present one-shot boundary. It is enough to prove `H001 -> phase B -> H002`, but
only if the proof also demonstrates the stop/preemption paths that prevent `H002`.
A two-call happy path without those inter-Hop gates would not establish safe
multi-Hop composition.

The current Run/Hop/reducer schema needs no redesign for that first increment.
The required work is composition plus bounded observability and validation at the
existing authority ingress. In particular, no supervisor, parent/child Run,
continuing context, execution selector, machine-readable MaintainerGrant, graph
engine, or DMC-specific code is required.

The existing human-authored WorkItem, pinned profile, pinned repository policy,
and explicit autonomous-Hop limit are sufficient to describe a preauthorized Run
envelope. The future implementation contract must make one operator launch's
meaning explicit: it authorizes *up to* the configured and rollout-capped number
of invocations, never an unbounded retry, and only while all deterministic
continuation conditions remain true. An agent-requested route remains untrusted
input and cannot increase that envelope.

== 2. Current N=1 baseline

=== 2.1 Accepted supported path

*Accepted evidence.* The declarative N=1 operator was accepted by
`agent_workflow_coordinator_n1_operator_review_2026-09-11_review_002.adoc`. It
requires a fresh external state root, pinned clean HEAD, strict committed
WorkItem/Profile/RepositoryPolicy/component/task inputs, exactly one invocation,
and no retry. Its accepted shell distinction is pre-attempt failure versus a
provider-capable attempt, with best-effort attempt evidence on failure.

*Accepted evidence.* The commissioning diary records multiple materially distinct
real N=1 executions: the fail-closed invocation-identity incident, a successful
productive assessment, a successful source/test implementation, and the first
declarative generic-operator dogfood. The last exposed action-authority ambiguity
before the real Run; human review corrected the configuration and the Run then
completed successfully. The fixed commissioning launchers are explicitly
historical evidence, not supported executables.

*Accepted evidence.* Action-authority Review 001 found `AAH-R1`; delta Review 002
accepted the correction. Current strict profiles require `edit` and `commit` as a
pair for mutating phases, required durable artifacts require both, operator
preflight requires every phase's actions to be a subset of repository-policy
actions, and the runtime refuses trusted commit unless the current phase has both
tokens. The agent still has no direct Git authority.

*Accepted evidence.* Slice 4B has a real accepted N=1 happy path: agent-owned
worktree mutation and `CommitIntent`, Coordinator-owned bounded commit, factual
post-commit Git observation, clean completion, and reconstructable Run/checkpoint.
The current-schema provider-conformance obligation is satisfied. Old transient
result compatibility, the optional low-level checkout-validator footgun, commit
ordering, preemption-ledger detail, and naming/efficiency notes remain carried
WATCH/MINOR items.

=== 2.2 Current supported composition

The supported path is:

----
operator.main
  -> one pinned-input preflight
  -> new_run
  -> register_checkout
  -> run_real_one_hop
       -> run_one_hop
            -> preflight Git
            -> fresh prompt + adapter execution
            -> correlate/validate result
            -> optional trusted commit + factual observation
            -> record_hop + reduce_result + checkpoint projection
       -> atomically replace run.json and checkpoint.json
       -> retire dispatch.json
  -> one terminal operator-summary.json
----

*Code fact.* `operator._preflight()` rejects
`WorkItem.max_autonomous_hops != 1`; `operator.main()` allocates one
`invocation_id`; its plan hard-codes `max_autonomous_hops: 1`; and it calls
`run_real_one_hop()` exactly once. The summary is shaped around the last Hop and
one provider outcome. This is deliberate accepted N=1 behavior, not a defect in
that slice.

== 3. Original Slice-5 scope vs current reality

The original section 11.5 bundles at least five independent risk classes:

* serial `N>1` lifecycle composition;
* integrated Finding/correction/re-review convergence;
* optional supervisor judgment;
* prerequisite suspension plus parent/child return/reconcile;
* complex-profile and DMC-shaped profile validation followed by separately
  authorized dogfood.

That bundle made sense before the state/reducer, real N=1 boundary, trusted commit,
generic operator, and action-authority ingress existed. It is now too broad for a
single reviewable change. The first class is the only capability necessary to
cross N=1. The reducer already encodes substantial portions of the second through
fourth classes, but their integrated drivers carry distinct authority and recovery
risks. The fifth class is evidence and application of mechanics, not a prerequisite
for writing the serial driver.

*Assessment.* The "two-hop composition" hypothesis is confirmed only in a
qualified form: `N=2` is the right first rollout ceiling and deterministic proof
size, but the deliverable is an inter-Hop transaction/eligibility driver rather
than a two-call script. Hard-coding a two-node workflow or introducing a graph
engine would rebuild capabilities already represented by finite profile routes.

== 4. Exact N=1 -> N>1 capability gap

=== 4.1 What prevents H002 today

The exact supported-path blockers are:

. *Code fact -- explicit N=1 admission guard.* `operator._preflight()` rejects
  every WorkItem whose `max_autonomous_hops` is not one.
. *Code fact -- one invocation allocation.* `operator.main()` creates one
  invocation ID before the attempt and records one ID in the operator plan.
. *Code fact -- one call.* `operator.main()` calls `run_real_one_hop()` exactly
  once and immediately writes the final summary/exit result.
. *Code fact -- no continuation eligibility loop.* No supported layer checks the
  returned Run for `status == ready`, remaining budget, absence of preemption,
  durable checkpoint publication, clean/current Git, unchanged governing inputs,
  and then elects to invoke again.
. *Code fact -- lower one-Hop function is not a lifecycle gate.* `run_one_hop()`
  invokes the adapter before `record_hop()` checks Run status and budget. A future
  loop must check eligibility *before* calling it; blindly calling the function on
  an awaiting-human or exhausted Run could consume a provider invocation before
  the late state rejection.
. *Code fact -- operator evidence assumes one Hop.* `_summary()` reports commits
  from only the last Hop, reconstructs `changed_paths` as baseline-to-live-HEAD
  (the accepted N=1 WATCH-2), and carries one invocation/provider outcome. That is
  insufficiently precise for N>1 attempt accounting.
. *Code fact -- invocation inputs are initial-phase shaped.* Durable-artifact CLI
  declarations are preflighted only against the initial phase and then passed
  unchanged. A general later required-artifact phase has no phase-specific
  declaration path. The first bounded proof can avoid this expansion by using a
  supported phase shape whose H002 has no required durable artifact; later
  convergence work must solve it deliberately.
. *Code fact -- bounded prior context is not forwarded.* Prompt assembly has an
  existing `ContextItem` seam, but `run_one_hop()` calls it without Run/Finding/
  previous-evidence context and neither vertical API accepts such context. H002
  would see current repository state, current HEAD, changed phase, task, routes,
  and selected components, but not a compact H001 checkpoint/findings/evidence
  projection.
. *Code fact -- part of phase authority is not projected.* The prompt header
  includes scope, routes, and evidence, but not `authorized_actions` or
  `human_gates`; those fields are otherwise only stored/validated. Deterministic
  commit guards remain authoritative, so this is not an action-authority bypass,
  but a first autonomous phase change must make the current phase's declared
  authority/stops visible and must not imply that an unused human-gate label is
  mechanically enforced.
. *Code fact -- governing-file mutation is not an inter-Hop guard today.*
  `observe_hop()` supports `pinned_paths`, but the accepted vertical calls do not
  pass them. A trusted in-scope commit can therefore land a governing input if a
  profile scope includes it; a second Hop would continue with the original
  in-memory objects while the repository copy differed. First N>1 must revalidate
  the pinned WorkItem/profile/policy/task/component facts before H002 or otherwise
  prove those paths cannot change.

The state root itself is not intrinsically one-invocation. Its Run snapshot and
dispatch marker schemas carry sequence, Hop, invocation, base HEAD, and one-Hop
reservation. `run_real_one_hop()` derives the next Hop from `hop_used`, overwrites
the atomic marker for the current dispatch, persists the returned Run/checkpoint,
and removes the marker. Those mechanics can be repeated serially in one Run root.
The fixed `result-message.json`/schema files are transient and may be overwritten,
but the first-N>1 contract must ensure all advancement-relevant facts have already
been promoted to the Run/checkpoint/per-Hop evidence before that overwrite.

== 5. Inter-Hop authority model

=== 5.1 Existing prior authority

*Contract fact.* Authority is partitioned among operator/Run policy, the pinned
profile, the WorkItem/task, deterministic reducer rules, and human gates. The
profile contains finite routes and phase-local scope/actions; the WorkItem names
the authority source, repository, concrete scope, profile, initial phase, and
positive Hop limit. Agent prose, requested routes, claims, and Finding proposals
are untrusted.

*Assessment.* A maintainer-authored committed WorkItem plus the selected committed
profile/policy and an explicit `max_autonomous_hops: 2`, followed by a deliberate
operator launch, can be the preauthorized Run envelope. The operator launch
consumes no implied authority beyond that envelope. The machine need not parse a
second centrally stored grant merely to prove that the selected files and
invocation cap were supplied.

This requires the future contract to state that `max_autonomous_hops` is both a
mechanical ceiling and part of the operator's pre-authorized invocation envelope.
It is an upper bound, not an instruction to spend every Hop. Stops are expected
and dominate the remaining budget.

=== 5.2 Necessary decision before H002

H002 may be invoked without a new human decision only when all of the following
are established by Coordinator-owned logic:

. H001 reached adapter acceptance exactly once and is charged exactly once.
. Its structured result correlated to the exact Run/Hop/invocation and validated.
. Git/result/evidence processing and deterministic reduction completed.
. The applied route was a finite route already declared for H001's pinned phase.
. The route effect is `goto`, and deterministic reduction produced
  `Run.status == ready` in an existing target phase. `complete`, `stop`,
  `await_human`, `suspend_for_prerequisite`, supervisor-required,
  `reconcile_required`, malformed/unknown route, escalation, evidence error,
  anomaly, or any other status prevents H002.
. `hop_used < hop_limit`, and the separately reviewed Slice-5A rollout ceiling
  also permits H002.
. The H001 Run snapshot and checkpoint were atomically published and no active
  dispatch marker remains in the normal in-process path.
. A new pre-H002 observation establishes the registered checkout, exact expected
  `HEAD == H001.end_head`, clean tracked/non-ignored state, resolved submodules,
  and unchanged pinned governing inputs.
. The current phase's scope/actions/evidence/components and phase-specific
  invocation inputs remain within the preflighted Run envelope.
. A fresh invocation ID and a concrete allowed per-invocation execution binding
  are chosen and durably recorded before dispatch.

This is the inter-Hop authority gate. It is deterministic and should remain in
the operator/application composition layer, before `run_real_one_hop()`.

=== 5.3 Why the route request creates no authority

The agent can name only a string. `reduce_result()` first applies mechanical and
human preemption, then looks that string up in the current pinned phase. An unknown
key stops. A known `goto` can target only a phase whose existence was validated
when the profile was parsed. The target phase's scope/actions/role/components and
the outer Hop limit were authored before H001. Reduction, not the result, changes
the phase.

Therefore the chain is:

----
agent request (untrusted evidence)
  -> current finite route lookup
  -> deterministic preemption/finding/budget rules
  -> ready target phase already present in pinned profile
  -> independent inter-Hop eligibility check
  -> H002 under the original operator envelope
----

The unsafe alternative would be treating `Reduction.autonomous_route == true`,
or any agent `outcome=completed`, as sufficient dispatch authority. Neither proves
clean Git, durable publication, unchanged governing inputs, remaining budget, or
eligible Run status. Slice 5A must not introduce that shortcut.

=== 5.4 Authorization consumption

MACHINE-READABLE MAINTAINER GRANT REQUIRED BEFORE N>1:: *NO.*

The historical one-shot proof authorizations were governance records because each
allowed exactly one particular real invocation. They do not demonstrate that a
new authorization aggregate is necessary. For a future preauthorized `N=2` Run,
the committed WorkItem/profile/policy and deliberate bounded operator launch can
state the whole authority before H001. Dispatch markers already consume one Hop at
a time conservatively; the Run budget already persists cumulative consumption.

A `MaintainerGrant` would duplicate authority already carried by the selected
inputs and would not solve the actual missing continuation gate. It should be
reconsidered only if a later requirement needs independently transferable,
revocable, or centrally exclusive authorization across processes. None is
required for one serial local Run.

== 6. Git/checkpoint/persistence readiness

=== 6.1 Required inter-Hop transaction

The required normal path is:

----
H001 preflight: independently observed clean HEAD A
  -> invocation / bounded semantic mutation
  -> optional Coordinator trusted commit B
  -> factual base A .. end B observation
  -> Hop charge + deterministic reduction
  -> atomic Run snapshot + checkpoint publication
  -> dispatch marker retirement
  -> continuation eligibility check
H002 preflight: independently observed clean HEAD B
----

*Code fact.* Existing one-Hop mechanics already implement every operation inside
each Hop and publish the reduced snapshot/checkpoint before returning. Calling the
same accepted real boundary again would independently check `run.current_head`,
which the H001 Hop summary/reduction set to B. No Git transaction redesign is
required.

*Recommendation.* The serial driver must regard the successful return and the
published state as a prerequisite, not hold a speculative next action. It must
perform a fresh pre-H002 observation even though H001's post-observation was clean.
A test-only between-Hop hook may inject dirty state or HEAD movement to prove the
second observation, but no general hook/plugin surface should be added.

=== 6.2 Trusted commit before later reduction rejection

*Accepted evidence.* `S4B-R4` records that commit permission is decided before
route/Finding validity. A valid completed result with an authorized `CommitIntent`
can create a legitimate in-scope commit B, after which the reducer may reject an
unknown route or invalid Finding delta and stop `awaiting_human`.

*Assessment.* This ordering is acceptable for N>1 and requires explicit contract
documentation plus regression coverage, not reordering or rollback:

* the commit exercised pre-existing phase `edit+commit` authority and passed
  independent Git checks;
* the invalid routing/finding fact produces no phase/semantic authority;
* the reduced status is not `ready`, so the inter-Hop gate prohibits H002;
* Run/current HEAD and checkpoint truthfully retain B;
* the Coordinator must not reset or erase legitimate observed work to manufacture
  an all-or-nothing semantic transaction.

GIT/CHECKPOINT ORDERING BLOCKS N>1:: *NO.* `S4B-R4` becomes a required stated and
tested first-N>1 invariant, but no Git semantic change is demonstrated.

=== 6.3 Concurrency and recovery

The accepted single-writer assumption remains valid when Hops are serial: one
process, one checkout, one active invocation, and no authorized writer after H001
returns and before trusted commit/checkpoint/preflight. No lock, worktree fan-out,
or concurrency framework is required. Same-path substitution by an unauthorized
concurrent writer remains outside the declared ownership model; independently
observable movement/dirty state fails closed where visible.

An interruption or uncertain dispatch continues to use `reconcile_required` and
never automatically replays. First N=2 normal-path composition need not implement
a resume command. If a crash leaves a marker or mismatched snapshot/checkpoint,
the next provider invocation must not occur automatically. Operationalizing
multi-Hop resume is a later, separately reviewed slice.

The fixed per-run-root result/schema filenames are acceptable as transient files
only if advancement-critical H001 facts are already in the atomic Run/checkpoint
and referenced evidence. Overwriting them for H002 must never erase the sole copy
of an authority-relevant finding, escalation, binding, or uncertain-dispatch fact.

== 7. Policy/action authority readiness

ACTION-AUTHORITY WATCH-1 BLOCKS N>1:: *NO*, provided the supported N>1 path remains
inside the accepted operator authority ingress.

*Code/accepted-evidence fact.* Operator preflight checks every profile phase, not
only the initial phase, against `RepositoryPolicy.actions`. Consequently a route
from phase A to phase B cannot expose a phase-B action omitted by policy when the
same pinned profile/policy pair passed that preflight. Runtime still requires the
current phase's `edit` and `commit` immediately before trusted Git mutation.

The smallest safe composition is therefore to extend or internally refactor the
current operator so the once-per-Run cross-input preflight is a mandatory
dominator of every iteration. A separate supported driver that directly calls
`new_run()`/`run_one_hop()` without that invariant would turn WATCH-1 into a real
supported-path authority bug. Slice 5A must either reuse the current check or
extract one canonical check and call it before Run creation; it need not move
RepositoryPolicy actions into `Run` or `vertical.py`.

The same authority-ingress review should explicitly prove phase scope and trusted
evidence/component selections across both phases, and prove pinned governing
inputs unchanged before H002. This is once-per-Run validation plus per-Hop
revalidation of facts, not a new authority model.

== 8. Execution-binding/context readiness

=== 8.1 Per-invocation execution binding

*Contract fact.* The current FTR requires a concrete binding per provider-capable
invocation and forbids making model/reasoning/provider/context an immutable
Run-lifetime choice. Execution selection grants no workflow authority.

*Code fact.* The existing boundary already has the needed structural seam:
`run_real_one_hop()` constructs a `CodexCliAdapter` for that call, and the adapter
carries executable, model, and reasoning effort while its argv requests ephemeral
execution. A future driver can ask the same trivial source on each iteration and
obtain the same Codex/Terra/medium/fresh values. Because construction happens per
call, this does not freeze those values in `Run`.

NEW EXECUTION-SELECTION API REQUIRED FOR FIRST N>1:: *NO.* No selector, provider
registry, difficulty classifier, quota optimizer, fallback policy, or Run field is
needed. A small internal value/local helper is permissible if useful for passing
the already-existing adapter arguments, but it must not pretend to be selection
policy.

*Bounded observability obligation.* The actual binding used for each invocation
must be durable evidence associated with that invocation. The current operator
plan records executable and timeout once, while model/reasoning/context are mostly
implicit in defaults/Hop context. Slice 5A should record per-invocation facts such
as Hop/invocation ID, adapter/provider, model, reasoning, context mode, executable
settings, and timeout without adding them to the Run aggregate. Silent fallback
remains forbidden; first Slice 5A has no fallback.

=== 8.2 Fresh context and continuity

CONTINUING CONTEXT REQUIRED FOR FIRST N>1:: *NO.* Strict profile parsing accepts
only `fresh`; Hop records use `fresh`; the Codex path is ephemeral. No accepted
adapter proves continuing context, so first N>1 must remain fresh.

Fresh does not mean stateless. H002 can derive continuity from:

* authoritative repository state and independently observed HEAD B;
* the same Run ID and new Hop/invocation IDs;
* current phase, finite routes, authorized scope/actions, and selected components;
* compact prior Hop summaries and current Finding ledger;
* bounded observations/evidence references and the H001 checkpoint/diff reference;
* the unchanged pinned task payload.

The prompt code already supports bounded `ContextItem` and diff projection, but
the vertical does not currently pass prior Run/evidence context. Slice 5A should

== 10. Proposed Slice-5 rescoping

=== 10.1 Slice 5A -- N=2 serial continuation

Purpose:: Cross the one-shot boundary with the smallest independently useful
serial lifecycle capability.

New capability:: One supported operator Run may execute H001 and, only through the
inter-Hop gate, H002. Preserve N=1 and apply a separately configured/contracted
rollout ceiling of two; do not hard-code a two-node workflow into the model.

Explicitly reused:: Existing Run/Hop/budget schema; finite route reducer; strict
inputs; current operator preflight/action subset; external checkout association;
dispatch accounting; trusted commit; factual Git; atomic Run/checkpoint;
`fresh` prompt assembly and context bounds.

Non-scope:: Finding convergence, failed-gate correction semantics, supervisor,
resume command, prerequisite/child Run, continuing context, provider/model
selection, N>2 rollout, DMC profile/code, real provider, Project Memory.

Deterministic acceptance:: The section 11 minimum proof passes, including fresh
IDs/bindings, authoritative A->B HEAD handoff, durable H001 state, H002 phase/context,
exact budget, no H003, and all H001 stop/anomaly variants preventing H002.

Real provider required:: *NO.*

Independent review required:: *YES*, focused on authority dominance, dispatch
accounting, inter-Hop transaction, and false-continuation adversarial paths.

Evidence to proceed:: Accepted implementation review with all deterministic N=2
criteria green and no unresolved authority/accounting finding. That evidence
permits drafting Slice 5B only; it does not authorize N>1 provider execution.

=== 10.2 Slice 5B -- integrated review/correction/Finding convergence

Purpose:: Move already-proven reducer convergence into the integrated serial
driver without adding judgment machinery.

New capability:: Fresh-context review -> correction -> re-review routes with stable
Finding identity, accurate per-Hop deltas, phase-specific durable-artifact inputs,
and failed-gate versus evidence-error handling. Use the existing non-DMC complex
fixture to falsify DMC overfit.

Explicitly reused:: Slice 5A driver/gate; existing gate authority, Finding states,
finite loops, context bounds, Git/checkpoint, and replay J workflow semantics.

Non-scope:: Supervisor, parent/child Runs, continuing context, DMC code/profile,
real provider, arbitrary N rollout, graph engine.

Deterministic acceptance:: A local fake workflow creates a blocking Finding,
routes to correction, returns to fresh re-review, closes only under declared gate
authority, retains exact Hop/Finding/evidence attribution, completes cleanly, and
also proves non-progress/human/budget stops. Required-evidence `fail` may follow a
declared correction route while `error` hard-stops.

Real provider required:: *NO.*

Independent review required:: *YES*, especially Finding disposition authority and
context/evidence completeness.

Evidence to proceed:: Accepted non-DMC integrated convergence review with no
generic special cases and truthful per-Hop reconstruction.

=== 10.3 Slice 5C -- multi-Hop interruption and explicit resume

Purpose:: Operationalize the already-modeled common reconcile boundary for a
multi-Hop Run, separately from ordinary continuation.

New capability:: Load/revalidate one interrupted current-schema Run, conservatively
charge an uncertain marked dispatch, discard stale continuation, checkpoint, and
resume only after explicit maintainer action; never replay the uncertain Hop.

Explicitly reused:: Dispatch markers, `recover_uncertain_dispatch`,
`require_reconcile`, `resume_after_reconcile`, pinned-input/Git revalidation, and
budget monotonicity.

Non-scope:: Child Runs, old-schema migration, automatic resume, provider retry,
central grant, real provider.

Deterministic acceptance:: Crash-before-marker consumes zero; crash-after-marker
consumes one; crash between H001 publication and H002 dispatch cannot duplicate
H001/H002; changed HEAD/input/anomaly prevents resume; explicit clean resume uses
a fresh invocation ID and remaining budget.

Real provider required:: *NO.*

Independent review required:: *YES*, focused on exact recovery anchors and
authorization consumption.

Evidence to proceed:: Accepted crash/recovery matrix with no automatic replay and
truthful reconstruction without relying on overwritten transient files.

=== 10.4 Slice 5D -- human-authorized prerequisite parent/child lifecycle

Purpose:: Integrate the distinct nested-work authority boundary only after serial
continuation/reconcile are accepted.

New capability:: Explicit human authorization creates a separate child Run,
suspends the parent, and returns through common reconcile without restoring a
stale route.

Explicitly reused:: Existing child/suspension fields and reducer transitions,
Slice 5C reconcile path, separate Run budgets, finite routes.

Non-scope:: Preauthorized/autonomous child creation, recursion framework,
parallelism, supervisor, DMC-specific behavior, real provider.

Deterministic acceptance:: No agent route creates a child; human authorization is
mandatory; parent is inactive during child; return uses current Git/governing
facts; stale next action is absent; anomaly requires human disposition.

Real provider required:: *NO.*

Independent review required:: *YES*, focused on child authority and stale-action
prevention.

Evidence to proceed:: Accepted nested-return/reconcile proof. It does not authorize
autonomous children.

=== 10.5 Slice 5E -- optional supervisor judgment

Purpose:: Integrate the optional read-only classifier only if an actual profile
has a declared ambiguous judgment point that deterministic reduction cannot own.

New capability:: One supervisor invocation consumes a Hop and selects only an
already-declared supervisor route or requests human authority.

Explicitly reused:: Existing supervisor status/finite-route reducer semantics,
fresh binding/context, budget, and preemption ordering.

Non-scope:: Finding disposition, scope/action changes, provider selection,
semantic acceptance, mandatory supervisor, child creation.

Deterministic acceptance:: Forbidden/new/ambiguous choice fails to human; no
Finding mutation; budget charged; mechanical preemption cannot be overridden;
workflows without supervisor remain unchanged.

Real provider required:: *NO* for implementation proof.

Independent review required:: *YES*, because the feature introduces a new
invocation role and judgment boundary.

Evidence to proceed:: A concrete profile need plus accepted fake/local authority
proof. If no need appears, this slice remains optional and may never be built.

=== 10.6 Slice 5F -- profile application and separately authorized dogfood

Purpose:: Demonstrate generic mechanics against realistic profiles only after the

New capability:: First a DMC-shaped declarative profile with no DMC vocabulary in

Explicitly reused:: Accepted Slice 5A/5B mechanics, non-DMC genericity evidence,

Real provider required:: *NO* for profile implementation; *YES only for a later

Independent review required:: *YES* for profile genericity and *YES* for any

Evidence to proceed:: Accepted generic profile review, followed by explicit new

== 11. Minimum first N>1 proof

The first proof should use a fake adapter or fake executable and a temporary Git
repository. Real provider behavior is irrelevant to the driver properties and
would confound authority/accounting with nondeterministic output.

Recommended happy-path fixture:

. Create one strict two-phase profile and a WorkItem with
  `max_autonomous_hops: 2`. Preserve a single Run ID.
. H001 starts clean at A in phase `prepare`, receives `H001` plus fresh `INV-1`,
  mutates exactly one authorized file, returns a valid completed result and
  declared `goto` route, and requests one valid Coordinator commit.
. The Coordinator creates/observes B, records H001 once, reduces to phase
  `verify`/`ready`, and publishes a checkpoint showing B, used `1`, remaining `1`,
  applied route, and H001 evidence. The dispatch marker is retired.
. Before H002, inject no mutation; independently observe exact clean B and verify
  governing inputs. Resolve the same trivial execution binding anew and record it
  against fresh `INV-2`.
. H002 receives `H002`, `INV-2`, base B, phase `verify`, its own selected
  components/routes/scope/actions/human-gate declarations, and bounded H001
  Run/Finding/evidence context in a fresh prompt. It performs observation-only
  completion. The fixture uses no unresolved/non-empty human gate.
. Final state is completed at B, used `2`, two ordered unique Hop summaries, no
  active marker, truthful per-Hop invocation/binding/range evidence, and no H003.

Minimum adversarial acceptance surface:

* H001 `requires_human` or escalation: reduced human stop, invocation count one.
* H001 malformed/uncorrelated/uncertain result: one conservative charge,
  `reconcile_required`, no H002.
* H001 unknown route or invalid Finding delta: human stop and no H002, including a
  variant where a legitimate trusted commit B already exists.
* H001 dirty/out-of-scope/divergent/pinned-input anomaly: no H002. Include one
  injected dirty/HEAD/governing-input change after the H001 checkpoint so the
  independent pre-H002 guard, not only H001 post-observation, is proved.
* Exact budget: when H002 requests another `goto`, reduction records
  `awaiting_human_budget`; provider invocation count remains two and no H003
  marker/identity exists.
* Ineligible Run status supplied to the driver: refusal precedes adapter entry.
* Phase-B action outside repository policy: once-per-Run preflight rejects before
  H001, proving WATCH-1 is not bypassed.

This is intentionally a small matrix centered on false continuation. Existing
N=1 Git/action/serialization tests need not be duplicated wholesale.

REAL PROVIDER REQUIRED FOR FIRST N>1 IMPLEMENTATION PROOF:: *NO.*

== 13. Readiness recommendation

ADDITIONAL N=1 COMMISSIONING REQUIRED BEFORE FIRST N>1 IMPLEMENTATION:: *NO.*

The accepted evidence already covers real correlation failure, uncertain recovery,
productive documentation and source/test WorkItems, review-gate separation,
generic-operator execution, action-authority correction, trusted Coordinator
commit, clean post-observation, and durable reconstruction. Another synthetic or
real N=1 Run would not resolve the actual missing serial driver. The identified
first-N>1 obligations are deterministic and should be proved without a provider.

No current WATCH requires an additional N=1 commission. The concrete requirements
that matter before H002 -- pre-dispatch eligibility, governing-input/Git
revalidation, phase-correct context, per-invocation binding evidence, and truthful
N>1 summary -- belong in the Slice-5A implementation contract and deterministic
acceptance proof.

ORIGINAL SLICE 5 SHOULD BE SPLIT:: *YES.*

RECOMMENDED FIRST N>1 SUB-SLICE:: *Slice 5A -- N=2 serial continuation:* extend
the accepted operator composition to perform at most one deterministically
authorized continuation after H001, with fresh context/identity/binding,
independent Git and governing-input verification, durable checkpointing, and fake
local proof only.

READY TO DRAFT BOUNDED FIRST-N>1 IMPLEMENTATION CONTRACT:: *YES.* Readiness means
the contract can now be drafted with the section 11 acceptance surface. It does
not mean implementation, `N>1` execution, a real provider call, or any later
sub-slice is authorized.

Blockers to satisfy in that future contract::

* replace the N=1-only supported composition with a rollout-capped serial driver
  while preserving N=1;
* establish continuation eligibility before adapter entry;
* publish and revalidate the H001 checkpoint, HEAD, checkout, and pinned governing
  inputs before H002;
* allocate/record a fresh invocation ID and concrete binding per Hop;
* project phase-B and bounded prior Run/Finding/evidence context under `fresh`;
* make operator evidence truthful per Hop and prove exact budget/no H003;
* keep the same once-per-Run policy/action authority ingress so WATCH-1 remains
  non-blocking.

WATCH / later:: Integrated Finding convergence and its attribution/artifact/evidence
corrections; multi-Hop resume; prerequisite parent/child; optional supervisor;
DMC-shaped profile/dogfood; all execution-selection, provider-diversity,
continuing-context, concurrency, sandbox-portability, and centralized-grant ideas.

Final disposition:: *Technically ready to draft a bounded Slice-5A implementation
contract. Slice 5 remains not authorized by the normative FTR, and this assessment
does not change that status.*
