=== 5.1 Is the constraint real?

Yes, and it is stronger than "would break one pinned test." Independently
read: `apply_derived_column_policy`'s own docstring
(`derived_column_policy.py:84-90`) states the *documented policy contract*:
"`drop` -- remove derived columns; no value comparison." Key-form
resolution exists for exactly one purpose -- to compute the
`(payload_keys, lookup_keys)` a *value comparison* needs. A policy whose own
documented contract is "no value comparison" therefore has no legitimate
reason to ever trigger key-form resolution, independent of whatever any
particular test happens to pin. `enforce_derived_column_policy_frame`
(`derived_column_policy.py:225-259`) confirms this structurally:
`_resolve_derived_identity` runs unconditionally for every policy (line 243);
`_check_enrich_lookup_values` (where key-form resolution lives) is gated
behind `policy in ("warn_on_mismatch", "fail_on_mismatch")` (line 247) --
this gating is original, untouched code, not something Slice 1 introduced.
Folding key-form resolution into the function `_resolve_derived_identity`
calls would not merely break a test; it would make `drop` silently start
performing work its own documented contract says it never does.

=== 5.2 Was a single merged function actually authorized by the governing chain?

Independently re-read `2a8ff36` Section 4 and `c7f205c` Section 18
side-by-side with the actual pre-6f15026 call graph. Two independent
tensions exist, not one:

* Section 4's literal sketch is one function,
  `interpret_written_enrich_lookup_provenance`, doing "exactly what
  `_validated_enrich_spec` + `_validated_mismatch_keys` + ... do today."
  Section 18's own instruction is to have `_resolve_derived_identity` "call
  the two new facade functions" -- which, read as "one per owning family"
  (the only reading consistent with Section 4's one-function sketch), means
  calling the *merged* Lookup function from `_resolve_derived_identity`,
  unconditionally, for `drop` too. This is the deviation both the
  implementation record and the ultrareview already identify and discuss
  (`291c6b5`, Section 4).
* A second, narrower tension neither the implementation record nor the
  ultrareview names explicitly: `c7f205c` Section 18 also states, in the
  same paragraph, "It must not touch `_check_enrich_lookup_values`... no
  other change to this module in this slice." The actual diff *does* edit
  `_check_enrich_lookup_values`'s body (its provenance-extraction preamble,
  `derived_column_policy.py:540-551`) -- necessarily, because the same
  Section 18 paragraph explicitly authorizes removing
  `_validated_mismatch_keys`, and that private function's only call site was
  inside `_check_enrich_lookup_values`. Removing a function without updating
  its sole caller is not an available option; the literal "must not touch"
  wording and the literal "remove `_validated_mismatch_keys`" instruction in
  the same sentence are mutually unsatisfiable as written. Read charitably
  (and the only way that makes the sentence coherent), "must not touch
  `_check_enrich_lookup_values`" means its comparison/finding-construction
  body (`lookup_df = lookup_frames.get(...)` onward, line 553+), which is
  confirmed byte-identical in the diff -- not its provenance-extraction
  preamble, whose replacement is the direct, unavoidable consequence of an
  explicitly authorized removal.

Both tensions are gaps in the governing chain's own call-site tracing (the
same class of gap F-CORR-1 itself caught, pre-implementation, on the FK
side), not implementer errors. The implementer resolved the first
explicitly (implementation record Section 6); the second was
absorbed silently as an unavoidable consequence of the first without being
named as its own deviation. Recorded here as a supplementary observation,
not a new deviation requiring separate resolution -- see <<find-1>>.

=== 5.3 Is the resulting split semantically coherent, not just test-preserving?

Yes, on two independent grounds, one already cited by the ultrareview and
one newly verified here:

* **Precedent** (ultrareview's own finding, independently reconfirmed): read
  `reconcile_enrich_lookup_provenance` directly
  (`enrich_lookup/provenance.py:252-293`). It extracts only
  `helper_columns` identity and never reads `on`/`source_key`/`lookup_key`
  at all -- an existing, unmodified, H5-accepted function already treating
  shape/identity as separable from key-form, for a different caller with
  the identical requirement (identity, not key semantics).
* **Documented policy contract** (newly cited here, <<sec5-1>>): `drop`'s own
  docstring commitment to "no value comparison" is a stronger, more
  authoritative basis for the laziness than test-pinning alone -- the tests
  (`test_malformed_key_form_drop_is_value_blind`,
  `test_asymmetric_drop_mode_is_value_blind`) are evidence that this
  contract is enforced, not the source of the obligation itself. This
  directly answers the task's instruction not to accept the deviation
  "merely because it preserves tests": the deviation is required by
  `drop`'s own documented semantics, independent of any test.

`InterpretedEnrichLookupProvenance`'s four fields are consumed exactly as
designed (`_check_enrich_lookup_values` converts every field to a plain
`list`/`str` immediately, confirmed at `derived_column_policy.py:549-551`);
the split does not pressure the value object to grow or fragment further.

*Verdict: ACCEPT DEVIATION.* Primarily disposition (A) with an element of
(C) (per the ultrareview's own A/B/C/D framing, independently reconfirmed
rather than adopted): a necessary preservation of two distinct semantic
timing contracts, not accidental API duplication, and mild evidence the
readiness design under-traced its own retained call site on the Lookup
side -- the same class of gap F-CORR-1 caught on the FK side. Not a
MATERIAL design violation and not a mere test-preservation artifact: it is
grounded in `drop`'s own documented "no value comparison" contract, which
is independent of and prior to any test.

=== FINDING-001 -- MINOR -- overstated "never re-validated twice" claim (confirms UR-001)

*Observation:* `enrich_lookup/provenance.py`'s module docstring
(lines 37-39) and the implementation record (Sections 4, 6) both claim the
two entry points share `_validated_enrich_record_shape` "so the record is
never re-validated from scratch twice in one call." Under
`warn_on_mismatch`/`fail_on_mismatch`, this is false: `_resolve_derived_identity`
-> `validated_enrich_lookup_helper_columns` validates the record's shape
once; `_check_enrich_lookup_values` -> `interpret_written_enrich_lookup_provenance`
validates the identical record's shape again, from scratch, in the same
`apply_derived_column_policy` call.
