qualifications*. It accurately synthesizes the completed three-family Human
Readability investigation, keeps direct evidence, cross-family inference, and
broader AI-development hypothesis honestly separated, treats readability as a

== 6. Trade-off-model assessment

Seven named trade-offs, each with two legitimate pressures and a "larger reader
cost" test.

[cols="3,1,1,1", options="header"]
|===
| Trade-off | Both sides legitimate? | Hidden default? | Evidence both sides?

| Narrow deps vs coherent domain values | Yes | No | Yes (FK bag; EL policy; XRef descriptor)
| Small functions vs algorithmic locality | Yes | No | Yes (XRef 516/411)
| Strong typing vs truthful heterogeneous boundaries | Yes | No | Yes (`_ResolvedKeys` vs `Any` cells)
| Vocabulary purity vs boundary truth | Yes | No | Yes (`lookup_sheet`, `derived.sheets`)
| Explicitness vs idiomatic language | Yes | No | Yes (rejected Java-shaping)
| Reuse vs local explainability | Yes | No | Yes (shared tabular validators vs XRef order)
| Minimal APIs vs visible contracts | Yes | No | Yes (FK raw bag)
|===

No pair is rhetorical balance followed by a hidden universal default: the decision
rule is to "name the reader question before the change, the reader question after
the change, and the contract cost of moving between them" (202–204), and the
document accepted real changes (FK Slice 1, formula provider) as well as three
"Stop here" outcomes — so it favors neither change nor status quo by default. An
AI reviewer could still, in principle, latch onto one proxy, but the paired
counterexamples and the explicit before/after reader-question requirement are the
intended guard, and they are present.

CR1-MIN-004 records the one precision gap: the per-row framing centers "reader
cost" while some pairs (notably "Minimal APIs vs visible contracts") trade
compatibility and maintenance cost; the concept distinguishes these only at line
204, not in the axis framing.

*Result: symmetric; decision criterion usable; Minor precision item only.*

== 12. Static-analysis and practical-usability assessment

*Static analysis:* the boundary is realistic. Static tools supply mechanical
evidence (import cycles, public-surface drift, complexity and duplicate signals,
missing type coverage, declared architecture contracts, persistence invariants)
that "can direct the Sentinel toward a location and can guard a decision after
humans establish it" (597), while judgment remains for authority-overstating
names, coherent-vs-broad mappings, long-function locality, comment value, layer
truthfulness, ceremonial types, and extraction cost (599–603). The concept does
not dismiss metrics, does not claim static analysis can determine reader cost,
does not overstate SonarQube (named only as a signal source in a future tandem,
534), and permits static guards only for forbidden dependency directions
(340, 383). It creates no static style rule (605–608).

*Practical usability:* the concept is applicable during an ordinary Domain refactor
cycle (659), keeps the concept/guide distinction explicit (30–34, 651–659), gives
decision support (trade-off table + reviewer questions) rather than philosophy
alone, and explicitly guards against making every small refactor a formal program
("A finding is not a task", 569; "without creating a style bureaucracy or an
automatic source of work", 661–662). It is long and dense with project-internal
references, which is acceptable for a concept and is precisely what the later,
distilled guide is meant to resolve.

*Result: realistic static-analysis boundary; practically usable; low bureaucracy
risk.*
