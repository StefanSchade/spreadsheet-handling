== 1. Scope / question

This assessment asks whether any *material hidden cross-owner ontology*,
duplicated foreign semantic knowledge, or misplaced semantic ownership remains
inside the bounded FK / Reference-Helper family slice and its concrete
immediate consumers after F-002 closed.

The operational test is the Domain Maintainer Contract (DMC) question:

[quote]
____
Does some capability still need to understand another capability's internal
Domain semantics or metadata representation in order to perform its own job?
____

This is not a request for a global Domain census, file-layout normalization,
public-surface consolidation, bug fixing, or Family Cycle 2. Dependencies were
followed only where current source presented a concrete candidate for hidden
FK or Lookup ontology.

== 3. Cycle-1 closure criterion

Family Cycle 1 may close only if all of the following hold in the bounded
slice:

. no material hidden cross-owner ontology remains;
. owner-local handoffs keep foreign primitive semantics out of consumers;
. remaining work is later-cycle work, a separate bug/FTR, or harmless residue;
. F-002 and H5/deletion-authority closure remain valid; and
. closure requires no speculative global abstraction or taxonomy.

The DMC does not require zero coupling. An explicit producer/consumer handoff
may carry an owner-defined semantic value. A Cycle-1 defect exists when a
consumer privately reconstructs the producing owner's representation or
semantic algorithm, especially where a one-sided representation change would
silently break or change the consumer.

== 5. DCP closure check

Current `derived_column_policy.py` was read in full at `74df62a`.

=== 5.1 Lookup knowledge removed

DCP no longer contains or reconstructs:

* the `on` versus `source_key` / `lookup_key` representation rules;
* symmetric/asymmetric key-form validation;
* Lookup canonical-map construction;
* duplicate-key policy;
* scalar mismatch-row calculation;
* `LookupFormulaSpec` structural relationship interpretation; or
* the multi-key formula-mode inability-to-verify rule.

It extracts the raw per-sheet `enrich_lookup` record from the shared
`_meta.derived.sheets[frame]` container, then calls the Lookup facade:

* `validated_enrich_lookup_helper_columns` for value-blind helper identity;
* `interpret_written_enrich_lookup_provenance` when a mismatch policy makes
  key interpretation relevant; and
* `evaluate_lookup_mismatches` for Lookup-owned mismatch meaning.

The returned `InterpretedEnrichLookupProvenance` and `LookupMismatchReport`
are explicit owner-local handoff values. DCP consumes their semantic results;
it does not reproduce the algorithm that created them.

=== 5.2 FK knowledge removed

DCP no longer parses entries inside transient FK `helper_columns`. It performs
the accepted composite-side extraction:

[source,text]
----
_meta.derived.sheets[frame].helper_columns
    -> raw per-sheet value
    -> fk_helpers.validated_helper_columns(...)
----

This follows F-CORR-1 exactly: the shared composite navigates the shared
container; the FK owner interprets the raw owner value.

DCP's diagnostic-only durable-policy path calls
`resolve_v2_fk_relations`. Its subsequent selection of source-matching helper
identity is an explicit FK facade handoff used only to report that durable
intent is *not* deletion authority. It does not infer a relation, validate FK
values, materialize helpers, or turn durable policy into deletion candidates.

=== 5.3 Knowledge correctly retained by DCP

The following current knowledge is DCP-owned and is not ontology leakage:

* navigation of the shared `_meta.derived` / `sheets` composite container;
* recognition and routing of the two owner subkeys;
* union with explicit durable Workbook-View helper identity;
* policy selection (`drop`, `warn_on_mismatch`, `fail_on_mismatch`);
* severity, DCP `rule_type`, and Finding construction;
* aggregation and the `fail_on_mismatch` boundary;
* diagnostic-only enforcement that durable FK policy is not deletion
  authority; and
* provenance consumption plus payload/findings publication lifecycle.

*DCP residual-ontology verdict: NONE.* F-002's DCP relocation is genuine in
current source, not merely a review-artifact claim.

== 6. Lookup closure check

Current `enrich_lookup/{__init__,operation,policy,provenance,mismatch}.py` was
read in full.

Lookup now owns its complete primitive seam locally:

* `policy.py` owns call-time symmetric/asymmetric key selection, missing/order/
  helper/value-mode policy, and the shared duplicate-key predicate;
* `operation.py` owns projection, collision checks, ordering, formula/value
  production, and written provenance;
* `provenance.py` owns the written-record shape, key-form interpretation,
  helper identity, and H5 truthfulness predicate; and
* `mismatch.py` owns canonical-map construction, current duplicate-key
  validity, scalar mismatch, formula structural mismatch, and unverifiable
  outcomes.

`mismatch.py` has no runtime dependency on FK and contains no FK relation,
target, cleanup, validation, or provenance semantics. Its only feature-local
dependencies are Lookup provenance and the shared `LookupFormulaSpec`
carrier.

Lookup does not construct a DCP `Finding`, select severity, choose a DCP
`rule_type`, aggregate findings, implement warn/fail policy, or publish the
findings/payload lifecycle. References to those responsibilities in
docstrings state the boundary; they are not executable ownership.

One stale sentence in `InterpretedEnrichLookupProvenance`'s docstring says
mismatch evaluation remains DCP-owned until a later slice. Current runtime and
the surrounding module documentation correctly show that Slice 2 already
moved it. This is documentation residue, not surviving semantic ownership.

*Lookup residual-ontology verdict: NONE inside Lookup.*

== 7. FK closure check

Current FK relation, configuration, transformation, layout, and validation
sources were read in full or at their complete relevant call sites:

* `domain/fk_relations.py`;
* the FK half of `domain/helper_policies.py`;

  formula_provider}.py`;

* `validations/fk_helpers.py`.

The strict transient-provenance reader
`fk_helpers.policy.validated_helper_columns` is owner-local and accepts only
the already-extracted raw per-sheet value. It does not walk `frames`, inspect

The existing `derived_helper_columns_by_sheet` reader remains intentionally
lenient for its established FK consumers (direct cleanup, FK layout, FK
validation, and column-role helper identity). Different strictness does not
create cross-owner ontology: both functions interpret FK-owned state, for
different caller contracts.

`fk_helpers/provenance.py` retains only one Lookup key literal, used to route
the opaque sibling record to
`enrich_lookup.reconcile_enrich_lookup_provenance`. It passes post-mutation
column labels and applies the returned Boolean; it does not read Lookup's
`helper_columns`, key form, formula, or mismatch semantics. This is the
accepted H5 handoff, not a shadow Lookup parser.

FK validation and layout still read resolved FK relation/provenance values,
but those are roles inside the accepted FK family even though their modules
are not all physically nested under `fk_helpers/`.

*FK residual-ontology verdict: NONE inside the accepted FK family.*

== 8. H5 / deletion-authority consistency

Current source remains coherent with the closed H5/deletion-authority result:

* `fk_helpers.enrich_helpers` records only definitions physically materialized
  by the current call;
* direct FK cleanup derives deletion candidates only from current transient FK
  provenance;
* durable v2 FK relation policy is used for configuration/precondition and a
  non-raising refusal diagnostic, never as physical deletion authority;
* `enrich_lookup.operation._write_provenance` invalidates all stale provenance
  at a decoupled output rebind before writing any fresh Lookup record;
* DCP uses the same transient-FK-only deletion-authority rule and invalidates
  stale provenance at each of its physical publication targets;
* FK hands Lookup record truthfulness to the Lookup-owned H5 facade;
* Workbook View's explicit durable `_meta.sheets[*].helper_columns` authority
  remains separate and is not treated as FK provenance; and
* `pipeline.persistence_boundary` strips top-level transient `derived` while
  preserving durable helper policy and Workbook-View intent.

No current contradiction was found. The Cell Codec finding below consumes
provenance incorrectly but neither grants deletion authority nor mutates the
closed H5/deletion-authority lifecycle. It therefore blocks Cycle 1 without
reopening the deletion-authority subroutine.

*H5/deletion-authority consistency verdict: INTACT / REMAINS CLOSED.*

=== 9.2 Concrete counterexample

`domain/transformations/cell_codec/frame.py::_helper_columns_for_frame`
performs all of the following itself:

* navigates `_meta.derived.sheets[frame]`;
* assumes the sibling `helper_columns` value can be converted directly to a
  set of column names;
* opens `enrich_lookup` and reads its `helper_columns` member directly; and
* uses the resulting union to enforce Cell Codec's owner-local exclusion
  policy.

The helper is not using either owner facade. Its one generic parser is not
semantically valid for both shapes:

* Lookup writes `helper_columns: [<string>, ...]`;
* current FK provenance writes
  `helper_columns: [{column, fk_column, target, target_key, value_field}, ...]`.

A read-only public-path probe through `encode_cell_values` with current rich
FK provenance reproduced:

[source,text]
----
TypeError: unhashable type: 'dict'
----

The current Cell Codec unit test uses `derived.helper_columns: ["b"]`, which
matches neither current rich FK writer output nor the nested Lookup record. It
therefore protects the shadow assumption rather than either current owner
contract.

This is material under the Cycle-1 test: changing either owner representation
requires synchronized private knowledge in Cell Codec, the code already
misunderstands current FK representation, and Cell Codec cannot reliably
enforce its own rule without foreign semantic interpretation.

== 13. Formula-producer defect disposition

== 16. Findings

[[finding-001]]
=== FINDING-001 -- MATERIAL -- Cell Codec privately reconstructs FK/Lookup helper identity and misreads current FK provenance

Affected source::
`src/spreadsheet_handling/domain/transformations/cell_codec/frame.py::_helper_columns_for_frame`
and `_column_name_set`, called by `_reject_helper_participating_columns` from
the public position-based `encode_cell_values` path.

Observation:: Cell Codec directly opens the FK `helper_columns` and Lookup
`enrich_lookup.helper_columns` carriers and applies one locally invented
shape-normalizer to both. This is foreign primitive interpretation rather
than an owner handoff.

Evidence:: Lookup writes a list of strings; FK writes a list of rich mappings.
The Cell Codec parser calls `set(value)` for either iterable. A public-path
read-only probe with a current rich FK entry raises `TypeError: unhashable type:
'dict'`. Its existing unit fixture instead supplies a list of strings directly
at the FK subkey, masking the mismatch.

Semantic owners:: FK Relation Helpers owns interpretation of the raw transient
FK `helper_columns` value. Lookup Enrichment owns interpretation of the raw
`enrich_lookup` record and its declared helper identity. Cell Codec owns only
the decision that identified helper/derived columns may not participate.

Why material / why Cycle 1:: Cell Codec must understand and synchronize with
two foreign metadata representations to enforce its own invariant; one of
those understandings is already wrong. This satisfies all of the Cycle-1
signals: direct foreign metadata interpretation, a private shadow parser,
misplaced ownership decision, and synchronized representation-change risk.

Smallest required closure slice:: Keep shared-container navigation and the
Cell Codec exclusion policy in Cell Codec. Replace only the two foreign
subkey interpretations with the already-existing owner facades:

* pass the already-extracted raw FK per-sheet `helper_columns` value to
  `fk_helpers.validated_helper_columns`;
* pass the already-extracted raw Lookup `enrich_lookup` record to
  `enrich_lookup.validated_enrich_lookup_helper_columns`;
* retain the explicit durable Workbook-View helper list as its separate
  handoff; and
* add public-path tests using current writer-shaped rich FK provenance and
  current Lookup provenance, with an explicit malformed-state disposition.

No new registry, global taxonomy, generic helper-identity protocol, metadata
shape, public surface, or package move is needed. Exact failure compatibility
and whether the two existing facade return types should be normalized only at
the Cell Codec call site belong to the bounded implementation-readiness step.

Blocking consequence:: Family Cycle 1 cannot yet be recommended for closure.

=== FINDING-002 -- MINOR -- one Lookup provenance docstring retains obsolete Slice-1 ownership wording

`InterpretedEnrichLookupProvenance` says mismatch evaluation stays DCP-owned

This does not hide an executable semantic algorithm, affect the owner handoff,
