== 3. Finding-by-finding disposition

=== 3.1 I1 -- partial mode, `--force`, halt behavior -- *CLOSED*

Both documents now state that `--refs refs/heads/main` implies filter-repo
partial mode. Both require C to record the tool's actual reported or effective
option state, or equivalent evidence sufficient to show partial mode is active,
and both state that the contracted argv remains authoritative. `--force` remains
in the forbidden list in both documents. Both add the halt rule: if pinned
git-filter-repo `2.47.0` refuses the contracted invocation on its fresh-clone
safety check, C stops and B re-opens; C must not add `--force` or any other
option on its own judgment. FTR section 13.5 and readiness section 6.2 agree
sentence for sentence, and the readiness section-13 summary now reads "partial
mode evidenced as active". No local filter-repo execution was required or
performed.

=== 3.2 I2 -- unreachable Core object leak -- *CLOSED*

The FTR block is now titled *Target-population and phase boundary* and names the
three boundaries explicitly: Core source, disposable scratch extraction,
standalone target. It states that partial mode may leave original Core objects
physically present but unreachable in the scratch object database, and that
scratch reachability checks therefore do not prove physical absence -- which is
precisely the blind spot I2 identified. Forbidden: copying scratch `.git`,
copying the scratch object store, `git clone --mirror`, mirror push, and any
other mechanism transferring unreachable scratch objects. Permitted: a normal
clone of the filtered reachable `main` history, or an explicit push of accepted
reachable `main` ref semantics only. The resulting standalone repository must
have its own independently checked reachable object closure, and Core-owned
history must not be reachable there. Readiness section 8.5 carries the same text
and retains "Unreachable scratch objects/pack artifacts are not provenance",
which is now a consequence of a stated mechanism rather than an unsupported
assertion.

No target mutation is authorized in B. The same block retains verbatim "B shall
not initialize or write `/home/stefan/repos/spreadsheet-handling/workflow-coordinator/`,
alter either repository's remotes, or contact/push
`git@github.com:StefanSchade/workflow-coordinator.git`", assigns "any later
target population after independent acceptance" to C, and readiness section 9 is
unchanged, still enumerating target population and push among the operations
this contract authorizes for nobody. The population rules are stated
impersonally but are bounded on both sides; they constrain C, they do not
license B.

=== 3.3 I3 -- tree-union inclusion proof -- *CLOSED*

The decisive accidental-inclusion test is now the full union of every path
present in every tree reachable from rewritten `main`, in both documents, in the
exact operational form requested:

[source,shell]
----
git rev-list refs/heads/main |
while read c; do
    git ls-tree -r --name-only "$c"
done |
LC_ALL=C sort -u
----

and the result must be a subset of the exact 50-path allow-list. Verified
absent: no changed-path union survives anywhere (`grep -nE 'changed path'` in
both documents returns nothing), `git log --name-only` is no longer cited as
proof, and `git rev-list --objects` was not substituted -- its only remaining
occurrence is `rev-list --all --objects` in the sole-ref/object-closure
recording list, which is its original and correct use. High-risk negative
searches are now explicitly "legibility checks in addition to, never
replacements for" the universal tree-union proof. The readiness section-13
summary was updated to match, so FTR and readiness no longer diverge: the
normative inconsistency I3 flagged is gone in both directions.

=== 3.5 I5 -- backward references and self-reference -- *CLOSED*

`result.bootstrap_head` is now "a strictly backward reference to the earlier
commit that introduced the initial standalone bootstrap/provenance state
containing this field as `null`; a strictly later provenance-update commit may
write that already-existing OID." `target.accepted_head` is "a strictly backward
reference to the already-existing standalone commit independently accepted by the
maintainer", recorded by a strictly later provenance-update commit. Both rows
state that the value never denotes the commit currently writing itself and that
it is outside source identity, rerun equality, extraction/result digests, and
mechanical extraction acceptance; both state that `null` is truthful until the
referenced earlier commit exists. The FTR carries identical semantics.

Circularity search: `bootstrap_head` and `accepted_head` occur exactly four
times across both documents -- the two schema rows and the one FTR paragraph.
No acceptance gate, digest definition, rerun comparison, or validation list
references either field. The earlier `target.accepted_head` phrasing "accepted
standalone HEAD" -- the actual source of the self-invalidation, since any commit
writing it moves HEAD -- is gone; the field now denotes an accepted commit, not
a current HEAD. The closed v1 schema permits `null`, and readiness section 8.5's
"the instantiated manifest must validate against section 7" therefore does not
re-impose a fixed point. No recursive commit requirement remains.
