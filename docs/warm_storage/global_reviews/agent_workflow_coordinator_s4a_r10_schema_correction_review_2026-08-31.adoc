== 1. Root-cause closure

The original S4A-R10 defect: the transport schema declared the inner `result` as
opaque `{"type":"object"}`, which strict Structured Outputs rejects
(`context=('properties','result')`, HTTP 400 `invalid_json_schema`).

* `slice4.py` no longer hand-builds the transport schema: the inline `schema_data`
  dict is removed and replaced by `atomic_write_json(schema,
  structured_result_envelope_schema())` (`slice4.py:151`, import at
  `slice4.py:25`).
* The opaque `result:{"type":"object"}` node no longer exists anywhere in the
  emitted schema.
* Test `test_invoke_codex_writes_the_canonical_structured_result_schema` drives the
  real `invoke_codex()` path with a fake executable and asserts the on-disk
  `structured-result.schema.json` equals `structured_result_envelope_schema()`, so
  the live path provably emits the canonical schema.

Root cause is closed: the real Slice-4A invocation path now emits the complete
strict schema. *CLOSED.*

== 2. Complete strict schema

Outer envelope (`structured_result_envelope_schema`): `type=object`,
`additionalProperties=false`, `required` = all five envelope keys
(`STRUCTURED_RESULT_ENVELOPE_KEYS`), `schema_version` `const 1`,
`run_id`/`hop_id`/`invocation_id` remain `{"type":"string"}`, `result` =
`routing_result_json_schema()`. Correlation fields remain strings. *OK.*

Inner `RoutingResult` (`routing_result_json_schema`): strict object,
`required` = `ROUTING_RESULT_REQUIRED_KEYS` (all ten), with exactly the ten
accepted keys (`schema_version`, `outcome`, `requested_route`, `scope_changed`,
`requires_human`, `escalation`, `findings`, `claimed_commits`, `evidence_refs`,
`summary`). No omitted keys, no invented keys, all declared keys required.
`outcome` enum is derived from the actual model vocabulary
(`[outcome.value for outcome in Outcome]`). *OK.*

== 3. Every nested object is strict

Empirically enumerated the built schema with the corrected walker: exactly four
object nodes -- envelope, `result`, escalation object, and `FindingDelta` item --
each with `additionalProperties is False`, an explicit `properties`, an explicit
`required`, and `set(required) == set(properties)`. Objects are reached via
`properties` (envelope->result), `anyOf` (`escalation`), and array `items`
(`findings`). No opaque object remains. *OK.*

Regression detectability (the decisive check): the walker in `6bfad5bb`
identified objects by `"properties" in schema`. An opaque `{"type":"object"}`
node has no `properties`, so that walker would silently *skip* it -- the
strictness assertion would never run on a reintroduced defect and the test would
falsely pass. `41ff4e35` corrects the walker to detect objects by
`schema.get("type") == "object"`, so a reintroduced opaque node is now yielded and
fails the assertion. Verified empirically: mutating `result` back to
`{"type":"object"}` makes the strictness walk raise (`KeyError` on the absent
`additionalProperties`). The exact original S4A-R10 defect is now deterministically
caught without a provider call. *OK.*

== 4. Nullable / required semantics

* `escalation`: `{"anyOf":[{"type":"null"}, <strict {kind,question}>]}` -- null or
  strict object, matching the validator's `if data["escalation"] is not None`.
* `finding_id`: `{"type":["string","null"]}`.
* `successor_ref`: `{"type":["string","null"]}`.
* `new_material_evidence`: `{"type":"boolean"}` -- required, non-nullable.

The two formerly optional `FindingDelta` provider fields (`successor_ref`,
`new_material_evidence`) are placed in the provider `required` list (all seven keys
via `FINDING_DELTA_KEYS`). This is the benign tightening the original review
explicitly allowed: it does not alter Python-side acceptance, because
`_finding_delta` still passes `required=FINDING_DELTA_REQUIRED_KEYS` (five keys)
and `optional=FINDING_DELTA_OPTIONAL_KEYS` (the two). Python continues to accept
its broader historical input (those two absent); the provider merely requires
explicit presence. No demand for symmetry is imposed. *PRESERVED.*

== 5. Enum / contract alignment and drift closure

* `outcome` enum == `[o.value for o in Outcome]` (verified equal).
* `proposed_state` enum == `[s.value for s in FindingState]` (verified equal).
* escalation `kind` enum == `ESCALATION_KINDS`, the same constant the validator now
  checks (`if kind not in ESCALATION_KINDS`).

The shared constants `ROUTING_RESULT_REQUIRED_KEYS`, `FINDING_DELTA_REQUIRED_KEYS`,
`FINDING_DELTA_OPTIONAL_KEYS`, `FINDING_DELTA_KEYS`, `ESCALATION_REQUIRED_KEYS`, and
`ESCALATION_KINDS` are each defined once and consumed by *both* the validator
(`routing_result_from_data`, `_finding_delta`) and the schema builders. Their
contents are byte-identical to the previous inline literals, so the validator's
behaviour is unchanged while the provider schema is now generated from the same
source of truth. This materially closes the hand-written-spec drift the original
review flagged, without introducing a general schema framework or code generator.
*ALIGNED.*
