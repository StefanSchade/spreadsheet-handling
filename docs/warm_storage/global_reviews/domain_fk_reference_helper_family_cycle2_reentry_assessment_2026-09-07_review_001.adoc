=== 3.1 F-1 -- rationale robustness -- RESOLVED

*Original finding.* The census leaned on the "caller-precondition surface"
(direct / `run_pipeline` callers) as the load-bearing reason to keep each guard.
Taken as a general principle this proves too much -- every domain transformation
is importable and reachable via `run_pipeline`/direct calls, so it would imply
no guard is ever Cycle-2-removable and Cycle 2 is structurally impossible. The
correct primary reason is that each check protects a condition Trusted Ingress
does not establish on any path.

*Verification against `312f712c...`.* The rationale is now correctly
re-anchored:

* "Trusted-Ingress facts actually relied on" demotes `run_pipeline`/direct calls
  to "secondary execution context only: their caller preconditions include
  supplying an Ingress-Conformant payload, so they do not make a hostile-object
  guard necessary," and states the *primary* retention test explicitly: "does
  Trusted Ingress actually establish the condition a guard protects?"
* The census preamble now states: "'Keep' means a business/transformation
  invariant, a family-owned metadata schema, carrier capability, or
  configuration/argument contract whose protected condition Trusted Ingress does
  not establish. It does not mean 'keep because a direct caller may violate
  ingress.'"
* The "Next implementation slice" section reframes the slice-selection test
  around whether the protected condition "is established by Trusted Ingress on
  every supported invocation contract," and adds that caller-precondition
  surfaces "provide execution context, but do not excuse nonconformant payloads
  and are not the primary retention rationale."

This is exactly the requested re-anchoring: the establish-the-condition test is
now primary; caller-precondition/direct-call context is explicitly secondary.
*F-1 RESOLVED.*
