== Direct regressions introduced by `dd3d73d1`

=== S4A-R8 -- BLOCKING -- dispatch marker published too early (pre-spawn failures leave a phantom-Hop anchor)

*Violated authority.* WFC-AUTO-03 ("Local failure before adapter/provider acceptance, ... prompt assembly ... do not consume Hops"); WFC-AUTO-02 ("once the atomic dispatch marker exists, acceptance that cannot be disproved is conservatively charged"); WFC-FAIL-04 (marker published *before invocation*).

*Mechanism.* `run_real_one_hop` writes `dispatch.json` at slice4.py:228, then calls `run_one_hop`, which performs its *own* pre-spawn work before the real `Popen`: `phase = profile.phases[run.phase]`, a repeated `preflight_hop` (`vertical.py`, raising `VerticalRunError` on `GitPreflightError`), and `assemble_prompt` (`prompt.py:97`, raising `ValueError("selected prompt component is unavailable: ...")`). `run_real_one_hop` catches only `Slice4Error` (unlink + reraise) and `ResultValidationError` (recover). A `ValueError` from prompt assembly, a `VerticalRunError` from the inner preflight, or a `KeyError` from a missing phase is none of those, so it escapes uncaught with `dispatch.json` still on disk -- for a process that never started. On restart, `recover_uncertain_dispatch` treats the correlated marker as an uncertain invocation and charges one phantom Hop plus `reconcile_required`. A misconfigured profile (a phase selecting an unprovided component) triggers this every run; it is not a contrived race.

*Failure scenario.* A phase selects a component absent from `components` -> `assemble_prompt` raises `ValueError` after the marker is written -> `run_real_one_hop` does not catch it -> `dispatch.json` remains -> next restart charges H001 as an uncertain Hop although no Codex process ever spawned.

*Smallest correction.* Classify by *factual execution state*, not exception class: replace the two narrow `except` clauses with one that inspects `adapter.outcome`. If `adapter.outcome is None` (no `CodexOutcome` was ever produced, i.e. nothing spawned), `dispatch_path.unlink(missing_ok=True)` and re-raise (no Hop); only when `adapter.outcome is not None` with an invalid result run the uncertain recovery. `invoke_codex` returns a `CodexOutcome` whenever `Popen` succeeded (it never re-raises post-spawn), so `adapter.outcome is None` reliably marks pre-spawn/local failure. Add a deterministic test forcing a post-marker pre-spawn failure (e.g. a phase selecting a missing component) and assert no residual `dispatch.json` and `hop_used == 0`.

*Live invocation needed to close:* No.

=== S4A-R9 -- BLOCKING -- successful Hop never retires the in-progress dispatch marker

*Violated authority.* WFC-PERSIST-01 (the dispatch/in-progress marker is a *trusted resume anchor*); WFC-AUTO-02 marker semantics; WFC-PERSIST-06 (atomic publication and correlation of resume-advancing state).

*Mechanism.* The success branch (slice4.py:257-259) atomically writes the completed `run.json` and `checkpoint.json` but does not remove `dispatch.json`; the only `unlink` is in the `Slice4Error` branch (:239). A fully reduced, completed Run therefore retains an in-progress dispatch anchor. The committed consumer `recover_uncertain_dispatch` (`persistence.py`), given a present correlated marker whose Hop already exists in the completed snapshot, does not double-charge (it matches `existing.sequence`) but still returns `require_reconcile(..., reason="interruption")`, forcing `reconcile_required`. So any restart/resume path built on the accepted anchor semantics would spuriously reconcile a completed Run. The persisted state is itself untruthful: completed work carrying an "in-progress" anchor.

*Failure scenario.* `run_real_one_hop` completes successfully (Run `completed`, H001 reduced), `dispatch.json` remains; a later restart observes the correlated in-progress marker and forces the completed Run into `reconcile_required` instead of recognizing accepted completion.

*Smallest correction (crash-safe).* On the success path, after atomically writing the completed `run.json` and `checkpoint.json`, retire the marker: `dispatch_path.unlink(missing_ok=True)`. Ordering is crash-safe: the durable completed snapshot is the authority before removal; a crash in the residual gap leaves a marker whose Hop already exists in the completed snapshot (no double-charge; the only residual is the pre-existing `recover_uncertain_dispatch` "reconcile a completed Hop" behavior, which is out of this bounded scope and fails safe toward a human). Add a deterministic test asserting `dispatch.json` does not exist after a successful `run_real_one_hop`. No event log or additional persistence machinery is required.

The prescribed S4A-R8 fix generalizes the existing factual discriminator to all failures, keeping classification truthful without a generic exception taxonomy.

== RealHopRun truthfulness (section 7)

The small dataclass + `reduction` property wraps the existing `VerticalRun`/`Run` and does not create a second coordinator contract. *Sound.*
