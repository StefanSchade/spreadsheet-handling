== Verdict and bounded answer

*Verdict B -- BOUNDED DESIGN ACCEPTED AFTER CORRECTION.*

The prior Fable audit's Class-A finding survives independent inspection and
reproduction. There
is no accepted relation-key identity owner today. Maintained authorities do,
however, constrain a minimum rule strongly enough to commission bounded
implementation slices without creating a general Scalar equality or
normalization system. Review 001 findings F1-F6 are corrected below; a fresh
bounded delta re-review remains the gate before Slice 1 may be authorized.
No unresolved architecture question remains inside the bounded relation-key
design: F1 is closed by the exact Number and explicit DateTime bases. The
generic tuple-uniqueness question is recorded as an out-of-scope follow-up,
not as a blocker to relation-key work.

[cols="2,5",options="header"]
|===
| Question | Decision

| Which values may be relation keys?
| An already-admitted Domain scalar is eligible exactly when it is not in the
Missing category. Composite keys are eligible exactly when every component
is eligible.

| When are two eligible relation keys equal?
| Relation-key identity defines *new, bounded semantics for relation keys*;
the scalar classifier did not already define within-category equality. Two
keys are equal exactly when they have the same arity and each corresponding
component has the same category-tagged, owner-defined identity. The relation
is reflexive, symmetric, transitive, and consistent with the hashable identity
used by maps, sets, counters, and merge-style consumers. Category boundaries
mean String `"1"` is not Number `1`, and Boolean `true` is not Number `1`
despite Python equality.

| Is whitespace trimming part of identity?
| *No.* String comparison is exact. `" 1 "` and `"1"` are different keys;
whitespace-only non-empty Strings are eligible keys. No `.strip()` operation
may participate in relation-key identity.

| Is any Missing carrier a relation key?
| *No.* `None`, `""`, NaN, `pandas.NA`, `NaT`, and every other carrier
recognized as Missing by the accepted scalar contract are ineligible. An
allowed absent source reference may be skipped by caller policy, but it never
matches a Missing target.

| How do relevant carrier/type differences compare?
| Number is one key category and compares by the exact mathematical numeric
value represented by each admitted carrier, without NumPy weak-scalar
promotion. Thus `1`, `1.0`, and `numpy.int64(1)` agree, while
`numpy.float32(0.1)` and Python `0.1` do not when their exact values differ.
`Decimal` is not admitted. Date and DateTime remain distinct categories.
DateTime identity is relation-key-specific: naive values compare by their
exact wall-clock coordinate, aware values by their exact UTC instant, and an
aware value never equals a naive one. No precision is discarded and no
general timezone or DateTime normalization API is introduced.

| Which layer owns the rule?
| *Domain.* The preferred owner is one narrowly named shared Domain primitive,
`domain/relation_keys.py`, consuming the accepted Core scalar classifier but
not extending it. FK Helpers, Lookup Enrichment, and validation consume that
owner. Neither pandas, display formatting, Core scalar admission, nor the FK
family alone owns the rule.

| What happens for incompatible categories?
| They are unequal, not coerced and not stringified. The owner exposes
eligibility/equality; each caller retains its existing resolution policy
(empty result, configured failure, or finding). Raw pandas dtype errors must
not leak as the semantic outcome.
|===

This is a relation-key rule only. It does not assert that general Domain
scalar equality is identical to relation-key equality.

== Scope and conceptual separations

This assessment covers in-memory relation resolution in value mode for
`add_fk_helpers` and `add_lookup_helpers`, and key eligibility/equality in
`validate_fk_helpers`, declarative `primary_key`/`foreign_key` validation, and
`validate_graph` endpoint checks. It also covers the relation-key duplicate
checks those paths depend on. Graph `unique_edges`, including configurable
qualifier columns, and reference `unique_reference` remain generic tuple-
uniqueness checks under their current semantics; neither migrates to
relation-key Missing-ineligibility in this work. Formula helper modes author
backend-neutral formula Intent rather than performing Domain resolution; they
are not evidence that a spreadsheet engine implements this in-memory rule and
are not changed here.

The following remain separate:

* *scalar admission* is owned by the accepted Domain scalar language and
  Trusted Ingress;
* *relation-key eligibility* is the new bounded question of whether an
  admitted scalar can participate as a key;
* *relation-key equality* is the new bounded comparison above;
* *generic tuple uniqueness* remains a separate, undecided contract for graph
  `unique_edges` and reference `unique_reference`;
* *representation/carrier* remains the current Python, NumPy, pandas,
  spreadsheet, or metadata representation and is not normalized by this
  contract; and
* *display/stringification* remains diagnostic or presentation mechanics and
  never establishes identity.

No configuration, metadata, projection, persistence, reconstruction, or
cleanup lifecycle is introduced. The primitive consumes values already in
Domain state and returns no persistent state or provenance.

=== Maintained consumer inventory

The maintained consumer surface includes more than the direct primitives:

* the registered `validate` pipeline step calls `check_duplicate_ids` and
  `check_unresolvable_fks`;
* maintained demo pipelines use `validate`, including the failure demo with
  both `mode_duplicate_ids: fail` and `mode_missing_fk: fail`;
* maintained demos also exercise `add_fk_helpers`; and
* the policy-independent `check_duplicate_ids` fallback selects
  `defaults['id_field']` (or `"id"`) even without an FK relation policy.

When Slice 2 migrates FK relation-key behavior, that fallback duplicate-check
path adopts the same shared relation-key eligibility, equality, and hashing
rule. Slice 2 therefore includes one bounded maintained-consumer probe through
the registered `validate` step and representative maintained demo
configurations. This is a compatibility probe, not a demo-suite redesign.

== Authority search

=== Maintained authority found

The accepted Semantic Model's “Domain scalar language” and the Technical
Model's “Internal Scalar Value Model” establish these constraints:

* the admitted categories are String, Boolean, Number, Missing, Date, and
  DateTime;
* numeric-looking Strings remain String; content is not parsed to infer a
  different category;
* carrier representation and category are distinct, and accepted carrier
  variants are classified without narrowing;
* Number is one category while Integer-versus-Float remains deliberately not
  a general scalar-type split;
* Missing is recognition over carriers, including `""`, not a value or a
  canonical representation; and
* general scalar normalization does not exist and is not owned by Trusted
  Ingress or the scalar classifier.

Those authorities classify carriers but do *not* define same-category value
equality or hashing. The equality bases in this assessment are new semantics
owned only by the bounded relation-key contract; they are not promoted into a
universal Scalar equality API.

The Functional Model defines FK helper resolution, reference/uniqueness
validation, and graph endpoint validation, but does not define key equality,
whitespace normalization, or cross-category coercion. The Technical Model
describes `core/fk.py` as low-level FK wire-format/helper mechanics and Domain
as the layer containing business rules, transformation semantics, and
validation invariants.

The implemented `FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A` calls
`core/fk.py:_norm_id` an FK-specific identity contract. In context this is a
classification of then-current local code during a missingness inventory: it
restates `str`/`None` mechanics and says they must not be collapsed into the
general Missing predicate. It neither defines a cross-owner relation-key rule
nor addresses Lookup/reference/graph disagreement. It is evidence that key
identity is distinct from scalar admission, not an accepted definition of the
shared equality now under review.

Declarative `primary_key` validation already owns a non-Missing requirement
when that rule is explicitly configured. It does not make every FK target
column an implicit primary-key rule. Source `foreign_key` validation may
allow an absent reference, while excluding Missing target rows. These are
role-specific validity/reporting decisions consistent with, but not ownership
of, shared key eligibility.

Relevant tests protect ordinary same-type examples, missing-source skipping,
primary-key presence, duplicate lookup rejection, and ordinary unresolved
references. No accepted test specifies the representative cross-category,
whitespace, or producer/validator-conformance matrix.

== Semantic decisions

=== Missing-as-key

No Missing carrier is a relation key. This applies symmetrically to source and
target identity, while caller policy remains role-specific:

* a source Missing may mean “no relationship supplied” and be allowed or
  skipped (`foreign_key allow_empty`, FK validation);
* a target Missing is never entered into a relation lookup or endpoint set;
* an explicitly configured `primary_key` continues to report Missing as a
  presence violation;
* a generic duplicate-key check ignores ineligible Missing entries rather
  than declaring Missing carriers equal keys; and
* neither `"" == ""` nor `None == None` may resolve a relation.

This does not introduce an unconditional rule that every frame row must have a
key. It decides participation, not whether a particular optional row is
invalid. Current blank/None matches in FK/Lookup producers are accidental
implementation behavior; current source-side skipping and explicit
primary-key findings are deliberate role policy.

This answers the accepted Cycle-3 missing-target-ID maintainer question --
whether Missing target IDs are invalid values, rows excluded from identity,
or values participating in duplicate identity -- with “excluded from
identity.” It introduces no new FK-side “invalid target ID” finding. Missing
target values are excluded from maps, sets, matching, and duplicate identity;
an explicit `primary_key` presence rule remains separate caller policy.

=== Whitespace

Whitespace is payload for an admitted non-empty String key. Exact String
comparison is required; trimming is forbidden in key identity.

This matters for ordinary spreadsheet input. XLSX and ODS parsing stringify
payload cells without stripping them. Their `.strip()` uses in the inspected
paths determine table extents and header presence, not payload normalization.
Consequently `" 1 "` is reachable payload and is not safely rewritten to
`"1"`. Whitespace-only non-empty String payload is likewise not Missing under
the scalar grammar, although a parser's table-boundary mechanics can affect
whether an otherwise empty row is discovered. That separate table-extent
question is unchanged.

=== Category and carrier differences

Relation-key equality is a new bounded Domain relation, not a reuse of an
existing universal Scalar equality. For every eligible key it must be
reflexive, symmetric, and transitive, and it must agree with the owner-defined
hashable identity consumed by dicts, sets, counters, and merge-style
mechanics. It never depends on NumPy weak-scalar promotion and never falls
back to Python/native equality where that equality disagrees with hashing.
It also never falls back to `str`, `repr`, parsing, or pandas dtype coercion.

The minimal owner shape may therefore be an opaque, category-tagged hashable
relation-key identity. “Opaque” describes the mechanical value presented to
maps or merge columns; it must not hide the visible Domain contract or become
a universal Scalar equality API.

Category is part of the identity, so Python accidents cannot collapse
Boolean/Number or Number/String:

* String identity is its exact string value, including every whitespace
  character;
* Boolean identity is the Boolean value, tagged as Boolean;
* Number identity follows the exact-value rule below;
* Date identity is the exact `datetime.date` calendar value, tagged as Date;
* DateTime identity follows the explicit key-specific rule below and remains
  tagged as DateTime; and
* Missing is rejected before any identity is produced.

==== Number exact-value basis

Number remains one category; carrier type alone does not distinguish Number
keys. Two eligible Number components are equal exactly when their admitted
carriers represent the same mathematical numeric value. For finite integers
and binary floating values, this means the same exact integer or rational
value, not a comparison after promotion to a common NumPy dtype. Equal signed
zeros share one value; signed infinities compare only with the same infinity;
NaN carriers are Missing and therefore ineligible. The hashable Number
identity must be derived from that same exact value.

Consequences required by the bounded rule:

* `1 == 1.0`;
* `numpy.int64(1) == 1`;
* `numpy.float32(0.1) != 0.1` because their exact represented rational values
  differ, even though NumPy weak-scalar promotion currently reports equality;
  and
* `numpy.int64(2**53 + 1) != numpy.float64(2**53)`: the integer above exact
  float64 integer precision must not collapse onto the rounded float merely
  because NumPy promotion reports equality.

This exact value is private relation-key identity material only. It does not
design a general numeric canonicalization framework or alter admitted
carriers.

==== DateTime relation-key basis

Accepted DateTime authority classifies `datetime.datetime`,
`pandas.Timestamp`, and every non-`NaT` `numpy.datetime64` as DateTime without
narrowing. It deliberately establishes no cross-carrier equality,
canonicalization, timezone, or precision policy. Native equality cannot fill
that gap: an equal-looking `numpy.datetime64[ns]`/`pandas.Timestamp`/
`datetime.datetime` triple can compare true for the first two pairs and false
for the outer pair.

For relation keys only, DateTime identity uses this smallest explicit basis:

* a naive DateTime is identified by its exact proleptic-Gregorian wall-clock
  coordinate;
* an aware `datetime.datetime` or `pandas.Timestamp` is identified by its
  exact instant on the UTC timeline;
* aware values at different offsets are equal when they represent the same
  exact UTC instant; timezone name and authored offset are not separate key
  identity;
* aware and naive values are always unequal -- a naive value is never assumed
  to be UTC or any other timezone;
* the full value represented by the carrier participates, with no rounding or
  truncation. A NumPy unit or pandas/Python precision difference alone does
  not distinguish equal coordinates, but sub-microsecond or other retained
  precision must not be discarded; and
* Date remains a separate category, so a day-precision
  `numpy.datetime64` DateTime never equals a `datetime.date` key.

Thus the equal naive timestamp represented as `numpy.datetime64[ns]`,
`pandas.Timestamp`, and `datetime.datetime` receives one identity despite the
non-transitive native comparison chain. Aware Timestamp/datetime values use
the same instant basis; an aware value and a naive value do not. This rule
defines only the equality/hash coordinate needed by relation keys. It does
not convert stored values, prescribe a general DateTime normalized carrier,
or establish a general timezone policy.

Composite relation keys apply the same component identity in order. Their
hashable identity is the ordered tuple of component identities, so arity,
component order, equality, and hashing cannot disagree.

=== Minimum owner contract

The preferred owner is `spreadsheet_handling.domain.relation_keys` (exact
public exposure is not implied). Its minimum semantic contract is:

. accept only already-admitted scalar components;
. decide eligibility as non-Missing;
. produce equality and hashable identity from the same category-tagged basis,
  as an equivalence relation for every eligible key;
. preserve String whitespace and never parse/stringify for identity;
. compare Number by exact represented numeric value without NumPy promotion;
. compare DateTime by the explicit naive-wall-clock/aware-UTC-instant basis
  above, at full represented precision;
. provide componentwise composite-key behavior;
. distinguish “ineligible Missing” from “eligible but unequal”; and
. leave caller-specific finding, empty/fail policy, display formatting, and
  DataFrame mechanics to consumers.

The assessment deliberately does not choose a string token, normalized stored
carrier, concrete hash encoding, dataclass, or pandas dtype. Those are
implementation mechanics, not the Domain abstraction. An implementation may
expose an opaque/category-tagged hashable relation-key value if that is the
minimal shape, but must not expose pairwise equality that can disagree with
raw-carrier hashing or invite consumers to reconstruct identity themselves.

=== Local Human Readability requirement

After a future change, each scoped path must import or call a name containing
`relation_key`, and a nearby comment/docstring must state why local pandas or
string equality is insufficient. A maintainer must be able to see locally:

* Missing is ineligible;
* scalar category is part of identity;
* Strings are exact and not trimmed;
* equality and hashing use one owner-defined identity;
* Number uses exact represented numeric value without NumPy promotion;
* DateTime uses the explicit naive-wall-clock/aware-UTC-instant basis without
  precision loss;
* incompatible categories do not coerce;
* the caller retains only its resolution/finding policy; and
* pandas merge, maps, sets, and counters are mechanics after owner resolution.

Names such as `_norm`, `_plain`, `_token`, or `_coerce` alone do not satisfy
this requirement because they hide the Domain reason for the operation.

== Lookup and pandas boundary

`DataFrame.merge` is acceptable only after the Domain rule has determined the
join representation and eligibility. A future Lookup implementation must:

* reject/route Missing source components before matching and exclude Missing
  target rows;
* detect duplicate eligible target keys with the shared owner;
* compare category-tagged values rather than pandas dtypes;
* preserve the source and target payload/key carrier columns presented to the
  caller; and
* translate unequal keys through Lookup's existing
  `missing="empty"` or `missing="fail"` policy, never through a raw pandas
  dtype `ValueError`.

It may create temporary internal join values and use `merge`, or use an
owner-keyed mapping. This assessment does not create a generic DataFrame
normalization framework and does not make any temporary token part of the
public Domain contract.

== Adjacent and lifecycle dispositions

=== Generic tuple-uniqueness identity

Follow-up:: *generic tuple-uniqueness identity / consistency across graph
`unique_edges` and reference `unique_reference`.*

Graph `unique_edges` may include configurable qualifier columns,
and reference `unique_reference` performs structurally equivalent generic
tuple uniqueness. Today a blank qualifier still participates in duplicate
identity. Applying relation-key Missing-ineligibility to graph unique edges
would silently remove duplicate findings, while leaving `unique_reference`
unchanged.

This cycle therefore delegates only graph endpoint relation identity.
`unique_edges` and `unique_reference` both retain their current tuple-
uniqueness semantics. A bounded follow-up must decide generic tuple-
uniqueness identity and consistency across those two surfaces; this assessment
does not solve it. Until then, `foreign_key` identity and
`unique_reference` tuple identity may intentionally differ on the same
columns after relation-key migration. A retained-blank-qualifier acceptance
case makes that deliberate boundary visible.

=== B-2 whole-frame Missing rewrite

*FOLLOW-UP.* `enrich_lookup` values mode currently applies
`where(pd.notnull(enriched), "")` to the whole output, rewriting Missing
carriers in untouched source columns as well as helpers. Because every
