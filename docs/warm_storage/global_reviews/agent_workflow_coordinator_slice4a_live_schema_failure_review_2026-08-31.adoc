== 2. The actual schema path (transport schema vs internal validation)

The provider-facing schema is constructed inline in `invoke_codex()` at
`scripts/workflow_coordinator/slice4.py:150-156` and passed to Codex via
`--output-schema <path>` (`slice4.py:159-162`). It is written to
`structured-result.schema.json` under the checkout state root.

The exact schema written (verified byte-for-byte against the retained
`.../trusted-state/checkouts/6f387fb8-.../structured-result.schema.json`) is:

[source,json]
----
{"additionalProperties":false,
 "properties":{
   "hop_id":{"type":"string"},
   "invocation_id":{"type":"string"},
   "result":{"type":"object"},
   "run_id":{"type":"string"},
   "schema_version":{"const":1}},
 "required":["schema_version","run_id","hop_id","invocation_id","result"],
 "type":"object"}
----

The retained artifact and the current `slice4.py` source are identical in shape;
the failure is fully attributable to committed code, not to a one-off local edit.

Two distinct contracts must be separated:

*A. Provider-facing JSON Schema* consumed by Codex Structured Outputs
(`response_format 'codex_output_schema'`, param `text.format.schema`). This is
what `--output-schema` supplies. OpenAI strict Structured Outputs requires that
*every* object node declare `additionalProperties: false` and list *every*
declared property in `required`.

*B. Coordinator-side Python validation* performed *after* the JSON is received:
`adapter.validated_result()` (`adapter.py:52-68`) checks the envelope key set,
`schema_version==1`, and identity correlation, then delegates the inner object to
`serialization.routing_result_from_data()` (`serialization.py:371-429`), which
fully validates the `RoutingResult` shape.

The transport schema (A) is sufficient for the envelope but under-specifies the
inner `result`; the Python validator (B) fully specifies `result`. They are two
independent hand-written specifications of the same envelope, and they have
already drifted -- (A) says `result` is any object, (B) requires ten specific
fields.

== 3. The `result` object -- root cause

The provider rejects `context=('properties','result')` because the `result`
subschema is exactly `{"type":"object"}`: no `additionalProperties`, no
`properties`, no `required`. Under strict Structured Outputs this is invalid --
the outer envelope object satisfies the rule (it has `additionalProperties:false`
and every property in `required`), so `result` is the first offending node, which
is precisely the context the provider names.

Crucially, `result` is not merely a strict-flag omission; it does not describe the
`RoutingResult` shape at all. The provider therefore fails the request *before*
agent execution: `turn.failed` follows `turn.started` immediately, with no model
work performed. This is a hard, deterministic, 100%-reproducible block of the
entire real vertical happy path.

A one-line "add `additionalProperties:false` to `result`" patch is *insufficient
and actively harmful*: an object schema with `additionalProperties:false` and no
`properties`/`required` admits only the empty object `{}`. The real agent's valid
`RoutingResult` (ten populated fields) would then either be rejected by the
provider (extra properties) or, if it somehow passed, be an empty object that the
Python validator immediately rejects. The correction therefore requires a
*complete strict inner result schema* describing the actual `RoutingResult`
contract.

== 5. Required / optional / nullable semantics (mismatch call-outs)

Strict Structured Outputs requires every declared property to appear in
`required`; "optional" is expressed as a nullable union, not by omission from
`required`. The internal Python contract has three subtle cases that must be
represented without changing accepted semantics:

* `escalation` -- internal: object *or* `None` (`if data["escalation"] is not
  None`). Represent as `anyOf[null, strict-object]`. Null maps to internal
  `None`. Semantics preserved.
* `FindingDelta.finding_id` and `FindingDelta.successor_ref` -- internal
  `_optional_string` accepts a string *or* `null` (→ `None`). Represent as
  `{"type":["string","null"]}`. Semantics preserved.
* `FindingDelta.new_material_evidence` -- internal
  `data.get("new_material_evidence", False)` then `_boolean(...)`. It accepts
  *absence* (default `False`) or a boolean, but *not* `null` (`_boolean(None)`
  raises). In strict mode a field cannot be absent, so it must be `required` and a
  plain non-nullable `boolean`. *Do not make it nullable* -- a nullable union
  would let the provider emit `null`, which the Python validator would then
  reject, reintroducing an uncertain result. This is a *benign tightening*: the
  model must state the flag explicitly instead of relying on the Python-side
  default. Call it out, but it is safe and semantics-consistent (any explicit
  boolean the model emits is accepted unchanged).

One residual mismatch that must *not* be "fixed" in the provider schema:
`requested_route`, `summary`, `invariant`, and every string element are validated
Python-side by `_string` as *non-empty / non-whitespace*. Strict Structured
Outputs disallows `minLength`, so emptiness cannot be expressed in the
provider-facing schema. Leave the provider schema as `{"type":"string"}` and let
the Python validator remain the authority for non-emptiness. The provider schema
is intentionally a *superset guard*, not a replacement for `routing_result_from_data`.

== 6. Single source of truth

The provider-facing schema (A, `slice4.py`) and the Python validator (B,
`serialization.py`) are currently duplicated specifications that have already
drifted; the retained failure is the proof of drift. For V1 the smallest safe
correction is *option A of the prompt*: explicitly construct one strict
provider schema that matches the existing `RoutingResult` contract. Do *not*
build a generalized schema-generation framework or a code generator.

To keep the two specs from silently re-diverging, co-locate the strict schema
builder next to the validator in `serialization.py` (e.g.
`routing_result_json_schema()` and `structured_result_envelope_schema()`),
deriving the required-key lists from the same source the validator uses, and have
`slice4.py` import and call it instead of the inline dict. A drift-guard test
(section 10) then pins the schema's `result.required` to the validator's required
set. This is a bounded consolidation, not new abstraction.

== 7. Correlation envelope integrity

The outer envelope must remain strict and correlated: `schema_version` (`const 1`),
`run_id`, `hop_id`, `invocation_id`, `result`; `additionalProperties:false`;
all five `required`. The correction replaces *only* the inner
`result:{"type":"object"}` node with the full strict `RoutingResult` schema and
must not touch the envelope keys, their required-ness, or `additionalProperties`.

Run/invocation/hop correlation is enforced Python-side by
`adapter.validated_result()` (exact five-key envelope set, `schema_version==1`,
identity tuple `(run_id,hop_id,invocation_id)` equality against the dispatch
`Invocation`). That correlation is independent of the transport-schema fix and is
unaffected by it. Correlation envelope remains sound.

== 10. Bounded correction plan (one implementation hop; specify, do not implement)

Goal:: Make the provider-facing structured-output schema a complete, strict
representation of the `RoutingResult` envelope, from a single canonical builder,
with deterministic tests that would have caught this exact defect. No provider
invocation.

Production files likely affected::

* `scripts/workflow_coordinator/serialization.py` -- add two builders returning
  plain `dict` JSON Schema: `routing_result_json_schema()` (the section-4 `result`
  schema) and `structured_result_envelope_schema()` (the strict five-key envelope
  wrapping it). Derive required-key lists from the same constants the validator
  uses so the two cannot drift silently.
* `scripts/workflow_coordinator/slice4.py` -- replace the inline `schema_data`
  dict at lines 150-156 with a call to `structured_result_envelope_schema()`.
  Nothing else in `invoke_codex()` changes; `--output-schema`/`--output-last-message`
  wiring and the envelope key set stay identical.

Exact schema semantics required::

* Every object node: `additionalProperties:false` + all properties in `required`.
* `schema_version`: `const 1` (envelope and result).
* Enums: `outcome`, `proposed_state`, `escalation.kind` per section 4.
* Nullables: `escalation` as `anyOf[null,object]`; `finding_id`, `successor_ref`
  as `["string","null"]`; `new_material_evidence` as required non-nullable
  `boolean` (section 5).
* Strings stay `{"type":"string"}`; non-emptiness remains Python-side only
  (no `minLength`).

Deterministic tests required (all fake/offline; the first is the one that would
have caught this defect)::

. *Strictness traversal* (in `test_slice4.py` or `test_serialization.py`):
  recursively walk `structured_result_envelope_schema()`; for every node that is
  an object schema (has `properties`), assert `additionalProperties is False` and
  `set(required) == set(properties)`. Recurse through `properties.*`, array
  `items`, and every `anyOf` branch. Against today's schema this test fails at the
  `result` node (no `additionalProperties`, empty/absent `properties`/`required`),
  i.e. it reproduces the provider's complaint deterministically without a network
  call.
. *Emitted-file identity*: drive `invoke_codex()` with a fake executable (existing
  pattern) and assert the on-disk `structured-result.schema.json` equals
  `structured_result_envelope_schema()` and that its `properties.result` carries
  `additionalProperties:false` and exactly the ten `RoutingResult` keys in
  `required`. This pins `slice4.py` to the canonical builder.
. *Drift guard*: assert the schema's `result.required` set equals the required-key
  set used by `routing_result_from_data`, and that each `findings` item requires
  the union of `_finding_delta` required+optional keys.
. *Positive round-trip*: take the known-good envelope already used by
  `test_real_vertical_composition_uses_fake_cli_and_existing_reducer`
  (`test_slice4.py:112`) and assert (a) it passes `validated_result(...)` and
  (b) it structurally satisfies the built schema via a small explicit local
  checker.

Structural validation without a dependency:: `jsonschema` is *not* installed in
`.venv` (confirmed). The correction must therefore validate schema shape with
explicit assertions / a small recursive checker in tests, not by importing
`jsonschema`. Do not add a new runtime dependency for this fix.

Retained strict correlation behaviour:: unchanged -- envelope keys, required-ness,
`additionalProperties:false`, and `adapter.validated_result` identity correlation
are preserved.

Fake-executable coverage:: all new tests use the existing fake-CLI / fake-executable
harness; no live Codex/provider call is added or required to test schema shape.

Out of scope for the correction:: a second live proof (still a separate maintainer
gate), the models-cache warning, S4H WATCH residuals, Slice 4B/5, and any
authorization-consumption machinery.
