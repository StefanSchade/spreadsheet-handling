== 4. Two-entry-point deviation review [[sec4]]

This is the task's central question. Independently traced, not accepted from
the implementation record's own framing.

*Is the constraint real?* Yes, concretely and unavoidably. `enforce_derived_column_policy_frame`
calls `_resolve_derived_identity` unconditionally, for every policy including
`drop` (confirmed at `derived_column_policy.py:243`). If `_resolve_derived_identity`
called a single merged interpreter that also resolved key-form (as the
readiness design's Section 4 literally specifies:
`interpret_written_enrich_lookup_provenance` "performs exactly what
`_validated_enrich_spec` + `_validated_mismatch_keys` + ... do today"), every
`drop` call with a present-but-key-form-malformed `enrich_lookup` record
would newly raise. This is not hypothetical: `test_malformed_key_form_drop_is_value_blind`
(unmodified, still green) directly asserts the opposite for exactly this
malformed-key-form-under-`drop` case, including the doubly-null asymmetric
pair.

*Was this actually authorized as a single function by the governing chain?*
Partially ambiguous, and this ultrareview flags the ambiguity explicitly.
The readiness design's Section 4 names exactly one new Lookup function. The
independent review's own Slice-1 gate text (`c7f205c`, Section 18) instructs:
"update `_resolve_derived_identity` to call *the two new facade functions*"
-- grammatically consistent with either "one per owning family" (FK's
`validated_helper_columns` + Lookup's single merged function, i.e. exactly
what a literal reading of Section 4 implies) or "whatever two-or-more
functions ultimately prove necessary." Read literally as "one per family,"
following that instruction would have silently broken the pinned `drop`
test -- an outcome flatly inconsistent with the same review's own Section 8
"byte-identical error paths" contingent verdict and the readiness design's
own repeated "zero intended behavior change" contract. This is a real,
if narrow, internal tension in the governing chain that neither `2a8ff36`
nor `c7f205c` explicitly resolved (neither artifact traces `_resolve_derived_identity`'s
unconditional-call nature against the *literal* one-function Lookup sketch
the way F-CORR-1 traced the analogous FK-side signature question). The
implementer did not silently pick either horn: it re-derived the constraint
from the pinned test and the actual call graph, and escalated the deviation
explicitly (implementation record <<sec4>>/Section 6) rather than either (a)
mechanically following the literal instruction and breaking the pinned test,
or (b) silently keeping the old private functions to dodge the conflict.
That is the correct response to a design/review artifact that did not fully
trace one of its own call sites -- structurally the same class of problem
F-CORR-1 itself was (a signature/boundary that doesn't match its call site's
actual timing requirement), and the implementation record says so explicitly.

*A/B/C/D disposition:*

* Not *(B)* accidental API-surface duplication for convenience. The second
  entry point exists to satisfy a concrete, currently-pinned test that would
  otherwise break; it was not added because splitting was easier to write.
* Primarily *(A)*, with an element of *(C)*: this is a necessary
  preservation of two distinct semantic timing contracts (shape identity,
  needed unconditionally; key-form, needed only for value-checking
  policies). It is also mild evidence that the readiness design's Section 4
  literal one-function Lookup sketch under-traced its own retained call
  site -- the same class of gap F-CORR-1 caught on the FK side, just not
  caught pre-implementation on the Lookup side. It is not evidence that
  `InterpretedEnrichLookupProvenance` itself is too coarse: that value
  object's four fields are consumed as designed by `interpret_written_enrich_lookup_provenance`
  and nothing about the split changes its shape.
* Is "shape-only helper identity, key-form blind" a legitimate Lookup-owned
  primitive rather than a DCP convenience surface? *Yes, independently
  confirmed*, and confirmed by evidence the implementation record itself did
  not cite: `reconcile_enrich_lookup_provenance` -- the existing, H5-accepted,
  unmodified function in the same module -- already has exactly this
  posture. It extracts only declared `helper_columns` identity from a
  written record and is deliberately blind to join-key form (it never reads
  `on`/`source_key`/`lookup_key` at all), for the same underlying reason:
  its caller (FK cleanup reconciliation) needs identity, not key semantics.
  `validated_enrich_lookup_helper_columns` is not a novel invention; it is
  the same established "shape/identity separable from key-form" pattern
  this module already uses for a different caller, applied to a second
  caller with the identical requirement. This is stronger, independently
  discovered support for the deviation than the implementation record itself
  offers.

*Verdict: the two-entry-point design is CORRECT and adequately justified --
not an unauthorized behavior change, not accidental duplication, and not
evidence the readiness design needs a broader redesign. It is a narrow,
well-precedented, explicitly-flagged correction of a gap in the readiness
design's literal Section 4 sketch, handled exactly as the task instructs
(escalated, not silently resolved). The governing chain's own Section 18
wording should be read as "the two facade functions ultimately required by
the retained call sites," not as a literal ban on a third function; no
retroactive correction to `2a8ff36`/`c7f205c` is required by this finding,
but it is worth recording that neither fully traced this call site.*

=== FINDING-UR-001 -- MINOR -- overstated "never re-validated twice" claim

*Observation:* `enrich_lookup/provenance.py`'s module docstring (and the
implementation record's Section 4/Section 6 prose) states the two entry
points share `_validated_enrich_record_shape` "so the record is never
re-validated from scratch twice in one call." Under `warn_on_mismatch`/
`fail_on_mismatch`, this is false: `_resolve_derived_identity` ->
`validated_enrich_lookup_helper_columns` validates the record's shape once;
`_check_enrich_lookup_values` -> `interpret_written_enrich_lookup_provenance`
validates the identical record's shape again, from scratch, in the same
`apply_derived_column_policy` call.

*Evidence:* direct call-graph trace, `derived_column_policy.py:243,249,296,300,548`
and `enrich_lookup/provenance.py:66-123` (<<sec8>>).

*Concrete risk if ignored:* none material -- the second validation is
idempotent (data that failed would have already raised at the first call
site) and costs a few extra dictionary/isinstance checks per call, not a
correctness risk. The only real cost is a factually incorrect code comment
that could mislead a future maintainer reasoning about call cardinality.

*Recommended action:* reword the docstring's claim (in a future,
non-blocking edit) to something like "both entry points share the same
shape-validation logic; note that under warn/fail policies this means the
record's shape is validated twice per call (once for identity resolution,
once for key-form resolution) -- harmless because the second validation is
idempotent, not eliminated here to avoid widening Slice 1's scope."

*Disposition:* non-blocking for Slice 1 acceptance; a documentation-only
correction, appropriate to fold into Slice 2's own touch of this file or a
trivial standalone follow-up.

=== FINDING-UR-002 -- MINOR -- test-coverage completeness gaps in the two new isolated unit files

*Observation:* neither new test file exercises a tuple-typed `helper_columns`
input (both functions' type checks accept `(list, tuple)`); the Lookup file
does not test non-string helper-column entries or record isolation of
`lookup` absent/non-string; the FK file does not test an explicit empty list
or falsy/non-string `column` values.

*Evidence:* direct read of both new test files against their target
functions' `isinstance`/coercion logic (<<sec9>>).

*Concrete risk if ignored:* low -- these are type-coercion edge cases with
identical behavior to the pre-existing, relocated code (not new logic), and
the most significant related case (asymmetric null key halves) is already
thoroughly pinned via the unmodified DCP integration suite.

*Recommended action:* optionally add the listed cases to the two new files
at Slice 2 time or as a small, separate test-hardening follow-up; not
required before Slice 1 acceptance.

*Disposition:* non-blocking; additive only.
