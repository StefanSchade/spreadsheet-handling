== 1. Executive conclusion

The two live Slice-4A proofs failed for the *same architectural reason expressed
in two different fields*: the end-to-end coordinator proof is the first place the
system exercises the OpenAI/Codex *strict Structured Outputs dialect*, so the
expensive E2E is discovering that dialect one rule at a time.

* Proof 1 (11.4.2, `ae5d36c3`): inner `result` was `{"type":"object"}` -- rejected
  because strict mode requires `additionalProperties:false` and a complete object.
  Fixed as S4A-R10 (`6bfad5bb`/`41ff4e35`).
* Proof 2 (11.4.4, `455e456e`): the corrected schema's `schema_version:{"const":1}`
  node was rejected because strict mode requires a `type` key on *every* schema
  node, `const` included. Not yet fixed; maintainer stopped field-level patching.

The dialect rules ("every object strict and complete", "every node typed") are
*Codex/OpenAI transport facts*, not `RoutingResult` semantics. They currently live
in the provider-neutral `serialization.py`, and the CLI mechanics that carry them
live inline in `slice4.py` mixed with coordinator orchestration. The offline test
suite encodes only the two rules discovered *so far*, so it cannot pre-empt the
next one. That is the root cause of incremental discovery.

The fix is not "adopt hexagonal architecture." It is a small, concrete relocation
of responsibility plus one missing test layer:

. lift the OpenAI strict-schema *projection* out of `serialization.py` and behind a
  Codex adapter, leaving the *canonical semantic contract* in the domain;
. give the already-existing `Adapter` port enough shape to carry invocation
  identity, timeout, result contract, and a structured transport outcome (today
  these bypass the port or are smuggled back by mutation);
. add an offline provider-conformance layer that encodes the *documented* OpenAI
  strict subset in full, so the E2E stops being the discovery mechanism;
. add one tiny separately-authorized real smoke/probe below the coordinator before
  the next full E2E.

Verdict *A*. This is a bounded, incremental, code-working-at-each-step sub-slice,
not a redesign. Slice 4B and Slice 5 remain gated behind it.

Reading of the map:

  (`vertical`, `git_facts`, `evidence`, `prompt`, `persistence`) are already

boundary: "Invoke one configured local agent ...; capture output. It is not a
universal adapter, credential store, or sandbox." The current code has the port
(`Adapter`) and a concrete implementation (`_CodexAdapter`) but has not finished
pushing provider dialect and CLI mechanics behind that boundary.

== 3. Concrete coupling findings

Each finding: current owner -> correct owner -> why. These are dependency-direction
defects that inhibit provider replacement, conformance testing, and a future second
adapter -- not mere imports.

=== PB-1 (material) -- OpenAI strict-dialect projection sits in the domain serializer

`serialization.py:452 routing_result_json_schema()` and `:497
structured_result_envelope_schema()` encode OpenAI Structured Outputs *dialect*
rules: `additionalProperties:false` on every object, `set(required)==set(properties)`,
enum/`anyOf` shape, and (by omission) the "every node needs `type`" rule that
11.4.4 hit. These are not `RoutingResult` semantics; they are one provider's
transport constraints.

* Current owner: `serialization.py` (imports only `model`; otherwise
  provider-neutral).
* Correct owner: a Codex/OpenAI transport-projection behind the adapter. The
  *canonical semantic contract* (required-key sets, nullable rules, enums) stays in
  the domain and is the single source the projection derives from.
* Why it matters: a second provider (e.g. Claude) needs a *different* transport
  representation from the *same* semantic contract. With the projection fused into
  the domain serializer, adding a provider means editing shared domain code, and
  the drift-guard tests conflate "the semantic contract" with "OpenAI's dialect."
  The 11.4.4 failure is precisely a dialect rule the domain serializer got wrong.

=== PB-2 (material) -- `slice4.py` conflates the Codex adapter with coordinator orchestration

`slice4.py` mixes two layers in one file:

* Codex-specific (belongs in an adapter): `invoke_codex()` builds argv
  (`--ask-for-approval never`, `exec --ephemeral --json --color never --sandbox
  workspace-write`), pins `--model gpt-5.6-terra` and `model_reasoning_effort`,
  wires `--output-schema`/`--output-last-message`, launches a process group, and
  maps timeout/`SIGTERM`/`SIGKILL` and returncode.
* Provider-neutral (belongs in orchestration/`vertical`): `run_real_one_hop()`
  does dispatch-marker write, external-trusted-state-root enforcement, checkout
  association validation, run-snapshot/checkpoint persistence, and
  `reconcile`/uncertain-recovery -- none of which is Codex-specific and much of
  which duplicates `vertical.run_one_hop`.

* Correct owners: CLI mechanics -> `CodexCliAdapter`; orchestration ->
  `vertical`/application layer reused unchanged for any adapter.
* Why: a second adapter must not reimplement checkout association, reconcile, or
  persistence, and the Codex CLI contract must be changeable without touching Hop
  accounting.

=== PB-3 (material) -- the `Adapter` port is too thin, so provider facts bypass it

`adapter.py:26 Adapter.invoke(prompt, repository) -> str` cannot express the facts
the real path actually needs. Evidence of the mismatch, all in `slice4.py`:

* `invoke_codex` receives `expected: Invocation`, `timeout_seconds`, `state_root`,
  and `association` *directly*, not through the port.
* `_CodexAdapter` (a `@dataclass`, not frozen) returns the result *string* but
  smuggles the structured `CodexOutcome` (returncode, `timed_out`, stdout/stderr
  tails, `acceptance`) back to the caller by mutating `self.outcome` as a
  side-channel (`slice4.py:191, 194, 233, 250`). `run_real_one_hop` then reads
  `adapter.outcome` to build evidence.

* Correct owner: a richer port whose *return type* carries the transport outcome
  and bounded diagnostics, and whose *request* carries invocation identity, result
  contract, timeout, and an execution-policy/capability request.
* Why: the side-channel mutation is the concrete symptom that the port does not
  model what the coordinator needs; every adapter would have to reinvent the same
  smuggling. A typed return also lets Level-1 tests assert diagnostics without a
  process.

=== PB-4 (material) -- offline strictness invariant encodes only rules discovered so far

`tests/unit/workflow_coordinator/test_slice4.py:135
test_structured_result_schema_makes_every_object_strict_and_complete` walks object
schemas and asserts only `additionalProperties is False` and
`set(required)==set(properties)`. It never asserts that *every* schema node
(including `const`/`enum`/leaf nodes) carries a `type`. That is exactly the rule
11.4.4 discovered live. Tests are green (72 passed) yet the emitted schema is
provider-invalid.

* Current owner: a single ad-hoc walker in one test.
* Correct owner: a named offline *conformance* check that encodes the full
  *documented* OpenAI strict subset and runs over the adapter's projected schema.
* Why: this is the mechanism by which the expensive E2E stopped being able to
  catch dialect errors; encoding the documented subset offline is what ends
  incremental live discovery.

=== PB-5 (watch) -- `proof_harness.py` defaults a provider executable name

`proof_harness.py:176,263` default `executable="codex"`. This is an operator
default, not a domain coupling, and is acceptable. Note only: when the adapter
seam is formalized, the harness should select an *adapter*, not an executable
string, so provider identity is named in one place.

Non-findings: `vertical`, `reducer`, `model`, `git_facts`, `evidence`, `prompt`,
`persistence` contain no provider knowledge and need no change. Do not "clean them
up."

== 4. Proposed port/adapter boundary

Smallest useful provider-neutral execution interface. This is *not* a plugin
framework, registry, or dynamic discovery. One port, one concrete adapter, typed
request/response.

[source,python]
----
# provider-neutral (application layer) --------------------------------------
@dataclass(frozen=True)
class AgentExecutionRequest:
    invocation: Invocation          # run_id, hop_id, invocation_id (identity)
    prompt: str                     # already-assembled semantic prompt
    repository: Path                # agent workspace
    result_contract: ResultContract # canonical RoutingResult contract handle
    timeout_seconds: float
    capabilities: ExecutionPolicy   # writable-workspace? continuing-context? -- request, not flags

@dataclass(frozen=True)
class AgentExecutionOutcome:
    disposition: str                # 'established' | 'uncertain' | 'transport_error'
    result: RoutingResult | None    # semantic result iff Python-validated + correlated
    transport: TransportOutcome     # returncode|None, timed_out, bounded stdout/stderr tails
    diagnostics: tuple[str, ...]    # bounded, provider-neutral failure lines
    provider_ref: str | None        # opaque adapter-owned reference/evidence pointer

class AgentExecutionPort(Protocol):
    def execute(self, request: AgentExecutionRequest) -> AgentExecutionOutcome: ...

# Codex/OpenAI-specific (adapter layer) -------------------------------------
class CodexCliAdapter(AgentExecutionPort):
    # owns: argv/flags, --model, sandbox, --output-schema/--output-last-message,
    #       process group + timeout mapping, OpenAI strict-schema projection,
    #       Codex JSONL/stdout interpretation, Codex diagnostics.
    ...
----

Boundary rules the port must hold:

* The port MUST NOT expose Codex CLI flags, the model name, `--output-schema`,
  sandbox flags, or the OpenAI JSON-Schema dialect. Those are adapter-internal.
* `AgentExecutionOutcome.result` is the *semantic* `RoutingResult`, established
  only by the existing Python `validated_result` correlation check -- unchanged
  authority. `transport` carries the provider representation and diagnostics
  separately; the two must not be merged (they were merged, informally, via
  `adapter.outcome` today -- PB-3).
* Migration is behaviour-preserving: today's `_CodexAdapter.invoke` + external
  `adapter.outcome` read collapses into one typed `execute() -> AgentExecutionOutcome`.

This keeps the port at "what the coordinator needs to dispatch one bounded agent
Hop and reduce its result," matching design-doc section 3's Agent-adapter boundary,
and no larger.

== 5. Result-contract ownership

Desired dependency direction (derived from the code, not imposed):

[source,text]
----
canonical semantic RoutingResult contract        (domain: serialization/model)
    |         required-key sets, enums, nullable rules -- ONE source
    +--> Python validator            routing_result_from_data / validated_result   (domain)
    +--> OpenAI/Codex strict projection   CodexCliAdapter                           (adapter)
    +--> future Claude transport projection  ClaudeAdapter                          (adapter)
----

Where `routing_result_json_schema()` / `structured_result_envelope_schema()` should
live: *the projection functions belong in the Codex/OpenAI adapter*, deriving their
required-key lists and enums from the domain contract they already import
(`FINDING_DELTA_KEYS`, `ROUTING_RESULT_REQUIRED_KEYS`, `FindingState`, `Outcome`,
`ESCALATION_*`). The review `75c63d4f` section 6 correctly placed them in
`serialization.py` *as the smallest S4A-R10 correction* -- that was right for that
bounded hop and must not be criticized retroactively. The long-term correct owner
is nonetheless the adapter: the strict-dialect facts are provider-specific, and
11.4.4 is the proof that treating them as domain-level produced a provider-invalid
artifact that passed domain tests.

Concretely: keep in the domain the *canonical contract* (key sets, enums, nullable
semantics, the Python validator). Move to the adapter the *strict-schema builder*
that turns that contract into OpenAI's dialect. The drift-guard test then splits
into (a) contract<->validator alignment (domain) and (b) projection-conforms-to-
OpenAI-strict-subset (adapter conformance, section 8).

== 6. Codex adapter responsibilities

`CodexCliAdapter` owns, and is the *only* place that owns:

* the `codex` executable, argv, `exec`/`--ephemeral`/`--json`/`--color`,
  `--ask-for-approval`, `--sandbox workspace-write`, `--cd`;
* `--model gpt-5.6-terra` and `model_reasoning_effort` selection;
* `--output-schema` / `--output-last-message` wiring and reading;
* the OpenAI strict Structured Outputs projection of the canonical contract;
* process launch, `start_new_session`, timeout -> `SIGTERM`/`SIGKILL` process-group
  mapping, returncode capture, bounded stdout/stderr tails;
* Codex `--json` event-stream / `turn.failed` / HTTP-400 interpretation and
  provider-diagnostic extraction;
* Codex/OpenAI acceptance and conformance specifics.

It does NOT own (these stay in the application/vertical layer, reused by any
adapter): checkout association and external-trusted-state-root enforcement,
dispatch-marker lifecycle, Git preflight/observation, reconcile/uncertain recovery,
run-snapshot/checkpoint persistence, Hop accounting, evidence collection,
prompt assembly, and the semantic `validated_result` correlation gate.

== 7. Future Claude test (architectural probe only -- do not implement)

If a `ClaudeAdapter` were added tomorrow, the following MUST remain untouched
(today they already carry no provider token, so this is achievable):

* `reducer.py`, `model.py` (Run/Hop/Finding), `persistence.py`, `evidence.py`,
  `git_facts.py`, `prompt.py` (semantic assembly), `vertical.run_one_hop`, and the
  Python `RoutingResult` validation/correlation in `adapter.validated_result` /
  `serialization.routing_result_from_data`.

New provider-specific code that WOULD be added: a `ClaudeAdapter` implementing
`AgentExecutionPort`, its own transport projection of the *same* canonical
contract into Claude's tool/output representation, its own CLI/SDK mechanics, and
its own adapter-level conformance tests.

Current decisions that make a second adapter awkward (all are the section-3
findings): (a) the strict projection living in `serialization.py` (PB-1) forces a
second provider to edit shared domain code; (b) the thin port + `adapter.outcome`
side-channel (PB-3) forces every adapter to reinvent outcome smuggling; (c) the
orchestration duplicated inside `slice4.py` (PB-2) invites a second copy. Fixing
PB-1..PB-3 is exactly what makes a second adapter a *new file*, not a *domain edit*.

== 8. Conformance ladder

Design goal: the expensive coordinator E2E must stop being the first place a
provider dialect rule is exercised. Four levels; each states what it proves and
what it deliberately does not.

*Level 1 -- pure/offline adapter tests (REQUIRED).* No process, no provider.
Assert: the OpenAI strict-subset projection of the canonical contract satisfies the
*full documented* strict rule set -- every object `additionalProperties:false`,
`required==properties`, and *every schema node carries a `type`* (the PB-4 gap that
would have caught 11.4.4), across `properties`, array `items`, and `anyOf`; argv
construction; result parsing; diagnostic extraction; strictness invariants; the
projection derives from the domain contract (drift guard). Proves: the adapter emits
a provider-*valid*, contract-*complete* schema and parses results. Does NOT prove:
the live provider accepts it (documentation may lag the live API).

*Level 2 -- Codex CLI integration against a local stub/mock (PRACTICAL for argv/
request-shape; UNCERTAIN for full request/response).* The Codex CLI is installed
locally (`/usr/local/bin/codex`, `codex-cli 0.147.0`), so exercising *argv
acceptance* and *`--output-schema` file handling* without a model call is
practical. Driving the CLI's full request/response against a stubbed OpenAI
endpoint depends on whether `codex-cli` supports a base-URL/endpoint override to a
local mock; that is UNCERTAIN and must be investigated (not built) before being
promised. Proves (if achievable): the CLI transmits the schema in the shape the
provider will see. Does NOT prove: real-provider acceptance semantics.

*Level 3 -- tiny real-provider adapter smoke/probe (RECOMMENDED before Level 4).*
No coordinator Run, no Git workflow, no findings lifecycle: minimal prompt, the
real strict envelope schema, one real invocation, assert the provider accepts the
schema and returns a parseable correlated envelope. Authority/safety boundary: its
own explicit one-shot maintainer authorization, disposable workspace, no `.git`
authority needed, bounded evidence -- strictly smaller than a Slice-4A proof.
Proves: current real Codex/OpenAI schema compatibility. Does NOT prove: the
coordinator vertical, Git ownership, or reconcile.

*Level 4 -- full coordinator E2E proof (only after Levels 1--3 green).* The
existing Slice-4A one-shot live happy-path proof. Proves: the whole vertical
(WFC-AUTO/GIT/OUTPUT/FAIL/SEC) end-to-end. Does NOT prove: anything Levels 1--3
already isolate -- and must no longer be the place dialect rules are discovered.

== 9. Documented contract vs empirical probe (section 7 of prompt)

Separate three things and stop using live E2E as the exploration tool:

* *Documented contract*: the OpenAI Structured Outputs strict-subset rules
  (`additionalProperties:false` required and `false`; `required` must list every
  key; every schema node must have `type`; limited keyword support). These are
  encodable offline (Level 1) from primary OpenAI documentation and the local
  `codex --help`/CLI surface -- consult those, do not invoke the provider.
* *Locally testable contract*: argv/request-shape and schema-file handling via the
  installed CLI (Level 2, to the extent practical).
* *Real-provider smoke evidence*: one tiny Level-3 probe to confirm the live API
  matches the documented contract at a moment in time.

Continued field-by-field E2E trial-and-error is explicitly rejected as the design;
the maintainer already stopped it. If network access is available, consult only
primary OpenAI/Codex documentation to seed the Level-1 rule set; do not call the
provider in this or the implementation work until Level 3 is separately authorized.

== 14. Risks and rejected alternatives

* *Rejected: one-line `schema_version:{"type":"integer","const":1}` patch.* It would
  likely pass this node and re-enter live discovery on the next unseen strict rule;
  it is the exact pattern 11.4.4 forbids and the maintainer stopped. It also leaves
  PB-1..PB-4 intact.
* *Rejected: full hexagonal build-out / registry / capability negotiation.* No
  current change pressure supports it; it violates the human-readability/locality
  guidance and the "no generic framework" constraint.
* *Rejected: leave projection in `serialization.py` and only add tests.* Tests alone
  cannot fix the dependency direction that makes a second adapter a domain edit; and
  a domain-owned dialect keeps conflating "contract" with "OpenAI's rules."
* *Risk: Level-2 stub may be impractical.* Mitigated by making Level 1 + Level 3 the
  required gates and Level 2 best-effort; the ladder does not depend on Level 2.
* *Risk: documented strict subset may lag the live API.* Mitigated by the Level-3
  smoke as a dated empirical confirmation; but Level 1 still ends *incremental*
  discovery of already-documented rules, which is the actual failure mode observed.
* *Watch: `supports_parallel_tool_calls` models-cache warning* remains
  UNRELATED/WATCH (per `75c63d4f` section 9); out of scope here.

== 15. Human readability / locality

diagnostics on `AgentExecutionOutcome`, semantic acceptance on `validated_result`).
No abstraction is added whose only benefit is fewer lines.
