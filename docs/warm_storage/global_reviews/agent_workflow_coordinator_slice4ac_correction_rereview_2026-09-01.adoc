== 2. S4AC-R1 (BLOCKING) -- CLOSED

The correction replaces the blanket `except Exception: dispatch_path.unlink();
raise` with an explicit classification:

[source,python]
----
    def recover_uncertain(outcome):        # retains marker, charges Hop, reconcile
        ...
    try:
        vertical = run_one_hop(...)
    except ExecutionResultValidationError as error:
        return recover_uncertain(error.outcome)   # provider ran, bad result
    except ExecutionNotStartedError:
        dispatch_path.unlink(missing_ok=True); raise      # proven pre-execution
    except CodexCliError as error:
        dispatch_path.unlink(missing_ok=True); raise Slice4Error(...)   # pre-Popen
    except Exception:
        return recover_uncertain(None)            # maybe-executed -> fail closed
----

The required semantic rule -- *marker deletion only when execution is proven not
to have begun; otherwise fail closed* -- holds.

=== R1-A -- pre-execution deletion proven safe

Only two exception classes delete the marker, and every current raise site is
proven pre-execution:

* `ExecutionNotStartedError` -- raised at exactly two sites, both in
  `vertical.run_one_hop` *before* `adapter.execute()`: `preflight_hop` failure
  (`vertical.py:99`) and any `assemble_prompt` failure (`vertical.py:104`, a broad
  `except Exception` wrap that is lexically before the execute call, so nothing has
  executed). No post-execution site raises it.
* `CodexCliError` -- raised at exactly three sites in `CodexCliAdapter.execute`,
  all *before* `subprocess.Popen` succeeds: unsupported result contract
  (`codex_adapter.py:148`), non-positive timeout (`:150`), and the `OSError` launch
  wrap (`:161`). Verified from the actual `execute` body: after `Popen` succeeds
  the only failures are `TimeoutExpired` (handled internally) and any
  `os.killpg`/`read_text` error, none of which is wrapped as `CodexCliError` --
  they propagate as generic exceptions and therefore fail closed. No `CodexCliError`
  can occur after `Popen`.

=== R1-B -- post / may-have-executed fail-closed

* AgentExecutionOutcome validation failures (`candidate_result is None`;
  `validated_result` rejection) reach `ExecutionResultValidationError` ->
  `recover_uncertain(error.outcome)` -> marker retained. Unchanged, correct.
* Arbitrary exceptions after `adapter.execute()` returns
  (`observe_hop`/`_subject_anomalies`/`run_evidence`/`record_hop`/`reduce_result`/
  `checkpoint_projection`) reach the generic `except Exception` ->
  `recover_uncertain(None)` -> marker retained + reconcile. This is the exact fix.
* An unclassified exception raised *from* `adapter.execute()` where execution
  cannot be disproved also reaches `recover_uncertain(None)` and fails closed
  (conservatively charged), rather than being treated as pre-execution. The adapter
  contract is: raise `CodexCliError`/`ExecutionNotStartedError` only for
  proven-not-started; anything else is treated as maybe-started. Conservative
  over-charging is the safe direction (never forgets a Hop, never replays).
* No absence-of-outcome condition is read as proof of non-execution:
  `recover_uncertain(None)` retains the marker and charges the Hop.

=== R1-C -- secondary recovery failure preserves no-replay authority

If `recover_uncertain(None)` itself raises (e.g. its `observe_hop` fails), the new
exception propagates out of `run_real_one_hop`. Crucially, the dispatch marker was
written before the `try` and is deleted *only* in the ENS/`CodexCliError` branches,
so it *remains durable* through a secondary recovery failure. Later reconstruction
sees the marker -> a Hop was dispatched -> it cannot be classified as "never
dispatched", preserving no-replay authority (WFC-PERSIST-01, WFC-AUTO-02). The
pre-`try` `run.json` snapshot may then be stale (`hop_used` unchanged), but the
marker, not the snapshot, is the resume authority -- acceptable per the review
bound.

=== R1-D -- Hop charging / fact truthfulness

`recover_uncertain_dispatch` (reused unchanged) charges exactly one Hop
idempotently (skips if the `marker.hop_id` Hop already exists), records
`role="uncertain_dispatch"`, `invocation_status="acceptance_not_disproved"`,
`outcome="uncertain"`, and populates `end_head`/`actual_commits` from independent
Git observation. It fabricates no provider result or acceptance; a later explicit
reconcile reconstructs truth from Git + dispatch state. Consistent with the
WFC-AUTO/WFC-FAIL invariants cited in the original S4AC-R1.

=== R1-E -- regression test quality and independent confirmation

* `test_real_driver_retains_dispatch_after_post_execution_mutating_failure`: fake
  CLI runs exactly once (`executions=="1"`), mutates and commits
  (`PROOF.md=="after"`, HEAD advanced), then `vertical.observe_hop` is monkeypatched
  to raise -> marker survives, `hop_used==1`, status `reconcile_required`,
  `stop_reason=="reconcile_requires_explicit_resume"`, checkpoint persisted, no
  replay. This test fails against the pre-correction code, so it genuinely guards
  the original defect class. The monkeypatch targets *only* `vertical.observe_hop`,

  and valid: it isolates "primary post-execution observation failed, recovery

* `test_real_driver_fails_closed_for_unclassified_execution_boundary_exception`:

== 3. S4AC-R2 (IMPORTANT) -- CLOSED

* `const` removed from `_STRICT_KEYS` (`codex_adapter.py:41`).
* Both `schema_version` nodes now emit `{"type": "integer", "enum": [1]}`
  (routing-result and envelope).
* The checker now *rejects* `const`:
  `test_conformance_rejects_constructs_outside_the_projection_subset` injects
  `{"type":"integer","const":1}` and asserts "unsupported keywords".
* `test_schema_version_uses_the_documented_single_value_enum_in_both_envelopes`
  pins both nodes to the enum form.
* Python semantic validation independently still requires `schema_version == 1`
  (`validated_result` and `routing_result_from_data._version`) -- unchanged.

Primary-documentation basis (no provider called): the OpenAI Structured Outputs
guide demonstrates `enum` as a supported strict keyword with concrete examples and
supports the `integer` type; it does not document a minimum enum cardinality, and
it does not list `const`. Therefore a single-value `{"type":"integer","enum":[1]}`
is a *direct and reasonable consequence of the documented contract* (enum with one
member), not the prior ambiguity: the projection moved from an *undocumented*
keyword (`const`) to a *documented-supported* one (`enum`). The generator and
checker are now anchored on a documented rule, and the injected-`const` rejection
gives the checker independent bite. The bounded Level-1 claim is justified; the
only residual (single-value enum minimum is not *explicitly* enumerated) is a
trivial consequence and is precisely what a later Level-3 smoke would confirm
empirically, as designed.

*R2 disposition: CLOSED.*
