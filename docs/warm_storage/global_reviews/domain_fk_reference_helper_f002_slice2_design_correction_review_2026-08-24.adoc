== 4. F-CORR-2 closure -- multi-key formula mode

Reasoned through each of the seven review questions against current source
and an independent repro:

. *Does `InterpretedEnrichLookupProvenance` preserve the full key tuple?*
  Yes, confirmed directly (`provenance.py:114-122`): symmetric mode returns
  the full `on` list twice (`payload_keys == lookup_keys`, both the complete
  tuple); asymmetric mode returns exactly one key per side. No truncation
  occurs at this seam -- truncation is exclusively `_build_formula_enrichment`'s
  own defect, three call-frames away from where the guard is evaluated.
. *Is multi-key formula mode currently reachable?* Yes, confirmed by the
  independent repro above: `enrich_lookup(..., keys=["id","part"],
  helper_value_mode="formula")` succeeds today with no `ValueError` from any
  registered validation path.
. *Would the original `[0]`-comparison falsely certify it?* Yes, confirmed by
  direct construction: cell tuple `('stories', 'id', 'id', 'title')` against
  expected tuple `('stories', payload_keys[0]='id', lookup_keys[0]='id',
  'title')` are equal -- the original design's validator would report zero
  findings under `warn_on_mismatch` and no raise under `fail_on_mismatch` for
  a cell that does not, in fact, faithfully encode the declared two-key
  relationship.
. *Does the corrected `len != 1` carve-out eliminate that risk?* Yes. The
  guard is directly computable from data already proven correct in (1); no
  further Lookup-side change is needed to implement it. The design's own
  claim that `len(payload_keys) != 1` and `len(lookup_keys) != 1` are
  equivalent conditions is independently verified true by source inspection
  (both are always equal by construction -- symmetric mode duplicates one
  list, asymmetric mode is always exactly 1/1).
. *Is `unverifiable_enrich_lookup` the correct semantic category?* Yes.
  A structurally-incorrect single-key formula genuinely *is* checked and
  found wrong (`derived_formula_mismatch` is correct there, per the
  governing review's Section 13.1, not reopened here); a multi-key formula
  cell *cannot* be checked at all given the current single-key
  `LookupFormulaSpec` representation -- that is precisely what
  `unverifiable_enrich_lookup` already exists to express, matching the
  duplicate-key correction's identical reasoning in the same document.
. *Does this avoid accidentally fixing or legitimizing the producer defect?*
  Yes. The design is explicit and repeated on this point: "Do NOT fix
  multi-key formula generation in F-002," and "multi-key formula-mode
  `enrich_lookup` remains as functionally broken after Slice 2 as before it
  -- Slice 2 only stops *certifying* that brokenness as structurally
  correct." This is the correct scope boundary; fixing the producer would be
  a materially larger, unrelated `enrich_lookup`-write-path change.
. *Is the proposed test plan sufficient?* Yes. Section 12.2's mandatory
  multi-key block covers exactly the four cases the governing review
  required: warn -> `unverifiable_enrich_lookup`; fail -> failure at the DCP
  orchestration boundary; an explicit no-`[0]`-only-false-valid assertion;
  an explicit no-`derived_formula_mismatch`-merely-because-impossible
  assertion. No gap identified.

*F-CORR-2: CLOSED.* No missing decision remains; the carve-out is fully
specified (branch condition, target category, reason-string content) and
independently verified against current runtime behavior.

== 5. F-CORR-3 closure -- `LookupFormulaSpec.missing`

Confirmed directly: `core/formulas.py::LookupFormulaSpec` declares five
fields including `missing: str = ""`. Confirmed
`enrich_lookup/operation.py:164-168` raises before formula-building whenever
`use_formulas and missing_mode == "fail"`. Confirmed further, independently
of the design's own claim, that `_build_formula_enrichment`
(`operation.py:469`) hardcodes `missing=""` as a *literal* in the
`lookup_formula(...)` call -- it does not even reference its own
`missing_mode` parameter at that call site, so the invariant is stronger than
"currently the only reachable value happens to be empty": it is currently
impossible for this one producer to emit anything else, independent of the
upstream `fail` rejection.

Questions:

* *Is `missing=""` genuinely invariant for currently reachable formula
  writes?* Yes, confirmed as above, by two independent mechanisms
  (upstream rejection of `fail`, and a hardcoded literal at the one write
  site) -- doubly invariant, not merely coincidentally so today.
* *Does formula mode reject `missing="fail"` before writing?* Yes, confirmed.
* *Is excluding `missing` more semantically honest than pretending provenance
  can validate something it does not encode?* Yes -- this is exactly
  parallel to Section 6.2's already-accepted values-mode `missing`
  disposition (provenance never records the `missing` mode used at
  enrichment time; DCP structurally cannot reconstruct it; declining to
  guess is the sound choice), and the correction explicitly draws that
  parallel rather than inventing a new rule.
* *Does this leave an implementation-time ambiguity?* No. The 4-tuple is
  named explicitly (which four fields, in what order, against what expected
  values), `missing` is named explicitly as excluded with a stated reason,
  and a revisit trigger is named (if `_build_formula_enrichment` ever gains
  the ability to emit non-empty `missing`, revisit). Nothing is left for an
  implementer to decide.

*F-CORR-3: CLOSED.*

*Verdict: ACCEPT DESIGN DETAIL.* This is the smallest coherent
