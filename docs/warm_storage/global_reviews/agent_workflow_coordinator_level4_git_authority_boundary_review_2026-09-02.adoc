== 7. Finding / escalation persistence analysis (L4-R1, WATCH)

*Question:* the durable `result-message.json` preserves `escalation != null`
and one blocking Finding `git-metadata-read-only`, but `run.json` /
`checkpoint.json` record `findings=[]`, `human_question=null`, and
`finding_delta_ids=[]`, while Hop `H001` records `outcome=blocked`. Is this
intentional?

*Answer: YES -- intentional, and a direct deterministic consequence of the
reducer ordering.* `reducer.reduce_result` (`scripts/workflow_coordinator/
reducer.py:238`) documents "Apply mandatory preemption before any Finding or
route authority." The dirty-worktree anomaly ("dirty tracked state", raised in
`git_facts.py:198` and carried as `MechanicalFacts.repository_anomaly` via
`vertical.run_one_hop`, `vertical.py:135-138`) is checked in the
`mechanical_errors` tuple at `reducer.py:258-268` and returns
`_stop_for_human(run, "mechanical_preemption:dirty tracked state")` with
`question=None`. That return occurs *before*:

* the `requires_human`/`escalation` branch (`reducer.py:271-278`), which would
  otherwise have set `human_question` from the escalation text, and
* `apply_finding_deltas` (`reducer.py:301-308`), which would otherwise have
  promoted the blocking Finding into the run ledger.

So `human_question=null` and `findings=[]` in the reduced state are the correct,
designed result of mechanical dirty-state preemption dominating semantic
Finding/escalation reduction. The blocking Finding and escalation survive
durably *only* in the persisted `result-message.json` under
`trusted-state/checkouts/<id>/`.

*Sufficiency of the artifact as durable authority:* for this N=1 disposable proof
the result is fail-closed `awaiting_human` with `budget remaining=0` and no
authorized resume/retry; human disposition is mandatory and the human has the
full `result-message.json` (escalation kind `operational`, question text,
blocking Finding, evidence refs). At *this* boundary the artifact is sufficient
durable authority and no behavior is incorrect.

*Why WATCH, not a blocking finding:* the authoritative *run finding-ledger* does
not carry the blocking Finding or the escalation question; `stop_reason` encodes
only the class string `dirty tracked state`, not the *reason* the tree is dirty
(`git-metadata-read-only`, `operational` escalation). A consumer that resumes or
reconstructs from `run.json`/`checkpoint.json` alone -- without reading the raw
`result-message.json` -- would not see the blocking Finding or the human
question. That is harmless now (no resume authorized; disposition is manual with
the artifact present), but when Slice 4B introduces coordinator-owned commit and
any resume/reconstruction path, the promotion contract at the preemption
boundary should be revisited so a blocking Finding/human-question raised in the
same reduction as a mechanical preemption is not dropped from the authoritative
ledger. Recorded as *L4-R1 (WATCH)*; do not redesign Findings in this hop.

== 8. changed_paths analysis (L4-R2, MINOR)

`proof-summary.json` records `git_status="M PROOF.md"` (dirty worktree) yet
`changed_paths=[]`.

*Derivation.* `changed_paths` is a *committed-range* diff, not a working-tree
status. In the proof summary it is computed at `proof_harness.py:169` as
`git diff --name-only {initial_head}..{final_head}`; the analogous
Coordinator-side field `GitDelta.changed_paths` is likewise
`git diff --name-only {base_head}..{head}` (`git_facts.py:193`). Because
`initial_head == final_head` (no commit was created), the range is empty and
`changed_paths=[]` is *correct commit-range semantics*, consistent with
`actual_commits=[]` and `actual_commit_range` being an empty range.

*Judgement.* `changed_paths=[]` alongside `git_status="M PROOF.md"` is
*CORRECT, not misleading* in substance: the two fields measure different things
(committed range vs. working-tree status) and both are individually truthful; on
the expected happy path (a clean tree after exactly one commit) they coincide.
The residual concern is *naming/documentation only*: the bare name
`changed_paths` could invite a casual reader to expect "all mutated paths,"
which would be wrong when uncommitted dirty state exists. Because `git_status`
is present in the same record and disambiguates, this is *MINOR*. Recorded as
*L4-R2 (MINOR)*; not fixed in this hop.
