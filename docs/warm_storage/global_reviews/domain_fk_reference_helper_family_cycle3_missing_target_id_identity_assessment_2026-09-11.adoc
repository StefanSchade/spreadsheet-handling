== Scope and method

This is a bounded, read-heavy assessment of Missing target-ID treatment in
`domain.validations.fk_helpers:check_duplicate_ids`.  It reads current
Cycle-3 assessment/review authority, the scalar-value contract, FK-helper
validation and immediate FK materialization consumers, declarative reference
validation, and focused tests.  It includes an empirical probe of the current
pandas string-carrier path.  It does not implement or change runtime or test
behavior.

The assessment distinguishes an ordinary string from a Missing carrier.  It
does not decide the separate question of whether a Missing value can serve as
a target identity.

== Current authority and boundary meaning

=== What a target ID means here

`check_duplicate_ids` is a generic per-sheet uniqueness check.  For a sheet
named as an FK target in v2 relation policy or current helper provenance, it
selects that relation's declared `target_key`; otherwise it falls back to
`defaults['id_field']` (default `"id"`).  Thus it has a broader caller surface
than the FK-helper primitive and may also check a workbook with no FK policy.
It emits a `duplicate_id` finding, whose maintained meaning is simply that a
sheet has duplicate values in its selected ID column.

The scalar model separately classifies `None`, `""`, NaN, `pd.NA`, and `NaT`
as Missing carriers.  That is carrier recognition, not an identity rule: it
does not say whether such a carrier is an invalid ID, an absent/non-identity
row, or a duplicate identity when repeated.  Literal String `"nan"` is an
ordinary String, not a Missing carrier.

Accordingly, the current repository authority supports these distinctions:

* an *ordinary identity candidate* is a non-Missing selected ID value; current
  duplicate detection compares its pandas String rendering;
* a *Missing carrier* is a scalar-value classification, not an established
  target-ID disposition;
* *invalid or unusable target identity* is not a category currently emitted
  by `check_duplicate_ids` or automatically established by FK relation policy;
* *absence of a usable map key* is current materialization behavior: FK target
  maps and target-ID sets omit normalized Missing target values; and
* *duplicate identity* is a `duplicate_id` finding after the check's current
  string-backed counting.  This observation does not establish that repeated
  Missing carriers are intended duplicate identities.

=== Existing owner of a non-missing primary-key invariant

There is a current validation boundary that can own this invariant, but only
when explicitly configured: `domain.validations.reference_validations`
`primary_key` rules.  `_validate_primary_key` reports every empty key with
`"Primary key values must be present and non-empty."`, then runs uniqueness
only over complete rows.  Its `foreign_key` target set likewise excludes empty
keys.

That is a declarative, rule-owned primary-key contract.  FK v2 relation policy
does not implicitly create such a rule, and `validate_fk_helpers` does not
delegate its `target_key` to it.  No current accepted boundary therefore owns
an unconditional “every FK-helper target ID must be usable/non-Missing”
invariant.  `check_duplicate_ids` must not silently acquire that ownership.

== Empirical current behavior

The probe used `check_duplicate_ids({"T": DataFrame({"id": values})},
{"id_field": "id"})` with two equal candidate values and one ordinary value.
It ran with the repository environment's pandas version.  The function applies
`astype("string")`, then `value_counts(dropna=False)`, and retains counts over
one except a rendered value exactly equal to `"nan"`.

The current `str(idx) != "nan"` guard is consequently vestigial for its
apparent Missing-carrier purpose: Missing carriers render as `<NA>`, not
`"nan"`.  It is live only for literal String `"nan"`, which the scalar
authority says is ordinary.  Dead-looking code alone would not authorize a
Missing-ID policy change; here the distinct ordinary-String authority and the
maintained `duplicate_id` meaning are the evidence for the narrow slice below.

== FK/helper handoff evidence

Missing target IDs can reach the duplicate check: it runs over every checked
frame before the other FK-helper findings, and neither policy resolution nor
the generic `validate` step first enforces target-key presence.

Later FK/helper consumers do not make Missing a valid target identity:

* `core.fk:build_id_value_maps` normalizes a target ID and omits it when it has
  no map key; target-ID sets used by FK validation likewise omit normalized
  Missing values.
* FK enrichment resolves a source FK only through that map.  A map miss,
  including a Missing source FK or a source key without a usable target ID,
  materializes helper `""`; the helper cell is not resolution authority.
* Normalized duplicate ordinary target keys remain operationally hazardous:
  map construction overwrites an earlier value with a later one, as an
  existing test records.  This is evidence that ordinary duplicate reporting
  is useful, not authority for how a Missing target row must be classified.

The accepted C3-S1 reviews deliberately left `check_duplicate_ids` untouched.
They establish that changing Missing handling here to ignore, reject, or retain
repeated Missing IDs would choose an unresolved target-identity policy.

== Missing target-ID decision

The repository does *not* currently authorize an answer to whether multiple
Missing target IDs are invalid independently of duplication, ignored as
non-identity rows, or real duplicate-ID findings.  Present behavior reports
them as duplicate findings, but accepted reviews describe that behavior as a
consequence of the current carrier conversion, not an accepted semantic
decision.  The scalar Missing contract and the explicit declarative
`primary_key` rule do not decide the FK-helper target-key policy.

The required maintainer decision for a later Missing-target-ID slice is:

[quote]
____
For an FK-helper relation target's declared `target_key`, are Missing values
invalid primary-key values, rows excluded from identity/duplicate checking, or
values that participate in duplicate identity?  If invalid, which validation
surface emits that finding and how is it configured?
____

That decision needs an owning FK/helper or declarative-rule contract and
focused tests before any change to Missing handling in `check_duplicate_ids`.

== One safe next Cycle-3 slice

*SELECTED: C3-S2 -- restore duplicate reporting for literal String `"nan"`
only; implementation is NOT STARTED.*

This slice is safe because literal `"nan"` is already an ordinary String under
the accepted scalar contract, while `duplicate_id` already means repeated ID
values.  It removes only the contradictory special case.  It does not decide,
normalize, reject, or ignore Missing target IDs.

Exact source/test scope::

* `src/spreadsheet_handling/domain/validations/fk_helpers.py` -- remove the
  literal-`"nan"` exclusion from `check_duplicate_ids` only.
* `tests/unit/domain/validations/test_fk_check.py` -- add focused
  `check_duplicate_ids` coverage for literal `"nan"`, and characterization
  coverage for the current Missing-carrier results needed to prove the slice
  has not chosen their disposition.

Acceptance criteria::

* Two literal String `"nan"` IDs produce `duplicate_id`, just as repeated
  ordinary Strings do.
* `None`, `""`, float/NumPy NaN, `pd.NA`, and `NaT` retain their exact current
  `check_duplicate_ids` outcomes; no Missing-aware exclusion or new
  invalid-ID finding is introduced.
* Repeated ordinary IDs remain findings; target-key choice remains v2
  `target_key` for declared target frames and the existing fallback elsewhere.
* No change occurs to source-FK Missing handling, key-domain equality,
  trimming, target-map materialization, helper payload behavior, public
  signatures, YAML, or Trusted Ingress.
* Focused validation tests pass, including the existing policy-independent
  duplicate-check use case.

Semantics explicitly unchanged:: Missing target-ID identity remains
*UNDECIDED*.  In particular, C3-S2 neither makes Missing IDs invalid nor
declares them ignored/non-identity nor ratifies their present duplicate
findings as the intended policy.
