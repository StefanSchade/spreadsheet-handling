== 3. Lookup mismatch evaluator/report added

`enrich_lookup/mismatch.py` exposes:

[source,python]
----
@dataclass(frozen=True)
class LookupMismatchReport:
    missing_lookup_frame: bool = False
    unverifiable_reason: str | None = None
    value_mismatches: Mapping[str, tuple[RowIndex, ...]] = field(default_factory=dict)
    formula_mismatches: Mapping[str, tuple[RowIndex, ...]] = field(default_factory=dict)


def evaluate_lookup_mismatches(
    payload: pd.DataFrame,
    *,
    interpreted: InterpretedEnrichLookupProvenance,
    lookup_frames: Mapping[str, pd.DataFrame],
) -> LookupMismatchReport: ...
----

Exactly the four fields the design's Section 10 (as reconfirmed by the
correction review's F-CORR-2 disposition) specifies -- no richer shape was
needed; the multi-key formula carve-out and the duplicate-key carve-out both
route through the existing `unverifiable_reason: str | None` field alongside
the pre-existing missing-key-column reasons, using the same reasons-list-
and-join pattern the former DCP code used. `LookupMismatchReport` carries no
`Finding`/severity/`rule_type` of its own (composite/primitive contract);
`evaluate_lookup_mismatches` never raises for a data-shaped mismatch --
only DCP's own `fail_on_mismatch` orchestration boundary
(`apply_derived_column_policy`) does.

== 4. Values-mode behavior preserved exactly

Canonical lookup-map construction and scalar comparison are unchanged in
substance: normalized value tuples keyed by the lookup-side key column(s),
compared against the payload keyed by the payload-side key column(s) (the
symmetric/asymmetric key-name distinction Slice 1 already resolves). The one
change is structural, not semantic: `_canonical_value_map` no longer needs
its former "first occurrence wins" branch (`if key in canonical: continue`)
because duplicate lookup keys are now rejected *before* the canonical map is
ever built (<<sec7>>), so every key reaching the map is provably unique.
Message wording for `missing_lookup_frame` and `derived_value_mismatch` is
preserved verbatim at the DCP call site; the `unverifiable_enrich_lookup`
missing-key-column reason text no longer repeats the frame name inline
(Lookup's evaluator does not receive `frame_name`; DCP's own message still
names the frame via the unchanged `_meta.derived...` provenance-path
suffix). No existing test pins the exact former wording of that reason
fragment (confirmed by grep against
`tests/unit/domain/transformations/test_derived_column_policy.py`); the
`unverifiable_enrich_lookup` `rule_type` and the presence of the missing key
name inside the message are both still asserted and still pass.

== 5. Formula-mode correction (single key) [[sec5]]

Per-cell dispatch (`isinstance(cell, LookupFormulaSpec)`), reached only when
the interpreted provenance is single-key (`len(payload_keys) == len(lookup_keys) == 1`,
<<sec6>>): the cell's own
`(lookup_sheet, source_key_column, lookup_key_column, lookup_value_column)`
tuple is compared against the expected
`(interpreted.lookup_name, payload_keys[0], lookup_keys[0], helper_col)`
tuple. Equal -> no finding. Unequal -> a `derived_formula_mismatch` finding
(new `rule_type`, severity from `policy`, distinct from
`derived_value_mismatch`). `LookupFormulaSpec.missing` is deliberately
excluded from the comparison, per F-CORR-3's binding disposition -- not
inferred, not added to provenance. A plain scalar cell (including a formula
cell manually overwritten with a literal value) is compared via the
unchanged values-mode path on that row alone; dispatch is per-cell, not
per-column, so a mixed column is evaluated correctly with no cross-row
leakage (verified by
`test_formula_helper_mixed_scalar_and_formula_rows_evaluated_per_cell`).

An unresolved payload row (its join-key value has no match in the current
lookup frame) is skipped for both the scalar and the formula path, matching
the existing, deliberately preserved "unresolved reference is a separate
concern" behavior (Section 6.2 of the design) -- extended uniformly rather
than left scalar-only, since nothing in the design or its test plan
distinguishes the two for this case and doing otherwise would have required
inventing a new, undesigned asymmetry.

== 6. Multi-key formula-mode carve-out (F-CORR-2) [[sec6]]

Binding correction, implemented exactly as specified. Before any per-cell
formula comparison, `evaluate_lookup_mismatches` computes
`multi_key = len(payload_keys) != 1 or len(lookup_keys) != 1` from the
already-resolved `InterpretedEnrichLookupProvenance` (which -- confirmed
directly, matching the correction-closure review's own independent
confirmation -- already carries the full, untruncated key tuple; no
Lookup-side provenance change was needed to make this guard computable).
When `multi_key` is true and at least one in-scope helper column holds a
`LookupFormulaSpec` anywhere in the payload, the *entire call* returns
`unverifiable_reason` (never `derived_formula_mismatch`, never zero
findings, never an index-`[0]`-only structural comparison that could
certify a broken multi-key formula as correct). The reason string states,
in substance, that `LookupFormulaSpec` is a single-key representation and
cannot structurally verify the declared multi-key relationship. DCP maps
this to the existing `unverifiable_enrich_lookup` `rule_type` -- no new
vocabulary for this case, per the design.

The underlying `_build_formula_enrichment` `[0]`-only truncation
(`enrich_lookup/operation.py`) is **untouched**: multi-key formula-mode
`enrich_lookup` remains exactly as functionally broken as before this
slice. This slice only stops the mismatch evaluator from *certifying* that
brokenness as structurally correct.

== 7. Duplicate lookup keys corrected; shared predicate location [[sec7]]

Reviewed, intentional behavior correction, replacing DCP's former unowned
"first occurrence wins" tie-break. `evaluate_lookup_mismatches` checks
duplicate lookup keys on the *current* lookup frame -- after the
missing-key-column check, before canonical-map construction -- via a new
private, non-raising predicate:

[source,python]
----
# enrich_lookup/policy.py
def _lookup_frame_has_duplicate_keys(lookup_df: pd.DataFrame, join_keys: list[str]) -> bool:
    return bool(lookup_df.duplicated(subset=join_keys, keep=False).any())
----

`operation.py`'s existing raising `_check_duplicate_lookup_keys` now calls
this same predicate instead of its own inline boolean expression -- one
source of truth for "does this lookup frame currently have duplicate keys,"
consumed by both the enrichment-time raising check and the
mismatch-evaluation-time non-raising check, exactly per the accepted
shared-primitive design. The predicate is private, not exported through
`enrich_lookup/__init__.py`'s `__all__`; `mismatch.py` imports it directly
from `.policy` (same-family private import, the codebase's established
idiom, unaffected by the architecture guard, which only blocks
*cross-family* imports).

When duplicate lookup keys are found, the whole call returns
`unverifiable_reason` naming the lookup frame and the duplicated key
columns; DCP maps this to the existing `unverifiable_enrich_lookup`
`rule_type` -- a warning under `warn_on_mismatch`, a raise (at the DCP
orchestration boundary) under `fail_on_mismatch`.

== 14. Intentional behavior changes (explicit, complete list)

. Formula-mode helper mismatch checking now compares
  `LookupFormulaSpec`-declared structural identity instead of
  `str(LookupFormulaSpec)` against a plain scalar. A structurally-correct
  formula cell now produces no finding (previously always a spurious
  `derived_value_mismatch`/unconditional raise); a structurally-incorrect
  one now produces `derived_formula_mismatch` (new `rule_type`).
. A multi-key symmetric `enrich_lookup` combined with a formula-mode helper
  cell is now `unverifiable_enrich_lookup` rather than silently unchecked
  (it was never checked correctly before -- the former defective scalar
  comparison happened to fail closed by accident for this combination too).
. Duplicate lookup keys on the current lookup frame at mismatch-check time
  are now `unverifiable_enrich_lookup` (warn: finding; fail: raise) instead
  of DCP's former silent "first occurrence wins" certification.

No other behavior changed. Values-mode comparison semantics, all existing
`rule_type`/severity/message wording for every previously-passing path
(other than the two named corrections' own new/adjusted wording), the
`fail_on_mismatch` raise/collect boundary, and the publication-lifecycle
contract are all unchanged and confirmed by the unmodified assertions in
<<sec13>>'s test run.
