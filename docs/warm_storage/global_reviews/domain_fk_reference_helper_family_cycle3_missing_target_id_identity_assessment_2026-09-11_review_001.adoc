== 1. Target-ID boundary meaning (VERIFIED)

`check_duplicate_ids` (`fk_helpers.py:247-278`) is a generic per-sheet
uniqueness check, not an FK-helper-specific validation:

* It selects each sheet's id column from `_target_id_fields(frames)` -- the
  declared v2 relation / provenance `target_key` for a sheet that is an FK
  target (`fk_helpers.py:473-496`) -- and otherwise falls back to
  `defaults['id_field']` (default `"id"`) (`:258-264`). Confirmed.
* It is explicitly policy-independent: `test_check_duplicate_ids_remains_policy_independent`
  passes on a workbook with no FK relations. Its maintained finding meaning is a
  `duplicate_id` for a sheet with repeated values in the selected id column
  (`:269-276`). Confirmed.
* Current accepted authority does *not* define Missing target IDs as invalid
  identity, ignored/non-identity rows, or legitimate duplicate identity. The
  scalar model performs *carrier recognition* only (`is_missing_carrier` is
  documented as "recognition, not representation", `scalar_values.py:204-238`);
  the C3-S1 assessment and its accepted review both record the Missing
  target-ID disposition as UNDECIDED.

The assessment neither overstates nor understates an owner of target identity
semantics. In particular it correctly does *not* claim that
`check_duplicate_ids`, the v2 relation policy, or the FK target-map/id-set
construction establishes a Missing-target-ID disposition; each merely omits or
counts, it does not decide.

== 2. Missing-carrier authority (VERIFIED)

The accepted Cycle-3 scalar contract (C3-S0 assessment "Authoritative value
contracts"; C3-S0 Review 001 §"Missing contract"; `internal_value_model.adoc`;
`is_missing_carrier` source + docstring) accepts as Missing carriers exactly
`None`, `""`, float/NumPy NaN, `pd.NA`, and `NaT`
(and `numpy.datetime64('NaT')`), and classifies literal String `"nan"` as an
ordinary String. Empirically confirmed (project `.venv`, pandas 3.0.2):

[cols="2,1",options="header"]
|===
| value | is_missing_carrier

| `None`, `""`, `float('nan')`, `numpy.nan`, `pd.NA`, `pd.NaT` | `True`
| `"nan"` (literal String) | `False`
| `"  "` (whitespace String), `"x"` | `False`
|===

Literal `"nan"` being an ordinary String is *accepted authority*, not merely
current behavior: it is stated in the accepted C3-S0 assessment and upheld in
its accepted Review 001, and is the exact, tested behavior of the shared
predicate. This point -- critical to C3-S2 -- holds.

== 4. `"nan"` guard semantics (VERIFIED -- classification B, no accepted purpose)

The guard `str(idx) != "nan"` (`fk_helpers.py:269`) is the core falsification
target. Result: *classification B* -- vestigial for Missing carriers, live only
for the ordinary literal String `"nan"`.

* Missing carriers never render `"nan"` under `astype("string")` (they render
  `<NA>` / `''`), so the guard cannot and does not exclude Missing values
  (probe, §3). It fires only for exact literal `"nan"`.
* History (point 9): the guard was introduced at module creation in
  `fd8afa97` (`FTR-FK-HELPER-REFACTOR-P3B: domain validation layer for FK
  helpers`), already with `astype("string")` + `value_counts(dropna=False)`.
  Its apparent intent was to suppress a NaN-rendered id from duplicate
  reporting -- an anti-Missing guard -- but under the nullable `"string"` dtype
  that suppression never functioned for real Missing carriers. This is
  *historical implementation rationale*, not accepted DMC authority for a
  Missing-target-ID policy: `FTR-FK-HELPER-REFACTOR-P3B` was a validation-layer
  refactor, not a semantic decision that Missing IDs are ignored. It therefore
  does not authorize treating Missing target IDs as non-identity.
* No *other* accepted purpose was found (source/tests/docs/history): no test
  depends on the suppression; no doc contract assigns it meaning; the C3-S0/S1
  authority describes it as effectively vestigial and already flags that it
  currently reports Missing target IDs as duplicates.

Removing the guard is therefore a *bug correction restoring ordinary-String
semantics* (literal `"nan"` is an ordinary String; `duplicate_id` means
repeated ID values), not a semantic change to Missing handling and not reliant
on "looks dead" as authority -- the independent ordinary-String authority (§2)
and the maintained `duplicate_id` meaning carry it. It remains a user-visible
output change (see §8, release-notes checkpoint).

== 5. Primary-key ownership (VERIFIED)

`domain.validations.reference_validations` owns a non-empty primary-key
invariant *only when explicitly configured*:

* `_validate_primary_key` runs only for a caller-supplied `type: "primary_key"`
  rule (`reference_validations.py:135-136`), reports every empty key with
  `"Primary key values must be present and non-empty."`
  (`:188-200`), then checks uniqueness only over complete rows
  (`complete_frame`, `:202-215`).
* `_validate_foreign_key` excludes empty keys from the target key set
  (`:273-277`).
* Rules originate solely from the caller's `rules=[...]` list
  (`_validate_rules`, `:109-143`). FK v2 relation policy does *not* implicitly
  instantiate or delegate a `primary_key` rule, and `validate_fk_helpers`
  (`fk_helpers.py:281-308`) composes only the `check_*` functions -- it never
  calls `validate_references`.
* `validate_fk_helpers` does *not* enforce a universal non-Missing target-ID
  invariant.

Therefore *no current accepted boundary owns an unconditional "every FK-helper
target ID must be usable/non-Missing" invariant*. The assessment's claim is
correct; `check_duplicate_ids` must not silently acquire that ownership, and
C3-S2 does not give it that ownership.
