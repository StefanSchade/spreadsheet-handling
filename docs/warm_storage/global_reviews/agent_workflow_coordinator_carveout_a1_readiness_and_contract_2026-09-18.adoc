== 1. Determination

A1 is ready to remain *one bounded implementation slice*. Its three schema
additions and admission checks close one trust boundary: consumer policy must
dominate the repository-backed authority accepted for a single WorkItem Run.
There is no independent second boundary that would make a split safer. Schema,
operator, focused test, neutral-fixture, and current consumer-YAML changes are
several files but one reviewable invariant.

The minimum A1 model change is RepositoryPolicy schema version 2 with three new
required fields:

[source,yaml]
----
schema_version: 2
policy_id: core-example
revision: r2
scope: [core]
governance_paths:
  - docs/ai_info
  - scripts/workflow_coordinator/resources/agent_operating_contract_v1.txt
work_item_scope_ceiling:
  - src/spreadsheet_handling/example.py
max_autonomous_hops: 4
actions: [edit, commit, review]
evidence_states: [diff_hygiene, git_version]
----

The existing `scope` remains a repository-identity vocabulary: current
`new_run()` checks `WorkItem.repository in RepositoryPolicy.scope`. It is not a
filesystem scope. `work_item_scope_ceiling` is the consumer-authorized mutation
ceiling. `governance_paths` is the protected authority area. These three
concepts remain distinct even though the latter two use the same normalized
repository-relative path syntax.

No A2 field is added. A1 establishes a truthful v2 baseline; A2 may later add a
strictly additive, optional-to-parse declaration under v2 if its own contract
can make use conditional and fail-closed. If A2 instead changes required policy
shape for every policy, A2 must use v3. A1 reserves no empty mapping, generic
extension bag, command field, or compatibility machinery.

== 2. Current repository truth

=== 2.1 Current authority ingress

The supported entry point is `operator.main()`. `_preflight()`:

. observes repository identity, pinned HEAD, cleanliness, submodules, and
  state-root absence;
. normalizes the five supplied input paths;
. reads those paths at `expected_head` with `_pinned_text()`;
. parses WorkItem, WorkflowProfile, RepositoryPolicy, and the components
  manifest;
. selects component IDs from every profile phase and pins each selected
  component source;
. checks phase actions against policy actions, phase scope against WorkItem
  scope, selected evidence names, durable-artifact paths, and the five-Hop hard
  product limit; and
. returns admission facts to `main()`.

Only after `_preflight()` returns does `main()` allocate a Run ID, call
`new_run()`, create `state_root`, write `operator-plan.json`, register the
checkout, and enter the serial driver/provider-capable path. This is already the
correct A1 refusal boundary.

The current lexical containment helper is `_within_scope(path, scope)`:
equality or a `/`-delimited descendant. Current path normalization is split
across four helpers with different vocabularies. `operator._relative_path()`,
`serialization._repository_path()`, and the component-manifest check all accept
`.`, and none rejects glob metacharacters; the latter two also accept
surrounding whitespace. `git_facts._normalized_path(allow_root=True)` accepts
`.` as *the whole repository* for trusted-commit authorized scope. A1 does not
consolidate these layers. It adds one pure A1 path-shape predicate for the A1
operands only (section 3.1) and retains `_within_scope()` as the single
containment relation.

== 3. Normative governance-path semantics

=== 3.1 Representation and normalization

`RepositoryPolicy.governance_paths` is a required, non-empty YAML list of
strings. Each string is one glob-free repository-relative lexical path.

A1 defines one *pure A1 path-shape predicate*. It applies to exactly these A1
operands:

* the path entries of the new RepositoryPolicy fields `governance_paths` and
  `work_item_scope_ceiling`;
* `WorkItem.scope` entries as they participate in A1 admission;
* phase `authorized_scope` entries as they participate in A1 admission;
* the five supplied governing-input paths; and
* selected component paths.

Each existing layer retains its own exception class (`ValidationError` in
serialization, `OperatorPreflightError` in the operator) and its established
diagnostic vocabulary; the predicate supplies the decision, not a shared
exception or message. `git_facts._normalized_path`, CommitIntent path
validation, and all trusted-commit/Hop-observation path semantics are excluded
from A1 and remain unchanged. Unselected manifest entries, durable-artifact path
validation, and other path layers are not refactored by A1.

A path satisfying the predicate:

* is a non-empty string equal to its stripped spelling;
* uses `/`, never `\`;
* is not absolute;
* has no empty, `.`, or `..` segment;
* is exactly equal to `PurePosixPath(value).as_posix()`;
* has no trailing or repeated slash; and
* contains none of the glob metacharacters `*`, `?`, `[`, or `]`; and
* is not `.`.

The repository root has no spelling in this contract. Empty string, `/`, and
`.` reject.

This is a *deliberate A1 tightening*, not a preservation of current behavior.
Current normalization does not reject `.` (section 2.1). A1 makes `.` reject for
governance paths, WorkItem ceiling entries, WorkItem scope, and phase
`authorized_scope`; glob metacharacters and surrounding whitespace reject
wherever the A1 predicate applies. The `.` rejection is required: `git_facts`
treats an authorized scope of `.` as the whole repository for trusted commit,
while `_within_scope` treats `.` lexically, so `within(".", g)` and
`within(g, ".")` are both false for every governance path `g`. Admitting `.`
would let a whole-repository mutation scope bypass the governance-overlap
invariant. Rejecting root for governance paths also prevents an accidental
policy value from converting every mutation path into a governance overlap.

Paths are lexical: files and directories are both allowed, and a governance
path need not exist at admission. Non-existence is required for A1 to reserve
the future A3 location. Actual selected governing inputs continue to be required
tracked files at the pinned HEAD by `_pinned_text()`.

Exact duplicates reject. Two distinct governance paths also reject when either
is equal to, an ancestor of, or a descendant of the other; redundant overlapping
roots add no authority and otherwise create multiple spellings of the same
boundary. Ordering does not affect meaning or diagnostics. Diagnostics shall
sort reported paths where source order is not semantically relevant.

=== 3.2 Containment and overlap

Define `within(path, root)` by the existing `_within_scope` relation:

----
path == root OR path starts with root + "/"
----

A selected governing input is admitted only when
`within(input_path, governance_path)` is true for at least one declared
governance path. A file may equal its governance path. Multiple selected files
may be contained by one governance directory.

Overlap is symmetric. For every phase-scope entry `p` and governance path `g`,
overlap is:

----
within(p, g) OR within(g, p)
----

Therefore all three cases reject:

* equality (`p == g`);
* `p` is an ancestor/wider scope containing `g`; and
* `p` is a descendant/narrower scope inside `g`.

Sibling paths do not overlap. An empty read-only phase scope has no overlap.
No filesystem resolution, symlink traversal, glob expansion, scope lattice, or
cross-repository comparison is introduced.

If governance paths overlap one another, policy deserialization rejects. If a
selected governing input lies outside every path, admission rejects. If any
phase scope overlaps any governance path in either direction, admission rejects
the whole WorkItem before Run creation. There is no warning/fallback mode.

== 4. Policy domination

=== 4.1 WorkItem path-scope ceiling

`RepositoryPolicy.work_item_scope_ceiling` is a required, non-empty list using
the same normalized path syntax. Exact duplicates and redundant ancestor/
descendant entries shall reject for a canonical policy, using the same overlap
primitive as governance-path validation.

Every normalized `WorkItem.scope` entry must be equal to or descend from at
least one ceiling entry:

----
forall w in WorkItem.scope:
    exists c in RepositoryPolicy.work_item_scope_ceiling:
        within(w, c)
----

Equality is allowed. A narrower WorkItem is allowed. A sibling, ancestor/wider
WorkItem entry, absolute/ambiguous path, or path outside all ceiling entries
rejects. The existing rule remains independently enforced for every phase:

----
Phase.authorized_scope subset-of WorkItem.scope
----

The policy ceiling does not substitute for phase-to-WorkItem domination and is
not compared with repository identity `scope`. WorkItem scope is allowed to be
empty for a fully read-only profile; the required policy ceiling remains an
explicit consumer authority boundary.

Positive example:

----
policy ceiling: [src/spreadsheet_handling]
WorkItem scope:  [src/spreadsheet_handling/io_backends/router.py]
phase scope:     [src/spreadsheet_handling/io_backends/router.py]
----

Exact-boundary positive:

----
policy ceiling: [docs/warm_storage/review.adoc]
WorkItem scope:  [docs/warm_storage/review.adoc]
----

Deterministic negatives:

----
policy ceiling: [src/spreadsheet_handling/io_backends]
WorkItem scope:  [tests/unit/example.py]                    # outside
WorkItem scope:  [src/spreadsheet_handling]                 # ancestor/wider
----

=== 4.2 Autonomous-Hop ceiling

`RepositoryPolicy.max_autonomous_hops` is a required integer. Booleans reject.
The valid A1 range is `1..COORDINATOR_HARD_MAX_AUTONOMOUS_HOPS`, currently 5, the
independent Coordinator hard product ceiling. There is no absent/default value.

A1 introduces one named Coordinator constant,
`COORDINATOR_HARD_MAX_AUTONOMOUS_HOPS = 5` in `model.py`, used by
RepositoryPolicy Hop-limit validation, `_preflight()`, and `run_serial_hops()`,
replacing the current literal `5` checks. No other budgeting change is made.

Admission requires both checks, independently:

----
WorkItem.max_autonomous_hops <= RepositoryPolicy.max_autonomous_hops
WorkItem.max_autonomous_hops <= COORDINATOR_HARD_MAX_AUTONOMOUS_HOPS  # current 5
----

Policy serialization also rejects a policy ceiling above the current hard
product ceiling. Equality is allowed. Raising the product constant later does
not require a schema-shape redesign; it requires its own authorized product
decision and tests. A1 neither removes nor weakens the current direct hard-limit
guard in `_preflight()` and `run_serial_hops()`.

Negative cases are non-integer/boolean, 0, negative, above 5, a missing field,
and a valid policy value smaller than the WorkItem request.

== 5. Schema version and compatibility

A1 is a breaking RepositoryPolicy shape change because its three authority
fields are required and absent values cannot be inferred safely. RepositoryPolicy
therefore moves from `schema_version: 1` to `schema_version: 2`. WorkItem,
WorkflowProfile, components-manifest, routing-result, Run, and dispatch schemas
remain version 1.

The current shared `_version()` accepts only 1 for every document. Implementation
shall make RepositoryPolicy version validation document-specific instead of
loosening every schema. The v2 parser accepts exactly the v2 required fields and
continues rejecting unknown fields and duplicate YAML keys.

RepositoryPolicy v1 is rejected with an explicit unsupported/migration-required
diagnostic. It is not upgraded in memory, supplied defaults, or accepted through
a compatibility branch. Migration tooling is unnecessary: there are only the
two real committed policies, the one aggregate neutral fixture, and bounded unit
fixtures, all in one repository and all can change atomically in the later A1
implementation commit.

No empty A2 command container is reserved. `evidence_states` retains its current
name and semantics. A2 must explicitly state whether its new field is additive
under v2 or requires v3; it must not reinterpret the A1 fields or silently
accept v1. This is coordinated evolution without pre-implementing A2.

== 7. A1 precedes A2

A2 will later allow consumer policy to define trusted evidence argv. The policy
file would then be executable-authority input: trusted origin of a host process
definition, though neither execution nor outcome is inherently trusted. A1 must
first ensure the selected policy lies within a governance path declared by the
admitted policy and that no phase mutation scope is equal to, above, or below
that path. Otherwise a Hop of a Run admitted under that policy could modify the
admitted policy or its governance area and thereby change a later Run's trusted
argv.

The guarantee is relative to the governance paths declared by the admitted
policy. It does not prevent a Run admitted under a different policy, with
different declared governance paths, from mutating another bundle, and it does
not prevent a Hop from authoring a new bundle inside its own mutation scope
whose policy self-declares governance. Such cross-bundle or new-bundle authority
takes effect only through external launch authorization and remains outside A1
(plan 6.2/6.3). Protection of every current core bundle relies on the consumer
convention that both core policies declare `docs/ai_info`; the consumer
integration test asserts that convention.

This dependency does not implement commands, subprocess execution, timeouts,
environment policy, or evidence semantics. It only orders the trust boundaries:

----
A1 protected policy authority -> A2 trusted command definitions
----

=== 8.1 Pure A1 admission function

The A1 cross-document relations live in one pure, I/O-free function in
`operator.py`, of the intended shape:

----
_admit_a1(work_item, profile, policy, governing_paths) -> None
----

`work_item`, `profile`, and `policy` are already parsed model objects;
`governing_paths` is the tuple of selected repository-backed governing-input
paths (the five supplied inputs plus selected component paths). The function
applies the A1 path-shape predicate to WorkItem-scope, phase-scope, and
governing-path operands and checks governing containment, symmetric
phase/governance exclusion, WorkItem-scope domination, and Hop domination. It
raises `OperatorPreflightError` with sorted, deterministic diagnostics and
performs no Git, filesystem, state-root, or adapter access. No new module,
class, or policy engine is introduced.

`_preflight()` calls it after component resolution and before returning.
Pinned/tracked Git reads, clean-worktree and HEAD checks, state-root absence,
and side-effect boundaries remain owned by `_preflight()` and tested by unit
tests on temporary repositories.

The integration test belongs at a focused boundary such as
`tests/integration/workflow_coordinator/test_core_consumer_governance.py`. It
reads the worktree bundle files, parses them through the supported loaders,
resolves selected components through the manifest, and calls `_admit_a1()`. It
shall not call live-repository `_preflight()`, whose clean-worktree and pinned
HEAD requirements would couple the test to repository state rather than to the
change under test, and shall not reimplement the admission rules. It may name
core-owned paths and IDs and asserts that both core policies declare
`docs/ai_info` and the A3 path; generic Coordinator production code may not gain
DMC, spreadsheet, IOR, XLSX, or ODS semantics.
