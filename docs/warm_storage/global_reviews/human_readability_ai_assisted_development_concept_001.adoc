== Status and purpose

This concept synthesizes the completed three-family Human Readability
investigation into a reusable engineering model for this project and a possible
future AI-assisted workflow. It explains what the investigations established,
what they only suggest, and how later reviews could use the evidence without
turning it into mechanical style enforcement.

The central conclusion is that software quality includes both
*macroarchitecture* and *local Human Readability*. Local Human Readability is the
bounded reconstruction of current semantics, lifecycle, ownership, constraints,
and reasons. Neither dimension subsumes the other. Good macroarchitecture can
still leave a human paying an avoidable local reconstruction cost; locally simple
code can still violate package, persistence, public-interface, or ownership
architecture.

This document is intentionally provisional. It is not a binding style guide,
creates no automated rule, authorizes no runtime refactor, and does not replace
architecture review. In particular, HR-04 and HR-08 remain comparatively
provisional. Lessons stated beyond this repository remain project-derived
hypotheses until tested elsewhere.

== Evidence base and limits

The direct evidence is the sequence of read-only review, bounded implementation,
independent acceptance, and cross-family validation recorded in:

* `docs/warm_storage/global_reviews/review_001_fk_helpers_human_readability_revalidation_001.adoc`;
* `docs/backlog/FTR-FK-HELPERS-ENRICH-READABILITY-PILOT-P5_slice2_package_assessment_001.adoc`;
* `docs/backlog/FTR-FK-HELPERS-FORMULA-PROVIDER-READABILITY-P5_slice1_review_001.adoc`;
* `docs/warm_storage/global_reviews/review_002_enrich_lookup_human_readability_second_family_validation_001.adoc`;
* `docs/warm_storage/global_reviews/review_003_xref_crosstable_human_readability_third_family_validation_001.adoc`.

The broader workflow context comes from
`docs/warm_storage/global_reviews/ai_assisted_development_practices_review.adoc`,
`docs/warm_storage/global_reviews/architecture_health_review.adoc`, the current
review workflow, and the Project Memory curation workflow. Current code,
executable contracts, accepted reviews, and corrected technical documentation
outrank historical descriptions when they disagree.

This concept uses three evidence labels:

. *Direct project evidence* — observed in FK Helpers, Enrich Lookup, or XRef
  Crosstable and supported by current code, review evidence, or accepted
  behavior.
. *Cross-family inference* — supported by comparison among the three families,
  but not tested outside this repository.
. *Broader AI-development hypothesis* — a plausible general lesson derived from
  the project, not an established fact about AI-assisted development elsewhere.

Three local families do not prove universal laws. The families are useful
because they differ: one exposed a real raw-options boundary, one had explicit
arguments and a coherent resolved policy, and one had long, validation-sensitive
operations with opaque values and cohesive descriptor mappings. They are still
one repository, one language, one maintainer context, and one development method.

== Macroarchitecture and local Human Readability

*Direct project evidence.* The reviewed families generally have healthy package
boundaries, facades, ownership, tests, and architecture guards. Yet the first
family still contained local names that overstated authority, a broad raw-options
parameter whose lifecycle was not locally visible, and an existing callback
contract that was not surfaced at its factory boundary. Macroarchitecture did not
make those reader questions disappear.

*Direct project evidence.* The inverse also occurred. A rename, type, extraction,
or copy fix could look locally attractive while crossing an accepted public,
persisted, or architecture boundary. Examples include the load-bearing
FK relation-to-`core.fk` adapter, Enrich Lookup provenance ownership, and XRef
Intent-versus-Resolution persistence. Local simplicity would not justify changing
those contracts.

*Cross-family inference.* A useful review therefore asks two independent sets of
questions:

* Is the ownership and dependency direction architecturally sound, with public,
  persisted, and lifecycle contracts respected?
* Can a maintainer reconstruct the current local behavior, state, constraints,
  and non-local reason without avoidable archaeology?

Passing one set is not evidence that the other set passes. The desired condition
is bounded reconstruction inside sound architecture, not local prettiness and not
architecture diagrams alone.

== AI and human reading asymmetry

*Direct project evidence.* The repository's AI-assisted method has used agents
effectively for inventory, reference search, caller tracing, contradiction
detection, comparison, structured drafting, and review. These activities let an
agent repeatedly traverse code, tests, metadata consumers, documentation, and
history to reconstruct distributed context. The Human Readability reviews also
showed that this reconstruction can be expensive even when it succeeds.

*Broader AI-development hypothesis.* An AI agent may tolerate technically
recoverable but unnecessarily non-local code better than a human because it can
cheaply repeat search and traversal. The same capability may let it generate or
accept code that preserves macrostructure while accumulating idiosyncratic names,
broad bags, weak lifecycle distinctions, or explanatory gaps. Recoverability is
not the same as humane local cost.

*Direct project evidence.* Humans benefited from truthful cues such as
`target_lookup_index` versus authoritative relations, raw versus resolved option
names, `_ResolvedKeys`, `dense_config` versus `dense_resolved`, an existing
`HelperValueProvider` annotation, and comments explaining replay safety or
validation precedence. These cues reduced the number of caller, consumer, or
history questions required to understand the code.

*Broader AI-development hypothesis.* Truthful local cues also improve AI
reliability by constraining reconstruction, but the larger marginal benefit may
belong to human maintainers who cannot afford repeated repository-wide traversal
for every edit. The target is reliability for both, with special protection
against avoidable human cost; it is neither humans-only nor AI-only readability.

*Direct project evidence.* AI-assisted cleanup can overcorrect. The three-family
reviews rejected scalar explosions, excessive extraction, ceremonial types,
comments for ordinary empty paths, and language-foreign expansion of
comprehensions, tuple unpacking, closures, mappings, and pandas idioms.

*Broader AI-development hypothesis.* Without counterexamples and contract gates,
an AI reviewer may optimize the most measurable proxy — parameter count, function
length, type coverage, import spelling, or explicit branch count — and create
Java-shaped Python whose local ceremony is more costly than the original code.

== Readability as trade-off judgment

Human Readability is not a one-dimensional optimization. Each of the following
axes has two legitimate concerns; the decision turns on which side imposes the
larger reader cost in the current boundary.

[cols="2,3,3", options="header"]
|===
| Trade-off | Legitimate pressure on one side | Legitimate pressure on the other side and current larger-cost test

| Narrow dependencies versus coherent domain values
| Broad frames or metadata bags are costly when a helper consumes one already
resolved value; FK mode normalization and Enrich Lookup's repeated metadata walk
show that cost.
| Atomizing a coherent lookup policy or XRef dense-axis descriptor into many
scalars can hide identity and invariants. Prefer the smallest *coherent owned
concept*. The larger cost is whichever choice makes the reader reconstruct either
unused context or a concept scattered across parameters.

| Small functions versus algorithmic locality
| Extraction helps when a block owns an unrelated responsibility or a genuinely
shared contract.
| XRef's 516-line operation and 411-line dense-axis owner keep validation-sensitive
sequence and ownership locally auditable. Scattering that sequence can be worse
than length. The larger cost is unrelated responsibility in one place versus a
reader having to jump among helpers to recover phase order and error precedence.

| Strong typing versus truthful heterogeneous boundaries
| Stable owned lifecycle states benefit from types: `_ResolvedKeys`, concrete
`FKDef` lists, callback aliases, and resolved XRef identities.
| Pandas cells, persisted mappings, carrier payloads, and intentionally opaque
XRef values may truthfully require `Any` or heterogeneous mappings. The larger
cost is repeated interpretation of a stable shape versus a ceremonial or false
type imposed on an unsettled boundary.

| Vocabulary purity versus boundary truth
| Calling a domain frame a sheet misleads when no workbook or persisted namespace
is involved.
| `lookup_sheet`, workbook targets, and `_meta.derived.sheets` legitimately name
sheet concepts. The larger cost is layer confusion versus erasing the actual
workbook or persisted contract in pursuit of vocabulary uniformity.

| Explicitness versus idiomatic language
| Hidden lifecycle changes, broad bags, surprising skips, and non-local ordering
reasons deserve explicit names, boundaries, or explanations.
| Comprehensions, tuple unpacking, closures, mappings, conditional expressions,
and pandas idioms are normal Python. The larger cost is hidden meaning versus
procedural ceremony that obscures a compact, conventional operation.

| Reuse versus local explainability
| A real shared contract, such as tabular validation or the provider callback,
should be reused and guarded.
| Extraction or indirection can hide local XRef validation order, error precedence,
or family-specific semantics. The larger cost is duplicated contract logic versus
the navigation and reconstruction burden introduced by reuse.

| Minimal APIs versus visible contracts
| Every public parameter and exported symbol carries compatibility and maintenance
cost.
| An over-compressed signature or generic option bag can hide real inputs,
lifecycle, defaults, and constraints. The larger cost is unnecessary surface area
versus implementation archaeology required to discover the contract.
|===

No metric resolves these pairs by itself. The reviewer must name the reader
question before the change, the reader question after the change, and the
contract cost of moving between them.

== Lessons from the three domain families

[cols="1,4,3", options="header"]
|===
| Family | Direct project evidence | How it changed the emerging model

| FK Helpers
| A real broad raw-options bag justified making the raw/resolved split locally
visible. The local `target_registry` name overstated an execution lookup index.
The accepted formula-provider slice surfaced the existing callback type rather
than redesigning the interface and used truthful private factory/callback
argument names. Some historical internals, including
`build_v2_target_registry`, were consciously deferred; its adapter remained
load-bearing. The remaining residue did not justify another cycle.
| Established concrete gains from narrow inputs, lifecycle names, existing
contracts, and precise local vocabulary, while already warning against adapter
removal, blanket sheet renames, and Java-shaped expansion.

| Enrich Lookup
| There was no comparable authored options bag. One resolved coherent policy was
narrower than all frames, but scalarization was not an improvement.
`_ResolvedKeys` was a positive lifecycle/type boundary. Real workbook and
persisted sheet vocabulary stayed. Its local import rule differed from FK's but
was coherent. A nested provenance mutation was important, but belonged to
architecture/lifecycle authority. `Stop here` was correct.
| Narrowed HR-01, HR-05, HR-07, HR-09, and HR-11: use the coherent value, do not
manufacture configuration, respect heterogeneous/boundary terms, and judge import
consistency locally. A readability review can succeed without implementation.

| XRef Crosstable
| The 516-line operation remained locally reconstructable; the 411-line dense-axis
owner was cohesive. Size did not justify extraction. Validation order was
contract-bearing and documented. Authored intent and transient Resolution were
distinct. Cohesive mappings were domain descriptors. Empty, sparse, and dense
paths were ordinary semantics. `Any` was legitimate at opaque/heterogeneous
boundaries. The only local package problem was a stale docstring; the more serious
error was reversed directions in the technical model, not runtime code.
`expand_xref` is matrix to relation; `contract_xref` is relation to matrix. After
documentation correction, `Stop here` remained correct.
| Further narrowed the first-family conclusions: function length, mapping width,
`Any`, empty paths, and explicit comments are contextual. It established that a
technical model can impose a higher reader cost than healthy runtime code.
|===

*Cross-family inference.* The second and third families validate the review
method more strongly than they validate any particular FK implementation shape.
The durable method is to identify concrete reconstruction cost, compare it with
contract and locality costs, preserve positive structures, and permit no change.

== Provisional Human Readability principles

The following principles synthesize HR-01 through HR-13. They are provisional
review aids, not copied rule matrices and not deterministic enforcement policy.
Most belong in human checklists and AI reviewer prompts because they require
boundary and counterexample judgment.

[cols="1,2,2,2,2,1,2", options="header"]
|===
| ID | Principle | Reviewer question | Project evidence | Counterexample or misuse risk | Confidence | Suitable use

| HR-01
| Pass the smallest coherent owned dependency.
| Does the callee receive unused context, or would further narrowing atomize one
real policy or descriptor?
| FK mode normalization needed one value; Enrich Lookup benefited from the
resolved policy rather than all frames; XRef dense descriptors remained cohesive.
| Maximum scalarization can create parameter explosions and hide invariants.
| established across three families
| human review checklist; AI reviewer prompt

| HR-02
| Names and descriptions should state current semantics and authority.
| What would a reader incorrectly infer about role, state, direction, or
authority from this name?
| FK's local execution index was not a registry; XRef's stale technical model
reversed public directions while runtime names were correct.
| Renaming public, persisted, compatibility, or genuine workbook vocabulary can
create churn or make boundary truth worse.
| established across three families
| human review checklist; AI reviewer prompt

| HR-03
| Name or type materially distinct lifecycle states where they are real.
| Can the reader distinguish authored, raw, resolved, validated, persisted,
replayed, derived, and rendered states that matter here?
| FK raw/resolved options, Enrich Lookup `_ResolvedKeys`, and XRef Intent versus
Resolution are three different positive forms.
| A universal state wrapper or suffix taxonomy can add ceremony where no
transition exists.
| established across three families
| human review checklist; AI reviewer prompt

| HR-04
| Let signatures expose real inputs without falsifying heterogeneous boundaries.
| Can supported inputs and dependencies be learned from the signature, and is a
mapping or `Any` boundary genuinely part of the contract?
| FK surfaced an existing callback type; Enrich Lookup used explicit authored
arguments; XRef retained cohesive mappings and opaque cells.
| Mandating dataclasses, scalar parameters, or total typing can duplicate an
unsettled persisted model or lie about pandas/cell values.
| provisional
| human review checklist; AI reviewer prompt

| HR-05
| Resolve each genuine authored configuration or policy once per relevant phase.
| Is there a real resolution boundary, and do later consumers use the same
resolved snapshot?
| FK had a real options bag; Enrich Lookup had a coherent policy but no bag;
XRef separated authored dense intent from run-local domains.
| Manufacturing a config object where arguments are already explicit increases
indirection and invents lifecycle.
| established but boundary-sensitive
| human review checklist; AI reviewer prompt

| HR-06
| Comments should explain non-local reason, ownership, ordering, compatibility,
or side-effect boundaries.
| What wrong edit becomes plausible if this reason is absent?
| FK replay safety, Enrich Lookup collision/key-mode reasoning, and XRef
validation precedence all needed non-local explanations.
| Narrating syntax or every branch produces noise that hides contract-bearing
comments.
| established across three families
| human review checklist; AI reviewer prompt

| HR-07
| Use layer vocabulary locally while preserving truthful public, workbook,
carrier, and persisted terms.
| Does this term describe the object at this layer or a real boundary it crosses?
| FK frame-local renames helped while `lookup_sheet` stayed; Enrich Lookup and
XRef preserved registered/persisted vocabulary.
| A blanket `sheet` ban would corrupt genuine workbook and
`_meta.derived.sheets` meaning.
| established but boundary-sensitive
| human review checklist; AI reviewer prompt; automated static guard for forbidden dependency directions only

| HR-08
| Keep version, legacy, and slice labels only when they communicate an active
operational, compatibility, or historical distinction.
| What current distinction does the label protect, and who relies on it?
| FK private `v2` names carried residue while `schema_version: 2` remained
operational; XRef historical wording was acceptable only when accurate.
| Removing labels because they look old can erase active compatibility; keeping
them everywhere can make migration history masquerade as the domain model.
| provisional
| human review checklist; AI reviewer prompt

| HR-09
| Type stable states owned by the code; keep heterogeneous boundaries honest.
| Is this `Any` hiding a known stable value, or representing an opaque or
unsettled boundary?
| Concrete FK work items and Enrich Lookup keys could be typed; XRef cells,
pandas objects, and persisted mappings remained legitimately heterogeneous.
| An `Any` ban or premature domain model can add casts, duplicate schemas, and
false certainty.
| established but boundary-sensitive
| human review checklist; AI reviewer prompt

| HR-10
| Explain exceptional no-ops and skips; leave ordinary empty outcomes ordinary.
| Could this path conceal invalid input or loss, or is it a normal part of the
domain semantics?
| FK replay/header skips required reasons; Enrich Lookup empty selections and
XRef empty/sparse/dense outcomes did not require ceremony.
| Commenting every empty path makes genuine exceptional handling harder to see.
| established but boundary-sensitive
| human review checklist; AI reviewer prompt

| HR-11
| Keep imports locally coherent and make architectural boundaries visible.
| Can a reader infer package-local versus cross-subsystem ownership, and is the
local convention consistent?
| FK accepted one local spelling; Enrich Lookup and XRef used different but
coherent boundary rules.
| One repository-wide relative or absolute mandate confuses syntax uniformity
with architecture.
| established but boundary-sensitive
| human review checklist; AI reviewer prompt; automated static guard for forbidden dependency directions only

| HR-12
| Preserve reconstructable phases, validation order, and positive postconditions
during cleanup.
| Which reader-visible sequence or invariant would extraction, inlining, or
shortening make harder to audit?
| FK phased orchestration and flatness protection, Enrich Lookup operation/policy
phases, and XRef precedence-sensitive operations were positive structures.
| File/function length or helper-count targets can scatter an algorithm and
change error precedence.
| established across three families
| human review checklist; AI reviewer prompt

| HR-13
| Optimize for local explainability in the project's language and domain, not
maximum explicitness.
| Is the construct actually misleading, or merely unfamiliar to the reviewer?
| All three families protected comprehensions, tuple unpacking, mappings,
closures, conditional expressions, and pandas/Python idioms.
| Expanding concise Python procedurally can create ceremony and new state while
making the algorithm less visible.
| established across three families
| human review checklist; AI reviewer prompt
|===

No principle here supports a static maximum for parameter, function, or file
length; a ban on `Any` or `sheet`; a relative-import mandate; a helper-extraction
mandate; a dataclass mandate; or comments for every empty path.

== Anti-rules and counterexamples

The following are explicit anti-rules because each turns one legitimate pressure
into a universal cleanup recipe.

[cols="2,5", options="header"]
|===
| Anti-rule | Concrete counterexample and trade-off

| Always minimize APIs
| FK's generic raw-options bag compressed the visible contract; explicit resolved
inputs improved reconstruction. Minimal surface is valuable only until it hides
real authored inputs or lifecycle.

| Atomize coherent values into scalars
| Enrich Lookup's resolved policy and XRef's dense-axis descriptors are narrower
than an entire frame universe precisely because they remain coherent mappings.
Scalar expansion would scatter their invariants.

| Shorten every large function or file
| XRef's 516-line operation and 411-line dense-axis owner were cohesive and
locally reconstructable. Extraction by length would hide validation order and
increase navigation.

| Eliminate `Any`
| XRef values are intentionally opaque, and pandas/persisted boundaries are
heterogeneous. Type stable owned states; do not invent a false universal value
model.

| Replace `sheet` with `frame`
| `lookup_sheet`, workbook targets, and `_meta.derived.sheets` are truthful
boundary vocabulary. Rename only domain objects incorrectly called sheets.

| Use one import spelling repository-wide
| FK, Enrich Lookup, and XRef each had coherent local boundary rules. Dependency
direction can be guarded; relative-versus-absolute spelling requires local
judgment.

| Extract repeated-looking code
| XRef validation blocks may look similar while protecting different direction,
identity, and diagnostic precedence. Reuse only a real common contract, such as
the accepted shared tabular validators.

| Comment every empty or no-op path
| XRef empty/sparse/dense behavior and many Enrich Lookup empty selections are
ordinary semantics. Extra comments would dilute the signal from replay-safety,
loss, and lifecycle explanations.

| Introduce a configuration object
| FK had a real bag, but Enrich Lookup already had explicit arguments and XRef had
natural intent/Resolution boundaries. A new object is justified only by a real
resolution problem, not consistency pressure.

| Expand concise Python procedurally
| The accepted formula-provider closure, comprehensions, tuple unpacking,
`setdefault`, mapping operations, and pandas idioms were readable. Expansion
would create more names and state without a reader-facing gain.
|===

== Human Readability Sentinel

The *Human Readability Sentinel* is a provisional specialized AI review role,
not an autonomous refactoring agent and not an orchestration design. Its purpose
is to adopt the future-human-maintainer viewpoint: identify concrete local
reconstruction costs while preserving coherent values, algorithmic locality,
idiomatic language, and contract boundaries.

=== Inputs

The Sentinel needs the code under review; relevant callers and consumers; tests;
public and persisted contracts; architecture and Project Memory context; material
history; and the language/framework idioms used by the code. It should load only
enough distributed context to answer a concrete reader question, then return the
result as bounded evidence.

=== Required distinctions

The role must:

* distinguish an unfamiliar idiom from a misleading construct;
* distinguish a broad bag from a coherent policy or domain descriptor;
* preserve validation-sensitive locality and positive existing structure;
* recognize public, persisted, and architecture gates;
* treat findings as evidence, not automatic changes;
* explicitly permit and recommend `Stop here`;
* avoid one-dimensional cleanup;
* compare reader questions before and after a proposed change; and
* require a demonstrated reader-facing gain rather than a metric improvement.

=== Outputs and disposition

For each material item, the Sentinel should provide:

* the reader question that triggered investigation;
* direct evidence and the relevant evidence label;
* severity or priority;
* a safe local direction, if one exists;
* positive patterns that must be preserved;
* any public, persisted, lifecycle, or architecture contract gate;
* characterization requirements; and
* one disposition: `implement`, `coordinate under another authority`, `defer`,
  `accept`, or `stop here`.

It should also record positive patterns even when no finding exists. A review is
successful when it makes the reader and contract costs explicit; implementation
is not required.

=== Prohibitions

The Sentinel must not auto-refactor, optimize metrics, equate unfamiliar with
unreadable, create work from every observation, override architecture or public
contracts, replace judgment with a checklist, universalize one module or family,
or recommend a change without comparing before/after reader cost. It must not
design prompts or orchestration software as part of this concept.

=== Future tandem

In a later experiment, the Sentinel could work in tandem with:

* architecture reviewers, who own macrostructure, dependency direction, and
  contract boundaries;
* SonarQube or other static analysis, which supplies mechanical signals;
* tests and guards, which characterize behavior and executable constraints;
* implementers, who act only under explicit authorization;
* independent reviewers, who verify behavior and reader-facing gain; and
* Project Memory, which curates only durable steering conclusions rather than
  every observation.

The Sentinel complements those roles. It does not outrank or merge them.

== Findings, authorization, and disposition

The lifecycle must keep evidence, authority, implementation, acceptance, and
memory separate:

. *Observation* — something that makes a reader pause; it may be unfamiliar,
  benign, positive, or worth investigation.
. *Concrete readability finding* — evidence establishes a specific avoidable
  reconstruction cost, risk, and possible direction.
. *Contract/architecture gate* — the finding touches public, persisted,
  lifecycle, ownership, or architectural authority and is transferred to that
  owner before any change.
. *Authorized FTR/slice* — an explicit work unit defines scope, invariants,
  characterization, non-goals, and acceptance. A finding itself is never that
  authorization.
. *Implemented change* — an implementer performs only the authorized work and
  preserves named positive structures and contracts.
. *Independent acceptance* — a reviewer verifies scope, behavior, reader-facing
  gain, and residual risk without silently becoming the implementer.
. *Deferred/accepted residue* — a known item is consciously not selected because
  its value is too low, its gate belongs elsewhere, or the present structure is
  the better trade-off.
. *Project-Memory disposition* — only a durable steering lesson, material
  rejection/correction, current finding, or architecture direction is curated;
  extraction candidates and heatmaps remain evidence and attention aids.

A finding is not a task. Deferred does not mean unfinished. A review can succeed
with no implementation. An architecture finding transfers to the owning
authority rather than remaining disguised as readability cleanup. A completed
topic may retain known low-value residue without reopening the workstream.

`build_v2_target_registry` is the concrete residue example. Its historical name
and adapter role are known; the locally misleading execution variable was fixed,
while the load-bearing adapter and broader rename were consciously unselected.
That decision is memory-worthy evidence about proportionality, not an active task.

Enrich Lookup's nested provenance mutation is the contrasting gate example. It
was important, but its correct owner was the derived-provenance
architecture/lifecycle authority. The Human Readability review recorded and
transferred the issue; it did not authorize a local copy fix.

== Relationship to static analysis and guards

Static tools can contribute mechanical evidence about:

* import cycles and forbidden dependency directions;
* public surface drift;
* complexity signals;
* duplicate-code signals;
* missing type coverage;
* declared architecture contracts; and
* test, registry, metadata, or persistence invariants.

Those signals are useful inputs, not readability verdicts. They can direct the
Sentinel toward a location and can guard a decision after humans establish it.

Judgment remains necessary for an authority-overstating name; coherent versus
broad mapping; long-function locality; whether a comment supplies a non-local
reason; whether a layer term is truthful; clarity versus a ceremonial type; and
whether extraction raises or lowers reconstruction cost. Static evidence feeds
the Sentinel; it does not substitute for the Sentinel or an architecture review.

In particular, this concept creates no static rule for maximum parameter,
function, or file length; no `Any` or `sheet` ban; no mandated import spelling;
no helper-extraction or dataclass rule; and no requirement to comment every empty
path.

== Workflow implications

*Direct project evidence.* The current workflow already separates read-only
reviews from implementation, findings from authorized FTRs, implementation from
independent acceptance, and canonical Project Memory from extracted candidates.
Heatmaps are attention aids, not automatic task assignments. Those separations
are the foundation the Sentinel would use.

*Cross-family inference.* A future readability review should begin with concrete
reader questions, inventory only the necessary caller/consumer/contract context,
and record positive structures before proposing changes. It should state the
evidence class, compare before/after questions, name gates, and make `accept` or
`stop here` normal dispositions.

*Broader AI-development hypothesis.* Specialized review roles can reduce
one-dimensional AI cleanup when their authority and handoffs are explicit. The
benefit would come from disciplined perspective and evidence, not from adding
another agent stage for its own sake. This hypothesis requires a bounded project
experiment before adoption.

No workflow change follows automatically from this document. It defines neither
an agent prompt nor an orchestration implementation.

* Can static-analysis signals be routed as evidence without becoming proxy
  targets?
* How should the project observe human reconstruction cost without creating
  burdensome measurement ceremony?
* Do HR-04 and HR-08 become more reliable with additional families, or should
  they remain contextual questions only?
* Which broader AI-development hypotheses survive testing outside this
  repository, language, and maintainer workflow?

The next lifecycle steps are proposals only and are not performed or authorized
here:

. independent review of this concept;

Adoption would require evidence that the model improves review judgment without
creating a style bureaucracy or an automatic source of work.
