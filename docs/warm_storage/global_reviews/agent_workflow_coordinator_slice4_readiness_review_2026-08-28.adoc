== Verdict

*MATERIAL READINESS CORRECTION REQUIRED.*

The proposal is conceptually sound and its slice containment is clean, but the
*exact selected CLI boundary as written does not parse on the installed Codex
0.147.0* (S4-READY-R1), and three further precision gaps (S4-READY-R2..R4) plus
one Git-ownership decision-material correction (S4-READY-R5) should be closed
before the disposable proof is executed. None of these is a fundamental
architecture blocker: the Git-write ownership question is genuinely the
maintainer's Option-A/B choice and is well enough framed to decide for the
disposable proof. The proposal is therefore *not yet technically coherent enough*
to hand straight to that decision without correction, but the correction is
mechanical and the decision space is correctly drawn.

Severity-to-verdict mapping: R1 is BLOCKING for *execution of the proof command*
yet is a mechanical CLI correction, not an architecture defect; hence the
overall verdict is a material readiness correction rather than a fundamental
architecture decision.

== Findings

Severity: BLOCKING (must correct before the proof), IMPORTANT (should correct
before the proof), MINOR (improvement / clarification). Category tags:

=== S4-READY-R1 -- BLOCKING [defect] -- selected CLI boundary does not parse

The proposal's central artifact -- the one selected invocation in section 1 and
the safety keystone of section 2 -- places `--ask-for-approval never` *after* the
`exec` subcommand. On the installed 0.147.0 this is an `unexpected argument`
parse error (exit 2); the child parses its arguments and exits before any
provider contact. The section-1 factual claim that "the same help documents ...
`--ask-for-approval never`" is wrong: that flag is documented only on the
top-level `codex` command, not under `codex exec --help`. The review charter's
"do not assume undocumented behavior" is exactly the guard this trips.

Evidence:: parse probes above; `codex exec --help` option list contains no
`--ask-for-approval`; `codex --help` documents `-a, --ask-for-approval
<APPROVAL_POLICY>` with `never: Never ask for user approval. Execution failures
are immediately returned to the model (no per-call approval)`.

Risk if ignored:: the proof cannot run the selected command; the section-2 hang-
safety argument nominally rests on an invalid flag position. Under the
proposal's own Hop-accounting the parse-failing child would be *charged a Hop*
(nonzero exit after start), burning the single N=1 budget on a construction bug
and stopping `awaiting_human` -- safe but wrong, and it also demonstrates
S4-READY-R4.

Recommended action:: correct the command to one of the two forms verified above
-- move the flag to a top-level position (`codex --ask-for-approval never exec
...`) or set it via config override (`-c 'approval_policy="never"'`) -- and fix
the section-1 sentence to attribute the flag to the top-level command. The
underlying *semantics* the proposal relies on (non-interactive `exec`; approval-
requiring commands fail back to the model rather than presenting an invisible
human question) are real and documented; only the syntax and the "same help"
attribution are defective.

=== S4-READY-R2 -- IMPORTANT [defect] -- timeout/kill omits process-group termination

Section 5 requires graceful child termination, a fixed grace interval, then
kill "if necessary." Under `--sandbox workspace-write` the Codex process may
spawn descendant shell/tool processes. Killing only the direct child (the
`codex` process) can leave orphaned descendants alive past the parent deadline.
The proposal lists "child/orphan process survival" as a *distinction to make*
but does not commit to terminating the whole process group.

Risk if ignored:: the "parent never waits indefinitely" guarantee holds for the
parent but not for leaked sandbox descendants; a stalled tool subprocess can
survive the deadline. Low durable harm in a disposable repo, but it is a real
gap in the bounded-execution claim and material for any real adapter.

Recommended action:: specify that the adapter starts the child in its own
process group / session (`start_new_session=True`) and, on deadline or
cancellation, signals the whole group (graceful, grace, then `killpg`), so no
orphaned descendant outlives the reconcile. This is a small, well-scoped adapter
requirement, not an architecture change.

=== S4-READY-R3 -- IMPORTANT [defect] -- coordinator result/schema/state files should sit outside the agent-writable workspace

Section 4 states the coordinator creates `<result-schema.tmp>` and a "private
transient `<result-message.tmp>` path" and validates after completion, but it
never asserts these paths are *outside* the agent's writable scope. With
`--cd <repository>` and `workspace-write`, the entire workspace working root --
including any in-repository coordinator-state root (WFC-PERSIST-02) -- is
writable by model-issued shell commands. Crucially, `codex`'s *own* IO for
`--output-schema` (read) and `--output-last-message` (write) is performed by the
Codex parent, not the sandboxed shell, so those files do *not* need to live
inside the sandbox for the mechanism to work.

Risk if ignored:: a model-issued shell command could pre-write or overwrite the
result-message file, or write into the coordinator-state root (dispatch marker,
Run snapshot -- the trusted resume anchors of WFC-PERSIST-01/06). Post-hoc
`validated_result()` re-validation plus independent Git-fact observation
(WFC-SEC-02) and the WFC-SEC-01 "not a hostile-code sandbox" trust scope keep
this *acceptable for the disposable proof*, and the result envelope is agent-
authored by design so its writability is not a new trust escalation. But relying
only on validation-after-the-fact leaves the trust boundary as policy, not
mechanism.

Recommended action:: locate coordinator-owned schema, result, dispatch-marker,
and Run-snapshot files *outside* the `--cd` workspace (and grant no `--add-dir`),
making the boundary mechanical. This is feasible precisely because Codex's own
file IO is unaffected by the sandbox. State the placement invariant explicitly in
the proof profile.

=== S4-READY-R4 -- IMPORTANT [defect] -- Hop accounting over-charges WFC-AUTO-03 local pre-acceptance failures

The section-5 rule charges a Hop for *any* nonzero exit once the child started,
carving out only a `Popen`/executable-launch failure as "no Hop." But a started
`codex` child can fail *locally, before any provider acceptance*: argument-parse
error (exactly S4-READY-R1, exit 2), config load error, missing/expired login,
or the Git-repo check. WFC-AUTO-03 states that "local failure before
adapter/provider acceptance ... do[es] not consume Hops." Charging these
contradicts WFC-AUTO-03; in the N=1 proof it burns the sole Hop on a local
construction error.

The conservative default -- charge when non-acceptance genuinely cannot be
disproved -- remains WFC-AUTO-02-compatible (WFC-AUTO-02: "acceptance that cannot
be disproved is conservatively charged"). The over-reach is only the *blanket*
treatment of all post-start nonzero exits as accepted.

Recommended action:: (a) move predictable local failures into coordinator-side
preflight before spawn (validate the constructed command; confirm `codex login
status`; run the repo/HEAD checks) so they never reach "child started"; and
(b) define a stronger observable acceptance boundary -- e.g. a Hop is charged
once a provider/model event appears in JSONL or a valid correlated result
exists, with conservative charging retained only where that signal's absence is
genuinely indeterminate. The proposal explicitly declines to trust undocumented
JSONL event semantics for acceptance, which is defensible; preflight (a) is then
the primary lever and shrinks the conservative-overcharge window without
depending on any undocumented event. Answer to the charter question: *conservative
and contract-compatible for the uncertain cases, but the child-start-vs-provider-
acceptance boundary needs the stronger, preflight-backed observable above to stop
over-charging the WFC-AUTO-03 local-failure cases.*

=== S4-READY-R5 -- IMPORTANT [decision] -- Option A's real `.git` authority is under-described relative to detection coverage

The proposal frames the Git-write ownership question well and recommends Option A
(agent-owned commit) for the disposable proof, correctly warning against deciding
on the stale-lock nuisance alone. But the material handed to the maintainer
under-states the *authority* Option A actually grants.

Established fact:: `--sandbox workspace-write` supplies *no* path-level allowlist
and *no* independent `.git` exclusion (the proposal itself records this; the
inspected help confirms no such option, and `--add-dir` is deliberately unused).
Therefore, with a writable repository working root, an agent under Option A has
write access to the *entire* `.git` directory -- refs, `packed-refs`, reflogs,
the object store, lock files, *and* `.git/hooks/*` -- not merely "ordinary
add/commit."

Charter questions answered::

* *Does agent-owned commit imply arbitrary Git metadata/ref mutation?* Yes,
  mechanically, under workspace-write with no `.git` exclusion.
* *Can the selected sandbox mechanically restrict the agent to ordinary
  add/commit?* No. The inspected CLI surface offers no such restriction.
* *Does FTR/architecture intentionally trust the agent with this authority, or
  was only ordinary commit authorship intended?* Architecture section 8 ("V1
  agents create their own semantic content/review commits") and WFC-GIT-03 ("the
  coordinator shall not synthesize semantic commits") intend *ordinary agent
  commit authorship only*. The broader ref/history/hook authority is an
  *incidental* consequence of the sandbox lacking `.git` exclusion, not a
  deliberately granted trust.
* *What mutation is hard to reconstruct / not covered post-hoc?* Post-Hop
  observation (WFC-GIT-02/04/05) detects rewritten/divergent ancestry, HEAD
  movement outside the window, dirty/out-of-scope *paths*, and merge commits --
  so ref/history mutation affecting the tracked branch *is* caught and blocks the
  next Hop. But the documented post-Hop checks read HEAD/range/paths; they do
  *not* inspect injected `.git/hooks/*` contents or reflog edits. An injected
  hook executes on *subsequent* git invocations (by the coordinator or a human),
  independent of the scope check -- the one authority that survives observation
  and disposal boundaries.

Disposition::

* *Option A for the disposable proof: ACCEPTABLE.* Repository disposal plus
  post-Hop observation neutralize the unrestricted-`.git` authority (including a
  malicious hook, which dies with the discarded repo); treating any stale lock as
  a blocking post-Hop anomaly is adequate.
* *Option A for routine repository use: NOT YET SAFE* without one of: a real
  isolation boundary that restricts `.git` writes; expanded post-Hop verification
  that also covers `.git/hooks`/reflog; or an explicit maintainer decision to
  accept full `.git` trust. The gap is larger than the stale-lock nuisance the
  proposal foregrounds.

Recommended action:: enrich the maintainer decision material to present this full
authority surface -- especially `.git/hooks` injection and its non-coverage by
the post-Hop scope check -- so the A/B choice for *routine* use is made on
complete information. This is decision material to correct, not a defect that
blocks the *proof*; the proof is safe under Option A regardless.

=== S4-READY-R6 -- MINOR [defect] -- stale-lock path is cited imprecisely and should be detected broadly

Section 3 cites an empty `.git/HEAD.lock`. The Slice-3 source artifacts disagree
on the exact residue: the implementation evidence says `.git/HEAD.lock` while the
implementation review says `.git/logs/HEAD.lock` -- and these are *different*
locks (HEAD ref-update lock vs reflog lock). The proof's stale-lock stop-
detection should therefore scan for any `.git/**/*.lock` residue, not one
hardcoded path. This does not reopen attribution: it remains a known external
Codex-local environment artifact, not coordinator code (already established in
the Slice-3 review; no Slice-1..3 code creates or manipulates lock files).

=== S4-READY-R7 -- MINOR [defect] -- make "correct commit + stale lock" an expected, human-inspected proof-1 outcome

The observed stale lock appeared *after a successful commit*. The proof's stop
rules treat lock residue as a blocking anomaly. Proof #1 may therefore
legitimately produce the exact required commit *and* a stale lock, which the rule
then classifies as a stop. That conservatism is correct (stop and inspect), but
the proposal should state explicitly that "correct deterministic commit + stale
lock" is an *expected possible* outcome to be inspected by a human, not evidence
that the adapter logic failed -- so the result is not misread as an adapter
defect during acceptance.
