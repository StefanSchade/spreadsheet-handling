== 12. `update-ref -d` versus `symbolic-ref --delete` (gating)

This was tested empirically under Git 2.47.3 in disposable repositories rather
than assumed.

Probe 1 reproduces the state: after `git remote remove origin` on an ordinary
fresh clone, `.git/refs/remotes/origin/HEAD` survives as a broken symbolic ref,
`git symbolic-ref -q` resolves it (rc `0`), `git for-each-ref` does *not* list
it, and `git fsck` fails rc `2` with `invalid sha1 pointer`.

Probe 4 settles the semantics definitively. With `refs/remotes/origin/main`
still present, `git update-ref -d refs/remotes/origin/HEAD` deletes
`refs/remotes/origin/main` and leaves the `origin/HEAD` symref file intact.

Answering the commissioned questions:

. It does *not* delete the symbolic ref itself.
. It dereferences and deletes the target; when the target is already missing the
  command is a silent rc `0` no-op.
. After the command `.git/refs/remotes/origin/HEAD` still exists,
  `git symbolic-ref -q` still resolves it, and `git fsck --full` still fails
  rc `2`.
. `git update-ref --no-deref -d` does work (probe 2).
. `git symbolic-ref --delete` works (probe 2) and is the command already
  independently proven by the accepted reopened-B evidence; it should be used at
  all clone-transfer boundaries for consistency.

Probe 7 runs the plan's staging snippet verbatim end to end: the guard fires,
`update-ref -d` returns rc `0`, the sole-ref proof passes blind because
`for-each-ref` cannot see a broken symref, and the plan's own `git fsck` gate
then fails rc `2`. The identical snippet with `symbolic-ref --delete`
substituted passes fsck, the sole-ref proof, and physical/reachable closure.

The synchronized command therefore does not remove the broken symbolic ref. This
is a real gating synchronization defect. It is fail-closed rather than
silently corrupting, because `git fsck` is required at all three cleanup sites,
but a mechanically executing implementation agent deterministically halts at a
gate its own prescribed command cannot satisfy.

== 16. Findings

=== F1 -- BLOCKING -- `update-ref -d` does not delete the broken symbolic ref

Observation:: At both clone-transfer boundaries -- scratch to staging (plan
lines 691--694) and staging to target (plan lines 739--742) -- the synchronized
cleanup is a guarded `git update-ref -d refs/remotes/origin/HEAD`. Under pinned
Git 2.47.3 this dereferences the symref, returns rc `0`, and leaves
`.git/refs/remotes/origin/HEAD` in place as a broken symbolic ref.

Concrete failure:: `git fsck` continues to fail rc `2` with
`refs/remotes/origin/HEAD: invalid sha1 pointer`. The plan requires `git fsck`
at both boundaries, so mechanical execution halts at the staging validation gate
and C cannot reach candidate submission. The sole-ref proof does not catch it
first, because `git for-each-ref` does not list a broken symref.

Smallest correction:: Replace the command at both sites with the already
independently proven `git symbolic-ref --delete refs/remotes/origin/HEAD`
(`git update-ref --no-deref -d` is equivalent in effect). No other plan text
changes.

=== F2 -- IMPORTANT -- Actual-run post-filter cleanup names no command

Observation:: The actual-run post-filter cleanup in the authorized sequence, and
the corresponding FTR sentence, require C to "guardedly delete residual/broken
symbolic `refs/remotes/origin/HEAD` if present" without naming a command.

Concrete failure:: The only two worked examples in the same document use the
defective `update-ref -d`, so a mechanically executing agent will reproduce F1
at the third site, halting instead at the run-level `git fsck --full` gate
before any B result proof.

Smallest correction:: Name `git symbolic-ref --delete refs/remotes/origin/HEAD`
once as the authoritative residual-symbolic cleanup command binding all three
boundaries.

=== F3 -- INFO/WATCH -- Broken symrefs are invisible to ref-set proofs

`git for-each-ref`, `git show-ref`, `git count-objects -v`, `git cat-file
--batch-all-objects`, and `git rev-list --all` all ignore a broken symbolic ref.
`git fsck` (plain and `--full`) is the only gate in the plan that detects it.
This is why F1 is fail-closed rather than silent, and why the fsck gates must
not be weakened. No change required.

=== F4 -- INFO/WATCH -- `packs == 1` versus `packs <= 1`

The M1 numeric gate asserts `packs == 1` where the pinned tool's descriptive
predicate tolerates an empty repository. Not a concrete risk: the anchor-source
is never empty, and probe 6 confirms exactly one pack at both trivial and real
Core scale and under forced unpack limits. Recorded, not raised.

Finding counts:: BLOCKING `1`; IMPORTANT `1`; MINOR `0`; INFO/WATCH `2`.
