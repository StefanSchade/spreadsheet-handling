== 6. Filter-repo command semantics

`git-filter-repo` is not installed, not vendored, and not on `PATH`, and this
review did not install it. No bundled help or man page was available locally.
Statements below about tool behavior therefore rest on documented upstream
semantics, not on local execution, and are marked as such. See W1.

[cols="2,4",options="header"]
|===
|Option |Assessment

|`--refs refs/heads/main`
|Correct scope. Documented to imply `--partial`, which B does not state and which
has two consequences B partly depends on. See I1 and I2.

|`--paths-from-file`
|Correct. Literal entries match a path exactly or as a directory prefix
terminated by `/`, so no entry can match a sibling by shared string prefix. None

The options can coexist as specified. The dangerous implicit behavior is not in
the options themselves but in what `--partial` suppresses (I2).

=== 6.1 A well-designed defense worth recording

An empty line in a filter-repo paths file is an empty path expression, which
matches every path. A single stray blank line would silently convert the
operation into a no-op and carry all Core history forward. B's requirement to
verify the path file's line count *and* SHA-256 before use forecloses this
completely, because any inserted blank line changes the digest. No action; noted
because it is the failure mode with the worst consequence and B already closes
it.

== 7. Pre-filter ref model, scratch boundary, and pruning

The required pre-filter state -- sole `refs/heads/main` at the anchor, no remote,
remote-tracking ref, tag, replace ref, note, stash, or other branch -- is
sufficient for deterministic filtering and achievable without touching Core: the
clone is the thing mutated, Core is only read. Core's stash is not copied by
`git clone`, and its 8 tags and remote-tracking refs are removed in the clone.

The `--no-local` rationale is sound: it forces the pack transport instead of
hardlinking object files, so scratch operations cannot reach Core's object store.
The three-way separation of Core source, disposable scratch clone, and standalone
target is stated consistently in both documents, and no filtering is permitted in
Core or in the target.

Pruning is the correct definition of product history here. Because 51 of the 118
selected-path commits are mixed, the projection necessarily produces partial
commits, and B says so plainly rather than claiming identity. Empty and
degenerate-merge pruning discards Core-only topology that carries no product
meaning; no merge touches a selected path, so no meaningful selected-history
topology is lost. B's truthfulness claims hold: projections are not
identity-equivalent copies, commit and tree OIDs change, signatures and excluded
topology are not promised, and parent order is preserved only within rewrite
semantics.

== 8. No filter-time path rewrite

Deferring layout to an ordinary C bootstrap commit is the stronger choice, and
this review found no correctness or history problem with it.

* Verification is materially simpler: the raw filtered HEAD can be compared
  byte-for-byte and mode-for-mode against the anchored Core projection using the
  same 47-path, byte-count, and manifest digests B already fixes. A filter-time
  rename would force every comparison through a mapping.
* An ordinary `git mv` in a reviewed bootstrap commit preserves blame and
  `--follow` adequately, by the same rename-detection mechanism the three `R100`
  document moves already rely on.
* It defers package and layout choice to C without ambiguity, because B fixes
  `selection.path_rewrites` to the empty array and the acceptance proof runs
  before any move.

=== 9.2 IMPORTANT

I1 -- `--refs` implies `--partial`, and the absolute `--force` prohibition may collide with the tool's fresh-clone check::
+
--
*Observation.* B specifies `--refs refs/heads/main` and forbids `--force`
unconditionally, while also requiring C to delete `origin` and every non-`main`
ref in the clone before filtering. `--refs` is documented to imply `--partial`,
which B never mentions. filter-repo also refuses to rewrite a repository that
does not look like a fresh clone unless `--force` is given. Whether the mandated
ref surgery trips that check could not be determined locally, because the tool is
not installed and this review was instructed not to install it.

*Risk.* C reaches the one contracted operation and the pinned tool either refuses
to run or reports an effective option set different from the contracted argv. C
must then either halt mid-phase or improvise -- adding `--force` is exactly a
B-level decision about what the authoritative invocation is, which defeats the
contract's purpose.

*Smallest correction.* Three sentences in 13.5 and readiness section 6.2: state
that `--refs` implies `--partial` and name what that changes; require C to record
the tool's own reported effective options alongside the argv; and state that if
the pinned tool refuses the contracted argv, C halts and B is re-opened, rather
than C adding any option on its own judgment.
--

I2 -- `--partial` leaves the entire Core object graph in the scratch clone, and the ref/object proof cannot see it::
+
--
*Observation.* Because `--refs` implies `--partial`, filter-repo skips its normal
post-run `reflog expire` and `gc --prune=now`. Every original Core object
therefore remains in the scratch object store after filtering, unreachable but
physically present. B's ref and object proof uses `show-ref` and `rev-list --all
--objects`, both of which observe only reachable objects and are blind to this by
construction. B asserts that "unreachable scratch objects/pack artifacts are not
copied to the accepted repository" but never fixes the mechanism that guarantees
it.

*Risk.* If the standalone repository is later populated by copying the scratch
`.git`, by `git clone --mirror`, or by a mirror push, the complete Core history
-- domain source, dogfood bundles, commissioning evidence, Project Memory -- is
carried into the standalone repository as unreachable objects and can be
recovered from it. This is the single largest Core-material leak path in the
plan, and the contracted proof returns green while it happens.

*Smallest correction.* One clause in 13.5: the standalone target may be populated
only by `git clone` of, or `git push refs/heads/main` from, the filtered scratch
-- never by copying `.git`, never with `--mirror` -- and C proves the accepted
repository's own object closure independently of the scratch proof.
--

I3 -- the inclusion proof is weaker than the FTR's own wording, with a verified merge-commit blind spot::
+
--
*Observation.* The FTR requires that "every path in every rewritten commit is one
of the 50 allowed historical paths" -- a tree-union statement. The readiness
artifact operationalizes it as "the union of changed paths" across reachable
commits, which is strictly weaker. Verified on this repository: for merge commit
`b9850a5f`, `git log -1 --format='' --name-only` yields *0* paths, while the same
command with `-m` yields *39*. `git log` suppresses merge diffs by default, so a
path present only through a merge is invisible to a changed-path union.

Also verified, because it is the obvious-looking substitute and is wrong: `git
rev-list --objects` is *not* a valid path union. It prints each object once with
a single name. 19 paths at HEAD share the empty blob
`e69de29bb2d1d6434b8b29ae775ad8c2e48c5391` and only one name is printed for it,
and all three `R100` rename pairs share identical blob OIDs -- for example both
sides of the system-boundary review are blob `3e625ea9d3e811cab9e6485436ecb4cddb54ab82`
-- so an `--objects`-based check would also misreport the rename proof.

*Risk.* A false green on the decisive accidental-inclusion test, and a normative
inconsistency where the FTR controls but the operational artifact specifies
something weaker.

*Smallest correction.* Define the union in the readiness artifact as the full
tree union over reachable commits, matching the FTR's wording:
`git rev-list refs/heads/main | while read c; do git ls-tree -r --name-only "$c";
done | LC_ALL=C sort -u` must be a subset of the 50 lines.
--

I4 -- the commit-map digest does not unambiguously bind to the filter-repo output bytes::
+
--
*Observation.* `result.commit_map.path` is
`docs/provenance/incubator-commit-map.tsv` and `result.commit_map.sha256` is
defined over "exact tracked commit-map bytes", while readiness section 8.4
requires rerun equality of `.git/filter-repo/commit-map` *bytes*. Nothing states
that the tracked file is a byte-verbatim copy of the generated one. The generated
commit map is whitespace-padded rather than tab-separated, so the `.tsv` suffix
actively invites reformatting.

*Risk.* If C normalizes the file to real TSV, `result.commit_map.sha256` and
`verification.rerun_commit_map_sha256` are digests of two different byte streams,
and the reproducibility check compares artifacts that were never meant to be
equal -- either a spurious failure or a meaningless pass.

*Smallest correction.* One sentence in schema section 7.2: the tracked file is a
byte-verbatim copy of run one's `.git/filter-repo/commit-map`; both digests are
taken over those exact bytes; the `.tsv` suffix is naming only and implies no
reformatting.
--

I5 -- `target.accepted_head` cannot be truthful as written, and `result.bootstrap_head` leaves its lifecycle to C::
+
--
*Observation.* The prompted circularity check resolves as follows. The manifest
is itself committed, so any commit that writes `target.accepted_head` changes the
standalone HEAD and invalidates the value it just recorded. `result.bootstrap_head`
has the same shape. B softens both with "or YAML `null` until it exists", which
breaks the hard self-reference -- the bootstrap commit can carry `null` -- but B
never says which commit writes the real value or what it then denotes.

*Risk.* C must invent the provenance lifecycle, which is a B-level provenance
decision, or record a value that is false the moment it is committed. A manifest
that claims more than Git can prove is exactly what B set out to avoid.

*Smallest correction.* Define both as strictly backward references written by a
strictly later commit than the one they name: `result.bootstrap_head` is the
commit that introduced the manifest, `target.accepted_head` is the commit the
maintainer accepted. State that neither participates in any digest, equivalence,
or acceptance comparison.
--

I6 -- the imported-history authority notice is optional by disjunction and under-specified for the documents that actually read as authority::
+
--
*Observation.* B requires C to "place them below an imported-history boundary
*or* add one directory-level notice". Verified at the anchor, the imported set is
not uniform. `FTR-AGENT-WORKFLOW-COORDINATOR-P5.adoc` carries `*Lifecycle:* Open`
and `*Status:* *ACCEPTED AS V1 IMPLEMENTATION AUTHORITY ...*`, and contains 92
Core-domain references. `agent_workflow_coordinator_proposed_architecture_2026-08-25.adoc`
carries `Status:: *FORMAL ARCHITECTURE DESIGN -- ACCEPTED FOR V1*`.
`agent_workflow_coordinator_concept_2026-08-25.adoc` has no `Status` line at all.
The other nine carry explicit non-normative or non-authorizing status lines. The
12 documents originate in 5 distinct source directories, so after C chooses
layout, "one directory-level notice" may not cover all of them.

*Risk.* A standalone reader or agent treats an imported document as the
standalone product's governing contract, including its authorization language.
The divergence is permanent and grows: phase D transitions Core's FTR toward
`Superseded` while the imported copy states `Lifecycle: Open` forever.

*Smallest correction.* Make the notice mandatory rather than a disjunct, require
it per file or require all 15 imported document paths to land under one clearly
named imported-history root, and name the FTR and the proposed-architecture
document explicitly as the two that assert current authority.

=== 9.3 MINOR

M1 -- Git-entry manifest digest definition is ambiguous and its natural reading does not reproduce::
The artifact defines it as "the bytewise sorted sequence emitted by `git ls-tree
<anchor> -- <path>` for each current path". Read as "iterate the current paths,
which are already bytewise sorted", the digest is
`88ea354f43ac4d64a828e007078e10b89db1229cee9c5dd6d1d0df1d9d88045a`, which does
not match. Only re-sorting the emitted *lines* as whole lines reproduces the
published `dae0e060...`. Because all 47 entries are `100644 blob`, sorting whole
lines is in effect sorting by blob OID, which is not what the prose suggests.
*Correction:* say "the `ls-tree` output lines sorted bytewise as whole lines".

M2 -- the anchor's own survival is an unstated precondition of the commit-map acceptance criterion::
B requires an anchor row mapping to rewritten `main`. That holds only because
`e4a0b20a` changes an allow-listed path (verified: it changes exactly the FTR).
*Correction:* state the precondition explicitly, so a future re-freeze on a
different anchor cannot silently invalidate the criterion.

M3 -- `selection.included_paths_sha256` is not bound to a serialization in the schema::
The digest is over the 50-line file, but the manifest holds a YAML array, and the
schema does not say how to get from one to the other. *Correction:* one clause --
the digest is over the array entries joined by LF with a terminal LF.

M4 -- `result.reachable_object_ids_sha256` does not say "before any bootstrap commit"::
`result.rewritten_head` carries that qualifier and this field does not, although
the rerun requirement makes the pre-bootstrap reading the only consistent one.
*Correction:* add the same qualifier.

M5 -- "no second filter pass" reads against the mandated second run::
Readiness section 6.2 forbids a "second filter pass" while section 8.4 requires
repeating the filter in a second fresh clone. The intended distinction -- no
second pass over the same clone -- is inferable but not stated. *Correction:* add
"over the same clone".
