=== helper_prefix / naming (Area 4)

Section 4's naming-asymmetry row states, in substance, that current runtime
"does not compute helper names from a prefix parameter *at all*" and that the
real mechanism is a declared-name schema field. This review traced every
`helper_prefix` occurrence in `src/` and finds the claim *imprecise, not
materially false*:

* `domain/transformations/fk_helpers/drop.py:49` (`remove_fk_helpers.prefix`)
  and `domain/transformations/helpers.py:219` (`reorder_fk_helpers.helper_prefix`)
  are both confirmed, verbatim, inert: `del prefix  # retained for
  backwards-compatible step binding only` / `del helper_prefix  # retained
  for backwards-compatible step binding only`. These specific claims are
  correct as literally stated.
* However, `domain/helper_policies.py::_v2_relations_from_explicit_policies`
  (line 166) and `domain/fk_relations.py::_try_build_inferred_relation`
  (line 162) *do* compute `helper_columns[].column` from a live
  `helper_prefix` parameter, via `f"{helper_prefix}{target_frame}_{field}"` --
  this runs inside `configure_fk_helpers`/`infer_fk_relations`, at
  *declaration* time, not at materialize/reorder/drop time. The resolved
  string is then baked into the durable v2 relation entry;
  `fk_relations.py::build_v2_relation`'s own docstring confirms
  `helper_prefix` itself is deliberately *not* re-emitted into that entry
  ("were redundant projections of `helper_columns` ... and are no longer
  emitted"). Downstream consumers (`enrich_helpers`, `reorder_helpers_next_to_fk`,
  `remove_fk_helpers`) read only the already-resolved `column` field and never
  see a live prefix parameter again.

The blanket clause "does not compute helper names from a prefix parameter at
all" is therefore false as literally written; the correct statement is
"downstream materialization/layout/cleanup steps do not; the earlier
declaration steps (`configure_fk_helpers`/`infer_fk_relations`) do, and bake
the result into the durable schema field every downstream step then reads."
This correction does *not* undermine Section 8's architectural point: whether
the alias comes from an author-supplied override or a prefix-derived
template, it is resolved once, at configuration time, into a durable
config-schema field -- not recomputed live from FK's relation-lifecycle
machinery at every later stage. A hypothetical Lookup alias/prefix option
could equally live inside `configure_lookup_helpers` today without adopting
any part of FK's durable, centrally-conflict-resolved relation model. Section
8's weakening of the FTR's naming-alias argument survives the correction
intact.

*Verdict: imprecise, not materially false; does not alter F-002 selection or
Section 8's argument. MINOR correction required (<<findings>>).*

== 10. Formula-mode risk -- empirically confirmed defect

The assessment leaves formula-mode mismatch semantics explicitly unresolved
(Section 11, item 5). This review went further and empirically reproduced the
interaction through the installed package (read-only; no source or test file
was modified):

[source,text]
----
enrich_lookup(..., helper_value_mode="formula", missing="empty")
  -> title cell value: LookupFormulaSpec(source_key_column='story_id',
     lookup_sheet='stories', lookup_key_column='id',
     lookup_value_column='title', missing='')

apply_derived_column_policy(..., policy="warn_on_mismatch")
  -> finding: derived_value_mismatch, "2 row(s) differ from canonical
     lookup 'stories' for helper column 'title'." (both rows are, in fact,
     correctly enriched -- the "mismatch" is spurious)

apply_derived_column_policy(..., policy="fail_on_mismatch")
  -> raises ValueError: "Derived column policy failed:
       - derived_value_mismatch: 2 row(s) differ from canonical lookup
       'stories' for helper column 'title'."
----

Root cause, independently traced: `_norm()` (`derived_column_policy.py:820-828`)
calls `str(value).strip()` on whatever cell value it receives.
`core/formulas.py::LookupFormulaSpec` is a frozen dataclass with no custom
`__str__`, so `str()` on a formula-mode cell yields its dataclass-generated
`repr()` -- which will essentially never equal `_norm()` of the plain scalar
canonical value pulled from the lookup frame. `_write_provenance`
(`enrich_lookup/operation.py:495-565`) writes the identical provenance record
regardless of `helper_value_mode`, so DCP has no way to know from the
provenance shape alone that it is looking at formula-mode cells. A repository-wide
grep confirms *zero* existing tests anywhere exercise
`apply_derived_column_policy`'s mismatch-checking path against a
`helper_value_mode="formula"`-produced Lookup helper column; the one file
that matches both search terms (`tests/roundtrip/test_cleanup_invariants.py`)
uses `helper_value_mode: "values"` with `policy: "drop"` (which skips
mismatch-checking entirely), not the combination that triggers the defect.

This is a real, live, currently-reachable defect through two ordinary
registered/YAML surfaces (`add_lookup_helpers(helper_value_mode="formula")`
then `apply_derived_column_policy(policy=...)`), independent of who owns the
comparison code -- moving `_check_enrich_lookup_values` into Lookup, verbatim,
would reproduce the identical defect there, since the cause is comparing a
`LookupFormulaSpec`'s identity representation against a plain scalar, not a
DCP-versus-Lookup ownership question.

*Verdict: reveals a genuine, independently-confirmed semantic defect in
current behavior. Non-blocking for F-002 *selection* (the defect's cause is
orthogonal to code ownership), but this finding upgrades the assessment's own

== 19. Findings

=== FIND-C1-001 -- MATERIAL -- Formula-mode value-mismatch checking is empirically confirmed defective, not merely unresolved

*Observation:* `apply_derived_column_policy`'s mismatch-checking path, when
run against a Lookup helper column produced with
`helper_value_mode="formula"`, produces spurious `derived_value_mismatch`
findings under `warn_on_mismatch` and unconditionally raises `ValueError`
under `fail_on_mismatch`, for every row, regardless of whether the formula is
correct.

*Evidence:* Direct execution through the installed package (<<area-9>>);
root cause traced to `_norm()` stringifying a `LookupFormulaSpec`'s
dataclass-generated `repr()` instead of its semantic value; zero existing
test coverage of this combination anywhere in the repository (confirmed by
targeted grep).

*Concrete risk if ignored:* An implementer of F-002, told to "preserve
current behavior exactly," could faithfully move this defect into Lookup's
own module verbatim, formalizing a bug as the newly-canonical owned contract,
or could silently "fix" it as an incidental side effect of the ownership
move, either of which the assessment's own Section 11 item 5 already
(correctly, if only speculatively) warns against.

*Recommended action:* The next implementation-readiness/design step must
treat the formula-mode decision (preserve-as-named-defect vs. explicit
correction) as a mandatory, first-class, resolved precondition -- not an
optional audit -- before finalizing the value-mismatch delegation's shape.

*Disposition:* Non-blocking for F-002 selection; blocking for F-002
implementation until explicitly resolved.

=== FIND-C1-002 -- MATERIAL -- Section 7's "FK's relation-shape knowledge is correctly not reimplemented here" is incomplete

*Observation:* The claim is true only for the durable relation-policy path
(`_durable_fk_policy_helper_names` -> `resolve_v2_fk_relations`). DCP also
independently reimplements FK's own *transient* provenance-shape validation
(`_validated_fk_helper_names`, ~18 lines) with zero delegation to FK's own
package, a smaller instance of the identical pattern F-002 targets.

*Evidence:* Direct source read of `derived_column_policy.py:286-303` and
`fk_helpers/policy.py::derived_helper_columns_by_sheet`; directly exercised
by `test_malformed_helper_columns_entry_raises_clear_value_error` (<<area-6>>).

*Concrete risk if ignored:* Section 9's "F-002... is the one item that
squarely matches" reads as exhaustive when it is not; a maintainer who
completes F-002 exactly as scoped could reasonably (again) conclude the whole
DCP-reimplements-a-producer's-provenance-shape pattern is now closed, when a
small FK-side residual would remain -- a milder recurrence of the exact risk
Section 7's own "concrete risk of not fixing it" paragraph names regarding
H5.

*Recommended action:* Correct Section 7/9's characterization to name this
gap explicitly; decide at implementation-readiness time whether to fold it
into F-002's own scope (natural, since it is the mirror-image fix in the same
seam) or name it as an explicit tiny separate follow-up. Do not leave it
silently unaddressed.

*Disposition:* Non-blocking for F-002 selection; should be recorded before
implementation-readiness work, per the "ACCEPT WITH MINOR CORRECTIONS"
definition.

=== FIND-C1-003 -- MINOR -- helper_prefix claim overstated in one clause

*Observation:* "current runtime does not compute helper names from a prefix
parameter at all" is false as literally written; `configure_fk_helpers`/

*Evidence:* `domain/helper_policies.py:162-166`,
`domain/fk_relations.py:117-166`.

*Concrete risk if ignored:* Minimal -- a future reader tracing `helper_prefix`
end to end would find the blanket claim contradicted, but the downstream-inert
claims (which carry the argument's real weight) remain fully correct, and
Section 8's conclusion is unaffected.

*Recommended action:* Reword to scope the claim to downstream
materialize/reorder/drop steps specifically.

*Disposition:* Wording-only; does not alter F-002 selection or sequencing.
