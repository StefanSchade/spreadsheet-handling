== 5. Detailed material findings

=== S1-R1 (IMPORTANT) -- reconcile path can launder a human/semantic stop

Location:: `scripts/workflow_coordinator/reducer.py` `require_reconcile`
(lines 382--406, esp. the `human_question` overwrite at line 404) and
`resume_after_reconcile` (lines 409--426).

Invariant:: WFC-AUTH-02/06 make a non-null unresolved escalation / `requires_human`
a *mandatory* human-authority stop; architecture case I states the checkpoint
"retains the question" and the human must "decide the semantic question". The
common reconcile mechanism (WFC-FAIL-04/07, R4) is scoped to `interruption` and
`prerequisite_return` provenance -- both arising from non-semantic states.

Evidence (reproduced):: An agent result with `requires_human=true` +
`escalation=semantic_authority` correctly yields `AWAITING_HUMAN` with
`human_question="Who may accept this contract?"`. Calling
`require_reconcile(reason="interruption")` on that Run overwrites the question
with the generic "Validate current reality and explicitly authorize resume." and
sets `RECONCILE_REQUIRED`; `resume_after_reconcile` then returns it to `READY`.
Every *other* transition (`record_hop`, `confirm_supervisor_route`,
`authorize_prerequisite`, `resume_after_reconcile`) guards its input status;
`require_reconcile` does not.

Consequence:: The reducer -- the Slice-1 acceptance surface for exactly this
invariant -- permits `AWAITING_HUMAN (semantic) -> RECONCILE_REQUIRED -> READY`
without the semantic question being resolved, and erases the escalation text from
the record. Not agent-reachable (agents cannot call these mechanics; input is
only the `RoutingResult`), so this is trusted-caller misuse, not an external
exploit -- which is why it is Important, not Blocking. But it is a latent hole in
the central corrected invariant, and Slice 1 provides no other resolver for a
non-prerequisite semantic escalation, so `require_reconcile` is the accidental
escape hatch.

Smallest correction:: Guard `require_reconcile` to reject entry states that
represent an unresolved human/semantic stop (i.e. restrict it to the
interruption/prerequisite provenance states such as `RUNNING`/`READY`/
`AWAITING_SUPERVISOR`/`SUSPENDED`), and/or preserve an existing
`human_question`/escalation rather than overwriting it. Implementation-local; the
architecture already scopes reconcile correctly.

=== S1-R2 (IMPORTANT) -- checkpoint route keys are untruthful for paused states

Location:: `reducer.py` `permitted_route_keys` (lines 429--439, the fall-through
`return tuple(sorted(phase.routes))`), surfaced by `persistence.py`
`checkpoint_projection` `next_permitted_route_keys` (line 185).

Invariant:: WFC-OBS-02 -- "finite next permitted routes ... recomputed from
pinned profile, phase, *and preemption state*."

Evidence (reproduced):: For a Run in `AWAITING_HUMAN_BUDGET`
(`stop_reason=autonomous_hop_budget_exhausted`) the checkpoint lists
`('again','ask','done')` -- including a `goto` and a `complete` -- although no
invocation can run. Same for `RECONCILE_REQUIRED` (requires explicit resume
first) and `AWAITING_HUMAN`. `COMPLETED`, `STOPPED`, `SUSPENDED`, and
`AWAITING_SUPERVISOR` are handled correctly; the three human-pause states are
not.

Consequence:: Observability only -- the reducer never consults
`permitted_route_keys` for routing, so no unsafe route can execute. But the named
contract output overstates what is permitted for roughly a third of the status
space, including the common budget-exhaustion and reconcile cases, and is
untested for those states.

Smallest correction:: Return `()` for `AWAITING_HUMAN`, `AWAITING_HUMAN_BUDGET`,
and `RECONCILE_REQUIRED` (mirroring the terminal/`suspended` handling), and add a
focused test.

=== S1-R3 (MINOR) -- `outcome` is validated but never enforced

Location:: `reducer.py` `reduce_result` (lines 232--333) reads
`schema_version`, `scope_changed`, `requires_human`, `escalation`,
`requested_route`, and `findings`, but never `result.outcome`; `Outcome`
(`model.py` 59--64) is validated at `serialization.py:417`.

Assessment:: Read against the accepted contract, this is *correct* for Slice 1.
The FTR pins routing to the finite profile route table keyed by `requested_route`
(WFC-AUTH-03) and pins preemption as outcome-independent (architecture 9.2:
"regardless of `outcome`"; replay I). No accepted A--J case requires `outcome` to
gate a route. The required mediation (requested_route validated against
`phase.routes`) exists. Reproduced: `outcome in {failed, blocked}` +
`requested_route=done(complete)` completes autonomously.

Consequence / recommendation:: When real agent results arrive (Slice 3+), a
contradictory result (`failed`/`blocked` yet requesting completion) will route
successfully. Consider a fail-closed cross-check then (e.g. `failed`/`blocked`
incompatible with autonomous `complete`/`goto`, or profile-declared
outcome-to-route compatibility). Not required for Slice-1 acceptance and no
architecture reopening.

=== S1-R4 (MINOR) -- new-vs-existing Finding operation vocabulary

Location:: `reducer.py` `_operation` (79--89) new-Finding branch returns
`proposed.value`; creation authority check at 121--128; permitted operations
constrained to `{resolve, residual, supersede, reopen}` at `serialization.py:218`.

Evidence (reproduced):: A gate granted `("resolve","residual","supersede",
"reopen")` can create a new `residual` Finding but is rejected creating a new
`resolved` or `superseded` Finding ("gate cannot create Finding ... as
resolved"); `residual` succeeds only because its state value equals its
operation token. Behaviour is fail-closed (safe); the concern is that the same
conceptual grant maps to transitions but silently not to creation, by incidental
string equality rather than a stated rule.

Smallest correction:: Unify the operation vocabulary so a gate's granted
operations map deterministically to both creation and transition (or state
explicitly that direct creation as `resolved`/`superseded` is disallowed and make
that intentional rather than string-incidental).

=== S1-R5 (MINOR) -- checkpoint per-Hop rows lose finding-delta/evidence

Location:: `model.py` `HopSummary` (214--227) and `Hop.compact` (198--211) omit
`finding_delta_ids` and `evidence_refs`; `persistence.py` checkpoint hop rows
(152--163) therefore cannot present them.

Assessment:: Architecture 10.3 enumerates the Hop row as "(role, outcome,
commits, finding delta, evidence, route)". The compaction is defensible under
"compact Hop summaries" (WFC-MODEL-02) and the data is cross-referenceable via
Finding `introduced_by_hop`/`changed_by_hop` and the observation list, so this is
Minor. If exact per-Hop fidelity is intended, carry the two fields into
`HopSummary`.

== 7. Model / reducer / authority assessment

* *Model* (WFC-MODEL-01..06): WorkItem is input data; Run/Hop/Finding carry the
required fields with no issue-tracker growth; next routes derived, not persisted.
`Finding` states are exactly `open|resolved|residual|superseded`.
* *Reducer ordering* (WFC-AUTH-01..03): reconstructed manually. Order is
schema/correlation + mechanical facts -> `scope_changed` -> human/escalation ->
unknown route -> advisory-complete block -> Finding authority -> budget ->
supervisor -> route. No later step can bypass an earlier stop; the
`outcome=completed`+`requires_human`+escalation combination always stops before
route lookup and before any supervisor path (verified).
* *Finding authority* (WFC-FIND-01..03, WFC-AUTH-04/05): agents create only
`open`; `SUPERVISOR` deltas raise; gate operations are limited to the phase's
declared `finding_authority`; invariant rewrite, unauthorized blocking downgrade,
reopen without new material evidence, non-blocking-residual, and
superseded-without-successor all fail closed. Blocking downgrade is bound to
`residual` disposition only. Solid, apart from S1-R4's creation-vocabulary quirk.
* *Supervisor* (section 7 probes): consumes exactly one Hop (via `record_hop`,
which keeps `AWAITING_SUPERVISOR`), cannot mutate Findings
(`confirm_supervisor_route` has no delta surface), cannot select an
undeclared/non-`supervisor` route, and is budget-checked before invocation and
again on a `goto` after its own Hop.

== 8. Persistence / reconcile assessment

* *Atomic anchors* (WFC-PERSIST-01/06): `atomic_write_text` uses a
same-directory temp, `flush`+`fsync`, `os.replace`, then directory `fsync`, with
temp cleanup on any `BaseException`. Interrupted-before-replace preserves the old
file and leaks no temp (tested). Judged against the explicit same-checkout V1
promise this is sufficient; a directory-`fsync` failure after a successful
`replace` surfaces as an exception while the (atomic) new content is in place --
acceptable for V1, not a data-loss path.
* *Crash charging* (WFC-AUTO-02): no marker -> no Hop; marker present -> exactly
one conservative `uncertain_dispatch` Hop then `reconcile_required`; re-running
recovery is idempotent (still one Hop). `budget_reserved != 1` and Run-identity /
base-HEAD / sequence mismatches fail closed.
* *Reconcile/resume* (WFC-FAIL-04/07, R4): one `require_reconcile` serves
`interruption` and `prerequisite_return`, discards stale next action, records
reason+anchor, and resume requires clean unchanged HEAD, zero anomalies, and
`limit >= used`. The shared-path proof (replay B) is real. The one defect here is
S1-R1 (missing entry-state guard).
