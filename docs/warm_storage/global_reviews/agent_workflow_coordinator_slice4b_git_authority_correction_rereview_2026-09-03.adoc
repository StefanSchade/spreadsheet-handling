== 3. S4B-R1 disposition -- CLOSED

*Every trusted subprocess uses the trusted policy.* `trusted_commit`
(`git_facts.py:432-509`) now issues all of its Git calls through `_trusted_git` /
`_trusted_git_succeeds` (identity, filter probe, repository observation, staged and
worktree-path reads, `add`, pre-commit `rev-parse`, `commit`, post-commit
`_observe_hop`, and the `show` subject read). `_observe_hop` receives the trusted
`git_command`/`git_succeeds` injectors, so its `cat-file`, `merge-base`,
`rev-list`, and `diff` calls also run under the policy. No ordinary `_git` or raw
`subprocess.run` remains reachable from inside `trusted_commit`: the three residual
raw `subprocess.run` calls in the file are all inside `preflight_state_root`
(read-only `check-ignore`/`ls-files`/`diff --quiet`), which executes no hook and is
not on the trusted-commit path.

*Hook resolution is command-local and override-proof.* `_run_git(..., trusted=True)`
prepends `-c core.hooksPath=<os.devnull> -c commit.gpgSign=false -c
core.fsmonitor=false` *before* the subcommand (`git_facts.py:78-99`). `/dev/null`
is a non-directory, so no `<hooksPath>/pre-commit` can exist or be created.

Verified Git semantics (local experiments):

* command-line `-c core.hooksPath=/dev/null` overrides a *repository-local*
  `core.hooksPath=.githooks`: the worktree hook does not execute on `git commit`;
* it also overrides a `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`
  injection of `core.hooksPath`; and independently, the trusted environment strips
  those variables, so the injection is neutralized twice over.

`--no-verify` on the trusted `commit` is genuine defense-in-depth, not the sole
protection: the hooks-path pin already prevents `pre-commit`/`prepare-commit-msg`/
`commit-msg`/`post-commit` discovery regardless of `--no-verify`.

*Reproduction of the prior path.* `test_trusted_commit_neutralizes_agent_authored_worktree_hook`
materially reconstructs the S4B-R1 execution path -- worktree-relative
`core.hooksPath`, an agent-authored `pre-commit` inside the authorized scope, the
hook *included in the commit intent*, and an ordinary commit that *succeeds* -- and
asserts the side-effect file is absent. My own independent experiment reproduced
the same outcome. Agent-written, in-scope hook content can no longer execute with
Coordinator privileges during the trusted commit.

*S4B-R1 = CLOSED. Hook execution surface: NEUTRALIZED.*

== 4. S4B-R2 disposition -- CLOSED

`_trusted_git_environment()` (`git_facts.py:102-105`) returns the process
environment with every variable whose name begins `GIT_` removed, and
`_run_git`/`subprocess.run` pass it as a full `env=` replacement with `shell=False`.
This removes `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG_COUNT`,
`GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_GLOBAL`,
and signing/hook-related `GIT_*` controls from the trusted operation, while keeping
ordinary settings (`PATH`, `HOME`) so Git still functions.

`test_trusted_commit_strips_inherited_git_config_hook_injection` deterministically
exercises the prior concern (a `GIT_CONFIG_*`-injected `core.hooksPath`) and proves
the injected hook does not become effective; my experiment confirmed it.

Sufficiency for the bounded threat model: the remaining `-c` pins and the filter
refusal also neutralize *non-`GIT_`* operator config that could otherwise carry
external execution -- global/local `core.hooksPath` (overridden), `commit.gpgSign`
/`gpg.program` (signing forced off, so the program is never invoked),
`core.fsmonitor` (forced off), `diff.external`/textconv (`--no-ext-diff` plus
`--name-only`), and `filter.*.clean`/`*.process` (refused, section 5). Git aliases
cannot shadow the literal built-in subcommands used here. No concrete
agent-reachable *or* operator-config external-execution path remains through the
commands `trusted_commit` invokes; removing the `GIT_`-prefixed variables is
sufficient for this bounded boundary. I do not demand general process-environment
sanitization, as no further concrete path exists.

*S4B-R2 = CLOSED. Inherited Git config/routing: NEUTRALIZED.*

== 5. Clean / process filter analysis -- FAIL-CLOSED BEFORE STAGING

`_configured_external_filters` (`git_facts.py:411-429`) runs, under the trusted
policy, `git config --null --name-only --get-regexp
'^filter\..*\.(clean|process)$'` and `trusted_commit` refuses (before any `add`) if
the result is non-empty (`git_facts.py:452-456`). This is the correct, conservative
policy: a worktree `.gitattributes` can only *select* a named filter, while the
executable command lives in Git configuration; refusing on any effective
clean/process filter configuration prevents agent-authored attributes from
activating an operator-configured process, without needing to reason about which
paths the filter would touch.

Narrow false-negative check on the query:

* the regex anchors `^filter\.` and `\.(clean|process)$` with `.*` spanning the
  subsection, so dotted filter names (`filter.a.b.clean`) still match;
* Git canonicalizes the section (`filter`) and final variable (`clean`/`process`)
  to lower case, so mixed-case declarations are still matched;
* `--get-regexp` reads all config files (system/global/local/worktree); `GIT_CONFIG_*`
  is stripped and no `-c` adds a filter, so the effective set is exactly the file
  configuration;
* `smudge` is correctly *not* checked -- it runs on checkout, which `trusted_commit`
  never performs; only `clean`/`process` can run at `git add`.

`test_trusted_commit_refuses_configured_clean_filter_before_staging` proves a
configured `filter.agent.clean` selected by an agent-authored `.gitattributes`
raises `TrustedCommitError` with HEAD unchanged and the filter command not executed;
my experiment confirmed the detection. *Clean/process filter execution:
FAIL-CLOSED BEFORE STAGING.*

== 6. Direct regression analysis -- none material

The refactor introduced `_run_git`, `_trusted_git`, `_git_succeeds`,
`_trusted_git_succeeds`, and injected `git_command`/`git_succeeds` into
`_observe_hop`/`_observe_repository`. Verified no regression of the accepted
invariants:

* *Repository identity* still validated: `_repository_identity(..., git_command=
  _trusted_git)` compared to `expected_repository.resolve()`
  (`test_head_and_registered_repository_preconditions_refuse_before_commit` passes).
* *HEAD precondition* preserved (initial `facts.head != base_head` and pre-commit
  `rev-parse HEAD != base_head`).
* *Exact dirty-path comparison* preserved via trusted `_changed_worktree_paths`
  (unrelated-dirty and staging-failure tests pass; the latter now monkeypatches
  `_trusted_git` and still asserts `awaiting_human`, unchanged HEAD, preserved file).
* *Factual derivation* preserved: actual commit hash/path set/subject come from Git
  via `_trusted_git`; `max_commits=1`, non-merge, dirty-state, and
  `claims_existing_commits=False` semantics are unchanged in `_observe_hop`.
* *Public read-only API unchanged*: `observe_repository`/`observe_hop` wrappers keep
  ordinary `_git`/`_git_succeeds` (non-trusted) so preflight and Option-A paths are
  behaviourally identical; `--no-ext-diff` on read-only `diff --name-only` does not
  change the returned names.
* *No new external execution*: the added filter probe is a read-only `git config`
  query under the trusted policy; no config is persistently written anywhere
  (only command-local `-c`).
* *Trusted API not broadened*: `CommitIntent` remains `paths + subject`; no argv,
  shell, generic Git command, reset/clean/restore, or push/fetch/pull surface.

Post-commit observation uses the *same* trusted execution policy, so verification
cannot reactivate the forbidden surface. Full coordinator unit suite: 142 passed.
