== Findings

Classes: BLOCKING, IMPORTANT, MINOR, WATCH, NON-FINDING.

=== S4A-R1 -- BLOCKING -- external trusted state written before fail-closed boundary validation

*Violated authority.* WFC-PERSIST-02: operational/association state must "have its storage/correlation boundary verified fail-closed *before the first Run write* and each Hop"; the external trusted checkout-associated root "shall be outside the agent-writable workspace." WFC-PERSIST-02 authority-correction review NON-FINDING C/D.

*Mechanism.* The only containment guard is inside `invoke_codex`:

[source,python]
----
if repository.resolve() in (state_root.resolve(), *state_root.resolve().parents):
    raise Slice4Error("trusted state root must be outside agent workspace")
----

`register_checkout()` performs the *first* trusted writes -- `atomic_write_json(state_root/"checkout-association.json", ...)` and `mkdir(state_root/"checkouts"/<uuid>)` -- with *no* containment check. `validate_checkout()` likewise never checks containment. So when `state_root` lies inside the repository, the association mapping and per-checkout state directory are materialized inside the agent-writable workspace, and only a *later* `invoke_codex` call rejects the configuration -- after the trusted write already happened. The committed test encodes exactly this ordering (`test_real_boundary_rejects_state_inside_agent_workspace` calls `register_checkout(repository / "bad-state", repository)` and relies on it *succeeding* before `invoke_codex` raises), so the defect is asserted as intended behavior.

*Scope of live exposure.* In the consumed proof the maintainer supplied an *external* `state_root` (`wfc-s4-state.NlGwY4`), so no actual in-workspace contamination occurred. The defect is that the code and its test *permit and bless* an in-workspace trusted-state root, defeating the fail-closed-before-first-write invariant that is the entire purpose of the external trusted-state form.

*Smallest correction.* Extract one `_require_external_state_root(state_root, repository)` helper carrying the existing containment predicate and call it *before any write* in `register_checkout()` and at the top of `validate_checkout()` (and keep the `invoke_codex` per-Hop check). Rewrite the test to assert `register_checkout()` itself fails closed for an in-workspace root.

*Live invocation needed to close:* No.

=== S4A-R2 -- IMPORTANT -- acceptance conflated with transport presence; strict validation bypassed

*Violated authority.* WFC-AUTO-02 conservative accounting and the accepted Slice-3 strict `structured_result_v1` / `RoutingResult` validation authority; Slice-4 readiness S4-READY-R4 ("charged only on positive acceptance evidence or genuinely uncertain acceptance"); FTR 11.4 safety acceptance ("structured-result transport ... independently reviewed"). The code's own comment states "Only an independently validated correlated result establishes acceptance."

*Mechanism.*

[source,python]
----
result_text = result.read_text(encoding="utf-8") or None
acceptance = "established" if result_text else "uncertain"
----

`invoke_codex` never calls `adapter.validated_result()`. Any non-empty transport file -- including malformed JSON, a valid envelope with a *non-correlated* `run_id/hop_id/invocation_id`, or a schema-invalid `result` -- yields `acceptance == "established"`. This (a) contradicts the adjacent comment, (b) conflates "provider/model accepted the invocation" with "a correlated valid result exists," and (c) leaves the strict Slice-3 authority (`validated_result()`, used only in `vertical.py`) entirely out of the real-adapter path. A downstream reducer that treats "established" as "accepted + reducible" would then reduce a malformed or mis-correlated result.

*Note.* The failure path happened to be safe here: the empty result file produced `uncertain`, correctly charged. That is luck of the failure mode, not a proven happy-path guarantee.

*Smallest correction.* Do not derive acceptance from raw text length. Route `result_text` through `validated_result(raw, Invocation(run_id, hop_id, invocation_id))`; establish acceptance only on a schema-valid, identity-correlated result, and keep every other post-spawn state `uncertain`/charged.

*Live invocation needed to close:* No.

=== S4A-R3 -- IMPORTANT -- happy-path vertical integration is uncommitted and unproven

*Violated evidence.* FTR 11.4 intends the proof path `coordinator -> external trusted state -> real Codex -> strict result validation -> Git observation -> evidence -> record_hop -> reduction -> checkpoint`. The evidence doc claims all of these occurred (dispatch marker, `reconcile_required`, `hop_used=1`, HEAD/range observation, lock scan).

*Mechanism.* `slice4.py` is imported only by its own test. It stops at `CodexOutcome`; it does not call `validated_result`, `observe_hop`, `run_evidence`, `record_hop`, `reduce_result`, or `checkpoint_projection`. The failure-path accounting seen in the evidence (`recover_uncertain_dispatch` -> `require_reconcile`) is *reusable Slice-1 code* in `persistence.py`, but the *glue* that composes `invoke_codex` with the strict-validation and reduction chain is not committed anywhere. The happy path (correlated result -> observe -> reduce -> checkpoint) was therefore only manually composed for the one proof and is neither committed nor tested.

*Assessment.* This is not a second parallel coordinator contract -- the reusable pieces are the accepted Slice-1..3 ones, and a thin real boundary is explicitly acceptable. The defect is that the thin boundary is *disconnected*: no committed driver, no deterministic test exercising the composed path with a fake executable emitting a correlated result.

*Smallest correction.* Commit a thin driver composing `invoke_codex -> validated_result -> observe_hop/run_evidence -> record_hop/reduce_result -> checkpoint_projection`, plus a deterministic test using a fake `executable` that writes a correlated valid result to the `--output-last-message` path. Reuse `vertical.run_one_hop` semantics rather than reimplementing reduction.

*Live invocation needed to close:* No (fake executable suffices).

*Smallest correction.* Add the above as deterministic tests (fake executables and temp state roots; no provider). Keep them proportional -- no generic process-supervision framework.

== Read-only-filesystem failure -- root-cause assessment (no live invocation)

*Observed.* `Error: failed to initialize in-process app-server client: Read-only file system (os error 30)`, Codex exit 1, before any repository mutation or structured result.

*Environment facts (safe local inspection only).* `HOME=/home/stefan` (writable), `~/.codex` present and writable, `CODEX_HOME` unset, `XDG_RUNTIME_DIR=/run/user/1000`, `XDG_CACHE_HOME` unset. On a *non-nested* host these paths are writable, so the app-server would not hit a read-only filesystem there.

*Most plausible cause.* The failing `app-server` init writes runtime/cache/socket/session state (default `~/.codex` / `XDG_RUNTIME_DIR` / XDG cache). The proof was executed *from inside the implementing Codex agent's own `workspace-write` sandbox*; under that outer sandbox everything outside the writable workspace -- including the inherited `HOME`/`CODEX_HOME`/XDG paths the nested app-server needs -- is read-only. The nested `codex exec` therefore failed at app-server initialization, *before* provider contact. This is consistent with the failure preceding any result, timeout, or Git mutation.

*Classification.* (c) experimental-environment / nested-Codex limitation, compounded by (b) incomplete local preflight -- the coordinator does not preflight app-server writable-home/runtime requirements before spawn. It is *not* (a) an implementation defect of the boundary logic and *not* (d) a plain external CLI bug: the same argv is expected to initialize on a non-nested host.

*Representativeness.* Executing the first proof from inside the implementation agent's Codex session was *NOT* representative of the intended coordinator deployment boundary (a normal host/CI process). The failure is a proof-harness/environment error, distinct from the committed product defects S4A-R1/R2.

*Exactness.* The precise write path cannot be pinned without either another invocation or deeper Codex-internal knowledge; available evidence supports "nested-sandbox read-only inherited runtime/home path" but does not isolate the exact file. *Narrowest next experiment a maintainer could separately authorize:* one disposable `codex ... exec` from a *non-nested* host shell (or a pre-provider app-server writable-home/runtime probe in the target environment). This review authorizes neither.
