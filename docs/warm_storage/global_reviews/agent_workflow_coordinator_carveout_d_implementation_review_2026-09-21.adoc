=== 7.2 No route can reach a real provider

`--executable` is always supplied as an absolute path to a test-created file.
The `provider_block` fixture additionally prepends a temporary directory
containing `codex` and `claude` shims that write a sentinel and exit `97`, and
asserts the sentinel is absent at teardown. The adapter's default executable is
the bare name `codex`, so any future omission of `--executable` is caught by
the shim rather than silently reaching a provider.

This machine has both `/usr/local/bin/codex` and a real `claude` on `PATH`, so
the shim is genuinely load-bearing rather than decorative. Across every test
execution performed for this review the sentinel was never created.

The rejection test deliberately passes the blocking `codex` shim itself as
`--executable`; because rejection occurs before dispatch, the shim never runs,
and the sentinel assertion doubles as proof that no dispatch occurred.

== 14. Findings

=== 14.1 BLOCKING

*BLOCKING-1 -- The installed-identity guard fails on the project's own
virtual-environment layout, so the always-on CI path cannot pass.*
_(Category A -- implementation defect.)_

Observation:: `tests/architecture/dependency_guards/test_workflow_coordinator_consumer_boundary.py:136`
asserts `not package_path.is_relative_to(CORE_ROOT)`. The Makefile installs the
pin into `$(VENV) = $(ROOT).venv`, which lies inside `CORE_ROOT`, and
`make test` runs `$(PYTEST)` from that same environment. Reproduced in a
faithful mock tree: `1 failed, 4 passed`, failing exactly on that assertion
while the PEP 610, A3-resource and structural assertions pass. The same file
contradicts itself, since line 109 excludes `.venv` precisely because the
installed package lands inside the Core tree.
Consequence:: The CI `test` job -- which by contract always runs `make
wfc-setup` and therefore never skips these assertions -- fails deterministically
on every push to `main` and every `v*` tag. The documented local path
`make setup && make wfc-setup && make test` fails the same way. The steady
state "CI can resolve the private exact pin read-only and non-interactively,
and the consumer boundary is green" cannot be demonstrated on any sanctioned
path. The guard currently passes only from an out-of-tree environment, which is
not how the repository installs or tests anything.
Smallest bounded correction:: Narrow that one assertion from "not under the
repository root" to "not under the Core *source* tree", keeping the
anti-regression strength. For example, retain
`assert "scripts/workflow_coordinator" not in package_path.as_posix()` and
replace the failing line with a check that the package resolves inside the
active interpreter's environment and outside Core's own sources, such as
`assert package_path.is_relative_to(Path(sysconfig.get_paths()["purelib"]).resolve())`
together with
`assert not package_path.is_relative_to(CORE_ROOT / "scripts")` and
`assert not package_path.is_relative_to(CORE_ROOT / "src")`. No embedded copy
can satisfy that, and an install made *from* the Core tree would still fail the
PEP 610 assertion. One file, one assertion; no architecture reopens.

=== 14.2 IMPORTANT

*IMPORTANT-1 -- D acceptance never exercises the always-on CI path.*
_(Category C -- validation/CI prerequisite gap, with a documentation
component.)_

Observation:: Readiness section 13.1 provisions `fresh_root="$(mktemp -d)"` and
installs Core and the pin into `$fresh_root/core-venv`; sections 13.2-13.4 then
run every focused and full acceptance command through that out-of-tree
interpreter. No acceptance step runs `make wfc-setup` followed by `make test`
using the repository's own `.venv`, which is exactly and only what CI does.
FTR 13.6 correspondingly claims acceptance through "fresh-environment
installation".
Consequence:: The accepted validation recipe is systematically blind to any
defect that depends on the repository-local environment layout. BLOCKING-1 is
one instance and passed every accepted acceptance command while being
guaranteed to fail in CI. Correcting BLOCKING-1 alone leaves the blind spot
intact for the next change to the guard, the Makefile, or the stamp chain.
Smallest bounded correction:: Add one acceptance step that runs, from the Core
checkout, `make wfc-setup` followed by `make test` (or at minimum
`make test-arch` and `make test-integ`) against `$(VENV)`, and record its
result in the D implementation evidence. This needs no architecture change and
no new framework.
