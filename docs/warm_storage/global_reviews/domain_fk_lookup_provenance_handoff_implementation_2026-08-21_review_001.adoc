== 4. Ownership separation and H5 handoff

=== 4.1 FK side

`fk_helpers/provenance.py::_clean_helper_provenance` no longer reads
`enrich_lookup.helper_columns` or any other Lookup record field. Its local work
is now reconstructable as:

. identify and remove FK-owned `helper_columns` provenance;
. observe the post-FK frame column labels;
. ask the Lookup facade whether its sibling record remains truthful;
. apply the returned retain/remove decision while owning the existing
  copy-on-write and structural-pruning sequence.

The remaining literal `enrich_lookup` key in FK is necessary routing and
mutation knowledge for the explicit cross-family handoff; it is not residual
interpretation of Lookup's shape. FK passes the record opaquely and supplies
only the post-mutation observation. It passes no relation, target, key, value
field, or policy object.

The delegation test is intentionally architectural: replacing the facade
predicate with one that always returns `False` causes FK to remove a record
whose helper remains present. That establishes that FK does not recompute or
override Lookup's answer.

=== 4.2 Lookup side

`enrich_lookup/provenance.py::reconcile_enrich_lookup_provenance` reads only:

* Lookup's own `record.helper_columns`; and
* `present_columns`, the post-mutation frame observation.

`frame_name` exists only to make validation diagnostics path-specific. The
function contains no FK relation, fallback, target, policy, formula, or cleanup
mode semantics. Its docstring names FK as the motivating H5 caller while also
stating the general owner-local invariant: the function does not know or care
which transformation removed columns. That is useful non-local rationale, not
reverse semantic coupling.

The semantic knowledge was therefore moved to the correct owner rather than
to a neutral mechanism or another cross-cutting module.

=== 4.3 API/facade design

The facade is narrow and coherent:

* `record` is the smallest coherent Lookup-owned value. Scalarizing its one
  currently-used field into an FK-side extraction would restore the ownership
  leak this slice removes.
* `present_columns` is the necessary and sufficient post-mutation observation.
  Passing the whole frame would be broader; passing the removed FK columns
  would make the predicate FK-shaped.
* a Boolean retain decision leaves mutation, copy detachment, sibling
  preservation, and parent pruning with the caller that already owns the
  composite cleanup publication sequence;
* the name states the Lookup provenance invariant rather than advertising a
  generic metadata cleanup protocol. Although the function itself is a
  predicate, the explicit `retained = ...` call site and return annotation make
  that behavior locally clear.

The facade does not become a generic cleanup API. It operates on exactly one
Lookup provenance record and one frame observation.

== 5. FIND-001 malformed-state review

FIND-001 is resolved coherently and safely.

Validation is Lookup-owned. A mapping record whose `helper_columns` is present
but is not a `list` or `tuple` raises `ValueError` with the specific path
`_meta.derived.sheets[<frame>].enrich_lookup.helper_columns`. This matches the
nearby `_validated_enrich_spec` behavior in `derived_column_policy.py` and
removes the old type-dependent string/dict iteration or opaque `TypeError`.

Accepting both lists and tuples is intentional and consistent with that nearby
validator. Lookup's writer emits a list; accepting tuples preserves the former
iterable behavior without accepting arbitrary strings, mappings, or scalars.
Element stringification and empty/missing `helper_columns` behavior remain the
same as before, so weird-but-previously-valid iterable contents are not newly
rejected.

The apparently asymmetric malformed-state rule is acceptable bounded scope:

* malformed field inside a mapping record -> fail clearly;
* non-mapping record itself -> retain/pass through.

The parent implementation evaluated the predicate only for `dict` records, so
a non-mapping record was retained. Review-001 FIND-001 targeted the malformed
`helper_columns` field, not wholesale validation of every shared-carrier shape.
Preserving non-mapping pass-through therefore avoids an unrelated failure-
contract change and does not make H5's supported valid-state invariant
misleading. A later owner-local validation decision could address the outer
record shape, but it is not needed for this slice.

== 6. Copy, mutation, and failure atomicity

The caller-owned `frames` mapping, DataFrames, and nested metadata remain
unmodified.

`drop_helpers` constructs `out`, detaches the top-level metadata mapping, and
constructs replacement DataFrames before reconciliation. Within
`_clean_helper_provenance`, `derived` and `derived_sheets` remain aliases only
until the first mutation; `copy_derived_path()` detaches both before changing a
sheet entry, and the affected sheet entry is then copied before either producer
subkey is removed. Unchanged sibling entries and a retained Lookup record keep
their prior object identities.

On malformed Lookup provenance, reconciliation occurs before the mutation block
for that sheet. If an earlier sheet has already been cleaned in the local
candidate, all mutations are still confined to detached `out`/`meta` state and
no result is returned. The input mappings and frames remain untouched. Thus
failure cannot partially publish output or mutate caller-owned input.

The pre-existing nested-ownership tests continue to protect copy-on-write,
unchanged sibling identity, retained Lookup-record identity, empty-parent
pruning, and repeated cleanup. The new malformed end-to-end test pins the
exception but does not itself snapshot the caller after failure; direct code
tracing establishes the guarantee, and the neighboring copy tests exercise the
same detachment path. This is adequate and is not a finding.

Repeated invocation, partial overlap, full absence, and total container pruning
remain safe and idempotent at the semantic level.

The package's `__all__` is a sufficient local supported-symbol list for the

infrastructure is justified. The existing AST guard only needs to recognize
all equivalent direct-submodule import spellings.

== 13. Finding

[[impl-rev-001]]
=== IMPL-REV-001 -- MINOR -- Import guard misses `from <family> import <internal_module>`

Affected files/symbols::

* `tests/architecture/domain_transformations/test_no_cross_family_internal_imports.py::_resolved_imports`;
* `GUARDED_INTERNAL_PREFIXES` consumption in
  `test_transformations_do_not_import_other_families_internal_modules`;
* the FIND-003 claim in
  `domain_fk_lookup_provenance_handoff_implementation_2026-08-21.adoc`.

Evidence:: For `ast.ImportFrom`, `_resolved_imports` appends only
`resolve_name(node.module, package_context)` and ignores `node.names`. For the
executable statement
`from spreadsheet_handling.domain.transformations.enrich_lookup import provenance`,
the guard therefore records only
`spreadsheet_handling.domain.transformations.enrich_lookup`, which is not one of
the three internal prefixes. An independent probe printed that package root and
`detected=False`; importing the statement then produced the actual module
`spreadsheet_handling.domain.transformations.enrich_lookup.provenance`.

Concrete failure mode:: A future transformation-family caller can import
`operation`, `policy`, or `provenance` through the package-plus-imported-name
spelling and couple directly to that internal module while the architecture
test remains green. The narrow facade may then widen silently, defeating the
specific FIND-003 protection this slice claims.

Smallest correction:: Extend `ImportFrom` resolution to consider the qualified
candidate formed by the resolved package plus each imported name when that
candidate matches a guarded internal prefix. Add a focused parser/guard
regression for at least
`from spreadsheet_handling.domain.transformations.enrich_lookup import provenance`
(and preferably parameterize the three guarded Lookup module names). Preserve
the current exemption for within-family imports and the permitted FK import of
`reconcile_enrich_lookup_provenance` from the package facade.

Blocks slice closure:: *yes*. This is not a runtime ownership or compatibility
defect, but FIND-003 was an explicit required correction for the authorized
first slice. It does not warrant rework of the runtime handoff.
