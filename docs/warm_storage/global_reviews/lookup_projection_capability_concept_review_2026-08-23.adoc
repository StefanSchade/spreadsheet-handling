=== 3.2 Output-naming correction -- MATERIAL finding (FIND-1)

The note's "Correction to the original sketch" paragraph (section 3.1,
labelled `Current fact, re-derived this session`) is independently checked
line-by-line and its *narrow* claims are true:

* `fk_helpers/enrich.py:129-136` calls `core.fk._materialize_fk_helpers`
  with a hardcoded literal `helper_prefix="_"` -- confirmed.
* That parameter only feeds the dict-shaped fallback branch inside
  `_materialize_fk_helpers` (`core/fk.py:304-317`); the actual call path from
  `enrich_helpers` always passes `FKDef` namedtuples built by
  `iter_relation_fk_defs` (`fk_helpers/policy.py:119-144`), which take the
  `else` branch (`core/fk.py:313-317`, `helper_col = fk.helper_column`) and
  never reach the `fk.get("helper_column") or f"{helper_prefix}..."`
  fallback at all. So for the actual `add_fk_helpers` call path the hardcoded
  `"_"` is not merely inert-but-present, it is unreachable -- an even
  stronger form of the note's own point than the note states.
* `remove_fk_helpers`'s `prefix` parameter is dead:
  `del prefix  # retained for backwards-compatible step binding only`
  (`fk_helpers/drop.py:49`) -- citation exact.
* `reorder_fk_helpers`'s `helper_prefix` parameter is dead:
  `del helper_prefix  # retained for backwards-compatible step binding only`
  (`domain/transformations/helpers.py:219`) -- semantically confirmed, but
  the note's own citation ("`drop.py`: `del prefix ...`") attributes *both*
  quotes to `drop.py`. Only the `remove_fk_helpers` quote is in `drop.py`;
  the `reorder_fk_helpers` quote is in a different file
  (`domain/transformations/helpers.py`) with a different parameter name
  (`helper_prefix`, not `prefix`). Citation-precision slip only (FIND-2,
  MINOR) -- both underlying dead-parameter facts are independently true.

The note then generalizes these three (accurate) observations into: *"FK's
real output-naming mechanism is the declared `helper_columns[].column` field
in relation policy -- config-schema data belonging to the relation, not a
live `helper_prefix` knob at any layer."* This generalization is false.
`configure_fk_helpers` -- one of the note's own two named "producer steps"
that write the durable relation -- has a live, actively used
`helper_prefix: str = "_"` parameter (`domain/helper_policies.py:100`) that
is the *sole* mechanism by which that step computes the `column` value it
writes into `helper_columns[]`:

[source,python]
----
# domain/helper_policies.py:162-170 (_v2_relations_from_explicit_policies)
helper_prefix = str(policy.get("helper_prefix", "_"))
helper_columns = [
    {"column": f"{helper_prefix}{target_frame}_{field}", "target_field": field}
    for field in helper_fields
]
----

`configure_fk_helpers` currently exposes *no other* way to set a helper
column's name -- there is no per-field literal-alias parameter anywhere in
its signature (`domain/helper_policies.py:91-148`); `helper_prefix` (global,
or per-target via `cfg.get("helper_prefix", helper_prefix)` at line 311) is
the only naming lever a caller of this producer step has. `infer_fk_relations`
has the identical live mechanism for its heuristic path
(`domain/fk_relations.py:36,117,155-166`:
`"column": f"{helper_prefix}{target_frame_name}_{field}"`). Both are
exercised by the test suite (e.g. `tests/unit/domain/test_fk_relations_inference.py`,
`tests/unit/pipeline/test_pipeline_basic.py:29,90`); neither is dead code.
`tests/unit/domain/test_fk_relations_inference.py:217-227`'s own comment
confirms the narrower, correct framing: the prefix's effect "now lives where
it is actually consumed: the materialized `helper_columns[*].column` name" --
i.e. `helper_prefix` is not a *stored relation field* any more (true, and
this is what that test protects), but it is very much a live *parameter*
computing that field's value at configuration time. The note's own citation
discipline (checking `add_fk_helpers`, `remove_fk_helpers`,
`reorder_fk_helpers`) never reached the configuration layer where the live
knob actually lives, then generalized past what it checked.

*Why this rises to MATERIAL rather than a wording nit:* the active
surface-consolidation FTR's own Scope explicitly names this exact question
("Support explicit helper output aliases/names/prefix semantics (currently
only `add_fk_helpers`'s `helper_prefix` provides this)" --
`FTR-FK-REFERENCE-HELPER-SURFACE-CONSOLIDATION-P5.adoc:211-212`), and the
Cycle-1 assessment already flagged that specific FTR attribution as
imprecise (its Section 4 naming row: "current runtime does not compute
helper names from a prefix parameter at all"). This note's "not... at any
layer" repeats and *strengthens* the same imprecision independently derived
this session rather than correcting it, in the one area the review brief
identified as previously wrong once. A future surface-consolidation designer
relying on this note could reasonably conclude that no live prefix-based
naming mechanism survives anywhere in the FK family to reconcile against
Lookup's (currently nonexistent) aliasing capability -- when in fact
`configure_fk_helpers`'s *only* naming affordance today is exactly that
prefix template, a materially relevant fact for the FTR's own "achieve the
capability set required by consumers" method step. Note this finding is
independent of, and does not adjudicate, whether the Cycle-1 assessment's
parallel Section 4 wording should itself be revised -- that is Cycle-1's own
review's business, not this one's.

*Recommended correction (not performed by this read-only review):* narrow the
closing sentence to the layer actually checked, e.g. "...not a live
`helper_prefix` knob at the materialization/reorder/remove-primitive layer
(`add_fk_helpers`, `remove_fk_helpers`, `reorder_fk_helpers` all read only
the declared field); `configure_fk_helpers` and `infer_fk_relations` do still
compute that field's default value from a live `helper_prefix` parameter at
configuration time, and currently offer no other way to name a helper
column."

=== 4.1 "Non-durable helper policy" -- MINOR finding (FIND-3)

Section 3.2's opening `Current fact` paragraph describes Lookup's optional
policy as "an optional non-durable helper policy." This is imprecise:
`configure_lookup_helpers` persists the policy into
`_meta.helper_policies.lookup.<lookup>` (`domain/helper_policies.py:80-88`)
by exactly the same `_meta`-persistence mechanism FK's relations use, and it
survives across pipeline steps within a run identically to FK's durable
relation list. It is not "non-durable" in the sense the codebase's own
vocabulary uses that word elsewhere (persisted vs. transient); what
distinguishes it from FK's relation policy is that it is not
centrally-merged / conflict-resolved across producer calls and carries no
relation-shaped cross-call identity -- which is exactly what the note's own
section 4 says two paragraphs later, correctly, calling it "a standing
policy." The two characterizations ("non-durable" vs. "standing") are in
mild tension within the same note. Low practical impact -- section 4's
sharper language is what a reader would likely rely on -- but it is a
`Current fact` label attached to an imprecise claim, worth a one-word fix
("standing but not centrally-merged" or similar) rather than "non-durable."

== 5. Capability-boundary falsification (section 5 of the note)

Testing the note's central claim -- durable, centrally-merged, multi-operation
relation vs. per-call-authoritative, non-merged projection -- against DMC's
ownership axes (user meaning, semantic state, authority, lifecycle, inverse,
compatibility, handoffs):

* *User meaning*: genuinely different ("materialize my declared relation's
  helpers" vs. "produce this one explicit projection now") -- supported.
* *Semantic state*: genuinely different topology -- a cross-call-merged,
  conflict-resolved list (FK) vs. a per-key, wholesale-overwrite dict
  reconciled only against the current call (Lookup) -- supported, verified
  directly in sections 3-4 above.
* *Authority*: different -- FK's naming authority is the relation entry
  (subject to FIND-1's correction about how that entry's default is
  computed); Lookup has no naming authority at all (no alias field exists in
  `helpers`, confirmed) and the *call* is authoritative for output identity.
* *Lifecycle*: FK spans five owner-local operations sharing one durable
  state; Lookup has no dedicated validate/reorder step (DCP-mediated, per
  Cycle-1 section 7, cited only as historical evidence here, not
  re-litigated). This asymmetry is real but, as the note itself concedes in
  section 4, does not by itself newly prove separate ownership -- it could
  equally read as "Lookup's lifecycle is less complete," which is exactly
  the reading the note explicitly declines to over-claim.
* *Inverse*: both none, confirmed identically for both capabilities
  (section 6 below).
* *Handoffs*: FK -> Lookup's sibling-record reconciliation on removal
  (`enrich_lookup.reconcile_enrich_lookup_provenance`, Cycle-1 section 4's
  Cleanup row) is a real, asymmetric, one-directional handoff; the note does
  not misstate or omit it in a way that changes its conclusion.

*Verdict:* the distinction is *strongly supported* as an observable current-runtime
distinction (not merely rhetorical or a difference in configuration
carrier shape), consistent with -- not independently re-proving beyond --
Cycle-0/Review-001/Cycle-1's already-established separate-ownership
conclusion. The note is careful to frame it exactly this way ("reconfirms,
rather than newly proves") and does not overclaim DMC ownership status from
this evidence.

=== 6.1 "Lookup Projection" terminology -- MINOR finding (FIND-4)

DMC's own working definition of *projection*
(`05_domain_maintainer_contract.adoc`, `dmc-working-model`) is not a neutral
synonym for "one-way derivation": it specifically "defines the authority,
precedence, conflict, and reconstruction semantics by which edits are mapped
back toward canonical state." The same DMC document elsewhere draws an
explicit, named contrast: "A one-way extraction needs no invented inverse. A
non-projection needs no fake projection precedence contract"
(`dmc-state-lifecycle`, adjacent to the projection-lifecycle guidance the
note cites in its own section 6). Current Lookup (like current FK) has no
inverse at all -- confirmed independently in section 5 above and conceded by
the note's own section 5. By DMC's stricter internal vocabulary, current
Lookup is arguably closer to what DMC itself calls a "one-way extraction"
than to a "projection." The note quotes DMC's edit-mapping-back clause
verbatim in its own naming-question paragraph (section 3.2) -- so the tension
is visible in the note's own text -- but does not name or engage the
"one-way extraction" alternative, and does not flag that its chosen label
imports inverse/editing connotations DMC's canonical vocabulary structurally
carries and current Lookup does not possess. This does not undermine the
note's explicit "descriptive label only... does not canonicalize the name"
disclaimer, which remains adequate cover, but the note would be sharper if
it named the tension explicitly rather than only citing the clause that
creates it. MINOR: a terminology-precision improvement, not a substance
correction.
