== Verdict

*HUMAN ARCHITECTURE DECISION REQUIRED BEFORE PROOF AUTHORIZATION.*

All seven findings are closed / adequate. No new material direct regression was
introduced. The corrected proposal is technically coherent. The single remaining
gate is *not a proposal defect*: by adopting the S4-READY-R3 hardening (coordinator
state mechanically *outside* the agent-writable workspace) as a mandatory adapter
boundary -- and baking it into the disposable-proof profile -- the correction
surfaces a genuine, bounded conflict with the accepted *WFC-PERSIST-02*
repository-local-ignored state-root contract. The proposal correctly declines to
resolve this unilaterally and records it as "authority reconciliation required
before runtime implementation." Because the disposable proof cannot run without
the coordinator placing its trusted resume state somewhere, and that placement is
exactly the contested point, this bounded persistence-authority decision must be
made by the maintainer before proof authorization. It is a maintainer architecture
decision, not a material contract *correction* and not a defect.

== Finding dispositions

=== S4-READY-R1 -- CLI syntax -- CLOSED

The command (section 1) now reads `codex --ask-for-approval never exec ...`, with
`--ask-for-approval` correctly positioned as a *top-level* option before the
subcommand. Section 1's bullet now states accurately that `codex --help` documents
`-a, --ask-for-approval`, `codex exec --help` does not, `codex --ask-for-approval
never exec --help` exits successfully, and placing the option after `exec` is a
parse error.

Re-verification (read-only, no provider):

[source,text]
----
$ codex --ask-for-approval never exec --ephemeral --json --color never \
    --sandbox __bad__ --model gpt-5.6-terra -c 'model_reasoning_effort="medium"' \
    --cd /tmp --output-schema /tmp/s.json --output-last-message /tmp/m.txt - </dev/null
error: invalid value '__bad__' for '--sandbox <SANDBOX_MODE>'
  [possible values: read-only, workspace-write, danger-full-access]
  -> exit 2   # clap accepted the global-flag placement AND the whole exec option
              #   set, failing only on the deliberately-bad --sandbox value
$ codex --ask-for-approval never exec --help >/dev/null ; echo $?   # -> 0
----

The deliberately-invalid `--sandbox __bad__` forces clap into value validation,
proving the global-flag placement and the entire `exec` option set are recognized;
only the bad value errors, at parse time, before any provider connection. The
non-interactive approval argument remains valid. *CLOSED.*

=== S4-READY-R2 -- process-group termination -- CLOSED

Section 5 now requires launching the subprocess in its own process group/session
(`start_new_session=True`), signalling the *process group* for graceful
termination at timeout/cancellation, waiting one fixed short grace period, then
killing the group if any descendant remains -- "Descendants therefore cannot
silently survive a parent timeout" -- and entering charged `reconcile_required`
for any uncertain timeout/cancellation/kill. All required elements are present as
a readiness contract (implementation is correctly not required here). *CLOSED.*

=== S4-READY-R3 -- trusted file placement -- CLOSED (mechanism); raises a bounded authority decision (see WFC-PERSIST-02 below)

Section 4 now requires the result schema, result-message file, dispatch marker,
Run snapshot, and all coordinator transient state to be *outside* the
agent-writable repository/workspace, with no `--add-dir` re-exposure, and states
the correct reasoning that `--output-schema` / `--output-last-message` are
parent-Codex I/O paths that do not need to sit inside the agent workspace (I
confirm this: the sandbox restricts model-issued shell commands, not the Codex
parent's own file I/O, so external paths are feasible and remove the files from the
agent's writable reach). Section 6 carries the same placement into the disposable
proof profile ("no agent-writable coordinator state root"). The trust boundary is
now mechanical rather than post-hoc-validation-only. *The R3 mechanism is CLOSED.*

This mechanism creates the WFC-PERSIST-02 tension assessed next; the correction
records it explicitly (section 4 and section 7) and does not silently change the
FTR.

==== WFC-PERSIST-02 external-state tension -- classification: (B) explicit but bounded maintainer architecture decision required before Slice-4 authorization

Grounding in accepted authority:

* *WFC-PERSIST-02* (FTR section 8.2): operational state "shall live on persistent
  local storage at a configured, *repository-specific root ignored by tracked
  repository policy*," and "Before the first Run write and each Hop, preflight
  shall verify *Git's ignore resolution* for the candidate path and fail closed ...
  if unignored; a local exclude alone is insufficient."
* Accepted architecture section 8 restates this with the `git check-ignore
  --no-index` mechanism and the "same-checkout resume promise."

The mandated *cleanliness mechanism* -- verification via Git's ignore resolution --
presupposes an in-worktree path that Git can evaluate as ignored. A location moved
*entirely outside* the repository/workspace (as R3 requires for a mechanical
sandbox-exclusion boundary) cannot be verified by `git check-ignore` as "ignored";
it is simply not in the repository. Thus the corrected placement satisfies
WFC-PERSIST-02's protective *intent* more strongly (external state categorically
cannot dirty the tracked worktree) while not matching its *specific mandated
preflight*.

Why (B) and not (A): WFC-PERSIST-02 is emphatic and mechanism-specific ("shall
verify Git's ignore resolution ... a local exclude alone is insufficient"), and the
proposal's own authors elevated the conflict to "authority reconciliation required
before runtime implementation" and listed it under Unresolved decisions. A
re-reviewer should not overrule that considered deferral by declaring the accepted
contract's mechanism merely illustrative. The reconciliation touches the wording
and intent of an accepted requirement and its interaction with the newly-recognized
live-agent workspace-write reality; that is a maintainer call, not something an
implementer resolves silently within existing authority.

Why (B) and not (C): the collision is *bounded and Slice-4-specific* -- it arises
only because the live agent under `workspace-write` makes an in-repo-ignored state
root agent-writable. It does not contradict or invalidate the accepted design; it
is reconcilable by a small, bounded decision (for example: clarify WFC-PERSIST-02 to
permit an external, sandbox-excluded coordinator-state location carrying an
equivalent non-`git check-ignore` cleanliness/exclusion guarantee and a preserved
same-checkout-correlation property; or explicitly accept external state for the
disposable proof). No material FTR/architecture rewrite is forced.

Consequence for authorization: because the disposable proof is itself a runtime
execution of the coordinator adapter, and the adapter must place its trusted resume
anchors (WFC-PERSIST-01/06) somewhere, the maintainer must settle this bounded
placement question before authorizing the proof. This is the sole gate remaining.

Observation (not a demand): the correction chose to make external placement a
*mandatory* adapter property and to bind it into the *proof* profile. That is
defensible -- it is exactly the stronger R3 boundary -- but it is what couples the
proof to the WFC-PERSIST-02 decision. Had the disposable proof instead used the
FTR-compliant in-repo-ignored root (accepting R3's residual agent-writability for a
benign, disposable, WFC-SEC-01-trusted N=1 task, as the prior review noted was
tolerable for the proof), the proof could proceed under existing authority with
external placement deferred to routine use. Choosing between those two is itself the
maintainer's bounded decision; the re-review does not make it.

=== S4-READY-R4 -- Hop accounting -- CLOSED

The revised table no longer equates child-process start with provider acceptance.
Pre-spawn command/parse, executable, login-status, repository/HEAD, and external
schema/temp-preparation failures are classified No Hop under WFC-AUTO-03; a
post-spawn failure that *positively establishes* non-acceptance is No Hop;
positively observed provider/model acceptance (including a valid correlated result)
is charged; genuinely uncertain acceptance is conservatively charged under
WFC-AUTO-02; cancellation/timeout/kill/unreadable state is charged
`reconcile_required` under WFC-FAIL-04. Section 5 and section 7 state explicitly
that no undocumented JSONL acceptance semantics are used and that a started child is
charged "only on positive acceptance evidence or genuinely uncertain acceptance,
never merely because it started." No hidden retry.

Acceptability of the remaining unknown acceptance signal for a first disposable
proof: acceptable. The default for any post-spawn state that cannot positively
disprove acceptance is to charge; the only No-Hop-after-spawn path requires
non-acceptance to be actually established. Therefore no real provider invocation can
occur in the proof without a Hop being conservatively accounted; the only residual
effect of the unknown signal is possible *over*-charging in ambiguous cases, which
fails safe (toward stopping). *CLOSED.*

=== S4-READY-R5 -- Git authority decision material -- DECISION MATERIAL ADEQUATE

Section 2's `.git` row now states Option A effectively grants the entire `.git`
directory -- refs and `packed-refs`, reflogs, object database, lock files, and
`.git/hooks` -- and that existing post-Hop checks "do not establish integrity of all
Git metadata, especially hooks and reflogs." Post-Hop observation is therefore not
falsely claimed to establish full `.git` integrity. Section 3 preserves the
disposition: Option A / disposable proof acceptable; Option A / routine real
repository *not yet accepted as safe* (requiring stronger isolation restricting
`.git` authority, materially expanded Git-integrity verification, or explicit
maintainer acceptance of the broader `.git` trust); Option B changes the accepted
ownership model, conflicts with section-11.4, and must not be an incidental adapter
detail. No trusted-commit-helper, bubblewrap, delegated-identity, or broker
mechanism is introduced as accepted architecture. *DECISION MATERIAL ADEQUATE.*

Sections 3 and 6 now require a broad `.git/**/*.lock` post-Hop residue scan,

Section 6 now explicitly recognizes "correct deterministic commit + valid
