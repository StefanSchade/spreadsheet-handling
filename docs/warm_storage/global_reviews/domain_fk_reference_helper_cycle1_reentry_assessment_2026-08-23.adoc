== 3. Corrected genealogy implications

*Historical evidence, from the FTR's 2026-08-23 section and independently
consistent with the roadmap.* FK materialization capability
(`apply_fks`/`add_fk_helpers`) genuinely predates `enrich_lookup` by roughly
seven months at the runtime-capability level. But once both are considered as
Domain-transformation-layer citizens, their formalizations are four days
apart (`a83c29e` vs `8e620b4`), and their current public names
(`add_fk_helpers`, `validate_fk_helpers`, `add_lookup_helpers`) were coined
together in one commit (`d9bbae8`) one day after Lookup's Domain-layer
introduction. `enrich_lookup`'s own founding commit message states its
purpose was to replace ad hoc consumer-side enrichment plugins with
declarative YAML config -- it was not conceived as an FK-helper alternative.

*Inference.* This genealogy is evidence about code-age sediment, not about
semantic ownership or which surface should survive a future consolidation.
It neither strengthens nor weakens the Cycle-0/Review-001 separate-ownership
conclusion (Section 5 below), which was derived from current semantics, not
history. It does, however, undercut one specific argument a future
consolidation design might be tempted to use ("FK is older, therefore more
canonical") -- the "older" claim is true only at the pre-Domain-layer
capability level, not at the public-surface level where the two names are
literally the same age.

== 5. Semantic-owner analysis

*Historical evidence, independently re-derived and confirmed by Review 001,
not revisited de novo here because nothing evidenced since changes it.*

FK Relation Helpers answers: "given a declared, durable relation between two
frames, keep selected attributes of the related record visible beside the FK
reference, across materialize/layout/validate/direct-drop, without inferring
identity from column names." Lookup Enrichment answers: "given one explicit,
self-contained request naming a source, a lookup frame, and a key pairing,
project selected lookup attributes into a named output, once, with no
durable relation memory beyond the projection's own record."

These remain genuinely different domain transitions, not two spellings of
one operation:

* FK's Intent is a standing *relation* (durable, centrally
  conflict-resolved, consumed by five different owner-local operations over
  its lifetime); Lookup's Intent is a standing *policy* that participates in,
  but does not itself constitute, a per-call *projection request* -- the
  call, not the policy, is authoritative for each run's output identity.
* FK has an owner-local validation capability (`validate_fk_helpers`);
  Lookup has none (Section 4). This is not symmetric duplication to
  eliminate -- it is a capability Lookup is missing, not one FK has that
  should be deleted.
* Neither has a data-level inverse (Cycle-0 D.4, reconfirmed): helper-cell
  edits are discarded on both sides; "cleanup" means artifact-identity
  reconstruction, not data reconstruction, for both.

No new evidence surfaced in this re-entry that would flip the Cycle-0/Review
001 separation conclusion. The corrected genealogy (Section 3) is orthogonal
to it: age says nothing about current semantic shape.

== 6. Worldbuilding forcing cases (historical evidence, not re-verified this cycle)

* `places.region_id -> regions.id` forces `_regions_name`/`_regions_kind`
  because `places` already owns `name`/`kind`. `add_lookup_helpers` cannot
  express this today (Section 4's naming-asymmetry row): it has no alias
  field and `_check_column_conflict` correctly rejects the raw names.
* `story_group_matrix` (`story_id -> stories.id`, output
  `story_group_matrix_view`, `title` before key) is a Lookup-only shape:
  separate output frame, no relation declaration, no durable FK-style
  identity.

*Inference, refining Section 4's naming-asymmetry finding.* The Places ->
Regions case is real and not a preference example -- but it is forced by a
**missing alias field in Lookup's config schema**, not by anything about FK's
relation-declaration lifecycle being semantically required. A hypothetical
`add_lookup_helpers` with a per-field output-name option could express this
same case without adopting FK's durable-relation Intent shape at all. This
matters for Section 8/10: it means the forcing case is evidence for "Lookup's
config surface needs an aliasing capability" (a scoped, surface-consolidation
-- not Family-cycle-1 -- design question), not evidence that FK and Lookup
are the same capability wearing different names, and not evidence for which
one should be "canonical."

== 7. F-002 analysis

*Observed current fact, directly re-inspected in full at this baseline; H5's
implementation record explicitly left this untouched and nothing since has
touched it.*

`derived_column_policy.py` still independently reimplements, with zero
import from `enrich_lookup`:

* provenance-shape parsing and validation for the `enrich_lookup` record
  (`_validated_enrich_spec`, mirroring but not reusing
  `enrich_lookup/provenance.py`'s validation style introduced by H5 for the
  *sibling* `helper_columns`-only case);
* join-key-shape resolution from the *written* provenance record
  (`_validated_mismatch_keys`, `_validated_symmetric_on`,
  `_validated_single_key`) -- structurally parallel to, but independent of,
  `enrich_lookup/policy.py::_resolve_join_keys`/`_ResolvedKeys`, which
  resolves the same symmetric/asymmetric distinction from *call-time
  parameters* rather than from the already-written record;
* full value-mismatch checking (`_check_enrich_lookup_values`,
  `_canonical_value_map`, `_column_mismatch_indices`), including duplicate
  handling, missing-key detection, and row-level comparison against the
  lookup frame.

This is roughly 200 lines (measured directly against current
`derived_column_policy.py`, slightly larger than Review 001's "~180 lines"
estimate, consistent within measurement variance) of Lookup-semantic logic
that Lookup itself does not expose as a reusable, owned function -- and,
per Section 4's validation row, Lookup has **no owned validation capability
of its own at all** to expose. FK's relation-shape knowledge, by contrast, is
correctly *not* reimplemented here: `_durable_fk_policy_helper_names` calls
the public `resolve_v2_fk_relations` facade.

*Answering the assessment's central F-002 question (A/B/C/D):*

F-002 is **(A) a straightforward cross-owner knowledge leak that should be
fixed next**, and simultaneously **(D) safely separable regardless of which
surface ultimately survives consolidation** -- not (B) evidence that Lookup
is incoherent, and not (C) coupled to surface consolidation.

* Not (B): the leak is DCP's, not Lookup's. Lookup's own module boundary
  (`enrich_lookup/policy.py`, `operation.py`, `provenance.py`) is internally
  coherent; nothing about F-002 shows Lookup failing to own its own facts.
  It shows a *different* module (DCP) failing to consume them.
* Not (C): DCP's reimplementation operates entirely on the *already-written*
  transient provenance record shape -- the same shape Lookup's own writer
  (`operation.py::_write_provenance`) produces today. Whatever a future
  consolidation decides about the *public* surface name/vocabulary
  (`add_fk_helpers` vs `add_lookup_helpers` vs a merged name), Cycle-0's
  high-confidence, twice-independently-reviewed conclusion is that Lookup
  Enrichment survives as a distinct semantic capability with its own Intent
  shape (Section 5). As long as that holds, the *internal* module boundary
  F-002 would fix -- DCP calling Lookup-owned parsing/validation instead of
  reimplementing it -- does not depend on, or presuppose, which public name
  wins. This is the identical relationship H5 already established one level
  down: H5 fixed a boundary between two *already-separated* owners without
  waiting for, or deciding, surface consolidation.
* (D) also holds in the narrower sense: even in the limit case where
  consolidation eventually changes the provenance *shape* itself, fixing
  F-002 now does not make that harder -- it makes it easier, because the
  shape-parsing/validation logic would then live in exactly one place
  (Lookup's own module) instead of two that must be kept in sync by hand.

*Concrete risk of not fixing it.* A reader or future implementer, having
seen H5 close the smaller predicate, can reasonably (and per Review 001's
FIND-002, already once did in the Cycle-0 artifact's own first draft)
conclude the FK/Lookup cross-owner-knowledge problem is solved. It is not:
the larger instance survives untouched, and it is the concrete blocker the
roadmap itself names for Family cycle 1's exit criteria (Section 9 below).

== 8. Surface-consolidation analysis

*Reading the FTR as an active problem statement, not an accepted design*, per
the assessment's own instruction.

The FTR's Section D ("required consolidation method") and Acceptance criteria
describe a full public-surface, vocabulary, and consumer-migration design
cycle: choose one canonical name, decide FK-vs-lookup vocabulary, define
collision/in-place/output-naming semantics for the surviving surface, decide
the Trusted-Ingress formula-producer target, and migrate Worldbuilding. This
is materially larger and more decision-heavy than a Family-cycle-1 "remove
implicit ontology" slice -- it is a `dmc-semantic-decisions`-shaped exercise
(DMC Section 4: "decide semantics, public surfaces, and configuration"),
closer in kind to the roadmap's own Family cycle 4 (structural
refactoring/public surface) than to Family cycle 1.

*Testing the FTR's working hypothesis ("`add_fk_helpers` is likely the
surviving surface") against this cycle's own capability-matrix evidence
(Section 4):*

* *Weakened, on the specific naming-alias argument.* The FTR's Context
  section attributes FK's output-aliasing advantage to `helper_prefix`; that
  parameter is confirmed inert. The actual mechanism is a config-schema
  field (`helper_columns[].column`) that has no architectural dependency on
  FK's durable-relation model -- it is a generic "declared output name per
  projected field" affordance that Lookup's `helpers` schema could
  independently gain (Section 6). This specific piece of evidence for "FK
  is more capable, therefore canonical" does not survive close reading.
* *Neither strengthened nor weakened by the corrected genealogy* (Section 3):
  age is explicitly not ownership evidence, and the FTR's own text already
  says so.
* *Not addressed either way by F-002*: F-002 is orthogonal to which surface
  survives (Section 7).
* *New, previously untabulated asymmetries surfaced this cycle cut in both
  directions*: FK silently skips a collision where Lookup raises (Section 4)
  -- if anything this favors Lookup's contract as stricter/safer, not FK's;
  Lookup has no owned validation capability at all where FK does (Section 4)
  -- this favors treating FK's validation lifecycle, not its relation model,
  as the piece worth generalizing.

*Conclusion on Section 6's outcome menu.* Current evidence is insufficient to
confirm, weaken to rejection, or replace the working hypothesis outright; it
is weakened on one specific sub-argument (aliasing) and otherwise unmoved.
More importantly, the working hypothesis frames the question as "which
surface wins," but Cycle-0/Review-001's separation conclusion (Section 5)
means the more accurate framing may be "should there be one user-facing verb
for this class of helper-column operation even though two differently-shaped
Domain capabilities continue underneath it" -- a UX/compatibility question
distinct from the semantic-ownership question this pilot already answered.
That reframing is itself a piece of evidence surface consolidation needs, not
something this bounded re-entry may decide.

*Is consolidation ready to be the next slice?* No. It requires its own
bounded DMC application (public-surface naming, config-schema decisions,
Trusted-Ingress producer choice, consumer migration plan) that the FTR
itself explicitly defers ("Do not propose an implementation yet"). Attempting
it as "the next Family-cycle-1 slice" would not fit Family cycle 1's own
goal ("remove implicit global classifications... hidden cross-family
knowledge") -- it is a different, larger kind of work.

== 10. Candidate next slices

=== Option A -- F-002 first

* *Semantic purpose:* make Lookup Enrichment the sole owner of its own
  provenance-shape interpretation and value-mismatch semantics, mirroring
  H5's already-accepted pattern one level up in size: `enrich_lookup` grows
  owned functions (shape/key parsing, mismatch checking) that
  `derived_column_policy.py` calls instead of reimplementing.
* *Dependencies:* none beyond H5's already-accepted precedent and the
  already-in-place cross-family import guard (`enrich_lookup` is already in
  `GUARDED_INTERNAL_PREFIXES` since H5's FIND-003 fix), which would need to
  keep covering whatever new public/internal facade this slice adds.
* *Uncertainty removed:* closes the roadmap's own named blocker for Family
  cycle 1's exit criteria for this family; removes the concrete risk
  (Section 7) that a reader mistakes the smaller H5 fix for having solved the
  whole cross-owner-knowledge problem.
* *Reversible/local:* yes -- an internal module-boundary move behind
  unchanged registered-step names, YAML parameters, metadata shapes, and
  (with care) error messages/finding rule types, exactly like H5.
* *Blast radius:* one composite module (`derived_column_policy.py`) and one
  owner module (`enrich_lookup/`); no public surface, no consumer migration,
  no registry change.
* *Risk of prematurely choosing surface ownership:* none -- operates
  entirely below the public-surface line (Section 7's "not (C)" argument).
* *Fit with Family cycle 1:* direct match -- this is exactly "remove...
  hidden cross-family knowledge."

=== Option B -- surface-consolidation assessment/design first

* *Semantic purpose:* decide the FK/Lookup public-surface question the FTR
  poses.
* *Dependencies:* its own bounded DMC semantic-decision cycle (naming
  vocabulary, config-schema decisions for aliasing/collision, Trusted-Ingress
  producer target, Worldbuilding migration plan) -- explicitly not yet done
  by the FTR itself.
* *Uncertainty removed:* would resolve the FTR, but at the cost of a much
  larger, higher-risk, consumer-facing design decision undertaken before the
  smaller, already-scoped item (F-002) is closed.
* *Reversible/local:* no -- a public rename/removal decision with real
  consumer migration cost (Cycle-0 E.2/E.3).
* *Blast radius:* large -- public API, config schema, Trusted-Ingress
  certification target, Worldbuilding.
* *Risk of prematurely choosing surface ownership:* this *is* the
  surface-ownership choice; doing it now, ungated by a completed Family
  cycle 1, risks designing the consolidation against a Domain area that still
  has an acknowledged internal ownership leak (F-002) coloring what "the
  Lookup capability's real surface area" looks like.
* *Fit with Family cycle 1:* poor -- this is closer to Family cycle 4
  (structural refactoring/public surface) in kind and size, not "remove
  implicit ontology."

=== Option C -- a smaller preparatory capability/boundary slice

No such slice was found to be independently evidenced as necessary before
Option A. Two candidates were considered and rejected:

* *Extend Lookup's config schema with an output-alias field* (motivated by
  Section 6/8's naming-asymmetry finding): this is explicitly
  surface-consolidation Scope work per the FTR's own Section D method
  ("achieve the capability set required by consumers" is method step 4,
  after "choose ONE canonical surface" step 1). Doing it piecemeal now would
  pre-empt the FTR's own required sequencing without the naming/vocabulary
  decision that should come first. Rejected.
* *A dedicated `validate_lookup_helpers` step* (motivated by Section 4/7's
  finding that Lookup has no owned validation capability at all): plausible
  future work, but not evidenced as a *prerequisite* for F-002 -- F-002's fix
  only needs Lookup to expose the parsing/checking *functions* DCP would
  call, not a new registered pipeline step. Making it a registered step is a
  larger, separable public-surface decision of its own. Rejected as a
  prerequisite; noted as a plausible independent follow-up.

=== Recommendation

Option A. It is the only candidate that is simultaneously: the roadmap's own
named blocker, bounded, reversible, evidenced in full at the current
baseline (Section 7), and structurally identical in kind to the already
twice-independently-accepted H5 pattern -- it does not require inventing a
new kind of DMC judgment call, only applying an accepted one at the next
scale.
