deterministically with a visible reason; they shall never silently substitute a
sibling checkout. CI always runs `wfc-setup` and therefore never skips them.
The ordinary fresh Core setup remains:

[source,shell]
----

----

`wfc-setup` obtains the exact revision from the configured GitHub repository
and builds/installs it with pip. Every SSH-based WFC install path shall set
`GIT_SSH_COMMAND='ssh -o BatchMode=yes'` and `GIT_TERMINAL_PROMPT=0`, so absent
credentials or an inaccessible pin fail non-interactively. Network access was
already required for normal PyPI dependency setup; only the opt-in WFC action
additionally requires read access to the private standalone Git repository.

The Core CI test job shall install ordinary dependencies and then run
`wfc-setup` with a dedicated read-only `WFC_READ_DEPLOY_KEY` secret. The
corresponding public key must be a read-only deploy key on the standalone
repository. CI pins GitHub host keys in
the same bounded manner already used by Core's documentation deployment. No
write credential, branch checkout, tag, package registry, or GitHub API mutation
is required. Missing/empty secret, host-key mismatch, inaccessible commit, or
pin-resolution failure stops the job.
