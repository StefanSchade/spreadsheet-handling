== 5. F4 -- digest-only runtime content identity

Verified in WFC-PROMPT-05 and 13.3 "Loader": `importlib.resources` read bytes ->
missing/unreadable refuse -> SHA-256 != `REVIEWED_SHA256` refuse -> strict UTF-8
decode -> loaded text. The reviewed SHA-256 is declared the sole runtime
content-identity check. ID, version, resource path/name are module/provenance
constants; the prologue is human-readable content with one positive test "not
runtime parsing". Empty-bytes, wrong-ID, unsupported-version, and
filename/prologue branches are removed from failure semantics and the negative
matrix (empty/altered bytes become digest-mismatch representatives). No
compatibility or negotiation machinery was added; the invariant "dispatch only
reviewed v1 bytes" is preserved.

Subtle point: after a digest match against reviewed bytes that the positive
test proves decode, strict UTF-8 failure is not reachable. The contract writes
"where independently reachable after digest validation" in WFC-PROMPT-06,
failure semantics, and the matrix. This does not require a negative test or a
dedicated branch; it is a harmless hedge. The decode stays strict as a total
function, which is correct.

Residue (MINOR, non-gating, M1): 13.3 "Architecture questions" still says
"identity is one ID/version/name/prologue/digest tuple", and "Identity and
version:: A3 supports exactly this tuple" remains. Neither requires runtime
parsing and the loader paragraph is unambiguous, so this is descriptive, not
contradictory.

Disposition: *closed*.
