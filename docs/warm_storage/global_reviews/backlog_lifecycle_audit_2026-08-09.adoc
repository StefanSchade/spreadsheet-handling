== 2. Method

`docs/backlog/_ftrs_open.adoc` states its own role plainly: "This file is the
active backlog include surface. Only open work belongs here." That makes
`include::` membership a strong, repository-authored signal, but not a
sufficient one on its own (a genuinely open FTR can simply be missing an
include line by oversight, and a `Done`-labelled root could in principle still
be included by mistake).

Concretely:

. Diffed all 101 active `FTR-*` files against the `include::` targets in
  `_ftrs_open.adoc`. 65 root FTRs are included; spot-checked every included
  root's `*Status:*` line -- none read `Done`/`Superseded`/`Fixed` (all
  `New`/`Open`/`Open (Umbrella)`), so no included item needed eviction.
. The remaining 36 files split into:
   .. review/assessment companions of an *included* (hence active) root FTR --
      correctly inert; not independent archival units under the Umbrella FTR
      convention (only *sub-features*, not review notes of a single still-open
      FTR, archive individually).
   .. 9 standalone families with no include line anywhere -- each was
      reconstructed from primary evidence: the FTR's own `*Status:*` line and
      body, `project_memory/canonical/ftrs.json` (authoritative machine
      registry, cross-checked against git log for commit hashes it cites), and
      grep for cross-references from ADRs, other FTRs, and generated Project
      Memory context.
. The largest and most consequential of the 9 -- the
  `FTR-META-ONTOLOGY-REMOVAL-WORKBOOK-PROJECTION-EPIC-P4A` family (18 files)
  -- was delegated to a dedicated read-only research pass that read all 18
  files end to end plus corroborating git history, reconstructing the true
  review chronology from each file's own verdict language (not from filename
  suffixes, since review numbering within that family is non-monotonic --
  reviews 004 and 005 explicitly withhold acceptance, only 006 accepts).

== 4. Special Audit: META-ONTOLOGY-REMOVAL-WORKBOOK-PROJECTION-EPIC-P4A Family

=== 4.1 What the epic originally required

The root FTR (`:status: Draft for architecture review`, revdate 2026-07-18)
defines an 8-slice program (Slices 0-7: characterization, narrow
domain-cleanup contract, final domain cleanup transformation, explicit
Workbook View projection contract, remove lifecycle-based render inference,
projection-plan conflict validation, documentation/registry realignment,
future M:N projection prep) plus a repository-wide `== Epic Acceptance`
criteria list.

The audited *Cell Codec* and *XRef* "projection-family slices" are not among
these numbered slices -- they are later, separately-scoped work layered on top
of the epic once its ontology-removal core (Slices 1/2/4) had landed, each
carrying its own independent multi-round review chain. `compact_multiaxis` and
Legend Blocks are the epic's remaining, still-open composed families.

Review 002 (residual partial + sentinel leak) -> corrected -> Review 003 (one

CELL CODEC PROJECTION-FAMILY SLICE ACCEPTED
SHARED PHYSICAL-LABEL AND EXPLICIT-ONLY CODEC CONTRACTS VERIFIED
READY AS A PRIMITIVE FOR LATER COMPOSED-FAMILY WORK

=== 4.4 Epic-level residual scope

The epic-level bundle's own files state, in multiple places, that the epic is
not done and no artifacts should move:

* Cell Codec review 004's own Lifecycle Cleanup Check: "the parent
  `FTR-META-ONTOLOGY-REMOVAL-WORKBOOK-PROJECTION-EPIC-P4A` remains an active
  multi-family implementation epic. Its status must not change to `Done`."
* `_implementation_review.adoc`'s Lifecycle Cleanup Check (reviewing the
  ontology-removal core, Slices 1/2/4): "This review closes the
  ontology-removal implementation step but not the epic; Slices 3/5-adjacent
  projection-family work and documentation slices remain open, so the epic
  stays on the active backlog ... No artifacts move to cold storage."
* `_additional_information_epic_review.adoc` (pre-implementation
  architecture-approval, 2026-07-18): "no artifacts move to cold storage" --
  time-scoped to before Slice 1 even started, not stale.
* `_codex_implementation_review.adoc` and `_human_review_appraisal.adoc` are
  mid-epic infra checkpoints / pre-implementation approvals; neither claims
  epic completion.

None of the six epic-level files name "Legend Blocks" as residual scope in so
many words (`ftrs.json`'s `implementation_notes` field is the source for that
specific fact); the audited files corroborate that `compact_multiaxis` is the
actively-tracked residual composed family, and that the epic generically
"stays open."

=== 4.5 Self-containedness of the two archived bundles

Both bundles can be read and understood in isolation without the root epic
file. There is one real (code-level, not merely documentary) coupling worth
recording for a future reader: Cell Codec's Review-001 correction extracted a
shared `domain/tabular.ensure_unique_physical_column_labels` boundary helper
and migrated XRef's implementation to reuse it ("XRef was migrated to the
shared helper with no behavior change ... its full regression suite is
unchanged and green"). This fact is fully explained *inside* the Cell Codec
bundle, so no cross-bundle read is required to understand either family's own
accepted scope -- but the shared module means the two are not independent at
the code level, only at the documentation level. This note exists so a future
reader is not surprised that XRef's behavior partially depends on a helper
introduced under the Cell Codec slice name.
