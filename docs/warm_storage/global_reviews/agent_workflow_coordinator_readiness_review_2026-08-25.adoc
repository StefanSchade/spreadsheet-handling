== 4. Overall architectural assessment

The proposed architecture is *high quality*. It performs a genuine falsification
and simplification pass (its sections 2 and 17), reducing the hypothesis's large
taxonomy to three operational records (Run, Hop, Finding), WorkItem-as-input,
finite typed profiles with five route effects, one adapter, a fixed evidence
registry, and Git-as-authority with safe (no auto-cleanup, no auto-replay)
failure. The strongest parts are the Git transaction model and the
determinism -> supervisor -> human precedence.

The draft FTR faithfully projects that architecture into 87 mostly
well-formed, individually testable contracts, an A--H matrix, and five
independently gated slices. Requirement quality is generally high: findings are
separated into deterministic signals versus delegated judgment (a real strength;
e.g. `WFC-FIND-04` deterministic vs `WFC-FIND-05` judgment), future capability is
excluded rather than leaked, and the anti-ceremony linchpin
(`WFC-REVIEW-04`: availability never implies execution) is present and load-bearing.

The design is *not yet* ready to become implementation authority. One *Blocking*
internal contract contradiction and seven *Important* findings must be corrected
and independently re-reviewed first. Critically, none of the findings overturn
the empirical basis or the core reduction; all are precise "tighten this
contract / collapse this concept / make this trigger objective" corrections. The
architecture is close.

The single most consequential finding (R1) is that the FTR's own closed
enumeration of reducer inputs (`WFC-AUTH-03` "shall use *only* ...") and
mechanical-preemption triggers (`WFC-AUTH-02`) *excludes* the structured
`requires_human` flag and `escalation` object, while `WFC-AUTH-06` declares human
escalation mandatory. As written the contracts contradict each other, no A--H
case forces the escalation path, and a conforming implementation could pass all
tests while silently routing an escalating agent onward -- simultaneously a
human-authority breach (Axis 4) and suppression of the exact AI epistemic
contribution the project values (Axis 5).

=== R1 -- Escalation and `requires_human` are not wired into routing authority (internal contract contradiction)

Severity:: BLOCKING. Layer:: CROSS-LAYER (architecture section 5.2; FTR
`WFC-AUTH-02`, `WFC-AUTH-03`, `WFC-AUTH-06`, `WFC-OUTPUT-01/02`).

Problem/invariant:: A structured `requires_human=true` or a non-null
`escalation` from an agent must unconditionally preempt autonomous routing. The
FTR states the *policy* (`WFC-AUTH-06`: "Human escalation shall be mandatory for
...") but not the *mechanism*.

Evidence:: `WFC-AUTH-03` says deterministic reduction "shall use *only* validated
outcome, current review authority/blocking policy, Finding state, evidence state,
budget, and the current finite route table." The word "only" *excludes*
`requires_human` and `escalation`. `WFC-AUTH-02` enumerates mechanical-preemption
triggers as "malformed state/result, Git anomaly, policy mutation, budget
prohibition, or required evidence-provider error" -- which also *excludes* a
validly-formed result carrying `requires_human`/`escalation`. Therefore a
well-formed result with `outcome=completed` and `requires_human=true` passes
preemption (not malformed, no anomaly), reaches reduction, and reduction -- by
its own "only" clause -- ignores the human-stop request and routes to the single
declared `complete`/`goto`. No A--H case exercises this: Replays B and E carry
`outcome=blocked` (so the stop comes from the outcome, not from
`requires_human` overriding a completable outcome); no case pairs
`outcome=completed` with `requires_human/escalation`.

Consequence:: The contracts are mutually contradictory (`WFC-AUTH-06` vs
`WFC-AUTH-02`+`03`). A conforming implementation, wiring the reducer strictly from
`WFC-AUTH-03`'s enumerated inputs, can pass the entire A--H matrix while silently
dropping a mandatory human escalation. This is at once (i) a broken
human-authority boundary (Axis 4) and (ii) suppression of AI epistemic
contribution -- the agent discovered something and asked for a human, and the
engine drove past it (Axis 5). It is a textbook "implementation could satisfy
tests while violating the intended contract."

Smallest correction:: Make `requires_human=true` and any unresolved `escalation`
first-class *mechanical-preemption* inputs in `WFC-AUTH-02` (they stop autonomous
routing regardless of outcome or available route); adjust `WFC-AUTH-03`'s "only"
enumeration so it cannot be read as forbidding escalation-awareness; and add one
A--H-adjacent case (e.g. A') that forces a stop when `outcome=completed` but
`requires_human`/`escalation` is set, so the matrix pins the behaviour.

Human semantic authority required:: No -- a precise contract fix; the intent is
already clearly `WFC-AUTH-06`.

=== R2 -- Blocking-downgrade / residual-acceptance authority is contradictory

Severity:: IMPORTANT. Layer:: ARCHITECTURE/FTR (`WFC-FIND-03`, `WFC-AUTH-05`;
Replay G).

Problem/invariant:: Exactly one authority may downgrade a blocking finding to
residual (a semantic acceptance of a real defect).

Evidence:: `WFC-FIND-03`: "*Only the current declared gate or human authority*
may validate closure, blocking downgrade, residual acceptance, or supersession."
`WFC-AUTH-05`: the supervisor "shall not ... downgrade a blocker *without
delegated authority* ...". The italicised clause implies a profile *may* delegate
blocker-downgrade to the routing supervisor -- but the supervisor is a read-only
routing agent invoked at a judgment point (`WFC-AUTH-04`), not the declared
reviewer gate. The two requirements cannot both be true.

Consequence:: If resolved toward `WFC-AUTH-05`, an LLM routing supervisor can
perform semantic acceptance (blocker -> residual): hidden semantic authority
delegated to the supervisor. If resolved toward `WFC-FIND-03`, `WFC-AUTH-05`'s
"without delegated authority" is misleading and should be removed.

Smallest correction:: Reserve closure / blocking-downgrade / residual-acceptance
/ supersession to a phase with `authority: gate` (reviewer role) or to a human;
forbid the *routing supervisor* from performing them regardless of profile
delegation (it may only route *to* a gate/human that decides). Reword
`WFC-AUTH-05` to match `WFC-FIND-03`. Note Replay G already routes residual
acceptance through "blocking policy ... and its authority," so this only removes
the supervisor loophole; it does not change G.

Human semantic authority required:: No.

=== R3 -- Clean-worktree invariant depends on a non-portable scratch-root ignore

Severity:: IMPORTANT. Layer:: CROSS-LAYER/LIFECYCLE (`WFC-GIT-01/04/06`,
`WFC-PERSIST-02`).

Problem/invariant:: The coordinator writes operational state into a Gitignored
root, and its central invariant treats any non-ignored untracked file as "dirty,"
blocking the next Hop (`WFC-GIT-04`). This only holds if the chosen root is
*reliably and portably* ignored.

Evidence:: In this repository the example root `.agent_tmp/` is ignored *only* via
`.git/info/exclude` (line 8: `/.agent_tmp/`), a *local, per-clone, uncommitted*
mechanism; the tracked `.gitignore` has no `.agent_tmp` entry (an untracked file
already sits in `.agent_tmp/` for exactly this reason). Cross-repository reuse is
an explicit design pressure, and a fresh clone or a sibling repo would *not*
inherit `.git/info/exclude`.

Consequence:: On a fresh clone or a sibling repo, the coordinator's first write
to `.agent_tmp/workflow_coordinator/<run-id>/` produces non-ignored untracked
files -> the clean-state check fails -> the coordinator dead-locks on its own
invariant before the first mutating Hop. Slice-1/2 fixtures that set up
`.gitignore` correctly would not surface this; it is silent until first real use.

Smallest correction:: Require the state root to be ignored via *tracked* repo
policy (a committed `.gitignore` entry), not `.git/info/exclude`; add a
coordinator precondition that verifies (e.g. `git check-ignore`) that its
configured state root is actually ignored before the first mutating Hop, failing
closed with a clear diagnostic otherwise; and change the FTR/architecture example
so it does not lean on a local exclude. (This root must also be on persistent
storage -- see R8.)

Human semantic authority required:: No.

=== R4 -- Nested-return rebaseline duplicates crash-resume reconciliation

Severity:: IMPORTANT. Layer:: ARCHITECTURE (`WFC-MODEL-02` `rebaseline_generation`,
`WFC-FAIL-04`, `WFC-FAIL-06/07`, `WFC-PROFILE-03/04`; architecture section 11;
Replays B/E).

Problem/invariant:: Two mechanisms perform the same operation: reconcile current
Git / governing artifacts / findings against a stored base, recompute a
newly-valid route, require explicit human resume, and never restore or replay a
stale next action. `WFC-FAIL-07` (nested return -> `rebaseline` status + increment
`rebaseline_generation`) and `WFC-FAIL-04` (crash -> `invoking` marker ->
reconcile actual Git -> explicit resume, never replay) are that same operation
under two names.

Evidence:: Compare `WFC-FAIL-04` and `WFC-FAIL-07`: both compute current-vs-stored
Git state and select a valid route rather than restoring the old one. The only
real difference is provenance (intentional suspension vs unexpected crash), which
is a single status flag, not a second state machine plus a monotonic counter.

Consequence:: Avoidable conceptual mass and a duplicated state-machine branch,
front-loaded into Slice 1 (the B/E replays). `rebaseline_generation` is
observability sugar, not a safety necessity -- the safety property is "recompute,
never restore," which needs no counter.

Smallest correction:: Unify on one reconcile-and-resume contract; distinguish
intentional suspension from crash with a single status flag; delete
`rebaseline_generation` (or demote it to a derived display count). This preserves
Replays B and E, which require only that the parent recomputes from current
reality rather than replaying a stale action.

Human semantic authority required:: No (a simplification; the maintainer may
elect to keep the counter purely for checkpoint readability).

=== R5 -- The durable-artifact trigger is subjective and drives a slice acceptance test

Severity:: IMPORTANT. Layer:: FTR/CROSS-LAYER (`WFC-OUTPUT-04`, `WFC-REVIEW-04`;
Slice-3 acceptance criterion 4).

Problem/invariant:: The boundary between "durable engineering knowledge (commit
an artifact)" and "documentation factory / ceremony" must be objective and
profile-determined, because the coordinator's economic goal is to *reduce*
bureaucracy, and because a slice acceptance test depends on it.

Evidence:: `WFC-OUTPUT-04` obliges a committed artifact for "*substantial semantic
analysis* (architecture/design, material review, assessment/census, closure
assessment, durable rationale)" -- a subjective judgment with no objective
trigger. An agent could self-judge its analysis "non-substantial" to avoid the
obligation; a strict reading forces artifacts for trivial reviews. Slice-3
acceptance criterion 4 ("A *material-review* fixture writes a durable artifact
while terminal output stays concise") presupposes the trigger is already defined,
so the test leans on an undefined term.

Consequence:: Untestable acceptance and ceremony risk in both directions -- the
"machine-generated bureaucracy" failure the design explicitly warns against.

Smallest correction:: Define the trigger *by phase role / breadth* rather than by
subjective substance: e.g. phases with `role in {analyst, designer}` or review
`breadth in {broad_discovery, design, closure/counterexample, lifecycle}` must
commit an artifact; routine-implementation and pure-observation phases must not.
This makes the obligation profile-determined and Slice-3 objectively testable.

Human semantic authority required:: No.

=== R6 -- Prompt assembly bounds duplication but not relevance (RRQ-01 substance)

Severity:: IMPORTANT. Layer:: ARCHITECTURE/FTR (`WFC-PROMPT-02`, `WFC-POLICY-02`,
`WFC-RRQ-01`; architecture section 9.1).

Problem/invariant:: The primary economic goal ("eliminate 100+ manual copy/paste
hops") requires both *deduplication* and *bounded relevance*. Versioned pinned
components solve deduplication (the main pain). But `WFC-PROMPT-02` treats
"repository engineering policy" as a single monolithic component, and
`WFC-POLICY-02` lets that policy reference the whole architecture / coding /
testing / docs / commit / AI / Human-Readability corpus.

Evidence:: There is no selective-relevance or per-phase composition requirement.
Injecting the full repo-policy and phase policy on every Hop is precisely the
"every versioned file -> every prompt" anti-pattern the design says it wants to
avoid; as policy grows, context grows unbounded. `WFC-RRQ-01` already flags the
bounding question as open.

Consequence:: Context economy -- a primary goal -- is only half-met, and
`WFC-RRQ-01` stays unresolved at the gate where it is meant to be decided.

Smallest correction:: Resolve `WFC-RRQ-01` via *explicit profile/phase
composition*: each phase declares which policy components it includes (no
automatic retrieval -- correctly out of V1 scope). Affirm the already-present
omission/reference-manifest invariant (Slice-3 acceptance criterion 5, "reports
omissions/references explicitly"). Defer *only* the numeric size threshold to
Slice-2 empirical measurement. This keeps context bounded without inventing
retrieval.

Human semantic authority required:: No.

=== R7 -- Complex-feature genericity is demonstrated only by the DMC-derived profile

Severity:: IMPORTANT. Layer:: FTR/LIFECYCLE (FTR section 11.5 Slice 5, section
2.1; `WFC-SYS-03`; architecture section 18).

Problem/invariant:: The design's headline claim is that the engine is generic and
the DMC-ness lives only in a profile. Structural anti-overfit (`WFC-SYS-03`:
generic code contains no DMC/family/cycle/E-phase primitive) is provable and is a
real strength. But *empirical* genericity for the features that matter
(multi-review, convergence, suspension/rebaseline) must be demonstrated on more
than the profile derived from the same history used to design the engine.

Evidence:: V1 ships two profiles: a *routine* profile (Slice 3/4) that is too
trivial to exercise reviews/corrections/suspension, and the *DMC-shaped* profile
(Slice 5) that exercises all of them. So the complex-feature genericity rests on
DMC alone -- the design's own stated acceptance risk ("DMC dogfood still overfits
history").

Consequence:: Risk that the engine is fit to DMC history; the genericity claim is
under-supported exactly where overfit is most likely.

Smallest correction:: Either (a) add one *cheap* non-DMC profile that exercises
review/correction/convergence (e.g. the "bug investigation/fix/review" workflow
named aspirationally in the concept, section 3) as falsification -- *profile data
+ replay tests, not new engine code*; or (b) explicitly document DMC-overfit as an
accepted V1 limitation with a concrete post-V1 falsification commitment. This is
not program expansion; a second profile is data if the engine is truly generic.

Human semantic authority required:: Marginal -- the choice between (a) and (b) is
a bounded maintainer decision that fits inside the correction cycle; it does not
require standalone product/authority adjudication.

=== R8 -- Crash-resume trusts a persisted result/marker with under-specified atomicity

Severity:: IMPORTANT. Layer:: ARCHITECTURE/FTR (`WFC-PERSIST-01`, `WFC-FAIL-01/04`;
Slice-1 acceptance criterion 4; architecture section 11).

Problem/invariant:: The core V1 promise is "same-checkout crash/resume." That
requires every crash-relevant persisted artifact -- the `invoking` marker, the
Run snapshot, and any structured result present at resume -- to be either
atomically written or safely ignored, and it requires the resume path to state
what it trusts.

Evidence:: `WFC-PERSIST-01` and Slice-1 acceptance criterion 4 require atomic
write for the *Run snapshot*, but not explicitly for the result envelope or the
`invoking` marker. `WFC-FAIL-04` ("restart reconciles actual Git ... never
replays") is silent on whether a result written just before the crash is
re-validated, trusted as a hint, or discarded. A crash mid-write of a result file
could leave a truncated result that a resume path mis-parses.

Consequence:: The crash-consistency of the resume path -- the central safety
promise -- rests on atomicity that is only contracted for one of several
resume-relevant files. (This is *not* Blocking: Git remains the authority for
what changed, so the worst case is a mis-trusted *hint*, not corrupted repository
truth -- provided resume-time schema re-validation is mandatory.)

Smallest correction:: Specify that (i) the `invoking` marker and `run.json` are
the only trusted resume anchors and are atomically written; (ii) any result
present at resume is schema-revalidated and treated as a hint unless fully valid,
else fail closed to human; (iii) Git remains authority for repository change.
State the boundary that crash/resume assumes the Gitignored state root persists
(see R3), and that if state is lost, there is no automatic recovery -- Git is
intact and a fresh Run is the recourse. Extend the atomic-write tests to the
marker and result files.

Human semantic authority required:: No.

=== R9 -- Reopen authority for a resolved finding is not enumerated

Severity:: MINOR. Layer:: ARCHITECTURE (`WFC-FIND-03`, `WFC-FIND-04`,
`WFC-REVIEW-05`).

Problem/evidence:: `WFC-FIND-04` exposes finding "transitions/*reopens*," and
`WFC-REVIEW-05` allows new material evidence to escape the delta bound, but
`WFC-FIND-03`'s authority list covers only closure/downgrade/residual/supersession
-- not *reopen*. Nothing gates who may move a finding `resolved -> open`.

Consequence:: An agent could keep a correction loop alive by re-asserting a
resolved finding, weakening Replay A's "resolved findings stay closed" progress
signal.

Correction:: Add "reopen" to `WFC-FIND-03`'s authority-gated transitions and bind
it to `WFC-REVIEW-05` ("new material evidence"), so re-assertion alone cannot
resurrect a resolved finding.

Human authority required:: No.

=== R10 -- Evidence status enum cannot represent the repository's warning class

Severity:: MINOR. Layer:: FTR (`WFC-EVID-02`, `WFC-EVID-03`, `WFC-FIND-04`).

Problem/evidence:: `WFC-EVID-02` fixes the observation status to
`pass|fail|error|not_run`. One initial provider is "source/style checks"
(`WFC-EVID-03`), but this repository's source-style guards emit *warnings*
("overlong functions, high branch complexity, dense comprehensions -> warning
(review triggers, not automatic failures)," per `conventions.adoc`). The enum has
no `warn`; mapping warn -> pass hides a rising warning count from the convergence
signals that `WFC-FIND-04` exposes as "evidence changes."

Correction:: Add a `warn` status (or a secondary numeric count) and preserve it in

== 8. Complexity and deletion assessment (Axis 2/3)

The reduction from the hypothesis is *genuine* and mostly cannot be pushed
further without losing required behaviour:

* *Run* -- irreducible (the resumable aggregate; phase/status/budget/route-intent
  are not in Git).
* *Hop* -- thin but justified; it binds one invocation to its Git range +
  finding-delta + route. The Git range is derived; the binding is not.
* *Finding* -- justified; identity-via-invariant is correct and matches real E4
  history (the invariant stays stable while the mechanism changes).

Deletion/collapse opportunities actually found:

* *Collapse nested-return rebaseline into crash-resume reconcile* (R4) -- the one
  material simplification; deletes `rebaseline_generation` and one state-machine
  branch.
* *`next_route_keys` is a derived view, not state* (R13).
* *`continuing` context need not be an engine feature in V1* (R14).
* *`suspend_for_prerequisite`* is the thinnest-evidenced route effect (one
  episode) and its autonomous path can be deferred (R17) -- but the effect itself
  is not deletable, because B/E need parent-suspension + child-Run identity that
  `goto`/`await_human` cannot express.

Profile-as-DSL judgment (Axis 3): the profile *is* a small declarative state
machine (finite phase graph, five typed edge effects, no code / conditions /
computed graphs / fan-out). The design's "not a DSL" framing is defensible on
*substance* (no arbitrary computation) even though it is, honestly, a minimal
transition language. Complexity roughly matches demonstrated need: the five
effects are each exercised by the replays; the review descriptor sub-schema is
needed to express F-002 advisory vs formal gate. `complete` carries a latent
semantic ("accepted completion") that must be defined (R12). The five effects are
minimal; `stop` vs `await_human` are close but retain a real difference
(budget-raise-and-resume vs answer-a-specific-question), so no collapse is
recommended there.

Net: no abstraction is carried purely as historical accident except the
rebaseline/resume duplication (R4) and the derived-state item (R13).

== 9. Authority and AI-epistemic-agency assessment (Axes 4, 5, 19)

The precedence order (mechanical preemption -> deterministic reduction -> optional
supervisor -> human) is sound, and determinism is *safely gated*: reduction
auto-routes only when policy yields a single permitted route, so any ambiguity
falls through to supervisor (only at a declared judgment point) or human. A
single determined route correctly preempts the supervisor, so deterministic cases
are not needlessly delegated to an LLM.

The design *intends* the correct distinction -- "AI may originate knowledge and
proposals; AI may not silently self-authorize new governing semantics" -- and
largely encodes it well: findings, escalation, and (critically) the durable-
artifact channel (`WFC-OUTPUT-04`) preserve AI epistemic contribution as durable
repository knowledge rather than transient prose. Structured output cannot buy
authority: advisory reviews cannot advance (`WFC-REVIEW-02`), findings are
validated by gate/human (`WFC-FIND-03`), and reduction only routes within policy.

Two authority defects break the boundary as *written*:

* *R1 (Blocking)* -- the mandatory human-escalation rule is not wired into the
  reducer/preemption inputs, so an agent's stop request can be driven past. This
  is both an authority breach and a suppression of epistemic agency (the two
  concerns the maintainer most cares about, in one gap).
* *R2 (Important)* -- blocking-downgrade/residual-acceptance authority is
  contradictory; as written a profile could delegate semantic acceptance to the
  LLM routing supervisor.

A minor scope-expansion route (R17, preauthorized prerequisite) rounds this out.
With R1, R2, and R17 corrected, the boundary is both safe (no silent
self-authorization) and non-suppressive (any discovery/escalation reaches a human
or a bounded supervisor classification). The security model (Axis 19) is
truthfully scoped -- not oversold as a sandbox -- and has a valuable emergent
property: because the coordinator independently observes Git and evidence and
validates every route, it *degrades gracefully under prompt injection* of
repository content; a manipulated agent still cannot alter Git truth, route
beyond policy, or (after R1/R2) suppress a human stop or achieve a downgrade.

Economics (Axis 20): the coordinator's honest value is *deterministic mechanics*
(Git truth, evidence packaging, prompt assembly, checkpoints) plus *bounded
correction-loop autonomy*, useful even at N=1 (Replay H). On its flagship DMC
profile the autonomous *semantic* dividend is deliberately modest -- capability
deletion and trust-boundary decisions (the essence of DMC Cycle 2) are
human-gated by `WFC-AUTH-06` -- so the saving is concentrated in mechanical
packaging and correction-loop running, not autonomous routing. This is consistent
with the stated goal (maximize verification depth per unit of scarce human
attention) and is not oversold. It does imply the payoff is on *repetitive*
bounded workflows, not one-off tiny work (where per-Run setup may exceed the
manual cost) -- an acceptable and correctly-scoped V1 position.

*Project-Memory boundary (Axis 13): excellent fit.* "Project Memory remembers what
matters; the coordinator records what happened" maps directly onto the actual

*Lifecycle closure (Axis 14): adequate by reference, not self-contained.* The

*Canonical-documentation destination (Axis 15): correctly deferred.* The FTR

== 11. Implementation-slice assessment (Axis 17)

The five-slice order (reducer/model/replay -> Git/evidence -> N=1 fake-adapter
vertical -> real local adapter N=1 -> bounded multi-Hop + DMC dogfood) is sound,
small, and each slice is independently reviewable. Assessment:

* Slice 1 is *horizontal* (whole reducer + all five effects + full A--H at fixture
  level) before any vertical property. The "encode-to-green" risk is real -- Slice-1
  replays operate on hand-authored fixtures, not real Git/evidence -- but the FTR
  *discloses* this ("Later slices replace fixture assumptions") and re-validates A
  and reclassification against the integrated coordinator in Slice 5. Acceptable,
  provided the disclosure is loud: Slice-1 "green A--H" proves reducer logic, not
  system behaviour.
* R4 (unify rebaseline/resume) would *shrink* Slice 1 by removing the front-loaded
  suspension/rebaseline branch.
* Git transaction mechanics (Slice 2) are the most load-bearing safety property;
  the R3 portable-ignore precondition should be proven explicitly in Slice 2.
* Fake-adapter N=1 (Slice 3), real adapter N=1 with a heavy safety gate (Slice 4),
  and optional supervisor + multi-Hop (Slice 5) are appropriately staged; risky
  live invocation and LLM routing authority come last.
* DMC dogfood overfit is the main slice risk (R7); a cheap non-DMC complex profile
  would falsify it as data, not program expansion.

The plan should *not* be expanded into a larger program; R4/R7 shrink or
data-augment it rather than grow it.

== 12. Disposition of open readiness items

=== WFC-ODI-01 -- one V1 serialization (YAML vs JSON)

*Resolvable now; mechanical from precedent -- do not inflate into architecture.*
Use *YAML* for human-authored profiles / repository policy / prompt components
(matches `registries/meta_registry.yaml`; supports the commented-config
convention "Comment config keys with expected type and semantics"; the
architecture's own profile example is YAML). Use *JSON* for machine-written
transient run state / checkpoint data (matches `project_memory/canonical/*.json`
and simple atomic writes). One canonical serialization per role; unknown fields
*reject* (fail-closed), consistent with Slice-1 acceptance criterion 3. This is a
disposition, not a design question.

*Partly already resolved; see R6.* The *contract* that must be true before Slice 3

with references -- no silent truncation," which Slice-3 acceptance criterion 5
already states. Add *explicit per-phase policy composition* (R6) as the
context-bounding mechanism. Defer *only* the numeric threshold to Slice-2
empirical measurement. Prefer invariant + omission manifest over magic thresholds
-- which the FTR already does; the missing half is per-phase relevance.

=== WFC-RRQ-02 -- real adapter and fresh/continuing context

*Sound to defer the provider choice to Slice 4.* On the substance: `fresh`
(no history) is universally guaranteeable by a plausible adapter (new
session/process) and suffices for all A--H replays; `continuing` (retain a bounded
thread) *is* provider-specific and cannot be guaranteed by all adapters. Resolve
by requiring only `fresh` in V1 and treating `continuing` as an optional *declared
adapter capability* (R14), not a guaranteed engine feature. This removes the
"hidden provider-specific semantics" worry.
