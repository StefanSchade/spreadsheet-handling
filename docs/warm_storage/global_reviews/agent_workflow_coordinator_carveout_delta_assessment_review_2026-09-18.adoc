== 2. Verdict

*B -- PLAN ACCEPTED AFTER BOUNDED CORRECTION.*

The plan preserves the accepted boundary, reconstructs P1--P6 almost faithfully, correctly closes P6, correctly keeps Outer Loop, professional trust, 5C+, TUI, PyPI, and a second consumer out of the gate, and defines an observable bilateral exit. It avoids broad pre-split perfectionism.

== 4. A1--A5 assessment

=== 4.1 A1 -- governing-input and WorkItem ceilings

* *Minimal?* Yes for F2 (two domination checks, same shape as existing phase-within-WorkItem and phase-actions-within-policy). Does not import Outer Loop provenance, identity, or signatures. The hard five-Hop constant correctly stays as an additional product limit.
* *Path rule well-defined?* Yes given current scope semantics: `_within_scope(path, scope)` is equality or directory-prefix over normalized, glob-free paths, so "phase scope entry equal to or ancestor of a governing path" is exactly `_within_scope(governing_path, phase_scope)`. Governing inputs are files, so the descendant case is empty. Not overbroad: it is fail-closed and consumers narrow scopes.
* *Sufficient?* Not against original F1. The rule protects this Run's selected files. A phase scoped over a *sibling* directory of the workflows tree can author the next Run's WorkItem/policy through a trusted commit. PMR-M1 records exactly this cross-Run gap as open (R3).
* *Generated/indirect governing artifacts:* component sources are included (good). Pre-split, the A3 contract resource lives at a repository path inside core; until extraction the F1 set must cover it as a *path*, not only as a digest (M9). Evidence-defining files (`conftest.py`, Makefiles) and harness files (T8) are not governing inputs; this is a documented limitation, not a new prerequisite (W1).
* *Documented-only parts:* the cross-Run part may legitimately remain documented-unsupported (plan 6.3) if the maintainer so decides explicitly; it must not be implied closed.

=== 4.2 A2 -- consumer-owned evidence commands

* *Ownership:* argv values do belong in pinned consumer policy; the Coordinator keeps trust origin, observation shape, and pass/fail/error/not_run semantics. Correct and not a plugin framework.
* *New trusted-execution surface:* yes, and the plan under-states it. Today's evidence (`git diff --check`) never executes repository content. Policy argv such as `pytest` or `make` executes agent-modified code at the candidate HEAD (conftest, test files, Makefile) in the Coordinator's host process context, *outside* the provider sandbox. `shell=False` removes shell injection only. "Trusted evidence" can therefore mean trusted argv *origin*, not trusted execution or trusted outcome (R4).
* *Bounded semantics missing:* current `_run_registered_evidence` has no timeout; a hanging `pytest` blocks the operator indefinitely. cwd (repository root), executable resolution (PATH at operator start, resolved path recorded), and environment (inherited, recorded as a fact) need one explicit sentence each, not a mechanism.
* *Dependency on A1:* genuine and stronger than "schema coordination": argv in policy is safe only because A1/F1 keeps policy files outside every phase scope; otherwise an agent Hop authors the next Run's trusted commands.
* *W7:* supports consumer-configurable evidence selection; it does not prove the design (the commissioning record says so). Adequate justification for P2, which predates W7 anyway.
* *Pre-split?* Yes (section 3).

=== 4.3 A3 -- Coordinator-owned operating contract

* Right minimum for C2. Coordinator-owned content: trusted Git ownership (no `git add`/`commit`), CommitIntent meaning, result-envelope discipline, truthful non-completion, escalation vocabulary. Consumer task prose keeps the work and consumer engineering guidance.
* Hidden prompt authority: acceptable because the text is versioned, digested, recorded, and fixed per Coordinator version; it is exactly the "Coordinator-authored reference material distinguished by recorded digest" class of original 4.5. Duplication with structured schema is intended projection of the same rules to the agent, not a second authority, provided the text references schema fields rather than restating validation rules.
* Version/digest evidence is sufficient pre-split. Post-split it is sufficient only together with Coordinator code identity (R5).
* Resource loading must use `importlib.resources` and be declared package data from the start (M9).
* Pre-split is justified by atomic removal of rules from consumer `task.txt` files.

=== 4.4 A4 -- extraction-ready subproject inside core

*Assessment: narrow; move the package/copy-run proof to split-time.*

Costs of the in-core `workflow-coordinator/` subproject:

. *Double topology churn in core.* Core receives a large move plus a nested `pyproject.toml`, then at D a large deletion. Operator invocation paths used by consumer docs/launchers change twice (to the nested path, then to `wfc`).
. *Throwaway interim wiring.* Core must either editable-install its own subdirectory or extend paths to keep consumer invocation and WFC tests running between A4 and D.
. *Silent coverage loss.* Core's `testpaths = ["tests"]`; tests moved into `workflow-coordinator/tests` leave core's default suite unless explicitly wired, dropping 228 WFC tests (including replays A--J) from core's gate for the A4--D window.
. *Weaker proof.* "Without core on `sys.path`" must be simulated inside core; editable installs can mask missing package data. In a filtered scratch clone core does not exist at all -- the independence proof is structural.
. *No history benefit.* Blame preservation is equal: one move per file either way. A filter-time `--path-rename scripts/workflow_coordinator/:src/workflow_coordinator/` (and matching test renames) yields cleaner history -- files appear at their standalone location throughout -- with the mapping recorded in provenance.

Benefit that is real but not decisive: byte-identical tree equality between the split-anchor subtree and the filtered HEAD, and core CI exercising the packaged form. The same verification is available as "filtered tree equals manifest projection at anchor" plus the Phase-C install gate.

Recommended narrowing (A4'): in core, only *relocatability hygiene*, no new layout: intra-package imports relative; remove the three `sys.path` repairs (entry point via `python -m` or a `main()` callable); tests locate fixtures/package via `__file__` or module resolution rather than cwd (`Path("scripts/workflow_coordinator")`, `Path("tests/data/...")`); string monkeypatch targets derived from the imported module; contract resource loaded through `importlib.resources`. Then in Phase C, before push: path-rename at filter time, one bootstrap commit with `pyproject.toml`, `wfc` entry point, import-root rewrite in tests, README/LICENSE/provenance; build wheel, install into a fresh venv, run the standalone suite against the *installed* wheel, and run the neutral N>=2 fake/local convergence through the `wfc` executable in a separate non-spreadsheet Git repository. `wfc --help` alone is insufficient CLI identity; the convergence run must go through `wfc`. The "no `scripts.workflow_coordinator` imports" check is then satisfied by construction in the standalone and becomes a D-time guard in core.

If the maintainer prefers tree-equality verification, A4 as written remains admissible (W4) but must add explicit core `testpaths`/CI wiring for the moved tests; it is not the smallest safe plan.

=== 4.5 A5 -- lifecycle handoff timing

*Ownership logically transfers at C (consumer reconnection).* Reasons: until D lands, core still contains, runs, and tests the implementation, so the incubator FTR is truthfully the authority for the code in core; the standalone repository before D is a validated copy with no consumer.

Failure behavior of the plan as written: if the FTR is `Superseded` before filtering and extraction then fails or is abandoned, core holds a superseded FTR, active executable code, and no successor -- authority-false. A retry after a core-side fix would require editing a superseded FTR or un-superseding it (R1).

Corrected sequence:

. Pre-split (Phase B, one governance commit): maintainer decision selecting option (b); FTR stays `Open` with an explicit *carve-out freeze* (no further incubator slices; exact split anchor; 5C--5E named as candidate standalone backlog; 5F disposition per M6). This commit is the split anchor.
. Phase C first standalone acceptance: record the received backlog as non-authoritative, pending reconnection.
. Phase D, atomic with removal of the incubator implementation: FTR `Superseded`, navigation/backlog updated.
. On abandonment: a note lifts the freeze; nothing false was ever recorded. On retry: new freeze commit, new anchor.

== 6. Extraction and history assessment

Sound: fresh `--no-local` clone; explicit path allow-list; `main` only; release tags excluded (8 core tags would mislabel consumer releases); commit map retained; core remains pre-split citation authority; scratch discarded on failure; no in-place repair; no force push; target populated only by cloning the accepted remote.

Corrections (M3, M4):

* `--force` disables filter-repo's fresh-clone sanity check; a `--no-local` fresh clone needs no `--force`. Keep the safety check.
* `--refs refs/heads/main` rewrites only `main`; `refs/remotes/origin/*` and tags stay pointing at full core history, so the scratch object database still carries all core content. Remove non-`main` refs and the `origin` remote before filtering (or filter all remaining refs), then verify with `git rev-list --all` and a post-`gc` object check. Ancestry of `main` is complete (13 merges, no needed side branches); degenerate merges will be pruned -- acceptable.
* filter-repo by default rewrites abbreviated old commit hashes in commit *messages* to new hashes, while in-file document citations keep incubator SHAs. That contradicts plan 8.3 ("never substitute a rewritten SHA into an old citation"). Use `--preserve-commit-hashes`, or state explicitly that message rewriting is accepted and why.
* Rename closure: 28 Coordinator documents were renamed warm-to-cold storage. A manifest listing only current paths truncates their history at the move commit. Derive the manifest mechanically as the rename closure (`git log --follow --name-only` per selected current path), record the derivation command, review its output.
* Mixed commits: only one code/test commit also touches non-Coordinator paths; mixed docs commits retain partial projections -- the plan's provenance statement covers this.
* Empty-commit pruning and parent rewriting: acceptable and correctly stated.
* Reproducibility: pin filter-repo version (absent from this environment), record manifest digest and full command; the same inputs reproduce the same commit map.

== 9. Consumer reconnection

* Exact Git commit pin is the right first reproducible boundary; PyPI is not required. But core publishes to PyPI (`release.yml`, Trusted Publisher), and PyPI rejects distributions whose metadata contains direct URL references. The pin must live outside `[project]` metadata -- a requirements/constraints file or a non-metadata dependency group -- never in `[project.optional-dependencies]` (M7). Target repository visibility must allow core CI to resolve the pin, or the dependent core tests need an explicit skip policy.
* Core needs both surfaces: Python API for loading/cohering its governing inputs, CLI for a fake/local invocation. The Python surface used by core must be named (serialization loaders) so "no standalone internals" is checkable (M8).
* "Retain consumer integration tests": none exist. No core test loads `docs/ai_info/workflows/**`. They must be created -- naturally in A1/A2 when consumer ceilings and evidence values are introduced -- and then survive D (M8).
* Atomic vs staged removal: both options acceptable; the staged option's architecture guard plus the bilateral fresh-clone check is sufficient against fallback.
* No circular bootstrap: the standalone neither imports nor tests against core.
* With R1, the D commit also carries the FTR `Superseded` transition.
