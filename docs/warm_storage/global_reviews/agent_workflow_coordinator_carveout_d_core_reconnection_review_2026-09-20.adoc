truthful and mechanically executable Phase-D transition from "Core contains

== 4. Dependency and pin model

Disposition:: *Accepted.*

* Exact Git OID pinning is sufficient and reproducible. Git content addressing
  makes the OID an integrity anchor no weaker than a hash pin; no registry
  release exists and none should be invented for convenience.
* Keeping the requirement outside `[project]` and
  `[project.optional-dependencies]` is correct and verified consistent with the
  packaging configuration: no `src/spreadsheet_handling` module imports WFC, and
  the built distribution never contained it. Classifying WFC as developer and
  workflow tooling is truthful.
* `tools/pip_install_spec.sh` already documents and accepts
  `-s "-r requirements.txt"`, so the claimed helper reuse is real. `DEV_INPUTS`
  is a plain Make prerequisite list (`Makefile:54`), so adding the requirement
  file genuinely invalidates `$(DEV_STAMP)` on a changed pin, and every test
  target depends on `deps-dev` (`Makefile:129`, `Makefile:543`).
* `requirements/` does not yet exist and is not gitignored; adding it is clean.
* There is no silent path by which an editable sibling satisfies acceptance,
  provided the guard asserts on `vcs_info`: an editable install records
  `dir_info.editable` and no `vcs_info`, so the exact-identity assertion fails
  closed. A developer who installs the sibling after a valid stamp will not
  trigger reinstallation, but the architecture guard is the backstop and it
  fires. `make clean-stamps && make setup` deletes `$(STAMP_DIR)`
  (`Makefile:143-144`) and reinstalls the pinned requirement, so the documented
  restore path is truthful.

== 8. Consumer API boundary and retained-test feasibility

Disposition:: *Boundary decision accepted; the proposed retained-test contract
is falsified.*

The decision to treat installed `wfc` as the Core application boundary, rather
than importing underscored implementation helpers, is right and is not an
accidental invention of a standalone Python API: the plan explicitly defers any
Python surface to a future standalone change.

However, the pinned implementation cannot support what sections 7 and 13.3 of
the plan -- and the normative FTR 13.6 "Consumer reconnection" clause -- require
of the retained test. Three mechanical facts, read at the pin:

. `_parse_args` exposes no subcommand, no `--dry-run`, and no preflight-only
  mode (`src/workflow_coordinator/operator.py:187-201`). The only entry is a
  full run.
. `_preflight` requires `facts.head == args.expected_head` *and* `facts.clean`,
  and reads every input through `_pinned_text`, i.e. `git show <rev>:<path>`
  (`operator.py:78-84`, `operator.py:203-225`).
. For a phase whose `durable_artifact` is `required`, a `completed` outcome
  yields `("required durable artifact is missing, unrepresented, or uncommitted")`
  unless `delta.actual_commits` is non-empty and the durable path appears in both
  `commit_intent.paths` and `delta.changed_paths` and is a tracked regular file
  at end HEAD (`src/workflow_coordinator/vertical.py:92-140`). Any such anomaly
  is a mechanical preemption that stops for human authority rather than
  completing (`src/workflow_coordinator/reducer.py:327-337`).

The Core DMC bundle's only phase declares `durable_artifact: required`,
`authorized_actions: [edit, commit]`, and a single `complete` route
(`docs/ai_info/workflows/dogfood/dmc_fk_c3_wi02/profile.yaml`). Standalone's own
completing fixture demonstrates the consequence directly: its fake writes into
the target repository and the run commits before `main` returns `0`
(`tests/unit/test_operator.py:205-228` at the pin).

Consequences are stated as BLOCKING-1 and BLOCKING-2.

What the public CLI *can* prove black-box, and what the corrected plan should
rely on: preflight/admission failure is distinguishable by exit code `2` with no
state root created, post-admission failure by exit code `1` with a failure
summary, and success by exit code `0`; `operator-plan.json` is a durable public
artifact that records the resolved governing inputs, digests, evidence plan, and
contract provenance (`operator.py:674-760`). `slice4.register_checkout`
additionally enforces an external state root, so no Coordinator state can land
inside Core (`src/workflow_coordinator/slice4.py:91-102`).

== 12. One-commit atomicity

Disposition:: *One commit is correct; but the plan omits a real intra-commit
ordering constraint.*

Splitting would produce two generic authorities, a non-working consumer, or a
false lifecycle state, exactly as argued. No review or implementation boundary
justifies a second Core commit.

There is nevertheless a mechanical ordering constraint the plan does not state.
Because `wfc` reads its inputs from `--expected-head` and refuses a dirty
worktree, no consumer test that drives the *real* Core repository can pass while
the D change is uncommitted. Under the current design the implementer must
commit and only then validate, and the plan's own stop condition "the worktree
is not clean at the WFC operator preflight needed by the consumer test" would
fire in the ordinary implementation workflow. The correction in BLOCKING-1
dissolves this, because a seeded temporary repository is clean and at a known
head by construction; the ordering constraint should be retired rather than
documented.

== 18. Findings

=== 18.1 BLOCKING

*BLOCKING-1 -- A one-Hop completion of the real DMC bundle cannot leave the Core
repository unmutated.* (Class A: D plan defect.)

Observation:: Plan section 7 and FTR 13.6 require "one provider-free one-Hop
completion" with "a clean unchanged Core worktree" and "without repository
mutation", driven against `--repository <Core>`. At the pin, the DMC phase
declares `durable_artifact: required`; `_preflight` refuses the run outright if
no `--durable-artifact` is supplied; and a `completed` outcome without a real
commit containing that path produces a durable-artifact anomaly that the reducer
converts into a stop-for-human, not a completion
(`vertical.py:92-140`, `reducer.py:327-337`). A truthful completion therefore
requires the Coordinator to commit an edit of
`docs/warm_storage/global_reviews/domain_fk_reference_helper_family_cycle3_missing_target_id_identity_assessment_2026-09-11.adoc`
into Core.
Consequence:: The implementer must either let `make test` create junk commits on
Core `main` on every run, or silently redefine "completion" as
`AWAITING_HUMAN`, making the acceptance claim untrue. Both outcomes defeat the
purpose of the retained test.
Smallest bounded correction:: Drive the completion Hop against a disposable
temporary Git repository seeded from the real committed Core bundle files and
their selected components -- the pattern standalone already uses for its own
operator acceptance -- and keep any assertion about the live Core checkout
read-only. Restate plan section 7 and the FTR 13.6 "Consumer reconnection"
clause accordingly. No standalone change, no change to the section 11 file set.

*BLOCKING-2 -- The plan's "no-side-effect preflight/admission probe" does not
exist at the pin, and the real-repository probe is worktree-coupled.* (Class A:
D plan defect.)

Observation:: `wfc` has no preflight-only or dry-run mode
(`operator.py:187-201`); the only admission path is a full run. `_preflight`
additionally requires `facts.clean` and `facts.head == --expected-head`, and
reads all inputs with `git show <rev>:<path>` (`operator.py:78-84`,
`operator.py:203-225`).
Consequence:: Three failures follow. The promised side-effect-free probe is
unavailable through the public CLI, and the obvious substitutes are importing
`operator._preflight` -- which plan section 6 forbids -- or amending standalone,
which is forbidden outright. The retained test fails for any developer with a
dirty worktree, so `make test` becomes conditional on local Git state. The
revised `r3` policies cannot be exercised until after they are committed, so the
plan's own section 14 stop condition would fire during ordinary D
implementation.
Smallest bounded correction:: Adopt the seeded temporary repository from
BLOCKING-1 for both bundles, and define the admission probe by the CLI's public,
observable contract: exit `2` with no state root for a rejected bundle, versus a
written `operator-plan.json` for an admitted one. Retire the "no-side-effect"
wording and the corresponding stop condition.

=== 18.2 IMPORTANT

*IMPORTANT-1 -- `make setup` becomes gated on private-repository access for a
public Core repository, with no non-interactive guarantee.* (Class B:
operational prerequisite, with a plan-text component.)

Observation:: `spreadsheet-handling` is public (API 200); the standalone
repository is not anonymously resolvable (API and web 404). The plan puts the
`git+ssh` install on the normal `make setup` / `deps-dev` path, and every test,
lint, and format target depends on `deps-dev` (`Makefile:129`, `:157`, `:162`,
`:543`). Nothing in the plan sets `BatchMode=yes` or `GIT_TERMINAL_PROMPT=0`;
the existing docs deploy-key step sets neither (`release.yml:122`).
Consequence:: A contributor without access to the private tooling repository can
no longer run the standard Core development commands at all, and pip's `git`
child process can block on an interactive SSH or passphrase prompt instead of
failing closed -- the readiness artifact records that this very environment was
prompted for credentials.
Smallest bounded correction:: Mandate `GIT_SSH_COMMAND='ssh -o BatchMode=yes'`
and `GIT_TERMINAL_PROMPT=0` for the WFC install step in both `Makefile` and CI,
and state explicitly in `ch04_project_setup` whether the WFC tooling stamp is on
the default path or an opt-in target. If opt-in, the two WFC consumer tests must
skip deterministically and visibly when the distribution is absent, while CI
always installs and runs them.

*IMPORTANT-2 -- Two section 13.4 gates contradict the section 8 guard.* (Class
A: D plan defect.)

Observation:: `! git grep -n -I 'scripts\.workflow_coordinator' -- '*.py'` and
the `agent_operating_contract_v1.txt` gate scoped over `tests` will both match
`tests/architecture/dependency_guards/test_workflow_coordinator_consumer_boundary.py`,
which by section 8 must carry exactly those literals to assert their absence.
Consequence:: Both gates fail deterministically at the end of a correct
implementation, and the likely reaction is to weaken the guard instead of the
gate.
Smallest bounded correction:: Add
`':(exclude)tests/architecture/dependency_guards/test_workflow_coordinator_consumer_boundary.py'`
to both gates, or require the guard to compose the literals at runtime.

*IMPORTANT-3 -- `project_memory/canonical/ftrs.json` stays falsely
authoritative after D.* (Class A: D plan defect, bounded.)

Observation:: The canonical FTR registry row for
`FTR-AGENT-WORKFLOW-COORDINATOR-P5` records
`status: "open (V1 through Slice 5B implemented and accepted; ...)"`,
`current_relevance: "current"`, and
`source_path: "docs/backlog/FTR-AGENT-WORKFLOW-COORDINATOR-P5.adoc"`. Neither
`ftrs.json` nor `concern_event_xrefs.json` appears in the plan's six deferred
Project Memory files, so section 3's completeness claim is inaccurate.
Consequence:: After D the registry asserts an open, current FTR at a path that
no longer exists, which is the one deferral case the review scope treats as
gating. No test validates `source_path`, so this is a truthfulness defect, not a
suite failure.
Smallest bounded correction:: Either include the single-row truthful update to
`ftrs.json` in D -- status, `current_relevance`, and `source_path` only -- or
classify both files explicitly in section 3.4 with a recorded reason why the
stale row is tolerable until the curation task. The first is preferable and is
one file.
