== 1. Question, evidence, and method

=== 1.1 Threat model applied

As set by the review prompt and consistent with `ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY` Decision 1 and `ADR-DOMAIN-BOUNDARY-ROBUSTNESS`:

* runtime/operator, installed framework, interpreter, and dependencies are trusted;
* arbitrary hostile same-process Python is out of scope; kernel/interpreter/dependency compromise is out of scope;
* the attacker controls an input artifact accepted by a public/application boundary: workbook bytes, ZIP members, XML, formulas, links, metadata, scalar payload, malformed encodings, extreme-but-accepted dimensions, directory contents;
* targets: CPU, memory, disk, parser behavior, diagnostics, unexpected file/network access, semantic confusion.

Five concerns are kept distinct throughout: (1) physical parsing / resource boundary; (2) external/description structural validation; (3) payload ingress validity (Trusted Ingress, E1--E3); (4) Domain semantic/invariant validity; (5) output-sink behavior. A parser issue is never reported as a Trusted-Ingress classification defect, and no parser fix is proposed as global scalar censorship.

== 2. Verdict

*B -- DIRECTION SOUND WITH BOUNDED HARDENING REQUIRED.*

The trust transition is complete on every framework-managed external route: all ten router loader kinds return through `orchestrate` -> `establish_initial_state` -> `run_domain_ingress` before any configured step, cleanup, or saver runs; no alternate loader, fallback, or compatibility path produces ordinary Domain Frames without establishment. No supported payload can activate an import, callable, subprocess, network, or plugin capability through parsing. Trusted Ingress's own diagnostics discipline holds inside the ingress package.

The physical boundary in front of it, however, is not what the professional sentence under test claims. Only ODS has a framework-enforced resource ceiling, and that ceiling bounds cell/row/column materialization only. Three framework-owned amplifiers exist where a small input controls work that is not proportional to its size: the XLSX presentation-metadata walk materializes the whole sparse bounding rectangle (H1); the ODS `text:s` count expands a scalar without any budget (H3); and the `_meta` substrate validator itself traverses shared-alias DAGs by path, so the admission check is the first exponential amplifier for a small YAML sidecar (H4). One dependency-owned amplifier (openpyxl merged-range materialization, H2) runs before any framework code. Directory carriers follow symlinks, which is a filesystem-read capability exercised by artifact structure before rejection (H5). All are bounded, format-local corrections; none requires a change to Trusted Ingress's architecture, and none should be absorbed into `run_domain_ingress`.

Findings by severity: BLOCKING 0; IMPORTANT 5 (H1--H5); MINOR 4 (H6--H9); INFO/WATCH 5 (HW1--HW5).

=== 2.1 Answers to the required questions

. *What exact guarantee begins only at Trusted Ingress, too late to protect the parser?* Payload-language conformance: that every ordinary cell is one of the six Scalar categories and `_meta` satisfies the closed, bounded, acyclic substrate grammar. This is established over already-materialized Python/pandas carriers. It says nothing about the bytes, archive members, XML structure, decompressed size, or the memory and CPU that producing those carriers consumed; every resource-exhaustion path in this review completes or fails before `establish_initial_state` is reached.
. *Is every framework-managed external payload forced through Trusted Ingress before ordinary Domain execution?* Yes. `orchestrate` is the sole macro seam; `run_app`, `sheets-run`, `run_schema_maintenance`/`sheets-schema-maintain`, and the `spreadsheet_handling.orchestrator` shim delegate to it. `_load_frames` reaches only `router.LOADERS`. `apply_overrides` re-runs ingress on merged `_meta`. No loader-side error/fallback path returns Frames around the seam; a loader exception aborts before establishment and before any saver. `run_pipeline` and direct backend reads remain documented caller-precondition surfaces, not accidental external routes.
. *Which supported formats have a genuine framework-enforced resource boundary?* ODS only, and only for row/column/materialized-cell counts per sheet (`ParserLimits`, enforced before repeat expansion in `_parse_table_grid` and in the four presentation extractors). XLSX, CSV, JSON, YAML, and XML have none; their cost is dependency-owned and, apart from the amplifiers in H1--H4, proportional to decompressed input.
. *Can any supported input activate filesystem/network/executable capability before semantic rejection?* Executable/network: no, by inspection of every loader (section 9). Filesystem: yes in one bounded form -- the directory carriers (`csv_dir`, `json_dir`, `yaml_dir`, `xml_dir`, and the `_meta.yaml` sidecar) glob and open whatever the directory contains, including symbolic links to files outside the input root (H5). The operator-designated input path itself is trusted by precondition.
. *Are XLSX formulas/external references inert in the security-relevant sense under the current loader?* Yes, for execution. `data_only=True` selects the cached `<v>` value and discards formula text (`WorksheetReader.parse_cell`); openpyxl evaluates nothing; `keep_vba` defaults to `False`; external-link parts are read from the archive only (`read_external_link(archive, book_path)`), never fetched. "Inert" is not "harmless": formula cells without a cached value read as `""`, and formula metadata still costs parse work. `data_only` is a value-selection switch, not a security control.
. *Is `_meta` safely promoted from hostile serialized input to trusted substrate?* Structurally yes: every carrier (`json.loads`, legacy `ast.literal_eval`, `yaml.safe_load`) can construct only literal Python types, so no hostile special method can exist in `_meta`; E3 rejects every out-of-grammar node with positional diagnostics; the legend delegate stages safely. Resource-wise no: E3 admits shared aliases and walks them by path, so the admission pass is O(paths), not O(nodes) (H4). Between parser and ingress, `build_sheet_meta_hints`, `_legend_table_hints`, `canonicalize_workbook_meta`, and `_strip_legend_resolved` read raw `_meta` with `isinstance`/`.get()`/`int()` on literal-only values; that is safe preparation work under the capability-activation principle.
. *Are failure diagnostics safe under hostile/parser-pathological input?* Inside `domain.ingress` and `core.scalar_values`: yes (no `repr`/`str`/comparison/hash/iteration of a rejected value; type names constant). Around it: content-safe but length-unbounded. Sheet/table names and frame names (exact `str`) are echoed verbatim in `SpreadsheetTooLargeError` contexts and in `OrdinaryStructureAdmissionError`; `run_cli` prints `str(e)` in full (H7). Library exceptions reaching the CLI carry position or type information, not raw payload, except `int()` conversions of attacker attributes in the ODS parser (CPython bounds that message; UNVERIFIED in session).
. *Single most important newly discovered pre-ingress risk?* H1: the XLSX read path turns one far-away cell into full materialization of the `max_row x max_column` rectangle through `ws.iter_rows` -> `ws.cell()` (openpyxl creates and retains a `Cell` on first access), so framework-owned memory is set by the sparse extent rather than by the populated cells or the file size, with no ceiling and before any rejection point. It is the XLSX analogue of the repeated-carrier hazard the review instructions already flag for ODS, and ODS already clips for it.
. *What should be hardened locally rather than added to Trusted Ingress?* All of it: H1/H2 in the XLSX parser and the open XLSX limits design; H3 in the ODS parser; H4 in the `_meta` substrate validator's own algorithm plus a persistence-contract clarification; H5 in the directory loaders / router; H7 in parser and CLI diagnostics. Nothing here changes the six-category grammar, `run_domain_ingress`, or the managed seam.
. *What must be true before this area can credibly be presented as a professional security/governance example?* (a) The written claim must match the runtime: "bounded adapters" must be replaced by the truthful sentence in section 3; (b) `FTR-XLSX-PARSER-RESOURCE-LIMITS-P4A` must have at least its census closed with H1/H2 recorded; (c) H3 and H4 must be fixed or explicitly listed as accepted non-guarantees; (d) the directory-symlink behavior must be either contained or documented; (e) the boundary matrix in section 4 must live in permanent documentation with the "dependency-owned / framework-owned / deliberately unbounded" classification per format.

== 3. Falsification of the primary claim

Claim under test:

> "External artifacts are parsed through bounded format-specific adapters, then semantic payload conformance is established before ordinary Domain transformations consume the result."

The second clause is true for every framework-managed route (section 10). The first clause is false for five of six formats and only partially true for the sixth: XLSX, CSV, JSON, YAML, and XML adapters enforce no framework bound of any kind; the ODS adapter bounds three dimensions of its own materialization and nothing else (not archive size, decompression, sheet count, style count, scalar length, or `text:s` expansion). The repository's own permanent documentation does not make the claim; the historical concept and the open XLSX FTR say the opposite. The claim is therefore an overstatement a presenter could make by accident, not a documented position.

Smallest truthful replacement:

> "External artifacts are parsed by format-specific adapters whose resource use is dependency-owned and proportional to the decompressed input, except that ODS row/column/cell materialization is framework-bounded and a small number of identified amplifiers (XLSX sparse-extent walk, XLSX merged-range materialization, ODS repeated-space expansion, shared-alias `_meta` traversal) are not yet bounded. After parsing, semantic payload conformance -- the six-category Domain scalar language and the closed, bounded, acyclic `_meta` substrate -- is established at the single framework-managed seam before any ordinary Domain transformation, cleanup, or sink consumes the result."

== 6. Container / archive / XML security

*XLSX (openpyxl 3.1.5, normal mode).* The package is opened with `zipfile.ZipFile`; content types, workbook, shared strings, styles, theme, core/custom properties, and every worksheet are read before `load_workbook` returns (`reader/excel.py`). XML parsing uses `defusedxml.ElementTree.iterparse`/`fromstring` when `defusedxml` is importable (`xml/functions.py` L38--42), which in this environment it is; `defusedxml` defaults forbid entity declarations and external references and permit a DTD. `keep_links=True` keeps `ExternalLink` parts as parsed objects read from the archive (`read_external_link(archive, book_path)`); nothing dereferences the target. `keep_vba=False` drops `vbaProject.bin`. Embedded objects, drawings, and pivots are read as parts or ignored; none is executed. Path handling inside the archive is openpyxl's relationship resolution; no member is written to disk. Conclusion: no capability beyond memory/CPU is activated by any XLSX feature under the current invocation.

*ODS (odfpy 1.4.1).* `load` opens the ZIP, reads the manifest, and feeds each XML part through `defusedxml.sax.make_parser` (`opendocument.py` L886--916; `load.py` L27) into a full DOM. Entities and external references are forbidden. Pictures listed in the manifest are read into memory. No external resource is opened.

*XML backend.* Stdlib `ET.parse` on a local file with the comment "trusted local files only". Expat 2.7.1 provides amplification limits; external entity resolution is not performed by stdlib ElementTree (standard behavior; not probed).

*Dependency declaration.* `pyproject.toml` declares `openpyxl>=3.1`, `odfpy>=1.4.1`, `pyyaml>=6`; `defusedxml` is not declared but is a hard `Requires-Dist` of odfpy 1.4.1, so any install that satisfies the declared dependencies also carries it and openpyxl picks it up. The guarantee is real but accidental (HW3).

== 7. XLSX specifically

* `load_workbook(str(path), data_only=True)`: `data_only` only decides whether `parse_cell` stores the formula text or the cached `<v>` value; with `data_only=True` formula elements are skipped and the cached value (or `None`) is used. It protects against nothing at the parser level; openpyxl never evaluates formulas in either mode. Shared/array/data-table formula metadata still costs parse work but is discarded.
* Cached-value behavior: a formula cell with no cached value reads as `None` -> `""` after the string collapse -- silent data loss, semantic not security.
* External links: kept as parsed archive parts; never resolved. Named ranges: `DefinedName.destinations` tokenizes the value with openpyxl's formula tokenizer and yields only RANGE parts; the framework then applies its own regex and drops anything not `A1:B2`-shaped on a known sheet. No resolution or fetch.
* Hidden sheets: `sheet_state == "hidden"` -> key/value hidden sheet; `veryHidden` is not matched and the sheet is parsed as visible payload (H6). A `veryHidden` `_meta` sheet becomes `frames["_meta"]` as a DataFrame and is rejected by E3 as `invalid_metadata_root` (fails closed).
* Shared strings / styles: fully materialized by openpyxl; no framework bound; proportional to decompressed input.
* Merged cells: dependency-side materialization (H2) plus framework per-lookup enumeration (known).
* Dimensions: `max_row`/`max_column` derive from `_cells` keys, which include style-only `<c>` elements without values (`parse_cell` returns an entry for every `<c>`; `bind_cells` creates a `Cell` for each).
* Presentation walk: `_extract_text_orientations`, `_extract_horizontal_alignments`, `_extract_vertical_alignments` each call `ws.iter_rows(min_row=1, max_row=ws.max_row, max_col=ws.max_column)`; `_cells_by_row` calls `self.cell(row, column)` for every coordinate and `_get_cell` creates and stores a `Cell` if absent (H1). Column-dimension fallbacks clip to `max_column` but that is the same sparse extent.
* `_meta` handling: first two columns via `iter_rows(min_col=1, max_col=2)` -- bounded by two columns, unbounded rows (proportional). Blob parse as in section 4.
* Where does "visible cells collapse to string" happen? In `_parse_table_block` / `_parse_exact_table_block`, after `load_workbook` and after the three presentation walks. It matters only for the Domain-language question; it has no parser-security effect.

== 8. ODS specifically

* Limits apply *before* expensive allocation for the table grid: `_parse_table_grid` collects a row's cell descriptors (O(elements)), skips content-free repeated rows entirely, computes the projected extent, and calls `limits.enforce` before the expansion loop. This is the strongest bounded path in the repository and it is tested.
* All dimensions the limits name are bounded: rows, columns, materialized cells, per sheet. Not bounded: sheets, DOM size, style count, named/database ranges, validations, `text:s` expansion (H3), scalar length, hidden-sheet count.
* Repeated structure amplifying work before the check: a content-bearing row with a huge `number-columns-repeated` on an *empty* cell is O(1) per descriptor; the projected extent only counts content cells; `enforce(cells=len(values) + row_repeat * content_cols)` is correct. Covered-cell and span handling extend bounds by span size only.
* Metadata / non-cell structures: `_build_column_style_map`, rotation/alignment maps, and `_parse_hidden_style_names` iterate every `Style` in the document -- proportional to DOM. `_parse_hidden_sheet` goes through the bounded grid. Column-width and default-cell-style maps clip to `max_col` and enforce per axis.
* Parser and projection limits are coherent: projection reads the already-bounded `ParsedTable`; `_find_col_extent`/`_find_row_extent` scan within `parsed.max_col`/`max_row`.
* Diagnostics on malformed input: `int(attribute)` on non-integer repeat/span/`text:c` attributes raises a raw `ValueError` echoing the attribute (CPython bounds the echo; UNVERIFIED in session); negative repeats are accepted and move `row_index`/`col_index` backwards, overwriting earlier cells (semantic confusion, bounded). `SpreadsheetTooLargeError` context strings embed the table name verbatim (H7).
* Alternative ODS loader: none. `ods` and `calc` both map to `load_ods`.
* What the limits actually guarantee: per-sheet materialization of at most 10,000,000 content cells and axis extents within the format maxima, enforced before the expanding loop. They do not guarantee a memory budget (10,000,000 Python string entries plus their re-materializations is multi-gigabyte; HW1), a workbook-wide bound, or any bound on scalar size or DOM size.

== 9. YAML / JSON / XML / CSV structured backends

* *Safe YAML constructors versus resource guarantees.* `yaml.safe_load` blocks object construction; it does not bound document size, alias fan-out, or nesting. libyaml handles scanning/parsing in C; composition and construction are Python and recursive (deep nesting -> `RecursionError`, fails closed). Aliases resolve to the *same* Python object (`compose_node` returns `self.anchors[anchor]`; `construct_object` caches by node), so parsing is linear and the DAG is handed to ingress (H4). `!!set`, `!!binary`, `!!omap` (list of tuples), `!!timestamp`, and non-`str` keys are reachable and are rejected by E1/E3 with structural diagnostics (tested in `test_metadata_admission.py`; sheet-side, nested containers in cells are rejected by E2).
* *JSON.* `pd.read_json(dtype=str, convert_dates=False)`: pandas parses with its vendored ujson and then `astype(str)` per column (`_try_convert_data`); nested objects stay as Python containers inside object cells and E1 rejects them. `astype(str)` renders booleans as `"True"`/`"False"` (HW4). The `_meta.yaml` sidecar is PyYAML as above.
* *pandas inference / missing values.* CSV and JSON reads disable NA inference; YAML relies on pandas' `DataFrame` construction and then `.where(notnull, "")`, which converts YAML `null` to `""` and leaves native scalars in place -- the one backend that produces Boolean/Number/Date/DateTime carriers.
* *XML.* Stdlib `ET.parse`; `_flatten_element` is recursive over element depth; leaf text `str`. No sidecar.
* *CSV.* `dtype=str`, no NA inference; header rows are the only structural assumption.
* *Directory enumeration and symlinks.* All four directory loaders use `Path.glob` and open every match; `Path.glob` yields symlinked entries and `open`/`read_csv`/`ET.parse` follow them. No `is_symlink()`/`resolve().is_relative_to(root)` check exists on the read side, unlike the writer-side containment tested in `test_description_authorization_resources.py` (H5).
* *Can a format create in-memory structures that themselves cause pathological behavior when Trusted Ingress traverses them?* Yes: the YAML alias DAG in `_meta` (H4). Sheet-side, ingress cost is linear in cells; a nested container in a cell is rejected at first sight without traversal.

== 10. `_meta` boundary and trust-transition correctness

Path from hostile serialized input to accepted `_meta`:

[source,text]
----
XLSX/ODS: hidden sheet cells -> str -> json.loads | ast.literal_eval | {str: str}
          -> parser-side reads (build_sheet_meta_hints, _legend_table_hints,
             apply_cell_addressed_presentation_meta)
          -> _store_workbook_meta (json.dumps) only when presentation meta changed
          -> workbookir_to_frames: _try_parse_blob again -> canonicalize_workbook_meta
             (recursive nested-blob unwrap, marker strip) -> _strip_legend_resolved
JSON/YAML dir: _meta.yaml -> yaml.safe_load -> exact dict check (YAML) / isinstance dict (JSON)
-> orchestrate: establish_initial_state -> run_domain_ingress:
     ordinary_structural_admission (never opens _meta)
     legend_blocks_shape (safe classify-before-inspect delegate)
     metadata_substrate (exact dict/list, exact str keys, E1 leaves, path-active cycle guard)
----

Before the framework calls `_meta` trusted, the following hostile-controlled operations have already occurred: JSON decode (recursive), Python-literal parse (recursive; can build set/tuple/bytes/complex/non-`str` keys), dict lookups by literal keys, `int()` of `top`/`left` legend coordinates (bounded by CPython's digit limit; a negative or huge anchor reaches `ws.cell()` which raises for row out of range or creates a bounded scan), one `json.dumps` of the merged meta when presentation families changed (exponential under H4), nested-blob unwrap recursion bounded by escaping growth, and a second decode in projection. None of these can execute attacker-selected code; all operate on literal types. The gap between parser safety and trust promotion is therefore resource-shaped, not authority-shaped: H4 inside E3 and the pre-ingress `json.dumps`.

Transition completeness: every `LOADERS` entry returns to `orchestrate`; `establish_initial_state` runs unconditionally before `steps`; uncertified step returns are re-established; `apply_overrides` re-runs ingress on merged metadata; `finalize_managed_state` runs before every saver. No loader, projection, or compatibility path implicitly claims trust it did not establish. The one "already parsed" path that legitimately skips establishment is `run_pipeline`, a documented caller-precondition surface; no framework-managed external route reaches it directly (`managed_pipeline._run_one` calls it only after establishment). Existing tests `test_run_pipeline_performs_no_automatic_ingress_establishment` and `test_managed_seam_establish_initial_state_rejects_the_same_candidate` confirm the split.

== 11. Diagnostics as an attack surface

* Inside `core.scalar_values`, `domain.ingress.*`, and `managed_pipeline`: constant type names, positional paths, no value rendering. Holds.
* `OrdinaryStructureAdmissionError` includes `frame_name!r`; the name is proven exact `str` before use, so `repr` is safe, but its length is attacker-controlled (workbook sheet name, directory file stem). `SpreadsheetTooLargeError` embeds the ODS table name in its context string. `run_cli` prints the complete message. (H7)
* Library exceptions crossing to the CLI: PyYAML errors carry marks and short snippets; `json.JSONDecodeError` carries positions; pandas `ParserError` carries counts; openpyxl raises typed errors; `ValueError` from `int()` in the ODS parser carries the attribute text (bounded by CPython's message formatting; UNVERIFIED in session). No f-string, `%s`, or logging call renders a raw cell value on any pre-ingress path; `orchestrate` logs kind and path only.
* Exception chaining: `OrdinaryScalarAdmissionError` and E2/E3 errors use `from None`; parser errors propagate unchained. `_meta_change_trace` runs only at DEBUG logging and swallows its own failures.
* Unbounded error aggregation / diagnostic loops over attacker structures: none found; every admission error is raised at the first offending location.

== 14. Findings (new only)

Known limitations already recorded in current authority (no XLSX `ParserLimits`; ODS limits cover materialization only, not sheet count or archive size; YAML aliases resolve to shared identity; `!!binary`/`!!set` reachable; legacy `ast.literal_eval` fallback; XLSX `=`-prefixed strings become live formula cells at the sink; `run_pipeline` is a caller-precondition surface; no CSV/JSON/YAML/XML ceilings; XML entity protection is expat-owned; `defusedxml` not declared) are *not* counted below. Each finding states what is new relative to that record.

=== H1 -- IMPORTANT -- XLSX presentation-metadata walk materializes the sparse bounding rectangle before any rejection point

Observation:: `_extract_text_orientations`, `_extract_horizontal_alignments`, and `_extract_vertical_alignments` (`openpyxl_parser.py` L252, L300, L331) iterate `ws.iter_rows(min_row=1, max_row=ws.max_row, max_col=ws.max_column)`. In openpyxl's normal mode `iter_rows` -> `_cells_by_row` -> `self.cell(row, column)` -> `_get_cell`, which *creates and stores* a `Cell` for every coordinate not already present (`worksheet.py` L251--262, L444--450). `max_row`/`max_column` come from `_cells` keys and include style-only `<c>` elements without values.
Evidence:: Source lines above; `_reader.py` `parse_cell`/`bind_cells` (every `<c>` becomes a `Cell`). The ODS twin extractors clip to `parsed.max_col`/`max_row` and enforce limits; the XLSX ones do not.
What is new:: `FTR-XLSX-PARSER-RESOURCE-LIMITS-P4A` §1.2 records that the extractors "walk the used max_row by max_column rectangle and may build cell-addressed dictionaries". The consequence not recorded is that the walk *allocates and retains* one openpyxl `Cell` per coordinate of the rectangle, so framework-owned memory is governed by the sparse extent (one far cell) rather than by populated cells or file size, and it happens three times over before the table parse and long before establishment.
Risk if ignored:: A kilobyte-scale workbook selects megabyte-to-gigabyte framework allocation with no ceiling; the failure is a `MemoryError`/OOM kill, not a typed rejection. This is exactly the repeated-carrier hazard `review_instructions.adoc` names for ODS, present on the XLSX read path.
Action:: Format-local: iterate only populated cells (`ws._cells` items or `iter_rows` bounded to the parsed table extents), or clip the walk to the discovered table blocks as ODS does; record H1 in the XLSX FTR census as a framework-owned dimension. No Trusted Ingress change.
Disposition:: Open; bounded parser-hardening candidate; magnitude UNVERIFIED.

=== H2 -- IMPORTANT -- openpyxl materializes every coordinate of every merged range during `load_workbook`

Observation:: `WorksheetReader.bind_merged_cells` calls `ws._clean_merge_range(mcr)` for each `<mergeCell>`; that method iterates `mcr.cells` (itertools product over the full range) and assigns a `MergedCell` per coordinate (`worksheet.py` L605--615).
Evidence:: Source lines above; the framework passes `read_only=False`.
What is new:: The FTR records framework-side merged-coordinate enumeration in `_cell_value`; it does not record that the dependency itself expands each merge declaration to per-cell objects before any framework code runs, making a single small `<mergeCell ref="...">` a file-size-independent allocation the framework cannot intercept after `load_workbook` is called.
Risk if ignored:: Same class as H1, but not fixable by clipping the framework walk; any XLSX limits design must either preflight the sheet XML for merge extents or accept this as a dependency-owned non-guarantee.
Action:: Record as dependency evidence in the XLSX FTR's resource decision table; evaluate whether a package-level preflight (parse `mergeCells` refs from the worksheet part before `load_workbook`) or read-only mode is viable without breaking merge-based header detection.
Disposition:: Open; design input for `FTR-XLSX-PARSER-RESOURCE-LIMITS-P4A`; magnitude and read-only behavior UNVERIFIED.

=== H3 -- IMPORTANT -- ODS `text:s` count expands a scalar without any budget

Observation:: `_cell_text` (`odf_parser.py` L75--78) converts `<text:s text:c="N"/>` into `" " * int(N)`; `N` is attacker-controlled and unbounded. `ParserLimits` counts cells, not scalar bytes. The resulting string object is stored once per `(row, col)` in `values`, copied by reference across `number-columns-repeated`, then flows into row lists, the DataFrame, ingress, and every sink.
Evidence:: Source lines above; `parser_limits.py` has no byte or length dimension.
What is new:: Current authority lists "string-size" as an unbounded ODS dimension at the archive level; it does not record a framework-owned multiplier that turns a few attribute bytes into an arbitrarily large scalar. It is also a non-integer-echo diagnostic path (`int()` `ValueError`).
Risk if ignored:: Gigabyte allocation from a sub-kilobyte ODS; if allocation succeeds, the oversized scalar passes ingress as an ordinary String and is written to every sink.
Action:: Format-local: clamp or reject `text:c` above a small constant (ODF authoring never needs more than a few thousand), or add a scalar-length dimension to `ParserLimits` if a second consumer needs it. No Trusted Ingress change.
Disposition:: Open; bounded parser-hardening candidate; magnitude UNVERIFIED.

=== H4 -- IMPORTANT -- The `_meta` substrate validator and spreadsheet meta sinks are exponential over admitted shared aliases

Observation:: `admit_metadata_substrate` permits shared acyclic aliases and rejects only path-active cycles: `_validate_container_with_cycle_guard` adds the node id before validating and discards it after (`metadata_admission.py` L208--225); there is no "already validated" memo, so a container reachable by many paths is re-validated once per path. PyYAML resolves aliases to one shared object, so a k-level doubling DAG in `_meta.yaml` is linear to parse and 2^k to admit. The same DAG is expanded to a tree by `json.dumps` in `flow._dump_workbook_meta_blob` (XLSX/ODS sink) and in the parser-side `_store_workbook_meta`; `yaml.safe_dump` on the JSON/YAML-dir sink preserves aliases (expected; UNVERIFIED).
Evidence:: Source lines above; `test_shared_acyclic_alias_is_admitted_without_rejection` documents the accepted alias admission.
What is new:: Alias sharing is a known accepted grammar property. The consequence not recorded is that the admission check is itself an O(paths) walk -- the first amplifier -- and that the persisted `_meta` contract on spreadsheet sinks is a *tree*, so the substrate grammar admits metadata whose serialized form on one sink is unbounded relative to its serialized form on the input. This is a cross-backend inconsistency in an accepted invariant (bounded substrate).
Risk if ignored:: A small YAML sidecar makes ingress and/or the spreadsheet meta write take unbounded CPU/memory, after every parser has succeeded.
Action:: Two local corrections, both outside the scalar grammar: (a) in the substrate validator, keep the path-active cycle guard and add a `validated_ids` set so each container is validated once (validity is path-independent, so this is a pure complexity fix); (b) an architectural clarification of whether the substrate contract is a DAG or a tree -- if a tree, reject or bound shared containers at ingress; if a DAG, bound expanded size at the JSON-blob sinks. Recommend (a) immediately and (b) as a small contract note.
Disposition:: Open; current correctness/resource bug in the substrate validator plus architectural clarification; magnitude UNVERIFIED.

=== H5 -- IMPORTANT (deployment-qualified) -- Directory carriers follow symbolic links, reading files outside the input root before ingress

Observation:: `csv_backend.read_multi`, `json_backend.read_multi` (files and `_meta.yaml`), `yaml_backend.load_yaml_dir` (files and sidecar), and `xml_backend.read_multi` enumerate with `Path.glob` and open every match; none checks `is_symlink()` or that the resolved path stays under the input directory. Writers have exact-root containment and a symlink-escape test; readers have none.
Evidence:: Source of the four loaders; `test_description_authorization_resources.py::test_structured_yaml_existing_symlink_escape_denies` (writer side only).
What is new:: Not recorded in any authority. It is a filesystem-read capability exercised by artifact *structure* before any rejection point: the contents of an arbitrary operator-readable file become a Frame and are written to the configured output.
Risk if ignored:: When the artifact is a directory delivered by extraction of an archive that preserves symlinks or by a repository checkout, an attacker can exfiltrate any file the process can read into the pipeline's output. Qualification: the operator chooses the input path and many deployments never accept directory artifacts from outsiders.
Action:: Router/loader-local: skip or reject members whose `resolve()` is not under the input root's `resolve()` (one small shared helper for the four directory loaders is justified: same accepted/rejected vocabulary, same layer, same diagnostics), or document the non-guarantee explicitly in the boundary matrix. No Trusted Ingress change.
Disposition:: Open; bounded parser-hardening candidate or documented non-guarantee; platform behavior UNVERIFIED in session.

=== H6 -- MINOR -- `veryHidden` XLSX sheets are read as visible payload

Observation:: `parse_workbook` treats only `sheet_state == "hidden"` as a hidden key/value sheet (`openpyxl_parser.py` L57); openpyxl also yields `"veryHidden"`. Such a sheet becomes a payload frame; a `veryHidden` `_meta` sheet becomes `frames["_meta"]` as a DataFrame, rejected by E3 as `invalid_metadata_root`.
Risk if ignored:: Semantic confusion only (unexpected frame in output, or a confusing rejection); fails closed for `_meta`.
Action:: Treat `veryHidden` like `hidden` in the XLSX parser.
Disposition:: Open; format-local correctness.

=== H7 -- MINOR -- Attacker-controlled identifiers are echoed at unbounded length in pre-ingress and CLI diagnostics

Observation:: ODS table names appear verbatim in every `SpreadsheetTooLargeError` context (`f"ODS sheet '{table_name}' ..."`); `OrdinaryStructureAdmissionError` renders `frame_name!r`; `run_cli` prints the full `str(e)`. Content is safe (exact `str`), length is not.
Risk if ignored:: Log/terminal flooding by a multi-megabyte sheet name; no code execution or value disclosure beyond the name itself.
Action:: Truncate identifiers in parser/CLI diagnostics (a bounded `_short_name` helper local to `parser_limits`/`cli.runtime`).
Disposition:: Open; optional defense-in-depth.

=== H8 -- MINOR -- `RecursionError` from deep `_meta` blobs bypasses the typed fallback chain

Observation:: `_read_meta_sheet`, `_read_meta_payload`, `_try_parse_blob`, `_dump_workbook_meta_blob`, and `_workbook_meta` catch `(JSONDecodeError, TypeError)` / `(ValueError, SyntaxError, TypeError)` only; a deeply nested blob raises `RecursionError` from `json.loads` or `ast.literal_eval`, which propagates as an untyped failure from inside the parser.
Risk if ignored:: Fails closed, but with a non-typed error and after parser work; a reviewer could misread it as a crash rather than a rejection.
Action:: Catch `RecursionError` at the blob decode sites and raise the parser's typed malformed-metadata error.
Disposition:: Open; optional defense-in-depth.

=== H9 -- MINOR -- Negative and non-integer ODS repeat/span attributes are accepted or echoed

Observation:: `int(...)` on `number-rows-repeated`, `number-columns-repeated`, `number-rows-spanned`, `number-columns-spanned`, and `text:c` accepts negatives (indices move backwards and overwrite earlier cells) and raises a raw `ValueError` with the attribute text for non-integers.
Risk if ignored:: Bounded semantic confusion; diagnostic echo (CPython-bounded; UNVERIFIED).
Action:: Parse repeats through one bounded helper that rejects `< 1` and non-digit values with a typed error.
Disposition:: Open; format-local correctness.

=== INFO / WATCH

* *HW1* -- The ODS default cell ceiling is a format maximum, not a resource budget: 10,000,000 content cells per sheet, unbounded sheets, and the same payload materialized up to four times before ingress completes. Known in outline (release notes: "generous"); worth stating plainly in the boundary matrix.
* *HW2* -- `data_only=True` and the string collapse are semantic choices with no parser-security effect; presenters must not describe them as protections. Formula cells without cached values silently read as `""`.
* *HW3* -- `defusedxml` protects both spreadsheet parsers only because odfpy requires it; the XML backend uses stdlib ElementTree and inherits expat's limits only. Declaring `defusedxml` and using `defusedxml.ElementTree.parse` in `xml_backend` is a one-line professional-demo prerequisite.
* *HW4* -- Backend divergence on booleans: YAML `true` -> Boolean; CSV `true` -> String `"true"`; JSON `true` -> String `"True"` via `astype(str)` (Python repr, not JSON syntax, so a JSON->JSON round trip changes the literal). Accepted carrier semantics under the no-normalization decision; a backend-contract wart, not a trust-boundary defect. Large JSON integers may be rendered through float conversion (UNVERIFIED).
* *HW5* -- E2 admission is a per-cell Python loop (`frame.iat`); at the ODS ceiling this is tens of millions of Python calls after the parser has already succeeded. Proportional, not amplifying; relevant to any future time budget.

== 17. Durable hostile-input / parser-boundary conclusions

. Trusted Ingress is a semantic postcondition over parsed carriers: it decides admissibility of what a parser produced, never the cost or safety of producing it. Parser safety and payload conformance are two boundaries with two owners.
. Every framework-managed external route passes through one seam, and no loader or projection path can return ordinary Domain Frames without establishment; the caller-precondition surfaces are deliberate, documented, and not reachable by accident from an external artifact.
. No supported input format can activate an import, callable, subprocess, or network access through parsing; the only payload-driven capability is filesystem read via symlinked members of directory carriers.
. Resource bounding is format-specific by construction: ODS bounds its own materialization of repeated carriers before expansion; every other format's cost is dependency-owned and proportional to decompressed input, with a short list of identified non-proportional amplifiers.
. The dangerous amplifiers are those where a small declaration controls work independent of file size: sparse-extent walks, repeat/count attributes, merge declarations, and shared-alias DAGs. Bounds must be enforced at the point where the declaration is expanded, in the parser that owns it.
. An accepted substrate grammar that permits shared structure must specify whether consumers may treat it as a tree; otherwise every tree-walking validator or serializer is a latent exponential path.
. Value-selection switches (`data_only=True`, string collapse) and safe constructors (`yaml.safe_load`) are semantic guarantees, not resource guarantees; each parser needs both stated separately.
. Diagnostics discipline has two independent dimensions: never executing a rejected value's behavior, and bounding the length of what is echoed. The ingress package satisfies both; surrounding parsers and the CLI satisfy only the first.
. Transitive dependency facts (`defusedxml` via odfpy) are real protections but not portable claims until declared.
. "Boundary identified" is not "boundary hardened": the open XLSX FTR's own rule applies to every finding here.

=== Claims the project should not make

. "Trusted Ingress makes untrusted spreadsheet files safe to process."
. "External payloads are resource-bounded" or "parsed through bounded adapters" (true only for ODS materialization).
. "`data_only=True` protects against malicious workbooks" or "formulas are neutralized on input".
. "Parser behavior is format-neutral" or "ODS and XLSX offer the same guarantees".
. "A value admitted by Trusted Ingress is safe for every sink."
. "Public/untrusted XLSX upload readiness is established" while `FTR-XLSX-PARSER-RESOURCE-LIMITS-P4A` is open and H1--H5 are unaddressed.
