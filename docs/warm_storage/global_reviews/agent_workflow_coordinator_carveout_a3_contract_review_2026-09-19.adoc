== 3. Ownership / authority

The steady-state model -- one Coordinator-owned resource, one production
loader, mandatory injection, no selector, no registry, no runtime override, no
repository fallback -- is coherent and fits current seams.

* *No new selector.* WorkItem/Profile/RepositoryPolicy/component manifest are
  strict-key schemas (probe above); `_parse_args()` gains nothing; `prompt.py`
  and `operator.py` read no environment for prompt material. Contract forbids
  adding any. Confirmed.
* *Not a `PromptComponent`.* Correct: `PromptComponent.reference()` carries a
  `git show <rev>:<path>` retrieval identity and participates in
  `COMPONENT_LIMIT_BYTES`/`CONTEXT_LIMIT_BYTES` omission; neither fits a
  mandatory Coordinator resource. Keeping it out of `governing` and
  `_governing_inputs_unchanged()` is correct because those re-read the operated
  repository at later HEADs.
* *Test injection.* Passing a loader-produced value through internal parameters
  is not production authority provided the parameter has no default and
  assemble-time re-validation is defined (F5).
* *A1 reservation vs. loader authority.* Truthful. The reservation is a
  physical mutation ceiling over a Core-tracked file; the loader never consults
  `--repository`, `git show`, or `_pinned_text()`.
* *Hidden second authority -- found, but in content precedence, not in
  loading.* The contract states "Consumer task and selected component content
  remain authoritative for the work and repository engineering rules" without a
  conflict rule. Because a selected consumer component contradicts the generic
  Git-ownership rule, consumer material becomes a de facto second authority over
  Coordinator invariants once the task restatement is removed. See F1.

== 4. Package-relative loading

`importlib.resources.files(__package__)` in `prompt.py` resolves to
`scripts.workflow_coordinator` (a regular package inside the `scripts`
namespace root) and returns a `pathlib.Path` in the current source layout
(probe: `PosixPath('.../core/scripts/workflow_coordinator')`). This holds for
module import, pytest, and both direct-script launchers, because `prompt.py` is
always imported as a package member (`from .adapter import ...`). No A4' or C
work is needed to make it work now.

Challenges:

* Source-package success proves nothing about installed behavior: `scripts/` is
  not in the distribution, so there is no installed package to prove. The
  contract correctly does not claim otherwise and assigns package-data to C.
* `requires-python = ">=3.10"`. Multi-argument `Traversable.joinpath(a, b)` is
  only guaranteed from 3.11; the readiness example uses it. It works today only
  because the source reader returns `pathlib.Path`. Watch W1: prefer
  `files(__package__) / "resources" / "agent_operating_contract_v1.txt"`.
* In the dogfood configuration the Coordinator is imported from the same Core
  checkout it operates on, so the package-resolved file can be the operated
  repository's own tracked file. This does not violate "no repository fallback"
  (the path is never derived from repository inputs), but it means the no-fallback
  test must force unavailability by replacing the reader, not by deleting the
  real file (W2).

*Result:* implementable at HEAD without A4'/C.

== 5. Identity / version / digest -- simplicity challenge

Elements assessed against the actual system (one resource, one version,
source-checkout execution, one maintainer, no distribution):

[cols="2,4,2",options="header"]
|===
|Element |Assessment |Keep?

|Fixed contract ID
|Needed only as a provenance label so the plan names what the digest belongs
to. A module constant.
|Keep (constant)

|Integer version `1`
|Same; lets a later identity decision be visible. No multi-version machinery is
proposed. Good.
|Keep (constant)

|Fixed filename/path
|Needed to load. Encoding `v1` in the name is harmless.
|Keep (constant)

|Identity prologue
|Useful *content*: the agent and a human reader see which contract this is. As
a *runtime validation branch* it is redundant (see below).
|Keep as content; do not parse at runtime

|Hard-coded reviewed SHA-256
|See below.
|Keep; make it the sole runtime content check
|===

*Does the runtime digest earn its place?* Yes, for one concrete invariant:
_the Coordinator never dispatches operating-contract bytes other than the
reviewed v1 bytes._ The resource is deliberately *not* Git-pinned by preflight
(it is not a consumer input), and the Coordinator runs from a source checkout
whose working tree may be dirty or may be the operated repository itself.
Without the constant, a local edit would silently flow into every prompt,
labelled "version 1", with only a changed digest in `operator-plan.json` for a
later auditor to notice. With it, the edit fails closed at preflight and forces
the explicit identity decision the contract already requires. Cost: one
constant, one comparison, and a deliberate constant update whenever the text
changes -- which is the intended review forcing function, not duplicate truth.

It is *not* a security control (anyone who can edit the resource can edit the
constant in the same tree) and should not be described as one; the contract
does not, which is correct.

*Where the proposal is over-specified:* WFC-PROMPT-05 and the failure/acceptance
lists require the loader to validate "exact bytes, identity, version, and
reviewed SHA-256" and treat empty bytes, invalid UTF-8, wrong ID, unsupported
version, filename/prologue inconsistency and digest mismatch as distinct
refusals. Once the reviewed digest matches, every one of those properties is
already fixed by the reviewed bytes; once it does not match, the load refuses
anyway. The extra branches are either dead (if the digest is checked first) or
redundant (if checked before it), and the matrix asks for a negative test per
branch. Similarly the loaded value's ID/version/resource fields are constants,
and byte count/digest are derivable from the text because strict UTF-8
decoding round-trips exactly (probe: `"﻿abc\r\n"` round-trips
byte-identically). Smallest simplification: F4.

== 6. Prompt semantics

Mandatory position `header -> contract -> selected consumer components ->
workflow policy -> task -> context/diff -> result footer` preserves the
existing authority model (generated facts first; Coordinator authority before
consumer material; footer last) and is a one-line insertion in
`assemble_prompt()`. Excluding the contract from `used`/omission accounting is
correct for a fixed reviewed text.

Generated facts vs. contract prose do not conflict *provided* the prose only
names facts that are actually projected (F3). The contract's instruction to
"point to projected schema/phase facts rather than duplicate validation
algorithms" is right; the Conventional-Commit/identity-token rule should be
stated as an obligation, not as its regex.

Generic-rule challenge against the V1 bullets:

* "current phase authority are the invocation facts" -- only partly projected;
  actions, human gates and review/Finding authority are not in the prompt (F3).
* "read-only Git inspection is permitted only where current work/phase authority
  allows it" -- no phase authority governs Git reads; current truth is "allowed
  unless the task restricts it" (F3).
* Missing generic, code-enforced rules that current task text supplies: the
  WFC-GIT-08 CommitIntent subject rule; that agent-reported test results are not
  Coordinator-trusted evidence (A2); an explicit list of forbidden mutating Git
  commands (F2).
* Missing precedence rule over conflicting consumer material (F1).
* All other bullets (identity use, no agent-owned mutating Git, CommitIntent is
  a proposal, mandatory correlated envelope, truthful fields, escalation
  vocabulary) are generic and backed by current code.

== 8. Failure / provenance

*Pre-Run boundary.* `_preflight()` is side-effect free and precedes
`uuid4()`/`new_run()`/`state_root.mkdir()`/`register_checkout()`/adapter
construction in `main()`; the existing `except Exception` boundary returns
exit status 2. Loading inside `_preflight()` therefore satisfies WFC-AUTH-09 by
construction. `test_operator.py` already instruments `uuid4`, `new_run`,
`register_checkout` and `CodexCliAdapter` with `forbidden(...)` (l.160-163), so
the refusal proof reuses an existing seam.

*Proof harness.* Loading as the first statement of `run_disposable_proof()`
(before `root.mkdir`) refuses before proof-root creation; propagation matches
the existing "proof root must be a new path" refusal. No summary can or need be
written.

*Direct seams.* `run_real_one_hop()` writes `run.json` and `dispatch.json`
before calling `run_one_hop()`; `run_one_hop()` wraps any `assemble_prompt()`
exception as `ExecutionNotStartedError`, and `run_real_one_hop()` then unlinks
the marker and re-raises. So an inconsistent value is correctly classified as
execution-not-started, *but* only after marker/snapshot writes -- acceptable for
an internal inconsistency, unacceptable as a normal load path. Hence the
parameter must be required with no lazy default (F5).

*Single error.* One exception class defined in `prompt.py` is sufficient:
the operator boundary catches `Exception`, the harness propagates, the vertical
seam wraps. No hierarchy is needed; the contract does not propose one.

*Provenance.* ID, version, resource, byte count, SHA-256 in one
`agent_operating_contract` plan object is bounded and sufficient; kept separate
from `governing_inputs` (correct -- different owner, different re-read
semantics); not duplicated per Hop (correct -- one immutable value per Run);
mirrored in the proof summary (reasonable -- no plan exists there). Byte count
is redundant with the digest but mirrors `PromptComponent.reference()["bytes"]`
and costs nothing; not a finding. The optional `PromptPackage` reference is
unnecessary: plan/prompt agreement is provable by asserting the exact contract
text appears once at the required position (W3).

== 10. Simplicity assessment

A3 reduces maintainer concepts: today the generic contract lives in four
places with no identity; after A3 it lives in one file with one constant set,
one loader, one prompt position and one plan object. No registry, module,
schema family, or compatibility path is introduced.

Machinery that does not earn its place: the separate runtime prologue/ID/
version/filename validation branches and their per-branch negative tests, and
carrying constant/derivable fields in the loaded value (F4); the optional
`PromptPackage` reference (W3). Everything else supports the target model:

----
Coordinator owns one generic operating contract.
One loader obtains it (bytes -> reviewed digest -> strict decode).
Every provider-capable Hop receives it, before consumer material, with precedence.
Consumers cannot replace it.
Existing preflight/plan carries its bounded identity.
----

== 11. Acceptance matrix

Sufficient and feasible with current seams, not testing A4'/C, with these
adjustments:

* *Collapse* the identity/version/digest negative rows to: missing/unreadable
  resource; digest mismatch (represented by e.g. one mutated-byte and one
  empty-bytes reader). Replace "wrong ID/unsupported version/prologue mismatch
  each refuse" with one positive test that the reviewed bytes' prologue equals
  the ID/version constants and the filename encodes the version (F4).
* *Add* to real-consumer coherence: for every phase of both real bundles, the
  assembled prompt contains the contract (with its precedence clause) exactly
  once, after the header and before the first consumer component; and each
  removed task clause is covered by V1 text (checked by review of the diff, not
  by an LLM) (F1/F2).
* *Serial reuse:* assert identity (`is`) of the value observed by
  `assemble_prompt` across Hops of one `run_serial_hops` call, plus exactly one
  loader call per operator process.
* *No fallback:* force the reader to fail while a byte-identical file exists in
  the temporary operated repository and cwd; admission refuses (W2).
* *Zero provider:* existing `forbidden(...)` instrumentation for operator;
  `root.exists()` false and fake executable untouched for harness.

The matrix otherwise avoids duplication and tests only A3 concerns.

== 12. Findings

=== F1 -- IMPORTANT -- No precedence rule; a selected consumer component contradicts the generic Git rule once task restatements are removed

Observation:: Every phase of both real consumers selects
`docs/ai_info/git_and_workflow.adoc`, which instructs agents to commit. The
only current override is the task's AGENT GIT RULE, placed after components.
A3 removes that rule from the task and places the generic rule *before* the
components, while section 13.3 says consumer task and component content
"remain authoritative for the work and repository engineering rules".
Risk:: After cleanup the prompt contains two contradictory instructions with
the later, consumer one textually closer to the task and nominally
"authoritative"; an agent commit is then detected only post hoc as an
anomaly/failed Hop. This is a hidden second authority over a Coordinator
invariant and a regression caused by A3 itself.
Smallest correction:: Add to the V1 content contract one precedence clause:
the operating contract's rules (Git ownership, CommitIntent, structured result,
identity, escalation) prevail over any conflicting consumer task or component
text; consumer material may narrow but never widen or replace them. Reword the
13.3 sentence to "... authoritative for the work and repository engineering
rules, except where they conflict with the operating contract". Add the
real-consumer prompt-position assertion in section 11. No component or policy
edit is required.

=== F2 -- IMPORTANT -- Cleanup removal criterion can lose generic rules the V1 list omits

Observation:: The task files carry generic, code-enforced rules absent from the
V1 bullets: the WFC-GIT-08 CommitIntent subject obligation
(Conventional-Commit-compatible, contains WorkItem ID and Hop ID;
`git_facts.commit_subject_error`); "agent-reported tests are not
Coordinator-trusted evidence" (A2); and a concrete forbidden-command list
(add/commit/reset/clean/push/rebase/amend). The removal rule ("remove generic
semantics now supplied by the resource") does not say what happens to generic
clauses the resource does *not* supply.
Risk:: An implementer following "remove generic Coordinator semantics" deletes
IOR-04's subject-identity sentence and evidence-trust sentence, silently losing
instructions whose violation the Coordinator enforces (rejected CommitIntent,
untrusted evidence), or keeps them and re-creates the fragmentation A3 is meant
to end.
Smallest correction:: (a) Add to the V1 content contract: the CommitIntent
subject obligation stated in words; that agent-reported validation is not
Coordinator-trusted evidence; and a named minimum list of forbidden mutating Git
commands (at least the union already in the two tasks). (b) State the removal
invariant: a task clause may be removed only if V1 states it with equal or
stronger force; otherwise it is retained. Section 7 of this review gives the
clause map.

=== F3 -- IMPORTANT -- V1 wording may assert authority facts that are not projected

Observation:: The prompt header projects IDs, base HEAD, phase, scope, routes,
evidence names and output contract; `[workflow_policy]` projects
`durable_artifact`. `authorized_actions`, `human_gates` and the review/Finding
descriptor are not projected. V1's "current phase authority are the invocation
facts" and "read-only Git inspection is permitted only where current work/phase
authority allows it" refer to authority the prompt does not carry; IOR-04's
generic "ROLE AND PHASE" paragraph already makes the false claim that actions
and Finding authority are in the Coordinator prompt.
Risk:: A Coordinator-owned, mandatory text that is untruthful about its own
projection -- worse than the same error in one consumer task, because it is
now in every Hop of every consumer. Also a likely transplant path for the IOR-04
paragraph.
Smallest correction:: Constrain V1 to reference only the projected facts by
their prompt names (`[identity]` fields and `[workflow_policy]
durable_artifact`) and the adapter-supplied result schema; state that read-only
Git inspection is allowed unless the task restricts it; state that IOR-04
"ROLE AND PHASE" is removed, not transplanted. Do not extend the header in A3
(projection of actions/Finding authority is out of scope).

=== F4 -- MINOR -- Identity validation is layered redundantly; the digest alone suffices at runtime

Observation:: WFC-PROMPT-05 plus the failure list and acceptance matrix require
separate runtime validation of prologue, ID, version, resource name, empty
bytes, UTF-8 and digest. The reviewed digest subsumes all of them. The loaded
value also carries three constants and two text-derivable fields.
Risk:: Dead or redundant branches and five-plus negative tests that each
restate "bytes differ from reviewed bytes"; four representations of one
identity to keep in sync.
Smallest correction:: Loader = read bytes via `importlib.resources` -> refuse
if unreadable -> refuse if `sha256(bytes) != REVIEWED_SHA256` -> strict UTF-8
decode. ID/version/resource are module constants reported in provenance; the
prologue stays in the file and is checked once by a positive unit test. The
loaded value may be a frozen dataclass holding the text, with byte count and
digest as derived properties (mirroring `PromptComponent`). Amend WFC-PROMPT-05
("validate its exact bytes against the reviewed SHA-256") and the failure and
acceptance lists accordingly. Keep the runtime digest (section 5 rationale).

=== F5 -- MINOR -- Internal seam contract underspecified: default and "reassert" undefined

Observation:: The contract says the value is passed through `run_serial_hops()`
-> `run_real_one_hop()` -> `run_one_hop()` -> `assemble_prompt()` and that
prompt assembly "shall reassert the supported tuple", but not that the
parameter is mandatory, nor what reassertion checks. There are roughly fifty
direct test call sites of these functions, a strong incentive for a
default/lazy-load shortcut.
Risk:: A defaulted parameter that lazily loads creates a second load point
after `run.json`/`dispatch.json` writes, silently bypassing WFC-AUTH-09 for any
future caller; a field-only reassertion lets a hand-built value with arbitrary
text reach dispatch.
Smallest correction:: State: the parameter is keyword-only and required at all
four seams (no default, no lazy load); tests obtain the value from the
production loader via one fixture. Define reassertion as
`sha256(value.text.encode("utf-8")) == REVIEWED_SHA256` (exact because strict
UTF-8 round-trips), raising the single Coordinator resource error, which
`run_one_hop()` already classifies as execution not started.

== 13. Verdict

*B -- A3 CONTRACT ACCEPTED AFTER BOUNDED CORRECTION.*

The architecture is the right one and the smallest viable: one Coordinator-owned
resource, one package-relative loader, mandatory injection, bounded plan
provenance, correct phase separation, and no hidden loading authority. It is
not yet safe to implement because the *content* and *cleanup* contracts can
produce an untruthful or self-contradicting prompt (F1-F3). The identity
machinery is slightly over-specified (F4) and the internal seam needs two
sentences of precision (F5).

Bounded corrections required before implementation (FTR 13.3 /
WFC-PROMPT-05 text only; no code):

. F1 -- precedence clause in V1 content; reword the "remain authoritative"
  sentence; add the real-consumer prompt-position acceptance row.
. F2 -- add the WFC-GIT-08 subject obligation, the untrusted agent-reported
  evidence rule and the forbidden-command minimum to V1 content; state the
  removal invariant.
. F3 -- restrict V1 to actually projected facts; fix the read-only Git wording;
  state that IOR-04 "ROLE AND PHASE" is removed, not transplanted.
. F4 -- digest as the sole runtime content check; constants plus derived
  properties; collapse the negative matrix.
. F5 -- required keyword-only parameter at all four seams; define reassertion
  as the digest re-check.

No unresolved architecture question requires maintainer selection.
