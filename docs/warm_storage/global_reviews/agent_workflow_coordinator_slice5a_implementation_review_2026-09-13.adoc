== 1. Verdict

*VERDICT: B -- BOUNDED IMPLEMENTATION CORRECTION REQUIRED.*

The core Slice-5A machinery is sound. Authority ingress (action + path-scope
domination over every profile phase, canonical normalizer), the `> 2` preflight
rejection, the two-layer dispatch eligibility, the H001->H002 serial
continuation gate, governing-input content identity, the publication/marker
ordering, and the structural impossibility of H003 are all correctly
implemented and, for the happy N=2 path, proven with a deterministic fake
adapter and zero real-provider invocations.

Acceptance is nonetheless withheld because of one confirmed correctness
regression and two supporting defects that violate explicit verdict-A gates
("attempt accounting remains truthful", "N=1 evidence remains truthful", "all
18 acceptance cases adequately proven"):

* *F1 (BLOCKING, CONFIRMED):* the operator's post-provider failure path
  regresses N=1/N=2 attempt accounting -- a failure after a consumed provider
  attempt is persisted as the *pre-provider* Run. This reverts the behavior
  that commit `5ec5a7d5` ("correct N=1 operator attempt accounting")
  established.
* *F2 (IMPORTANT):* per-invocation execution-binding evidence hard-codes
  `model=None` / `reasoning=None` even on the supported `CodexCliAdapter` path,
  which carries a concrete `model="gpt-5.6-terra"` / `reasoning_effort="medium"`
  binding. The actual binding is not durably observable.
* *F3 (IMPORTANT):* the adversarial acceptance matrix is not fully proven.
  Several mandated inter-Hop false-continuation cases -- most importantly the
  contract-mandated trusted-commit-B-then-rejection case (matrix item 9) --
  have no direct executable test; the N=2 `main()` integration path is
  untested.

All three corrections are bounded and local; none requires a live provider,
and none indicates a material architectural mismatch. Hence verdict B, not C.

== 3. Implementation topology

The supported declarative operator (`operator.py:main`) remains the sole
authority ingress. `_preflight` now:

* normalizes `WorkItem.scope` and every phase's `authorized_scope` with the
  single canonical `_relative_path` normalizer and requires every normalized
  phase-scope entry to be contained beneath a normalized WorkItem-scope entry
  (`operator.py:136-145`);
* checks every profile phase's `authorized_actions` against
  `RepositoryPolicy.actions` (`operator.py:137-142`);
* rejects `max_autonomous_hops > 2` before Run creation (`operator.py:146-147`);
* pins SHA-256 digests of every repository-backed governing input -- the five
  YAML/task sources and every selected component -- into `governing`
  (`operator.py:161,169`).

`main()` delegates the serial lifecycle to the new
`run_serial_hops()` (`operator.py:206-267`), which:

. runs H001 via the reused `run_real_one_hop`;
. appends per-attempt evidence and publishes `execution-evidence.json`;
. returns immediately unless `hop_limit == 2` and `status is READY`;
. re-validates checkout + `preflight_hop` at the current HEAD, then re-reads and
  re-hashes every governing input; either failure calls `stop_continuation`
  (publishes `awaiting_human`) with no H002;
. runs H002 with a fresh invocation ID and a bounded H001-summary context item.

The canonical provider boundary `run_real_one_hop` gained a small
`dispatch_eligible(run)` fail-closed assertion before marker creation /adapter
entry (`slice4.py:38-40,159-160`) and an injectable `adapter` seam plus a
`context_items` pass-through into `assemble_prompt`. `vertical.run_one_hop`
gained the `context_items` parameter only. The Run/Hop/reducer model is
unchanged; the `N=2` ceiling is rollout policy (`hop_limit =
work_item.max_autonomous_hops`) and not a two-node redesign.

== 4. Authority ingress (axis 1)

*SOUND.* `RepositoryPolicy.scope` is still consumed only as a repository-identity
allowlist (`repository_identity` admission); it is not reinterpreted as a path
lattice. Action and path-scope domination are computed for *every* phase before
H001 and before any Run creation or provider entry, with fake/provider
invocation count zero on rejection (proven by `test_phase_actions_exceeding_
repository_policy_reject_before_provider` and `test_phase_scope_escape_rejects_
before_provider`). The normalizer rejects absolute, `..`, and ambiguous
spellings via one shared `_relative_path`; there is no second, weaker path
normalizer (WATCH-1 hardened -- see section 12).

The only supported ingress is `main()`. `run_serial_hops` and `run_real_one_hop`
are lower-level and remain dominated by the pre-H001 ingress; the tests exercise
them directly but that is test-only wiring, not a supported alternate authority
ingress. No supported caller bypasses the canonical ingress.

== 5. Serial continuation / false-continuation analysis (axes 2, 3, 4)

*Continuation gate (axis 2 / axis 3): SOUND for closure, contract-incomplete in
two predicates (WATCH).* The gate proceeds to H002 only when `hop_limit == 2`
and `run.status is RunStatus.READY`, then re-runs `validate_checkout` +
`preflight_hop` at `run.current_head` (HEAD B) and re-hashes every governing
input. Because *any* H001 rejection (unknown route ->
`mechanical_preemption:unknown_route`, invalid Finding -> `ReductionError`,
human/escalation/malformed -> `awaiting_human`, budget -> `awaiting_human_
budget`) produces a non-`READY` status, the single `status is not READY` check
closes matrix items 5-10 by construction. The current phase is guaranteed inside
the pre-H001 authority envelope because *every* phase was validated pre-H001, so
no per-Hop re-check is required.

Two continuation-gate predicates named by the contract are satisfied only
*indirectly* (safe, but not asserted independently):

* *Checkout-association equality (axis 3 IMPORTANT PROBE):* the outer gate calls
  `validate_checkout(state_root, repository)`, which checks the on-disk
  association against live Git facts but does *not* compare against the
  originally supplied `association` object. Exact original-association equality
  is enforced only by the inner `run_real_one_hop` for H002
  (`slice4.py:166,176`). In the single-association design the on-disk mapping is
  written once by `register_checkout` and never rewritten between Hops, so the
  combined two-layer architecture *does* satisfy the invariant. Disposition:
  option *B* -- safe, but the OUTER gate is contract-incomplete (WATCH-3).
* *Marker retirement / publication sequence:* the gate infers these from a
  non-`READY` status rather than asserting marker-absence or checkpoint-presence
  directly. Safe (a surviving marker or reconcile leaves the Run non-`READY`),
  but not an explicit predicate (WATCH-4).

*Real-boundary eligibility (axis 4): SOUND.* `dispatch_eligible` is asserted at
the very top of `run_real_one_hop`, before `preflight_hop`, marker creation, and
adapter entry. It is a single small predicate (`status == ready and hop_used <
hop_limit`); it does not duplicate route evaluation, governing-input identity,
Git revalidation, or prompt construction. Proven for the *exhausted* case by
`test_real_boundary_refuses_ineligible_or_exhausted_run_before_marker`
(`hop_used == hop_limit`, no `dispatch.json`). The non-`ready`/preempted status
branch is logic-closed but not directly asserted at this boundary (folded into
F3).

*No-H003 (axis 2): SOUND.* `run_serial_hops` has no loop past H002; after H002
`hop_used == hop_limit == 2`, so both `dispatch_eligible` and `record_hop`
("autonomous Hop budget exhausted") make a third attempt impossible, and no
H003 marker or invocation ID can be allocated. Proven by
`test_n2_serial_driver_uses_fresh_context_and_never_allocates_h003` (H002 routes
`goto prepare` yet terminates `awaiting_human_budget`, `hop_used == 2`, exactly
two Hops).

== 6. Persistence / recovery / attempt accounting (axes 6, 7)

*Publication / crash semantics (axis 6): SOUND.* The one-Hop sequence remains
run.json -> checkpoint.json -> marker retirement, sequential and non-compound
(`slice4.py:213-215`). There is no auto-resume or replay: `main` rejects a
pre-existing `state_root` (`operator.py:120-121`), so re-running requires a new
root; the only continuation is in-process inside a single `run_serial_hops`
call. A present/stale marker or reconcile state leaves the Run non-`READY`, so
the gate refuses H002. No event store or two-phase commit was added.

*Post-dispatch failure accounting (axis 7): REGRESSED -- see F1 (BLOCKING).*
`main()` sets `real = None` at `operator.py:365` and again at `:373`, and never
rebinds it to the completed Hop run. Its exception handler therefore computes
`known_run = run` (the *original* pre-H001 `new_run`, `hop_used=0`,
`status=ready`, `current_head=A`), `known_outcome = None`, and hard-codes
`invocation_id="unknown"` (`operator.py:384-388`). Any exception raised after a
consumed provider attempt -- H002 provider entry, `execution-evidence.json`
publication, `stop_continuation` I/O, `recover_uncertain` observation, or
`_summary` Git observation -- is persisted as a pre-provider failure. The
authoritative `final_run` computed at `:368` is in scope but the handler never
references it.

This was confirmed with a deterministic probe (fake executable, no provider)
reproducing the exact scenario of the pre-existing
`test_post_provider_summary_failure_is_attempt_failure_with_evidence`: after a
successful, charged N=1 Hop with a forced `_summary` failure, the persisted
`operator-summary.json` reports `run_status='ready'`, `hop_used=0`,
`invocation_id='unknown'`. Pre-Slice-5A, `main` captured
`real = run_real_one_hop(...)` and reported `run_status='completed'`,
`hop_used=1`, and the real invocation ID. For N=2 the misrepresentation is
worse: a post-H001 failure hides committed HEAD B and the consumed H001 attempt
entirely.

Attempt *consumption* on the durable side is partially preserved -- per-attempt
`execution-evidence.json` is written before most post-attempt failures -- but
the top-level operator summary, which is the operator evidence of record,
regresses. The pre-existing guard test passes only because it asserts
`operator_status`/`operator_error` and not `run_status`/`hop_used`/
`invocation_id`.

== 7. Context / binding / evidence (axes 8, 9, 10)

*Fresh H002 context (axis 9): SOUND.* `run_one_hop` derives its phase from
`run.phase` (phase B after reduction) and the header projects phase B's name,
`base_head=B`, authorized scope, permitted routes, and evidence
(`prompt.py:65-75`); `_h1_context` adds a single bounded prior-Hop summary
context item. No stale phase-A projection survives, and no continuing provider
conversation is introduced (`context="fresh"`). Proven by the H002 prompt
assertions (`phase=verify`, `prior_hop=H001`). The header not projecting
`authorized_actions` is pre-existing accepted behavior, not a Slice-5A change.

*Per-invocation binding (axis 8): DEFECTIVE for the supported path -- see F2
(IMPORTANT).* `_execution_evidence` records `model=None` and `reasoning=None`
unconditionally (`operator.py:199`). For the injected local fake this is
truthful. But the supported normal boundary uses `CodexCliAdapter`, which binds
`model="gpt-5.6-terra"` and `reasoning_effort="medium"` and passes them to the
provider command (`codex_adapter.py:143,149-150`). The contract requires "the
actual binding used for every attempt shall be durable execution evidence ...
model, reasoning configuration ...". Because the values are hard-coded rather
than resolved from the adapter, the actual binding is not durably observable on
the codex path. This is a resolver/observability gap, not a request for a
ModelSelector.

*N>1 / N=1 operator evidence (axis 10): TRUTHFULLY MIGRATED, with minor loss.*
Per-Hop `hops[]` and `execution_evidence[]` truthfully reconstruct ordered Hop
IDs, distinct invocation IDs, per-Hop base/end HEADs, actual commits, per-Hop
changed paths (from each Hop's `base..end`), outcomes, and cumulative
budget/final status. Top-level `invocation_id` is preserved via the last
attempt. However `main` now passes `outcome=None` to `_summary`, so the
top-level `provider` object is always `null`; per-Hop `returncode`/`timed_out`
migrated into `execution_evidence`, but `candidate_result_present` is dropped
entirely (MINOR, F4). The implementer claim "existing top-level one-Hop summary
facts remain meaningful" is therefore slightly overstated but not misleading.

== 11. Findings

[discrete]
=== F1 -- Post-provider failure is persisted as a pre-provider Run

ID:: F1
SEVERITY:: *BLOCKING* (CONFIRMED)
CONTRACT CLAUSE:: 11.5.1 "Attempt consumption" ("attempt is consumed ... whether
the result succeeds, is malformed, times out, is uncertain, or is rejected");
"N>1 operator evidence and summary" ("shall remain truthful for both N=1 and
N=2"); review axis 7. Regresses commit `5ec5a7d5`.
CODE / TEST EVIDENCE:: `operator.py:365` and `:373` set `real = None` and never
rebind it; `:384-388` compute `known_run = run` (original), `known_outcome =
None`, `invocation_id="unknown"`. The authoritative `final_run` (`:368`) is
ignored by the handler.
REPRODUCER OR PROOF:: Deterministic probe (fake executable, no provider)
mirroring `test_post_provider_summary_failure_is_attempt_failure_with_evidence`:
after a charged, completed N=1 Hop with `_summary` forced to raise, the
persisted `operator-summary.json` shows `run_status='ready'`, `hop_used=0`,
`invocation_id='unknown'`. Pre-5A it showed `completed` / `1` / real ID.
WHY IT MATTERS:: The operator evidence of record misrepresents a consumed
provider attempt as never having occurred. For N=2 it hides committed HEAD B and
the consumed H001 attempt. Directly violates the verdict-A "attempt accounting
remains truthful" and "N=1 evidence remains truthful" gates.
SMALLEST BOUNDED CORRECTION:: In `main`, capture the authoritative latest Run,
outcome, and invocation ID from `run_serial_hops` (e.g. rebind a `known` tuple
as each Hop returns, or have `run_serial_hops` also return the last outcome /
invocation), and have the exception handler report that latest state and the
last known invocation ID instead of the original `run` / `"unknown"`. Strengthen
the guard test to assert `run_status`/`hop_used`/`invocation_id`.
LIVE PROVIDER NEEDED TO CORRECT:: No.
RE-REVIEW REQUIRED:: Yes -- confirm N=1 and N=2 post-provider failure summaries
report the latest authoritative Run and invocation.

=== F2 -- Execution-binding evidence omits the actual model/reasoning

ID:: F2
SEVERITY:: *IMPORTANT*
CONTRACT CLAUSE:: 11.5.1 "Per-invocation execution binding" ("the actual binding
used for every attempt shall be durable execution evidence ... model, reasoning
configuration, context mode, and timeout/execution settings"); review axis 8.
CODE / TEST EVIDENCE:: `operator.py:199` hard-codes `"model": None, "reasoning":
None`; `codex_adapter.py:143,149-150` shows the supported adapter binds
`model="gpt-5.6-terra"`, `reasoning_effort="medium"` and passes them to the
provider command.
REPRODUCER OR PROOF:: Static: on the `CodexCliAdapter` path the recorded
`model`/`reasoning` can never reflect the values actually used, because they are
constants in `_execution_evidence` rather than resolved from the binding.
WHY IT MATTERS:: The durable per-invocation binding is the contract's audit

blank. This is the "actual binding used to be durably observable as applicable"
requirement.
SMALLEST BOUNDED CORRECTION:: Have the trivial per-invocation resolver surface
the adapter's `executable`/`model`/`reasoning_effort` (e.g. read them from the
`CodexCliAdapter`, or thread a small binding record) and record those in
`_execution_evidence`; keep `None` only for a fake/local adapter that has none.
LIVE PROVIDER NEEDED TO CORRECT:: No (fake/local proof suffices; no invocation).
RE-REVIEW REQUIRED:: Yes -- confirm codex-path evidence records the real
binding.
