Three properties make this Class A rather than B:

. For one whitespace-padded row, one `validate_fk_helpers` run says the key
  is resolvable *and* that the helper is wrong; the helper is `""` because
  enrichment did not resolve it. The diagnostic names the wrong cause.
. Spreadsheet parsers do not strip payload cells (their `.strip()` calls
  serve table-extent detection and style names only), so whitespace-padded
  keys are reachable from ordinary XLSX/ODS input, and `" "` is an ordinary
  String under the accepted scalar grammar.
. A blank or `None` target row is a resolution target for `add_fk_helpers`
  (`""`) and `add_lookup_helpers` (`None`, `""`) while every validator
  treats the same carriers as non-identity. The accepted C3-WI02 assessment
  recorded Missing target-ID identity as UNDECIDED; enrichment has already
  decided it, twice, differently.

No Functional Model, Semantic Model, User Guide, or test states a key
equality or trimming rule (`grep` over `docs/functional_model`,
`docs/user_guide`, and the FK/Lookup/reference tests finds none). This is an
unowned semantic, not a disputed one.

=== B-1 (Class B) -- Missing carrier as key is decided implicitly by producers

Subsumed in A-1's last two rows but distinct in ownership: the C3 assessments
correctly declined to let a validator decide it; the producers
(`_norm_id`, pandas merge) decide it silently. Any bounded key-identity
decision must include "is a Missing carrier ever a key?" or it will be
undone by the producers.

=== B-2 (Class B) -- Lookup value mode rewrites every Missing carrier in the output frame

`enrich_lookup/operation.py:209` applies
`enriched.where(pd.notnull(enriched), "")` to the whole merged frame in value
mode, regardless of `missing` mode. Source-frame columns that carried `None`
or NaN leave the step as `""` (probe: a source `note` column of `[None]`
becomes `[""]`). Semantic category is preserved (`""` is Missing), but the
carrier changes silently outside the documented miss-local rule, and the
accepted posture is "classification does not normalize; no general scalar
normalizer". Bounded, owner-local, and worth a decision when A-1 is opened,
not a separate cycle.

=== C-1 (Class C) -- Verbatim missingness predicate copies

`_cell_primitives._is_empty_cell`, `discriminator_split/values._is_empty_cell`,
`sparse_defaults._is_blank_cell`, `odf_renderer._is_missing_carrier` are

unbounded `pd.isna` dispatch, which Trusted Ingress makes harmless). Two
variants are deliberate and documented: `physical_labels._is_missing_like`
(a `""` label is not missing) and `sparse_defaults._is_missing_scalar`
(strings never missing, for equality). Mechanical duplication with shared
semantics; low risk; not a cycle on its own.

== FK Family Cycle 3 disposition

*Verdict: REDIRECT -- CURRENT EVIDENCE POINTS TO A DIFFERENT BOUNDED QUESTION.*

* *What "supported types" question is still real?* The accepted C3
  supported-types assessment already established that the six-category
  scalar grammar is inherited, that policy names are deliberately strings,
  that helper payload is verbatim, and that sink stringification is
  adapter-owned. Its own "unresolved questions" list is dominated by key
  identity: `1`/`"1"`, trimming, Missing target IDs, Lookup's textual versus
  pandas comparison. That is the only live type question left in the family.
* *Which code paths encode it?* The four interpreters in A-1. Two of them
  (`reference_validations`, `graph_validations`) are outside the FK family
  and were never in Cycle 3's scope.
* *Would continuing reveal ownership problems or confirm contracts?* C3-S2
  (remove the `"nan"` guard) is a correct, tiny bug fix that confirms an
  existing contract and yields no new information. Any further FK-internal
  Cycle-3 slice on key identity would decide the rule for one of four
  owners, which is exactly the "sort of A and sort of B" ownership the DMC
  forbids.
* *Has later work made it less important?* C3-S1 already delivered the one
  safe, family-local alignment. The probe shows the rest is cross-owner.
* *Is the ambiguity owned by a different area now?* It is owned by no area.
  That is the redirect target.
* *Would starting the next Cycle-3 slice produce meaningful information?*
  No. Candidate #1 would.

Practical consequence: C3-S2 may be executed at any time as an ordinary
bounded bug fix under its accepted assessment, but it should not be
presented as Cycle-3 progress, and Cycle 3 should be closed with a pointer
to candidate #1 once #1 is commissioned. This assessment does not close or
start anything.

== FK public helper-surface evidence

*Determination: SOME NEW EVIDENCE, BUT STILL PREMATURE.*

New evidence, verified by probe and absent from the FTR's Section B
capability inventory: the two surfaces do not share key semantics.
`add_fk_helpers` resolves `1` against `"1"` and misses `1.0` against `1`;
`add_lookup_helpers` raises a raw pandas `ValueError` for the first and
resolves the second; `add_lookup_helpers` resolves a `None` source key to a
`None` target row; both resolve `""` to a `""` target row while every
validator treats those as non-identity. Consolidation is therefore not only
a naming/aliasing/certification decision; migrating a consumer from one
surface to the other can change which rows resolve.

Why still premature: the FTR's stated method (inventory, then decide per
feature) cannot run truthfully until candidate #1 has decided what "resolves"
means. Commissioning the FTR now would either bake one producer's accidental
key rule into the canonical surface or re-open the key question inside a
public-API FTR. No rename, alias, or certification broadening is
recommended.
