== Phase-E Ingress Reachability and Boundary Census

_Reconstructs the maintained paths by which payload and pipeline-description
input can currently reach ordinary Domain operations, before Phase-E Trusted
Ingress design begins._

Status: *Pre-design, pre-normative evidence artifact.* This is not an ADR, a
Technical Model amendment, an FTR, a Project Memory update, or a Phase-E
design. It authorizes no runtime or test change. In particular it does not
choose a Trusted Ingress mechanism, make `run_pipeline` an error, constrain

introduce Pydantic, select a family pilot, or start `D-T3`.

These bypass/reachability rows are not automatically defects. `run_pipeline`
is documented as an intentional trusted programmatic composition surface;
other direct Domain and backend surfaces have varying public/support evidence
and local preconditions. Ordinary Python importability does not establish a
supported API or intentional bypass. The future coverage contract must state
which actual surfaces are excluded, gated, or covered rather than silently
treating Python-level reachability as framework-managed ingress.

The high-level macro flow automatically applies ingress only to the payload
returned by the router loader. Once `run_pipeline` begins, each executable
step's returned value becomes the next step's input directly. The provenance
and shape of payload created or replaced by arbitrary executable code are
therefore DYNAMIC/OPEN. `bootstrap_meta` and `apply_overrides` are special only
because their implementations voluntarily re-run the current metadata ingress
rule after merging metadata; arbitrary/plugin steps receive no such automatic
post-step ingress.

=== 3. Entry-surface inventory

The path matrix below is the authoritative inventory. A path or participant is
materially separate at this evidence granularity when at least one of the
following changes:

* the initiating supported interface;
* the external carrier/parser behavior;
* the description-binding or capability route;
* the automatic macro-flow guarantee; or
* a structural carrier crossing the Domain boundary.

Under that grouping rule the matrix has *22 role-granularity paths or
participants*. This is an illustrative summary, not a stable architecture
invariant and not a claim that the repository has 22 disjoint call graphs.
The two grouped reconstruction rows are specialized subpaths of the XLSX/ODS
orchestrated paths because `ExactTable` adds a materially different carrier and
Domain boundary. The metadata and post-ingress executable-step rows are
cross-cutting participants which can occur inside other paths.

The current illustrative reconciliation is 12 framework-managed high-level
families, 7 bypass/reachability rows, 2 post-load metadata-introduction
participants, and 1 post-ingress executable-step payload participant. Of the
7 bypass/reachability rows, 5 have positive row-level evidence for intentional
or supported trusted-programmatic use; 2 are mixed aggregates requiring
classification per actual sub-surface. These role summaries overlap and must
not replace the matrix or make harmless future regrouping look like an
architecture regression.

For this pre-design census, *framework-managed* means a high-level entry whose
fixed application macro flow owns the loader, initial ingress, final cleanup,
persistence projection, and saver. It does not mean every action performed by
arbitrary executable steps, or every payload those steps create or replace, is
framework-validated.

Maintained initiating or participating surfaces are:

* installed CLIs `sheets-run` and `sheets-schema-maintain`;
* public `application.orchestrator.orchestrate`, plus the compatibility
  `spreadsheet_handling.orchestrator` re-export;
* public `pipeline.runner.run_app(AppConfig)`, config loaders, step builders,
  `pipeline.run_pipeline`, registry, and dotted-path resolver;
* the deliberate application use-case
  `application.schema_maintenance.run_schema_maintenance`, which is
  package-public for application/CLI use but undocumented as a general
  consumer API;
* package-root family exports and directly importable Domain registry targets;
* public backend convenience loaders/savers and backend classes;
* XLSX/ODS `ExactTable` projection, workbook-view remapping, grouped-xref
  reconstruction, and public grouped-xref construction/composites; and
* Domain pipeline writer steps for structured YAML, key-value resources, and
  artifact manifests, which materially participate by activating filesystem
  sinks during a pipeline.

The consumer-interface guide intentionally keeps the Python stability surface
small: `orchestrate`, `run_app`, config/step builders, and selected family
package roots are stronger public evidence than arbitrary importability.
Tests and examples establish supported call shapes but test-only direct calls
are not promoted to product surfaces merely because they import successfully.

=== 5. Payload-plane reachability

Externally originated payload reaches all CLI paths, `run_app`, any
router-backed `orchestrate`, both reconstruction paths, and any direct Python
composition that calls a public loader. Direct Python callers can additionally
place arbitrary Python objects in a DataFrame cell, arbitrary values under
`_meta`, or even pass a non-DataFrame frame value: `Frames` is a static alias,
not a runtime boundary.

Effective current scalar carriers differ:

* XLSX and ODS visible cells collapse to strings at spreadsheet parser
  interpretation; absent cells become `""`. XLSX uses cached formula results
  (`data_only=True`); ODS derives textual values from ODF value types.
* CSV requests `dtype=str`, disables default NA recognition, and preserves
  blank cells as `""`.
* JSON requests `dtype=str`, disables date conversion, and replaces pandas
  missing values with `""`. Nested JSON values are therefore subject to
  pandas string coercion; the private temporal decoder is not in the read path.
* YAML `safe_load` feeds list/dict/scalar structures to pandas before missing
  replacement. Safe YAML date/datetime and other structured built-ins can
  survive where pandas construction permits, including object cells; pandas
  may also infer/coerce column carriers.
* XML contributes flattened leaf text and `""` for absent text/missing fields.
* Direct programmatic Frames can carry arbitrary Python values.

No payload scalar grammar is enforced before ordinary Domain operations.
Parser-local conversion is not Domain ingress normalization; persistence-local
conversion is not ingress; and scalar classification is not conversion.

Initial router-loaded payload and post-ingress step-introduced payload are
distinct reachability facts. `orchestrate` applies the current ingress rule to
the loader result, then `run_pipeline` assigns each callable's return value to
`out` and passes it directly to the next callable. A plugin, arbitrary dotted
target, caller-supplied `BoundStep`, or other executable step may therefore
create, replace, drop, or materialize Frames after the initial seam. No
automatic ingress follows that return. Such values are not labelled external
payload by default: their provenance is DYNAMIC/OPEN and callable-dependent.

=== 6. Description/control-plane reachability

`sheets-run` reads config and ad-hoc steps with `yaml.safe_load`, selects a
named pipeline or top-level list, applies CLI IO overrides, and binds every
step before calling `orchestrate`. `load_app_config` similarly safe-loads YAML
into dataclasses; it explicitly requires a list for `pipeline`, while Python
constructor errors and family binders supply the remaining diffuse structural
checks. There is no Pydantic model or single config-schema boundary.

Current configurable target surfaces include registry short names, registry
entries whose target is a string, `plugin` dotted references, colon-style
factory references, and nested generic string targets. Runtime inspection at
the baseline found 44 registry entries: 38 `StepRegistration` string targets
and 6 bare factories. `resolve_configuration_callable` centralizes string
resolution, accepts colon or final-dot references, imports the module, obtains
the attribute, and requires it to be callable. Its sole namespace rule rejects
`spreadsheet_handling.domain.ingress` and all its submodules. There is no
general allowlist, operator policy object, or runtime representation of
trusted versus less-trusted pipeline descriptions.

Binding and therefore dotted import happen before payload loading for the CLI
and `run_app` paths. Safe parsing/preparation and capability activation are not
currently separated for arbitrary imports. This is an addressability fact,
not a payload-validation fact. Direct Python callable targets and prebuilt
steps bypass string resolution entirely under the trusted-operator/programmatic
precondition.

The four trust combinations are architecturally representable but not equally
protected:

[cols="2,2,2,3",options="header"]
|===
|Payload |Pipeline description |Runtime representability |Current intended/protected status
|trusted |trusted |ordinary configured or programmatic run |intended; protected only by local checks and current limited ingress
|externally originated / less trusted |trusted |external file + fixed or operator-chosen steps |intended motivation, but no closed scalar/general-meta ingress guarantee
|trusted |less trusted |operator loads a description containing selectable dotted targets |representable; no trust flag or operator allowlist, so not established as safely protected
|less trusted |less trusted |external carrier plus such a description |representable by separate inputs; not thereby claimed safely supported
|===

=== 7. `domain.ingress` call census

`domain/ingress/coordinator.py` defines frozen `IngressRule(name, apply)`, an
ordered `INGRESS_RULES` tuple, and `run_domain_ingress`, which applies the
rules to a shallow `dict[str, Any]` Frames carrier. The tuple currently has
one rule: `legend_blocks_shape`.

That rule touches only mapping-shaped `_meta.legend_blocks`. It converts
`None` to an empty mapping, copies mappings while dropping derived `resolved`,
and converts list-form authoring sugar into an identity mapping after checking
member shape/name uniqueness. If `_meta` is absent or not a mapping, it is a
no-op. It does not traverse DataFrame cells, `ExactTable.data`, any other
metadata root, or scalar values.

There are exactly three production call sites:

* `application/orchestrator.py`: mandatory immediately after every router
  load and before the first configured step;
* `domain/meta_bootstrap.py`: after the profile/persisted/CLI merge is prepared
  and before the merged frames are returned; and
* `domain/yaml_overrides.py`: after the override merge is prepared and before
  the merged frames are returned.

Thus bootstrap and override processing are not fixed orchestrator stages.
They are ordinary selectable steps; when selected, each re-runs ingress after
introducing metadata. Their merge is prepared on a copy, so a failing ingress
does not partially mutate the caller's input through that return path.

The coordinator is absent from the runtime and descriptive registries, cannot
be built by the YAML dialect, and is explicitly blocked by the centralized
dotted resolver. Architecture tests pin those properties. Nevertheless the
package exports its symbols for framework/test import. That export does not
make `IngressRule` the final Phase-E architecture: accepted promotion evidence
identifies it as one current implementation detail, not a design decision.

Obvious bypasses are `run_pipeline`, direct Domain calls, direct backend-to-
Domain composition, and reconstruction driven outside `orchestrate`. A caller
can explicitly invoke ingress, but no such call is mandatory on those paths.

=== 8. `scalar_values` call census

Production search found *zero imports or calls* of `scalar_category`,
`is_missing_carrier`, `is_supported_scalar`, or `UnsupportedScalarError`
outside `core/scalar_values.py`. Tests exercise the vocabulary. The ODS
renderer has a private, independently implemented `_is_missing_carrier`; it
does not import the shared function.

Consequently no maintained parser, loader, orchestrator, ingress rule,
Domain transformation, persistence boundary, or writer currently enforces
the accepted six-category vocabulary (String, Boolean, Number, Missing, Date,
DateTime). The classification vocabulary exists; mandatory ingress enforcement
does not. `scalar_category` classifies without narrowing and remains unwired.

=== 9. `orchestrate` versus `run_pipeline`

`orchestrate` expects IO descriptor mappings and already-bound optional steps.
Its exact fixed order is:

[source,text]
----
coerce input/output descriptors
  -> route and load backend payload
  -> mandatory current domain ingress
  -> run already-bound steps, if any
       -> bootstrap_meta/apply_overrides may occur here if configured
       -> each such metadata merge invokes ingress again
       -> any step may return replacement Frames or another value
       -> the next step receives that return directly, without automatic ingress
  -> final Domain cleanup
  -> persistable _meta projection, only when _meta is dict
  -> route and invoke saver
  -> return saved-shape Frames
----

`run_pipeline` expects a Frames-shaped object and an iterable of callables. It
sets `out = frames` and calls each step linearly, with optional diagnostic meta
snapshots. It does not resolve a registry entry, run ingress, perform cleanup,
project persistence metadata, or save. Resolution happens only if the caller
separately uses a builder. There is no runtime validation of the Frames alias.
The return-value rule also means a plugin/custom callable or caller-supplied
`BoundStep` can replace the payload after orchestrator ingress. Only a callable
that explicitly invokes ingress receives another ingress pass;
`bootstrap_meta` and `apply_overrides` are the two maintained special cases
because they voluntarily do so for their metadata merge.

The accepted Technical Model documents `run_pipeline` as a *trusted
programmatic composition surface*. Public exports, integration tests, and the
GX5 public roundtrip confirm plausible ordinary consumer use. Its bypass is
therefore category A/B below, not a bug finding. Whether Phase E preserves,
gates, or explicitly excludes it remains a design question.

A disposable monkeypatch probe against real public functions produced:

Invocation: `.venv/bin/python -` with an inline script which monkeypatched the
orchestrator load/save/ingress/cleanup/persistence seams, called public
`orchestrate` and `run_pipeline`, and installed a temporary in-memory module
to observe one plugin bind. No script file was retained.

[source,text]
----
ORCHESTRATE_ORDER=load > ingress:initial > step:bootstrap > ingress:profile > cleanup > persistence > save
RUN_PIPELINE_ORDER=step:direct
PLUGIN_BIND=import:census_probe_plugin > bound:plugin
----

The first trace used `orchestrate` with its load/save/cleanup/persistence seams

=== 10. Direct Domain API reachability

`domain/__init__.py` and `domain/transformations/__init__.py` do not provide a
universal barrel. Selected package roots do re-export operations and models,
including cell codec, discriminator split/merge, enrichment, foreign-key
helpers, grouped xref, xref contraction/expansion, validations, extractions,
tabular helpers, and schema maintenance. Registry target modules are also
directly importable. Grouped-xref documentation/tests explicitly demonstrate
public direct and builder-driven composition. The consumer guide cautions that
arbitrary internal barrels are not all stable public API.

A Python consumer can call these operations with arbitrary Frames/DataFrames.
Such calls bypass ingress, configurable addressability, final cleanup,
persistence projection, and backend output by construction. Individual
operations defend their own semantic invariants: required frames/columns,
geometry, canonical constructors, key uniqueness, metadata preconditions,
schema request validity, and similar family rules. Those are Domain invariants,
not evidence of a general payload ingress grammar.

The evidence classes must remain separate:

* *Python-reachable* means an import or call can be expressed; it says nothing
  by itself about support or intent.
* *Package-public* means a package or module deliberately exports the name;
  that can still be undocumented as a general consumer API.
* *Documented consumer API* has positive interface-guide or user-documentation
  evidence.
* *Deliberately supported lower-level API* has positive export, contract, and
  repeated supported-use evidence under a stronger caller precondition.
* *Internal/test-facing* helpers remain outside a supported-public inference
  even when Python can import them.

Accordingly, selected package-root APIs are intentional trusted-programmatic
surfaces with explicit/local preconditions, while the aggregate direct-Domain
row is MIXED and must be classified per actual sub-surface. The application
`run_schema_maintenance` callable is a deliberate package-public application-
use-case seam used by its CLI, but is undocumented as a general consumer API.
The lower-level `domain.schema_maintenance` package has separate positive
package-public evidence. Phase E must define the claim boundary; this census
does not prohibit direct calls or promote importability into support.

=== 12. Metadata ingress

Metadata is independently externally reachable:

* XLSX/ODS parse a hidden carrier and recover a structured mapping from JSON
  or a legacy literal form; workbook presentation carrier facts may update
  canonical metadata before frames return.
* JSON accepts a safe-loaded `_meta.yaml` sidecar only when its root is a dict.
* YAML treats `_meta.yaml` as an ordinary tabular frame, so the current mapping
  ingress and later dict-only persistence projection are no-ops for it.
* CSV/XML create no metadata mapping.
* direct callers can supply any `_meta` value.
* `bootstrap_meta` and `apply_overrides` introduce profile, persisted, CLI, or
  YAML-derived metadata after the initial ingress, then invoke the LB rule.

Ordinary Domain or arbitrary executable steps can also generate metadata under
their own contracts. That internally/step-generated metadata is not external
by default and is not a third post-load metadata-introduction row merely
because it resides under `_meta`; its provenance remains callable-dependent.

Only `legend_blocks` has framework-owned ingress shape normalization. Other
metadata roots can reach ordinary Domain steps; family-specific resolvers and
transformations validate what they consume. Persistence projection removes or
projects derived/runtime roots (including cleanup commands and resolved
legend/xref data) immediately before saving, but otherwise preserves much
metadata. That output projection is not input validation.

Phase-E design must therefore reason about both cell payload and metadata
payload. This census does not decide whether they share a walker, policy, or
execution pass.

=== 13. Reconstruction and reverse paths

XLSX/ODS exact-read options identify per-frame header depths and construct
`ExactTable`. Its header grid is string-based; its data tuple preserves the
values supplied by the parser (strings on maintained spreadsheet paths).
Current ingress ignores `ExactTable`.

The registered reverse path applies persisted workbook-view sheet mappings,
requires an `ExactTable`, reconstructs a grouped matrix, and expands it to a
relation. Reconstruction verifies rectangular geometry, configured header
depth and row keys, visible/logical mapping, source-axis lookup, and canonical
grouped-matrix construction. Those checks are strong local reconstruction
invariants, not a general ingress boundary.

Within `orchestrate`, the one LB ingress call precedes reconstruction. In the
public GX5 integration flow, backend loaders/savers, config builders, and
`run_pipeline` are composed directly; reconstructed values receive no ingress,
cleanup, or persistence boundary. Reconstruction does not create a new scalar
class on maintained spreadsheet paths, but direct callers can construct
`ExactTable` data with arbitrary Python carriers before invoking it.

Confidence is VERIFIED STATIC for the orchestrated call chain and VERIFIED
RUNTIME for the public XLSX/ODS roundtrip composition exercised by the focused
GX5 suite. No other maintained workbook projection/reconstruction entry was
found that changes this conclusion.

=== 14. Output and sink continuation

On `orchestrate`, final Domain cleanup precedes the persistence boundary; the
boundary projects only dict-shaped `_meta`. Router savers then serialize the
Frames they receive. CSV/YAML/XML skip `_meta`; JSON writes dict metadata to a
YAML sidecar; XLSX/ODS build render IR and embed their metadata carrier.

The persistence boundary does not traverse or validate payload cells. Writers
perform sink-local representation conversions, for example JSON temporal
envelopes and YAML Timestamp conversion. Formula capability differs by sink:
an ordinary XLSX string beginning with `=` can become an openpyxl formula,
whereas ODS formula emission follows its explicit `FormulaSpec` path. This is
output-sink capability, not payload trust.

Three registered Domain pipeline steps can activate additional filesystem
sinks before final save: `write_structured_yaml`,
`write_key_value_resources`, and `write_artifact_manifest`. Their configured
relative paths are checked against a resolved `output_dir`; absolute and
escaping paths are rejected. Those are sink-local containment and semantic
checks. They neither provide general ingress nor prove a less-trusted pipeline
description safe to activate. The main output descriptor is operator/config
selected and is not constrained to one framework root; `discard` is also a
maintained saver.

=== 17. Mandatory-ingress coverage test

*Claim A:* framework-managed orchestration invokes a function named
`domain.ingress`. This is *true*. The illustrative 12 framework-managed
high-level rows converge on `orchestrate`; their fixed macro flow invokes the
current coordinator after router load and before the first configured/private
step. Here “framework-managed” has the bounded section 3 meaning: ownership of
loader, initial ingress, final cleanup, persistence projection, and saver.

*Claim B:* framework-managed external payload is thereby transformed into a
trusted Domain payload contract before ordinary transformations. This is
*false*. The current coordinator establishes only one metadata-shape
assumption. It establishes no scalar grammar, no general Frames/carrier
contract, no `ExactTable` contract, and no general metadata contract. Later
bootstrap/override steps add metadata and re-run only that same LB rule.

There is a further coverage qualification. The high-level rows converge on
initial ingress for *router-loaded payload*. After that seam, an arbitrary
executable step can create or replace Frames, and `run_pipeline` passes its
return directly to the next step without automatic ingress. Even if the
initial router-loaded payload later becomes fully covered, framework-managed
macro flow would not by itself prove that every value subsequently produced by
arbitrary executable code has crossed the same boundary. Step-introduced or
replaced payload has DYNAMIC/OPEN provenance and requires an explicit future
coverage contract; this census does not decide that post-step ingress is the
solution.

For a future truthful claim, Phase E would have to classify the current paths
as follows, without this census choosing how:

* *wire/strengthen*: the initial router-loaded payload on the 12 illustrative
  framework-managed high-level rows needs a successful boundary that actually
  establishes the assumptions later Domain code is promised; the existing
  convergence point is evidence, not a preselected final mechanism;
* *define post-ingress coverage*: payload created or replaced by a plugin,
  arbitrary dotted target, caller-supplied `BoundStep`, or other executable
  step needs an explicit in-scope, out-of-scope, or separately contracted
  treatment;
* *explicitly exclude, gate, cover, or reclassify*: the 7 bypass/reachability
  rows need a stated contract, with the 5 positive row-level surfaces kept
  distinct from the 2 mixed aggregates that require per-surface evidence;
* *separately guard or redesign*: metadata introduced after initial load,
  `ExactTable`/non-DataFrame carriers, and filesystem-capable pipeline steps
  require explicit treatment if they fall inside the claim; and
* *keep distinct but coordinate*: pipeline-description addressability and
  authorization must not be mistaken for payload ingress. Dotted import can
  activate code before payload loading today, so a less-trusted-description
  claim requires its own authority/activation answer.

The claim should name the entries and assumptions it covers. Merely renaming
the current coordinator would not satisfy it.

=== 18. Phase-E design questions

==== Must decide in Phase-E design

The census leaves an illustrative current inventory of *15 bounded mandatory
design questions*. The number is a review aid, not a stable architecture
invariant:

. What exact framework-managed entries and carrier variants are inside the
  mandatory Trusted Ingress coverage claim?
. What operational definition of “framework-managed” will the future coverage
  contract use, distinguishing the fixed high-level application macro flow,
  arbitrary executable code running inside that flow, and trusted
  programmatic/lower-level surfaces?
. What guarantee do `sheets-run`, schema maintenance, `run_app`, `orchestrate`,
  and the compatibility shim each publish?
. Does `run_pipeline` remain explicitly trusted and outside the guarantee, or
  is it gated/reclassified in some way?
. Which documented direct Domain/package APIs are explicitly trusted surfaces,
  and how are merely importable internals distinguished?
. What scalar locations/carriers are traversed, and what does successful
  six-category classification establish without prematurely choosing
  normalization?
. What metadata roots and externally authored metadata carriers are traversed;
  do metadata and cells share any mechanism or only a lifecycle boundary?
. Where is mandatory ingress ordered relative to parser conversion, initial
  load, bootstrap/profile merge, overrides, and reconstruction?
. How, if at all, does payload created or replaced after initial ingress by a
  plugin, arbitrary dotted target, caller-supplied `BoundStep`, or other
  executable step participate in the future Trusted Ingress guarantee?
. How are DataFrame, `ExactTable`, grouped/canonical composites, and future
  structured values included or explicitly excluded?
. What extensibility seam must the Phase-E payload contract preserve so a
  later explicitly declared bounded composite such as `List[Scalar]` can be
  added without replacing or bypassing the trust grammar, while leaving the
  actual category, codec, schema, and representation decision deferred?
. What normalization, if any, is permitted, who owns it, and how is that kept
  distinct from parser and persistence conversion?
. Where does operator-owned policy enter, and how are payload and
  pipeline-description trust represented independently?
. How does pipeline addressability/authorization coordinate with ingress while
  preserving addressability != payload validation and preparation !=
  capability activation?
. What rejection, diagnostic, and failure-atomicity guarantees apply when a
  boundary or later metadata introduction fails?

==== Already decided by ADR/Technical Model

* Runtime/operator trust is a fixed precondition; payload and pipeline
  description trust are independent variables.
* Operator-owned policy is outside a less-trusted description; restrictions
  narrow by payload/operation kind; rejection precedes capability activation.
* Output-sink capability is separately owned.
* Domain owns semantic invariants and final cleanup; persistence projects
  metadata; writers serialize rather than becoming payload validators.
* XLSX/ODS visible cells use the string substrate unless explicit typing is
  separately reopened.
* The six scalar categories classify without conversion; no general
  `normalize_scalar` contract has been accepted.
* Reconstruction invariants and ingress validation are different
  responsibilities.

==== Deferred to later work

* family-by-family hardening, the Domain Maintainer Contract application, the
  first family pilot, and `D-T3` selection/start;
* the actual `List[Scalar]` or other bounded-composite category, codec, schema,
  and representation; preserving an extensibility seam remains a Phase-E
  design question above;
* sink-specific formula/output policy changes;
* broad per-backend resource-limit projects outside the Phase-E boundary
  decision; and
* Pydantic adoption or a replacement config-model architecture, which would
  require its own design authority.

=== 19. Facts, gaps, and design questions

*Facts:* every router-backed framework execution converges on `orchestrate`;
current ingress is mandatory there and metadata-only; arbitrary executable
steps can introduce or replace payload afterward without automatic re-ingress;
`run_pipeline` and direct Domain use bypass the macro flow; shared scalar
classification is unused; string/config resolution is centralized except for
trusted direct callables; backend carrier behavior and metadata carriers
differ.

*Gaps:* the accepted durable architecture's eventual mandatory-ingress
assumption is not universally implemented; less-trusted description policy and
activation separation are not represented in runtime; general metadata and
scalar assumptions are not established.

*Design questions:* the illustrative 15-question inventory above determines
coverage, contracts, sequencing, policy, traversal, extensibility, and
atomicity. It is not converted here into BUG/FTR items or implementation
choices.

=== 20. Explicit non-decisions

This census does *not* conclude that all public Python APIs must route through
Trusted Ingress, that `run_pipeline` must be removed, that direct Domain calls
must be forbidden, that Pydantic should validate configuration, or that the
current `domain.ingress` coordinator is the final Phase-E mechanism. It does
not choose native-Python scalar normalization, a shared metadata/cell walker,
Domain ownership of pipeline addressability, identical backend carriers,
post-step ingress, plugin-output trust, `List[Scalar]`, or a first family
pilot. It does not decide that direct Domain APIs will be forbidden or that
`run_pipeline` will remain exempt. It does not write an ADR, update the roadmap
or Project Memory, authorize guards, or start implementation.

The only authorized next step is a fresh-context follow-up review of this
corrected reachability and boundary census.
