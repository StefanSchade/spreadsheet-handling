=== 2. Governing authority reconstructed independently

The accepted authority establishes the following constraints without selecting
a Phase-E mechanism:

* `ADR-DOMAIN-BOUNDARY-ROBUSTNESS` and the normative Domain Boundary Robustness
  concept require proportionate validation for documented pandas, NumPy,
  configuration, metadata, and artifact contracts. They do not promise a
  sandbox for arbitrary Python already running in the trusted process.
* `ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY` makes runtime/operator trust a
  fixed precondition, keeps payload and pipeline-description trust independent,
  places less-trusted-input policy outside the less-trusted description, and
  requires rejection before capability activation. Importing an untrusted-
  selected Python module is explicitly capability activation.
* `ADR-DOMAIN-OWNS-VALIDATION-WRITERS-STAY-DUMB` assigns semantic cleanup and
  validation to Domain flow. Persistence projects metadata; writers serialize
  rather than becoming payload validators.
* `ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` fixes maintained XLSX/ODS visible
  payload as strings unless that decision is separately reopened.
* ch06 keeps structural validation, payload ingress validity, Domain semantic
  invariants, and sink capability separately nameable.
* ch08 Internal Scalar Value Model owns the implemented six-category
  classification vocabulary but explicitly says no maintained ingress point
  enforces it. Classification does not normalize.
* ch08 Pipeline Semantics makes ingress macro flow rather than a configurable
  step, and keeps cleanup and persistence projection separate.
* the Spreadsheet Parse Contract ends format-specific parsing at `WorkbookIR`
  and generic projection at Frames plus persisted metadata; it does not claim
  that parsing is general Domain ingress validation.
* the provisional ch04 Trusted Ingress concept is useful historical evidence,
  including its description of `run_pipeline`, but is not mechanism authority.

The roadmap order is Phase E, then the Domain Maintainer Contract stage, then
Phase F family hardening. `D-T3` is a still-unselected family-pilot candidate
gated behind both Phase E and the Maintainer Contract.

At the lifecycle baseline, canonical Project Memory independently confirms the
handoff. `CONC-DOMAIN-BOUNDARY-ROBUSTNESS.next_action` calls for the repository-
wide Phase-E ingress/reachability/boundary census before design, explicitly
naming CLI/orchestration, `run_pipeline`, direct APIs, loaders, dotted
resolution, reconstruction, and bypasses. The accepted promotion event
`SIG-ACT-DOMAIN-TECHNICAL-MODEL-PROMOTION-ACCEPTED` says Phase E and `D-T3`
remain unstarted. The census therefore was the recorded next dependency-ready
action.

=== 3. Independent grouping rule and path map

This review calls a path family materially distinct when at least one of these
changes:

* the supported initiating interface;
* the external carrier/parser and therefore the value or resource behavior;
* the description-binding/capability-activation route;
* the automatic macro-flow guarantees; or
* a structural carrier crossing the Domain boundary.

Aliases with the same implementation (`ods`/`calc`, `json`/`json_dir`,
`yaml`/`yaml_dir`, `xml`/`xml_dir`) are one family. A configured reverse path
using `ExactTable` is kept separate from its ordinary spreadsheet path because
the carrier and reconstruction invariants materially change. Cross-cutting
steps are participants, not new top-level call graphs.

Under that rule, source reconstruction produces the census's 21 rows plus one
missing cross-cutting participant: post-ingress payload introduction by a
plugin, arbitrary resolved callable, or caller-supplied `BoundStep`. The review
count is therefore *22 role-granularity families/participants*. This is not a
claim that the repository has 22 disjoint call graphs.

The independently reconstructed macro map is:

[source,text]
----
sheets-run
  -> safe YAML parse / selection
  -> build every configured step (string target import can happen here)
  -> orchestrate

run_app
  -> build configured steps
  -> orchestrate

sheets-schema-maintain
  -> run_schema_maintenance
  -> private fixed BoundStep
  -> orchestrate

orchestrate
  -> coerce descriptors
  -> router loader
  -> run_domain_ingress                         [legend_blocks only]
  -> run_pipeline(already-bound steps)
       -> bootstrap_meta/apply_overrides may merge metadata and re-run ingress
       -> arbitrary plugin/BoundStep may also replace payload without re-ingress
  -> execute_final_domain_cleanup
  -> project_meta_to_persistable_contract       [dict _meta only]
  -> router saver

run_pipeline
  -> call each supplied callable in order
  -> no automatic loader, binding, ingress, cleanup, projection, or saver

direct Python
  -> package-public or internal loader / caller Frames
  -> selected package-public or internal Domain callable
  -> only that callable's local contract
----

Maintained loader/carrier branches are XLSX, ODS/Calc, CSV directory, JSON
directory, YAML directory, and XML directory. The reverse spreadsheet branch
can additionally publish `ExactTable` when exact-header options are selected.

=== 5. `orchestrate` order and runtime probes

Source and an independent disposable probe establish this fixed order:

[source,text]
----
_coerce_io(input), _coerce_io(output)
-> get_loader/load payload
-> domain.ingress.run_domain_ingress
-> run_pipeline(already-bound steps), when present
-> execute_final_domain_cleanup
-> project_meta_to_persistable_contract, only when _meta is dict
-> get_saver/save
-> return the saved-shape Frames
----

`bootstrap_meta` and `apply_overrides` are not fixed stages. If selected as
ordinary bound steps, each prepares a metadata merge, runs ingress on a
temporary `{"_meta": candidate}` mapping, and only then sets the metadata.
They therefore add later ingress calls without changing the orchestrator's one
fixed initial call.

Step binding is outside `orchestrate`. `sheets-run` and `run_app` bind every
configured step before entering it; a configured module import therefore occurs
before backend payload load. Direct `orchestrate` callers already possess
callables/`BoundStep` objects, so no addressability/import work is performed by
the function. Backend selection does not change this order.

Independent probe output:

[source,text]
----
ORCHESTRATE load > ingress > step > ingress > cleanup > persistence > save
RUN_PIPELINE step-only
CLI_BIND import:review_probe_plugin > orchestrate-entry
POST_INGRESS_REPLACEMENT ingress > custom-introduce > next-step-saw-opaque:True
----

The first probe used the real public orchestration function with load/save,
cleanup, and projection seams replaced only to record calls; the selected step
called real `bootstrap_meta`. The binding probe ran the real CLI `main` and real
step builder with a temporary YAML file and in-memory module. The final probe
used public `orchestrate` plus two real `BoundStep` objects to demonstrate that
a replacement payload introduced after initial ingress reaches the next step.
No probe script or fixture was retained.

=== 6. Independent `run_pipeline` classification

Verdict: *INTENTIONAL TRUSTED PROGRAMMATIC SURFACE*.

Evidence:

* `pipeline.execution.run_pipeline` sets `out = frames`, calls every supplied
  callable in order, and returns the final value.
* `pipeline.__init__` explicitly re-exports it.
* ch08 Internal Scalar Value Model normatively calls it the documented trusted-
  programmatic-composition surface.
* the accepted/provisional trust history, integration uses, and GX5 user-facing
  roundtrip establish non-test-only consumer use.
* expected steps are pre-bound callables. Registry, dotted resolution, and
  factory binding happen only if the caller separately uses a builder.

It does not perform ingress, persistence projection, final cleanup, save,
registry lookup, addressability checks, or runtime Frames validation. “Trusted”
is therefore a stronger caller/operator precondition, not a property the
function constructs. Whether Phase E preserves, gates, splits, or covers this
surface remains a design question.

=== 8. `domain.ingress` production census

Repository-wide symbol and import tracing confirms exactly three production
source call sites and three semantic uses:

. `application/orchestrator.py` -- one initial call after every router load;
. `domain/meta_bootstrap.py` -- one post-merge call before setting metadata; and
. `domain/yaml_overrides.py` -- one post-merge call before setting metadata.

Tests invoke ingress directly, but those are not production call sites. The
bootstrap/override calls operate on a temporary mapping containing only the
candidate metadata; the orchestrator call operates on the complete loaded
Frames mapping. They share the coordinator but are not the same state shape.

`INGRESS_RULES` contains exactly one `IngressRule`, `legend_blocks_shape`.
It:

* is a no-op without mapping-shaped `_meta.legend_blocks`;
* maps `None` to `{}`;
* converts list authoring sugar to a mapping after member/identity checks;
* copies mapping form; and
* drops each block's render-derived `resolved` facet.

It does not inspect DataFrame cells, `ExactTable.data`, other metadata roots,
schema, policy, grouped carriers, or scalar values. “Only legend_blocks is
normalized” is confirmed specifically as a claim about the current
`domain.ingress` rule set. Parser-local workbook metadata canonicalization,
missing replacement, presentation-carrier reconciliation, family configuration,
cleanup, and persistence projection are separate operations and must not be
silently renamed ingress.

=== 10. Description/control-plane binding

All maintained *configuration-derived callable strings* pass through
`pipeline.dotted_paths.resolve_configuration_callable`:

* a colon-style `step:` factory through `resolve_registration`;
* the public `plugin` step's `dotted` value;
* the 38 string targets among the 44 registry entries; and
* nested string targets accepted by the generic frames-first/builder binders.

The resolver accepts colon or last-dot syntax, rejects only the complete
`spreadsheet_handling.domain.ingress` namespace, imports the module, reads the
attribute, and checks callability. The other six registry entries are bare
factories. Direct callable targets and prebuilt `BoundStep` objects intentionally
bypass string resolution.

“Centralized” is therefore confirmed only for configured strings, not for all
ways Python code can become a step. The resolver is an ownership/addressability
boundary, not authorization. Safe syntax parsing and namespace checking precede
import, but there is no operator allowlist or less-trusted-description policy.
For CLI and `run_app`, module import occurs during binding before payload load;
that is capability activation under the accepted ADR.

=== 12. Metadata input and normalization

Independent metadata flows are:

* XLSX/ODS hidden carriers -> structured mapping plus parser-owned carrier
  reconciliation -> Frames `_meta` -> initial LB ingress;
* JSON `_meta.yaml` -> safe-loaded dict only -> initial LB ingress;
* YAML `_meta.yaml` -> ordinary DataFrame frame -> LB ingress no-op;
* CSV/XML -> no external metadata mapping;
* direct Frames -> arbitrary `_meta` value and no automatic ingress unless the
  chosen high-level surface is `orchestrate`;
* `bootstrap_meta` -> profile defaults, persisted metadata, and runtime/CLI
  overrides -> merge -> LB ingress;
* `apply_overrides` -> inline or safe-loaded YAML metadata -> selected merges ->
  LB ingress; and
* ordinary Domain steps -> internally generated policy, provenance, cleanup,
  workbook-view, or family metadata under their local contracts.

Metadata and cell ingress are independent in current code. Only
`_meta.legend_blocks` receives `domain.ingress` shape normalization. Other
parser/bootstrap/configuration transformations are real, but semantically
different. Internally generated metadata is not external ingress merely because
it lives under `_meta`.

The census's “two metadata paths” is confirmed only as “two cross-cutting
post-load metadata-introduction steps” (`bootstrap_meta`, `apply_overrides`), not
as a total census of metadata origins.

=== 13. Reconstruction and reverse paths

XLSX/ODS exact-header options attach a lossless string header grid and publish
`ExactTable`. `ExactTable` owns tuple/string carrier conversion but does not by
itself validate rectangular geometry. `reconstruct_grouped_matrix` then checks:

* exact carrier identity;
* configured header depth and rectangular header/data widths;
* unique row-key positions and blank upper row-key cells;
* complete/unique visible dynamic tuples;
* live source-axis resolution; and
* validated `GroupedMatrix` construction before atomic publication.

These are strong local reconstruction and canonical-carrier invariants, not a
general scalar, Frames, or metadata ingress contract. The registered workbook-
view mapping and reconstruction steps run after initial orchestrator ingress.
The documented/public GX5 composition can instead call loaders, builders,
`run_pipeline`, and savers directly; it bypasses automatic ingress, cleanup, and
persistence projection. A reconstructed carrier can therefore reach ordinary
Domain transformations without `domain.ingress` on that programmatic route.

=== 14. Framework-managed, bypass, public, and trusted wording

The evidence supports these review meanings:

[cols="2,4",options="header"]
|===
| Term | Evidence-backed meaning

| framework-managed
| A high-level entry whose fixed application macro flow owns loader, initial
  ingress, final cleanup, persistence projection, and saver. It does not mean
  every action or new payload created inside an arbitrary configured callable is
  framework validated.

| public
| Explicit CLI/YAML surface or intentional Python import named by exports,
  interface guidance, user documentation, or a feature contract. Ordinary
  module importability is insufficient.

| supported
| Positive stability/use evidence exists. Package-public but undocumented and
  internal/test surfaces must remain distinguishable.

| intentional bypass
| Positive evidence establishes a lower-level composition contract with a
  stronger caller precondition. Absence of ingress alone is not intent evidence.

| trusted
| A runtime/operator/caller precondition for programmatic composition, not a
  validation result manufactured by `run_pipeline` or direct Domain APIs.

| mandatory
| Automatically executed for every path explicitly inside a named guarantee;
  it cannot mean every Python-reachable path.
|===

The census generally uses these distinctions, but “7 intentional trusted-
programmatic bypass families” drifts across aggregate direct-Domain and backend
rows whose public/support evidence varies internally. That wording must be
corrected before it becomes a Phase-E contract premise.

=== 16. Output continuation

On `orchestrate`, final Domain cleanup precedes the dict-only metadata
persistence projection, which precedes the router saver. The projection prunes
runtime metadata and Resolution facets; it does not traverse payload cells.
CSV/YAML/XML skip `_meta`; JSON writes dict metadata to a YAML sidecar; XLSX/ODS
render and embed metadata.

The XLSX renderer returns ordinary string values unchanged to OpenPyXL, so a
string beginning `=` is interpreted as a formula by that sink. ODS formula
emission uses its explicit intent path. This is sink capability, not a reason to
globally reject formula-looking payload text.

The three registry-exposed filesystem writers (`write_structured_yaml`,
`write_key_value_resources`, `write_artifact_manifest`) validate relative target
paths against resolved output roots. Those sink-local checks neither validate
payload generally nor protect activation selected by a less-trusted description.
The census preserves the accepted writer/persistence/Domain responsibility
separation.

=== 17. Dynamic/open evidence and probe reproducibility

The arbitrary installed module universe, plugin side effects, direct callables,
Python library consumers, and monkeypatched/custom step behavior are genuinely
DYNAMIC/OPEN. Static search can verify maintained resolver call sites and
registry objects, but cannot close calls made by imported external code.

=== 18. Findings

==== PHASE-E-CENSUS-REVIEW-F1 -- Aggregate Python rows overstate intentional/public support

Severity: *Important*.

Census sections/paths: sections 3, 4, 10, and 15;
`PATH-PY-SCHEMA-MAINTENANCE`, `PATH-PY-DIRECT-DOMAIN`, and
`PATH-PY-BACKEND-TO-DOMAIN`; the “7 intentional trusted-programmatic bypass
families” total.

Observation and evidence: the consumer-interface guide says the Python surface
is intentionally small and explicitly warns against treating every module or
barrel export as public. `domain.__init__` and `domain.transformations.__init__`
export nothing. Selected family roots and `domain.schema_maintenance` do export
deliberate APIs; arbitrary registry targets/private helpers do not. Likewise,
`io_backends` exports `make_backend` and selected classes, while convenience
loader/saver visibility and documentation differ by backend; `write_xlsx` is
explicitly test-facing. The aggregate rows acknowledge some ambiguity but the
headline count still calls all seven intentional.

Why it matters: Phase-E design must not impose, exclude, or preserve a public
contract based on ordinary Python reachability. The stronger caller precondition
is load-bearing only for surfaces the repository actually intends consumers to
use.

Smallest documentation-only correction: label the application schema callable
package-public/undocumented; split the direct-Domain and backend-composition
rows' Surface/Trust verdict by evidence class; replace “7 intentional” with
“7 bypass rows: 5 positively intentional/supported at row granularity and 2
mixed aggregates requiring per-surface classification.” No runtime ticket is
created.

==== PHASE-E-CENSUS-REVIEW-F2 -- Post-ingress payload introduction by executable steps is not mapped

Severity: *Important*.

Census sections/paths: executive graph; sections 4, 6, 15, 17, and 19; all
orchestrated configured-operation rows.

Observation and evidence: `run_pipeline` assigns every callable's return value
to `out` and supplies it to the next step. `make_plugin_step` permits a plugin to
return replacement Frames; direct `BoundStep` has the same ability. The accepted
Pipeline Semantics explicitly says plugins may create, replace, drop, or
materialize frames. `orchestrate` invokes automatic ingress only before
`run_pipeline`; only the two known metadata merge steps voluntarily re-run it.
The independent runtime probe observed
`ingress > custom-introduce > next-step-saw-opaque:True`. The census correctly
marks arbitrary plugin calls DYNAMIC/OPEN, but does not state the resulting
post-ingress payload path in the payload matrix or mandatory-coverage analysis.

Why it matters: a future claim about all framework-managed external payload
cannot be inferred from initial loader convergence alone. Phase-E design must
explicitly define whether step-introduced payload is outside framework-managed
coverage, requires a separate contract, or participates in a future boundary.
This is independent of sandboxing arbitrary Python.

Smallest documentation-only correction: add one DYNAMIC/OPEN cross-cutting row
for plugin/custom-step payload introduction; qualify the 12-path convergence
claim as covering router-loaded payload up to the first configured step; add an
unresolved coverage question for payload introduced/replaced after that seam.
No runtime ticket is created.

==== PHASE-E-CENSUS-REVIEW-F3 -- The 12-question design inventory is not yet sufficient

Severity: *Important*.

Census section: section 18, “Phase-E design questions”; core claim 17.

Observation and evidence: the 12 questions cover high-level entries, public
guarantees, `run_pipeline`, direct APIs, scalar/metadata traversal, ordering,
structural carriers, normalization, operator policy, capability activation, and
failure atomicity. Three load-bearing questions are only implicit or absent:

* the operational definition of “framework-managed” used by the guarantee;
* treatment of payload created/replaced by a plugin, arbitrary dotted target,
  or caller-supplied step after initial ingress; and
* the required future bounded-composite extension hook (`List[Scalar]` or an
  equivalent bounded composite), which the census currently places only in a
  deferred-work bullet.

Why it matters: the first two determine the truthful coverage boundary; the
third prevents a scalar-only Phase-E design from accidentally foreclosing the
already accepted open composite candidate.

Smallest documentation-only correction: expand the mandatory design-question
inventory from 12 to 15 with those questions, without answering any of them or
changing the already-decided/deferred lists. No design or runtime ticket is
created.

==== PHASE-E-CENSUS-REVIEW-F4 -- Numeric totals are role-granularity summaries, not stable architecture facts

Severity: *Minor*.

Census sections: 3, 4, 15, 17, and 19.

Observation and evidence: backend variants are split where carriers differ,
while entry wrappers (`sheets-run`, `run_app`, direct `orchestrate`) overlap;
schema CLI/application are two entry surfaces over one use case;

Why it matters: later design review could mistake a harmless regrouping for a
coverage regression or force new paths into misleading bins.

Smallest documentation-only correction: make the matrix and grouping rule
authoritative; label all totals illustrative role-granularity summaries and
report mixed classifications rather than forcing them into “intentional.”

=== 22. Mandatory-ingress truth test and architecture implications

Claim A -- “framework-managed orchestration invokes a function named
`domain.ingress`” -- is true for all router-loaded `orchestrate` flows. The
initial call occurs after load and before the first configured/private step.

Claim B -- “framework-managed external payload is validated/normalized into a
trusted Domain payload contract before ordinary transformations” -- is false.
The function establishes only the Legend Blocks container shape and removes one
derived facet. It establishes no scalar grammar, general Frames shape,
`ExactTable` contract, general metadata vocabulary, resource-neutral trusted
carrier, or policy result. In addition, executable steps can introduce new
payload after the initial seam.

The evidence therefore proves only that:

* a framework-managed orchestration seam exists and is a plausible place to
  consider a future stronger contract;
* current ingress does not establish that contract;
* `run_pipeline` and selected lower-level/programmatic APIs exist under stronger
  caller preconditions and require explicit Phase-E contract treatment;
* direct-Domain support must be decided per actual public surface, not inferred
  from importability;
* payload ingress and pipeline-description authorization are independent
  coverage problems;
* metadata and cell payload have distinct current flows;
* reconstruction invariants do not replace general ingress; and
* an orchestrator guarantee cannot silently cover direct calls or payload
  introduced by arbitrary executable steps.

This means Phase E contains semantic normalization/validation, wiring/ordering,
and coverage-contract questions. This review does not choose their solution.

=== 23. Verdict

*ACCEPTED WITH CORRECTIONS -- CENTRAL MAP IS SOUND; BOUNDED DOCUMENTATION
CORRECTIONS ARE REQUIRED BEFORE PHASE-E DESIGN.*

The census accurately identifies the maintained high-level seam, the current
coordinator's narrow behavior, `run_pipeline` bypass, backend carrier
differences, metadata separation, resolver timing, reverse-path invariants, and
the absence of substantive mandatory Trusted Ingress. It is not yet sufficient
as-is because the post-ingress executable-step payload path is missing, aggregate
Python surfaces are over-classified, and the mandatory design-question list is
incomplete. Correcting those points requires census documentation only; it does
not authorize Phase-E implementation.
