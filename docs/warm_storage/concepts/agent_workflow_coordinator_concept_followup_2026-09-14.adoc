== Purpose and reading rule

The accepted Slice-5A proof is deliberately narrow evidence: one disposable, real-provider, bounded serial `N=2` Run under a maintainer-selected and pinned envelope. The original concept pre-dated the implementation, fixed-launcher commissioning, declarative N=1 operator, and that proof. This follow-up asks what those facts now justify *conceptually*, without turning future possibilities into present machinery.

The terms below remain distinct:

* *Accepted current mechanics* are established by the accepted FTR, implementation/reviews, and commissioning records.
* *Architectural inference* is suggested by those facts, not an accepted subsystem boundary.
* *Strategic future runway* identifies seams worth preserving, not a design to implement.
* *Unresolved questions* remain for independent adversarial review.
* *Non-goals / not-authorized work* preserve the current boundary.

== What commissioning has established

=== Accepted current mechanics

The execution evolution and Commissioning Diary establish a progression from manual provider operation, through a deterministic proof harness and fixed one-shot launchers, to a repository-backed declarative operator. The operator admits a maintainer-authored WorkItem, profile, repository policy, component manifest, task, expected Git head, and external one-shot state root. It validates repository identity, a clean pinned checkout, authority/scope domination, and selected governing inputs before a provider-capable boundary.

The Coordinator, not the agent, owns durable Run/Hop evidence, deterministic reduction, invocation accounting, and a trusted mechanical Git commit after a valid CommitIntent. `commit` is a Coordinator workflow effect, not permission for an agent to run Git. A correlated agent result is necessary input but never repository or transition authority by prose alone.

Slice-5A additionally established one real `N=2` path: H001 at clean head A, then the authorized Coordinator-owned A-to-B commit where applicable, durable publication, independent revalidation of checkout/Git and byte-identical governing inputs at B, and a fresh H002 identity and context. The proof exhausted two Hops and created no H003. Each provider-capable Hop had separately retained binding/outcome evidence. Earlier dogfood showed why a semantically plausible result with missing invocation identity must fail closed.

This proves bounded serial continuation, not routine multi-Hop operation, general recovery, provider choice, or autonomous work selection. It also shows that a mechanically completed Run and a semantically/lifecycle accepted outcome are distinct: independent review found material scope and governance issues in otherwise mechanically successful N=1 commissioning Runs.

=== Architectural inference: the inner Coordinator boundary

The strongest current inference is that the proven Coordinator is primarily an *inner execution system for an already-authorized WorkItem*. Its concern is to bind an admitted WorkItem to a finite profile/phase, construct bounded Hop context, apply deterministic gates, account for attempts, invoke a concrete binding, and preserve evidence around effects. It is not justified as owner of deciding which problem exists, which candidate should be pursued, or which trust classification governs material.

The following is a responsibility map, not a proposed chain of subsystems:

[source,text]
----
candidate / authorized backlog
        -> intake / work assessment
        -> work selection
        -> workflow/profile selection
        -> single-WorkItem Coordinator
        -> per-Hop execution binding
        -> provider / model / execution environment
----

Only the latter three responsibilities have concrete current mechanics, and even there the profile is supplied to the operator rather than selected by it. The earlier boxes may remain human- or policy-governed, or later prove repetitive enough for limited automation. They do not currently justify separate services, databases, or a general outer loop.

== A possible outer loop, kept outside the inner Coordinator

An authorized candidate/backlog space is a useful precondition for future outer-loop assistance. Candidate work may be introduced by maintainers and other explicitly authorized repository governance processes; an agent may surface a candidate or assessment, but that is a recommendation rather than authority. A possible conceptual flow is:

[source,text]
----
Candidate -> Intake Assessment -> Policy / Maintainer Authority -> WorkItem -> Coordinator
----

Intake assessment could collect evidence, identify dependencies, assess whether work is bounded, propose scope/profile options, or recommend no WorkItem. It must not create unrestricted scope merely because it can describe an attractive next task. Work selection weighs priority, value, sequence, and risk; execution performs one selected and bounded item. Where selection becomes mechanical, deterministic selection from an explicitly authorized finite candidate set is more accountable than opaque preference. Semantic judgment may later inform a recommendation or human/policy decision without becoming self-issued scope.

The principle to preserve is: *Agent assessment may recommend governance. It may not weaken its own governance.* No outer-loop implementation, autonomous product management, autonomous ticket creation, or automatic WorkItem creation follows.

== Authority architecture

=== Action authority is current, concrete work

Commissioning makes the separation between cognition and effects precise. Within a granted Hop, an agent may analyze, propose, implement, review, and report findings. Operational authority remains bounded by declared action and path scope, reducer, trusted Git boundary, durable transition rules, continuation budget, and human stops. Examples include inspection, edits in declared scope, the Coordinator's trusted commit capability, and other repository effects. They are not interchangeable shell privileges and do not become agent-owned merely because an agent can reason about them.

This supports: *delegate cognition aggressively; constrain effects mechanically.* The maintainer need not replay every local reasoning step to retain control, because the deterministic layer governs meaningful effect boundaries. Nor does responsibility disappear into the agent: maintainer authorization and policy set the envelope, while the Coordinator records and enforces transition/effect facts. Manual H002 dispatch becoming bounded, revalidated N=2 continuation is evidence for this division, not unbounded autonomy.

=== Information and execution-trust authority are future runway

Whether an agent may modify material and whether an execution environment may receive it are different questions. Present evidence establishes action authority and a concrete binding; it does not establish a normative classification system.

A future model could derive information/trust requirements from repository policy, WorkItem, phase, and explicitly constructed Hop context. Downstream stages could preserve or tighten inherited restrictions, but must not silently weaken them. An agent could recommend a classification or different environment, but must not thereby grant itself a weaker trust requirement. PUBLIC, INTERNAL, CONFIDENTIAL, and RESTRICTED are illustrations only, not a taxonomy.

Classification authority remains explicit and human/policy-owned unless a separately reviewed mechanism establishes otherwise. This introduces no fields, policy engine, or enforcement rules.

== Execution binding: trust first, capability and cost second

The accepted per-invocation binding seam is valuable because workflow semantics do not require a Run-lifetime provider/model choice. Future selection could, if justified, choose among already admissible bindings using capability required by the bounded task, expected convergence/review quality, cost, latency/capacity, availability, and information/trust constraints. A small inexpensive worker -> stronger worker -> frontier escalation sequence is illustrative, not vendor architecture or a prescribed escalation ladder.

An intake or assessment signal such as complexity may independently inform workflow/profile policy (for example, choreography or review/gate intensity) and execution policy (for example, model, reasoning, or capability choice). Those decisions are orthogonal: neither automatically implies the other. In particular, a stronger execution binding must not broaden workflow authority. Choosing a stronger model, provider, or reasoning level must not by itself increase route availability, repository/path scope, action authority, review authority, Hop budget, or retry/resume authority. An agent or intake assessment may recommend either policy decision, but does not authorize either. This is an invariant to preserve, not a workflow-policy framework, execution-policy framework, complexity taxonomy, model tier, or resolver design.

Decomposition can lower capability required per Hop while automation can increase invocation count. The longer-term problem is therefore minimizing total execution cost while preserving correctness, review quality, and convergence -- not simply minimizing tokens or always choosing the strongest model. Provider attractiveness will change; current semantics should not assume a vendor or strongest-default.

The ordering matters:

[source,text]
----
WorkItem / phase
  -> context construction
  -> information / trust requirement
  -> eligible execution bindings
  -> capability / cost choice
  -> provider invocation
----

Capability/cost optimization belongs only inside an admissible trust boundary. A cheaper or stronger binding that may not receive selected context is not a candidate. If realized, deterministic fail-closed compatibility checking is preferable to asking provider or agent whether it may see material. This preserves a seam only; it does not design a router, optimizer, benchmark registry, provider marketplace, capability ontology, fallback engine, or provider registry.

== Evidence and professional-deployment runway

If later suitable for professional or company-internal use, evidence may need to establish which adapter/provider/model executed a Hop; which execution/trust zone and information classification applied; which context sources/version bindings were selected; and which compatibility decision admitted invocation. Existing per-Hop binding facts, pinned governing-input identities, and bounded projections are promising starting forms.

This must not imply copying confidential prompt/context payloads into another audit store. Evidence that a governed context was supplied differs materially from persisting another raw copy. Provenance, stable identifiers, source/version bindings, classifications, execution-binding facts, policy-decision evidence, and hashes/digests where useful can often support the former without making the latter default. Retention, regulatory controls, DLP, certification, and a compliance platform are outside this follow-up.

== Carve-out hypothesis: generic tooling, consumer semantics

Current directories and modules show a possible reusable tooling domain: declarative WorkItem/profile/policy admission, reducer and Run/Hop lifecycle, prompt/context composition, bounded adapter execution, trusted Git handling, persistence, and evidence. These mechanics are not inherently spreadsheet or DMC semantics. Spreadsheet domains, DMC vocabulary, repository-specific policies, source/test conventions, acceptance criteria, and backlog priority are consumer semantics and should stay outside a generic Coordinator.

This supports a possible history-preserving repository carve-out in which spreadsheet-handling becomes first consumer/dogfood repository rather than the Coordinator's semantic owner. Evidence from a second genuinely different consumer/profile would materially strengthen confidence in the generic boundary, but is not a mandatory prerequisite. A carve-out may be justified earlier when semantic ownership, lifecycle/release ownership, generic-versus-consumer boundaries, and history-preserving extraction are already sufficiently clear. Supported ingress and evidence contracts must also be understood well enough for the intended ownership. A split must follow semantic clarity, not manufacture it; no carve-out or anticipatory plugin platform is authorized.

== Relationship to future Slice 5B+

This follow-up reinforces the FTR's separation of risk boundaries. Slice 5B's review/correction/Finding convergence is an inner-Coordinator question only after authority and evidence semantics are independently contracted. Slice 5C's interruption and explicit resume must not be confused with fail-closed N=2 continuation. Slice 5D's human-authorized parent/child lifecycle touches the outer-versus-inner boundary and should be assessed against candidate selection before mechanization. Slice 5E's optional supervisor is not implied by semantic freedom; it needs demonstrated work deterministic reduction cannot own. Slice 5F should test consumer semantics without turning them into generic ownership.

These conclusions may justify reassessing sequencing before more mechanics are stacked on Slice 5A. They do not alter dispositions or authorize Slice 5B.

== Non-goals and not-authorized work

This document introduces no requirement for a workflow DSL, general event store, mandatory supervisor, autonomous ticket creation, provider registry framework, capability ontology, classification framework, cost optimizer, plugin system, universal adapter hierarchy, policy engine beyond demonstrated need, arbitrary-N orchestration, or automatic retry/resume. Narrow seams and explicit authority boundaries are preferable to speculative infrastructure.

No runtime code, tests, FTR lifecycle state, historical concept, Project Memory, current execution authority, provider invocation, carve-out, or outer-loop implementation is authorized or changed. The accepted Slice-5A proof remains consumed; all other live `N>1` and real-provider authority remains as in the FTR.

== Questions for independent adversarial review

* Where should the outer-loop / inner-Coordinator boundary lie, and what repeated evidence would justify moving a responsibility across it?
* Which candidate introductions, intake recommendations, and selections may be made by human, policy, or agent, and how is self-weakening governance prevented?
* Which action authorities remain distinct from information/execution-trust authority, and what must be explicit before either is delegated?
* Can trust compatibility be deterministic and fail-closed before execution selection without prematurely creating a classification framework?
* What evidence justifies capability/cost escalation while avoiding both strongest-model defaulting and false economy that harms convergence?
* What minimum provenance proves governed-context use without retaining raw confidential payloads, and where should that evidence live?
* What must stabilize, and what history travel, before a carve-out makes spreadsheet-handling a real consumer rather than owner?
* Does Slice-5B sequencing remain the best next step, or should outer-boundary and evidence questions be resolved first?
* Which proposed abstractions are demonstrated seams, and which would be accidental platform-building if introduced now?
