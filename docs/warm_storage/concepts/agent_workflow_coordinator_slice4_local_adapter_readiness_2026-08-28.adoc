== 1. Local CLI evidence and selected boundary

Read-only inspection on this machine established the following facts:

* `/usr/local/bin/codex` reports `codex-cli 0.147.0`.
* `codex exec --help` describes a non-interactive command. A missing prompt, or
  prompt `-`, reads instructions from stdin; `--json` writes events as JSONL to
  stdout; `--output-schema FILE` constrains the final response; and
  `--output-last-message FILE` writes the final agent message to a file.
* `codex --help` documents the top-level `-a, --ask-for-approval` option;
  `codex exec --help` does *not*. `codex --ask-for-approval never exec --help`
  exits successfully, while placing the option after `exec` is a parse error.
  The documented approval policy promise is that execution failures are returned
  to the model immediately. `exec --help` also documents `--ephemeral`,
  `--sandbox workspace-write`, and `--add-dir`, which this proposal deliberately
  does not use.
* The active local configuration selects `model = "gpt-5.6-terra"` and
  `model_reasoning_effort = "medium"`. `codex login status` reports ChatGPT
  login. No credential value was read. `codex doctor` reports configured
  file-backed ChatGPT authentication, but its provider reachability probe fails
  in this restricted inspection environment. Thus authentication is present;
  a future authorized run must treat reachable provider transport as a preflight
  observation, not as assumed readiness.

The selected single local adapter invocation is the following, with all angle-
bracket paths supplied by trusted coordinator mechanics:

[source,bash]
----
codex --ask-for-approval never exec \
  --ephemeral --json --color never \
  --sandbox workspace-write \
  --model gpt-5.6-terra -c 'model_reasoning_effort="medium"' \
  --cd <repository> --output-schema <result-schema.tmp> \
  --output-last-message <result-message.tmp> -
----

The Python parent writes the already assembled prompt to the child's stdin,
captures stdout and stderr separately, waits with a finite deadline, and never
allocates a TTY. Stdin closes after the prompt. `--json` stdout is transient
JSONL diagnostics/events, not the routing result; stderr is likewise transient
diagnostic material. The final-message file is the sole proposed result
transport. The process exit status is independently recorded. The command and
all shown `exec` options were parse-checked through `--help` only; no provider
connection was attempted.

This deliberately uses one executable and one subcommand, not an SDK or a
generic provider layer. Pinning the currently configured model and reasoning
effort makes the first proof reproducible. A later change is an explicit
operator/configuration decision, not silent model selection.

== 2. Non-interactivity and permission boundary

`codex exec` is the documented non-interactive surface. Piped stdin, no TTY,
and `--ask-for-approval never` together mean that a command which would require
approval fails back to the agent instead of presenting an invisible human
question. This proposal does *not* use `--approve-for-me`,
`--dangerously-bypass-approvals-and-sandbox`, or
`--dangerously-bypass-hook-trust`. A permission failure is therefore an
observable process/result failure, never a reason for the coordinator to wait
or retry.

The selected `workspace-write` sandbox is the smallest documented mutating
mode. It is not represented here as a hostile-code sandbox (WFC-SEC-01), and
the inspected help supplies no path-level allowlist or independent `.git`
exclusion guarantee. The eventual profile and pre/post Git observations remain
the authoritative scope check.

[cols="2,5",options="header"]
|===
|Surface |V1 boundary

|Worktree
|Mutation is permitted only in the selected disposable repository working root;
the profile's authorized path is narrower still and is checked from Git after
the Hop. No `--add-dir` is supplied.

|`.git`
|No separate denial is proven by the selected CLI surface. A writable repository
under `workspace-write` effectively grants the entire `.git` directory: refs and
`packed-refs`, reflogs, object database, lock files, and `.git/hooks`. Existing
post-Hop checks detect important HEAD/range/scope/history anomalies, but do not
establish integrity of all Git metadata, especially hooks and reflogs. The
coordinator observes facts and never repairs or deletes locks.

|External filesystem
|No additional writable directory is granted. The existing OS/Codex sandbox is
the permission boundary; this proposal makes no whole-filesystem claim.

|Network and provider
|Provider transport is necessarily used by Codex itself. `--search` is omitted,
so no agent web-search capability is requested. Shell/network access remains
the configured sandbox's restricted boundary. Provider reachability is an
explicit launch/preflight fact.

|Credentials
|Codex uses its existing authenticated CLI state. The coordinator neither reads
`auth.json` nor passes an API key, token, environment dump, or credential-bearing
output through the prompt, result, checkpoint, or evidence.
|===

== 3. Git-write ownership requires a maintainer decision

The accepted architecture says that V1 agents create content/review commits;
WFC-OUTPUT-04 requires a successful mutating Hop to commit its required
artifact; WFC-GIT-08 validates the WorkItem/Hop-shaped commit subject after the
fact. Slice-3 fixtures already prove that validation shape.

However, the Slice-3 evidence records a reproducible Codex-local interactive-path
observation: a successful commit may leave a stale empty Git lock. The source
artifacts do not establish one stable path, so the future post-Hop observation
must scan `.git/**/*.lock` and treat *any* residue as an anomaly requiring human
inspection. No lock workaround, automatic deletion, or cleanup is proposed or
implemented here.

Option A is the contract-preserving V1 ownership model: the real agent edits and
creates its own in-scope workflow commit, and the coordinator only observes and
validates the range/subject. It keeps semantic authorship and section 11.4's
prohibition on coordinator-created semantic commits. But it has the full `.git`
authority stated above, not merely ordinary `git add`/`git commit`; range/scope
observation cannot establish integrity of hooks or reflogs.

*Option A -- disposable proof* is acceptable because the repository is
disposable, the budget is N=1, and every observed anomaly stops. *Option A --
routine real repository* is *not yet accepted* as safe merely from that proof.
It would later require stronger isolation that restricts `.git` authority,
materially expanded Git-integrity verification, or explicit maintainer acceptance
of the broader `.git` trust.

Option B, trusted coordinator mechanics committing an agent-authored worktree,
could avoid exposing Git write to the agent but changes the accepted ownership
model and conflicts with the section-11.4 wording against coordinator-created
semantic commits. It must not be implemented as an incidental adapter detail.

Decision required:: A maintainer must choose either (A) agent-owned commit for
the disposable proof with any lock residue treated as a blocking post-Hopf
anomaly, or explicitly amend the accepted architecture/FTR before any
coordinator-owned commit mechanism is designed. This proposal recommends
*Option A for the disposable proof only*, subject to that explicit decision; it
makes no routine-repository safety decision.

== 4. Result transport and fresh context

The trusted coordinator creates `<result-schema.tmp>` as a JSON-Schema rendering
of the existing authoritative strict `structured_result_v1` validation contract,
and a private transient `<result-message.tmp>` path before launch. Both paths,
the dispatch marker, Run snapshot, and all coordinator transient state must be
outside the agent-writable repository/workspace; no `--add-dir` is supplied for
any of them. `--output-schema` and `--output-last-message` are parent-Codex I/O
paths and do not require those files to be inside the agent workspace. This is a
mechanical adapter boundary, not an agent policy assertion.

The accepted WFC-PERSIST-02 repository-local state-root contract must be
reconciled with this required external adapter state placement before runtime
implementation; this proposal changes neither FTR nor architecture and does not
redesign persistence. The prompt generated by Slice 3
already states `output_contract=structured_result_v1`, includes Run/Hop identity,
and requires exactly one JSON envelope. Codex receives the prompt on stdin.
The CLI writes its schema-constrained final message to the transient result file;
the parent reads it only after process completion, applies the existing
`validated_result()` envelope/identity validation again, then atomically
publishes a coordinator-owned correlated result only if it passes. Partial,
missing, extra-field, malformed, or identity-mismatched data is never promoted.

Thus the boundary is:

[source,text]
----
Slice-3 prompt -> stdin -> codex exec -> final-message tmp file
  -> existing strict structured_result_v1 validation -> atomic result publication
----

JSONL stdout may help diagnose launch/provider/process state but is not trusted
as the result envelope. Raw prompt, stdout, stderr, and the unvalidated result
file remain transient under WFC-PERSIST-04 and are never promoted with secrets.

`--ephemeral` is the fresh-context proof: the inspected CLI documents it as
running without persisting session files. The selected command has no `exec
resume`, `resume`, `--last`, session identifier, or continuation input. Together
with a new process and new stdin prompt, the V1 invocation cannot request reuse
of an earlier Codex conversation. This proves the `fresh` baseline; it neither
asserts nor implements `continuing`.

== 5. Acceptance, Hop accounting, cancellation, and timeout

Before attempting process creation, the coordinator atomically publishes the
existing correlated dispatch marker with base HEAD and a pending one-Hop budget
reservation (WFC-FAIL-04). The reservation is not itself proof that a Hop was
consumed. Before spawn it completes command construction and parse validity,
executable availability, login-status, repository/HEAD/clean-state preflight,
and required external schema/temp preparation. A positively established local
failure at any of those points consumes no Hop under WFC-AUTO-03.

The following is the V1 accounting rule. It does not equate child-process start
with provider acceptance, does not infer acceptance from prose, and does not
retry any outcome. The exact provider-acceptance event is not proven without a
live invocation, and no undocumented JSONL event semantics are used.

[cols="2,2,3,3",options="header"]
|===
|Observation |Hop |Required state/action |Reason

|Pre-spawn command/parse, executable, login-status, repository/HEAD, or required
external schema/temp preparation failure
|No Hop
|Record local launch failure; remove/close the pre-launch marker only after
proving no child existed; `awaiting_human` if human action is needed.
|WFC-AUTO-03 local pre-acceptance failure.

|After spawn, a local failure positively establishes that provider/model
acceptance did not occur
|No Hop
|Record the local pre-acceptance failure, reconcile any process-local facts, and
stop without replay; do not convert process start into acceptance.
|WFC-AUTO-03. This row applies only when non-acceptance is actually established.

|Provider/model acceptance is positively observed
|Charged
|Reconcile Git/evidence after exit; valid result may reduce, otherwise stop.
|WFC-AUTO-02.

|Provider/model acceptance cannot be disproved after the remaining runtime
outcome
|Charged
|Conservative one-Hop record; never replay automatically.
|WFC-AUTO-02 requires conservative charging for genuinely uncertain acceptance.

|Exit 0 and valid, correlated final-message result
|Charged
|Observe Git/evidence; reduce once under existing Slice-3 rules.
|A valid model result is positive acceptance evidence.

|Nonzero exit, explicit provider/unavailable/capacity failure, or invalid,
missing, truncated result
|No Hop only if pre-acceptance failure is positively established; otherwise
charged
|For a charged outcome, reconcile Git/evidence, retain concise diagnostic, and
stop `awaiting_human`; no route inference or hidden retry.
|WFC-AUTO-03 or, where acceptance cannot be disproved, WFC-FAIL-01. A capacity
error is ordinary explicit unavailability for now; there is no quota waiting or
routing.

|Cancellation, deadline expiry, forced kill, parent interruption, or unreadable
process/result state
|Charged
|Enter `reconcile_required`, retain marker, inspect Git/evidence/current inputs,
and require explicit resume/human authority.
|WFC-FAIL-04 uncertain outcome.
|===

The parent sets one bounded wall-clock timeout in the authorized profile/run;
no provider quota window is modelled. It launches the subprocess in its own
process group/session (for example Python `start_new_session=True`). At timeout
or cancellation, the parent signals the *process group* for graceful
termination, waits one fixed short grace period, then kills that group if any
descendant remains. Descendants therefore cannot silently survive a parent
timeout. Any timeout/cancellation/kill is uncertain unless a valid result and
clean post-Hopf facts were already observed, and enters charged
`reconcile_required`. The parent itself never waits indefinitely.

No hidden retry exists. `max_autonomous_hops=1` is checked before spawn and
after all safe post-Hopf observation; it cannot issue a second local invocation.

== 6. First eventual live proof -- separately authorized, not executed

The first proof shall use a newly initialized disposable Git repository, not
this product repository. It has one tracked `PROOF.md` containing a known initial
line, no agent-writable coordinator state root, and no remote, submodule, product
code, or Domain material. Coordinator schema/result/marker/snapshot paths are in
a separate parent-owned location outside this workspace, with no `--add-dir`.
Its pinned profile authorizes only `PROOF.md`, one `durable_artifact=none` routine
documentation/tooling phase, and one trusted `git diff --check` observation.

The sole deterministic task is: replace the known line in `PROOF.md` with a
specified replacement, run `git diff --check`, create exactly one commit whose
subject is `docs(workflow): WFC-S4-PROOF H001 mark fixture`, and return the
correlated `structured_result_v1` envelope. The human-authorized WorkItem ID is
`WFC-S4-PROOF`, the Run budget is one, and the prompt prohibits work outside
that file and commit.

Expected success observations are one child process, one charged Hop, exactly
one descendant commit, only `PROOF.md` changed, the required subject identity,
a valid result file correlated to Run/H001/invocation, clean post-Hopf Git,
passing `git diff --check`, transient redacted process diagnostics, and a compact
checkpoint. Any permission prompt, nonzero exit, bad result, extra path/commit,
any `.git/**/*.lock` residue, dirty state, timeout, cancellation, or provider
failure stops. The observed Codex-local environment means this first proof may
produce a correct deterministic commit and valid structured result *plus* a
stale empty Git lock. That is an expected possible human-inspected outcome: it
blocks continuation and requires inspection, but alone is not proof that adapter
logic failed. There is no automatic second invocation, cleanup, lock workaround,
reset, or routine-repository follow-up. Only after independent acceptance and
separate maintainer authorization may a narrow routine documentation/tooling task
be considered.

== 7. Unresolved decisions and recommendation

* The maintainer Git-ownership decision above is required. It determines whether
the accepted agent-commit contract remains the first live proof boundary or the
accepted architecture/FTR must change before Slice 4.
* The actual provider is unreachable from this read-only inspection environment.
An authorized disposable proof must record its own provider reachability result;
this proposal neither fixes connectivity nor authorizes a retry.
* `--json` event names and semantics were not empirically observed because that
would require a provider invocation. The adapter therefore does not depend on
an undocumented acceptance event: a started child is charged only on positive
acceptance evidence or genuinely uncertain acceptance, never merely because it
started.
* External coordinator state required by this adapter boundary and the accepted
repository-local WFC-PERSIST-02 root require an explicit authority reconciliation
before runtime implementation. This correction records the conflict; it changes
neither contract and authorizes no persistence redesign.
* The exact timeout/grace values are an authorized-run configuration decision;
the required property is bounded parent waiting and uncertain-outcome reconcile.

Recommendation:: *HUMAN ARCHITECTURE DECISION REQUIRED.* This proposal is ready
for independent Slice-4 readiness review as a proposal, but it is *not ready to
authorize Slice 4* until the Git-write ownership/lock-hazard decision is made.

No real agent invocation occurred. No Slice-4 runtime, continuing context,
