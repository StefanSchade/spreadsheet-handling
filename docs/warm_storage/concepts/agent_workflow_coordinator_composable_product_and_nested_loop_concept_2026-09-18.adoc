== 1. Purpose and central constraint

This document preserves an intended product direction before carve-out so that later work does not collapse the Coordinator into one exclusive UX model.

Three concepts are kept *independent but optionally composable*:

[cols="1,3,3",options="header"]
|===
| | Concept | Status

| A | Bounded inner WorkItem execution loop | Proven mechanics (Slice 5B, first Useful Loop)
| B | Optional outer loop that inspects, prepares, selects, and dispatches WorkItems | Future possibility
| C | Optional interactive CLI/TUI assistant for authoring, inspection, approval, and operation | Future possibility
|===

None replaces the others. A is useful alone. B and C each consume A; C may also operate B. Neither B nor C is a prerequisite for the other.

== 3. A -- The proven inner loop

[source,text]
----
bounded WorkItem
    -> pinned governing inputs / profile  (admitted at expected HEAD)
    -> implementation Hop
    -> fresh review Hop
    -> correction / re-review             (when declared and needed)
    -> converge | complete | bounded human stop
    -> durable Git / Run evidence
----

Established:: One human launch -> real implementation -> fresh independent review -> terminal completion, without human Hop dispatch (`implement -> review -> accept -> complete`, two of four authorized Hops). The Coordinator, not the agent, created both trusted commits.
Not established:: Arbitrary domain correctness; the correction/re-review route under a real provider; routine or reusable live authority (the one-shot authority is consumed); sufficiency of focused agent-reported tests as repository-wide acceptance evidence (W7).

The inner loop is a *useful execution primitive*. It is not necessarily the final user-facing product boundary: an operator still authors the WorkItem, chooses the profile, and decides what runs next.

== 4. B -- The loop around the loop

=== 4.1 Shape

A plausible outer loop is not `pick ticket -> run`. It is closer to:

[source,text]
----
inspect authorized backlog
    -> identify candidate
    -> assess actionability of the candidate description
    -> assess scope / acceptance / evidence readiness
    -> bounded clarification or preparation
    -> materialize child WorkItem
    -> obtain required authority / human gate
    -> launch child Run
    -> observe child outcome
    -> decide next bounded action
----

The readiness/preparation stage carries most of the value and most of the risk. It may itself eventually be a governed workflow with its own profile, Hops, and review, rather than an unstructured step inside the outer loop.

=== 4.2 Levels

More than one explicit orchestration level may prove useful, for example:

[source,text]
----
portfolio / backlog loop
    -> WorkItem readiness / preparation loop
        -> WorkItem execution loop   (A)
----

Preferred concept: *explicit bounded parent/child orchestration*, where every level is a visible Run with its own identity, profile, budget, and evidence. Not preferred: invisible recursion, in which an agent spawns agents inside a Hop. A new level is justified only when activity at that level has become mostly repetitive dispatch (strategy document); this concept does not claim any level beyond A has reached that point.

=== 4.3 Two directions of parent/child

The FTR already contains one parent/child shape: an *inner-discovered prerequisite*, where a Run routes `suspend_for_prerequisite`, a maintainer explicitly authorizes a separate child Run, and the parent stays `suspended` (WFC-PROFILE-04, WFC-FAIL-06/07; Slice 5D NOT AUTHORIZED).

The outer loop adds a second shape: an *outer-dispatched child*, where a parent orchestration Run launches an execution Run as its intended work. Both share the invariants below. Whether they are one mechanism is an open question (§13).

=== 4.4 Precondition inherited from prior review

An outer loop that materializes WorkItems is exactly the case F1 and F2 describe: WorkItems landed through the trusted commit path would otherwise become the next Run's governance, and no policy ceiling bounds WorkItem scope or Hop budget. Governing-input authorship must be mechanically distinguishable, and policy must dominate the WorkItem envelope, before any automated materialization. This concept restates that dependency; it does not resolve it.

== 5. Parent/child invariants (concept level)

These are invariants to preserve, not a state machine.

. Parent and child have distinct Run identities.
. Child launch is an explicit governed event with its own evidence, not a side effect of a Hop.
. The parent references child identity and child outcome; it does not embed child state.
. Child evidence remains child evidence. The parent may summarize; it does not rewrite child history.
. Authority does not increase because a parent launches a child. A child's envelope is bounded by its own authorized inputs, and those are bounded by the parent's envelope and trusted policy.
. Credentials and capabilities are not implicitly inherited; each child receives an explicit projection.
. Budgets (Hops, invocations, wall time, spend) are explicit at each level; launching a child does not implicitly extend the parent's budget.
. Nesting depth is bounded and configured, not emergent.
. Ambiguous child execution (unknown whether a child ran or committed) enters reconcile; it never causes blind duplicate dispatch.
. Child blocked, failed, awaiting-human, and stopped outcomes remain observable to the parent as distinct outcomes, not collapsed into failure.
. A human gate remains possible at every governed boundary: candidate admission, WorkItem materialization, child launch, and parent continuation.
. Serial execution (WFC-SYS-01) remains the default; a suspended or waiting parent is not an active Run.

== 6. C -- The interactive assistant (orthogonal)

Purpose: authoring, inspection, and ergonomics. Not a replacement for orchestration and not a source of authority.

Possible responsibilities: inspect repository state and authorized backlog; help formulate goal, non-goals, and scope; suggest profile, Hop/time/model budget, evidence and validation expectations; preview generated WorkItem/profile/policy material; explain Run state; surface diffs and Findings; request explicit approval; materialize approved inputs.

[source,text]
----
LLM proposes
    -> WFC validates  (schema, coherence, domination checks)
    -> human approves where required
    -> WFC materializes / commits
----

Two separations hold:

* *Authoring a WorkItem does not authorize executing it.* Launch remains a separate governed act.
* Materializing an assistant-drafted WorkItem is governing-input authorship (F1). Approval provenance must be distinguishable from ordinary agent output, whether the drafting agent ran inside the assistant or inside an outer-loop Hop.

The assistant may be a plain CLI dialogue first. A TUI is optional.

== 7. Composition modes

All modes use A as the execution primitive. Rows are possibilities, not a roadmap or ordering.

[cols="1,4,2",options="header"]
|===
| Mode | Flow | Availability

| A | Human authors WorkItem manually -> inner executor | Current mechanics (live Runs still individually authorized)
| B | Human uses `wfc assist` -> reviews/approves generated WorkItem -> inner executor | Future
| C | Outer loop selects an already-ready authorized backlog item -> inner executor | Future
| D | Outer loop performs bounded readiness/preparation -> optional human gate -> inner executor | Future
| E | Human uses CLI/TUI assistant to configure, inspect, or supervise an outer loop -> outer loop -> child executor Runs | Future
| F | Bounded unattended operation over an explicitly pre-authorized backlog subset with explicit budget, stop, and authority limits | *Future possibility only; not implemented, not authorized*
|===

Modes are not exclusive within one repository: a maintainer might use A for sensitive work and D for routine preparation.

== 8. Authoring versus execution

[cols="1,1",options="header"]
|===
| Authoring / preparation | Execution

| exploratory; conversational where useful | pinned inputs
| may use retrieval/search | explicit authority
| proposes governing artifacts | deterministic, pedantic state transitions
| output is a proposal | auditable, evidence-producing
|===

Working principle: *AI-assisted outside, deterministic/governed inside.*

The outer-loop idea exposes a consequence: once preparation is automated, preparation is itself governed execution -- a Run with a profile, whose output is a proposed WorkItem. Authoring versus execution is therefore a *role/lifecycle distinction*, not a human-versus-AI distinction. The same artifact can be the output of one Run's execution and the governing input of another Run's authoring-dependent launch. Where exactly the boundary sits for automated preparation is deliberately left open.

== 9. Capability composition

Direction: *roles authorize capabilities; adapters realize capabilities.*

[source,text]
----
system / repository ceiling  (trusted policy)
    -> parent WorkItem narrows
        -> child WorkItem narrows further
            -> Hop receives projected, exact capabilities
----

Installed services are not automatically Run capabilities. Presence on the host is an environment fact; availability to a Hop is a projection decided by the envelope chain and admitted against the environment boundary (T6). The current enforceable action model is repository-effect-only (`edit`, `commit`; carve-out C10); anything beyond it is an environment-boundary fact until separately designed.

Possible future integrations: local CLI tools, direct APIs, MCP tools, retrieval/embedding services, static-analysis services, Git hosting, issue trackers, repository-local services. Issue trackers and Git hosting are natural backlog sources for B; they supply candidates, not authority.

MCP is an interoperability mechanism for realizing capabilities, not the Coordinator domain model.

Provider subscription quotas and plan limits are adapter/environment facts. Coordinator budgets stay in Coordinator units (Hops, invocations, time, and optionally spend).

== 10. Product packaging and deployment (direction only)

=== 10.1 One distribution first

A plausible initial shape is one Python distribution, `workflow-coordinator`, published through PyPI, with internal layering such as:

[source,text]
----
workflow_coordinator.domain        # model, reducer, profile/route semantics
workflow_coordinator.application   # operator, run orchestration
workflow_coordinator.adapters      # provider adapters, git facts, persistence, evidence
workflow_coordinator.cli           # console entry point
----

and one console entry point, approximately `wfc`. Package entry points give users a real application; `python -m ...` is not the product surface. Illustrative commands: `wfc init`, `wfc workitem ...`, `wfc assist`, `wfc run`, `wfc status`, later backlog/outer-loop operations.

This is consistent with, and not additional to, carve-out C5 (minimal `pyproject`, one console entry point, declared dependencies for the copy-run proof).

Internal layering does not require separate distributions. Assumed-now splits such as `wfc-core`, `wfc-cli`, `wfc-assist`, `wfc-adapter-*` are not part of this direction. Possible later reasons to split or introduce optional extras: a stable embedding API used by other Python programs; heavyweight optional TUI dependencies; server/API deployment without interactive UI; separately versioned provider/plugin ecosystems. Until one appears: one package, one version, one `wfc` executable.

=== 10.2 Installation channels

A consumer repository may pin the Coordinator as a development/tool dependency in its environment/lockfile and invoke the pinned version, e.g. conceptually `uv run wfc ...`. A human may alternatively install an isolated global tool via `pipx` or `uv tool`. No installation workflow is prescribed.

=== 10.3 Pinned execution versus global UX

For governed execution, reproducibility favors the repository-pinned version: the Coordinator version is part of what makes a Run's semantics reconstructable. A later global launcher might coexist:

[source,text]
----
global / user-facing wfc
    -> detects repository
    -> governed execution delegates to repository-pinned WFC version
----

This delegation/bootstrap is future design only. Early standalone use invoking the pinned CLI directly is sufficient; a global bootstrapper is not a carve-out prerequisite.

=== 10.4 Shell wrappers

The portable product surface is the `wfc` console entry point. Repository-local wrappers such as `assist.sh` are optional consumer convenience, not required for distribution, and not the cross-platform product contract.

== 11. Relation to the carve-out

This concept concerns orchestration, WorkItem lifecycle, interactive UX, parent/child Runs, and packaging/deployment of the Coordinator itself. It contains no spreadsheet-domain architecture and is suitable to move with the Coordinator during a history-preserving carve-out. Under carve-out C4 the incubator remains citation authority; a copy in the new repository would be imported historical context, which matches this document's non-normative status.

*This concept paper is not a carve-out prerequisite.* It adds nothing to P1--P6. Slice 5C/5D sequencing relative to the carve-out remains as stated in the carve-out review §6.

== 12. Non-goals

Implementation now; arbitrary recursive autonomous agents; unlimited task generation; unconstrained AI product-owner behavior; spontaneous backlog invention outside authorized intake; implicit parent-to-child authority inheritance; hidden child-agent spawning; replacing the accepted inner reducer/profile model; choosing assistant *or* outer loop as the exclusive direction; requiring a TUI; requiring a global launcher; splitting PyPI distributions now; encoding provider subscription quotas into Coordinator domain logic; making MCP foundational; making this document normative; making this document a carve-out blocker.
