== 1. Current / proven

The current Workflow Coordinator establishes a bounded, Single-WorkItem model:
a deterministic reducer controls authority and lifecycle around agentic
execution, while a Hop is a bounded agent invocation. The accepted V1 work is
not evidence for autonomous orchestration beyond that model.

Within this distinction, an agent may exercise epistemic initiative without
receiving binding authority. It may assess, investigate, propose, implement,
review, correct, or verify within its authorized Hop. For example, it may
discover that a problem definition is wrong or that scope ought to expand, but
it returns that as a structured result; it does not thereby authorize the scope
expansion or the subsequent workflow transition.

In short:

[source,text]
----
LLM      = semantic / epistemic operator
Reducer  = deterministic authority + lifecycle controller
----

Epistemic freedom is not workflow freedom. Subject-matter initiative is not
decision authority.

The Coordinator's current Single-WorkItem status is governed by its accepted
FTR and proposed architecture: the existing N=1 authority model is accepted,
while further authorization, including Slice 5 and autonomous multi-Hop work,
is explicitly separate and absent here.

== 2. Strategic hypotheses

These are working hypotheses, not conclusions or design commitments.

Non-algorithmic work does not by itself require a freely orchestrating LLM
controller. A deterministic reducer need not calculate the substantive answer.
It only needs to determine the kind of contribution currently requested, the
agent's scope and permitted capabilities, allowed result types and their
authority, and the workflow transitions that may follow.

The corresponding hypothesis is that an LLM can be a nondeterministic semantic
or epistemic operator while the reducer remains the deterministic
authority/lifecycle controller. An open semantic space can therefore sit within
bounded deterministic control flow:

[source,text]
----
open semantic space
       -> bounded epistemic operation
       -> structured result
       -> deterministic authority/lifecycle transition
----

This leaves room for free micro-agenticity inside a sufficiently large
authorized Hop. The agent can locally plan, investigate, experiment, revise
its plan, and perform several connected steps, without the outer reducer
orchestrating each internal decision.

Another hypothesis concerns when governance is warranted:

[source,text]
----
Governance should follow repetition, not abstraction level.
----

The current Coordinator originated in repeated human dispatch work -- dispatch
implementation and review, route corrections and re-reviews, and reconstruct
Git/evidence state -- rather than in an attempt to automate the underlying
judgment. A higher-order loop becomes worth considering only if activity at
that level likewise becomes mostly repetitive dispatch.

One possible future shape is a Family / Workstream Coordinator above the
current Single-WorkItem Coordinator. It might select a next already-authorized
WorkItem, place completed results against an existing roadmap, start
mechanically convergent follow-up work, and stop for genuine priority or
authority questions. This is a possibility to test against observed repetition,
not a component to build.

== 3. Governance and scale boundaries

A Hop must be large enough to leave meaningful room for local planning,
investigation, experimentation, and creativity. Governing every read, test,
inspection, or edit as a separate workflow transition would turn useful local
agent work into inefficient micro-governance.

Three boundaries must remain distinct:

. *Environment boundary:* what the agent can technically reach.
. *Hop authority:* what the agent may semantically do for this concrete task.
. *Workflow/reducer authority:* which macro lifecycle transitions are allowed.

An agent VM, constrained SSH identity, and limited reachable target systems or
credentials can establish a broad safe execution envelope. Future sandboxing,
such as bubblewrap, could further bound worktree write access, visibility of
trusted `.git` metadata, Coordinator state, credentials, and host paths. Such
technical containment can reduce the need to govern every local action.

Local root inside an isolated agent VM is conceptually different from authority
over host or repository trust boundaries. The former can support maintenance of
the agent's local execution environment; it does not imply access to other trust
zones or authority to cross their boundaries.

== 4. Human role and the limit to higher-order automation

Orchestration layers should not be stacked merely because they can be modeled.
Requirement weighting, product priorities, architectural trade-offs, and
choosing which problem to solve remain maintainer work while they are genuine
judgment rather than repetitive dispatch.

The purpose is not maximum autonomy. It is removal of mechanical human dispatch
work while retaining human involvement where value, meaning, and authority are
still being decided.

== 5. Open questions and future tests

The following questions are intentionally unresolved:

* What Hop size is useful for different work types while still preserving real
  local freedom?
* Which generic epistemic phases remain adequate over time?
* What observed, manual dispatch repetition would justify a Family Coordinator?
* Which decisions could be automated at a higher level without hollowing out
  maintainer authority?
* How can an agent propose a new workflow without authorizing that workflow
  itself?
* Which capability envelopes are needed for different Hop types?
* How much VM or sandbox isolation makes additional workflow governance
  unnecessary?
* How can cost and token efficiency be managed for open analysis Hops?

There is also a productive tension to retain: a semantic problem can be open,
creative, and difficult without requiring unconstrained macro-orchestration.
Whether that hypothesis continues to hold, and where its practical boundary
lies, requires evidence from bounded work rather than premature generalization.
