= Agent Workflow Coordinator — Consolidated Hypothesis Paper
:toc:
:toclevels: 2

Status: consolidated, non-binding hypothesis paper and future design input.
Empirically informed by two historical AI-assisted engineering waves and
targeted reconstruction from their coordinating chats; externally sanity-checked
against selected practical code-review literature.  It is neither accepted
architecture nor an implementation specification.  It authorizes no source,
test, registry, Domain, Trusted-Ingress, FTR, Project-Memory, or DMC
family-cycle change.

Date: 2026-08-25.

* a decision that full autonomous agent execution is desired.

== 2. Motivation from the FK/DMC pilot

The completed FK/reference-helper pilot (Cycle 0 through Family Cycle 1, ~60+
commits) exposed a repetitive *human coordination* loop, distinct from the
semantic work itself:

[source,text]
----
agent receives prompt
  -> agent analyzes / designs / implements / reviews
  -> agent reports one or more commits
  -> human verifies actual git state
  -> human inspects git show / git show --stat / changed files / tests
  -> human packages the relevant evidence
  -> human selects the next agent / role / context
  -> human pastes the next bounded prompt
  -> independent gate / correction loop
  -> repeat
----

The recurring overhead is not the semantic judgment (design, implementation,
review) but the mechanical packaging and hand-off between agent turns. A
future automation effort should investigate automating this orchestration
overhead *without* prematurely automating the maintainer's semantic authority.

== 3. Generalization hypothesis

The useful abstraction should, if practical, be *more general* than the DMC
sweep. The candidate shape is not a narrow `dmc_loop.py`, but:

[source,text]
----
generic workflow coordinator
  + workflow profiles
----

with DMC family hardening as the *first* profile and source of empirical
requirements. Potential later profiles are aspirational only: FTR
implementation, ordinary feature development, bug investigation/fix/review,
architecture migration/refactoring, security hardening, release/quality
gates, and possibly other projects or repositories.

Cross-repository reuse is a design pressure, not a requirement for the first
implementation. The first design should avoid closing off later
extraction/reuse, without building a universal framework from day one.

== 4. Coordinator / Agent / Human boundaries

*Coordinator.* Trusted workflow mechanics, likely running on the development
VM with direct access to the repository filesystem, git, tests/make targets,
architecture/style guards, workflow state, and (where available) an agent
invocation mechanism. It should not rely on agent prose as repository
authority.

*Agents.* Perform semantic work: assessment, design, implementation, review,
correction, closure assessment. Agent self-report is evidence/input, not
repository truth.

*Git.* Authoritative for what actually changed. If an agent reports N commits,
the coordinator should be able to verify commit existence, expected ancestry,
actual HEAD, unexpected commits, changed paths, and worktree state.

*Reviewers.* Independent reviewers should be distinct runs/contexts from the
author. Provider/model diversity can be useful, but no exact model assignment
should become part of the architecture.

*Human.* Remains semantic authority for important gates. The goal is not to
remove the maintainer, but to stop requiring manual, repetitive mechanical
orchestration between every agent hop.

== 5. Generic workflow shape and profiles

Candidate generic structure:

[source,text]
----
work item
  -> author/analyst agent
  -> deterministic repository/evidence verification
  -> validations / evidence providers
  -> independent reviewer
  -> structured verdict
  -> workflow transition OR correction loop OR human stop
----

A DMC-specific profile may later define transitions such as assessment ->
readiness design -> independent readiness review -> implementation ->
independent implementation review -> closure assessment -> independent
closure review, but the generic coordinator should avoid hard-coding DMC
terminology where reasonably avoidable.

== 6. Workflow state (open question, no schema chosen)

A future coordinator likely needs explicit machine-readable workflow state,
possibly including: workflow/profile, current work item, current phase,
repository base commit, current HEAD, generated commits, accepted/rejected
gates, open findings, authorized scope, next permitted transition, blocked
transitions, and whether a human decision is required. No schema is chosen
here; see <<12>>.

== 7. Git authority and evidence packaging

One of the strongest concrete requirements observed in the FK pilot: a
*deterministic Git evidence packager*. Candidate evidence: repository path
identity, workflow base commit, current HEAD, commits produced by the current
work item, commit metadata, changed-path list, per-commit `git show` /
`git show --stat`, aggregate `base..head` diff, aggregate diff stat, worktree
state, validation results, and authorized-scope comparison.

Principle: *Git is authority over agent self-report.* If an agent reports
three commits but repository history contains four relevant new commits, that
mismatch should be detectable and potentially stop the workflow.

=== 7.1 Large-diff bounding

For ordinary bounded commits, the evidence package may contain full diffs.
For very large changes, the packager should avoid blindly injecting thousands
of lines into the next agent's context — candidate strategy: small diff -> full
`git show`/aggregate diff; large diff -> `git show --stat` + changed paths +
selected/priority-path diffs, with the reviewer able to inspect source
directly as needed. A rough ~1000-changed-line threshold was discussed during
this handoff but is explicitly *not* adopted as a permanent constant here; the
real principle is that evidence should be complete enough for review while
remaining bounded. Authorized/priority paths from the current work item could
help decide which diffs stay fully included.

== 8. Validation / evidence providers

Separate *evidence collection* from *gate semantics*. Candidate initial
providers: git evidence, unit/integration tests, architecture guards,
source/style guards, diff hygiene. Candidate later, optional providers:
SonarQube/static analysis, security scanners, dependency scanners, other
quality-analysis services.

Principle: evidence providers produce observations; workflow policy, the
reviewer, or the human determine meaning and gates. A Sonar Quality Gate (or
equivalent) must not become architecture truth by default — e.g. a complexity
warning may be useful evidence without automatically forcing a refactor.

== 9. SonarQube / external-analysis future option

Preserved as a *future option only*, not a decision: a later add-on may place
SonarQube (or similar) on a separate quality-services node reachable by the
development/agent VM, keeping persistent service state and optional external
evidence providers separate from the coordinator's own narrow integration
surface. Explicitly out of scope for this note and for any first slice: do
not install SonarQube now; do not create network/service configuration; do
not require a second node for an MVP; do not design a Sonar-specific
coordinator architecture. The first coordinator design should merely avoid
making later external evidence-provider integration unnecessarily difficult.

== 10. Human gates and autonomy boundary

Candidate human stop conditions (non-exhaustive): scope expansion beyond
authorized files/area; a new public-surface question; a new
metadata/lifecycle/persistence contract; conflict between governing
artifacts; a new Domain ownership-boundary question; unexpected repository
history/worktree state; a material review finding requiring fresh design; a
cross-profile/cycle transition; a strategy/roadmap/Project-Memory decision.

Principle: automate repetitive coordination; retain explicit human gates for
semantic/strategic changes.

Working autonomy hypothesis:

* Begin conservatively with state tracking, next-task/prompt preparation,
  Git/evidence verification, validation collection, and explicit human gates.
* Any later serial agent invocation must remain policy-bounded and be increased
  empirically rather than treated as a universally safe stage transition; see
  the bounded-autonomy hypothesis in <<21>>.

The observed successful workflow so far is fundamentally *serial* and
dependency-aware; avoid multi-agent parallelism unless a later use case
justifies it.

== 11. Possible minimal first slice (hypothesis, not scoped work)

A useful first automation slice may consist only of: a coordinator skeleton;
machine-readable workflow state; a deterministic Git evidence packager; a
role/prompt template mechanism; a structured-result parser/schema; and
explicit human stop gates. Structured agent results (status, commits, verdict,
material findings, scope_changed, next_requested_gate — no schema fixed here)
are meant to give the coordinator a machine interface alongside the normal
prose report, so it does not need to infer intent (e.g. whether "ACCEPT WITH
MINOR CORRECTIONS" authorizes the next transition) from free text. Role/prompt
templates (assessment, readiness design, independent design review,
implementation, independent implementation review, correction, delta review,
closure assessment, closure review) are a related candidate mechanism; none of
this is built by this note.

Explicitly *out* of initial scope: SonarQube; distributed service
architecture; autonomous full-family execution; generalized cross-repository
product packaging; a broad plugin ecosystem; a parallel agent swarm;
automatic architecture decisions.

== 15. Consolidated evidence basis and interpretation discipline

This paper evolves the early concept note rather than replacing its hypothesis.
The original FK/reference-helper DMC pilot exposed a human coordination loop:
agent work/report -> human Git verification -> evidence packaging -> next
bounded prompt/reviewer -> correction or gate.  The expanded evidence is now
sufficient to preserve a more substantial hypothesis before a later design task
chooses any architecture.

The evidence is deliberately heterogeneous.

[cols="1,2,3",options="header"]
|===
|Source |Supports |Does not support

|Repository commits and durable artifacts
|Chronology, recorded verdicts/findings, changed files, tests, and lifecycle
transitions.
|Detailed supervisory intent where it was not written in the artifact.

|Targeted follow-up questioning of the chats that coordinated each wave
|Reconstruction of how scope was bounded, why a parent stopped, and why the next
role or prerequisite was selected.
|Invented verbatim prompt text or certainty beyond retrospective reconstruction.

|External practical review literature
|A sanity check on selected review principles and comparison point.
|Governing authority, final validation, or a project-specific design mandate.
|===

The follow-ups were not retrospective storytelling. They were asked to
reconstruct actual steering behavior that commit subjects alone cannot expose.
Claims based on that reconstruction are represented as such below.

== 17. Workflow taxonomy: capabilities, not one enum

The waves observed orientation/re-entry/rebaseline; broad discovery,
architecture assessment, census, bounded counterexample search; design and
correction design; readiness/design gate; implementation, evidence/self-report,
and independent implementation review; correction/delta review; optional
adversarial pre-gate; integration/closure assessment and independent closure
review; prerequisite/nested work; documentation/lifecycle closure review;
concept review; Project-Memory curation; and handoff readiness.

Do not flatten these prematurely. Some are work kinds, review policies,
authority gates, evidence/result contracts, lifecycle operations, or supervisor
decisions. A later design must retain distinctions that alter authority,
evidence, or routing.

== 18. Review has independent dimensions

Review should not be one generic step.

[cols="1,3",options="header"]
|===
|Dimension |Candidate values and purpose

|Breadth / scope
|broad_discovery, bounded_design, implementation, delta_correction,
adversarial_implementation, integration, closure_census, lifecycle_docs.
Breadth defines the intended falsification/search surface.

|Authority
|advisory, readiness_gate, implementation_gate, correction_gate,
closure_recommendation, final_closure_gate. Authority defines what a verdict may
authorize, not how widely it searched.

|Reviewer context
|fresh, continuing. Fresh + broad is useful at independent discovery/acceptance
boundaries; bounded + continuing can preserve finding identity for stubborn
disposition. Context is neither scope nor authority.
|===

F-002 demonstrates adversarial breadth + advisory authority versus
implementation breadth + formal implementation gate. Historical ultrareview is
therefore a risk-triggered advisory pre-gate option, not mandatory final
authority.

=== 18.1 Breadth governance and product responsibility

A cross-wave steering rule was:

[source,text]
----
initial broad review -> establish finding set -> correction ->
deliberately narrow later review to known findings and direct regressions
----

A genuinely new MATERIAL issue may still stop the loop. A newly noticed,
unrelated MINOR after discovery intentionally closes can be residual,
observation, or backlog rather than another gate.

The framework provider is responsible for specified building blocks, promised
properties, supported/documented compositions, truthful/safe failure behavior,
and reasonable product safety where misuse could materially mislead or harm.
It is not automatically responsible for making every arbitrary user composition
meaningful or coherent. The Lego analogy is qualified: reliable pieces and set
instructions do not guarantee every arbitrary construction stands, but
unsupported construction does not excuse unreasonably dangerous failure modes.
This is a candidate review-goalpost boundary, not permission to ignore safety.

== 19. Convergence, reclassification, and outer safety

A fixed review-count threshold is rejected as the primary convergence rule.
There may be an outer safety budget, but E4 shows five or seven material loops
can be healthy.

Candidate progress signals are stable finding identity, narrowing residual
scope, material mechanism changes, material findings resolving, resolved
findings staying closed under regression checks, and no continuous invention of
new material findings without new evidence.

Candidate escalation/reclassification signals include superficial repeated
mechanism changes, textual oscillation over conflicting authorities, moving an
issue repeatedly between carrier/construction paths, bounded reviews reopening
unrelated scope, renegotiating accepted architecture without new evidence,
another semantic owner, incompatible contracts, or a required public/
compatibility decision. This is not a fake numeric convergence score.

== 20. Policy-bounded agentic coordination

The prior phrase deterministic coordinator with probabilistic work steps was too
strong. The refined hypothesis is a policy-bounded agentic coordinator running
on deterministic execution mechanics.

[cols="1,3",options="header"]
|===
|Layer |Candidate responsibility

|Deterministic mechanics
|Git state, base/head, changed paths, clean worktree, validation execution,
evidence collection, result-schema validation, allowed transition set, and
mechanically derivable artifact placement.

|Policy-bounded supervisor judgment
|Choose only among allowed routes: accept, bounded correction, narrow/retain
breadth, accept a MINOR, advisory adversarial review, policy-permitted
prerequisite, human escalation, or stop for lack of material progress. It must
not invent new authority to escape a gate.

|Semantic/strategic human authority
|New ownership/authority, incompatible contracts, plausible public-surface/
compatibility alternatives, security/trust boundary, capability deletion,
unexpected delegated-ownership crossing, roadmap/strategy, workflow/profile
redesign, and undelegated Project-Memory governance.
|===

The exact boundary remains open. Operational autonomy must not silently become
semantic authority.

== 21. Bounded autonomy and checkpoint reporting

The desired direction is not a prompt generator leaving 100+ manual copy/paste
hops. Candidate bounded LLM work/review invocations are:

[source,text]
----
max_autonomous_hops = N
N: 1 -> 2 -> 5 -> 10 -> possibly higher only for proven routine paths
----

Deterministic evidence collection does not consume a hop. The outer budget is a
safety/observability checkpoint, not review-iteration count. Work stops earlier
for explicit human gate, semantic escalation, anomaly, non-convergence,
unexpected Git state, or policy violation.

As N grows, humans must understand the sequence without rereading every prompt,
review, and diff. Candidate checkpoint content: work-item/run identity;
base/current HEAD; hops and commits; workflow state; open/resolved/non-blocking
findings; validation/evidence; stop reason; next allowed transition; human
attention status; and where the relevant semantic issue first appeared. Link
evidence rather than duplicate full review prose.

== 22. Git authority and future identity

Git is factual authority over self-report. Candidate invariant:

[source,text]
----
Every agent hop starts on a known Git commit and ends on a known Git commit
with a clean worktree.
----

A hop may create 1..n atomic commits; exactly one commit per hop is not
required. No later hop should start from uncommitted mutation. Candidate evidence
is base/head, commit range, paths, bounded diff/diff stat, worktree,
metadata, validation, and authorized-scope comparison. Bounding thresholds
remain open.

Do not assign synthetic historical hop IDs. Historical work remains addressable
through commits, ranges, artifacts, and Project Memory. Future identity might
distinguish WorkItem (semantic address such as DMC-FK-C2-S3, TI-E4,
BUG-NUMPY-TIMEDELTA64, DOC-CLOSURE-CDE), Run (possible execution instance), and
Hop (for example DMC-FK-C2-S3/H04). Run versus WorkItem semantics remain open.

Family/cycle/slice are profile labels, not generic schema. Commit subjects may
project genealogy, for example fix(domain): [TI-E4/H06] freeze executable
bindings; optional trailers might carry Workflow-Run, Work-Item, Hop, Hop-Kind.
This extends the non-binding traceability recommendation and does not rewrite
history.

== 23. Prompt composition, reproducibility, and retention

Candidate composition eliminates repeated huge prompts:

[source,text]
----
structured run specification
  + versioned reusable repository-local components
  -> expanded prompt
----

Components might include persona/base role, modifiers, repository policy,
workflow profile, step/evidence policy, output/result contract, and
documentation policy. Candidate base roles: analyst, designer, implementer,
reviewer, curator. Candidate modifiers: independent, bounded, fresh_context,
continuing_context, adversarial, correction, closure, lifecycle, review_only.
A historical bounded documentation-closure reviewer could be reviewer +
independent + bounded + lifecycle + fresh_context; this does not prove the
composition is sufficient for every role.

Structure process, provenance, and routing; retain prose for semantic argument.
What deterministic software can enforce should not only be LLM instruction.

Historical reproducibility should rely primarily on Git: old runs are
reconstructable from repository state at their historical commit. Components can
be maintained without an eternal v1/v2/v3 graveyard because forensic recovery
can use Git history. Candidate retention separates durable knowledge, workflow
evidence (compact spec, component refs, base/head, manifest, structured result,
validation), and raw material (expanded prompt, stdout, huge diffs/logs).
Compact specs may be retained every run; raw material is transient by default
and selectively archived. No final policy is chosen.

== 24. Project Memory, retrieval, and evidence providers

Candidate boundary:

[source,text]
----
Project Memory remembers what matters.
Coordinator records what happened.
----

Project Memory owns durable semantic orientation, decisions, residuals, roadmap,
next action, and historical references. A coordinator would own operational
genealogy: run/hop state, prompt specs, evidence, findings, reviews,
transitions, checkpoints. It must not use Project Memory as per-hop state.
Completed runs may promote important knowledge, normally by work-item/run,
accepted HEAD, or exceptional semantic hops rather than every hop.

Future semantic/vector document-inventory retrieval belongs mainly to knowledge/
memory. It must be authority/lifecycle aware: current canonical and Project
Memory high; warm accepted evidence medium; cold history on demand; superseded
strongly downranked. Similarity must not resurrect obsolete authority. No vector
design/implementation is authorized.

Evidence collection stays separate from gate semantics. Candidate providers:
Git, unit/integration tests, architecture guards, source/style checks, diff
hygiene; later SonarQube/static analysis, dependency/security scanners, and
other services. Providers report observations; a complexity threshold does not
mechanically equal architecture rejection.

SonarQube is future option only. One discussed deployment is a separate local
quality-services VM on the Proxmox N305/32 GB homelab, with SonarQube/local
PostgreSQL there and scanning where checkout exists. This is not MVP and
authorizes no infrastructure. The present pressure is only an EvidenceProvider
boundary.

== 25. Verification Depth and AI economics

Project evidence is consistent with, but does not prove causally, a quality
benefit from layered verification: many material problems were caught in
design/review/closure rather than later bug work. The apparently favorable
post-acceptance-bug/delivered-capability ratio is not a scientific measurement.

Verification Depth is distinct questions, not simply more reviews: semantic
coherence, ownership, implementation/design correspondence, truthful/fail-closed
failure semantics where required, known finding closure, counterexample search,
composition of accepted slices, and current canonical docs.

Machine loops change cost from scarce human attention/delay/context switching
toward tokens, compute, and elapsed time. More autonomy means less continuous
human observation and increases value of automated evidence, independent
falsification, convergence detection, and escalation. Candidate optimization:
maximize useful verification depth per unit human attention. This does not
justify ceremony: every stage needs distinct epistemic, falsification, or
authority purpose.

The project deliberately uses architecture such as pipelines, hexagonal
boundaries, Domain, rendering, adapter/IO separation, ownership, and Trusted
Ingress. A recent CLOC snapshot is weak corroboration that machinery has not
become the product: Domain 14,125 Python LOC; IO backends 3,804; pipeline 2,518;
rendering 1,628; core 575; application 348; CLI 319. LOC proves no architecture
quality. Hypothesis: AI makes architecture exploration, census, tests, review,
documentation, and refactoring cheaper and can shift break-even toward explicit
architecture/deeper verification; AI also makes bad abstraction cheap. Overhead
must reduce future complexity, improve verification, or reduce human attention.

== 26. Literature sanity check: _Looks Good to Me?_

The gitignored local draft tmp/draft_review_concept_vs_literature.adoc was read
and its reasoning incorporated; it remains untracked and uncommitted. External
source: Adrienne Braganza, _Looks Good to Me: Constructive Code Reviews_
(Manning, November 2024, ISBN 9781633438125; foreword Scott Hanselman). It is a
practical code-review text, not coordinator authority, and did not originate
the concept.

Strong agreements: explicit review purpose/focus/blocking criteria;
non-blocking treatment of nitpicks/MINOR residuals; automation of mechanical
checks; stable review targets; durable recordkeeping/context; repeated rework as
possible upstream design/acceptance issue; and incremental AI trust.

Extensions/differences: the coordinator covers assessment through lifecycle,
not only PR review; DMC Cell Codec shows known findings closed may not close
enclosing work; machine assistance may make deeper verification economic; and
increased autonomy increases value of machine verification. It explores beyond
AI suggests/human always approves while retaining human semantic authority.

The warning against stringent process overhead is accepted. The answer is not
AI makes ceremony free, so add every gate. Greater useful depth is plausible
only when each stage has distinct epistemic/authority value and human ceremony
does not scale with machine review depth. F-002 ultrareview is the example:
risk-triggered, useful, advisory, not mandatory authority. Established review
principles remain relevant; AI may alter rational depth. One book is not
academic validation or proof conventional engineering is obsolete.
