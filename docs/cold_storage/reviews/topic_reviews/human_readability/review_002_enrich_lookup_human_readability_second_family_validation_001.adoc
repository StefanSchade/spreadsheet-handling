== 6. File-by-file reader assessment

=== Facade

The three-line facade is a positive reference. Its one symbol is genuinely public
through direct imports and the registry target. No policy helper has an external
consumer. Changing the facade would create public-contract work without reader value.

=== Operation

`source`, `lookup`, and `output` truthfully name frame identities. Symmetric and
asymmetric keys are explicit, mutually exclusive, and normalized into a typed
state. Fail-closed collision and mismatch prerequisites are locally visible.
Missing-value and ordering behavior are visible before materialization, helper
selection is distinct from allowlist enforcement, and formula mode makes its
unsupported combinations explicit.

The data-frame path is non-mutating: merge/copy operations create output data and
the top-level frames mapping is copied. The metadata path is more subtle:
`_write_provenance` shallow-copies `_meta`, then `setdefault` can reuse and mutate
an existing nested `derived.sheets` mapping owned by the caller. A direct probe
confirmed that input metadata gains the new output record. This is already an
explicit unresolved concern in the provenance-lifecycle FTR and is not safe to
recast as a local readability edit.

Provenance is written after successful materialization and ordering. That is the
correct lifecycle boundary. The record's apparently verbose symmetric/asymmetric
fields are required by mismatch validation and must remain.

=== Policy

Policy resolution has one cohesive module owner and `_ResolvedKeys` makes key
state unusually clear. Inline values are reconciled with policy values for keys,
missing, order, defaults, allowlists, and value mode. Explicit asymmetric keys
authoritatively bypass only the policy key while retaining non-key policy.

The one local seam is that resolved `policy` is passed to key/missing/order/mode
resolvers but fields and allowlist rediscover it through `frames`. This is not a
behavior defect; it is an avoidable reader question about snapshot and ownership.

== 8. Concrete findings

[cols="1,1,2,5"]
|===
| ID | Severity | File / symbol | Assessment

| EL-HR-001
| Minor
| `policy.py::_resolve_fields`, `_resolve_allowed`; call sites in
`operation.py::enrich_lookup`
| *Reader question:* do keys, missing, order, mode, fields, and allowlist use the
same resolved policy instance? *Why real:* fields/allowed receive all frames and
repeat `_meta` traversal after the operation already resolved `policy`; a reader
must prove no distinct lifecycle exists. *Safe local direction:* pass the already
resolved coherent policy mapping to these private helpers and preserve every
branch/error. *Gate:* safe local/internal; no public or metadata-shape change.
*Preserve:* one policy module, `_ResolvedKeys`, conflict ordering, helper/default
semantics. *Characterization:* direct policy default/allowlist/conflict tests,
asymmetric-with-policy cases, and registry signature guard.

| EL-HR-002
| Important
| `operation.py::_write_provenance`
| *Reader question:* does the apparent output-copy boundary also protect caller
nested metadata? *Why real:* it does not when `derived` already exists; a direct
probe showed the caller's `_meta.derived.sheets` gaining output provenance.
Top-level mapping/data-frame non-mutation can therefore be mistaken for recursive
non-mutation. *Direction:* resolve copy-along-the-mutated-path and lifecycle
ownership under the already-open derived-provenance lifecycle authority; do not
normalize or fix it in a readability slice. *Gate:* architecture/lifecycle decision
required. *Preserve:* record shape, write timing, consumer behavior, persistence
stripping. *Characterization:* existing-derived sentinel, caller/input equality,
sibling preservation, and symmetric/asymmetric record parity.
|===

No Observation-only finding is forced. In particular, the unused `missing_mode`
parameter on `_build_formula_enrichment` is reachable only after formula mode has
rejected `fail`, so it creates little practical ambiguity and does not independently
justify work.

== 10. Recommended next step and stop-here option

*Recommendation: `Stop here — no enrich_lookup readability implementation currently justified`.*

EL-HR-001 is a valid small internal direction, but its reader gain does not by
itself exceed the cost of another FTR/implementation/review cycle. It may be
included only in a future independently justified low-touch maintenance slice,
with the characterization named above; this assessment does not authorize it.

derived-provenance lifecycle/ownership decision. It must not be mixed into a
readability slice. No implementation FTR is created and no implementation slice
is authorized.
