== 1. Review verdict

*Verdict: MATERIAL REVISION REQUIRED.*

The assessment is valuable evidence, but it is not safe to use as the direct
basis for DMC acceptance in its current form.

Its central negative conclusion survives in a narrower form: the repository
does not have a complete, current, authoritative semantic ownership map for the
whole Domain. Its strongest concrete conclusions also survive: package layout,
inverse pairing, metadata adjacency, and implementation reuse do not by
themselves establish common ownership; XRef, Compact, Sparse Defaults,
Trusted Ingress, schema maintenance, final cleanup, and Workbook View have
materially different shapes; and the FK/lookup boundary must not be decided by
package or provenance adjacency.

The material problem is what the assessment builds on top of those facts. It
omits the existing Domain Contracts Registry, including its explicit
`transformation_families` and `transformation_types` taxonomies and the accepted
Review 005 warning against introducing another universal ontology. It then
proposes a new classification whose rows mix owner kind, dependency relation,
architectural layer, planning cluster, artifact type, and uncertainty status.
Those categories are not one operational axis and do not justify nine new
DMC-acceptance MUSTs or a whole-module census.

The assessment also exceeds the active roadmap's bounded DMC mandate. The
roadmap authorizes consolidation of established module-responsibility, naming,
readability, and objectively enforceable architecture conventions. It does not
authorize a new whole-Domain ownership ontology as a prerequisite to the first
pilot. The smallest safe response is to correct the DMC so it is not limited to
inverse-shaped transformation families, require each pilot to declare its
semantic scope and dependency seams, and let the first pilot test any further
vocabulary. A repo-wide module disposition table is not required first.

== 2. What survived adversarial review

The following conclusions were actively tested and remain well supported.

. *No complete current whole-Domain ownership map exists.* The canonical
  Domain Contracts Registry is incomplete seed infrastructure, contains future
  and candidate rows, and maps poorly to the 44 current public pipeline steps.
  It is an important existing model, but not the missing complete map.
. *A transformation family cannot be the only shape covered by maintainer
  procedure.* Trusted Ingress, schema maintenance, final cleanup, Workbook
  View, configuration producers, validations, and resource-writing steps all
  require maintainer decisions even though several are not ordinary reversible
  frame transformations.
. *Semantic reconstruction must precede package movement.* Current packages
  contain both strong owners (`xref_crosstable`, `discriminator_split`) and
  technical/historical groupings (`validations`, `transformations.helpers`).
. *Shared implementation is not shared ownership.* `_where_predicates`,
  physical-label checks, formula intent, and axis mapping are reused without
  making their consumers one capability.
. *Shared metadata namespace is not shared ownership.* `meta_registry.yaml`
  explicitly says FK `helper_columns` and lookup `enrich_lookup` occupy
  independent subkeys under `_meta.derived.sheets.*`.
. *Composition does not transfer primitive semantics.* The maintained Compact
  contract delegates matrix addressing to XRef, cell representation to Cell
  Codec, optional vocabulary to Legend Blocks, and excludes Sparse Defaults.
. *FK helpers and lookup enrichment must not be presumed to be one family.*
  Their current configuration, scope, mutation/output behavior, lifecycle, and
  consumer uses differ even though both produce display helpers.
. *The Domain/Core rule cannot be “pure means Core”.* Current evidence shows
  pure Domain predicates and feature-specific FK mechanics in Core.
. *A full package template is undesirable.* Small operations and cross-cutting
  seams do not benefit from mandatory `model.py`/`policy.py`/`operation.py`
  skeletons.
. *The first detailed boundary decision belongs in a bounded Cycle 0.*
  In particular, FK/lookup consolidation must be decided against its actual
  public surfaces and consumer workflows, not by this global assessment.

== 3. Material findings

=== DSO-REV-001 -- Existing canonical taxonomy and its warning were omitted

*Classification:* BLOCKING FOR DMC ACCEPTANCE.

*Claim challenged:* “There is no canonical Domain family taxonomy today,”
followed by the introduction of a new umbrella and category set.

*Evidence:* `registries/domain_contracts/canonical/` contains checked canonical
tables named `transformation_families.json`, `transformation_types.json`, and
`transformations.json`. The first two currently contain ten family rows and ten
type rows. `tests/integration/domain_contracts/test_domain_contract_registry.py`
checks that transformations reference declared types and families, and
`make domain-contracts-check` is green. The registry README simultaneously says
the data is deliberately small seed infrastructure and not full transformation
coverage. Its current transformation names diverge heavily from the 44 current
pipeline-step names and include unimplemented future candidates.

The accepted Review 005 analysis is even more important. It records taxonomy
proliferation as an active maintenance risk, warns that contributors cite the
vocabulary they encountered last, and explicitly recommends not designing a
fifth unifying ontology. Its closure says runtime remains authority and the
registry should grow only through bounded code trace -> declaration -> guard
slices.

*Assessment/inference:* The literal existence of a canonical family taxonomy
falsifies the unqualified wording. Its incompleteness and candidate status mean
it does not falsify the narrower, useful claim that there is no authoritative
whole-Domain semantic ownership map. The omission matters because the proposed
new taxonomy repeats exactly the proliferation risk an accepted review already
identified.

*Confidence:* High.

*Architectural consequence:* The report must compare and map its vocabulary to
the Domain Contracts Registry before recommending any durable terms. It should
not establish a parallel ownership ontology in the DMC.

*Required correction:* Replace the absolute claim with the narrower conclusion,
add the registry and Review 005 to the evidence/disagreement baseline, and state
why the registry is insufficient without treating it as absent.

*DMC acceptance:* Blocking. A DMC based on the current assessment would add a
new taxonomy without reconciling a checked existing one.

=== DSO-REV-002 -- The proposed categories are not one classification axis

*Classification:* BLOCKING FOR DMC ACCEPTANCE.

*Claim challenged:* The categories in section 3 are sufficiently distinct to
be DMC ownership-unit kinds.

*Evidence:* “Transformation family”, “generic Domain operation”, and
“cross-cutting service” describe kinds of behavior or scope. “Composite” and
“shared primitive” primarily describe dependency roles. “Domain vocabulary”
describes an asset. “Core substrate” describes layer placement. “Capability
cluster” is explicitly non-owning. “Historical sediment or ambiguous” is a
confidence/status disposition. “Boundary-adjacent mixed responsibility” is a
review finding, not a durable owner. A single thing can occupy several rows:
Grouped XRef is a public capability, a composite, a consumer of a primitive,
and a controlled-carrier owner; Trusted Ingress is a boundary, service,
protocol, and vocabulary consumer.

The repository already keeps some of these axes separate: pipeline step
category, inverse kind, metadata lifecycle, transformation type/family,
public exposure, and source status are different fields in different
contracts.

*Assessment/inference:* The taxonomy is coherent as prose but not operational
as a single maintainer classification. It cannot answer which owner approves a
change, which dependency must coordinate, or which compatibility surface is
affected without additional relationship data. “Durable semantic ownership
unit” therefore risks becoming an abstract synonym for “whatever is in review”.

*Confidence:* High.

*Architectural consequence:* If copied into the DMC, maintainers will argue
about labels and still need to reconstruct dependencies, authority, and public
surface. The categories should be decomposed into a small scope declaration
plus relationship/status attributes, not normalized into an ontology.

*Required correction:* Keep only decision-producing distinctions. A pilot can
state the semantic scope being changed, its public/compatibility surface, its
owned state, and relations such as “composes”, “provides primitive to”, or
“consumes protocol from”. Do not require every scope to receive exactly one of
the proposed labels.

*DMC acceptance:* Blocking if the category list is made normative; not blocking
if retained as exploratory examples.

=== DSO-REV-003 -- The assessment expands the DMC beyond its authorized mandate

*Classification:* BLOCKING FOR DMC ACCEPTANCE.

*Claim challenged:* Nine ownership/taxonomy matters MUST be resolved before DMC
acceptance.

*Evidence:* The active roadmap's DMC section defines a bounded stage that
consolidates four established dimensions: module-responsibility vocabulary,
naming, evidence-derived readability, and objectively enforceable architecture
rules. It says this stage is not to author new style rules, not to impose a
universal package skeleton, and not to begin family hardening. The current DMC
design already expands that mandate and flags the narrow-versus-broad scope as
an open decision. The assessment resolves the open decision in favor of an even
broader whole-Domain taxonomy, Core placement criterion, global module census,
test ownership dimension, and documentation variants.

*Assessment/inference:* Some broad DMC rules are sensible, especially
semantic-first review and explicit compatibility/lifecycle decisions. They do
not make a global taxonomy a prerequisite. The report treats “this procedure
must work when the subject is not an inverse pair” as “the DMC must classify
the entire Domain before acceptance”; that implication does not follow.

*Confidence:* High.

*Architectural consequence:* Accepting these MUSTs would silently turn an
exploratory assessment into a new architecture stage and contradict the
roadmap's bound-complexity intent.

*Required correction:* Narrow the acceptance gate to scope-neutral maintainer
rules and explicit boundary/dependency recording. Leave taxonomy validation,
exact family boundaries, Core moves, and documentation format to pilots or
separately authorized work.

*DMC acceptance:* Blocking.

=== DSO-REV-004 -- The whole-module disposition and census recreate global analysis

*Classification:* IMPORTANT CORRECTION.

*Claim challenged:* Every Domain production module needs a provisional owner or
`ambiguous/sediment` disposition before DMC acceptance, supported by a global
census before the first pilot.

*Evidence:* The Domain currently has more than eighty Python files, including
package facades, private helpers, models, validators, boundary delegates, and
single-module operations. The repository already maintains overlapping module,
step, implementation-link, metadata-owner, and test-topology inventories. The
Semantic Model says adoption is triggered by operational friction, not by the
mere fact that a family has not yet been classified. The roadmap repeatedly
rejects big-bang adoption. Review 005 warns that broad tables accrete faster
than evidence and become pseudo-authority.

*Assessment/inference:* A row per module is easy to start and expensive to keep
truthful. “Ambiguous/sediment” also creates the appearance of completed review
without resolving any decision. A bounded pilot needs a complete local scope;
the DMC does not need a complete global module map.

*Confidence:* High.

*Architectural consequence:* The proposed census would duplicate registries,
age immediately after module splits, and delay the very pilot needed to test
the vocabulary.

*Required correction:* Replace the module census with a minimal global
orientation derived from existing maintained surfaces: current public steps,
known non-step Domain services, registered metadata producer/consumer seams,
and known composites. Require module-level disposition only inside the selected
pilot's bounded inventory.

*DMC acceptance:* The global requirement should be removed before acceptance;
the minimal orientation can be part of pilot selection.

=== DSO-REV-005 -- Several concrete classifications are too certain or wrong

*Classification:* IMPORTANT CORRECTION.

*Claim challenged:* The concrete capability map is reliable enough to support
the taxonomy.

*Evidence:* The clearest error is flat XRef axis projection. Its module states
that `project_axis_labels` and `restore_axis_keys` compose *around* XRef and do
not wrap it. The pipeline registry classifies both as `primitive`, not
`composite`. They own a public conditionally bijective vocabulary substitution
using the shared resolver. Calling flat axis projection a composite is not
supported by runtime structure or current contracts.

Cell Codec is independently public and semantically real, but current
maintained prose calls the explicit operations a compatibility primitive in
the Compact composition and repeatedly distinguishes them from the retired
`cell_codecs` metadata family. Historical artifacts also call it a projection
family. “Independent family, high confidence” hides that terminology conflict.

Grouped XRef is the reverse case: source docstrings, registry category, wrapped
steps, and tests already establish it as a composite. Whether it is also placed
under an XRef planning owner may remain open, but “composite versus subfamily”
is not an unresolved runtime-role question.

Derived-column policy is a common cleanup consumer, but the implementation is
not a general protocol: it knows the FK and lookup provenance shapes directly,
value-checks only lookup helpers, falls back to Workbook View declarations and
FK policy, and has a sequencing dependency on visible-sheet naming. The
evidence supports “cross-capability cleanup operation”; it does not yet prove a
durable generalized derived-column governance owner.

*Assessment/inference:* The report sometimes promotes relationship shape into
owner kind and sometimes preserves an open question that maintained contracts
already answer. These are correctable boundary errors, not a failure of the
semantic-first method.

*Confidence:* High for flat axis projection and Grouped XRef; medium-high for
Cell Codec and derived cleanup ownership.

*Architectural consequence:* Package and DMC decisions based on the map could
bury an independent public inverse pair as composition, revive a retired
metadata-family concept, or invent a protocol around one hard-coded consumer.

*Required correction:* Correct flat axis projection; distinguish the Cell Codec
capability from the retired metadata family and lower family-label confidence;
state Grouped XRef's composite role as settled while leaving only governance
grouping open; qualify derived-column policy as a common operation whose owner
is unresolved.

*DMC acceptance:* Important input correction; the DMC itself need not settle
these boundaries.

=== DSO-REV-006 -- Validation, generic-operation, and output classifications overfit

*Classification:* IMPORTANT CORRECTION.

*Claim challenged:* The proposed categories recover useful distinct owners
outside the XRef/helper lineage.

*Evidence:* The current Functional Model deliberately treats validation as one
cross-cutting use case with several forms. It says graph validation “is still
validation” and need not introduce a separate graph model.
`graph_validations.py` reuses reference-validation behavior. This supports a
validation capability with specializations at least as strongly as separate
reference and graph owners. FK-helper validation remains clearly family-local,
and `add_validations` produces workbook constraint intent, so the current
package still is not one owner.

Extract, join, and pivot are independent registered operations, but “generic
Domain operation” adds no maintainer decision beyond “public capability with no
inverse”. The Functional Model groups join with discriminator split as derived
frame views despite their different lifecycles, demonstrating that functional
navigation and ownership are different axes.

The three output steps are also not one candidate owner. Structured YAML and
key/value publication have distinct output grammars. Artifact Manifest consumes
their report frames and optionally reads/checksums and publishes a manifest.
The Technical Model groups them only for resource-sensitive authorization and
path containment. That common sink-security protocol does not make their
semantic projections one capability.

*Assessment/inference:* The assessment correctly detects that current packages
are not ownership maps, but then fragments or groups operations according to
whichever property is most visible. These examples do not validate the proposed
ownership taxonomy.

*Confidence:* High.

*Architectural consequence:* A taxonomy-driven reorganization could split a
coherent validation capability, create an empty “generic operations” owner, or
group distinct publishers because they share security mechanics/report shape.

*Required correction:* Present alternative owner interpretations and defer
them. Treat “validation form”, “lossy operation”, “publisher”, and
“resource-sensitive” as properties or relationships, not automatic owner
boundaries.

*DMC acceptance:* Not a reason to block a narrow DMC, but a reason not to adopt
the proposed category list.

=== DSO-REV-007 -- The proposed Domain/Core criterion conflicts with current authority

*Classification:* IMPORTANT CORRECTION.

*Claim challenged:* “Context-free representation/carrier/mechanism in Core;
spreadsheet-handling meaning/invariants/lifecycle in Domain” is a sufficient
replacement criterion.

*Evidence:* The authoritative architectural-layers chapter explicitly defines
Core as a stateless leaf and explicitly places FK wire-format and helper-column
utilities in `core/fk.py`. Its worked FK trace names `FK_PATTERN`, `FKDef`,
`build_id_value_maps`, and `apply_fk_helpers` as Core utilities while placing
policy, lifecycle, and provenance in Domain. The proposed criterion would move
some of those utilities, so it is an architectural change, not merely a clearer
reading of current policy.

The current tree also defeats a single semantic-strength test in both
directions. `core.formulas`, `ExactTable`, and `header_grid` carry
spreadsheet-relevant typed meaning but serve as dependency-safe inter-layer
carriers. Conversely, Domain writers and `yaml_overrides` perform filesystem
work even though the authoritative Domain description says Domain must not
know persistence details. `core.refs` is unused historical helper code and is
misdescribed as cell-reference arithmetic in the layer document. `core.indexing`
is generic but currently concentrated in the FK path.

*Assessment/inference:* Semantic meaning is necessary evidence but not a
sufficient placement rule. Dependency direction, inter-layer carrier role,
authority, side effects, and compatibility surface also matter. Semantic
stewardship need not equal physical package placement.

*Confidence:* High.

*Architectural consequence:* Making the new sentence normative in the DMC
would silently supersede maintained architecture and could force dependency
cycles or duplicate carrier types.

*Required correction:* Report the disagreement explicitly. Treat `core.fk`,
`core.indexing`, `core.refs`, Domain filesystem writers, and `yaml_overrides`
as bounded placement-review candidates. The DMC should link to current layer
authority and require an explicit architecture decision for exceptions; it
should not settle the placement rule itself.

*DMC acceptance:* The DMC must not adopt the assessment's criterion as new
authority. Resolving individual moves can remain later work.

=== DSO-REV-008 -- Package paths cannot normally encode all semantic ownership

*Classification:* IMPORTANT CORRECTION.

*Claim challenged:* Stable semantic ownership should normally become visible in
package paths.

*Evidence:* Shared primitives (`physical_labels`, `_cell_primitives`, axis
mapping) legitimately serve several consumers. Final cleanup has multiple
feature producers and an orchestrator-owned execution seam. Schema maintenance
must know feature-owned reference paths. Workbook View accepts a controlled
`GroupedMatrix` without owning Grouped XRef. FK validation belongs semantically
with FK behavior but is also part of the shared validation execution/reporting
surface. Small public operations such as extract or pivot do not justify a
package merely to display ownership. Existing architecture guards protect
package-root APIs for only two deliberately split families, not for every
Domain capability.

*Assessment/inference:* Discoverable paths help cohesive multi-module
capabilities, but a path can expose only one primary nesting. Forcing every
semantic relationship into nesting either duplicates shared code, creates
artificial packages, or misstates cross-cutting ownership.

*Confidence:* High.

*Architectural consequence:* Package movement could create cycles, barrels,
or “shared” dumping grounds while making the dependency graph less truthful.

*Required correction:* Change “normally visible” to a conditional rule:
package paths should reveal a cohesive implementation owner when that owner is
stable and large enough to benefit; relationship contracts and registries must
carry cross-owner edges that paths cannot express.

*DMC acceptance:* Package guidance may remain advisory; no package consequence
should be an acceptance prerequisite.

=== DSO-REV-009 -- The missing first-class dimension is ownership of interaction contracts

*Classification:* IMPORTANT CORRECTION.

*Claim challenged:* Assigning every module or capability an owner is sufficient
orientation for later hardening.

*Evidence:* The hardest current contracts live between owners:

* feature transforms produce cleanup commands while final cleanup executes and
  consumes them at an orchestrator-owned seam;
* Workbook View maps visible sheet identity before/after derived cleanup, and
  the ordering is a public contract;
* schema maintenance updates references owned by other capabilities while
  `meta_registry.yaml` remains the meaning/producer/consumer authority;
* Compact owns order and temporary-state handling while dependencies retain
  matrix and cell semantics;
* writer reports are produced by two publishers and consumed by Manifest; and
* FK/lookup provenance is consumed by render passes, cleanup, and validators.

The assessment lists many of these edges, but its DMC recommendations focus on
classifying nodes. The DMC design asks for state and consumers but does not make
the handoff contract itself carry an explicit steward, change gate, failure/
atomicity expectation, and compatibility obligation.

*Assessment/inference:* Many future regressions will arise at owner boundaries,
not inside an owner. A one-owner-per-module census cannot protect these seams.
The useful addition is not another ownership category; it is a relationship
record inside each pilot.

*Confidence:* High.

*Architectural consequence:* A local refactor can leave both adjacent owners
internally clean while breaking ordering, consumption, authority, or failure
atomicity between them.

*Required correction:* Add a scoped pilot requirement to identify material
handoffs: producer, consumer/executor, authoritative state, ordering,
failure/atomicity, compatibility surface, and the party responsible for
coordinated change. Also require the pilot to state which directly importable
Python surfaces are supported versus merely reachable; current public-step
registries do not answer that question.

*DMC acceptance:* A lightweight interaction-contract rule is more important
than a global owner taxonomy and should be included before the first pilot.

== 4. Taxonomy review

[cols="3,3,6",options="header"]
|===
| Proposed term | Verdict | Review

| Durable semantic ownership unit
| Useful only as informal umbrella; terminology should change or remain
  non-normative
| It correctly avoids forcing everything into an inverse-shaped family, but
  its inclusion criterion is circular and it adds little beyond “maintainer
  scope” or “Domain capability/change surface”. Do not register or package by
  this term.

| Transformation family
| Well supported but not universal
| XRef, discriminator split/merge, Sparse Defaults, and FK-helper lifecycle
  demonstrate coherent multi-operation lifecycles. The existing Domain
  Contracts Registry already uses this term, although incompletely.

| Capability variant or subcapability
| Hypothesis only
| The assessment offers only Grouped XRef as a possible example and then leaves
  it unresolved. No DMC rule needs this category before a pilot demonstrates a
  decision it changes.

| Composite capability
| Well supported as a dependency relationship
| Compact and Grouped XRef are independent examples with registered public
  composite steps. A composite may own a public contract, but “composes” should
  be recorded as an edge rather than treated as an exclusive owner kind. Flat
  axis projection is not a third example.

| Shared semantic primitive
| Useful, but not an ownership-unit kind
| Physical-label validation, bounded cell equality, where predicates, and axis
  mapping provide multiple examples. The operational question is who stewards
  the primitive and which consumers must coordinate, not which taxonomy box it
  occupies.

| Generic Domain operation
| Unnecessary/redundant
| Extract, join, and pivot are public operations with different semantics.
  “Generic, lossy, little lifecycle” does not produce a shared compatibility or
  maintenance owner.

| Cross-cutting Domain service or protocol
| Useful description of reach; terminology should not imply one owner kind
| Trusted Ingress, final cleanup, schema maintenance, and Workbook View provide
  independent examples. Their authority and execution seams differ too much
  for the category alone to guide maintenance.

| Domain vocabulary/value surface
| Useful asset relation, not a unit kind
| Scalar grammar, findings, column roles, physical labels, and `GroupedMatrix`
  have different scopes and owners. Record vocabulary stewardship and
  consumers directly.

| Core substrate
| Real architectural layer role, but outside a Domain ownership taxonomy
| `ExactTable`, formula intent, and header-grid mechanics demonstrate the role.
  Placement remains governed by the layer model and dependency direction.

| Capability cluster
| Unnecessary as a DMC category
| The assessment itself says it is non-owning. It may be a navigation heading,
  but it must not enter ownership records or acceptance criteria.

| Historical sediment or ambiguous
| Useful status, not a category
| This is a confidence/disposition field. It should trigger bounded evidence
  work only when touched, not count as a durable owner.

| Boundary-adjacent mixed responsibility
| Useful review finding, not a category
| It identifies likely separation work in writers and overrides but deliberately
  does not state the final owner.

| Configuration/policy production
| Missing role, already modeled elsewhere
| The pipeline registry and authoritative layer documentation explicitly
  distinguish configuration/policy producers from operation-time consumers.
  This should be a relationship/lifecycle role, not an eleventh owner kind.

| Interaction-contract stewardship
| Missing dimension
| Producer/consumer seams, ordering, authority, atomicity, and compatibility
  need an explicit steward in scoped reviews. This is an edge dimension, not a
  replacement taxonomy.
|===

== 6. Domain/Core review

The assessment correctly falsifies “purity alone decides Core”. It does not
establish a sufficient replacement.

Current maintained authority says:

* Domain owns business rules, transformation semantics, validation, and
  semantic metadata; and
* Core is a dependency-leaf of stateless utilities used by inner and outer
  layers.

That authority explicitly knows that `core.fk` is FK-specific. The assessment's
semantic-strength rule therefore proposes a different architecture. The current
tree shows why both dimensions are necessary:

* `core.fk` has feature vocabulary but keeps lower-level DataFrame mechanics
  below Domain policy/provenance;
* `core.formulas`, `ExactTable`, and `header_grid` have spreadsheet-relevant
  meaning but must cross Domain/render/backend boundaries without inward
  dependencies;
* `_cell_primitives`, `_where_predicates`, and physical labels are pure but
  encode local Domain admission/equality decisions;
* writers and override loading live in Domain while performing filesystem work,
  breaking the maintained “Domain must not know persistence details” statement;
  and
* `core.refs` and its layer-document description disagree, showing sediment can
  invalidate either a semantic or a structural reading.

The usable review question is multi-part: what semantic decision is made, which
layers need the value/mechanism, what dependency direction is legal, who has
authority, what side effects occur, and what compatibility surface exists?
Physical placement and semantic stewardship may differ. The assessment should
recommend bounded review of disagreements, not promote a new universal
placement test through the DMC.

== 7. Package-topology review

Visible ownership in paths is beneficial when a cohesive capability has enough
implementation surface to need navigation and encapsulation. XRef,
discriminator split, FK helpers, and schema maintenance demonstrate that case.

It is not a normal consequence for every semantic scope:

* extract, pivot, Workbook View, and final cleanup are coherent as single
  modules;
* shared primitives cannot be nested under every consumer;
* validators may be semantically local to a capability while sharing finding
  and severity execution;
* schema maintenance intentionally depends on declarations from multiple
  feature owners;
* a composite must depend on public dependency surfaces, but need not force all
  dependencies beneath one package; and
* filesystem writers share boundary mechanics without sharing output grammar.

The existing architecture guards correctly demonstrate a selective model: only
deliberately split packages get package-root API and no-private-cross-family
guards. Extending those guards when a new package is deliberately created is
sound. Creating packages so that the guards have something to protect is not.

The DMC should therefore say that topology must not contradict established
ownership and should expose a cohesive public implementation boundary when
useful. It should not promise that all semantic ownership is visible from the
directory tree.

== 8. Test-ownership and documentation-output review

=== Test ownership

A durable semantic ownership view can help answer impact questions that an FTR
marker cannot. FTR markers record historical work provenance. A test such as a
cleanup roundtrip may remain relevant after its originating FTR is archived.

The assessment nevertheless overstates the immediate need for a new ownership
dimension:

* current test topology is explicitly path-first; markers are secondary
  execution axes;
* Domain unit tests already usually sit beside their module/capability area;
* integration tests exercise contracts among several capabilities;
* roundtrip tests deliberately protect system invariants independently of
  which step implements them;
* architecture guards protect dependency or registry seams rather than one
  capability; and
* composite tests can be owned by the composite while also detecting dependency
  regressions.

One mandatory owner marker per test would be false precision. A many-to-many
owner annotation would add maintenance cost and duplicate paths, FTR markers,
and registries. The DMC should require each pilot to identify the tests that
protect its semantics and the cross-owner tests it must not break. It should
not require a new global marker, directory redesign, or complete ownership map
before acceptance.

=== User/LLM-facing references

Reference readability is a sensible completion property for supported public
capabilities. It does not imply one reference document per ownership unit.

A public pipeline capability or supported Python API needs discoverable current
purpose, configuration, invariants, lifecycle, and composition constraints in
the appropriate Functional/User/Technical surfaces. An internal shared
primitive may need only code-level and maintainer documentation. A
cross-cutting seam may need one lifecycle/interaction contract rather than one
document for every participant. Historical sediment needs a disposition, not a
public reference.

The DMC should require that a pilot updates the canonical documentation owned
by its affected supported surfaces and leaves no semantic meaning trapped in
an FTR ID. It should not prescribe one template or one document per provisional
owner.

== 10. Sequencing review

The assessment's sequence

[source,text]
----
DMC
-> lightweight whole-Domain capability census
-> pilot Cycle 0
-> family/capability hardening
----

still places an untested global taxonomy before the pilot. Completing a full
census before DMC acceptance is worse: it turns the DMC stage into the global
semantic normalization the roadmap and Semantic Model reject. Starting a pilot
with no global orientation is also unsafe because cross-cutting cleanup,
metadata, Workbook View, ingress, and output seams are easy to miss.

The smallest safe sequence is:

[source,text]
----
1. Correct and accept a bounded, scope-neutral DMC
   - semantic-first scope declaration
   - compatibility/state/consumer evidence
   - dependency and interaction-contract edges
   - no mandatory ownership taxonomy

2. Build a minimal orientation from maintained surfaces
   - current public pipeline steps and inverse/composite facts
   - non-step services: ingress, schema maintenance, final cleanup, Workbook View
   - relevant meta producer/consumer roots
   - explicit warning that the Domain Contracts Registry is incomplete

3. Run the FK/lookup pilot Cycle 0
   - test whether one family, two capabilities, primitive+consumers,
     or a non-owning cluster actually changes maintenance decisions
   - include derived cleanup and Workbook View ordering as interaction seams

4. Harden only the accepted pilot scope

5. Accrete any useful ownership mapping through later pilots
   - add a global census only if repeated pilot evidence proves it necessary
----

This sequence prevents a local refactor from assuming package or metadata
adjacency is ownership, while avoiding another Phase-E-scale analysis. The
pilot validates the vocabulary; the vocabulary does not pre-validate itself by
being applied to the whole repository.

== 11. Missed counterexamples / missing dimensions

This section is mandatory because several important counterexamples were not
carried into the assessment's conclusions.

=== Existing Domain Contracts Registry

The largest omission is the checked `registries/domain_contracts/` model. It
already has family, type, wrapper, configuration, infrastructure, maintenance,
carrier, exposure, inverse, source-status, implementation-link, and lifecycle
axes. Its poor current coverage and candidate sediment support the assessment's
skepticism, but also prove that adding another vocabulary without mapping is a
known failure mode.

=== Configuration production is a recurring role outside inverse families

`configure_fk_helpers`, `infer_fk_relations`, and
`configure_lookup_helpers` demonstrate a stable producer/consumer split that
the authoritative layer document already names. `bootstrap_meta`, Workbook
View configuration, and pipeline cleanup declarations add non-XRef examples.
This is better modeled as a lifecycle/authority role than as a new owner kind.

=== Validation supports both unity and separation

The assessment uses validation mainly to disprove package ownership. The
maintained Functional Model supplies the opposite counterexample to
over-fragmentation: reference and graph rules share one validation purpose,
and graph validation is explicitly a specialization unless a future graph
model requires more. Ownership cannot be inferred merely from distinct rule
schemas.

=== Resource authority cuts across semantic publishers

`apply_overrides` and the three writer/manifest steps are grouped by the
Technical Model for resource authorization, while only the latter three share
output roots and only Manifest has checksum-read authority. This is a
cross-cutting security relationship, not semantic ownership or a new Egress
family.

=== Functional documentation clusters can cross owners

The current “Derived Frame Views” chapter intentionally covers join and
discriminator split. One is a one-way join view; the other has an inverse and
owned metadata. This is direct non-XRef evidence that a user/problem-space
chapter is not a family map.

=== A controlled carrier can cross an owner boundary

Workbook View accepts and routes `GroupedMatrix` without owning Grouped XRef.
Core `ExactTable` crosses parse/render/Domain boundaries without owning grouped
reconstruction. Carrier acceptance, semantic creation authority, and
transformation ownership are separate.

=== Failure and atomicity belong to interaction contracts

Schema maintenance is transactional on blocked references; axis projection and
Grouped XRef use build-then-publish behavior; final cleanup has explicit command
conflicts; Manifest may read/checksum before publication. The DMC completion
checklist does not consistently require failure atomicity or partial-publication
behavior. This should be asked when a change crosses a handoff or mutates
shared Frames/meta, without becoming a universal section for pure functions.

=== Supported Python API status remains unresolved

The pipeline registry defines supported YAML steps, and package guards protect
some package-root imports. An empty `domain/__init__.py` does not define a
general Python API policy. A compatibility inventory that lists every
importable function but never states which are supported will preserve
sediment or authorize accidental breakage. Each pilot must make this surface
explicit.

== 13. Final recommendation

The assessment is *not yet good enough to serve as the authoritative evidence
base for DMC revision*. It is good enough to contribute several corrected
findings: broaden maintainer procedure beyond inverse-shaped families; reject
package, inverse, metadata, and reuse as sufficient ownership evidence; preserve
composite/dependency boundaries; and keep FK/lookup consolidation open for a
pilot.

Before DMC revision:

. incorporate the required corrections above, especially the Domain Contracts
  Registry/Review 005 evidence and the roadmap-scope correction;
. reduce the DMC acceptance gate to scope-neutral review rules plus explicit
  interaction/dependency seams; and
. prepare only the minimal global orientation needed to keep the first pilot
  from missing established cross-cutting contracts.

The following should deliberately remain unresolved until bounded pilot or
separate architecture work: FK/lookup higher-level ownership, Legend Blocks
ownership, derived-column protocol generalization, exact validation
sub-boundaries, output projection/publication separation, individual Core
placement changes, and all package moves.

The surviving conclusion is modest but durable: semantic ownership must be
argued from user meaning, state, authority, compatibility, and handoff contracts
before topology changes. The assessment should stop there instead of turning
its exploratory labels into architecture by repetition.
