== 1. Executive conclusion

The repository already has a checked Domain Contracts Registry under
`registries/domain_contracts/canonical/`, including
`transformation_families.json`, `transformation_types.json`, and
`transformations.json`. It is therefore incorrect to say that no canonical
Domain family taxonomy exists. The registry is deliberately small,
incomplete, and candidate-heavy; it contains intended and future rows as well
as observed implementation facts. It is not a complete authoritative
whole-Domain semantic ownership map, and its canonical directory status does
not make its candidate terminology authoritative over runtime semantics.

Review 005 is decisive context. It found parallel vocabularies and duplicated
contract facts, warned against designing another universal ontology, and then
hardened a narrow code-trace -> declaration -> guard loop. Its closure retained
runtime behavior as authority, joined schema-maintenance behavior to the
metadata registry rather than mirroring metadata ownership, and deliberately
paused further registry expansion. This assessment must not create a parallel
ownership registry or ontology.

The central surviving finding is pragmatic: semantic ownership must be
understood before topology changes. A Domain family is primarily a locality of
reasoning and comprehension boundary for maintainers and users -- a way to
divide and conquer the Domain. A useful boundary has:

* strong internal semantic and metadata coupling;
* substantial family-internal state communication that can be understood
  locally; and
* few, narrow, explicit, understandable external relationships.

The goal is not zero coupling. Cross-family dependencies are normal. The
strongest historical motivation is uncontrolled `_meta` coupling: genuinely
cross-family or Domain-wide metadata communication should be comparatively
small, explicit, and contract-backed. Independent usability and frequent
co-use are weak family criteria compared with locality of semantic and metadata
reasoning.

Family ownership should become clear even when another reasonable architecture
could have drawn the line differently. The partition is a pragmatic model, not
a mathematically unique decomposition. Contingent placement is acceptable;
ongoing ambiguity about who owns a type, path, policy, or change surface is not.

The Domain also contains bounded changes that are not inverse-shaped families:
configuration/state producers, validation, shared primitives, public
composites, schema maintenance, Trusted Ingress, final cleanup, Workbook View,
and output-side responsibilities. The DMC should work for a bounded Domain
scope, family, capability, or change surface without requiring a new universal
owner kind such as “durable semantic ownership unit.”

The other major finding is that important architecture lives between owners.
Material interaction contracts must identify producer, consumer/executor,
authoritative state, ordering, failure/atomicity, compatibility expectations,
and coordinated-change responsibility. Assigning labels to nodes is not a
substitute for understanding those handoffs.

No whole-Domain taxonomy or module census is required before the first pilot.
A small orientation from already maintained surfaces may help pilot selection;
detailed disposition belongs inside a bounded Cycle 0.

== 3. Analytical dimensions and working vocabulary

This section supplies decision aids, not a closed ontology. The dimensions
overlap and must not be collapsed into one classification column.

[cols="2,4,5",options="header"]
|===
| Dimension | Question | Examples / use

| Semantic ownership and scope
| Who owns this capability, state, policy, invariant, or change surface?
| Family, bounded capability, shared primitive steward, cross-cutting service,
  or a pilot-local change scope. The answer should make coordinated decisions
  and local comprehension possible.

| Role or kind
| What does the element do inside or around an owner?
| Projection, reconstruction, validation, configuration, helper, policy,
  model, extraction/derivation, or composition. This is an open list; roles can
  coexist.

| Relationship or dependency
| How does one owner/scope depend on another?
| Composes, consumes, provides a primitive, reads or produces metadata,
  validates, reconstructs, executes cleanup, updates references, renders, or
  publishes.

| Layer and placement
| Where can the mechanism live while preserving authority and inward
  dependencies?
| Domain, Core, Pipeline, Render IR, adapter/backend, or a boundary between
  them. Placement is not identical to semantic stewardship.

| Exposure and compatibility
| Which surfaces carry user or caller expectations?
| Registered YAML step, supported Python API, internal import, metadata shape,
  persisted state, carrier output, or consumer configuration.

| Lifecycle and authority
| Which state is authoritative, derived, temporary, persisted, reconstructed,
  consumed, or discarded, and in what order?
| Intent versus Resolution, provenance, precedence, cleanup, replay,
  atomicity, and coordinated-change responsibility.

| Confidence and status
| What is established, provisional, ambiguous, or historical?
| Current evidence supports, maintainer working model, Cycle-0 question,
  sediment, or compatibility candidate. Status is not an owner kind.
|===

Properties such as composite, shared primitive, public/internal, cross-layer,
confidence, or sediment are not mutually exclusive alternatives to family
ownership. Likewise, package, shared inverse, metadata root, output shape, or
documentation cluster is evidence rather than a classification proof.

=== Working concept: Domain transformation

For current Domain-maintenance discussion, a Domain transformation is a
bounded Domain step representable approximately as:

[source,text]
----
Frames -> Frames
----

`Frames` includes the controlled Domain state and metadata used by the
framework. Transformation is broader than projection. The whole Domain also
contains helpers, primitives, types, services, policies, and boundaries that
should not be forced into this term. This working concept does not globally
rename repository terminology.

=== Working concept: Projection

“Projection” is not used here in the strict mathematical sense. The maintainer
working concept is:

[quote]
____
A Projection is a Domain transformation that derives a user-oriented or
fachlich suitable editing/presentation surface from canonical state and
defines the authority, precedence, conflict, and reconstruction semantics by
which edits are mapped back toward canonical state.
____

A projection need not be bijective. It may introduce intentional redundancy;
reconstruction may be lossy; explicit precedence may resolve conflicting
redundant values; a hard overwrite may be correct when authority is clear;
policy/configuration may select conflict behavior; and controlled metadata may
be required for reconstruction. This creates a different maintainer contract
from a deliberately lossy extraction or configuration/state step. XRef-like
matrix surfaces and FK helper editing surfaces motivate the distinction.

This is clarified working vocabulary and DMC input, not promotion into the
canonical Functional Model by this assessment.

=== Domain validation and Workbook Editing Constraints

Two responsibilities must not be conflated because spreadsheet software calls
both “validation”:

* *Domain validation* asks whether existing Domain state satisfies a Domain
  invariant, such as dangling-reference, relational, or XRef validity.
* A *Workbook Editing Constraint* describes what values a spreadsheet editing
  surface should allow, suggest, or expose, such as an Excel “Data Validation”
  dropdown.

The second is declarative editing/presentation intent, not a canonical-data
validity check. A family may own Domain validation semantics while using shared
validation mechanics. Legend Blocks may contribute allowed-value vocabulary
without becoming Cell-Codec-owned. “Workbook Editing Constraint” is only a
useful descriptive phrase here; no global rename is proposed.

=== Structured hierarchy versus YAML publication

Historical naming such as “create YAML format” and the current
`structured_yaml` label can blur two responsibilities:

[source,text]
----
tabular / relational state
  -> hierarchical object-like structured projection
  -> YAML bytes / file publication
----

The first may be a semantic projection for configuration-shaped documents
(for example Kubernetes/GitLab-style structures); the second is carrier
serialization/publication. Carrier-oriented names are therefore unreliable
ownership evidence. `FTR-YAML-SURFACE-NORMALIZATION-P5` should later consume
the accepted boundary rather than define it. This assessment does not settle
package placement or design Egress.

== 6. Family, inverse, primitive, metadata, and composition reasoning

Family partitioning is a pragmatic architecture model. It should be good
enough to make ownership clear and reasoning local, not produce a mathematically
unique decomposition.

Useful questions include:

* Can a maintainer explain and change the capability mostly within one bounded
  area without repeatedly resolving distant semantic or metadata references?
* Do operations share one user/domain problem, authority, invariants, state,
  lifecycle, and compatibility decisions?
* Are internal metadata exchanges substantial while external exchanges are
  comparatively narrow and explicit?
* Would separating independently usable parts create excessive semantic/meta
  far references, or would combining frequently co-used parts hide a narrow,
  understandable dependency?

These are judgment prompts, not a scoring formula or global metric.

None of the following alone proves same-family ownership:

* shared implementation, inverse, helper, or primitive;
* shared metadata namespace or common state container;
* same output shape or common documentation cluster;
* common package or pipeline category;
* composition or one operation calling another;
* purity, statelessness, or absence of metadata.

A shared inverse is stronger evidence when it reconstructs state created under
one owned identity/provenance contract and all producers intentionally share
that lifecycle. It is weaker when producers retain different authority or
provenance, the inverse is generic, or a composite delegates reconstruction to
another owner.

A shared primitive can remain independent of its consumers when it has a
narrow stable contract and does not own their public lifecycle. Its steward and
coordinated consumers must still be clear.

Shared metadata placement is evidence only. Common-family ownership requires
aligned producer identity, staleness rules, reconstruction authority,
precedence/conflict behavior, cleanup, and compatibility. `_meta.derived` is a
channel, not proof that FK and lookup semantics are one family.

A composite owns irreducible composition: order, dependency configuration,
temporary artifacts, trace policy, public output identity, and cross-operation
failure/reconstruction behavior. Its dependencies retain their primitive
semantics. Persisted composite state should be minimal and truthful: operative
intent or explicitly non-authoritative diagnostics, never leaked temporary
implementation state presented as inverse authority.

== 8. Domain versus Core

The original assessment's proposed replacement rule was too strong. Current
maintained authority describes Domain as owning business rules,
transformation semantics, validation, and semantic metadata, and Core as a
leaf of stateless utilities used across layers. It explicitly places FK
wire-format/helper mechanics in `core.fk`. This assessment cannot replace that
architecture with a single “semantic means Domain” test.

Purity/statelessness and semantic/non-semantic are each insufficient. A later
local review should consider together:

* semantic decision and feature authority;
* legal inward dependency direction;
* reuse and cross-layer carrier/mechanism role;
* side effects and runtime ownership;
* wire-format or compatibility stability; and
* risk of duplication or dependency cycles.

Two useful hypotheses, not canonical rules, are:

* *Complexity isolation:* Core may host a small, well-bounded mechanism that
  keeps low-level processing complexity out of Domain algorithms.
* *Cross-layer neutrality:* a mechanism or type needed safely across several
  layers without owning feature policy may belong in Core.

Negative evidence against Core includes feature authority,
projection/reconstruction semantics, Domain metadata lifecycle, and feature
policy. Physical placement and semantic stewardship may differ.

`core.fk`, `core.indexing`, and `core.refs` remain local placement-review
candidates. `ExactTable`, `HeaderGrid`, formula intent, scalar grammar, and
other cross-layer carriers illustrate why semantic relevance alone is not a
move rule. No global placement decision, Core rename, or “Ports” layer is
proposed; the Ports analogy is imprecise because much of Core is substrate and
mechanism rather than ports/APIs.

== 9. Package-topology implications

The maintainer preference for a cohesive multi-module owner is:

[source,text]
----
family first
  -> kind / responsibility inside the family
----

For example, an FK-helper family might keep projection, reconstruction,
validation, model, and policy responsibilities near each other. This is not a
mandatory file skeleton. A small kind can remain `validation.py`; only if it
grows and a semantic seam warrants it might it become `validation/` with
focused modules. File naming can express kind until subdivision improves
comprehension.

The corrected principle is:

[quote]
____
Package topology should support locality of reasoning and should not
contradict established semantic ownership. A cohesive family large enough to
benefit from internal structure should normally have a recognizable
implementation/package boundary. Cross-owner relationships must remain
explicit rather than being hidden by nesting.
____

Small single-module operations, shared primitives, cross-cutting services, and
interaction contracts cannot always be represented by one nesting hierarchy.
Topology is for navigation and locality, not symmetry. Package facades and
private-import discipline should be preserved when a deliberate package
boundary exists; packages should not be created merely to satisfy a visual
template or guard pattern.

== 10. Test-ownership implications

Existing FTR markers remain valuable because they answer the historical
question: “Why does this test exist?” They should not be replaced by a new
family marker.

Test organization is less important than source comprehension. Tests primarily
stabilize established contracts against regression, and many important tests
belong to interactions or system invariants rather than one family. A bounded
Cycle 0 should identify:

* tests protecting the pilot's semantics and compatibility surface;
* managed-entry tests where Trusted Ingress or controlled state matters;
* inverse/roundtrip tests where reconstruction or cleanup matters; and
* cross-owner tests protecting ordering, metadata, atomicity, rendering, or
  consumer handoffs.

No global test-ownership census, directory redesign, or new marker is required.
Only repeated practical difficulty should justify a later mechanism.

== 11. Human- and LLM-facing reference implications

Users should be able to understand a supported public capability without
reconstructing it from unrelated sources. The project also intends to support
LLM-oriented context comparable in purpose to an `llms.txt` surface. That does
not require one manually maintained reference per provisional owner or a
second semantic authority.

Canonical information may remain distributed by ownership:

[source,text]
----
Functional Model  -> semantic behavior and user problem
Semantic Model    -> vocabulary, identities, invariants
Technical Model   -> lifecycle, persistence, boundaries
User Guide        -> usage, configuration, examples
Registries        -> machine-readable facts where justified

canonical sources
  -> deterministic aggregation / projection
  -> coherent human- and LLM-facing reference
----

A future command such as `make llm-context` could aggregate those sources,
potentially using templates and structured registry data. JSON should own only
facts that benefit from machine-readable canonical representation; narrative
semantics should not be forced into JSON for generation. Generated reference
output must not become a second authority.

A useful hardening completion property is:

[quote]
____
The semantics of a supported public family or capability have clear canonical
owners and are structured well enough that a coherent human- and LLM-facing
reference can be assembled without inventing missing semantics or creating
another source of truth.
____

This assessment neither designs nor implements the generator.

== 12. Bounded DMC implications

The DMC should be broadened only enough to govern bounded Domain changes that
are not classic inverse-shaped families. It should not classify the whole
Domain before acceptance.

=== Likely DMC requirements

* Establish the bounded semantic scope and current authority before topology.
* State the family locality/comprehension purpose where a family is the useful
  boundary: strong internal coupling, narrow explicit external relations, and
  maximized metadata locality.
* Keep family ownership separate from role/kind, relationship, layer,
  exposure, lifecycle, and confidence.
* Treat shared inverse, metadata, configuration, implementation, primitive,
  and composition as evidence rather than ownership proofs.
* Identify material interaction contracts: producer, consumer/executor,
  authoritative state, ordering, failure/atomicity, compatibility, and
  coordinated-change responsibility.
* For projections, establish reconstruction authority, precedence, conflict
  behavior, required metadata, cleanup, and expected loss/redundancy.
* Preserve relevant historical invariants -- including inward dependencies,
  Intent/Resolution separation, minimal truthful composite state, package
  facades, replay safety, and copy/failure atomicity -- without reopening all
  old findings.
* Make explicit compatibility and migration decisions using current maintained
  and external consumers where the affected surface requires it.
* Avoid competing contract authorities; ask which existing declaration owns a
  fact, whether machine-readable structure is needed, and whether mirrored or
  obsolete surfaces can be removed.
* Apply proportional package guidance and identify supported public Python
  surfaces separately from merely importable ones.
* Leave canonical documentation structured enough for deterministic human/LLM
  reference aggregation.

=== Compatibility working principle

Existing behavior is evidence, not an automatic compatibility obligation. A
hardening change may retire or alter behavior when architectural benefit
justifies compatibility cost. The decision should consider actual maintained
and external consumers, public-surface maturity and stability expectations,
migration effort and guidance, whether migration can be mechanical or
AI-friendly, and the architectural benefit.

Breaking changes may be reasonable before or after 1.0. Migration friction and
compatibility expectation matter more than whether syntax breaks or a version
threshold has been crossed. In the current project state, justified breaking
cleanup is intentionally acceptable because the public surface is not treated
as fully stable and external adoption appears very limited. That is present
evidence, not a timeless rule.

Every historical variant should therefore receive a local
preserve/simplify/replace/remove decision. Cell Codec's older code-row mode is
one example; existing behavior should not be fossilized automatically.

=== Useful pilot-local evidence

* complete inventory of the selected scope's modules, operations, state,
  supported APIs, configuration, consumers, tests, and material handoffs;
* only the relevant historical `HRS-*` signals and original rationale;
* current source, registry, documentation, tests, and consumer evidence for
  decisions that depend on them;
* confidence and alternative interpretations for unresolved boundaries; and
* local package or registry consequences after semantic decisions.

=== Later local architecture questions

* exact FK Helper / Lookup Enrichment boundary and derived-cleanup owner;
* Legend ownership and cross-consumer policy;
* individual Domain/Core borderline placements;
* validation sub-boundaries and Workbook Editing Constraint terminology;
* output projection/publication separation;
* exact package moves and supported Python facades;
* which historical modes survive a hardened contract.

=== Explicitly not DMC acceptance requirements

* a whole-Domain module or capability census;
* a new ownership registry, universal taxonomy, or complete Domain Contracts
  Registry population;
* a global Domain/Core placement decision;
* a global test-ownership marker or test-suite redesign;
* exact package moves or a mandatory skeleton;
* Egress design or implementation;
* complete historical-finding revalidation;
* a manually maintained reference document per provisional scope; or
* consumer migrations before a bounded change has selected a surface.

=== Egress context, not design

The only retained output-boundary context is:

* a feature/family owns semantic projection, reconstruction, provenance,
  authority, and cleanup;
* family code should not learn adapter identity merely to enforce sink
  compatibility;
* framework-owned output logic may later validate admissible Domain exit state
  and sink capability; and
* mixed output modules should be separated along evidenced semantic/publication
  boundaries, not moved wholesale into a hypothetical `egress` package.

A beyond-MVP idea is that future Egress could establish integrity evidence for
framework-controlled carrier state and Trusted Ingress could verify it on
re-entry. This might protect identity/meta surfaces from forbidden edits. It is
not a DMC requirement or an Egress design.

== 13. Counterexamples and unresolved questions

=== Counterexamples retained

* Trusted Ingress and schema maintenance are important Domain scopes without a
  public inverse transformation shape.
* Final cleanup is a producer/executor/orchestrator interaction, not one
  producer's family.
* Flat XRef Axis Projection is a public inverse pair around XRef semantics but
  is not a composite wrapping XRef.
* Cell Codec and XRef share Compact as a consumer but remain semantically
  independent.
* Legend Blocks may be consumed by Cell Codec and participate in Workbook
  Editing Constraints while remaining independently used.
* Sparse Defaults reads XRef metadata without becoming XRef-owned.
* Axis Mapping has no public pipeline workflow yet has real shared semantic
  invariants.
* Validation package adjacency does not merge Domain validity, family-local
  rules, and editing constraints.
* Extract, join, and pivot remain legitimate Domain changes without needing a
  new generic-operation owner class.
* Resource/path/security mechanics shared by publishers and Manifest do not
  make one semantic owner.
* `core.fk` shows that feature-relevant meaning and Core placement cannot be
  decided by purity or semantics alone.
* Shared `_meta.derived` placement does not merge FK and lookup ownership.

=== Unresolved questions for bounded work

. What exact family or collaboration boundary best serves FK Helpers and
  Lookup Enrichment while minimizing semantic and metadata far references?
. Who owns Legend Blocks, and which validation/fallback policies should be
  shared versus consumer-specific?
. Does derived-column policy remain a coordinated cleanup consumer, or does
  later evidence justify broader lifecycle ownership?
. Are `core.fk`, `core.indexing`, and `core.refs` best retained as complexity
  isolation/cross-layer-neutral mechanisms or moved after local review?
. Where does tabular-to-hierarchical structured projection end and carrier
  serialization/publication begin?
. Which directly importable Domain functions are supported Python APIs rather
  than reachable implementation details?
. Is “Workbook Editing Constraint” useful enough for later canonical
  terminology, and which owner supplies its declarative intent?
. Should the clarified Projection working concept be promoted into canonical
  Functional/Semantic documentation, and with what exact vocabulary?
. Which Cell Codec historical modes still carry architectural or consumer
  value after hardening?
. Is Grouped XRef governed as an XRef subfamily/sibling capability while
  retaining its established composite runtime role?
. Are reference and graph validation one capability with specialization, or
  separate owners sharing mechanics?
. Which output-side responsibility and package placement follows from the
  eventual projection/publication boundary?

== 14. Recommended next lifecycle step

The corrected sequence is:

[source,text]
----
corrected, bounded DMC revision
  -> independent DMC review
  -> DMC correction and acceptance
  -> first bounded pilot Cycle 0
  -> harden only the accepted pilot scope
  -> let useful ownership vocabulary/evidence accrete from repeated pilots
----

A small global orientation may be assembled from already maintained pipeline,
metadata, Domain-contract, and architecture surfaces if needed for pilot
selection. It must be clearly incomplete and should not become another
registry, census, or ratification stage.

The first pilot's Cycle 0 should test the model against real semantics,
metadata locality, supported surfaces, consumers, tests, and cross-owner
handoffs. FK/lookup remains a strong question precisely because one-family and
collaborating-capability models are both plausible; the pilot should decide
which produces clearer ownership and more local reasoning rather than assume
the DMC design's earlier grouping.

The durable endpoint of this assessment is deliberately modest: enough
semantic clarity, locality, and explicit interaction-contract reasoning to
support disciplined family-by-family hardening, without turning exploratory
labels into architecture by repetition.
