=== 2. Shared Missing authority used correctly, grammar not broadened (VERIFIED)

The commit imports `is_missing_carrier` from `...core.scalar_values`. This is
the accepted shared predicate, already imported by a sibling in the same package
(`domain/validations/reference_validations.py`), so no new or unwanted
dependency direction is introduced. Empirical probe (project `.venv`,
pandas 3.0.2) confirms the accepted grammar and no widening:

[cols="2,1",options="header"]
|===
| value | is_missing_carrier

| `None`, `""`, `float('nan')`, `pd.NA`, `pd.NaT`, `numpy.datetime64('NaT')` | `True`
| `"nan"` (literal String) | `False`
| `"  "` (whitespace-only String) | `False`
| `True`, `numpy.bool_(True)` | `False`
| `[1, 2]` (non-scalar) | `False`
|===

The implementation recreates no local Missing ontology; it delegates to the one
predicate. Bounded dispatch means arrays/opaque objects never reach
`pandas.isna`.

=== 3. check_unresolvable_fks (VERIFIED, correct, in-scope)

`_norm` now maps any `is_missing_carrier` value to `None`, else `str(v).strip()`.
The unresolved set comprehension gained an explicit `not is_missing_carrier(v)`
guard *and* still tests `_norm(v) not in target_ids`
(`fk_helpers.py:229-232`).

* All accepted Missing source-FK carriers are ignored. `None`/float-NaN/`pd.NA`/
  `NaT` are removed by the pre-existing `fk_series.dropna()`; `""` -- the one
  carrier that survives `dropna()` -- is now excluded by the explicit
  `is_missing_carrier` guard. Baseline reported `""` as `unresolvable_fk`; the
  fix suppresses that false finding. Verified via the parametrized test and by
  logic.
* Literal String `"nan"` remains a non-missing, reported finding
  (`is_missing_carrier("nan") is False`; `_norm("nan") == "nan"` not in
  `{"1"}`). Confirmed by `test_literal_nan_string_remains_an_unresolvable_fk`
  and empirically.
* An ordinary non-missing unresolved FK remains a finding (pre-existing tests
  green).
* Resolution authority is unchanged: source FK is checked against
  `_norm_key`-normalized target ids; helper-cell text is never consulted here.

=== 4. check_helper_values (VERIFIED, correct, in-scope)

== Findings and dispositions

=== FINDING-1 -- Release-notes checkpoint unmet (bounded, non-code)

*Observation.* The commit changes user-visible FK-validation output --
previously-emitted false `unresolvable_fk` (blank/`""` source FK) and
`value_mismatch` (`pd.NA`/`NaT`/`""` source FK) findings are now correctly
suppressed -- but adds no release-note bullet and records no justification for
its absence. *Evidence.* The narrowing review of the assessment
(`..._assessment_2026-09-11_review_001.adoc`, "Release-notes checkpoint")
states explicitly: "When C3-S1 is implemented, correcting false FK-validation
findings on supported Missing carriers is a behavior change and the implementer
must add a release note (or record why none is needed)." `review_instructions.adoc`
("Release-notes checkpoint") makes the same requirement normative and directs
reviewers to record a finding when release notes are missing for a
release-relevant change. The active unreleased section
(`docs/release_notes/release_notes.adoc`, `== unknown -- planned`) is being
maintained mid-cycle and is the correct placement target. *Risk.* Blank/optional
FK columns are common; users previously saw spurious findings for them. Shipping
the corrected behavior without a note leaves a release-relevant behavior change
undocumented, and leaves the accepted review directive unsatisfied. *Recommended
action (do NOT perform under this read-only review).* Smallest correction: add
one bullet under the active `== unknown -- planned` section noting that FK
validation no longer emits false `unresolvable_fk` / `value_mismatch` findings
for supported Missing source-FK carriers (`None`, `""`, NaN, `pd.NA`, `NaT`)
while literal String `"nan"` is still reported; or record in the implementation
change why no note is needed. Do not broaden C3-S1 while doing so.
*Disposition.* Bounded correction required -- the sole reason the verdict is B
rather than A.

=== WATCH-1 -- Some unresolvable-FK test parameters exercise dropna, not the new guard

*Observation.* `test_ignores_supported_missing_source_fk_carriers` is
parametrized over `[None, "", nan, pd.NA, pd.NaT]`, but for
`check_unresolvable_fks` only `""` survives the pre-existing `dropna()` and thus
actually exercises the new `is_missing_carrier` guard; the other four pass on the
baseline too. *Evidence.* `dropna().unique()` removes `None`/NaN/`pd.NA`/`NaT`
before the comprehension runs. *Risk.* Low -- the `""` parameter is a genuine
regression guard (baseline emitted the false finding), and the same parameter
set is fully meaningful for `check_helper_values` (which has no `dropna()`, so
`pd.NA`/`NaT`/`""` all regression-guard there). The contract asserted ("every
accepted Missing carrier is ignored") is correct and worth stating explicitly.
*Recommended action.* None required; optionally document that the shared
parameter list intentionally over-covers `check_unresolvable_fks` for symmetry.
*Disposition.* Watch-only; not a defect.
