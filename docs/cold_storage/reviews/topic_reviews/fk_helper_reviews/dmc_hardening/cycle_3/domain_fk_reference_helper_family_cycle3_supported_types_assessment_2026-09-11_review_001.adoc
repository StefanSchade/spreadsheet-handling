== What was independently verified

=== The Missing contract is real, importable, and applies at this boundary (VERIFIED)

The assessment's "accepted shared predicate" is
`spreadsheet_handling.core.scalar_values.is_missing_carrier`
(`core/scalar_values.py:204`). Verified behavior:

* Recognizes `None`, `""`, float/NumPy NaN, `pd.NA`, `pd.NaT`,
  `numpy.datetime64('NaT')`.
* *Excludes* literal String `"nan"` -- string ancestry is tested before any
  `pandas.isna`, then only `value == ""` (`:267`). Confirmed empirically:
  `is_missing_carrier("nan") is False`.
* *Excludes* whitespace-only strings (`"  " == ""` is `False`), pandas/NumPy
  scalar booleans, `ndarray`/`Series`, and arbitrary objects -- these never
  reach `pandas.isna` (bounded `int`/`float`/`np.generic` dispatch, `:275`),
  so the predicate cannot widen the accepted carrier set or invoke a foreign
  `__array__`.
* `numpy.timedelta64` is explicitly excluded (`:271`).

The scalar language is closed to String/Boolean/Number/Missing/Date/DateTime,
and `internal_value_model.adoc:70-73` names exactly the same Missing carriers.
The assessment's "Authoritative value contracts" section is accurate, including
"classification does not normalize" and "literal `nan` remains String".

*Boundary applicability (rules out any "authority does not apply here"
outcome):* `is_missing_carrier` is already imported by a sibling in the very
same package -- `domain/validations/reference_validations.py` -- and by
`domain/finding_frame.py` and `domain/ingress/scalar_admission.py`.
`domain/validations/fk_helpers.py` already imports `...core.fk` and
`...core.indexing`. Importing `...core.scalar_values` introduces no new or
unwanted dependency direction.

=== check_unresolvable_fks -- only `""` currently produces a false finding (VERIFIED, IN SCOPE)

`check_unresolvable_fks` (`fk_helpers.py:196`) builds the unresolved set from
`fk_series.dropna().unique()` filtered by a local `_norm` (`:209`) that only
maps `None` and `float` NaN to `None`, otherwise `str(v).strip()`.

Empirically (pandas 3.0.2):

* `dropna()` already removes `None`, float NaN, `pd.NA`, and `NaT` before
  `_norm` runs, so those carriers already yield *no* finding.
* `""` survives `dropna()`; `_norm("") == ""`; unless the target frame happens
  to contain a `""` key, a blank FK is falsely reported as unresolvable.

So the *only* behavioral correction needed here is recognizing `""` as Missing.
`is_missing_carrier` does exactly that and nothing more. Resolution authority
(source FK checked against `_norm_key`-normalized target ids) is preserved; a
non-missing unresolved FK still produces a finding. The assessment's acceptance
criteria for this function are correct and achievable without touching
non-missing key comparison. *In scope, safe.*

=== check_helper_values -- missing source FKs are falsely compared (VERIFIED, IN SCOPE)

`check_helper_values` (`fk_helpers.py:131`) has *no* `dropna()`. Its local
`_norm` (`:144`) maps only `None`/float NaN to `None`; the loop skips a row only
when `_norm(fk_val) is None` (`:175`). Empirically `_norm(pd.NA) == "<NA>"`,
`_norm(NaT) == "NaT"`, `_norm("") == ""` -- none are `None`, so a `pd.NA`/`NaT`/
`""` source FK is *not* skipped and is compared against `target_map.get(...)`,
producing a false `value_mismatch`. Routing the skip decision through
`is_missing_carrier` fixes this while leaving the successful-target and
unresolved-helper paths untouched. *In scope, safe*, provided the change
touches only the missing-skip test and leaves the `str(...).strip()` comparison
of non-missing values intact (see WATCH-1).

=== check_duplicate_ids -- the "nan" filter is effectively dead; the function currently REPORTS missing ids as duplicates (VERIFIED -- central finding)

This is the decisive runtime fact and it is *under-stated* in the assessment.

`check_duplicate_ids` (`fk_helpers.py:250`) does
`ids = level0_series(df, id_field).astype("string")`, then
`counts = ids.value_counts(dropna=False)`, then keeps
`str(idx) for ... if cnt > 1 and str(idx) != "nan"` (`:270-272`).

Empirically (pandas 3.0.2), under the `"string"` dtype every missing carrier
(`None`, float NaN, `pd.NA`, `NaT`) becomes `pd.NA`, whose `str()` is `"<NA>"`,
*not* `"nan"`. Therefore:

[cols="2,3",options="header"]
|===
| id column (2 missing + 1 real) | current finding

| `[None, None, "a"]`      | duplicate_id `['<NA>']`
| `[nan, nan, "a"]`        | duplicate_id `['<NA>']`
| `[pd.NA, pd.NA, "a"]`    | duplicate_id `['<NA>']`
| `[NaT, NaT, "a"]`        | duplicate_id `['<NA>']`
| `["", "", "a"]`          | duplicate_id `['']`
| `["nan", "nan", "a"]`    | duplicate_id `[]`  (only the *literal* string is filtered)
|===

Consequences:

. The `str(idx) != "nan"` guard is essentially vestigial: under
  `astype("string")` a missing carrier is never rendered `"nan"`, so the guard
  only ever suppresses the literal String `"nan"` -- which the global contract
  says is *not* Missing and *should* count. The guard is thus both ineffective
  against real missing and, in the one case it fires, arguably wrong.
. Current behavior is that *multiple missing ids are reported as a duplicate
  finding*. Making the exclusion "missing-aware" via the shared predicate would
  change that to *not reported*. That is a genuine behavior change, not a
  cleanup.

The assessment's census (C3-FK-05) and Mismatch item 1 describe this only as an
"accidental `\"nan\"` string test" / an exclusion. That characterization
understates the runtime reality and is the one factual correction this review
records (see FINDING-2).

=== FK vs Lookup remain separate, correctly deferred (VERIFIED)

* FK map/validation stringify keys (`core/fk.py:_norm_id`,
  `fk_helpers.py:_norm_key`); `1` and `"1"` collide -- a real undocumented
  family narrowing, as the assessment states (C3-FK-03).
* Lookup `enrich_lookup.operation` delegates equality/coercion to pandas
  `merge`; Lookup `mismatch._norm` (`mismatch.py:247`) uses `pd.isna` (broader
  missing recognition than FK validation's `_norm`) *and* `str(...).strip()`.
  These are three different normalization regimes.

The assessment is correct that FK key equality/stringification and Lookup
pandas equality are separate unresolved Cycle-3 questions that C3-S1 must not
unify. Date/DateTime and resolved-Missing-target questions are correctly
deferred.

== Findings and dispositions

=== BLOCKER-1 -- Narrow C3-S1 to exclude check_duplicate_ids

*Observation.* C3-S1's "Likely files" authorizes changing the duplicate-ID
missing exclusion "where applicable." *Evidence.* Runtime evidence above shows
`check_duplicate_ids` currently reports missing ids as duplicates; making it
missing-aware is a behavior change, not a correction of a false finding.
*Risk.* That change silently decides the question the assessment itself lists as
UNCERTAIN -- "Are missing target-key values invalid identity, ignored rows, or
duplicate validation findings?" -- committing to the "ignored rows" reading of
target-key identity inside a validation-only slice, with no accepted authority
for it. The global Missing contract classifies the *value* as Missing; it does
not decide what a *uniqueness/identity* validation must *do* with a Missing id.
That is a family target-key policy decision, not a scalar-classification one.
*Recommended action.* Restrict C3-S1 to `check_unresolvable_fks` and
`check_helper_values`. Leave `check_duplicate_ids` exactly as-is.
*Disposition.* Blocker for the slice as literally scoped; trivially resolved by
narrowing (smallest correction, below).

=== FINDING-2 -- Correct the census description of the duplicate-ID filter

*Observation.* C3-FK-05 and Mismatch item 1 describe the `check_duplicate_ids`
guard as an accidental `"nan"` exclusion. *Evidence.* Under `astype("string")`
missing carriers render `"<NA>"`, so the guard is dead against real missing and
the function reports missing ids as duplicates. *Risk.* The imprecision makes a
behavior-changing edit look behavior-preserving -- exactly the trap BLOCKER-1
addresses. *Recommended action.* When the assessment or a follow-up next
touches this area, state that the guard is effectively vestigial and that
current behavior reports missing ids as duplicate findings. *Disposition.*
Before-implementation documentation correction; does not change the verdict
direction -- it *reinforces* exclusion. Do not edit the assessment under this
read-only review.

=== WATCH-1 -- Keep the missing-skip change off the trim/key-domain path

*Observation.* `is_missing_carrier` does not strip; current `_norm` does
(`str(v).strip()`). A whitespace-only FK value is non-missing under both
regimes, but is compared as its stripped form today. *Risk.* An implementer who
replaces the whole `_norm` with the predicate (rather than only its
missing-branch) could accidentally alter trim behavior for non-missing values --
introducing/removing an undocumented key-domain normalization the assessment
deliberately defers. *Recommended action.* Apply `is_missing_carrier` only to
the "is this Missing?" decision; retain existing `str(...).strip()` comparison
for non-missing values. C3-S1's own acceptance criterion ("no string
conversion / trim policy is newly introduced") already guards this -- honor it
literally. *Disposition.* Watch-only implementation guardrail.

=== NON-FINDINGS (assessment challenged and upheld)

* Treating `""` as Missing in `check_unresolvable_fks` *preserves* the rule
  that source FK + current target is resolution authority -- only a blank
  source FK stops being falsely flagged.
* The shared predicate does *not* accidentally change literal `"nan"`,
  whitespace strings, pandas scalar booleans, or arrays -- its dispatch is
  bounded (verified in source and empirically). Choosing this predicate is the
  reason the two in-scope changes are safe.
* FK key equality vs Lookup pandas equality are correctly kept as separate
  unresolved questions, not solved by C3-S1.
* Date/DateTime and resolved-Missing-target questions are correctly deferred.
* No material type surface was missed that changes the slice; the one
  under-statement (duplicate-ID) reinforces exclusion rather than adding scope.

== Smallest correction required (do NOT perform under this review)

In the assessment's "Exactly one smallest safe next implementation slice",
"Likely files" bullet, remove the parenthetical:

  "(and make the duplicate-ID missing exclusion use the same explicit rule
   where applicable)"

so C3-S1 touches only `check_unresolvable_fks` and `check_helper_values`. No
acceptance criterion needs to change (none references `check_duplicate_ids`).
Optionally, open a separate, later decision item for the `check_duplicate_ids`
target-key identity contract (invalid-identity vs ignored-row vs duplicate),
which must be decided before that function's missing handling changes.

With that single narrowing, C3-S1 is authorized for implementation.
