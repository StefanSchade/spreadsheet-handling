[[A]]
== A. Executive design decision

[.lead]
Close the confirmed FK/Lookup deletion-authority defect with the smallest
rule the accepted research evidences: *a cleanup executor may delete a
column identified through an FK-attributed name only when truthful,
currently-unrevoked, same-run transient FK materialization provenance names
that column.* Durable FK relation policy (`_meta.helper_policies.fk.relations`)
is retained as a *materialization* input (it still tells `add_fk_helpers`
what to build) but is permanently removed as a *deletion-candidate* input
from both `fk_helpers/drop.py` and `derived_column_policy.py`. No
value/formula equivalence check, no claimant/reliance vocabulary, and no new
durable state are introduced anywhere in this design.

Review 001 independently reproduced a fourth defect variant (Repro 4,
<<repro-recap>>) proving that "truthful when written" alone is *not*
sufficient: a same-run `enrich_lookup` call can physically replace an
already FK-enriched column while leaving FK's transient provenance entry for
that sheet untouched, so a cleanup executor deletes Lookup's fresh data on
FK's stale-but-was-truthful record. Closing this required an additional
correction (<<K>>): "currently present" transient provenance is no longer
trusted merely because nothing has since told the cleanup executor
otherwise; instead, the one identified way that provenance can go stale is
closed *at its source*, by making the transformation that can invalidate it
responsible for doing so at write time.

That correction, as first specified, was itself incomplete in two ways
independently reproduced by two further, independent adversarial reviews
(Review 001 Section 14, Review 002; see <<review-disposition-2>>): its
invalidation logic lived inside `enrich_lookup`'s provenance writer *behind*
a guard that a documented, supported call shape
(`enrich_lookup(..., helpers=None)`) never reaches, so that shape's own
decoupled rebind bypassed invalidation entirely (FIND-D9); and the identical
decoupled-rebind hazard is independently, supportedly reachable through
`apply_derived_column_policy`'s own `output` parameter — one of this
design's own two mandatory cleanup-executor sites, not a neighboring family —
which this design had previously, incorrectly, deferred as unevidenced
(FIND-D10). Both are now closed in this pass, with no change to the
underlying architectural approach: the same owner-local, write-time,
presence-only pattern, applied completely at its original site and
symmetrically at the one other site now shown to need it.

A fourth, still narrower gap was found by Review 001's own final targeted
closure pass (Section 15; see <<review-disposition-3>>): the second site's
FIND-D10 fix, as specified, keyed its lifecycle decision to the *raw*
`output` parameter, but `apply_derived_column_policy` physically publishes
using `output or source` and separately publishes a second frame (`findings`,
under `policy="warn_on_mismatch"`) with no lifecycle handling at all —
leaving an `output=""` alias (Variant A, FIND-D13) and the independent
`findings` publication (Variant B, FIND-D13) as two further supported
decoupled-rebind paths at the same site. Both are closed in this pass by
generalizing site 5's mechanism to derive lifecycle behavior from each
publication's own *effective* physical target rather than from the raw
`output` parameter — no new site, no change to the semantic rule itself,
which Review 001 has now separately confirmed *ACCEPTED* (<<H>>).

Four runtime corrections, applied together, close all eight reproduced
variants (same-run collision; durable-policy-only with FK never run; the
second `derived_column_policy.py` executor; the same-run staleness Repro 4
exposes; Lookup's own `helpers=None` decoupled-rebind bypass, Repro 5;
`derived_column_policy`'s own pre-existing-output rebind, Repro 6; its
`output=""` alias, Repro 7; and its independent `findings` publication,
Repro 8):

. *Truthful FK provenance* (site 1) — `core/fk.py`'s materialization
  primitive reports, per resolved FK definition, whether it actually wrote
  the helper column this call or found the label already occupied.
  `fk_helpers/enrich.py` writes `_meta.derived.sheets.*.helper_columns`
  entries only for definitions it can truthfully claim (see <<E>>). This
  alone closes the same-run collision variant, because FK no longer writes a
  false claim for a column it did not write.
. *Deletion-authority rule* (sites 2 and 3) — `fk_helpers/drop.py` and
  `derived_column_policy.py` both stop treating durable FK relation policy as
  sufficient evidence to delete a physically present column. Each keeps
  reading FK's own transient provenance (already correct data, already
  correctly scoped per caller); each simply stops falling back to durable
  policy when transient provenance is silent. This alone closes both
  durable-policy-only variants, because "declared but never proven
  materialized this run" no longer authorizes deletion.
. *Decoupled-rebind invalidation at `enrich_lookup`'s own write site* (site
  4, corrected in this pass) — `enrich_lookup`'s own provenance writer
  (`enrich_lookup/operation.py::_write_provenance`) unconditionally discards
  any provenance already present under `_meta.derived.sheets.<output>`
  (foreign, or its own stale prior record) whenever it writes into an
  `output` that is not its own `source` for that call, *regardless* of
  whether this call itself has fresh helper provenance to record (see
  <<K>>). This closes Repro 4 and Repro 5, because no stale record — FK's or
  Lookup's own — survives a decoupled rebind to be read by either cleanup
  executor.
. *Decoupled-rebind invalidation over `derived_column_policy`'s complete
  publication inventory* (site 5, completed in this pass) —
  `apply_derived_column_policy` has exactly two physical DataFrame
  publications: the primary payload write, whose *effective* target is
  `payload_target = output or source` (not raw `output`), and the
  `findings` write (`policy="warn_on_mismatch"` only), whose target is the
  literal `findings` value. Each publication independently invalidates any
  pre-existing `_meta.derived.sheets` entry at its own effective target
  before the call returns, reusing the module's own existing
  `_strip_consumed_provenance` helper (see <<H>>). This closes Repro 6
  (FIND-D10's original non-empty distinct-output case, now one instance of
  the general rule), Repro 7 (the `output=""` alias, FIND-D13 Variant A),
  and Repro 8 (the independent `findings` publication, FIND-D13 Variant B),
  because neither publication can leave a stale record at the name it
  physically just overwrote, regardless of which parameter or alias named
  that target.

All four corrections are independently necessary and jointly sufficient
against the accepted evidence, extended by both reviews, in <<repro-recap>>.
None requires value/formula equivalence machinery, a claimant/reliance
primitive, generation IDs, a central invalidation bus, or new durable state.
The third and fourth corrections reuse the same owner-local, write-time,
per-sub-key pattern `_write_helper_provenance` already established for FK's
own stale-sheet cleanup (`fk_helpers/provenance.py:69-95`), applied
completely at `enrich_lookup`'s own write site and, independently, at
`derived_column_policy`'s — see <<find-d1-bound>> for why these two sites,
and no shared cross-family primitive, are the correct and sufficient scope.

* mandatory: `domain/transformations/fk_helpers/drop.py`;

== C. Canonical semantic distinctions

This design uses exactly the vocabulary the accepted research converged on
(Section F of the assessment; Review 001 Area 3 and FIND-007). No broader
vocabulary is introduced.

[cols="2,4", options="header"]
|===
| Term | Meaning in this design

| Physical producer
| The operation that actually wrote the currently present column/cell state.

| Requested / declared policy
| A family's transient or durable statement that it *wants* a helper at a
  named identity. Never sufficient deletion authority by itself.

| Truthful materialization provenance
| A same-run transient record written only for a definition the writing
  primitive freshly wrote this call (<<E>>). Necessary but, corrected per
  Review 001 FIND-D1, not by itself sufficient — see "current" below.

| Current (as applied to provenance)
| Corrected term, introduced by this pass: a truthful record that has not
  since been invalidated by a decoupled rebind of the sheet it describes
  (<<K>>). Truthful-and-current together are the *only* thing that can
  authorize FK-attributed deletion in this design; truthful alone is not
  (Repro 4, <<repro-recap>>).

| Deletion authority / precondition
| The verified fact ("truthful, current materialization provenance names
  this column") that must hold before a cleanup executor removes a column
  identified through a requested/declared name.

| Cleanup executor
| The operation that mutates the physical frame to remove a column:
  `fk_helpers/drop.py` and `derived_column_policy.py`, the two mandatory
  sites.

| Decoupled rebind
| Term introduced in the second correction pass: a write that binds
  `output` to a frame name that already exists in `frames` but was not the
  write's own `source`/input, so the write's physical content has no
  provable relationship to whatever the name previously held. The trigger
  is the physical publication event itself, not whether that write happens
  to emit fresh derived metadata of its own (corrected in this third pass,
  <<K>>). The identified trigger for provenance going stale after being
  truthfully written, now evidenced and closed at exactly two write sites:
  `enrich_lookup` (<<K>>) and `apply_derived_column_policy` (<<H>>).
|===

*Explicitly not introduced:* claimant, current reliance, claim
registration/release, reference counting, a central claim ledger, stable
artifact identity, or an adopt/share protocol. <<Q>> restates why each is
unnecessary against the evidence in <<repro-recap>>.

[[D]]
== D. FK collision semantics

*Design Question 1 answer.* The smallest sufficient policy is *A: decline
materialization on collision, no provenance claim* — `core/fk.py`'s
materialization primitive must never overwrite an existing column at the
requested helper label (Candidate D — FK overwrites — was independently
rejected by Review 001 as strictly worse: it trades a wrongful-deletion
defect for silent, unwarned data corruption of whichever producer's column
FK overwrote). On collision, the primitive continues to skip the write,
exactly as today; what changes is that the skip must be *reported*, not
silently absorbed, so provenance can be truthful (<<E>>).

*Naming, corrected per Review 001 FIND-D3:* this design previously labeled
this "reject on collision." That word already has an established, different,
*raising* meaning elsewhere in this same subsystem (Discriminator split's
`framecheck.py:28` hard failure; `apply_v2_relations`'s own durable-policy
collision handling, documented as "cross-producer collisions on the same key
fail"; `enrich_lookup`'s own `_check_column_conflict` /
`_check_key_helper_collision` guards, which do raise). A reader carrying any
of those precedents into this design would wrongly expect `add_fk_helpers`
to raise on a label collision. It does not, by design. "Decline
materialization" is used throughout this corrected artifact instead; "reject"
is reserved for behavior that actually raises.

Policy A alone is *sufficient* to close all six reproduced variants once
paired with the deletion-authority rule in <<F>> and the write-time
invalidation obligations in <<K>> and <<H>> — see <<repro-closure>>. Per the design
brief's own instruction ("If A or B is sufficient, do not design generic
adoption"), *Candidate C (value/semantic-equivalence adoption of a foreign
producer's column) is rejected outright and not designed here* — <<L>> gives
the full disposition.

*Optional self-verified-reuse refinement — removed (Review 001 FIND-D2).*
The original design proposed an optional Domain-layer refinement letting a
collided definition be recognized as FK's own idempotent prior output by
comparing definition *shape* (never cell values) against FK's own
already-present transient provenance entry. Review 001 constructed a direct
disproof: continuing Repro 4 with a second `add_fk_helpers` call after
`enrich_lookup` has already decoupled-rebound the column shows the
refinement re-affirming a foreign, stale claim purely because the shape
still matched a record that had never been invalidated — and in doing so it
defeats the one incidental self-healing property `_write_helper_provenance`'s
existing per-sheet replace-not-merge semantics would otherwise provide
(a re-run over an unmatched collision naturally drops the provenance entry
under Policy A alone). This is not "not required," it is actively unsafe as
specified once combined with Repro 4, so it is *removed from this design
entirely*, not scheduled as a deferred slice. <<K>>'s new write-time
invalidation obligation closes the specific staleness Review 001 used to
construct the disproof, which means the refinement's *original* safety
argument ("compares only FK's own metadata shape, never a foreign
producer's") would, after <<K>> lands, once again be reasoning about a
record that cannot be stale in the one way this design has evidence for. That
is grounds for a *future*, separately authorized reconsideration — not for
reinstating it in this pass; see <<R>>.

*Does not help post-persistence.* Regardless of the refinement's removal,
this point stands for the mandatory mechanism: transient provenance does not
survive persistence (`docs/ai_info/agent_rules.adoc`'s persistence-boundary
rule: Intent survives, Resolution/derived provenance does not). On a freshly
reimported frame there is no surviving transient record at all, so a
physically present FK-shaped column is *always* treated as an unverified
collision after reimport. That is intentional — see <<I>>.

[[E]]
== E. Truthful FK materialization provenance

*Design Question, site 1 concrete answer.*

*Is the existing return contract sufficient?* No. `core/fk.py::apply_fk_helpers`
today returns only the resulting `pd.DataFrame`; the per-definition
materialized/skipped fact is computed (`if helper_col in first_cols:
continue`) and then discarded. `fk_helpers/enrich.py::enrich_helpers` cannot
write truthful provenance without that fact.

*Is a narrow result structure needed?* Yes, but it must not change
`apply_fk_helpers`'s existing signature or return type. `apply_fk_helpers` is
re-exported from `spreadsheet_handling.core.__init__` (`__all__` includes
`"apply_fk_helpers"`) and is exercised directly, as a DataFrame-returning
call, by `tests/unit/domain/transformations/test_fk_helpers_enrich.py` and by
the primitive-package architecture guard
(`tests/architecture/dependency_guards/test_fk_helper_primitives_consume_policy.py`,
which allow-lists `apply_fk_helpers` by name). Changing its return type is a
gated public-surface break for no evidenced benefit.

*Public or internal? Corrected per Review 001 FIND-D8: internal.* The
original design left the new reporting primitive's public-barrel status as
an open question (former <<S>> item, "does `interfaces_and_gates.adoc` gate
adding it to `core/__init__.py`'s `__all__`?"). Review 001 checked whether
that question is even reachable: `fk_helpers/enrich.py` already imports
directly from the `core.fk` *submodule*
(`from ....core.fk import apply_fk_helpers, build_id_value_maps`),
bypassing `core`'s `__all__`-gated barrel entirely, and the architecture
guard that must be updated regardless
(`_ALLOWED_CORE_FK_NAMES` in
`test_fk_helper_primitives_consume_policy.py`) operates on submodule-level
imports via AST inspection, not on `__all__` membership.
`interfaces_and_gates.adoc` itself distinguishes the Python import surface
("keep intentionally small... do not treat every internal module or barrel
export as public API") from the CLI/YAML/plugin surfaces it actually gates.
Nothing about the sole evidenced consumer (`fk_helpers/enrich.py`) requires
public status. The new primitive is therefore designed as a private,
leading-underscore symbol in `core/fk.py`, allow-listed in the existing
architecture guard by name, and *not* added to `core/__init__.py`'s
`__all__`. This makes the former open question moot rather than something
requiring a maintainer decision before Slice 1 (<<S>>).

*Proposed shape (design-level, not final naming):*

[source,python]
----
class _FkHelperMaterializationResult(NamedTuple):
    frame: pd.DataFrame
    materialized: list[FKDef]        # definitions this call actually wrote
    skipped_existing: list[FKDef]    # definitions whose helper_col collided
                                      # with an already-present column

def _materialize_fk_helpers(
    df, fk_defs, id_value_maps, levels, helper_prefix="_",
    helper_value_provider=None,
) -> _FkHelperMaterializationResult: ...

def apply_fk_helpers(df, fk_defs, id_value_maps, levels, helper_prefix="_",
                      helper_value_provider=None) -> pd.DataFrame:
    """Preserved for compatibility; existing callers unaffected."""
    return _materialize_fk_helpers(
        df, fk_defs, id_value_maps, levels, helper_prefix,
        helper_value_provider,
    ).frame
----

`_materialize_fk_helpers` becomes the real implementation (identical
materialization logic to today, plus bucket bookkeeping); `apply_fk_helpers`
becomes a thin compatibility wrapper. No duplicated materialization logic, no
change to any existing caller's observed behavior or type. If a genuine
external need for a public `materialize_fk_helpers` later emerges, promoting
the private symbol is a small, separately evidenced follow-up, not something
this design needs to pre-authorize.

*How `fk_helpers/enrich.py` uses it:* `enrich_helpers` calls
`_materialize_fk_helpers` per frame instead of `apply_fk_helpers`. For each
frame, it builds the *provable* set passed to `_write_helper_provenance` from
exactly `materialized` (definitions freshly written this call). Definitions
in `skipped_existing` are never included — no refinement re-admits them
(<<D>>, FIND-D2). This is simpler than the original design's provable-set
construction, not merely equally safe: there is no second case to reason
about.

Definitions in `skipped_existing` writing *no* provenance entry is the
direct fix for the confirmed contract violation (FK provenance must record
only materialized state; three independent maintained sources —
`docs/semantic_model/12_contract_matrices.adoc`,
`docs/technical_model/ch04_concepts/fk_helper_metadata.adoc`,
`docs/ai_info/concepts_fk_helpers.adoc` — already say this; only the runtime
was wrong).

*Avoiding duplicated physical-materialization decisions in Domain code:*
Core (`core/fk.py`) remains the *sole* place that decides column-level
collision (`helper_col in first_cols`); it only gains a reporting
obligation, not new policy. Domain (`fk_helpers/enrich.py` /
`fk_helpers/provenance.py`) owns the *meaning* of that report — this matches
the existing Core/Domain boundary (Core is a content-free mechanism; Domain
owns metadata lifecycle, per the Domain Maintainer Contract §8).

*Replay/idempotence:* a single call to `enrich_helpers` is unaffected. A
second call in the same session against frames that already carry FK's own
prior output writes no provenance for the re-collided definitions (they
land in `skipped_existing`, never claimed) — an accepted, narrow,
currently-unevidenced-as-relied-on behavior change flagged in <<D>> and
<<P>>. This is deliberately conservative rather than merely convenient:
Review 001's FIND-D2 showed that trying to be more clever here (the
now-removed optional refinement) can be actively unsafe, not just
unnecessary.

*Pre-existing requested label — final rule:* absent → materialize and claim;
present (verified or not; no self-check exists) → no-op, no claim, no
overwrite, no error by default (diagnostic per <<J>>).

[[F]]
== F. Deletion-authority rule

[.lead]
*A cleanup executor may delete a column identified through an FK-attributed
candidate name if and only if that name is currently present in
`_meta.derived.sheets.<sheet>.helper_columns` (truthful, same-run,
materialized-only transient provenance, per <<E>>, that has not since been
invalidated by a decoupled rebind of that sheet, per <<K>> or <<H>> —
whichever family performed the rebind).
`_meta.helper_policies.fk` (durable v2 relation policy) never independently
authorizes deletion — it identifies what FK would request, not what FK
currently produced.*

*Corrected per Review 001 FIND-D1.* The rule's shape is unchanged from the
original design ("presence of truthful transient provenance is required and
sufficient"); what changed is that "presence" is no longer trusted as a
standing fact once written. Review 001 independently reproduced (Repro 4,
<<repro-recap>>) that a same-run `enrich_lookup` call with `source != output`
can physically replace an already-FK-enriched sheet while leaving FK's
transient record for that sheet completely untouched, because
`enrich_lookup`'s own provenance writer *merges into* the existing sheet
entry rather than reasoning about whether its own write invalidates a
sibling's claim. Both cleanup executors then trusted that now-stale record.
Neither of the original two corrections (<<E>>, and the durable-fallback
removal in <<G>>/<<H>>) touches this path: FK's write in Repro 4 genuinely
was fresh and uncollided (so <<E>> reports it as `materialized`, correctly),
and the stale record was never sourced from durable policy at all (so the
durable-fallback removal is irrelevant to it). Closing it required a third,
independent correction, made at the site that can actually know the
staleness is happening — see <<K>>.

*Further corrected in this third pass (Review 001 FIND-D9/D10, Review 002
FIND-D9/D10).* The second pass's own third correction was itself incomplete
in two independently reproduced ways: its invalidation logic lived behind a
guard a documented `enrich_lookup(..., helpers=None)` call never reaches
(Repro 5), and the identical hazard is independently reachable through
`derived_column_policy.py`'s own `output` parameter — one of this design's
two mandatory executor sites, previously misclassified as an unevidenced
analog (Repro 6). Both are now closed: <<K>>'s mechanism is corrected to
trigger unconditionally on the decoupled-rebind event rather than on
provenance emission, and <<H>> gains the symmetric obligation at its own
write site.

*Further corrected in this fourth pass (Review 001 FIND-D13).* Review 001's
own final targeted closure pass confirmed FIND-D9 and FIND-D10 closed
exactly as written, and confirmed the underlying lifecycle rule *ACCEPTED*,
but found <<H>>'s FIND-D10 fix keyed to the *raw* `output` parameter rather
than the operation's actual effective publication target(s): a registered
`output=""` alias physically publishes into `source` while the raw-`output`
check inspects the empty-name slot instead (Repro 7), and
`apply_derived_column_policy`'s independent `findings` publication
(`policy="warn_on_mismatch"`) was not reasoned about as a physical
publication at all, so a `findings` value naming an existing
provenance-bearing frame (including `source` itself) replaces it while that
frame's stale provenance survives (Repro 8). Both are closed by
generalizing <<H>>'s mechanism to key every publication's lifecycle behavior
to that publication's own effective target, not to a raw parameter value —
no change to the semantic rule, no new site.

[[find-d1-bound]]
=== Why the invalidation is applied at exactly two write sites, and no shared primitive is designed

The second pass reasoned that the decoupled-rebind hazard was bounded to one
write site (`enrich_lookup`), with `derived_column_policy.py`'s own `output`
parameter recorded as a theoretical, unevidenced analog. Both Review 001 and
Review 002 independently disproved that: `derived_column_policy.py`'s own
`output` parameter has no "new name only" precondition in its registered
contract, and both reviews reproduced the exact hazard through it
(FIND-D10, <<repro-recap>> Repro 6). This design no longer defers that site.
Re-derived against the current runtime, exactly two write *sites* (one per
family/module) are evidenced, and the case against a third or against
generic infrastructure is now stated on that corrected basis. Review 001's
final closure pass (FIND-D13, <<review-disposition-3>>) subsequently found
that the `derived_column_policy` site itself has *two* internal physical
publications (payload and findings, <<H>>) — this does not add a third
*site*; both publications are covered by the same local, owner-local
mechanism inside the same module, generalized in <<H>> to key off each
publication's own effective target rather than off a single raw parameter:

* *FK's own writer (`fk_helpers/enrich.py` / `core/fk.py`) is structurally
  immune*, for two independent reasons confirmed by reading it: it is always
  self-referential — `enrich_helpers` iterates `iter_data_frames(frames)`
  and reads and writes the *same* frame name for every sheet it touches;
  there is no `source`/`output` decoupling anywhere in FK's materialization
  path. And even within that self-referential shape, the existing collision
  check (`helper_col in first_cols: continue`, unchanged by <<D>>) already
  prevents FK from ever overwriting a Lookup-produced column's physical
  content in place. FK cannot reproduce this hazard's shape against a
  sibling's provenance.
* *`enrich_lookup` and `derived_column_policy` are the two evidenced sites*,
  both correspondingly fixed in this pass: <<K>> (Lookup's own write) and
  <<H>> (the new subsection there, DCP's own write). Both fixes are
  owner-local — each implemented entirely inside its own module, using its
  own existing code shapes (Lookup: restructures its own provenance writer;
  DCP: adds a second call to its own already-existing
  `_strip_consumed_provenance` helper) — deliberately *not* factored into a
  shared cross-family primitive. This is a considered choice, not an
  oversight: the two write sites have different shapes (Lookup writes a
  fresh own record after invalidating; DCP never writes derived provenance
  of its own and only invalidates), a shared primitive would need to
  abstract over that difference for two call sites, and this design's own
  brief instructs against generic infrastructure introduced for aesthetic
  consistency rather than evidenced duplication. Each owner implementing the
  same documented lifecycle *rule* locally, rather than importing a shared
  mechanism across the `fk_helpers` / `enrich_lookup` / `derived_column_policy`
  family boundary, is also the smaller change against the existing
  architecture guard (`test_no_cross_family_internal_imports.py`) that
  already constrains cross-family imports in this codebase.
* No third site was found within this design's authorized FK/Lookup
  pairing. A future family exhibiting the same `source`/pre-existing-
  decoupled-`output` shape while sharing a `_meta.derived.sheets` entry with
  FK or Lookup should apply the same documented lifecycle rule (decoupled
  rebind of an existing output frame discards prior provenance for that
  slot unconditionally, before any new provenance of its own is
  (re-)established) locally, at its own write site; whether a *third*
  evidenced instance would justify extracting a shared Domain-level
  primitive is recorded, not decided, in <<S>> and <<R>> — two instances is
  not evidence for a generic mechanism.

=== Design Question 2 — what proves current FK production?

*Same-run transient provenance is necessary but, corrected per Review 001
FIND-D1, not by itself sufficient.* "Truthful when written" (<<E>>) proves
only that FK's record was accurate at the moment it was written; it does not
prove the record is still accurate now. The exact additional condition this
design requires, corrected in this third pass to state the trigger at the
right level (Review 001 FIND-D9/D10, Review 002 FIND-D9/D10): *no
decoupled rebind of that sheet has run since* — where a decoupled rebind is
either an `enrich_lookup` call or an `apply_derived_column_policy` call that
writes into an `output` equal to that sheet with `source` different from
`output`, *regardless of whether that call itself emits any provenance of
its own*. The trigger is the physical publication event (`out[output] =
...`), not whether the call happens to write fresh derived metadata — the
prior "no `enrich_lookup` call with helper provenance has run since" framing
was falsified by a documented no-helper call shape that publishes without
ever emitting provenance (FIND-D9). This is the one identified, evidenced
way a sheet's sibling record can go stale while every other reader observes
it as untouched (Review 001 section 4 and Section 14.3; Review 002 Sections
5-6; confirmed independently against `enrich_lookup/operation.py`,
`derived_column_policy.py`, `fk_helpers/provenance.py`, and
`registries/meta_registry.yaml`'s own per-sub-key-locality invariant, which
documents that each producer owns only its own subkey but has no mechanism
for a sibling's subkey to survive a wholesale content replacement it did not
itself produce).

This condition is enforced *by construction*, not by the cleanup executors
re-verifying anything at read time: <<K>> and <<H>> make the two
transformations that can create the staleness responsible for closing it at
the moment they write, so a cleanup executor's simple "is the entry present"
read (unchanged from the original design) is correct again. This is why the
rule's *header* in <<F>> did not need to change shape — only the meaning of
"currently present" did, and that meaning is now something the corrected
write-time contracts actually guarantee, not an unproven assumption. The
corresponding Design Question 2 assumption in the original design ("no
supported transformation is known to silently overwrite another family's
helper column... named as an open assumption, not a proven invariant") is
superseded: both identified paths are now closed by construction within the
authorized FK/Lookup pairing; an implementer extending FK/Lookup interaction
beyond that pairing later should still re-verify no new decoupled-rebind
shape has been introduced, per <<find-d1-bound>> and <<S>>.

*Durable-policy-only path:* does not, and structurally cannot, prove current
physical production, with or without persistence (<<I>>). This design
deliberately does *not* build a value-verification override
(`should cleanup verify the current column against what FK would produce?`
from the design brief) — see <<L>> for why. It does *not* ask the caller to
supply a stronger durable declaration — that would be new durable producer
history, explicitly disallowed (the design brief's own instruction: "Do not
invent durable producer history merely to preserve old cleanup behavior"). The
chosen answer is the brief's own named conservative option: *the existing
persistence/reimport contract intentionally leaves the helper column in
place rather than risk deleting Lookup- or user-owned data* — the safe
migration path for pipelines that need durable, persistence-surviving
cleanup identity is named concretely in <<I>>.

== G. FK direct-cleanup design

`fk_helpers/drop.py::_columns_to_drop_by_sheet` currently builds its result
from `provenance_by_sheet` (transient, preferred) with a *fallback* to

*New behavior:* `columns_to_drop` is built from `provenance_by_sheet` only —

*Concrete disposition:*

[[H]]
== H. Derived-column-policy integration design

`derived_column_policy.py::_safe_policy_helper_names` exists *solely* to
supply FK-attributed deletion candidates from durable v2 relation policy.
Under <<F>> that source is never authorized, so this function's entire
purpose is removed: `apply_derived_column_policy` stops calling it, and its
result is no longer unioned into `durable_helper_names` in
`apply_derived_column_policy`'s body.

*What remains, and why it is not touched:* `_resolve_derived_identity`'s
reading of `_meta.derived.sheets[source].helper_columns` (FK's transient
provenance) is *already correct* — it reads the same truthful subkey
`fk_helpers/drop.py` reads. `_resolve_derived_identity`
also reads Lookup's own `enrich_lookup` declared names in the same call —
that half is Lookup's own self-declared identity of its own column and is
*not* the defect (a family deleting a column via its own declaration of its
own artifact is not "requested identity borrowed from a different owner");
it is untouched.

*Shape-validation divergence between the two transient-provenance readers —
corrected per Review 001 FIND-D6, made explicit rather than a passing
aside.* `fk_helpers/policy.py::derived_helper_columns_by_sheet` (used by
`drop_helpers`) silently filters out non-mapping `helper_columns` entries;
`derived_column_policy.py::_validated_fk_helper_names` (used here) raises a
clear `ValueError` on the identical malformed shape. This is a genuine,
deliberate operational divergence, not an oversight, and it is *not* a
deletion-authority divergence: both directions are conservative toward "do
not wrongly delete on bad data" — one silently proceeds without the
malformed candidate, the other aborts the whole call rather than guess. Per
this repository's own domain-boundary policy (shared helpers require shared
*accepted/rejected vocabulary*, not merely the same accepted-value read),
this divergence does not by itself justify a shared facade, and none is
designed here. It is recorded, not silently left as a one-clause aside, so a
future reader does not mistake it for an unnoticed inconsistency.

*Workbook-View's durable `helper_columns` declaration — corrected per
Review 001 FIND-D5, "different owner" replaced with the actual distinction.*
`_safe_durable_helper_names` reads `_meta.sheets[source].helper_columns` and
feeds it into `durable_helper_names` with *no* physical-producer check at
all — structurally the same "requested/declared identity, unverified
against current physical production" pattern this design eliminates for
FK's durable relation policy (confirmed by the existing, unchanged,
currently-green test
`test_drop_uses_durable_workbook_helper_columns_when_derived_is_absent`).
Leaving it untouched is correct, but "different owner" alone does not make
it safe by itself; the real, citable distinctions are:

* *producer* — this carrier is written only by `configure_workbook_view`
  (`domain/workbook_views.py:55-165,349-379`), whose entire parameter
  surface is a human pipeline author's *explicit* sheet-shape declaration,
  closer in kind to XRef's guarded, caller-asserted `drop_source` flag (a
  pattern the accepted research already treats as legitimate) than to FK's
  auto-derived "what I would build" intent;
* *canonical content contract* — `fk_helper_metadata.adoc`'s "First
  conservative policy" section states, as maintained authority, that
  "manual edits to helper values are not treated as source truth; helper
  values may be ignored or overwritten on re-enrichment." A column declared
  a helper by workbook-view configuration is canonically defined as
  never-authoritative content, independent of who currently produced it;
* *purpose-built origin* — `BUG-HELPER-CLEANUP-CONTRACT-P4A` built this
  carrier, together with the FK-relation-policy fallback this design now
  removes, specifically as durable cleanup identity surviving the
  persistence boundary; it is the carrier this repository already chose for
  this exact job, not an accidental byproduct being repurposed — see <<I>>,
  where this same carrier is named as the concrete, recommended migration
  path for pipelines the durable-fallback removal affects.

This is a real, defensible distinction that makes the residual risk
*smaller and differently justified*, not a distinction that makes the
residual risk *zero*: nothing prevents a caller from repurposing a
historically-FK-derived label for genuine hand-entered data without also
updating the separately-maintained `configure_workbook_view` declaration.
That residual staleness risk is recorded explicitly, not implied away, in
<<R>>. It remains out of scope for this design (see
<<repository-boundaries>> in <<Q>>) — the accepted research's own
narrowed-scope authorization treats Workbook View as a constraint/boundary,
not a mandatory Design-Phase site, and nothing found by this correction pass
forces that boundary open.

*Net effect on `apply_derived_column_policy`:* `durable_helper_names` in the
function body is fed only by `_safe_durable_helper_names` (Workbook-View,
unchanged, out of scope); `policy_helper_names` (`_safe_policy_helper_names`,
FK durable-relation fallback) is deleted. FK-attributed candidate names come
exclusively from `_resolve_derived_identity`'s transient-provenance read,
unchanged.

[[dcp-invalidation]]
=== Decoupled-rebind invalidation over `apply_derived_column_policy`'s complete publication inventory (site 5, third pass, generalized in this fourth pass — closes FIND-D10 and FIND-D13)

*Design Question, corrected per Review 001 FIND-D10 / Review 002 FIND-D10,
generalized per Review 001 FIND-D13 (fourth pass).* The third pass keyed
this site's invalidation to the *raw* `output` parameter
(`output is None or output == source`). Review 001's own final targeted
closure pass (Section 15) confirmed that fix correct for the exact case it
was built against, but found the raw-`output` framing itself incomplete:
`apply_derived_column_policy` does not have one physical publication, it has
*two*, and the raw parameter that decided lifecycle behavior is not the
same thing the runtime actually uses to decide *where* it publishes. This
subsection replaces the raw-`output`-keyed wording with a design derived
from the operation's complete, explicitly inventoried publication set — the
wording change Review 001 asked for, not a reopening of the semantic rule
itself (which Review 001 separately confirmed *ACCEPTED*: producer
provenance attached to a physical frame slot does not carry across a
replacement of that slot unless continuity is explicitly re-established).

==== Complete local publication inventory (mandatory per FIND-D13; not a whole-Domain census)

A direct reading of `apply_derived_column_policy`'s body
(`derived_column_policy.py:43-110`) finds exactly two statements that
publish a `pd.DataFrame` into the returned `frames` mapping. No third
publication exists in the function.

|===
| Publication | Effective target | Replaces a slot? | Continuity with old target established? | Invalidation required

No further `out[...] = <DataFrame>` statement exists in
`apply_derived_column_policy`; `out[META_KEY] = ...` writes metadata, not a
data frame, and is the mechanism this subsection specifies, not a third
publication needing its own lifecycle rule.

==== FIND-D13 Variant A — the `output=""` alias

`derived_column_policy.py:99`'s physical publication is
`out[output or source] = cleaned` — Python's `or` treats an empty string as
falsy, so `output=""` resolves to `source`. The registered contract
(`registries/pipeline_step_registry.json:1778-1782`) declares `output` as
`string_or_null` with no non-empty constraint, and the generic registered
binder (`pipeline/build.py::_build_trusted_steps_from_config`,
`pipeline/steps.py::make_frames_target_step`) passes it through without
value validation, so `output=""` is a genuinely reachable, registered call
shape, not a hand-constructed edge case. The third pass's lifecycle branch,
however, reasoned from *raw* `output` — `replacing = output is None or
output == source` — which is `False` for `output=""` (assuming, as is
always true in this reproduction, `source != ""`). The corrected branch
therefore inspected the empty-string metadata slot, found nothing there,
and never stripped `source`'s own stale provenance, even though `source`'s
*physical* frame had just been overwritten with the cleaned payload.

The fix: derive `payload_target` once, from the same expression the runtime
already uses for physical publication, and branch on `payload_target ==
source` instead of on raw `output`. `payload_target = output or source`
resolves `output=""` to `payload_target = source`, so it now correctly
falls into the *same-target* branch alongside `output=None` and
`output=source` — all three are, and always were, the identical physical
event (self-cleanup in place), and now receive the identical, correct
lifecycle treatment.

==== FIND-D13 Variant B — the independent `findings` publication

Corrected Section H (third pass) reasoned only about the primary
`output or source` publication. It deliberately preserves `source`'s own
provenance whenever `payload_target != source` — correct for that write in
isolation. But `apply_derived_column_policy` can *also*, in the same call,
publish a second, independent frame — `out[findings] = findings_to_frame(...)`
under `policy="warn_on_mismatch"` — and the third pass never reasoned about
this write as a physical publication requiring lifecycle handling at all.
`findings` is a registered plain string parameter
(`registries/pipeline_step_registry.json:1789-1794`) with no freshness or
distinctness precondition against `source`, `payload_target`, or any other
frame name; nothing in the registered contract or the runtime prevents a
caller from setting `findings` to an existing, provenance-bearing frame
name — including `source` itself. When that happens, the findings frame
physically replaces whatever was at that name, but no invalidation runs, so
stale provenance for the replaced frame survives and authorizes a later
cleanup executor to delete columns that are now the findings frame's own
canonical columns.

The fix: treat the findings publication as its own, fully independent
decoupled-rebind case. Unlike the payload publication, there is no
"self-extension"/continuity variant for findings to consider — the findings
frame's content is *always* synthesized fresh, never derived from whatever
was previously at that name — so the rule is unconditional: whenever
`policy == "warn_on_mismatch"`, invalidate any pre-existing
`_meta.derived.sheets.<findings>` entry as part of the same call, regardless
of what `findings` equals.

==== Publication order and what survives the final physical state

Because both publications can occur in the same call, and both write into
`out` (a plain `dict`), the *order* in which they run determines final
physical content when their targets coincide. The runtime publishes the
payload first (`derived_column_policy.py:99`) and the findings frame second
(`derived_column_policy.py:100-101`, gated on `policy`); this design's
lifecycle logic follows the same order, processing each publication's
invalidation immediately after (or with) that publication, using the
metadata state as of that point in the call — not the state captured once
at function entry.

* If `payload_target != findings` (the common case, and the *only* possible
  case when `policy != "warn_on_mismatch"`, since no findings write occurs
  at all), the two publications target different names and their
  invalidations are independent; each target's final content and final
  provenance state are exactly what that publication's own step decided.
* If `payload_target == findings` (a caller sets `findings` equal to
  `source` or to a non-empty `output`), the findings write is the *last*
  physical writer to that name: `out[<name>]` ends the call holding the
  findings frame, not the cleaned payload, regardless of what the payload
  step published there moments earlier. The payload step's own invalidation
  (correct for *its* write) may already have stripped that name's old
  provenance; the findings step's own invalidation then re-checks the same
  name against the *current* accumulated metadata and finds nothing further
  to remove — a safe, idempotent no-op, not a second, contradictory
  decision. Processing sequentially against accumulated state, rather than
  against a single snapshot taken at function entry, is what makes this
  outcome correct without relying on which write "conceptually owns" the
  coincidental final content: no stale record survives the call regardless
  of which physical write actually produced the final bytes at that name.

No DCP-owned `_meta.derived.sheets` producer record needs to be preserved or
re-established by either step — `apply_derived_column_policy` never writes
to that namespace itself (confirmed by the complete publication inventory
above); both steps are pure invalidate-and-stop operations, unlike Lookup's
own write in <<K>>, which also re-establishes a fresh record after
invalidating.

==== Explicit case answers

*Primary payload target:* `output=None` → `payload_target = source`,
same-target branch, strips `source`'s own consumed provenance (unchanged
behavior). `output=""` → `payload_target = source`, same as above (corrected
in this pass; previously misrouted, <<repro-recap>> Repro 7). `output=source`
→ `payload_target = source`, same as above (unchanged). `output=<distinct
new name>` → `payload_target = <that name>`, decoupled branch,
`_safe_sheet_meta` finds no entry, true no-op (unchanged, matches FIND-D10's
original evidence). `output=<distinct existing name>` → `payload_target =
<that name>`, decoupled branch, invalidates that name's pre-existing entry
if one exists (FIND-D10's fix, now keyed to `payload_target` rather than raw
`output`, <<repro-recap>> Repro 6).

*Findings target (only relevant when `policy == "warn_on_mismatch"`):*
findings omitted from the call shape entirely — not applicable; the
parameter always has a value (default `"derived_column_findings"`), but no
findings write happens at all when `policy != "warn_on_mismatch"`, so no
invalidation runs either. `findings` targets a brand-new frame — no entry to
invalidate, true no-op, matching today's behavior for the default value in
every currently maintained test (none overrides `findings`). `findings ==
source` — invalidates `source`'s own entry unconditionally, even if the
payload step's own branch had a reason to preserve it (`payload_target !=
source`); the findings write is the last physical writer to `source` in
that case, so its own invalidation is the one that must run
(<<repro-recap>> Repro 8). `findings == payload_target` — see publication
order above: the second (findings) invalidation step re-checks accumulated
state and is a safe no-op if the first (payload) step already invalidated
that name, or performs the invalidation itself if the payload step's own
rule did not touch that name (e.g. `payload_target == source` and
`findings` also equals `source`: the payload step already stripped it,
findings finds nothing left). `findings` targets a third, distinct,
pre-existing frame — invalidates that frame's own entry unconditionally,
the direct Variant B reproduction.

==== Implementation shape

Reuses, not duplicates, the module's own existing `_strip_consumed_provenance`
helper at three call sites written into one function — the mutually
exclusive same-target/decoupled branches of the payload publication, plus
the independent findings branch — of which at most two actually execute in
any single call (the payload branch is exactly one of the first two; the
findings branch runs independently whenever `policy == "warn_on_mismatch"`),
each gated on its own publication's effective target:

[source,python]
----
out = dict(frames)
payload_target = output or source
out[payload_target] = cleaned

new_meta = meta
touched = False

# Primary payload publication (generalizes FIND-D10; closes FIND-D13
# Variant A by keying off the same effective target used for publication).
if payload_target == source:
    if sheet_meta:
        new_meta = _strip_consumed_provenance(new_meta, source)
        touched = True
else:
    target_meta = _safe_sheet_meta(new_meta, payload_target)
    if target_meta:
        new_meta = _strip_consumed_provenance(new_meta, payload_target)
        touched = True

# Findings publication (independent physical target -- closes FIND-D13
# Variant B). Always runs its own invalidation when it runs at all; there
# is no "same-target" continuity variant for a synthesized findings frame.
if policy == "warn_on_mismatch":
    out[findings] = findings_to_frame(found, columns=FINDING_COLUMNS)
    findings_meta = _safe_sheet_meta(new_meta, findings)
    if findings_meta:
        new_meta = _strip_consumed_provenance(new_meta, findings)
        touched = True

if touched:
    out[META_KEY] = new_meta
return out
----

No new primitive, no new `_meta` key, no cross-family import, no shared
publication framework, no central invalidation bus, no generation or frame
identity IDs: every call site is `_strip_consumed_provenance`, already
present in this module, applied at each publication's own effective target
instead of at a single raw parameter. `_safe_sheet_meta` is likewise reused
unchanged (it
already takes a generic frame-name argument). At implementation time,
`_strip_consumed_provenance`'s parameter may be worth renaming from `source`
to a neutral `frame_name` to reflect its now-three call sites — a
non-behavioral naming cleanup, not part of this design's required contract.

==== Local completeness check (FIND-D13's mandatory audit, re-run for this pass)

For every `out[<target>] = <DataFrame>` publication reachable through
`apply_derived_column_policy` — the primary payload write and the
conditional findings write, confirmed to be the *only* two by direct
reading of the function body — this subsection now states explicitly what
happens to any pre-existing `_meta.derived.sheets[<effective target>]`
provenance. No further publication path was found. This check is local to
`derived_column_policy.py`; it is not a whole-Domain publication census, and
none is authorized or needed here.

==== Diagnostics

Unchanged in kind from the third pass: every invalidation described above
is a conservative no-op from the caller's perspective — no exception raised,
no findings-frame entry added, and — consistent with <<J>>'s existing rule
that diagnostics never inspect or report unrelated frame contents — no
mandatory logging. An implementer may add the same non-mandatory
debug-level log <<J>> already permits for <<K>>'s case, naming the
publication (payload or findings) and its effective target.

[[9-facade]]
=== Design Question 9 — why no new shared facade is designed

The two executors do not, in the corrected design, need a shared *data*
accessor: each already reads FK's transient provenance correctly and
independently, at acceptably low duplication risk (a short,
already-well-validated read of one `_meta.derived.sheets[*].helper_columns`
subkey). The defect-causing logic — the *durable-policy fallback* — is not
consolidated into a shared function; it is *deleted outright* from both call
sites, because the answer both sites need ("durable policy never
authorizes deletion") is a fixed rule, not a computed value. This is the
smallest design that prevents both executors from "independently
reimplementing FK authority semantics" (the concern in the design brief):
after this change, neither module contains *any* FK-authority-adjacent logic
beyond reading FK's own truthful transient record.

A narrow, optional hygiene improvement (not required for correctness, not
part of the mandatory scope): `derived_column_policy.py` could call
`fk_helpers.derived_helper_columns_by_sheet` instead of maintaining its own
parallel reader, purely to reduce the duplicate-implementation surface
Review 001's FIND-002 already flagged as a readability/duplication risk one
cycle earlier. This is left to the implementer's judgment at slice time (see
<<N>>) and is explicitly not mandated here.

[[I]]
== I. Persistence/reimport behavior

*Design Question 3 answer.* No special-casing of "before persistence" versus
"after persistence" is designed or required. <<F>>'s rule is stated once,
uniformly: *truthful same-run transient provenance is required; durable
policy alone is never sufficient — regardless of whether a persistence
boundary was crossed.* Persistence does not change the rule; it only changes
which evidence is available. Transient `_meta.derived` is stripped at the
persistence boundary by existing, unchanged, and out-of-scope machinery
(`pipeline/persistence_boundary.py`; "Persist Intent, discard recomputable
Resolution" — `docs/ai_info/agent_rules.adoc`); durable
`_meta.helper_policies.fk.relations` survives.

*Concrete consequence:* after a reimport with no fresh `add_fk_helpers`
materialization pass in the same session, `remove_fk_helpers` and
`apply_derived_column_policy` can no longer automatically delete a
physically present FK-shaped helper column from durable policy alone. This
is a *deliberate, evidenced* compatibility narrowing, not an oversight — see
<<P>> for its scope. It is consistent with `derived_column_policy.py`'s own
pre-existing docstring, which already hedges that durable fallback
declarations "identify columns only" — the implementation was out of sync
with its own documented contract before this design.

*Does running `add_fk_helpers` first restore automatic post-reimport
cleanup?* No, and this must not be assumed by an implementer. Running
`add_fk_helpers` against a freshly reimported frame treats the physically
present column as an unverified collision (no claim); there is no surviving
transient record from before the current run to compare against. No
mechanism in this design can regenerate trustworthy same-run evidence for a
column that already existed before the current run started, short of FK
genuinely re-materializing it from a state where the label was absent.

*Corrected per Review 001 FIND-D4: the compatibility narrowing is larger
than the original design stated, and the migration path was never named.
Further corrected per Review 001 FIND-D11 (third pass): a fourth maintained,
currently green test, at the sibling mandatory executor site, pins the
identical capability and was missed by both the original review and the
second pass.* Four maintained, currently green tests exist *specifically* to
pin the capability this design removes. The first three all exercise
`apply_derived_column_policy` (confirmed by re-reading
`tests/roundtrip/test_cleanup_invariants.py`'s reverse pipeline, whose
cleanup step is `apply_derived_column_policy`, not `remove_fk_helpers`), two

Diagnostics never inspect or report unrelated frame contents; they name only
the frame, the candidate column label, and (where available) the FK relation
identity that was declined.

*`fail_on_mismatch` decision, corrected per Review 001 FIND-D7.* The
original design proposed routing `fk_deletion_unauthorized` through
`fail_on_mismatch`'s existing raise path, flagging it for maintainer
sign-off because it would give a registered pipeline step a genuinely new
failure trigger unrelated to value mismatch. Review 001 found this
repository already has a purpose-built, separately composable mechanism for
exactly the "fail loudly if cleanup silently no-op'd" need:
`validate_references`'s `no_helper_columns` rule, added by
`BUG-HELPER-CLEANUP-CONTRACT-P4A` for precisely this reason ("Architectural
direction": cleanup stays a safe no-op; strictness is opt-in via a separate
validation rule, deliberately not folded into the cleanup step's own
severity ladder), already exercised today by
`test_no_helper_columns_validation_reports_bypassed_cleanup`. Authorization
refusal ("we cannot prove FK currently produced this column") and value
mismatch ("FK's value differs from what the canonical lookup would produce")
are different failure classes; conflating them in `fail_on_mismatch`'s raise
path would re-conflate at the control-flow level what the findings-frame
separation deliberately keeps apart one step earlier. `fk_deletion_unauthorized`
is therefore designed as *always* a conservative, non-raising diagnostic,
emitted under both `warn_on_mismatch` and `fail_on_mismatch`, never routed
into the `raise` path. Callers wanting fail-fast "deletion definitely
happened" enforcement are pointed at the existing `no_helper_columns` rule
instead of a newly grown `fail_on_mismatch` failure surface. This closes the
sign-off question the original design left open in <<S>> with a concrete
decision, not a re-flag.

[[K]]
== K. Lookup interaction / H5 relationship

*Design Question 5 answer, corrected per Review 001 FIND-D1, and again per
Review 001 FIND-D9 / Review 002 FIND-D9 in this third pass.* The original
design's answer — "no new Lookup-owned pre-deletion handoff is
introduced... it never reads... any other Lookup-owned shape" — is no
longer accurate and is replaced. Closing Repro 4 requires one narrowly
necessary, Lookup-owned *write-time* correction, permitted explicitly by the
design brief's scope check ("the corrected design may add a narrowly
necessary modification/handoff at Lookup Enrichment if FIND-D1 proves it
necessary"). It is a write-time obligation on Lookup's *own* provenance
write, not a new pre-deletion query FK or a cleanup executor makes of
Lookup, and not a change to what either cleanup executor reads — <<F>>'s
rule is still decided entirely from FK-owned evidence, read exactly as
before.

=== Why the second pass's mechanism was itself incomplete (FIND-D9)

The second pass placed the invalidation *inside* `_write_provenance`'s body,
gated behind writing Lookup's own `enrich_lookup` record. But
`_write_provenance`'s first statement is, and remains,
`if fields is None: return` (`operation.py:502-503`) — executed *before*
any `_meta`/`sheet_entry` handling. `enrich_lookup(..., helpers=None)` is a
documented, supported call shape ("`None` — no helper projection (only the
join key is used)", the function's own docstring), pinned by the maintained
test `test_enrich_lookup_no_helpers_returns_source_joined_on_key`. That call
still physically publishes via the unconditional `out[output] = enriched`
(`operation.py:211`, unaffected by the `fields is None` branch) — with
`enriched` in this mode built from `source_df.merge()` against a
join-key-only projection, so its *content* is effectively `source_df`'s own
columns. When `output` names a pre-existing, decoupled sheet (`output !=
source`), this is exactly Repro 4's physical-rebind shape, but
`_write_provenance` returns before the second pass's invalidation logic is
ever reached — confirmed directly: a probe call,
`_write_provenance(probe_out, "orders", ..., fields=None)`, leaves
`probe_out["_meta"]` byte-identical to the input. Any sibling record already
attached to `output` — FK's, or a stale prior `enrich_lookup` record of
Lookup's own — survives untouched, and either cleanup executor then deletes
the current, foreign, physical column trusting it (<<repro-recap>> Repro 5).

The trigger the second pass used, `output != source`, was correct; what was
wrong was making the invalidation conditional on *this call itself having
new provenance to write*. The corrected rule, stated at the right level: the
trigger is the *physical publication event* (`out[output] = enriched`, which
always runs), not whether this specific call happens to emit derived
metadata of its own.

=== The corrected mechanism: unconditional invalidation at decoupled rebind, independent of provenance emission

`enrich_lookup/operation.py::_write_provenance` currently builds
`sheet_entry = dict(derived_sheets.get(output, {}))` — i.e. it starts from
whatever sibling entry already exists for `output` — and then only ever sets
`sheet_entry["enrich_lookup"] = record`, leaving every other subkey (in
practice, FK's `helper_columns`) untouched, and skips this entirely when
`fields is None`. This is exactly right when `output == source`:
`enrich_lookup`'s merge (`source_df.merge(...)`, or `source_df.copy()` in
formula mode) provably preserves every pre-existing column's physical
content unchanged — the existing `_check_column_conflict` guard, which
inspects only `source_df`, is sufficient in this case because `source_df`
*is* the frame being extended, so any sibling's claimed columns are already
visible to that guard. It is exactly wrong when `output != source`: the
physical content now written to `output` is derived entirely from `source`,
which the pre-existing frame at `output` was never party to;
`_check_column_conflict` never inspects the pre-existing `output` frame at
all, so a sibling family's claimed columns — or Lookup's own stale prior
record — can be silently replaced/orphaned with no guard seeing it happen.

The correction: `_write_provenance` gains one new parameter, `source`, and
its body is restructured so the decoupled-rebind check runs *before*, and
independently of, the `fields is None` early exit:

[source,python]
----
def _write_provenance(
    out: Frames,
    output: str,
    source: str,
    lookup: str,
    resolved: _ResolvedKeys,
    fields: list[str] | None,
) -> None:
    decoupled = output != source
    if not decoupled and fields is None:
        return  # unchanged: ordinary same-source, no-helper call is a no-op

    meta: dict[str, Any] = dict(out.get("_meta") or {})
    derived: dict[str, Any] = dict(meta.get("derived", {}))
    derived_sheets: dict[str, Any] = dict(derived.get("sheets", {}))
    had_entry = output in derived_sheets

    if decoupled:
        # Decoupled rebind: nothing already attached to `output` -- foreign,
        # or this family's own prior record -- describes the content just
        # published there. Start from a clean slate unconditionally, before
        # deciding whether this call has a fresh record of its own to write.
        sheet_entry: dict[str, Any] = {}
    else:
        sheet_entry = dict(derived_sheets.get(output, {}))

    if fields is None:
        # No helper projection this call: nothing of Lookup's own to
        # record. The branch above has already discarded whatever was
        # there; commit that removal if there was something to remove.
        if decoupled and had_entry:
            derived_sheets.pop(output, None)
            derived["sheets"] = derived_sheets
            meta["derived"] = derived
            out["_meta"] = meta
        return

    record: dict[str, Any] = {"lookup": lookup}
    # ... unchanged shape construction (symmetric/asymmetric key recording) ...
    sheet_entry["enrich_lookup"] = record
    derived_sheets[output] = sheet_entry
    derived["sheets"] = derived_sheets
    meta["derived"] = derived
    out["_meta"] = meta
----

The call site in `enrich_lookup()` threads `source` through:
`_write_provenance(out, output, source, lookup, resolved, fields)`. This is
a small, uncontroversial signature change local to one module and its one
internal call site — no public surface is affected.

This closes both Repro 4 and Repro 5 (<<repro-recap>>), because the
discard-on-decoupled-rebind step now runs unconditionally on `output !=
source`, whether or not this call has fresh helper provenance of its own —
and it now also correctly discards a stale *own* prior `enrich_lookup`
record at the replaced output (the "same-owner variant" Review 002
independently identified: a `helpers=None` decoupled rebind that leaves an
old `enrich_lookup` record in place has no fresh record of its own to
overwrite it with, so without this the old record would falsely describe
content it no longer does). The mechanism remains:

* *mechanical, not value-based* — the trigger is `output != source`, a
  parameter comparison already available at the call site; it never
  inspects cell values, never compares definition shapes, and cannot become
  Candidate C (<<L>>) by construction, because it never reads any record's
  *content*, only its *presence*;
* *generic, not FK-specific* — on a decoupled rebind it discards the
  *entire* prior `sheet_entry`, not a specific named subkey, so it does not
  need updating if a future producer family adds a third subkey to the same
  `_meta.derived.sheets.<sheet>` entry;
* *owner-local* — implemented entirely inside `enrich_lookup`'s own
  provenance writer, reusing the same write-time, per-sub-key pattern
  `fk_helpers/provenance.py::_write_helper_provenance` already established
  for FK's own stale-sheet cleanup (`_write_helper_provenance:69-95`,
  "Remove stale provenance for sheets without current FK defs"), applied
  completely at this site and, independently, at the one other evidenced
  site (<<H>>'s new subsection, <<find-d1-bound>>); it requires no new
  `_meta` key, no cross-family read at write time beyond the sibling-presence
  check already implicit in `derived_sheets.get(output, {})`, and no new
  primitive;
* *unconditional on provenance emission* — corrected in this pass: the
  trigger is now the `output != source` publication event itself, checked
  before, not after, the `fields is None` early exit, so every supported
  helper-projection mode (`helpers=None`, `helpers={}` with no matching
  policy, `helpers={"fields": [...]}`, value mode, formula mode) reaches it
  identically — the branching in `_resolve_fields`/`_fields_with_sort_helpers`
  that produces `fields is None` is orthogonal to value-vs-formula mode
  selection, so no mode-specific casing is needed;
* *a true no-op in the two ordinary cases* — when `output == source` (the
  self-extension shape), behavior is completely unchanged from today: the
  existing `_check_column_conflict` guard remains the only relevant check,
  and `sheet_entry` is extended, not discarded. When `output` is a brand-new
  sheet name with no pre-existing `_meta.derived.sheets` entry at all (the
  typical `enrich_lookup` shape, per the accepted research's own "Output
  frame name already exists -> replacing the prior mapping" note and the
  package's own test fixtures), `had_entry` is `False` and, for the
  `fields is None` sub-case, `out["_meta"]` is not touched at all — matching
  today's behavior exactly, confirmed against the maintained
  `test_enrich_lookup_no_helpers_returns_source_joined_on_key` test, which
  uses this exact shape.

=== Why H5 is unaffected

H5 (`reconcile_enrich_lookup_provenance`) remains exactly as it was: a
stateless, recompute-on-demand, *post*-mutation truthfulness predicate over
Lookup's own declared `helper_columns` and the frame's current columns,
called by `fk_helpers/provenance.py::_clean_helper_provenance` after *FK's*
own column removal. It answers a different question ("is Lookup's own
sibling record still truthful after FK deleted something") than the new
mechanism above ("should Lookup invalidate a foreign sibling record because
Lookup itself just replaced the frame's content"), and the two do not
overlap in the case they each handle: H5 never runs as part of
`enrich_lookup`'s own write, and the new mechanism never runs as part of FK's
cleanup. H5's existing job is still necessary for cases outside this
defect's scope (e.g. a *legitimate* FK deletion of its own helper that
happens to share a sheet entry with an unrelated Lookup record) and is left
untouched.

[[D6]]
[[L]]
== L. Formula/value and foreign-artifact equivalence disposition

*Design Question 6 (user/canonical collisions) answer.* <<F>> and <<D>> are
both stated purely in terms of "does FK have truthful evidence it produced
this column" — neither ever asks "was the current producer Lookup." A
caller-supplied ordinary column that happens to collide with FK's requested
helper label is handled identically to a Lookup-produced collision: skipped
at materialization (<<D>>), never claimed, never deleted by either cleanup
executor without truthful transient evidence (<<F>>). This generality is
structural, not a separately maintained rule — there is no producer-identity
branch anywhere in this design to keep in sync.

*Design Question 7 answer.* Value/semantic-equivalence adoption of a foreign
producer's physically present column (Candidate C) is *rejected outright and
not designed*. Reasons, all evidenced by the accepted research and review:

* Candidate A (decline materialization on collision) is already sufficient
  to close the confirmed defect (<<repro-closure>>); building equivalence
  machinery before it is needed contradicts the design brief's explicit "if
  A or B is sufficient, do not design generic adoption."
* Review 001 names the concrete risk directly: a Lookup-produced formula and
  an FK-produced value can display equal current results while carrying
  different update/lifecycle semantics; current value equality does not
  imply equivalent producer semantics — Review 001's own disproof of the
  original design's optional self-verified-reuse refinement (<<D>>, now
  removed) is a direct instance of this: even a check that inspects nothing
  but a producer's own prior *metadata shape*, not a foreign producer's data
  at all, can affirm a stale claim once the underlying record is no longer
  current. Value/shape equivalence of any kind is not identity.
* The two mechanisms this corrected design adds that inspect sibling state
  (<<K>>'s and <<H>>'s decoupled-rebind write-time invalidations)
  deliberately check only *presence*, never content, shape, or value, of a
  prior subkey — neither can drift into Candidate C because neither ever
  reads what a prior record claims, only whether one exists. This holds even
  under content coincidence: Review 002 independently constructed a case
  where the replacement content happens to be byte-identical to what the
  invalidated record described (two FK-enriched frames, one rebound from the
  other for an unrelated helper); dropping the old record is still correct,
  because *no current maintained contract transfers producer provenance from
  the old output object to the replacement object merely because labels,
  shapes, or values happen to coincide* — see <<P>>'s corrected wording on
  this point.

No equivalence/adoption machinery is designed for any site in this document.
If a future, separately evidenced need for adopting a foreign producer's
artifact arises, it is out of this design's authorization — see <<R>>.

* claim registration, claim release, a claim AST, a claim ledger, reference
  counting, a shared-claim protocol;
* a generic artifact registry, stable artifact IDs, global artifact
  identity, or rename-following identity;
* a central producer registry or whole-Domain materialization census;
* Trusted-Ingress redesign, persistence redesign, or schema-maintenance
  redesign;
* promotion, deprecation, removal, or merge of Lookup Enrichment as a
  product concept (<<R>>);
* value/formula equivalence or adoption machinery for a foreign producer's
  artifact (<<L>>);
* any new `_meta` root, sub-key, or schema-version bump — this design adds
  zero new metadata; it only changes which existing, already-registered
  entries are written or consulted, and for what purpose. This holds after
  the correction pass too: <<K>>'s invalidation mechanism *removes* an
  existing subkey under an existing path; it introduces nothing new.

Reconfirmed after the second pass specifically for the two findings that
could plausibly have reopened scope: <<K>>'s write-time mechanism reads only
subkey *presence*, never a foreign record's shape or content, so it does not
become the "physical-production verification override" the original design
brief explicitly disallowed; and removing the optional self-verified-reuse
refinement (<<D>>, FIND-D2) *narrows* this design further rather than
adding anything.

Reconfirmed again after this third pass, specifically because its own brief
named an explicit disallow list to check the corrected <<K>> and new <<H>>
mechanisms against: neither introduces generation IDs, a frame identity
UUID or any other stable/global artifact identity, a central invalidation
bus, a claim/reliance system, a generic producer ledger, or a whole-Domain
rebind framework. Both remain owner-local, presence-only checks implemented
inside their own module using their own existing code shapes (<<find-d1-bound>>
explains why a shared cross-family primitive is deliberately not designed
even though the pattern is now applied at two sites). No new `_meta` key is
introduced by either correction; both only ever *remove* an existing subkey
under an existing, already-registered path.

Reconfirmed once more after this fourth pass: generalizing <<H>> to cover
`apply_derived_column_policy`'s complete publication inventory (<<review-disposition-3>>)
adds no new mechanism against that same disallow list — it is the same
`_strip_consumed_provenance` call, reused at each publication's own
effective target within one already-mandatory module, keyed off that
target's own expression instead of a single raw parameter. No shared
cross-family publication framework, central invalidation bus, or generic
producer registry was introduced to close FIND-D13; the fix is strictly a
completeness correction to an already-accepted, already-scoped mechanism.

[[repository-boundaries]]
Also explicitly out of scope: Workbook-View-owned durable sheet helper
declarations (`_meta.sheets[*].helper_columns`). These are not
"untouched because they belong to a different owner" without further
qualification (Review 001 FIND-D5) — the actual, load-bearing distinction is
recorded in <<H>>: explicit human pipeline-author declaration via
`configure_workbook_view`, a canonical "helper values are not source truth"
contract independent of current producer, and a carrier purpose-built by
`BUG-HELPER-CLEANUP-CONTRACT-P4A` for exactly the persistence-surviving
cleanup-identity job this design's own durable-fallback removal now makes
more load-bearing (<<I>>). It remains untouched by <<H>>; its residual
staleness risk is recorded, not treated as zero, in <<R>>.

[[R]]
== R. Deferred follow-ups

* *Restoring automatic post-reimport FK-helper cleanup without a
  Workbook-View declaration* (named gap, <<I>>): if a real maintained or
  credible external consumer is later shown to need automatic deletion from
  durable FK relation policy alone after persistence — despite the
  already-existing, already-documented `configure_workbook_view` migration
  path named concretely in <<I>> — the necessary follow-up is a *new*,
  separately authorized design choosing between (a) a narrow,
  explicitly-scoped, FK-owned physical-production verification performed at
  cleanup time against current source/target data (weighing the
  formula/value risk named in <<L>> honestly, not reflexively), or (b) an
  explicit, opt-in, caller-asserted durable declaration analogous to XRef's
  guarded `drop_source` flag. Neither is designed or authorized here.
* *Whether `configure_fk_helpers`/`infer_fk_relations` should auto-populate
  the Workbook-View `helper_columns` carrier* (Review 001 FIND-D4, evaluated
  but not designed): would remove the dual-configuration burden the
  migration path in <<I>> otherwise imposes on pipeline authors, but crosses
  a family-ownership boundary (FK writing into a Workbook-View-owned
  durable structure) this design's narrowed scope does not authorize
  opening. Recorded as a real, evidenced candidate for a future, separately
  scoped design — not a rhetorical placeholder.
* *Reconsidering the removed optional self-verified-reuse refinement*
  (<<D>>, Review 001 FIND-D2): the refinement's original safety argument
  ("compares only FK's own metadata shape, never a foreign producer's") was
  correct for the question it was built to answer but insufficient against
  Review 001's disproof, because FK's own prior record could itself be
  stale. <<K>>'s write-time invalidation obligation now closes the specific
  staleness Review 001 used to construct that disproof within the
  authorized FK/Lookup pairing. That is grounds for a *future*, separately
  authorized reconsideration of the refinement — establishing affirmatively
  that FK's own prior transient record can be trusted to still describe the
  physical column before re-authorizing shape-based reuse — not for
  reinstating it in this pass.
* *Generalizing the decoupled-rebind invalidation pattern beyond the two
  now-evidenced sites* (<<find-d1-bound>>): the second pass deferred
  `derived_column_policy.py`'s own `output` parameter as an unevidenced
  analog; both independent third-pass reviews disproved that (FIND-D10), and
  this pass now fixes it at both sites (<<K>>, <<H>>). What remains
  genuinely deferred is *further* generalization: whether a *third* family
  exhibiting the same `source`/pre-existing-decoupled-`output` shape while
  sharing a `_meta.derived.sheets` entry should reuse a shared Domain-level
  primitive rather than implementing the same documented lifecycle rule
  locally. Two evidenced instances justified fixing both sites but not
  extracting shared infrastructure between them (<<find-d1-bound>>); a third
  evidenced instance would be new evidence for that question, not something
  to build ahead of it.
* *Registry and Functional wording* identified in <<M>> but not written.
* *Optional hygiene simplification* in `derived_column_policy.py`
  (<<9-facade>>): reuse `fk_helpers.derived_helper_columns_by_sheet` instead
  of a parallel reader, purely to reduce duplication flagged by an earlier
  review cycle. Not required for correctness.
* *Residual staleness risk of the Workbook-View `helper_columns`
  declaration* (Review 001 FIND-D5, named explicitly rather than implied
  away): nothing prevents a caller from repurposing a historically-FK- or
  Lookup-derived column label for genuine hand-entered data without also
  updating the separately-maintained `configure_workbook_view` declaration,
  and nothing enforces that the declared label is non-editable in the
  rendered workbook. The risk is real, structurally the same shape as the
  defect this design fixes for FK's durable relation policy, and smaller
  only because of the three distinctions named in <<H>> — not absent. Left
  unaddressed here because Workbook View remains a constraint boundary, not
  a mandatory Design-Phase site, per the accepted research's own
  narrowed-scope authorization.
* *Lookup Enrichment user-facing publication posture*: a separate maintainer
  question (not decided here, not decided by this design) is whether Lookup
  Enrichment's independent user-facing product status should be marked, in a
  future DMC/publication-posture convention (e.g.
  `user_facing_documentation: false` with an explicit reason), as
  not-yet-established rather than promoted or merged with FK Helpers. This
  design takes no position and does not touch Lookup's user-facing
  documentation, DMC, or product status. Recorded here only so the intent
  is not lost.
* *Architecture guard* for the boundary in <<9-facade>> (recommended in
  <<O>>, not mandatory; Review 001 recommends promoting it to mandatory
  given it also now guards <<F>>'s corrected sufficiency claim — left to
  implementer/maintainer judgment, not mandated here).

[[S]]
== S. Open questions

* The two former sign-off items in the original design are now closed
  rather than open: whether the new Core reporting primitive needs
  `interfaces_and_gates` sign-off is moot because it is designed as private
  (<<E>>, FIND-D8); whether `fail_on_mismatch` should raise on authorization
  refusal is resolved as "never" (<<J>>, FIND-D7).
* Whether the four tests dispositioned in <<I>> should be edited in place
  (inverting their existing assertions) or deleted and replaced by fresh
  tests with new names reflecting the new contract — both satisfy this
  design's requirement that the *behavior* they cover be correctly proven;
  the choice is a repository-convention question for the implementer, not
  an architectural one. The same applies to the additional, Slice-3-local
  disposition of `test_enrich_lookup_provenance_write_preserves_nested_caller_ownership`
  (Review 002 FIND-D11).
* Whether <<K>>'s and <<H>>'s invalidation triggers should be scoped even
  more narrowly than "`output != source`" (for example, only when `output`
  is *also* not itself one of the join keys or otherwise structurally
  related to `source`) — this design deliberately does not add that
  narrowing because no evidence was found that the plain `output != source`
  trigger over-invalidates in any currently supported pipeline shape (the
  over-invalidation regression tests in <<O>> exist specifically to catch
  this if it is wrong, at both sites now); an implementer who finds a
  legitimate `output != source` case that should *not* invalidate should
  treat that as new evidence for a follow-up, not silently narrow the
  trigger without a test proving why.
* Whether a future, *third* family exhibiting the decoupled-rebind shape
  identified in <<find-d1-bound>> should reuse <<K>>'s/<<H>>'s exact
  mechanism locally, or justify extracting a shared Domain-level primitive
  — deliberately left undecided per <<R>>'s generalization entry; two
  evidenced instances justified fixing both sites in this pass but not
  extracting shared infrastructure between them; premature to decide
  further without a third evidenced instance.

[[T]]
== T. Design readiness verdict

*READY FOR INDEPENDENT FINAL FINDING CLOSURE*, not implementation-ready. Per
the correction brief's own gate, this design does not declare itself
implementation-ready merely because this pass resolves FIND-D13, the sole
remaining open finding (and, through it, the sole remaining open path of
FIND-D1); Review 001 must independently close FIND-D13 against the actual
corrected text before implementation begins. The lifecycle rule itself is
not reopened by this pass — Review 001's Section 15 already confirmed it
*ACCEPTED* — this pass completes that rule's *enforcement* at the one site
shown to need it: `apply_derived_column_policy`'s two physical publications
(the primary payload write, keyed to its effective target `payload_target =
output or source` rather than raw `output`, and the independent `findings`
write) are now both reasoned about and both invalidate any pre-existing
provenance at their own effective target before the call returns
(<<dcp-invalidation>>). This closes all eight reproduced variants
(<<repro-closure>>), using no mechanism beyond what was already accepted:
the same `_strip_consumed_provenance` helper, reused at each publication's
own effective target in one already-mandatory module, keyed off that
target's own expression. It introduces no new metadata, no claim/reliance
infrastructure, no generation IDs, no central invalidation bus, no shared
cross-family publication framework, and no value/equivalence machinery — a
completeness correction to an already-accepted rule's enforcement, not a
new mechanism.

== Independent review recommendation

A fourth independent adversarial review of this *corrected* design artifact
is recommended before any implementation, test, or canonical-document change
proceeds from it — the same review discipline already applied to the
research artifact this design builds on, and to this design's own first
three reviews. A reviewer should independently verify, at minimum: that the
complete local publication inventory in <<dcp-invalidation>> is actually
complete against the current `apply_derived_column_policy` body (exactly two
`out[<target>] = <DataFrame>` statements, no third); that FIND-D13 Variant A

receives the same-target strip, not the empty-name no-op — by re-running or
re-deriving Review 001's own `output=""` reproduction against the corrected
pseudocode; that FIND-D13 Variant B is genuinely closed — `findings`
naming an existing frame (including `source`) is unconditionally

reasoning (sequential invalidation against accumulated metadata, not a

claim/ledger/global-identity/generation-ID/central-invalidation-bus/shared-
publication-framework machinery has been reintroduced anywhere in this pass
