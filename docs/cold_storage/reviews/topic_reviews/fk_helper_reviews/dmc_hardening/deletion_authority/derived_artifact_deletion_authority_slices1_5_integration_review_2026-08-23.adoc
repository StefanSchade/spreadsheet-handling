== 2. Accepted integrated contract

Restated once, as the composed system the rest of this review verifies
against (accepted design Section F, as corrected through FIND-D13 and
FIND-S5-01):

A cleanup executor may delete a column identified through an FK-attributed
name if and only if that name is currently present in
`_meta.derived.sheets.<sheet>.helper_columns` -- truthful, same-run,
materialized-only transient provenance that has not since been invalidated
by a decoupled rebind of that sheet. Durable `_meta.helper_policies.fk`
never independently authorizes deletion. Two other, structurally distinct,
non-FK deletion identities remain untouched and legitimate: Workbook-View's
explicit `_meta.sheets[*].helper_columns` declaration, and Lookup's own
`enrich_lookup` provenance over its own artifact. Diagnostics must describe
the executor's *actual final* behavior, not merely its intent.

== 3. Materialization + provenance lifecycle (Invariant 1)

`core/fk.py:279-375` -- `_FkHelperMaterializationResult` /
`_materialize_fk_helpers` is exactly the design's Section E reference shape:
per-definition, `helper_col in first_cols` (line 320) routes to
`skipped_existing`, absence routes to `materialized`; `apply_fk_helpers`
(line 378) is an unchanged-signature compatibility wrapper returning only
`.frame`. `fk_helpers/enrich.py:122-140` builds
`materialized_by_frame[frame_name] = result.materialized` -- exactly the
provable set, never `skipped_existing` -- and passes it to
`_write_helper_provenance`, which (`fk_helpers/provenance.py:51-68`) writes a
`helper_columns` entry only for sheets with a non-empty materialized list and
removes stale entries (lines 69-95) for sheets with none. No
self-verified-reuse fallback exists anywhere in this path (grep for
`skipped_existing` confirms its only consumer is the diagnostic list built
alongside `materialized`, never merged into it).

Attacks re-verified directly against this code, all independently confirmed
correct: all-new helpers (both land in `materialized`); all-collision (both
land in `skipped_existing`, no provenance entry, physical values from the
pre-existing column untouched); mixed fresh/collision
(`test_mixed_definitions_report_each_independently`,
`test_mixed_definitions_provenance_contains_only_materialized`); repeated FK
enrichment call over an already-materialized frame
(`test_second_call_does_not_reaffirm_provenance_from_collision` -- the second
call's own re-collision lands in `skipped_existing`, so provenance is *not*
reaffirmed, matching the design's explicitly accepted, deliberately
conservative replay behavior, not a regression). "Requested artifact
identity != physical production" holds throughout: nothing in `core/fk.py`
or `enrich.py` ever treats a durable relation's mere existence as evidence of
this run's physical write.

*Verdict: intact, no gap.*

== 4. Replacement/rebind lifecycle (Invariant 2)

`enrich_lookup/operation.py:495-566` matches the design's Section K
reference implementation statement-for-statement: `decoupled = output !=
source` (line 520) is evaluated first, unconditionally, before the `fields is
None` short-circuit (line 521) -- so `helpers=None` decoupled rebinds reach
invalidation exactly like fields-bearing ones (closes FIND-D9). On
`decoupled`, `sheet_entry` starts from `{}` (line 534) regardless of what
subkeys the prior entry held -- generic, not FK-specific, and correct for a
replacement column that happens to reuse a formerly FK-produced label. On
`not decoupled` (`output == source`), `sheet_entry` is the *merge* branch
(`dict(derived_sheets.get(output, {}))`, line 536) -- the existing sibling
`helper_columns` entry is preserved by identity, matching
`test_enrich_lookup_same_source_preserves_sibling_fk_provenance_helpers_*`.

Composition with Slices 1-2 verified directly: FK truthfully claims a helper
(Section 3 above) -> Lookup's `output != source` call replaces the physical
frame -> `_write_provenance`'s `decoupled` branch discards the entire prior
sheet entry, including FK's `helper_columns`, before this call's own record
(or nothing, if `fields is None`) is written -- confirmed by
`test_enrich_lookup_fields_bearing_decoupled_rebind_invalidates_stale_fk_provenance`
and `test_enrich_lookup_helpers_none_decoupled_rebind_invalidates_stale_fk_provenance`.
No later executor can reconstruct the stale claim: neither `drop_helpers` nor
`apply_derived_column_policy` reads anything but the current
`_meta.derived.sheets` state at call time, and that state no longer contains
it. The `helpers=None` case, `same-label` collision case, and brand-new
`output` no-op case (`out.get("_meta")` untouched,
`test_enrich_lookup_brand_new_output_decoupled_rebind_is_a_no_op`) all
independently re-verified against the current file.

*Verdict: intact, no gap.*

independently authorizes), confirmed at runtime by the still-green

which asserts survival at both sites from one shared fixture.

== 6. DCP publication lifecycle (Invariant 6)

Direct grep of every `out[...] =` write in the current
`derived_column_policy.py` finds exactly three: `out[payload_target] =
cleaned` (line 181, unconditional), `out[findings] =
findings_to_frame(...)` (line 209, `warn_on_mismatch` only), and
`out[META_KEY] = new_meta` (line 216, metadata, not a `DataFrame`). No fourth
publication exists; `enforce_derived_column_policy_frame` returns a tuple and
writes into no mapping. This independently reproduces the design's own and
Review 001 S16.1's inventory.

* *A -- `payload_target == source`* (`output` is `None`, `""`, or literally
  `source`): same-target branch (lines 193-196), strips `source`'s own
  consumed provenance -- continuation semantics, unchanged in effect from
  pre-Slice-5 `replacing` behavior. All three aliases confirmed to resolve
  identically by `payload_target = output or source` (line 180), the single
  place raw `output` feeds a lifecycle decision in the module (grep
  confirms).
* *B -- `payload_target != source`*: decoupled branch (lines 197-201),
  invalidates any pre-existing entry at `payload_target` only if one exists
  (`test_payload_decoupled_target_invalidates_preexisting_provenance`,
  `test_payload_decoupled_new_frame_target_is_true_noop`); `source`'s own
  entry is never touched by this branch.
* *C/D -- `output=None` / `output=""`*: both alias to `payload_target =
  source`, same-target branch, per A --
  `test_payload_output_empty_string_and_none_both_alias_to_source_target`
  (parametrized) confirms both.
* *E -- findings publication*: unconditional under
  `policy == "warn_on_mismatch"` (lines 208-213), always freshly synthesized,
  its own invalidation runs regardless of what `findings` equals --
  `test_findings_publication_invalidates_preexisting_provenance_at_target`.
* *F -- `findings == payload_target`*: payload publish-and-invalidate runs
  first (lines 193-201) against `new_meta`, findings publish-and-invalidate
  second (lines 208-213) against the *same, already-updated* `new_meta` local
  -- the findings write is the last physical writer to that name and its own
  invalidation re-checks accumulated state, a safe no-op if payload's branch
  already stripped it. Directly confirmed physically, not merely at the
  provenance level, by
  `test_findings_equals_payload_target_publication_order_leaves_no_stale_provenance`
  (`out["B"].columns == FINDING_COLUMNS`).

`_strip_consumed_provenance` (lines 510-549) is the single reused primitive
at all three invalidation call sites; it copies rather than mutates its
input at every level (`dict(meta)`/`dict(derived)`/`dict(sheets)`) and prunes
empty containers.

*Verdict: intact, no gap. No third publication bypasses lifecycle handling.*

== 8. Diagnostics/failure semantics (Invariants 9, 10)

=== 8.1 Diagnostic truthfulness (FIND-S5-01 re-verification)

`_fk_deletion_unauthorized_candidates` (lines 477-507) computes
`present_labels` from `cleaned.columns` (line 502) -- the frame *after*
`enforce_derived_column_policy_frame`'s own drop, i.e. after every
currently accepted deletion authority (transient FK provenance,
Workbook-View, Lookup's own identity) has already had its chance to remove
the column. A column any of those authorities validly removed is, by
construction, absent from `cleaned` and therefore never reaches the
candidate set. This is the exact post-fix shape the Slice-5 closure review
verified against `86eebab`; independently re-confirmed here by reading the
current file directly (not by re-trusting the prior review's quoted diff)
and by the still-passing
`test_workbook_view_authorized_removal_emits_no_false_fk_deletion_unauthorized`
/ `test_lookup_identity_authorized_removal_emits_no_false_fk_deletion_unauthorized`
pair in this run's own full-suite execution (Section 12).

`fk_helpers/drop.py`'s `_log_durable_policy_only_survivors` (lines 99-133) is
independently gated the same way: it only fires for a sheet *absent* from
`provenance_by_sheet` and only when the named column is still physically
present (`source_frame_has_column`) -- symmetric truthfulness discipline at
the sibling executor, though log-only (no findings-frame surface exists for
`drop_helpers`).

=== 8.2 Failure/strictness semantics

`_fk_deletion_unauthorized_findings` (lines 410-474) constructs findings with
`severity="warn"` unconditionally and returns `[]` under any policy other
than `warn_on_mismatch` (routing instead through `log.warning`, lines
466-473). `failures = [finding for finding in found if finding.severity ==
"fail"]` (line 138) can therefore never contain an authorization-refusal
entry under any policy, including `fail_on_mismatch` -- the diagnostic is
structurally incapable of reaching the `raise ValueError(...)` path (line
139-140). Ordinary genuine `severity == "fail"` value-mismatch findings
(from `_check_enrich_lookup_values`) are computed independently and their
raise behavior is untouched.

`drop_helpers`'s `missing_fk_policy_error` precondition (`relations is None
and not provenance_by_sheet`, line 54) remains distinct from, and unaffected
by, the fail-closed deletion-refusal path: after a reimport with surviving
durable FK relations, `relations is not None`, so no precondition error
fires even though provenance is absent -- the column simply survives with a
diagnostic, matching Section G's disposition exactly. No accidental coupling
was found between deletion authorization and mismatch strictness anywhere in
either executor.

*Verdict: intact, no gap.*
