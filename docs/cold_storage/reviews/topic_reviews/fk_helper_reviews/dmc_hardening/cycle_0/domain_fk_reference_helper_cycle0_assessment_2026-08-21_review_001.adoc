== 2. Review Area 1 -- FK family boundary

*Verdict: supported, high confidence, no correction required.*

Direct code inspection confirms the family shares one metadata/lifecycle
problem rather than merely a package: `drop.py::_columns_to_drop_by_sheet`,
`policy.py::resolve_v2_fk_relations`, `provenance.py`, and
`validations/fk_helpers.py::_expected_helper_columns_by_sheet` all consume
the *same* v2 relation shape (`source_frame`, `source_column`, `target_frame`,
`target_key`, `helper_columns[].column`) with the same
provenance-preferred/policy-fallback precedence repeated verbatim in three
places (`drop.py`, `validations/fk_helpers.py`,
`derived_column_policy.py::_safe_policy_helper_names`). A single-sided change
to that shape would silently break materialization, validation, layout, and
both cleanup paths -- exactly the DMC's family test (internal semantic and
metadata coupling; external references narrow and explicit).

Layout (`reorder_helpers_next_to_fk`) living in the historically mixed
`transformations/helpers.py` module does not weaken the family claim: the
topology assessment's own evidence table already flags that module as
"historical aggregation with a real header-shape pair among other helpers,"
i.e. a package-hygiene question, not an ownership question. The DMC is
explicit that package layout is not ownership evidence in either direction.

FK-helper validation is genuinely family-owned and not shared reference-rule
plumbing: `validate_fk_helpers`'s value-mismatch and unresolvable-FK checks
require the FK relation's `target_key`/`value_field` to mean anything, which
only the FK relation model supplies. This differs in kind from
`reference_validations.py::validate_references`, which validates declarative
primary/unique/foreign-key rules independent of the FK-helper projection.

One accurate pre-existing observation from the Cycle-0 artifact (F.2) was
independently confirmed in code: `check_duplicate_ids` inside
`validate_fk_helpers` iterates *every* sheet (falling back to
`defaults["id_field"]` for sheets that are not FK targets), not just
FK-related ones, and is only reachable standalone. The artifact's disposition
(a genuine but non-blocking Local Human Readability hotspot, not an ownership
defect) is correct and needs no correction.

== 3. Review Area 2 -- Lookup separation

*Verdict: supported, high confidence, no correction required, with one
evidence-provenance caveat (<<f-006>>).*

`enrich_lookup/policy.py::_ResolvedKeys` and `_resolve_join_keys` confirm the
artifact's central claim: Lookup's authoritative Intent is an explicit
source/lookup/output projection request with its own symmetric/asymmetric
key resolution, `missing`/`order`/`allowed`/`default` policy, and no read of
`_meta.helper_policies.fk` or FK relation state anywhere in the module.
`configure_lookup_helpers` in `helper_policies.py` writes to
`_meta.helper_policies.lookup.<lookup>`, a namespace FK code never reads.
`schema_maintenance/meta_update.py` independently confirms the separation at
a third owner: `_handle_fk_policies` and `_handle_lookup_policies` are two
distinct functions walking two distinct metadata roots, each with its own
malformed-shape handling -- schema maintenance, a genuinely independent
capability, already treats FK and Lookup as separate facts to maintain.

The counterfactuals the review prompt requested were run explicitly:

* *Merge counterfactual:* a merged "helper" family would need one relation
  model that supports both durable source-column-keyed intent (FK) and
  explicit output-frame-keyed projection with asymmetric keys (Lookup) inside
  one shape. No such unified shape exists in the current metadata registry,
  and `configure_fk_helpers`/`configure_lookup_helpers` do not share a
  resolution function beyond incidental helpers (`_dedupe`,
  `_resolve_allowed_helpers`/`_resolve_default_helpers`, which are themselves
  small enough that shared use is weak evidence per the DMC's "evidence is
  not ownership proof" section). Merging would not shrink any external
  reference; it would only make the merged family's internal state space
  larger and its consumers (schema maintenance, cleanup, validation) harder
  to reason about, since each would need to re-derive which half of the
  merged model applies.
* *Separation counterfactual:* keeping them separate leaves each capability's
  external contract narrow -- Lookup exposes one policy root and one
  provenance shape; FK exposes one relation root and one provenance shape.
  The one place they collide (H5) is exactly one narrow function, which is
  the strongest possible evidence that separation, not merger, minimizes
  cross-owner surface.

Lookup's lack of an inverse is semantic, not accidental: `enrich_lookup`
never reads FK relation Intent, has no relation-declaration step analogous to
`configure_fk_helpers`/`infer_fk_relations`, and its provenance
(`_meta.derived.sheets.*.enrich_lookup`) records a one-way output projection
rather than a durable source-column relation. There is no evidence of an
abandoned or partially-implemented FK-style declare/materialize/drop
lifecycle for Lookup that a hardening cycle would be re-inventing; this is a
different Intent shape by design.

== 5. Review Area 4 -- H5 first slice

*Verdict: SLICE ACCEPTED WITH CORRECTION.* Lookup ownership of the
reconciliation rule is correct and well-evidenced; two concrete
implementation-readiness gaps must be closed as part of the slice, not after
it (<<f-001>>, <<f-003>>).

=== 5.1 Ownership: why Lookup (option A), not B/C/D/E

Direct inspection of `_clean_helper_provenance` shows the predicate needs
exactly two inputs: Lookup's own declared `enrich_lookup.helper_columns` list
(a shape only Lookup defines and only Lookup's writer,
`enrich_lookup/operation.py::_write_provenance`, produces) and the current
frame's column labels after FK's own removal has already run. It needs *no*
FK-specific knowledge -- not the relation shape, not `target_key`, not
`value_field`. That is the strongest possible evidence for Lookup ownership
under the DMC's family test: the fact that is being interpreted ("is my
provenance record still truthful") is entirely Lookup's own declared
contract.

* *Option B (derived-cleanup owns it):* rejected. `apply_derived_column_policy`
  is a different, reimport-time entry point that is never invoked by
  `remove_fk_helpers`/`drop_helpers`. Routing H5 through it would require a
  new call path between two currently-independent registered steps for no
  benefit; the predicate does not need cleanup-policy's drop/warn/fail
  distinction at all.
* *Option C (neutral coordinator):* considered and rejected as
  over-engineering for one call site. `derived_column_policy.py` already is
  the project's "neutral coordinator" pattern, and it is not the caller here.
  Introducing a third module solely to mediate one FK-to-Lookup call adds
  navigation without adding a real shared contract (the DMC's own
  "extraction that merely adds jumping" caution in the Human Readability
  guide applies directly).
* *Option D (FK owns it because FK drop causes the transition):* rejected.
  Causing a state transition is not the same as owning the semantic
  truthfulness of another owner's provenance about that transition. FK has no
  way to decide when Lookup's own record is stale except by consulting
  Lookup's own declared contract -- which is exactly what moving the
  predicate into Lookup formalizes, rather than changes.
* *Option E (current behavior is sediment; change it now):* rejected for this
  slice, correctly. No evidence surfaced (by the Cycle-0 artifact or this
  review) that the current conditional-preservation behavior is wrong; the
  DMC requires evidence to justify breaking a working contract, not merely
  the opportunity of a refactor.

=== 5.2 Dependency direction and circularity

Verified directly: `fk_helpers/*.py` currently imports nothing from
`enrich_lookup`, and `enrich_lookup/*.py` currently imports nothing from
`fk_helpers`. `derived_column_policy.py` imports from `fk_helpers`'s public
facade only. Adding one narrow `fk_helpers -> enrich_lookup` edge (FK-drop
composition calling a small Lookup-owned public function) introduces no
cycle: `enrich_lookup` has no dependency back onto `fk_helpers` or
`derived_column_policy`, and nothing else in the graph would need to depend
on `fk_helpers` through `enrich_lookup`. Dependency direction remains legal
under the DMC's "narrow, explicit, few" cross-family standard.

This review found one implementation-readiness gap the Cycle-0 artifact did
not surface: the cross-family import guard test
(`test_no_cross_family_internal_imports.py`) currently protects only
`fk_helpers` and `discriminator_split` -- its `GUARDED_INTERNAL_PREFIXES`
dictionary has no entry for `enrich_lookup`. Once the first slice makes
`fk_helpers` a real cross-family caller into `enrich_lookup`, nothing
prevents a *future* change from reaching past `enrich_lookup`'s public facade
into `operation.py`/`policy.py` internals directly, silently widening the
handoff the slice deliberately narrows. See <<f-003>>.

=== 5.3 Malformed and partial-overlap ownership

The review prompt asked who owns malformed-provenance handling, partial
overlap, and empty-container pruning. Partial overlap and empty-container
pruning are already correctly Lookup's concern under the proposed
disposition (its own `helper_columns` list is the only input that decides
"still present"), and empty-container pruning after the subkey is removed
remains a mechanical, shape-independent step that can stay with whichever
side performs the final mutation (currently FK-drop's `copy_derived_path`
pattern) without changing meaning.

Malformed-provenance handling is where this review found a genuine,
previously unflagged gap: current `_clean_helper_provenance` performs *no*
shape validation on `enrich.get("helper_columns")` before iterating it
(`{str(c) for c in (enrich.get("helper_columns") or [])}`). If that field is
present but not a list -- for example a string, an int, or a dict -- the
predicate either silently misinterprets it (a dict yields its keys as
"columns") or raises an opaque, untyped `TypeError` from inside FK's private
helper, with a traceback that names FK code for a defect that is Lookup's
provenance shape. This contrasts sharply with
`derived_column_policy.py::_validated_enrich_spec`, which raises a clear,
path-naming `ValueError` for the identical malformed shape. No test in
`test_derived_provenance_nested_ownership.py` currently exercises a malformed
`enrich_lookup.helper_columns` value at this seam. See <<f-001>>; this is the
review's most important individual finding because the Cycle-0 artifact's own
completion-evidence bullet ("Lookup tests prove its conditional
reconciliation for present, absent, malformed-as-currently-specified, and
repeated states") presumes a "currently-specified" malformed behavior that,
on inspection, does not actually exist as a deliberate contract -- it is
undefined, type-dependent behavior that the implementer must consciously
choose to freeze or correct.

== 7. Review Area 6 -- State/meta lifecycle

*Verdict: accurate; the data/artifact-identity/projection-replay distinction
is valid and earns its keep.*

The lifecycle diagram in the Cycle-0 artifact (D.1) matches what the
inspected code actually does: `enrich_helpers` materializes from durable
relation policy and writes transient provenance
(`_write_helper_provenance`); `drop_helpers` consumes that provenance with a
durable-policy fallback and never reads spreadsheet cell values to decide

code path in `fk_helpers/` or `enrich_lookup/` reads back a materialized

The three-way distinction (data reconstruction / artifact-identity
reconstruction / projection replay) is useful and not merely renamed
vocabulary: "artifact-identity reconstruction" precisely names what
`drop_helpers`'s policy fallback does (recover *which columns* to remove
after transient provenance is gone, from durable relation policy) without
claiming any data-level inverse exists. This is a real, load-bearing
distinction the DMC's provisional Projection vocabulary supports without
being stretched -- the artifact does not claim FK or Lookup are bijective
projections, and the code confirms neither is.

== 11. Review Area 10 -- Local Human Readability

*Verdict: correctly applied; `_clean_helper_provenance` is the right hotspot,
and this review adds one concrete detail the artifact's discussion did not
reach (<<f-001>>).*

Direct inspection agrees with F.1: `enrich_helpers` (`enrich.py`) is a
genuinely phase-coherent 36-line body with two non-local-reason comments
(the `detect_fk` two-key resolution-timing comment, and
`_preserve_source_flatness`'s replay-safety rationale referencing a named
historical bug) that a reader could not reconstruct from the code alone.
Splitting it further would remove exactly the kind of algorithmic locality
the Human Readability Guide protects.

`_clean_helper_provenance` is correctly identified as the highest-value
hotspot, and this review's independent reading sharpens *why*: it is not
merely that the function name/module implies FK-only ownership while
containing Lookup logic (a naming problem) -- it is that the embedded logic
has a materially weaker error contract than the equivalent logic living in
its rightful owner's neighborhood (`derived_column_policy.py`'s
`_validated_enrich_spec`). A reader auditing `remove_fk_helpers` today must
notice, without being told, that a bare `.get(...) or []` with no isinstance
check sits inside an otherwise metadata-driven, well-validated FK module.
Moving it behind a Lookup-owned function is therefore not "extraction that
merely adds jumping" (the anti-pattern the guide warns against) -- it
relocates code to where its error-handling quality can be judged against the
right sibling logic (Lookup's own provenance validation) instead of against
FK's unrelated conventions. This satisfies both the ownership test and the
bounded-reconstruction test simultaneously, which is the strongest
justification the Human Readability Guide recognizes for `implement` over
`accept`/`defer`.

`enrich_helpers` (F.3's "topology scattered but locally coherent") point is
also independently confirmed: the FK lifecycle genuinely spans five files
plus `core/fk.py`, yet each individual file remains locally readable. This is
a real, not rhetorical, distinction between family/repository locality and
Local Human Readability, and the artifact does not conflate the two.

=== FIND-001 -- Malformed Lookup-provenance shape at the H5 seam is undefined, not "currently specified"

Severity:: IMPORTANT
