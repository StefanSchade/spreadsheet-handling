== 1. Executive summary

The spreadsheet write chain -- `compose_workbook` -> IR passes -> `build_render_plan` -> format renderer -- is a sound and proportionate design for the demonstrated requirement: two spreadsheet renderers (openpyxl for XLSX, odfpy for ODS) execute one backend-neutral `RenderPlan`, the parity tests prove that the same plan yields the same parsed result on both, and architecture guards keep raw formula syntax inside the two adapters. The non-spreadsheet sinks (JSON, YAML, XML, CSV directories, `discard`) correctly bypass that chain. Designed today from the same requirements, substantially the same shape would be built.

The defects are not in that shape. They sit at the two places the chain touches the outside world:

* *The XLSX sink activates a capability nobody authorized.* Every ordinary payload string longer than one character that starts with `=` is bound by openpyxl as a formula cell (`openpyxl/cell/cell.py` lines 198-199). Trusted Ingress explicitly keeps formula-looking strings as ordinary Strings; `ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY` Decision 5 assigns "security-sensitive interpretation" to the sink; the XLSX renderer implements no policy at all. ODS writes the same string inertly. The project's own XLSX reader (`data_only=True`) then returns the formula's cached value -- empty for a freshly written file -- so the value is silently lost or, after an application recalculation, silently replaced. This is a known, documented, unowned gap; it is the one finding here with an adversarial story, and its correction is a few lines in one file.
* *Persistence has no durability model and one ingress-accepted value that the XLSX sink cannot serialize.* All sinks open their target for writing in place (`ZipFile(..., "w")`, `open(..., "w")`); a serialization error after that point leaves a truncated artifact where the previous good one was. A timezone-aware `DateTime` -- accepted by ingress by documented decision -- is exactly such a value for XLSX: openpyxl raises during `wb.save`, not at assignment. Directory sinks are overlay writers: a frame dropped or renamed by the pipeline leaves its stale file behind, and the next reimport of that directory reads it back as a live frame.

Beyond those, the subsystem carries a measurable amount of accretion that the current runtime no longer consumes: three empty "export marker" cells written by `MetaPass` and a two-layer strip helper that exists only to remove them again; the canonical `_meta` dict serialized to a JSON blob in the composer and re-parsed by three passes in the same process, with the blob-decoding rule (JSON first, `ast.literal_eval` fallback) copied five times; four passes that each copy one options key into a dunder key for the plan builder to read back; a parse-side `WorkbookIR` that reconstructs validations, named ranges, freeze and filter hints that no production consumer reads; a legacy `_p1_validations` path with no producer; a parsed-but-ignored `excel:` configuration section; a `BackendBase` class hierarchy whose default `write_multi` silently overwrites one path per sheet and which the router does not use. None of this causes an observable failure today; all of it is deletable with existing tests as the safety net.

Findings by severity: BLOCKING 0; IMPORTANT 3 (IOR-01 to IOR-03); MINOR 11 (IOR-04 to IOR-14); INFO/WATCH 8 (IOW-1 to IOW-8).

== 4. Part B -- Responsibility boundaries

Questionable boundaries, each judged for observable effect:

. *Sink capability owned by nobody.* Ingress: "formula-looking strings remain plain strings" (`core/scalar_values.py` lines 21-23). ADR Decision 5 and `architectural_layers.adoc` lines 349-359: "Security-sensitive interpretation belongs to the sink". XLSX renderer: `ws.cell(row, column, value=val)` with no string handling (`openpyxl_renderer.py` lines 225-238, 271-273, 245-247). *Observable failure:* yes (IOR-01).
. *Sink-capability vocabulary parallel to the router.* `projection.py` line 46 `frozenset({"xlsx", "ods"})` versus router `SAVERS` keys incl. `calc`. *Observable failure:* spurious rejection of `output.kind: calc` for formula helpers (IOR-04).
. *Persistence encoding used as in-process transport.* `compose_workbook` writes `json.dumps(workbook_meta)` into `hidden_sheets["_meta"].meta["workbook_meta_blob"]` (`layout_composer.py` lines 372-376); `apply_all` re-seeds it if missing (`passes/__init__.py` lines 38-45); `StylePass`, `ValidationPass`, `ProtectionPass` each call `_workbook_meta(doc)` which `json.loads` it again (`passes/_base.py` lines 114-133). Aesthetic plus duplicated decoding rule; no failure (IOR-08).
. *Options copied through four trivial passes.* `ColumnWidthPass`, `TextOrientationPass`, `HorizontalAlignmentPass`, `VerticalAlignmentPass` each copy `options[<family>]` to `meta["__<family>"]` for `flow.py` to read. No failure; derived-state symmetry (section 13).
. *Format-independent formula addressing done twice at format level.* `_collect_formula_context` (XLSX, lines 93-109) and `_collect_sheets` headers/data_bounds (ODS, lines 340-376), plus verbatim copies of `_header_col`/`_data_bounds`. No failure today; divergence risk (IOR-09).
. *Parse-side meta interpretation in adapters.* Both `parser_interpretation.py` modules carry an identical `OPTION_HINT_KEYS` tuple and `build_sheet_meta_hints`; both parsers read `legend_blocks[*].resolved`. Duplicated, not wrong; the projection later discards `options` anyway (only tests read them).
. *Path rewriting in the adapter entry.* `Path(path).with_suffix(".xlsx")` (`xlsx_backend.py` line 38; `ods_backend.py` line 38; again in `odf_renderer.py` line 700). *Observable:* yes for operator paths whose last segment contains a dot (IOR-05).
. *Value coercion in the router-facing savers.* `save_xlsx`/`save_ods` coerce any non-carrier frame value with `pd.DataFrame(obj)` (lines 118 / 107). Reachable only outside `orchestrate` (ingress admits only DataFrame/`ExactTable`), except `ExactTable`, which ingress admits and every saver rejects (IOR-12).
. *Domain semantics in directory writers.* JSON and XML drop columns whose first header segment starts with `_` in the MultiIndex branch only (`json_backend.py` line 135, `xml_backend.py` lines 167-168, 176). Flat-header JSON keeps helper columns; flat XML drops them. Cleanup is a Domain step by ADR; this residual writer-side filter is inconsistent across the two branches and the two formats. No test asserts it; INFO in section 15.

No backend owns "substantially more than IO adaptation". The ODS renderer's `_BufferedSheet` grid is a legitimate format necessity (ODS is row-major XML; the plan is op-major).

== 6. Part D -- Formula / controlled-role / capability activation

*Types that can reach sinks.* Two controlled value classes exist (`core/formulas.py`): `ListLiteralFormulaSpec` (validation intent; never a cell value) and `LookupFormulaSpec` (cell value). `GroupedMatrix` is a controlled structural carrier that the composer projects to an exact table; `ExactTable` is an ordinary structural carrier by ingress definition (`structural_admission.py` lines 138-140) but no sink accepts it (IOR-12).

*Where authorization is expressed and where it acts.* `finalize_managed_state` (`managed_pipeline.py` 378-399) authorizes each *tracked role* against `sink_kind` using the name set `FORMULA_CAPABLE_SINK_KINDS` and `MANIFEST_ADAPTER_SINK_KIND`. It acts on predicted role state, not on the frames (the assurance review's TIA-02/03; not re-litigated here). The renderers act on *actual values*: `isinstance(value, LookupFormulaSpec)` at the cell (`openpyxl_renderer.py` 190, `odf_renderer.py` 569). The renderer has no knowledge of authorization and is not expected to (ADR "writers stay dumb"). The uncertified fallback re-establishes ordinary conformance, which rejects any surviving `LookupFormulaSpec` (`managed_pipeline.py` 168-180). The composite is therefore closed for `FormulaSpec` values *inside `orchestrate`*: a spec reaches a renderer only if a certificate placed it and the sink kind is in the set. Outside `orchestrate` (direct `save_xlsx`), any spec renders; this is the documented caller-precondition surface (`interfaces_and_gates.adoc` lines 119-127, `BackendBase` docstring).

*Do unsupported sinks fail closed?* Inside `orchestrate`: yes, before the saver runs, with a typed error naming role kind, frame, and sink (`test_trusted_ingress_e5_managed_lifecycle.py` lines 348-360 prove `json_dir` rejection and that no output directory is created). Outside: JSON/YAML fail with untyped errors after truncating the target; XML/CSV silently stringify the dataclass (matrix).

*Can ordinary strings cross into active formula semantics?* Yes, on XLSX only (IOR-01). The chain of individually correct decisions: ingress correctly refuses to police sink syntax; the composer passes the string; the plan carries it as data; openpyxl's default binding turns it into a formula; the renderer never intervenes. The read side (`load_workbook(data_only=True)`, `openpyxl_parser.py` line 48) then returns the cached value, which for an openpyxl-written file is `None` -> `""`. So `"=1+1"` in a JSON input becomes an empty string after one XLSX roundtrip through the project alone, and becomes `"2"` after a roundtrip through Excel/LibreOffice. The `_meta` hidden sheet is also written cell-by-cell with `str(v)` (`_write_meta`, 241-250); the JSON blob starts with `{` and is safe, but the three marker cells and any other kv value are subject to the same binding.

*Can controlled values degrade and regain capability?* Degrade: yes by design on reload -- a written formula reads back as its cached value (`""` for project-written files on both formats) and re-enters the Domain as an ordinary Missing/String. Regain: only through the IOR-01 path, and only if the degraded text itself starts with `=`, which a cached value does not. `FormulaSpec` stringified by CSV/XML yields `LookupFormulaSpec(...)` text, which cannot regain capability.

*Escaping at the correct layer.* Formula and validation syntax lives only in the two adapters and is guarded (`tests/architecture/formula_boundary/test_raw_formula_boundary_guards.py`). Within XLSX, sheet-name quoting is inconsistent: `_quote_xlsx_sheet_name` doubles apostrophes for lookup formulas, `_define_named_range` (253-259) does not (IOR-10). Within ODS, `_quote_sheet_name` is used consistently.

*External references.* No op emits them. The only path is the accidental string path in IOR-01. `LookupFormulaSpec.lookup_sheet` is a *frame* name rewritten to the physical sheet by `frame_selection` and re-checked by `reject_referenced_lookup_sheet_rename` before the renderer; the renderers raise `KeyError` if the referenced sheet or column is absent from the plan (`_header_col`/`_data_bounds`), which is fail-closed before file effect on XLSX (context is collected before `wb.save`) and before file effect on ODS (raised inside `_build_table`, before `doc.save`).

*Relation to Trusted Ingress.* Nothing here requires expanding ingress. Decision 5 already assigns the `=` question to the sink. The correction belongs in `openpyxl_renderer.py`, not in `scalar_values.py` or `structural_admission.py`.

== 8. Part F -- Filesystem / durability / failure semantics

*What the product claims.* Nothing. No document in `docs/` claims atomic, transactional, or crash-safe output (search terms: atomic, durable, temp file, partial artifact; only unrelated hits). This section therefore records behaviour.

[cols="2,4",options="header"]
|===
| Aspect | Behaviour at HEAD

| Target path authority | Spreadsheet: operator path rewritten by `with_suffix` (IOR-05). Directory sinks: path used verbatim as a directory. `IODesc.path` is stripped and lowercased only for `kind`, not the path.
| Overwrite | Always, silently. Single files are truncated at open (`ZipFile(filename, "w")`, `openpyxl/writer/excel.py` 291; `zipfile.ZipFile(outputfile, "w")`, `odf/opendocument.py` 595; `open(p, "w")` in the directory writers).
| Directory creation | `parent.mkdir(parents=True, exist_ok=True)` for spreadsheets; `out_dir.mkdir(parents=True, exist_ok=True)` for directories.
| Symlinks | not handled; a symlinked target or directory is followed. Read-side member symlinks were H5 of the parser review; not re-reviewed.
| Temp-file / atomic replace | none anywhere.
| Partial artifacts | XLSX: openpyxl streams worksheets into the zip during `save`; an exception after the first entry leaves a truncated zip at the target (IOR-02 is a concrete trigger). ODS: odfpy builds the DOM first and serializes in `__zipwrite`; a serialization error would also truncate, but no concrete trigger was found because the renderer stringifies everything. JSON/YAML: `json.dump`/`yaml.safe_dump` stream to the open file; an unsupported value raises mid-stream, leaving a truncated file.
| Multi-file output | files written in frame order; no removal of files not produced in this run (IOR-03); no manifest of what was written; a failure at file N leaves files 1..N-1 new, N truncated, N+1.. from the previous run.
| Manifest/resource consistency | not applicable to router sinks; the artifact-manifest step writes its own records with containment checks.
| Cleanup on failure | none.
| Ordering | authorization and `_meta` projection strictly precede any filesystem effect (`_finalize_and_persist` before `_save_frames`). Within the XLSX renderer, every plan op executes before `wb.save`, so op-level errors (`KeyError` for a missing lookup column, openpyxl `ValueError` for an unbindable object or an invalid sheet title) are raised with *no* file effect. Save-time errors (tz-aware datetime) are the exception.
| Crash/interruption | a `KeyboardInterrupt` during `save` leaves a truncated artifact; the CLI's clean exit does not restore anything.
|===

Assessment: the implementation is consistent with the (absent) claim. The one place where the absence of a claim hurts is IOR-02, because the framework *accepted* the value at ingress and then destroys the previous artifact while failing to write the new one.

== 10. Part H -- Performance / resource model (static)

No measurement exists anywhere in the repository for the write path; the parser-side limits census (`FTR-XLSX-PARSER-RESOURCE-LIMITS-P4A`) is read-side only. Observed cost shapes:

* *Composer:* `df.values.tolist()` -- one full materialization per frame, plus a second copy in `build_render_plan` (`tuple(tuple(row) ...)`), plus (ODS) a third copy into `_BufferedSheet.cells`. O(cells) x 3 on ODS, x 2 on XLSX. Not a problem at demonstrated scale; not justified by anything either.
* *Passes:* three passes each `json.loads` the full canonical meta (`_workbook_meta`); O(|meta| x 3) redundant parsing.
* *XLSX renderer:* sparse, O(populated cells + ops). `ApplyColumnStyle` and `ApplyCellLock` are O(rows) per helper column.
* *ODS renderer:* emits a `TableCell` element for every position in the `max_row x max_col` rectangle (`_build_table` 540-612), with no `number-columns-repeated` compression. A wide legend placed `right_of_table` on a tall sheet produces `rows x (table_cols + gap + legend_cols)` elements in odfpy's DOM. O(R x C) memory and file size regardless of sparsity (IOW-2).
* *XLSX parser:* `_cell_value` (`parser_interpretation.py` 255-267) resolves a merged cell by materializing every coordinate of every merged range on each call -- O(#merges x area) per merged-cell read; header extraction calls it per header cell. Quadratic in merged-header area (IOW-3). The three presentation extractors each iterate the full used rectangle (parser review H1).
* *ODS parser:* bounded by `ParserLimits`; the four presentation extractors each walk the table DOM once (four passes over the same rows).
* *Multi-backend duplicated work:* none at runtime; a pipeline writes one sink.

No current architectural complexity is justified by performance. The only performance-motivated code is the parser-side repeat handling, which is essential and separately reviewed.

== 14. Part L -- Product responsibility

* *Caller-provided direct API (`make_backend`, `save_xlsx`, `BackendBase`):* documented caller-precondition surface (`interfaces_and_gates.adoc`). The silent stringification of `FormulaSpec` by XML/CSV and the CSV `write_multi` trap live here; they are contract defects, not security defects.
* *External spreadsheet applications:* Excel's Protected View, DDE prompts, and LibreOffice's macro/link security are the reader's controls. The framework's responsibility ends at not *emitting* an active formula it was not asked to emit. CSV opened in a spreadsheet application is reader-side interpretation of text and out of scope.
* *Dependencies:* openpyxl's `=`-prefix binding and tz rejection, odfpy's in-place zip writing, pandas' `values` widening are dependency behaviours; the framework wraps them and therefore owns the wrapping decision, not the library.

== 16. Part N -- Findings

=== 16.1 IMPORTANT

==== IOR-01 -- XLSX sink turns ordinary `=`-prefixed strings into active formula cells; no sink policy exists; project reload loses the value

* *Severity / motivation:* IMPORTANT; A (adversarial), secondary B (accidental text such as `=see note`), C (ODS/XLSX parity contract).
* *Evidence:* `openpyxl_renderer.py` `_write_data_block` 225-238, `_execute_render_op` `SetHeader` 271-273, `_write_meta` 245-247 assign raw values; openpyxl 3.1.5 `cell/cell.py` 198-199 sets `data_type = 'f'` for `len(value) > 1 and value.startswith("=")`; `openpyxl_parser.py` 48 `load_workbook(..., data_only=True)`; `odf_renderer.py` 602-609 writes the same value as a string cell; `scalar_values.py` 21-23; ADR Decision 5; `architectural_layers.adoc` 349-359; concept reviews 001-003 recorded the reproduction.
* *Mechanism:* ingress admits the string; composer/plan carry it; openpyxl binds it as a formula; the file carries `<f>`; the consumer evaluates it; the project's own parser returns the cached value (`None` -> `""`).
* *Actor / failure story:* a partner-supplied JSON directory contains `"note": "=HYPERLINK(\"https://...\",\"click\")"` or a DDE-style string; the operator exports to XLSX and opens it. Accidental variant: a legitimate `"=1+1"` text disappears after one export/reimport cycle through the project alone.
* *Observable consequence:* capability activation in the reader; silent data loss or substitution on reimport; XLSX/ODS parity broken for such strings.
* *Affected:* XLSX only (data cells, header cells, hidden-meta kv values).

* *Readiness:* implementation-ready. Application-side display of `inlineStr` cells starting with `=` as text is expected but *UNVERIFIED* in Excel/LibreOffice.

==== IOR-02 -- Ingress-accepted timezone-aware DateTime fails inside `wb.save` on XLSX, leaving a truncated artifact

* *Severity / motivation:* IMPORTANT; B (robustness), secondary D (durability).
* *Evidence:* `scalar_values.py` 56-60 (aware `datetime`/`Timestamp` classify as DateTime, never stripped); `structural_admission.py` admits it; JSON/YAML tests prove aware values are written (`test_json_roundtrip.py` 89-129, `test_yaml_roundtrip.py` 92-111); no XLSX/ODS test uses a tz-aware value; openpyxl `cell/_writer.py` 28-31 raises `TypeError` for `tzinfo is not None` during cell serialization, which runs inside `save` after `ZipFile(filename, "w")` (`writer/excel.py` 291); `openpyxl_renderer.py` 393.
* *Mechanism:* the value binds fine at assignment (`_bind_value` checks only the type), so no early failure; the error occurs while streaming the worksheet into the already-truncated zip.
* *Actor / failure story:* an operator's `yaml_dir` input has `updated: 2026-09-16T10:00:00+02:00` (PyYAML yields an aware datetime); the pipeline exports to XLSX over last week's workbook; the run fails and the previous workbook is gone.
* *Observable consequence:* uncaught `TypeError` from a dependency; a 0-byte or partial `.xlsx` at the operator's path.
* *Affected:* XLSX. ODS stringifies (asymmetry, not failure).
* *Smallest correction:* reject (typed error, before any file effect) or convert tz-aware values in `_xlsx_cell_value`; add one test.
* *Must not expand into:* a Domain timezone canonicalization policy (deferred by the value-model FTR); a general pre-save validation framework.
* *Readiness:* implementation-ready for the reject variant. The exact runtime failure was derived from dependency source and is *UNVERIFIED* by execution.

==== IOR-03 -- Directory sinks are overlay writers; stale frames and sidecars silently re-enter the next roundtrip

* *Severity / motivation:* IMPORTANT; D (operational), secondary C (roundtrip contract).
* *Evidence:* `json_backend.py` 227-270, `yaml_backend.py` 155-176, `xml_backend.py` 149-187, `csv_backend.py` 115-122: `mkdir(exist_ok=True)` then per-frame writes; no listing, no deletion; JSON writes `_meta.yaml` only when `_meta` is a dict (265-270) and never removes an existing one; loaders glob the directory (`json_backend.py` 204, `yaml_backend.py` 129-140, `xml_backend.py` 133, `csv_backend.py` 76). No document describes directory output as overlay or replace (search in section 8).
* *Mechanism:* run 1 writes `a.json`, `b.json`; run 2's pipeline drops or renames `b`; `b.json` persists; run 3 loads `b` as a frame.
* *Actor / failure story:* the documented workflow (`--out-path build/output`, repeated) after a frame rename in `_meta.workbook_view` or a `pipeline_cleanup` drop.
* *Observable consequence:* a frame the pipeline removed re-appears with stale content; FK validation may then report phantom references; no error.
* *Affected:* json_dir, yaml_dir, xml_dir, csv_dir.
* *Smallest correction:* state the overlay semantics in the user guide and release notes; optionally add an opt-in replace mode (remove known-extension files and the sidecar before writing).
* *Must not expand into:* a transactional output layer; deleting unknown files in operator directories by default.
* *Readiness:* documentation is implementation-ready; a replace mode needs a small design decision (opt-in vs default).

== 17. Part O -- Required explicit answers

. *Is the rendering/backend responsibility split sound?* Yes for the compose -> passes -> plan -> render chain and for keeping directory sinks outside it. Two misplacements: format-independent formula addressing is resolved inside each renderer (IOR-09), and the persistence encoding of `_meta` is used as in-process transport (IOR-08).
. *Does any backend activate capabilities not authorized at the sink boundary?* Yes: XLSX activates formula cells for ordinary `=`-prefixed strings that no layer authorized (IOR-01). `FormulaSpec` activation is authorized inside `orchestrate` and is a documented caller precondition outside it.
. *Are ordinary strings and controlled/formula values kept semantically distinct all the way to persistence?* In the framework's own types, yes (`FormulaSpec` vs `str` through IR and plan). At the XLSX file boundary, no (IOR-01). At the ODS boundary, yes. In CSV/XML direct writes, `FormulaSpec` collapses into text (unmanaged surface).
. *Are non-spreadsheet sinks fail-closed for unsupported controlled values?* Through `orchestrate`: yes, typed and before any file effect. Directly: JSON/YAML fail after truncating the target; XML/CSV do not fail.
. *Are roundtrip claims stronger than tests/implementation justify?* Yes in `roundtrip_spreadsheet_layout.adoc` (guarantee wording, named-range mode, sidecar, formula columns) and in the capability profile's read expectations. The release-note limitation and the parity tests are truthful.
. *Are output formats silently lossy in ways the contract obscures?* Yes: `=`-strings on XLSX (IOR-01); overlay directories (IOR-03); `_meta` dropped by yaml/xml/csv (documented for YAML only in release notes; contradicted by a docstring); csv multi-level headers; numeric widening and boolean spelling (IOR-11).
. *Does filesystem persistence have a coherent failure/durability model?* No model is claimed; behaviour is uniformly in-place, non-atomic, overlay for directories. Coherent by absence; IOR-02 is the one case where an accepted value converts that absence into artifact loss.
. *Duplicated or misplaced format semantics across rendering and backends?* Duplicated: lookup context, blob decoders, `" / "` token, option hint keys, small helpers. Misplaced: none in the renderers beyond the accidental openpyxl default; the composer's `values.tolist()` widening is a Domain-side type decision made in rendering.
. *Derived-state / synchronization machinery like the anti-accretion pattern?* Yes, in small form: marker cells plus strip (IOR-07); blob re-seed plus re-parse (IOR-08); copy passes plus dunder keys; parse-side dunder hints parallel to the blob; sink-capability name set parallel to the router (IOR-04); legend `resolved` stripped twice (IOW-7). None is large; all are deletable.
. *Which abstractions would not be introduced today?* Section 11, last paragraph: `BackendBase`/`BackendOptions`, the copy passes, marker cells, parse-side validation/named-range IR, validation `kind`, the capability name set, `excel:` config.
. *Complexity justified mainly by unmeasured performance or speculative flexibility?* No performance-motivated complexity exists on the write path. Speculative: `DataValidationSpec.kind`, `StyleSpec`, `header_cols`, parse-side reconstruction, `WriteMeta.sheet`'s "other carriers remain possible" comment.
. *Cross-layer defects previous local reviews could have missed?* IOR-01 (each layer correct, composite wrong; already recorded as evidence in the trust ADR but never assigned a fix) and IOR-02 (ingress vocabulary wider than the XLSX sink's; each layer documented its own decision). IOR-12 is the same shape for `ExactTable`.
. *Justified action:* (a) bounded fixes -- IOR-01, IOR-02, IOR-04, IOR-05, IOR-10, IOR-12, plus documentation for IOR-03; (b) bounded simplification -- IOR-07, IOR-08, IOR-09, IOR-13, IOR-14 and the copy passes; (c) no deeper architecture review is needed; (d) not applicable.

*Empirical unknowns:* section 19.

*Future optional improvements:* single-file atomic placement if a durability claim is ever wanted; replace mode for directory sinks; ODS repeat compression if wide sparse sheets appear; one boolean spelling across spreadsheet backends.

*Top 3 durable architectural conclusions:*

. The rendering chain's abstraction cost is earned by two real renderers and a parity oracle; keep `RenderPlan` as the only thing an adapter executes and do not add a third representation between IR and file.
. Sink capability is activated at exactly two library calls; the sink that owns a capability must implement its inert default in code, not in an ADR. Assigning ownership in documentation while the code delegates to a library default is the cross-layer gap this subsystem actually had.
. The ingress vocabulary and each sink's serializable vocabulary must be compared explicitly per sink; where they differ (tz-aware DateTime, `ExactTable`), the sink must reject before the target is opened. This is a per-sink table, not a framework.

*Top 3 implementation follow-ups:* IOR-01 inert-string default in the XLSX renderer with tests; IOR-02 pre-save rejection of tz-aware datetimes on XLSX; IOR-03 documentation of overlay semantics (plus IOR-04 and IOR-05 as one-line fixes in the same slice).

*Top 3 things NOT to build:* a transactional or manifest-tracked output layer; a typed IR substrate or per-cell type hints to "fix" IOR-11; an ingress-side content filter or formula allowlist in response to IOR-01.

*Is another Frontier review justified?* No. The remaining work is bounded implementation with existing tests as the safety net. One narrow follow-up review after the sink-boundary slice lands is sufficient and does not need Frontier capacity: "Do all XLSX write paths (data, header, hidden-meta, validation literal) now emit inert text for non-`FormulaSpec` strings, and does the XLSX/ODS parity oracle include `=`-prefixed strings, booleans, and tz-aware datetimes?"
