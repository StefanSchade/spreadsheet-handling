== 4. N=2 rollout and preauthorized-run-envelope review (Axes 2, 3)

=== 4.1 N=2 rollout boundary

`max_autonomous_hops = 1` remains valid `N=1`; `= 2` permits the bounded
H001-then-eligible-H002 path; `> 2` fails preflight before Run creation or
provider-capable execution; no path may create H003, publish an H003 marker, or
allocate an H003 invocation identity (lines 2121--2128). The draft explicitly

WFC-AUTO-01 (architecture supports `N=1->2->5->10` without schema redesign): the
ceiling is an execution-authority gate, not a model change, so existing reducer
semantics are not weakened. "Up to two provider-capable attempts" is consistent
with the conservative attempt-consumption rule (WFC-AUTO-02/03), which the
"Attempt consumption" clause (lines 2140--2146) restates without relaxation
(no hidden retry/fallback/resume).

N=2 ROLLOUT CONTRACT SOUND:: *YES.*

=== 4.2 Preauthorized run envelope

The pinned WorkItem/Profile/Policy/task/component-manifest/components/expected
repository/HEAD/`max_autonomous_hops` plus a deliberate operator launch constitute
the bounded `N=2` authority envelope (lines 2130--2138). The draft states the
envelope "does not require two attempts, retry a failed H001, guarantee H002, let
the agent enlarge the envelope, turn a route into execution authority, permit

matches the accepted disposition:

* H002 needs no new human grant while every preauthorized condition holds

* H001 cannot manufacture new execution authority -- the agent route chain
  (lines 2294--2309) forbids any agent field (`outcome=completed`,
  `requested_route`, target phase, Finding proposal) from authorizing H002;
* budget is a ceiling/preauthorization, not an instruction to spend;
* no machine-readable `MaintainerGrant` is required (Non-scope, line 2440;
  Re-Review 002 answer `NO`).

RUN ENVELOPE CONTRACT SOUND:: *YES.*

== 5. Action / scope-authority review (Axis 4)

The three-field distinction is stated correctly and matches the accepted,
code-verified semantics:

* `RepositoryPolicy.scope` -- repository-identity allowlist, *not* a path lattice
  (lines 2150--2154; `model.py:343`);
* `WorkItem.scope` -- maintainer-declared outer repository *path* envelope
  (line 2155);
* `Phase.authorized_scope` -- phase-local repository-relative path/prefix
  authority (line 2155; `vertical.py:160,176`, `slice4.py:174`).

The domination check (lines 2158--2169) requires, at the single pre-H001 ingress,
that every phase's `authorized_actions` be a subset of `RepositoryPolicy.actions`
and that each normalized `Phase.authorized_scope` entry be equal to or contained
beneath at least one normalized `WorkItem.scope` entry, under *the same*
repository-relative path/prefix semantics used by bounded Git authority
(`git_facts.py:369` / `operator.py:74`: `path == allowed or
path.startswith(allowed + "/")`). It checks *every* phase, establishes an
upper bound only (reachability still governed by routes/reduction/preemption),
and fails before Run creation with zero fake/provider invocations. The canonical
ingress dominates the serial driver, and a bypassing lower-level caller is
declared outside 5A (lines 2171--2174).

*Attempted escape construction (Axis 4 adversarial task).* I could not construct
a path-normalization or prefix case that escapes `WorkItem.scope` while passing
the stated contract:

* *sibling-prefix* (`WorkItem.scope=src`, `Phase.authorized_scope=src-secret`):
  rejected -- `"src-secret"` neither equals `"src"` nor starts with `"src/"`. The
  `allowed + "/"` guard is exactly what defeats this.
* *`..`-escape / absolute path* (`Phase.authorized_scope=src/../../etc` or
  `/etc`): defeated only because the contract binds *both* operands to the *same*
  bounded-Git normalization rather than inventing a parallel weaker one; a
  repo-relative normalization that collapses `..` and repo-roots the path leaves
  the entry outside every `WorkItem.scope` entry, so acceptance case 4 rejects it
  before H001.

The load-bearing safety property is therefore "one normalization, applied to both
sides." The contract states this as a MUST. See WATCH-1 for an optional
strengthening of the acceptance matrix. No generic permission lattice is required
or introduced; the draft explicitly forbids moving scope authority into Run or
reinterpreting policy scope (lines 2173--2174).

ACTION/SCOPE AUTHORITY CONTRACT SOUND:: *YES.*

== 6. Dispatch-eligibility / publication / recovery review (Axes 5, 6)

=== 6.1 Two-layer dispatch eligibility

The rich serial-driver continuation gate (lines 2178--2200) owns continuation
semantics (Run `ready`; H001 correlation/validation/Git/evidence/reduction done;
`hop_used < hop_limit` within the rollout ceiling; no preemption/human/budget/
supervisor/prerequisite/suspend/reconcile/stop/complete/terminal state;
publication sequence completed and marker retired; Git/governing-input
revalidation passed; phase still in-envelope; fresh invocation identity and
binding established). The canonical real-boundary assertion (lines 2202--2212) is
a small defense-in-depth predicate (`Run.status == ready`, `hop_used <
hop_limit`, not preempted/suspended/reconcile/stopped/completed/terminal) that
fails closed before marker publication and adapter/provider entry, and is
explicitly forbidden from duplicating route evaluation, governing-input identity,
full Git revalidation, phase authority, execution-binding selection, or prompt
construction -- "the boundary shall not become a second reducer."

The inner predicate is a strict subset of the outer, so it can only be more
permissive; because it fires at the actual dispatch site, an ineligible Run
supplied *directly* to the real boundary (bypassing the outer gate) is still
refused (matrix case 13). The "same eligibility concept" cannot diverge
dangerously because a single small predicate may be reused. Existing `RunStatus`
vocabulary is sufficient (`model.py:64-74`). Locating governing-input/Git/phase
revalidation *only* in the outer gate is the accepted F2 disposition, not a gap:
demanding the inner boundary re-perform them would be over-specification.

TWO-LAYER ELIGIBILITY CONTRACT SOUND:: *YES.*

=== 6.2 Publication / crash semantics

Publication is three *sequential* atomic operations -- authoritative `run.json`
-> derived `checkpoint.json` -> `dispatch.json` retirement -- explicitly *not* a
compound atomic transaction (lines 2214--2227; matches `slice4.py:203-205`). The
draft resolves the Re-Review-002 residual by naming carriers distinctly: the
returned immutable Run is the *live in-process* authority carrier, `run.json` is
the *durable/recovery* authority carrier, and `checkpoint.json` is a derived
projection that "shall never independently authorize H002." Normal H002 may
proceed only after all three operations complete and no marker remains. A
present/stale marker preempts continuation; a stale/missing checkpoint never
causes H002; recovery uses existing authoritative Run/dispatch facts under
existing `reconcile_required` semantics (`persistence.py:73-122`) with no
automatic replay/resume. No event store, 2PC, combined transactional DB, compound
atomic Run+checkpoint file, or new persistence substrate is added (lines
2233--2234; consistent with WFC-PERSIST-01/02 prohibitions). The crash window is
fail-closed and matrix case 15 exercises it. There is no residual ambiguity
between the in-memory Run and `run.json` after a partial failure: normal flow
requires the full sequence before H002; any partial failure leaves the marker and
routes into recovery.

PUBLICATION/CRASH CONTRACT SOUND:: *YES.*

== 7. Governing-input / inter-hop Git review (Axes 7, 8)

=== 7.1 Governing-input content identity

The pinned set (lines 2236--2244) is exactly the six repository-backed inputs the
operator already pins (WorkItem, profile, policy, component manifest, task, every
selected repository-backed prompt/component source; `operator.py:112-153`).
Non-repository execution settings (executable, timeout) are correctly excluded
from content addressing. Before H002 the driver observes expected HEAD B, re-reads
each exact originally pinned path at B, and requires byte or equivalent
cryptographic-content identity against the pre-H001 content; changed/deleted/
moved/no-longer-tracked/non-identical fails closed; an untracked replacement
cannot satisfy tracked identity; `pinned_paths` remains a cheap in-Hop tripwire
only (lines 2246--2252). Normal mismatch -> `awaiting_human`; recovery mismatch ->
`reconcile_required` (existing statuses, `model.py:68,71`); no new status and no
content-addressed configuration subsystem (lines 2254--2258). This also correctly
operationalizes WFC-PROFILE-06 (a governing-input mutation committed by H001
within an in-scope phase is detected and blocks H002 while leaving commit B
factual).

GOVERNING-INPUT CONTRACT SOUND:: *YES.*

=== 7.2 Inter-hop Git transaction

The normal pipeline (lines 2260--2283) bases H002 on exact `H001.end_head`,
independently re-observes the registered checkout, exact HEAD identity, clean
tracked/non-ignored worktree, and acceptable submodule state, and unchanged
governing inputs, before H002 at clean HEAD B. The trusted-commit-before-later-
rejection rule (lines 2285--2292) preserves existing ordering: a valid H001
`CommitIntent` may create legitimate commit B before a later route/Finding
validation stops; B remains factual, `Run.current_head` retains B, the invalid
route/Finding creates no new authority, the resulting non-ready status prohibits
H002, and the Coordinator shall not reset/erase B to manufacture atomicity
(consistent with WFC-GIT-01..05 and WFC-FAIL-03: stop without rollback). No
speculative route/prompt/invocation identity/next action survives H001 as
authority.

INTER-HOP GIT CONTRACT SOUND:: *YES.*

FRESH-CONTEXT CONTRACT SOUND:: *YES.*

=== 8.2 Per-invocation execution binding

Every provider-capable Hop has a concrete binding, resolved *per invocation* (not
stored as an immutable Run-lifetime selection); the 5A resolver may be trivial and
return the same current binding for H001 and H002 (lines 2332--2338). No
ModelSelector/ProviderRegistry/difficulty classifier/quota optimizer/fallback
framework/provider-diversity policy/new Run execution-selection field is added.
The actual binding is durable execution evidence (Hop ID, invocation ID, adapter/
provider, executable, model, reasoning config, context mode, timeout), kept
outside the semantic Run aggregate unless already-accepted architecture requires
otherwise; no silent fallback/substitution (lines 2340--2345). This preserves the
seam recorded by `50532460` without promoting it to a selection framework.

EXECUTION-BINDING CONTRACT SOUND:: *YES.*

=== 8.3 N>1 operator evidence

Evidence must remain truthful for both `N=1` and `N=2` and must not collapse H001
and H002 into one "last Hop" record; an `N=2` Run's bounded durable evidence must
reconstruct both attempts separately (ordered Hop IDs, distinct invocation IDs,
attempt/outcome, concrete bindings, base/end HEADs, commit/range, changed paths,
cumulative budget, final status), preferring a bounded per-Hop/per-attempt
projection and *not* an event store or unbounded raw transcript archive (lines
2347--2356). `N=1` summary semantics "shall either remain truthful or be
deliberately migrated." This is consistent with WFC-MODEL-02/04, WFC-OBS-01..04,
and the WFC-PERSIST-02 event-store prohibition.

N>1 EVIDENCE CONTRACT SOUND:: *YES.*

lock/worktree fan-out; sandbox redesign; DMC-specific code / DMC C3-S2 / DMC Family

Conversely, nothing required for *safe* `N=2` is deferred: Finding-delta
*validation* (case 8), scope/action domination, governing-input identity, inter-hop
Git revalidation, and crash fail-closure are all inside 5A; only Finding
*convergence* (multi-round resolution) is deferred to 5B, which is the correct
validation-vs-convergence split.

5A BOUNDARY SOUND:: *YES.*
