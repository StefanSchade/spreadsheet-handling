== 7. Assessment of candidate observation A -- last-Hop summary semantics

*Observation.* Console prints `LAST COMMIT: none`; `operator-summary.json` has
top-level `commits: []` and `changed_paths: []`, while its per-Hop `hops[]`
correctly record H001's commit B and `PROOF.md`.

*Root cause (verified in accepted code, `operator.py` `_summary` and the print
line).* Both the console `LAST COMMIT` field and the top-level summary
`commits` / `changed_paths` are computed from `run.hops[-1].actual_commits`
(the *last* Hop). Because the authorized final Hop (H002) is observation-only,
its `actual_commits` is empty, so all three render empty. `changed_paths`
additionally short-circuits on the falsy `run.hops[-1].actual_commits` before the
`baseline..head` diff, so it is `[]` rather than `[PROOF.md]`.

*Assessment.* The console `LAST COMMIT` line is *correct last-Hop semantics*
(H002 indeed committed nothing) -- at most a terse label. The top-level
`operator-summary.json` `commits` / `changed_paths` are more problematic: they
read as run-level aggregates but use last-Hop-only semantics, so a run whose
final Hop is observation-only under-reports its net effect at the top level, and
the same file's `baseline_head=A`, `current_head=B`, `final_head=B` and its
`hops[]` array contradict those empties. This is *not an evidence defect*: the
authoritative per-Hop structures, heads, `run.json`, `checkpoint.json`, and
`execution-evidence.json` all truthfully record commit B under H001. Practical
consequence does not change the proof disposition.

*Classification.* MINOR observability / summary-consistency issue (WATCH-7, new,
non-blocking). See findings.

== 8. Assessment of candidate observation B -- transient result carrier

*Observation.* Retained `result-message.json` contains H002 only. Readiness doc
section 11 requested retention of "the two provider transcripts / result
carriers."

*Root cause (verified in accepted `codex_adapter.py`).* `CodexCliAdapter.execute`
uses a single fixed path `<result_directory>/result-message.json`, truncated
(`atomic_write_text(result, "")`) and rewritten on *every* invocation. It is by
design a single transient carrier, reused per Hop, not a per-invocation retained
artifact. H002 therefore necessarily overwrote H001's raw carrier. H001's
advancement-relevant facts were promoted into durable structures before that
overwrite: `run.json` `hops[0]` (route `verify`, summary, `actual_commits=[B]`,
`evidence_refs=[PROOF.md]`), `checkpoint.json` `hops[0]` (range `A..B`),
`execution-evidence.json` `attempts[0]` (H001, `INV-38948bf4...`,
`actual_commits=[B]`, binding, `returncode 0`).

*Assessment.* This matches option three: *the readiness review's section-11
wording was stricter than the accepted implementation actually promises.* The
accepted implementation (`f5106edb`) was run *as-is* per readiness section 12
("no code or configuration change is required"); that as-is design physically
produces exactly one, overwritten, carrier file. The section-11 wish to retain
"two ... result carriers" is thus internally inconsistent with running the
accepted code unchanged, and live execution surfaced that inconsistency. For
*this* proof the retained durable evidence is *sufficient*: the two distinct
invocation IDs, per-Hop routes/commits, and the reflog independently establish
the `N=2` transition without the raw H001 carrier. So this is *not* an
evidence-retention gap that undermines the consumed proof.

However, if any *future* `N>1` authorization genuinely requires verbatim
per-Hop raw provider carriers (not merely promoted facts), that expectation
cannot be met by the accepted single-overwriting-carrier design and would first
require either relaxing the retention wording or changing persistence to write
per-invocation carrier files. That reconciliation is a precondition on a future
gate, not a correction to this run. This review proposes no such implementation.

*Classification.* MINOR documentation/expectation-reconciliation issue (WATCH-8,
new, non-blocking for this proof).
