== 1. Question, evidence, and method

The follow-up proposes that a future professional deployment derives a phase's information/trust requirement from a *declared disclosure surface* (constructed context plus reachable execution surface), admits only execution bindings whose trust capability satisfies that requirement, and optimizes capability/cost only inside the admissible set. This review tries to break that model against the system as built and against the host it actually runs on.

Evidence inspected at the reviewed commit:

* host facts that determine the real reachable surface: the provider CLI version and user-level configuration (`sandbox_mode`, project trust levels, approval rules), the repository's tracked `.gitignore`, the ignored `tmp/` content, the parent directory of the checkout, environment variable names, and the provider's own host-side session/history stores.

Read reachability does not depend on the workspace root.

Method: for each element of the proposed ordering, identify what would establish it as a fact, then look for the smallest realistic case in which the fact is absent, self-reported, or circular. Consequences are derived for the Coordinator architecture, not enumerated as a generic threat list.

== 2. Verdict

*B -- DIRECTION SOUND WITH BOUNDED MATERIAL REVISIONS.*

The separation of action authority, information authority, reachability, execution compatibility, and economic selection survives attack: no finding shows that these are the wrong concepts or that their ordering is wrong. What does not survive is the model's *one-sidedness*. As written, the disclosure surface is something a phase *declares*; in the running system it is something the environment *provides*, and today nothing the Coordinator controls provides it. As written, information authority governs what an environment may *receive*; the Coordinator's own trusted commit is a *disclosure to the repository's audience* that the model never checks. As written, the derived-material rule joins over *sources*; the only honest join is over the *reachable surface*, and under the current binding that surface is the entire user account. Each correction is additive and small in formulation, so the verdict is B rather than C. The professional demonstration, however, has a hard prerequisite: the Coordinator must own or verify an environment boundary before any information-authority claim can be made at all.

Findings by severity: BLOCKING 0; IMPORTANT 6 (T1--T6); MINOR 4 (T7--T10); INFO/WATCH 3 (TW1--TW3).

Strongest newly discovered consequence: under the accepted binding, the reachable surface is the whole user account (provider credential file, shell history, sibling repositories, prior Runs' state roots, the provider's own session history), not the workspace. The Coordinator's `_require_external_state_root` makes the state root *disjoint*, not *unreachable*. Applied honestly, the follow-up's own join rule therefore labels every derived output of every Hop to date -- including artifacts the trusted commit landed in a public repository -- at the classification of the entire host account. The model is not merely unimplemented; without a Coordinator-owned boundary it is *unimplementable*, and its egress side is missing.

== 3. Findings

Each finding states observation, evidence, risk if ignored, recommended conceptual action, and disposition. Actions are corrections to the concept; none authorizes implementation.

=== T1 -- IMPORTANT -- The disclosure surface is a *provided* fact, not a *declared* one; the ordering needs both halves and a comparison

Observation:: The follow-up's ordering reads `phase -> declared disclosure surface -> trust requirement -> eligible bindings`. The phase can declare which *context* is constructed (it does: components, task, bounded context items) but it cannot declare what is *reachable*; reachability is whatever the execution boundary happens to admit. Today that boundary is the provider CLI's own sandbox, configured in the user's home directory, launched with `--sandbox workspace-write --cd <repo>` and a full inherited environment.
Evidence:: `codex_adapter.py` `argv` and `execute` (no `env=`, no mount or read policy); `slice4.py` `_require_external_state_root` (disjointness only); user-level provider configuration declares the whole home directory a trusted project; the local sandbox probe read the provider credential file, the SSH public key, shell history, personal notes in the home directory, the parent directory's sibling repositories, the ignored `tmp/` directory of the checkout, and `operator-plan.json` of the retained Slice-5A state root, while every write and every outbound network connection from model-run commands was denied.
Risk if ignored:: A profile field "this phase discloses only the pinned components" would be a false statement of fact that policy then relies on. The trust requirement computed from a declared surface under-classifies by exactly the difference between declared and provided; here that difference is the entire account.
Action:: Split the concept into *required surface* (declared by phase/policy: the maximal set the phase may reach) and *provided surface* (established by the environment boundary the Coordinator constructs or verifies). Admission is `provided ⊆ required`, computed fail-closed before binding selection. The Coordinator may claim a disclosure bound only for a surface it constructed (recorded construction arguments) or verified (a trusted in-boundary probe, in the shape of the existing evidence-provider registry). Restated ordering: `phase -> required surface -> environment boundary provides surface -> provided ⊆ required -> eligible bindings -> capability/cost -> invocation`.
Disposition:: Open; concept revision. Professional-demonstration prerequisite.

=== T2 -- IMPORTANT -- Information authority has an egress side; the trusted commit and every promotion are disclosures the model never checks

Observation:: The follow-up treats information authority as "what an execution environment may receive". The Coordinator's principal *effect* is to land agent-authored content in a repository whose audience is fixed by that repository (here: a public GitHub remote), to feed the previous Hop's summary into the next prompt, and to allow promotion of Run reports and review artifacts. `trusted_commit` validates paths, subject, and worktree facts; it has no notion of the content's classification or of the repository's audience.
Evidence:: `git_facts.py` `trusted_commit` (path-scope and subject checks only); `vertical.py` (durable artifact required by WFC-OUTPUT-04 is committed on success); `operator.py` `_h1_context` (`prior_summary` prose flows into H002); `review_instructions.adoc` ("Assume review artifacts may be committed to the public repository"); WFC-PERSIST-05 promotion.
Risk if ignored:: "Constrain effects mechanically" currently constrains *where* an effect lands, not *what information* it carries. With T1, an agent that reaches confidential sibling material can lawfully write a derived assessment into the authorized scope path, and the Coordinator itself publishes it. The exfiltration path is the sanctioned effect, not a bypass.
Action:: State information authority as two predicates: *ingress* (environment may receive the surface) and *egress* (a sink may receive derived output). Every sink -- repository commit, next-Hop context, state root, promoted report, terminal, CI log -- has an audience label; derived output may land in a sink only if its label (T4) is dominated by the sink's audience. With the join rule this fail-closes today unless the surface is narrowed, which is the correct default and the concrete reason T1 is a prerequisite rather than a nicety. No content scanner or DLP is implied; the check compares two labels.
Disposition:: Open; concept revision.

=== T3 -- IMPORTANT -- Git HEAD does not identify the reachable tree: ignored content, caches, and prior evidence are inside the surface but outside every Coordinator check

Observation:: The prior review proposed checkout HEAD plus sandbox/network mode as the reachable-surface identity. HEAD identifies the *tracked* tree. `preflight_hop` requires no tracked or non-ignored untracked changes; ignored paths are invisible to it by construction and remain fully readable by the agent. The repository's tracked `.gitignore` ignores `tmp/`, `build/`, `.venv/`, caches, and logs; `tmp/` currently holds a raw failed-Run dump and several `git show` extracts.
Evidence:: `git_facts.py` `_observe_repository` (`status --porcelain --untracked-files=all` respects ignore rules); `.gitignore`; `tmp/` listing; the probe read `tmp/` from inside the sandbox.
Risk if ignored:: A surface manifest of the form "checkout at HEAD X" would be provably incomplete; two Runs at the same HEAD have different surfaces depending on local residue. Ignored directories are precisely where raw evidence, virtualenvs, and build products accumulate, i.e. the highest-entropy material.
Action:: Define the surface's tree identity as an *exported tree* (the pinned tree written into the boundary), not the live checkout, or record "live checkout; ignored content unbounded" as an explicit surface fact that policy must accept. The former also removes `.git` metadata (other branches, reflog, remote URLs, stashes) from the surface. This is a construction rule for the environment boundary, not a new classification field.
Disposition:: Open; concept revision.

=== T4 -- IMPORTANT -- The join rule must join over the reachable surface, is a floor rather than a ceiling, and must not be computed from agent-cited sources

Observation:: "Derived material inherits the join of its sources unless explicitly declassified" leaves *sources* undefined. The agent's `evidence_refs` are untrusted input (WFC-SEC-02); the Coordinator cannot enumerate in-Hop reads; the only source set it can vouch for is the provided surface (T1).
Evidence:: `adapter.py` / `serialization.py` (`evidence_refs` are free strings); `codex_adapter.py` (stdout is a transient 16 KiB tail; no read log); WFC-SEC-02.
Risk if ignored:: Computing the join from cited sources lets the agent lower its own output label by citing less, which is exactly the self-weakening governance the follow-up forbids. Conversely, a join over public inputs can still produce material that policy considers sensitive (aggregation); a rule that only ever *computes* labels cannot express that.
Action:: Restate: *derived material carries at least the join of the provided surface; a label below that join is assigned only by explicit declassification recorded as provenance; a label above it may be assigned by classification authority at any time.* Distinguish three operations precisely: (1) *removing* an item from the required surface changes what the next Hop may reach and is a policy act on inputs; (2) *redaction/transformation* produces a new item whose label is *assigned* by the declassifying authority, never computed from the transformation; (3) *declassification* is the assignment itself. None of the three is performed by summarization, prompt omission, or the omission manifest.
Disposition:: Open; concept revision.

=== T5 -- IMPORTANT -- Trust compatibility is a vector with two owners; a scalar zone predicate misadmits

Observation:: `phase trust requirement <= binding trust capability` reads as a total order over zones (external / enterprise / local). The properties that matter are owned by different parties and are not monotone in any zone name: *provider facts* (retention, training use, region, contractual confidentiality, sub-processors) are contractual and unverifiable locally; *environment facts* (provided surface, network egress set, credential exposure, host persistence) are technical and locally verifiable. The reviewed host demonstrates the non-monotonicity: an "external" provider running in a sandbox with network disabled for model commands and `.git` read-only, versus a hypothetical "local" model runner launched with full disk and network access, differ in opposite directions on the two axes.
Evidence:: Provider configuration (`sandbox_mode`, project trust levels, approval rules) is host state, not a property of the model; `_execution_binding` records adapter, executable, model, reasoning only; the strategy doc already separates "environment boundary" from provider.
Risk if ignored:: "On-prem" admits a binding whose host leaks everything; "enterprise API" admits a binding whose local harness persists transcripts in the user's home directory. Both would pass a zone comparison and fail the intended guarantee.
Action:: Define compatibility as a conjunction of per-property dominations, each property tagged with its owner (provider-contractual or environment-technical) and its evidence status (constructed, verified, asserted-by-config, contractual). Zone names may exist only as policy *presets* that expand to such property sets; the predicate never compares names. This is the same predicate shape the prior review's F5 unified for trust and capability, made honest about who supplies each fact.
Disposition:: Open; concept revision.

=== T6 -- IMPORTANT -- A provider-owned boundary makes the ordering circular; the environment boundary must be binding-independent

Observation:: Today the only isolation is the provider CLI's sandbox, so the provided surface is a *function of the binding*. The follow-up orders surface before binding selection. With a second adapter whose sandbox semantics differ (or none), "eligible bindings" would depend on a surface that depends on the binding.
Evidence:: `codex_adapter.py` (sandbox mode is an adapter argv detail); FTR 11.4.8 ("the accepted proof relies on the currently observed adapter execution boundary for agent isolation"); the follow-up's own note that provider attractiveness will change.
Risk if ignored:: Multi-provider binding, the seam the follow-up most wants to preserve, cannot be added without either a Coordinator-owned outer boundary or per-adapter surface facts that are verified rather than assumed. Without one of these, the first non-Codex adapter silently redefines what every phase discloses.
Action:: Record that the environment boundary is an explicit port with facts, parallel to the execution port, and that the provided surface is established by that port *before* binding selection and independent of it. A provider's inner sandbox may exist and may add restrictions, but it is not the disclosure boundary and need not be trusted for disclosure. Section 4 gives the minimum contract.
Disposition:: Open; concept revision. Precondition for multi-provider binding.

=== T7 -- MINOR -- Execution evidence records the *requested* binding, not the *effective* boundary; audit claims must be scoped accordingly

Observation:: `execution-evidence.json` records adapter, executable, model, reasoning, timeout, return code, heads, and commits. It does not record the provider CLI version, sandbox mode, network mode, environment policy, the user-level configuration digest, or the workspace trust state that together determine reachability -- and even if it did, values copied from a configuration file are assertions, not observations, because the provider's layered configuration can be overridden by flags, environment variables, and project-level files.
Evidence:: `operator.py` `_execution_binding` / `_execution_evidence`; retained Slice-5A `execution-evidence.json`; provider CLI help text (`-c` overrides, `--ignore-user-config`, `sandbox_permissions`).
Risk if ignored:: "This Run executed under sandbox mode X" would be recorded from a source that does not prove it, and later cited as if it did.
Action:: Distinguish four evidence classes in the concept: *constructed* (the Coordinator built it and records the construction), *verified* (a trusted probe observed it inside the boundary), *asserted* (copied from configuration), *contractual* (provider terms). Only the first two support a disclosure bound. Record the class with every environment fact. A trusted in-boundary probe is one more entry in the existing fixed evidence registry, not a framework.
Disposition:: Open; concept wording and evidence schema note.

=== T8 -- MINOR -- Governing inputs are not only repository content: the provider harness carries unpinned governing content from the host and, potentially, from the repository

Observation:: The Coordinator pins five inputs plus selected components and rejects drift at B. The provider CLI additionally shapes agent behavior from user-level configuration, host approval rules (which currently pre-allow `git add` and `git commit`), rules/skills/plugins directories, and -- for this provider -- an `AGENTS.md` file at the workspace root if present. None is pinned, digested, or drift-checked. The consumer repository has `AGENT.md` (a different name, not auto-loaded); a consumer repository that does contain `AGENTS.md` inside a phase's authorized scope would let a Hop rewrite the next Hop's provider-level instructions without touching any governing input the Coordinator watches.
Evidence:: `operator.py` `_preflight` / `_governing_inputs_unchanged` (five inputs plus components); user-level provider rules file; provider CLI documentation of workspace instruction files; `AGENT.md` at the checkout root.
Risk if ignored:: The prior review's F1 (agent output becoming governance) has a second channel that bypasses the Coordinator entirely, and the professional deployment's "governing content" definition would miss it. Commit provenance is irrelevant to it.
Action:: Define *governing content* as everything read by the Coordinator *or by the execution harness* to shape a Hop. The minimal distinction from application content is therefore not a repository path list but a two-location rule: repository-side governing inputs (pinned, drift-checked, excluded from agent scope per prior F1) and host/harness-side governing inputs (identified and recorded as part of the environment boundary per T7). This does not require governance to live outside the consumer repository; it requires that harness-level governance be *named* as such. A carve-out neither helps nor hurts this point, because the harness lives with the executing host, not with either repository.
Disposition:: Open; concept revision.

=== T9 -- MINOR -- The candidate operating rule maximizes the wrong quantity

Observation:: "Choose the richest execution environment that is both authorized for the information it can reach and capable enough for the phase; optimize cost only within that set." Three defects. (a) "Authorized for what it can reach" observes the surface instead of choosing it (T1). (b) "Richest" maximizes the surface, hence the derived-output label (T4), hence egress restriction (T2): the richest admissible environment can make the phase's *output* unpublishable to its intended sink. (c) It omits egress entirely.
Evidence:: T1, T2, T4.
Risk if ignored:: A rule that is locally sensible for capability produces globally unusable Runs whose artifacts cannot land where the workflow needs them.
Action:: Smallest corrected formulation: *Fix the phase's required surface to the narrowest surface sufficient for its work. Admit only bindings whose environment provides a surface within it, whose provider facts satisfy the surface's requirements, and whose declared sinks accept the surface's join. Among admissible bindings choose by capability, then cost.* "Sufficient" is a policy judgment made per phase, which is where the follow-up already puts it.
Disposition:: Open; concept revision.

=== T10 -- MINOR -- The result channel writes into the trusted state root from inside the provider process; a Coordinator-owned boundary must replace it with an explicit export channel

Observation:: The adapter passes `--output-last-message <state-root>/.../result-message.json` and `--output-schema <state-root>/...`. The provider *client* process writes the result into the external state root; only the model-run shell is denied writes there. Under a Coordinator-owned outer boundary enclosing the client, the state root would have to be mounted writable, re-exposing exactly what WFC-PERSIST-02 keeps outside the agent-writable workspace.
Evidence:: `codex_adapter.py` `argv` / `execute`; `slice4.py` `invoke_codex` (`result_directory = run_root`).
Risk if ignored:: The first sandbox implementation would either weaken the state-root invariant or fail; the concept should settle the channel before the mechanism.
Action:: Record that artifacts leaving the boundary do so through exactly one Coordinator-owned export channel (a pipe or a dedicated single-file mount), validated on the Coordinator side as today, and that the state root is never inside the boundary. This is a contract clause for section 4, not a design.
Disposition:: Open; concept clause.

== 4. Execution isolation as an enforcement hypothesis (bubblewrap and equivalents)

The question is not whether bubblewrap is secure but what an isolation mechanism must provide before the Coordinator may treat the resulting surface as a disclosure boundary. Attacking a bwrap-shaped boundary against the reviewed host yields the following minimum contract. Items are properties, not an implementation.

. *Constructed by the Coordinator, provider-independent (T6).* The Coordinator launches the boundary with recorded arguments and runs the provider client *inside* it. The provider's inner sandbox may remain and may add restrictions but is not relied on for disclosure.
. *Exported tree, not live checkout (T3).* The workspace inside the boundary is the pinned tree written by the Coordinator, without `.git`, ignored content, caches, or virtualenv residue unless a phase explicitly requires them (a required-surface fact). Git observation stays outside the boundary, as today. Consequence: the agent loses `git diff`/`git log` as tools; the Coordinator already supplies bounded diffs and can supply more, but this is a real capability cost (section 6).
. *Mount allow-list with no ancestor visibility.* Only the exported tree, a private temporary directory, and a minimal toolchain are mounted; the home directory, `/run/user`, sibling repositories, prior state roots, and the provider's own host stores are absent, not read-only. Read-only is an action bound, not an information bound. Symlinks inside the exported tree are harmless only because their targets are not mounted; the export step must therefore not dereference symlinks that point outside the tree.
. *Fresh `/proc` in a new PID namespace.* Without it, `/proc/<pid>/environ` and `cmdline` of host processes are readable. With it, the agent still sees its own environment, which is why the next item exists.
. *Cleared environment with an explicit allow-list.* The adapter today inherits everything; a boundary must start from an empty environment and add named variables. Provider credentials must reach the client process without being readable by model-run commands; this is a provider-client property (its environment policy) that the boundary cannot guarantee alone and must be recorded as asserted (T7).
. *No inherited descriptors except the export channel (T10).* The result and any diagnostics leave through one Coordinator-owned channel; the state root is never mounted.
. *Network namespace with a controlled egress path (TW3).* Unsharing the network namespace also removes abstract Unix sockets and the session bus; the provider endpoint then needs an explicit pass-through whose allowed set is a recorded surface fact.
. *No host-side persistence by the client.* The provider client's session, history, cache, memory, and plugin directories must resolve inside the boundary's private temporary space or be absent, so that nothing from this Hop is readable by a later Hop or Run at another classification (TW1).
. *Verified, not asserted.* A trusted in-boundary probe (fixed argv in the evidence registry) confirms the effective mounts, environment names, and network state before the prompt is delivered, and its digest is recorded as *verified* evidence (T7).
. *Host-escape is out of scope, not assumed absent.* Kernel-level escape from user namespaces is a threat the Coordinator does not model (WFC-SEC-01 already excludes hostile code). The claim supported is "presumed disclosure bounded by the constructed surface under a non-adversarial agent", never "isolation against a hostile agent".

With these properties a bwrap-like boundary is *plausibly adequate* for the local half of the trust vector: it can make the provided surface a constructed, verifiable fact. It is inadequate, and no filesystem sandbox can be adequate, for the provider half (retention, training, region) and for the credential-separation property, which belongs to the provider client. Where the contract cannot be met for a given binding, the honest fallback is to record the provided surface as "host account" and let T2/T4 fail the egress check.

== 6. Derived state, secondary disclosure, and the cognition trade-off

*Derived state.* `run.json`, `checkpoint.json`, `result-message.json`, `execution-evidence.json`, Hop summaries, Findings, commit subjects, promoted reports, terminal output, and CI logs are all derived prose or its projections (prior F4). This review adds that they are *reachable* by later Hops and Runs on the same host (T1, TW1) and that the repository commit is itself a sink (T2). The distinction the follow-up needs is therefore not three storage tiers but two labels per item: the item's *content label* (join of its Hop's provided surface unless declassified) and its *sink audience*. "Operational state", "audit evidence", and "exportable evidence" are then just sinks with different audiences: the state root is operational and carries the Run's join; audit evidence carries the join but is read only by classification-authorized reviewers; exportable evidence is whatever has been explicitly declassified. Evidence becomes an exfiltration path exactly when the second label is missing; the prevention principle is one sentence -- *no sink without an audience label, no promotion without a label comparison* -- and creates no subsystem.

*Delegate cognition aggressively.* Stronger enforcement does not destroy the principle, but it changes what "aggressively" can mean. The value of a large Hop is *investigation breadth* (the agent reads what it decides to read); narrowing the surface removes breadth, not reasoning. Three consequences the follow-up understates. (a) The practical unit of classification is the unit the boundary can export: a repository tree or subtree. "Public source, confidential configuration in one repository" cannot be governed by a reachable-surface boundary without splitting the export, and a partial export usually breaks builds and tests; such a repository is confidential for surface purposes. (b) Under the egress rule, a phase whose sink is a public repository must run on a surface whose join is public, regardless of how capable or trusted the binding is; the binding's trust helps ingress, not egress. (c) Removing `.git` and ignored content from the surface removes tools the agent uses to investigate; the Coordinator must supply bounded substitutes (diffs, listings, selected history) as constructed context, which is more prompt engineering, not less. The trade-off is real and should be stated as such: *information governance is paid in investigation breadth per phase, chosen by policy, and made visible through the required-surface declaration in the same way the omission manifest makes context bounds visible.*

== 8. Explicit answers

. *Is reachable execution surface a sound basis for Information Authority?* Yes, and it is the only honest basis; but only as a *provided* fact established by a Coordinator-owned or verified boundary, compared against a *required* surface, and paired with an egress predicate over sinks (T1, T2). Today no such fact exists: the provided surface is the user account.
. *Can an OS-level sandbox plausibly enforce it?* For the environment half, yes, under the section-4 contract: constructed, provider-independent, exported tree, mount allow-list, fresh `/proc`, cleared environment, single export channel, controlled network egress, no host-side client persistence, verified by probe. For the provider half and for credential separation, no filesystem sandbox can; those remain contractual or client-owned facts and must be recorded as such.
. *Can provider/model trust remain vendor-neutral?* Yes, if compatibility is a conjunction of per-property predicates tagged by owner and evidence class (T5). It cannot remain vendor-neutral as a zone ordering; "on-prem" and "enterprise API" are presets, and each can be less trustworthy than the other on one axis.
. *Is the derived-information rule sufficient?* Not as written. It must join over the provided surface, not cited sources; it is a floor that classification authority may raise; and removal, redaction/transformation, and declassification must be three distinct operations, none performed by summarization (T4).
. *What can the Coordinator honestly audit?* Its pinned inputs and digests, its constructed prompt, its admission/egress decisions, the binding it requested, and -- once it constructs and probes a boundary -- the surface it provided. It cannot audit in-boundary reads, provider processing, retention, or "compliance" beyond its own decision path (section 5).
. *Is the proposed operating model viable for professional internal use?* Viable after correction: narrowest sufficient surface first, then admissibility by provider and environment facts and by sink audience, then capability, then cost (T9). The uncorrected "richest environment" rule is not viable because it maximizes the output label.
. *Does any finding block Slice 5B?* No.
. *What must be true before this architecture could credibly be demonstrated as a professional governance pattern?* (a) The Coordinator constructs or verifies the environment boundary and records the provided surface as constructed/verified evidence. (b) Required-surface declarations exist per phase and `provided ⊆ required` is a fail-closed admission step. (c) Sinks carry audience labels and the egress comparison exists for commit, context hand-off, and promotion. (d) Trust compatibility is a per-property predicate with owners and evidence classes; no zone names in the predicate. (e) Prior F1/F2 hold (governing-input authorship distinguishable; policy dominates WorkItem scope and budget), extended to harness-level governing content (T8). (f) The demonstration states the claims it does not make (section 9).

== 9. Durable professional-governance conclusions

Claims defensible in a future technical presentation if the corrected architecture remains valid:

. Prompt filtering is not an information boundary when the agent can read the workspace, and a workspace is not an information boundary when the sandbox can read the account.
. The disclosure surface is a fact established by the execution boundary, not a declaration in a policy file: policy declares the surface a phase may have, the boundary provides the surface it does have, and admission compares the two.
. Information authority has an ingress side and an egress side; a trusted commit into a repository is a disclosure to that repository's audience and must pass the same label comparison as any promotion.
. Derived material carries at least the join of the reachable surface, never the join of the sources an agent chooses to cite; labels are lowered only by explicit declassification and may be raised by classification authority at any time.
. Provider selection is downstream of surface compatibility, so the boundary that provides the surface must be independent of the provider; otherwise selection is circular.
. A stronger model may increase capability but must not increase authority or surface.
. Trust is a vector with two owners: provider facts are contractual and locally unverifiable; environment facts are technical and locally verifiable. A zone label is at most a policy preset over that vector.
. Git HEAD identifies the tracked tree, not the reachable tree; ignored content, caches, and prior evidence are inside the surface unless the boundary is built from an exported tree.
. Audit evidence proves the Coordinator's decision path and the boundary it constructed; it does not prove in-boundary reads, provider processing, or provider retention.
. The practical granularity of classification is the unit a boundary can export, a repository tree or subtree, not a per-file label set.

Claims the project should *not* make, because the architecture and evidence cannot support them:

. "The provider saw only the files in the prompt" or "only the files in the workspace". At most: "could not have reached anything outside the recorded surface".
. "No confidential data left the environment" or "the model did not retain data". Egress to the provider is the invocation; retention is contractual.
. "This Run was compliant." Only the Coordinator's admission and egress decisions over recorded evidence classes can be claimed.
. "On-premises or enterprise execution is inherently more trusted." Each is a preset over a vector on which it can lose.
. "The Coordinator sandboxes the agent." Today it delegates isolation to the provider client's own sandbox, whose read surface is the user account; the Coordinator bounds effects, not information.
