. `max_autonomous_hops: 2`; normal current `operator.py`; real `CodexCliAdapter`

== 6. Expected declarative inputs and topology

The minimal useful two-phase workflow mirrors the accepted `main()` `N=2`

`work_item.yaml`::

`profile.yaml` (two phases)::
* `prepare`: `role` component `[worker]`, no modifiers/policy components,
  `durable_artifact: none`, `authorized_scope: [PROOF.md]`,
  `authorized_actions: [edit, commit]`, `routes: {verify: {effect: goto, target:

* `verify`: same components/scope, `authorized_actions: [edit, commit]`
  (may be `[]`-of-effect for a read-only H002 but must remain dominated by
  policy), `routes: {done: {effect: complete}}`.

`repository_policy.yaml`:: `scope: [<disposable-repo-identity>]`,
`actions: [edit, commit]`, minimal `evidence_states`.

`components.yaml`:: `worker -> worker.txt` only.

`task.txt`:: trivial deterministic instructions: in `prepare`, rewrite the single
line of `PROOF.md` and request route `verify` with a `commit_intent` over
`PROOF.md` and a subject carrying WorkItem/Hop identity (WFC-GIT-08); in
`verify`, make *no* worktree change and request route `done` (`complete`) with
`commit_intent: null`.

Topology summary:

----
A (clean)
  -> H001 prepare: edit PROOF.md, route goto verify, CommitIntent(PROOF.md)
       -> trusted mechanical commit B
       -> reduce to phase verify, status ready, hop_used=1, current_head=B
       -> publish run.json -> checkpoint.json -> retire dispatch marker
  -> serial gate: checkout + Git revalidation at B + governing-input identity at B
  -> H002 verify: no mutation, route done -> complete
       -> completed, hop_used=2, no H003
----

Governing inputs re-read at B: `work_item.yaml`, `profile.yaml`,
`repository_policy.yaml`, `components.yaml`, `task.txt`, `worker.txt`. H001 mutates
only `PROOF.md`, which is outside the governing set and the only path in
`authorized_scope`, so identity holds and H002 is eligible.

== 7. H002 disposition -- read-only / completion-only (recommended)

*H002 should be read-only / completion-only* (no trusted commit), for the first
live proof:

* It matches the accepted contract fixture ("H002 ... complete through an
  observation-only result with no trusted semantic mutation required",
  FTR 11.5.1) and the accepted `main()` `N=2` test.
* The trusted-commit path is *already* proven live at `N=1` (Slice-4B proof); a
  second commit in H002 adds Git-write surface without exercising anything new.
* The genuinely novel, never-live-exercised surface is the *serial continuation
  mechanics*: post-H001 publication ordering, marker retirement, checkout/Git
  revalidation at B, governing-input content identity at B, fresh phase-B
  prompt/context, a distinct H002 invocation identity and per-invocation binding,
  and budget exhaustion at 2. A read-only H002 isolates exactly those.

A trusted commit in H002 would *increase* proof surface (a second commit,
`current_head` movement to C, a second range) for no first-proof benefit and is
therefore *not* recommended.

== 8. Provider / invocation budget

*Exactly two real Codex invocations are authorized: H001 and H002.* Consumption
follows existing per-Hop one-shot accounting (FTR 11.5.1 "Attempt consumption"):

* H001's invocation is consumed once its provider-capable boundary is reached,
  regardless of outcome (success, malformed, timeout, uncertain, rejected).
* H002's invocation is authorized *only if* the deterministic continuation gate
  passes after H001; if the gate stops (any non-ready state, dirty worktree,
  Git/governing mismatch), H002 is never dispatched and *only one* invocation is
  consumed. The second authorization is then *unused, not banked* -- it may not be
  redirected into a retry or a fresh run.
* No third invocation is possible: `hop_limit==2`, the budget guard, and
  `dispatch_eligible` prevent any H003 marker, invocation identity, or dispatch.

Model/provider are fixed at the accepted binding (`codex`, `gpt-5.6-terra`,
`medium`). No provider fallback or substitution is authorized.

== 9. Consumption / no-retry semantics

Events that consume authority:

* Reaching H001's provider-capable boundary consumes invocation 1.
* Reaching H002's provider-capable boundary (only after a passing gate) consumes
  invocation 2.
* The overall one-shot proof authorization is consumed the moment invocation 1's
  boundary is reached, *irrespective of final Run status*.

After *any* H001 failure, uncertain dispatch, continuation rejection,
dirty-worktree condition, publication fault, or unexpected stop, the required
response is identical: *STOP. Do not retry, resume, re-run, or launch a
replacement.* Preserve the state root and disposable repository verbatim and
record the actual facts for independent review. If execution did not reach the
provider boundary at all, consumption is inspected from durable state, not
guessed (mirrors FTR 11.4.2 "One-shot rule"). Recovery, if ever pursued, is a
separate maintainer decision and uses existing `reconcile_required` semantics; it
is not part of this authorization.

== 10. PASS / STOP criteria

The proof proves *Coordinator mechanics*, not agent competence. Define outcomes
on durable, independently reproduced facts (reproduce Git reality directly from
the disposable `.git`, not from `operator-summary.json`).

*PASS (the one intended happy path) requires all of:*

* exactly two real Codex invocations with two *distinct* `INV-` identities;
* `run_status=completed`, `hop_used=2`, `hop_limit=2`, ordered Hops
  `[H001, H002]`, no H003 marker/identity/invocation;
* H001: `PROOF.md` mutated; exactly one trusted mechanical commit B under the
  configured proof identity (author/committer = the repo-config identity, not an
  agent identity); `current_head=B`; subject carries WorkItem/Hop identity;
* serial gate observably passed: `run.json` -> `checkpoint.json` -> marker
  retirement for H001; checkout + Git revalidation at B; governing-input content
  identity at B;
* H002: no new commit (read-only), `requested_route` reduced to `complete`;
* `execution-evidence.json` has two truthful per-attempt entries (distinct
  invocation IDs, Codex binding, base/end HEADs, outcomes); `operator-summary.json`
  reconstructs both Hops separately and is byte-consistent with reproduced Git
  facts;
* disposable worktree clean; no `*.lock` residue; exit code 0.

*STOP / INCONCLUSIVE (never permission to retry) -- any of:*

* the real agent emits an H001 result that does not reduce to `ready`+route
  `verify` (wrong/unknown route, `requires_human`, malformed, uncorrelated,
  uncertain, invalid finding): H002 legitimately never dispatches. Coordinator
  mechanics may still be *correct* (truthful one-invocation accounting, no H002,
  no H003), but the `N=2` continuation is *not demonstrated*. This is a truthful
  inconclusive result, not a failure to fix and not a licence to re-run.
* any dirty-worktree, unexpected-HEAD-movement, or governing-input mismatch
  between Hops -> `awaiting_human` / `inter_hop_git_validation_failed` /
  `governing_input_changed`, no H002;
* a publication-region fault inside the boundary (WATCH-6) -> best-effort summary
  may under-report `hop_used`; the durable `run.json` + retained dispatch marker
  are authoritative and drive fail-closed `reconcile_required`;
* provider spawn failure, timeout, or non-zero return where accounting is
  conservative;
* any commit under an agent identity, any commit outside `PROOF.md`, any second
  H001 commit, or any H003 artifact -> STOP and treat as a *finding*, not a retry.

The distinction is deliberate: a PASS is the completed `N=2` happy path with
truthful evidence; everything else is STOP/inconclusive and the authorization is
already consumed.

== 13. Known WATCHes / residual risk

* *WATCH-6 (low, non-blocking):* a publication-region crash *inside*
  `run_real_one_hop` skips the `progress` callback, so `main()`'s best-effort
  `operator-summary.json` may report the pre-Hop `hop_used` and
  `invocation_id="not_dispatched"`. Durable `run.json` + retained marker remain
  the truthful recovery authority. Does not make the proof unsafe; it shapes the
  STOP semantics in section 10.
* *WATCH-3 / WATCH-4 (non-blocking):* the outer gate does not itself re-compare
  the exact original checkout association / some marker predicates are inferred
  through Run status; the inner H002 boundary still enforces equality. Unchanged.
* *WATCH-5:* the low-level happy fixture historically ends
  `awaiting_human_budget`; practical significance reduced by the accepted
  completed `main()` `N=2` test. No effect on this proof.
* *Novel-surface residual (the real risk):* the real agent's H002 behavior under
  a fresh phase-B prompt has never been exercised live. This is not a code defect
  and needs no change; it is exactly what the proof observes, and section 10
  classifies a non-cooperating agent as truthful STOP/inconclusive, not failure.
* *Token-efficiency WATCH* (carried from the Slice-4B proof): large input tokens
  relative to a trivial edit; observational only.

None of these makes the proof unsafe or misleading provided the STOP semantics
and evidence retention above are honored. The disposable-repository requirement
(section 4.1) contains all Git-write risk away from `core`.
