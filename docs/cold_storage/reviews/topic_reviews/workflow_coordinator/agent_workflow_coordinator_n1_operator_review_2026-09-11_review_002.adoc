== B1 -- attempt accounting / exit status / summary (RESOLVED)

`operator.py::main` now splits into two regions:

* a *pre-attempt* region (argument parse, `_preflight`, Run construction, fresh
  state-root creation, plan write) whose handler returns `2`
  (`SystemExit` from argparse maps to `0` for `--help`, else `2`; any other
  exception returns `2`);
* an *attempt* region beginning at `register_checkout`, wrapped in
  `except Exception`, which returns `1` and writes a best-effort failure summary
  -- no reclassification by exception type after that boundary.

Answers to the required questions:

. *Original defect eliminated?* Yes. The provider-capable path is entirely
  inside the attempt region, whose handler returns `1`, so a post-dispatch
  failure can no longer be reported as `exit 2`.
. *Can any post-provider failure still escape to exit 2?* No. `exit 2` is only
  reachable from the pre-attempt region, which ends before `register_checkout`
  and therefore before any provider-capable step. The attempt region catches
  `Exception` (deliberately not `BaseException`).
. *Can any post-attempt exception bypass best-effort summary?* No.
  `_write_failure_summary` runs in the attempt handler for every failure,
  including a failure of the success-path summary write itself.
. *Does `_write_failure_summary` preserve only operator-known facts?* Yes. It
  records Run identity/status/budget/anomalies from the known Run
  (`real.run` when available, else the pre-attempt `run`), provider transport
  facts only if an outcome exists, empty `commits`/`changed_paths` (no
  fabrication), and `final_head`/`worktree_clean` only when a fresh
  `observe_repository` succeeds. When observation fails it omits those keys
  rather than inventing Git facts.
. *Can summary writing obscure the original failure?* No. The original error is
  always printed and `exit 1` returned; `_write_failure_summary` suppresses its
  own exceptions and cannot replace the failure with a false success
  (`operator_status: failed`).
. *Second recovery/state machine?* No. It writes one JSON view of known facts;
  it does not reduce, charge Hops, or reconcile. Authoritative recovery remains
  in `run_real_one_hop` (`recover_uncertain`).
. *Authoritative `RealHopRun` preferred?* Yes.
  `known_run = real.run if real is not None else run` and the success path uses
  `real.run`/`real.outcome`.
. *Opposite bug (pre-provider reported as exit 1)?* A genuinely pre-provider
  failure inside the attempt region -- `register_checkout` config rejection or a
  `CodexCliError`/preflight failure inside `run_real_one_hop` (which unlinks the
  dispatch marker) -- now returns `1` rather than `2`. This is the deliberate
  conservative boundary the prior review prescribed ("from `register_checkout`
  onward -> exit 1"). It never *under*-reports consumption: `exit 1` directs the
  operator to inspect the attempt root, where the absence of a dispatch marker
  proves no Hop was consumed. It does not materially misrepresent
  provider/attempt semantics and is not a rejection reason.

== Direct regression check

Because `main` was restructured, the specific regression surface was inspected:

* *hidden retry / second `run_real_one_hop`* -- none; a single call remains, and
  the attempt handler does not re-invoke;
* *provider invocation before plan persistence* -- unchanged; the plan is
  written in the pre-attempt region before `register_checkout`/`run_real_one_hop`;
* *one-shot state-root semantics* -- unchanged (`state_root.exists()` still
  rejects in `_preflight`);
* *`KeyboardInterrupt`/`SystemExit` in the attempt region* -- not caught
  (`except Exception`); the pre-attempt `SystemExit` handler only maps argparse
  exits and is materially correct;
* *false success after summary failure* -- impossible; the success path returns
  `0` only for a completed clean Run, and a success-path summary write failure
  falls to the attempt handler and returns `1`;
* *summary overwriting authoritative Run state* -- no; only
  `operator-summary.json` is written by the operator, never `run.json`;
* *new authority/recovery semantics, altered serialization/config contract,
  changed N=1 scope* -- none; `serialization.py` is untouched by this commit and
  the composition boundary is unchanged.

*DIRECT MATERIAL REGRESSION: NO. SECOND COORDINATOR CREATED: NO.*
