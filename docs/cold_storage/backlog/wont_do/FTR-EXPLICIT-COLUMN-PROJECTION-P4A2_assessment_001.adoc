== 1. Executive conclusion

The hypothesis under test was that `project_by_role` presents an unintuitive
implicit contract, that callers only really need explicit column selection and
ordering, that a direct `project_columns`-style ordered column list would be
clearer, and that `project_by_role` could be removed after migration.

The evidence *falsifies* the load-bearing parts of that hypothesis:

* `project_by_role` is *not* a convenience wrapper over an explicit column
  list. Its essential responsibility is resolving a *dynamic* `matrix_value`
  column set that is **unknowable at pipeline-authoring time** (the per-cast /
  per-group columns of a crosstable matrix grow with the data), plus a
  **direction-coupled retention rule** (inbound drops `display_helper`). An
  explicit ordered column list cannot name columns that do not exist until
  runtime, and cannot express "drop the helper on the way back in" without
  re-enumerating a set it cannot know.
* An explicit, static, ordered column-projection primitive *already exists*:
  `extract_frame` (`columns:` selects and orders columns exactly, strict on
  missing columns, with `rename`, `sort_by`, and NaN->"" normalisation). A new
  `project_columns` step would duplicate an existing capability under a new
  name -- exactly what `docs/ai_info/agent_rules.adoc` ("Metadata, registry,
  and step-surface changes") forbids.
* `project_by_role` cannot be deleted. Its *only* runtime consumer is the
  external `worldbuilding` dino_insel pipeline (10 call sites), which is
  out of scope for this context and which relies on the dynamic-column
  behaviour that no explicit projection can replace. Inside `core` there are
  zero runtime call sites -- only tests and the registry entry -- so there is
  nothing in this repository to migrate atomically.
* The choice of role-based projection *over* explicit positional column lists
  was a *recorded, accepted architectural decision*
  (`FTR-DYNAMIC-FRAME-PROJECTION-P5_decision.adoc`, "Adopt Option C + minimal
  Option-B surface"). The driver review found the *opposite* pain to the
  hypothesis: the same role partition was being reconstructed with *positional
  parameters* at four consumer points, and role-based projection removed that
  duplication. The hypothesis would re-introduce the very pattern the decision
  eliminated.
* The owning FTR (`FTR-DYNAMIC-FRAME-PROJECTION-IMPL-P5`) is still on the open
  backlog surface pending a lifecycle close. Opening a replacement while the
  original slice is mid-acceptance is an ownership conflict.

One narrow, *non-blocking* observation survives (see §9): the `direction` knob
bundles ordering with retention, and outbound `role_order` must be a full
permutation of all three roles. These are minor rigidities, intentional per
the decision, and not motivated by any current consumer need. They do not
justify a replacement step.

Confirmation verdict (companion artifact): *EXPLICIT COLUMN PROJECTION NOT
READY FOR IMPLEMENTATION* -- not because the repository is complex, but because
a bounded implementation is blocked by concrete facts: no in-repo consumer,
essential dynamic-column semantics that explicit projection cannot express, a
pre-existing equivalent primitive (`extract_frame`), and an open owning FTR.

== 4. Role-source trace

`resolve_column_roles` computes three role lists for one frame. Precedence and
sources are concrete (`resolver.py`):

* `row_identity`:
** explicit `key_columns=` override if given (`_string_list`), *else*
** `row_keys` declared on a *single* matching `_meta.xref_crosstable[*]`
   entry whose `matrix == frame` (`_row_keys_from_xref_meta`); *two* matching
   entries raise `ValueError` (ambiguity), *else*
** empty (warn-only via `logging.WARNING`; no exception).
* `display_helper`:
** explicit `helper_columns=` override if given, *else* the ordered *union* of
*** `_meta.sheets.<sheet>.helper_columns` for the sheet mapped to `frame` via
    `_meta.workbook_view.sheets[*]` (`_view_helper_columns` + `_sheet_for_frame`), and
*** FK-helper `derived` provenance columns under
    `_meta.derived.sheets.<frame>.helper_columns`
    (`_fk_helper_provenance_columns` -> `derived_helper_columns_by_sheet`).
* `matrix_value`: **rest-by-exclusion** -- every frame column not classified as
  identity or helper. This is the source of the *dynamic* behaviour.

Precedence / ordering rules (verified):

* Explicit overrides *win* over scattered sources (no union with metadata when
  an override is present).
* *Within-role order follows the frame's column order*, not the override or
  source order (`_ordered_intersection` iterates `df.columns`). Override order
  is intentionally discarded.
* identity/helper overlap: a column claimed by both is logged and treated as
  `row_identity` (removed from helper).
* Missing role metadata: identity -> warn-only empty; helper -> silent empty.
* Unknown role name only arises via `role_order` validation or
  `ColumnRoles.columns_for` (`UnknownRoleError`); the three role names are a
  fixed `frozenset`, not caller-extensible.
* A single column can be in exactly one role (partition). One role may hold
  zero columns. Duplicate frame columns are rejected upstream by pandas
  addressing / the migration-parity fixtures assume unique labels.

The mapping is *derived per run* from current frames + `_meta`; it is **not
persisted** as a role channel. The FTR and decision both flag this as an
*interim* computed strategy pending a future unified
`_meta.derived.sheets.<frame>.column_roles` channel (owned by the foundation
FTR, explicitly out of scope here).

== 5. Exact behaviour matrix

Verified by reading `project_by_role.py` / `resolver.py` and by a read-only
probe on small DataFrames (not committed).

[cols="2,3"]
|===
| Scenario | Observed behaviour

| Single role
| `columns_for(role)` returns that role's frame-ordered columns.

| Multiple roles / role ordering
| Output = concatenation of roles in `role_order`; within-role = frame order;
  duplicates across roles de-duplicated by first occurrence.

| Ordering within a role
| Always the input frame's column order. Never re-sorted.

| Columns without a requested role
| Not possible: every column is partitioned into exactly one role
  (`matrix_value` catches the rest).

| Column with no role declaration
| Becomes `matrix_value` by exclusion.

| Requested role with no matching column
| Contributes nothing; no error (empty role list).

| Unknown role in `role_order`
| `ValueError` naming the offending value and the accepted names.

| Duplicate role in `role_order`
| `ValueError` ("must not repeat role names").

| Outbound `role_order` not a full 3-role permutation
| `ValueError` ("requires role_order to be a permutation of
  [display_helper, matrix_value, row_identity]"). *Cannot select a subset.*

| Inbound `role_order` containing `display_helper`
| `ValueError` (inbound drops `display_helper`).

| Empty / missing `direction`
| `ValueError` (no silent default).

| Missing / blank `frame`
| `ValueError` ("frame must be a non-empty string").

| Frame absent from state
| `KeyError` from `resolve_column_roles._require_data_frame`.

| Non-DataFrame frame value
| `TypeError` ("must be a pandas DataFrame").

| Empty DataFrame
| Reorders an empty column set; no error (all roles empty).

| `_meta` behaviour
| Read-only. `_meta` is not written; `out = dict(frames)` copies the mapping,
  `_meta` object passed through by reference (unchanged).

| Caller-frame mutation
| *None.* Returns a new `frames` dict; the target frame is replaced with a
  `.copy()` (`_reorder_dataframe`). Probe confirmed caller frame unchanged.

| Output-frame identity
| New DataFrame object (copy), same frame *name* (in-place semantics).

| Source == target frame name
| Always: the step is in-place; there is no separate source/output.

| Column labels / types
| Labels coerced to `str` in `_reorder_dataframe`; data values (incl. NaN)
  preserved verbatim (no NaN->"" normalisation).

| Reserved / internal columns
| No special handling; all columns partitioned by role rules.

| Desired visible order not grouped by role
| *Unsupported.* Output is always role-grouped; interleaving a specific column
  between identity columns is impossible (also meaningless for dynamic
  `matrix_value`).
|===

Behaviour that exists only incidentally:

* The exact ordering of the union of helper sources depends on frame column
  order (deterministic, not dict/set iteration order -- `_ordered_intersection`
  re-imposes frame order, so this is *intentional*, not incidental).
* The `sorted(...)` in error messages is cosmetic.
* No behaviour was found that depends on Python dict/set iteration order in a
  way that leaks into results.

== 6. Responsibility classification

[cols="1,3,1"]
|===
| Category | Behaviour | Essential?

| A. Explicit column projection
| Mechanical reorder/retain of a *known* column list.
| Present only as the final `df.loc[:, ordered]` step; the *column list itself
  is not caller-supplied* -- it is derived. So A is not the caller's contract.

| B. Role resolution
| Translate scattered metadata + dynamic rest-by-exclusion into three ordered
  column lists.
| *Essential.* This is the reason the step exists and cannot be expressed by an
  explicit list (dynamic `matrix_value`).

| C. Schema / semantic validation
| `direction` validation; `role_order` permutation/subset/duplicate checks;
  frame-presence and type checks; xref ambiguity.
| Essential-adjacent (guards), but *coupled to the role model*, not to a
  generic projection.

| D. Workbook / presentation policy
| Default outbound order `[display_helper, row_identity, matrix_value]`;
  inbound drop of `display_helper`.
| Domain-roundtrip policy (matrix render vs. reimport), configurable via
  `role_order`. Not pure presentation; it drives the canonical<->matrix
  roundtrip.

| E. Compatibility baggage
| `name` parameter is accepted and discarded (`del name`) for binder
  compatibility.
| Minor; shared convention across steps. Not replacement-motivating.

| F. Unintended implementation artifact
| Outbound requiring a *full* 3-role permutation (no subset selection);
  identity/helper overlap resolution.
| Arguably over-strict, but harmless and consumer-satisfying. Not a defect.
|===

Conclusion: the step's core is **B + direction-coupled D**, not A. A generic
"explicit column projection" transformation would have to *drop* B and D, at
which point it no longer serves the only consumer.

== 9. Architecture assessment

Evaluating `project_by_role` against the requested properties:

* *Explicitness at call site*: partial. `frame`/`direction` are explicit;
  `matrix_value` is intentionally implicit because it is dynamic. Worldbuilding
  call sites pass explicit `helper_columns`/`key_columns`, so identity/helper
  are explicit there.
* *Determinism*: yes -- frame-ordered, override-precedence, single-xref-match.
* *Local understandability*: moderate. Requires knowing the 3-role taxonomy and
  that `direction` bundles order + retention.
* *Composability*: good -- pure `Frames -> Frames`, backend-neutral, no mutation.
* *Arbitrary desired order*: *no* -- only role-grouped permutations; cannot
  interleave. No consumer needs this.
* *Separation of semantic metadata from mechanical projection*: the resolver
  cleanly separates *resolution* (B) from the mechanical `df.loc` reorder (A).
* *Layer ownership*: correct (domain/Frame).
* *Testability*: good (overrides make it unit-testable without `_meta`).
* *User-documentation ease*: moderate; the role vocabulary needs a primer.
* *Future typing compatibility*: fine.
* *Suitability as a public step*: yes for its scoped purpose.

Where is the real problem? Not "only naming" -- the name accurately describes
the operation. The genuine, *narrow* observations are:

. `direction` conflates *ordering* and *retention* (inbound drop). Intentional
  per the decision (symmetric pair as one step), but it is the least obvious
  part of the contract.
. Outbound `role_order` must be a full 3-role permutation; there is no way to
  express a subset. This is a rigidity, not a bug.

Neither observation is a replacement driver, and neither has a demonstrated
consumer need. The hypothesis's premise ("callers only need explicit column
selection and ordering") does not describe the actual consumer, whose need
includes *dynamic column discovery* and *directional retention*.

== 10. Options considered

* *Option 1 -- reuse an existing explicit step and delete `project_by_role`.*
  Rejected. `extract_frame(columns=...)` covers the static case but cannot name
  dynamic `matrix_value` columns; deletion regresses the (external) consumer.
* *Option 2 -- introduce one small explicit `project_columns` step.* Rejected.
  Duplicates `extract_frame`; still cannot serve the dynamic/directional need;
  violates the "no redundant root/step under a new name" rule.
* *Option 3 -- separate resolution and projection.* Already the case: the
  resolver (B) is a separate module from the mechanical reorder (A). No further
  split is needed, and exposing a public "resolve-then-explicit-project" pair
  would push the dynamic column list into user YAML, which cannot be authored.
* *Option 4 -- move selection into Workbook View configuration.* Rejected. The
  operation is not presentation-only: it runs symmetrically on the inbound
  reimport path, which the render-side view step cannot own (the decision's
  documented rationale).
* *Option 5 -- another bounded result.* The only evidence-supported bounded
  result is *no change*: keep `project_by_role`, keep `extract_frame` for
  explicit static projection, and close the owning FTR through its existing
  lifecycle (not through this assessment).

*Selected: Option 5 (no replacement).*

== 11. Selected target contract

None. No new callable, step, parameter, or schema is introduced. `extract_frame`
remains the explicit ordered-column-projection primitive for static columns;
`project_by_role` remains the role-based dynamic matrix projection. The
column-role resolver remains the single source of truth shared by
`project_by_role` and `add_validations` targeting.

== 12. Compatibility / removal decision

* No deprecation, no wrapper, no removal. `project_by_role` is not superseded.
* The project is pre-1.0, but that permits removal only when a replacement
  exists and consumers can migrate; neither holds here.
* Role metadata and the role taxonomy are *retained* -- they have a second live
  consumer (validation targeting) entirely independent of this question.
