== Review questions and findings

=== Consumer evidence

Checked: the decision rests on the *actual* worldbuilding pipelines
(`json_to_spreadsheet.yaml`, `spreadsheet_to_json.yaml`), traced call site by
call site, not on the prior Core assessment's count. All ten sites were read in
their local sequence; the outbound `contract_xref -> join_frames(+title) ->
project_by_role` separation and the inbound `project_by_role -> expand_*`
adjacency were verified directly. *Sound.*

=== Ordinary versus grouped XRef ownership

Checked: the assessment restricts itself to the normal
`contract_xref`/`expand_xref` (+ `expand_compact_multiaxis`) path and explicitly
excludes grouped-XRef, confirming grouped composites wrap *unchanged*
`contract_xref`. The refactor, had one been warranted, would never have belonged
in the grouped specialization. *Correctly scoped.*

=== Accidental API expansion

Checked: the verdict adds no public surface. It keeps `project_by_role` exactly
as shipped and touches no XRef primitive. There is no risk of minting a new
generic step (the rejected `project_columns` proposal is not revived). *Clean.*

=== Hidden compatibility assumptions

Checked: because nothing changes, there is no compatibility exposure. The one
assumption worth naming -- that `expand_xref` is depended on by grouped-XRef and
compact-multiaxis -- was verified in source (`expand_compact_multiaxis` imports
and calls `expand_xref`; the registry documents grouped composites wrapping
`contract_xref`). This *strengthens* the "do not touch it" conclusion. *No
hidden assumption.*

=== Whether explicit composition has value

Checked: yes. `join_frames` (add display helper), `project_by_role` (role
ordering/retention), and `expand_*` (canonical inverse) are individually
meaningful and keep the canonical-vs-view boundary visible. Collapsing them
would hide that boundary. The decision does not "hide useful composability
merely to reduce YAML lines". *Consistent with the decision criteria.*

=== Whether wrappers genuinely reduce consumer knowledge

Checked: a composite would *not* reduce the knowledge a pipeline author needs.
The outbound helper join is consumer-specific and would have to be surfaced as
composite configuration anyway; the inverse split across `expand_xref` /
`expand_compact_multiaxis` means one wrapper cannot serve all five surfaces.
Net knowledge is not reduced. *Wrapper rejection justified.*

=== Whether the design duplicates an existing composite

Checked: no existing composite already does this. `expand_compact_multiaxis` is
the closest (it wraps `expand_xref`), but it is a code/legend codec composite,
not a display-helper projector. The decision to add nothing avoids duplicating
or shadowing it. *No duplication.*

=== Whether all ten call sites can migrate

Checked: not applicable under the selected option -- there is no migration,
because the sites stay as composed. Had Option C been chosen, four of five
surfaces would migrate cleanly and the fifth (`story_group`, compact-multiaxis
inverse) would not, which is itself part of the evidence against Option C.
*The "no migration" outcome is coherent.*

=== Smoke-test integrity

Checked: the FK-helper smoke test used the official Makefile path, wrote only to
gitignored `tmp/`, left `daten/` clean, and classified the result as *not
reproduced* with a concrete provenance (older/incomplete pipeline state; current
pipeline drops the helper on both paths). It did not create a spurious BUG and
did not conflate the leak with `project_by_role` or the nan-semantics xfail.
*Faithful.*

== Residual risk

Low. The only path back to this question is a *new* ordinary XRef consumer that
reproduces the identical display-helper ordering/retention around a symmetric
`contract_xref`/`expand_xref` pair. That consumer does not exist today; if it
appears, it should open its own FTR with concrete call sites.

== Verdict

XREF CROSSTABLE PROJECTION ENCAPSULATION CONFIRMATION ACCEPTED IN REVIEW 001
