==== Architectural Assessment

* `LookupFormulaSpec` (`src/spreadsheet_handling/core/formulas.py`) is
  unchanged by this series and remains backend-neutral: no ODS- or
  LibreOffice-specific vocabulary was added to it.
* `COM.MICROSOFT.XLOOKUP` is confined to
  `_ods_lookup_formula` in the ODS adapter
  (`src/spreadsheet_handling/io_backends/ods/odf_renderer.py`). The diff
  touches only that function's final `return` line plus a comment.
  `tests/architecture/formula_boundary/test_raw_formula_boundary_guards.py`
  (part of the focused run below) mechanically forbids `of:=`/ODS-shaped
  formula syntax in `core`, `domain`, `pipeline`, and `rendering`, giving an
  automated guard -- not only a visual read -- that the fix did not leak
  adapter vocabulary into the domain-neutral layer.
* XLSX rendering (`src/spreadsheet_handling/io_backends/xlsx/openpyxl_renderer.py`)
  is untouched by the diff and still emits Excel-native `=XLOOKUP(...)`;
  `helper_value_mode: values` never constructs a `LookupFormulaSpec` and is
  therefore structurally unaffected by this change.
* The fix does not depend on, or assume, a future ODF specification: it uses
  LibreOffice's existing Microsoft-extension-qualified identifier, which is
  part of the currently supported interoperability surface, and the BUG's own
  Scope and Non-Goals sections explicitly exclude implementing against an
  unpublished future ODF version.
* The pre-fix renderer source already emitted `of:=XLOOKUP(...)` in
  **uppercase** (visible directly in the `5397d9d` diff's removed line), which
  independently falsifies a pure-capitalization explanation before the real
  LibreOffice evidence is even considered. The real headless LibreOffice 25.2.3.2
  UNO run performed during the original review (and re-run during this
  materialization pass, see Validation Evidence) showed the qualified form
  evaluating immediately under a cold `calculateAll()` with no cached value
  involved, and correct recalculation on both an unknown-key edit and a
  valid-key edit -- proving the namespace qualification, not capitalization
  and not a cached result, was the cause.

==== Findings

===== ODS-XLOOKUP-REVIEW-F1 -- File URL construction

*Classification:* Minor / maintainability-portability follow-up.

*Observation:* `tests/utils/libreoffice_uno_probe.py:92` builds the document
URL as `"file://" + ods_path`, and its caller,
`tests/integration/io_backends/ods/test_ods_libreoffice_interop.py:155`, builds
the LibreOffice profile URL as `f"-env:UserInstallation=file://{profile_dir}"`.
Both use plain string concatenation rather than a URI-aware conversion.

*Concrete risk:* a path containing a space, `#`, `%`, non-ASCII characters, or
another URI-significant character could be misinterpreted by LibreOffice/UNO.
Not observed in practice: `pytest`'s `tmp_path` on this project's supported
Linux environment does not produce such paths, so this is not a live defect
today.

*Recommendation:* use `uno.systemPathToFileUrl(...)` (the module already
imports `uno`) in the probe script, and `Path(...).as_uri()` for the profile
directory in the test file.

*Disposition:* does not block acceptance or pushing `c5320a4`; optional,
narrow test-harness follow-up. Not implemented as part of this review.

===== ODS-XLOOKUP-REVIEW-F2 -- Free-port selection race

*Classification:* Minor / watch-only test-assurance risk.

*Observation:* `_free_tcp_port()`
(`tests/integration/io_backends/ods/test_ods_libreoffice_interop.py:63-66`)
obtains a port by binding a temporary socket and closing it, then starts
`soffice` on that port afterward.

*Concrete risk:* another process could claim the same port in the interval
between the probe socket closing and `soffice` binding, producing rare
environmental flakiness. This is a generic pattern shared by many test suites,
not a defect specific to this change's design.

*Disposition:* watch-only unless the opt-in test is observed to be flaky in
practice. No immediate production or test change required. Does not block
pushing `c5320a4`.

===== ODS-XLOOKUP-REVIEW-F3 -- Archived heading convention inconsistency

*Classification:* Minor documentation-convention observation / non-blocking.

*Observation:* the corrected BUG fragment now has, within itself, a genuinely
nested hierarchy: the BUG title (`=====`) is the structural parent of every
`======` BUG section. This was independently confirmed by rendering the file
standalone with Asciidoctor and inspecting the generated HTML: the title
renders as a level-4 section (`<div class="sect4">`, `<h5>`), and each BUG
section (Summary through Resolution) renders as a level-5 section
(`<div class="sect5">`, `<h6>`) nested *inside* that title's container --
i.e. genuinely a child, not a sibling.

Two corrections to the originally assumed framing, based on what was actually
found:

* The effective rendered levels are `<h5>`/`<h6>` (`sect4`/`sect5`), not
  `<h3>`/`<h4>`.
* No document in this repository currently includes
  `ftrs_done/BUG-ODS-XLOOKUP-FORMULA-INTEROP-P4A.adoc` (or, as far as checked,
  any other `ftrs_done/*.adoc` file) -- `docs/cold_storage/backlog/_backlog.adoc`
  only references it by path in prose, and `docs/cold_storage/_cold_storage.adoc`
  itself is not included by anything either. There is therefore no live
  multi-file include chain currently exercising a `leveloffset` against this
  file; the parent-child nesting confirmed above is a property of the
  standalone file, verified by direct rendering, not of an active include
  pipeline.

Separately, inspecting sibling completed-BUG documents in the same directory
(`BUG-XLSX-WORKBOOK-VIEW-BLOB-READBACK-P4A.adoc`,
`BUG-HELPER-CLEANUP-CONTRACT-P4A.adoc`,
`BUG-RUNTIME-META-PERSISTENCE-BOUNDARY-P4A.adoc`) and one currently open
backlog document (`docs/backlog/BUG-COLUMN-LEVEL-PRESENTATION-META-READBACK-P5.adoc`,
live-included into `docs/backlog/_ftrs_open.adoc` with `leveloffset=-2`) shows
all of them use the *opposite* pattern: title at `=====`, sections at `====`
-- one level *shallower* than the title, rendering as siblings rather than
children (directly confirmed for one sibling by the same HTML-nesting check).
Two of four inspected `*_review.adoc` artifacts in this same directory
(`BUG-CROSS-CARRIER-META-ROUNDTRIP_review.adoc`,
`BUG-XLSX-WORKBOOK-VIEW-BLOB-READBACK-P4A_review.adoc`) follow that same
shallower-sections pattern for their own review title. No written convention
document in `docs/ai_info/` or `docs/developer_guide/` was found stating which
pattern is the intended one.

This additional evidence reinforces, rather than weakens, the original
observation, so it is preserved as a Minor finding rather than downgraded to a
non-finding: the fix makes this one BUG document internally self-consistent
and correct against the specific contract stated for this review, but it is
now the outlier relative to the dominant pattern used by both older sibling
BUG documents and most inspected review artifacts, including at least one
still-open, live-included backlog document. Whether the newly applied pattern
or the dominant older pattern is the "correct" one for the archive as a whole
was not established by this or the prior review round.

*Disposition:* the current BUG hierarchy is accepted and must not be reverted.
Any broader normalization of historical archive documents (or of the review
convention itself) is outside this BUG's scope and should only happen under a
separate, explicit documentation-hygiene decision. No residual scope is
created against `BUG-ODS-XLOOKUP-FORMULA-INTEROP-P4A` by this observation.
