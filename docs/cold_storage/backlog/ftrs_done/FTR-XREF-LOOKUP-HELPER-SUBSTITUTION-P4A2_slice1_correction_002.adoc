== 3. Exact correction per finding

=== 3.1 R002-IMP-001 — equal-name asymmetric helper collisions

`_check_key_helper_collision` (`enrich_lookup/operation.py`) no longer exits
early on label equality. It now gates only on the *selected* mode
(`resolved.is_asymmetric`) and handles two cases:

* *equal key names* (`source_key == lookup_key`): a projected field equal to
  that single key is rejected as one collision spanning both roles — in explicit
  asymmetric mode the key is the authoritative source key and cannot also be an
  independent derived helper;
* *distinct key names*: unchanged — a field equal to the lookup key is rejected
  (leak) and a field equal to the source key is rejected (overwrite).

Because the guard runs over `projection_fields` (which excludes a source/output
key sort — that field equals the join key and is therefore filtered out by
`_fields_with_sort_helpers` before it can become a temporary projection), a
plain `sort_by=[<key>]` remains a valid source-key sort. Policy-derived helpers
flow through `_resolve_fields` into the same check, and a mixed list such as
`[id, title]` fails atomically on the first offending entry, before
`out`/provenance is built, so caller frames are never mutated. Legacy symmetric
mode is untouched (the guard returns immediately for symmetric mode).

=== 3.2 R002-IMP-002 — mismatch verification fails closed

`derived_column_policy._check_enrich_lookup_values` now validates provenance
*before* coercion via `_validated_mismatch_keys`, and requires the named key
columns to exist before comparing:

* *symmetric `on`* must be a non-empty list/tuple of non-empty strings
  (`_validated_symmetric_on`); a bare string, integer, mapping, empty list,
  blank element, or non-string element raises a clear `ValueError` naming the
  `_meta.derived` path — no more character-by-character or key iteration;
* *asymmetric* keys must each be a single non-empty string
  (`_validated_single_key`); blank/whitespace, list/object/integer values, a
  partial pair, or an `on`+asymmetric mix raise a clear `ValueError`;
* before building the canonical map, every resolved payload key column must
  exist in the payload and every lookup key column in the lookup frame. If one
  is absent, verification is impossible, so the reader emits a
  severity-appropriate `unverifiable_enrich_lookup` finding (naming the missing
  columns, frames, and provenance path) instead of an empty comparison.

Deterministic settled behavior:

* invalid provenance *shape* (types/blank/partial/mixed/bad `on`) raises a
  `ValueError` in both warn and fail modes — a broken contract, not a data
  mismatch;
* a *missing key column* on well-formed provenance produces the inability-to-
  verify finding: under `warn_on_mismatch` it is a warning; under
  `fail_on_mismatch` it is a failure finding, so `apply_derived_column_policy`
  raises before consuming provenance or removing the helper;
* `policy: drop` never calls the checker and stays value-blind.

Preserved unchanged: valid symmetric records, valid different-name and
equal-name asymmetric records, unchanged/edited warn/fail, unmatched-reference
skipping, null-key normalization, duplicate-lookup first-occurrence rule,
missing-lookup-frame findings, and stale absent-helper-column no-op.

=== 3.3 R002-IMP-003 — duplicate helper requests

A new `_check_duplicate_helper_fields` guard rejects a duplicate entry in the
resolved helper `fields` (inline `helpers.fields` *or* policy `default_helpers`)
with a clear domain `ValueError` before projection, formula construction,
ordering, output, or provenance. This is applied consistently to values and
formula modes and to both `after_data` and `before_key`. A helper that is also
named in `sort_by` is *not* a duplicate helper and remains valid.

*Decision — generic guard (symmetric and asymmetric).* The same silent
duplicate-label / duplicate-provenance defect already existed in symmetric mode
via the retained `fields` list (`_reorder_helpers_before_key` and
`_write_provenance` consume the raw list). Rejecting literal duplicates is a
safe, backward-compatible tightening: no valid pipeline requests the same helper
twice, the full suite stays green, and the parent/current symmetric probe is
`exact_equal` for every non-duplicate input (section 13). A symmetric
`[label, label]` request now raises rather than silently producing duplicate
columns/provenance.

=== 3.4 R002-IMP-004 — load-bearing formula-renderer tests

`TestAsymmetricFormulaRendering` was rebuilt on a nontrivial layout: the source
key `story_id` is not the first source column (column B by default, column C
after `before_key`); the lookup key `id` is at column D and the lookup value
`title` at column B, separated by unrelated columns (`misc1`, `misc2`); and the
lookup frame is mapped to a physical sheet named `Entity Lookup` (with a space).
Each test asserts the *exact* rendered formula string, so a swap of the key and
value ranges — or a positional renderer — fails. Both `after_data` and
`before_key` are covered for XLSX and ODS, plus an equal-name explicit
asymmetric formula collision test from R002-IMP-001.

== 4. Equal-name asymmetric helper/key contract

For an explicit `source_key`/`lookup_key` pair with equal names, the single key
is the authoritative source key. A requested helper (inline or policy-derived)
equal to that key is rejected before projection/formula/provenance in both value
modes; a mixed list containing it fails atomically; and no output frame or
provenance is produced on failure. This mirrors the distinct-name contract and
follows the selected public mode, not label equality.

== 5. Source-key sorting distinction

`sort_by=[<key>]` is a source/output-key sort, not a helper projection: the key
equals a join key, so `_fields_with_sort_helpers` never adds it as a temporary
lookup projection and it never enters `projection_fields`. The collision guard
therefore never sees it, and the sort remains valid in both equal-name and
distinct-name asymmetric modes. Requesting the key as a *helper* is invalid;
sorting the output by it is valid — the two are explicitly distinguished.

== 6. Mismatch-provenance validation contract

`_validated_mismatch_keys` accepts exactly:

* symmetric `{"on": [<non-empty str>, ...]}` (non-empty list/tuple); or
* asymmetric `{"source_key": <non-empty str>, "lookup_key": <non-empty str>}`.

Everything else (bare-string `on`, integer/mapping `on`, empty list, blank/
non-string element, blank/whitespace key, list/object/integer key, partial
pair, `on`+asymmetric mix) raises a `ValueError` naming the `_meta.derived`
path. A record with no join-key form yields empty key lists (value-check no-op).

== 7. Missing-column failure behavior

When provenance is well-formed but a named key column is absent from the payload
(source key) or the lookup frame (lookup key), the reader returns an
`unverifiable_enrich_lookup` finding carrying the missing column(s), the frame
names, and the provenance path. Under `fail_on_mismatch` the finding is a
failure and `apply_derived_column_policy` raises before dropping the helper or
consuming provenance; under `warn_on_mismatch` it is an emitted warning. This
closes the fail-open path where verification was impossible but zero mismatches
were certified.

== 8. Duplicate-helper rule

Each helper column may be requested at most once. A duplicate in the resolved
`fields` list raises `ValueError` before any projection/output/provenance. The
rule is generic (symmetric and asymmetric), deterministic across value modes and
helper positions, and does not affect a helper that is also used as a `sort_by`
criterion. Valid calls therefore always carry each materialized helper exactly
once in output and provenance.
