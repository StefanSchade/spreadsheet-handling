===== BUG-ODS-MISSING-CARRIER-LITERAL-NAN-RENDERING-P4A -- ODS renderer's NaN-blind emptiness check can serialize a real missing carrier as literal text "nan"

*Status:* Fixed
*Priority:* P4A
*Area:* ODS render/write boundary / carrier-missing-value handling
(`io_backends/ods/odf_renderer.py`)
*Release relevance:* Post-`0.2.0`. Not a runtime blocker by itself. A
concrete, evidenced carrier leak at the ODS write boundary, discovered and
independently reproduced during Semantic Contract Review 001 of
`BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`
(commit `c32bbb3ecb9659324bb98dc769dafdeaddd78564`). Preferably closed before
the future Minimal Internal Value Model (`roadmap_domain_hardening_sequence.adoc`
Phase D) begins, since it is an existing, reproducible `Missing`-adjacent
carrier defect that model will otherwise have to route around or rediscover.

==== Summary

`io_backends/ods/odf_renderer.py`'s per-cell write branch tests cell
emptiness with:

[source,python]
----
if value in (None, ""):
    table_cell = TableCell(attributes=attributes)
----

Python's `in` uses `==` comparisons, and by IEEE-754 definition
`float('nan') == float('nan')` is `False`, so `nan in (None, "")` is
`False`. A raw pandas/NumPy missing carrier therefore *fails* this
emptiness check and falls through to the next branch,
`isinstance(value, (int, float)) and not isinstance(value, bool)` -- which
is `True` for a Python/NumPy `float('nan')` -- and is written as
`valuetype="float"` with paragraph text `str(value)`, i.e. the literal text
`"nan"`, into the cell. On reload, `odf_parser.py`'s `_cell_value` reads
that paragraph text first and returns the literal string `"nan"`, silently
turning framework/carrier missing state into legitimate-looking domain
text.

This is the same underlying mechanism `BUG-UNRESOLVED-HELPER-VALUE-NAN-
SEMANTICS-P4A` originally pinned and fixed *one* trigger of (an FK-helper
*lookup miss*). This BUG is the residual: the renderer branch itself is
still unfixed and is reachable by *any* real missing carrier that gets as
far as the renderer, not only by the now-fixed lookup-miss path.

==== Scope boundary: this is not the unresolved-FK lookup-miss defect

`BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`'s Implementation slice 1
already closed the lookup-miss cause:

[source,text]
----
lookup miss -> apply_fk_helpers supplies "" -> no pandas missing carrier
introduced by the miss
----

That fix, and the accepted semantic contract reviewed and accepted in
Semantic Contract Review 001 (helper value is derived presentation;
resolution authority is the source FK reference plus a live target lookup;
unresolved and resolved-empty helper cells may both legitimately be `""`),
are both unaffected by this BUG and are explicitly *not* reopened here.

The defect this BUG owns is the separate, still-open residual case that
review confirmed and re-verified end to end:

[source,text]
----
lookup succeeds
-> target payload itself is None / NaN / another maintained missing carrier
-> successful dictionary hit in apply_fk_helpers returns that payload verbatim
-> pandas helper column contains a real missing carrier
-> layout_composer.compose_workbook copies df.values.tolist() with no
   NaN/None normalization
-> ODS renderer's `value in (None, "")` check is NaN-blind and misses it
-> literal text "nan" is written
----

`apply_fk_helpers` (`core/fk.py:~327-352`) is correct and unaffected: its
`value_map.get(_norm_id(rid), "")` default only ever fires on a dictionary
*miss*. A dictionary *hit* -- a successful FK resolution -- returns its
stored target payload unchanged, by design; that is not a bug in
`apply_fk_helpers`, it is the renderer boundary mishandling a legitimate
carrier value it receives.

==== Confirmed generality: not FK-helper-specific

The task framing that motivated this BUG treats the FK-helper successful-hit
case as the *proven trigger*, not necessarily the *only* trigger, and asks
for the narrowest evidenced generality rather than an assumed one. Two
independent, real end-to-end reproductions were run for this BUG (read-only
probes, no production/test file modified; full transcripts in "Validation"
below):

. *FK-helper successful hit with a missing target payload* (the originally
  suspected trigger, now re-confirmed on real files rather than only
  in-memory): a target row's `name` field is `None` (or, separately,
  `math.nan`); the FK resolves successfully; `apply_fk_helpers` returns the
  stored missing carrier verbatim; after a real render+reload cycle,
  XLSX reloads the cell as `''` (OpenPyXL's own accidental NaN-to-blank
  write behavior), ODS reloads it as the literal string `'nan'`. True for
  *both* a Python `None`-derived carrier and a genuine `numpy.nan`.
. *An ordinary, non-FK, non-helper column sourced from `csv_dir`* --
  `io_backends/csv_backend.py`'s `CSVBackend.read_multi` (used by
  `load_csv_dir`, the `csv_dir` loader) calls
  `pd.read_csv(p, header=0, encoding="utf-8")` *without* `dtype=str` or
  `keep_default_na=False` (unlike the single-file `CSVBackend.read` path,
  which deliberately sets both). A blank CSV cell in this path becomes a
  genuine pandas `NaN` with no FK-helper machinery, no `apply_fk_helpers`
  call, and no helper column involved at all. Rendering that frame directly
  to XLSX and ODS reproduces the identical pattern: XLSX reloads `''`, ODS
  reloads the literal string `'nan'`.

Reproduction 2 has no dependency on FK helpers whatsoever, so this is
correctly scoped as a general *ODS render/carrier-boundary* defect --
*any* raw pandas/NumPy missing carrier that reaches
`io_backends/ods/odf_renderer.py`'s per-cell write branch is at risk of
this corruption -- with the FK-helper successful-hit case and the
`csv_dir` ordinary-column case both serving as proven, independently
reproduced triggers. No claim broader than what these two reproductions
show is made; other potential carriers of a raw missing value into the
same renderer branch were not enumerated or tested here.

==== Root cause -- pinned

Distinguishing observed fact from prior BUG's already-recorded trace
(re-verified current, not re-derived from scratch, since the code has not
changed since `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A` originally
pinned it):

. `rendering/composer/layout_composer.py:353` (`compose_workbook`) copies
  `df.values.tolist()` directly into `TableBlock.data` with no NaN/None
  normalization at the render-IR boundary. Confirmed unchanged.
. `io_backends/ods/odf_renderer.py:546-563` (inside the per-row/per-cell
  write loop): `value = "" if cell is None else cell.value`, then
  `if value in (None, ""):`. Confirmed still present, unmodified, at these
  exact lines.
. `nan in (None, "")` is `False` because `nan == nan` is `False`
  (IEEE-754). The check therefore does not recognize a missing carrier.
. The value falls through to
  `elif isinstance(value, (int, float)) and not isinstance(value, bool):`
  (line 573) -- `True` for a Python `float('nan')` and for
  `numpy.float64('nan')` alike (both are real `float` instances) -- and is
  written as `valuetype="float", value=value` plus
  `table_cell.addElement(P(text=str(value)))`, i.e. the literal paragraph
  text `"nan"`.
. `io_backends/ods/odf_parser.py`'s `_cell_value` reads the cell's
  paragraph text first, before consulting `office:value-type`/
  `office:value`, so the mistaken `"nan"` text is exactly what round-trips
  back out.
. *XLSX comparison, confirmed unchanged:* `io_backends/xlsx/
  openpyxl_renderer.py`'s `_xlsx_cell_value` (`~line 182-198`) passes the
  raw value straight to `ws.cell(..., value=val)` with no NaN handling at
  all; OpenPyXL itself silently converts a NaN-valued cell to blank/`None`
  on save (accidental library behavior, not a decision made anywhere in
  this codebase, exactly as the original BUG already established). XLSX
  therefore does not corrupt to `"nan"` text, but this is luck, not a
  correct or owned carrier-missing check either -- it has simply never
  been observed to misfire the way the ODS check does.

This is the identical mechanism `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-
P4A`'s "Root cause -- pinned" section already traced for the lookup-miss
case; that BUG's Implementation slice 1 fixed the *miss* by never
introducing the carrier in the first place, while leaving this renderer
branch itself untouched (explicitly recorded there as "still open" and
"outside this slice's owned contract"). This BUG owns fixing the branch
itself, since a lookup miss is not the only way a real missing carrier can
reach it.

==== Existing NaN-aware precedents in this codebase

The project already has multiple correct, `pd.isna`-based "is this a
missing carrier" predicates; none is applied at the ODS renderer's write
boundary:

* `core/fk.py:_norm_id` -- returns `None` for a value that fails
  `pd.isna(v)`-based recognition; used for FK key normalization. Lives in
  `core`, a layer `io_backends` already depends on (both ODS and XLSX
  renderer/parser modules already import from `spreadsheet_handling.core.
  formulas`).
* `domain/transformations/derived_column_policy.py:_norm` (line ~605) --
  `bool(pd.isna(value))`-guarded, used for `enrich_lookup` mismatch
  comparison.
* `domain/validations/fk_helpers.py:_norm` / `_norm_key` -- same pattern,
  used for FK-helper diagnostics.
* `domain/_cell_primitives.py:_is_empty_cell` -- the closest match in
  *shape* to what the renderer needs (a boolean "is this cell empty"
  predicate: `None`, `""`, or `pd.isna(value)`), and is already reused
  across many `domain` consumers (`tabular_views.py`, `cell_codec/*.py`,
  `join_views.py`, `resource_overrides.py`, `xref_crosstable/*.py`,
  `discriminator_split/values.py`, `_legend_blocks.py`,
  `_where_predicates.py`, `validations/reference_validations.py`,
  `validations/graph_validations.py`, `structured_yaml.py`). It is,
  however, in `domain`, a layer `io_backends` does not currently import
  from at all (confirmed: no `io_backends/**/*.py` file imports anything
  from `spreadsheet_handling.domain`); reusing it directly at the renderer
  boundary would be a new, currently-absent dependency direction, not a
  drop-in reuse.

No fix is chosen here. This section is evidence for "a fix belongs to a
recognized, already-established pattern, not a novel one," not a decision
about where the concrete predicate should live.

==== Recommended narrow direction (not implemented, not authorized)

*Recommended, non-binding:* replace the ODS renderer's hand-written
`value in (None, "")` test with an owned, `pd.isna`-aware carrier-missing
predicate at the ODS render boundary, applied *before* the
`isinstance(value, (int, float))` branch is reached, so a real missing
carrier is recognized regardless of which upstream path produced it. Two
concrete shapes are plausible and neither is chosen here:

* a small local predicate inside `io_backends/ods/odf_renderer.py` (no new
  cross-layer dependency, mirrors how the ODS/XLSX adapters are otherwise
  self-contained); or
* a shared predicate hosted in `core` (a layer both renderers already
  depend on), so XLSX's currently-accidental-but-harmless pass-through
  could optionally adopt the same explicit check for symmetry, without
  requiring it to change behavior.

Whether the XLSX renderer should also gain an explicit (currently merely
accidental) missing-carrier handling path is an open question this BUG
does not decide; XLSX's current behavior is not evidenced as broken, only
as undocumented luck.

==== Resolution

*Chosen boundary:* a local `_is_missing_carrier` predicate defined directly
in `src/spreadsheet_handling/io_backends/ods/odf_renderer.py`, applied in
the per-cell write loop (`_build_table`) immediately before the
`isinstance(value, bool)` / numeric / string branches. This is the first of
the two "plausible shapes" this BUG's "Recommended narrow direction" left
open -- a small local predicate, no new cross-layer dependency -- chosen
over hosting it in `core` because the defect and its fix are both owned
entirely by the ODS renderer's own write boundary; nothing about the XLSX
renderer's currently-accidental-but-harmless pass-through needed to change
to close this BUG, so no shared module was introduced. `io_backends` does
not import `domain._cell_primitives._is_empty_cell`; the predicate is a
self-contained copy of that established shape (`None` -> `True`; `str` ->
`value == ""`; else `bool(pd.isna(value))` guarded by
`try/except (TypeError, ValueError)`), not an import.

*Root cause, confirmed as pinned:* `value in (None, "")` uses `==`, and
`float('nan') == float('nan')` is `False` (IEEE-754), so a real
pandas/NumPy missing carrier fell through into
`elif isinstance(value, (int, float)) and not isinstance(value, bool):` and
was written as `valuetype="float"` with paragraph text `str(value)`, i.e.
the literal text `"nan"`. Confirmed via a pre-fix reproduction script
(`RenderPlan` + `WriteDataBlock` carrying `math.nan` / `numpy.float64('nan')`
directly, `render_workbook`, then parsing `content.xml`): both produced
`office:value-type="float"` with paragraph text `"nan"`. A genuine
`pandas.NA` reaching the same branch pre-fix did not even reach the
`"nan"` text -- it raised `TypeError: boolean value of NA is ambiguous`
inside `value in (None, "")` itself, an additional pre-existing defect this
fix also incidentally closes since `pd.isna(pd.NA)` is a safe, unambiguous
`True`.

*Fix:* replace `if value in (None, ""):` with
`if _is_missing_carrier(value):`. `None`, `""`, `math.nan`,
`numpy.float64('nan')`, and `pandas.NA` all now take the existing blank-cell
branch (`TableCell(attributes=attributes)`, no `office:value-type`, no
paragraph text) instead of falling into the numeric branch.

*Literal `"nan"` preservation:* the predicate detects the carrier, not the
spelling -- `isinstance(value, str)` is checked before `pd.isna`, so a
legitimate domain string equal to `"nan"` returns `False` (not the empty
string) and still takes the existing string branch
(`valuetype="string"`, paragraph text `"nan"`), unchanged.
