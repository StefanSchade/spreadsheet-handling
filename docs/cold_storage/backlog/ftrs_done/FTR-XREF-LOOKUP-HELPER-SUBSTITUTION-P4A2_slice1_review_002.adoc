==== XREF-S1-R002-IMP-001 — equal-name asymmetric helpers bypass collision safety

Severity:: Important
File / symbol:: `src/spreadsheet_handling/domain/transformations/enrich_lookup/operation.py` —
`_check_key_helper_collision`, `_build_helper_projection`,
`_build_formula_enrichment`, and public documentation describing the guard.
Evidence::
`_check_key_helper_collision` returns immediately when
`source_key == lookup_key`. Explicit asymmetric mode remains asymmetric in
`_ResolvedKeys`, but collision safety is decided by label inequality. Direct
probes with `source_key=id`, `lookup_key=id` showed:

* `helpers.fields=[id]`, values mode succeeds with output `[id,dyn]`; no
  independent helper is materialized, but provenance claims
  `helper_columns=[id]`;
* the same request in formula mode replaces every authoritative source `id`
  value with `LookupFormulaSpec(...lookup_value_column='id')`;
* `helpers.fields=[id,title]` silently claims both helpers in values mode and
  overwrites `id` in formula mode;
* a helper policy whose `default_helpers=[id]` is accepted and publishes the
  same false helper provenance; and
* normal `title` enrichment and `sort_by=[id]` are safe, because the latter
  is an output/source-key sort and is not a temporary lookup projection.

The symmetric legacy `key=id, helpers.fields=[id]` behavior is the same, but
compatibility does not require the new, explicitly selected asymmetric mode to
inherit that unsafe ambiguity. Review 001 explicitly required asymmetric mode
identity and key authority to follow the public form even when labels are
equal.
Impact::
The source identity can be destroyed in formula mode; values mode can silently
claim a helper that does not exist independently; downstream helper removal may
drop the authoritative key because provenance calls it a helper. Public docs
state without an equal-name exception that a helper equal to either key is
rejected and the source key is never overwritten, so the runtime contradicts a
public safety guarantee.
Required correction::
Apply the asymmetric helper collision rule by selected mode, including equal
labels. Reject requested helper fields equal to the single asymmetric key in
both values and formula modes, including policy-derived helpers and mixed
`[id, other]` lists, before projection/formula/provenance. Preserve
`sort_by=[id]` as a legitimate source-key sort when `id` is not requested as
a helper. Do not tighten symmetric legacy behavior unless separately scoped.
Add direct and YAML equal-name tests for values, formula, policy helpers, and
mixed helper lists; assert the caller inputs remain unchanged and no returned
output/provenance exists because the call fails.
Blocks Slice 2:: Yes.

==== XREF-S1-R002-IMP-002 — mismatch verification still silently accepts invalid key contracts

Severity:: Important
File / symbol:: `src/spreadsheet_handling/domain/transformations/derived_column_policy.py` —
`_resolve_mismatch_keys`, `_canonical_value_map`, and
`_column_mismatch_indices`.
Evidence::
The correction rejects partial and mixed provenance, but converts present key
values with `str(...)` without validating that they are non-empty strings.
It also does not require the resolved payload and lookup key columns before
comparison. Review probes edited `title`, invoked `fail_on_mismatch`, and
observed successful helper removal with zero findings for each of:

* empty `source_key` or `lookup_key`;
* list/object `source_key`;
* list/integer `lookup_key`;
* missing payload `source_key` column; and
* missing lookup `lookup_key` column.

The wrong metadata values become misleading column names such as
`"['story_id']"`. Missing payload keys are skipped by the conditional tuple
comprehension; missing lookup keys make the canonical map empty. Both paths then
treat every row as unverifiable/unmatched, return no finding, drop the helper,
and strip the consumed provenance. Symmetric malformed `on` values retain
similarly inconsistent behavior (a string is iterated character by character,
a mapping iterates keys, and an integer raises raw `TypeError`).

Valid asymmetric records are corrected: unchanged helpers pass, edited helpers
warn/fail, equal names work, null keys compare, multiple helpers isolate the
edited field, missing lookup frames warn/fail, unmatched references remain a
documented separate concern, and `drop` remains value-blind. Duplicate lookup
keys retain the established symmetric first-row-wins behavior; no new
asymmetric regression was found there.
Impact::
A public `fail_on_mismatch` gate can silently certify an edited helper when
the provenance key shape or available frames make verification impossible. This
violates the confirmed clear-error treatment for malformed provenance and
repeats the core safety failure from Review-001 IMP-002 on adjacent inputs.
Required correction::
Validate both provenance shapes before coercion: symmetric `on` must have the
writer's list/tuple shape containing non-empty strings; asymmetric keys must
each be a single non-empty string. Before canonicalization, require every
payload and lookup key column, producing clear path/frame diagnostics (or a
severity-appropriate inability-to-verify finding) rather than an empty
comparison. Add wrong-type, blank, missing-column, null, duplicate, and
equal-name tests for both warn and fail, while preserving intentional unmatched
reference and value-blind drop behavior.
Blocks Slice 2:: Yes.

==== XREF-S1-R002-IMP-003 — duplicate helper requests create ambiguous output and provenance

Severity:: Important
File / symbol:: `src/spreadsheet_handling/domain/transformations/enrich_lookup/operation.py` —
`_fields_with_sort_helpers`, `_build_helper_projection`,
`_reorder_helpers_before_key`, and `_write_provenance`.
Evidence::
`_fields_with_sort_helpers` deduplicates the projection used for validation,
but the original `fields` list is retained for reordering and provenance.
With distinct asymmetric keys and `helpers.fields=[title,title]`:

* default `after_data` returns one physical `title` but writes
  `helper_columns=[title,title]`; and
* `helper_position=before_key` returns duplicate output labels
  `[title,title,story_id,...]` and duplicate provenance in both values and
  formula modes.

The duplicate-label result triggers pandas warnings during ordinary inspection
and is ambiguous for downstream projection/removal. No public documentation
forbids duplicate field entries, and the correction's collision contract
claims deterministic safe projection.
Impact::
An accepted asymmetric helper request can still publish duplicate column labels
or false/non-canonical provenance. This is a real projection correctness defect,
not a style preference, and leaves the collision/output contract unstable.
Required correction::
Define a deterministic public rule for duplicate requested helper names.
Prefer rejecting duplicates with a clear domain error before any output, or
canonicalize once and use the same canonical list consistently for validation,
formula construction, ordering, output, and provenance. Add values/formula and
before-key/default tests. Preserve legacy symmetric behavior if compatibility
requires an asymmetric-only guard.
Blocks Slice 2:: Yes.

==== XREF-S1-R002-IMP-004 — renderer regression tests cannot prove lookup argument order

Severity:: Important
File / symbol:: `tests/unit/domain/transformations/test_lookup_formula_mode.py` —
`TestAsymmetricFormulaRendering.test_xlsx_renders_asymmetric_lookup_formula`
and `test_ods_renders_asymmetric_lookup_formula`.
Evidence::
The tracked source/spec tests correctly assert distinct key names. The two
renderer tests, however, use source key in the first source column and lookup
`id,title` as the first two adjacent lookup columns. They assert only that the
rendered text contains the source reference and both range substrings. A
renderer that always chooses positional columns, or swaps the XLOOKUP key and
value arguments, would still satisfy those membership assertions because both
ranges remain present.

The independent nontrivial probe placed the source key at column B (and C after
`before_key` reordering), lookup value at B, lookup key at D, separated by
unrelated columns, and mapped frames to physical sheet names containing spaces.
Current implementation rendered correctly:

* default XLSX:
  `=XLOOKUP($B2,'Entity Lookup'!$D$2:$D$3,'Entity Lookup'!$B$2:$B$3,"")`;
* `before_key` XLSX:
  `=XLOOKUP($C2,'Entity Lookup'!$D$2:$D$3,'Entity Lookup'!$B$2:$B$3,"")`;
* ODS used the corresponding source reference, D key range, and B value range.

That runtime evidence proves the code is currently correct, but the committed
tests would not fail for swapped/positional regressions. Review 001 classified
the changed formula path as Important precisely because later changes need
load-bearing regression protection.
Impact::
Incorrect lookup formulas could be emitted while every tracked asymmetric
formula/rendering test remains green. The tests do not meet the stated
Review-002 standard for distinct-key rendering semantics.
Required correction::
Use nontrivial source and lookup layouts (key not first; value non-adjacent and
at a different position; unrelated columns present; physical sheet rename) and
assert the exact XLSX formula or parse and compare its ordered arguments.
Assert the exact/parsed ordered ODS formula rather than unordered substring
membership. Cover default and `before_key` source-column movement.
Blocks Slice 2:: Yes.

== 5. Collision-contract assessment

For distinct names (`story_id -> id`), the new guard works as intended:

* helper `story_id` and helper `id` fail deterministically in values and
  formula modes;
* `sort_by=[id]` fails as a lookup-key projection collision;
* `sort_by=[story_id]` sorts the source/output key safely;
* an unselected independent lookup `story_id` does not leak;
* a selected field differing only by case is treated as a distinct,
  case-sensitive label; source/lookup key spellings differing only by case join
  correctly, while exact matches to either role are rejected;
* a sort helper also requested as an output helper is retained once and sorts
  correctly;
* an empty helper list returns the source columns and an empty helper record;
  `helpers=None` returns the source columns without provenance; and
* collision errors are raised before `out` or `_write_provenance` is
  reached, so no observable output mapping can be returned.

The tests' assertions that the caller mapping lacks the output are not proof of
the last point—the callable never mutates that mapping even on success—but code
inspection confirms the guard precedes output/provenance construction.

Equal-name asymmetric helpers and duplicate helper lists remain unsafe under
R002-IMP-001 and R002-IMP-003.

== 6. Equal-name asymmetric assessment

`_ResolvedKeys` correctly preserves explicit asymmetric mode when both labels
are `id`, and provenance retains
`{"source_key":"id","lookup_key":"id"}` in direct and YAML calls.
Normal helpers, normal values/formula specs, sorting by the source/output key,
and mismatch checking work.

Collision safety does not follow the preserved mode. The explicit equality
early return treats helper `id` like legacy symmetric overlap. In values mode
the key projection is deduplicated and no independent helper exists; provenance
nevertheless declares `id` a helper. In formula mode assignment by field name
overwrites the key. A policy-selected `id` and a mixed `[id,title]` list have
the same defect.

The public asymmetric form should retain stricter source-authority semantics
even though a rename is unnecessary. Symmetric compatibility can remain
unchanged. R002-IMP-001 is load-bearing.

== 7. Mismatch-policy assessment

For valid in-memory provenance, the correction successfully separates payload
`source_key` from lookup `lookup_key`:

* unchanged warn/fail: no mismatch;
* edited warn: one `derived_value_mismatch` finding;
* edited fail: raises;
* drop: helper removed without value comparison;
* unmatched reference: skipped consistently with symmetric behavior;
* equal-name asymmetric: unchanged passes and edited warns;
* null source/lookup key: normalized consistently and edited helper detected;
* two helpers with one edit: only the edited field is reported;
* absent helper payload column: stale identity remains a safe no-op;
* lookup frame unavailable: warn emits `missing_lookup_frame`, fail raises;
* partial asymmetric and mixed symmetric/asymmetric records: clear
  `ValueError`; and
* successful in-place policy execution removes consumed transient provenance;
  a failure leaves caller state unchanged, and distinct output retains source
  provenance per the established contract.

Missing key columns, blank/wrong-type metadata, and inconsistent symmetric
`on` shapes are not validated and can silently bypass fail checking under
R002-IMP-002. Duplicate lookup keys use the same deterministic first-occurrence
rule as the symmetric reader; the original enrichment producer rejects them, so
no asymmetric-only behavior change was found.

No durable workbook-provenance binding was required or implemented here.

== 8. Mode-identity assessment

`_resolve_join_keys` constructs `_ResolvedKeys(mode=...)` from the selected
public form:

* `key`, `keys`, quoted `"on"`, and policy key -> symmetric;
* explicit `source_key` + `lookup_key` -> asymmetric, including equal names.

All current consumers use the resolved object. Symmetric provenance writes
`on`; both different-name and equal-name explicit asymmetric provenance write
the pair. Direct Python and YAML agree. A policy key is ignored only for the
explicit pair; default helpers, allowed fields, missing mode, order, and value
mode continue through their existing independent policy resolvers. Symmetric
inline/policy conflicts remain enforced.

Normal resolution always supplies one key tuple member per asymmetric side, so
the convenience properties cannot index an empty tuple. Symmetric call paths do
not use the single-key properties. `_ResolvedKeys` is private; repository
search found no source/test import expecting the old tuple return shape and no
import cycle. Invalid direct private construction could create inconsistent
mode/cardinality, but no normal runtime path exposes it; no finding is raised.

Label equality affects projection rename (correctly a no-op), provenance
(correctly mode-driven), formula names (correctly equal), mismatch checking
(correctly equal), and collision handling (incorrect early exemption under
R002-IMP-001).

== 9. Formula and rendering assessment

* lookup key does not appear in output;
* default `after_data` and `before_key` placement work;
* provenance is asymmetric;

The independent layout probe proved that a lookup key at D and value at B,

Formula helper/key collision remains unsafe only in equal-name explicit mode
(R002-IMP-001). Duplicate helpers can create duplicate formula output labels
(R002-IMP-003). The committed renderer assertions do not prove ordered
distinct-range semantics (R002-IMP-004).
