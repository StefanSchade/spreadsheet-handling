=== 4.2 Important findings

==== XREF-S1-R003-IMP-001 — mismatch validation still fails open for absent or explicitly null key forms

Severity:: Important
File / symbol::
`src/spreadsheet_handling/domain/transformations/derived_column_policy.py` —
`_validated_mismatch_keys` and `_check_enrich_lookup_values`; public claims in
`docs/release_notes/release_notes.adoc` and
`FTR-XREF-LOOKUP-HELPER-SUBSTITUTION-P4A2_slice1_correction_002.adoc`.
Evidence::
`_validated_mismatch_keys` reads `on`, `source_key`, and `lookup_key` with
`spec.get(...)`; `has_asymmetric` is true only when a value is non-null; the
symmetric branch is entered only when `on is not None`; and the fallback
returns `([], [])`. `_check_enrich_lookup_values` treats an empty payload-key
list as a successful no-op. Thus member *presence* is lost when a member's
value is `None`, and a present `enrich_lookup` record with no join-key form is
also accepted.

An independent probe used an edited `title`, an available lookup frame, and
each of these key payloads:

[source,json]
----
{}
{"on": null}
{"source_key": null}
{"lookup_key": null}
{"source_key": null, "lookup_key": null}
----

For every case, `warn_on_mismatch` returned zero findings; and
`fail_on_mismatch` returned normally. Both policies removed `title` and pruned
the consumed `_meta.derived` record. The same edited payload with proper
`{"source_key":"story_id","lookup_key":"id"}` raises under
`fail_on_mismatch`, proving that the observed pass is caused by malformed key
form resolution rather than matching values.

The behavior contradicts the Correction-002 contract that only a non-empty
symmetric list or two non-empty asymmetric strings are accepted, that
everything else is rejected, and that wrong-typed mismatch keys fail closed.
JSON/YAML `null` is a non-string value. It also contradicts the release-note
safety statement that wrong-typed keys raise instead of silently passing.
Impact::
A malformed or degraded provenance record can still silently certify an edited
derived value under the public `fail_on_mismatch` gate, remove the helper, and
erase the evidence needed to diagnose why verification did not occur. This is
the same safety class as Review-001 IMP-002 and Review-002 R002-IMP-002.
Required correction::
Determine join-form selection from mapping-member presence, not only from
non-null values. A present `on` member must always be validated by
`_validated_symmetric_on`, including `None`; any present asymmetric member must
select/validate the asymmetric form, including null halves; and mixed member
presence must be rejected even when one value is null. A present
`enrich_lookup` helper record with no usable join-key form must produce a clear
malformed-provenance error or a severity-appropriate inability-to-verify result
instead of a zero-finding pass. Add warn/fail tests for the five reproduced
shapes, mixed-null forms, caller-state preservation, and provenance
non-consumption on failure. Preserve the intentional value-blind `drop` path.
Blocks Slice 2:: Yes.

== 5. Equal-name collision assessment

The equal-name correction is sound. `_check_key_helper_collision` returns only
for symmetric mode, then treats an equal asymmetric key as one authoritative
source-key role. The guard executes after field resolution and before value-
mode selection, projection, merge, formula assignment, output construction, or
provenance writing.

Tracked tests and independent probes established:

* helper `[id]` fails in values and formula modes;
* mixed `[id,title]` fails atomically in both modes;
* a policy-derived `[id]` and the YAML `[id]` call fail;
* failure leaves source, lookup, frames mapping, and metadata unchanged and no
  output/provenance can be returned;
* helper `[title]` plus `sort_by=[id]` succeeds and sorts the authoritative
  output key;
* `sort_by=[id]` succeeds with an empty helper list and with no helpers;
* helper `[id]` plus an unrelated sort field still fails;
* policy helper `[title]` plus the source-key sort succeeds;
* equal-name formula mode with normal helper `title` preserves the source key;
* distinct-name source-key and lookup-key helper collisions still raise domain
  errors in both value modes; and
* legacy symmetric `key=id, helpers.fields=[id]` remains accepted exactly as
  before.

The distinction between requested helper projection and source/output-key
sorting is correct: `_fields_with_sort_helpers` excludes a sort field equal to
the join key before the collision guard sees projection fields. No key
overwrite, key leakage, false helper provenance, or raw pandas error remained
in the reviewed combinations.

== 6. Mismatch fail-closed assessment

For valid records, the corrected mismatch implementation uses payload
`source_key` values against lookup `lookup_key` values and preserves symmetric
multi-key behavior. Direct probes and tests verified:

* unchanged and edited differently named asymmetric helpers under warn/fail;
* explicit equal-name asymmetric records;
* valid symmetric `on` lists, including multiple keys;
* unmatched references (still a separate concern and skipped);
* null join-key values;
* duplicate lookup keys (established deterministic first occurrence);
* multiple helpers with only the edited helper reported;
* stale helper columns absent from the payload (established safe no-op);
* unavailable lookup frames (warning/failure by selected policy); and
* value-blind `drop`, including malformed key metadata.

For non-null malformed values, the implementation now rejects bare-string,
integer, mapping, empty-list, blank-element, and non-string-element symmetric
`on`; blank/list/object/integer asymmetric keys; partial pairs; and mixed
non-null forms. Missing payload or lookup key columns now emit
`unverifiable_enrich_lookup`, with warning/failure severity and useful frame,
column, and provenance-path context. Failures leave caller state and provenance
unchanged.

The remaining presence/null hole is R003-IMP-001. It also exposes the broader
problem that a present helper-bearing `enrich_lookup` record with no key form
is treated like missing provenance, although missing *the entire record* is the
established safe no-op. Those states must not be conflated for value-checking
policies.

== 7. Duplicate-helper assessment

The generic `_check_duplicate_helper_fields` guard is called immediately after
field resolution. It applies equally to inline and policy-derived fields,
symmetric and asymmetric modes, values and formulas, and both helper positions.
It runs before allowed-field checks and all output/provenance work.

Independent probes covered `[title,title]` across the full two-mode,
two-position, symmetric/asymmetric matrix, policy-derived duplicates,
`[title,other,title]`, caller non-mutation, and absence of output/provenance.
Exact duplicate names are rejected clearly. Case-distinct `title` / `Title`
remain separate, consistent with the framework's case-sensitive DataFrame
labels. Empty helper lists and no-helper mode still work. Repeated temporary
sort criteria do not duplicate helper projection, duplicate allowlist entries
do not create a duplicate helper request, and one helper also used in
`sort_by` remains present exactly once with one provenance entry.

Rejecting a repeated helper declaration is a justified correction of the
pre-existing ambiguous duplicate-label/provenance behavior. Representative
non-duplicate symmetric behavior remains exact to the parent. The only issue
is the non-load-bearing tracked-test/claim gap in R003-MIN-001.

== 8. Formula and rendering-test assessment

The formula implementation and Correction-002 renderer tests are
load-bearing:

* direct `LookupFormulaSpec` tests assert source key `story_id`, lookup key
  `id`, value `title`, lookup frame, source-key preservation, lookup-key
  non-leakage, placement, and asymmetric provenance;
* the source fixture starts with `P_lead`, so `story_id` is B under
  `after_data` and C after `before_key` inserts the helper;
* the lookup fixture is `[misc1(A), title(B), misc2(C), id(D)]`, so key and
  value ranges are non-adjacent and reverse their ordinary positional order;
* the physical sheet name is `Entity Lookup`, not the logical frame name; and
* XLSX and ODS assert complete ordered formula strings for both positions.

Consequently, swapping lookup key/value ranges changes expected D/B ordering;
using the first lookup column selects A rather than D/B; using the first source
column selects A rather than B/C; ignoring physical mapping emits `entities`
rather than `Entity Lookup`; and retaining the old source-key cell after
`before_key` emits B rather than C. Each simulated regression contradicts an
exact assertion. R002-IMP-004 is fully closed.

Equal-name normal formula enrichment and equal-name collision rejection were
also probed successfully. Formula duplicate rejection is correct by the common
guard, subject only to R003-MIN-001's tracked matrix gap.
