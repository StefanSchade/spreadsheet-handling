== 1. Executive verdict

*The behaviour of `project_by_role` is fully reproducible by the existing
provenance-aware lookup/helper family — `enrich_lookup` (registered step
`add_lookup_helpers`) outbound, and `apply_derived_column_policy` (`policy:
drop`) inbound — with no surviving dynamic-ordering algorithm.* On real
worldbuilding data, across all five projected surfaces and a generic
dynamic-axis test, the candidate reproduces the exact current outbound matrix
view (columns and values) and the exact current inbound canonical relation,
through a real XLSX write/read boundary.

This is *Outcome A* on the decisive axis the outcomes are built around: after
candidate helper materialization the exact outbound order
(`display_helper -> row_identity -> matrix_value`) is *already* produced, and
after candidate helper removal the remaining matrix is *already* correct for the
XRef inverse. No call to `project_by_role`, no role-order calculation, no new
reorder step, and no static matrix-column list is required.

Two *enabling requirements* (not dynamic ordering, not the rejected
static-column / large-wrapper routes) must be settled by the implementation FTR:

. *Outbound symmetric key.* `enrich_lookup` requires the join key to have the
  *same name* in the source (matrix `story_id`) and the lookup (`stories.id`).
  The current `join_frames(+title)` performs the `story_id -> id` key mapping;
  no rename/alias pipeline step exists today. A minimal key-alias affordance for
  `enrich_lookup` (or a story_id-keyed `stories` view) is needed to feed it.
. *Inbound provenance binding.* The transient `enrich_lookup` helper provenance
  (`_meta.derived.sheets.<frame>.enrich_lookup`) does *not* survive the workbook
  persistence boundary. The *durable* workbook-view helper provenance
  (`_meta.sheets.<sheet>.helper_columns = [title]`, written by
  `configure_workbook_view`) does survive, but is keyed by *workbook sheet
  name*. Inbound removal must bind to that durable carrier (drop by sheet name
  before `apply_workbook_view_sheet_mappings`, or re-key it to the logical
  frame name).

The shared role resolver `resolve_column_roles` has a *second live consumer*
(validation role targeting, `validate_columns.py:184`) and MUST be retained.

The only live runtime consumers of `project_by_role` are the ten worldbuilding
sites; no Core pipeline, Project Memory pipeline, or domain-contract generator
executes it.

== 6. Current helper-capability contracts (as implemented)

[cols="2,5"]
|===
| Capability | Contract facts relevant to substitution

| `project_by_role` (`domain.transformations.project_by_role`)
| In-place strict reorder `df.loc[:, ordered].copy()`. Outbound order
  `display_helper, row_identity, matrix_value`; inbound drops `display_helper`,
  keeps `row_identity, matrix_value`. Delegates *all* role detection to
  `resolve_column_roles`; never reorders by static list.

| `resolve_column_roles` (`domain.column_roles.resolver`)
| Within-role order follows *frame* column order. `row_identity` from
  `xref_crosstable.row_keys` or `key_columns` override; `display_helper` from
  `configure_workbook_view` helper_columns, FK `derived` provenance, or
  `helper_columns` override. *Does not read the `enrich_lookup` provenance
  subkey.* Second live consumer: `validate_columns`.

| `enrich_lookup` / `add_lookup_helpers` (`domain.transformations.enrich_lookup`)
| Joins source+lookup on a *single key name present in both frames*. Projects
  *bare* field names (`title`, no prefix). `order.helper_position: before_key`
  places helpers immediately before the key -> `[title, story_id, <rest>]`.
  Duplicate lookup keys raise; `missing` is `fail` or `empty`. Value mode copies values
  and fills NaN with `""`. `_check_column_conflict` *raises* if a helper field
  already exists in the source. Writes provenance
  `_meta.derived.sheets.<output>.enrich_lookup.helper_columns`.

| `add_fk_helpers` (`domain.transformations.fk_helpers.enrich`)
| *Hardcodes `helper_prefix="_"`* -> produces `_stories_title`, NOT bare
  `title`. Cannot preserve the exact `title` workbook label. Writes
  `_meta.derived.sheets.<sheet>.helper_columns` (list of `{column, fk_column,
  target, ...}`).

| `apply_derived_column_policy` (`domain.transformations.derived_column_policy`)
| `policy: drop` removes derived columns by provenance, *order-preserving* (no
  reorder). Identity sources: transient `_meta.derived.sheets[frame]`
  (FK `helper_columns` + `enrich_lookup`), durable
  `_meta.sheets[frame].helper_columns`, and FK `helper_policies.fk.relations`.
  `drop` does not value-check -> an edited helper is discarded, not written
  back. No explicit helper-name override parameter.

| `contract_xref` / `expand_xref` / `expand_compact_multiaxis`
| Canonical XRef primitives; relation is exactly `row_keys + column_key +
  value`; inverse melts every non-key column. Column order of the matrix does
  not affect the melt result.
|===

FK-helper vs matrix `title` classification: worldbuilding's `title` is a
*read-only display helper* whose source key (`stories.id`) stays authoritative
and whose edited value is dropped inbound. It is *not* directly expressible as
an existing FK helper because `add_fk_helpers` forces the `_` prefix
(`_stories_title != title`). It *is* expressible as an `enrich_lookup` helper
(bare name preserved), subject to the symmetric-key requirement. It must remain
a read-only FK/display helper; this task does not broaden it into an editable
reference projection.

== 9. Workbook-persistence probe

* `_meta` *does* survive the XLSX roundtrip (hidden meta sheet). Restored keys:
  `auto_filter, constraints, freeze_header, helper_policies, sheets,
  workbook_view, xref_crosstable`. *No `derived` key* -> transient derived
  provenance (including the `enrich_lookup` channel) is stripped at the
  boundary.
* Restored `_meta.sheets` is keyed by *workbook sheet name*
  (`"Story Groups"`, `"Cast Roles"`, ...), each `helper_columns: [title]`.
  `apply_workbook_view_sheet_mappings` renames frames to logical names but does
  *not* re-key `_meta.sheets`.
* Consequence: inbound removal must address the durable carrier by sheet name
  (proven: `apply_derived_column_policy(source="Story Groups", policy="drop")`
  drops `title`) or the provenance must be re-keyed to the logical frame name
  (also proven). FK display helpers (`_places_name`, etc.) survive inbound via
  `helper_policies.fk.relations`, a path unavailable to non-FK `title`.
* Backend scope: the maintained worldbuilding path is XLSX and was exercised
  end-to-end. If the implementation introduces a Core capability expected to be
  backend-neutral (e.g. an `enrich_lookup` key-alias), the FTR must add an
  equivalent ODS persistence acceptance criterion; ODS was not required to prove
  this probe because the substitution reuses the same durable meta carrier that
  the existing FK-helper roundtrip already exercises on both backends.

== 11. Edited-helper behaviour

With `title` correctly identified (durable provenance), `apply_derived_column_policy(drop)`
removes the column without any value comparison. An edited `title`
(`"EDITED-TITLE-XYZ"`) is therefore discarded — not melted into XRef values and
not written back to `stories.title` — exactly matching current
`project_by_role(inbound)` behaviour. (When provenance is *not* found — the
logical-frame-name path — `title` survives and would be melted; this is why the
durable sheet-name binding is a hard requirement, not a nicety.)

== 13. A/B/C decision

* *Not B*: Outcome B requires a surviving runtime ordering algorithm. The probe
  proves the exact order is produced *without* any ordering step
  (`before_key` placement outbound, order-preserving `drop` inbound). B is
  factually excluded.
* *Not C*: exact workbook and roundtrip behaviour is preserved with the existing
  helper family; the initial "cleanup cannot find the helper after readback"
  blocker is *surmounted* by binding to the durable workbook-view provenance
  (proven). C would overstate unsuitability.
* *A*: `project_by_role`'s function is fully reproducible by
  `enrich_lookup` + `apply_derived_column_policy`, with no surviving
  dynamic-ordering algorithm, and the only live consumers are the ten
  worldbuilding sites. The two enabling requirements (symmetric-key title
  source; durable-provenance inbound binding) are implementation scope, not a
  dynamic-ordering residual and not the rejected static-column / large-wrapper
  routes.

== 14. Surviving responsibilities of project_by_role

None that the helper family cannot own, *except* the incidental
`story_id -> id` key mapping currently folded into `join_frames(+title)`, which
`enrich_lookup` cannot express (symmetric keys) and no rename step replaces
today. That responsibility is a *join/alias* concern, not a projection or
ordering concern.

== 15. Migration consequences

* Outbound (per surface): replace `join_frames(+title)` + `project_by_role`
  with a symmetric-key title source + `add_lookup_helpers` (`before_key`).
* Inbound (per surface): replace `project_by_role(inbound)` with
  `apply_derived_column_policy(drop)` bound to the durable workbook-view helper,
  addressed by sheet name (drop before `apply_workbook_view_sheet_mappings`) or
  via a provenance re-key.
* Core: delete `project_by_role` step, registration, registry/impl-unit records,
  and docs; *retain* `resolve_column_roles` (second consumer = validation); the
  `helper_columns`/`key_columns` override params become validation-unused and
  may be simplified in a later, separate step.

== 16. Risks and overlooked constraints

* *Symmetric-key affordance* is a genuine Core gap; scoping it as an
  `enrich_lookup` `source_key`/`lookup_key` option is the smallest change and
  must not become a broad join redesign.
* *Provenance carrier*: relying on durable workbook-view helper_columns couples
  inbound removal to `configure_workbook_view` declarations; the FTR must state
  this dependency explicitly and add a guard that a matrix view declares its
  display helper.
* *Column-conflict guard* means `enrich_lookup` cannot merely reorder an
  already-present `title`; the outbound must materialize `title` via
  `enrich_lookup` itself, not after a separate join.
* *Do not* broaden the FK-helper API (prefix-forced, editable-reference future)
  to solve this; `title` stays a read-only display helper.
* Grouped-XRef and `expand_compact_multiaxis` internals are untouched; only the
  worldbuilding composition around them changes.
