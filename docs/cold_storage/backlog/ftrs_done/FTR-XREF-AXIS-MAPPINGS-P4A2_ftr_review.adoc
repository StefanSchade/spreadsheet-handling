= FTR Review: XRef Axis Mappings P4A2
:revdate: 2026-07-30
:toc:

== Verdict

The repaired and refined FTR is ready for implementation of its explicitly
authorized Slice 1: the pure axis-mapping model and resolver.

The pre-review document described a coherent capability but combined the model,
public YAML, XRef integration, metadata lifecycle, schema maintenance,
hierarchical DataFrame shape, two spreadsheet adapters, and adoption
composition in one implementation scope. It also suggested persisting resolved
key-to-label mappings even though the current repository contract preserves
Intent and drops XRef Resolution.

The revised FTR settles the primitive semantics, selects composition around
unchanged XRef, removes speculative API and metadata shapes, and stages later
public/carrier work behind separate reviews. No blocker remains for Slice 1.

== Syntax repairs performed

Commit `0aa4952` contains clear paste damage rather than intentional AsciiDoc:

* fourteen source examples had UI prefixes such as `## [source,text]` instead
  of AsciiDoc source declarations and fences;
* several examples used separator-like hyphen runs as accidental closing
  fences;
* the hierarchical header used Markdown backticks inside the AsciiDoc file;
* the stray fragment `## requirement` appeared between the example and its
  sentence;
* two YAML examples lost list syntax and nested indentation;
* the metadata YAML example lost all nesting and ended with an eleven-hyphen
  fragment;
* several one-line examples were left as prose prefixed with `##`.

Phase 1 restored balanced `----` blocks, proper `[source,text]` and
`[source,yaml]` declarations, YAML list markers/indentation, and the boundary
between examples and prose. The repaired 470-line document rendered
successfully with Asciidoctor before semantic editing began.

The final refinement removed the non-normative YAML and metadata sketches
rather than allowing repaired but unapproved surfaces to look contractual.

== Findings by severity

=== Blockers

None remain for Slice 1 after refinement.

=== High findings resolved in the FTR

H-1 -- The implementation scope crossed too many gates::
The prior FTR combined identity/lifecycle, a possible new metadata root, public
step configuration, schema maintenance, XLSX/ODS behavior, and adoption. FTR
Sizing Preflight items 3 through 6 all fired. Implementing that scope as one
slice would make independent review impractical and couple unrelated decisions.
+
Disposition: resolved. The FTR is now a staged contract and authorizes only the
pure model/resolver. Public, metadata, carrier, and adoption changes are later
slices.

H-2 -- Resolution persistence conflicted with the current lifecycle::
The prior acceptance required the workbook carrier to preserve resolved
key-to-label data while also saying later renders should re-resolve current
source frames. Current XRef explicitly strips analogous Resolution from every
persisted carrier.
+
Risk: stale labels could become a second identity authority and diverge from
the live source frame.
+
Disposition: resolved. Intent is explicit input; Resolution is run-local.
Slice 1 creates no metadata. A later persistent-Intent need must be proven and
reviewed separately.

H-3 -- The preferred architecture was undecided::
The prior FTR offered separate transformations, XRef options, and metadata
pre-resolution as peer possibilities. This left implementation free to turn
`contract_xref` / `expand_xref` into lookup-and-render coordinators.
+
Disposition: resolved. Separate bijective projection transformations composed
around unchanged XRef are selected. An optional XRef block is rejected for the
initial slices, and a wrapper is deferred until the primitives are proven.

=== Medium findings resolved in the FTR

M-1 -- Axis Mapping and Grouped Columns overlapped::
The prior FTR required hierarchical XRef integration and XLSX/ODS parity while
the sibling FTR also claimed grouped-axis configuration and MultiIndex
conversion.
+
Disposition: resolved in this FTR. Axis Mapping owns key-to-tuple identity.
Grouped Columns owns physical multi-row rendering/readback. The sibling FTR
still needs alignment before its implementation.

M-2 -- Bijection validation needed one tuple rule::
The earlier text was directionally correct but mixed label-level uniqueness,
carrier representability, and persisted mapping checks.
+
Disposition: resolved. Only the complete label tuple is the reverse key;
individual levels may repeat. Duplicate complete tuples, wrong arity, empty
levels, and unknown keys fail.

M-3 -- One-level and multi-level models risked divergence::
The prior document discussed flat strings and MultiIndex as alternate physical
forms without making the logical invariant the primary contract.
+
Disposition: resolved. Every logical label is a tuple; a flat label is a
one-element tuple. Carrier shape is downstream.

M-4 -- Ordering was not fully deterministic::
`order_by` was required, but ties were not settled.
+
Disposition: resolved. Intent selects source order explicitly or configured
field order; configured-field ties use canonical key as the final tie-breaker.

=== Remaining non-blocking findings

R-1 -- The sibling Grouped Columns FTR still claims identity behavior::
Its current Scope says grouped XRef transforms expand/contract axis levels and
its configuration includes a mapping reference. Before Slice 4, that FTR must
be refined so it consumes Axis Mapping and owns only logical-to-physical grouped
header shape and readback.

R-2 -- Current MultiHeader readback is not an arbitrary-label contract::
The present implementation joins levels with `" / "` and later splits the
string. Literal delimiter text is therefore ambiguous, and auto-detection
leans on merge geometry. This is not a Slice 1 or Slice 2 blocker, but Slice 4
must add carrier-level tests and remove lossy identity reconstruction.

R-3 -- XRef projection-scope semantics remain adjacent::
Missing, deleted, renamed, or reordered workbook axis members can express
damage, user intent, or changed source scope. Existing XRef audits already mark
this as a writeback-scope question. Axis Mapping should fail on unknown tuples;
it must not claim to solve all structural-deletion policy by persisting stale
Resolution.

== Architecture alternatives

Separate axis-projection transformations::
Selected. They maximize primitive reuse, are independently testable, and leave
XRef's current responsibility intact.

Optional configuration inside XRef::
Not selected for initial implementation. It would couple lookup, order,
identity, matrix shape, metadata, and compatibility in two already substantial
primitives.

Higher-level XRef-view wrapper::
Potential later convenience layer only. It may compose accepted primitives but
must not precede them or hide discriminator, row-helper, role-projection, and
workbook-view semantics.

Large `project_faceted_xref` step::
Not approved. Repository evidence shows repetition in one consumer but also
shows that the explicit stages have separate ownership and review value.

== Settled contract

* Canonical keys and full label tuples form an exact bijection.
* Labels are ordered tuples of non-empty strings; one level is arity one.
* Duplicate keys and duplicate full tuples fail.
* Unknown used keys, incomplete source fields, empty labels, wrong arity, and
  invalid order data fail with feature-specific diagnostics.
* Ordering is explicit and deterministic.
* Resolution is current-run data and does not persist in Slice 1.
* XRef remains unchanged and flat-compatible.
* Grouped physical headers are a downstream consumer, not identity authority.
* Row helpers, role projection, discriminator splitting, and cell semantics
  remain outside Axis Mapping.

== Remaining decisions

The following are intentionally open because they do not affect Slice 1:

* Slice 2 step names, parameter shape, and in-place versus source/output
  behavior;
* the Slice 3 logical DataFrame representation handed to Grouped Columns;
* whether any persistent mapping Intent is needed after explicit inverse
  configuration and live-source roundtrip are proven;
* projection-structure policy for deleted/renamed/missing axis members;
* a non-lossy XLSX/ODS tuple carrier/readback contract;
* whether later adoption evidence justifies a thin XRef-view wrapper.

== Recommended implementation slices

. Pure typed axis-mapping model and resolver, covering one/multiple levels and
  exact forward/reverse lookup. No public or persistence changes.
. Flat one-level outbound/inbound transformations around unchanged XRef, with
  gated YAML/registry/docs and XLSX/ODS roundtrip.
. Backend-neutral hierarchical logical projection using the same tuple model.
. Grouped Columns physical integration and hardened XLSX/ODS carrier parity.
. One adoption migration, followed by a separate decision on any wrapper or
  faceted multiprojection.

This sequence matches the likely target sequence in the review request. The
important qualification is that hierarchical logical tuples in Slice 3 do not
claim physical workbook support; that remains Slice 4.
