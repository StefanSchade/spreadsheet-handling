== Diagnostic-safety assessment

Invalid-type rejections now interpolate a single constant detail
("unsupported value type") shared by `model.py` and `resolver.py`. No path reads
caller-controlled `repr`, `str`, type-name, hash, equality, comparison,
conversion, length, or iteration merely to describe a rejected value.
Deliberate `missing value`/`empty value` diagnostics keep their specificity, and
every rejection carries surrounding context (field name or source frame, row,
role, and column), so diagnostics remain understandable for competent users
despite the constant type wording. The constant-detail helper does not introduce
misleading abstraction: its docstring states the safety intent.

== NumPy-vocabulary and dependency assessment

The platform-derived set is correct and safe: identity-only membership avoids
hostile metaclass dispatch, accepted scalars convert to unbounded built-in
`int` so signed/unsigned boundaries cannot overflow, and exact-type acceptance
(not broad `isinstance(np.integer)`) preserves subclass safety. The
`numpy>=1.23.2` declaration is architecturally acceptable because production
code imports NumPy and contracts against its scalar classes; the bound matches
pandas' own historical NumPy floor and does not conflict with the pandas
requirement. As correction review 002 already notes, the derived set is
platform-specific; exercising additional NumPy/platform combinations in CI
remains a reasonable watch-only item, not a Slice-1 defect.

== Exact-tuple and immutability assessment

Direct construction invariants hold under re-probing: exact strings, exact tuple
labels, exact built-in integer positions (excluding `bool`), contiguous
zero-based positions, correct arity, duplicate-key and duplicate-complete-tuple
rejection, exact member types, copied ordered member/label containers, and
`MappingProxyType`-backed derived lookups with no caller-retained mutable
backing. With the tuple-subclass hole closed, accepted Resolution values are
effectively immutable and lookup-stable. The defensive revalidation of
`member.labels` inside `ResolvedAxisMapping` is proportionate: it is one guarded
call, it protects the mapping's own bijection invariants against a forged frozen
member that bypassed `__post_init__`, and a dedicated forged-member test proves
it is not redundant. Arbitrary member-iterator side effects remain outside the
immutability claim, consistent with the documented scope.

== Readability and defensive-complexity assessment

The hardening is localized and understandable. The resolver's domain flow
(require frame -> read records -> ensure bijection -> order -> check used keys ->
build members) is still linear and easy to follow. Adversarial concerns live
behind narrowly named helpers (`_unsupported_type_detail`, `_resolved_labels`,
`_require_order_value`, `_ExactNumpyIntegerTypes`). `_ExactNumpyIntegerTypes` is
a small, self-documenting collection with identity membership and is
proportionate to the exact-type contract it enforces; exact-type contracts are
documented close to their implementation. Test-only adversarial machinery
(hostile metaclass, mutable/hostile tuple, hostile NumPy subclass, forged
member) stays in the test module and does not leak into production. No
readability issue materially obscures or destabilizes the domain contract.

== Architecture and scope assessment

The package remains domain-owned and pure. It imports only pandas, NumPy, the
shared `domain/tabular` boundary helpers, and its own model. The correction diff
touches no pipeline, registry, YAML, metadata, persistence, schema-maintenance,
render-flow, adapter, workbook, XLSX/ODS, or grouped-header surface, and changes
no XRef behavior. `resolve_axis_mapping` reads only, returns no Frames, and
writes no metadata. The direct NumPy dependency is acceptable. Later slices 2-5
remain open. No release note is required for an internal Slice-1 contract change.
