==== Purpose

Promote the durable Trusted-Ingress architecture into short, human-readable
owning documentation after Phase-E runtime truth has stabilized, while
preserving the existing FTR and review ledger as historical evidence.

This is not cosmetic cleanup. The accepted architecture currently depends on
an approximately 4,000-line FTR plus an approximately 8,000-line chronological
review/evidence ledger. Those artifacts are appropriate provenance, but they
are not an acceptable permanent maintainer entry point. Current truth must be
understandable without replaying the design and correction history.

This FTR defines the promotion ownership, timing, review boundary, and
historical-evidence disposition. It does not perform the promotion now.

==== 1. Sizing preflight and bounded scope

The repository FTR sizing preflight classifies this as one documentation-
lifecycle/modeling slice:

* no runtime export, reimport, backend, metadata-root, registry, YAML, CLI,
  plugin, or public-import behavior changes;
* no identity, precedence, fallback, or reconstruction mechanism is added;
* the one lifecycle rule is explicit: promote actual accepted runtime truth,
  independently verify it, then decide archival before downstream family
  hardening begins; and
* acceptance criteria are meaningful because the work must prove ownership,
  readability, cross-model separation, and preserved historical traceability.

No implementation or architecture FTR is nested inside this work package. If
promotion discovers a genuine semantic or architectural contradiction, this
FTR records and routes it to the existing owning slice or a separate bounded
work item; it does not silently redesign Trusted Ingress.

==== 3. Durable promotion model

===== A. Semantic Model ownership

The Semantic Model owns only durable value/domain semantics needed to explain
what values mean independently of orchestration:

* the six Scalar semantic categories;
* carrier identity versus semantic-category membership;
* Date versus DateTime;
* FormulaSpec as framework-authored output Intent rather than ordinary Scalar;
  and
* future composite semantics only where a genuinely semantic composite has
  been independently accepted.

It MUST NOT own E1-E7 orchestration, conformance intervals, macro wiring,
transition execution, review history, or package organization.

===== B. Technical Model ownership

The Technical Model owns durable Trusted-Ingress architecture after the
corresponding implementation facts are independently accepted:

* the serialized-input/parser boundary and its handoff to Trusted Ingress;
* the independent runtime/operator, payload-origin, pipeline-description, and
  output-sink trust dimensions;
* Ingress-Conformant ordinary payload versus controlled framework execution
  state;
* final E1-E7 responsibility boundaries;
* ordinary re-establishment semantics after uncertified returns;
* controlled roles, exact transition provenance, closed composition, and no
  authority from class, shape, factory, or object identity alone;
* the classify-before-inspect boundary principle and bounded safe diagnostics;
* the relationship to current open physical-column authority, including that
  E1 cell Scalar categories are not an axis grammar and row indexes remain
  positional traversal structure; and
* parser/resource safety and Trusted Ingress semantic admission as separate,
  complementary boundaries.

The Technical Model must describe the permanent architecture, not reproduce
the FTR's rejected alternatives, correction chronology, or test transcript.

===== C. Developer Guide ownership

The Developer Guide owns maintainer-facing extension and organization rules:

* how to add or change an accepted carrier without falling through generic
  recursion;
* how to introduce a controlled role and its exact producer, location,
  consumers, transitions, composition, and termination contract;
* how to classify safely before carrier-specific inspection;
* how to construct bounded diagnostics without unsafe rejected-value
  reflection;
* why class, shape, factory, or object identity cannot establish authority;
* how `domain.ingress` package responsibilities are organized after E1-E7;
* which validations stay carrier/ingress-owned and which Domain invariants stay
  family-local; and
* when a change needs a new FTR, an ADR, or only a bounded implementation/
  documentation update.

Examples may point to accepted code, but the guide must not promise a package
shape that implementation has not stabilized.

===== D. Historical evidence ownership

The giant FTR/review pair remains the provenance source for rationale,
counterexamples, rejected options, compatibility evidence, correction history,
and exact acceptance proof. Historical artifacts answer questions such as:

[source,text]
----
Why was this decision made?
Which counterexample forced this rule?
What evidence and review accepted it?
----

After durable promotion is complete and independently verified, the workstream
must decide whether the FTR, mega-review, and slice-specific review bundle
should move to `docs/cold_storage/backlog/ftrs_done/` under the normal archive
and index conventions. Archival is preferred when Phase E and this promotion
workstream are complete, but no move is authorized by this planning FTR alone.

==== 4. Timing and lifecycle gate

Incremental promotion is permitted during E2-E7 when one implemented slice has
stable, independently accepted facts and the edit will not claim unfinished
later behavior. Incremental work does not satisfy this FTR's final acceptance.

Final promotion/condensation MUST occur after all Phase-E implementation has
stabilized sufficiently to document actual runtime truth. It MUST complete
before Domain Maintainer Contract work, Phase F / the first family-hardening
pilot, or D-T3 begins.

The required lifecycle is:

[source,text]
----
Phase E implementation complete
-> Trusted Ingress documentation promotion/condensation
-> independent documentation review
-> historical evidence archival decision
-> Domain Maintainer Contract
-> Phase F / first family pilot / D-T3
----

This is a near-term closure obligation, not an indefinite cleanup candidate.
Phase-E completion does not permit the downstream stages to bypass it.

==== 5. Human-readability acceptance criterion

A maintainer who has not read the historical FTR or mega-review MUST be able to
use the permanent Semantic Model, Technical Model, Developer Guide, and current
source layout to:

* explain the Trusted-Ingress architecture and its parser handoff;
* distinguish ordinary ingress facts from controlled execution state;
* locate where parser/resource protection ends and parsed-carrier admission
  begins;
* safely modify the implementation area owned by any E1-E7 slice;
* preserve the trust, authority, re-establishment, physical-axis, and diagnostic
  invariants; and
* determine when a carrier/role extension requires separate design authority.

The historical artifacts may be linked for “why/evidence” questions, but no
load-bearing current rule may exist only in those artifacts. Permanent active
documentation explains current truth without replaying review history.

Independent documentation review must test this criterion from a fresh
maintainer context, verify every promoted statement against accepted runtime
and architecture authority, and identify any current rule still trapped only
in historical evidence.

==== 6. Scope-accretion rule for remaining Phase E

New concerns discovered during E2-E7 MUST be classified before they are added
to `FTR-TRUSTED-INGRESS-P4A`. Independent parser/resource hardening,
output/sink security, unrelated metadata ontology cleanup, general pipeline
extension architecture, generic framework security, documentation
restructuring, and other independently sequenced concerns remain in their own
FTRs or backlog work items.

Trusted Ingress is amended only when new evidence directly contradicts, or is
required to complete, an existing accepted E1-E7 obligation. Discovery near an
ingress boundary is not sufficient ownership evidence.

The steering goal is:

[source,text]
----
finish the accepted Trusted-Ingress arc;
do not turn it into an umbrella for every adjacent concern.
----

This documentation-condensation FTR is itself the separate owner for
documentation restructuring and therefore is not appended to the architecture
mega-FTR.

. a fresh-context independent documentation review against section 5; and
. an explicit archive/retain decision for the historical FTR and all review
  artifacts under the normal warm/cold-storage conventions.

==== 8. Acceptance criteria

This FTR is complete only when:

* Phase E, including E7, is implemented and independently accepted, or a later
  accepted lifecycle correction explicitly supplies equivalent final runtime
  truth;
* the Semantic Model contains durable value semantics without orchestration
  machinery;
* the Technical Model contains the implemented permanent Trusted-Ingress
  architecture and parser/ingress separation;
* the Developer Guide contains actionable carrier, role/transition,
  diagnostics, package-responsibility, and escalation rules;
* every durable current rule has one clear owner and no current rule requires
  chronological reconstruction from the giant FTR/review pair;
* the fresh-context maintainer-readability criterion passes independent review;
* all E2-E7 implementation reviews use bounded slice-specific artifacts and no
  post-`d2af3c` material has been appended to the mega-review;
* the historical bundle remains discoverable and unchanged except for any
  explicit historical/discovery annotation authorized by the archival step;
* the archive/retain decision is recorded and, if archival is selected, the
  bundle is moved with include/reference/index consistency;
* roadmap, Project Memory, and active-backlog lifecycle state agree; and
* Domain Maintainer Contract, Phase F / first family pilot, and D-T3 have not
  started before this documentation closure is independently accepted.

==== 9. Non-goals

This FTR does not authorize:

* E2-E7 implementation or a physical-axis compatibility census;
* a new or narrower physical-axis grammar;
* runtime, test, public API, YAML, registry, or parser-limit changes;
* a rewrite of accepted Trusted-Ingress architecture;
* immediate movement, condensation, or rewriting of the historical FTR/review
  pair;
* repository-wide review-artifact convention redesign;
* Domain Maintainer Contract, Phase F, a family pilot, D-T3, or D-T4 work; or
* promotion of proposals that are not yet accepted runtime truth.
