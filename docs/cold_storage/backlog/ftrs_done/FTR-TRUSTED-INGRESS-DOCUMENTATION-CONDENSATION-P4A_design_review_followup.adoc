== 3. Controlled-role lifecycle check

C6 correctly separates ordinary Ingress-Conformant Domain state from Conformant
Framework Execution State. Non-ordinary state requires an exact declared role;
initial ingress and ordinary re-establishment reject role-shaped values.

C7 accurately states the closed current set as exactly three semantic role
kinds:

* `LookupFormulaSpec` at a declared helper-cell role;
* `GroupedMatrix` at a producer-declared top-level frame role; and
* `ArtifactManifestSourceFrames` at the manifest output frame's exact
  `source_frames` column.

Current source has four descriptor classes because
`GroupedMatrixFormulaRole` represents the one admitted nested composition; it
is not a fourth semantic role kind. This matches the accepted FTR algebra.

C8 accurately preserves both accepted composition proof forms: disjoint-role
products require exact locality/non-interference proof, and the sole admitted
nesting is
`GroupedMatrix[LookupFormulaSpec@grouped-dynamic-value-cell-role]`. It explicitly
rejects automatic composition and a general commutative role algebra.

C9 honestly synthesizes three distinct concepts: exact certificate/binding
identity, transition authority to establish a named role, and the currently
live role state. It does not present the synthesis as verbatim historical
terminology.

C10 matches accepted final authority: every controlled-role authorization ends
at an uncertified return, and a framework-managed flow must perform complete
ordinary re-establishment before later ordinary Domain work, cleanup, or
persistence. It correctly says this proves nothing about side effects already
performed inside the callable.

C11 remains bounded to accepted role-specific consumer, relocation, cleanup,
adapter, and sink exits. Its examples do not create a generic consumer law;
pending cleanup remains live role state until the exact cleanup transition.

Result: *CONTROLLED-ROLE EXACTNESS CONFIRMED*. A fresh maintainer can determine
what controlled state exists, how it composes, and how its authority ends.

== 7. G5 security/robustness assessment

G5 is honestly classified as *New explanatory framing*. It usefully explains
that trusted operator/runtime control and deliberately authorized arbitrary
same-process Python are inside the process-level security trust base, without
claiming that authorized code is bug-free.

The cited examples support the robustness distinction: C10 re-establishes
ordinary state after uncertified/plugin return; C1/C5 prevent ordinary
mutation-through-alias of effective binding state; and B2/B3 preserve bounded
classification/diagnostic behavior for malformed output.

The hard security boundary remains explicit. G5 does not promise containment
of deliberately hostile same-process Python and specifically excludes arbitrary
filesystem/network activity, `os.remove`, monkeypatching, `ctypes`, interpreter
compromise, and arbitrary malicious plugin side effects. The qualification
"where technically enforceable" prevents the robustness discussion from
becoming a vague survival guarantee.

Result: *G5 ACCEPTABLE AS EXPLANATORY SYNTHESIS*.
