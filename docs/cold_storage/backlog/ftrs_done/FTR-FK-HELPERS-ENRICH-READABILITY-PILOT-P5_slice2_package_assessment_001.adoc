== 3. Slice-1 pilot lessons (what was actually validated)

Slice 1 changed only `enrich.py` (+ two alias characterization tests). It
practically validated a *subset* of the candidate patterns and, importantly,
also demonstrated their *limits*:

* *Raw→resolved boundary (Form A).* `enrich_helpers` consumes exactly three
  scalar keys from a raw `defaults` bag; the accepted form was explicit resolved
  scalars under a boundary comment, *not* a value object or resolver helper. This
  worked because a genuine raw options bag existed. It is not a template to copy
  where no such bag exists (see the drop.py counterexample, section 6).
* *Narrow helper input.* `_helper_value_mode(defaults)` →
  `_normalize_helper_value_mode(raw_mode: str)`. A clean, general win — but the
  rest of the package was *already* mostly narrow, so the recurrence is small.
* *Frame vs sheet vocabulary.* Local frame-iteration variables were renamed
  `sheet_* → frame_*`, while `fields_by_target_sheet` was *retained* because it
  mirrors the `core.fk` adapter contract keyed by `sheet_key`. This split
  (local rename vs contract retention) is the single most reusable lesson and
  recurs across siblings.
* *Execution-index naming.* `target_registry → target_lookup_index`, contrasted
  with the authoritative `relations` list.
* *Deliberate deferrals held.* No FK-HR-012 typing, no FK-HR-016 ownership
  change, no cross-module edit for consistency.

Lesson for Slice 2: the pilot's *vocabulary* discipline generalizes; its
*configuration-resolution* form was contract-specific; consistency pressure alone
is not a sufficient reason to refactor a sibling.

* *Contract:* `resolve_v2_fk_relations` (absent/unsupported → `None`, present →

=== 6.4 `formula_provider.py` — disposition: safe local cleanup candidate (FK-HR-013/014/015)

* *Contract:* `_lookup_formula_provider(registry)` returns a closure conforming to

* *Cross-module:* `core.fk.FKDef`, `core.formulas.lookup_formula`; imported *only*

* *Strengths:* the closure cleanly binds the shared lookup structure once and

* *Disposition:* the tightest, lowest-risk local slice in the package (section 21,

=== 6.5 `drop.py` — disposition: safe local cleanup candidate (vocabulary only)

* *Contract:* `drop_helpers(frames, *, prefix="_")` removes helper columns using
  derived provenance first, then v2 policy; raises the shared missing-policy error
  when both are absent. `prefix` is explicitly `del`-ed and documented as retained
  only for step binding.
* *Cross-module:* `frame_keys`, `policy` (four readers), `provenance`
  (`_clean_helper_provenance`, `_visible_label`).
* *Strengths:* the `del prefix` line + comment is an exemplary explicit no-op of a
  compatibility parameter; the "provenance is authoritative" skip carries a local
  comment (a second HR-10 instance); the two-source (provenance then policy)
  merge is clearly ordered.
* *Reader costs:* `for sheet, df in iter_data_frames(frames)` and
  `known_sheets`/`provenance_by_sheet`/`columns_to_drop_by_sheet` use *sheet*
  vocabulary for domain frames (FK-HR-017 recurrence) — *but* partly reflect the
  persisted `_meta.derived.sheets` namespace (section 12 caveat).
* *Non-findings:* `dict.setdefault` grouping; the dict/set comprehensions; the

* *Disposition:* frame-vocabulary parity is a safe local rename, tempered by the
  persisted-namespace caveat; *no other pattern recurs* (no raw options bag — a
  deliberate counterexample). Enrichment and dropping intentionally differ

=== 6.6 `provenance.py` — disposition: mostly no change (one param-name seam)

* *Contract:* `_write_helper_provenance(out, fk_defs_by_sheet)` writes/prunes
  `_meta.derived.sheets.*.helper_columns`; `_clean_helper_provenance` removes
  entries after drops; `_visible_label` extracts the human-visible header label.
* *Cross-module:* consumed by `enrich` (write) and `drop` (clean, `_visible_label`).
* *Strengths:* the key-selective merge comment explains *why* only `helper_columns`

* *Reader costs:* the parameter `fk_defs_by_sheet` now receives enrich's

  local `sheet_name` loop variables mirror the persisted `derived.sheets`
  namespace (so *sheet* is defensible here, unlike a pure frame iteration).
* *Non-finding:* the function is already locally clear; do not introduce
  abstraction merely because two callers exist.
* *Disposition:* no change required in isolation; the param-name seam is a
  candidate only if the frame-vocabulary parity slice is taken, and even then must
  weigh the persisted-namespace naming (section 12).

== 7. Where enrichment and dropping intentionally differ

Symmetry must not be assumed. Concrete differences:

* *Configuration:* `enrich_helpers` takes a raw `defaults` bag (three consumed
  keys); `drop_helpers` takes a single explicit keyword `prefix` that is `del`-ed.
  The raw→resolved pattern (Pattern A) therefore *does not recur* in `drop.py`;
  it was specific to enrich's option contract.
* *Policy role:* enrich *requires* v2 policy (raises if absent); drop treats policy
  as a *fallback* behind authoritative derived provenance, and only raises when
  *both* are absent.
* *No-op semantics:* enrich's no-ops are "target frame absent" and "source header
  absent"; drop's no-op is "no columns to drop for this frame".
* *Provenance direction:* enrich *writes* provenance; drop *cleans* it.

These are genuinely different contracts, not inconsistencies to be unified.

== 8. `enrich.py` after Slice 1 — generalizability and limits (package evidence, not a correction finding)

* *Generalizable:* frame-vs-sheet vocabulary discipline; narrow helper input;
  execution-index naming.
* *Contract-specific (did not generalize):* the raw→resolved Form-A boundary
  depended on enrich's three-scalar `defaults` contract; no sibling has an
  equivalent bag.
* *Awkward local divergence introduced:* enrich now says `frame_*` /
  `fk_defs_by_frame`, while `policy.known_data_frame_names`, `drop`, and the
  `provenance` parameter still say `sheet_*`. This is a real package-consistency
  signal, recorded as evidence.
* *Consistency pressure is insufficient on its own:* per the FTR, matching
  siblings to enrich purely for uniformity is not a valid reason to refactor. A
  vocabulary-parity slice is justified only because it independently reduces
  reader cost (frames named as sheets), and even then must respect the persisted
  `derived.sheets` namespace (section 12).

No concrete defect was found in accepted `enrich.py`; Slice 1 is not reopened.

== 13. Raw/resolved lifecycle assessment

* *enrich.py:* resolved (Slice 1). The only module with an authored-config →
  resolved-runtime transition; it is now locally visible.
* *policy.py:* transitions persisted policy → validated list → adapter shape →
  `FKDef` work items. These are *state* transitions, not config resolution; each

  resolution to make explicit.
* *Conclusion:* the raw→resolved boundary problem is *enrich-local and solved*. It

== 14. Dependency-width assessment (Pattern B)

The package is already mostly narrow. Whole-`frames` arguments
(`resolve_v2_fk_relations`, `derived_helper_columns_by_sheet`,
`known_data_frame_names`, `build_id_value_maps`) are appropriate: those functions
read `_meta` or enumerate frames — the whole mapping *is* their dependency.
`_lookup_formula_provider(registry)` captures the whole adapter but the closure
reads only the matched entry — a deliberate strategy binding, not accidental
coupling. `_clean_helper_provenance(out, meta, derived_sheets)` passes `meta` and
`derived_sheets` that the caller derived from `out`; mildly redundant but not a
broad-bag smell. No new dependency-width finding is raised.

== 17. Flatness-ownership assessment (FK-HR-016, deferred — not authorized)

* `apply_fk_helpers` (core.fk) materializes helper columns as MultiIndex tuples
  padded to `levels`; on a flat source frame this yields a non-flat frame.
* `enrich._preserve_source_flatness` repairs this so durable relations replayed
  against un-flattened frames do not crash downstream flat-only steps
  (`join_frames`, structured persistence) — the documented Dino-shaped replay
  failure.
* *Callers requiring the repair:* `enrich_helpers` (the only materialization
  caller); protected by `test_orchestrator_persistence_boundary.py`
  (`*absent_target*`, `*repeated_run*`, `*survives_spreadsheet_carrier*`) and
  `test_persistence_boundary.py`.
* *Could `apply_fk_helpers` own it?* Only by learning the caller's flat/non-flat
  shape contract, which would broaden `core.fk` with a domain-layer concern.
* *Classification:* **acceptable compensating wrapper** (leaning "correct
  ownership"): the domain layer, which knows the flat contract, repairs a
  representation choice made by generic core plumbing. Moving it down would
  broaden `core.fk`; moving it into a separate wrapper adds a concept without
  benefit. Retain as the accepted Slice-1 positive reference; no implementation
  proposed.

== 19. Adapter / `core.fk` boundary assessment

* *`FKDef`:* a `core.fk` NamedTuple, *not* in `core.__all__`; reused by the
  package as the materialization work-item shape and read by
  `formula_provider`/`provenance`. Package-shared core plumbing; replacing it is
  an architecture decision, not a readability edit.
* *`target_sheet_key`:* a real historical-vocabulary field; it carries a workbook
  *sheet key* used by both the adapter and the formula provider (which resolves a
  genuine `lookup_sheet`). It is closer to "real workbook concept, historically
  named" than pure sediment. Migration is staged/architecture.
* *Target-registry reuse:* `build_v2_target_registry` mirrors
  `core.fk.build_registry` so `build_id_value_maps`/`apply_fk_helpers` and the
  formula provider can drive materialization unchanged. Confirmed *load-bearing*
  (all three consumers read `sheet_name`/`id_field`). Reuse remains valuable.
* *Materialization contracts:* stable and tested; no evidence of drift.
* *Source-flatness ownership:* belongs *above* this boundary today (section 17);
  moving it below would broaden `core.fk`.
* *Proportionality:* changing this boundary (replacing `FKDef`, retyping the
  registry, relocating flatness) is disproportionate to the readability gain.
  **Conclusion: retain the boundary.** If the adapter is ever touched, the
  smallest honest step is to *name it an adapter* and type its I/O — not to
  redesign `core.fk`. No replacement architecture is designed here.
