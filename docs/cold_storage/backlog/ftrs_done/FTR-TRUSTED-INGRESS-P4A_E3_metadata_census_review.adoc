== 2. Accepted authority reconstructed independently

`TRUSTED-INGRESS-DESIGN-REVIEW-F4` originally found that the proposed exact
dict/list/scalar grammar preceded the necessary metadata inventory and that an
unconstrained root delegate could bypass both grammar and atomicity. Its
accepted disposition changed the exact vocabulary into a preferred hypothesis
and required a focused, independently accepted pre-E3 census. It also made
delegates central, static, staged, non-mutating, safe-inspection constrained,
bounded in output, and subject to a central post-check. Legend Blocks is named
as compatibility evidence to migrate, not as an automatically approved
delegate.

The exact E3 precondition is an independently accepted census of *external,
persisted, runtime-created, projected, and consumed* metadata node shapes. The
evidence must accept dict/list/scalar or provide an explicit bounded
alternative and migration treatment. Acceptance requires supported metadata
to survive in an owned bounded substrate; invalid roots, opaque values, and
cycles reject atomically; delegate output is post-checked; YAML Option A is
implemented at the backend boundary; and family semantics remain local.

The accepted F4 correction therefore confirms all of the following:

* dict/list/scalar was a hypothesis, not authority;
* supported existing shapes cannot become silent rejection;
* a Legend Blocks or later delegate cannot bypass the common postcondition;
* `meta_registry.yaml` is a manual review artifact, not runtime grammar; and
* census evidence may revise E3's vocabulary or require migration.

The accepted F5 disposition selected YAML Option A: reserve stem `_meta`,
safe-load at most one `_meta.yaml`/`_meta.yml` mapping, reject duplicates and
non-mapping roots at the parse boundary, never reinterpret a DataFrame in
Domain ingress, and provide release-note/migration treatment for the lost
ordinary sheet name.

The accepted F7 disposition is equally load-bearing here. A conformance
interval is not an alias tracker or isolation mechanism. Atomicity means that
ingress/delegates do not mutate caller input through their own work and publish
no staged candidate before success. It explicitly excludes deep-copy
ownership, retained-alias guarantees/tracking, concurrent isolation, later
mutation, and rollback of prior/plugin side effects.

== 6. Aliasing, cycles, and ownership

Aliasing and cycles are distinct. A shared child can be reached from two paths
without any path reaching an ancestor. Such a graph is acyclic. A cycle exists
only when traversal reaches an active ancestor/self.

The accepted contract forbids cycles. It does not forbid acyclic aliases,
require global alias detection, require aliases to be copied, or promise
retained-alias isolation. Identity-based cycle detection should therefore be
path-active/ancestor detection, not a global “seen twice means cycle” rule.

The census's ownership consequence is not sound. In particular:

* F7 expressly excludes deep-copy ownership and alias tracking from ingress
  atomicity.
* Current code commonly copies only the mutated path and retains unrelated
  aliases. Existing metadata ownership work names
  `copy-along-the-mutated-path`, not blanket recursive copying.
* Maintained tests do assert nested `_meta` identity in failure-atomicity paths
  (`test_domain_ingress_boundaries.py` preserves `sheets`, sheet metadata,
  `options`, and `column_widths` identities). Other tests assert direct
  `_meta` pass-through. Even where a success-path identity is not asserted,
  absence of an assertion is not compatibility authority.

“Owned bounded acyclic substrate” therefore requires ingress-owned staging,
validation, and publication; no mutation through ingress/delegate work; and
copying along paths that ingress/delegates actually rewrite. Retained aliases
outside mutated paths may remain. It does *not* require every accepted
container to be recursively deep-copied or to have unique identity throughout
the graph.

== 7. YAML, programmatic, and delegate dispositions

PyYAML safe-load reachability was independently confirmed for `!!set`,
`!!omap`, `!!pairs`, `!!binary`, date, and datetime. Date/datetime are E1
Scalar categories. The census correctly recognizes `!!set`, `!!omap`, and
`!!binary` as reachable but incorrectly treats all of them as unsupported on
the rationale that no writer produces them. The maintained structured
metadata writer produces and roundtrips set and bytes. Omap/pairs remain
reachability-only on current evidence.

Direct programmatic `_meta` has no blanket “arbitrary Python object graph”
promise. Exact-container E3 is the accepted establishment of a bounded
substrate, not an accidental change merely because Python can pass an object.
That conclusion cannot be used to discard an explicit carrier roundtrip or
legacy-read promise.

Legend Blocks is correctly classified as the anticipated E3 delegate
migration rather than evidence that the common vocabulary must be dynamically
extensible. Current normalization accepts Mapping/list, emits an exact dict,
shallowly retains nested values, and performs unsafe truthiness/`str` identity
resolution. Its block-internal values are not currently recursively checked.
E3 may authorize the delegate only if the complete post-delegate output is
walked against the accepted common substrate (or an explicitly named bounded
root contract). Delegate status cannot let tuple/set/bytes/opaque values pass
unchecked.

== 8. Backend and parked concerns

The YAML reserved-stem treatment is sound and already decided by F5/Option A:
at most one spelling, mapping root at the backend boundary, no DataFrame
reinterpretation, Domain E3 validation of the resulting values, and release
notes for the reserved-name migration.

CSV/XML are not documented metadata carriers and both writers deliberately
omit `_meta`. A foreign `_meta.csv`/`_meta.xml` currently becomes a DataFrame;
E3 invalid-root rejection safely prevents it becoming metadata. Cross-backend
filename reservation would improve ergonomics/consistency but is not an E3
vocabulary prerequisite. Parking it is sound.

The FK/helper tuple-tolerance inconsistency is dormant. The v2 FK producer
writes an exact list, the primitive requires a list, and searches found no
maintained producer, fixture, documented example, or supported programmatic
contract supplying a tuple at the affected paths. Generic Sequence or
list/tuple consumer tolerance does not make tuple input load-bearing.

== 10. Findings

=== TRUSTED-INGRESS-E3-CENSUS-REVIEW-F1 -- Blocking -- current and historical metadata writers falsify the “reachable only/no producer” basis for rejecting special shapes

*Evidence:* Current `yaml.safe_dump` writes set and bytes and the JSON metadata
reader restores them exactly. The pre-JSON workbook writer used `str(dict)`,
and the retained literal-eval fallback restores tuple, set, bytes, and complex.
Both paths were reproduced. The generic metadata persistence acceptance says
metadata roundtrips end to end; the accepted serialization ADR promises legacy
Python-literal workbooks remain readable.

*Impact:* Exact dict/list/E1-Scalar enforcement would reject or change these
values without the admission/migration decision F4 requires. The census's
claim that safe dumping rejects set/tuple/bytes is factually wrong (tuple is
serialized as a sequence; set and bytes use safe standard tags), and its “no
known producer ever wrote” legacy claim is contradicted by repository history.

*Required correction:* Reopen only the bounded compatibility disposition for
current structured-sidecar set/bytes and legacy literal tuple/set/bytes/complex.
For each, either retain it in an explicit bounded vocabulary or name the
migration/rejection boundary, legacy handling, tests, and release consequence.
Also include `!!pairs` in the reachable safe-load inventory. This review does
not choose or implement that correction.

=== TRUSTED-INGRESS-E3-CENSUS-REVIEW-F2 -- Important -- ownership is incorrectly converted into blanket deep-copy permission/possible requirement

*Evidence:* The accepted F7 disposition explicitly excludes deep-copy
ownership, alias tracking, retained-alias isolation, and concurrent/later
mutation guarantees. Phase E requires staged non-mutating ingress/delegate
work and publication only after success. Current metadata contracts use
copy-along-the-mutated-path, and maintained tests do pin nested identity in
failure-atomicity paths.

*Impact:* This does not by itself widen the node vocabulary, but it would send
E3 implementation toward a stronger and potentially incompatible ownership
architecture not authorized by the accepted design.

*Required correction:* State that acyclic aliasing is permitted; cycle
detection is ancestor/path-active rather than global alias rejection; ingress
copies paths it rewrites and otherwise owes caller-input non-mutation and
staged publication, not universal recursive deep copying.

== 11. Overall verdict and lifecycle consequence

*C. CHANGES REQUIRED -- COMPATIBILITY EVIDENCE INCOMPLETE.*

The census successfully reconstructs the need for a central bounded substrate,
correctly keeps the registry out of runtime grammar, and correctly classifies
Legend Blocks and YAML Option A at an architectural level. It does not yet
authorize the preferred exact dict/list/E1-Scalar vocabulary because current
and historical framework writers supply material compatibility evidence for
out-of-vocabulary nodes that the census incorrectly denies.

E3 remains blocked until F1's exact compatibility issue is independently
resolved. If the resolution chooses migration rather than vocabulary widening,
the preferred bounded substrate may remain the final E3 target. F2 must also be
corrected so E3 does not infer blanket deep-copy/alias elimination from
“owned.” No E3 implementation, lifecycle alignment, E4+ work, or correction is
performed by this review.
