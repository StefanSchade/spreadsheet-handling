Where the current `""` is introduced: not at the FK-key normalization layer
(`core/fk.py:_norm_id`), which correctly returns `None` for a missing/NaN key
and the literal string `"ENT-MISSING"` or `""` unchanged for a present key.
It is introduced at the *write/read boundary of the XLSX backend*, where a
missing helper *value* (see "Root cause -- pinned") round-trips through
openpyxl as a blank cell and the XLSX parser's `str(val) if val is not None
else ""` (the accepted visible-cell string-substrate contract, per
`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE`) turns the blank cell into `""`.
This is *not* an accepted semantic contract for "unresolved" -- it is an
accidental byproduct of one specific library's (openpyxl's) NaN-to-`None`
write behavior, which happens to compose with the string-substrate ADR to
produce `""`. The ODS backend, going through the same in-memory NaN, produces
`"nan"` instead, via an unrelated accidental defect (below). Neither backend's
current output is a deliberate representation of "unresolved."

==== Root cause -- pinned

Distinguishing *observed current fact* from *historical explanation* from
*hypothesis*, per the full trace (probes in the checkpoint file; all read via
`.venv/bin/python`, no production code modified):

. *observed current fact* -- `domain/transformations/fk_helpers/enrich.py`'s
  `enrich_helpers` calls `core/fk.py:apply_fk_helpers`
  (`src/spreadsheet_handling/core/fk.py:~327-333`). For each unresolved row,
  `value_map.get(_norm_id(rid))` returns Python `None` (dict-default
  behavior; `_norm_id` itself is correct and unchanged since the historical
  BUG -- `core/fk.py:26`).
. *observed current fact* -- assigning a Python list containing `None`
  (mixed with resolved `str` values) into a new DataFrame column
  (`core/fk.py:337`, `new_df[col_tuple] = values`) does not preserve the
  `None`. Under the project's currently active pandas string dtype, the
  column reports `dtype == "str"` but the unresolved cells are stored as an
  actual Python `float('nan')`, confirmed by direct inspection
  (`type(value) is float`, `repr(value) == 'nan'`). This is the FK-helper
  value materialization step turning "no match" into a *pandas/NumPy carrier
  missing value* -- not yet a string, and not yet `"nan"` as text.
. *observed current fact* -- `rendering/composer/layout_composer.py:353`
  (`compose_workbook`) copies `df.values.tolist()` directly into
  `TableBlock.data` with *no* NaN/None normalization at the render-IR
  boundary. The raw float NaN reaches both backend renderers unchanged.
. *observed current fact, XLSX* -- `io_backends/xlsx/openpyxl_renderer.py`
  passes the raw value straight to `ws.cell(..., value=val)`
  (`_xlsx_cell_value`/`_write_data_block`, ~line 218-235) with no NaN
  handling. A minimal openpyxl-only probe (write `float('nan')`, save,
  reload) confirms openpyxl itself silently converts a NaN-valued cell to
  `None` on save/reload -- this is accidental library behavior, not a
  decision made anywhere in this codebase. The XLSX parser then applies its
  documented, ADR-compliant `str(val) if val is not None else ""`
  (`io_backends/xlsx/parser_interpretation.py`), producing `""`.
. *observed current fact, ODS* -- `io_backends/ods/odf_renderer.py:563`
  contains the cell-emptiness check `if value in (None, ""):`. Python's `in`
  operator uses `==` comparisons, and `float('nan') == float('nan')` is
  `False` by IEEE-754 definition, so `nan in (None, "")` evaluates to
  `False`. The NaN therefore *fails* the emptiness check and falls through to
  the numeric branch (`isinstance(value, (int, float))`, line 573-579),
  which writes `valuetype="float"` with a paragraph text of `str(value)` --
  literally `"nan"` -- into the cell. This is a genuine, narrow correctness
  defect in this one emptiness check: the project already has at least three
  independent, *correct* implementations of "carrier-missing vs literal
  string" elsewhere (`core/fk.py:_norm_id`,
  `derived_column_policy.py:_norm` at line 605, and
  `domain/_cell_primitives.py:_is_empty_cell`, all of which use
  `pd.isna(...)` rather than `in (None, "")`), none of which is applied at
  this write boundary.
. *observed current fact, ODS read* -- `io_backends/ods/odf_parser.py:86`'s
  `_cell_value` reads the cell's paragraph text (`_cell_text`) *first*, before
  consulting `office:value-type`/`office:value`. Since the renderer wrote a
  non-empty paragraph text of `"nan"`, the parser returns the literal string
  `"nan"` without ever reaching the float-attribute branch.
. *hypothesis, explicitly not claimed as fact* -- whether the *historical*
  8f8b519-era reproduction went through exactly this same ODS code path is
  plausible (same architecture family, same string-substrate contract) but
  not re-verified against that historical commit; this revalidation verifies
  the *current* HEAD path only, which independently reproduces the same
  symptom via the mechanism traced above.
. *historical explanation, superseded* -- the historical BUG's "Root cause
  sketch" left open whether a downstream stringification artifact or
  contaminated replay was responsible. This revalidation rules out
  contaminated replay for the current reproduction (fresh synthetic fixture,
  no `"nan"` in seed data) and identifies the "stringification artifact" as,
  specifically, the ODS renderer's NaN-blind emptiness check -- not a generic
  or diffuse stringification problem.

==== Semantic distinctions (grounded in the current trace, not assumed)

The trace above shows the *in-memory* value materialization step already
distinguishes more than the persisted representation preserves: a
successfully resolved helper whose target value happens to be a legitimate
empty string is represented in-memory as the Python string `''`, genuinely
different from the unresolved case's `float('nan')`. The information loss is
introduced entirely at the render-write / string-substrate boundary, not in
FK resolution itself. This bounds the fix: normalization at or before the
write boundary can recover the distinction; no change to FK resolution logic
is implied.

Applying the task's six-way split to what actually happens today:

* *Missing source* -- source FK column value itself is empty/absent.
  `_norm_id("")` returns `''` (a real, distinct key, not `None`) so an empty
  source string is technically a *key that fails to match* rather than a
  `None` key -- but in practice it behaves identically to "unresolved
  reference" below because no target row has an empty-string ID. Direct-Frame
  probing shows a *programmatic* `None` or NumPy `NaN` source value
  normalizes to `_norm_id(...) -> None`, which is a genuinely distinct case
  from the empty-string source at the key level, though it collapses to the
  same downstream `nan` value carrier once the lookup misses.
* *Unresolved reference* -- a non-empty, well-formed key
  (`_norm_id` succeeds) with no matching target row (`"ENT-MISSING"`).
  Currently indistinguishable from "missing source" once the lookup misses;
  both produce the same `value_map.get(...) -> None` outcome and the same
  downstream `nan` carrier.
* *Carrier missing value* (pandas `NaN`/`NA`/`NaT`) -- confirmed as the
  actual in-memory carrier for every unresolved case today (step 2 above),
  regardless of which of the above caused the lookup miss.
* *Domain empty string* -- a legitimate resolved value of `''`. Proven
  distinct from "unresolved" *in memory* (step 2), but currently collapses to
  the *same* `""` output as an unresolved value on the XLSX no-cleanup path
  (proven collision, see reproduction table).
* *Literal domain `"nan"`* -- a legitimate resolved value that is textually
  `"nan"`. `_norm_id`/`_norm` both correctly keep this distinct from a
  carrier-missing value when acting on *keys* or *comparison values*. But as
  a resolved *helper value* it currently collapses to the *same* `"nan"`
  output as an unresolved value on the ODS no-cleanup path (proven collision,
  see reproduction table).
* *Spreadsheet/carrier error* -- not currently modeled or producible by any
  maintained automated path. Formula-mode helpers (`helper_value_mode:
  formula`) emit a generic per-row lookup formula
  (`core/formulas.py:lookup_formula`, consumed by
  `fk_helpers/formula_provider.py`) whose `missing=""` fallback is baked into
  the formula text itself, identical for every row regardless of whether that
  row's key is present, missing, or unresolved -- the actual
  resolved/unresolved distinction is deferred entirely to spreadsheet-app
  formula evaluation (Excel/LibreOffice), which no test in this repository
  executes. This is genuinely untested territory for the nan-semantics
  question, not merely unexercised by the current xfail.

The evidence does *not* support minting six separate persisted
representations. It supports: (a) a normalization step that treats
"carrier-missing" uniformly regardless of which upstream cause produced it
(missing source vs. unresolved reference collapse naturally and do not need
separate persisted tokens, since neither `_norm_id` nor any consumer
currently distinguishes them operationally); and (b) that the resulting
uniform "unresolved" representation must not equal either `""` or `"nan"`,
because both already collide with proven legitimate domain data.

==== Evaluated contract options

CAUTION: Superseded for the "is a distinct unresolved-value representation
needed at all" question by "Semantic-contract decision (2026-08-08)" below.
This section and "Recommended direction" reflect the revalidation's
reasoning *before* the semantic-ownership investigation; retained as
historical evidence, not current recommendation. In particular, the
revalidation's assumption that *some* non-`""`/non-`"nan"` carrier
representation would be needed is not supported once the authoritative
source reference and the maintained `validate_fk_helpers` diagnostic are
taken into account -- see the decision section for why.

===== Option A -- collapse unresolved helper value to empty/missing

A bare `""` is evidenced-insufficient: this revalidation proves it already
collides with a legitimate resolved empty-string helper value on the XLSX
no-cleanup path today. JSON `null` does not have this collision (`null !=
""`) but cannot be spelled as a distinct value inside a plain string
spreadsheet cell without a reserved-token convention -- the visible-cell
typing ADR fixes the substrate as plain string and this BUG does not reopen
it. So: `null` is viable wherever the value never has to pass through an
actual visible cell (a pure in-memory or forward-only canonical view); a
plain `""` alone is not viable wherever it does, because it already loses a
real distinction. Diagnostics can be preserved separately (see Option B) but
that is additive, not a substitute for choosing a non-colliding cell value.
Compatible with the visible-cell string substrate as long as the eventual
in-cell token is still an ordinary string.

===== Option B -- visible/payload fallback plus structured diagnostic

`domain/finding_frame.py` (`Finding`, `findings_to_frame`, the shared
seven-column schema) and `derived_column_policy.py`'s
`derived_column_findings` output are an *owned, existing, reusable*
mechanism -- no new diagnostics mechanism is needed structurally. However,
today that mechanism is wired *only* for the `enrich_lookup` family's value-
mismatch checks, and it *explicitly skips* unresolved references
(`derived_column_policy.py:555`, `# unresolved reference is a separate
concern`). FK helpers are "dropped but not value-checked" in the current
slice (module docstring). Extending it to cover FK-helper unresolved
references is real, bounded, new wiring (new `rule_type`, a new value-check
entry point for the FK-helper family, which currently has none) -- not a
reuse-only change. This makes Option B a credible *complement* once
implemented, not a currently-available shortcut.

===== Option C -- spreadsheet/carrier error representation

Not viable as the sole or primary answer. It cannot cover the missing-source
or unresolved-reference case at all (no spreadsheet error token exists
without a formula being evaluated), and this project's automated tests
cannot exercise real LibreOffice/Excel evaluation to validate formula-mode
behavior. Adopting a spreadsheet error token as the *canonical* domain
representation would also cut against the spirit of
`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` (no native typed substrate is
authorized here) and the task's own guidance against making spreadsheet error
syntax the canonical representation merely because spreadsheets support it.
A reserved ordinary *string* sentinel (still plain text, not a spreadsheet
error type) remains compatible with the string substrate and is a different,
viable idea from adopting `#N/A`-style tokens as canonical.

===== Other option considered

A dedicated reserved string sentinel, distinct from both `""` and `"nan"`,
used uniformly wherever the value must pass through a visible cell; JSON
`null` used wherever it does not. This is not one of the original three
options as literally written (the original Option 1 conflated `""` and
`null` as interchangeable) but follows directly from the current evidence:
neither `""` nor `"nan"` is safe alone, and the in-memory materialization
step already has the information needed to know "this is unresolved" before
it is ever forced through the string substrate.

==== Recommended direction

==== Implementation slice 1 -- carrier defect fixed (2026-08-07)

*Scope of this slice:* eliminate the backend-divergent accidental
serialization of the unresolved helper's pandas missing carrier only. Does
*not* finalize the broader unresolved-reference semantic contract (see
"What remains open" below, and "Evaluated contract options" /
"Recommended direction" above, both still current).

*Normalization owner chosen:* `core/fk.py:apply_fk_helpers`
(`value_map.get(_norm_id(rid), "")`, now line ~346), the sole FK-helper
*value* materialization point -- confirmed single call site
(`domain/transformations/fk_helpers/enrich.py`), no other production caller.

Rejected alternatives, and why:

* *workbook/TableBlock projection* (`rendering/composer/layout_composer.py`
  `compose_workbook`) -- too broad. It would normalize *every* DataFrame
  cell reaching every table, not just FK-helper columns, silently changing
  behavior for any other current or future NaN-carrying payload cell (for
  example CSV-sourced missing values, which retain a real pandas NaN on the
  directory read path per the internal-value-model sketch). That is exactly
  the "arbitrary object-column values outside the owned visible-cell/
  carrier contract" this slice was told not to touch.
* *independent per-renderer emptiness-check patches* (fixing
  `io_backends/ods/odf_renderer.py:563`'s `value in (None, "")` in place,
  and/or hardening the XLSX renderer to match) -- duplicates the same
  "is this a missing carrier" predicate across two backend-specific files.
  That duplication is *how the divergence happened in the first place*
  (OpenPyXL's implicit NaN-to-`None` write behavior and the ODS renderer's
  hand-rolled check drifted independently). It also risks "ODS merely
  emulating an OpenPyXL accident" if the ODS predicate were patched to
  match XLSX's specific library-internal behavior rather than being
  correct on its own terms.

Fixing at `apply_fk_helpers` means neither renderer ever receives a raw NaN
for an FK-helper *lookup miss* -- both backends consume an already-decided,
ordinary Python string for that case. A successful lookup is unaffected by
this fix and still returns its stored target payload verbatim; if that
payload is itself a missing carrier, the column can still carry a raw NaN
into a renderer for that row (outside this slice; see "What remains open"
below). No renderer code was changed.

*Fix:* an unresolved lookup (missing source key, or a non-empty key with no
matching target row) now supplies an explicit `""` default to the
`dict.get` call, instead of relying on Python's implicit `None`. `None`
mixed into a pandas column assignment was silently coerced into a real
`float('nan')` carrier under the project's active string dtype -- confirmed
during revalidation (`type(value) is float`, `repr(value) == 'nan'`) -- and
that NaN was what let the two backend renderers diverge: OpenPyXL silently
drops a NaN-valued cell to blank on save (accidental library behavior);
the ODS renderer's NaN-blind `value in (None, "")` check falls through to
its numeric branch and writes the literal text `"nan"`. A lookup *miss* no
longer introduces a pandas missing carrier for a helper column, so neither
renderer has anything to mishandle for that miss. A successful lookup
(a dict hit) still returns its stored payload verbatim, including a stored
`None`, NumPy NaN, pandas `NA`, or another maintained missing carrier --
that case can still materialize a missing helper carrier and is outside
this slice's owned contract (precision correction per Implementation
Review 001, finding NAN-SEMANTICS-REVIEW-F1).

==== Semantic-contract decision (2026-08-08)

*Scope of this investigation:* decision-only. No production code, tests,
types, or FTR were created or changed. This section records the central
question, the evidence trace, the evaluated options, and a *recommended*
(not accepted, not implementation-authorized) contract.

===== Central question, restated

> Must an unresolved derived FK-helper value itself be distinguishable from
> a legitimately resolved empty helper value, or is the semantic
> distinction correctly owned by the authoritative source reference plus
> its resolution state/diagnostics?

The existing xfail
(`test_unresolved_helper_value_distinguishable_from_legitimate_empty_string`)
was evidence that this question was open, not evidence that the framework
must answer it by making the two helper-cell values differ. This
investigation does not start from the assumption that the xfail's own
assertion shape is correct.

===== Semantic ownership, traced through the current codebase

. *Authoritative source value.* The FK column on the source frame (e.g.
  `items.entity_id`) is ordinary domain payload: an FK-bearing table's own
  reference to a row in the target table. It is never dropped, never
  helper-prefixed, always round-trips as plain text per the visible-cell
  string substrate, and is the sole input `core/fk.py:_norm_id` normalizes
  for lookup.
. *Target lookup/resolution state.* Computed fresh, on demand, by joining
  the source FK value against the *current* target frame's key column.
  `domain/validations/fk_helpers.py:check_unresolvable_fks` (line 196) does
  exactly this: `missing = {... for v in fk_series ... if _norm(v) not in
  target_ids}` -- comparing the authoritative source column directly
  against a live target-id set, with *no reference to the helper column at
  all*. Resolution state is therefore a pure function of
  `(source_frame, target_frame)` at read time, not a stored fact.
. *Derived helper payload.* `core/fk.py:apply_fk_helpers` materializes a
  copy of the resolved target field next to the FK column, purely for
  spreadsheet display/editing convenience. Per
  `docs/technical_model/ch04_concepts/fk_helper_metadata.adoc` ("First
  conservative policy"): "manual edits to helper *values* are not treated
  as source truth; helper values may be ignored or overwritten on
  re-enrichment." The helper column is explicitly *not* authoritative.
. *Diagnostics.* `domain/validations/fk_helpers.py:validate_fk_helpers`
  (line 284, registered pipeline step `validate_fk_helpers`,
  `pipeline/steps.py:make_check_fk_helpers_step`) runs
  `check_unresolvable_fks` (source-vs-target, described above) and
  `check_helper_values` (line 131: recomputes the *expected* helper value
  from a fresh target lookup and reports a `value_mismatch` finding when
  the materialized helper cell disagrees). Both are opt-in (a pipeline
  author includes the step; default severity `warn`), pure, and
  independent of any special helper-cell spelling.
. *Workbook-visible helper projection.* Per Implementation slice 1, always
  `""` today for an unresolved lookup, on both backends, in `values` mode.
  In `formula` mode, a backend-neutral `LookupFormulaSpec` with
  `missing=""`, evaluated live by the spreadsheet application -- the
  framework never even chooses a static unresolved value in that mode.
. *Canonical persisted payload.* Under the recommended/normal lifecycle
  (`apply_derived_column_policy: drop` + `validate_references:
  no_helper_columns`, per the same concept doc's "Cleanup direction"), the
  helper column never reaches canonical persistence at all. The
  unresolved-vs-resolved-empty ambiguity is therefore a non-issue on the
  recommended path; it exists only when a helper is *deliberately* retained
  (an upstream/editable view, or a no-cleanup reimport used to inspect
  workbook state, as the BUG's own reproduction and regression tests do).
. *Reconstruction/replay behavior.* Verified directly (probes below): after
  a full `sheets-run` export -> real XLSX/ODS file -> reimport cycle on
  *both* backends, the authoritative source FK column round-trips
  unchanged, and `validate_fk_helpers` run against the reimported frames
  still correctly and exclusively flags the unresolved row -- even though
  the helper cell shows the identical `""` for both the unresolved and the
  legitimately-resolved-empty row.

*Empirical evidence (read-only probes, no production/test files changed):*

[source,python]
----

entities = {"id": ["ENT-001", "ENT-002"], "name": ["Alpha", ""]}   # ENT-002 legitimately ""
----

In-memory, immediately after `add_fk_helpers`:

ITEM-002  ENT-002       _entities_name = ""      (legitimately resolved empty)
ITEM-003  ENT-MISSING   _entities_name = ""      (unresolved)

----

Identical result after a full `sheets-run` forward export to a real file and

backend=ods:  ITEM-002 -> "", ITEM-003 -> ""; validate_fk_helpers flags only ITEM-003

The two rows are byte-identical in the helper cell on both backends, and

===== Direct answers to the lifecycle questions

* *Is the helper column authoritative data or a derived projection?*
  Derived projection. Explicitly documented as such; manual edits are not
  source truth; values may be silently overwritten on re-enrichment.
* *Can unresolved state always be recomputed from the authoritative source
  FK?* Yes, whenever the target frame is also available -- which holds for
  every currently maintained materialization path (`add_fk_helpers`,
  in-process) and every currently maintained reimport path that loads both
  the FK-bearing and target sheets (as the roundtrip fixtures and the
  probes above do; a pipeline that reimports only the FK-bearing frame and
  never loads the target cannot check any cross-frame reference, which is
  a general property of cross-frame validation, not specific to this BUG).
* *Are helper columns persisted canonically, or dropped/reconstructed by
  the normal lifecycle?* Dropped, under the recommended/documented
  lifecycle. `BUG-HELPER-CLEANUP-CONTRACT-P4A` (Done) exists specifically
  to keep this drop working.
* *Which workflows intentionally retain helpers?* Only "upstream/editable"
  workbook views meant for human editing (per the concept doc's "for
  display" framing and the catalog's `formula` vs. `values` mode
  discussion), and diagnostic/no-cleanup reimports used to inspect
  workbook state (as this BUG's own regression tests do). No documented,
  maintained workflow treats a retained helper's *value* as a
  machine-authoritative signal.
* *Does any maintained consumer depend on the helper cell alone to
  distinguish unresolved from resolved-empty?* No. Every FK-helper
  consumer inspected (`drop.py`, `provenance.py`, `policy.py`,
  `validations/fk_helpers.py`, `derived_column_policy.py`,
  `workbook_views.py`, the rendering passes) identifies or drops helper
  columns by *name/provenance declaration*, never by value; the one
  consumer that does inspect the value
  (`check_helper_values`) does so specifically to *detect disagreement*
  with a fresh lookup, which presumes the helper cell is *not* trusted as
  ground truth.
* *Does formula mode change the answer?* No -- it reinforces it. In
  `formula` mode the framework never chooses a static cell value at all;
  it emits `LookupFormulaSpec` Intent (`missing=""`) and the spreadsheet
  application recomputes the displayed value live from the *same*
  authoritative source + target relationship at open/recalc time. Formula
  mode is architecturally the clearest existing proof that the helper's
  displayed value is already treated as ephemeral, never authoritative.
* *Does cleanup/replay make cell-level preservation unnecessary?* Yes, in
  two ways: cleanup removes the ambiguity from canonical persistence
  entirely on the recommended path, and replay (reimport) preserves the
  authoritative source FK column, from which resolution state is always
  recomputable, as demonstrated above.

===== Option A -- distinct helper carrier (conceptual only; not designed here)

Contract: `resolved empty -> ""`, `unresolved -> distinct carrier`.

* *Reserved string sentinel.* Does not remove ambiguity, it relocates it:
  any sentinel is itself an ordinary string that could collide with real
  domain data (lower probability than `""`/`"nan"`, not zero), and -- more
  importantly -- since the semantic information is *already* fully
  recoverable from the source reference (proven above), a sentinel would
  duplicate information the framework does not need duplicated. It would
  also leak into canonical JSON on any retained-helper path, presenting a
  confusing framework-internal token as if it were domain data to any
  downstream consumer that does not know the convention -- arguably worse
  than a plain `""`, which at least reads as "nothing" rather than "some
  unexplained text." It would need write/read plumbing in both renderers
  and would need to survive spreadsheet-application autocorrect/spellcheck
  without justification, since nothing currently needs it to survive.
* *Spreadsheet error token.* Not viable as a `values`-mode representation
  at all -- error tokens are formula-evaluation results, not literal
  written values, and no maintained writer path emits them outside actual
  formula evaluation. Already rejected in the "Evaluated contract options"
  section above for the same reason; this investigation finds no new
  reason to revisit that.
* *Another projected representation* (e.g. conditional styling on the
  unresolved row). This is a presentation-layer idea, not a value
  representation, and does not touch canonical JSON/YAML/CSV/CSV output at
  all. It is conceptually orthogonal to this BUG (it would be a `StylePass`
  feature, parallel to the existing `helper_fill_rgb`/protection styling)
  and is not evaluated further here.
* *ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE impact:* a sentinel would
  remain an ordinary string, so it would not *require* reopening the ADR
  on its face -- but it works against the ADR's rationale ("domain
  semantics live in opt-in metadata families, separate from substrate
  semantics") by encoding framework state directly into what looks like
  ordinary payload text. No form of Option A is recommended, so this
  investigation does not require or propose reopening that ADR.
* *Verdict:* not supported by evidence. No maintained consumer needs it;
  every concrete form either duplicates already-recoverable information,
  degrades spreadsheet ergonomics for a redundant display column, or both.

===== Option B -- helper is presentation only (recommended)

Contract: `resolved empty -> ""`, `unresolved -> ""`; the semantic
distinction lives in the authoritative source reference plus resolution
state/diagnostics, exactly as already implemented today.

* *Information loss under maintained lifecycle paths:* none found. The
  empirical probes above show the distinction survives a full real
  export/reimport cycle on both backends without any helper-cell-level
  marker, because it was never actually carried by the helper cell -- it
  is recomputed from the source FK and the target frame.
* `ENT-42 -> target exists, target label ""` vs. `ENT-MISSING -> target
  absent`: after normal write/read/replay, the framework *can* reliably
  distinguish them without inspecting the helper value -- demonstrated
  directly, not assumed.
* *Consequence:* the current xfail requires information duplication in a
  derived column that the framework does not otherwise need duplicated.
  Its assertion (comparing two helper-cell values for inequality) tests an
  implementation detail of a presentational column, not the actual
  invariant that matters (row-level resolution state remains determinable).
* *Diagnostics assessment:* `validate_fk_helpers` (specifically
  `check_unresolvable_fks`, and redundantly `check_helper_values`) already
  exists, is already tested
  (`tests/unit/domain/validations/test_fk_check.py`), and already answers
  this need with zero new code. It is *not* required for semantic
  correctness -- the information is preserved regardless of whether a
  pipeline runs it, because it lives in the persisted source FK column, not
  in the diagnostic's output. It is useful, optional, opt-in *feedback* for
  a pipeline author who wants it surfaced as a `Finding` rather than
  recomputing it themselves. This corrects a gap in the revalidation's
  earlier Option B framing, which proposed *extending*
  `derived_column_findings` (`domain/finding_frame.py`, the family used by
  `apply_derived_column_policy`'s `enrich_lookup` mismatch checks) to cover
  FK helpers -- that extension is unnecessary: a *different*, already-wired
  finding family (`domain/validations/findings.py` via
  `validate_fk_helpers`) already covers exactly this case for FK helpers
  specifically. Adding new diagnostics work is not required; a possible
  *optional* future polish (not required, not designed here) would be
  deduplicating the redundant `value_mismatch` finding that fires
  alongside `unresolvable_fk` for the same row.
* *Verdict:* supported by direct evidence, on both backends, through a
  real roundtrip. Recommended.

===== Option C -- explicit internal unresolved state, lossy visible projection

Conceptual contract: an internal resolution-state distinction, projected
losslessly to `""` on the visible surface, reconstructed from the
authoritative source reference on replay.

* Evaluated conceptually only; no `UnresolvedReference`, `Missing`, or
  other class was created or is proposed.
* Tracing the current control flow shows this already exists, informally,
  exactly where it is needed and nowhere else: `apply_fk_helpers`'s
  per-row loop already "knows" hit-vs-miss for the single instant it
  matters (an ordinary `dict.get` branch), and `check_unresolvable_fks` /
  `check_helper_values` independently *recompute* the same fact on demand
  from two DataFrames, with no stored intermediate value passed between
  the two computations.
* No maintained consumer needs a *named, persisted* unresolved-state value
  or type: it would have nowhere correct to live (not the helper column --
  Option A already rejected embedding framework state there; not the
  source FK column -- that must stay a plain domain value used for joins,
  display, and the `id_(<target>)` wire format). Introducing one now would
  preempt `roadmap_domain_hardening_sequence.adoc` Phase D (the internal
  type model), which explicitly reserves this kind of decision for its own
  evidence-gated slice -- and there is no evidence here of a maintained
  need, only a hypothetical future one.
* *Verdict:* Option C's *intent* is already substantially realized by
  existing control flow plus the existing diagnostic recomputation. A
  first-class internal type is not evidenced as necessary and is not
  recommended; doing so now would be exactly the kind of premature typing
  the roadmap warns against ("New infrastructure is justified only when it
  removes repeated complexity from supported paths").

===== Missing target payload (separate concern, unaffected)

Kept distinct throughout, per the task framing:

* *source key unresolved* -- this BUG's question, addressed above.
* *source key resolves, target payload itself missing* -- proven still
  maintained behavior by the prior implementation review
  (`TestMissingLabelField::test_missing_label_field_results_in_none_helper`
  in `tests/unit/domain/transformations/test_fk_edge_cases.py`) and
  reconfirmed here by a read-only probe: a genuine `numpy.nan` target
  payload, reached via direct Frame construction (not the JSON loader,
  which already coerces `null` to `""` on load), still produces `""` on
  XLSX and *still* produces the literal string `"nan"` on ODS -- because
  Implementation slice 1's fix only supplies a default for a `dict.get`
  *miss*; a *hit* whose stored value is itself a missing carrier is
  returned verbatim, unchanged, and is not caught by the ODS renderer's
  still-unfixed NaN-blind `value in (None, "")` check
  (`io_backends/ods/odf_renderer.py:563`).
* *Does this affect the unresolved-helper contract?* No. It is a
  same-shaped but distinct residual defect: it is about a *resolved*
  reference whose target data quality is itself poor, not about
  distinguishing unresolved from resolved-empty. `check_unresolvable_fks`
  correctly does *not* flag such a row (the key does resolve);
  `check_helper_values` correctly does *not* flag it either (both sides of
  its comparison normalize a missing carrier to the same `None` via its
  own `pd.isna`-based `_norm`). This BUG's semantic-ownership conclusion is
  unaffected.
* *Transferred, not owned here:* this residual ODS-renderer gap was
  discovered *while resolving this BUG*, but it is not this BUG's remaining

  is now the sole owner of the general "real missing carrier reaches the

  text `\"nan\"`" defect. The lineage:

Formula mode does not create any reason for an unresolved helper *cell

==== Deferred formula / typing constraint for future Internal Value Model work (2026-08-08)

*Scope of this section:* recorded architecture/design constraint only, for
whichever future FTR eventually defines the Minimal Internal Value Model
and any formula-preservation feature. Nothing here is implemented,
designed in detail, or implementation-authorized. This BUG does not create
that future FTR and does not decide its DSL; it records the constraint so
that future work does not have to rediscover it, per the task that
produced this section.

This is additional to, not a restatement of, "Formula-mode / read-policy
non-goal" above (which establishes only that FK-helper formula mode does
not require this BUG to decide anything about formulas). This section
instead records what *future* typing/formula work must respect.

===== Formula is outside the typing MVP

A future Minimal Internal Value Model MVP should focus on primitive
payload semantics: `String`, `Boolean`, `Number`, `Missing`, `Error`. The
exact `Integer` vs. `Float` distinction remains a later explicit decision,
not fixed here. Formula handling is explicitly outside this MVP -- a
formula is not a scalar payload value, it is carrier/workbook behavior
layered on top of whatever value the formula evaluates to. Folding formula
representation into the same first slice as primitive scalar typing would
conflate two different kinds of problem (what shape can a value be; what
does a workbook cell do) and is not recommended for the MVP's scope.

===== Observed formula is not automatically authored Formula Intent

A formula read from an input spreadsheet is carrier/workbook information
produced by whoever last edited that workbook. It must not automatically
become the same thing as the framework's own authored `FormulaSpec` output
Intent (`core/formulas.py`, currently `ListLiteralFormulaSpec` and
`LookupFormulaSpec` -- both dataclasses the *framework* constructs to
*request* that a renderer emit a specific formula; neither represents an
arbitrary formula the framework merely observed in an input file). For
example, an input workbook may contain an ID or sequence-number column
computed by a user-authored formula, while the canonical/domain value any
external consumer needs is simply that formula's evaluated result, not the
formula text or a live recalculation contract.

Current evidence this distinction already exists in practice, informally:
`io_backends/xlsx/openpyxl_parser.py` loads workbooks with
`openpyxl.load_workbook(str(path), data_only=True)` -- ordinary payload
formula cells are already read as their last-cached/materialized value by
default, not as formula text. This is a hardcoded parser choice today, not
a deliberate, documented, general read policy; the two `FormulaSpec`
variants exist solely on the *write* side, for content the framework
itself decides to emit. Nothing today generically carries an *observed*
input formula forward as Intent, and nothing should be assumed to, without
a dedicated future decision.

===== Default formula-reading direction (deferred design direction, not decided here)

Recorded direction for future design, not accepted implementation
authority:

____
Spreadsheet formulas should normally be consumed as their
materialized/cached values. Formula preservation should require explicit
pre-load/read policy.
____

This is consistent with, and generalizes, the existing `data_only=True`
XLSX read behavior noted above -- but as a *deliberate, documented,
cross-backend policy* rather than a single backend's hardcoded loader flag.
Not implemented or finalized by this BUG.

===== Formula preservation is pipeline/projection policy, not immutable column type

Important constraint for future work: the desire to preserve a formula
must not permanently attach to the domain column as its type or as
immutable metadata. The same canonical value may legitimately need two
different projections depending on the consuming use case:

*Editable workbook roundtrip:*

[source,text]
----
canonical value -> formula-preserving projection -> XLSX/ODS formula
----

*External extraction:*

[source,text]
----
canonical value -> materialized-value projection -> CSV/JSON/XLSX value
----

A later pipeline/output projection policy must therefore be able to choose
formula preservation versus value materialization per use case, not have
that choice baked permanently into the column's declared type. This BUG
does not design that policy's DSL, its configuration surface, or its
default.

===== Pre-load timing constraint

Any policy controlling whether an existing workbook formula is read as a
formula or as a value must be available *before carrier interpretation* --
that is, at or before the parser (`router.get_loader(kind)`), not as an
ordinary pipeline step. Confirmed against the current architecture: a
normal pipeline step such as `bootstrap_meta`
(`domain/meta_bootstrap.py:bootstrap_meta`, wired via
`pipeline/steps.py:make_bootstrap_meta_step`) executes inside
`pipeline/execution.py:run_pipeline(frames, bound_steps)`, which per the
documented Pipeline flow
(`docs/ai_info/architecture_primer.adoc`) runs strictly *after*
`router.get_loader(kind) -> Frames` has already parsed the file. By the
time any pipeline step (including `bootstrap_meta`) runs, the parser has
already decided formula-vs-value (today, unconditionally `data_only=True`
for XLSX) and the original formula text is already gone if the parser
discarded it. A future formula-preservation read policy is therefore an
adapter/application-boundary concern (part of the loader/parse-contract
layer), not a pipeline-step concern. This BUG does not change
`bootstrap_meta` and does not propose where exactly such a policy would be
threaded through; it only records that a pipeline step is architecturally
too late.

===== Relationship to existing FormulaSpec

Kept explicit for future work: `FormulaSpec` (the `ListLiteralFormulaSpec`
/ `LookupFormulaSpec` union) is authored, backend-neutral, *output* Intent
-- something the framework itself decides to write. It is not, and must
not silently become, a generic representation of every formula observed in
an input workbook. A future formula-preservation feature reading formulas
*in* would need its own distinct carrier/provenance model, or an explicit
projection mechanism translating observed formulas into something
`FormulaSpec`-shaped only where that is actually the intended semantics
(the "editable workbook roundtrip" case above). This BUG does not design
that model.

===== Visible-cell typing ADR remains unchanged

`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` is not reopened by this BUG or
by this recorded formula constraint; the formula note above is future
design context only, contingent on work this BUG does not authorize. If a
future Minimal Internal Value Model MVP stops collapsing visible
spreadsheet payload to strings, *that* is itself a deliberate
successor/revisit decision the future work must make explicitly and
separately -- not something this BUG decides, implies, or pre-authorizes.

===== How this BUG should be used by future typing/formula work

When a future FTR defines the Minimal Internal Value Model or a
formula-preservation feature, this BUG (specifically this section and
"Semantic-contract decision (2026-08-08)" above) should be one of its
inputs for non-goals and constraints: no premature `UnresolvedReference`/
`Missing` type was found necessary for the FK-helper case; formula
representation is explicitly out of the typing MVP; observed formulas are
carrier state, not authored Intent, until a dedicated projection decision
says otherwise; and any formula-vs-value read policy is a pre-load/adapter
concern, not a mid-pipeline step.
