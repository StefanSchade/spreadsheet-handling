== 3. Reproduced absent/null behavior

An untracked probe used an edited `title`, an available lookup frame, and the
five degraded key payloads. *Before* the fix, every case failed open:

[cols="3,2,2"]
|===
| Key payload | `warn_on_mismatch` | `fail_on_mismatch`

| `{}` (no key form) | 0 findings, `title` dropped | no raise, `title` dropped
| `{"on": null}` | 0 findings, `title` dropped | no raise, `title` dropped
| `{"source_key": null}` | 0 findings, `title` dropped | no raise, `title` dropped
| `{"lookup_key": null}` | 0 findings, `title` dropped | no raise, `title` dropped
| `{"source_key": null, "lookup_key": null}` | 0 findings, `title` dropped | no raise, `title` dropped
|===

The same edited payload with a proper `{"source_key":"story_id","lookup_key":"id"}`
raised under `fail_on_mismatch`, proving the pass was caused by malformed
key-form resolution, not by matching values.

*After* the fix, every degraded payload raises a clear `ValueError` naming the
`_meta.derived.sheets['matrix'].enrich_lookup` path and the invalid/missing
member, under both policies; the valid asymmetric control still detects the
edit (warn: one finding; fail: raises).

== 4. Presence-based form-selection rule

`_validated_mismatch_keys` now selects the join-key form from mapping-member
*presence*, not from value truthiness:

[source,python]
----
has_on         = "on" in spec
has_source_key = "source_key" in spec
has_lookup_key = "lookup_key" in spec
----

Selection and validation:

* `has_on and (has_source_key or has_lookup_key)` → *mixed* form → `ValueError`
  (regardless of whether any value is `null`);
* `has_on` → *symmetric* form → validate `spec.get("on")` via
  `_validated_symmetric_on` (which rejects `None`, non-list, empty, blank, and
  non-string elements);
* `has_source_key or has_lookup_key` → *asymmetric* form → *both* members must
  be present (else `ValueError` "requires both …"), then each is validated via
  `_validated_single_key` (which rejects `None`, blank, and non-string);
* otherwise → a present record with *no join-key form* → `ValueError`.

Absent/present/null are now distinct: an absent member no longer masquerades as
a chosen form, a present `null` member is validated (and rejected) by its
selected form, and a present record with no key form is malformed rather than a
silent no-op.

== 5. Accepted symmetric shape

Only a present `on` member whose value is a non-empty list/tuple of non-empty
strings is accepted, e.g. `{"on": ["id"]}` or `{"on": ["k1", "k2"]}`. Rejected:
`{"on": null}`, `{"on": "id"}`, `{"on": 123}`, `{"on": {}}`, `{"on": []}`,
`{"on": [""]}`, `{"on": [null]}`. `payload_keys == lookup_keys` for symmetric
records; the writer's multi-key shape is preserved.

== 6. Accepted asymmetric shape

Presence of either asymmetric member selects the asymmetric form; both must be
present and each a single non-empty string, e.g.
`{"source_key":"story_id","lookup_key":"id"}`. Rejected: `{"source_key": null}`,
`{"lookup_key": null}`, `{"source_key": null,"lookup_key": null}`,
`{"source_key":"story_id"}`, `{"lookup_key":"id"}`,
`{"source_key":[],"lookup_key":"id"}`, `{"source_key":"story_id","lookup_key":{}}`.

== 7. Mixed / no-form rejection

Any record containing `on` together with either asymmetric member is rejected as
mixed, including `{"on": null,"source_key":"story_id"}`,
`{"on":["story_id"],"lookup_key": null}`, and
`{"on": null,"source_key": null,"lookup_key": null}`. A present helper-bearing
`enrich_lookup` record with none of `on`/`source_key`/`lookup_key` (e.g.
`{"lookup":"stories","helper_columns":["title"]}`) is malformed for a
value-checking policy and raises. This is distinct from the *absence of the
entire* `enrich_lookup` record: the caller only routes a *present* record into
`_check_enrich_lookup_values`, so a missing record retains its established safe
no-op.

== 8. Warn/fail behavior

* Malformed provenance *shape* (mixed, no-form, `null`/blank/wrong-typed key
  values, partial pair, malformed `on`) raises a clear `ValueError` under both
  `warn_on_mismatch` and `fail_on_mismatch` — a broken contract, not a data
  mismatch.
* A missing required payload/lookup key column on a well-formed record continues
  to use the existing severity-appropriate `unverifiable_enrich_lookup` finding
  (warn: warning; fail: failure → raise).
* Valid-but-unmatched reference values retain their existing skip behavior.
* `policy: drop` never calls key-form validation and stays value-blind.

== 9. Caller-state and provenance safety

The validation raises inside `_check_enrich_lookup_values`, which runs in
`enforce_derived_column_policy_frame` *before* the drop columns are computed and
before `apply_derived_column_policy` builds any output. On a malformed-provenance
raise: the source DataFrame, lookup DataFrame, and caller `frames` mapping are
unchanged; the helper column remains present in caller data; the provenance
record remains present in caller metadata; and no findings/output mutation is
committed. This was verified by probe and by a tracked test asserting frame
equality and provenance identity after the raise.

== 10. Value-blind drop preservation

`enforce_derived_column_policy_frame` invokes `_check_enrich_lookup_values` only
for `warn_on_mismatch`/`fail_on_mismatch`. For `policy: drop` the key-form
validator is never reached, so every malformed shape (`{}`, `{"on": null}`,
`{"source_key": null}`, `{"source_key": null,"lookup_key": null}`) drops the
helper by identity, emits no findings frame, and never raises — verified by a
parameterized tracked test.

== 11. Minor duplicate-test closure (R003-MIN-001)

No runtime change. The common `_check_duplicate_helper_fields` guard runs before
value-mode or placement branching, so it is mode- and position-independent.
Parameterized formula-mode duplicate-helper tests were added to make the tracked
matrix match reality: `symmetric formula/after_data`, `symmetric
formula/before_key`, `asymmetric formula/after_data`, and `asymmetric
formula/before_key`, each asserting a clear `Duplicate helper field` domain
failure with no output/provenance produced. Combined with the pre-existing
values-mode duplicate tests (default/`before_key`, inline and policy-derived,
symmetric and asymmetric) and the helper-plus-sort validity test, the tracked
duplicate-helper matrix is now truthful and complete.

== 13. Runtime-complexity assessment

The runtime diff is confined to one function, `_validated_mismatch_keys`:

* three `"<member>" in spec` presence checks replace three
  `spec.get(...) is not None` value tests;
* the asymmetric "both present" check is computed from presence flags;
* the trailing `return [], []` no-op is replaced by a single explicit `raise`
  for a present record with no key form.

No new abstraction, class, module, or public API was introduced; the two
existing validation helpers (`_validated_symmetric_on`, `_validated_single_key`)
are unchanged. Branch structure is essentially the same shape (mixed →
symmetric → asymmetric → no-form); cyclomatic branching and helper count did not
materially increase. The change is proportionate to the finding: it corrects
form *detection* to use presence, which is the minimal root-cause fix, and does
not harden unrelated code or introduce a general metadata-validation framework.
