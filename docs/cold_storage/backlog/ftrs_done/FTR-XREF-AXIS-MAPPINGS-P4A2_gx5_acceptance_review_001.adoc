== Scope fidelity

GX-5 changes only the public adoption gates:

. `configure_workbook_view` (`domain/workbook_views.py`): a selected
  `GroupedMatrix` is admitted for inclusion, declaration order, and visible-sheet
  rename; grouped column-targeted options are rejected.
. `select_render_frames` (`rendering/frame_selection.py`): a `GroupedMatrix` is
  admitted by identity; formula sheet-name rewriting stays DataFrame-only.
. Router savers `save_xlsx` / `save_ods` (`io_backends/.../*_backend.py`):
  preserve a `GroupedMatrix` through to the render path.
. Workbook View readback `_normalize_visible_sheet_names` /
  `apply_workbook_view_sheet_mappings` (`domain/workbook_views.py`): counts a
  `core.ExactTable` as a projected visible sheet during reverse mapping.

A fifth runtime module -- `io_backends/spreadsheet_contract.py` -- gained the
bounded `is_render_carrier` predicate; this is the user-approved deviation
assessed below, not a new capability.

Independent confirmation of "no new semantics": `git diff b33d5fd..a936129`
touches none of `grouped_xref`, `xref_crosstable`, `xref_axis_mapping`,
`GroupedHeader`, `ExactTable`, the composer, `WorkbookIR`, render flow/passes,
the XLSX/ODS parsers or renderers, the pipeline runtime registry, persistence, or
schema maintenance. No new callable, step, parameter, metadata root, carrier
class, or registry entry was added. The protected surfaces named in the
confirmation and self-review remain byte-unchanged in runtime code.

== Architecture and facade assessment

The confirmation expected the carrier decision inside the two backend savers via
a direct `GroupedMatrix` import. The active guard
`tests/architecture/spreadsheet_contract/test_adapter_contract_boundary_guards.py::
test_backend_entrypoints_delegate_generic_orchestration_to_spreadsheet_contract`
forbids `xlsx_backend.py` / `ods_backend.py` from importing
`spreadsheet_handling.domain.*`. The implementation instead added
`io_backends/spreadsheet_contract.py::is_render_carrier`, and both savers
delegate to it. Independently verified:

* *Dependency direction preserved.* Both savers import only
  `spreadsheet_handling.io_backends.spreadsheet_contract`
  (`build_spreadsheet_render_plan`, `is_render_carrier`, `read_spreadsheet_frames`)
  and no `domain`/`rendering.*`/`pipeline` module. The adapter-entrypoint ->
  neutral-facade direction holds; the facade guard
  `test_spreadsheet_contract_facade_stays_backend_neutral` still passes (the
  facade imports `rendering.workbook_projection` and `rendering.plan` and no
  `openpyxl`/`odf`/backend module). Domain import from the facade is permitted by
  that guard.
* *No import cycle.* The `grouped_xref` package imports neither `rendering` nor
  `io_backends` nor the contract facade (grep confirmed); a fresh interpreter
  imports the facade and both savers cleanly.
* *No weakened or bypassed guard.* No architecture test was modified. The full
  `tests/architecture` tree passes.
* *Recognizes exactly `pd.DataFrame` and `GroupedMatrix`.* Probe: `is_render_carrier`
  returns `True` for `DataFrame` and `GroupedMatrix`; `False` for `ExactTable`,
  `str`, and a bare `object`.
* *Not a generic carrier registry or protocol.* It is a two-type `isinstance`
  predicate with no registration, dispatch table, or `Protocol` surface.
* *Existing coercion preserved for other values.* In both savers, reserved keys
  pass through first; `DataFrame`/`GroupedMatrix` pass through by identity; every
  other non-reserved value keeps `_ensure_dataframe(...)` coercion.

The deviation is correct and is accepted. It is not a reason to reject: the
resulting dependency direction and behavior are both correct.

== Forward Workbook View behavior

Verified through `domain/workbook_views.py` and probes:

* accepts both `DataFrame` and `GroupedMatrix` selected frames;
* preserves a grouped carrier by object identity (`out["grouped"] is gm`);
* applies selection, declaration order, and visible-sheet rename; excludes
  undeclared frames;
* raises `KeyError` for a missing selected frame; raises `ValueError` for
  duplicate visible sheet names -- before any publication;
* leaves ordinary DataFrame behavior unchanged (mixed-order identity preserved;
  DataFrame `options` still produce the sheet-options blob).

For a grouped sheet, non-empty `helper_columns`, `editable_columns`, column
`protection`, and a non-empty generic `options` map are each rejected with
`ValueError ("... unsupported in GX-5 ...")` before publication, because GX-5 has
no tuple-aware grouped column targeting. Empty/no-op option values retain
compatibility: an empty `options={}` is a no-op (grouped carrier preserved, no
sheet-options blob), and `_merge_sheet_options` treats grouped and DataFrame
sheets identically for empty inputs, so no ambiguous leaf-only targeting is
produced.

`build_spreadsheet_render_plan` render path.

== ExactTable reverse mapping

`_normalize_visible_sheet_names` now counts exactly the two generic projected
read carriers -- `pd.DataFrame` and `core.ExactTable` -- as visible sheets; a
probe confirmed a mapped `ExactTable` is re-keyed unchanged from its physical
visible sheet name to the logical frame name (`out["grouped"] is exact`).
Workbook View code interprets no grouped-XRef descriptor and derives no header
depth. `exact_header_depths` remains solely an input backend option
(`input.options.extra.exact_header_depths`), keyed by the physical visible sheet
name; the integration evidence supplies it that way. Grouped-XRef configuration
is never interpreted in Workbook View code.

== Public XLSX/ODS adoption evidence

`tests/integration/pipeline/test_gx5_grouped_xref_public_roundtrip.py` was
reviewed critically. It uses public configuration construction
(`build_steps_from_config` + `run_pipeline`), `contract_grouped_xref`,
`configure_workbook_view`, the router-facing `save_xlsx`/`save_ods` and
`load_xlsx`/`load_ods` seams, real XLSX and ODS files, `exact_header_depths`
keyed by the renamed physical sheet, `apply_workbook_view_sheet_mappings`,
`reconstruct_grouped_matrix`, and `expand_grouped_xref`. It never calls the
composer directly.

The evidence proves, for both backends: unchanged canonical relation identity;
one edited boundary value returning to canonical form; repeated upper labels
(`"Kredit"` twice); a literal `" / "` leaf-label component; a renamed physical
sheet (visible name differs from the logical frame); XLSX/ODS semantic parity
(both restore identical relations); and carrier reachability through the router
path (`isinstance(forward[frame], GroupedMatrix)` before the router saver
persists it).

Editing the loaded `ExactTable` (rebuilding it with one dynamic data cell
changed) is an acceptable simulation of a spreadsheet-boundary edit: the value
was read back from a real persisted file and re-enters through the same
reconstruction chain a spreadsheet edit would. The accepted contract does not
require a further write/read cycle to prove a boundary edit survives, so none is
demanded.

== Failure atomicity

`test_gx5_pre_render_grouped_view_failure_is_atomic` and a unit twin confirm a
pre-render validation failure (duplicate visible sheet name reached in

content asserted). One backend-specific atomicity probe (XLSX) is sufficient
because the failure occurs before any backend-specific rendering; the ODS path
shares the same pre-render selection gate.
