[cols="2,3,4",options="header"]
|===
| Option | Path through the classifier | Disposition

| `matrix`, `output`, `source_frame`, `value`, `drop_source`, `base_relation`

  non-empty/`bool`-typed, and stored in `ExpandGroupedCertificate`

  or a `str`/`list`/`tuple` of exact `str`, frozen into an owned tuple by
  `snapshot_string_sequence`

  caller-owned custom iterable is rejected `Uncertified`, not silently
  passed through

| `order_policy`

  tests/config
| Closed scalar/default only
|===

The report's 6/7/1 categorization matches the code exactly (verified by
direct reading, not by trusting the summary).

`_unsupported_grouped_option` iterates every key *present* in `call.kwargs`
(already filtered to `_EXPAND_KNOWN_KEYS` by `only_known_keys`), not only
the six keys the certificate stores -- so a by-reference leaf on an
*unused* option (e.g. `order_columns`, `xref_config_id`) is rejected exactly
as strictly as one that feeds the certificate. This mirrors the precedent
`_classify_reconstruct` already established and is stronger than the
acceptance criterion strictly requires.

*Confirmed*: no currently `CERTIFIED` `expand_grouped_xref` configuration
can retain a caller-mutable by-reference value, whether or not that value's
key is one the certificate itself stores.
