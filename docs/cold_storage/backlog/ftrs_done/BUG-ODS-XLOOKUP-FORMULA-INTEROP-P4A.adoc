===== BUG-ODS-XLOOKUP-FORMULA-INTEROP-P4A -- Generated ODS XLOOKUP helpers open as `#NAME?` in LibreOffice

*Status:* Fixed
*Priority:* P4A
*Area:* ODS formula-mode FK helpers / `LookupFormulaSpec` ODS translation / LibreOffice interoperability
*Release relevance:* Affects only `helper_value_mode: formula` on the ODS
backend. XLSX formula mode and `helper_value_mode: values` on either backend
are unaffected.

====== Summary

ODS workbooks generated with FK helpers in formula mode
(`step: add_fk_helpers`, `defaults: {helper_value_mode: formula}`) contain
lookup formulas that are structurally valid but display `#NAME?` when the
workbook is first opened in LibreOffice Calc, with LibreOffice reporting
"Error: Invalid name". Opening the affected cell's Function Wizard and
confirming with `OK`, without changing any argument, makes that individual
cell work and LibreOffice then displays the formula in normalized uppercase.
The generated workbook must render working helper formulas immediately;
users must not have to confirm every formula cell manually.
`helper_value_mode: values` remains a functional fallback but does not update
helper values live while the workbook is edited, so it is not an equivalent
replacement for formula mode.

====== Reproduction

Environment: generated Dino-Insel ODS workbook; LibreOffice Calc 25.x; FK
helper columns generated from `LookupFormulaSpec`; source and lookup
references are present and valid.

. Generate the ODS workbook with `helper_value_mode: formula`.
. Open the workbook in LibreOffice Calc and navigate to the `Places` sheet.
. Helper cells such as `_regions_name` and `_regions_kind` show `#NAME?`.
. Select an affected cell; the formula bar shows, e.g.:
+
[source,text]
----
=xlookup(C10,Regions.A2:Regions.A12,Regions.B2:Regions.B12,"")
----
. Open the Function Wizard (`fx`). LibreOffice recognizes `XLOOKUP`, accepts
  all arguments, and the wizard preview shows the correct lookup result.
. Confirm with `OK` without editing any argument. The cell now evaluates
  correctly and the formula bar subsequently shows the function name in
  normalized uppercase.

This isolates the failure to formula serialization/import interpretation:
the lookup key, ranges, and workbook data are all valid, and LibreOffice
supports `XLOOKUP` -- the defect is not in FK resolution or lookup data.

====== Verified Facts vs. Hypothesis

Verified (maintainer-observed):

* formula-mode FK helpers in generated ODS files initially show `#NAME?`;
* LibreOffice reports an invalid name;
* the formula arguments and ranges are correct;
* LibreOffice 25.x supports `XLOOKUP`;
* confirming the unedited formula through the Function Wizard makes that
  cell work, and LibreOffice then displays the function name in normalized
  uppercase;
* `helper_value_mode: values` works as a fallback but loses live updates.

Hypothesis, not yet accepted implementation truth: the ODS renderer emits
the function in an unqualified form, approximately `of:=XLOOKUP(...)`.
`XLOOKUP` is not part of the standard OpenFormula vocabulary; LibreOffice may
require its extension-qualified name, approximately
`of:=COM.MICROSOFT.XLOOKUP(...)`. This is consistent with the observed
symptom (unqualified name treated as unknown -> `#NAME?`; Function Wizard
confirmation reparses it as LibreOffice's supported function -> evaluates),
but it is unproven until Phase 2 inspects the actual `table:formula` value in
a generated `content.xml` and confirms which representation LibreOffice
evaluates without manual intervention.

Do not treat this hypothesis as already proven, and do not treat the
uppercase/lowercase display change alone as the root cause -- the case
change may simply be a visible side effect of LibreOffice normalizing a
successfully recognized function. Any fix must not assume or promise
support against an unpublished future ODF version.

====== Resolution

*Verified root cause:* the ODS renderer's `_ods_lookup_formula`
(`src/spreadsheet_handling/io_backends/ods/odf_renderer.py`) emitted the
unqualified `of:=XLOOKUP(...)`. `XLOOKUP` is not part of the standard
OpenFormula vocabulary; LibreOffice 25.2.3.2 only recognizes it under its
Microsoft-extension-qualified identifier, `of:=COM.MICROSOFT.XLOOKUP(...)`.
The hypothesis in this BUG's original "Root-Cause Hypothesis" section is
confirmed as the complete cause -- no cached-value framework was needed, and
the uppercase display normalization was, as suspected, a side effect of
LibreOffice recognizing the function, not the defect itself.

*Discarded hypotheses:* none of the alternative explanations considered
during investigation (a caching requirement, a lowercase/uppercase parsing
defect, a range/argument error) held up; the missing `COM.MICROSOFT.`
qualification was sufficient by itself.

*Verified via a real headless LibreOffice 25.2.3.2 process* over the UNO
bridge (`tests/utils/libreoffice_uno_probe.py`, exercised standalone before
any production change and again by the opt-in
`tests/integration/io_backends/ods/test_ods_libreoffice_interop.py`), not
only by XML inspection:

* pre-fix minimal reproduction formula:
+
[source,text]
----
of:=XLOOKUP([.B2];[Customers.A2:Customers.A3];[Customers.B2:Customers.B3];"")
----
  opened with `cell.getString() == "#NAME?"` and `cell.getError() == 525`.
* post-fix formula:
+
[source,text]
----
of:=COM.MICROSOFT.XLOOKUP([.B2];[Customers.A2:Customers.A3];[Customers.B2:Customers.B3];"")
----
  opened with `cell.getString() == "Ada"` and `cell.getError() == 0` on a
  cold `calculateAll()` -- no cached result was involved or required.
* editing the source FK cell to an unresolvable key recalculated the helper
  to the configured missing result (`""`) with `getError() == 0`, not an
  invalid-name error; editing it to a different valid key recalculated the
  helper live to the new lookup value.
* the real Worldbuilding `Places`/`Regions` export (`make export-stories-ods`)
  produced 48 formula-mode helper cells, all using
  `of:=COM.MICROSOFT.XLOOKUP(...)`, zero using the unqualified form; 24
  checked helper rows showed no `#NAME?`/error, and editing one `region_id`
  live-recalculated both `_regions_name` and `_regions_kind`.

*Fix:* `_ods_lookup_formula` now emits `of:=COM.MICROSOFT.XLOOKUP(...)`
instead of `of:=XLOOKUP(...)`; no other renderer, parser, or domain code
changed. `LookupFormulaSpec` remains backend-neutral; the qualification is
adapter-local to the ODS renderer.
