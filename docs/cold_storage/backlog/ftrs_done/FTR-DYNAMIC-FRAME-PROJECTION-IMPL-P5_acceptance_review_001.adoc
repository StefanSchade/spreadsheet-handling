== Scope of this review

This is a fresh, independent lifecycle review of the *implementation slice*
`FTR-DYNAMIC-FRAME-PROJECTION-IMPL-P5`. The prior artifacts
(`_impl_slice_assessment.adoc`, `_review.adoc`) are treated as evidence, not as
conclusions to repeat. The question is narrow: is the delivered implementation
complete against its own accepted contract, are the previously open findings
closed by committed evidence, and can the FTR be marked `Done` and archived.

The later possibility of encapsulating the public `project_by_role` step inside
normal XRef-crosstable forward/inverse capability is *out of scope* here. It is
not residual scope of this implementation FTR: the FTR's accepted contract does
not name it (the *Non-Goals* explicitly exclude redesigning `contract_xref` /
`expand_xref`). A completed FTR is not held open because a later refactor may
alter its surface.

== Lifecycle questions (answered independently)

. *What exact accepted scope did the FTR own?* Add a backend-neutral
  `project_by_role` pipeline step (in-place `frame:` transform, required
  `direction: outbound | inbound`, optional `helper_columns` / `key_columns` /
  `role_order`); introduce a shared column-role resolver as the single
  role-detection path; register the step; add the public YAML gate entry;
  add release notes; add resolver / outbound / inbound / validation unit tests,
  a roundtrip integration test, migration-parity tests, and a shared-resolver
  architecture guard; migrate all 10 worldbuilding projection call sites
  (5 outbound + 5 inbound) via upstream-rename without adding `source:` /
  `output:`. Keep the two projection plugins importable for one release cycle.

. *What runtime and public surfaces were delivered?*
+
--
* `src/spreadsheet_handling/domain/column_roles/` — shared resolver
  (`resolve_column_roles`).
* `src/spreadsheet_handling/domain/transformations/project_by_role.py` — the
  Frame-layer `(Frames) -> Frames` step.
* `registries/pipeline_step_registry.json` — `project_by_role` registered, with
  an inverse-step entry.
* `docs/ai_info/interfaces_and_gates.adoc` — gated YAML surface entry.
* `docs/release_notes/release_notes.adoc` — entry under the active
  `unknown -- planned` section.
* Worldbuilding: both dino_insel pipeline YAMLs migrated at all 10 call sites;
  `plugins/story_cast_views.py` plugins retained with one-line comments (in the
  worldbuilding repo; committed there separately at WB HEAD `83dc2bb` lineage).
--

. *What findings were previously open?* Exactly one: implementation-review
  *Medium-1* — the required migration-parity test fixture (covering all 10
  surfaces, frame-name parity, outbound row-order parity, empty-cell behavior,
  and resolver-input availability) was reported missing at review time
  (`_review.adoc`, 2026-06-08). No Blocking / High implementation finding was
  open. (The `_impl_slice_assessment.adoc` planning findings High-1 and
  Medium-1 were already closed Green before implementation.)

. *Which commit or test closed each required finding?* Feature commit `4bedcf5`
  (2026-06-08) bundled the implementation, the tests, and the (already-written,
  now stale) Yellow review. That same commit added
  `tests/integration/pipeline/test_project_by_role_migration_parity.py`, which
  is the fixture Medium-1 required. The review text predates the test added
  alongside it; the finding is closed by committed evidence, not by narrative.

. *Does the row-order migration-parity fixture test the required behavior
  rather than merely execute the step?* Yes.
  `test_outbound_row_order_parity_per_surface` builds a fixture pre-sorted by
  `story_id` (mirroring the deterministic upstream `contract_xref
  dense_axes.rows_from` order), asserts the fixture is in that order, runs
  `project_by_role(outbound)`, and asserts the emitted `story_id` order is
  unchanged. This is a genuine behavioral assertion that the removed plugin-side
  `sort_by=("story_id",)` is redundant for ordered input — not a smoke run.

. *Are all ten documented Worldbuilding migration surfaces represented?* Yes.
  `OUTBOUND_SURFACES` enumerates the five `*_matrix_view` frames and
  `INBOUND_SURFACES` reuses them; the column-shape, row-order, and
  resolver-availability tests are parametrized over all five outbound and five
  inbound surfaces, and the empty-cell parity tests cover the
  `expand_compact_multiaxis` group surface plus the four `expand_xref`
  story-cast surfaces.

. *Are caller mutation, metadata availability, empty cells, and row ordering
  covered?*
+
--
* *Caller mutation:* the step returns a new `dict(frames)` and a copied frame
  (`df.loc[:, ordered].copy()`), so the caller's frames dict and DataFrame are
  not mutated in place. This is caller-safe. There is no *dedicated*
  non-mutation assertion; recorded as a watch-only note, not a blocker (the
  FTR acceptance criteria did not require one).
* *Metadata availability:*
  `test_resolver_meta_sources_supply_roles_without_explicit_overrides` exercises
  role resolution from `_meta` sources; the resolver-availability tests confirm
  explicit overrides are honored where scattered sources are absent.
* *Empty cells:* the two `drop_empty: true` end-to-end parity tests assert
  NaN-vs-`""` equivalence through both downstream consumers.
* *Row ordering:* covered as in question 5.
--

. *Does any Blocking or Important finding retain implementation scope?* No.
  Medium-1 was the only open finding and is closed. No Blocking / High finding
  remains. The single watch-only caller-mutation note carries no implementation
  obligation.

. *Is the FTR accepted, merely implemented, or still incomplete?* *Accepted.*
  It was previously "implemented but review-marked Yellow" solely because of the
  Medium-1 test gap; that gap is closed by committed tests that pass on the
  current baseline.

. *Can it be marked Done and archived without prejudging the new encapsulation
  hypothesis?* Yes. Closure records that `project_by_role` shipped and is
  accepted as its own step. Whether that step should later be encapsulated
  inside XRef-crosstable wrappers is a separate assessment
  (`FTR-XREF-CROSSTABLE-PROJECTION-ENCAPSULATION-P4A2`) and does not depend on
  keeping this implementation FTR open.
