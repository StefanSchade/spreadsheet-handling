== Findings

=== Important I-3R -- colon-style `step:` resolution still invokes ingress

`build_steps_from_config` first calls
`pipeline.registry.resolve_registration(step_id)`. For any `step_id` containing
`:`, that resolver imports the named module, fetches the named object as a
factory, and returns it as a `StepRegistration`. This path is distinct from
`step: plugin` and therefore bypasses `_ensure_plugin_addressable`.

Direct probes using each of the package export, coordinator, and rule path:

[source,yaml]
----
- step: spreadsheet_handling.domain.ingress:run_domain_ingress
  frames:
    _meta:
      legend_blocks: null
----

and the corresponding coordinator/rule paths all succeeded during config
construction and returned `[{"_meta": {"legend_blocks": {}}}]`. The result is
not a valid `BoundStep`, so a later pipeline execution would fail; nevertheless
the maintained public colon-factory configuration surface has already invoked
the framework-owned macro callable rather than rejecting it. The architecture
guard tests only short candidate names and `step: plugin`, so it misses this
route.

*Risk:* the FTR and technical model promise that ingress cannot be built or
invoked from YAML. Config construction can currently execute this and any
future ordered ingress rule against author-supplied literal Frames, making the
ownership boundary and correction review's complete-namespace claim false.
Green pipeline tests do not exercise this route.

*Recommended action:* apply the same package-ownership rejection at the common
dotted-resolution boundary used by colon-style `step:` factories, before
import/invocation, and guard package export, coordinator, and rule paths there.
Preserve legitimate external and internal dotted factories; do not turn this
into a general domain allow/deny framework.

== Original contract regression assessment

Apart from I-3R, the original slice remains coherent:

* list and mapping authoring converge to one insertion-ordered mapping;
  mapping/block field order and values are retained except for deliberate
  `resolved` pruning;
* `name`, then `id`, then one-based positional identity is preserved, and
  malformed members, duplicate identities (including positional collisions),
  and unsupported roots fail deterministically;
* empty list and explicit `null` become empty mappings, absent root is a
  no-op, and ingress does not apply Legend Entry value policy;
* orchestrator load, `bootstrap_meta`, and `apply_overrides` are the three
  maintained ingress points; normal CLI/runner/schema-maintenance application
  paths converge through the orchestrator;
* shared domain, ValidationPass, and composer readers now consume mapping form
  only. Direct low-level callers and arbitrary plugins retain the documented
  canonical-Frames precondition; persistence does not add a list-form bypass;
* stale `resolved` is pruned at ingress and persistence. The composer adds
  fresh coordinates only to its local block clones and does not mutate caller
  metadata;
* XLSX and ODS parsers consume carrier-local coordinates for table
  classification, and shared workbook projection strips them before canonical
  readback;
* a classified own-sheet Legend is excluded from payload Frames, while a
  colocated Legend leaves the first data table unchanged;
* the registry names canonical and carrier-local producers and the complete
  reviewed consumer/projector surface. Ingress remains absent from the normal
  runtime and descriptive registries;
* the shape slice did not absorb token, label, group, duplicate-entry,
  unknown-reference, or unhashable-value decisions owned by
  `FTR-LEGEND-BLOCKS-ENTRY-CONTRACT-P5`.

The overlap/tampered-coordinate case remains watch-only: a carrier hint at a
payload anchor can classify that already-overwritten surface as a Legend. This
is not a regression introduced by this slice.
