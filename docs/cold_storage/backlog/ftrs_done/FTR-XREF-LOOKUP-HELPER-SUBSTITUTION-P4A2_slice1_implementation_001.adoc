== 2. Exact previous symmetric contract

`enrich_lookup(frames, *, source, lookup, output, key=None, keys=None,
on=None, helpers=None, order=None, missing=None, helper_value_mode=None)`,
registered as the public step `add_lookup_helpers`
(`spreadsheet_handling.domain.transformations.enrich_lookup:enrich_lookup`).

* The join key(s) had to exist under the *same name* in both source and lookup.
  Forms `key` (single), `keys` (list), legacy quoted `"on"` (string/list), and a
  helper-policy `key` were mutually exclusive; exactly one had to resolve.
* The single resolved list `join_keys` drove: source-key validation, lookup-key
  validation, duplicate-lookup detection, the `merge(on=join_keys, how="left")`,
  `missing: fail` unmatched-row detection, `before_key` anchoring, and
  provenance.
* Provenance (transient): `_meta.derived.sheets.<output>.enrich_lookup =
  {"lookup": <lookup>, "on": [<keys>], "helper_columns": [<fields>]}`.
* `helper_position` in `{after_data (default), before_key}`; `missing` in
  `{fail (default), empty}`; `helper_value_mode` in `{values (default),
  formula}`.
* Output frame is a new frame written to `frames[output]`; source and lookup
  frames and the caller `frames` mapping are not mutated (a shallow copy is
  returned).

== 3. Final public API

Two new optional, mutually-exclusive parameters:

`enrich_lookup(frames, *, source, lookup, output, key=None, keys=None,
on=None, source_key=None, lookup_key=None, helpers=None, order=None,
missing=None, helper_value_mode=None)`

=== Legacy symmetric mode (unchanged)

[source,yaml]
----
key: id           # source key = id, lookup key = id
----

=== New asymmetric mode (opt-in)

[source,yaml]
----
source_key: story_id   # source key = story_id
lookup_key: id         # lookup key = id
----

Single key on each side (this is *not* a multi-column join). Only the
source-side key appears in the output; the lookup-side key never leaks.

== 4. Validation matrix

[cols="4,1,4"]
|===
| Parameter combination | Verdict | Reason / error

| `key` alone (or `keys`, quoted `"on"`, or policy `key`)
| accept
| Symmetric mode, unchanged.

| `source_key` + `lookup_key`
| accept
| Asymmetric mode.

| `key` (or `keys`/`on`) together with `source_key` and/or `lookup_key`
| reject `ValueError`
| "...either the symmetric `key`/`keys`/quoted `"on"` form or the asymmetric
  `source_key`+`lookup_key` pair, not both..."

| `source_key` only
| reject `ValueError`
| "Asymmetric ... require both `source_key` and `lookup_key`; missing
  ['lookup_key']"

| `lookup_key` only
| reject `ValueError`
| "...missing ['source_key']"

| blank / whitespace `source_key` or `lookup_key`
| reject `ValueError`
| "...must be a non-empty key name"

| non-string `source_key` or `lookup_key`
| reject `TypeError`
| "...must be a single string key name"

| neither symmetric nor asymmetric nor policy key
| reject `ValueError`
| "No join key configured for lookup ..." (unchanged)
|===

There is no precedence between the modes and no partial asymmetric fallback. The
helper-policy `key` participates only in symmetric resolution; asymmetric mode is
fully explicit and does not consult it.

== 5. Internal resolved-key design

`_resolve_join_keys(...)` now returns a `(source_keys, lookup_keys)` tuple of
lists (single element each in asymmetric mode; equal lists in symmetric mode).
All downstream logic consumes exactly that pair — no compatibility branching is
scattered through join, ordering, diagnostics, or provenance:

* source-key validation iterates `source_keys` against the source frame;
* lookup-key validation and duplicate detection iterate `lookup_keys` against
  the lookup frame;
* `_build_helper_projection` selects `lookup_keys + fields` from the lookup
  frame, then *renames* `lookup_keys -> source_keys` (a no-op in symmetric mode),
  so the merge is always `merge(on=source_keys, how="left")` and the lookup-side
  key name is dropped before it can enter the output;
* conflict detection, unmatched-row detection, and `before_key` anchoring all use
  `source_keys` (the names present in the output frame);
* `_build_formula_enrichment` receives `source_keys[0]`/`lookup_keys[0]` and
  emits a `LookupFormulaSpec` whose `lookup_key_column` is the lookup-side key.

== 6. Source/lookup cardinality behavior

Preserved exactly:

* missing source key -> `KeyError "Join key '<source_key>' not found in source ..."`;
* missing lookup key -> `KeyError "Join key '<lookup_key>' not found in lookup ..."`;
* duplicate lookup values (on `lookup_keys`) -> `ValueError "...duplicate keys..."`;
* `missing: fail` with unmatched source rows -> `ValueError "...no match in lookup..."`;
* `missing: empty` fills unmatched helper cells with `""`;
* helper field already present in source -> `ValueError "...already exist in source..."`.

Uniqueness and cardinality checks are not weakened; asymmetric merges are
left-joins on a unique lookup key, identical in strength to the symmetric path.

== 7. Ordering behavior

`helper_position: before_key` anchors on the *source-side* key (the key present
in the output). For the Worldbuilding-shaped case
(`source: [story_id, dynamic_1, dynamic_2]`, `lookup: [id, title]`,
`helper: title`) the output is exactly `[title, story_id, dynamic_1,
dynamic_2]`. `after_data` (default) yields `[story_id, dynamic_1, dynamic_2,
title]`. Dynamic trailing matrix columns keep their input order. Verified for
two differing dynamic column sets (`[Alpha, Beta]` and `[Beta, Gamma, Delta]`).

== 8. Provenance before/after

* *Symmetric mode — unchanged*: `{"lookup", "on": [<keys>], "helper_columns"}`.
  Regression-asserted byte-identical.
* *Asymmetric mode — additive*: `{"lookup", "source_key": <s>, "lookup_key":
  <l>, "helper_columns"}`. No misleading synthetic common `on` key is written.
  The distinction (source key, lookup key, lookup frame, helper columns) is fully
  recoverable.

The mode is derived from `source_keys == lookup_keys`, so asymmetric parameters
that happen to name the same key on both sides record the symmetric (accurate)
shape.

Persistence filtering is unchanged. The transient `derived` channel is stripped
at the workbook boundary exactly as before (Slice 2 concern). `apply_derived_column_policy`
`drop` reads only `helper_columns`, so it is unaffected. Its mismatch-policy
value-check (`warn_on_mismatch` / `fail_on_mismatch`) reads `on`; for an
asymmetric spec `on` is absent, so that path is a safe no-op — asymmetric
value-checking is a Slice 2 handoff item (see section 17).

== 9. Mutation / copy behavior

Preserved and explicitly tested for the asymmetric path:

* source DataFrame unchanged (asserted via `assert_frame_equal`);
* lookup DataFrame unchanged;
* caller `frames` mapping unchanged (`enrich_lookup` returns a new dict; the
  output frame is not written into the caller's mapping);
* the returned output frame is a new frame (merge result);
* `_meta` is updated on a shallow-copied meta dict; caller-owned nested data is
  not mutated beyond the established contract.

== 15. Known non-goals (Slice 1)

* No multi-column asymmetric join; asymmetric mode is single-key each side.
* No column-renaming feature, frame-alias feature, or broad lookup DSL.
* No wrapper around `join_frames`; no general join redesign.
* No worldbuilding-specific special case; the capability is generic.
* No inbound binding, no `project_by_role` change/removal, no worldbuilding
  migration, no Project Memory update.
* No change to `resolve_column_roles`, `apply_derived_column_policy` semantics
  (drop unchanged; asymmetric value-check deferred), persistence filtering, or
  any protected surface.

== 16. Residual risks

* Asymmetric mismatch-policy value-checking (`warn_on_mismatch` /
  `fail_on_mismatch` in `apply_derived_column_policy`) is a safe no-op for
  asymmetric specs because it keys on the absent `on` field. This is intended for
  Slice 1 (drop mode, the worldbuilding path, is unaffected) but must be
  addressed if a later slice value-checks asymmetric helpers.
* End-to-end XLSX/ODS parity for the *asymmetric* path was not exercised across
  the persistence boundary in Slice 1 (Slice 1 does not cross that boundary). The
  existing symmetric XLSX+ODS roundtrip test passes unchanged; asymmetric
  backend parity remains a parent-FTR / later-slice acceptance criterion
  (per FTR section 21).
