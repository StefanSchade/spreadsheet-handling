==== 2. Independent authority reconstruction

The governing chain is:

. The robustness ADR requires deliberate, proportionate validation at owned
  boundaries but explicitly does not promise a sandbox against same-process
  Python.
. The runtime/policy ADR fixes the trusted-operator precondition, keeps payload
  authorship and description authorship independent, places policy with the
  operator, combines restrictions per kind, requires rejection before
  capability activation, and keeps sink capability separate from payload
  shape.
. The validation/writer ADR puts Domain semantics and validity in the Domain;
  persistence writers translate already-decided intent and remain dumb.
. The visible-cell ADR and accepted Phase-D Technical Model establish the six
  scalar categories, exact carrier precedence, and classification without
  normalization. `FormulaSpec` is explicitly framework-authored output Intent,
  not a payload scalar.
. Phase E must establish a mandatory, documented boundary before ordinary
  Domain work, but may not absorb family invariants, reconstruction,
  persistence projection, or sink interpretation.

Payload authority and payload conformance are different. The ADR asks who
authored the payload; Phase E asks whether the current payload state conforms
to the Domain's bounded grammar. A trusted author does not make an unsupported
object part of the global Domain grammar. Conversely, applying the same global
grammar to both authority classes does not erase the authority dimension:
origin still selects the operator-owned policy context and the four
payload/description combinations remain representable.

The intended layering is understandable and mostly well separated:

        |

        |                         (trusted-description precondition before E7)
        v

        |

        |

        |\
        | reviewed exact invocation -> contractual preservation
        |

        v

This small diagram also exposes the two missing seams. First, framework-created

the saver but is neither admitted ordinary payload nor a declared carrier.
Second, “reviewed producer” must be attached to an exact behavior/configuration,
not inferred once for a callable with open parameters.

*Model D verdict:* *SOUND WITH CORRECTION.* It is the best target for this
repository only if its optimization is staged: unknown and configuration-open
producer forms remain uncertified, certification describes an exact bound
behavior (not a name or callable in the abstract), and current framework-owned
non-scalar Intent gets an explicit lifecycle. A safe initial implementation may
re-establish after more steps than the final optimized model; that is still
Model D's closed default, not a claim that all built-ins preserve.

Plugin support is strongest under corrected Model D: the framework makes no
claim about operations or side effects inside the plugin, but validates a
recognized returned candidate before any subsequent framework-owned consumer.
Plugins that return `None` through the maintained plugin/generic binders use the
mutated input as the candidate; a raw `BoundStep` passed to `run_pipeline` has
no such automatic convention and remains its caller's responsibility.

==== 6. Scalar grammar, normalization, and Missing

The FTR reproduces the accepted scalar grammar exactly:

* String: `str`, including `numpy.str_` by subclass behavior;
* Boolean: `bool` and `numpy.bool_`, dispatched before Number;
* Number: Python and NumPy integer/floating variants, after explicit
  `numpy.timedelta64` exclusion;
* Missing: `None`, empty string, supported float/NumPy NaN, `pandas.NA`,
  `pandas.NaT`, and `numpy.datetime64('NaT')`, but not
  `numpy.timedelta64('NaT')`;
* DateTime: `datetime.datetime`, `pandas.Timestamp`, and every non-NaT
  `numpy.datetime64`, dispatched before Date and without unit inference; and
* Date: `datetime.date` after DateTime.

Timezone-aware datetime/Timestamp carriers are admitted without timezone
stripping. No carrier was silently added or removed. The focused classifier
probe and accepted Phase-D tests confirmed bool-before-number,
DateTime-before-Date, `numpy.timedelta64` rejection, all listed Missing
carriers, `numpy.str_`, Timestamp, aware datetime, and NumPy datetime units.

===== Validate-only result

Validate-only is the least lossy decision and is architecturally sound. Its
precise safety benefit is:

[source,text]
----
ordinary input cell is a member of a small, known semantic carrier vocabulary
and is not arbitrary opaque Python
----

It does *not* prove uniform Python scalar semantics. Repository operations use
sets, dictionary keys, pandas merge/groupby/comparison, sorting, arithmetic,
string methods, serialization, and datetime comparison. Accepted carriers can
still differ materially:

* `pandas.NA` has tri-state comparison/boolean behavior;
* NaN remains non-reflexive and has surprising equality/hash behavior;
* aware and naive datetimes are both valid but may not be mutually orderable;
* NumPy numeric and datetime precision/overflow semantics remain carrier-owned;
* pandas/Timestamp and native datetime conversions can differ by backend; and
* no admitted-category cross-product is promised sortable or serializable.

Section 18's non-guarantees correctly preserve these facts. Family code may
remove generic arbitrary-object/container/callable defenses after a real
conformance precondition, but it may not remove family type constraints,
Missing handling, compatibility checks, comparison/sort rules, or sink
translation.

===== Missing preservation

Preserving all admitted Missing carriers is consistent with Phase D. Generic
code must use `core.scalar_values.is_missing_carrier`, not ordinary equality or
truthiness. That predicate is the Technical Model's stable shared classifier
primitive even though it is not re-exported from `core.__init__`; the FTR's
“may use” wording is therefore supportable. Empty string remains both a
legitimate String substrate value in source-specific contexts and a Missing
carrier under the accepted generic classifier; Phase E does not resolve that
family semantic ambiguity.

===== Framework-authored FormulaSpec conflict

The accepted Technical Model says `FormulaSpec` is framework-authored output
Intent, not a payload scalar. That does not mean it is absent from runtime
DataFrames: documented `add_fk_helpers` / `add_lookup_helpers`
`helper_value_mode: formula` creates `LookupFormulaSpec` cells and the XLSX/ODS
renderers deliberately consume them. The registry exposes `add_lookup_helpers`
as a normal configured step. A full post-step ingress pass would reject this
maintained path. Section 19's empty `DeclaredComposite` branch cannot repair
the gap because FormulaSpec is Intent, not a future `List[Scalar]`. See F1.

==== 7. Structural carriers, axes, and ExactTable

===== DataFrame traversal and axes

Positional traversal of every data cell is feasible and avoids promoting row
indexes to data. The current axis evidence includes:

* flat string labels from most tabular backends;
* supported numeric physical column labels;
* supported hashable tuple labels and MultiIndex roundtrip paths;
* default and non-monotonic numeric row indexes;
* family-specific rejection of MultiIndex in operations that require flat
  fields; and
* an existing physical column contract that accepts any non-missing-like,
  hashable, self-comparable, unique label, rather than a closed six-category
  vocabulary.

The proposed `AxisAtom`/finite-tuple grammar is coherent, and it admits known
numeric/MultiIndex examples, but it is a new tightening. No completed census
shows that all framework-generated and supported consumer-reachable labels fit
it. Row-index restriction is especially weakly motivated because ingress uses
positions and the index is not promoted to payload. Section 10 both fixes the
grammar and says the implementation must census before “tightening”; those
statements conflict. The exact grammar must be evidence-gated before it becomes
normative (F3).

“Deterministically comparable” has a narrow existing meaning in
`domain.tabular.physical_labels`: self-equality yields an unambiguous Boolean.
It is not an ordering promise. Labels satisfying the proposed grammar can
still be mutually non-orderable, and tuple labels can contain Missing atoms.
The FTR's non-guarantee for sorting/comparison is therefore load-bearing.

===== ExactTable

The proposed checks are generic carrier self-consistency, not grouped
reconstruction:

* exact `ExactTable` identity;
* exact non-negative integer `header_rows` and `n_cols`;
* `header_rows == len(header_grid)`;
* header/data row widths equal `n_cols`;
* string header cells; and
* accepted scalar data cells.

Current `ExactTable.__post_init__` owns container conversion but does not enforce
geometry: a probe constructed `header_rows=99`, `n_cols=-1`, and mismatched row
width without failure. Parser/workbook projection and grouped projection
construct consistent instances, so central checking is meaningful. Row keys,
header-depth intent, tuple uniqueness, mapping/bijection, and reconstruction
remain correctly local. *ExactTable verdict: SOUND.*

===== Grouped/canonical carrier trust

`GroupedMatrix` rejects direct raw construction and its public factory proves a
frame/header pair against a live mapping. That proves structural pairing, not
the ordinary scalar grammar of its contained mutable DataFrame. The public
factory can receive a validly headed DataFrame containing arbitrary values, and
`contract_grouped_xref` can propagate a caller-supplied `fill_value`. Therefore
“trusted by construction” must always name the exact property established.
Such carriers may extend a conformance interval only when their producing
invocation also preserves payload conformance; a dataclass/factory identity is
not a payload bypass.

==== 8. Metadata substrate review

The distinction between external/persisted metadata and runtime metadata is
correct. Current producers/consumers predominantly use mapping/list/string/
Boolean/number leaves under roots such as `sheets`, `constraints`,
`helper_policies`, `workbook_view`, `legend_blocks`, `xref_crosstable`,
`compact_multiaxis`, `split_by_discriminator`, `pipeline_cleanup`, and
`derived`. Persistence strips known runtime roots/facets. However,
`FTR-META-LIFECYCLE-INVENTORY-P5` explicitly records that the complete root and
sub-root lifecycle inventory does not yet exist.

Exact owned built-in dict/list nodes, string keys, scalar leaves, identity-based
cycle detection, and no arbitrary recursive attribute walking form a plausible
substrate. They are not yet proven compatible. Current Legend Blocks ingress:

* accepts general `Mapping` input;
* calls truthiness and `str` while resolving list identities;
* shallow-copies block mappings; and
* retains nested aliases.

E3 can replace those mechanics, but the design must first state delegate
governance. A root delegate must be centrally reviewed/owned, operate only on a
staged candidate, avoid side effects and unsafe rejected-value inspection, and
either return the common substrate or an explicitly named root-specific output
contract that central ingress checks. Arbitrary family registration must not
become a hidden plugin system. Without those rules a delegate can bypass the
grammar and atomicity (F4).

===== YAML `_meta.yaml`

The current `yaml_dir` loader treats every YAML filename as a sheet. A direct
probe of `_meta.yaml` containing a mapping returned
`frames["_meta"]` as a DataFrame; the YAML saver then skips `_meta`. This behavior
is explicitly documented in the accepted census and Minimal Internal Value
Model, and `yaml_dir` is a documented CLI backend. Declaring this DataFrame an
invalid metadata root is a defensible hardening decision, but it changes a
user-reachable reserved-name behavior. The design does not choose among:

. teaching the YAML backend to produce a metadata mapping;
. rejecting the reserved input with an explicit compatibility error; or
. preserving a deliberately reinterpreted ordinary sheet.

E3 cannot discover that release/migration decision after the contract has
already declared the input invalid. The option, compatibility statement, and
release-note consequence must be decided before implementation (F5).

==== 9. Producers, trust epochs, and re-establishment

===== What can actually be certified

The runtime registry currently contains 44 entries: 38 `StepRegistration`
entries with fixed targets and six bare factories (`identity`, `validate`,
`add_fk_helpers`, `remove_fk_helpers`, `validate_fk_helpers`, `plugin`).
`BoundStep` contains only `name`, mutable `config`, and `fn`; there is no current
producer-state representation.

A preservation proof cannot generally attach once to a callable or family:

* `contract_xref` with an otherwise conforming input and an opaque configured
  `fill_value` placed that exact object in a missing matrix cell in a direct
  probe;
* `validate_references` on a conforming DataFrame with a tuple/MultiIndex row
  label emitted that tuple into the ordinary `validation_findings.row_index`
  cell;
* formula-mode lookup-helper configuration emits `LookupFormulaSpec` cells;
* grouped producers hold mutable DataFrames and accept configuration-dependent
  fill values; and
* wrappers/factories may close over callbacks or mutable configuration even
  when the outer callable is built in.

The certified unit must therefore be the exact bound behavior/configuration
whose output contract is closed. Callable/family review may establish
eligibility, but it is not the certificate. Any unreviewed option, nested
callback, mutable post-binding configuration, or wrapper composition returns
the invocation to the uncertified default. The FTR need not choose the metadata
field/API now, but this granularity is contract-load-bearing.

E4's present requirement to inventory all registered producers and provide
payload/metadata output tests for every preserving declaration is not a small
infrastructure slice. Current counterexamples show it entails behavior-mode
and family-output analysis across 44 entries. That pulls Phase-F compatibility
work ahead of the Domain Maintainer Contract unless E4 starts from a very small
closed certification set or conservatively re-establishes after unproven steps.
See F2.

===== Trust epoch enforceability

Without a wrapper/token, deep copy, ownership-enforcing carrier, or mutation
tracking, a trust epoch is explanatory state. The framework can know that an
ingress/re-establishment pass succeeded and that the next producer was marked
for a reviewed bound behavior. It cannot know that a caller, closure, plugin,
thread, retained DataFrame alias, retained `_meta` alias, or in-place operation
will not mutate the graph later. Many current transformations shallow-copy the
top-level Frames mapping and retain unchanged DataFrames.

This is acceptable under the trusted-runtime ADR only if stated as a
caller/producer obligation, not as mechanically certified isolation.
“Must not retain an out-of-band mutation path” is not an ingress guarantee; it
is a reviewable producer obligation with the same-process threat-model limit.
The macro can advertise conformance only while these obligations hold (F7).

===== Uncertified-return boundary

Full re-establishment after an uncertified return is sufficient to protect the
*next framework-owned consumer* if the returned candidate is a recognized
Frames mapping and if all intended downstream internal carriers are modeled.
It does not protect:

* ordinary Domain calls made inside the custom callable;
* a sink side effect performed by that callable;
* in-place mutation before returning `None` or the same mapping;
* effects performed before a non-Frames return is rejected; or
* later mutation through an alias retained by the callable.

The FTR states most of these limits correctly. Maintained plugin/generic
binders translate `None` to the mutated input and therefore give the macro a
candidate to check. A raw `BoundStep` in `run_pipeline` does not; that surface
remains caller-owned. Re-establishment must reject a non-Frames return before
cleanup, projection, or save. It cannot roll back custom side effects.

No current YAML/JSON path constructs a callable object from payload data.
Configured string identifiers are centrally resolved during binding. Future

deserialize callable objects through YAML/JSON/pickle-like mechanisms. Direct
callables and BoundSteps remain trusted-programmatic capability and cannot be
made less-trusted by a flag.

==== 11. Description plane and E7 lifecycle

The two-plane split is correct:

* E1-E6 may establish a payload-conformance guarantee for entries whose
  description is trusted by precondition.
* Less-trusted configured descriptions require structural parsing and
  operator authorization before import/binding/acquisition; module import is
  capability activation.
* Payload admission cannot compensate for an already activated forbidden
  callable.

The stated dependency exists:
`FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A.adoc` is still an open architecture
assessment. Its original readiness review found it not ready; a correction
self-review exists, but no accepted architecture selection yet supplies E7's
per-surface policy metadata.

The design says E7 is a Phase-E sub-slice and required before advertising
less-trusted descriptions, but does not define whether “Phase E complete” means
E1-E6 or E1-E7. The roadmap's Phase E and accepted ADR require the two authority
questions to remain representable; they do not require payload implementation
to wait for E7. The lifecycle must therefore name an intermediate state, for
example an accepted payload milestone under a trusted-description precondition,
while reserving Phase-E completion for E7 -- or explicitly move E7 to another
lifecycle feature. Current CLI/user documentation must not imply that
operator-untrusted pipeline YAML is supported during that intermediate state.
See F9.

D-T3 still does not follow E1-E6 or this review. The roadmap gates it on
completed Phase E and the Domain Maintainer Contract, and no family pilot is
selected here.

==== 12. Atomicity, diagnostics, and security

===== Atomicity and aliasing

Read-only DataFrame traversal plus a staged top-level mapping and fully owned
metadata dict/list graph can ensure that ingress performs no mutation and
publishes no candidate on failure. It cannot ensure isolation against concurrent
or later writes by external aliases. DataFrames are intentionally not deep
copied; existing metadata normalizers retain nested aliases; delegates could
have side effects unless forbidden.

The contract should promise:

[source,text]
----
ingress and every approved delegate perform no mutation of caller-owned input;
no staged candidate is published before all checks succeed
----

It should not be read as proof that the object graph remained unchanged by all
actors during the attempt. Post-custom-step re-establishment rejects the
returned state before later macro consumption but cannot roll back earlier
mutation or side effects.

===== Diagnostic feasibility

Safe diagnostics are feasible with closed dispatch:

* exact type checks precede arbitrary value inspection;
* DataFrame cells are located by frame and positional row/column ordinals;
* axis tuples are recursively type-checked before physical-label equality/hash;
* exact dict keys are type-checked while traversing the container contract;
* cycle detection uses `id(container)`, not container hashing; and
* rejected values need only a bounded carrier/type category, never `repr` or
  `str`.

The prohibition on equality/hash/iteration applies to the rejected unsupported
*value*, not to iteration of an already-admitted exact dict/list/DataFrame
container. Existing Legend Blocks `str`/truthiness behavior must be replaced or
bounded during E3; it cannot simply be grandfathered as a delegate.

===== E4 scope explosion

Auditing 44 registry forms is not automatically Phase F, but proving every
parameter combination's payload, axis, metadata, internal-carrier, and policy
output is. The `LookupFormulaSpec`, opaque `fill_value`, and tuple-finding
examples show this is not theoretical. The narrowest sequence-compatible rule
is a closed uncertified default plus a small initial set of exact invocations
whose preservation is already implied by infrastructure-level behavior. Model
E-style validation after all other steps may be a temporary migration strategy;
it must not be advertised as proof that current outputs all satisfy the
proposed grammar.

===== Performance sanity

Initial ingress is O(total DataFrame and ExactTable data cells plus metadata
nodes). Each uncertified return repeats that cost. This is reasonable once at
framework ingress and after occasional plugins. Re-establishing after every one
of a long 44-step built-in pipeline can multiply full-workbook traversal and is
unattractive for large object-dtype workbooks. Corrected Model D therefore has a
real performance advantage over permanent Model E, but only after bounded
preservation evidence exists. No benchmark is needed to decide the contract.

==== 15. Findings

===== TRUSTED-INGRESS-DESIGN-REVIEW-F1 -- Blocking -- the closed ordinary-cell postcondition rejects the repository's maintained framework-authored formula Intent path

*Exact FTR sections:* 7 (Payload grammar), 10 (Structural-carrier contract), 12
(Trust propagation), 17 (Downstream postconditions), 19 (Bounded-composite
seam), 23/E2-E5, and 24 (formula sink policy defer).

*Primary authority:* Technical Model ch08 Internal Scalar Value Model explicitly
classifies FormulaSpec as framework-authored output Intent, not a payload
scalar; spreadsheet backend capability profiles and the validation/writer ADR
keep backend-neutral intent distinct from sink translation.

*Runtime/evidence:* `pipeline.registry` exposes `add_lookup_helpers`;
`domain.transformations.enrich_lookup` documents and implements
`helper_value_mode="formula"` by storing `LookupFormulaSpec` in DataFrame cells;
the User Guide documents that mode; XLSX/ODS renderers consume it. Focused tests
confirm the output. The FTR explicitly excludes FormulaSpec from every ordinary
cell and declares no Phase-E `DeclaredComposite` variant.

*Architectural impact:* A preserving declaration is impossible for the formula
mode, while an uncertified return followed by required full re-establishment
rejects it before cleanup/save. E5 would break a supported framework-managed
workflow. Deferring generic formula *ingress/roundtrip* policy does not resolve
the already-supported framework-authored output-Intent lifecycle.

*Smallest correction:* Before E2/E4, add an explicit, bounded lifecycle for
framework-created FormulaSpec Intent (or explicitly migrate/remove the current
mode with compatibility/release treatment). State whether it is a special
producer-created cell Intent, a dedicated structural carrier, or moved out of
ordinary DataFrames; define which consumers may see it and how re-establishment
recognizes it. Do not admit arbitrary external formula objects and do not use
the future `List[Scalar]` seam as a false substitute.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F2 -- Blocking -- producer preservation is scoped too broadly and E4 is not bounded independently of family hardening

*Exact FTR sections:* 4 questions 1/9/10, 5 (Model D), 12 (Trust propagation),
17 (Postconditions), and 23/E4-E5.

*Primary authority:* The robustness ADR requires checkable boundary contracts;
the roadmap orders Phase E before the Domain Maintainer Contract and Phase-F
family hardening. The trusted-runtime ADR does not make built-in or registered
code payload-preserving.

*Runtime/evidence:* There are 44 registry forms and no producer metadata on
`BoundStep`. A direct probe showed `contract_xref(fill_value=object())` emitting
that object into a cell. `validate_references` emitted tuple row-index labels
into finding cells. Formula mode and grouped configurations add further
configuration-dependent outputs. Factories, wrappers, mutable configs, and
nested callbacks prevent a once-per-callable proof.

*Architectural impact:* E4's “inventory registered producers” plus output tests
either certifies too broadly and makes the downstream postcondition false, or
requires broad parameter/family proof before E5 and accidentally pulls Phase F
ahead of its roadmap gate. Model D's claimed implementation advantage is not
currently enforceable.

*Smallest correction:* Define preservation at exact bound behavior/invocation
granularity; callable/family review supplies eligibility only. Keep every
unknown option/callback/wrapper uncertified. Bound E4 to a small closed initial
certificate set and permit conservative re-establishment for all other steps.
Inventory current non-grammar outputs as compatibility/design work rather than
silently treating them as producer test failures.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F3 -- Important -- the exact DataFrame axis grammar is normative before its required compatibility evidence and is narrower than existing physical-label authority

*Exact FTR sections:* 7 (Axis grammar), 10 (DataFrame contract), 17
(Postconditions), and 23/E2.

*Primary authority:* Existing shared physical-label authority permits
non-missing-like, hashable, deterministically self-comparable, unique labels and
explicitly is not string-only; parser/reconstruction and family-specific axis
contracts remain separate.

*Runtime/evidence:* Numeric and tuple/MultiIndex labels are supported. The
existing physical contract is open to other safe hashable labels. No accepted
inventory covers all framework-generated and consumer-reachable column/index
extension types. Row indexes are traversed positionally and need not be Domain
data.

*Architectural impact:* E2 could reject currently supported labels for no
demonstrated downstream safety gain. Section 10's compatibility prerequisite
cannot repair a design that already fixes the narrower grammar and claims it is
not a new universal column-label type system.

*Smallest correction:* Make the exact axis vocabulary provisional. Complete
and accept the E2 axis census first; either confirm the scalar/tuple grammar
with named migrations, or retain the existing physical-column contract and add
only the minimal safe row-index rule. Define “deterministically comparable” as
self-comparability, not ordering.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F4 -- Important -- metadata vocabulary and delegate governance are fixed before the relevant lifecycle inventory and permit a grammar/atomicity bypass

*Exact FTR sections:* 11 (Metadata contract), 15 (Failure atomicity), 16
(Diagnostics), and 23/E3.

*Primary authority:* ch06 separates metadata structure from family semantics;
the robustness ADR permits narrow owned representations; the persistence model
and `FTR-META-LIFECYCLE-INVENTORY-P5` say the complete runtime/persisted root
inventory is not yet established.

*Runtime/evidence:* Current metadata is mostly mapping/list/scalar, but current
Legend Blocks accepts general Mapping, invokes truthiness/`str`, shallow-copies,
and retains nested aliases. Runtime and persistence have many roots/facets and
the manual registry is not runtime authority.

*Architectural impact:* Unsupported existing shapes could be rejected without
migration, and an unconstrained root delegate could introduce opaque values,
mutate aliases, inspect hostile values, or become a hidden extension registry.
The central owned-substrate and atomicity postconditions would then be false.

*Smallest correction:* Treat the exact dict/list grammar as acceptance-gated by
a focused external/runtime metadata node census. Normatively require delegates
to be centrally reviewed, staged/pure, non-extensible by arbitrary family code,
and to return either the common substrate or a named explicit root contract
that central ingress rechecks.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F5 -- Important -- YAML `_meta.yaml` rejection lacks a compatibility and migration decision

*Exact FTR sections:* 4 question 7, 11 (Metadata contract), 23/E3, and 35-like
compatibility consequences implicit in the design.

*Primary authority:* Spreadsheet Parse Contract keeps backend conversion
backend-owned; the accepted Minimal Internal Value Model and census explicitly
document YAML's current `_meta.yaml`-as-DataFrame behavior. `yaml_dir` is a
documented CLI backend.

*Runtime/evidence:* A real `load_yaml_dir` probe returned a DataFrame at the
reserved `_meta` key; `save_yaml_dir` skips that key. The FTR declares it invalid
but does not choose backend conversion, reserved-name rejection, or a preserved
interpretation.

*Architectural impact:* E3 changes a user-reachable backend behavior without a
decided error/migration/release contract. It may also silently remove a
currently addressable sheet named `_meta`.

*Smallest correction:* Select and document one explicit YAML behavior before
E3, identify whether existing input needs migration, and require release notes
for the observable change. Keep the conversion in the backend rather than
teaching Domain ingress to reinterpret a DataFrame as metadata.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F6 -- Important -- “Trusted Domain Payload” materially collides with the ADR's payload-trust authorship dimension

*Exact FTR sections:* 2 (Vocabulary), 6 (Surface guarantees), 13 (Operator
policy), and every downstream normative sentence using the term.

*Primary authority:* `ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY` defines “Is the
payload trusted?” as an external authorship/authority question independent of
pipeline-description trust.

*Runtime/evidence:* The FTR defines “Trusted Domain Payload” as conformance, then
later refers to a “trusted-payload authority assessment.” All four combinations
must remain understandable. The same adjective now denotes two different axes
in one contract.

*Architectural impact:* A reader can plausibly infer that conforming payload
came from a trusted author or that less-trusted payload cannot become
conforming. This is security-significant vocabulary ambiguity, not cosmetic
wording.

*Smallest correction:* Rename the conformance state to a term such as
“Ingress-Conformant Domain Payload” or “Conformant Domain Payload,” and reserve
trusted/less-trusted payload for the ADR's authorship dimension. Preserve the
rule that neither authority class bypasses global grammar.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F7 -- Important -- trust epoch and atomicity wording must be explicitly contractual rather than mechanically enforceable isolation

*Exact FTR sections:* 2 (Vocabulary), 12 (Trust propagation), 15 (Failure
atomicity), and 17 (Downstream postconditions).

*Primary authority:* The robustness and trusted-runtime ADRs disclaim protection
against hostile same-process code; pandas DataFrames are mutable; no wrapper or
copy-based ownership system is selected.

*Runtime/evidence:* Current transformations frequently shallow-copy Frames and
reuse DataFrames; current metadata normalization retains nested aliases. A
plugin/closure can retain or mutate a reference after re-establishment, and the
framework cannot detect that without new state/copying architecture.

*Architectural impact:* “Must not retain an out-of-band mutation path” cannot be
mechanically certified as an ingress guarantee. Downstream entitlement is
conditional on caller/producer obligations; failure atomicity cannot assert
concurrent isolation.

*Smallest correction:* State that epoch is an explanatory contract interval,
not runtime state. Make no-out-of-band-mutation a producer/caller obligation.
Narrow atomicity to “ingress/delegates do not mutate caller input and do not
publish staged output before success,” explicitly excluding concurrent or
later external alias mutation.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F8 -- Important -- concrete payload-policy dimensions are premature without an operator use site

*Exact FTR sections:* 4 question 12, 13 (Operator payload policy), 21 (API-shape
implications), and 23/E1.

*Primary authority:* The policy ADR requires operator ownership and per-kind
combination, but deliberately does not choose policy kinds, profile/API
transport, or ingress mechanism.

*Runtime/evidence:* The accepted census and FTR acknowledge no current payload
policy object or transport. No operator case demonstrates a need to distinguish
NumPy versus Python carriers within one semantic category or to narrow metadata
leaves independently of valid framework metadata.

*Architectural impact:* E1 would create generic security knobs and combination
semantics before their effects on backends, framework metadata, or users are
known. Carrier-variant policy can reject semantically admitted values without
improving the ordinary Domain postcondition.

*Smallest correction:* Keep the ADR-derived rule that any policy is operator-
owned, narrowing, immutable per macro, and per kind. Defer carrier-variant and
independent metadata-leaf dimensions until a concrete operator use site defines
them; implement only the minimum evidenced category/structural restrictions.

===== TRUSTED-INGRESS-DESIGN-REVIEW-F9 -- Important -- E7's dependency is real but the Phase-E completion state is undefined

*Exact FTR sections:* 4 question 13, 14 (Description trust), 23/E7, 24 (scope
matrix), and 26 (Acceptance criteria).

*Primary authority:* The runtime/policy ADR requires independent authority
dimensions and pre-activation rejection; the roadmap gates later work on Phase
E; D-T3 also requires the Domain Maintainer Contract.

*Runtime/evidence:* Current configured binding imports before payload load.
`FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A` exists but has not completed its
architecture assessment. The design says E1-E6 support trusted descriptions
and E7 is a Phase-E sub-slice, without naming whether E1-E6 can close Phase E.

*Architectural impact:* The project could mark Phase E complete while one of its
declared sub-slices and less-trusted-description authority combinations remains
unimplemented, incorrectly unblocking the Maintainer Contract/D-T3; or it could
unnecessarily block a valid payload milestone.

*Smallest correction:* Define lifecycle explicitly: E1-E6 may be accepted as a
payload-conformance milestone under a mandatory trusted-description
precondition, while Phase E remains open until E7, or move E7 to a separately
named lifecycle feature and update roadmap dependencies before implementation.
Publish the interim CLI support boundary.

====== Negative-ingress proof

Authorization may live in framework control flow and exact bound-step metadata;
it need not live on the object. Initial ingress always chooses ordinary
establishment and rejects FormulaSpec. Only the recognized exact producer
transition can set the declared helper role. On every uncertified return, the
macro discards the prior execution-state authorization and selects ordinary
re-establishment. That pass rejects FormulaSpec even if plugin code:

* returns the identical DataFrame;
* copies the previously valid FormulaSpec instance;
* constructs a fresh `LookupFormulaSpec` directly;
* places it in the same physical helper column; or
* returns the same Python class/shape as a reviewed producer.

This is conceptually enforceable without an unforgeable token under the
accepted same-process threat model. A plugin can execute arbitrary trusted
Python while it runs; it cannot make the enclosing macro choose the certified
transition merely by shaping its return. A runtime implementation must keep the
certificate mechanism framework-owned and derive it from exact bound behavior,
not from returned class identity.

===== 8. Execution-state and exact-certification judgments

The two named payload categories are semantic contract states, not required
runtime wrapper types. Ordinary framework control flow can implement them when
every transition carries a closed descriptor naming input state, output state,
producer behavior, role, and allowed consumer. Producer provenance is required
for FormulaSpec authority because class/role identity alone is rejected.

The FormulaSpec-only execution state is role-specific enough for its current
purpose and does not create a generic “framework-owned object” escape hatch.
Future Intent requires a named kind, exact introducing behavior, declared
frame/column role, allowed consumers, re-establishment behavior, sink/output
ownership, and no admission by external class identity. No extensible registry
is required now.

The state set is nevertheless incomplete. `GroupedMatrix` is a top-level
structural runtime carrier, not a cell Intent, and the report composites force
a choice the empty `DeclaredComposite` branch currently denies. A maintainer
cannot determine the next consumer precondition for those supported values
from the corrected state vocabulary.

An exact certificate must be a closed description of all behavior-affecting
state: effective values after default resolution, dynamically generated
mappings once bound, nested callbacks, closure/external references, mutable
options, wrapper/factory composition, and any later mutation. If any such state
is outside the reviewed immutable description, the invocation remains
uncertified. The FTR need not choose hashes, wrapper classes, or another runtime
representation now. This is precise enough to prevent callable/family registry
identity from becoming a certificate.

[source,text]

ConformantFrameworkExecutionState
  = ordinary ingress facts outside controlled roles

current controlled roles
  = LookupFormulaSpec@declared-helper-cell-role
  | GroupedMatrix@producer-declared-frame-role

===== 3. Controlled transitions versus preserving certificates

The correction separates two proof mechanisms that the earlier migration proof
conflated:

* a *controlled transition* is required semantic authority to introduce, carry,
  retain, consume, or terminate one maintained non-ordinary role; and
* a *preserving certificate* is an optional optimization for an exact bound
  behavior/configuration that permits omission of redundant ordinary
  re-establishment.

Callable/family review remains eligibility only. A certificate still requires
a closed description of every behavior-affecting effective value, default,
nested callback, mapping, closure/object state, and mutable option; otherwise
the exact invocation remains uncertified. The ordinary preserving-certificate
set may be zero. The required controlled transition/state set may not omit a
maintained non-ordinary flow.

There is no dedicated role re-establishment in this correction. Every
uncertified return ends all role authority and is subjected to ordinary
re-establishment. It continues only if it reaches Ingress-Conformant Domain
Payload; it is not presumed capable of doing so. A controlled role can reappear
only through a fresh exact introducing transition.
