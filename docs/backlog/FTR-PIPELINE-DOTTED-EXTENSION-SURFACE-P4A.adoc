===== FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A -- Assess and define the pipeline dotted-extension surface

*Status:* New; architecture assessment and contract work only.

*Priority:* P4A

*Type:* Pipeline extension-surface architecture / compatibility assessment.

==== Purpose

Determine which dotted-callable pipeline forms are intentional consumer,
expert, registry-internal, or programmatic extension contracts; document the
responsibility and trust model for each; and decide whether the current shared
mechanics should remain shared, gain explicit syntax, or be separated in a
later implementation slice.

This FTR is deliberately unbiased about retention, deprecation, or technical
separation. It first gathers evidence and makes an explicit surface decision.
It performs no runtime implementation.

==== Context and discovery history

The pipeline has accumulated several related but not identical extension forms:

* registered short-name steps;
* `step: plugin` plus a dotted `Frames -> Frames` callable;
* direct colon-style `step: module:function` factories that return a
  `BoundStep`;
* registry-owned `StepRegistration.target` strings consumed by generic
  frames-first and builder-style binders;
* nested string targets supplied to those generic binders; and
* direct Python callable targets passed programmatically.

Earlier pipeline cleanup explicitly retained both the plugin form and direct
colon-style factory form as intentional extension mechanics. The June 2026
transformation-family inventory classified `pipeline_extension` /
`identity_plugin` as registry infrastructure rather than a transformation
family, and routed the topic toward Technical Model or user-facing contract
work rather than forcing it into the Functional Model.

The Legend Blocks correction work then exposed a narrower ownership issue.
Framework-owned `domain.ingress` code was not supposed to be selectable as an
ordinary configured step, but the same string-resolution mechanics were
reachable through plugin, direct factory, and nested-target paths. Correction 3
centralized the current checked string resolver to close that concrete defect.
That correction did not decide the long-term public extension surface and must
not be treated as having done so.

This FTR exists so a local ownership correction does not silently become a
general plugin/factory policy. It also prevents the opposite mistake: treating
current implementation reachability as proof that every reachable Core
callable is a supported public API.

Problem-space inputs include:

* `docs/cold_storage/working_context/functional_model_inquiry/metadata_foundations/app_boundary_meta_authority.adoc`;
* `docs/cold_storage/working_context/functional_model_inquiry/metadata_foundations/schema_maintenance_structural_drift.adoc`;
* `docs/cold_storage/working_context/functional_model_inquiry/metadata_foundations/key_lifecycle.adoc`;
* `docs/ai_info/interfaces_and_gates.adoc`;
* `docs/technical_model/ch04_concepts/pipeline_step_registration.adoc`;
* `docs/technical_model/ch08_architecture_details/pipeline_semantics.adoc`; and
* the Correction 2, Acceptance Review 3, and Correction 3 artifacts for
  `FTR-LEGEND-BLOCKS-RESOLVED-SHAPE-CORRECTION-P5`.

The metadata-foundations inquiries are problem-space evidence, not approved API
contracts. Their relevant principle is that this project is a toolkit:
workflow builders can compose capabilities in unforeseen ways, while the
framework provides deterministic building blocks and clear contracts rather
than attempting to prevent every inadequate composition.

==== Existing surfaces

[cols="2,2,3,3"]
|===
| Surface | Current shape | Current mechanics | Contract question

| Registered short name
| `- step: identity`
| `REGISTRY` resolves a reviewed name to a direct factory or
  `StepRegistration`.
| This is the normal maintained YAML surface. What stability promise
  distinguishes it from expert extensions?

| Plugin callable
| `- step: plugin` plus
  `dotted: package.module:function` or the supported final-dot form
| `make_plugin_step` resolves the callable at construction and invokes it as
  `(frames, **args)`.
| Is this the single intended consumer escape hatch, one of several equal
  expert forms, or a transitional convenience?

| Direct colon factory
| `- step: package.module:make_step`
| `resolve_registration` interprets a colon-bearing `step` value as a
  `StepFactory`, then passes the remaining YAML keys to it.
| Is implicit colon detection an advanced supported protocol, accidental
  reachability, or syntax that should become explicit?

| Registry-owned string target
| `StepRegistration(factory=..., target="module:function")`
| The registry selects a generic builder or frames binder; the binder resolves
  the target.
| Can this remain an internal representation even if the same notation also
  appears in consumer YAML?

| Nested configured string target
| A selected generic factory receives `target: module:function`
| `_resolve_target` resolves strings through the shared checked resolver.
| Is this an intended expert surface, merely a consequence of direct factory
  access, or a form that should be unavailable to configuration?

| Direct Python callable target
| `make_frames_target_step(target=callable, ...)` or builder equivalent
| `_resolve_target` returns the callable without dotted-string classification.
| What programmatic compatibility promise is appropriate, independent of YAML?

| Direct `BoundStep`
| Application code constructs a `BoundStep` and passes it to `orchestrate`
| No dotted resolution is involved.
| This is a Python composition path, including private application flows; it
  must not be conflated with configuration addressability.
|===

The current implementation uses one checked resolver for configuration-derived
callable strings. Sharing a parser/resolver does not by itself require all
callers to have the same public contract. Conversely, declaring different
contracts does not automatically justify duplicate technical resolvers. The
assessment must decide between:

* shared implementation with surface-specific contracts and diagnostics; and
* technically separate channels where separation materially improves clarity,
  compatibility, or ownership.

==== Known use and unknown use

The 2026-07-30 repository census provides evidence, not telemetry.

Known Core use:

* maintained Core YAML contains 16 `step: plugin` occurrences:
** four domain-contract workbook plugins; and
** twelve Project Memory query/workbook plugins;
* the runtime `REGISTRY` has 40 entries, of which 34 are
  `StepRegistration` entries with Core-owned string targets;
* direct colon-style external factories are exercised by focused pipeline
  tests and shown in `pipeline.build` documentation;
* nested configured string targets are exercised by boundary and compatibility
  tests, but no maintained Core YAML uses them as ordinary workflow authoring;
* direct Python callable targets are tested as a supported programmatic binder
  path;
* `StepRegistration` is re-exported from the pipeline package, while the
  `StepFactory` type alias is currently an internal type import rather than a
  separately documented consumer API; and
* historical architecture material explicitly states that plugin and direct
  colon factory forms were retained during pipeline cleanup.

Known inspected adoption-repository use:

* `spreadsheet-handling-demo`: four plugin occurrences for extraction examples;
* `worldbuilding`: three plugin occurrences for model-specific cleanup and
  view preparation;
* `ssdp` and `msg_ssdp_rollout`: two plugin occurrences each for frame cleanup;
* the inspected `personal`, `personal_data`, `home-lab`, and Pages trees contain
  no matching configured dotted-extension occurrence at this snapshot; and
* no inspected adoption YAML uses direct colon factories or nested dotted
  targets.

The adoption examples show that plugins are a real extension mechanism, not
only a test fixture. They also show different legitimate roles: teaching,
domain-specific transformation, local roundtrip policy, and temporary
capability incubation before promotion to a registered generic step.

Unknown use remains material:

* external consumers outside the available workspace are not observable;
* local or uncommitted expert pipelines may use direct factories;
* Python callers may construct registrations, bind callables, or build
  `BoundStep` objects without YAML;
* a finite absence of direct-colon use in inspected adoption YAML does not show
  that the protocol is unused; and
* adoption repositories are migration evidence, not immutable constraints.

The investigation must not use "not found in these repositories" as sufficient
grounds for removal. It must also not treat every currently importable Core
symbol as a supported extension target.

==== Toolkit responsibility model

The extension contract must preserve the toolkit model.

Framework responsibilities:

* provide deterministic calling conventions for supported extension forms;
* distinguish normal registered steps, expert extension points, internal
  registry wiring, programmatic composition, and framework-owned macro flow;
* validate reference syntax and callability with actionable diagnostics;
* document construction-time versus execution-time failure behavior;
* state compatibility and migration policy for any supported public surface;
* keep pipeline mechanics independent of domain implementation imports;
* provide examples of intended extension use and promotion to registered
  capability when a pattern becomes generic; and
* avoid presenting an ownership guard as a security boundary.

Workflow-builder responsibilities:

* trust and review all Python code selected by plugin or factory reference;
* ensure each extension receives the Frames and configuration it requires;
* own domain correctness, side effects, frame-set changes, and interaction with
  later pipeline steps;
* account for stale or foreign data and metadata crossing the application
  boundary;
* choose validation, review, promotion, or sanitization gates appropriate to
  the workflow; and
* migrate local extensions when the framework intentionally changes a public
  contract under an approved compatibility plan.

The framework is not responsible for proving that arbitrary trusted extension
code is semantically appropriate. It is responsible for making supported
mechanics and failure modes understandable.

==== Trust and safety distinctions

The assessment must keep these concepts separate:

* *Importable:* Python can import a symbol.
* *Configuration-addressable:* maintained config infrastructure permits a
  string reference to select it.
* *Public or supported API:* the project promises a documented contract and
  compatibility posture.
* *Semantically safe composition:* the selected step is appropriate for a
  particular workflow and input.
* *Security sandbox:* untrusted code is contained or prevented from arbitrary
  process access.

Plugin and factory extensions execute trusted Python in the application
process. Dotted-path syntax checks, namespace ownership rules, allowlists, or
construction-time diagnostics do not make them a sandbox. An external module
can deliberately import and call internal code; preventing that is outside
this mechanism.

Configuration-addressability policy may still be valuable for architecture
ownership and accidental misuse. It must be described as such, not as defense
against malicious code.

==== Framework-owned macro-flow category

Some importable and testable Python capabilities are framework-owned macro
flow rather than ordinary user-placeable steps. The category is defined by
responsibility, not by module name or chronology:

* it invokes one or more domain/application capabilities as part of an
  application or orchestration boundary;
* once the application use case is selected, the framework invokes the
  boundary-owned operation at its required position rather than letting the
  user place each component as an ordinary configured step;
* placing it arbitrarily in a configured linear pipeline would bypass,
  duplicate, reorder, or partially execute a larger boundary contract; and
* it remains directly testable and may remain programmatically callable
  without becoming configuration-addressable.

Current examples include:

* the command-only schema-maintenance application flow, which constructs a
  private `BoundStep` to reuse orchestration and persistence without exposing a
  public YAML step;
* domain ingress at the external-to-domain boundary;
* final domain cleanup at the post-pipeline boundary; and
* persistence-contract projection before saver invocation.

Ingress is one current example, not claimed as the first example or the
definition of the category.

Possible future examples include domain egress, transactional migration or
reconciliation commands, key-maintenance workflows, artifact
review/promotion gates, and other boundary-owned multi-capability operations.
Naming a possibility here does not approve its design.

The assessment should decide whether macro-flow addressability needs a reusable
declaration, such as explicit policy data owned by pipeline/application
architecture, or whether narrow declarations remain clearer. It must not
implement a generic permission system in this FTR.

==== Evaluated options

No option is preselected. A reviewed decision may choose one option, a
well-defined hybrid, or retain uncertainty where evidence is insufficient.

===== Option A -- retain and document current expert factory syntax

Keep YAML such as:

[source,yaml]
----
- step: my_package.steps:make_special_step
----

Document it as an advanced trusted extension surface with an explicit
compatibility and responsibility contract.

Questions to test:

* Is the `StepFactory -> BoundStep` signature stable and explainable?
* Must a factory accept `name`, and how are YAML parameters forwarded?
* Can construction-time side effects or ambiguous `TypeError` fallback be
  constrained or documented?
* Does retaining implicit colon syntax make registered-name typos or errors
  harder to diagnose?
* Which Core factories, if any, are supported examples rather than merely
  importable internals?

===== Option B -- make factory use explicit

Replace or supplement implicit colon detection with:

[source,yaml]
----
- step: factory
  dotted: my_package.steps:make_special_step
----

Separate registry-name resolution from dynamic factory selection and assess
compatibility and migration.

Questions to test:

* Does explicit syntax improve diagnostics and ownership enough to justify a
  new registered step kind?
* Should implicit colon syntax remain as an alias, receive a deprecation
  window, or remain permanently supported for experts?
* How are factory-specific arguments distinguished from resolver arguments?
* Would `factory` be confused with internal `StepRegistration.factory`
  terminology?

===== Option C -- plugin-only consumer extension

Retain `step: plugin` as the supported consumer escape hatch and deprecate
direct consumer factories. Core registry-owned targets and factories may remain
internal.

Questions to test:

* Can the plugin `(frames, **args) -> Frames | None` protocol express all
  legitimate consumer use cases currently served by factories?
* Are factories needed for custom construction, reusable closures,
  state/config validation, custom names, or other lifecycle behavior?
* Can expert factories migrate without forcing runtime work into module import
  or each invocation?
* Would plugin-only guidance oversimplify legitimate Python composition?

===== Option D -- namespace policy

Allow plugins/factories only from external or configured extension namespaces,
or from an explicit allowlist of public Core utility targets.

Questions to test:

* How would extension namespaces be declared and versioned?
* Does blocking all `spreadsheet_handling.*` break legitimate utilities,
  documented examples, tests, or internal registry targets?
* Can surface-specific policy distinguish consumer configuration from
  registry-owned wiring?
* Would an external re-export trivially bypass the policy, confirming that the
  rule is architectural rather than security enforcement?
* Does Core namespace membership say anything reliable about public API
  status?

No proposal may equate "inside `spreadsheet_handling`" with "private" or
"outside `spreadsheet_handling`" with "safe".

===== Option E -- retain behavior, clarify contracts only

Keep all current surfaces but document intended users, stability, ownership,
diagnostics, non-sandbox nature, and workflow-author responsibility.

Unlike Option A, this option would not necessarily elevate direct colon factory
syntax into a stronger advanced compatibility promise. It could retain current
behavior while explicitly labeling unresolved or provisional parts.

Questions to test:

* Is current behavior coherent enough that documentation alone resolves the
  ambiguity?
* Which surfaces can be labeled stable, expert, internal, or provisional
  without changing mechanics?
* Would leaving implicit overlap create recurring ownership defects or
  confusing public diagnostics?
* What evidence threshold would trigger a later structural option?

==== Evidence-gathering plan

. *Freeze a current-surface inventory.*
  Record runtime entry points, type/signature shapes, resolver call graph,
  descriptive registry claims, public import claims, tests, docs, and active
  YAML examples. Separate current fact from inferred intent.
. *Survey history.*
  Review the commits and closed FTRs that introduced or deliberately retained
  plugin, direct factory, generic binder, `StepRegistration`, and private-step
  patterns. Record which decisions were explicit and which were incidental.
. *Survey adoption.*
  Inspect available consumer and adoption repositories read-only. Classify
  each extension as domain-specific, teaching/example, generic-capability
  incubation, cleanup, external-system adapter, or unexplained. Invite
  maintainers to report external expert use that local search cannot observe.
. *Exercise a behavior matrix.*
  For registered names, plugin references, direct factories, nested targets,
  registry-owned targets, direct callables, and direct `BoundStep` composition,
  record construction timing, invocation timing, accepted syntax, signature
  requirements, name/argument handling, error classes, and output behavior.
. *Exercise compatibility candidates.*
  Prototype options only in disposable tests or an explicitly approved later
  branch/slice. Demonstrate whether plugin can represent legitimate factory
  cases and whether explicit factory syntax improves diagnostics.
. *Assess ownership declarations.*
  Inventory current and plausible macro flows, legitimate Core utilities, and
  consumer extensions. Compare a narrow explicit declaration with namespace or
  per-registration policy without implementing a permission framework.
. *Produce a decision matrix.*
  Score Options A-E and any hybrid against clarity, compatibility, expert
  capability, internal layering, diagnostics, migration cost, adoption
  evidence, and maintenance burden.
. *Record uncertainty.*
  Identify evidence unavailable to the local repository and state how that
  uncertainty affects the decision. Do not turn absence of telemetry into a
  removal argument.

==== Compatibility and adoption strategy

Any later change must follow these principles:

* treat plugin and documented direct-factory behavior as gated surfaces until a
  reviewed decision says otherwise;
* retain registered short-name behavior unless a separate surface FTR changes
  it;
* preserve direct Python callable and direct `BoundStep` composition unless
  evidence shows they are part of the chosen change;
* trial migrations in representative adoption repositories before claiming an
  option is viable, without treating those repositories as immutable;
* prefer additive explicit syntax or compatibility aliases before removal;
* if deprecation is selected, specify warning location, migration examples,
  minimum support window, removal gate, and rollback path;
* do not force consumer plugins into Core merely to reduce dotted references;
* allow recurring generic plugin patterns to graduate into reviewed registered
  capabilities through separate FTRs; and
* distinguish internal registry representation migration from consumer YAML
  migration even when both use `module:function`.

No deprecation, removal, or migration is approved by this FTR draft.

==== Scope

This architecture-assessment FTR will:

* inventory and classify every maintained dotted/callable pipeline surface;
* document current syntax, signatures, timing, failure behavior, and ownership;
* classify known Core and adoption usage without claiming exhaustive telemetry;
* define the toolkit/workflow-author responsibility boundary;
* define the framework-owned macro-flow category independently of ingress;
* evaluate Options A-E without preselecting an outcome;
* decide whether internal and consumer colon notation should share mechanics
  with distinct contracts or use technically separate channels;
* decide the intended stability tier of direct callable and direct
  `BoundStep` programmatic composition;
* decide how configuration-addressability policy should be declared at an
  architecture level;
* produce a compatibility/adoption decision and evidence matrix; and
* derive one or more narrow implementation/documentation FTRs only if the
  decision requires change.

==== Non-goals

This FTR does not:

* implement, deprecate, remove, or rename an extension surface;
* change Correction 3 or reopen its concrete Legend Blocks closure;
* delay Acceptance Review 4 or Legend Blocks finalization;
* assume that current implementation reachability equals public API;
* assume that missing local adoption evidence means a surface is unused;
* make plugin/factory execution safe for untrusted Python;
* create a Python sandbox, generic permission framework, package-signing
  system, or dependency isolation mechanism;
* block all `spreadsheet_handling.*` callables by default;
* forbid expert workflows merely because normal authoring should prefer
  registered names;
* redesign linear pipeline execution, routing, branching, retries, or
  transactions;
* absorb schema-maintenance, key-lifecycle, metadata-authority, or structural
  drift policy;
* absorb XRef axis labels, XRef mappings, grouped columns, projection scope, or
  any XRef behavior;
* redesign the descriptive pipeline-step registry as a runtime plugin registry;
* modify adoption repositories during assessment; or
* add release notes before a later slice changes a public or release-relevant
  surface.

==== Architecture questions

. Which surfaces are normal user API, advanced trusted extension API,
  registry-internal representation, provisional reachability, and direct
  Python composition?
. Is direct `step: module:function` factory syntax a compatibility contract or
  only an intentionally retained expert mechanism without long-term stability?
. Does `StepFactory` need a documented protocol, including configuration
  validation, naming, return type, and construction-time behavior?
. Can `step: plugin` express all legitimate consumer extensions, including
  factory-style closure construction and early validation?
. Should implicit colon detection be retained, made explicit, supplemented, or
  deprecated?
. Should `module.function` final-dot syntax remain plugin-only, and is that
  difference useful or accidental?
. Should user-supplied nested `target` strings be supported independently of
  registry-owned targets?
. Can internal `StepRegistration.target` strings and consumer colon syntax
  share one resolver while carrying different compatibility contracts?
. Would technical separation improve diagnostics or merely duplicate parsing
  and ownership logic?
. Which Core callables, if any, are legitimate documented extension utilities?
. How should framework-owned macro flows declare non-addressability without
  turning the pipeline into a generic permission system?
. Is namespace policy maintainable, and what does it protect if external
  re-export remains possible?
. Which errors must occur during configuration construction versus step
  execution?
. What introspection or diagnostics should identify the chosen surface and
  target without leaking a promise that every import path is stable?
. What compatibility evidence is required before changing an expert surface
  with unknown external use?
. Which recurring plugins should instead become registered generic
  capabilities, and which should remain consumer-owned?

==== Acceptance criteria

. A committed assessment inventories all existing surfaces listed above and
  distinguishes mechanics from public contract.
. Known Core and adoption use is classified, with unknown external use and
  census limits stated explicitly.
. Options A-E are evaluated against a common evidence matrix; the final
  decision records why alternatives were selected, combined, deferred, or
  rejected.
. The result explicitly decides or defers with a gate whether consumer and
  internal `module:function` notation share implementation, contracts, both,
  or neither.
. The toolkit responsibility model and trust/safety distinctions are reflected
  in Technical Model and developer/user guidance recommendations.
. Framework-owned macro flow is defined as a reusable architecture category
  with schema maintenance, ingress, cleanup, and persistence examples; no
  chronology claim about ingress is made.
. The result states whether configuration-addressability policy should remain
  narrow or gain reusable declaration data, without implementing generic
  permissions.
. Direct Python callable and direct `BoundStep` composition receive an explicit
  scope/stability decision.
. Any selected public-surface change has a migration plan tested against
  representative adoption evidence, including deprecation and rollback gates
  where applicable.
. No removal is justified solely by absence in inspected repositories.
. No import/namespace guard is described as a security sandbox.
. XRef labels and mappings remain owned by their existing FTRs.
. Any runtime, registry, test, release-note, or adoption change is deferred to
  a separately approved implementation slice with its own review artifact.

  removal or stabilization claims.
