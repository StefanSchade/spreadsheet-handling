*Problem statement:*::

Compact Multiaxis is a thin, explicit composition: both directions delegate
matrix addressing to XRef Crosstable and cell-value grammar to the historical
Cell Codec `mode` code-row path, derive substep configuration deterministically
from explicit high-level parameters, and coordinate their substeps through
*direct function arguments and returned frames* -- never through a metadata
message bus. The composition mechanics are correct. The defects are entirely on
the *persisted metadata contract it emits* and on the *documentation/registry
descriptions* of that contract:

* *CM-1 (important).* Both directions route XRef through an internal temporary
  relation frame (`__compact_multiaxis_<id>_xref` on expand,
  `__compact_multiaxis_<id>_encoded` on contract), which the composite deletes
  before returning. XRef writes its normal `_meta.xref_crosstable[config_id]`
  entry naming that temp frame in its `relation` field. After the composite
  returns, that persistent, public metadata field references a frame that
  exists nowhere in the output. The dangling reference is inert today (no
  consumer reconstructs from it), but it leaks the composite's internal
  temp-frame naming convention into a public, persisted metadata contract.
* *CM-2 (important).* `_meta.compact_multiaxis[config_id]` is a *write-only*
  root: no runtime code path in either direction reads it. The
  `registries/meta_registry.yaml` entry nevertheless describes it as
  roundtrip-relevant consumed intent that "preserves composed transform mode,
  row/column key names, codec configuration, sparse behavior, and optional
  group projection" -- overstating it as operative roundtrip authority and
  claiming Sparse Defaults behavior the composite does not implement at all.
* *CM-3 (minor).* The schema-maintenance blocked-root registration for
  `compact_multiaxis` never fires against the real payload (the payload carries
  no recognised `FRAME_KEYS` key; frame identity lives under
  `matrix`/`output`/`relation`, which are not frame keys), yet it is tested only
  with a fabricated `{"frame": ..., "value_column": ...}` shape the producer
  never emits -- giving false confidence.
* *CM-4 (minor).* `registries/pipeline_step_registry.json` omits accepted
  historical-path parameters that are actually used (`mode`, `drop_empty`, and
  others), understating the public surface and mis-describing the
  historical-codec dependency.
* *CM-6 (observation).* The functional model (`compact_multiaxis.adoc`)
  suggests the convenience surface "may also compose Sparse Defaults"
  internally, contradicting the code, which composes no Sparse Defaults.

This slice makes the persisted contract, registries, and prose tell the truth
about what the runtime does, without expanding the runtime surface.

*Verified current behavior:*::

Re-verified at the assessment commit (probes with `PYTHONPATH=src`; the
project `.venv` resolves a non-editable installed copy, so `PYTHONPATH=src`
binds the working tree):

* *CM-1 dangling reference (both directions).* After
  `expand_compact_multiaxis`, `_meta.xref_crosstable[config_id].relation ==
  "__compact_multiaxis_<id>_xref"` and that name is not a key of the returned
  frames (`exists as frame? False`). After `contract_compact_multiaxis`,
  `_meta.xref_crosstable[config_id].relation == "__compact_multiaxis_<id>_encoded"`,
  likewise absent. Source: `compact_multiaxis.py:53-64,84` (expand),
  `:154-185` (contract); XRef writes at
  `xref_crosstable/operation.py:196-208` (expand) and `:354-372` (contract).
* *Compact trace references only public frames.* The `_meta.compact_multiaxis`
  payload records public frame names (`matrix`/`output`/`relation`) and carries
  no `__compact_multiaxis_*` temp name (probed: "has any temp name? False").
  Producer: `_write_multiaxis_meta` (`compact_multiaxis.py:379-389`).
* *Trace is write-only / not consumed.* Grep finds no runtime reader of
  `_meta.compact_multiaxis`. A reverse roundtrip succeeds with the root absent
  and is *unaffected* by a deliberately conflicting root (probed: a contract fed
  `compact_multiaxis[rel] = {"mode":"WRONG","column_key":"BOGUS"}` produced the
  correct matrix columns `[feature_id, Product A, Product B]`; explicit args
  win, and no precedence conflict is even representable).
* *Same-`config_id` atomic replacement is already correct.*
  `_write_multiaxis_meta` reads `configs = dict(meta.get("compact_multiaxis") or {})`,
  assigns `configs[config_id] = payload`, and reattaches. A rerun with the same
  `config_id` overwrites the single mapping entry (probed: the entry stays a
  `dict`, not a list; keys remain `['rel']`). No nested or historical execution
  list accumulates beneath one ID.
* *Different `config_id` values coexist.* Because the producer copies the prior
  `configs` mapping and only assigns its own key, unrelated entries survive
  (probed: after a second expand under `name="other"`, keys are
  `['rel','other']`). The producer deletes *no* entry it did not rewrite, so
  it does not prune other configured instances absent from the current run.
* *Failure atomicity (carried from the assessment, re-affirmed).* Every
  composite function operates on `dict(frames)` copies and shallow-copies
  `_meta`; the compact-trace write runs only after all frame work succeeds. An
  invalid code during expand raises `ValueError` with no temp-frame leak into
  the caller's mapping, no source-frame mutation, and no compact-trace write to
  the input. A failed rerun therefore leaves the previous successful trace and
  caller input unmodified.
* *Reverse column-order fallback is XRef-owned.* When the reverse `column_keys`
  argument is omitted, `contract_xref` reads
  `_meta.xref_crosstable[config_id].column_keys` (exact config-id match), else
  derives distinct column values from the relation. This is the accepted XRef
  contract, not a compact-owned inference. `column_keys` is a Resolution facet
  stripped at the persistence boundary (`persistence_boundary.py:181-206`), so
  it is an in-run facet only and does not survive a persistence roundtrip.

*Resolved human decisions:*::

The following decisions arrived resolved with this correction request. They are
recorded here as binding and are *not* reopened by implementation.

. *Retain `_meta.compact_multiaxis` as a persistent, feature-owned diagnostics
  and composition trace.* It exists to explain which high-level Compact
  Multiaxis configuration was executed -- for diagnostics, auditability, agent
  comprehension, and roundtrip explanation. It is explicitly *not*: necessary
  inverse intent; an operative configuration source; a fallback for missing
  step arguments; a precedence authority over explicit configuration; a message
  consumed by a later runtime step; or evidence that Sparse Defaults was
  composed. Explicit step configuration and primitive-owned metadata remain the
  operative authorities. The registry and live documentation must state this
  distinction precisely.
. *Trace replacement and lifecycle.* The trace represents the *current* trace
  per stable, feature-owned `config_id`; it is not an append-only execution
  history. A successful rerun with the same `config_id` atomically replaces the
  previous trace entry and must not append historical executions beneath that
  ID. Different valid `config_id` values remain independent; the implementation
  must not delete every trace not rewritten during the current run, because
  other configured instances may legitimately be absent from that run.
. *Explicit prune and rename lifecycle.* Removal or renaming of a configured
  Compact Multiaxis instance must have an *explicit* way to remove or migrate
  its diagnostics trace. Generic staleness inference (from broad metadata
  attributes, frame existence alone, or absence from the current run) is
  forbidden. The selected outcome is specified below (*Trace replacement and
  prune lifecycle*).
. *Sparse Defaults.* Sparse Defaults remains a separate, explicit pipeline
  composition *around* Compact Multiaxis. Compact Multiaxis must not internally
  invoke or embed Sparse Defaults. Functional Model and registry prose implying
  otherwise are corrected (Target A from the assessment).
. *Compute composition preserved.* The accepted composition is retained
  unchanged:
+
[source,text]
----
explicit high-level Compact Multiaxis configuration
  → deterministic local derivation of primitive arguments
  → XRef and historical Cell Codec calls
  → optional Legend token/group projection
  → locally-created temporary frame removed
  → caller source frame preserved
----
+
The temporary-frame mechanism is accepted for this slice as a robust
copy-oriented composition over existing frame-to-frame primitive APIs. This FTR
does *not* redesign the primitives as DataFrame-in/DataFrame-out functions and
does *not* introduce a composite plan object.

*Target metadata ownership model:*::

After this slice, the persisted-metadata ownership for a composed run is:

* *XRef inverse intent* (`_meta.xref_crosstable`) is XRef-owned and must
  reference only frames that exist in the composite's output. No entry may name
  an internal Compact Multiaxis temporary frame after either direction returns.
  For a composed leg, the internal XRef entry is *not* public XRef inverse
  intent (see CM-1 analysis) and is not persisted as such.
* *Cell Codec* produces no `_meta.cell_codecs` (the codec `del`s the `name`
  argument the composite passes); codec intent lives entirely in the explicit
  call arguments. Unchanged.
* *Legend Blocks* (`_meta.legend_blocks`) is read-only input to the composite;
  the composite records only the `allowed_from_legend` *name* (a string) in its
  trace, never legend content. Unchanged.
* *Compact composition trace* (`_meta.compact_multiaxis`) is a persistent,
  feature-owned, *diagnostics-only* root: written by both directions, read by
  no runtime path, describing the executed high-level configuration. It carries
  no operative authority, no inverse intent, and no Sparse Defaults claim. Its
  frame references are public frames only.

Explicit step configuration and primitive-owned metadata are the sole operative
authorities; the compact trace is descriptive.

*CM-1 option analysis and recommendation:*::

Constraint: *No persistent metadata field may represent an internal Compact
Multiaxis temporary frame as a durable public frame reference after the
composite returns.* The dangling reference must not be solved by leaving the
temporary frame persistent (non-goal).

Persistence facts that constrain the choice. In *both* directions the wrapped
XRef entry persists three fields (`relation`, `matrix`, `row_keys`;
`column_keys` is a Resolution facet stripped at the boundary). Exactly *one*
persistent field dangles per direction -- the field naming the internal
long-form temp frame: `relation` on expand and `relation` on contract. The
other frame field names a *real public frame* (`matrix` = the public source
matrix on expand; `matrix` = the public output matrix on contract). Critically,
the internal temp frame is a *different shape* from any surviving public frame:
the XRef long-form relation (a `value`-column frame) only ever exists as the
internal temp; the composite's public long-form (`output` on expand) is the
*codec-decoded* `code`-column frame, and the composite's public relation input
(`relation` on contract) is the *pre-encoding* `code`-per-row frame. Neither is
a valid bare-XRef `relation` for the composed leg.

* *Option A -- suppress the internal XRef metadata entry for the composed leg.*
  XRef exposes no `emit_meta=False` option today, so the mechanism is a narrow,
  feature-owned post-delegation action: the composite snapshots
  `_meta.xref_crosstable[config_id]` before delegating and, after the delegated
  frame work succeeds, restores that field to its *pre-delegation* value
  (prior entry if one existed, else absent). This removes the internal leg's
  temp-referencing write while (a) leaving *bare* XRef usage completely
  unchanged, (b) preserving any legitimately caller-supplied XRef entry for the
  same id, and (c) leaving the reverse column-order fallback intact *within the
  call* (the composite's `contract_xref` reads any pre-existing entry before the
  composite restores state). Truthful: it asserts no false public inverse
  intent.
* *Option B -- project XRef metadata to public composite frames.* Rewrite the
  dangling `relation` to a surviving public frame. Rejected as *misrepresentation*:
  there is no public frame that is a valid bare-XRef `relation` for the composed
  leg (shape mismatch above). Rewriting `relation` to `output` (expand) or to
  the caller `relation` (contract) would tell a generic XRef consumer "contract
  this frame to recover the matrix," which is false -- the codec must
  re-encode/decode first. A projected entry would be *plausible-looking but
  wrong* inverse intent, which is worse than a dangling but inert reference.
* *Option C -- remove the internal XRef entry and let the compact trace explain
  the composition.* Directionally similar to Option A but forbidden in its
  literal form: the compact trace is diagnostics-only and must not become
  operative inverse intent to compensate. The reverse composite is already
  driven by explicit reverse configuration (`column_keys`, `canonical_order`,
  `fill_value`, `column_key`, `value`) plus XRef's own last-resort
  relation-value derivation, so removing the internal XRef entry does not
  require the trace to carry intent. Option A is Option C's disciplined form:
  restore-to-prior rather than unconditional delete, so caller-supplied entries
  survive.
* *Option D -- other.* No repository evidence supports a narrower
  contract-preserving alternative.

*Recommendation: Option A (feature-owned suppression by restore-to-prior).*
After successful delegation, the composite restores
`_meta.xref_crosstable[config_id]` to its pre-delegation state, so the composed
internal XRef leg persists no entry (and no temp-referencing `relation`). This
is the smallest change that preserves the accepted XRef contract and is
truthful about ownership. Required explanations:

* *Metadata ownership.* XRef remains the sole owner of `_meta.xref_crosstable`;
  the composite never fabricates or edits XRef fields -- it only reverts the
  entry its internal leg produced, restoring the caller's prior state.
* *Whether the XRef root remains necessary after the composite returns.* No. For
  a composed leg there is no valid public bare-XRef relation, so a persisted
  XRef inverse-intent entry for that leg has no legitimate consumer; the
  composite's public inverse is `contract_compact_multiaxis` driven by explicit
  configuration.
* *Effects on XRef column-order fallback.* The bare-XRef fallback is unchanged.
  The composite's reverse column order remains governed by explicit
  `column_keys`/`canonical_order`, with XRef's relation-value derivation as the
  deterministic last resort. The only facet removed is an *in-run,
  non-persistent* (`column_keys` is boundary-stripped) same-run carry between a
  composite expand and a later composite contract sharing a `config_id` -- the
  muddy CM-8 path; a test must pin the post-correction behavior.
* *Effects on forward/reverse roundtrips.* Unchanged: XRef and codec still run
  with full validation each direction; only the persisted XRef entry for the
  internal leg is reverted after success.
* *Interaction with repeated runs under the same `config_id`.* Deterministic:
  each run restores the pre-delegation XRef state, so no temp-referencing entry
  ever accumulates and repeated runs converge to the same persisted state.
* *Persistence behavior.* No `_meta.xref_crosstable` entry describing an internal
  composed leg is persisted; structured persistence and the workbook carrier
  therefore carry no temp-frame reference.
* *Schema-maintenance behavior.* Removing the temp-referencing XRef entry
  removes the only place `_meta.xref_crosstable[*].relation` named a
  non-existent frame; the real XRef blocked-root handler (which the assessment
  confirms is feature-aware) then sees only truthful public references.
* *Compatibility risk.* Low. The removed entry is inert today (no consumer
  reconstructs from it). The bare XRef and bare Cell Codec contracts are
  untouched. Callers who supplied their own `xref_crosstable[config_id]` entry
  keep it (restore-to-prior). The only observable change is the disappearance of
  a dangling, never-read field.

*Diagnostics trace field-level contract:*::

Target contract for `_meta.compact_multiaxis[config_id]`. The trace records a
*truthful explanation of the executed high-level configuration*, not a raw dump
of irrelevant defaults, and never operative inverse intent. For values the
runtime normalises, the trace records the *effective normalised value actually
executed* (this is what "explains the executed configuration" means); it records
the *authored* value only where no normalisation occurs. No trace field may name
an internal temporary frame (already true; add a guard test).

Decisions the contract fixes:

* *Authored vs effective.* Record the *effective normalised* value for every
  field the runtime normalises or defaults (`mode`, `delimiter`, `strip`,
  `row_keys`, selectors, `code_groups` normalised keys), because the trace's
  job is to explain the *executed* configuration. Record the *authored* value
  (with `None` sentinel) only for `value_columns`/`column_keys`/`canonical_order`
  where the effective order is XRef Resolution state the trace must not
  duplicate.
* *No inverse-intent promotion.* The trace must remain non-operative: no runtime
  transformation may read it as configuration, inverse intent, or fallback. A
  guard test asserts a conflicting trace cannot alter explicit behavior.
* *Minimisation.* The contract may drop a field only if it is neither useful
  diagnostics nor needed for roundtrip explanation; this slice retains the
  current field set (all fields explain the executed configuration) and instead
  fixes the *description* of the root, rather than trimming fields, to keep the
  change narrow. Any future trimming is out of scope here.

*Trace replacement and prune lifecycle:*::

Repository mechanisms assessed for trace rename/drop ownership:

* *Schema maintenance* (`schema_maintenance/meta_update.py`,
  `meta_refs.py`): operates on *column* rename/drop and blocks references; it has
  no *frame*-rename or *config-instance*-removal trigger. It cannot remove or
  migrate a whole `compact_multiaxis[config_id]` trace.
* *Explicit metadata pruning* (`request.prune` on `DROP_COLUMN`): prunes
  column-list references within some roots; not a config-id removal surface.
* *Pipeline cleanup* (`pipeline_cleanup.py`): explicitly *preserves* the
  `compact_multiaxis` and `xref_crosstable` intent families unchanged; it never
  removes per-config entries.
* *Feature-local rename/drop commands*: none exist for Compact Multiaxis
  (contrast `fk_helpers/drop.py::drop_helpers`, which is FK-scoped).
* *Existing prune transformations*: column-scoped only.

*Same-`config_id` replacement is already correct* (verified above):
`_write_multiaxis_meta` copies the prior `configs` mapping and assigns the single
`config_id` key, so a rerun atomically replaces its own entry, no historical
list accumulates, and other IDs coexist untouched. This slice adds tests to lock
that behavior; it changes no replacement code.

*Explicit removal/migration: no appropriate lifecycle surface exists today.*
Selected outcome (Decision 3): **outcome 3 -- correct/confirm replacement
semantics now and record a tightly scoped follow-up FTR for explicit
removal/migration.** Rationale and reconciliation:

* Inventing a broad generic staleness/GC mechanism is forbidden (non-goal); no
  existing surface owns config-instance trace removal; adding a new
  prune/rename command is scope creep for a narrow metadata-truthfulness slice.
* Because the trace is declared *non-authoritative and never consumed*, a stale
  trace after an instance rename/drop misleads only a human/agent reader, not
  the runtime -- residual risk is bounded to *diagnostic staleness*, not
  correctness. This is acceptable to defer explicitly.
* The follow-up FTR (title reserved below) owns a narrow, feature-local
  `drop`/`rename` surface for `compact_multiaxis[config_id]` traces, keyed by the
  stable `config_id`, with no inference from absence-in-run or frame existence.
* If, during implementation, the minimal feature-local drop-by-`config_id`
  command proves trivial and self-contained, the implementer *may* fold it into
  this slice instead of deferring; the default is defer.

Follow-up reserved: `FTR-COMPACT-MULTIAXIS-TRACE-LIFECYCLE-COMMANDS-P5`
(explicit `config_id`-keyed diagnostics-trace drop/rename; no generic staleness
inference).

*Schema-maintenance policy:*::

Selected target (from the four options): **target 3 -- declare
`_meta.compact_multiaxis` non-authoritative and exclude it from
schema-maintenance blocking, with the explicit trace lifecycle above preventing
misleading stale records.** Rationale:

* The root is diagnostics-only and never consumed; blocking a column
  rename/drop because a *descriptive, unread* trace mentions the column provides
  no real protection and is vacuous today anyway (CM-3: the block never fires
  against the real payload).
* Retaining a vacuous blocked-root registration "for appearances" is explicitly
  disallowed. Making the block *fire* (target 1/2) would newly block edits on
  behalf of a root nothing reads -- a regression in edit ergonomics for zero
  correctness benefit.
* Reconciliation with the prune/rename lifecycle: excluding the root from
  blocking is consistent with outcome 3 above -- the trace is non-authoritative,
  its staleness is a diagnostic (not correctness) concern, and the reserved
  follow-up owns explicit removal/migration.

Concrete change: remove `compact_multiaxis` from `BLOCKED_ROOTS_BY_NAME`
(`meta_refs.py:59`) and its `ReferenceRoot.COMPACT_MULTIAXIS` blocked handling
(or move it to the out-of-scope / non-blocking classification consistent with
how unread descriptive roots are treated), and delete/replace the fabricated
`{frame,value_column}` test at `test_metadata_refs.py:450-467`. Tests must use
the *real* producer payload shape (keys `operation`/`matrix`/`output`/`relation`/
`row_keys`/`column_key`/`value`/`code`/... as emitted by `_write_multiaxis_meta`),
asserting a column rename/drop is *not* blocked by the compact trace. No
fabricated `{"frame": ..., "value_column": ...}` surrogate may remain.
