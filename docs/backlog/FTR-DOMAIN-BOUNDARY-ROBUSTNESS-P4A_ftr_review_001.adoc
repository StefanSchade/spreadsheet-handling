== Verdict summary

The refined FTR is ready for implementation as a bounded, documentation-only
Slice 1. It states a proportionate threat-model boundary, balances framework and
workflow-builder responsibility without letting either excuse the other,
distinguishes validation robustness from process isolation, constrains
adversarial review without suppressing correctness findings, defines
semantic-DRY criteria that create no premature helper, and names exact
documentation owners. No runtime change is authorized. Residual items are
open implementation decisions, not blockers.

This review covers only the FTR text and its intended documentation scope. It
does not review or authorize any runtime code.

== Relation to the application-boundary inquiry

`app_boundary_meta_authority.adoc` is human-authored working context, not a
contract. Its stable, promotable parts are the framework-vs-workflow-builder
responsibility split, external-artifact trust ("framework-shaped metadata is not
authoritative merely by existing"), and the runtime-resolution/lifecycle
distinction. The FTR correctly (a) promotes the responsibility split and
external-artifact trust into level 3 of its taxonomy, (b) delegates the deeper
external-artifact and entity-lifecycle policy back to that inquiry rather than
absorbing it, and (c) does not edit the cold-storage source. The
runtime-resolution vs persistence question is left to its existing owners
(persistence boundary, `FTR-META-LIFECYCLE-INVENTORY-P5`), which is the correct
non-duplication call.

== Relation to the Axis Mapping review experience

The FTR generalizes the Axis Mapping history without copying it. The concrete
mechanisms (arbitrary comparators, `type(value).__name__` diagnostics, the
`longlong`/`ulonglong` gap, retained `tuple` subclasses, narrow `ValueError`
translation, the `_column_positions`/`_resolved_labels` helpers) appear only as
generalized principles, not as FTR content. The most important lesson is faithfully
captured: acceptance rounds 001->002 escalated the applied threat model on a
single internal resolver, and round 003 explicitly deferred the repo-wide
question to "the planned Domain Boundary Robustness clarification" -- i.e. this
FTR. The FTR's review policy directly targets that escalation pattern.

Cross-check on balance: Axis Mapping review 002 also produced *genuine*
correctness findings via adversarial probes (effective-immutability break through
a retained mutable-hash tuple; a real incomplete-vocabulary defect). The FTR's
review policy must not, and does not, suppress these -- see finding F4.

== Findings

=== Blocking

None.

=== Important (addressed during refinement)

F1 -- responsibility balance previously one-sided::
The initial proposal listed framework responsibilities and non-responsibilities
but omitted the guardrail that workflow-builder responsibility must not excuse
ambiguous behaviour, silent coercion, hidden mutation, weak diagnostics, or
inconsistent contract interpretation. Without it, "user responsibility" can be
read as cover for weak framework contracts -- an explicit anti-goal of this work.
Resolved: the refined "Framework responsibility" subsection states the guardrail
directly.

F2 -- artifact ownership was underspecified::
The initial proposal named four artifact *types* but not exact paths, nor which
artifact owns normative rules versus rationale versus examples versus reviewer
guidance. Resolved: an ownership table gives exact paths (ADR for rationale, a
new `ch04_concepts` concept for normative rules, a new `ch06_code_conventions`
file for examples, an appended `review_instructions.adoc` section for reviewers)
and the registration steps (`_adrs.adoc`, `_concepts.adoc`, chapter `include::`).

F3 -- no reconciliation with settled contracts::
The initial proposal risked duplicating or contradicting existing decisions.
Resolved: a "Relationship to existing contracts" section positions the FTR
against `ADR-DOMAIN-OWNS-VALIDATION-WRITERS-STAY-DUMB` (this FTR says how robust
domain validation must be, not where it lives),
`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` (carrier payload typing vs in-memory
value-object boundaries), and the persistence/Intent-vs-Resolution boundary
(persistence vs in-memory ownership).

F4 -- review policy could read as suppressing correctness findings::
Resolved: the refined review policy states a review *may and must* still report a
concrete violation of an explicit contract even when the probe is adversarial,
and that the policy "must never be cited to suppress" such findings. This keeps
the Axis Mapping-style genuine adversarial findings legitimate while blocking
silent threat-model expansion.

=== Minor

F5 -- length and repetition::
The initial proposal was ~550 lines with overlapping principle/pattern/acceptance
restatements. Reduced to ~300 lines by merging the robustness principles into one
list, compacting the taxonomy, and stating each acceptance criterion once. No
normative content was lost.

F6 -- semantic-DRY lacked a "now" decision::
Resolved: the FTR states that Axis Mapping searches found no second consumer of
the exact configured-field-reference, safe-diagnostic-detail, or exact-NumPy
contracts, so no runtime extraction is justified by this FTR, and names
`domain/tabular` as the likely future home only if a second consumer appears.

=== Observations / residual (for implementation, not blockers)

* O-1 -- normative home choice. `ch02_contracts/01_contracts.adoc` is a `TBD`
  stub. The FTR routes normative rules to a new `ch04_concepts` concept file,
  matching the chapter that already holds real cross-cutting concept content, and
  deliberately does not open the empty contracts chapter in this slice. Reasonable;
  flagged so implementation confirms the placement.
* O-2 -- ADR vs concept split. The FTR recommends a separate short ADR and
  concept but allows folding the concept into the ADR's Decision section. Left as
  an explicit implementation decision (open question 1).
* O-3 -- four artifacts is the upper bound for a "minimum" set. Justified because
  each has a genuinely distinct owner (rationale / normative / examples /
  reviewer), and each is small. If the ADR+concept merge is taken (O-2), the set
  drops to three.

== Assessment against the Phase 1 questions

. Repo-wide vs Axis-specific: the responsibility split, threat-model
  proportionality, ownership/diagnostics/atomicity/readability principles,
  semantic-DRY criteria, and review policy are repo-wide; Axis-specific mechanics
  are correctly demoted to generalized evidence.
. Pre-existing principles: framework/user split (cold-storage inquiry),
  domain-owns-validation (ADR), string substrate (ADR), Intent-vs-Resolution
  (persistence boundary) all pre-exist and are now referenced rather than
  restated.
. Taxonomy: the four levels are useful; the FTR names the load-bearing
  distinction (level 1 assume vs level 4 do-not-contain) and notes levels 2/3
  overlap, which prevents over-reading the taxonomy as four hard tiers.
. Threat model: explicit, proportionate, and paired with an explicit statement
  that cheap simplifying hardening remains in scope -- so the boundary is not a
  licence to under-harden.
. Isolation vs validation: clearly distinguished ("validation robustness is not
  process isolation").
. Review constraint vs correctness: balanced (F4).
. Slice size: bounded, documentation-only, testable by inspection/rendering.

== Runtime / non-runtime boundary (endorsed)

Slice 1 is documentation-only. Existing code may be inspected as evidence but not
changed. No universal safe-value framework, exact-type refactor, field-selection
rewrite, broad exception-wrapper utility, or helper migration is authorized. Any
future extraction requires its own FTR with a demonstrated second consumer. This
matches the Axis Mapping reviews' explicit "no second consumer found" conclusion.
