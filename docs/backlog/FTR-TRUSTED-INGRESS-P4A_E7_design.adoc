= FTR-TRUSTED-INGRESS-P4A -- E7 Less-Trusted Description Authorization Design
:toc: left
:toclevels: 3

Narrow design for `E7 -- less-trusted description authorization`, the
Phase-E completion slice.  This artifact selects the concrete E7 mechanism;
it does not implement that mechanism, start E7 runtime work, independently
accept this design, complete Phase E, or perform lifecycle curation.

== 1. Scope and accepted authority

Starting lifecycle HEAD: `151db64c76f602402e71d96618568e3128feb72d`
(`docs(trusted-ingress): satisfy E7 extension-architecture prerequisite`).

The governing contract is `FTR-TRUSTED-INGRESS-P4A.adoc`, especially its
pipeline-description trust plane, E7 slice, compatibility/migration section,
and Phase-E scope/defer matrix.  E7's exact accepted scope is:

[source,text]
----
define and implement operator-owned authorization for the supported
declarative surface, with rejection before import/binding/acquisition
----

The independently accepted dotted-extension architecture assessment, its
independent review, and its accepted correction follow-up freeze the eight
surface decisions and six capability kinds used below.  This design does not
reopen those decisions.  `ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY` Decisions
1--5 govern trusted-runtime assumptions, independent payload/description
authority, operator policy ownership, per-kind combination, pre-activation
rejection, and separate sink ownership.  The accepted E6 implementation review
governs the programmatic-surface split.  `interfaces_and_gates.adoc`, the
Phase-E roadmap, and current Project Memory corroborate the lifecycle state.

E1--E6 remain independently accepted and form the independently accepted
Phase-E Payload-Conformance Milestone under the current trusted-description
precondition.  The Dotted-Extension architecture remains independently
accepted.  E7 is current but unimplemented; Phase E remains open.

No new ADR is required.  This design chooses a concrete representation and
enforcement seam inside already-accepted policy authority; it discovers no new
architectural axis and no prerequisite runtime refactor.

=== 1.1 In scope

* An additive trusted-description / less-trusted-description distinction.
* A small operator-owned, closed, immutable authorization value.
* Positive authorization for exact registered short names and exact canonical
  plugin targets.
* Closed parameter policy for the four currently evidenced resource-touching
  registered steps.
* Rejection before the first governed import, factory call, target acquisition,
  binding, external-resource acquisition, or invocation, as applicable.
* Narrow programmatic transport into builders and framework-managed execution.
* Safe diagnostics and implementation tests.

=== 1.2 Exclusions

* Python, process, container, or plugin sandboxing.
* Payload scalar/carrier changes, payload-policy knobs, or a combined security
  level.
* General filesystem, network, environment, subprocess, formula, or sink
  policy outside the selected E7 registered-step capability contracts.
* Top-level input/output sink authorization.  The trusted operator continues
  to own I/O descriptors; E7 governs pipeline-description-selected step
  capabilities only.
* Generic recursive plugin-argument policy or target-specific plugin schemas.
* Roles, users, groups, policy languages, policy profiles, inheritance,
  capability graphs, or a general IAM/security framework.
* Lifecycle curation, release notes, Project Memory updates, adoption-repo
  changes, and the separate extension-contract publication FTR.

== 2. Current construction and activation topology

Current source establishes the following order:

[source,text]
----
sheets-run
  -> parse config/steps YAML
  -> build_steps_from_yaml or build_steps_from_config
     -> resolve_registration(step_id)
     -> registration.factory(**kwargs)
     -> plugin/internal/nested target resolution and import while binding
  -> orchestrate(pre-bound steps)
     -> load payload
     -> E1-E3 initial establishment
     -> E4/E5 managed step execution
     -> cleanup/projection/save

load_app_config
  -> inert AppConfig, including an unbound pipeline list

run_app(AppConfig)
  -> build_steps_from_config(app.pipeline)
  -> orchestrate(pre-bound steps)
  -> load payload and execute the same managed macro
----

`pipeline.build.build_steps_from_config` currently copies each step mapping,
removes `step`, checks parameter-key strings, calls
`registry.resolve_registration`, injects a registration-owned target over any
configured `target`, and calls the selected factory.  Activation already occurs
inside this build phase:

* `step: plugin` calls `resolve_configuration_callable(dotted)` as the first
  operation of `make_plugin_step`; that resolver parses, imports, acquires the
  attribute, and checks callability.
* An unregistered colon-bearing `step` causes `resolve_registration()` itself
  to call the dotted resolver and import the selected factory.
* Generic binders resolve a configured or registry-owned string `target` while
  constructing the `BoundStep`.
* Direct callable targets and already-created `BoundStep` objects need no
  description-derived resolution.

Therefore policy supplied only to `orchestrate(..., steps=prebound_steps)` is
too late.  E7 authorization belongs in description construction, while the
trusted application entry owns selecting and transporting that construction
mode.  Payload load and E1--E6 remain later and independent.

Schema maintenance constructs its private `_schema_maintenance_private`
`BoundStep` in trusted application code.  The compatibility orchestrator shim
is an alias of the application orchestrator.  `run_pipeline` only invokes
already-bound steps and remains intentionally unwired.

== 3. Trust-mode contract

=== 3.1 Representation and selection

E7 uses one explicit value-object variant:

* `authorization=None` means *trusted description*.  This is the existing
  default and takes the existing construction path without policy checks.
* `authorization=LessTrustedDescriptionAuthorization(...)` means
  *less-trusted description*.  The value itself contains the complete positive
  operator policy.  An empty value authorizes no step or plugin target.

There is no separate boolean or enum.  Consequently mode and policy cannot
diverge: less-trusted mode cannot exist without a concrete fail-closed policy,
and trusted mode does not pass through a pretend allow-all policy.  The
trusted operator selects the variant through a Python call argument outside
the description.  The pipeline YAML/config mapping has no field that can
construct, replace, weaken, or remove this value.

The absence default is required for compatibility: every current caller that
does nothing retains trusted-description semantics.  A caller deciding that
external description content is less trusted must positively construct and
pass the value; E7 cannot protect a caller that falsely labels external input
as trusted, just as the governing ADR does not protect against the trusted
operator.

=== 3.2 No description-owned request vocabulary

Initial E7 selects Option A from the design question: the description exposes
*no* narrowing or policy-request shape.  No maintained use case justifies a
profile name, requested allowlist, or requested resource limit.

Accordingly there is no operator-policy/description-policy merge.  ADR
Decision 4 remains controlling for any future evidenced request kind, but E7
does not invent one merely to exercise intersection.  Keys such as
`description_authority`, `description_authorization`, or
`description_policy` at the step-spec level are reserved and reject in
less-trusted mode as invalid policy requests; the same text nested inside a
plugin's `args` remains target-local data and never affects E7.  A same-file
top-level key ignored by an existing parser likewise grants nothing: mode and
policy arrive only through the separate operator argument.

=== 3.3 Fail-closed default

Less-trusted mode is fail closed:

* no registered step is permitted without an exact operator-policy entry;
* no plugin is permitted without an exact canonical target entry;
* direct-colon and nested configured targets are never permitted;
* a resource-touching step must also satisfy its complete selected resource
  contract; and
* an unclassified current or future registration is unavailable to
  less-trusted descriptions even if its name appears in caller input.

Trusted mode preserves the complete current behavior, including plugins,
direct-colon factories, nested targets, direct Python targets, and registry
binding.

== 4. Operator-policy representation and lifetime

=== 4.1 One narrow public value

`LessTrustedDescriptionAuthorization` is a supported programmatic value with
one stable construction operation, conceptually:

[source,python]
----
LessTrustedDescriptionAuthorization.from_mapping(
    {
        "registered_steps": {
            "identity": {},
            "apply_overrides": {},
            "write_structured_yaml": {
                "output_roots": ["/srv/operator/generated"],
            },
            "write_artifact_manifest": {
                "output_roots": ["/srv/operator/generated"],
                "allow_checksum_reads": False,
            },
        },
        "plugin_targets": ["operator_plugins.cleanup:clean_frames"],
    }
)
----

This is a Python data contract, not a new policy-file format.  Initial E7 adds
no CLI flag, environment variable, profile, or policy parser.  The trusted
application/operator creates the value.  The value is narrowly exported from
`spreadsheet_handling.pipeline`; internal capability/constraint enums are not
exported.

The external construction grammar has exactly two top-level fields:

[cols="2,3,4"]
|===
| Field | Shape | Meaning

| `registered_steps`
| mapping from exact registered short name to an exact constraint mapping
| Positive per-name authority.  Absence denies.  `plugin` is not legal here;
  it uses `plugin_targets`.

| `plugin_targets`
| collection of dotted-reference strings
| Positive exact canonical plugin-target authority.  Absence/empty denies all
  plugins.
|===

Unknown top-level fields, unknown/unregistered step names, `plugin` in the
registered map, unknown constraint fields, wrong shapes, duplicate/conflicting
canonical entries, and a constraint shape not owned by that exact step reject
when the operator value is constructed.  Direct-factory identifiers and
framework lifecycle names are not representable as policy entries.

=== 4.2 Immutable effective snapshot

The public value is frozen and slot-based and owns disconnected immutable
state: registered mappings are copied into owned immutable mappings; target
collections and root collections become `frozenset`/tuple values; nested
constraint input is copied; plugin identifiers and roots are canonicalized
once.  A caller-retained dict, list, set, mapping proxy, or nested alias cannot
widen the stored value later.

At every less-trusted build entry, the implementation requires the exact
public value type and derives a fresh private effective snapshot from its
closed stored fields.  It does not accept subclasses or arbitrary policy
callbacks.  The same snapshot is used for every step in that one description
build.  This repeats E4's important lesson: authorization and later binding
must read the same immutable effective facts, not separately mutable views.

The less-trusted builder also takes an owned recursive snapshot of exact
built-in description containers before classifying them.  Authorization and
binding use that same owned snapshot, so mutation of a caller-retained nested
list/dict after authorization begins cannot swap a resource selector or target
before binding.  This is description-data stability, not a hostile-Python
sandbox; less-trusted declarative input is limited to safe parsed/built-in
container shapes.

The effective policy is needed only until all description-derived `BoundStep`
objects have been constructed.  It is not stored in mutable config dicts, not
attached as a descriptive flag to `BoundStep`, and not required by E5 after
construction.  Resource steps retain and execute their already-existing
closed bound parameters and containment checks.  An implementation may retain
a safe summary for diagnostics, but no mutable or authorizing object survives
as hidden runtime state.

== 5. Capability-policy vocabulary

E7 preserves all six accepted kinds but grants policy entries only for the
first two.  The third is categorically denied and kinds 4--6 cannot be made
user-authorizable.

[cols="3,3,4"]
|===
| Accepted capability kind | E7 policy representation | Disposition

| Registered framework capability
| exact short-name entry plus the exact step-owned constraint mapping below
| Positive authorization before factory, internal target import, binding, or
  invocation.

| Arbitrary plugin callable invocation
| exact canonical target in `plugin_targets`
| Positive authorization before resolver/import/acquisition.  Authorized
  Python remains unsandboxed trusted code once invoked.

| Compatibility dynamic callable construction/acquisition
| none
| Direct-colon factory and its nested configured target route are denied to
  less-trusted descriptions before `resolve_registration()`.

| Internal framework callable acquisition
| none
| Registration-owned target is trusted internal wiring after short-name
  authorization, not a second request.

| Trusted direct-Python composition
| none
| Direct callable and direct `BoundStep` composition remain trusted
  programmatic APIs outside E7.

| Framework lifecycle capability
| none
| Fixed macro phases and application-private composition remain
  non-addressable/non-reorderable by description.
|===

An internal, package-complete classification table covers every runtime
`REGISTRY` name other than `plugin` with exactly one of four closed parameter
contracts:

* `ordinary` -- no E7 authority-widening resource selector;
* `inline-overrides-only` -- `apply_overrides`;
* `root-contained-writer` -- `write_structured_yaml` and
  `write_key_value_resources`; or
* `artifact-manifest` -- `write_artifact_manifest`.

Every current name must appear exactly once.  A new registry entry is denied in
less-trusted mode until this classification and its tests are deliberately
updated.  This is a small coverage guard, not a generic effect system and not
new public registry metadata.

== 6. Per-capability authorization

=== 6.1 Registered short names

The authorization identifier is the exact `step` string.  The less-trusted
builder first requires an exact string, recognizes `plugin` separately, and
performs an import-free exact lookup in `REGISTRY`.  Unknown names report
`unknown_capability`.  Registry membership establishes vocabulary only; the
effective operator mapping must also contain that exact name.

The decision order is:

[source,text]
----
validate step-spec shell and exact string step id
-> identify plugin / registered / direct-colon / unknown without import
-> for registered: look up internal E7 parameter contract
-> require exact operator short-name entry
-> validate and authorize authority-relevant selectors
-> only then obtain the StepRegistration, inject its target, call its factory,
   resolve/import the registry-owned target, and bind the BoundStep
----

An `ordinary` entry has an empty constraint mapping.  Any resource constraint
on an ordinary step is incomparable with its contract and rejects.  Positive
name authority grants that step's current documented parameter surface; E7
does not attempt to infer general security meaning from every other parameter.

=== 6.2 Plugin targets

The plugin description must have an exact string `dotted` field.  A new pure,
import-free canonicalizer in `pipeline.dotted_paths` uses the resolver's one
accepted parser and ownership check, returning the textual form
`module.path:attribute`:

* `package.module:function` remains that canonical text;
* supported final-dot `package.module.function` canonicalizes to
  `package.module:function`; and
* malformed, whitespace-bearing, multi-colon, missing-module, missing-
  attribute, and framework-internal references reject before import.

Both operator entries and description identifiers use this same canonicalizer.
Thus colon/final-dot spelling cannot bypass the allowlist.  Authorization is
textual identifier authorization, not proof of Python callable identity.
Aliases and re-exports have different canonical text and require separate
operator entries; authority does not follow an imported object automatically.

Initial E7 authorizes plugins by exact target only.  The `args` mapping is not
examined for filesystem/network/etc. meaning, because arbitrary plugin code
may interpret any value as authority.  Exact-target authorization therefore
means the operator accepts that target under its complete current argument
surface.  If that is too broad, the operator must omit the target.  The policy
grammar accepts no plugin constraint mapping; a caller attempting to supply
target-specific constraints receives `invalid_policy` rather than a false
claim that E7 enforced them.  A later evidenced target contract may add a
closed target-specific kind under separate design.

After exact authorization, and only then, the existing
`resolve_configuration_callable()` imports/acquires the target and the existing
plugin factory binds it.  Invocation remains inside ordinary E5 managed
execution when using a framework-managed entry.

=== 6.3 Direct colon factory and nested configured target

For a non-registered colon-bearing `step_id`, less-trusted construction
rejects `forbidden_capability` *before calling* `resolve_registration()`.
That exact ordering is load-bearing because `resolve_registration()` imports
the selected factory inline today.  The smallest implementation is an inert
classification helper used by `build_steps_from_config`: it distinguishes the
exact registered-name hit, exact `plugin`, colon-bearing compatibility form,
and unknown name without resolving any callable.  It does not split or replace
the accepted resolver architecture.

The only current nested configured string-target route is inside the outer
dynamic-factory expert route.  Denying the outer route before import therefore
denies its nested target too.  Registered targets overwrite configured
`target`, and plugin's frames-first calling convention does not create a
second binder route.  No nested-target policy vocabulary is added.

Trusted mode continues through current `resolve_registration()` behavior, so
direct-colon and nested-target compatibility is unchanged and not deprecated.

=== 6.4 Registry-owned targets

Once a registered short name and its relevant parameters are authorized, the
`StepRegistration.target` value is framework-owned wiring.  The implementation
injects that target only after authorization and then lets the current generic
binder resolve it.  It does not canonicalize or compare the internal target
against plugin policy, and the operator never allowlists Core implementation
paths separately.

This ordering makes the distinction structural: consumer data selects the
short name; trusted registry data supplies the implementation target only
after that selection is authorized.

=== 6.5 Direct Python and pre-bound steps

Direct callable targets and caller-created `BoundStep` values do not pass
through the less-trusted-description builder.  They remain trusted
programmatic composition.  `orchestrate(..., steps=prebound_steps)` and
`run_pipeline(frames, prebound_steps)` retain accepted E6 semantics.

The new configured orchestrator route uses a separate `step_specs` parameter.
`steps` and `step_specs` are mutually exclusive, and an authorization value is
accepted only with `step_specs`.  Provenance is therefore selected by the
entry variant; it is never inferred from the shape of a `BoundStep`.

=== 6.6 Framework lifecycle

E7 exposes no entries for initial ingress, final cleanup, persistence
projection, sink authorization, private schema-maintenance steps, or phase
ordering.  Those remain fixed application flow.  If an exact underlying
function is separately reachable as an authorized plugin target, E7 governs
that plugin-code selection; it does not grant the description authority to
move, replace, or reorder the framework-owned lifecycle phase.

== 7. Resource-selector policy

=== 7.1 Shared path preparation and guarantee

E7 introduces no generic filesystem policy.  It uses one exact-output-root
primitive only for the three evidenced writer registrations.

Operator `output_roots` entries must be exact path strings that are absolute
after `expanduser`.  During policy construction each is expanded and resolved
with `Path.resolve(strict=False)` and stored as a canonical absolute path.  It
need not exist.  A less-trusted
description's exact-string `output_dir` is resolved the same way; a relative
value is anchored to the trusted process working directory captured once at
build entry.  After authorization the owned step snapshot carries the
canonical absolute `output_dir`, so later binding/execution cannot reinterpret
it under a changed working directory.

An output directory is authorized only when its canonical path equals one of
that exact step's operator roots.  E7 does not treat an operator root as a
parent under which the description may choose arbitrary second-level roots.
Once the exact root is selected, subordinate static or pattern/payload-derived
paths are governed by that step's current resolved containment check.

Static subordinate paths are parsed without opening them, required to be
relative, resolved with `strict=False` below the selected root, and required
to remain relative to that root.  Existing symlinks are followed by
canonicalization, so an existing link resolving outside the root rejects.
Files/directories need not yet exist.  Opens, reads, writes, `mkdir`, and
target factory invocation happen only after authorization.

This is a framework-level resolved-path guarantee under ADR Decision 1's
trusted operator/runtime/filesystem precondition.  It is not descriptor-based
OS isolation and does not claim resistance to a concurrently hostile process
swapping symlinks between check and use.  Authorized plugin Python is likewise
not contained by these roots.  Current writer primitives repeat containment
during execution before opening a selected target; E7 neither weakens nor
generalizes those checks.

=== 7.2 Exact per-step rules

[cols="3,2,2,3,4"]
|===
| Registered step | Selector | Direction | Operator-policy shape | Decision and activation boundary

| `apply_overrides`
| `overrides_path`
| uncontained arbitrary file read under process-user OS permissions
| no path field is supported; the step's policy entry must be `{}`
| In less-trusted mode `overrides_path` must be absent or exactly `None`.
  Any supplied path, including empty/relative/absolute, rejects before the
  internal target import, binding, `Path.exists`, or open.  Inline `overrides`
  remains available when the exact step name is authorized and is still
  subject to its existing metadata/managed-flow validation.

| `write_structured_yaml`
| `output_dir`; every `files[].path`
| write under exact output root
| exactly `{"output_roots": [absolute roots...]}`; non-empty
| Canonical `output_dir` must equal an allowed root.  `files` must expose a
  built-in sequence of mapping specs and every exact-string `path` must be a
  resolved as contained by that root before binding.  Current target
  containment repeats at execution before `mkdir`/open/write.

| `write_key_value_resources`
| `output_dir`; `file_pattern` rendered with payload group values
| pattern-derived writes under exact output root
| exactly `{"output_roots": [absolute roots...]}`; non-empty
| Canonical `output_dir` must equal an allowed root and `file_pattern` must be
  an exact string before binding.  The complete target path cannot exist until
  payload grouping; operator authority intentionally grants pattern-derived
  writes *within that exact root*.  The current target resolves and contains
  every rendered path before directory creation/open, rejecting absolute,
  traversal, or payload-derived escape.

| `write_artifact_manifest`
| `output_dir`; `manifest_path`; report-row `path`; `checksum`
| optional manifest write and optional checksum-triggered reads under exact
  output root
| `{}` for in-memory-only use, or
  `{"output_roots": [...], "allow_checksum_reads": bool}`; roots non-empty
  when present; boolean defaults false
| With no `output_dir`, both `manifest_path` and `checksum` must be absent/None
  and the step is in-memory only.  Any `output_dir` must equal an allowed root.
  A supplied exact-string `manifest_path` must be relative/contained before
  binding.  `checksum` may be only absent/None or `sha256`; `sha256` additionally
  requires `allow_checksum_reads=True`.  At execution current code validates
  every payload/report-derived artifact path under the selected root before
  reading and validates the manifest target before writing.
|===

=== 7.3 Artifact-manifest checksum decision

Checksum reads are an evidenced distinct optional authority and therefore use
one boolean subpermission, `allow_checksum_reads`.  This is not a second path
vocabulary: the same exact authorized `output_root` bounds both manifest writes
and checksum reads.  The boolean prevents a description authorized merely to
write a manifest from silently enabling reads of arbitrary existing files
named by report rows under that root.  Combination is conjunction:

[source,text]
----
authorized write_artifact_manifest short name
AND exact authorized output root
AND checksum is a supported value
AND allow_checksum_reads (when checksum == sha256)
----

The checksum implementation reads raw bytes only after report-path
normalization/containment.  It may read files that were not created during the
current run; that fact is part of the explicitly granted boolean capability.

=== 7.4 Why no `overrides_path` root or exact-file policy

Current `load_overrides` uses `Path(path)` directly and has no root contract.
Adding a second path-containment mechanism solely in E7 would create a new
semantic split with the underlying primitive and invite symlink/TOCTOU claims
the current function does not make.  Exact-file authorization would likewise
add path policy only for a zero-adoption less-trusted use case.  The smallest
truthful initial contract is therefore: permit the useful inline form when the
step name is allowed, and categorically reject the uncontained path selector.

This is a final E7 decision, not a deferral.  A future evidenced need for
less-trusted external override files requires its own containment design or a
separately reviewed exact-file policy.

== 8. Policy combination semantics

No description-owned request exists, so E7 does not calculate an effective
policy by combining two documents.  Every adopted decision is nevertheless
exact and per kind:

[cols="3,4"]
|===
| Kind | Combination/decision rule

| Registered step
| exact registry membership *and* exact operator-map membership *and* the
  step's internal E7 classification *and* its parameter predicate.  These are
  conjunctive/intersection checks; none substitutes for another.

| Plugin target
| canonical description target membership in the operator's canonical
  `frozenset`.  Colon/final-dot aliases collapse; sibling and re-export names
  do not.

| Exact output roots
| canonical candidate equality membership in the exact step-owned root set,
  followed by subordinate resolved containment.  Roots from different steps
  are never unioned implicitly.

| Checksum permission
| logical conjunction with step and root authority; omission is false.

| `overrides_path`
| constant false in less-trusted mode; no policy field may turn it on.
|===

Unknown policy kinds/fields and unknown registered names reject.  Constraint
fields attached to the wrong step are incomparable and reject.  Empty required
writer roots, checksum permission without roots, plugin constraint mappings,
and a `plugin` registered-step entry are contradictory and reject.  A
description-level attempt to claim trusted mode or supply/widen policy rejects
at its reserved step field or, when ignored by a legacy outer parser, has no
effect on the separately supplied operator value.  Nothing silently wins by
precedence.

== 9. Structural validation and pre-activation call graph

=== 9.1 Structural boundary

Less-trusted construction adds only the explicit parsing/classification needed
for authorization; it does not redesign the full application-config schema.
Before authorization it may:

* require the step collection to be an exact built-in `list` or `tuple`;
* require each step item to be an exact built-in `dict` snapshot;
* require exact-string keys and a non-empty exact-string `step`;
* identify `plugin`, registered name, colon compatibility shape, or unknown;
* parse/canonicalize a plugin identifier;
* read only authority-relevant selector fields;
* validate the closed policy grammar; and
* canonicalize paths without opening them.

Malformed shells, missing/non-string `step`, malformed plugin identifiers,
wrong selector container/text shapes, and invalid static relative paths reject
as `malformed_description` before authorization/activation.  After a capability
is positively authorized, existing factories retain responsibility for the
remainder of their established parameter schema and diagnostics.  E7 adds no
Pydantic dependency.

=== 9.2 Future call graph

[source,text]
----
trusted operator/application
  -> choose trusted default (authorization=None)
     OR construct/freeze LessTrustedDescriptionAuthorization outside description

sheets-run (initial E7: trusted only)
  -> parse config
  -> existing trusted build path
  -> orchestrate(steps=prebound_steps)

run_app / build_steps_from_* / orchestrate(step_specs=...)
  -> receive operator authorization argument
  -> if None: existing trusted build behavior
  -> otherwise snapshot/freeze effective operator policy once
  -> snapshot less-trusted step description containers
  -> for each step description:
       inert structural validation/classification
       identify accepted capability kind
       extract/canonicalize identifier and selected resource selectors
       authorize exact name/target and per-step selector predicate
       only after allow:
         resolve registration as applicable
         inject trusted registry-owned target as applicable
         resolve/import/acquire callable as applicable
         call factory and bind BoundStep
  -> existing orchestrate managed macro
       coerce/load trusted-operator I/O descriptor
       E1-E3 initial payload establishment
       E4/E5 managed execution and re-establishment
       framework cleanup / sink role authorization / projection / save
----

For `orchestrate(step_specs=...)`, all description building completes before
payload load, matching current ordering and ensuring no description-selected
import is hidden behind payload ingress.  Building may process steps in order;
rejection of one forbidden step guarantees that step's capability has not
activated, but does not roll back already authorized imports for earlier
steps.  No broader transactional-import claim is made.

=== 9.3 Required signature changes

Future implementation changes only these supported seams:

* `build_steps_from_config(step_specs, *, authorization=None)`;
* `build_steps_from_yaml(path, *, authorization=None)`;
* `run_app(app, run_id=None, *, description_authorization=None, **compat)`;
* `orchestrate(..., steps=None, step_specs=None,
  description_authorization=None, header_levels=1)`.

The `orchestrate` rules are exact: `steps` and `step_specs` are mutually
exclusive; `description_authorization` is legal only with `step_specs`; and
`steps` always means trusted caller-supplied programmatic composition.  The
compatibility shim re-exports the same function and gains no separate logic.
`load_app_config`, schema maintenance, and `run_pipeline` signatures do not
change.

The supported public claim after implementation is deliberately narrow:

[source,text]
----
build_steps_from_config/build_steps_from_yaml, run_app's pipeline field, and
orchestrate(step_specs=...) may treat the supplied pipeline step description
as less trusted when the trusted caller supplies a
LessTrustedDescriptionAuthorization.  Such a description cannot activate a
capability outside that E7 policy before rejection.
----

This is not a claim that arbitrary pipeline YAML, AppConfig I/O, plugins, or
Python are safe.  Authorized same-process plugin Python remains trusted code.

== 11. Payload/description independence

Payload trust remains provenance/authorship, not a runtime switch.  E1--E6
apply the same bounded conformance grammar to either provenance.  The new
description value is orthogonal:

[cols="2,2,3,3"]
|===
| Payload authority | Description authority | Representation | Resulting obligations

| Trusted payload
| Trusted description
| Current entry with `authorization=None`
| Description retains current capability freedom; payload must still satisfy
  E1--E6 conformance.

| Less-trusted payload
| Trusted description
| Current entry with `authorization=None`, external payload provenance
| Trusted description unchanged; E1--E6 establish/reject payload exactly as now.

| Trusted payload
| Less-trusted description
| Operator authorization value plus trusted-operator I/O and a supported
  authorized description entry
| E7 bounds description capability; trusted payload still receives ordinary
  E1--E6 checks.

| Less-trusted payload
| Less-trusted description
| Same operator authorization value plus external payload provenance
| E7 bounds description before import/binding; E1--E6 independently
  establish/reject payload after load.
|===

E7 authorization success does not establish payload conformance.  Payload
conformance success does not authorize a step, plugin, resource selector, or
description.  Tests use paired provenance-labelled fixtures, not a combined
security-level enum.

== 12. Diagnostics and failure model

One focused `DescriptionAuthorizationError(ValueError)` with a stable `kind`
field is sufficient; no large exception hierarchy is required.  The closed
kinds are:

[cols="2,4"]
|===
| `kind` | Meaning/context

| `malformed_description`
| Invalid step shell, identifier syntax, or authority-relevant selector shape.

| `unknown_capability`
| Exact non-registered, non-plugin, non-colon step identifier.

| `forbidden_capability`
| Direct-colon/nested route or a categorically unavailable kind.

| `forbidden_identifier`
| Known registered name absent from operator map, or canonical plugin target
  absent from target set.

| `forbidden_resource_selector`
| `overrides_path`, unapproved root, escaping static path, or checksum without
  permission.

| `invalid_policy`
| Unknown/contradictory/incomparable operator policy shape.

| `invalid_policy_request`
| Description attempts to select trust or supply/widen E7 policy despite E7
  having no description-request grammar.
|===

The exception carries only safe built-in context: step ordinal/location,
accepted capability kind when known, exact validated textual identifier,
selector field, and stable reason code.  Diagnostics never resolve/import a
forbidden target, call a factory/plugin, open a path, include file contents or
secrets, or use unsafe `repr`/`str` on arbitrary runtime objects.  Exact
description strings may be reported only after their exact-string structural
check.  Trusted-mode exceptions and messages remain unchanged.

== 13. Implementation placement and slicing

One coherent E7 runtime slice is sufficient; no prerequisite FTR or five-part
micro-sequence is justified.

Likely source ownership:

* `pipeline/description_authorization.py` -- public value construction,
  immutable effective snapshot, closed registered-step classification,
  resource-selector preparation/authorization, and focused error type;
* `pipeline/dotted_paths.py` -- one pure import-free canonicalizer shared by
  operator policy and description target, while retaining
  `resolve_configuration_callable` as the one checked importer;
* `pipeline/build.py` -- trusted fast path plus less-trusted inert
  classify/authorize-before-resolution seam;
* `pipeline/runner.py` and `application/orchestrator.py` -- transport only;
* `pipeline/__init__.py` -- narrow exports for
  `LessTrustedDescriptionAuthorization` and `DescriptionAuthorizationError`;
  no internal kinds or generic security barrel;
* `cli/apps/run.py`, schema maintenance, `pipeline/execution.py`, Domain,
  registries, and backends -- no E7 runtime behavior change required.

This placement matches the dependency rules: description capability
authorization is Pipeline/Application control-plane work, not Domain payload
semantics.  The implementation may use small private helpers rather than the
conceptual internal enum names above, but it must preserve every closed
behavior and ordering decision in this design.

The coherent implementation slice contains: closed value/policy, canonical
identifier preparation, resource contract table, builder enforcement,
application transport, focused diagnostics, unit/integration/architecture
tests, and public contract/release-note updates required by the later
implementation review.  It does not require a registry schema migration or a
new policy file.

== 14. Test architecture for implementation

No tests are implemented by this design.  E7 implementation must add the
following executable evidence.

=== 14.1 Import/activation observation

* Denied plugin: monkeypatch the import hook and resolver; assert zero target
  module import, zero attribute acquisition, zero factory call, zero binding,
  and zero invocation.
* Denied direct colon: monkeypatch `resolve_registration`; assert it is not
  called for the denied colon-bearing form and the target module import
  sentinel remains untouched.
* Denied registered short name: assert its registration factory and internal
  dotted resolver are not reached.
* Authorized registered short name: assert the short-name decision precedes
  the internal target resolver and that plugin-target policy is not consulted
  for the internal path.
* Nested target: assert outer direct-factory denial leaves both outer and
  nested import sentinels untouched.
* Authorized plugin: assert import/acquisition occurs only after allow, binding
  occurs, and invocation occurs only during execution.

An architecture guard must enumerate configuration-derived resolver call sites
and pin that every less-trusted path crosses the builder authorization seam
before `resolve_configuration_callable`; direct Python remains the explicit
exception.

=== 14.2 Identifier policy

* Exact registered-name allow and adjacent registered-name deny; registry
  membership alone denies.
* Exact plugin target allow and sibling target deny.
* Colon and supported final-dot spellings canonicalize identically and cannot
  bypass the same entry.
* An alias/re-export spelling remains denied until separately listed.
* Malformed/blocked targets reject without import.

=== 14.3 Resource policy

* `apply_overrides` inline use succeeds when the name is authorized;
  `overrides_path` rejects for relative, absolute, empty, and path-like
  supplied values before target import/binding and before `exists`/open.
* Each writer accepts exactly an approved canonical output root and rejects a
  sibling/unlisted root before its internal target import/binding.
* Structured-YAML static absolute/traversal/escaping `files[].path` rejects
  before binding; an in-root path reaches the current runtime containment.
* Key-value patterns write only contained paths; payload-derived absolute or
  traversal output is rejected by the existing per-rendered-path containment
  before `mkdir`/open.
* Manifest in-memory-only mode needs no root.  Manifest path writes require an
  exact root.  `sha256` rejects without the boolean and succeeds with it;
  import/read sentinels prove denial precedes read.  Reported outside-root
  paths reject before `read_bytes`.
* Existing symlink-to-outside cases reject at resolved containment.  Tests do
  not claim hostile concurrent symlink-race isolation.

=== 14.4 Policy construction and lifetime

* Operator name/target/root allowlists and parameter predicates act
  conjunctively.
* Unknown top-level/constraint fields, unknown names, wrong-step constraint
  kinds, `plugin` in the registered map, empty required roots, checksum
  permission without roots, and plugin constraint mappings reject.
* Reserved description policy/trust fields cannot select trusted mode or widen
  the supplied value.
* Mutating every caller-retained top-level and nested policy container after
  construction does not change effective authority.
* Mutating caller-retained description containers after build entry cannot
  swap the authorized target/root/path before binding.

Because E7 selects no description-owned narrowing grammar, there is no
operator/request intersection test.  The required intersection evidence is
the real adopted one: registered-name membership plus its parameter predicate,
canonical target membership, root equality plus containment, and checksum
boolean conjunction.  Future description-request tests remain inapplicable
until such a kind is separately accepted.

=== 14.5 Trust modes and programmatic boundary

* Omitted authorization retains current trusted behavior for every registered
  step, plugin, direct-colon factory, and nested target compatibility case.
* An empty less-trusted value denies all declarative capabilities.
* A description-embedded claim of trust does not change the operator-selected
  route.
* `orchestrate(steps=...)` rejects an accompanying authorization argument and
  otherwise leaves direct `BoundStep` behavior unchanged.
* Direct callable targets and `run_pipeline` remain unchanged and do not import
  or depend on the E7 authorization module.
* Schema maintenance's private step remains unaffected and non-addressable.
* Current Core and maintained consumer trusted configurations require no
  rewrite and keep passing their existing suites.

=== 14.6 Four-way and E1--E6 independence

Parameterize valid and invalid payload fixtures labelled by trusted/less-
trusted provenance across trusted and less-trusted description construction:

* both payload provenance labels succeed when ordinary conformance succeeds;
* both reject through the same E1--E6 error when conformance fails;
* a forbidden less-trusted description rejects during construction before
  payload load, regardless of payload provenance; and
* an authorized less-trusted description proceeds through the ordinary E5
  managed flow, including uncertified plugin-return re-establishment and
  existing payload rejection.

The tests must observe real resolver/import/factory/resource sentinels, not
infer pre-activation rejection merely from a missing output file or an
exception.

== 15. Compatibility and migration

E7 is additive:

* current trusted YAML and `AppConfig` continue without new arguments;
* current plugin sites retain spelling, calling convention, and behavior;
* direct-colon and nested-target trusted compatibility remains supported,
  unpromoted, and undeprecated;
* registry-owned string targets remain replaceable internal wiring;
* direct callable targets, direct `BoundStep`, `run_pipeline`, schema
  maintenance, macro phases, and I/O/backends remain unchanged; and
* no Core/demo/worldbuilding/SSDP/rollout or other adoption configuration must
  migrate merely because E7 is added.

Less-trusted adoption is opt-in and programmatic.  Operators enumerate the
exact step names/plugin targets and only the selected writer roots they intend
to grant.  Rollback removes the explicit authorization argument/configured
entry variant and returns to the unchanged trusted-description contract; it
requires no YAML rewrite.

The implementation changes public Python signatures/exports additively and is
therefore gated/release-relevant under `interfaces_and_gates.adoc`; the later
implementation must update the appropriate public contract/release notes.
This design-only artifact does not do so prematurely.

== 17. Acceptance criteria and final self-review

E7 implementation is acceptable only when:

. supported less-trusted step descriptions cannot activate a forbidden
  registered, plugin, factory, nested-target, or selected resource capability;
. trusted mode preserves all current behavior and requires no migration;
. direct Python forms remain trusted-only and outside declarative policy;
. all four payload/description authority combinations remain representable;
. payload-conformance behavior/tests remain independent; and

== 18. Design conclusion

The smallest truthful E7 seam is an explicit immutable
`LessTrustedDescriptionAuthorization` supplied by trusted Python outside the
description and enforced while description data is still inert in
`pipeline.build`.  Exact registered names and canonical plugin targets are the
only consumer-grantable capability identities.  Direct factories/nested
targets remain denied; registry-owned targets remain internal; direct Python
and macro lifecycle remain outside E7.  The only parameter policy covers the
four evidenced registered resource steps: inline-only overrides, exact
operator output roots for the two writers, and exact-root manifest access with
an explicit checksum-read boolean.

All required decisions are final.  E7 design is complete but not
independently accepted.  E7 remains unimplemented.  Phase E remains open.
Fresh independent design review is the next required lifecycle action; E7
implementation remains blocked until that review accepts this design.  No
lifecycle curation is performed by this artifact.
