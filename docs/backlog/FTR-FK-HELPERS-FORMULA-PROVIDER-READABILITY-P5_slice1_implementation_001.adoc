== 5. Pre-edit algorithmic reading

The baseline factory accepted the target lookup index, returned a closure, and
captured that index once. On each positional callback call it resolved the
target with `registry.get(fk.target_sheet_key)`, selected a physical sheet name
or the target-key fallback, built one backend-neutral `lookup_formula` spec from
the `FKDef`, and repeated that exact object once per list item. `enrich_helpers`
was its sole runtime client and installed it only for formula modes; value mode
passed `None` to `apply_fk_helpers`.

== 9. Import-convention evidence and decision

Sibling `enrich.py` imports `core.fk` with `from ....core.fk ...`; sibling
`policy.py` does the same; feature-local sibling imports use dot-relative form.
This establishes the local convention: within this feature package, traverse
relatively to shared project layers and use local relative imports for siblings.
Accordingly, `formula_provider.py` now uses:

[source,python]
----
from ....core.fk import FKDef, HelperValueProvider
from ....core.formulas import lookup_formula
----

This is a one-module normalization. No repository-wide import rule or external
import cleanup was inferred.

== 10. Callback-parameter alternatives

[cols="2,4"]
|===
| Candidate | Assessment

| `raw_ids` | Rejected: says raw ID values are interpreted, which formula mode
does not do.
| `rows` / `row_count_inputs` | Rejected: emphasizes cardinality but hides that
the shared callback is handed source-key values.
| `source_rows` | Rejected: list elements are keys, not row objects.
| `items` | Rejected: too generic to expose the shared contract.
| `source_keys` | Selected: names the list truthfully at the shared callback
boundary while remaining compatible with formula mode's cardinality-only use.
|===

== 11. Selected-name rationale

`source_keys` is truthful in both relevant senses: `apply_fk_helpers` passes the
source FK-column values, and this strategy deliberately does not inspect them.
The underscore target in the exact expression makes cardinality-only use visible.
The closure name `provider` was retained: renaming it merely for symmetry would
add churn after the factory name and return annotation already expose its role.

== 12. Optional factory-rename decision

All FTR §8 gates held: genuinely private; one definition and one sibling
import/call; no caller outside the package; no registry, metadata, re-export,
public, cross-family, or architecture-symbol pin; only the two authorized runtime
files affected. `build_lookup_formula_value_provider` states construction
(`build`), strategy (`lookup_formula`), and returned role (`value_provider`). The
name prevents mistaking the factory for a provider or direct lookup operation,
and the gain exceeds the two-line `enrich.py` rename diff. The extended private
name form was therefore used.

== 19. Exception precedence and object identity

The pre- and post-edit trace is identical:

[source,text]
----
fk.target_sheet_key
registry.get:Target
target.get:sheet_name
fk.target_sheet_key              # only when the sheet-name value is falsy
fk.fk_column
fk.id_field
fk.value_field
----

A forced `target_sheet_key` `RuntimeError` still occurs before registry access;
a forced `id_field` `LookupError` still occurs before `value_field` access. No
exception is caught, translated, or reordered. For three source keys, the three
list elements remain the identical single formula object (`is` true), not merely
equal dataclass values.
