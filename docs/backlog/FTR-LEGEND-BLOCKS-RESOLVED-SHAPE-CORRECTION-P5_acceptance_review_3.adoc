=== Important N-1 -- maintained generic-binder target bypasses the ownership boundary

The Correction 2 helper classifies only the top-level reference passed to
`make_plugin_step` or `resolve_registration`. Direct colon resolution can
legitimately select the framework's generic frames-target binder:

[source,yaml]
----
pipeline:
  - step: spreadsheet_handling.pipeline.steps:make_frames_target_step
    name: nested_ingress
    target: spreadsheet_handling.domain.ingress:run_domain_ingress
----

`resolve_registration` correctly allows the top-level
`spreadsheet_handling.pipeline.steps` factory. During factory binding,
`make_frames_target_step` calls `_resolve_target`, whose string branch calls
`_resolve_callable` without `ensure_configuration_addressable`. The nested
ingress target is therefore imported during configuration construction and the
resulting `BoundStep` invokes ingress during pipeline execution.

Independent sentinels reproduced this for all three ownership targets:

[source,text]
----
3/3 nested generic-binder routes built and invoked ingress
----

An actual YAML file using the package export also built and invoked the
sentinel. A selective importer proved that the ingress importer is reached
during construction.

This is a maintained framework configuration path, not an arbitrary external
module deliberately re-exporting an internal callable. The generic binder is
the registry's normal binding mechanism, lives in the maintained
`pipeline.steps` module, returns a valid `BoundStep`, and is itself reachable
through the documented direct colon factory protocol. It therefore falls
inside this FTR's promise that ingress cannot be built or invoked from YAML.

*Risk:* configuration can still select framework-owned macro flow, so the FTR,
technical-model, release-note, and Correction 2 statements that the entire
namespace is rejected across maintained dotted configuration paths are false.
Future ingress rules would inherit the same exposure.

*Recommended correction:* classify string targets at the shared target
resolution boundary, or otherwise prevent direct configuration from using a
generic binder to address framework-internal targets. Preserve registered
targets, legitimate external/internal factories, direct Python callables, and
the explicit external-re-export non-security boundary.

*Disposition:* important; prevents acceptance.

== Shared-boundary assessment

`pipeline.dotted_paths` is an architecturally appropriate location for a
pipeline configuration ownership rule. It imports no domain implementation
module and contains one explicit namespace list rather than duplicate or broad
domain ownership lists.

For a reference it receives, the helper correctly:

* blocks exactly `spreadsheet_handling.domain.ingress` and every descendant;
* leaves the broader `spreadsheet_handling.domain` namespace available;
* handles `module:function` and plugin-only `module.function` forms;
* rejects ownership before the relevant importer; and
* produces the documented
  `framework-internal and not configuration/plugin-addressable` diagnostic.

Both directly claimed routes call the same helper. The boundary is nevertheless
incomplete because `_resolve_target` is a third maintained string-to-callable
resolution point reachable from the direct factory configuration surface.
There is one ownership list, but not one enforced ownership boundary for every
supported configuration-addressed target.
