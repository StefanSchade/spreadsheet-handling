== Findings

=== Important I-1 -- `legend_blocks: null` escapes the canonical-shape contract

`domain.ingress.legend_blocks._normalize_root` treats `None` as absent and
`normalize_legend_blocks_shape` returns the original Frames with the explicit
root still set to `None`. The persistence boundary also passes it through.
An application-level JSON-directory probe therefore returned and wrote
`legend_blocks: null`.

This preserves the old falsey/no-render behavior, and optional roots elsewhere
often treat `None` as absent. It nevertheless contradicts the reviewed FTR:
only an *absent key* is a no-op, every present root that is neither mapping nor
list must fail, and runtime/persisted Legend Blocks are mapping-only. The new
unit test silently creates an undocumented exception, while the registry and
live documentation state the stricter contract.

*Disposition:* important undocumented contract gap. Decide explicitly whether
`null` is rejected or canonicalized to actual absence/empty mapping, then align
runtime, tests, registry, and docs. Keeping an explicit persisted `null` is not
compatible with the accepted mapping-only invariant.

=== Important I-2 -- `apply_overrides` failure is not atomic

`get_meta` makes only a shallow top-level copy. `apply_overrides` then mutates
the existing nested `sheets` mapping before invoking ingress. A probe starting
from canonical Legend metadata, adding a sheet override, and introducing two
duplicate Legend identities through `defaults` raised the expected
`ValueError` but changed
`frames["_meta"]["sheets"]["Data"]["freeze_header"]` from `False` to `True`.

The orchestrator still suppresses the saver and later steps, but a direct
maintained `apply_overrides` caller observes partial mutation. This falsifies
the FTR's caller-graph immutability/failure-atomicity criterion and the
self-review's claim that canonicalizing before `set_meta` makes this boundary
atomic.

*Disposition:* build the whole override candidate without sharing/mutating the
caller's nested `sheets` mapping, and add an override-stage failure test that
checks the complete object graph plus saver suppression.

=== Important I-3 -- ingress is YAML-invokable through the public plugin step

Ingress is correctly absent from `pipeline.registry.REGISTRY` and
`registries/pipeline_step_registry.json`; short-name builds fail. However, the
registered public `plugin` step accepts a dotted Frames callable. This YAML
configuration builds and runs successfully:

[source,yaml]
----
- step: plugin
  dotted: spreadsheet_handling.domain.ingress:run_domain_ingress
----

The new architecture guard checks only candidate step names and misses this
maintained extension path. Current Legend normalization is idempotent, so the
probe showed no immediate semantic drift, but the reviewed contract says
ingress is not YAML-buildable/selectable. User-controlled invocation also
weakens that guarantee for every future ordered ingress rule.

*Disposition:* either enforce non-addressability through the plugin surface,
or explicitly revise the settled contract to distinguish “no dedicated
registered step” from unsupported-but-executable plugin use. Add a guard for
the chosen rule; the current absolute documentation is false.

== Ingress and call-graph assessment

The maintained macro call graph is structurally correct:

[source,text]
----
CLI / run_app / schema-maintenance application
  -> application.orchestrator.orchestrate
  -> router loader
  -> run_domain_ingress
  -> configured steps
       -> bootstrap_meta -> post-merge run_domain_ingress
       -> load_and_apply_overrides -> apply_overrides
          -> post-merge run_domain_ingress
  -> final cleanup
  -> persistence projection
  -> router saver
----

All router-backed input kinds converge before the first configured step.
`domain.ingress` has no forbidden higher-layer imports, exposes one explicit
ordered `INGRESS_RULES` tuple, and is a reusable carrier-neutral
`Frames -> Frames` boundary. Arbitrary plugins remain responsible for returning
canonical Frames. Direct `run_pipeline`, transformation, render, and backend
calls remain lower-level preconditioned APIs.

Calling ingress twice is value-idempotent. The coordinator itself and
`bootstrap_meta` preserve caller state on normalization failure. The
`apply_overrides` invocation path does not, per I-2. Registry
non-registration is correct, but YAML non-buildability is not, per I-3.

== Own-sheet projection assessment

The shared change is narrow: only the already-selected `tables[0]` is omitted
when its parser classification is `kind == "legend"`. Default-placement
Legend-only sheets are therefore absent in both XLSX and ODS readback; a data
table followed by a colocated Legend still returns the data; empty sheets still
return an empty DataFrame. Multiple/manual tables do not create a new
second-table loss because generic projection already selected only the first
table.

Residual risk: classification trusts carrier `resolved` coordinates. A
deliberately overlapping Legend at `(1,1)` marks both the payload anchor and
Legend anchor as `kind == "legend"` in both parsers, so projection returns no
payload frame. The carrier has already overwritten that payload with Legend
cells, so this is not a new legitimate-data regression, but overlap/tampered
hint behavior remains outside the narrow fix and deserves watch-only status.
