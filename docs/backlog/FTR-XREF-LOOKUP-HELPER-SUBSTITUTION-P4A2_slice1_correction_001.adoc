== 3. Correction per finding

=== 3.1 IMP-001 — key/helper collision safety

A deterministic collision rule is now enforced *before* any projection, merge,
or formula assignment, in a single guard `_check_key_helper_collision`
(`enrich_lookup/operation.py`), called inside the `projection_fields`
validation block so it covers both value and formula modes and the temporary
sort-helper projection.

Rule (asymmetric mode only; symmetric and equal-name asymmetric are unaffected
because the lookup-key rename is a no-op there):

* if a projected field (a requested helper *or* a temporary lookup sort helper)
  equals the *lookup key*, raise `ValueError` — it would leak the lookup key
  into the output (values mode collapses it onto the renamed key; formula mode
  emits a lookup-key output column);
* if a projected field equals the *source key*, raise `ValueError` — it would
  overwrite the authoritative source key (values mode produces a duplicate
  output label; formula mode overwrites the key column with formula specs).

Because the guard runs before `out`/provenance is built, a rejected request
writes *no* output frame and *no* provenance, so provenance can never claim a
helper that was not materialized.

The concrete review cases now behave as follows (`source_key=story_id`,
`lookup_key=id`):

[cols="3,2"]
|===
| Request | Result

| `helpers.fields=[story_id]`, values mode
| `ValueError` "collides with the asymmetric source key"

| `helpers.fields=[id]`, values mode
| `ValueError` "collides with the asymmetric lookup key"

| `helpers.fields=[story_id]`, formula mode
| `ValueError` (source key) — before formula assignment

| `helpers.fields=[id]`, formula mode
| `ValueError` (lookup key) — before formula assignment

| lookup frame has an independent non-key `story_id`, `helpers.fields=[title]`
| Success; source key retains source values; `id` and lookup `story_id` absent

| `order.sort_by=[story_id]` (source key)
| Success; sorts the output source key; lookup's independent `story_id` not projected

| `order.sort_by=[id]` (lookup key)
| `ValueError` "collides with the asymmetric lookup key"
|===

No helper renaming and no general collision-resolution DSL were introduced.

=== 3.2 IMP-002 — asymmetric mismatch checking

`derived_column_policy._check_enrich_lookup_values` now resolves its join keys
through `_resolve_mismatch_keys(spec)`, which understands both provenance
shapes:

* symmetric `{"on": [...]}` → payload and lookup share the key name(s)
  (`payload_keys == lookup_keys`); behaviour unchanged;
* asymmetric `{"source_key": <s>, "lookup_key": <l>}` → payload is keyed on
  `source_key`, the lookup frame on `lookup_key`.

The canonical value map is built keying the lookup frame on `lookup_keys`; the
payload is compared keying on `payload_keys`. The join-key *values* line up
across the two frames, so the normalized value tuples match even though the
column names differ. Consequently:

* `warn_on_mismatch` emits a `derived_value_mismatch` finding for an edited
  asymmetric helper;
* `fail_on_mismatch` raises for an edited asymmetric helper;
* an unchanged asymmetric helper yields no findings;
* an unmatched source reference is skipped (a separate concern), consistent with
  symmetric behaviour;
* malformed partial asymmetric provenance (only one of `source_key`/`lookup_key`,
  or `on` mixed with an asymmetric key) is rejected with a clear `ValueError`
  rather than silently skipping the check;
* `policy: drop` remains intentionally value-blind (it never calls the checker).

No Slice-2 persistence binding was implemented; the correction operates only on
the in-memory `_meta.derived` asymmetric provenance record.

=== 3.3 IMP-003 — preserve selected public mode

`_resolve_join_keys` (`enrich_lookup/policy.py`) now returns a small private
frozen dataclass `_ResolvedKeys(mode, source_keys, lookup_keys)` instead of a
bare tuple. `mode` is `"symmetric"` for `key`/`keys`/legacy `"on"`/policy-key
forms and `"asymmetric"` for an explicit `source_key`/`lookup_key` pair — set
from the *selected public form*, never inferred from label equality.

`_write_provenance` writes the record shape from `resolved.mode`:

* symmetric → `{"on": [...]}`;
* asymmetric → `{"source_key": <s>, "lookup_key": <l>}`, *even when the two
  names are equal*.

The asymmetric pair still owns key selection and ignores a configured
helper-policy `key`, while all non-key policy settings remain active
(unchanged behaviour, now covered by a tracked test).

== 4. Final collision contract

For a resolved asymmetric mode with `source_key != lookup_key`, every projected
lookup-side field (requested helper or temporary sort helper) must differ from
both key roles. A field equal to the lookup key is rejected (would leak); a
field equal to the source key is rejected (would overwrite). The check runs
before projection/merge/formula, raises a domain `ValueError`, and leaves no
output frame or provenance behind. Symmetric mode and equal-name asymmetric
mode are unaffected (the lookup-key rename is a no-op, so no collision is
possible). Sorting on the source key remains a legitimate output-key sort and
never projects an independent same-named lookup column.

== 5. Final resolved-key / mode design

[source,text]
----
_ResolvedKeys(frozen):
  mode:        "symmetric" | "asymmetric"   # from selected public form
  source_keys: tuple[str, ...]              # symmetric: shared; asymmetric: one
  lookup_keys: tuple[str, ...]              # symmetric: shared; asymmetric: one
  is_asymmetric / source_key / lookup_key   # convenience accessors
----

`_resolve_join_keys` produces exactly one `_ResolvedKeys`. All downstream
operations consume it consistently: source validation, lookup validation,
duplicate checking, helper projection, formula construction, missing checks,
ordering, and provenance. Asymmetric mode remains exactly one key per side;
multi-key symmetric behaviour is unchanged. No implicit tuple shapes remain.

== 6. Mismatch-reader behavior

`_resolve_mismatch_keys(spec)` returns `(payload_keys, lookup_keys)`:

* symmetric `on` → `(on, on)`;
* asymmetric pair → `([source_key], [lookup_key])`;
* `on` + asymmetric key → `ValueError` (mixed form);
* one asymmetric half missing → `ValueError` (partial);
* neither → `([], [])` (no-op, as before).

The reader value-checks against the correct lookup row, preserves symmetric
behaviour, keeps `drop` value-blind, and reports edited helpers under
warn/fail.

== 7. Formula behavior

Ordinary asymmetric formula mode is unchanged and now regression-protected:
`LookupFormulaSpec(source_key_column=source_key,
lookup_key_column=lookup_key, lookup_value_column=field, lookup_sheet=lookup)`.
The source key is preserved, the lookup key never becomes an output column, and
helper placement obeys `helper_position`. Collision requests fail before any
formula cell is assigned. Rendered XLSX uses the source-key cell (`$A2`), the
lookup-key range (col A on the physical lookup sheet), and the lookup-value
range (col B); rendered ODS uses `[.A2]`, `[Entities.A2:Entities.A3]`, and
`[Entities.B2:Entities.B3]`.
