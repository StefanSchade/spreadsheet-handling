==== 4. Problem statement

Stated as observable reader cost, not as an assumed solution:

A reader opening `formula_provider.py` today cannot answer three questions as
directly as the code allows:

> What callable contract does the factory return; does the formula strategy
> actually read the ID values it is handed or only their row count; and which
> architectural import boundary is this module crossing?

Concretely:

* The factory `_lookup_formula_provider` has *no declared return type*, although
  `core.fk` already defines and exports the exact callback alias
  `HelperValueProvider` (`core/fk.py:15`) and an architecture guard already names
  it as a contract the primitives consume
  (`test_fk_helper_primitives_consume_policy.py:48`). The returned closure is
  generically named `provider`.
* The closure parameter `raw_ids: list[Any]` implies the formula strategy reads or
  interprets ID *values*. It does not: it uses the iterable only to emit one
  formula specification per output row (`return [formula for _ in raw_ids]`). The
  name overstates the dependency.
* The module mixes import styles across the *same* `core` boundary: a relative
  `from ....core.fk import FKDef` (line 10) and an absolute
  `from spreadsheet_handling.core.formulas import lookup_formula` (line 11). There
  is no visible semantic reason for the distinction.

This is a small internal clarity improvement, not an architecture correction. The
closure is legitimate and must be preserved; backend-neutral formula intent is
already correct; the current provider behavior is stable and tested.

==== 5. Goals

* Make the provider factory's *existing* return contract explicit by annotating it
  with the already-defined `core.fk.HelperValueProvider` alias.
* Give the closure's row-list parameter a name that truthfully reflects what the
  formula strategy uses (row cardinality) while remaining truthful under the
  shared callback contract.
* Apply one consistent internal import style for this module, following or
  documenting an existing repository convention where one can be established.
* Optionally sharpen the private factory name so it reads as *constructing* a
  provider (decision in section 8), if and only if the section-8 criteria hold.
* Reduce reader effort with zero behavioral change and no new abstraction.

==== 6. Non-goals

* No change to the `core.fk.HelperValueProvider` alias or the callback signature/arity.
* No change to `FKDef`.
* No change to the target-registry / lookup-index shape.
* No change to formula specifications or to lookup-sheet resolution.
* No split into separate value-mode and formula-mode provider interfaces.
* No replacement of, or expansion of, the closure into repeated parameter plumbing.
* No new protocol, dataclass, `TypedDict`, provider class, or alias competing with
  `HelperValueProvider`.
* No direct XLSX/ODS formula generation in the domain transformation.
* No change to `core.fk` (or any module other than `formula_provider.py` and, only
  if the section-8 rename is taken, the single private import/call line in
  `enrich.py`).
* No public import, re-export, registry, meta, persisted-schema, or public-YAML change.
* No broad typing cleanup and no `Any` removal beyond the one authorized return
  annotation.
* No import cleanup outside `formula_provider.py`.
* No `enrich.py` cleanup beyond the optional authorized private factory rename.
* No package-wide frame/sheet vocabulary work (Candidate L2 is not authorized).
* No style-guide refinement or publication.

==== 8. Optional factory-rename decision

The Slice-2 assessment identified a possible private factory rename of
`_lookup_formula_provider` (currently reads as a noun — "the lookup-formula
provider") to a name that reads as construction, e.g.
`build_lookup_formula_value_provider`.

Evidence gathered for this decision (verified at HEAD `77b4caf`):

* the symbol is genuinely private (leading underscore);
* its *only* references are its definition (`formula_provider.py:14`) and a single
  import + call site in `enrich.py` (`enrich.py:19,90`);
* the architecture guards that name the `formula_provider` module
  (`test_no_cross_family_internal_imports.py:26`,
  `test_package_public_api_boundaries.py:27`) reference the *module path*, not this
  symbol; the `HelperValueProvider` guard names the *alias string*, not this
  symbol;
* it is not registry-pinned, meta-pinned, re-exported, or documented as a public
  symbol path.

*Decision:* the factory rename is *authorized as an optional part of Slice 1,
defaulting to inclusion (the extended private-name form, section 9.2)*, gated on
the implementation agent re-verifying at implementation time that all of the
following still hold; if any fails, the agent must fall back to the minimal form
(section 9.1) and record why:

* the symbol is genuinely private with no caller outside `formula_provider.py` and
  the single `enrich.py` import/call line;
* the new name materially clarifies that the function *builds* a formula-value
  provider rather than *is* a provider or *performs* a lookup;
* only `formula_provider.py` and that one `enrich.py` line are affected;
* no public, registry, metadata, re-export, or cross-family surface changes;
* the readability gain exceeds the extra two-file diff.

Rationale for defaulting to inclusion: `_lookup_formula_provider` reads as a noun
and is easy to mistake for the provider itself; a construction-verb name resolves
the same ambiguity that FK-HR-013 addresses for the return type, at the cost of a
single, fully private import/call line. Excluding it (relying on the three core
findings alone) remains a valid outcome if any criterion above fails — the three
core findings are sufficient on their own.

==== 11. Positive patterns to preserve (acceptance conditions)

Preservation of each is an explicit acceptance condition:

* *Closure-based strategy binding.* The factory must continue to capture the
  target lookup structure once and return a callable matching the shared provider
  contract. Do not expand it into repeated parameter plumbing.
* *Backend-neutral formula intent.* The provider must continue to return
  backend-neutral `lookup_formula` specifications; no workbook-carrier (XLSX/ODS)
  syntax may enter the domain transformation.
* *Genuine workbook-sheet vocabulary.* Variables that refer to the actual workbook
  sheet a lookup formula references — notably `lookup_sheet` — must retain *sheet*
  vocabulary. The frame-vocabulary rule must not be applied mechanically here.
* *Shared callback contract.* The provider must continue to conform to the existing
  `HelperValueProvider` contract. This slice *clarifies* the contract; it does not
  redesign it.

==== 12. Protected non-findings

Slice 1 must not rewrite these merely to look different:

* the nested-function (closure) construction — a legitimate strategy-injection
  pattern, not a smell;
* the `[formula for _ in raw_ids]` per-row replication (its *name* may change; its
  behavior and shape may not);
* the use of the shared value/formula callback signature (do not split it).

==== 13. Behavioral invariants

No invariant may be relaxed because the change is "only readability." Derived from
current code (`formula_provider.py`, `core/fk.py`) and tests:

* same callable *arity* for the returned provider (`(fk, <row-list>)`);
* same accepted `FKDef` work item;
* same number of output values as input rows;
* the same formula specification object emitted for each row where current behavior
  repeats it;
* same target lookup behavior (`registry.get(fk.target_sheet_key)`);
* same target-key resolution (`fk.id_field`);
* same lookup-sheet resolution
  (`str(target.get("sheet_name") or fk.target_sheet_key)`);
* same lookup value-field resolution (`fk.value_field`) and `missing=""` behavior;
* same current exceptions and error precedence;
* same output ordering;
* identical formula-mode output through `enrich_helpers` (value mode unchanged and
  untouched);
* backend-neutral formula objects unchanged;
* helper column order unchanged;
* no public symbol, re-export, registry, meta, or persisted-schema change.

No output or exception drift is authorized.

==== 14. Typing boundary

Authorized: exactly the narrow use of the *existing* `core.fk.HelperValueProvider`
alias as the factory's return annotation.

Prohibited: `TypedDict`, dataclasses, registry-shape aliases, relation typing,
`FKDef` replacement, a competing protocol/alias, or any package-wide `Any`
removal. The value of the slice is exposing an already-existing contract, not
inventing a new type system.

==== 15. Naming criteria

The implementation agent must choose and *justify* each name against evidence, not
preference; the reviewer must assess:

* whether the renamed callback parameter describes what the formula strategy
  actually uses (row cardinality) and remains truthful under the *shared* provider
  contract (which also serves value mode). The FTR does not prescribe a spelling;
  `source_keys` is a candidate only if current code and the shared interface
  support it as the clearest term. The agent must select the exact name and
  justify it;
* whether the factory name, if changed (section 8), describes *construction* of a
  provider rather than direct formula execution;
* whether every retained `sheet` term (e.g. `lookup_sheet`) refers to an actual
  workbook sheet and therefore must keep sheet vocabulary.

A callback-interface split to eliminate the unused values is *not* authorized.

==== 16. Import-style decision boundary

Authorize one consistent internal import style *for `formula_provider.py` only*.
The selected style must follow or explicitly document an existing repository
convention where one can be established (a plausible rule, consistent with sibling
modules `enrich.py`/`policy.py` which use relative `from ....core.fk import ...`:
relative imports within the feature package's own layer traversal to `core`,
applied uniformly to both `core.fk` and `core.formulas`; or, if the repository
convention is absolute across subsystem boundaries, absolute for both — the agent
picks the one supported by current convention and states it).

Prohibited: any import change outside `formula_provider.py`; a repository-wide
import-style migration. If the exact rule cannot be established without a
repository-wide decision, that is a stop condition (section 21).

==== 18. Implementation-form neutrality

The FTR defines the problem and constraints, not every spelling. It may authorize:

* one return annotation using `HelperValueProvider`;
* one precise callback-parameter rename;
* one consistent import form for the module;
* optionally, one private factory rename (section 8).

It prohibits: new abstractions; new provider interfaces or classes; protocols
duplicating the existing alias; moving code between modules; touching `core.fk`;
and expanding the closure.

==== 19. Human-readability acceptance criteria

Slice 1 is accepted only if, reading the resulting `formula_provider.py`, a
reviewer can answer the following more directly than today, with unchanged behavior:

. What callable contract does the factory return?
. What dependency does the closure capture?
. What does the callback's row-list argument actually represent?
. Does the formula strategy inspect those values or only use row cardinality?
. Where is the workbook lookup sheet determined?
. Where is backend-neutral formula intent created?
. Which import boundary does the module cross?
. Which parts are shared `core.fk` contracts and therefore unchanged?

The acceptance test is *not* more annotations in general, removal of nested
functions, more lines, fewer relative imports in the abstract, or Java-shaped
explicitness. It is a more visible *existing* callback contract with unchanged
behavior and preserved strategy structure. If the result is merely different rather
than a demonstrable contract clarification, it must not be merged (stop condition).

==== 21. Stop conditions

Stop and escalate (revise this FTR) if any becomes true:

* the factory or callback is found imported outside the identified private path;
* an architecture guard treats the current private symbol name
  (`_lookup_formula_provider`) as a pinned contract;
* the exact import-style rule cannot be established without a repository-wide
  decision;
* the return annotation would require changing `HelperValueProvider`;
* a clearer parameter name would require changing callback semantics or arity;
* the implementation would need to touch `core.fk`;
* formula-specification behavior would have to change;
* `lookup_sheet` (or another genuine workbook-sheet reference) would be renamed to
  frame vocabulary;
* the closure would have to be replaced or expanded;
* the diff would extend beyond `formula_provider.py`, the one optional `enrich.py`
  import/call line, and narrowly necessary tests;
* the result is cosmetic rather than a demonstrable contract clarification
  (section 19).
