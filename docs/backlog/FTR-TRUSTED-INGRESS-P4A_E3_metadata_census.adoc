== 1. Exact question and preferred hypothesis under test

Per FTR section 23/E3 precondition and section 11: before E3 may treat the
`_meta` substrate as an owned, bounded, acyclic framework structure, an
independently accepted focused census must confirm or replace this preferred
hypothesis:

....
root:                    exact dict
recursive owned containers: exact dict, exact list
ordinary leaves:         E1-admitted Scalar (str | bool | int | float |
                         datetime.date | datetime.datetime | None, plus
                         admitted numpy/pandas carrier variants -- see
                         core/scalar_values.py:103-150)
exceptional semantics:   only explicitly named and governed delegates
....

The census must answer: what metadata node shapes must current supported
behavior admit at the E3 substrate boundary -- confirming this hypothesis, or
replacing it with a bounded alternative plus named migrations.

== 5. Container subclasses -- exact vs. generic

*Producers:* zero custom `Mapping`/`Sequence` subclasses exist anywhere in
`src/spreadsheet_handling/` (`grep -rn "class .*(.*Mapping.*)"` /
`"class .*(.*Sequence.*)"`, excluding tests: zero hits). Every current
producer emits exact `dict`/`list`.

*Consumers:* essentially every subtree handler (`meta_update.py`'s ~15
handlers, `workbook_views.py`, `legend_blocks.py`, `persistence_boundary.py`)
gates with `isinstance(x, Mapping)`/`isinstance(x, Sequence)` -- generic ABC
checks, not `type(x) is dict`. `domain/schema_maintenance/meta_update.py`'s
`_is_sequence` (line 1036) explicitly tolerates any non-`str`/`bytes`
`Sequence`, including `tuple`, for `constraints`, `helper_columns`,
`fk.relations`, and several `workbook_view`/`lookup` fields.

This is consumer-side duck-typed *tolerance*, never producer-side *reliance*:
no current path constructs a genuine `Mapping`/`Sequence` subclass instance
and writes it into `_meta`. Per FTR section 4's own reachability principle
("a node shape that is technically constructible but has no supported
producer or consumer is not automatically part of the compatibility
contract"), this tolerance does not force the vocabulary open. E3 may
legitimately narrow to `type(x) is dict`/`type(x) is list` at ingress without
breaking any current producer -- it only tightens what a duck-typed
direct-Python caller could get away with today. One inconsistency is worth a
small parked follow-up: `domain/transformations/fk_helpers/policy.py:53`
(`resolve_v2_fk_relations`) requires `isinstance(relations, list)` **exactly**
for `_meta.helper_policies.fk.relations`, while `meta_update.py`'s validator
for the *same* path tolerates any `Sequence`. No producer ever creates a
tuple there, so this is dormant, not load-bearing (<<parked-concerns>>).

E2's own (currently unwired) admission function uses the strictest form
already -- `type(frames) is not dict` at the outer Frames level
(`structural_admission.py:117`) -- consistent with, and useful precedent
for, an exact-dict E3 boundary check.

[[aliasing]]
== 6. Aliasing and cycles

*Aliasing is the single most systemic finding of this census.* Every runtime
producer traced (`meta_bootstrap.deep_merge`, `yaml_overrides.apply_overrides`,
`legend_blocks._strip_resolved`, `workbook_views.configure_workbook_view`,
`persistence_boundary.project_meta_to_persistable_contract`,
`rendering/frame_selection.py:85-86`, `frame_keys.copy_reserved_frames`) uses a
shallow-copy-on-write idiom: only the top-level dict (or the exact key path
being mutated) is freshly copied; every sibling key and every untouched
nested container remains the *same object* referenced by the caller's input.
Two places pass `_meta` through by direct reference with **zero** copying at
any level (`frame_selection.py:85-86`, `frame_keys.py:21-25`). This is
implementation reality, confirmed independently for Legend Blocks by
executing it against HEAD:

....
entries = [{'token': 'A'}]
frames = {'_meta': {'legend_blocks': {'b': {'entries': entries, 'title': 'B'}}}}
out = normalize_legend_blocks_shape(frames)
out['_meta']['legend_blocks']['b']['entries'] is entries   # True
....

*Load-bearing counter-finding:* no test anywhere under `tests/` asserts
object-identity on a nested `_meta` container. `test_legend_blocks_ingress.py`
asserts outer non-identity (`out is not frames`) and nested-content
*value*-equality (`==`), never nested `is`. `test_meta_bootstrap.py` and
`test_yaml_overrides.py` assert only scalar boolean flags. **This means an
E3 implementation that deep-copies (fully owns) `_meta` at the ingress
boundary, instead of aliasing, would not break any currently pinned test.**
Aliasing is therefore "currently relied upon" only in the weak sense of being
the default unexamined implementation pattern, not in the strong sense of
being asserted/depended-on supported behavior -- classified per FTR section 9
as *no current producer requires the aliasing to be observable*, so
normalizing ownership at E3 is compatible, at the cost of touching the
shallow-copy idiom in most producer modules (an E3 implementation-scope
consequence, not a compatibility blocker).

*Cycles:* no maintained code constructs a self-referential or mutually
cyclic `_meta` (no `d[k] = d` pattern, no `deep_merge(x, x)` call site found
repository-wide). No cycle-detection/guard code exists anywhere in the `_meta`
pipeline (`grep` for `cycle`/`circular`/`visited`/`seen` near meta code:
zero relevant hits; all hits are unrelated column-dedup loops or Python
import-cycle comments). No test constructs or asserts cyclic `_meta`
behavior. Classification per FTR section 9: *no current producer creates a
cycle* (not "explicitly unsupported" via an active rejection, and not
"currently relied upon") -- rejecting cycles at E3 is fully compatible.

== 8. YAML reserved metadata -- node-shape consequence

Current (pre-E3) behavior, confirmed independently: `yaml_backend.py`'s
`load_yaml_dir` globs `*.yml`/`*.yaml` generically with no exclusion for a
file stemmed `_meta`; such a file is parsed like any other sheet and lands
in `frames["_meta"]` as a `pd.DataFrame`. `save_yaml_dir` already skips
writing `_meta` (asymmetric convention, no round-trip promise). Duplicate
`.yaml`/`.yml` spellings are not de-duplicated on read; whichever the glob
processes last silently wins with no error.

This matches, node-shape-for-node-shape, the "before" state the FTR's
already-accepted Option A/F5 decision targets (reserve stem `_meta`,
safe-load exactly one file as a mapping, reject non-mapping/duplicate
spellings at the backend boundary, never reinterpret a DataFrame as
metadata from Domain ingress). **E3's consequence is to actually implement
that already-decided loader behavior; this census surfaces no new
YAML-shape question beyond what section 11 of the FTR already resolved.**
The one addition this census contributes: once the sidecar is safe-loaded as
a mapping, E3's substrate validation must still walk that mapping's *values*
(not just check the root), because `yaml.safe_load` can produce `set`
(`!!set`), `list[tuple]` (`!!omap`), and `bytes` (`!!binary`) leaves that the
root-is-mapping check alone would not catch.

* CSV/XML backends' missing filename exclusion for a foreign `_meta.csv`/
`_meta.xml` file (produces a `pd.DataFrame` root instead of a dict, mirroring
the pre-E3 YAML-dir gap). Neither backend is designed to carry `_meta`

already decided for YAML, once E3 lands -- not itself E3 scope.

and `_meta.sheets.*.helper_columns`: `meta_update.py`'s `_is_sequence`

== 14. Compatibility verdict

*A. PREFERRED VOCABULARY CONFIRMED*, with the following precise
qualifications, each already reflected in the sections above:

. **Legend Blocks** is the sole current delegate-shaped subtree (Mapping/list
authoring polymorphism, normalized to exact dict, nested-value aliasing
retained). It is explicitly anticipated by the accepted FTR text as the
delegate to migrate under section 11's governance rules -- not a new finding
requiring vocabulary revision.
. **Ownership/aliasing** is the systemic implementation default across nearly
every producer (shallow-copy-on-write; two paths pass `_meta` through by
direct reference with no copy at any level). No test pins nested-container
identity, so E3 may require full ownership (deep-copy at the ingress
boundary) without breaking any currently pinned behavior -- but doing so
touches the shallow-copy idiom across roughly fifteen producer modules, an
implementation-scope consequence for E3, not a compatibility blocker.
. **Cycles** are absent from every current producer and unguarded by any
current code; rejecting them is fully compatible.
. **YAML tag surface** (`!!set`/`!!omap`/`!!binary`) and the **legacy
`ast.literal_eval` blob fallback** are currently *reachable* but not
*relied upon* by any producer, test, or documented feature; E3's own
substrate validation is the correct place to close them, not a vocabulary
extension.
. The **YAML-dir accidental DataFrame root** is precisely the already-decided
Option A/F5 migration target -- E3 implements it, this census surfaces no
new disposition.
. **CSV/XML accidental DataFrame roots** and the **tuple-tolerance
inconsistency** on FK-relation paths are parked (<<parked-concerns>>) as
narrow, dormant, non-blocking follow-ups.
. **Unconstrained programmatic `_meta`** (bare `run_pipeline`, or
`orchestrate` without a `legend_blocks` key) reflects the deliberate absence
of any gate today -- not a counterexample to the vocabulary, but confirmation
of E3's necessity.
. **Consumer-side `Mapping`/`Sequence` duck-typing** (vs. producer-side exact
`dict`/`list`) is real and pervasive in validation code, but no producer ever
creates a genuine subclass instance; per FTR section 4's reachability
principle this tolerance does not force the vocabulary open, and E2's own
(unwired) admission already establishes `type(x) is dict` as the codebase's
precedent for exact-type boundary checks.

No concrete counterexample surviving this census requires E3 to adopt a
bounded alternative vocabulary or a pre-E3 migration. Every apparent
counterexample resolved to one of: transient/local-only computation never
reaching the `_meta` boundary; a currently-ungated gap that is exactly E3's
own job to close; or a migration already named and scoped by the accepted
FTR text itself.
