== 1. Exact question and preferred hypothesis under test

Per FTR section 23/E3 precondition and section 11: before E3 may treat the
`_meta` substrate as an owned, bounded, acyclic framework structure, an
independently accepted focused census must confirm or replace this preferred
hypothesis:

....
root:                    exact dict
recursive ordinary containers: exact dict, exact list
ordinary leaves:         E1-admitted Scalar (str | bool | int | float |
                         datetime.date | datetime.datetime | None, plus
                         admitted numpy/pandas carrier variants -- see
                         core/scalar_values.py:103-150)
exceptional semantics:   only explicitly named and governed delegates
....

The census must answer: what metadata node shapes must current supported
behavior admit at the E3 substrate boundary -- confirming this hypothesis, or
replacing it with a bounded alternative plus named migrations.

== 5. Container subclasses -- exact vs. generic

*Producers:* zero custom `Mapping`/`Sequence` subclasses exist anywhere in
`src/spreadsheet_handling/` (`grep -rn "class .*(.*Mapping.*)"` /
`"class .*(.*Sequence.*)"`, excluding tests: zero hits). Every current
producer emits exact `dict`/`list`.

*Consumers:* essentially every subtree handler (`meta_update.py`'s ~15
handlers, `workbook_views.py`, `legend_blocks.py`, `persistence_boundary.py`)
gates with `isinstance(x, Mapping)`/`isinstance(x, Sequence)` -- generic ABC
checks, not `type(x) is dict`. `domain/schema_maintenance/meta_update.py`'s
`_is_sequence` (line 1036) explicitly tolerates any non-`str`/`bytes`
`Sequence`, including `tuple`, for `constraints`, `helper_columns`,
`fk.relations`, and several `workbook_view`/`lookup` fields.

This is consumer-side duck-typed *tolerance*, never producer-side *reliance*:
no current path constructs a genuine `Mapping`/`Sequence` subclass instance
and writes it into `_meta`. Per FTR section 4's own reachability principle
("a node shape that is technically constructible but has no supported
producer or consumer is not automatically part of the compatibility
contract"), this tolerance does not force the vocabulary open. E3 may
legitimately narrow to `type(x) is dict`/`type(x) is list` at ingress without
breaking any current producer -- it only tightens what a duck-typed
direct-Python caller could get away with today. One inconsistency is worth a
small parked follow-up: `domain/transformations/fk_helpers/policy.py:53`
(`resolve_v2_fk_relations`) requires `isinstance(relations, list)` **exactly**
for `_meta.helper_policies.fk.relations`, while `meta_update.py`'s validator
for the *same* path tolerates any `Sequence`. No producer ever creates a
tuple there, so this is dormant, not load-bearing (<<parked-concerns>>).

E2's own (currently unwired) admission function uses the strictest form
already -- `type(frames) is not dict` at the outer Frames level
(`structural_admission.py:117`) -- consistent with, and useful precedent
for, an exact-dict E3 boundary check.

== 6. Aliasing and cycles

*Aliasing is the single most systemic finding of this census.* Every runtime
producer traced (`meta_bootstrap.deep_merge`, `yaml_overrides.apply_overrides`,
`legend_blocks._strip_resolved`, `workbook_views.configure_workbook_view`,
`persistence_boundary.project_meta_to_persistable_contract`,
`rendering/frame_selection.py:85-86`, `frame_keys.copy_reserved_frames`) uses a
shallow-copy/copy-along-the-mutated-path idiom: only the top-level dict or the
exact rewritten key path is freshly copied; sibling keys and untouched nested
containers retain caller-visible aliases. Two places pass `_meta` through by
direct reference with no copying (`frame_selection.py:85-86`,
`frame_keys.py:21-25`). This is implementation and compatibility evidence,
confirmed independently for Legend Blocks by executing it against HEAD:

....
entries = [{'token': 'A'}]
frames = {'_meta': {'legend_blocks': {'b': {'entries': entries, 'title': 'B'}}}}
out = normalize_legend_blocks_shape(frames)
out['_meta']['legend_blocks']['b']['entries'] is entries   # True
....

The original census incorrectly inferred blanket deep-copy permission from an
incomplete identity-test search. Maintained failure-atomicity tests in
`tests/integration/pipeline/test_domain_ingress_boundaries.py` explicitly pin
the identities of `_meta`, `sheets`, sheet metadata, `options`, and nested
`column_widths` after a failed staged operation. Other producer tests pin
untouched sibling aliases. More importantly, tests are not the whole contract:
the accepted F7 disposition explicitly excludes deep-copy ownership, alias
tracking, retained-alias isolation, concurrent isolation, and later-mutation
guarantees.

The E3 consequence is therefore precise. Ingress and governed delegates build
and validate staged candidates without mutating caller-owned input through
their own work, copy along paths they normalize or rewrite, and publish only
after successful validation. They need not recursively deep-copy every
accepted container, establish globally unique container identity, or isolate
retained aliases outside rewritten paths. Acyclic shared aliases are permitted.

*Cycles:* no maintained metadata producer constructs a self-referential or
mutually cyclic `_meta`; cycle rejection is the already-accepted acyclic E3
contract. It is not alias rejection. Traversal reaches a cycle only when an
object is encountered while that same object is active on the current ancestor
path. Encountering the same acyclic child again after another path has
completed is a shared alias and must not be rejected merely because it was
globally "seen" before. E3 owes cycle detection, not alias detection or
copying.

== 8. YAML reserved metadata -- node-shape consequence

Current (pre-E3) behavior, confirmed independently: `yaml_backend.py`'s
`load_yaml_dir` globs `*.yml`/`*.yaml` generically with no exclusion for a
file stemmed `_meta`; such a file is parsed like any other sheet and lands
in `frames["_meta"]` as a `pd.DataFrame`. `save_yaml_dir` already skips
writing `_meta` (asymmetric convention, no round-trip promise). Duplicate
`.yaml`/`.yml` spellings are not de-duplicated on read; whichever the glob
processes last silently wins with no error.

This matches, node-shape-for-node-shape, the "before" state the FTR's
already-accepted Option A/F5 decision targets (reserve stem `_meta`,
safe-load exactly one file as a mapping, reject non-mapping/duplicate
spellings at the backend boundary, never reinterpret a DataFrame as
metadata from Domain ingress). **E3's consequence is to actually implement
that already-decided loader behavior; this census surfaces no new
YAML-shape question beyond what section 11 of the FTR already resolved.**
The one addition this census contributes: once the sidecar is safe-loaded as
a mapping, E3's substrate validation must still walk that mapping's *values*
(not just check the root). `yaml.safe_load` can produce `set` (`!!set`),
`list[tuple]` (`!!omap` and `!!pairs`), and `bytes` (`!!binary`) that the
root-is-mapping check alone would not catch. The structured JSON-sidecar writer
also currently emits set and bytes; section 17 distinguishes those
compatibility-relevant cases from syntax that is merely safe-load reachable.

=== 17.1 Compatibility authority and decision principle

The corrected census distinguishes four levels of evidence that the original
text conflated:

* *mechanically writer-producible:* a serializer happened to accept the Python
  value;
* *maintained roundtrip-supported:* the maintained carrier's broad acceptance
  promises metadata roundtrips through its writer and reader;
* *intentionally semantic:* a maintained metadata family, public contract,
  example, or consumer assigns stable meaning to the value category; and
* *historically compatibility-promised:* an accepted decision preserves read
  compatibility for an older framework-produced carrier.

The Domain vocabulary is selected by maintained semantic/support contracts,
not by the accidental union of PyYAML and `ast.literal_eval`. Conversely, a
published generic roundtrip or legacy-read promise is real compatibility and
cannot be narrowed silently merely because no family-specific producer or test
uses a value.

Current sidecar set and bytes have a combination of broad carrier-roundtrip
authority and incidental serializer capability (levels two and one), but no
intentionally semantic metadata authority was found. The legacy special
literals have historical readability authority and were mechanically
writer-producible, but likewise have no family-semantic contract. The accepted
`ADR-META-BLOB-SERIALIZATION` promise means the retained reader recovers the
legacy metadata dict and its literal values; it is stronger than byte-level
carrier parseability. It does not require every Python-literal value to remain
in the canonical Domain grammar forever. Narrowing that later contract is an
explicit compatibility migration with a release consequence, selected here
under FTR section 11's pre-E3 evidence gate.

No generic normalization is authorized. In particular, set-to-list,
tuple-to-list, bytes-to-string, and complex-to-string/pair/object conversions
are not semantics-preserving without a family-specific contract. The
correction chooses targeted rejection/migration instead of adding accidental
serializer categories to the common grammar or to E1 Scalar.

=== 17.5 F2 ownership and graph-topology correction

The phrase "owned bounded acyclic substrate" means framework authority and
responsibility for validation, normalization, staged publication, and
sanctioned mutation. It does *not* mean recursively unique Python-object
ownership.

Trusted Ingress establishes:

* staged candidate construction and validation;
* no mutation of caller-owned input through ingress/delegate work;
* publication only after successful validation;
* copy-along-the-mutated-path where normalization or rewrite requires it; and
* an acyclic bounded substrate.

Trusted Ingress does not establish:

* complete recursive physical ownership or mandatory blanket deep copying;
* retained-alias isolation or alias tracking;
* globally unique container identity;
* concurrent isolation or protection from later out-of-band writes; or
* rollback of prior/plugin/external side effects.

A shared alias is the same acyclic child reachable through multiple completed,
non-ancestor paths. It is permitted and does not require detection or copying.
A cycle exists when traversal reaches an object already active on the current
ancestor path. E3 must reject the latter without using a global "seen once"
rule that would reject the former. This contract supplies no alias-isolation
guarantee.

In framework-managed normal execution, a parsed payload is logically handed
to Domain processing; no supported execution model assumes an independent
concurrent owner mutates the same conformant graph out of band. Mandatory deep
copy would add cost and complexity without serving that model. Programmatic or
library callers may retain references, but must not mutate conformant state
through those aliases out of band while the framework operates on it. A caller
that needs stronger isolation must establish it itself. Permanent explanatory
treatment belongs to the post-Phase-E Technical Model/Developer Guide
condensation, not this bounded correction.

output (section 17.4) rejects a non-`str` key here identically to an
ordinary metadata path; no separate delegate exemption.
|===

No generic normalization is authorized. In particular, `int`/`bool`/`float`/
`None` -> `str` key coercion is *not* adopted, for two independently
sufficient reasons demonstrated in section 18.2: (1) it is not
semantics-preserving without a family-specific contract, matching section
17.1's rule for values; and (2) it is demonstrably lossy under collision --
Python's own `{1: ..., True: ...}` equality (`1 == True`) already collapses
distinct-looking keys before any carrier is involved, and the current JSON
carrier's silent `int -> str` coercion independently loses data when both
`1` and `"1"` are present. Targeted rejection, not coercion, is the only
disposition consistent with the no-generic-normalization rule already
established for values.

=== 18.7 Diagnostic safety consequence

A rejected non-`str` key must be identified by structural coordinates only:

....
metadata path to the parent container
entry ordinal within that container
failure kind = unsupported_metadata_key
....

The diagnostic must not include `repr(key)`, `str(key)`, or any operation
beyond the safe classification already used elsewhere in this census
(`type(x) is dict`-style exact-type checks): an unclassified rejected key may
carry a hostile or expensive `__repr__`/`__str__`, and retaining the key
object itself for later diagnostic formatting is not required. This mirrors
the value-shape diagnostic rule already stated in section 17.2 ("without value
`repr`/`str`"), extended to keys. This section states the safety obligation;
it does not name a final error-class, which existing E3 diagnostic authority
owns elsewhere.

=== 18.8 Delegate consequence

The exact-`str`-key rule applies to *complete* delegate output, not just
directly-authored metadata. Legend Blocks (or any later governed delegate)
may not emit an out-of-contract dictionary key and escape the central
post-check by virtue of delegate status; section 17.4's "complete output
subject to the common recursive post-check" already covers this without
further change. Legend Block entry-value semantics remain out of scope here,
per section 17 and `FTR-LEGEND-BLOCKS-ENTRY-CONTRACT-P5`.
