==== 1. Problem statement

The project intends to harden Domain transformations one family at a time
(roadmap Family cycles 0-7). Without a durable maintainer contract, each family
refactor would re-derive package shape, naming, compatibility judgment, ingress
assumptions, provenance handling, and test expectations from first principles --
exactly the re-derivation the completed three-family Human Readability
investigation performed once already. Repetition risks two failure modes:

. *Sediment preserved as architecture.* Overlapping public transformations,
  obsolete version vocabulary (`v2` with no live `v1`), implementation-shaped
  configuration, duplicated mechanisms, compatibility workarounds, inconsistent
  provenance/lifecycle conventions, and arbitrary defensive ingress logic get
  frozen into the "cleaned-up" result merely because they already exist.
. *Gratuitous breakage.* An over-eager simplification removes real distinct
  capability, or broadens/rewires Trusted Ingress opportunistically, because no
  rule forced the maintainer to justify the change against evidence.

The Domain Maintainer Contract (DMC) is the durable, bounded, reusable rule set
that governs *how* a maintainer evaluates and refactors one family without
committing either failure. It is not a transformation-family design and it does
not freeze current behavior.

The concrete forcing example throughout is
`FTR-FK-REFERENCE-HELPER-SURFACE-CONSOLIDATION-P5`: one helper-column concept
currently exposed through two public routes (`add_fk_helpers` in
`domain/transformations/fk_helpers/` and `add_lookup_helpers` in
`domain/transformations/enrich_lookup/`) with different capabilities, aliasing,
in-place-vs-new-frame semantics, provenance shapes, and Trusted-Ingress
certification. It is used only to test the contract's rules; this artifact does
*not* design that family or decide its canonical surface.

==== 2. Contract scope and non-scope

*Scope: option H from the task's step 3 -- all layers, explicitly separated.*
The DMC governs, as distinct layers a maintainer must address in order and must
not collapse into one another:

[cols="1,4",options="header"]
|===
| Layer | The DMC's concern

| A. Public transformation semantics | What domain concept a family exposes and
  the smallest coherent public surface for it (<<semantic-first>>).
| B. Internal implementation structure | Package shape, module responsibility,
  navigability -- but only as the roadmap's *advisory* structural conventions,
  never silently promoted to hard gates (<<doc-ownership>>, cites the roadmap's
  Family cycle 4 and the Human Readability Review Guide).
| C. Family-level lifecycle / provenance / metadata | Where derived state and
  its provenance live, cleanup/replay/reconstruction, in-place vs new-frame
  (<<state-provenance>>).
| D. API compatibility and breaking-change decisions | The
  preserve/migrate/deprecate/remove/merge/rename rule (<<compat>>).
| E. Trusted-Ingress assumptions | What a family may assume after the managed
  boundary, and what it must not reintroduce (<<trusted-ingress>>).
| F. Testing / review requirements | The layered test contract and independent
  review gate (<<testing>>, <<review-gate>>).
| G. Documentation ownership | Which permanent surface owns which outcome, with
  one canonical owner per rule (<<doc-ownership>>).
|===

*Why H and not a single layer.* The roadmap's Family cycles 0-7 already own
these as *distinct* concerns (ontology, security, types, structure, tests,
maintainer-readiness, durable docs). Forcing them into one layer would erase the
distinctions the project explicitly wants to preserve, and would let a
structural cleanup silently make a semantic or compatibility decision. The DMC
therefore layers them and requires each to be answered on its own evidence.

*Non-scope.* The DMC does *not*:

* design any transformation family, or decide the FK/lookup canonical surface;
* freeze current behavior, or treat existing public surface as automatically
  worth preserving;
* add new `make source-style-guards` rules or change any existing guard's
  severity (roadmap DMC non-goal);
* convert the provisional, non-binding Human Readability Review Guide into a hard
  CI gate (roadmap DMC non-goal; guide's own §1 status);
* re-document Trusted Ingress -- it points to the permanent owning docs;
* start Phase F, the first family pilot, or D-T3.

[[family-def]]
==== 3. Family definition -- the unit of refactor

A Domain *family* is a bounded set of transformations, helpers, metadata
policies, and inverse operations that together express *one coherent domain
capability*. A family is *not* defined by a single Python module boundary, and
*not* by a single registered step name.

A maintainer draws the family boundary by identifying, together:

* the conceptual capability the family exposes to a user or domain caller;
* every *public entry point / registered step* that expresses part of that
  capability -- including historically separate routes that overlap (the FK
  example spans `add_fk_helpers`, `add_lookup_helpers`, and their reorder /
  removal / `apply_derived_column_policy` siblings across two Python packages);
* the shared *helper / private mechanisms* (provenance writers, key resolvers,
  formula producers) the routes rely on;
* the *metadata / provenance policies* the family produces or consumes
  (for FK helpers: the `_meta["derived"]` transient side-channel and any
  `helper_policies` shape);
* the *inverse / readback / cleanup* operations that belong with the forward
  path (removal, reorder, derived-column policy, drop-on-persist);
* the *maintained consumers* that exercise it (the Worldbuilding smoke path for
  FK helpers);
* the *related active FTRs* that must be considered together rather than
  refactored in isolation -- for the FK family that includes
  `FTR-FK-HELPER-POLICY-LIFECYCLE-P4A`, `FTR-META-LIFECYCLE-INVENTORY-P5`, and
  `FTR-FK-HELPER-COLUMN-GROUP-META-P5`.

A Python package boundary is *evidence* for a family boundary, not a definition
of it: two packages may be one family (FK helpers + enrich lookup), and one
package may host more than one capability.

==== 4. Inventory contract -- minimum before touching a family

Before changing a family, the maintainer produces a *bounded* working inventory
(temporary material, not a new permanent specification -- roadmap Family cycle
0). It is deliberately smaller than the Phase-E census machinery. It records:

. public transformations / registry step names, and their registry targets;
. direct programmatic surfaces (importable functions callers actually reach);
. configuration / YAML forms that drive the family;
. inputs and outputs (frames, carriers), and which is canonical vs derived;
. metadata / provenance produced or consumed, with lifecycle class;
. reversibility / cleanup / readback operations;
. external adapters or sinks involved, if any;
. maintained-consumer usage (which consumer, which call sites);
. tests that exercise the *actual managed entry points*, not only direct
  transformation functions;
. obsolete aliases / duplicate routes / dead compatibility paths;
. historical versioned terminology present (`v2` without live `v1`, slice IDs
  in symbols/config/docs);
. Trusted-Ingress controlled-state interaction, if any (controlled roles,
  certificates, formula producers).

If a row is empty for a family (e.g. no controlled-state interaction), the
maintainer records "none" rather than omitting it, so the reviewer can see the
question was asked. The inventory is complete when the supported behavior and
public surface are identifiable and proposed changes can be separated from
unrelated family behavior (roadmap Family cycle 0 exit criteria).

==== 5. Semantic-first rule -- concept before function graph

[[semantic-first]]
A family refactor *starts from desired domain semantics, not the current
function graph*. Before proposing any surface change, the maintainer answers:

* What single concept does this family expose?
* What is canonical data vs derived / display state?
* What public operation should a user think in?
* Which configuration dimensions are *semantic* vs merely implementation
  accidents?
* What is the smallest coherent public surface for the concept?
* Which current variants are genuinely distinct capabilities, and which are
  duplicate historical routes to the same capability?

The number of existing functions is *not* the answer. `add_fk_helpers` and
`add_lookup_helpers` must not automatically become two permanent concepts merely
because two functions exist; nor must they automatically merge merely because
they overlap. The maintainer decides from the concept, then reconciles the
surface to it.

*One concept -- one preferred surface.* A single conceptual Domain capability
should normally have *one* canonical public surface. Exceptions -- multiple
surfaces retained -- are legitimate only when the surfaces represent genuinely
*distinct domain transitions*, not differently-shaped historical APIs for the
same transition. Two operations may stay separate because they mean different
things (forward projection vs inverse cleanup); two APIs must not stay separate
merely because they already both exist. This is an anti-sediment rule, not a
function-count-minimization rule: minimizing surface is not itself the goal, and
must never hide a real input, lifecycle, or capability (Human Readability Review
Guide §5 counterexamples).

==== 6. Compatibility / simplification rule

[[compat]]
The project has non-beta releases but has *explicitly not* promised long-term
stability of the current user surface, and no known independent consumer is
outside project-owner control (`interfaces_and_gates.adoc`; roadmap "complete
behavior before consolidation"). Breaking cleanup is therefore permitted but
must be *deliberate and evidence-backed*, never gratuitous.

For each element of a family's surface (a step, a flag, a config field, a helper
name, a provenance shape), the maintainer selects exactly one disposition and
records the evidence:

[cols="1,3,2",options="header"]
|===
| Disposition | When | Evidence required

| *preserve* | The element is a distinct capability *and* is actively relied
  upon, or removing it costs more than it saves. | A named current consumer or
  distinct-capability argument. Duplicate surface is *not* preserved for
  compatibility without such evidence.
| *migrate* | The capability survives under a different canonical surface. | A
  migration path plus a maintained consumer moved onto the new surface as an
  acceptance probe.
| *deprecate* | The element is redundant but immediate removal is disruptive. |
  A canonical replacement exists; deprecation is time-bounded, not permanent.
| *remove* | The element is redundant, dead, or historically defensive with no
  live capability. | Proof no maintained consumer needs it, or an accepted
  breaking-change decision.
| *merge* | Two surfaces are the same domain transition through different
  historical shapes. | A semantic argument that the transition is identical, and
  a superset surface that loses no real input (cf. the FK example's alias/prefix
  vs asymmetric-key capabilities, which a merge must *both* retain).
| *rename* | The name states mechanism or historical ontology rather than the
  domain concept. | A naming decision per <<naming>>, plus symbol/config/doc/
  provenance update scope.
|===

Rules of the road: evidence is required *before preserving* duplicate surface,
and evidence is equally required *before breaking* it. Maintained consumers act
as the migration-evidence and acceptance probes. Where a break is chosen, the
release-notes checkpoint (`git_and_workflow.adoc`) applies.

==== 7. Naming and version-sediment rule

[[naming]]
Naming decisions prefer *domain / user vocabulary* over implementation
mechanism, and state *current* responsibility rather than historical ontology or
accidental shape (`01_code_conventions.adoc` naming conventions; Human
Readability Review Guide §2 truthful vocabulary). The DMC defines *how* the
decision is made, not the answer: for the FK example, whether "FK helper",
"reference helper", or "lookup helper" is canonical is decided by the family
design from the concept -- treating "lookup" as *mechanism* unless the design
establishes it as the domain term.

*Obsolete version labels.* A version / slice label (`v2` where no `v1` remains,
`E4`, `D-T1`, `I-2`) may remain only as *optional provenance*. It must be
*removed from public config, metadata, code symbols, and permanent prose* when
it no longer communicates a *current* compatibility, migration, or operational
distinction. Keep such a label only on that test -- for example `schema_version:
2` that is still operationally meaningful stays; a private `v2` symbol that is
mere residue goes (Human Readability Review Guide §2). A historical ID retained
purely as a citation next to otherwise-complete prose does not need stripping;
the rule bites only when understanding the *sentence* requires resolving the ID
(Reference Readability, `01_code_conventions.adoc`; see <<reference-readability-rule>>).

==== 8. Trusted-Ingress relationship

[[trusted-ingress]]
Trusted Ingress is established permanent architecture. Its owning documents are
`docs/technical_model/ch06_architectural_layers/architectural_layers.adoc`
("Establishing and Re-establishing the Domain Scalar Language" and "Description
and Resource Authority"), the caller-facing summary in
`docs/ai_info/interfaces_and_gates.adoc`, and the maintainer checklist in
`docs/developer_guide/ch06_code_conventions/04_trusted_ingress_extension.adoc`.
The DMC does *not* re-document Trusted Ingress; it states the *family-level
consequences*:

* Ordinary family code *may assume* Ingress-Conformant Domain Payload after the
  framework-managed boundary (six-category Scalar grammar for ordinary cells;
  preserved carrier identity; established Missing representation).
* Family code *retains its own semantic / business preconditions* (required
  columns, unique keys, complete mappings, header depth, forbidden information
  loss, ordering constraints).
* Family code *must not reintroduce arbitrary external-carrier defensive
  interpretation* (rejecting arbitrary Python objects, callables, modules,
  handles, opaque binaries) that the managed boundary already owns -- such
  historical guards are removed with their redundant tests (roadmap Family cycle
  2 classification).
* *Controlled non-ordinary state* (exact `FormulaSpec` producers, `GroupedMatrix`
  and other composites, cleanup / manifest states) requires *explicit accepted
  transition authority*; a family must not manufacture controlled-role identity.
* A family refactor *must not opportunistically broaden Trusted-Ingress
  certification* merely to keep a redundant historical API alive. (The FK FTR
  makes this explicit: do not add a second certification path for the legacy
  `add_fk_helpers` formula producer to preserve the overlap.)
* Once the canonical family surface is chosen, Trusted-Ingress transition
  authority *aligns to that surface* -- exactly one formula producer /
  controlled transition per accepted capability, targeted at the canonical
  public function.

==== 9. State / provenance / lifecycle rule

[[state-provenance]]
Every family review *explicitly classifies* each piece of state it touches,
using the vocabulary the Semantic and Technical Models already own (do not
invent a new generic ontology):

* *canonical* -- source of truth for persistence and roundtrip
  (`meta_canonical`, canonical frames);
* *derived* -- recomputable presentation/enrichment (helper columns, the
  `_meta["derived"]` transient side-channel; `meta_rendering`);
* *helper / presentation* -- workbook-view-only state;
* *controlled temporary state* -- Trusted-Ingress controlled roles / certificates;
* *metadata / provenance* -- where a derived value records where it came from;
* *external representation* -- carrier / sink form.

The classification answers, per state: may it be edited? recomputed? must it
round-trip? may it be dropped before persistence? does it need inverse
reconstruction? is it merely workbook presentation? The provenance questions the
maintainer must answer for the family:

* where derived state records its provenance, and who consumes it;
* cleanup / removal semantics (who drops it, and when);
* replay / idempotence and reconstruction behavior;
* stale-provenance handling;
* in-place mutation of the source frame vs producing a new frame / output;
* relation to the workbook view / render lifecycle.

The FK example exposes exactly the accidental differences this rule is meant to
surface: `add_fk_helpers` decorates the source frame in place and writes one
`_meta.derived` shape; `add_lookup_helpers` projects a differently-named output
and rejects source-column collisions, with a different provenance shape. The DMC
requires these differences to be *rationalized*, not preserved by default. It
does *not* prescribe one universal provenance mechanism unless the current
architecture already supports one -- coordinate with
`FTR-META-LIFECYCLE-INVENTORY-P5` rather than inventing a mechanism here.

==== 10. Configuration rule

[[config]]
Family configuration is evaluated against these properties, distinguishing
*semantic configuration* from *transport / YAML syntax*:

* explicit *semantic dimensions* only (each option maps to a real domain choice);
* *bounded vocabulary* (closed value sets, not open-ended interpretation);
* *no hidden interpretation heuristics* inferred from payload shape;
* *no obsolete fields* retained without a current purpose (v1/v2 residue);
* *no duplicated config paths* for the same concept;
* *clear defaults* and clear alias / naming semantics where relevant;
* *declarative form and programmatic surface aligned* where feasible.

YAML/CLI keys and step-parameter shapes are gated surface
(`interfaces_and_gates.adoc`); a configuration change that touches them takes the
compatibility disposition from <<compat>> and the config/CLI-owner gate from the
Human Readability Review Guide §6.

==== 11. Consumer-evidence rule

[[consumer-evidence]]
Maintained consumers are *migration evidence and acceptance probes*, not
decoration. The Worldbuilding smoke test already demonstrated their value:
core tests were green while a maintained consumer exposed both the
`add_fk_helpers` / `add_lookup_helpers` overlap and a managed-pipeline formula
producer mismatch. Evidence is *proportional to the surfaces the family actually
touches* -- a family that never renders a spreadsheet does not run spreadsheet
parity tests.

A family needs the corresponding evidence when it has the corresponding surface:

[cols="2,3",options="header"]
|===
| The family... | ...requires
| has a maintained consumer | a consumer usage census and a migration plan
| changes a public surface a consumer uses | that consumer migrated as an
  acceptance probe before the redundant surface is removed
| produces spreadsheet output | a fresh export/reimport and, where the consumer
  maintains both, XLSX/ODS parity
| changes semantics of produced data | a semantic diff across the migration
| interacts with controlled state / Trusted Ingress | an end-to-end
  managed-pipeline compatibility probe, not only a direct-function test
|===

==== 12. Testing contract

[[testing]]
A family refactor carries layered test expectations, sized to its surfaces (no
exhaustive combinatorial matrices -- roadmap "test contracts, not every
Cartesian combination"; Family cycle 5):

* *(A) Semantic unit tests* for the family's domain invariants, owned once at
  the domain boundary.
* *(B) Managed-boundary tests* where Trusted Ingress or controlled state matters
  -- exercised through the managed entry point, not only the direct function.
  The FK discovery is the standing evidence that direct transformation tests
  alone miss managed-pipeline regressions.
* *(C) Architecture guards* for the public / registry surface (package-root
  public API stability; `pipeline_step_registry` mirror; `meta_registry`
  producer/consumer registration; layer/import boundaries).
* *(D) Inverse / roundtrip tests* where the family has readback / cleanup /
  reversal.
* *(E) Maintained-consumer integration tests* where real usage exists.

Redundant hostile-input tests move to ingress (roadmap Family cycle 5); private
implementation-detail snapshots are removed unless they protect a deliberate
stable representation. Module/function size and complexity stay *advisory*
(WARN, review trigger), never auto-failing CI, unless a separate explicit
decision changes that (roadmap Family cycle 4 "Size guidance"; Human Readability
Review Guide §1).

The advisory structural conventions (module responsibility vocabulary, package

==== 14. Family completion checklist -- exit criteria for one family

[[exit-checklist]]
A family refactor is complete only when all apply (skip a row only by recording
"not applicable" with a reason):

. desired *concept* stated (semantic-first, <<semantic-first>>);
. canonical *public surface* chosen; redundant-surface disposition decided per
  <<compat>>;
. *semantic configuration* defined; obsolete config/version sediment removed
  (<<config>>, <<naming>>);
. *state / provenance lifecycle* defined and rationalized (<<state-provenance>>);
. *Trusted-Ingress relationship* defined; exactly one controlled transition per
  accepted capability; no opportunistic certification broadening
  (<<trusted-ingress>>);
. *maintained-consumer migration* completed as an acceptance probe
  (<<consumer-evidence>>);
. relevant *managed / roundtrip / parity tests* green (<<testing>>);
. *permanent docs* updated with one canonical owner per rule (<<doc-ownership>>);
  release-notes checkpoint applied or waived with reason;
. *obsolete terminology* removed from symbols/config/metadata/prose; historical
  IDs retained only as optional provenance;
. *historical evidence* archived / curated to cold storage;
. *Project Memory* updated with a concise lifecycle pointer;
. *Reference Readability* satisfied: the family's permanent docs and code read
  correctly without resolving old FTR IDs, review-finding IDs, obsolete version
  names, or implementation archaeology (<<reference-readability-rule>>).

==== 15. Reference Readability / archaeology rule

[[reference-readability-rule]]
The established *Reference Readability* principle
(`docs/developer_guide/ch06_code_conventions/01_code_conventions.adoc`,
`[[reference-readability]]`) governs the finished family: a transient
work-package or review-finding ID may carry *provenance* but never the
*semantic meaning* of permanent prose. A completed family's implementation and
documentation must be understandable without resolving old FTR IDs, review
finding IDs, obsolete version names, or historical implementation archaeology
against a backlog artifact or review ledger. Historical IDs may remain as
optional provenance (a parenthetical citation, a "see also"); permanent meaning
must stand independently. This is the same standard `DOC-COMP-TEST-1` applied to
Trusted Ingress documentation closure, and it is the family analogue of the
Human Readability Review Guide's "bounded reconstruction without avoidable
archaeology".

==== 16. First-pilot sequencing assessment

[[first-pilot]]
*Recommendation: the FK / reference-helper family
(`FTR-FK-REFERENCE-HELPER-SURFACE-CONSOLIDATION-P5`) is the correct first family
pilot after the DMC is accepted -- with a bounded family boundary drawn per
<<family-def>>.* Justification against the roadmap's "Selecting the first
family" criteria:

* *Real, already-surfaced pain.* A maintained consumer (Worldbuilding
  `Places -> Regions`) has *already* exposed concrete surface overlap and a
  managed-pipeline formula mismatch -- the strongest evidence any candidate has,
  and the reason Project Memory records it as the strongest candidate.
* *Representative.* It spans domain transformation, provenance/metadata carriers
  (`_meta.derived`), the pipeline registry (five registered steps), and
  spreadsheet adapters (formula vs values, XLSX/ODS) -- it exercises the whole
  DMC.
* *Bounded and measurable.* The overlap is concrete and the simplification
  (one canonical surface) is measurable, without a new feature effort.
* *Distinct capabilities on the table*, which stress-tests the merge rule: the
  pilot must retain *both* `add_fk_helpers`' alias/prefix output naming *and*
  `add_lookup_helpers`' asymmetric `source_key`/`lookup_key` -- a good test that
  the DMC prevents lossy over-merging.

*Caveats / prerequisites the DMC forces the pilot to honor (not blockers, but
coordination):*

* Draw the family boundary to include `enrich_lookup`, the reorder / removal /
  `apply_derived_column_policy` siblings, and the `_meta.derived` provenance --
  not just `fk_helpers/`.
* *Coordinate with, do not absorb,* `FTR-FK-HELPER-POLICY-LIFECYCLE-P4A`
  (v1/v2 `helper_policies` sediment) and `FTR-META-LIFECYCLE-INVENTORY-P5`
  (provenance mechanism) -- both are explicitly named non-goals of the FK FTR
  itself.
* Do *not* broaden Trusted-Ingress certification to the legacy producer as a
  substitute for consolidation (FK FTR non-goal; <<trusted-ingress>>).

*Why not D-T3 first.* `FTR-DATE-TIME-INTERNAL-VALUE-MODEL-P4A`'s D-T3 is named
in the roadmap as a *candidate* first pilot, but it is a still-unselected
compatibility pilot tied to Date/Time typing, without the standing maintained-
consumer pain the FK family already has, and its own scheduling is deferred
behind D-T2. It remains a candidate, not a preferable first pilot, and this
artifact does not start it. No *prerequisite family must precede* the FK
family; the FK family is the recommended pilot, subject to the coordination
above.

*This is a recommendation only. No family refactor is started by this artifact.*

==== 17. Permanent placement recommendation

[[placement]]
*Recommendation: the DMC's single canonical permanent home is the Developer
Guide*, as a new maintainer-contract section in / alongside
`docs/developer_guide/ch06_code_conventions/` (the chapter that already owns code
conventions, domain-boundary patterns, the Human Readability Review Guide, and
the Trusted-Ingress extension checklist). Rationale:

* the DMC is *maintainer procedure*, and the Developer Guide is the documented
  owner of maintainer procedure (<<doc-ownership>>);
* ch06 already hosts the exact evidence base the roadmap says the DMC should
  *graduate* rather than re-derive (`01_code_conventions.adoc`,
  `02_domain_boundary_patterns.adoc`, `03_human_readability_review.adoc`,
  `04_trusted_ingress_extension.adoc`);
* it avoids creating a competing normative copy in the Technical Model.
