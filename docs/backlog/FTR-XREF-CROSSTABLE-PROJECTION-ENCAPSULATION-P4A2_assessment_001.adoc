== 1. Executive conclusion

*Keep `project_by_role` a public, consumer-facing pipeline step, separately
composed (Option A).* Do not encapsulate its logic inside the normal
XRef-crosstable forward/inverse capability, and do not open an implementation
FTR.

The narrower encapsulation hypothesis -- that `project_by_role` contains normal
XRef-crosstable adaptation logic exposed at the wrong abstraction level -- is
not supported by the consumer evidence:

* On the *outbound* path `project_by_role` is *not* adjacent to the XRef
  forward. A `join_frames` step sits between `contract_xref` and
  `project_by_role`; that join adds the workbook-view display helper
  (`title`). The projection adapts a *view-enriched* matrix, not the raw
  contracted relation.
* The columns `project_by_role` orders (outbound) and drops (inbound) are
  *workbook-view* artifacts (`title`), which the canonical XRef relation model
  deliberately does not represent: `contract_xref` requires the relation to be
  exactly `row_keys + column_key + value`, and `expand_xref` melts every
  non-key column. Folding view-helper handling into those primitives would
  conflate canonical relation transformation with workbook-view adaptation.
* `expand_xref` is a *foundational* primitive that both grouped-XRef
  (`contract_grouped_xref` / `expand_grouped_xref`) and compact-multiaxis
  (`expand_compact_multiaxis`) build on. It is a protected surface.
* The five projected surfaces do not even share one symmetric XRef pair: four
  use `contract_xref` / `expand_xref`; the fifth (`story_group`) uses
  `contract_xref` forward and `expand_compact_multiaxis` inverse. No single
  normal-XRef composite could cover all five symmetrically.
* The shared `column_roles` resolver has a second live consumer (validation
  role targeting), so it must remain shared regardless of the projection step's
  fate.

`project_by_role` is therefore correctly placed: a small, backend-neutral,
role-aware view-adaptation step that composes *around* the canonical XRef
operations, not *inside* them.

== 4. Ordinary XRef public-path trace

Public ontology (Core `registries/pipeline_step_registry.json`,
`src/spreadsheet_handling/domain/transformations/`):

* *Normal XRef crosstable pair:* `contract_xref` (forward: long relation ->
  matrix) and `expand_xref` (inverse: matrix -> long relation), both in
  `xref_crosstable/operation.py`. `expand_xref.inverse_step = contract_xref`.
* *Compact-multiaxis pair* (code/legend matrices): `contract_compact_multiaxis`
  / `expand_compact_multiaxis` in `compact_multiaxis.py`.
  `expand_compact_multiaxis` *wraps `expand_xref`* internally (+ cell codec).
* *Grouped-XRef specialization* (out of scope for this assessment):
  `contract_grouped_xref`, `expand_grouped_xref`, `reconstruct_grouped_matrix`,
  `project_axis_labels`, `restore_axis_keys`. The registry states these compose
  *unchanged* `contract_xref`; grouped XRef adds no metadata root.

Contract facts that bound the design:

* `contract_xref(..., drop_source=True)` enforces that the relation holds *no
  fields beyond `row_keys + column_key + value`*. The canonical relation model
  has no slot for a display helper.
* `expand_xref` has no helper/exclude parameter; by default value columns are
  "every column except `row_keys`". A `title` column present at expand time
  would be melted as a spurious matrix-value column.
* Neither primitive reads or writes helper-column metadata; the display helper
  `title` originates entirely from `join_frames` (outbound) and is declared to
  the view by `configure_workbook_view` (`helper_columns: [title]`).

== 5. Shared-resolver versus XRef-adaptation boundary

Three responsibilities, cleanly separable:

. *Shared role resolution* -- `spreadsheet_handling.domain.column_roles`
  (`resolve_column_roles`) and its `{row_identity, display_helper,
  matrix_value}` taxonomy. Consumed by `project_by_role` *and* by
  `domain/validations/validate_columns.py` (validation role targeting;
  `add_validations ... roles: [matrix_value]`). *Must remain shared;* the
  second consumer disproves any "single-consumer, inline it" argument.
. *XRef-crosstable adaptation* -- direction-specific ordering and retention of
  the display helper relative to the dynamic `matrix_value` set (outbound:
  `display_helper`, `row_identity`, then dynamic values; inbound: drop
  `display_helper`, keep identity + dynamic values). This is *workbook-view*
  adaptation layered on top of the canonical matrix, *not* part of the
  canonical XRef relation.
. *Consumer-specific configuration* -- worldbuilding's `title` helper,
  `story_id` key, sheet names, and step placement. These are ordinary
  contract inputs (`helper_columns` / `key_columns`), not evidence that a
  consumer-specific wrapper is required.

== 6. Current consumer-facing friction

Real, but mild and legitimate:

* Ten near-identical `project_by_role` invocations across two files. The
  repetition is declarative and uniform; each site reads clearly.
* A pipeline author must understand the three-part choreography per surface:
  (a) outbound, join the display helper then `project_by_role(outbound)`;
  (b) inbound, `project_by_role(inbound)` to drop the helper before the XRef
  inverse. This is genuine required knowledge, but it reflects a real
  distinction (canonical relation vs. workbook view), not accidental
  complexity.

No friction rises to the level that justifies changing a protected canonical
primitive or minting a new public surface.

== 7. Option comparison

Option A -- *retain current public composition.* *Selected.* Steps are
individually meaningful; `join_frames`, `project_by_role`, and `expand_*` each
name a real operation. Explicit composition keeps canonical transformation and
view adaptation visibly separate.

Option B -- *absorb into `contract_xref` / `expand_xref`.* Rejected.
(1) The forward cannot fold it: the display helper is joined *after*
`contract_xref`, so `contract_xref` never sees it. (2) The inverse would need a
new "drop these view helpers" parameter, injecting workbook-view awareness into
a canonical relation primitive -- the exact conflation the task warns against.
(3) `expand_xref` is wrapped by grouped-XRef and compact-multiaxis; it is a
protected lower-level surface.

Option C -- *add normal XRef-crosstable composite wrappers (forward + inverse).*
Rejected. No clean symmetric pair exists: outbound has `join_frames` between the
contract and the projection and would force the composite to absorb
consumer-specific display-helper join configuration; the inverses split across
`expand_xref` (4 surfaces) and `expand_compact_multiaxis` (1 surface). A
composite that fits four of five surfaces asymmetrically is not an improvement.

Option D -- *keep the callable but remove public registration.* Rejected. Ten
live public call sites depend on the registered step, and there is no composite
to host an internal-only call. Removing registration would break the consumer
and the validation-targeting discoverability story with no offsetting gain.

Option E -- *worldbuilding-local wrapper.* Rejected as the answer. A local
composite would re-introduce exactly the consumer-plugin pattern that the
accepted `FTR-DYNAMIC-FRAME-PROJECTION-P5` decision migrated *away* from
(Option A "keep plugins" was rejected as the long-term end state). It remains a
last-resort fallback only if repetition ever becomes a maintenance problem.

Option F -- *other.* None with concrete supporting evidence.

== 8. Selected architecture

Option A. `project_by_role` remains a public, backend-neutral, role-aware
view-adaptation step, composed around (never inside) the canonical XRef
forward/inverse operations. The shared `column_roles` resolver remains the
single role-detection source of truth for both projection and validation
targeting. No Core runtime change; no worldbuilding pipeline change.

Grouped-XRef is explicitly *not* the owner of any refactor here: it is a
separate specialization that composes unchanged `contract_xref`, and the
worldbuilding projection surfaces use the *normal* XRef/compact-multiaxis path,
not the grouped path.

== 12. Risks and stop conditions

* *Risk of doing nothing:* the ten-site repetition persists. Mitigation: it is
  uniform and declarative; revisit only if a *new* ordinary XRef consumer
  reproduces the same helper-ordering pattern (a genuine second consumer would
  be new evidence for a composite).
* *Stop conditions that would reopen this* (any one): a second consumer needs
  the identical display-helper ordering/retention around a *symmetric*
  `contract_xref`/`expand_xref` pair; or the display helper becomes part of the
  canonical relation model; or `configure_workbook_view` is reordered so the
  resolver can reach view helpers, changing the override story. None hold today.
* *Protected surfaces (must not be touched by any follow-up):* grouped-XRef,
  axis mapping, `ExactTable`, WorkbookIR, render composer/flow, XLSX/ODS
  parsers and renderers, persistence boundary, schema maintenance, validation
  targeting semantics, the shared resolver taxonomy, Project Memory, and
  unrelated worldbuilding data.
