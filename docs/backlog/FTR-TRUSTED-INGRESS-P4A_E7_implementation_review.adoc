==== 15. Findings

===== Important I-1 -- direct construction of the public authorization value escapes the closed-contract error path

*Observation.* `LessTrustedDescriptionAuthorization` is declared
`@dataclass(frozen=True, slots=True, init=False, repr=False)` with no
hand-written `__init__`. Because `init=False` only suppresses the
*generated* `__init__` and no other is defined, the class inherits
`object.__init__`, so the zero-argument public constructor
`LessTrustedDescriptionAuthorization()` succeeds and produces an instance
whose slots (`_registered_steps`, `_plugin_targets`) were never assigned.

*Evidence.* Independently reproduced (section 5): direct construction
succeeds silently; passing that value to `build_steps_from_config(...,
description_authorization=...)` passes the exact-type check in
`_effective_authorization` (it *is* exactly
`LessTrustedDescriptionAuthorization`) and then raises a raw `AttributeError:
'...LessTrustedDescriptionAuthorization' object has no attribute
'_registered_steps'` at `build.py:41`, before any per-step processing begins.
None of the 84 new tests construct the value this way.

*Risk.* This is not a capability-activation bypass -- the crash happens before
the per-step authorization loop starts, so no registered step, plugin,
direct-colon factory, or resource selector activates early, and no widening
of authority occurs. The risk is the closed-construction/safe-diagnostics
public contract itself (design section 4.2, "It does not accept subclasses or
arbitrary policy callbacks," and the FTR's own promised stable
`DescriptionAuthorizationError(kind=...)` surface): a caller that
misconstructs the value -- most plausibly by assuming a bare constructor
yields a deny-all policy, a reasonable but wrong guess given the class is
documented as "construct with `from_mapping`" only in a docstring, not
enforced -- receives an unhandled internal `AttributeError` mentioning a
private attribute name, instead of the documented, stable, safe
`DescriptionAuthorizationError`. This matches the review-task's own Important
example: "public malformed policy construction escapes the closed contract in
a significant supported case."

*Recommended action (smallest correction).* Make direct/incomplete
construction fail through the same closed contract, either by giving
`_effective_authorization` (and any other internal reader of `_registered_
steps`/`_plugin_targets`) a defensive `hasattr`/`try-except AttributeError`
guard that raises `DescriptionAuthorizationError("invalid_policy",
"unsupported_authorization_value")`, or by adding a minimal `__new__`/
`__init__` override on the class that always initializes both slots (e.g. to
empty/deny-all values) so no code path can observe an uninitialized instance.
Either fix is local to `description_authorization.py` and requires no
design-decision change; a bare-constructor regression test
(`LessTrustedDescriptionAuthorization()` passed to `build_steps_from_config`
must raise `DescriptionAuthorizationError(kind="invalid_policy", ...)`, not
`AttributeError`) should accompany the fix.

*Disposition.* Important; narrow, local, single-file correction. Per this
review's own severity discipline and the precedent set by the accepted E7
design review's own I-1 finding, an Important finding requires `CHANGES
REQUIRED` regardless of how small the fix is.
