*Priority:* P4A2

*Type:* Staged capability contract. This FTR settles the shared model and
authorizes only Slice 1 below. Later slices require their own implementation
review and public-surface approval where applicable.

*Purpose:*::
Define a backend-neutral bijection between a stable canonical axis key and a
one- or multi-level visible label tuple:

[source,text]
----
CHAR-0002
<-> ("Galli")

credit.annuity_loan
<-> ("Kredit", "Annuitätendarlehen")

credit.fixed_rate_loan
<-> ("Kredit", "Festzinsdarlehen")

deposit.balance
<-> ("Einlage", "Guthaben")
----

Visible labels are projection data. The durable relation continues to use the
canonical key.

*Motivation and repository evidence:*::
Current XRef uses one flat string vocabulary for relation `column_key` values
and matrix headers. A readable axis therefore requires an explicit join before
`contract_xref` and the inverse join after `expand_xref`.
+
The reviewed worldbuilding adoption repeats this path for four Story Cast
facets:

[source,text]
----
extract facet
-> join character ID to character name
-> contract_xref
-> join story title
-> project_by_role
----

The reverse path repeats `project_by_role -> expand_xref -> join name to ID`.
Axis-label projection can replace the character-name joins. It does not replace
the row-helper join, `project_by_role`, or discriminator composition.

*Terminology:*::

Canonical axis key:: Stable, unique, exact built-in non-empty string identity
stored in the durable relation, for example `CHAR-0002` or
`credit.annuity_loan`. Python `str` subclasses are not accepted.

Visible label tuple:: An exact built-in `tuple` containing one or more exact
built-in non-empty strings. Tuple subclasses are not accepted. A one-level
label is always modelled as a one-element tuple, even when a carrier uses a
flat string physically.

Axis member:: One canonical key, its visible label tuple, and its resolved
position.

Axis-mapping Intent:: Declarative input naming the source frame, source key
field, ordered label fields, and explicit ordering policy.

Axis-mapping Resolution:: The ordered, run-local set of axis members produced
from current frames and Intent.

*Settled semantic contract:*::

. One canonical key resolves to exactly one complete visible label tuple.
. One complete visible label tuple resolves to exactly one canonical key.
. Reverse lookup uses the complete tuple. Repeated values at an individual
  label level are valid.
. Duplicate source keys and duplicate complete visible label tuples fail.
. Used canonical keys missing from the mapping source fail.
. Missing label fields, missing label values, empty label values, and wrong
  tuple arity fail. This capability defines no empty-level policy.
. Matching is exact. There is no fuzzy matching, case folding, delimiter
  parsing, concatenated-header parsing, or inference from formatting or merged
  cells.
. Source-frame and configured field names are exact built-in strings. A
  configured field matches only an exact built-in string physical column label;
  unrelated non-string physical labels remain governed by the shared physical
  label contract and cannot impersonate configured fields.
. Resolution order is explicit:
** source order may be used only when Intent selects it; or
** configured order fields are compared in declaration order, with canonical
   key as the deterministic final tie-breaker.
. Configured order values use a deliberately narrow vocabulary. Each order
  column contains one type only: exact built-in `str` or exact built-in `int`
  excluding `bool`. A complete, deduplicated, platform-aware set of exact
  NumPy integer scalar types produced by pandas is copied to built-in `int`
  before ordering. NumPy subclasses are not accepted. Floats, subclasses,
  mixed types within one order column, mutable values, and arbitrary comparator
  objects fail before comparison. The resolver does not attempt to prove
  arbitrary Python comparisons form a total order.
. Missing or unsupported order values fail before projection.
. Rejection diagnostics do not inspect caller-controlled type metadata or
  invoke caller representation, conversion, hashing, equality, iteration, or
  comparison behavior merely to describe an invalid value.
. A later run resolves again from current source frames. Stale Resolution is
  not durable identity.
. Axis projection changes only the selected axis-key vocabulary. XRef retains
  responsibility for relation/matrix shape and cell addressing.

*Architecture decision:*::
Implement axis projection as a pair of small bijective transformations composed
around unchanged XRef:

[source,text]
----
canonical relation with keys
-> outbound axis projection
-> relation with visible one-level labels
-> contract_xref
-> editable matrix

editable matrix
-> expand_xref
-> relation with visible one-level labels
-> inbound axis projection
-> canonical relation with keys
----

This direction reuses the existing primitives and keeps their public contracts
intact.

The following alternatives are not selected for the initial slices:

Optional axis configuration inside `contract_xref` / `expand_xref`::
Rejected initially because it would make the XRef primitives own lookup,
display, ordering, and lifecycle concerns in addition to shape conversion.

Higher-level XRef-view wrapper::
Deferred. A thin wrapper may later compose proven primitives, but it must not
be the first implementation or become an all-knowing
`project_faceted_xref` step.

Discriminator/facet multiprojection::
Deferred to a later composition feature. One repeated consumer is evidence for
the primitive, not sufficient evidence for a macro over extract, join, XRef,
row helpers, role projection, workbook views, and merge.

*Concern boundaries:*::

XRef relation/matrix conversion::
`contract_xref` and `expand_xref` continue to own tuple/matrix addressing,
scoped recomposition, blank-cell policy, and flat axis identity in their
current mode.

Axis Mapping::
This FTR owns canonical axis identity, visible label tuples, exact forward and
reverse resolution, and deterministic member order.

Grouped Columns (merged in)::
The physical representation and readback of hierarchical column tuples as
multi-row spreadsheet headers, including merge geometry and XLSX/ODS carrier
parity, was originally scoped to `FTR-XREF-GROUPED-COLUMNS-P4A2`. That design is
now *absorbed into this FTR* as the merged grouped-XRef capability (sub-slices
GX-1..GX-5); the superseded FTR consumes the identity model established here and
defines no separate identity model.

Row helpers and `project_by_role`::
A visible row such as `story_id | title | Galli | Trixi` contains a canonical
row-key column, a display-helper column, and dynamic matrix-value columns.
`title` is not a row-axis tuple. `project_by_role` continues to order or remove
declared row-identity/display-helper/matrix-value columns; it does not map the
dynamic column-axis identities.

Row-axis projection::
The pure mapping model is axis-neutral. Runtime row-axis projection, a
hierarchical row index, and row-header rendering are deferred. The first
integration is the dynamic column axis.

*Intent, Resolution, and metadata:*::

* Intent is explicit configuration or caller input.
* Resolution is computed from current source frames for each projection run.
* Slice 1 introduces no metadata root and persists no Resolution.
* Slice 2 should also prefer explicit inverse configuration plus live source
  frames. If a required source frame is absent, inverse projection fails
  rather than trusting stale or visible text.
* The current `_meta.xref_crosstable` contract remains unchanged. Its
  `column_keys` and `dense_axes.resolved` fields are existing XRef Resolution
  and are stripped at the carrier-neutral persistence boundary; they must not
  be repurposed silently as axis-label mapping truth.
* If a later slice proves that persistent discovery Intent is necessary, it
  must first decide whether to extend `_meta.xref_crosstable` or justify a new
  feature-owned root. That gated slice must define producers, consumers,
  persistence, replacement, ambiguity, and schema-maintenance handling.

*Schema maintenance:*::
Slice 1 has no schema-maintenance change because it adds neither persisted
references nor a public configuration surface.
+
A later persistent Intent would reference a source frame, source key, label
fields, and order fields. The same slice must extend the feature-aware
schema-maintenance checks to block or safely update affected renames/drops.
This requirement does not authorize a broad schema-maintenance redesign.

*Compatibility:*::

* Axis mapping is opt-in.
* Existing flat XRef YAML, Python calls, matrices, and metadata remain valid.
* Existing pipelines that enrich a relation with a unique visible name and use
  that name as the XRef key remain supported.
* One-level integration uses ordinary flat string labels and does not require
  MultiIndex support.
* Direct XRef callers may continue to use visible strings as their declared
  axis identity. Only an explicit axis-mapping boundary promises restoration to
  a different canonical key.

*Implementation sequence:*::

Slice 1 -- pure model and resolver (authorized by this FTR)::
Add internal typed Intent/Resolution/axis-member values and a pure resolver.
It reads ordinary frames and covers both one- and multi-level tuples,
completeness, bijection, exact inverse lookup, and deterministic ordering.
It changes no pipeline registry, YAML surface, metadata, XRef runtime, render
flow, adapter, or sibling repository.

Slice 2 -- flat one-level projection transformations::
Add separately reviewable outbound and inbound transformations composed around
unchanged XRef. Decide names and parameter shape in that slice, then apply the
YAML/public-surface gate and registry/documentation/release-note obligations.
Prove flat-string XLSX and ODS roundtrip without adding grouped headers.

Slices 3 and 4 (merged) -- grouped XRef::
The former "Slice 3 -- hierarchical logical labels" and "Slice 4 --
grouped-header integration" are merged into one grouped-XRef capability: project
visible label tuples onto matrix headers *after* unchanged `contract_xref`, and
restore canonical string headers *before* unchanged `expand_xref`. XRef keeps
canonical non-empty string identities; no public long-form level-column API is
introduced; do not encode tuples by joining strings, split on delimiters, or
depend on merge geometry. The architecture is fixed in
`FTR-XREF-AXIS-MAPPINGS-P4A2_slice3_4_architecture_confirmation_001.adoc` and
implemented as the sub-slices below.

GX-1 -- grouped matrix/header model + pure projection primitive::
A feature-owned `GroupedHeader` descriptor and a pure forward/inverse header
projection (flat canonical matrix <-> grouped matrix) over the Slice 1 resolver.
No carrier, public step, or metadata.

GX-2 -- grouped-XRef composites::
`contract_grouped_xref` / `expand_grouped_xref` wrapping unchanged XRef plus
GX-1; registry, docs, release note; Frames/descriptor-level roundtrip. Applies
the public-surface gate and closes the Slice 2 F-1 follow-up.

GX-3 -- XLSX carrier::
Lossless multi-row header write and merge-independent exact-tuple read using
configured depth; carrier-level tests including repeated/unmerged upper levels
and literal delimiter text.

GX-4 -- ODS carrier and parity::
Same contract for ODS with repeated-carrier bounding and ODF XML carrier
assertions; require XLSX/ODS semantic parity.

GX-5 -- adoption and optional view composition::
Replace one repeated adoption chain and measure whether a small wrapper is
justified (absorbs the former Slice 5). Discriminator-driven multiprojection
remains a later decision.

*Slice 1 acceptance:*::

* The resolver produces `CHAR-0002 <-> ("Galli")` from an ordinary source
  frame and performs both lookups exactly.
* The same model produces the three two-level credit/deposit mappings in the
  Purpose section.
* Two keys with the same complete visible label tuple fail before projection.
* Repeated upper-level labels with distinct complete tuples succeed.
* Duplicate keys, unknown used keys, absent configured fields, empty labels,
  wrong tuple arity, and invalid ordering data produce actionable diagnostics.
* Both explicit source order and configured-field order are deterministic; the
  latter uses canonical key as its final tie-breaker.
* Configured ordering accepts only homogeneous exact built-in string or integer
  values per order column; arbitrary comparator objects are rejected without
  invoking their comparison methods.
* Tests prove one-level and multi-level mappings use the same resolver and
  inverse representation.
* No executable XRef, registry, metadata, persistence, render-flow, adapter, or
  schema-maintenance behavior changes in this slice.

*Non-Goals:*::

* No domain-specific credit, finance, product, or worldbuilding policy.
* No parsing arbitrary workbook text as identity.
* No automatic creation or writeback of axis-source members.
* No tuple-to-string delimiter encoding.
* No grouped-header rendering/readback in Slices 1 or 2.
* No replacement of `project_by_role`.
* No cell-code, Legend Block, Sparse Defaults, or Compact Multiaxis behavior.
* No mandatory migration of existing consumers.
* No broad redesign of XRef, metadata lifecycle, schema maintenance, or
  workbook views.
