===== FTR-XREF-AXIS-MAPPINGS-P4A2 -- Bijective XRef axis label projection

*Status:* New; refined from the original axis-mapping backlog sketch and ready
for independent FTR review.

*Priority:* P4A2

*Current sequencing note:* Complete the active Legend Blocks resolved-shape
slice first. This FTR is then a suitable next adoption-driven capability slice.
It should precede `FTR-XREF-GROUPED-COLUMNS-P4A2`, because grouped workbook
headers require an explicit identity-preserving axis model. It does not require
a broad pipeline refactor before investigation; the repeated worldbuilding
projection chains are evidence for the missing capability.

*Purpose:*::
Define a backend-neutral, bijective projection between stable canonical XRef
axis keys and human-readable one- or multi-level workbook axis labels.

The projection must allow a canonical relation such as:

## [source,text]

## story_id | character_id | value

to appear in a workbook using readable column labels such as:

## [source,text]

## Story | Galli | Trixi | Donzo

and must also support hierarchical labels such as:

## [source,text]

```
          Kredit                       Einlage
          Annuitätendarlehen           Guthaben
```

## requirement

without replacing canonical identity with visible text or requiring helper
columns to be transposed into ad hoc header rows.

*Context:*::
The current XRef primitives intentionally use flat, explicit relation keys.
This is semantically sound, but adoption pipelines currently have to assemble
human-readable matrices from several low-level steps:

## [source,text]

join canonical ID to display name
-> contract_xref
-> join row helper label
-> project_by_role
------------------

The reverse pipeline repeats the inverse sequence:

## [source,text]

project_by_role inbound
-> expand_xref
-> join visible name back to canonical ID
-----------------------------------------

In the worldbuilding adoption, the same chain is repeated for Story Groups and
for several Story Cast facets. The repetition is not caused by XRef itself.
It arises because canonical identity, visible axis labels, and workbook helper
information are currently expressed through separate generic joins and role
projection steps.

`project_by_role` remains appropriate for ordinary vertical helper columns, for
example `story_id` plus a visible `title`. It is not a natural representation
for horizontal axis members because expressing each horizontal label as a
helper column would require transposition or special-purpose header
transformations.

The missing capability is therefore an explicit axis-label projection:

## [source,text]

canonical key
<-> ordered visible label tuple
-------------------------------

Examples:

## [source,text]

CHAR-0002
<-> ("Galli")

credit.annuity_loan
<-> ("Kredit", "Annuitätendarlehen")

deposit.balance
<-> ("Einlage", "Guthaben")
---------------------------

Visible labels are projection data. They are not canonical identity and must
never be parsed heuristically without an explicit resolved mapping.

*Relationship to existing capabilities:*::

* `contract_xref` and `expand_xref` remain responsible for relation/matrix
  shape conversion.
* Axis projection resolves canonical axis keys to visible label tuples and
  restores them on inbound processing.
* `project_by_role` remains responsible for declared key/helper/payload column
  roles outside the dynamic XRef axis.
* `FTR-XREF-GROUPED-COLUMNS-P4A2` owns MultiIndex/multi-row workbook rendering
  of hierarchical column labels.
* A later composition feature may combine discriminator split/merge, axis
  projection, XRef contraction/expansion, row helpers, and workbook views.
  This FTR does not require that higher-level macro.

*Terminology:*::

Canonical axis key:: Stable identity stored in the normalized relation, for
example `character_id` or `product_variant_id`.

Visible axis label:: A human-readable string projected for workbook use, for
example `Galli`.

Visible label tuple:: One or more ordered labels representing a hierarchical
axis member, for example `("Kredit", "Annuitätendarlehen")`.

Axis member:: One canonical key together with its resolved visible label tuple
and deterministic position.

Axis mapping:: The complete ordered, bijective mapping between canonical axis
keys and visible label tuples for one XRef view and one axis.

Intent:: The declarative source, key, label fields, optional order fields, and
projection policy.

Resolution:: The concrete ordered mapping resolved from current canonical
frames for a particular projection/render run.

*Core contract:*::

. Canonical relations retain stable axis keys.
. Outbound projection resolves each used canonical key to exactly one visible
label tuple.
. Inbound projection resolves each visible label tuple to exactly one canonical
key.
. The full label tuple, not an individual level, is the inverse lookup key.
. A one-level label is represented as a one-element tuple conceptually, even if
a flat physical column label is used.
. Axis member order is explicit and deterministic.
. Visible labels never become canonical identity.
. No reverse mapping is inferred from arbitrary merged cells, formatting, or
concatenated header text.
. A workbook-produced axis must carry sufficient framework-owned mapping
metadata for safe inverse projection.
. Externally authored workbooks without a matching mapping may fail rather than
guess identity.

*Configuration sketch:*::

## [source,yaml]

* step: contract_xref
  relation: product_requirement_values
  output: product_requirement_matrix
  row_keys: [requirement_id]
  column_key: product_variant_id
  value: value
  axis_mapping:
  column_axis:
  source: product_variants
  source_key: id
  relation_key: product_variant_id
  label_fields: [product_family, product_name]
  order_by: [family_order, product_order]

---

Equivalent one-level worldbuilding example:

## [source,yaml]

* step: contract_xref
  relation: story_cast_role_cells
  output: story_cast_role_matrix
  row_keys: [story_id]
  column_key: character_id
  value: value
  axis_mapping:
  column_axis:
  source: characters
  source_key: id
  relation_key: character_id
  label_fields: [name]
  order_by: [name]

---

The exact API shape remains subject to implementation review. In particular,
the project must decide whether axis mapping is:

* an optional configuration block on `contract_xref` / `expand_xref`;
* a separate pair of reusable transformations wrapped by XRef composition; or
* declarative metadata resolved before the existing XRef steps.

The semantic contract above is normative; the surface syntax is not yet fixed.

*Row-axis and helper distinction:*::
The same mapping model should be valid for row-axis members, but the first
implementation may focus on the dynamic column axis if that materially reduces
scope.

A visible row helper such as:

## [source,text]

## story_id | title | Galli | Trixi

is not automatically the same thing as a row-axis label tuple. The implementation
review must distinguish:

* canonical row-key columns retained visibly in the matrix;
* helper/display columns such as `title`;
* a true hierarchical row index or row-axis projection.

The FTR must not force all existing helper-column use cases into the new axis
mapping abstraction.

*Resolved metadata sketch:*::

## [source,yaml]

xref_axis_mappings:
product_requirement_matrix:
column_axis:
intent:
source: product_variants
source_key: id
relation_key: product_variant_id
label_fields: [product_family, product_name]
order_by: [family_order, product_order]
resolved:
- key: credit.annuity_loan
labels: [Kredit, Annuitätendarlehen]
position: 0
- key: credit.fixed_rate_loan
labels: [Kredit, Festzinsdarlehen]
position: 1
- key: deposit.balance
labels: [Einlage, Guthaben]
position: 2
-----------

The exact metadata family and lifecycle must be reviewed against the current
meta registry and Intent/Resolution conventions before implementation.

*Validation requirements:*::

Outbound resolution must fail clearly when:

* a used canonical axis key is missing from the lookup source;
* a source key is missing or duplicated;
* a required label field is missing;
* a required label value is empty, unless an explicit empty-level policy is
  defined;
* two different canonical keys resolve to the same complete visible label
  tuple;
* order fields are missing or produce a non-deterministic result;
* a resolved label cannot be represented by the selected carrier.

Inbound restoration must fail clearly when:

* a visible label tuple has no matching resolved axis member;
* a visible label tuple is ambiguous;
* the workbook axis contains an unexpected member;
* the persisted mapping is missing or inconsistent with the workbook surface;
* the number or ordering of label levels is incompatible with the declared
  mapping.

Validation of cell values remains outside this FTR.

*Ordering contract:*::

* Source-frame row order may be used only when explicitly selected as the order
  policy.
* Otherwise `order_by` defines deterministic member order.
* Stable ordering must survive outbound/inbound roundtrip.
* Grouping identical upper-level labels must not collapse or reorder lower-level
  members.
* Ordering metadata is part of Resolution and must not be reconstructed from
  physical workbook position alone when authoritative mapping metadata exists.

*Multi-level labels:*::
The model must support one or more label fields.

One level:

## [source,text]

## ("Galli")

Two levels:

## [source,text]

## ("Kredit", "Annuitätendarlehen")

Three levels must remain structurally possible:

## [source,text]

## ("Retail", "Kredit", "Annuitätendarlehen")

The core axis mapping must not impose a fixed level count. Carrier-specific
limits or presentation behavior belong to rendering adapters and
`FTR-XREF-GROUPED-COLUMNS-P4A2`.

Repeated upper-level labels may be rendered as repeated values or merged header
cells according to carrier/render policy. The axis mapping itself records the
complete tuple for every member and does not depend on merged-cell geometry.

*Persistence and lifecycle:*::

* Axis mapping Intent is canonical metadata when supplied by configuration or
  callers.
* Resolved axis members are framework-derived Resolution.
* The workbook carrier may persist resolved key-to-label information needed for
  safe readback.
* Structured persistence must follow an explicit lifecycle decision:
  ** preserve Intent;
  ** preserve, strip, or regenerate Resolution according to the maintained
  carrier contract;
  ** never treat physical header labels as sufficient canonical identity.
* A later render must resolve the mapping from current canonical source frames
  rather than blindly trusting stale Resolution.
* Schema maintenance of references inside axis-mapping Intent must be assessed
  explicitly.

*Compatibility:*::

* Existing flat XRef configuration without axis mapping remains unchanged.
* Existing matrices whose physical columns are already canonical keys remain
  valid.
* Existing manually composed `join_frames -> contract_xref` pipelines remain
  supported.
* The feature introduces a higher-level, safer alternative; it does not require
  immediate migration.
* Direct low-level XRef callers may continue to supply already projected flat
  labels, but such labels remain caller-owned identity unless an axis mapping is
  explicitly declared.
* XLSX and ODS must provide equivalent semantic roundtrip behavior before the
  feature is considered complete.

*Scope:*::

* Define the canonical axis-mapping Intent and Resolution contracts.
* Resolve one- or multi-level labels from ordinary frames.
* Preserve stable canonical keys separately from visible labels.
* Support deterministic ordering.
* Support outbound key-to-label projection.
* Support inbound label-tuple-to-key restoration.
* Integrate safely with XRef contraction and expansion.
* Persist sufficient workbook metadata for non-heuristic readback.
* Provide XLSX/ODS semantic parity.
* Document the distinction between axis labels and ordinary helper columns.

*Non-Goals:*::

* No domain-specific credit, product, finance, or worldbuilding semantics.
* No parsing of arbitrary visible text as identity.
* No fuzzy matching, case folding, or heuristic fallback.
* No automatic creation of new canonical axis members from workbook headers.
* No direct editing of lookup/source entities through the matrix header.
* No generic nested JSON import/export.
* No cell-code or Legend Entry policy.
* No discriminator/facet multiprojection in this slice.
* No replacement of `project_by_role`.
* No mandatory migration of current adoption pipelines.
* No broad redesign of `contract_xref` or `expand_xref` before the semantic
  contract is settled.
* No generic workbook-view macro language.

*Architecture questions for FTR review:*::

. Should axis projection be implemented as separate bijective transformations
composed around the existing XRef core, or as optional XRef configuration?
. Which metadata family owns axis-mapping Intent and Resolution?
. At what boundary is Resolution regenerated and at what boundaries is it
stripped?
. Should first implementation support only the column axis, while keeping a
symmetric model for later row-axis support?
. How should `project_by_role` helper metadata interact with a matrix carrying
projected axes?
. Can current MultiHeader XLSX and ODS adapters round-trip the required level
count and ordering without carrier-specific semantics leaking into domain
code?
. Should a one-level mapping physically remain a flat string column index while
multi-level mappings use a MultiIndex?
. How are literal values, empty labels, duplicate tuples, and non-string labels
represented and diagnosed?
. Does schema maintenance need to update frame and column references inside the
mapping Intent in the first slice?
. Which current worldbuilding steps can be migrated as evidence without making
the consumer repository part of the core implementation?

*Suggested implementation slicing:*::

Slice A -- semantic model and resolver::
Define typed Intent/Resolution structures and a pure resolver from ordinary
frames. Cover uniqueness, completeness, ordering, and one-/multi-level tuples.
Do not change XRef or rendering yet.

Slice B -- flat one-level XRef integration::
Integrate one-level key-to-label projection and inverse restoration with the
existing XRef primitives. Prove the worldbuilding-style `character_id <-> name`
case without MultiIndex rendering.

Slice C -- hierarchical column-axis integration::
Support multiple label fields and MultiIndex-compatible column tuples. Establish
XLSX/ODS semantic parity. This slice closes the dependency needed by
`FTR-XREF-GROUPED-COLUMNS-P4A2`.

Slice D -- adoption composition::
Migrate one neutral or worldbuilding projection chain from explicit
`join_frames -> contract_xref -> join helper -> project_by_role` assembly to the
new mapping. Measure YAML reduction and review whether a separate higher-level
XRef-view composition FTR is justified.

A later FTR may add discriminator-driven generation of several equivalent
matrix views.

*Acceptance:*::

* A neutral relation using stable column-axis IDs contracts to a matrix with
  human-readable one-level labels and expands back to the original IDs without
  parsing visible text.
* A neutral relation using stable column-axis IDs contracts to a matrix whose
  members have two visible label levels, for example:
  ** `Kredit / Annuitätendarlehen`;
  ** `Kredit / Festzinsdarlehen`;
  ** `Einlage / Guthaben`.
* Two canonical keys resolving to the same complete label tuple fail before
  rendering.
* Missing IDs and missing label fields fail with actionable diagnostics.
* Stable configured order survives XLSX and ODS outbound/inbound roundtrip.
* The workbook carrier preserves sufficient key-to-label mapping information to
  restore canonical IDs even though the visible headers contain labels only.
* No arbitrary workbook header text is accepted as canonical identity.
* Existing flat XRef tests and configurations remain green.
* The implementation does not absorb Legend Entry, cell-code, discriminator,
  or domain-specific policy.
* At least one repeated adoption chain is materially shortened without hiding
  the underlying canonical relation or weakening roundtrip guarantees.
* Documentation explains canonical key, visible label, visible label tuple,
  Intent, Resolution, helper column, and grouped header distinctly.

*Expected follow-up:*::
After this FTR is implemented and accepted:

* `FTR-XREF-GROUPED-COLUMNS-P4A2` can focus narrowly on rendering and readback
  of hierarchical headers.
* A separate XRef-view composition assessment may consider bundling:
  ** axis projection;
  ** XRef contraction/expansion;
  ** row helper labels;
  ** role projection;
  ** discriminator split/merge.
* The worldbuilding adoption may then replace repeated name joins and some
  explicit projection plumbing with the accepted capability.
