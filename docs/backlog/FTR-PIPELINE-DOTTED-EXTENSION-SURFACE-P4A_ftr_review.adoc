== Historical-intent assessment

The historical statement is materially supported, with one necessary
qualification.

* The pipeline registration normalization FTR explicitly required the plugin
  path to continue working and made immediate plugin removal a non-goal.
* The later pipeline ownership split intentionally removed the parallel
  `pipeline: {steps: ...}` dialect while leaving the canonical step-list
  builder and its colon-factory resolver unchanged.
* Most decisively, REVIEW-001 wave completion commit `8b2b058` states that the
  dotted extension surface remained intentional and names both
  `step: plugin` and direct `step: module:function` as supported forms that the
  cleanup did not remove.

This is stronger than accidental untouched behavior or implementation
simplification. It is explicit retention as extension mechanics and a
compatibility constraint on that cleanup. It is not, however, a complete
decision about the long-term stability tier, detailed `StepFactory` protocol,
deprecation window, or permanent equality of the two forms. The FTR preserves
that distinction: it treats retention as history while leaving the future
contract open.

== Framework-owned macro-flow assessment

`framework-owned macro flow` is not a label invented only after the ingress
guard. Persistence projection was already described in code as orchestrator
macro flow, and final cleanup independently uses the same placement model.
The category has a coherent reusable core: framework/application code owns a
fixed use-case or lifecycle position, while direct testability or Python
callability does not imply configuration addressability.

The four examples are real, but two qualifications are needed:

* schema maintenance is an application-owned private composition that inserts a
  private `BoundStep` into the ordinary linear execution slot after the command
  selects that use case; it is not an automatic orchestrator boundary phase;
* final cleanup is an automatic boundary executor, but it executes only
  explicit commands produced by transformations or
  `configure_pipeline_cleanup`. The executor's placement is framework-owned;
  the cleanup decision is not always framework-invented.

Ingress and persistence projection are direct fixed boundary-phase examples.
The category should explicitly name its two subtypes and appear in the primary
surface inventory so the assessment does not reason about it only as a
retrospective exception; see Minor M-1.

The FTR correctly says ingress is one current example and makes no claim that it
was chronologically first.

== Option-neutrality assessment

Options A--E are substantially neutral:

* A treats a documented expert factory protocol as a legitimate outcome.
* B asks about additive syntax, coexistence, permanent aliasing, deprecation,
  migration, and terminology.
* C fairly identifies closure construction, early validation, lifecycle, and
  custom-name capabilities that a frames-first plugin may lose or awkwardly
  emulate.
* D explicitly rejects any inference that Core namespace location establishes
  API status or safety, and describes namespace policy as architecture rather
  than security.
* E is distinguishable from A because it can preserve mechanics without
  granting the direct-colon form a stronger compatibility tier.

Option E nevertheless inherits Important I-1: “unresolved or provisional”
classification is not an adequate final state unless every provisional item
has a safe interim contract and a bounded evidence/reopening gate. Tightening
that rule will sharpen the A/E distinction without favoring either retention or
removal.

== Scope and cohesion assessment

The assessment is broad but can remain one architecture FTR if it produces a
single mandatory contract matrix and derives narrow implementation FTRs.
Consumer dotted syntax, internal registration targets, checked resolution, and
configuration addressability share one construction/resolution boundary.
Macro-flow ownership is relevant because it supplies the non-addressable case
that the policy must express.

Direct callable binders and direct `BoundStep` composition do not share dotted
resolution. They are still useful comparison boundaries, and current package
exports/tests provide enough evidence to assign a conservative stability tier.
They should not be changed under this FTR merely to make the dotted result
symmetrical. If evidence suggests a Python API reshape, that must become its
own implementation FTR.

The FTR risks becoming an open-ended inventory only because the present
acceptance contract permits incomplete decisions. Important I-1 is the needed
cohesion correction; splitting the whole assessment is not otherwise required.

== Acceptance-criteria assessment

Most criteria are relevant, achievable, and free of hidden runtime work:

* inventory, census limits, common option matrix, trust distinctions, namespace

* macro flow can be classified architecturally without implementing a generic

== Findings

=== Blocking

None.

=== Important I-1 -- completion can stop without a complete extension contract

*Observation:* The FTR requires an option matrix, but acceptance allows the
result to “decide or defer with a gate” only for the consumer/internal
`module:function` relationship. Option E can label portions unresolved or
provisional. No criterion mandates one completed row per surface with intended
audience, stability tier, supported syntax, trust/responsibility model,
configuration-addressability policy, internal/consumer notation relationship,
compatibility posture, and implementation-follow-up decision.

*Risk:* A lengthy inventory could satisfy the FTR while leaving the original
ambiguity in place. Multiple surfaces, especially nested targets, direct
factories, and programmatic APIs, could remain provisionally reachable with no
safe interim promise or reopening trigger.

*Recommended action:* Add a mandatory decision-output table covering every
surface and every field above. Permit deferral only when the result records the
concrete unresolved question, missing evidence, named evidence-acquisition
action, responsible follow-up, explicit date/release/milestone trigger, and
safe interim contract. Require the assessment to decide whether each deferred
item needs a new FTR. Apply the same bound to Option E.

*Disposition:* Important; correct before architecture assessment.

=== Important I-2 -- migration testing is ambiguous and can require forbidden implementation work

*Observation:* Acceptance requires any selected public-surface change to have a
migration plan “tested against representative adoption evidence.” Scope and
non-goals prohibit modifying adoption repositories and defer runtime, registry,
test, release-note, and adoption changes to later implementation slices.

*Risk:* An assessor can either under-satisfy “tested” with a prose claim or
cross the no-implementation boundary by prototyping runtime/migration changes
and editing consumer configurations. The criterion also mixes architecture
decision evidence with later implementation acceptance.

*Recommended action:* For this assessment require a read-only impact map,
representative before/after configuration examples, compatibility feasibility
analysis, and an executable migration-test plan. Reserve actual Core behavior
changes, adoption edits, migration execution, deprecation warnings, and
rollback validation for the derived implementation FTR. If disposable
prototypes are allowed, define their location, non-commit status, and exact
question; they must not mutate adoption repositories.

*Disposition:* Important; correct before architecture assessment.

=== Important I-3 -- the dated census is accurate but not reproducible from the FTR

*Observation:* The FTR gives counts and repository names but does not record
Core/adoption revisions, tracked-file versus worktree scope, literal search
patterns, or exclusions. “Maintained Core YAML” combines internal
domain-contract tooling and Project Memory; that classification appears only
in prose.

*Risk:* Counts can drift silently, generated/untracked content can change the
result, and a later assessor cannot tell whether a discrepancy is codebase
change or census-method change. Negative evidence is especially sensitive to
scope.

*Recommended action:* Pin the Core and inspected adoption commits, state that
the search covers Git-tracked `*.yaml` / `*.yml`, record the literal patterns
for plugin, direct-colon `step`, and nested dotted `target`, and preserve the
production/adoption, example, internal-tooling, test, documentation, and
registry-representation classifications. Retain the existing warning that the
snapshot cannot prove non-use elsewhere.

*Disposition:* Important; correct before architecture assessment.

=== Minor M-1 -- macro flow is absent from the main surface table

The “Existing surfaces” table lists seven callable/composition forms but omits
the framework-owned macro-flow contrast that the problem and later scope rely
on. Add a row and distinguish fixed orchestrator boundary phases from
application-owned private `BoundStep` composition. Qualify final cleanup as the
fixed executor of explicit commands. No generic declaration mechanism is
required to make this terminology correction.

=== Minor M-2 -- intended-audience vocabulary needs operational definitions

`consumer`, `expert`, `internal`, `programmatic`, and `framework-owned` are
used consistently in broad intent but are not defined as mutually intelligible
decision labels. Add concise definitions, especially whether “consumer”
includes expert YAML authors and whether an owning-module Python import can be
programmatic without being stable public API.

=== Observation O-1 -- no runtime factual dispute

The FTR's current implementation facts and quantitative claims were reproduced.
No runtime finding is raised. The focused 89-test result supports the factual
baseline; it is not an acceptance test of any future option.

=== Observation O-2 -- historical retention was explicit but bounded

Both plugin and direct-colon factory forms were explicitly retained as
intentional supported extension mechanics during cleanup. That evidence does
not itself grant either a permanent compatibility tier, which is exactly the
question this assessment should decide.

== Recommended corrections

Before starting architecture assessment:

. Make the full per-surface decision matrix mandatory and make every deferral
  time/evidence bounded with a safe interim contract.
. Rewrite migration acceptance as read-only impact/feasibility evidence plus a
  later executable migration-test plan.
. Add reproducible census revisions, tracked-file scope, literal searches, and
  classification rules.
. Add macro flow to the main inventory and qualify its boundary-phase and
  private-composition subtypes.
. Define the audience/stability terms and constrain Option E's provisional
  outcome with the same deferral gate.

These are FTR corrections only. No pipeline extension implementation,
deprecation, removal, migration, or security mechanism is recommended in this
review.
