*Problem:*::

`_meta.legend_blocks` currently accepts both a mapping and a list throughout
the domain and rendering stack. The two shapes have already diverged:

* the persistence boundary strips `resolved` only from mapping form;
* XLSX and ODS carrier parsers recognize legend hints only in mapping form;
* workbook readback returns carrier-derived `resolved` as canonical `_meta`;
* a legend rendered on its own sheet becomes an ordinary payload frame; and
* `registries/meta_registry.yaml` understates the real producer/consumer
  surface.

Maintaining two runtime shapes is the underlying defect. The correction is to
retain both external authoring forms, normalize once at each external-to-domain
ingress, and make mapping form the only downstream contract.

*Shape contract:*::

Both of these external authoring forms remain supported:

[source,yaml]
----
_meta:
  legend_blocks:
    status_codes:
      title: Status codes
      entries:
        - token: A
          label: Active
----

[source,yaml]
----
_meta:
  legend_blocks:
    - name: status_codes
      title: Status codes
      entries:
        - token: A
          label: Active
----

The single canonical runtime and persisted form is an insertion-ordered mapping
keyed by Legend Block identity. No domain transformation, renderer, validation
pass, persistence projector, or framework-produced carrier receives list form.

For a list item, identity is resolved using the existing compatibility
expression: `str(item.get("name") or item.get("id") or
f"legend_{one_based_position}")`. This preserves the current truthiness and
fallback behavior exactly. The block mapping and its field order are otherwise
preserved, including an authored `name` or `id`. An empty list becomes an empty
mapping.

Normalization rejects a list member that is not a mapping and rejects any
duplicate resolved identity, including a collision between an explicit identity
and a positional fallback. It must report the item position and, for a
collision, the resolved identity. It does not validate `entries` values.

An absent `legend_blocks` root is a no-op. An explicit `null` root is
compatibility syntax for an absent declaration and is canonicalized to an empty
mapping, preserving the root key in canonical mapping form. A mapping-form root
is preserved without observable shape or value change, except that the separate
ingress rule below removes `resolved`. Any other root that is neither a mapping
nor a list fails deterministically.

*Internal `domain.ingress` pattern:*::

Introduce a recognizable internal package under
`src/spreadsheet_handling/domain/ingress/`. It owns a carrier-neutral
`Frames -> Frames` coordinator, with Legend Blocks shape normalization as its
first feature-owned rule. The coordinator must make its ordered rule sequence
visible so later ingress normalizations can be added without hiding unrelated
logic in the orchestrator.

Ingress is framework-owned macro flow:

* it is invoked automatically;
* it is not a user-configurable pipeline step;
* it is absent from both `pipeline.registry.REGISTRY` and
  `registries/pipeline_step_registry.json`;
* it cannot be built from YAML: one shared pipeline ownership-boundary helper
  rejects the entire `spreadsheet_handling.domain.ingress` internal package
  namespace before import through both the generic dotted-callable `plugin`
  step and direct colon-style dotted `step:` factory resolution; and
* the orchestrator owns application call sites, while the domain package owns
  normalization semantics.

The current tree has three external metadata ingress points that must apply the
same coordinator:

. `application.orchestrator.orchestrate`, immediately after `_load_frames` and
  before the first configured step. Every router-backed input kind
  (`csv_dir`, JSON, YAML, XML, XLSX, ODS/Calc) converges here.
. `domain.meta_bootstrap.bootstrap_meta`, after its documented precedence merge,
  because profile and CLI overrides can introduce workbook metadata after the
  initial load.
. `domain.yaml_overrides.apply_overrides`, after its defaults/sheets merge,
  because `apply_overrides` is the other maintained configuration-to-meta
  boundary. `load_and_apply_overrides` inherits this behavior.

The latter two are registered user operations, but the ingress call they make
is automatic internal post-merge enforcement, not a separately selectable
step. Arbitrary plugins are domain producers rather than framework ingress;
they must return canonical mapping-form Frames.

Direct calls to `run_pipeline`, domain transformations, render functions, or
backend save functions bypass application ingress. Their precondition is
canonical mapping-form Frames. A caller intentionally starting with external
authoring data must call the internal ingress coordinator explicitly before
using those lower-level APIs. Existing downstream list branches should be
removed or reduced to clear contract failures; they are not a second
compatibility surface.

*Atomicity and immutability:*::

The ingress coordinator must not mutate caller-owned Frames, `_meta`, the
Legend Blocks container, or block mappings. It validates and constructs the
complete candidate result before returning it. On any shape or duplicate-name
failure:

* the input object graph remains unchanged;
* no configured step runs after the failing boundary; and
* the application saver is not invoked, so no partial output is produced.

Mapping-form intent input is value-equivalent after ingress. Object identity is
not part of the contract.

*`resolved` and carrier contract:*::

`legend_blocks.<name>.resolved` is render-derived Resolution, never durable
domain Intent.

* Domain ingress removes a pre-existing `resolved` facet from every canonical
  block, including stale structured input.
* The carrier-neutral persistence boundary continues to strip `resolved` from
  mapping form before every saver. This remains a defensive invariant for
  direct/bypassed runtime producers; persistence does not normalize list form.
* The composer may add fresh `resolved` only to its render-local metadata copy.
  It must continue not to mutate caller metadata.
* The XLSX and ODS parsers may consume fresh `resolved` from the
  framework-owned workbook carrier to locate and classify legend tables.
* The generic workbook-to-Frames projection removes `resolved` after table
  classification, before returning canonical readback metadata.
* A later render recomputes `resolved`; a stale value can never control layout.

Framework-produced workbook carriers therefore contain mapping form plus
render-local `resolved`. List form is external authoring sugar, not a supported
embedded-carrier shape. Both parsers retain their mapping-only hint contract;
the parity obligation is verified end to end from list-form authoring through
ingress and render, not by adding duplicate list walkers to the parsers.

*Legend-only sheet projection:*::

`TableBlock.kind == "legend"` is already the load-bearing parser
classification. `workbookir_to_frames` must not project a visible sheet's
selected table as a payload frame when that table is a legend. Default
own-sheet placement therefore yields no extra payload frame.

This is feature-owned projection behavior, not a generic frame ontology.
Data-sheet placement remains unchanged: the data table is still the first
payload table and the colocated legend remains support material.

*Ingress and future egress vocabulary:*::

This FTR establishes `domain.ingress` now. The corresponding future
`domain.egress` concept is reserved for framework-owned projection or pruning
when Frames leave the domain, such as persistable-contract projection.
This FTR does not create a generic egress engine, relocate every existing
projector, or expose ingress/egress in public YAML.

Framework egress is distinct from `domain.pipeline_cleanup`:

* egress projection enforces framework-owned boundary contracts
  automatically; while
* pipeline cleanup executes explicit user-configured drop/keep declarations.

No lifecycle, role, provenance, or name inference is introduced.

*Registry correction:*::

Update the `legend_blocks` entry in `registries/meta_registry.yaml` to state:

* external list-or-mapping authoring and canonical mapping-only runtime shape;
* `domain.ingress` as the canonical-shape producer;
* the composer as the producer of carrier-local `resolved`; and
* all current semantic readers/projectors, including the shared Cell Codec /
  Compact Multiaxis reader path, render `ValidationPass`, both carrier parsers,
  schema maintenance, persistence projection, and workbook projection.

The implementation must re-survey current call sites rather than preserve the
old draft's fixed “three omitted consumers” count. Add a focused registry guard
for the reviewed list; do not attempt a generic source-scanning registry
framework in this slice.

*Implementation scope:*::

. Add the internal `domain.ingress` coordinator and Legend Blocks rule.
. Invoke it at the three maintained load/config boundaries above.
. Simplify downstream domain, composer, and validation readers to the
  mapping-only contract; retain mapping-only carrier hint readers.
. Remove `resolved` at domain ingress and at canonical workbook readback while
  retaining fresh carrier-local production/consumption.
. Prevent an own-sheet legend table from becoming a payload frame.
. Correct the `legend_blocks` meta-registry entry and focused guards.
. Update live Legend Blocks documentation and release notes for the canonical
  persisted-shape and lower-level-call compatibility change.

The slice remains coherent: every runtime change enforces the same
external-authoring -> canonical-domain -> carrier-projection boundary. It does
not need division.

*Non-goals:*::

* Entry-value policy: token validity, label requirements, duplicate tokens
  within `entries`, unknown references, empty-entry policy, and unhashable
  tokens. These belong exclusively to
  `FTR-LEGEND-BLOCKS-ENTRY-CONTRACT-P5`.
* Sparse Defaults. The former assessment mismatch was resolved by the Compact
  Multiaxis workstream.
* `placement.target` frame maintenance. The current schema-maintenance package
  has column operations only; the still-live frame-reference concern remains
  deferred until a frame-rename capability exists.
* Generic metadata schemas or a registry-driven runtime contract.
* Public YAML exposure of ingress or egress.
* Generic `domain.egress` design or migration of the existing persistence
  boundary.
* Generic frame ontology, broad workbook-projection redesign, or broad
  orchestrator redesign.
* New behavior for Compact Multiaxis, Cell Codec values, visible legend entry
  rendering, or `ValidationPass.from_legend`.

*Compatibility:*::

* External list and mapping authoring remain accepted through maintained
  application/config ingress.
* An explicit `null` root remains compatible as an absent declaration but now
  becomes `{}` at ingress and persistence rather than surviving as `null`.
* Mapping-form callers retain their shape, ordering, and Intent values.
* List-form input is intentionally persisted and returned as mapping form.
* Existing mapping-form XLSX/ODS behavior remains carrier-parity compatible,
  except canonical readback no longer exposes `resolved` and own-sheet legends
  no longer appear as payload frames.
* Direct lower-level calls with list form are no longer supported. Those callers
  must normalize explicitly; this is a documented contract tightening, not
  removal of external authoring support.

*Acceptance criteria:*::

. Both external forms normalize to the same ordered mapping and all downstream
  consumers receive mapping form only.
. `name` / `id` / positional identity, empty-list behavior, explicit-null
  canonicalization, malformed member failure, duplicate resolved-name failure,
  and unsupported-root failure match the shape contract above without applying
  entry-value policy.
. The coordinator and its three invocation paths preserve caller inputs and
  fail before later steps or persistence.
. Loader, CLI/config runner, `run_app`, and schema-maintenance application paths
  pass through automatic ingress; `bootstrap_meta` and `apply_overrides`
  normalize metadata introduced after load.
. Ingress is absent from runtime/descriptive pipeline registries and is not
  YAML-buildable by short name, through the dotted-callable plugin surface, or
  through direct colon-style dotted `step:` factory resolution.
. The shared application persistence boundary supplies canonical mapping form
  without `resolved` to every saver. JSON directory sidecar persistence proves
  the on-disk structured-meta path; the current YAML/XML/CSV simple savers do
  not persist `_meta` sidecars and therefore provide no distinct sidecar path
  to duplicate.
. XLSX and ODS produce mapping-form carrier metadata, classify equivalent
  legends identically, and return canonical application readback without
  `resolved`.
. A default-placement legend-only sheet does not add a payload frame; a legend
  colocated with a data sheet leaves that data frame unchanged.
. Composer metadata cloning and fresh `resolved` production remain
  non-mutating; stale `resolved` cannot influence later layout.
. The meta registry reflects the current reviewed producer/consumer surface.
. Existing focused Cell Codec, Compact Multiaxis, validation, persistence,
  schema-maintenance, registry, and Legend Blocks tests remain green.

*Focused validation plan:*::

* Unit tests for `domain.ingress`: no-op/absent root, explicit-null

* Application tests proving ingress ordering around load, pipeline steps,

* Architecture tests proving the internal/non-registered/non-YAML-buildable

* Persistence tests for canonical mapping form and `resolved` stripping.
* XLSX/ODS roundtrip parity tests for list-authored input, canonical readback,

* Focused registry tests for the corrected Legend Blocks entry.
