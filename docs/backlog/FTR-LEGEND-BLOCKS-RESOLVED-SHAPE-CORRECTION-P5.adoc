*Problem statement:*::

Legend Blocks' `resolved` facet (`_meta.legend_blocks[*].resolved`) is
render-derived Resolution: a snapshot of the visible legend table's
carrier coordinates, written fresh by the composer on every render and
consumed by the XLSX/ODS parsers as a readback hint. The repository's
Intent-vs-Resolution rule
(`docs/ai_info/agent_rules.adoc`, "Persistence boundary for `_meta`") is
explicit that Resolution must not survive a structured, carrier-neutral
persist. Current code honours that rule only for the *mapping* form of
`_meta.legend_blocks`; the *list* form (a form the domain reader, composer,
and validation pass all already accept) is not recognised by the
persistence boundary or by either carrier parser's legend-hint
recognition, so it diverges silently at both ends. Separately, even the
mapping form's carrier readback briefly promotes `resolved` back into
canonical `_meta` before it is next overwritten or stripped, and a legend
rendered onto its own dedicated sheet is not distinguished from an
ordinary payload frame on structured readback -- both contrary to the
functional model's own stated target
(`docs/functional_model/ch04_use_case_concepts/legend_blocks.adoc`, "not
trusted from a prior `_meta`"; "generated legend surfaces do not become
ordinary payload frames"). Finally, `registries/meta_registry.yaml`'s
`legend_blocks` consumer list omits three real runtime consumers, making
the registry an inaccurate contract statement for anyone using it to judge
coupling before a future change.

*Current behavior:*::

* Structured sidecar persist (`json_dir`/`yaml_dir`/`xml_dir`/`csv_dir`):
  mapping-form `legend_blocks` has `resolved` stripped; list-form
  `legend_blocks` does not, and a derived render coordinate snapshot is
  written into a carrier-neutral, supposedly Intent-only artifact.
* Workbook readback (`xlsx`/`ods`, mapping form): `resolved` re-enters
  canonical `_meta.legend_blocks[*].resolved` immediately after
  `parse_workbook`, and stays there until the next render overwrites it or
  the next structured persist strips it. `resolved` is *always* freshly
  overwritten on the next render (`layout_composer.py:246`,
  unconditional), so this leak cannot influence layout -- but it is
  present as canonical state between those two events, contrary to the
  functional model's stated intent.
* Workbook readback (list form): the legend renders correctly (composer
  and domain reader both already accept list form), but on readback
  neither parser recognises the rendered table as a legend surface,
  because `_legend_table_hints` only walks a `dict`. A list-form legend on
  its own sheet is at risk of becoming a payload frame purely because of
  its shape, independent of `LB-4`.
* A legend with default placement (no explicit `target`) renders on a new
  sheet named after the legend block. `workbookir_to_frames` projects that
  sheet's first table into an ordinary frame regardless of `kind`, so the
  legend reappears as spreadsheet data (`frames` gain an extra payload
  entry, e.g. `['data', 'L']`) on structured readback. A legend anchored to
  the data sheet does not exhibit this, because it shares the data sheet's
  first table rather than occupying its own sheet.
* `meta_registry.yaml`'s `legend_blocks` consumer list understates real
  coupling by three entries; nothing currently guards this (the registry
  architecture tests pass regardless).

*Target contract:*::

Subject to the human decision below:

* Durable Legend Blocks Intent (`entries`, `title`, `placement`, `target`,
  block identity) has exactly one canonical runtime shape.
* `resolved` is carrier-derived Resolution. It is never durable canonical
  Intent, regardless of the shape `legend_blocks` is authored in.
* Rendering may produce `resolved` on a render-local copy, as it already
  does (`layout_composer.py` clones before writing).
* Carrier parsers may consume `resolved` as a readback hint to recognise a
  rendered legend surface -- this is the one legitimate reason `resolved`
  exists in the carrier blob at all.
* Canonical readback must not retain Resolution once its carrier purpose
  (surface recognition) is complete.
* Every structured persistence path strips Resolution, for every accepted
  `legend_blocks` shape -- not only the mapping form.
* XLSX and ODS apply equivalent legend-surface recognition for every
  accepted shape (they already agree with each other; the gap is
  shape-coverage, not backend divergence).
* A visible legend-only sheet is support/presentation material. It does
  not become a domain payload frame on structured readback.
* `meta_registry.yaml`'s `legend_blocks` producer/consumer statement
  reflects all real runtime consumers.

*Human decision:*::

*The following must be decided before implementation, not defaulted
silently:*

[quote]
____
Should list-form `_meta.legend_blocks` remain a supported canonical and
carrier shape, or should it be accepted only as input sugar and
normalised once to the mapping form?
____

*Recommendation (not a silent decision):* accept list form as input sugar
and normalise it to the mapping form at one well-defined ingress boundary.
Rationale: the mapping form is already the only shape every non-domain
consumer (persistence boundary, both carrier parsers) actually implements
correctly; the list form's only current advantage is convenience at
authoring time (positional `legend_{i}` naming). Patching every consumer's
list branch (persistence boundary *and* both parsers, with a matching
carrier-hint change) would triple the surface this correction slice has to
touch and would leave the same two-shape divergence available to the next
consumer that gets added. Normalising once removes the shape question from
every downstream consumer permanently.

*Ingress boundary analysis.* This must not become an arbitrary
renderer-only normalisation -- the domain reader, validation pass,
persistence boundary, and both carrier parsers all currently read
`legend_blocks` independently, and a renderer-local fix would leave the
other four blind to the list form exactly as they are today. Re-inspection
of `src/spreadsheet_handling/application/orchestrator.py::orchestrate`
(:98-131) shows the orchestrator already owns exactly this class of
whole-run, shape-level rule as part of its macro flow, symmetric on both
ends of a run:

[source,text]
----
frames = _load_frames(inp, header_levels=header_levels)      <-- load
...
frames = execute_final_domain_cleanup(frames)                 <-- cleanup boundary
frames["_meta"] = project_meta_to_persistable_contract(meta)  <-- persistence boundary
_save_frames(out, frames)
----

The persistence boundary at the bottom of this flow is documented
(`docs/ai_info/agent_rules.adoc`, "Persistence boundary for `_meta`";
`docs/semantic_model/08_lifecycle_and_update_semantics.adoc`, "Persistence
boundary") as orchestrator-owned, carrier-neutral, and running for *every*
output kind immediately before the saver -- explicitly not a configurable
pipeline step. The natural, symmetric counterpart is an ingress-side
normalisation immediately after `_load_frames` (:102), running for every
*input* kind (structured sidecar and workbook carrier readback alike)
before any pipeline step or the composer ever sees `_meta`. Placed there,
every consumer -- domain reader, validation pass, composer, persistence
boundary, carrier parsers on the *next* round-trip -- observes only the
mapping form, and the normalisation is written once.

This is a distinct concern from the "load-time sanitizer" the FK-helper
lifecycle work deliberately rejected
(`docs/semantic_model/08_lifecycle_and_update_semantics.adoc`, "Operational
scope: post-pipeline, write-side only"). That rejection was about
retroactively cleaning *contaminated* pre-existing data, a broader
lifecycle/quarantine question intentionally deferred to
`FTR-FK-HELPER-POLICY-LIFECYCLE-P4A`. Normalising an already-accepted
alternate *shape* of well-formed Legend Blocks Intent into one canonical
shape is a narrower, purely structural rule with no bearing on that
deferred question; the implementation must not be named or documented in
a way that conflates the two.

The implementation slice that establishes this (see *Implementation
Slices*, item 1) should evaluate, but is not required to adopt, the opt-in
`contract_lifecycle` model
(`docs/technical_model/ch05_registries/registry_semantics/05_contract_lifecycle.adoc`)
for documenting the list-form deprecation on the `legend_blocks`
`meta_registry.yaml` entry. That model's stated pilot is
`_meta.helper_policies.fk`, and `agent_rules.adoc` explicitly cautions
against retrofitting it onto stable single-shape entries -- so this is a
judgment call for the implementer, made explicitly, not a default.

*Acceptance Criteria:*::

. A canonical shape policy for `_meta.legend_blocks` is selected (list
  form as input-only sugar normalised at ingress, per the recommendation,
  or an explicit alternative) and documented in this FTR and in
  `registries/meta_registry.yaml`.
. Mapping-form and list-form `legend_blocks` input cannot diverge in
  observable behaviour across structured persistence and carrier readback
  -- either because list form is normalised away before any consumer sees
  it, or because every consumer (persistence boundary, both parsers)
  demonstrably handles both shapes identically.
. `resolved` never survives carrier-neutral structured persistence
  (`json_dir`/`yaml_dir`/`xml_dir`/`csv_dir`), for any accepted input
  shape. Guarded by a persistence-boundary test using a list-form fixture
  (none exists today).
. Carrier readback (`xlsx`/`ods`) does not leave `resolved` present in
  canonical `_meta.legend_blocks` returned by `workbookir_to_frames` /
  `frames["_meta"]` once the carrier-recognition purpose is served.
  Guarded by a roundtrip or workbook-projection test asserting `resolved`
  is absent from post-readback canonical meta.
. A stale `resolved` value cannot influence later layout. (Already true
  today via unconditional overwrite in `layout_composer.py:246` -- this
  criterion is a non-regression guard, not new behaviour.)
. XLSX and ODS classify equivalent legend surfaces consistently with each
  other for every accepted shape. Guarded by a parity assertion (existing
  or new) covering both backends with the same fixture.
. A legend rendered on its own dedicated sheet does not appear as an
  ordinary payload frame in `workbookir_to_frames`'s output. Guarded by a
  roundtrip test using default (no `target`) legend placement -- the exact
  gap the assessment's probe demonstrated (`frames` gaining an extra
  `'L'`-style entry).
. A legend anchored to the data sheet continues to roundtrip correctly
  (non-regression of the existing clean case).
. Cell Codec (`allowed_from_legend` token vocabulary), Compact Multiaxis
  (`_legend_groups` token/group projection), and the render
  `ValidationPass` (`from_legend` dropdown source) remain functional and
  unmodified in behaviour; existing focused test suites for each
  (`test_cell_codec.py`, `test_compact_multiaxis.py`,
  `test_validation_pass_infra.py`) stay green.
. `registries/meta_registry.yaml`'s `legend_blocks` entry lists all real
  consumers: the four existing entries plus `cell_codec`,
  `compact_multiaxis`, and the render `ValidationPass`.
. A rejected or malformed `legend_blocks` shape (e.g. an unrecognised list
  entry, or a shape neither list nor mapping) fails deterministically
  before producing output, with no partial mutation of `_meta` or partial
  writes to any output backend.
. Full Core (`pytest tests/unit tests/integration tests/roundtrip
  tests/architecture` / `make test`), architecture, the focused carrier
  roundtrip suites named in *Test Plan*, Demo, and any relevant
  Worldbuilding validation touching legend-block pipelines all remain
  green.

*Risks:*::

* *Ingress normalisation touches every input kind.* Wiring a new call into
  `orchestrate()` immediately after `_load_frames` runs for every backend
  (`csv_dir`, `json_dir`, `yaml_dir`, `xml_dir`, `xlsx`, `ods`, `calc`), not
  only the carrier paths this FTR is centred on. Mitigation: the
  normalisation must be a no-op whenever `legend_blocks` is absent or
  already mapping-form (the common case for every non-legend pipeline),
  and slice 1's unit tests must cover the no-op path explicitly so a
  regression there cannot silently affect unrelated pipelines.
* *List-form deprecation breaks an undiscovered external producer.* If any
  consumer repository (demo, worldbuilding) authors `legend_blocks` in
  list form today, normalising it to mapping form changes what a
  structured sidecar contains, even though runtime behaviour is intended
  to be equivalent. Mitigation: grep the demo and worldbuilding repos for
  list-form `legend_blocks` authoring before implementation; if found,
  the release-notes entry must call out the shape-preserving-vs-shape-normalising
  distinction explicitly.
* *`workbookir_to_frames` legend-sheet exclusion has a narrow correctness
  window.* Skipping a sheet by `kind == "legend"` must not skip a sheet
  that happens to contain both a legend table and unrelated payload data
  (mixed-content sheet). Mitigation: the fix should key off the specific
  table's `kind`, not the sheet as a whole, consistent with how
  `_apply_legend_table_hints` already sets `kind` per-table rather than
  per-sheet; the data-sheet-anchored legend case (which shares its sheet
  with payload data) is the acceptance-criteria non-regression case that
  catches an over-broad sheet-level exclusion.
* *Registry-completeness guard false positives.* A guard that fails when
  `meta_registry.yaml` omits a real `legend_blocks` reader could false-positive
  on incidental string matches (e.g. a comment or an unrelated `legend_blocks`-named
  local variable). Mitigation: scope the guard to actual import/attribute
  read sites already enumerated in the source assessment's *Producers and
  consumers* table, not a blind grep.
* *Scope creep into entry-value policy.* Because the four consumers this
  slice touches are the same four consumers `OB-1` describes as divergent
  on `label`/duplicate/unknown-reference handling, there is a standing
  temptation to "fix it while we're in there." Mitigation: the *Non-Goals*
  section forbids it explicitly; any reviewer encountering entry-validation
  changes in this slice's diff should reject them back to
  `FTR-LEGEND-BLOCKS-ENTRY-CONTRACT-P5`.

== Human decision -- resolved

List-form `_meta.legend_blocks` remains accepted as authoring and input sugar,
but it is not a second canonical runtime or persisted shape.

The canonical runtime and persisted representation is the mapping form keyed by
Legend Block identity.

List-form input is normalised exactly once at the orchestrator-owned
runtime-metadata ingress boundary, immediately after loading and before any
configured pipeline step or rendering consumer observes `_meta`.

The normalisation logic must live in a dedicated carrier-neutral helper. The
orchestrator owns the call site, not the feature-specific conversion logic.

Consequences:

* all downstream consumers observe only mapping-form `legend_blocks`;
* list-form identity resolution from `name` / `id` is performed once;
* duplicate resolved block identities and malformed entries fail
  deterministically at ingress;
* structured persistence emits only the canonical mapping form;
* no renderer-only or backend-specific list normalisation is introduced;
* the list form remains supported as input compatibility sugar unless a later
  lifecycle decision explicitly retires it.
