==== 2. Independently reconstructed E6 contract

From section 23, independent of the implementation's own summary: E6 must
publish contracts for `run_pipeline`, documented builders, supported
lower-level Domain/backend APIs, and internal/importable-only code, and
must decide -- from actual consumer evidence, not assumption -- whether
supported programmatic callers need an explicit conformance-establishment
helper. Acceptance requires a consumer be able to determine: where
establishment is automatic; where a conformant state is a caller
precondition; how an explicit helper is obtained *if* one is supported;
and which surfaces carry no promise. Constraints: `run_pipeline` stays
step-only/unwired; no aggregate importability promotion; no API
removal/rename; no universal Domain barrel; no E7 authorization; no Domain
Maintainer Contract work. Section 21 independently corroborates this: it
had already flagged `establish_ingress_conformance(frames)` as "LIKELY
IMPLEMENTATION" but explicitly deferred its public-export status to E6
consumer evidence, and separately marked "Automatic ingress inside
`run_pipeline`" REJECT. Section 25 independently requires E6 to give
`run_pipeline` an "explicit caller-precondition disposition" (no automatic
wiring) and to give Direct Domain/backend APIs a "support/precondition
classification."
