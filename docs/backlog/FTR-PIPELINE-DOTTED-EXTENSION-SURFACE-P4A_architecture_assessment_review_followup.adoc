invocation can read any file the process user can access under normal OS
permissions -- exactly the claim the corrected assessment text makes, and
materially different from the three write selectors, which are contained
by `_safe_target_path` per the independent review's own 6.4 source
citation (not re-verified line-by-line here since the correction assessed

== 4. M-1 closure

*Original finding:* the direct colon-style factory's pre-import
interception point was not explicit enough -- section 8's diagram states
the required outcome ("reject before importing the outer factory") but
nothing connected that outcome to the specific fact that
`resolve_registration()` performs the import itself for this one surface,
creating a risk that a future E7 implementer would authorize "after
calling `resolve_registration`, before calling its returned factory,"
which is already too late.

*Source verification, independently re-derived:*
`pipeline/registry.py::resolve_registration` (lines 199-205):

[source,python]
----
def resolve_registration(step_id: str) -> StepRegistration | None:
    entry = REGISTRY.get(step_id)
    if entry:
        return entry if isinstance(entry, StepRegistration) else StepRegistration(factory=entry)
    if ":" in step_id:
        return StepRegistration(factory=resolve_configuration_callable(step_id))
    return None
----

For an unregistered colon-bearing `step_id`, this function calls
`resolve_configuration_callable(step_id)` inline, on its own return path --
not lazily, not deferred. `pipeline/dotted_paths.py::resolve_configuration_callable`
(lines 31-38) calls `importlib.import_module(module_path)` directly inside
that same call. `pipeline/build.py::build_steps_from_config` (line 30)
calls `resolve_registration(step_id)` as its first step-processing
statement, with no intervening classification of `step_id`. This confirms
the finding precisely: there is currently no point in the call graph
between "step_id is known" and "import has happened" for this surface,
unless a future E7 implementer independently tests the colon-shape
condition (`":" in step_id and step_id not in REGISTRY`) *before* calling
`resolve_registration`. Calling `resolve_registration` first and then
authorizing its result is invalid, because the import already occurred
inside the call.

*Wording check:* section 8's "Compatibility dynamic callable
construction/acquisition" row now states: "For an unregistered
colon-bearing `step_id`, E7 must authorize or deny the direct-colon
capability *before calling* `resolve_registration()`: that function
performs resolution/import itself, so calling it first and authorizing its
result is invalid." This states detect/classify-before-call and
authorize/deny-before-import exactly as required, and states the reason
(import happens inside `resolve_registration`), not merely the outcome.

*Mechanism-freezing check:* the new paragraph after the section 8 diagram
states a later E7 implementation "may hoist or reuse the colon-shape test,
split lookup from resolution, or introduce a small preparation helper,"
and that "this assessment selects none of those mechanisms and requires no
prerequisite refactor." This leaves the implementation mechanism open
while fixing only the invariant (classify/decide before
`resolve_registration()` can import), matching the requirement exactly.

Section 7's "Direct colon-style factory" row was not touched by the
correction and still states the outcome only ("E7 must deny it before
import in less-trusted mode"), without the `resolve_registration()`-specific
detail. This is not a contradiction: section 7 states the surface-level
safe-interim-contract outcome, section 8 states the implementation-relevant
timing detail the independent review specifically asked to have connected
to that outcome. The review's own recommended action asked for the
sentence in "section 8's ... row (or section 6's derived-FTR handoff)" --
not section 7 -- so leaving section 7 as an outcome-level statement is
consistent with the recommended action as given.

*Result:* **M-1 RESOLVED.**
