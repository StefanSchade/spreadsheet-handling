===== TD64-REVIEW-F1 -- "complex is already, and remains, uniformly rejected (both NaN and non-NaN forms)" is true for plain Python `complex` but false for `numpy.complex128`

*Classification:* Minor. Documentation-only; does not affect the runtime
fix's correctness, scope, or the BUG's core reasoning (which rests on the
Duration-unsupported contract and `ADR-DOMAIN-BOUNDARY-ROBUSTNESS`, not on
this analogy alone).

*File/symbol:* BUG doc, "Reconciling with accepted Missing semantics and
prior findings" section, "Does this reopen `numpy.complex128`'s accepted
precedent?"; echoed in commit `022f651`'s message ("matching the
already-accepted complex128 precedent").

*Evidence, independently reproduced against current `HEAD`:*
[source,pycon]
----
>>> scalar_category(complex(float("nan"), 0))
UnsupportedScalarError('complex')                   # plain complex: uniform
>>> scalar_category(np.complex128(complex(float("nan"), 0)))
'missing'                                            # numpy.complex128: NOT uniform
>>> scalar_category(np.complex128(complex(1, 2)))
UnsupportedScalarError('complex128')
----
`numpy.complex128` NaN classifies as `"missing"`, not
`UnsupportedScalarError`, while non-NaN `numpy.complex128` is correctly
rejected -- an internally split family, exactly the pattern this BUG
describes as defective for pre-fix `numpy.timedelta64`. This is not a new
discovery: it is precisely the already-accepted, non-blocking
IVM-REVIEW-F7 gap (`FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A_review.adoc`,
independently re-confirmed still open and correctly not reopened by this
BUG). The BUG's own "uniformly rejected (both NaN and non-NaN forms)"
sentence is accurate only for plain Python `complex`, not for
`numpy.complex128`, and should not be read as claiming
`numpy.complex128` sets the uniform-rejection precedent it invokes.

*Why it matters:* a future reader could believe `numpy.complex128` is fully
consistent today and be surprised to find its NaN form still classifies as
Missing (IVM-REVIEW-F7, deliberately left open, unaffected by this BUG).

*Smallest correction:* narrow the sentence to name plain Python `complex`
specifically (`"plain Python complex is already, and remains, uniformly
rejected"`), and/or add one clause noting `numpy.complex128` NaN remains a
separate, already-accepted, non-blocking gap (IVM-REVIEW-F7), not silently
reopened or claimed as precedent here. Documentation-only; no runtime or
test change implied.

*Disposition:* non-blocking. Does not require reopening IVM-REVIEW-F7 or any
runtime change; recorded for a future documentation-precision pass, per this
review's read-only default (fix not applied here, consistent with
`review_instructions.adoc`'s "record a finding, not fix it" default).
