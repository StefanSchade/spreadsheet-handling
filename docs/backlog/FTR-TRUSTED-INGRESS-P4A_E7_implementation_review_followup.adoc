== 4. `from_mapping` / immutability regression check

Independently verified `from_mapping` remains the sole supported valid
construction route and is behaviorally unchanged:

* `LessTrustedDescriptionAuthorization.from_mapping({})` still succeeds and
  returns a valid empty deny-all policy; passing it to
  `build_steps_from_config([{"step": "identity"}], ...)` still raises
  `DescriptionAuthorizationError(kind="forbidden_identifier", reason=
  "registered_step_not_authorized")`, i.e. deny-all is preserved, not
  silently reinterpreted as an allow.
* `from_mapping({"registered_steps": {"identity": {}}, "plugin_targets":
  []})` still succeeds and authorizes exactly `identity`; the corresponding
  `build_steps_from_config` call succeeds. `registered_steps` and
  `plugin_targets` parsing are unaffected by the correction (the diff never
  touches `_parse_registered_authorities`, `_parse_plugin_targets`, or
  `_parse_step_authority`).
* No second supported constructor semantic was introduced. Bare
  `LessTrustedDescriptionAuthorization()` unconditionally raises before any
  attribute assignment -- it is not a deny-all shortcut, and no code path
  interprets it as one. The intended contract (bare constructor: controlled
  `invalid_policy` failure; `from_mapping(...)`: valid closed grammar) holds
  exactly as described.

Ordinary-path immutability of a `from_mapping`-constructed policy re-probed
directly (no `object.__setattr__`, ctypes, or other threat-model-excluded
bypass):

* `policy._registered_steps` is a real `mappingproxy`; item assignment
  raises `TypeError: 'mappingproxy' object does not support item
  assignment`.
* `policy._plugin_targets` is a real `frozenset`; `.add(...)` raises
  `AttributeError`.
* Ordinary attribute assignment on the frozen, slotted dataclass
  (`policy._plugin_targets = frozenset()`) raises
  `FrozenInstanceError: cannot assign to field '_plugin_targets'`, confirming
  the new `__init__` did not weaken `frozen=True`/`slots=True` in any way for
  the constructed-and-populated instance.

Because `from_mapping` bypasses `__init__` entirely via `object.__new__`,
confirmed it still initializes both slots correctly on every exercised path
(empty mapping, populated `registered_steps`, empty `plugin_targets`) -- no
partially-initialized instance is reachable through the supported route.

*NO `from_mapping`/IMMUTABILITY REGRESSION.*

== 5. Builder behavior for malformed direct construction

Re-drove the original defect's two-step reproduction
(`malformed = LessTrustedDescriptionAuthorization()` then
`build_steps_from_config(..., description_authorization=malformed)`)
end-to-end: step one now raises `DescriptionAuthorizationError` immediately,
so `malformed` is never bound and step two is never reached under ordinary
control flow. There is no ordinary supported way for ordinary Python to
construct an incomplete `LessTrustedDescriptionAuthorization` and pass it
into the builder; the rejection is unconditional and argument-free (the
`__init__` takes no parameters other than `self` and always calls
`_invalid_policy`, so there is no accidental "valid-looking" call shape that
skips it). Deliberate `object.__new__`/`object.__setattr__`/ctypes/pickle-
gadgetry bypasses remain out of the accepted threat model per task scope and
were not explored.
