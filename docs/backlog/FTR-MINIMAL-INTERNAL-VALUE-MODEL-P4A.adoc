==== Purpose and scope

*Central design question:*

____
What is the smallest closed internal payload-value contract that prevents
pandas/backend carrier artifacts from silently becoming domain semantics,
while preserving ordinary DataFrame ergonomics and avoiding a complete
spreadsheet cell-type system?
____

This FTR answers that question with a current-state inventory (Stages A-B
below), an evaluation of the candidate category set `String / Boolean /
Number / Missing / Error` against that evidence (Stages C-G), and a
recommended contract shape, boundary, and implementation slicing (the
numbered sections after the inventory). It does not start from a `CellValue`
wrapper hierarchy and does not assume every physical spreadsheet or Python
type needs a corresponding domain type, per the task brief and per
`roadmap_domain_hardening_sequence.adoc`'s own "types describe supported
values, not arbitrary Python" guiding principle.

*In scope:* the inventory itself; the category evaluation; a recommended
Missing/carrier-boundary contract; a native-scalar-vs-wrapper recommendation;
a contract-boundary-ownership recommendation; the relationship to
`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` and whether it must be reopened;
formula non-goals (restated from the BUG that deferred them); a compatibility
inventory; the relationship to `FTR-PAYLOAD-SEMANTICS-RECOVERY-P5`;
dependency-ordered implementation slices; acceptance criteria; required
executable tests; explicit non-goals; and the handoff shape for Trusted
Ingress (Phase E).

*Out of scope (this FTR does not do these; they are later, separately
authorized work):* any Python value-class implementation; any parser or
renderer change; any change to domain transformations; any registry or
`_meta` schema change; Project Memory updates; a successor/amendment ADR
(this FTR only determines *whether* one will eventually be needed); Trusted
Ingress (Phase E) implementation.

Additional re-verified facts, not backend-specific:

* *ODS boolean write* [FACT, re-verified this task] -- `io_backends/ods/odf_renderer.py`
  has an explicit `isinstance(value, bool)` branch (line ~587) that writes a
  native `valuetype="boolean"` ODS cell with `"TRUE"`/`"FALSE"` text. This
  branch can only fire for a real Python `bool` reaching the renderer, which
  -- because every spreadsheet ingress path stringifies before reaching
  Frames -- only happens via the direct-Frames/programmatic path (or a
  future non-spreadsheet backend that preserves native bool). *XLSX has no
  equivalent explicit branch*; `openpyxl_renderer.py:_xlsx_cell_value`
  passes a Python `bool` straight to `ws.cell(..., value=val)`, and OpenPyXL
  itself natively supports Python `bool` as a boolean cell value -- the
  *outcome* (native boolean cell) is the same on both backends for this
  input, but ODS's mechanism is an explicit, owned branch while XLSX's is an
  accidental library behavior, mirroring exactly the asymmetry already
  documented for missing-carrier handling.
* *Formula-vs-value read policy* [FACT] -- XLSX's `data_only=True` is a

  re-derive.

  pass-through sediment where it survives in old artifacts.
* *`domain.ingress` current shape* [FACT, re-verified this task] --

==== 4. Candidate-category evaluation (Stages C-G)

===== Stage C -- String [RECOMMENDATION]

Native `str` is sufficient. No wrapper is evidenced as necessary:

* Ordinary strings are already stable as native Python `str` on every
  ingress path re-verified in section 1 -- no maintained code treats a
  plain string as ambiguous.
* `""` must remain a legitimate payload value -- directly required by the
  accepted `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A` contract, which
  depends on `""` being able to mean *both* "legitimately empty" and
  "unresolved," disambiguated elsewhere (source FK + resolution), not by
  the string's own shape.
* Strings resembling `"nan"`, `"true"`, numbers, spreadsheet errors, or
  formulas are always literal text unless an owning parser/schema
  explicitly identifies another carrier -- directly confirmed: the ODS
  fix's own literal-`"nan"`-preservation test proves the framework already
  treats a domain string equal to `"nan"` as ordinary text, distinct from a
  missing carrier, by checking `isinstance(value, str)` *before*
  `pd.isna`.
* No evidence anywhere in this inventory shows a missing invariant that a
  `StringValue` wrapper would close. *Recommendation:* keep `str` native;
  do not introduce a wrapper.

===== Stage D -- Boolean [RECOMMENDATION, with an open compatibility note]

* JSON/YAML backends force `dtype=str` (JSON) or apply missing-only
  coercion after DataFrame construction (YAML) -- neither currently
  preserves a native Python bool as a *distinguishable* type through to
  Frames on the read side; a YAML `true`/`false` scalar in a non-missing
  cell is whatever `pd.DataFrame(...)` inferred (frequently, but not
  guaranteed, a real Python `bool`, since `yaml.safe_load` does produce
  real `bool` objects for non-missing YAML booleans).
* XLSX/ODS native boolean cells are stringified at the parser boundary
  exactly like every other visible payload, per the accepted ADR --
  `"TRUE"`/`"FALSE"` (ODS convention) or Python's own `str(True)` ->
  `"True"` (XLSX, confirmed no dedicated boolean handling in the XLSX
  parser at all -- an unaddressed cross-backend spelling asymmetry,
  recorded here, not fixed).
* CSV textual `"true"`/`"false"` is never interpreted as boolean by any
  maintained parser -- confirmed: no maintained backend reads a CSV or
  spreadsheet string and promotes it to a Python `bool` without an
  explicit owning schema. This directly satisfies the task's instruction:
  "do not treat the strings `\"true\"` / `\"false\"` as Boolean without an
  explicit owning parser/schema rule."
* On the write side, both renderers *do* special-case a real Python `bool`
  (ODS explicitly, XLSX via OpenPyXL's own native handling) -- but this
  path is only reachable from non-spreadsheet-ingress sources (direct
  Frames, or a future backend that preserves native types), because every
  spreadsheet ingress path already collapsed booleans to strings before
  Frames exist.

*Recommendation:* `bool` remains a legitimate, distinguishable in-memory
scalar for structured/programmatic Frames (JSON/YAML/direct construction),
consistent with current renderer behavior; the visible-spreadsheet-cell
boolean spelling stays a string, per the accepted ADR, exactly as it is
today. Preserving Boolean distinctly from String/Number removes real
ambiguity *only* for structured payload; it removes no ambiguity on the
spreadsheet-cell path, because that path never carries a native bool
through to Frames in the first place. *[OPEN]* whether the XLSX/ODS
boolean-text spelling asymmetry (`"True"`/`"False"` vs `"TRUE"`/`"FALSE"`)
should be reconciled is a separate, narrow, sink-local decision -- not part
of this FTR's scope, and not evidenced as causing any current defect (no
BUG or test failure traces to it).

===== Stage E -- Number; Integer versus Float [BOUNDED DEFER, per task instruction]

* JSON/YAML canonical serialization: the historical motivating pain point
  for `ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` was exactly `1` vs `"1"`
  round-tripping incorrectly through a workbook -- that ADR already decided
  the *visible-cell* side of this question (string substrate; opt-in
  typing only). This FTR does not reopen that.
* pandas does not reliably preserve `int` vs `float` across the maintained
  ingress paths inventoried in section 1: JSON forces `dtype=str`
  (no native numeric survives ingestion at all); CSV's directory path
  applies ordinary pandas dtype inference, which can silently promote an
  integer column to `float64` in the presence of any missing value (a
  well-known pandas behavior, not independently reproduced for this FTR
  since it does not change any conclusion already evidenced above); YAML
  is whatever `pd.DataFrame(...)` infers from parsed scalars.
* XLSX/ODS numeric-cell behavior is fully subject to the accepted string
  substrate -- no numeric type distinction survives spreadsheet ingress at
  all today.
* Actual domain families using sequence/order/count/index-like values were
  not found to depend on a canonical `int`/`float` distinction anywhere
  inventoried in this FTR's compatibility scan (Stage K, below) -- IDs
  remain strings by existing contract (confirmed: FK keys are normalized
  to `str` by `_norm_id`, never treated as numeric).
* Arithmetic/comparison behavior: no maintained transformation family was
  found, in this inventory's scope, to perform numeric arithmetic on
  payload cell values as a primary responsibility (arithmetic that exists
  -- e.g. row/column indices, dimension bounds -- operates on framework-
  internal counters, not on payload scalars).

*Recommendation, per the task's explicit permission to defer:* the MVP
adopts a single `Number` category for now, without committing to
`Integer | Float` as two separate MVP categories. This is *not* "collapse
because spreadsheets expose one numeric cell class" (the task's own
rejected reasoning) -- it is because no current evidenced consumer requires
the distinction to be typed, and pandas does not reliably preserve it
across every maintained ingress path regardless of what the MVP decides.
*[OPEN]* the exact eventual `Number` representation (a bounded `float`, a
tagged `int | float` union, or a `Decimal`-based contract) is left for the
implementation slice that actually needs it (see "Implementation slices");
this FTR does not choose one. `Decimal` is confirmed, per Technical Concept
001's own inventory (re-verified: no `Decimal` usage found anywhere in the
read/write paths inspected for this FTR either), to have no current
evidenced need.

===== Stage F -- Missing [RECOMMENDATION -- central]

This is the section the task explicitly names as central, and the
inventory above (sections 2-3) already supplies the evidence.

*[FACT]* Distinguishing the five listed manifestations against current
code:

* *`None`* -- a carrier manifestation. Never itself legitimate domain
  payload on any maintained path; always either normalized away (JSON/YAML
  post-construction coercion) or, where unnormalized (CSV directory read),
  a confirmed gap.
* *`numpy.nan` / `pandas.NA` / `NaT`* -- carrier manifestations, identical
  in kind to `None` for this purpose. The whole `_is_empty_cell` family
  already treats all three uniformly via `pd.isna(...)`, confirmed by
  reading the five implementations directly.
* *`""`* -- *[ACCEPTED]*, per `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`'s
  adopted contract, legitimate domain payload *and* the accepted carrier
  for an unresolved reference simultaneously, disambiguated by
  authoritative-source-plus-resolution, not by the string's own value.
  This FTR must not, and does not, propose collapsing `""` into a
  carrier-missing category at the domain-semantic level -- only the five
  *local* predicates above are entitled to treat `""` as "blank" for their
  own narrow, already-justified purposes (rendering emptiness, FK-key
  lookup-miss equivalence).
* *FK unresolved state* -- *[ACCEPTED]*, does not require an
  `UnresolvedReference` type; resolution state is a pure function of
  `(source_frame, target_frame)` recomputable on demand
  (`validate_fk_helpers`), not a stored value shape.
* *A successful lookup whose target payload is itself missing* -- *[FACT]*,
  distinct from an unresolved lookup (the BUG's own "Missing target
  payload" section proves this explicitly): the FK *resolves*; the
  *resolved value itself* is a missing carrier. This is exactly the
  carrier-boundary leak class both BUGs closed, not a reference-resolution
  question.

*Recommended contract:*

. *No new `Missing` type, class, or sentinel value.* The evidence
  (`BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`'s Option A rejection,
  reasoned through in detail there and not re-litigated here) shows a
  distinct in-band sentinel would relocate ambiguity rather than remove
  it, and duplicate information the framework does not need duplicated.
  This FTR adopts that reasoning as general, not FK-helper-specific: it
  generalizes because the underlying argument ("a derived/presentational
  value need not carry information recoverable from an authoritative
  source") does not depend on FK helpers specifically.
. *A shared carrier-missing recognition predicate is the correct
  mechanism*, not a value type. The five convergent implementations
  already agree on its shape:
+
[source,python]
----
def is_missing_carrier(value: Any) -> bool:
    if value is None:
        return True
    if isinstance(value, str):
        return value == ""
    try:
        return bool(pd.isna(value))
    except (TypeError, ValueError):
        return False
----
+
This is *recognition*, not *representation* -- it answers "is this cell's
current carrier a missing one," it does not mint a new value that flows
through the system. The MVP's job is to make this recognition available
at every carrier-boundary write/normalize point that currently lacks it
(the confirmed `csv_dir` gap), and to stop it from being silently
reinvented a sixth time.
. *On the spreadsheet-payload side*, the canonical missing representation
  stays `""` -- an ordinary string, per the accepted substrate ADR, exactly
  as already implemented by every closed BUG's fix. This FTR does not
  propose a spreadsheet-visible token distinct from `""`.
. *On the structured/programmatic side* (CSV directory, direct Frames), a
  real pandas/NumPy missing carrier may still legitimately exist in
  memory between ingress and any boundary that normalizes it -- the MVP
  does not need to eliminate pandas `NaN` from DataFrame internals (that
  would fight ordinary DataFrame ergonomics, which the task explicitly
  asks this FTR to preserve); it needs the *boundary* crossings
  (persistence, spreadsheet write, cross-format normalization) to
  recognize and normalize it consistently, using the shared predicate
  above, rather than each boundary reinventing its own detection.

*DataFrame ergonomics assessment* [FACT]: a recognition-predicate-only
contract imposes zero cost on ordinary pandas operations -- no column dtype
changes, no wrapper unwrapping before arithmetic/comparison/grouping, no
new object-column overhead. This is the direct reason this FTR prefers it
over any sentinel-object approach (which would either need to be a real
NaN-compatible float subclass, with the attendant IEEE-754 equality
problems the ODS BUG's root cause already demonstrates, or an object that
breaks numeric dtype columns).

===== Stage G -- Error [RECOMMENDATION -- deferred, not rejected outright]

*[FACT]* No current maintained path can actually observe a distinct
spreadsheet error carrier:

* XLSX: confirmed by direct probe this task (see section 1) -- without
  real spreadsheet-application evaluation, OpenPyXL has no cached error
  value to surface; `data_only=True` returns `None` for an unevaluated
  formula, not an error token.
* ODS: no maintained parser code path reads an ODS error `value-type` or
  error-specific attribute (grep-confirmed: no error-handling code exists
  in either backend package).
* A literal string such as `"#N/A"` appearing anywhere in payload is,
  to every current maintained code path, always an ordinary domain string
  -- confirmed, not merely asserted, by the absence of any distinguishing
  code.

*Recommendation:* Error is *justified in principle but currently blocked on
parser preservation*, not rejected and not adopted into the first MVP
slice. No maintained ingress path can currently produce the input an Error
category would need to distinguish, so typing it now would define a
category with no reachable instance -- exactly the "invent an Error class
merely because spreadsheets have error cells" outcome the task explicitly
warns against. *[OPEN]* if a future FTR adds real spreadsheet-application-
evaluated error-cell preservation to either parser, Error becomes
immediately actionable using the same recognition-not-representation
pattern as Missing; this FTR does not design that parser work and does not
block it, but the internal value model does not need to anticipate it with
an empty category today.

===== Explicitly undecided (per task brief, left undecided here as directed)

* *Integer vs Float* -- bounded-defer, per Stage E above.
* *Date / Time / DateTime* -- *[FACT]*: no maintained parser currently
  preserves a distinguishable date/time carrier through to canonical
  payload. ODS reads `date-value`/`time-value` attributes only as a
  fallback when paragraph text is empty (uncommon for LibreOffice/Excel-
  authored date cells, which normally do carry formatted paragraph text),
  and immediately stringifies whatever it finds; XLSX has no date-specific
  handling at all (`str(datetime_obj)` if a `datetime` object is present).
  No canonical parse-back exists anywhere. *[OPEN, explicitly deferred per
  task instruction]* -- this FTR records the current-state fact and takes
  no position on a future Date/Time/DateTime category; there is
  insufficient current evidence of a maintained consumer that needs it
  typed, and the visible-cell substrate ADR governs the spreadsheet side of
  any future answer regardless.
+
Date/Time is different in kind from Formula (section 9), not merely another
deferred item on the same list: `date`/`datetime`/pandas `Timestamp` are
genuine scalar-value-model candidates -- a `Timestamp` is payload data, not
carrier/workbook behavior -- and current repository evidence already shows
them occurring in direct-Frames/pandas paths (Stage A). They are out of
scope for this first MVP slice only because no canonical normalization
contract yet exists to decide, among others, `date` vs. `datetime`
coercion, timezone-aware vs. timezone-naive semantics, `Timestamp`
retention vs. normalization, Excel serial-date semantics, ODS date-carrier
semantics, and JSON/YAML date serialization -- open decision questions for
that future slice, not answers this FTR gives. Because spreadsheet
sorting/filtering/comparison by dates is a common and likely near-term
requirement, Date/Time is expected to be an *early* Phase-D follow-up slice
once this MVP lands -- unlike Formula, which is deferred indefinitely under
`FTR-FORMULA-INGRESS-ROUNDTRIP-WHITELIST-P5` pending its own dedicated
design/review slice.

==== 6. Native scalars versus wrappers (Stage I) [RECOMMENDATION]

[cols="2,3,3",options="header"]
|===
| Dimension | Native-value contract | Wrapper/value-object contract

| pandas compatibility
| No change -- `str`/`bool`/numeric/carrier-NaN are already what pandas
  columns hold today
| Every wrapper instance sits in an `object`-dtype column; loses
  vectorized dtype benefits pandas already provides for `str`/`bool`/
  numeric columns today

| DataFrame assignment/coercion
| Unaffected
| A wrapper assigned into a numeric-inferred column risks silent
  `object`-dtype demotion of the whole column, or requires per-column
  `dtype=object` pinning everywhere a wrapper might appear

| Vectorized operations
| Unaffected -- pandas' native numeric/string/bool vectorization applies
  normally
| Lost or requires per-operation unwrapping; defeats the DataFrame
  ergonomics the task explicitly asks this FTR to preserve

| Joins/grouping/filtering
| Unaffected -- FK joins, `groupby`, boolean filtering all already work on
  native scalars today (confirmed: `_norm_id`-based FK joins operate on
  plain `str`/`None`)
| Every join/group/filter key becomes a wrapper-equality question;
  `Missing`'s IEEE-754-adjacent equality problem (the exact root cause the
  ODS BUG traced) recurs unless the wrapper carefully reimplements
  `pd.isna`-compatible comparison itself

| Serialization / JSON / YAML ergonomics
| Unaffected -- native scalars serialize with stdlib `json`/`yaml.safe_dump`
  with no custom encoder
| Every wrapper needs a custom encoder/decoder pair, maintained in
  parallel with the native serializers already in use

| Backend adapters
| Unaffected -- adapters already read/write native scalars
| Every adapter (XLSX, ODS, CSV, JSON, YAML, XML) needs wrapper-aware
  read/write logic, multiplying the exact per-format duplication this FTR
  is trying to reduce

| Debugging
| A `repr()` of a DataFrame cell is already meaningful
| An extra unwrap step at every debugging/`print()`/log site

| Type annotations
| `str \| bool \| int \| float \| None` (or a `Number` alias per Stage E)
  is already expressible without new classes
| Requires a new union/protocol *and* still needs a native-value escape
  hatch wherever pandas vectorization is required, so the wrapper does not
  actually replace native typing, it adds a layer in front of it

| Amount of code "infected" by wrappers
| None -- every existing consumer keeps working unchanged
| Every domain transformation, every adapter, every test fixture that
  touches a payload cell needs wrapper-awareness -- a far larger blast
  radius than this FTR's evidenced need justifies

| Prevents any evidenced current defect?
| Yes -- the shared recognition predicate (Stage F) directly targets the
  exact evidenced defect class (a carrier silently becoming domain text)
| No additional defect prevention beyond what the native-value recognition
  predicate already provides; both closed BUGs were fixed with a
  *predicate*, not a wrapper, and neither fix needed one
|===

*Recommendation:* native scalars plus a shared recognition predicate for
Missing. No wrapper hierarchy is justified by current evidence. This
directly follows the task's own instruction to prefer the smallest
mechanism that establishes an enforceable contract, and not to favor
wrappers for theoretical purity -- every dimension compared above either
favors native values or is neutral; none favors wrappers.

==== 9. Formula hard non-goals [ACCEPTED -- restated, not re-derived]

Restated verbatim in substance from `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`'s
"Deferred formula / typing constraint" section, which this FTR is required
to treat as binding evidence, not re-open:

* *Formula is outside the MVP.* A formula is carrier/workbook behavior
  layered on top of whatever value it evaluates to, not a scalar payload
  value. It is not part of this FTR's recommended MVP category set.
* *Observed formula != authored `FormulaSpec`.* `core/formulas.py`'s
  `ListLiteralFormulaSpec`/`LookupFormulaSpec` are authored, backend-
  neutral, output Intent the framework itself constructs. A formula merely
  observed while reading an existing workbook is carrier/workbook state,
  not automatically that Intent. Confirmed unchanged this task
  (`core/formulas.py` re-read; both dataclasses `frozen=True`, directly
  constructible, unrelated to any read-path behavior).
* *Default read direction (deferred design direction, not implemented
  here)*: existing spreadsheet formulas should normally be consumable as
  their materialized/cached values; preservation requires explicit read
  policy. This FTR does not turn that direction into an implementation
  contract, consistent with the constraint that produced it.
* *Projection/use-case ownership.* Formula preservation must not become
  immutable column typing. The same canonical field may legitimately need
  both an editable-workbook-roundtrip (formula-preserving) projection and
  an external-extraction (materialized-value) projection. This FTR's
  recommended Number/Boolean/String/Missing categories describe *payload
  values*, not *projection policy*, and do not conflict with this
  constraint.
* *Timing.* Any future formula-preservation read policy must be available
  at or before the parser boundary (`router.get_loader(kind)`), not as a
  mid-pipeline step such as `bootstrap_meta` -- confirmed still true this
  task (pipeline execution order unchanged; `bootstrap_meta` still runs
  inside `run_pipeline`, strictly after the loader has already parsed the
  file). This FTR does not design that policy or its API/DSL, per the
  task's explicit instruction.
* *No generic Formula scalar/value class.* This MVP slice must not
  introduce a generic `Formula` scalar or value type merely because
  workbooks can carry arbitrary formula text. Nothing in the recommended
  String/Boolean/Number/Missing/Error category set (section 5) is a stand-in
  for formula representation, and a later slice may not silently widen one
  of those categories to also mean "formula."
* *Deferred formula-policy anchor.* Durable constraints for any future
  formula-preservation/roundtrip feature -- strict allowlist, feature-owned
  contracts, no general Excel/OpenFormula compatibility promise, the
  FK-helper emit-does-not-imply-preserve precedent, and the pre-load/
  pipeline-dependent policy timing above -- are tracked separately in
  `FTR-FORMULA-INGRESS-ROUNDTRIP-WHITELIST-P5` (deferred, not
  implementation-ready). This FTR does not restate those constraints; that
  FTR is the durable anchor for them.

===== 17.2 What was built

*D1 -- shared carrier-missing recognition predicate* and *D3 -- documented
MVP scalar-category contract*, implemented together in one new module
because D3's own acceptance bullet (section 12) already described it as
"type aliases and docstrings," and the natural docstring owner for those
type aliases is the module that also owns the one predicate they describe:

[source,text]
----
src/spreadsheet_handling/core/scalar_values.py (new)
----

Contents:

* `ScalarValue` -- `TypeAlias = str | bool | int | float | None`, matching
  `core/formulas.py`'s own `TypeAlias` convention for `FormulaSpec`. `None`
  is documented as the common Missing carrier, not the only one --
  `is_missing_carrier` is the actual recognition mechanism, per section 4
  Stage F.
* `ScalarCategory` -- `TypeAlias = Literal["string", "boolean", "number",
  "missing"]`. A closed set; Error, Integer-vs-Float, and Date/Time are
  deliberately absent, matching section 5's recommended MVP category list.
* `is_missing_carrier(value: Any) -> bool` -- byte-for-byte the same shape
  as the five already-converged local implementations and as this FTR's own
  section 4 Stage F pseudocode (`None` -> `True`; `str` -> `value == ""`;
  else `pd.isna`-guarded against `TypeError`/`ValueError`). Not a new
  semantic -- the first shared, importable copy of an already-accepted
  predicate.
* `UnsupportedScalarError(TypeError)` -- raised by the classifier below for
  anything outside the vocabulary. The diagnostic reports only
  `type(value).__name__`; it never calls `repr`, `str`, `==`, hashing, or
  iteration on the rejected value (verified empirically -- see 17.3 -- that
  `pandas.isna` itself does not trigger any of those on a generic object
  either, so this guarantee holds through the whole classification path,
  not only in the error constructor).
* `scalar_category(value: Any) -> ScalarCategory` -- a *classification*
  predicate, not a conversion/coercion function: for a supported value it
  returns a category label without inspecting string content, without
  unifying missing-carrier representation, and without mutating or
  rewrapping the value. Order is `is_missing_carrier` first (so a NaN-family
  `float`/`numpy.floating` classifies as `"missing"`, never `"number"`),
  then Boolean (`bool`, `numpy.bool_`) before Number (`int`, `float`,
  `numpy.integer`, `numpy.floating`), because Python's `bool` subclasses
  `int`. A `date`/`datetime`/`Timestamp`, a `FormulaSpec` instance, or any
  other object outside the vocabulary raises `UnsupportedScalarError`
  rather than being silently absorbed into an existing category -- this is
  the concrete mechanism that keeps sections 4/9's Date/Time and Formula
  deferrals enforceable rather than merely documented.
* `is_supported_scalar(value: Any) -> bool` -- convenience wrapper around
  `scalar_category` for a caller that only needs a yes/no answer; never
  raises.

*NumPy scalar policy decision* (task step 6.2/6.3, not explicitly resolved
by sections 1-16 above): empirically verified this task (not assumed) that
ordinary DataFrame cell access already surfaces `numpy.bool_`, `numpy.int64`
(etc.), and `numpy.float64` for columns built from native Python data (for
example, `yaml_backend.py`'s `pd.DataFrame(data)` construction, or any
direct-Frames caller) -- `df.iloc[0]["b"]` on a boolean column returns
`numpy.bool_`, not `bool`; an integer column returns `numpy.int64`, not
`int`. `numpy.float64` already subclasses `float` and `numpy.str_` already
subclasses `str` (so both were already covered by the plain `isinstance`
checks); `numpy.bool_` and `numpy.integer` do not subclass their Python
equivalents and needed an explicit `isinstance(..., (T, np.T))` check.
Classifying these as their natural category (not rejecting them) is treated
as within `ADR-DOMAIN-BOUNDARY-ROBUSTNESS`'s "reasonably implied by
documented pandas, NumPy... contracts" allowance, not new hardening scope
-- pandas/NumPy is already a direct dependency this module's own callers
already carry. `numpy.float16`/`numpy.float32` do *not* subclass `float`
(verified) and are covered by the explicit `numpy.floating` check.

*D2 -- `csv_dir` missing-value/dtype normalization*, closing the confirmed

===== 17.11 Review Follow-up (Independent Review 001 resolution)

`FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A_review.adoc` (Independent Review 001,
2026-08-09) accepted Slice 1 with verdict *ACCEPTED WITH MINOR FOLLOW-UP*: 0
Blocking, 3 Important (IVM-REVIEW-F1/F2/F3), 3 Minor (IVM-REVIEW-F4/F5/F6)
findings. This section records the resolution of the three Important
findings, strictly within their own stated smallest-correction scope --
no Date/Time, no Phase E, no formula work, no broad refactor, and no
Missing-semantics expansion beyond the already-accepted contract.

*IVM-REVIEW-F1 resolved.* `is_missing_carrier` no longer dispatches
`pandas.isna` to an arbitrary object. `pandas.isna` is now only called on a
value already known to be one of the accepted scalar-carrier shapes --
`int`, `float`, or a NumPy scalar (`numpy.generic`); `pandas.NA`/`pandas.NaT`
are recognized directly by identity (both confirmed stable singletons); any
other object -- including one implementing NumPy's `__array__`
array-conversion protocol -- is recognized as "not missing" without ever
reaching `pandas.isna`, so its `__array__` is never invoked at all. This is
the "bounded implementation that recognizes known scalar missing carriers
without invoking arbitrary NumPy conversion protocols on unknown objects"
the review's own smallest-correction language anticipated, not a mechanical
`except Exception` widening. The accepted Missing carrier set is unchanged
(`None`, `""`, the NaN/`pandas.NA`/`pandas.NaT` family) -- confirmed
byte-for-byte against every case the original 56-test suite already pinned,
independently re-verified before and after the fix. One narrow, previously
unspecified case incidentally changed: a Python `complex` NaN (e.g.
`complex(float("nan"), 0)`), which was never part of the accepted vocabulary
(`scalar_category` already rejects every other `complex` value with
`UnsupportedScalarError`), is no longer misclassified as `"missing"` by
`is_missing_carrier` -- it now falls through to the same
`UnsupportedScalarError` every other `complex` value already received. This
narrows an inconsistency, it does not expand Missing semantics. Three new
regression tests
(`test_is_missing_carrier_never_invokes_array_protocol_on_unrecognized_object`,
`test_is_supported_scalar_never_propagates_array_conversion_exception`,
`test_scalar_category_rejects_array_like_bomb_with_unsupported_scalar_error`)
use an object whose documented `__array__` raises a custom, non-`(TypeError,
ValueError)` exception and assert both the correct outcome and that
`__array__` was never invoked -- `tests/unit/core/test_scalar_values.py` now
has 59 tests (56 + 3), all passing. `is_missing_carrier`'s,
`scalar_category`'s, and `is_supported_scalar`'s docstrings, and the module
docstring's Missing bullet, were corrected to state the bounded-dispatch
mechanism precisely instead of the previous "safe on arbitrary objects via
`pandas.isna`'s own `TypeError`/`ValueError`" overclaim.

*IVM-REVIEW-F2 resolved.* No `normalize_scalar()` primitive was added --
the review explicitly accepted its absence as a legitimate Phase-E
deferral, not a defect, and this follow-up does not second-guess that.
`ScalarValue`'s docstring was rewritten to state plainly: `ScalarCategory`
is the actual Slice-1 semantic vocabulary; `scalar_category` classifies
values into it; its accepted carrier domain includes the NumPy scalar
variants named in the module docstring, without narrowing them to a
`ScalarValue` member; `ScalarValue` itself names only the candidate native-
Python value shape, not the complete accepted carrier domain and not a
canonical normalized representation; Slice 1 does not establish one; and
Phase E's "value normalization and type resolution" boundary stage still
owns adding a normalization primitive on top of these classifiers. The
alias name itself (`ScalarValue`) was not renamed -- no repository evidence
found the name materially misleading on its own, only its docstring's
framing, per the review's own "prefer documentation precision over renaming
APIs" guidance. Section 17.9's Phase-E handoff map gained an explicit

handoff-facing language, so a Phase-E implementer reading only 17.9 sees it
without needing to cross-reference `scalar_values.py`'s docstrings directly.
