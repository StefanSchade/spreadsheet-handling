== Status and authority

*Status:* active planning note.

*Authority:* sequencing and dependency planning only.

This document is not a runtime contract, public API specification, FTR, ADR, or
release commitment. Concrete behavior remains authoritative in the applicable
FTRs, BUGs, accepted reviews, domain contracts, registries, and executable tests.

The purpose of this note is to preserve the intended order of work after the
current ontology-oriented refactoring and to prevent several related concerns
from collapsing into one large refactor.

Concrete implementation work should continue to be carried by bounded FTRs,
BUGs, and review slices. This note links and sequences that work; it does not
replace it.

== Motivation

The project has accumulated substantial functional capability through iterative
development and AI-assisted implementation. The resulting system is increasingly
well-structured, but several concerns still overlap:

* remnants of implicit ontology and role-based behavior;
* incomplete internal typing;
* ambiguous missing, unresolved, and error-value semantics;
* defensive security logic distributed across domain transformations;
* inconsistent transformation-family structure;
* large and partially overlapping test suites;
* documentation and registry information maintained in several places.

These concerns should not be solved simultaneously.

The intended strategy is:

## [source,text]

complete current behavior
-> remove remaining implicit ontology
-> close type-blocking semantic contracts
-> establish internal types
-> establish mandatory trusted ingress
-> establish Domain Maintainer conventions
-> harden one transformation family at a time
-> consolidate durable documentation and contracts
--------------------------------------------------

Each stage should reduce uncertainty for the next one.

== Guiding principles

=== Bound complexity

The project may be larger than one person can understand at once, but each
individual transformation family and each local algorithm must remain
understandable.

New infrastructure is justified only when it removes repeated complexity from
supported paths. Theoretical edge cases should not automatically result in new
frameworks, carriers, registries, or metadata families.

=== Complete behavior before consolidation

Feature work and structural consolidation should remain separate whenever
possible.

Before a transformation family enters the hardening cycle, its intended behavior
should be implemented, tested, and independently accepted. Otherwise structural
changes and behavioral changes become difficult to distinguish.

=== Security belongs at explicit trust boundaries

Untrusted spreadsheets, JSON payloads, and externally supplied Frames must have
their declared ingress-conformance state established before normal domain
transformations consume them.

The domain should retain its own business invariants, but it should not repeatedly
defend against arbitrary Python objects, executable values, opaque binaries, or
other inputs that a mandatory ingress boundary already rejects.

=== Types describe supported values, not arbitrary Python

Transformations do not need to support every possible Python or pandas value.

Each transformation family should declare a closed and understandable set of
supported value types and deterministic behavior for those types.

=== Test contracts, not every Cartesian combination

Shared domain semantics should be tested once at the domain boundary.

Each adapter should test its own translation contract.

A small number of end-to-end tests should prove that the layers connect.

The test strategy should avoid multiplying every domain invariant by every file
format, parser representation, writer variant, and pipeline path.

=== One durable source of truth per concern

Public signatures, runtime registry entries, JSON registries, domain contracts,
and documentation must not become independent copies of the same information.

Later consolidation must establish which source is authoritative and how the
others are generated or verified against it.

== Phase B: replace `project_by_role`

*Status: DONE* — completed by `FTR-XREF-LOOKUP-HELPER-SUBSTITUTION-P4A2`
(Slice 4 removal implemented, corrected, and accepted in that FTR's independent
review 002; the FTR family is archived under
`docs/cold_storage/backlog/ftrs_done/`). The resolution differed from the
exploratory target below: rather
than introducing a new explicit projection API (`project_columns` and similar),
the only consumer — the ten worldbuilding matrix sites — migrated to the
existing explicit lookup/helper composition (`add_lookup_helpers` outbound +
`apply_derived_column_policy` inbound), and `project_by_role` was removed
outright with no wrapper or permanent deprecation. The shared
`resolve_column_roles` resolver is retained for role-targeted validation. The
problem/target analysis below is preserved as the rationale that led to removal.

=== Problem

`project_by_role` exposes implicit behavior through the term `role`.

A caller must discover:

* where column roles originate;
* which component defines their order;
* why role grouping controls projection order;
* what happens when the desired order does not follow role groups.

This is an unintuitive public API and retains ontology-like behavior in a place
that should express an explicit projection.

=== Target

Replace role-driven projection with an explicit column-selection and ordering
contract.

The public API should communicate directly:

* which columns are included;
* which columns are excluded;
* their intended order;
* how missing or additional columns are handled;
* whether the operation is projection-only or also renames columns.

Names should describe the operation rather than an inferred classification.

Possible vocabulary includes:

* `project_columns`;
* `select_and_order_columns`;
* `reorder_columns`;
* a declarative column projection specification.

The exact API requires a focused confirmation slice.

=== Constraints

* do not preserve role-based semantics merely under a new name;
* do not add another global column ontology;
* keep workbook-view behavior and domain transformations explicitly separated;
* preserve supported existing consumers through migration or a bounded
  compatibility path;
* remove the old API after adoption rather than maintaining two permanent
  alternatives.

=== Exit criteria (met by `FTR-XREF-LOOKUP-HELPER-SUBSTITUTION-P4A2`)

* supported consumers use the explicit lookup/helper composition instead of
  role-driven projection;
* `project_by_role` is removed (no wrapper, alias, or permanent deprecation);
* ordering behavior is visible from configuration (`helper_position: before_key`
  outbound; order-preserving `drop` inbound);
* projection tests describe the lookup/helper composition without relying on
  role ontology.

== Phase C: close type-blocking semantic contracts

=== Known blocking contract

Resolve:

`BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`

The currently expected failure demonstrates that an unresolved helper value may
return as the literal string `"nan"` after spreadsheet roundtrip without cleanup.

The project must decide the canonical distinction between:

* missing value;
* unresolved reference;
* empty string;
* numerical NaN;
* literal text `"nan"`;
* explicit error value, if supported.

This decision belongs before or at the beginning of internal typing. The type
model must not merely encode an accidental pandas or spreadsheet representation.

=== Additional contract scan

After the completed Phase B `project_by_role` retirement, perform a short,
bounded scan for other contracts that would block typing.

This is not a general transformation-family refactor.

The scan should look only for cases where:

* a supported value has several ambiguous internal representations;
* a transformation relies on arbitrary Python object behavior;
* missing/error semantics are implicit;
* a public boundary returns values that cannot be assigned a stable type;
* serialization and spreadsheet roundtrip disagree about identity.

Any discovered issue should become a small BUG or FTR with an explicit decision.

=== Exit criteria

* the known unresolved-value `xfail` is removed or replaced by an accepted
  explicit contract;
* missing, unresolved, null, and error values have defined semantics;
* no known unresolved semantic ambiguity blocks the initial internal type model.

== Phase D: establish the internal type model

=== Goal

Replace broad `dict[str, Any]` assumptions with explicit supported values and
controlled carrier construction.

The initial type model should remain small. It should not attempt to model every
possible future spreadsheet feature.

=== Required distinctions

The model should distinguish at least:

* externally parsed raw values;
* normalized scalar cell values;
* canonical metadata values;
* ordinary tabular frames;
* trusted internal carriers such as `ExactTable` and `GroupedMatrix`;
* missing, unresolved, and error states where the contract requires distinction.

=== Supported scalar types

A candidate closed set may include:

* `str`;
* `int`;
* finite `float` or an explicitly defined numeric representation;
* `bool`;
* `date`;
* `datetime`;
* `None` or another canonical missing representation;
* explicit formula or spreadsheet-error values only if intentionally supported.

The final set requires its own confirmation and compatibility analysis.

`FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A` narrows this candidate list for the
first MVP slice to String/Boolean/Number/Missing/Error, with Integer-vs-Float
bounded-deferred and Date/Time deferred as an expected early follow-up slice.
Formula is not a candidate for this or any typing slice; durable formula
constraints, should a future preservation feature ever be proposed, are
tracked separately by `FTR-FORMULA-INGRESS-ROUNDTRIP-WHITELIST-P5` (deferred).

=== Internal carriers

Internal carriers must be created only through controlled constructors or
factories.

Externally supplied payloads must not be able to claim trusted carrier identity
by reproducing an object-shaped payload.

Examples of trusted internal carriers include:

* `ExactTable`;
* `GroupedMatrix`;
* future explicitly registered domain values.

=== Typing strategy

Prefer a staged strategy:

. define type aliases and protocols around existing behavior;
. introduce typed constructors and normalization functions;
. type public transformation signatures;
. reduce `Any` at boundaries;
. tighten internal implementation types;
. add static checks only where the runtime contract is already clear.

Do not start by creating a deep class hierarchy for every frame and metadata
shape.

=== Exit criteria

* supported scalar and metadata types are explicit;
* trusted internal carriers are distinguishable from external payloads;
* public transformation boundaries have meaningful type signatures;
* unresolved uses of `Any` are identified as deliberate boundary points or
  follow-up work.

=== Goal

Ensure that untrusted spreadsheets, JSON documents, web-service uploads, and
CI/CD inputs reach normal Domain transformations only after the framework has
established Ingress-Conformant Domain Payload, and that every later
framework-managed producer return reaches either a declared exact controlled
state or ordinary re-establishment before ordinary macro flow resumes.

=== Boundary shape

## [source,text]

untrusted file or payload
-> backend parse / persistence-local conversion
-> establish Ingress-Conformant Domain Payload
   [ordinary DataFrame and ExactTable data cells use the six-category Scalar
    grammar; scalar carrier identity is preserved]
-> exact reviewed preserving, controlled-role, or composition transitions
   OR uncertified return followed by ordinary re-establishment/rejection
-> final Domain cleanup
-> persistence projection and sink
------------------

The initial establishment and later transition enforcement belong to the fixed
framework-managed application macro, not to an optional configured pipeline
step. `run_pipeline` remains step-only trusted-programmatic composition: its
caller supplies the execution state required by the first step and owns every
later preservation, controlled transition, or re-establishment.

=== File and parser protection

Existing parser conversions, `ParserLimits`, macro/external-link handling, and
format-specific protections remain owned by their parser/backend contracts.
Phase E composes after parse/conversion and does not itself introduce a
repository-wide resource-limit expansion, maximum text/collection policy, or
universal parser sanitizer. A later concrete parser/resource requirement must
retain its own owner and compatibility evidence rather than being inferred from
Trusted Ingress acceptance.

`FTR-XLSX-PARSER-RESOURCE-LIMITS-P4A` owns the current open XLSX
serialized-input parser/resource-limit work. It is independently sequenced,
is not E2 or another Phase-E sub-slice, and does not block E2 merely by
existing.

=== Semantic ingress validation

The accepted contract uses closed carrier dispatch, complete ordinary-cell
classification under the six-category Scalar grammar, and validate-only scalar
behavior. It preserves admitted carrier identity and Missing representation;
it does not introduce a general scalar normalizer. Exact internal FormulaSpec,
`GroupedMatrix`, composition, cleanup, and manifest states remain authorized
only through the bounded controlled transitions defined by the accepted FTR.
Every uncertified return ends that authority and must reach ordinary
re-establishment or rejection before ordinary macro flow resumes.

The ordinary `DeclaredComposite` branch remains empty in Phase E. Future
bounded `List[Scalar]` and `List[Object]`/nested-record concerns retain their
separate evidence and design gates.

=== Inert strings

Text resembling SQL, shell commands, source code, or HTML is not inherently an
invalid cell value.

Such strings must remain inert. Execution and injection risks are controlled at
the applicable output sink:

* SQL uses parameters;
* shell execution avoids string concatenation;
* HTML is escaped;
* YAML uses safe loaders;
* Python evaluation and dynamic imports are prohibited;
* formulas follow an explicit output policy.

Ingress should reject dangerous value structures, not attempt broad
content censorship.

=== Public enforcement

Framework-managed `sheets-run`, `run_app`, `orchestrate` and its compatibility
shim, and schema maintenance establish initial conformance automatically and
enforce later producer transitions. Supported lower-level Domain/backend APIs
retain explicit caller preconditions; importability alone grants no entry
guarantee. There is no automatic ingress inside `run_pipeline`.

Payload conformance and pipeline-description authorization remain separate.
Until E7 is accepted and implemented, configured CLI/`run_app` execution has a
mandatory trusted-description precondition and must not advertise less-trusted
pipeline YAML as protected.

=== Dimensions to establish

== Family cycle 0: inventory and behavioral baseline

=== Goal

Create a small working map before changing the family.

=== Record

* public entry points;
* registered steps;
* forward and reverse transformations;
* composites and primitives;
* internal carriers;
* metadata reads and writes;
* dependencies on other families;
* current modules and approximate sizes;

=== Exit criteria

* the supported behavior and public surface are identifiable;
* the current full and focused tests are green;
* proposed changes can be separated from unrelated family behavior.

== Family cycle 1: remove remaining ontology

=== Goal

Remove implicit global classifications, role assumptions, and hidden
cross-family knowledge.

=== Target shape

## [source,text]

explicit inputs
-> local deterministic transformation
-> explicit outputs
-------------------

Cross-family interaction remains allowed when it is:

* explicit;
* minimal;
* directed;
* documented;
* represented through a stable contract or carrier.

Metadata may support directed coordination, but generic pipeline infrastructure
must not route based on arbitrary payload metadata or treat `_meta` as an
ordinary frame.

=== Review questions

* Does the transformation infer behavior from an implicit role or family name?
* Does it depend on global ontology state?
* Does it inspect unrelated metadata to decide its algorithm?
* Could the caller express the same intent directly?
* Is cross-family communication explicit and one-directional?
* Is an old workaround still present after the capability that replaced it?

=== Exit criteria

* the family can be understood through its explicit API;
* no implicit ontology is required for supported behavior;
* remaining metadata communication has a named and documented purpose.

== Family cycle 2: remove redundant security defensive logic

=== Prerequisite

The mandatory ingress boundary is implemented and enforced.

=== Goal

Remove repeated protection against inputs that can no longer reach the normal
domain path.

=== Classification

For each defensive check:

## [source,text]

business or transformation invariant
-> keep in the family

conformant-value/type invariant guaranteed by ingress
-> remove from the family

historical guard for an unreachable payload
-> remove with its redundant test

output-sink security responsibility
-> move or retain at the sink
-----------------------------

Examples that may move to ingress include checks for:

* arbitrary Python objects;
* callables and modules;
* generators and file handles;
* opaque binary values;
* unexpected metadata object graphs;
* exotic comparison behavior from user-defined objects.

Examples that remain in the family include:

* required columns;
* unique keys;
* complete mappings;
* valid header depth;
* duplicate visible tuples;
* forbidden information loss;
* domain-specific ordering constraints.

=== Exit criteria

* the family assumes only the documented trusted input contract;
* hostile-object validation is not repeated locally;
* all remaining validation has a clear family-specific reason;
* complexity is measurably reduced or better localized.

== Family cycle 3: review supported types

=== Goal

Prove that the family behaves correctly for its declared type set and identify
where narrower domain-specific types are required.

=== Review questions

* Which scalar values are accepted in row keys, labels, canonical IDs, and data
  cells?
* Are values converted to strings unintentionally?
* How are `None`, NaN, empty strings, unresolved values, and spreadsheet errors
  handled?
* Do equality, grouping, sorting, and hashing assume homogeneous types?
* Are dates and datetimes preserved or normalized?
* Does pandas coerce values in a way that changes the contract?
* Is special handling required for a supported type?
* Can unsupported types fail early with a useful error?

The objective is not arbitrary-type support. The objective is an explicit
supported set.

=== Exit criteria

* public signatures and documentation state supported values;
* type-specific behavior is tested once at the appropriate domain boundary;
* accidental coercions are removed or documented;
* special cases exist only for supported requirements.

== Family cycle 4: structural refactoring

=== Goal

Make the family locally understandable and navigable by a maintainer.

Apply the
link:../developer_guide/ch06_code_conventions/05_domain_maintainer_contract.adoc[Domain
Maintainer Contract] rather than independently re-deriving package shape,
naming, and readability judgment calls per family.

=== Package shape

Where appropriate, place the family under:

## [source,text]

transformations/<family>/
**init**.py
model.py
validation.py
projection.py
reconstruction.py
composites.py
-------------

These names are examples, not mandatory structure. Files should reflect the
actual concepts of the family.

=== Conventions to establish

* one obvious public entry point;
* an `__init__.py` that exposes the intended API without hiding substantial
  behavior;
* descriptive module and function names;
* no broad `utils.py` dumping ground;
* explicit ownership of models, algorithms, validation, and boundary code;
* minimal import cycles and short navigation paths;
* forward and reverse directions visibly separated where useful;
* private helpers located close to the algorithm they support;
* registry targets pointing to stable public functions.

=== Size guidance

File and function limits should be warning thresholds, not mechanical goals.

A threshold breach should trigger review, not automatic splitting.

A cohesive 300-line algorithm may be easier to maintain than several tiny files
that require constant cross-navigation. Conversely, a large file containing
several responsibilities should be split even if every individual function is
short.

The project should define practical warning thresholds for:

* module length;
* function length;
* cyclomatic complexity;
* public symbols per module;
* dependency fan-out.

Any accepted exception should be documented briefly.

=== Exit criteria

* a maintainer can locate the public API, model, validation, forward path, and
  reverse path quickly;
* file boundaries correspond to responsibilities;
* no structural split exists solely to satisfy line counts;
* architecture and import guards describe the intended package shape.

== Family cycle 5: consolidate tests

=== Goal

Reduce duplication while preserving meaningful behavioral protection.

=== First classify

Classify tests as:

* shared domain contract;
* adapter or boundary contract;
* integration smoke test;
* public registry/configuration test;
* historical regression;
* security/ingress test;
* private implementation-detail test.

Do not remove tests merely because they overlap while structural work is still in
progress.

=== Consolidation model

## [source,text]

shared domain invariant
-> test once centrally

adapter translation
-> test once per adapter

layer connection
-> small end-to-end smoke set

historical bug
-> retain only when it protects a stable public contract

hostile external payload
-> ingress test, not repeated in every family
---------------------------------------------

Avoid test matrices of:

## [source,text]

every domain case
x every file format
x every parser representation
x every writer representation
x every pipeline invocation form
--------------------------------

=== XML and storage-level assertions

Direct XML, archive-content, or storage-representation tests are appropriate when:

* the concrete representation is itself a supported contract;
* security or resource-bounding behavior depends on it;
* the adapter was changed at that level;
* a known regression cannot be detected through the neutral carrier.

They should not be added automatically for every domain feature using the adapter.

=== Exit criteria

* each important invariant has an obvious owning test;
* adapters test only adapter responsibilities plus a bounded integration path;
* redundant hostile-input tests have moved to ingress;
* private implementation snapshots are removed unless they protect a deliberate
  stable representation;
* the focused suite is substantially easier to understand and maintain.

== Family cycle 6: maintainer-readiness review

=== Goal

Determine whether the family can be responsibly maintained without relying on
the implementation history or the original AI context.

=== Maintainer exercise

A reviewer should be able to:

. find the public entry points;
. explain the forward and reverse behavior;
. identify the main carriers and invariants;
. locate the applicable type and ingress assumptions;
. trace one normal execution path;
. find the correct test for a behavior;
. make a small local change;
. identify which documentation and registry entries require updates;
. distinguish domain, adapter, and pipeline responsibilities.

AI assistance may be used for navigation and explanation, but the resulting
mental model must be independently understandable.

=== Review outcome

Possible verdicts:

* maintainer-ready;
* ready with minor documentation or naming fixes;
* not ready due to a bounded structural issue;
* not ready because a missing contract requires a separate FTR.

The review should not reopen accepted behavior without concrete evidence.

=== Exit criteria

* the family is accepted as maintainer-ready;
* any remaining issue is explicit and bounded;
* no required understanding depends exclusively on old review artifacts or chat
  history.
