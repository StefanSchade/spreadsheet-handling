==== Central review question -- is this the smallest coherent extension of Slice 1?

*Finding: yes, for the category-set and carrier-model recommendation itself.*
Every one of the six challenge questions in section 1 of the review task was
independently checked:

* *Is Date semantically distinct from midnight DateTime?* Yes --
  independently reproduced: `datetime.date(2026,8,9) < datetime.datetime(2026,8,9)`
  raises `TypeError` at the Python level; a `date`+`None` DataFrame column
  stays `object` dtype with a plain `None` missing cell, while a
  `datetime`+`None` column is silently promoted by pandas itself to
  `datetime64[us]` with `pandas.NaT` -- the two categories are not
  interchangeable even at the pandas-ergonomics level, not merely the
  conceptual level.
* *Does current maintained data exercise Date? DateTime?* Yes, both,
  independently reproduced: `yaml.safe_load` on an unquoted `2026-08-09`
  scalar produces a real `datetime.date`; on `2026-08-09T10:30:00` produces a
  real `datetime.datetime`; on `2026-08-09T10:30:00+02:00` produces an aware
  `datetime.datetime`. This is PyYAML's own `SafeLoader` resolver, already
  reachable through `yaml_backend.load_yaml_dir`'s unmodified `yaml.safe_load`
  call, not a hypothetical.
* *Would collapsing either direction lose semantics?* Yes, independently
  confirmed both directions are lossy (day-vs-midnight ambiguity one way,
  dropped time-of-day the other), matching the FTR's own section 7/8
  analysis.
* *Does pandas coercion undermine the distinction at carrier level?*
  Partially, and the FTR states this correctly, not overclaiming: a pure
  `date` column stays `object`/`datetime.date` (undisturbed); a `datetime`
  column is promoted to `datetime64`/`Timestamp` (disturbed in carrier shape
  only, not in semantic category -- a promoted `Timestamp` is still
  conceptually DateTime, never reclassified as Date by the FTR's own
  recommendation).

No evidence found to challenge the two-category recommendation itself. The
concerns this review does raise are narrower: two specific claims inside the
FTR's own evidence base, and one slice-sequencing self-consistency question.

==== 1. numpy.datetime64 unit semantics -- independently probed, decision-ready

Ran the task's own representative probes
(`np.datetime64("2026-08-09","D")`, `np.datetime64("2026-08-09T12:34","m")`,
an `"ns"`-unit value) plus one additional probe the FTR itself did not run: a
`Timestamp` known to be a genuine midnight *DateTime* value, cast to `[D]`
unit, compared against a genuine day-only value at the same unit.

Result: `np.datetime64(pd.Timestamp("2026-08-09 00:00:00"), "D") == np.datetime64("2026-08-09", "D")`
is `True` -- the two are *bit-identical* once stored at day precision. Unit
alone cannot distinguish "this was authored as a date" from "this was a
midnight datetime that got truncated/resampled to day granularity," because
no information about intent survives the cast. Separately confirmed: pandas
does not even preserve the unit distinction on ordinary `Series` construction
-- both `datetime64[D]` and `datetime64[m]` source arrays produce a
`datetime64[s]`-dtype `Series` of `Timestamp` scalars in the installed pandas
version, discarding the original unit before any framework code runs.

*Assessment:* this independently reproduces and strengthens, rather than
contradicts, the FTR's own recommendation (section 8, open decision 1 in
section 24) not to infer Date-vs-DateTime from `numpy.datetime64` unit. The
evidence is now stronger than what the FTR itself presented -- the FTR
asserted the unit "is not used" as a matter of policy preference; this review
adds that the unit *could not reliably be used* even if a future slice wanted
to, because day-precision storage is genuinely ambiguous between "authored as
a date" and "datetime truncated to a date." This closes decision-ready
evidence gap 1 in the FTR's own favor: *uniform DateTime classification for
all `numpy.datetime64`, ignoring unit, is the only sound default*; a future
slice would need an out-of-band schema/producer-supplied hint (not carrier
inspection) if day-precision `Date` recognition from raw NumPy is ever
wanted.

==== Findings

===== DTVM-REVIEW-F1 -- section 3's inventory table and section 10 both misstate current `numpy.timedelta64` (non-NaT) classification behavior; it is not currently rejected, it silently misclassifies as `"number"`

*Classification:* Important.

*File/symbol:* FTR section 3 (inventory table, `numpy.timedelta64` (non-`NaT`)
row); FTR section 10 ("`scalar_category` already correctly rejects
`datetime.timedelta`, `pandas.Timedelta`, and non-`NaT` `numpy.timedelta64`
(`UnsupportedScalarError`, confirmed by probe) -- unaffected by this FTR.");
runtime: `src/spreadsheet_handling/core/scalar_values.py:202-208`
(`scalar_category`'s Boolean/Number branches).

*Evidence:* independently reproduced from a fresh process against current
`core` HEAD:

[source,pycon]
----
>>> import numpy as np
>>> from spreadsheet_handling.core.scalar_values import scalar_category
>>> v = np.timedelta64(1, "D")
>>> type(v).__mro__
(<class 'numpy.timedelta64'>, <class 'numpy.signedinteger'>,
 <class 'numpy.integer'>, <class 'numpy.number'>, <class 'numpy.generic'>,
 <class 'object'>)
>>> scalar_category(v)
'number'
----

`numpy.timedelta64` subclasses `numpy.signedinteger`/`numpy.integer` (unlike
`numpy.datetime64`, independently confirmed *not* to subclass `np.integer` or
`np.floating` -- its `__mro__` is only
`(numpy.datetime64, numpy.generic, object)`). `scalar_category`'s Number
branch is `isinstance(value, (int, float, np.integer, np.floating))`
(`scalar_values.py:206`); a non-`NaT` `numpy.timedelta64` satisfies this
before the function ever reaches its trailing `raise UnsupportedScalarError`.
The FTR's own claim that this "already correctly rejects... same path as
`datetime64` above" is false: `datetime64` correctly falls through to the
trailing raise (`np.generic` but not `np.integer`/`np.floating`); `timedelta64`
does not (it *is* `np.integer`), and the two carriers reach materially
different, not "same-path," outcomes. `tests/unit/core/test_scalar_values.py`
independently grepped: contains zero `timedelta64` test cases (neither NaT
nor non-NaT), so nothing in the existing suite would have caught this.

*Why it matters:* this is not a Date/Time-specific defect -- it predates this
FTR and is inherited unchanged from Slice 1 -- but it is exactly the "carrier
silently becoming domain semantics" defect class the entire value-model
program exists to close, and it is currently live in the accepted,
independently-reviewed `scalar_values.py` module today. A `numpy.timedelta64`
value (e.g. the natural result of subtracting two `datetime64` columns, a
completely ordinary pandas operation) reaching `scalar_category` today is
silently accepted as an ordinary `Number` -- its integer nanosecond/day count,
stripped of unit -- rather than rejected as an unsupported Duration carrier.
This directly undermines section 10's own reasoning for deferring Duration
("already correctly rejects... unaffected by this FTR") and weakens section
6's `complex128` analogy: `complex128`'s precedent holds because *every*
`complex128` instance, NaN or not, is uniformly rejected today; `timedelta64`
does not have that property today -- only its `NaT` form is (mis)handled via
Missing; its ordinary form is silently absorbed into Number, a strictly
worse defect (semantic corruption, not merely an inconsistent-Missing
classification) than the one section 6 is built to fix. Per
`ADR-DOMAIN-BOUNDARY-ROBUSTNESS`, this is exactly the class of "cheap,
simplifying, local hardening" the ADR calls desirable -- narrowing the
accepted vocabulary to what the category actually intends, not new defensive
introspection.

*Smallest correction:* (1) correct FTR section 3's inventory-table row and
section 10's claim to state the accurate current behavior (misclassifies as
`"number"`, not rejected); (2) fold the fix into D-T1's own scope -- D-T1
already touches the identical bounded-dispatch mechanism for the NaT case, so
adding an explicit `np.timedelta64` exclusion to (or ordering fix around) the
Number branch is a natural, narrow extension of work D-T1 is already doing,
not a new slice. A minimal fix shape: check for `np.timedelta64` (e.g. via
`isinstance(value, np.timedelta64)`) before the Number branch and route it to
`UnsupportedScalarError` unconditionally (consistent with the FTR's own
Duration-stays-deferred recommendation), mirroring the Boolean-before-Number
subclass-ordering pattern already established in this module.

*Disposition:* non-blocking for accepting this FTR's Date/DateTime category
recommendation (the recommendation does not depend on this claim being
correct). Should be corrected in the FTR text before D-T1 is treated as
implementation-ready, and the underlying runtime misclassification should be
fixed as part of D-T1 (or, if the maintainer prefers not to widen D-T1's
scope, filed as its own narrow BUG referencing this finding) before Phase E
begins relying on `scalar_category`'s Number classification as trustworthy.

===== DTVM-REVIEW-F2 -- D-T2 ("canonical Date/DateTime normalization primitive") contradicts this FTR's own section 12 posture and Slice 1's established Phase-E-owns-normalization precedent, without acknowledging the conflict

*Classification:* Important.

*File/symbol:* FTR section 12 ("Producing an actual canonical value from an
accepted carrier variant remains Phase E's future 'value normalization and
type resolution' stage, per Slice 1's own precedent (IVM-REVIEW-F2's
resolution) -- this FTR does not build that primitive either."); FTR section
20, D-T2 ("Adds the `normalize_scalar()`-shaped primitive Slice 1 and this
FTR both deliberately did not build (section 12) -- narrowing an accepted
carrier variant ... to its native-Python canonical form ... for whichever
future consumer needs one canonical representation rather than mere
classification.").

*Evidence:* `roadmap_domain_hardening_sequence.adoc`'s Phase E boundary shape
explicitly names "value normalization and type resolution" as a Phase E
stage, downstream of Phase D's "establish the internal type model."
`FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A_review.adoc`'s Independent Review 001
answers its own sub-question 4 ("Does Phase E need a normalization primitive
not provided here?") with "Yes," and its resolution of IVM-REVIEW-F2 states
explicitly: "Phase E's 'value normalization and type resolution' boundary
stage still owns adding a normalization primitive on top of these
classifiers." This FTR's own section 12 restates that precedent correctly and
applies it to Date/Time ("this FTR does not build that primitive either").
Section 20's D-T2 then proposes building exactly that primitive -- narrowing
an accepted carrier variant to a canonical native form -- as a *Phase D*
slice, under a `D-T` label, without flagging that this reassigns ownership
away from the precedent section 12 itself just restated two sections earlier
in the same document.

*Why it matters:* the task that produced this FTR explicitly named this a
"major architecture consistency check," and the FTR's own section 24 open
decision 4 asks the maintainer to "confirm... the D-T1..D-T5 slice sequence
and dependency ordering is the right shape" -- but that framing presents the
sequence as needing generic confirmation, not as containing a specific,
already-detectable self-contradiction against the document's own section 12.
A future implementer skimming section 20 in isolation (exactly the failure
mode Independent Review 001 warned about for `ScalarValue`'s
"Native Python representation" framing, IVM-REVIEW-F2) could reasonably
start building a general `normalize_scalar()` primitive inside Phase D,
re-litigating a boundary the project already spent one full review cycle
establishing. D-T3's own text compounds the ambiguity: it lists "a
`normalize_scalar()` call from D-T2" as one option for closing the YAML
write-side gap, treating D-T2's primitive as available Phase-D-internal
infrastructure rather than flagging that its existence there is itself the
open question.

*Smallest correction:* either (a) reframe D-T2 narrowly -- scope it to only
the local `Timestamp`/`numpy.datetime64` -> native-`date`/`datetime`
coercion D-T3's persistence fix concretely needs (a bounded, D-T3-owned
helper, not a general-purpose Phase-E-shaped `normalize_scalar()` contract),
and rename it to make that scope explicit; or (b) if the maintainer decides
Phase D should own the general primitive after all (a legitimate choice --
building it once, early, and having Phase E reuse it is defensible), state
that decision explicitly as an amendment to Slice 1's established boundary,
with its own rationale, rather than silently proposing it under a `D-T`
label two sections after restating the opposite precedent. Either
correction is a documentation-only change to this FTR; no runtime work is
implied by making the correction itself.

*Disposition:* non-blocking for accepting this FTR's Date/DateTime category
recommendation or D-T1. Must be resolved before D-T2 is treated as
implementation-ready; D-T1 does not depend on D-T2 and may proceed once
DTVM-REVIEW-F1 is addressed, independent of this finding's resolution.

*Evidence:* this review independently confirmed XLSX/ODS date cells carry no

  Genuinely open; both this review's and the FTR's own evidence support
  leaving it open rather than forcing a premature choice. *Recommended
  choice:* none forced by evidence; the FTR's own refusal to choose is
  correct. *Must decide before implementation:* yes, before D-T2 (the
  slice whose own acceptance criteria the FTR assigns this resolution to).
  *Owning slice:* D-T2 (contingent on DTVM-REVIEW-F2's resolution of what
  D-T2 actually is).
. *XLSX/ODS egress parity direction.* Genuinely open; three legitimate
  options with no forcing evidence, correctly not decided here.
  *Recommended choice:* none forced by evidence. *Must decide before

==== 2. JSON Missing/NaT -- new finding, independently discovered: a silent-corruption path, not merely a missing-symmetry gap

Section 27.9 states the JSON encoder dispatches "only on `isinstance(value,
datetime.datetime)` (covers `Timestamp`, checked first, same
subclass-ordering discipline D-T1 already established)". Independently
checked whether `pd.NaT` satisfies that `isinstance` check:

[source,pycon]
----
>>> import datetime, pandas as pd
>>> isinstance(pd.NaT, datetime.datetime)
True
>>> isinstance(pd.NaT, datetime.date)
True
>>> pd.NaT.isoformat()
'NaT'
>>> datetime.datetime.fromisoformat(pd.NaT.isoformat())
Traceback (most recent call last):
    ...
ValueError: Invalid isoformat string: 'NaT'
----

`pandas.NaTType` subclasses `datetime.datetime` (a deliberate pandas
compatibility shim). The design's own encoder dispatch order -- DateTime
checked first, exactly mirroring D-T1's DateTime-before-Date subclass
discipline -- means `NaT` matches the DateTime branch *before* it could ever
fall through to a rejection. Independently exercised the encoder exactly as
section 27.5/27.9 specify it:

[source,pycon]
----
>>> def _json_temporal_default(value):
...     if isinstance(value, datetime.datetime):
...         return {"$datetime": value.isoformat()}
...     if isinstance(value, datetime.date):
...         return {"$date": value.isoformat()}
...     raise TypeError(...)
...
>>> df = pd.DataFrame({"t": [pd.Timestamp("2026-08-09 10:30:00"), pd.NaT,
...                           pd.Timestamp("2026-08-10 11:00:00")]})
>>> json.dumps(df.to_dict(orient="records"), default=_json_temporal_default)
'[{"t": {"$datetime": "2026-08-09T10:30:00"}}, {"t": {"$datetime": "NaT"}}, {"t": {"$datetime": "2026-08-10T11:00:00"}}]'
----

No exception is raised. The write *succeeds*, silently, and produces
`{"$datetime": "NaT"}` for what should be an ordinary empty/missing cell
(every other column's Missing convention in this codebase is `""`, per
section 27.4's own table). This is strictly worse than YAML's failure mode
(a loud crash): it is a silent, non-round-trippable, malformed envelope
written to disk with zero test coverage catching it (section 27.13's own
proposed test matrix, independently re-read, does not include a
Missing-carrier case for either backend -- see `DT2-DESIGN-REVIEW-F6`). If
that file is ever read back through the standalone decode function (Option
A, or an adopter using the codec directly), `date.fromisoformat`/
`datetime.fromisoformat` on the literal string `"NaT"` raises a bare
`ValueError: Invalid isoformat string: 'NaT'` -- not the "explicit,
persistence-local decode error" section 27.12's own decode-rules row
promises for a malformed envelope value; it is an *unhandled* stdlib error
surfacing through a code path the design never considered a failure point
because the design believed Missing "bypasses the codec entirely."

This is exactly the "carrier silently becoming domain semantics" defect
class `DTVM-REVIEW-F1` (Independent Architecture Review 001, this same
review file) already flagged once for this FTR's own `numpy.timedelta64`
handling, and exactly the subclass-ordering hazard this FTR's own accepted
discipline (Boolean-before-Number, DateTime-before-Date) exists to catch --
section 27 applied that discipline to Date-vs-DateTime but not to
Missing-vs-DateTime for `NaT` specifically, even though `is_missing_carrier`
(the accepted D-T1 runtime, independently re-read,
`core/scalar_values.py`) already recognizes `pd.NaT` as Missing by identity,
*before* any DateTime dispatch -- the JSON encoder's proposed dispatch order
does not mirror that already-accepted precedence.

==== 5. Timezone fidelity -- review hypothesis 3 independently CONFIRMED: offset and named-zone identity are conflated in the design's wording

Independently probed all three named cases through the proposed
`.isoformat()` / `datetime.fromisoformat()` shape:

[cols="2,3,3",options="header"]
|===
| Input | `.isoformat()` | Decoded `tzinfo`

| naive `datetime.datetime`
| `2026-08-09T10:30:00`
| `None` (naive, correctly reconstructed)

| `datetime.datetime(..., tzinfo=timezone(timedelta(hours=2)))`
| `2026-08-09T10:30:00+02:00`
| `datetime.timezone(timedelta(seconds=7200))` -- exact offset match

| `pandas.Timestamp(..., tz="+02:00")`
| `2026-08-09T10:30:00+02:00`
| `datetime.timezone(timedelta(seconds=7200))` -- exact offset match

| `pandas.Timestamp(..., tz=ZoneInfo("Europe/Berlin"))`
| `2026-08-09T10:30:00+02:00`
| `datetime.timezone(timedelta(seconds=7200))` -- **a bare fixed-offset
  `datetime.timezone`, not a re-hydrated `ZoneInfo("Europe/Berlin")`**
|===

Awareness (naive vs. aware) and the numeric UTC offset *are* preserved
exactly, independently confirmed in all four cases. Named-zone *identity*
(the IANA key, DST transition rules, historical-offset-change awareness) is
*not* preserved and cannot be, by construction: `.isoformat()` on an aware
value emits only a numeric offset, never a zone key, and
`datetime.fromisoformat()` can only ever reconstruct a fixed-offset
`datetime.timezone`. A `Europe/Berlin` timestamp written in winter and one
written in summer would decode to two different, but equally
zone-identity-less, fixed offsets -- indistinguishable on decode from a
`Timestamp` that was always merely `+01:00`/`+02:00`-tagged.

The design's literal wording (section 27.4: *"Timezone/offset ... Yes,
exactly as authored -- aware stays aware with its original offset"*;
section 27.12: *"timezone/offset (exactly as authored, no UTC assumption)"*)
does not, read literally, claim named-zone identity preservation -- it says
"offset" specifically both times. But the *property* column header in both
places is the compound "Timezone/offset", and neither location states the
named-zone-identity loss as its own explicit, separate line -- exactly the
three-way distinction (awareness / offset value / named-zone identity) the
task asked this review to keep separate. A reader relying on the "Timezone
... preserved ... exactly as authored" phrasing without reading the word
"offset" precisely enough would reasonably, if incorrectly, expect
DST-safe/zone-identity-safe round-tripping. This is a real, if narrower than
the worst-case reading, wording gap -- confirmed, not invented.

==== 6. Precision guarantee -- review hypothesis 4 not confirmed as literally stated; independent investigation surfaces a related, more concrete JSON-specific gap instead

Section 27.4's "pre-existing, not introduced" framing is backend-neutral in
its own text (*"inherited, unchanged, from YAML's own format ceiling and
from what `to_dict(orient="records")` already hands the writer"*) -- it does
not, read literally, claim JSON already had a working, lossy roundtrip
before D-T2. Independently re-derived: YAML's own native timestamp scalar
genuinely has no sub-microsecond form (unaffected by D-T2 either way), so
the "pre-existing ceiling" framing holds for YAML. Review hypothesis 4, as
literally stated, is *not confirmed* -- the wording does not overstate a
JSON-specific pre-existing loss it never claims.

However, independent investigation surfaced a concrete, JSON-specific defect
the design does not address at all: section 27.6 explicitly requires
`.as_unit("us")` *before* `.to_pydatetime()` for YAML, but section 27.5/27.9
never apply an equivalent truncation step to the JSON encoder, which calls
`.isoformat()` directly on the raw `Timestamp`/`datetime.datetime` value.
`pandas.Timestamp.isoformat()` is a pandas override that emits up to *nine*
fractional-second digits (nanosecond precision), unlike
`datetime.datetime.isoformat()`, which emits at most six:

[source,pycon]
----
>>> ts = pd.Timestamp("2026-08-09 10:30:00.123456789")
>>> ts.isoformat()
'2026-08-09T10:30:00.123456789'
>>> datetime.datetime.fromisoformat(ts.isoformat())
datetime.datetime(2026, 8, 9, 10, 30, 0, 123456)   # silently drops the extra 3 digits, on Python 3.13
----

On this review's own Python (3.13), `datetime.fromisoformat()` silently
truncates the extra digits with no error, so decode still lands at
microsecond precision -- round-trip *correctness* is not broken on this
interpreter. But this repository's own `pyproject.toml` states
`requires-python = ">=3.10"`, and CPython's `datetime.fromisoformat()` was
documented to accept only the exact formats `date.isoformat()`/
`datetime.isoformat()` themselves produce (0, 3, or 6 fractional digits)
*before* Python 3.11 ("Changed in version 3.11: Previously, this method only
supported formats that could be emitted by `date.isoformat()` or
`datetime.isoformat()`.") -- a 9-digit fractional string is not one of
those. *This specific claim was not independently executed here* (only
Python 3.13 is available in this environment; no 3.10/3.11 interpreter was
reachable) and should be confirmed against a real 3.10 interpreter or this
repository's CI matrix before being treated as certain -- but if accurate,
a nanosecond-precision `Timestamp` written by the proposed JSON encoder
would produce a wire value that fails to decode with `ValueError` on the
minimum Python version this package declares support for, even though it
round-trips cleanly in this review's own environment. Independent of that
version question, the wire-format inconsistency is certain either way: JSON
would write a misleadingly precise-looking (nanosecond) string that YAML's
sibling helper deliberately never would, contradicting the design's own
implied uniform "truncated to microseconds" guarantee.

*Recommended contract wording:* state the precision guarantee per backend,
not jointly -- "YAML and JSON both guarantee microsecond precision; nothing
in this contract requires or preserves sub-microsecond input" -- and apply
the identical `.as_unit("us")`-style truncation in the JSON encoder that
27.6 already mandates for YAML, both for wire-format consistency and to
remove the version-dependent decode risk.

==== 7. JSON envelope collision and evolvability -- adequately handled, no correction required

Independently evaluated the `{"$date": ...}`/`{"$datetime": ...}` shape
against the four concrete risks the task named:

* *Collision with a legitimate nested payload.* Section 27.5 already names
  this explicitly as an accepted, bounded limitation (a MultiIndex-nested
  object whose *only* field is literally `$date`/`$datetime`), not silently
  risked. Independently re-confirmed no such column name exists anywhere in
  the current test/fixture corpus (grepped `tests/` and `docs/` for
  `$date`/`$datetime` as column-name literals -- none found).
* *`_records_nested_from_multiindex` behavior.* Independently re-read
  (`json_backend.py:41-66`) -- it builds nested dicts from MultiIndex column
  segments; a single-key `{"$date": ...}` result is only reachable if a
  MultiIndex path itself is named exactly `$date`, the same accepted
  limitation as above, not a new one.
* *Future bounded composite values (`List[Scalar]`).* No current design
  decision this FTR or `FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A` has made
  requires a single-key reserved envelope at the top level of a list
  element; nothing here forecloses a future composite-value wire shape.
* *Evolvability.* A two-tag scheme (`$date`, `$datetime`) rather than one
  shared `$type`-discriminated envelope was independently judged the more
  defensible choice given section 27.5's own cited reason (Date/DateTime are
  already two distinct top-level categories, not one shared "Temporal"
  category with a `kind` sub-field) -- adding a third scalar category later
  (e.g. Time) would add a third reserved key, not restructure the existing
  two, which is a reasonable evolution path.

*Conclusion:* the simple reserved single-key envelope is sufficient,
*provided* its reserved nature is written into the JSON backend's own public
contract/documentation once implemented (the task's own stated condition
for acceptance) -- not merely into this design document. Recommend this be
an explicit acceptance-criterion line item for whichever slice implements
D-T2.2, not a new finding of its own.

===== DT2-DESIGN-REVIEW-F1 -- section 27.4/27.6/27.9's Missing/NaT handling is factually wrong for the DateTime category; the proposed fix does not close D-T2's own headline motivating scenario when a temporal column contains any missing value

*Classification:* Blocking.

*File/symbol:* FTR section 27.4 (Missing row: *"already rewritten to `""`
... in both backends, before any record reaches the writer"*); section 27.6
(`_yaml_safe_temporal`, `isinstance(value, pd.Timestamp)`-only dispatch);
section 27.9 (`_json_temporal_default`, `isinstance(value,
datetime.datetime)`-first dispatch); runtime:
`src/spreadsheet_handling/io_backends/yaml_backend.py:60` (`load_yaml_dir`'s
`df.where`, read-side only, confirmed no equivalent call exists in
`save_yaml_dir`), `src/spreadsheet_handling/io_backends/json_backend.py:131`
(`write_multi`'s `df.where`, confirmed a no-op on a `datetime64`-dtype
column in this repository's pinned pandas `3.0.2`).

*Evidence:* independently reproduced in this review's sections 1 and 2
above, three ways for YAML (raw `df.where` no-op; the proposed helper
applied directly, still crashes on `NaT`; and the realistic
load-then-save-unmodified round trip, still crashes) and one way for JSON
(the proposed encoder applied directly, silently emits
`{"$datetime": "NaT"}` with no error).

*Impact:* D-T2's own section 14 motivating scenario -- "read a full-timestamp
YAML file, do nothing else, write it back" -- remains broken after the
proposed fix ships, for any file containing a missing temporal cell, which
is entirely ordinary given D-T1's own accepted vocabulary treats Missing and
DateTime as simultaneously applicable per-cell classifications. For JSON,
the defect is worse in kind, not merely degree: it is a silent
data-corruption path (a Missing cell becomes the non-round-trippable string
`{"$datetime": "NaT"}` instead of the codebase's own established `""`
convention), with zero test coverage in the design's own proposed test
matrix (section 27.13) that would catch it.

*Smallest correction:* in both helpers, add an explicit missing-value check
*before* the `Timestamp`/`datetime.datetime` dispatch, mirroring the
already-accepted precedence `is_missing_carrier` itself uses
(`core/scalar_values.py`: Missing is recognized before any semantic-category
dispatch). Concretely: `if isinstance(value, pd.Timestamp) and
value is not pd.NaT: ...` (or an equivalent `pd.isna`-guarded branch) for
YAML, returning `""` (or leaving the value for a corrected write-side
`df.where`/`fillna` step that actually works on a `datetime64`-dtype
column -- e.g. converting the column to `object` dtype before the fill, or
using `Series.mask`/`fillna` rather than `where` against an
incompatible-dtype scalar) so the eventual `None`/`""` reaches
`yaml.safe_dump` the same way Date's own Missing carrier already does; and
for JSON, check `pd.isna(value)` (or `value is pd.NaT`) *before* the
`isinstance(value, datetime.datetime)` branch in `_json_temporal_default`,
so `NaT` never reaches `.isoformat()`. Extend section 27.13's test matrix
with an explicit "Timestamp column containing one missing entry" case for
both backends (currently absent -- see `DT2-DESIGN-REVIEW-F6`).

*Blocks D-T2 implementation authorization:* yes. This is a correctness gap
in the design's `[DECIDED]`-tagged sections, not the one section the design
itself already marks `[OPEN]` for reviewer confirmation (27.11); it must be
corrected in the design document itself before implementation, not
discovered mid-implementation.

*Classification:* Important.

*File/symbol:* FTR section 27's opening paragraph (*"the smallest explicit
persistence contract that lets the accepted Date/DateTime categories ...
survive `save_yaml_dir`/`load_yaml_dir` and the JSON directory backend
without inventing general normalization"*); contrast with section 27.12's
own more precise summary-table row (*"json_dir read (unchanged at the

*Evidence:* independently reproduced in this review's section 3 above --
`write_json_dir` then `read_json_dir` does not recover a Date/DateTime
value; only the standalone codec pair, exercised directly (bypassing the
maintained backend entirely), round-trips.

*Impact:* a reader who stops at the opening framing (or a future changelog/
release-note author who cites it) would reasonably expect a working
`write_json_dir` -> `read_json_dir` round trip for JSON, which Option B
deliberately does not provide. This is a documentation-precision defect, not
a technical one -- Option B's underlying technical recommendation is sound
(see the Central contract question section above and finding disposition
below), but the framing that introduces it is not internally consistent
with the recommendation it leads to.

*Smallest correction:* reword the opening paragraph to state the two
guarantees separately and explicitly: YAML gets a full backend-level
(`save_yaml_dir` -> `load_yaml_dir`) roundtrip; JSON gets a working
`write_json_dir` (closing the current `TypeError` crash) plus a
codec-level-only encode/decode pair, with `read_json_dir` deliberately
unchanged. Apply the same precision to any future release note or Project
Memory entry describing D-T2.

*Blocks D-T2 implementation authorization:* no, on its own -- this is a
wording correction, not a design change. Should be corrected in the same
pass that resolves `DT2-DESIGN-REVIEW-F1`.

===== DT2-DESIGN-REVIEW-F3 -- the proposed JSON encoder omits the microsecond-truncation step YAML's own helper requires, producing an inconsistent wire representation and a plausible (not independently executed) Python-3.10 decode failure

*Classification:* Important.

*File/symbol:* FTR section 27.5 (*"`{"$datetime":
"<datetime.datetime.isoformat() string>"}`"*); section 27.6 (YAML's own
`.as_unit("us")` requirement, with no equivalent stated for JSON); section
27.9 (`_json_temporal_default`, calls `.isoformat()` directly with no
truncation step).

*Evidence:* independently reproduced in this review's section 6 above --
`pandas.Timestamp.isoformat()` (invoked polymorphically when the encoder's
`isinstance(value, datetime.datetime)` branch matches a `Timestamp`
specifically) emits up to nine fractional-second digits for a
nanosecond-precision value, unlike `datetime.datetime.isoformat()`'s maximum
of six; `datetime.fromisoformat()` silently truncates the extra digits on
this review's Python 3.13. The claim that a 9-digit fractional string fails
to parse under Python's pre-3.11 `fromisoformat()` (relevant because this
package's own `pyproject.toml` declares `requires-python = ">=3.10"`) is
based on documented CPython behavior, *not independently executed in this
review* -- no 3.10/3.11 interpreter was available in this environment. Flag
for confirmation against a real 3.10 interpreter or this repository's CI
matrix before treating it as certain.

*Impact:* at minimum, a documented wire-format inconsistency (JSON silently
carries more apparent precision than YAML's sibling format, contradicting
the design's own implied uniform "truncated to microseconds" guarantee, section
27.4). At worst (pending the version confirmation above), a version-dependent
decode failure for sub-microsecond-precision input on the minimum Python
version this package declares support for, even though it round-trips
cleanly on newer interpreters -- exactly the kind of latent, environment-
dependent defect that would surface only in a downstream adopter's CI, not
this review's own.

*Smallest correction:* apply the identical `.as_unit("us")`-style truncation
in `_json_temporal_default` that section 27.6 already mandates for
`_yaml_safe_temporal`, before calling `.isoformat()`. This removes both the
wire-format inconsistency and the version-dependent decode risk in one
change, and keeps the two helpers' precision behavior symmetric as the
design's own prose already implies they should be.

*Blocks D-T2 implementation authorization:* no, on its own -- straightforward
to fold into the same helper-shape correction as `DT2-DESIGN-REVIEW-F1`.
Should be resolved in the same pass, and the version claim above should be
confirmed (or the truncation applied regardless, which moots the version
question entirely) before implementation.

===== DT2-DESIGN-REVIEW-F4 -- "timezone/offset ... preserved exactly as authored" does not separately state that named-zone identity is lost

*Classification:* Important.

*File/symbol:* FTR section 27.4 (Roundtrip semantics table, "Timezone/offset"
row); section 27.12 (Preservation guarantees row, same compound phrasing).

*Evidence:* independently reproduced in this review's section 5 above -- a
`ZoneInfo("Europe/Berlin")`-tagged `Timestamp` survives `.isoformat()` /
`datetime.fromisoformat()` with its exact numeric offset intact, but decodes
to a bare fixed-offset `datetime.timezone`, never a re-hydrated
`ZoneInfo`-backed named zone. Awareness and offset value are independently
confirmed exact; named-zone/DST-rule identity is independently confirmed
lost, in every case probed.

*Impact:* the literal wording ("offset") is not technically false, but the
compound "Timezone/offset" property label and the absence of an explicit
named-zone-identity line invite a reasonable misreading -- an adopter
storing `Europe/Berlin`-zoned timestamps could believe D-T2 preserves that
zone identity across a save/load cycle when it does not; two timestamps
authored in different DST periods would decode to different, but equally
zone-identity-less, fixed offsets, which is a real, foreseeable point of
confusion for a wall-clock/DST-sensitive consumer.

*Smallest correction:* split the "Timezone/offset" row/label into three
explicit, separately-stated guarantees in both section 27.4 and 27.12:
awareness (naive vs. aware) preserved; numeric UTC offset preserved exactly
as authored; named-zone/IANA-identity *not* preserved -- decode always
yields a fixed-offset `datetime.timezone`, never a `ZoneInfo`-backed zone,
regardless of what tzinfo the original value carried.

*Blocks D-T2 implementation authorization:* no -- wording-only correction,
does not require a design or runtime change (the design correctly never
proposed preserving named-zone identity; it only failed to say so
explicitly). Should be corrected in the same pass as the other findings.

==== Conclusion

Section 27's central architecture is sound and independently reproduced:
YAML needs exactly one narrow, non-global-state-mutating write-side carrier
conversion; JSON needs a narrow, tagged-envelope wire format and a symmetric
encode/decode pair; neither helper is shaped as, or reachable as, a general
`normalize_scalar()`-style primitive, and neither wires into Trusted
Ingress. The recommended read-side posture for JSON (Option B) is
independently re-derived, not merely accepted on the design's word, and
remains this review's own recommendation, strengthened by independent
evidence the design itself did not cite (`test_json_read_preserves_iso_date_strings`'s
pinned no-type-guessing contract).

backends, for exactly the ordinary case D-T2's own section 14 motivation
scenario depends on: a temporal column containing any missing value.
`DT2-DESIGN-REVIEW-F1` is Blocking -- the proposed fix must be corrected (an
explicit missing-value check ahead of the `Timestamp`/`datetime.datetime`
dispatch, in both helpers) before D-T2 is authorized for implementation.

precision-truncation symmetry, `-F4` timezone/offset-vs-identity wording)
and two Minor findings (`-F5` decode-error-class resolution, `-F6`
test-matrix completeness) should be corrected in the same pass; none of
them independently blocks authorization, but `-F2` through `-F4` should not
be deferred past this correction round given they are wording-only and
cheap to fix now.

==== 8. JSON decoder -- independently probed at the codec level
