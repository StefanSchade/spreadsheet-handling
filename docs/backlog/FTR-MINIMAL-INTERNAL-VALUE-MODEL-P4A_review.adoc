==== Primary architecture question -- what is the internal value space?

This is the central question this review was asked to resolve without taking
the implementation report's framing on faith.

*Finding:* Model C is the accurate description -- `scalar_category` is a
classifier that tells a future Phase E boundary what a value looks like; it
is not yet the actual internal value boundary -- but the module's own naming
occasionally speaks in Model-A language ("Minimal Internal Value Model",
`ScalarValue` documented as "Native Python representation") that Slice 1 does
not actually deliver.

Evidence for Model C:

* `scalar_category`/`is_supported_scalar`'s own docstrings are explicit and
  correct about their own limits: "Pure classification, not conversion...
  unexamined in content and unchanged in identity"; "it classifies, it does
  not enforce."
* D3's own acceptance criterion (FTR section 12) scopes itself to "type
  aliases and docstrings... not new runtime classes."
* The accepted Trusted Ingress concept's own category table (`tirs-value-model`,
  section 7) already distinguishes category 3 ("pandas/NumPy carrier value in
  structured/programmatic Frames") from category 4 ("Canonical domain
  scalar... No framework-wide instance exists today"). Slice 1 classifies
  over category 3's existing, unnormalized shape; it does not create
  category 4.
* Roadmap Phase D's "Required distinctions" separately names "externally
  parsed raw values" and "normalized scalar cell values" as two required
  categories. Slice 1 delivers a classification vocabulary over the raw/
  carrier space; it does not deliver a "normalized scalar cell values"
  primitive.

Evidence of Model-A-flavored overclaim in the naming layer:

* `ScalarValue: TypeAlias = str | bool | int | float | None` is documented as
  "Native Python representation of the MVP internal scalar vocabulary." But
  `scalar_category` accepts and successfully classifies `numpy.int64`,
  `numpy.bool_`, and `numpy.float32` as `"number"`/`"boolean"` without
  narrowing them to that union -- independently verified none of the three
  subclass their Python equivalents (only `numpy.float64`/`numpy.str_` do).
  A value classified as `"number"` is therefore not guaranteed to actually
  *be* a `ScalarValue` member.
* No runtime type-checking violation results today, because `scalar_category`
  returns only a category label, never a re-typed value -- so nothing
  currently declares a variable `ScalarValue`-typed after classification.
  This keeps the gap a documentation/naming precision issue rather than a
  central contract defect, but it will mislead the first Phase E author who
  reads `ScalarValue` as "what actually flows through the system after
  classification."

See finding IVM-REVIEW-F2 below for the concrete correction recommended.

Answers to the six sub-questions this review was asked to resolve explicitly:

. *Canonical internal representation after Slice 1:* none is established
  yet. What exists is a semantic-category vocabulary (`ScalarCategory`) plus
  a recognition predicate (`is_missing_carrier`), layered over the
  pre-existing, unnormalized carrier space.
. *Are NumPy scalars valid internal values, or only accepted ingress
  carriers?* They classify successfully (functionally "accepted"), but
  nothing normalizes them into `ScalarValue`'s declared native types -- they
  remain accepted-but-unnormalized carriers.
. *Is `ScalarValue` consistent with accepting NumPy scalars?* Not strictly --
  a documentation/naming precision gap, not a runtime contract violation,
  because nothing currently enforces the alias as an actual type boundary.
. *Does Phase E need a normalization primitive not provided here?* Yes.
. *Is a missing `normalize_scalar()` a defect, deferral, or unnecessary?* A
  reasonable, legitimate deferral -- D3's own acceptance bullet never
  promised one, and Phase E's own "value normalization and type resolution"
  boundary stage is explicitly where it belongs -- but it should be named as
  required future work more clearly than section 17.9 currently does.
. *Can Phase E use this API without redesigning it?* Yes for the
  classification/recognition primitives as far as they go; Phase E will
  still need to add its own normalization step on top of them, which is not
  a redesign of what exists, only an addition.

===== IVM-REVIEW-F1 -- `is_missing_carrier`/`is_supported_scalar` overclaim safety against the NumPy array-conversion protocol

*Classification:* Important.

*File/symbol:* `src/spreadsheet_handling/core/scalar_values.py:102-124`
(`is_missing_carrier`), `:160-171` (`is_supported_scalar`).

*Evidence:* `is_missing_carrier`'s docstring states that `pandas.isna` on a
"non-scalar or otherwise incompatible object raises `TypeError`/`ValueError`,
which is caught." `is_supported_scalar`'s docstring states "Never raises."
Independently verified both claims are falsifiable: `pandas.isna()` invokes
`value.__array__()` for any object implementing NumPy's documented
array-conversion protocol (confirmed with a probe object printing from
inside `__array__`). An object whose `__array__` raises anything other than
`TypeError`/`ValueError` -- plausible for a real, non-hostile array-like
object, e.g. a domain-specific conversion-failure exception -- propagates
*uncaught* through `is_missing_carrier`, `scalar_category`, and
`is_supported_scalar`. Confirmed by direct probe:

[source,python]
----
class WeirdArrayLike:
    class ConversionError(Exception):
        pass
    def __array__(self, dtype=None):
        raise self.ConversionError("cannot convert to array right now")

is_supported_scalar(WeirdArrayLike())
# raises WeirdArrayLike.ConversionError -- not False, contradicting the
# function's own "Never raises" docstring
----

*Why it matters:* `__array__` is a *documented* NumPy protocol, so hardening
against its ordinary failure modes is exactly the "cheap, simplifying, local
hardening... reasonably implied by documented pandas, NumPy... contracts"
`ADR-DOMAIN-BOUNDARY-ROBUSTNESS` calls desirable -- this is not "arbitrary
hostile executable Python" the ADR explicitly excludes from scope. No current
call site is wired to this module, so today's blast radius is zero. FTR
section 17.9 lists these three functions as primitives "Phase E can now call
without redesigning them," implicitly relying on the safety claims in their
docstrings; a Phase E ingress boundary trusting "never raises" to safely
probe an unknown value would crash on such an object instead of cleanly
rejecting it with `UnsupportedScalarError`.

*Smallest correction:* either widen the `except` clause in
`is_missing_carrier` to also bound array-conversion failures (the function
is six lines and single-purpose, so this is not the "over-broad defensive
introspection" `ADR-DOMAIN-BOUNDARY-ROBUSTNESS` warns against), or narrow the
docstring claims to the guarantee actually delivered.

*Disposition:* non-blocking for Slice 1 as committed (nothing calls this
module yet). Should be fixed before Phase E wiring begins.

*Resolution (2026-08-09, follow-up commit
`fix(FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A): resolve scalar review
findings`):* **Resolved.** `is_missing_carrier` now bounds `pandas.isna`
dispatch to values already known to be one of the accepted scalar-carrier
shapes (`int`, `float`, `numpy.generic`); `pandas.NA`/`pandas.NaT` are
recognized by identity instead. Any other object -- including one
implementing NumPy's `__array__` protocol -- is recognized as "not missing"
directly, without `pandas.isna` (and therefore `__array__`) ever being
invoked on it. This is the narrower, bounded correction this finding's own
"smallest correction" language preferred over a mechanical `except
Exception` widening. Verified with three new regression tests using an
object whose `__array__` raises a custom, non-`(TypeError, ValueError)`
exception and asserting `__array__` is never called:
`test_is_missing_carrier_never_invokes_array_protocol_on_unrecognized_object`,
`test_is_supported_scalar_never_propagates_array_conversion_exception`,
`test_scalar_category_rejects_array_like_bomb_with_unsupported_scalar_error`
(`tests/unit/core/test_scalar_values.py`, now 59 tests, all passing). The
docstrings of `is_missing_carrier`, `is_supported_scalar`, and the module's
Missing bullet were corrected to state the bounded-dispatch guarantee
precisely instead of the previous overclaim. The accepted Missing carrier
set is unchanged; the only observable behavior change is that a Python
`complex` NaN -- never part of the accepted vocabulary -- is no longer
misclassified as `"missing"` and instead receives the same
`UnsupportedScalarError` every other `complex` value already received (a
narrowing, not an expansion, of Missing semantics). See FTR section 17.11.

===== IVM-REVIEW-F2 -- `ScalarValue`'s "Native Python representation" framing is narrower than what `scalar_category` actually accepts

*Classification:* Important -- documentation/naming precision, not a runtime
defect.

*File/symbol:* `src/spreadsheet_handling/core/scalar_values.py:69-77`
(`ScalarValue`), `:127-157` (`scalar_category`).

*Evidence:* see "Primary architecture question" above for the full
derivation. In short: `ScalarValue = str | bool | int | float | None`,
documented as "Native Python representation of the MVP internal scalar
vocabulary," but `scalar_category` classifies `numpy.int64`, `numpy.bool_`,
and `numpy.float32` into `"number"`/`"boolean"` without narrowing them to
that union, and no `normalize_scalar()`-shaped primitive exists anywhere in
the module to close the gap.

*Why it matters:* the Trusted Ingress concept's own category table already
distinguishes "pandas/NumPy carrier value" (category 3) from "canonical
domain scalar" (category 4, "no framework-wide instance exists today").
`ScalarValue`'s docstring implicitly claims to be category 4; it is
actually documenting category 3's classification target, not a normalized
category-4 representation. A future Phase E author reading `ScalarValue` in
isolation would reasonably but incorrectly assume it is what flows through
the system after classification.

*Smallest correction:* tighten `ScalarValue`'s docstring to state plainly
that `scalar_category`'s accepted domain is a strict superset of
`ScalarValue` (NumPy scalar carrier variants included), and that no
`normalize_scalar()`-style primitive currently narrows an accepted value
down to `ScalarValue`'s literal members -- naming this explicitly as what
Phase E's "value normalization and type resolution" boundary stage still
needs to add. Section 17.9's Phase-E handoff map should say so explicitly
rather than listing the three functions as reusable primitives without this
caveat.

*Disposition:* non-blocking. No test failure or runtime defect results;
correct before Phase E authors start relying on the alias's literal wording.

*Resolution (2026-08-09, follow-up commit
`docs(FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A): resolve review follow-ups`):*
**Resolved.** No `normalize_scalar()` primitive was added -- this finding's
own text explicitly accepted its absence as a legitimate Phase-E deferral,
not a defect, and the follow-up does not second-guess that. `ScalarValue`'s
docstring was rewritten to state explicitly: `ScalarCategory` is the actual
Slice-1 semantic vocabulary; `scalar_category` classifies carrier values
into it, including NumPy scalar variants, without narrowing them to a
`ScalarValue` member; `ScalarValue` names only the candidate native-Python
value shape, not the complete accepted carrier domain and not a canonical
normalized representation; Slice 1 does not establish one; and Phase E's
"value normalization and type resolution" boundary stage still owns adding
a normalization primitive on top of these classifiers. The alias was not
renamed, per this finding's own "prefer documentation precision over
renaming APIs unless the name itself is materially misleading" guidance --
no such evidence was found. FTR section 17.9's Phase-E handoff map gained an
explicit "Normalization primitive Phase E still owns" block restating the
same gap in handoff-facing language. See FTR section 17.11.
