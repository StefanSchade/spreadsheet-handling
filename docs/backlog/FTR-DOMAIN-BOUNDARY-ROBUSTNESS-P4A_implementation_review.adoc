== Artifact ownership (as built)

* *Rationale / decision* -- the ADR. Owns the central threat-model statement,
  the three balancing qualifications, the four rejected alternatives, non-goals,
  and the relationship to existing ADRs. It explicitly defers operational rules
  to the concept.
* *Normative rules* -- the Technical Model concept. Owns the four boundary
  levels, the normative principles, ownership/normalization/diagnostics/
  atomicity/semantic-DRY handling, the responsibility guardrail, and review
  classification.
* *Implementation examples* -- the Developer Guide catalogue. Owns the six
  patterns, each with Intent / Use when / Do not use when / Minimal example /
  Review questions / Search terms.
* *Reviewer guidance* -- the appended `review_instructions.adoc` section. Owns
  the operational reviewer rule and points back to the ADR and concept.

== Placement decisions (open questions resolved)

. *ADR versus concept split:* kept *separate*, as recommended. The ADR carries
  rationale; the concept carries operational rules. The threat-model sentence is
  stated once in each with different framing (decision vs normative rule) and the
  balancing qualifications are not copied verbatim between them.
. *Developer Guide placement:* kept in `ch06_code_conventions` as
  `02_domain_boundary_patterns.adoc`, included from the existing chapter. No new
  top-level chapter was created.
. *Functional Model promotion:* *deferred.* Only the stable framework/
  workflow-builder responsibility split was promoted (into the ADR and concept);
  level-3 external-artifact trust, metadata authority, and entity lifecycle
  remain with the cold-storage inquiry and their own modeling work, and are
  cross-linked rather than restated.

== Reconciliation with the cold-storage inquiry

`app_boundary_meta_authority.adoc` was treated as human-authored working
context, not normative text. Promoted, reconciled principles: the framework-vs-
workflow-builder responsibility split; "framework-shaped metadata is not
authoritative merely because it exists" (concept level 3); operational isolation
as a workflow-builder responsibility. Not promoted: external-artifact
classification detail, runtime-resolution/projection scope, entity lifecycle, and
schema-maintenance policy -- these stay in the inquiry and its follow-up modeling.
The inquiry was neither edited nor moved; all four artifacts cross-link to it or
inherit the link through the concept.

== Duplication and cross-link assessment

Cross-links, as built:

* ADR -> concept, and ADR -> `ADR-DOMAIN-OWNS-VALIDATION-WRITERS-STAY-DUMB`,
  `ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE`, cold-storage inquiry.
* Concept -> ADR, Developer Guide catalogue, review guidance, cold-storage
  inquiry, and both related ADRs.
* Developer Guide catalogue -> concept and ADR.
* Review guidance -> ADR and concept.

The threat-model boundary sentence appears in the FTR, the ADR, and the concept.
This is intentional single-sentence anchoring in each artifact's own voice
(backlog intent, architectural decision, normative rule), not paragraph-level
duplication. The balancing qualifications, boundary-level table, principle list,
and pattern examples each live in exactly one owner. No artifact reproduces
another's body prose.

== Readability assessment

The ADR and concept are understandable without metaclass expertise: hostile
behaviour is described by category (comparison, hashing, `repr`, iteration,
conversion, descriptors, metaclasses, mutable subclass state) rather than by
enumerating special methods. The catalogue leads with a note that exact-type
checks are not a default rule and require a semantic reason, and each pattern's
example is minimal and idiomatic. No Axis Mapping implementation detail leaked
into the normative documents; the only concrete identifiers used
(`_SUPPORTED_EXACT_NUMPY_INTEGER_TYPES` in one example) are illustrative, not a
description of the resolver.
