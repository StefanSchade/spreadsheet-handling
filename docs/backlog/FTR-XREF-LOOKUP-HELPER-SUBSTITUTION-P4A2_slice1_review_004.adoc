==== XREF-S1-R004-MIN-001 — formula duplicate tests do not prove the claimed pre-construction/pre-placement timing

Severity:: Minor
File / symbol::
`tests/unit/domain/transformations/test_lookup_formula_mode.py` —
`TestFormulaDuplicateHelperRejection`; its class docstring and the timing claim
reviewed for `_check_duplicate_helper_fields`.
Evidence::
The four new cases correctly assert an eventual `Duplicate helper field`
`ValueError` and that the caller mapping has no output. They do not assert that
`_build_formula_enrichment` or `_reorder_helpers_before_key` was never entered.
An independent process-local simulation disabled the early guard and invoked
the same guard (a) after successful formula construction and (b) after
`before_key` placement. In both simulations the public call produced the same
`ValueError`, the caller still lacked an output, and the tracked assertions
would pass. Therefore the tests do not prove that merely moving validation
later would fail them, despite the test docstring's stronger claim.

Current runtime order is correct: source inspection and a sentinel probe prove
`_check_duplicate_helper_fields` runs before value-mode selection, formula
construction, placement, output creation, and provenance. Formula construction
and placement are also local/copy operations, so the simulated late rejection
did not expose caller mutation or a current correctness defect.
Impact::
This is a non-load-bearing assertion-strength and claim-precision issue. The
settled four public combinations are tracked and current atomic behavior is
correct, but the tests would not catch a refactor that retained the final error
while doing unnecessary formula/placement work first.
Required correction::
As a non-blocking follow-up, either add sentinel/monkeypatch assertions that
formula construction and `before_key` placement are not called for duplicate
helpers, or narrow the test docstring/coverage claim to the observable contract
the tests prove: deterministic failure before output/provenance is committed.
Blocks Slice 2:: No.

== 5. Presence/null mismatch assessment

Correction 003 closes the root cause. `_validated_mismatch_keys` derives
`has_on`, `has_source_key`, and `has_lookup_key` with membership tests. There is
no remaining `is not None` or truthiness-based form selection in that reader.
The ordered contract is coherent:

. `on` plus either asymmetric member is mixed and raises, regardless of value;
. present `on` selects symmetric validation;
. either asymmetric member selects asymmetric validation and requires both
  members to be present;
. each selected value is validated for non-empty string/list shape; and
. a present record with none of the three key members raises as no-form.

The exact Review-003 forms all failed closed under both policies:

[source,json]
----
{}
{"on": null}
{"source_key": null}
{"lookup_key": null}
{"source_key": null, "lookup_key": null}
----

Independent probes also passed for:

[source,json]
----
{"source_key": "story_id", "lookup_key": null}
{"source_key": null, "lookup_key": "id"}
{"on": null, "source_key": "story_id"}
{"on": ["story_id"], "lookup_key": null}
{"on": null, "source_key": null, "lookup_key": null}
----

Every call raised a domain `ValueError` containing
`_meta.derived.sheets['matrix'].enrich_lookup`; none returned a misleading
zero-findings success. The adjacent earlier-review shapes also remain closed:
empty/blank/null-element/mixed-blank symmetric lists and blank/list/object
asymmetric halves all raise clearly.

Separately verified:

* absence of the entire `enrich_lookup` record is still the established no-op;
* malformed records under `policy: drop` are removed by helper identity without
  key-form validation or findings;
* valid symmetric, differently named asymmetric, and equal-name asymmetric
  records detect an edited helper; and
* null values in DataFrame join-key cells continue to compare normally.

Repository search found only one key-aware provenance reader:
`derived_column_policy._check_enrich_lookup_values`. Rendering, cell codec, and
FK cleanup readers consume only `helper_columns` and are unaffected by key-form
validity. No second value reader retains the former absent/null ambiguity.

== 6. Caller-state and lifecycle assessment

The operation order is safe. `apply_derived_column_policy` obtains caller
frames and metadata, then calls `enforce_derived_column_policy_frame` before it
constructs `out`. Inside the pure enforcement function, mismatch validation
runs before drop-column computation. A malformed-record exception therefore
escapes before cleaned data, findings, output aliases, or metadata pruning can
be committed.

For every requested malformed shape and both policies, a probe used a distinct
`output="cleaned"`, an existing `derived_column_findings` sentinel frame, and
deep snapshots. It verified:

* no `cleaned` output key appeared;
* caller source and lookup DataFrame objects and values were unchanged;
* the helper remained present;
* caller metadata object/value and provenance remained unchanged;
* the existing findings frame was unchanged; and
* no caller mapping mutation occurred before the exception.

Successful lifecycle behavior also remains established:

* warn removes the helper, returns the finding, and prunes consumed transient
  provenance only after enforcement succeeds;
* fail on a real mismatch raises before any output is committed;
* fail with an unchanged helper returns the cleaned result as before;
* drop removes the helper without value validation; and
* a distinct output preserves the original source/provenance under the
  framework's established contract.

No mutation or metadata-lifecycle regression was found.

== 9. Complexity and proportionality assessment

Disposition: *somewhat heavy but justified.* The cumulative Slice-1 runtime is
larger than the two-parameter happy path alone, but the added code makes public
mode, collision authority, provenance compatibility, and failure semantics
explicit. Much of the line growth is focused docstrings/diagnostics rather than
additional abstraction or scattered control flow.

[cols="1,5"]
|===
| Question | Assessment

| 1. One coherent concern per helper?
| Yes. `_ResolvedKeys` carries resolved state; `_resolve_join_keys` selects and
  reconciles the public form; duplicate and collision guards each enforce one
  projection invariant; `_validated_mismatch_keys` validates the reader's two
  provenance forms; column checks, formula construction, and provenance
  writing remain separate.

| 2. Modes resolved once or scattered?
| Resolved once in `_resolve_join_keys`. Consumers branch on the resolved mode
  only where semantics differ: collision authority and provenance shape.

| 3. Malformed validation local?
| Yes. It lives in `derived_column_policy`, the sole key-aware reader that must
  verify values. The producer and generic readers were not coupled to it.

| 4. Unrelated infrastructure pulled in?
| No. No generic metadata validator, provenance-family abstraction, pipeline
  binder, workbook boundary, or unrelated metadata family was introduced.

| 5. Duplicated checks?
| No material duplication. Producer `_require_key_name` and reader
  `_validated_single_key` look similar but own different trust boundaries and
  path-specific diagnostics. Consolidating them would create cross-module
  coupling. The post-validation `not payload_keys` clause is now redundant but
  harmless and too small to justify a finding.

| 6. Contradictory/unreachable branches?
| No contradictory behavior. Mode/cardinality invariants make the private
  single-key properties safe. The redundant empty-key check is the only stale
  defensive branch found; it does not obscure control flow.

| 7. Understandable errors?
| Yes. Public parameter errors name the selected forms/keys; collision errors
  name the key role; mismatch errors name the metadata path; missing columns
  identify payload/lookup frame and key.

| 8. Runtime increase proportionate?
| Somewhat heavy, but proportionate to preserving four legacy symmetric forms,
  adding explicit mode identity, protecting two output modes, and supporting
  the existing mismatch-policy reader without silent degradation.

| 9. Materially less code possible?
| Not without hiding mode/provenance semantics or weakening diagnostics. Removing
  comments/docstrings or the one redundant check is not material; a shared
  generic validator would add abstraction rather than simplify ownership.

| 10. Tests versus runtime?
| Tests are much larger because they enumerate public forms, value modes,
  placements, malformed provenance, render backends, and compatibility. That
  is contract documentation, not evidence that runtime itself is over-engineered.
|===
