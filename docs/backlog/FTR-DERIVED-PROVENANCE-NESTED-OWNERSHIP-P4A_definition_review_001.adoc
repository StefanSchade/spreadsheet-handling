=== DR-003 -- identity versus structural-snapshot test language

*Severity:* Minor.

*Exact locus:* FTR sections 5, 8.1, 8.2, and acceptance criterion 11.1.

*Concrete problem:* Section 8.1 calls unchanged keys/values an “identity-level”
assertion. That is structural equality, not identity. It also explicitly names
retained `_meta`, `derived`, and `sheets` references but leaves the per-sheet
record reference implicit, even though criterion 11.1 correctly includes
per-sheet records.

*Evidence:* The defect preserves the input containers’ identities while changing
their structure. An identity-only assertion therefore passes on the broken code.
Conversely, output identity must differ only for changed path nodes; untouched
sibling objects may legitimately remain shared.

*Correction/refinement:* Slice 1 tests must retain references *and* structural
snapshots through the touched per-sheet record, then assert every caller-retained
object remains structurally equal to its snapshot. They must separately assert
that changed output path nodes are not the input nodes. Unchanged siblings are
asserted by value and may share identity; no test may require copying every
caller-reachable object. A mutate-then-restore implementation would still
violate the contract even if an end-state snapshot happened to pass.

*Acceptance gate:* No. Sections 5 and 11 already state the controlling structural
non-mutation rule; this refinement removes a test-term ambiguity.

== 5. Ownership contract assessment

The governing sentence is narrow, observable, and testable:

[quote]
____
A Frames transformation that writes, replaces, or prunes nested `_meta.derived`
state must not mutate caller-owned nested mapping objects reachable from the
input payload.
____

“Caller-owned” means a mapping supplied through the input Frames graph and still
retained by the caller. “Reachable” closes the shallow-copy loophole: ownership
does not end at the top-level Frames or `_meta` mapping. The rule covers only
maintained `_meta.derived` writers and cleaners, preserves current returned
Frames semantics, and cannot be satisfied by suppressing the output update.

The output owns each changed path node. The input retains its original nodes.
Copy-along-the-mutated-path therefore requires new `_meta`, `derived`, `sheets`,
and touched sheet-entry containers as applicable. An untouched sheet entry or an
unrelated top-level metadata value may remain shared. Every caller-retained
object must remain unchanged; every object need not be copied. No DataFrame or
whole-Frames deep copy is authorized.

Human Readability lens:

* *Reader question before:* does a new output mapping and new top-level `_meta`
  also protect retained nested metadata? Answering required tracing both
  producers, FK cleanup, the registry, and prior ownership evidence.
* *Reader answer after Slice 1:* every `_meta.derived` writer/cleaner exposes one
  local copy-on-write boundary, while current record shapes, diagnostics, and
  cleanup timing remain visible.
* *Cost balance:* a few path copies and targeted tests are proportionate; a new
  public abstraction, deep-copy regime, or metadata framework is not.

== 8. Enrich Lookup stale-cleanup disposition

Current cleanup is intentionally asymmetric:

* the FK producer stale-cleans only its `helper_columns` records;
* `drop_helpers` conditionally removes `enrich_lookup` only when none of its
  helper columns remains;
* `apply_derived_column_policy` removes both sub-keys when it replaces the
  source frame;
* the Enrich Lookup producer replaces its record for the named output but does
  not scan other sheet entries.

For the same output, a second identical invocation is stable. A helper-list
change replaces the list rather than merging stale members. `output == source`
replaces the same record. With a renamed output, the old output frame is normally
preserved by the copied Frames mapping, so its provenance remains descriptive.
If a caller removes that frame before a later invocation, residue can remain
within the run; no accepted evidence assigns that broader cleanup to the
producer.

Slice 1 therefore characterizes these cases but does not add Enrich producer
stale cleanup. A newly observed orphan with observable harm requires explicit
coordination/fresh scope. There is no persistence-crossing stale state because
the boundary removes `derived`.

== 9. Implementation alternatives and dependency direction

The FTR leaves three genuine choices open: neutral common helper, family-local
copy-on-write, or a small owned nested-meta utility at an established boundary.
No choice is required by the review.

The implementation justification must distinguish a real common ownership
contract from merely similar dictionary code. A helper in FK or Enrich would
create a wrong cross-family dependency. `frame_keys` is a possible low-level
location only if its established reserved-Frames responsibility can truthfully
own nested metadata copying; using it merely because it already copies `_meta`
would broaden that module without evidence. A neutral meta module is not
automatically justified either. Family-local code remains acceptable when it
best preserves local diagnostics and cleanup nuance.

`_strip_consumed_provenance` is positive semantic evidence, not a mandatory
extraction target. Existing dependency guards remain authoritative.

== 10. Malformed-input boundary

Independent probing confirmed the asymmetry:

* FK write and drop/clean raise raw `AttributeError` on a non-mapping
  `_meta.derived`;
* Enrich Lookup write raises raw `AttributeError`;
* derived-column policy raises a path-named `ValueError`;
* `derived_helper_columns_by_sheet` treats the malformed container as absent.

Uniform hardening is not necessary to establish ownership for valid mapping
input and would create a second concern. Slice 1 may inspect and copy valid or
absent mapping levels. If that exact operation inseparably introduces a minimal
mapping check, the FTR permits only the copy-scoped check. It must not normalize
malformed metadata, invent a new public diagnostic requirement, support hostile
mapping objects, or broaden consumer behavior. Broad hardening remains optional
Slice 2 and requires separate review.
