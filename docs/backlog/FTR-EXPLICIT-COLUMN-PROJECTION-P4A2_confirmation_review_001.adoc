== Scope of this review

Confirm the assessment and confirmation are evidence-complete, free of
accidental overdesign and unproven compatibility assumptions, do not conflate
presentation with domain semantics, do not miss a duplicate capability, are
bounded, and that the *no-replacement / non-removal* conclusion is genuinely
supported.

== Checks

=== Evidence completeness

* Implementation, resolver, registry, gate, docs, tests, and both consumer
  classes were read directly (not inferred). ✓
* The controlling decision artifact was read from cold storage, justified by
  the navigation rule (a current open FTR names it as its source of truth). ✓
* Behaviour claims were confirmed by a read-only probe *and* by the passing
  baseline test suite, not by tests alone. ✓
* The dynamic-`matrix_value` claim -- the linchpin -- is triple-sourced:
  resolver code (rest-by-exclusion), the decision artifact ("set grows with the
  cast"), and the probe. ✓

=== Accidental overdesign

* The conclusion *adds nothing*: no step, parameter, schema, wrapper, or FTR.
  This is the opposite of overdesign. ✓
* The provisional ID is used only for artifact naming and is explicitly *not*
  registered, avoiding a phantom backlog item. ✓

=== Unproven compatibility assumptions

* No external deprecation cycle is asserted; the confirmation records that no
  external/unknown consumer evidence exists and none is needed because nothing
  changes. ✓
* The external worldbuilding consumer is treated as evidence only and left
  untouched, honoring the "do not start worldbuilding adoption" boundary. ✓

=== Hidden presentation / domain conflation

* The review explicitly resisted the tempting "move it into Workbook View"
  framing by identifying the inbound reimport mirror, which is a domain
  roundtrip concern, not presentation. Correctly classified (Option 4
  rejected). ✓

=== Duplicate capability

* `extract_frame` was found and correctly identified as the pre-existing
  explicit-projection primitive, which is the strongest single reason not to
  add `project_columns`. Not missed. ✓

=== Implementation boundedness

* Because the outcome is "no change," boundedness is trivially satisfied; the
  risk was the opposite (fabricating scope), which was avoided. ✓

=== Is removal truly supported?

* No -- and the confirmation says so. Removal would require both a replacement
  (absent for dynamic columns) and a migratable consumer (the only consumer is
  external/out-of-scope). Correctly concluded *not* removable. ✓

== Possible objections considered

* *"The hypothesis names real ergonomic friction (direction bundles order +
  retention)."* Acknowledged in §9 as a narrow, non-blocking observation. It
  does not rise to a replacement because no consumer needs subset ordering or
  non-role-grouped order, and the friction is an intentional decision outcome.
  Recording it (rather than acting) is the proportionate response.
* *"Should the owning FTR be closed as part of this?"* No -- that is a separate
  lifecycle task with its own review trail; folding it in would exceed this
  read-only assessment's mandate. Flagged, not performed.
* *"Is NOT READY being used merely because the repo is complex?"* No. Four
  concrete blockers are named (dynamic columns, existing `extract_frame`,
  no in-repo consumer, open owning FTR), matching the confirmation's required
  bar for that verdict.

== Residual risk

Low. The only risk is that a *future* consumer wants static explicit projection
in a `core` pipeline; that is already served by `extract_frame` and needs no
new work. If a consumer ever needs *non-role-grouped dynamic* ordering, that
would be genuinely new scope and should open its own FTR with a concrete
call-site -- it does not exist today.
