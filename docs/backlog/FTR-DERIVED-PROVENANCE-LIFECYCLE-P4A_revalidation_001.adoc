== 3. Original FTR summary (as historical claims)

The parent FTR is an *operational documentation FTR*: "document and tighten an
existing contract", explicitly "No code behavior change is required to satisfy
this FTR". It aimed to formalize the `_meta.derived` lifecycle:

* producers (`fk_helpers._write_helper_provenance`,
  `enrich_lookup._write_provenance`), consumers, and three cleanup sites in two
  modules with "no single owner";
* a *persistence asymmetry*: XLSX persisted only canonical `kv`, while the JSON
  `_meta.yaml` sidecar serialized the *entire* in-memory `frames["_meta"]` with
  no filter -- so absence of `derived` depended on *cleanup-step ordering*, and
  it explicitly left open "cleanup-before-serialize ordering vs. serializer-side
  exclusion";
* an ownership model, presence-checked pruning, nested-`_meta` copy hygiene,
  orphan/stale classes, a deterministic-vs-heuristic boundary naming the
  `drop_helpers` prefix fallback as the bounded anti-pattern, and a *concept
  only* future `reconcile_derived_provenance` step.

Its acceptance was entirely documentation; it deferred symmetric enrich-lookup
stale-removal, uniform malformed-`_meta.derived` hardening, the reconciliation
step, and durable derived-provenance persistence.

== 6. Current persistence and durable-carrier model

*Persistence (decided).* `application/orchestrator.py:138` calls
`persistence_boundary.project_meta_to_persistable_contract(meta)` for *every*
output kind, after final domain cleanup, immediately before `_save_frames`.
`derived` is in `RUNTIME_ONLY_TOP_LEVEL_META_KEYS`, so it is dropped for
JSON/YAML/XML/CSV directories *and* the spreadsheet path alike. The projection
is a pure function that returns a new dict. The parent FTR's open choice --
cleanup-step ordering vs. exclusion at serialization time -- is *decided in
favor of an orchestrator-owned persistence-boundary projection*: a single pure
projection, owned by the orchestrator and applied uniformly before save, excludes
`derived` independently of any individual backend serializer or of cleanup-step
ordering. This is a boundary-level exclusion, *not* serializer-owned behavior,
and the JSON-sidecar asymmetry is obsolete.

*Durable-versus-transient carriers (settled):*

[cols="1,2,2", options="header"]
|===
| Information | Carrier | Lifecycle
| FK helper *identity* | `_meta.helper_policies.fk.relations` (v2) | durable
| Workbook-view helper *identity* | `_meta.sheets.<sheet>.helper_columns` (canonical) | durable
| Rich helper *provenance* (`fk_column`, `target_key`, `value_field`, join keys) | `_meta.derived.sheets.*` | transient
| Value-/mismatch-check inputs | `_meta.derived.sheets.*.enrich_lookup` only | transient
|===

`apply_derived_column_policy` already realizes this split: it prefers transient
`_meta.derived`, and when that has been stripped it falls back to durable
canonical `helper_columns` (`_safe_durable_helper_names`) and v2 relations
(`_safe_policy_helper_names`) *for drop/identity only*; value checks remain
limited to the rich transient provenance and are intentionally lost after
persistence. Durable persistence of `_meta.derived` is therefore a *rejected
design*, not a live goal.

== 8. Nested-mutation assessment

*Direct evidence (probe under `/tmp`, repository untouched):*

* `enrich_lookup(..., output="src_enriched")` against frames whose input `_meta`
  already carries `derived.sheets`: the caller's *same* nested `sheets` object
  gained the `src_enriched` key; `out["_meta"]` is a distinct top-level object
  (shallow `dict(meta)`), so top-level non-mutation masks recursive mutation.
  This reproduces *EL-HR-002* independently -- it is not accepted on Project
  Memory's say-so.
* `enrich_helpers` (`_write_helper_provenance`): mutated the caller's nested
  `derived.sheets` in place (added the source sheet, pruned an unrelated stale
  sentinel sheet).
* `drop_helpers` (`_clean_helper_provenance`): mutated the input's nested
  `derived.sheets` in place (emptied it).

*Mechanism.* `frame_keys.copy_reserved_frames` aliases `_meta` by reference;
producers/cleaners then `dict(meta)` (shallow) and reach through the shared
`derived` / `sheets` dicts via `setdefault`. Only
`_strip_consumed_provenance` rebuilds each level with `dict(...)`.

*Blast radius.* Because `derived` is stripped at the persistence boundary, this
mutation *never leaks into persisted output*. It is observable *only* to an
in-process caller that retains a reference to the input frames' `_meta.derived`
within a single run. That is a real Frames-transformation non-mutation-contract
question, but a bounded, internal one. There is *no repository-wide, explicitly
codified* Frames non-mutation contract for nested `_meta`; the convention is
family-local and unevenly applied.

== 9. Stale / orphan assessment

* *Across persistence:* not reachable -- `derived` does not persist and read
  paths never reconstruct it. Remove this historical dimension.
* *Within one run / repeated invocation:* FK producer stale-cleans its own
  entries; `drop`/policy presence-check before pruning. `enrich_lookup` has no
  producer-side stale-removal, but its cleanup is consumer-owned and
  presence-checked, so present columns keep provenance and removed ones lose it.
* *Symmetric producer-side stale-removal for enrich_lookup:* not required on
  current evidence; the asymmetry is an *accepted trade-off*, not a defect.
* *Rename/sheet-rename orphans:* for *derived* these are within-run-only and
  largely moot; where rename matters is on the *durable* carriers
  (canonical `helper_columns`, v2 relations), owned by schema maintenance /
  `FTR-RENAME-RECONCILIATION`. Automatic reconciliation of derived provenance
  remains correctly rejected.

== 10. Malformed-input assessment

*Direct evidence (probe).* With `_meta.derived` set to a non-mapping:

* consumers are hardened -- `derived_helper_columns_by_sheet` is a safe no-op;
  `apply_derived_column_policy` raises a clear `ValueError` naming the path;
* producers/cleaners are *not* -- `_write_helper_provenance`,
  `enrich_lookup._write_provenance`, and `drop_helpers` raise a raw
  `AttributeError` (`'str' object has no attribute 'get'/'setdefault'`).

The parent FTR's deferred "uniform malformed-`_meta.derived` hardening inside
producers and `drop_helpers`" is therefore *still accurate*. Because malformed
`derived` can only arise from hand-authored input `_meta` or a producer bug (it
never round-trips through a carrier), this is an *internal runtime contract*
question, not a read-path robustness gap. Uniform hardening is *optional*: it
should be weighed against obscuring an internal-only contract, and belongs with
the nested-ownership slice if taken at all.

== 11. Ownership assessment

* *Producer ownership* of each sub-key is clear and single (FK vs. enrich_lookup).
* *Cleanup ownership* is still emergent across three sites with no single named
  owner -- unchanged from the FTR.
* *Mutation ownership* is the open question: producers and two cleanup sites
  mutate caller-owned nested `_meta`; one site (`_strip_consumed_provenance`)
  does not. There is no repo-wide contract; a common path-copy/prune helper would
  give the sites one owned convention.
* *Semantic classification, runtime ownership, persistence policy, and cleanup
  responsibility are distinct axes.* The registry/concept docs settle
  classification and persistence policy; they do *not* settle mutation ownership.
  A documented classification is not proof that code-level ownership is settled.

== 12. Positive patterns to preserve

  with idempotence and non-mutation tests -- the model any nested-cleanup helper
  should imitate;
* `_strip_consumed_provenance`'s copy-along-the-mutated-path shape;
* the presence-checked prune already used for `enrich_lookup`;
* `apply_derived_column_policy`'s clear, path-named malformed-input `ValueError`s
  and its durable-carrier fallback;
* `_ResolvedKeys` and the symmetric/asymmetric enrich_lookup record shape;
* FK replay-safety (`_preserve_source_flatness`) and validation-precedence

* the registry `derived` entry's sub-key-ownership `merge_behavior` note.

Any later slice must preserve record shape, write timing, consumer behavior, and
persistence stripping (per EL-HR-002's "Preserve" list).

== 14. Recommendation for the parent FTR

*Selected outcome: C -- Supersede with a new narrow FTR.*

Rationale: the parent's purpose was *documentation of a broad lifecycle +
persistence + heuristic-boundary contract*. Persistence is decided, the
durable/transient split is settled, the prefix anti-pattern is gone, and the
lifecycle is documented in the registry -- so the broad problem is largely
resolved and its "current behavior" sections are now historical. What remains is
a *different, code-level* problem (nested mutation ownership) of a *narrower*
purpose than the original. That is the textbook case for *supersede*, not
*retain-and-recut* (the remaining work no longer shares "substantially the same
purpose") and not *close-as-satisfied* (a coherent implementation problem
remains).

Parent-FTR handling: keep the ID archivable with traceability; a narrow
annotation at the top records the revalidation outcome (below). Do not rewrite
the original body in this task.

== 15. Recommendation for a later implementation FTR

Propose (do *not* create here):
`FTR-DERIVED-PROVENANCE-NESTED-OWNERSHIP-P4A`.

Suggested scope:

* copy-along-the-mutated-path semantics for every step that prunes/rewrites
  nested `_meta.derived`;
* caller-input non-mutation as the stated (family-local) contract, with a shared
  path-copy/prune helper as the single cleanup convention;
* precise stale-removal only where still reachable (within-run), keeping the
  accepted enrich_lookup consumer-owned asymmetry unless characterization shows a
  concrete defect;
* optional uniform malformed-`_meta.derived` hardening for producers/cleaners
  (RV-002), decided against obscuring an internal-only contract;
* targeted characterization across FK and Enrich producers/consumers proving
  input non-mutation, sibling preservation, and symmetric/asymmetric record
  parity.

Explicit non-goals for that FTR: no change to persisted output (boundary already
strips `derived`); no reconciliation engine; no durable `derived` persistence; no
change to the durable-carrier split.
