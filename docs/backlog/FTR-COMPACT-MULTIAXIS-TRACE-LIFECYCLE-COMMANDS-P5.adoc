===== FTR-COMPACT-MULTIAXIS-TRACE-LIFECYCLE-COMMANDS-P5 -- Explicit lifecycle commands for Compact Multiaxis diagnostics traces

*Status:* New

*Priority:* P5

*Type:* Narrow feature-local metadata lifecycle

*Depends on:* `FTR-COMPACT-MULTIAXIS-META-PERSISTENCE-CORRECTION-P5`

*Problem:*::

`_meta.compact_multiaxis[config_id]` is a persistent, feature-owned,
diagnostics-only trace. A successful run replaces the current entry for its own
stable `config_id`, and different IDs coexist. No existing command surface owns
the removal or migration of one configured Compact Multiaxis instance when its
ID is explicitly dropped or renamed.

The trace is not runtime configuration, inverse intent, or fallback, so stale
entries cannot change transformation results. They can nevertheless mislead
diagnostic readers and require an explicit feature-owned end-of-life operation.

*Required capability:*::

Provide a narrow Compact Multiaxis lifecycle surface with:

* explicit drop of exactly `_meta.compact_multiaxis[config_id]`;
* explicit rename/migration from one exact `config_id` to another;
* deterministic collision behavior when the target ID already exists;
* defensive copying and caller-input atomicity on success and rejection; and
* canonical omission of an empty `compact_multiaxis` root after the last entry
  is dropped.

*Boundaries:*::

* No deletion inferred from absence in a pipeline run.
* No deletion inferred from public-frame existence, rename, or drop.
* No generic metadata garbage collector or generic frame ontology.
* No promotion of the diagnostics trace to operative intent.
* No change to Compact Multiaxis compute composition, XRef fallback, Cell Codec,
  Legend Blocks, or Sparse Defaults.
* Column schema maintenance continues to ignore this non-authoritative trace;
  it does not silently maintain or prune it.

*Persistence and carrier interaction:*::

The command must operate on canonical `_meta` before the orchestrator
persistence boundary. Structured persistence and the workbook metadata carrier
must serialize only the post-command trace state. A lifecycle command is an
instruction, not history: any command envelope must be consumed before
persistence and must not roundtrip or replay.

*Acceptance criteria:*::

. Drop removes exactly the named `config_id`, preserves every other entry, and
  omits the root when no entries remain.
. Rename moves exactly the named entry, preserves its diagnostics payload, and
  removes the old key atomically.
. Missing source IDs and occupied target IDs have explicit, deterministic
  outcomes with no partial mutation.
. Caller-owned nested mappings and lists are not mutated.
. Absence-in-run and frame-existence changes do not trigger lifecycle actions.
. Column schema maintenance remains non-blocking and does not pretend to update
  trace fields.
. JSON/YAML structured persistence and XLSX/ODS workbook carriers roundtrip the
  resulting state without a command envelope.
. Focused tests cover same-ID no-op or rejection policy, different-ID
  preservation, last-entry root omission, repeated execution, failure
  atomicity, and both carrier families.

*Release-note checkpoint:*::

Determine release-note impact when the command surface is selected. A new YAML,
CLI, or public Python lifecycle surface is user-facing and requires an entry in
the active unreleased section.
