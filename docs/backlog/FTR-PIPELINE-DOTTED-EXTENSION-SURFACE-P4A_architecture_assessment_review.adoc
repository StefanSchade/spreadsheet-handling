== 3. Topology and adoption verification

=== 3.1 Resolver/build-flow topology

Independently reproduced at current HEAD (not copied from the assessment):

* `pipeline/dotted_paths.py` has exactly one checked resolver,
  `resolve_configuration_callable`. `_split_reference`/`_ensure_module_addressable`
  are pure string operations -- no import occurs until the final
  `importlib.import_module(module_path)` call inside
  `resolve_configuration_callable` itself. The one blocked namespace is
  `spreadsheet_handling.domain.ingress`.
* `pipeline/registry.py`'s `REGISTRY` dict has 44 entries (verified by direct
  count, matching readiness review 003 and the assessment); `resolve_registration`
  returns a dict-lookup hit unchanged for a registered name (no import: the
  `StepRegistration.target` string was never resolved when `registry.py`
  itself was imported at process start) but, for an unregistered colon-bearing
  `step_id`, calls `resolve_configuration_callable(step_id)` *inline*, i.e.
  the import happens synchronously inside `resolve_registration` itself.
* `pipeline/build.py`'s `build_steps_from_config` calls `resolve_registration(step_id)`,
  then unconditionally overwrites any user-supplied `target` key with
  `registration.target` (`factory_kwargs["target"] = registration.target`)
  before calling `registration.factory(**factory_kwargs)`. A configured
  `target` therefore *cannot* override a registration-owned target -- verified
  by reading the exact lines, not inferred from the assessment's prose.
* `pipeline/steps.py`: `make_plugin_step` calls `resolve_configuration_callable(dotted)`
  as its first statement; `make_builder_target_step`/`make_frames_target_step`
  both call the shared `_resolve_target`, which resolves only string targets
  and returns direct callables unchanged.
* Whole-tree re-search: `grep -rn "importlib.import_module\|import_module("
  src/spreadsheet_handling/` returns exactly four sites -- the one pipeline
  resolver plus three `io_backends` lazy-backend-loading sites (selected only
  after a fixed short `kind` such as `ods`/`xlsx` is chosen, not an arbitrary
  configuration-addressable resolver). No ninth maintained surface exists.

This independently confirms the assessment's section 2.1 topology claims

colon-style factory case (assessment line: "A missing name containing a colon

== 5. Eight-surface review

=== 5.1 Registered short-name step

Q6 (can short-name authorization occur before its registration-owned target
is resolved/imported?) was tested directly against source (3.1):
`resolve_registration` for a registered name is a pure dict lookup; the
registration-owned target string is not resolved until
`registration.factory(**factory_kwargs)` is called in `build_steps_from_config`.
A future E7 check placed between those two lines -- after
`resolve_registration()` returns, before `registration.factory(...)` is
called -- authorizes the short name with zero import having occurred yet.
*Confirmed: YES, cleanly, without any prerequisite refactor.* Per-registration
authorization metadata is correctly identified as necessary (section 7 row:
"registry membership alone is insufficient") and correctly left as an E7
design detail (section 11.1's "remaining design/implementation detail"
column), not implemented here. No conflict with any existing registry
contract was found.

=== 5.2 Plugin callable

`make_plugin_step`'s first statement resolves `dotted` immediately (3.1), so
authorization must be interposed in `build_steps_from_config` before calling
`registration.factory(**factory_kwargs)` for `step_id == "plugin"` -- the
`dotted` value is already available in the popped config dict at that point,
requiring no prerequisite refactor either. The assessment's claim that "exact
dotted target" is sufficient authorization *identity* (not callable identity)
was tested against the aliasing/re-export question: a re-exported spelling of
the same underlying function is a *different* string and would be denied by
default under an allowlist model (fail-closed, not a bypass); the assessment
and the FTR are both explicit and consistent that this is an
ownership/architecture choice, not a safety boundary, and that re-exports
"cross namespaces" without conferring authority. This is an explicit,
internally consistent choice under section 8 of the review task's own
permissive framing ("may legitimately authorize identifiers rather than
callable identity, but that choice must be explicit and safe under its
stated model") -- *no finding*.

=== 5.3 Direct colon-style factory

History support for indefinite compatibility was independently checked
against `_ftr_review.adoc`'s own historical-intent section (Wave 3r/REVIEW-001
commit `8b2b058` explicitly retained both plugin and direct-colon forms) --

=== 5.4 Registry-owned string target -- HIGH ATTENTION

Independently traced the exact build order (3.1): short-name lookup is a
dict hit with no import; the registration-owned target is resolved only
inside the subsequent factory call; a configured `target` key is
unconditionally overwritten by `registration.target` before that call, so no
configured value can ever reach import in place of the registration's own
target. This directly answers the task's three sub-questions: (a) the build
path already supports placing authorization exactly between lookup and
factory-call without a prerequisite refactor; (b) no path exists for a
configured value to influence or override the registration-owned target; (c)
no malicious/less-trusted short-name configuration can cause internal target
resolution before short-name policy, because the internal target is never
even read from configuration in the first place. *No Blocking risk found
here* -- the assessment's characterization ("Internal representation...
never reject solely because target is Core/internal after its short name was
authorized") is accurate and verified at the source level, not merely
asserted.

=== 5.5 Nested configured string target

Independently confirmed the only route to a nested `target:` is through the
outer *unregistered* direct-colon surface (`step:
spreadsheet_handling.pipeline.steps:make_frames_target_step` or
`make_builder_target_step`, neither of which is namespace-blocked, plus a
sibling `target:` key) -- registered steps cannot smuggle a nested target in
because of the unconditional overwrite in 5.4. A plugin-mediated route was
also tested: `make_frames_target_step`/`make_builder_target_step` are keyword-only
with no `frames` parameter, so a plugin's `(frames, **args)` call convention
cannot construct one as a working step (`TypeError` on the extra positional
argument) -- this route is not practically reachable today, consistent with,
not contradicting, the assessment's "outer factory then nested target" model.
*No finding.*

=== 5.8 Framework-owned macro flow

Tested the specific concern that a plugin could reach a fixed-phase function
directly by dotted path, since only `domain.ingress` is namespace-blocked.
`domain.pipeline_cleanup.execute_final_domain_cleanup(frames)` matches the
plugin calling convention exactly (`frames`-only) and is *not* blocked.
Read the function in full: it is a pure, idempotent consumer of
`_meta.pipeline_cleanup` that no-ops when no commands are pending and removes
the key once executed, so an early plugin-triggered call cannot double-apply
or corrupt anything -- it can only run declared drop/keep commands earlier
than the framework's own fixed post-pipeline call would. This is exactly the
case the FTR itself already anticipated and scoped ("the category classifies
invocation ownership, not authorship of every command executed at the
boundary") -- the *authorization ownership of the fixed lifecycle position*
is unaffected; only the underlying domain command, which the FTR always
allowed to originate in configured transformations, executes early. A
parallel check on `application.managed_pipeline.finalize_managed_state` and
`pipeline.persistence_boundary.project_meta_to_persistable_contract` found
both are also import-reachable in principle but require a private
`ManagedExecutionState` object as an argument that no plugin/YAML description
can construct or obtain -- not practically reachable. *No finding; the
framework-owned macro-flow classification survives this adversarial probe.*

== 6. E7 identifier/resource-policy review

=== 6.1 Pre-import boundary -- CRITICAL, tested against accepted ADR authority

`ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY.adoc` Decision 4 (independently
read in full) states the accepted capability-activation invariant this
assessment must satisfy: safe authorization-preparation (parsing,
canonicalizing an identifier) may run before a policy decision; module import
for an untrusted-selected callable is capability activation and must not run
before rejection. The assessment's section 8 diagram
(`parse/canonicalize -> combine policy -> authorize -> resolve/import ->
bind -> invoke`) restates this invariant correctly and its per-capability-kind
rows correctly instruct rejection "before import."

One implementation-relevant asymmetry was found and is *not* explicitly
flagged by the assessment: for the plugin and registered-short-name surfaces,
the identifier needed for authorization (`dotted`, or the short `step` name)
is available in the popped config dict *before* the factory that would import
it is called, so a future E7 check inserted in `build_steps_from_config`
naturally precedes import. For the direct colon-style factory surface,
`resolve_registration()` performs the colon-detection *and* the import in the
same function call (3.1) -- there is no intermediate point at which
`build_steps_from_config` already knows "this is a colon-bearing,
unregistered step" without either duplicating that one-line string test
itself before calling `resolve_registration`, or `resolve_registration`
being changed to defer the import. This does not require a *prerequisite*
architecture change (the string test `":" in step_id and step_id not in
REGISTRY` is trivial to hoist into `build_steps_from_config` unchanged), and
the assessment's own section 2.1 wording ("resolved immediately") already
puts the underlying fact on record, and section 8's "reject before importing
the outer factory" already states the required *outcome* correctly. But
because Decision 4 makes import-before-rejection a soundness violation, not
a style preference, a future E7 implementer working from section 8 alone
could plausibly write "call `resolve_registration`, then check the result,"
which would defeat the required denial for exactly this one surface. This is
a real, source-grounded, correctness-relevant implementation pitfall, not a
missing prerequisite architecture decision -- see Minor M-1.

=== 6.2 Identifier canonicalization

`_split_reference`/`_ensure_module_addressable` are demonstrably import-free
(3.1), so canonicalization without import is not merely asserted but proven
at the source level, matching ADR Decision 4's "authorization preparation"
category exactly. Colon and final-dot spellings are handled by distinct code
paths (`_split_reference`'s two branches) and the direct-factory position
does not accept final-dot at all (assessment's own claim, independently
verified against `resolve_registration`'s `":" in step_id` test, which final
dot never satisfies) -- no accidental double policy identity was found
between the two spellings for the *same* surface. Registry/factory positions
remain syntactically distinguishable (registered-name lookup vs. colon
detection are different branches of `resolve_registration`). *No finding.*

=== 6.3 Capability-kind vocabulary

The six kinds (registered framework capability; arbitrary plugin callable
invocation; compatibility dynamic callable construction/acquisition; internal
framework callable acquisition; trusted direct-Python composition; framework
lifecycle capability) were checked for overlap and hidden-timing risk. Direct
colon factory and nested configured target are correctly merged into one kind
("compatibility dynamic callable construction/acquisition") because both are
denied outright to less-trusted descriptions with the same "reject before
importing the outer factory" timing (5.5 confirms no nested-target route
bypasses the outer factory's own denial). Direct callable target and direct
`BoundStep` are correctly merged into "trusted direct-Python composition"
because both bypass description-derived resolution entirely and sit outside
E7 by construction, not by policy choice. No two kinds with materially
different authorization timing were found merged together. *No finding.*

=== 6.4 Authority-widening resource selectors -- CRITICAL

Independently re-derived the complete authority-widening surface by grepping
every domain module reachable from a registered step for filesystem/network
I/O primitives (`open(`, `Path(`, `.read_text`, `.read_bytes`, `glob.`,
`os.walk`, `requests.`, `urllib`, `socket.`, `subprocess.`) rather than
trusting the assessment's own enumeration. Exactly four files matched:
`domain/artifact_manifest.py`, `domain/yaml_overrides.py`,
`domain/structured_yaml.py`, `domain/key_value_writer.py` -- the same four
steps (`write_artifact_manifest`, `apply_overrides`, `write_structured_yaml`,
`write_key_value_resources`) the assessment names. No fifth resource-touching
registered step exists (`normalize_resource_overrides`'s "resource" is a
localization/value-override concept, verified by reading its module
docstring and signature -- no I/O). *The enumerated set of steps is complete
and not missing a currently relevant selector.*

However, reading each implementation in full surfaces one materially
under-characterized entry:

[cols="2,3,3"]
|===
| Field | Verified containment | Assessment characterization

| `write_structured_yaml.output_dir` / `files[].path`
| `_safe_target_path` rejects absolute paths and anything resolving outside
  `output_dir` (verified in source).

requiring the same kind of parameter constraint (an allowlist against an
already-contained root, matching the three write selectors) could reasonably
under-protect `overrides_path`, which has no existing containment to layer
policy on top of and can read outside any configured output directory
entirely, including files the pipeline never wrote and never declared as an
output root. See Important I-1.

== 11. Findings

=== Important I-1 -- `apply_overrides.overrides_path` is mischaracterized as equivalent-risk to the contained write selectors

*Observation:* section 7's "Registered short-name step" row and section 8's
capability-kind table list `apply_overrides.overrides_path` in the same flat
enumeration as `write_structured_yaml.output_dir`/`files[].path`,
`write_key_value_resources.output_dir`/`file_pattern`, and
`write_artifact_manifest.output_dir`/`manifest_path`/`checksum`. This review
independently read `domain/yaml_overrides.py` in full: the three write
selectors are all root-contained by `_safe_target_path` (absolute paths and
`..`-traversal rejected); `overrides_path` has *no* equivalent containment --
`load_overrides` calls `Path(path)` directly and reads whatever exists there,
anywhere the process user can access.

*Risk:* a future E7 parameter-policy design that treats these four names as
one uniform "root-contained resource selector" category (a reasonable
reading of the assessment's flat listing) would under-protect
`overrides_path`, which is a materially different, unbounded arbitrary-file-read
primitive reachable through an *ordinary registered step*, not even an
expert-only plugin. This is exactly the "security-critical exhaustive list...
half-specified... inaccurately" risk the review brief names for this section.

*Recommended action:* add one clause to the assessment's section 7
"Registered short-name step" row and section 8 capability-kind table
distinguishing `apply_overrides.overrides_path` as an unbounded/uncontained
file-read selector, explicitly contrasted with the three root-contained write
selectors, so a future E7 design does not silently assume symmetric
containment.

*Disposition:* Important; correct in the assessment text before treating this
architecture as a stable basis for E7 parameter-policy design. Does not
require any architecture-selection change (Option E for the registered-step
row remains correct) and does not require new source/runtime work -- a
documentation correction to the assessment artifact.

=== Minor M-1 -- pre-import interception point for the direct colon-style factory surface is not explicit

*Observation:* `pipeline/registry.py`'s `resolve_registration` performs
colon-detection and import in the same function call for unregistered
colon-bearing step IDs (verified in source, 3.1/6.1), unlike the plugin and
registered-short-name surfaces where the identifier is available before the
factory call that would import it. The assessment's section 8 diagram states
the required outcome ("reject before importing the outer factory") correctly
and section 2.1 already records the underlying fact ("resolved immediately"),
but nothing connects the two: a future E7 implementer who authorizes "after
calling `resolve_registration`, before calling its returned factory" would
defeat the required denial for exactly this one surface, because the import
already happened inside `resolve_registration` itself.

*Risk:* a straightforward, easy-to-make implementation mistake in the future
E7 slice, not a defect in this assessment's decisions.

*Recommended action:* add one sentence to section 8's "Compatibility dynamic
callable construction/acquisition" row (or section 6's derived-FTR handoff)
stating that E7 must test the identifier shape (`":" in step_id and step_id
not in REGISTRY`) *before* calling `resolve_registration`, not merely before
calling its result, because `resolve_registration` itself performs the import
for this one surface.

*Disposition:* Minor; a clarity improvement for the benefit of the future E7
design task. Does not block architecture acceptance and does not indicate a
missing prerequisite architecture decision (6.1 confirms no refactor is
required, only a documentation note).

=== Observation O-1 -- resource-selector list is correctly scoped to registered-step parameters, not the whole configuration surface

The top-level `io`/`profiles` I/O descriptor (`output.path`, selecting the
main backend destination) is a real, already-documented (accepted Trusted
Ingress concept doc, section 11) resource-widening capability, but it is not
a "registered step" parameter and is correctly outside this FTR's
dotted-callable/step-parameter scope. The assessment does not claim to cover
it and does not need to. Recorded for completeness, not as a finding against
the assessment.
