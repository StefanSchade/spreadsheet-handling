== Problem

Domain transformations increasingly validate pandas, NumPy, configuration,
metadata, and caller-owned Python values at their boundaries. There is no
repository-wide statement of *how far* a domain boundary must defend against
malformed or hostile input, so each FTR review re-decides it independently.

The Axis Mapping resolver made the cost concrete. Three acceptance rounds on a
single internal, pure, read-only resolver escalated the applied threat model
without a shared policy:

* round 001 found genuine defects (non-total comparators, configured-field
  aliasing, hostile `str` subclasses, over-broad exception translation);
* round 002 -- after those were fixed -- escalated to metaclass-controlled
  `__name__` access in diagnostics, an incomplete exact NumPy integer set, and
  a retained caller-owned tuple subclass, and rejected the slice;
* round 003 accepted the slice and explicitly deferred the repo-wide question
  to "the planned Domain Boundary Robustness clarification".

Each round improved the code. But without a shared boundary, a reviewer can keep
finding one more Python special-method hook, and a competent developer cannot
predict when hardening is required, sufficient, or excessive. The symptoms are
repository-wide:

* inconsistent validation semantics across features;
* repeated review/correction cycles driven by a silently expanding threat model;
* defensive code whose purpose is hard to read;
* implicit claims that in-process validation is a security sandbox;
* premature generic helpers that merge distinct identity concepts.

The governing question this FTR must settle once:

[source,text]
----
What malformed, unusual, or hostile input must a domain boundary defend
against, and when does further hardening stop being proportionate to the
framework's actual application boundary?
----

== Threat-model boundary (normative core)

[source,text]
----
Domain boundaries must robustly handle malformed and unusual values that are
reasonably implied by their pandas, NumPy, configuration, metadata, and
artifact contracts.

They are not required to contain arbitrary hostile executable Python behaviour
already admitted into the process.
----

Validation robustness is not process isolation. A caller that can execute
arbitrary Python in the same process is already inside the runtime trust
boundary; no amount of local defensive introspection changes that.

This boundary must not be read as a licence to skip cheap, simplifying
hardening. Hardening is *in scope and encouraged* when it narrows the accepted
vocabulary, normalizes at ingress, establishes ownership, avoids accidental
dynamic dispatch, improves determinism, or simplifies diagnostics -- and stays
local and readable. It is *out of scope* when it only defends against a
hostile-object threat the stated boundary excludes.

== Responsibility split

Both sides are load-bearing. Neither excuses the other.

=== Framework responsibility

The framework provides:

* clear capability contracts and deterministic interpretation;
* deliberate validation of the failure modes its contract implies;
* actionable diagnostics;
* documented ownership, mutation, and failure behaviour;
* safe, readable internal representations;
* consistent architecture boundaries.

Workflow-builder responsibility does *not* excuse ambiguous behaviour, silent
coercion, hidden mutation, weak diagnostics, undocumented assumptions, or
inconsistent interpretation of the same declared contract.

=== Workflow-builder responsibility

A competent workflow builder owns:

* choosing and composing suitable primitives;
* deciding trust and authority for external data, metadata, and artifacts;
* handling stale, foreign, or changed inputs across the application boundary;
* application-specific validation, bootstrap, and promotion;
* operational isolation where hostile *executable* input is possible;
* validating the assembled workflow for the intended domain.

The framework is not responsible for anticipating every composition, or for
sandboxing arbitrary Python already executing in-process.

== Boundary taxonomy

Four levels, distinguished by what the framework may assume:

. *Trusted internal values* -- produced by validated internal constructors or
  resolutions: narrow types, stable equality/hashing, effective immutability, no
  caller-owned mutable backing, explicit ownership. Internal logic operates on
  these without repeating ingress validation.
. *Competent-user workflow input* -- configuration, Frames, metadata, and
  artifacts from a competent user or user-assembled workflow. May be incomplete,
  malformed, stale, or shaped by pandas/NumPy scalar/container behaviour. The
  framework provides deliberate validation and useful diagnostics for the
  failure modes its contract implies.
. *External application-boundary artifacts* -- data entering from outside the
  managed workflow scope (Git-controlled data, hand-edited files, foreign
  spreadsheets, detached or stale `_meta`). Trust, bootstrap, and promotion are
  the workflow builder's decision; framework-shaped metadata is not authoritative
  merely by existing. Governed primarily by `app_boundary_meta_authority.adoc`;
  referenced here, not re-specified.
. *Arbitrary hostile in-process objects* -- objects designed to execute or
  disrupt through comparison, equality, hashing, representation, iteration,
  conversion, descriptors, metaclasses, or mutable subclass state. *Explicit
  non-goal.* The framework may reject such values safely when that follows
  naturally from a narrow value contract, but it does not promise containment.

Levels 2 and 3 overlap; the load-bearing distinction is level 1 (assume) versus
level 4 (do not attempt to contain).

== Normative robustness principles

* *Validate at ingress, simplify internally.* Validate or normalize caller-owned
  values once at the semantic boundary; downstream code then operates on narrow,
  stable values instead of re-defending against the whole object model.
* *Prefer narrow accepted representations.* When subclass behaviour is outside
  the contract, exact built-in representations (strings for stable identities,
  tuples for immutable compound identities, normalized ints for supported NumPy
  integer scalars) are appropriate. Justify exact-type restrictions from the
  contract, not mechanically.
* *Establish ownership when a value is retained.* When the framework keeps a
  caller-owned value beyond validation, copy or normalize it (copy accepted
  ordered containers, convert carrier scalars to canonical built-ins, build
  frozen feature-owned value objects). Do not claim effective immutability while
  retaining caller-controlled mutable or behaviourally unstable objects.
* *Keep diagnostics deliberate and safe.* Prefer feature-specific exceptions
  carrying field/frame/row/role/config context. Do not execute caller-controlled
  behaviour merely to enrich a message; a constant detail such as
  `unsupported value type` is preferable to unsafe introspection when the
  surrounding context is already actionable.
* *Preserve failure atomicity where promised, and scope the promise.* A
  validating transformation must not partially publish output, metadata, or
  caller-graph mutation before the full candidate state validates. Scope the
  promise (e.g. Frames, DataFrames, `_meta`, retained nested caller values); it
  need not claim that consuming an arbitrary caller iterator has no visible
  effect.
* *Do not simulate a sandbox with local validation.* Growing defensive
  introspection does not substitute for process isolation, serialization
  boundaries, restricted execution, or an explicitly trusted format. Hostile
  executable input must be solved at a real isolation boundary.
* *Treat readability as a contract quality.* Hardening is proportionate when it
  narrows vocabulary, removes ambiguous dispatch, stays behind a small well-named
  boundary helper, or simplifies the flow. It should be challenged when it
  obscures domain logic, stacks defensive fallbacks, invents a broad generic
  safety abstraction without a stable semantic contract, or defends against a
  threat outside the stated boundary. A reviewer should follow the main
  transformation flow without expertise in metaclasses or every special method.

== Semantic DRY

Shared helpers must represent a shared semantic *contract*, not repeated syntax.
These concepts must not be conflated automatically:

* physical DataFrame column-label validity;
* configured field-reference identity;
* matrix-axis identity;
* canonical domain identity;
* visible presentation labels;
* ordering values;
* metadata paths.

Evidence required before extracting a shared helper:

* at least two genuine consumers needing the same contract;
* matching accepted *and* rejected vocabularies;
* matching normalization, ownership, and diagnostics;
* the same architectural layer.

A feature-local helper is preferred while only one capability owns the contract.
The Axis Mapping reviews searched the tree and found *no* second consumer of the
exact configured-field-reference, safe-diagnostic-detail, or exact-NumPy-integer
contracts, so *no runtime extraction is justified by this FTR*. A likely future
home, if a second consumer appears, is `src/spreadsheet_handling/domain/tabular`,
beside but separate from the physical-label helper
(`domain/tabular/physical_labels.py`).

== Pattern catalogue (authorized, not written here)

Slice 1 authorizes a compact developer-facing catalogue; the Developer Guide
slice writes it. Each pattern must document: intent; when to use; when not to
use; a minimal idiomatic example; review questions; search terms for deeper
self-directed explanation. The catalogue must let a competent developer or an
AI-assisted novice grasp why a pattern exists without mastering metaclasses or
the full data model. No long tutorials belong in the FTR.

Initial patterns (add/merge/rename during implementation as evidence warrants):

. *Exact built-in value boundary* -- reject subclasses when subclass behaviour is
  outside the contract. Search: `Python exact type check`, `subclass rejection`,
  `value-object boundary`, `Liskov substitution trade-off`.
. *Normalize at ingress* -- validate an accepted carrier type, convert to a
  canonical internal value immediately. Search: `canonicalization`,
  `NumPy scalar normalization`, `anti-corruption layer`.
. *Defensive ownership copy* -- copy a retained caller-owned container. Search:
  `defensive copy`, `aliasing`, `effective immutability`,
  `frozen dataclass mutable members`.
. *Safe diagnostics* -- report context without unsafe `repr`/type introspection
  of the invalid value. Search: `hostile repr`, `diagnostic side effects`,
  `exception hygiene`.
. *Validate then commit* -- build and validate the complete candidate before
  publishing mutation or metadata. Search: `failure atomicity`,
  `two-phase update`, `strong exception guarantee`.
. *Narrow semantic helper* -- extract only for a shared semantic identity
  contract. Search: `semantic DRY`, `primitive obsession`,
  `accidental semantic coupling`.

== Review policy (enforceable)

Feature and FTR reviews *apply* this repository-wide policy; they do not redefine
it per feature.

A review *may and must* still report a concrete violation of an explicit,
documented contract even when the probe is adversarial -- immutability,
deterministic ordering, exact identity, deliberate diagnostics, failure
atomicity, or "no mutation of the documented caller graph". These are
correctness findings, not threat-model expansion, and this policy must never be
cited to suppress them.

A review *must not*:

* silently expand a feature's threat model;
* require containment of arbitrary in-process hostile Python;
* treat every special-method edge case as release-blocking;
* demand a shared helper without proving shared semantics;
* let hardening obscure the domain flow without explicit justification.

When a review uncovers an unresolved repo-wide policy gap, it must:

. separate the concrete feature defect from the broader question;
. judge the feature against the *currently approved* contract;
. record the broader question for a separate clarification;
. not embed a new permanent policy in the acceptance artifact alone.

== Runtime boundary

No runtime change is authorized in Slice 1. Existing code may be *inspected and
classified* as evidence only. Do not introduce a universal safe-value framework,
a repository-wide exact-type conversion refactor, mass pandas field-selection
changes, broad exception-wrapper utilities, or migration of feature-local
helpers without a demonstrated second consumer. Any runtime extraction requires
its own narrow FTR (or an explicitly reviewed extension of this one) with fresh
evidence.

== Slicing

*Slice 1 -- Policy and pattern clarification (documentation-only).* Deliver the
four artifacts above. No runtime change.

*Later targeted slices -- only on demonstrated evidence.* Create only if a
concrete second consumer or contract drift is found. Non-approved examples: a
shared exact configured-field-reference helper; a shared carrier-scalar
normalization helper; a shared safe-diagnostic-context helper; an architecture
guard against prohibited broad exception translation.

== Acceptance criteria

Slice 1 is complete when:

* the framework/workflow-builder responsibility split is explicit and neither
  side excuses the other;
* the threat-model boundary is stated and proportionate, and validation
  robustness is distinguished from actual security isolation;
* robustness guarantees and explicit non-guarantees are normative and reviewable;
* adversarial hardening has explicit proportionality and readability limits;
* semantic-DRY criteria are defined and no premature generic helper is created;
* the pattern catalogue is authorized with its required per-pattern structure;
* review guidance cannot be read as suppressing legitimate correctness findings;
* the four artifacts exist with the ownership above and cross-link the existing
  ADR and cold-storage inquiry;
* no unapproved runtime refactor is introduced;
* all changed AsciiDoc renders cleanly and `git diff --check` passes.

All criteria are verifiable by document inspection and rendering.
