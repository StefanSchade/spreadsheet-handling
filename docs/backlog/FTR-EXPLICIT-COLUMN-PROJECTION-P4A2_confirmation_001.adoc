== Purpose

State, precisely enough that a fresh implementation context need not redesign
anything, whether replacing `project_by_role` with an explicit
column-projection contract is ready for implementation, and if so under what
exact contract.

== Decision

*Do not replace `project_by_role`, and do not add a `project_columns` step.*

The requested transformation ("implicit `project_by_role` -> explicit column
projection") is not implementable as a bounded, evidence-supported slice,
because:

. The essential behaviour of `project_by_role` is resolving a *dynamic*
  `matrix_value` column set (rest-by-exclusion) that is unknowable at
  YAML-authoring time, plus a *direction-coupled* drop of `display_helper` on
  the inbound path. An explicit ordered column list cannot express either.
. An explicit, static, ordered column-projection primitive already exists:
  `extract_frame` (`columns:`). A new `project_columns` step would duplicate
  it.
. `project_by_role` has *no* `core` runtime consumer; its only real consumer is
  the external `worldbuilding` pipeline (out of scope). There is nothing in
  this repository to migrate, and the external consumer cannot migrate to
  explicit columns.
. The role-over-explicit-columns choice is a *recorded accepted decision*
  (`FTR-DYNAMIC-FRAME-PROJECTION-P5_decision.adoc`); the driver evidence showed
  explicit positional column reconstruction was the problem being removed, not
  the solution.
. The owning FTR (`FTR-DYNAMIC-FRAME-PROJECTION-IMPL-P5`) is still open.

== What remains true (kept as-is)

[cols="1,3"]
|===
| Surface | Status

| `project_by_role` callable + registry entry
| Retained unchanged. Role-based, in-place, `outbound`/`inbound`.

| `extract_frame`
| Retained as the explicit static column-projection primitive
  (`columns`, `rename`, `where`, `sort_by`, `constants`).

| Column-role resolver + taxonomy
| Retained. Single source of truth for `project_by_role` and `add_validations`
  role targeting.

| Owning FTR
| Closed through its own lifecycle, not through this work.
|===

== Contract table (current, authoritative -- no changes proposed)

[cols="1,3"]
|===
| Aspect | `project_by_role` (unchanged) -- and why explicit projection cannot replace it

| Callable
| `spreadsheet_handling.domain.transformations.project_by_role:project_by_role`

| Pipeline step
| `project_by_role` (`category: primitive`, `subtype: role_based_projection`,
  `status: current`, `factory_shape: frames_target`)

| Parameters
| `frame` (req, str), `direction` (req, `outbound`\|`inbound`),
  `helper_columns` (opt list), `key_columns` (opt list),
  `role_order` (opt list of role names), `name` (opt, discarded)

| Types
| `frames: Mapping[str, Any] -> Frames`; overrides are string sequences

| Defaults
| outbound order `[display_helper, row_identity, matrix_value]`;
  inbound order `[row_identity, matrix_value]`; no default `direction`

| Errors
| `ValueError` (missing/invalid `direction`, invalid/duplicate/non-permutation
  `role_order`, `display_helper` in inbound `role_order`, blank `frame`);
  `KeyError` (frame absent); `TypeError` (non-DataFrame frame);
  `UnknownRoleError` (unknown role); `ValueError` (ambiguous xref match)

| Mutation
| None. Returns a new `frames` dict; target frame replaced by a `.copy()`.
  Caller frames are not mutated.

| Metadata
| Read-only: `xref_crosstable`, `workbook_view`, `sheets`,
  `derived.sheets.*.helper_columns`. Writes nothing. No persisted role channel.

| Registry
| `registries/pipeline_step_registry.json` `project_by_role`; gated YAML
  surface per `interfaces_and_gates.adoc:26`

| Migration
| *None.* No in-repo consumer. Explicit projection cannot express dynamic
  `matrix_value` or directional drop, so migration is impossible, not merely
  unnecessary.

| Deletion / deprecation
| *None.* Not superseded; sole consumer is external and non-migratable.
|===

Why an explicit `project_columns(frame, columns=[...])` fails the same table:
it would require the author to enumerate every `matrix_value` column, which do
not exist until runtime, and would still need a separate mechanism for the
inbound `display_helper` drop -- reproducing the role model it claims to
replace.

== Missing / duplicate / empty-column policy (for reference)

If any future *static* need arises, `extract_frame` already sets the
conventions: strict on missing columns (raises), strict on duplicates (raises),
empty `columns` list rejected, `columns: None` = pass-through. No new policy
matrix is introduced.

== Terminal verdict

EXPLICIT COLUMN PROJECTION NOT READY FOR IMPLEMENTATION
