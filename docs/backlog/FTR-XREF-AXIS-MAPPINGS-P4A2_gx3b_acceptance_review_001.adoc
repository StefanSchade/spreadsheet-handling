== Verdict

*GX-3b is accepted.* The forward and reverse boundaries match the intended
GX-3b shape exactly:

* forward `GroupedMatrix -> grouped_matrix_to_exact_table -> TableBlock.header_grid
  -> existing XLSX rendering`;
* reverse `exact TableBlock -> core.ExactTable -> reconstruct_grouped_matrix ->
  GroupedMatrix -> unchanged expand_grouped_xref`.

No persisted mapping, grouped `_meta`, `MultiIndex` identity model, private frame
name, or ODS behavior is introduced. All required review areas pass. One *minor*
finding (release-notes checkpoint) and four observations are recorded; none block
acceptance.

=== Observations

* *GX3b-A-O1 (forward pairing residual is out-of-model).* `grouped_matrix_to_exact_table`
  proves only structural width equality (`frame.shape[1] == len(header.columns)`)
  and reads headers from `GroupedHeader` and data from `frame.values` by
  position. A same-width *positional data reorder* of the carried DataFrame would
  render header/data out of alignment, but this requires unsupported direct
  in-process rearrangement of the carrier's internal frame schema: the frame
  binding is frozen (foreign-frame substitution is blocked), `grouped_matrix_from_canonical`
  proved the pairing at construction, no registered step reorders a carrier's
  internal columns, and column *rename* has no effect on projection. This matches
  the accepted GX-1/GX-2 boundary; a live mapping in the forward composer is not
  warranted.
* *GX3b-A-O2 (workbook-view narrowing).* Explicit `workbook_view.sheets` selection
  rejects a `GroupedMatrix` (`rendering/frame_selection.py:57-60` requires a
  `DataFrame`). The default (no `workbook_view`, or a `workbook_view` without
  `sheets`) passes the carrier through. GX-5 adoption owns broadening; see below.
* *GX3b-A-O3 (unknown tuple surfaces `AxisMappingError`).* An unresolvable visible
  tuple propagates the resolver's own `AxisMappingError` rather than
  `GroupedXrefError`. This is the documented layering convention (`matrix.py`:
  "resolver failures stay `AxisMappingError`") and is consistent with GX-2, not a
  defect.
* *GX3b-A-O4 (registry category label).* The confirmation §3 informally named the
  category `transformation`; the implementation used `primitive`. `primitive` is a
  valid vocabulary term (the most common category, 28 entries) and `transformation`
  is not in the contract vocabulary at all, so the implementation is correct and
  the mirror/guard tests pass. No action.

== Forward pairing conclusion

`grouped_matrix_to_exact_table` (`grouped_xref/matrix.py:156`) produces data and
visible headers in the same physical column order for all supported construction:
data is `frame.values` in physical order; the grid is built from
`header.columns[i]` at position `i` (`RowKeyColumn` -> leaf label with blank
uppers; `DynamicColumn` -> `labels[level]`, repeated literal labels, no merges);
canonical dynamic keys are never read for display. Probes confirmed: edited data
values are preserved and rendered (supported); a dropped column is rejected by the
width guard; a column rename has no effect (frame labels are ignored);
foreign-frame substitution is blocked by the frozen carrier. The only way to
produce a silent same-width mispairing is unsupported in-process rearrangement of
the carrier's internal frame (GX3b-A-O1). *Forward pairing is safe within the
supported public/pipeline surface; no forward live mapping is required.*

== ExactTable boundary conclusion

`core.ExactTable` (`core/exact_table.py`) is a frozen, leaf-only dataclass
holding only built-in `str`/`Any` tuples and ints; it imports no pandas,
rendering, domain, openpyxl, or ODS type, and `test_core_modules_remain_leaf_only`
passes. `__post_init__` normalises header cells (`None -> ""`, non-string ->
`str`) -- verified: `header_grid=((None, 123), ...)` normalises to `(("", "123"),
...)`. It is the single exchanged exact-table value in both directions (no second
descriptor/frame pair). The constructor performs no geometry validation; instead
`reconstruct_grouped_matrix._validated_geometry` rejects malformed geometry at the
domain reconstruction boundary. Probes confirmed rejection of: header-depth
mismatch, `header_rows` vs grid disagreement, non-rectangular header, data-width
mismatch, and zero header rows/columns. *Invalid manual construction is caught at
the correct boundary without unnecessary constructor validation.*

== Data-typing conclusion

The repository's established XLSX read contract *stringifies every data cell*:
an ordinary typed DataFrame (`int64`/`float64`/`bool`/`date`/blank) round-trips
back as `str` (`'1'`, `'1.5'`, `'True'`, `'2026-08-01 00:00:00'`, `''`). The
GX-3b exact path is byte-identical to an equivalent ordinary read of the same
matrix for int, float, bool, blank, and date cells (probes compared both paths on
the same values). *GX-3b does not regress supported typing relative to an
equivalent ordinary workbook read;* no type preservation beyond the established
contract is claimed or required.

== Reverse reconstruction conclusion

`reconstruct_grouped_matrix` (`grouped_xref/reconstruction.py`) was verified to:
require an `ExactTable` input (bare DataFrame rejected); validate rectangular
geometry and configured depth (`len(header_grid) == len(label_columns)`); identify
row keys by unique leaf label (not blank shape); require blank upper cells above
row keys; forward-fill only non-row-key columns via the accepted GX-3a
`forward_fill_header_grid`; use no delimiter join/split; resolve *exactly one*
live mapping (monkeypatch counter = 1) feeding `key_for_labels`,
`build_grouped_header`, and the factory; reject unknown, duplicate, and incomplete
tuples; build columns/data in physical order; construct the result only through
`grouped_matrix_from_canonical`; and publish atomically (`out = dict(frames)` only
after full success -- on failure the input mapping and `_meta` are untouched and
`output` is never added). `drop_source` removes the input frame and rejects
`table == output`. A missing source frame fails (`AxisMappingError`) rather than
trusting stale text. Arity 2 and 3, moved/multiple row keys, reordered dynamic
columns, valid deletion, and edited values all reconstruct correctly end to end.

== Row-key and forward-fill handling

Probed and confirmed: two adjacent row keys; a row key between dynamic columns; a
leading dynamic blank (rejected as incomplete); a blank immediately after a
skipped row-key column (fill does *not* cross the row key -> incomplete ->
rejected); a duplicate leaf label shared by a row key and a dynamic column
(rejected as multi-match); and a non-blank upper cell above a declared row key
(rejected). `forward_fill_header_grid` resets its carry at every skipped column,
so a fill run never crosses a row-key column and an incomplete tuple can never be
silently completed into an unrelated valid tuple.

== Registry / API conclusion

Runtime `REGISTRY["reconstruct_grouped_matrix"]`
(`pipeline/registry.py`, `StepRegistration(make_frames_target_step, target=...)`)
and the JSON mirror agree on signature, `frames_target` factory shape,
parameters, frame contract (`reads: [table, source_frame]`, `writes: [output]`,
`preserves: [source_frame]`), empty `meta_contract`, and a truthful
`inverse` (`kind: projection_only`, `inverse_step: null`, reason names the
`compose_workbook` grouped projection). `drop_source` is documented as caller-
asserted. YAML `name` is the step name only; the XRef config identity
(`xref_config_id`) is deliberately not consumed here (GX-3b ends at
`GroupedMatrix`). The registry mirror and signature guards pass under
`tests/architecture`.

== Layering conclusion

The deliberate edge `rendering.composer -> domain.transformations.grouped_xref`
(composer detects a `GroupedMatrix` and calls the pure projection helper) is
consistent with the outer-to-inner hexagonal direction; no active guard forbids
`rendering` importing `domain`, and the full `tests/architecture` suite passes.
It does not create a cycle: `domain` imports no `rendering`/`io_backends`
(reconstruction imports only `core` and sibling grouped-XRef modules), `core`
stays leaf, and openpyxl types do not escape the XLSX adapter (the exact data
originates from the already-projected IR). The dispatch is bounded to one
documented carrier through one pure helper; it does not establish an uncontrolled
per-feature branching pattern in generic rendering. No ODS code changed and no
grouped-metadata/persistence change exists.

== Workbook-view limitation ownership

The limitation (explicit `workbook_view.sheets` selection rejects a
`GroupedMatrix`) is a *valid GX-3b scope boundary*, not a break of the forward
public path: the normal supported workflow (no `workbook_view`, or one without an
explicit `sheets` list) passes the carrier straight to `compose_workbook`, as the
shipped end-to-end test and independent probes exercise. Broadening explicit-sheet
selection to grouped carriers is GX-5 adoption responsibility. Recorded as
observation GX3b-A-O2.

== Complexity / sizing

GX-3b remains the intended small shape: one neutral carrier (`core.ExactTable`),
one forward projection helper (`grouped_matrix_to_exact_table`), one reverse
domain step (`reconstruct_grouped_matrix`), one composer dispatch branch, one
registry entry (runtime + JSON). Actual: ~330 runtime LOC across the expected
files; public surface = 1 type + 1 step (+1 forward helper) + 1 registry entry.
The `compose_workbook` source-style WARN (93 lines / complexity 18) is the
pre-existing helper marginally extended by the bounded dispatch; the source-style
guard returns rc 0. No generic workbook framework or speculative hardening is
present or warranted.

== GX-4 readiness

GX-3b leaves a clean seam for GX-4 (ODS): `core.ExactTable` and
`core.header_grid.forward_fill_header_grid` are backend-neutral, so an ODS exact
reader can populate `TableBlock.header_grid` and reach the identical
`reconstruct_grouped_matrix` step with no grouped-domain change. The forward
composer already emits an exact `TableBlock` independent of backend. The two
carry-forward items for GX-4/GX-5 are the release-notes consolidation (GX3b-A-M1)
and explicit-`workbook_view.sheets` grouped-carrier adoption (GX3b-A-O2).
