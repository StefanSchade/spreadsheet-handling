===== FTR-FK-HELPERS-ENRICH-READABILITY-PILOT-P5 -- FK Helpers Human Readability — Enrichment Pilot

*Status:* New — implementation not started

*Priority:* P5 (before-low-touch maintainability)

*Area:* `domain/transformations/fk_helpers/enrich.py`

*Type:* Bounded, behavior-preserving human-readability pilot. Single-module
scope. No public contract, persisted-schema, compatibility, or architecture
change.

==== 1. Status

Implementation has not started. This FTR authorizes only a narrow local pilot in
`enrich.py` (Slice 1) plus a post-Slice-1 read-only package assessment gate
(Slice 2). No later implementation slice is authorized yet. See the progress
table (section 23).

==== 2. Context

The FK-helper package was made policy-driven by
`FTR-FK-HELPERS-POLICY-DRIVEN-PRIMITIVES-P5` and split into modules by
`FTR-DOMAIN-TRANSFORMATION-MODULE-SPLIT-FK-HELPERS-P5`. During unrelated
refactoring, a human-readability review of the package was recorded in warm
storage and then revalidated against the current tree. `enrich.py`'s central
function `enrich_helpers` is structurally sound (clear phased orchestration) but
carries a cluster of *local* reader costs: a raw options bag resolved inline
across scattered call sites, historical sheet-vs-frame local vocabulary, and a
helper called with a whole dictionary when it needs one value.

This FTR converts the frequently revalidated *category-1* (local internal
cleanup) findings that are concentrated in `enrich.py` into one bounded,
behavior-preserving pilot, and defers everything that touches a public contract,
a persisted schema, a compatibility surface, another module, or an architecture
decision.

==== 3. Authority and relationship to the two warm-storage reviews

Two committed warm-storage artifacts are the authoritative evidence:

* Original rationale, positive patterns, non-findings, and candidate rules:
  `docs/warm_storage/global_reviews/review_001_fk_helpers_human_readability.adoc`.
* Current-state authority (dispositions, blast-radius, public-contract
  inventory, first-slice recommendation):
  `docs/warm_storage/global_reviews/review_001_fk_helpers_human_readability_revalidation_001.adoc`.

Neither review is modified or moved by this FTR.

==== 4. Problem statement

Stated as observable reader cost, not as an assumed solution:

A reader opening `enrich_helpers` today cannot locally answer, without
unnecessary archaeology into broad dictionaries and historical terminology:

> Which pipeline inputs does this operation actually depend on; which values are
> raw authored config versus resolved runtime values; which local objects are
> domain frames versus workbook sheets; and what each private helper actually
> consumes?

Concretely:

* `defaults: dict[str, Any]` is a raw options bag; defaults, normalization, and
  validation for `detect_fk`, `levels`, and `helper_value_mode` are applied by
  separate `defaults.get(...)` expressions scattered through the body
  (`enrich.py:44,51,52`). The effective input contract is reconstructable only
  by reading the whole function.
* `_helper_value_mode(defaults)` receives the entire bag but reads a single key
  (`enrich.py:52,163`), hiding its real dependency.
* Local variables (`sheet_name`, `sheet_relations`, `sheet_defs`,
  `fk_defs_by_sheet`, `target_registry`) name domain frames and an execution
  lookup index in historical workbook-sheet / broad-registry vocabulary
  (`enrich.py:68,83-94,102-117`), pulling the reader toward the wrong layer.

The core question this FTR must answer for `enrich.py` is: *can the reader
reconstruct inputs, states, dependencies, domain vocabulary, and orchestration
locally, without behavioral drift?*

==== 5. Goals

* Make the raw→resolved configuration boundary explicit and local at the top of
  `enrich_helpers`, with names that distinguish raw authored config from
  resolved runtime values.
* Give each private helper input as narrow as its actual dependency.
* Use domain (frame) vocabulary for local variables that hold domain frames, and
  an execution-purpose name for the local lookup index.
* Reduce contract archaeology in `enrich.py` with zero behavioral change.

==== 6. Non-goals

* No behavior change of any kind (see invariants, section 15).
* No change to public YAML, accepted config keys, defaults, or helper-mode
  aliases.
* No change to persisted `_meta` shapes or FK policy version semantics.
* No change to registries or registered/meta-pinned symbol paths.
* No cross-module edits (`policy.py`, `formula_provider.py`, `provenance.py`,
  `core.fk`, consumers) for consistency or otherwise.
* No introduction of a general readability framework or a repository style guide.
* No dataclass/`TypedDict` introduced to replace dictionaries cosmetically.

==== 7. Selected revalidated findings (Slice 1)

All selected findings are currently valid, category-1 (local internal cleanup),
behavior-preserving, concentrated in / owned by `enrich.py`, and independent of
public-contract, persisted-schema, compatibility, or architecture decisions.
They form one coherent reader-facing improvement: *make the local contract and
vocabulary of `enrich_helpers` reconstructable in place.* Their identities
remain distinct even though one resolution boundary may address several.

[cols="1,3,3"]
|===
| Finding | Local reader cost | Why behavior-preserving

| FK-HR-005 | `defaults` bag mis-named; input contract hidden in scattered `.get()` calls. | `enrich_helpers` consumes only `detect_fk`, `levels`, `helper_value_mode` from `defaults`; resolving them once, preserving every key/default, changes nothing observable.
| FK-HR-006 | Default/normalization/validation distributed across `enrich.py:44,51,52`. | Same reads, same order-independent results, gathered at one boundary.
| FK-HR-007 | `_helper_value_mode(defaults)` hides that it reads one key. | Passing the raw mode string instead of the bag yields identical normalization/validation.

|===

==== 9. Explicitly deferred: FK-HR-012 and FK-HR-016

==== 11. Positive patterns to preserve (acceptance condition)

Preservation of these revalidated positive patterns is an explicit acceptance
condition. All are currently present in `enrich.py` and must remain, with their
comments and structure intact:

* *FK-HR-POS-002* — phased orchestration (relation filtering → target lookup
  prep → source grouping → strategy selection → per-frame work-item derivation →
  shared id-map build → frame processing → provenance write).
* *FK-HR-POS-001* — replay-safety filter and its non-local contract comment
  (`enrich.py:54-66`) explaining why skipping an absent-target relation is a
  safe no-op.
* *FK-HR-POS-003* — `_preserve_source_flatness` and its docstring/behavior
  (`enrich.py:130-160`).
* *FK-HR-POS-004* — backend-neutral formula intent (formula-mode path installs a
  spec-producing provider, not backend syntax).
* Separation of preparation, materialization, shape preservation, and provenance
  writing must remain visible as distinct phases.
* The second explicit no-op (header-absent skip, `enrich.py:88-92`) and its
  comment must remain.

==== 12. Non-findings protected from mechanical rewriting

Slice 1 must not rewrite these idioms merely to look less Pythonic; the
revalidation confirmed each remains readable in context:

* tuple unpacking (`enrich.py:68`);
* `dict.setdefault` grouping (`enrich.py:75`);
* the replay-filter list comprehension (`enrich.py:62-66`);
* the bounded conditional expression for strategy selection (`enrich.py:77-81`);
* closure-based provider construction (installed at `enrich.py:77`, defined in
  `formula_provider.py`).

Expanding any of these into Java-shaped loops or plumbing is out of scope and a
stop condition.

==== 13. Slice-1 exact scope

Implementation and focused characterization only, confined to `enrich.py`:

* Introduce one explicit, local configuration-resolution boundary near the top
  of `enrich_helpers` that reads the three consumed keys (`detect_fk`, `levels`,
  `helper_value_mode`) once, applying the existing defaults and the existing
  `helper_value_mode` normalization/validation, and exposes them as clearly
  named resolved values (FK-HR-005, FK-HR-006).
* Narrow `_helper_value_mode` to receive the raw mode value it actually reads,
  rather than the whole bag (FK-HR-007).
* Rename the local `target_registry` variable to an execution-purpose name
  (e.g. a lookup-index name); do *not* rename `build_v2_target_registry`
  (FK-HR-011, local only).
* Rename `enrich.py`-local `sheet_*` variables that hold domain frames to
  `frame_*` (FK-HR-017 + enrich.py-local part of FK-HR-009).

Out of Slice-1 scope (hard boundary): any edit outside `enrich.py`; any type
annotation belonging to FK-HR-012; any change to `_preserve_source_flatness`;
`detect_fk`/`helper_value_mode` values; `schema_version`; the adapter shape;
`FKDef`; the provider strategy contract; any re-exported or registered symbol.

The implementation agent derives the exact resolved-value shape from the code
(see section 16); this FTR does not prescribe one.

==== 15. Behavior invariants (Slice 1)

No invariant may be relaxed because the change is "only readability." Derived
from the current implementation and its tests:

* *Public step:* `add_fk_helpers` step id and registration
  (`pipeline_step_registry.json`, `meta_registry.yaml`) unchanged; the
  registered/meta symbol paths `enrich_helpers`, `drop_helpers`,
  `_write_helper_provenance` unchanged.
* *Accepted config keys:* `detect_fk`, `levels`, `helper_value_mode` still read
  from the same `defaults` mapping with the same key names.
* *Defaults:* `detect_fk` defaults to `True`; `levels` to `3`;
  `helper_value_mode` to `"values"`.
* *Helper-mode aliases:* `{"value","values"}` accepted as value mode;
  `{"formula","formulas"}` accepted as formula mode; unknown modes raise
  `ValueError` mentioning `helper_value_mode`.
* *`detect_fk` kill switch:* when false, `enrich_helpers` returns the input
  `frames` object unchanged (identity), before policy resolution.
* *Missing-policy behavior:* absent v2 policy raises
  `MissingFkRelationPolicyError` naming `add_fk_helpers` and the producer steps.
* *Unsupported/v1-policy behavior:* a policy without `schema_version: 2` is
  treated as missing (raises the same error mentioning `schema_version: 2`);
  malformed non-list `relations` still raises the malformed-list `ValueError`.
* *Replay-safe skipping:* relations whose `target_frame` is not among the loaded
  data frames are skipped as a no-op.
* *Relation selection / grouping:* relations grouped by `source_frame`; a source
  frame lacking the configured FK header is passed through untouched.
* *Value mode:* helper columns materialized from id→value maps.
* *Formula mode:* helper columns materialized as `lookup_formula` specs, one per
  row, via the installed provider closure.
* *Helper column values, order, and lookup behavior:* identical to current
  output for all modes.
* *Source-frame copy semantics:* input frames not mutated; a new `out` mapping
  is returned; reserved (`_`-prefixed) frames copied via `copy_reserved_frames`.
* *Flat-frame preservation:* a flat source frame stays flat after enrichment
  (`_preserve_source_flatness`).
* *Genuine MultiIndex preservation:* genuinely multi-level frames are left
  untouched by the flatness repair.
* *Helper provenance:* `_meta.derived.sheets.<frame>.helper_columns` written /
  pruned exactly as today.
* *Partial frame-set behavior:* runs missing some target frames behave as today
  (skip + no crash).
* *Error types and messages* where contractually relevant (the two `ValueError`
  paths above and `MissingFkRelationPolicyError`) are unchanged.

==== 16. Implementation-form neutrality

The FTR does not prescribe an internal representation. The implementation agent
inspects the current code and selects a form, which may include: local variable
extraction; narrower helper parameters; private current-semantic renaming; one
explicit configuration-resolution boundary; a small internal immutable value
object; explicit resolved scalar values; or private helper/callback naming.

The chosen form must be justified against: local readability; number of concepts
introduced; call-site clarity; lifecycle-state visibility (raw vs resolved);
compatibility surface (none may change); and preservation of the positive
orchestration.

Prohibited: introducing types merely to replace dictionaries cosmetically;
breaking one readable phase into many tiny helpers; moving archaeology into a new
abstraction; building a general framework for future readability work; editing
other FK-helper modules for consistency.

Note: because `enrich_helpers` consumes only three scalar keys, "explicit
resolved scalars" and "a small internal value object" are both admissible; the
agent must not default to a value object without showing it beats explicit
scalars on the criteria above.

==== 18. Human-readability acceptance criteria

Slice 1 is accepted only if a reviewer can answer the following from the
resulting `enrich.py` with *less* non-local investigation than today. The
acceptance test is reduced contract archaeology without behavioral drift — not
fewer lines, more helpers, more dataclasses, fewer comprehensions, or fewer
dictionaries in the abstract.

. What raw pipeline inputs enter the operation?
. Where are defaults, normalization, and validation applied?
. What resolved values drive execution?
. Which local objects are domain frames and which are workbook sheets?
. Which structures are authoritative policy and which are execution adapters?
. Which dependency does each private helper actually consume?
. Where does actual helper materialization occur?
. Where does shape preservation occur?
. Where is provenance written?
. Which historical compatibility behavior remains, and why?

If the proposed code is merely *different* rather than demonstrably easier to
explain against these questions, it must not be merged (stop condition).

==== 20. Stop conditions

Stop and escalate (revise the FTR) if any of the following becomes true:

* a selected change would alter public YAML or accepted mode aliases;
* a current caller imports a symbol assumed private (verify before renaming);
* a local rename would cross a package/public boundary;
* a clearer contract would require deciding FK policy `schema_version` semantics;
* the target-registry adapter shape would have to change;
* `FKDef` would have to change;
* source-flatness ownership would have to change;
* a new relation model would be required;
* the implementation would expand beyond `enrich.py` and the narrowly necessary
  tests without explicit FTR revision;
* behavior cannot be characterized adequately by existing or minimal added tests;
* the proposed code is merely different, not demonstrably easier to explain
  (section 18).
