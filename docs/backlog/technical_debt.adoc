= Technical Debt Register

This document tracks active technical debt that is intentionally not
resolved in the current change set. Each entry names a follow-up FTR or
a containment strategy.

Entries listed here are observed gaps with a clear owner and a known cost,
not speculative ideas. Speculative or exploratory items belong in the
phase-grouped FTR backlog under ``docs/backlog/_ftrs_open.adoc``.

== TD-IOR04-ODS-CALC-FORMULAS -- ODS/calc FormulaSpec rendered-content assertion

*Status:* Open

*Severity:* Low

*Area:* ODS/calc integration coverage / FormulaSpec rendering

*Origin:* Independent review,
``docs/cold_storage/reviews/topic_reviews/io_backend_reviews/ior04_execution_state_boundary_correction_review_2026-09-18.adoc``
(W2; review commit `da72bda1f100da1bc8948ae7c4917b58ab54c89e`)

*Summary:*

The real `orchestrate` path is exercised for `ods` and `calc`, covering
successful authorization and persistence. The integration test currently
asserts file creation for those sinks but not the rendered FormulaSpec
formula-cell content; `xlsx` does verify formula content. This gap predates
the accepted IOR-04 boundary correction.

*Risk:*

A future regression could preserve successful file creation while changing or
losing FormulaSpec rendering semantics for `ods` or `calc` without this test
detecting the content error.

*Why not fix now:*

This is optional test hardening, not work required for the accepted IOR-04
architecture correction. There is no current evidence of incorrect ODS/calc
rendering.

*Expected resolution shape:*

Add focused rendered-content coverage for ODS/calc through the appropriate
integration or roundtrip seam, without prescribing implementation beyond the
current repository evidence.

*Promotion rule:*

No FTR is needed unless investigation reveals a materially broader rendering
or serialization design issue.

== TD-IOR04-EXECUTION-STATE-RELATIVE-IMPORT-GUARD -- execution_state architecture guard relative-import coverage

*Status:* Open

*Severity:* Low

*Area:* Architecture-test dependency enforcement

*Origin:* Independent review,
``docs/cold_storage/reviews/topic_reviews/io_backend_reviews/ior04_execution_state_boundary_correction_review_2026-09-18.adoc``
(W5; review commit `da72bda1f100da1bc8948ae7c4917b58ab54c89e`)

*Summary:*

The existing architecture guard protects `pipeline.execution_state` from
forbidden dependencies such as `io_backends`, but its AST/import matching
currently checks absolute import-module prefixes. An equivalent forbidden
relative import such as `from ...io_backends import router` may evade that
static check. The accepted IOR-04 correction does not exploit this weakness,
and the current dependency boundary is clean.

*Risk:*

A future change could introduce a forbidden dependency using relative-import
syntax without this particular guard detecting it.

*Why not fix now:*

This is optional architecture-test hardening. The production dependency
boundary is restored and independently validated, and this item is not needed
for IOR-04 closure.

*Expected resolution shape:*

Strengthen the architecture guard so equivalent forbidden relative imports are
detected, while preserving the existing dependency rule rather than redesigning
it.

*Promotion rule:*

No FTR is needed unless implementation exposes a broader architecture-
enforcement design problem.

== TD-META-LIFECYCLE-INVENTORY -- _meta lifecycle classification incomplete

*Status:* Open

*Severity:* Medium / High

*Area:* Metadata lifecycle / persistence boundary

*Origin:* ``BUG-RUNTIME-META-PERSISTENCE-BOUNDARY-P4A``

*Tracking FTRs:*

* `FTR-META-LIFECYCLE-INVENTORY-P5` -- full inventory
* `FTR-FK-HELPER-POLICY-LIFECYCLE-P4A` -- FK-helper-specific classification

*Summary:*

The current fix establishes a narrow persistence boundary in the
orchestrator and removes the known runtime-produced FK-helper v2 relation
carrier under ``helper_policies.fk.relations``. It does not complete a
full lifecycle classification of all ``_meta`` roots.

Until the inventory is done, new ``_meta`` producers must be conservative
and document whether their output is persistable, runtime-only, derived,
carrier-specific, or user-authored. Reviewers should treat any new
top-level ``_meta`` key as a flag for "needs classification" and either:

* extend the projection rules in
  ``src/spreadsheet_handling/pipeline/persistence_boundary.py`` with an
  explicit named rule, or
* document the key as a persistable canonical entry with a citation in
  the lifecycle chapter and the registry.

*Why not fix now:*

The complete classification is a structural change that touches the
registry, the lifecycle chapter, the architecture guards, and several
producers. Doing it before the next release would extend scope beyond
what the worldbuilding adoption surfaced and would conflict with the
deliberate "release-near" framing of the bug fix.

*Containment until resolved:*

* The orchestrator-owned projection in
  ``pipeline/persistence_boundary.py`` is the single chokepoint.
* New runtime-only top-level keys must be added to
  ``RUNTIME_ONLY_TOP_LEVEL_META_KEYS`` (or covered by an equally
  explicit rule).
* The ``__*`` root-level filter catches accidental new
  rendering/carrier artifacts.
* Consumer-side meta-stripping plugins are explicitly out of policy --
  the boundary belongs in core.

== TD-TRUSTED-INGRESS-INVARIANT-NAVIGATION-INDEX -- no machine-readable navigation index for the 48 condensed Trusted Ingress invariants

*Status:* Open

*Severity:* Low

*Area:* Documentation navigation / Trusted Ingress condensation

*Origin:* `FTR-TRUSTED-INGRESS-DOCUMENTATION-CONDENSATION-P4A` (Slice C+D+E),
per its own task section 9 ("Machine-readable contract / invariant index
question").

*Summary:*

The accepted condensation design's canonical inventory names 48 Trusted
Ingress invariants (categories A-H), each with a *nature* classification
(directly accepted authority / faithful synthesis / derived maintainer rule
/ new explanatory framing), a canonical owning document, and a semantic
anchor. The complete A+B+C+D+E condensation promotes every one of those 48
into prose: Slices A+B promoted categories A-G into the Semantic Model and
Technical Model; Slices C+D+E added category H's maintainer guidance
(Developer Guide) and the public-surface/history/navigation ownership
(`interfaces_and_gates.adoc`, Project Evolution, cross-document
navigation). None of the 48 is orphaned. What does *not* exist is a
structured, machine-readable
navigation index over that inventory -- something that could answer "which
permanent document and anchor owns invariant C7" without grepping prose.

*Registry fit investigated:*

* `registries/meta_registry.yaml` and `registries/pipeline_step_registry.json`
  are runtime-mirroring inventories of `_meta` fields and pipeline steps
  respectively (`docs/semantic_model/09_registry_role.adoc`); neither has any
  concept of a normative "invariant" or a nature classification, and both are
  explicitly scoped away from general architectural-contract statements.
* `registries/domain_contracts/` (canonical/staging JSON tables, rendered via
  `tools/domain_contracts/render_contracts.py` and gated by
  `make domain-contracts-check`) is the closest existing structured-contract
  machinery. It is explicitly *transformation*-centric by its own README
  ("transformation contracts are the anchor") and its `RULE-DOMAIN-CONTRACTS-
  NON-RUNTIME` note scopes it to "documentation and review infrastructure
  only in this slice." Its `requirements.json` schema
  (`id, status, capability_family, statement, user_visible_effect,
  source_kind, source_ref, notes`) has no `nature` field and no
  owner-document/anchor field, and its only populated rows today are two
  transformation-shaped seeds -- reusing it as-is would either misuse
  `capability_family` to mean something it does not, or require a schema
  change plus matching `check_contracts.py`/`render_contracts.py` additions.

*Why not fix now:* per the governing task, adding a new table schema, a new
`check_contracts.py` entry, and generated-view changes to accommodate 48
navigation-only entries is more than a documentation-only condensation slice
should absorb, and risks creating a second normative authority or
overloading `domain_contracts`' existing transformation-centric semantics if
done hastily.

*Smallest future option:* a small, purely additive sibling table (for
example `registries/domain_contracts/canonical/invariant_index.json`, schema
`id, nature, owner_doc, owner_anchor, category, note`) that is explicitly
navigation-only and carries no normative statement text of its own -- every
row points at the one place the actual prose lives (Semantic Model,
Technical Model, Developer Guide, or `interfaces_and_gates.adoc`) rather than
restating it. This should be scoped and reviewed as its own small design
before implementation, not added opportunistically inside a later,
unrelated documentation change.

*Containment until resolved:* the prose promotion itself is complete and
carries no orphaned invariant (see the Slice A+B condensation-matrix and this
slice's own self-review); the only gap is discoverability *by ID* outside of
grep. A maintainer or reviewer who needs to find invariant `<letter><n>`
today should grep the accepted condensation design's canonical inventory
(`docs/cold_storage/backlog/ftrs_done/FTR-TRUSTED-INGRESS-DOCUMENTATION-CONDENSATION-P4A_design.adoc`,
section 3 -- archived by `DOC-CLOSE-LIFECYCLE-1` after `ARCHIVE-DECISION-1`;
see that directory's `index.json`) for the ID, then follow that row's "Primary
home" to the permanent document. Archival does not change this disposition:
the inventory remains discoverable, and the absence of a permanent
machine-readable index does not block documentation closure.
