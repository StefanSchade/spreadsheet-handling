==== 2. Problem statement and contract vocabulary

Current framework-managed execution has a load-time function named ingress,
but that function establishes only one `_meta.legend_blocks` shape. It does
not establish a scalar grammar, general metadata substrate, DataFrame or
`ExactTable` carrier contract, policy result, or post-step payload guarantee.
`run_pipeline` is intentionally step-only, and executable steps may replace
payload after the initial seam.

This design makes the following statement precise without using “trusted
payload” as a synonym for conformance:

[source,text]
----
Successful Trusted Ingress establishes a named payload-conformance state whose
assumptions downstream code may rely on under its declared execution-state
contract.
----

The following terms are used normatively in this design:

* *Ingress-Conformant Domain Payload* is the postcondition established over an
  external/router-loaded candidate or an uncertified producer return. Its
  ordinary DataFrame and `ExactTable.data` cells contain only the six-category
  Scalar grammar. It says nothing about who authored the payload.
* *Conformant Framework Execution Payload* is a later framework execution state
  that satisfies every Ingress-Conformant Domain Payload fact except that an
  exact reviewed framework producer transition may additionally place a named,
  framework-owned Intent kind in explicitly declared cell roles. The only
  current such kind is `LookupFormulaSpec` output Intent from the exact reviewed
  formula-helper behavior. This is a bounded runtime role, not a seventh scalar
  category, external ingress carrier, or `DeclaredComposite`.
* *conformant execution state* means either of those two states, according to
  the precondition declared by the next framework consumer.
* *ordinary Domain operation* is a transformation, cleanup, validation, or
  reconstruction consumer that declares the exact conformant execution-state
  contract it accepts as its general payload precondition. An ordinary scalar
  consumer that is not explicitly Intent-aware accepts only Ingress-Conformant
  Domain Payload. Family-specific preconditions remain additional.
* *conformance interval* is explanatory/contractual state: the period after a
  successful establishment or reviewed transition during which downstream code
  may rely on the applicable conformance facts, provided caller and producer
  obligations continue to hold. It is not a runtime token, ownership proof,
  alias tracker, mutation detector, or isolation guarantee.
* *preserving producer invocation* is one exact reviewed bound behavior and
  configuration whose closed output contract preserves its declared input
  execution-state contract. Callable/family review may establish eligibility;
  a callable name, registry entry, module, family, wrapper, factory, or
  built-in status is never the certificate.
* *Intent-introducing producer invocation* is an exact reviewed bound behavior
  authorized to transition an Ingress-Conformant Domain Payload into a
  Conformant Framework Execution Payload by creating a named Intent kind only in
  declared output roles. It does not authorize an external or returned
  arbitrary object of the same Python type.
* *uncertified producer* is an executable step without that reviewed producer
  invocation contract. Unknown/unreviewed options, nested user callbacks,
  mutable post-binding behavior, wrapper/factory composition, dotted plugins,
  generic custom callables, and caller-supplied `BoundStep` values are
  uncertified by default.
* *re-establishment* is a new successful ordinary payload-conformance pass over
  an uncertified producer's returned candidate before the framework resumes
  ordinary macro flow. An uncertified transition ends any prior internal-Intent
  authorization; its candidate must satisfy Ingress-Conformant Domain Payload,
  so FormulaSpec cannot gain or retain authority merely by object identity.

Four responsibilities remain independent throughout:

[cols="2,4",options="header"]
|===
|Responsibility |Owner and meaning

|Description / control input
|Structural parsing and authorization of what operation/capability may be
selected. This is the pipeline-description trust plane.

|Payload input
|Recognized structural carriers, scalar grammar, framework-owned metadata
substrate, and any evidenced operator narrowing. This is the payload-
conformance responsibility of Trusted Ingress.

|Domain invariants
|Family- or reconstruction-local semantic validity, including reusable
Finding-based checks where appropriate.

|Output adaptation
|Persistence projection and sink-specific capability. Writers do not become
payload validators, and formula-looking text is not globally invalid.
|===

Runtime/operator trust remains a fixed precondition. Payload authority and
pipeline-description authority remain independent variables. Output-sink
capability remains separately owned. This design introduces no scalar trust
level. A less-trusted authored payload may become conformant; a trusted authored
payload may be non-conformant. Neither authority class bypasses the globally
supported grammar.

==== 3. Current-state evidence to which the design responds

The accepted census establishes these load-bearing facts:

* router-backed high-level flows converge on `orchestrate`, whose fixed order
  is load, current ingress, linear steps, final Domain cleanup, metadata
  persistence projection, and save;
* `sheets-run` and `run_app` bind configured strings before payload load, so a
  dotted import can activate capability before any payload ingress occurs;
* the current ingress coordinator has three production call sites and one
  Legend Blocks rule;
* the shared six-category scalar classifier has no production caller;
* DataFrame cell carriers differ across XLSX/ODS, CSV, JSON, YAML, XML, and
  direct Python inputs;
* exact spreadsheet paths may carry `ExactTable` into reconstruction;
* maintained `add_lookup_helpers(helper_value_mode="formula")` behavior creates
  framework-owned `LookupFormulaSpec` output Intent in DataFrame cells for the
  XLSX/ODS output adapters;
* metadata has initial parser origins plus post-load bootstrap/override origins;
* every executable step return is passed directly to the next step, with no
  automatic post-step ingress; and
* `run_pipeline`, supported lower-level APIs, mixed direct reachability, and
  importable internals do not have one uniform public contract.

Those facts show why “call `scalar_category()` once in `orchestrate`” cannot be
the contract.

==== 5. Coverage-model evaluation and decision

[cols="2,3,3",options="header"]
|===
|Model |Fit to repository |Decision

|A -- universal ingress
|A simple slogan, but it would either wrap every supported low-level call or
silently call importability public. It also obscures producer-created payload.
|Rejected. Too broad for the actual API and not the smallest truthful contract.

|B -- framework-managed guarantee
|Matches the main convergence seam and preserves `run_pipeline`, but by itself
does not answer replacement payload after a custom step.
|Necessary but insufficient alone.

|C -- capability/payload certification wrapper or type state
|Could track provenance across many producers, but current Frames APIs and

|Rejected for Phase E. No evidence justifies the complexity.

|D -- hybrid
|Framework-managed load establishes ordinary external conformance; exact

|Selected with a closed uncertified default. Preservation is an evidence-backed

|===

The selected coverage model is therefore:

[source,text]
----
external router-loaded payload
  -> backend parse/conversion (including reserved YAML metadata sidecar)
  -> establish Ingress-Conformant Domain Payload
     [ordinary DataFrame/ExactTable data cells = six-category Scalar]

conformant ordinary execution state
  -> exact bound preserving invocation
       -> preserves the declared conformance interval
  -> exact reviewed Intent-introducing invocation
       -> Conformant Framework Execution Payload
          [Scalar plus named framework-owned Intent in declared roles]
       -> only declared Intent-aware or Intent-transparent framework consumers
  -> uncertified invocation
       -> returned candidate loses any internal-Intent authorization
       -> re-establish Ingress-Conformant Domain Payload
       -> ordinary macro flow may resume only on success

output adaptation
  -> consumes ordinary values and declared Intent under adapter/sink contract
  -> FormulaSpec-capable XLSX/ODS adaptation translates LookupFormulaSpec
  -> unsupported sink/Intent combinations reject or require prior resolution

trusted programmatic composition
  -> caller supplies the conformant execution state required by its first step
  -> caller owns every preserving, Intent, and re-establishment transition

supported lower-level Domain API
  -> local documented contract, including Ingress-Conformant Domain Payload
     where the operation consumes ordinary payload
----

The currently accepted Intent transition is deliberately narrow:

[source,text]
----
exact reviewed add_lookup_helpers invocation
  with helper_value_mode = formula
  and reviewed closed parameters
    -> may create LookupFormulaSpec only in its declared helper output columns
    -> may flow through declared cell-transparent cleanup/projection operations
    -> may be consumed by FormulaSpec-capable XLSX/ODS output adaptation
----

An ordinary Domain transformation may not receive that execution state unless
its exact contract declares it Intent-aware or Intent-transparent. Framework
cleanup/persistence operations qualify only after review proves that they do
not interpret, copy into new roles, or transform those cell values. Sink
capability remains separate: authorizing the framework Intent role does not
authorize every output adapter or formula family.

Initial ingress always rejects externally supplied FormulaSpec. An uncertified
producer cannot introduce, preserve, or authenticate FormulaSpec merely by
returning the same class or object; ordinary re-establishment rejects it. If a
workflow needs arbitrary/custom code between formula-Intent creation and
output, that code needs its own exact reviewed Intent contract or the Intent
must be resolved/removed and deliberately reintroduced afterward.

==== 6. Framework-managed definition and entry-surface guarantees

“Framework-managed” adopts the accepted census meaning:

[source,text]
----
A high-level entry is framework-managed when its fixed application macro flow
owns the loader, initial conformance establishment, final Domain cleanup, persistence
projection, and saver.
----

Delegating one or more of those responsibilities to an owned helper does not
change the definition. The definition is semantic, not tied permanently to the
current `orchestrate` function name.

Framework management does not make arbitrary plugin behavior safe or payload
conformant while the plugin is executing. It does require the enclosing macro
to apply the producer-transition contract to the candidate the plugin returns
before ordinary macro flow resumes.

==== 7. Ordinary payload grammar and controlled framework Intent

The Phase-E *external/ordinary* cell-payload grammar is positive and closed:

[source,text]
----
CellPayload       ::= Scalar | DeclaredComposite
Scalar            ::= String | Boolean | Number | Missing | Date | DateTime
DeclaredComposite ::= <no admitted variants in Phase E>
----

Successful ordinary scalar ingress is defined by membership returned by the
accepted `scalar_category(value)` classifier. Initial Phase E has no
configurable payload-policy matrix; the global grammar is the admitted set.

The globally supported carrier variants are exactly those owned by the current
Internal Scalar Value Model:

[cols="2,4",options="header"]
|===
|Category |Admitted carrier variants

|String
|`str`, including `numpy.str_` through its string-subclass behavior.

|Boolean
|`bool`, `numpy.bool_`.

|Number
|`int`, `float`, `numpy.integer`, `numpy.floating`, subject to the classifier's
explicit exclusions.

|Missing
|`None`, `""`, supported float/NumPy NaN, `pandas.NA`, `pandas.NaT`, and
`numpy.datetime64('NaT')`, exactly as recognized by
`is_missing_carrier`; `numpy.timedelta64('NaT')` is not admitted.

|Date
|`datetime.date` after DateTime precedence.

|DateTime
|`datetime.datetime`, `pandas.Timestamp`, and every non-NaT
`numpy.datetime64`, with no unit-based Date inference.
|===

`datetime.time`, Duration/Timedelta carriers, `FormulaSpec`, spreadsheet Error,
collections, bytes, callables, classes, modules, generators, file handles, and
opaque objects are not scalar payload. An unsupported carrier does not become
valid because pandas can store it in an object-dtype cell.

Framework-created cell Intent uses a different positive runtime grammar:

[source,text]
----
FrameworkExecutionCell ::= Scalar | DeclaredFrameworkIntent
DeclaredFrameworkIntent ::= LookupFormulaSpec@declared-helper-role
----

This second grammar is not initial ingress admission. Only the exact reviewed
formula-helper producer transition may create the current Intent kind, only in
its declared output columns, and only for downstream consumers whose exact
contract is Intent-aware or cell-transparent. A FormulaSpec object found at
external ingress or after an uncertified return is rejected. FormulaSpec is not
Scalar, not `DeclaredComposite`, not a seventh scalar category, and not made
valid by class identity alone.

DataFrame axes are structural labels, not `CellPayload`. Phase E preserves the
existing physical-column addressability authority:

* non-missing-like;
* hashable;
* unambiguously self-comparable; and
* unique where physical scalar addressing requires uniqueness.

“Deterministically comparable” in this contract means only that self-comparison
produces an unambiguous Boolean. It is not total ordering, cross-label
comparability, or sorting compatibility. Row indexes are positional locations,
not ordinary payload data, and Phase E imposes no new closed scalar/tuple
grammar on them.

The earlier `AxisAtom ::= Scalar` / finite-tuple proposal is retained only as a
candidate hypothesis for the E2 compatibility census. E2 may propose it (or a
different bounded grammar) only through a separately accepted design gate that
inventories framework-produced and supported consumer-reachable axes. E2 MUST
NOT silently tighten the accepted contract. Any confirmed supported label that
would be removed requires explicit compatibility/migration treatment before
implementation.

Classification occurs before any policy decision and before any future
category-specific normalization. The current design performs no scalar
normalization afterward.

The classifier's bounded dispatch is the ordinary-cell robustness boundary: it does not run
general equality, hashing, `repr`, string conversion, iteration, or NumPy array
protocols on an unsupported value. Trusted Ingress must not add such probes to
make diagnostics richer. It does not attempt to contain arbitrary hostile
Python already executing in process.

String content is never shape-guessed. Numeric-looking, boolean-looking,
date-looking, formula-looking, SQL-looking, shell-looking, and HTML-looking
strings remain String. Sink-specific interpretation remains sink-owned.

==== 8. Classification, normalization, and Missing

The scalar-normalization alternatives were evaluated as follows:

[cols="2,3,3",options="header"]
|===
|Alternative |Benefit |Disposition

|A -- validate only
|Preserves accepted carriers, pandas behavior, temporal precision/timezone,
and the established classifier boundary.
|Selected for scalar payload.

|B -- minimal canonicalization
|Could stabilize a demonstrated problematic carrier, but no such general
post-classification carrier is evidenced for this slice.
|Preserved as a future per-category option, not selected now.

|C -- full canonical scalar set
|Would simplify types superficially but force precision, timezone, Missing,
and pandas rewrite decisions without consumer evidence.
|Rejected.

|D -- category-specific policy
|Is the correct shape if a future category proves it needs conversion.
|Extension rule only; all six categories currently specify identity
preservation.
|===

Ordinary payload-conformance ingress therefore does not convert `numpy.int64` to `int`,
`numpy.bool_` to `bool`, `pandas.Timestamp` to `datetime.datetime`, or
`numpy.datetime64` to another carrier. It does not strip/convert timezone
information or reduce precision. DataFrame dtype behavior may still box values
according to pandas; ingress does not add another conversion.

Missing remains recognition, not representation. Every admitted Missing carrier
is preserved. In particular:

* `""` is not replaced by `None` or a sentinel;
* NaN/NA/NaT carriers are not globally unified;
* literal string `"nan"` remains String, not Missing; and
* ordinary empty domain text remains possible. Where `""` means missing,
  unresolved presentation, or legitimate empty text depends on the consuming
  feature's authority and context, not on a new ingress sentinel.

Successful ordinary ingress promises that every Missing-shaped cell is one of the
accepted recognized carriers. It does not promise representation equality
between Missing cells. Downstream generic code may use the accepted missing
predicate; family semantics such as unresolved FK authority remain unchanged.

Ingress may still perform two non-scalar forms of normalization:

* construct a new owned top-level Frames mapping and owned metadata containers;
  and
* apply explicit feature-owned authoring-to-canonical metadata rules such as
  the existing Legend Blocks rule.

Parser conversion and persistence-local conversion remain owned by their
respective boundaries and are not renamed scalar normalization.

Creating `LookupFormulaSpec` under the reviewed formula-helper transition is
neither scalar normalization nor external payload admission. It is an explicit
framework output-Intent transition governed by sections 5 and 12.

==== 9. Traversal ownership

Trusted Ingress does not use one universal recursive walker. Initial ingress
and uncertified-return re-establishment use the ordinary grammar; reviewed
framework-Intent transitions use their own closed role-aware validator.

[cols="2,3,4",options="header"]
|===
|Traversal owner |Unit |Contract

|Frames dispatcher
|Top-level exact mapping entries
|Validates exact string frame names, reserves `_meta`, dispatches recognized
payload carriers, and constructs the staged result. It does not infer a carrier
from mapping shape.

|Ordinary DataFrame ingress/re-establishment
|Every cell by physical row/column position plus physical columns
|Checks the DataFrame structural substrate, including the established physical
column-label contract (non-missing-like, hashable, unambiguously
self-comparable, and unique), then classifies every ordinary cell. Row indexes
are used only to locate positions and are neither classified as cells nor
rendered in diagnostics. No new closed axis grammar is assumed.

|Framework Intent transition
|Producer-declared frame/column roles and every candidate cell in those roles
|Checks the exact producer invocation, accepts only its named Intent kind in
declared output roles, and verifies every other ordinary cell under Scalar.
Class identity outside an authorized role rejects. No universal intent registry
or attribute recursion exists.

|`ExactTable` ingress
|Header/geometry fields and every `data` cell
|Checks carrier self-consistency and the string header substrate, then applies
scalar grammar to row-major data. Reconstruction meaning remains local.

|Metadata ingress
|The `_meta` structural tree and explicit root delegates
|Uses the exact node vocabulary accepted by E3's independent compatibility
gate, ownership copying, bounded traversal, cycle rejection, and closed
root-local authoring delegates.

|Controlled internal carrier constructor
|Carrier-specific fields
|Owns only its named construction invariant. It does not prove ordinary cell
conformance unless its exact contract says so. No fallback recursively walks
an unknown object's attributes.
|===

Selected payload frames means every recognized payload carrier at the top level
other than `_meta`; there is no sample-based, dtype-based, or “pandas accepted
it” exemption. A Conformant Framework Execution Payload additionally carries
the explicit Intent-role declaration established by its reviewed transition;
without that declaration the candidate is checked as ordinary payload.

==== 11. Metadata contract

`_meta` participates in payload-conformance ingress, but cell payload and
metadata remain different flows. Phase E accepts this contract now:

* `_meta` is absent or becomes an owned, bounded, acyclic framework metadata
  substrate before publication;
* arbitrary opaque object graphs, callables, binary/runtime objects, and
  undeclared recursion are not valid merely because Python can store them;
* external/persisted metadata and later runtime-created metadata remain
  distinct origins whose relevant transitions are checked;
* family meaning, references, conflicts, and invariants remain local; and
* root-specific authoring normalization is possible only through the closed
  delegate contract below.

The exact node vocabulary is *not yet accepted*. The preferred hypothesis is
an exact built-in `dict` root and nested mappings, exact string keys, exact
built-in `list` sequences, admitted scalar leaves, identity-based cycle
detection, and explicitly named root-specific structural contracts. Before E3,
a focused compatibility census MUST inventory current external/persisted and
runtime-produced/consumed node kinds, aliases, and special roots. That evidence
gate must be independently accepted and must either:

. confirm the preferred vocabulary;
. revise it to another bounded positive vocabulary; or
. name every supported-shape migration and release consequence.

Here “bounded” means a closed positive node/edge vocabulary and named delegate
roots. It does not promise maximum depth, cardinality, bytes, or traversal cost;
those resource limits remain separately owned and are explicit non-guarantees.

E3 MUST NOT silently turn the preferred hypothesis into runtime rejection.
`meta_registry.yaml` remains a manual review artifact and MUST NOT become
runtime authority without separate architecture.

===== Controlled metadata delegate governance

A metadata ingress delegate MUST:

* be centrally reviewed and owned; arbitrary family/plugin code cannot
  dynamically register one;
* be selected by a statically declared root contract, not by caller-provided
  executable identity;
* operate only on a staged candidate and perform no caller-input mutation;
* avoid unsafe `repr`, `str`, truthiness, equality, hashing, iteration, or
  protocol probing on a rejected unsupported value beyond operations explicitly
  safe in its already-admitted container contract;
* return either the common accepted substrate or one explicitly named
  root-specific structural contract;
* have its entire output checked against that declared postcondition before
  publication;
* never use delegate status to introduce opaque values or bypass the global
  bounded/acyclic structural postcondition; and
* own authoring shape only, not absorb family semantics merely because it
  normalizes the root.

The current Legend Blocks normalizer is compatibility evidence for the
authoring form, not an automatically approved delegate implementation. E3 must
migrate its Mapping acceptance, identity resolution, shallow alias retention,
and `str`/truthiness behavior to the accepted node vocabulary and the rules
above.

Bootstrap and YAML overrides MUST build merged candidates without mutating the
published Frames graph, run accepted substrate validation and every relevant
delegate, and publish only on success. Exact preserving producer invocations
may create framework/family metadata under their reviewed output contract;
uncertified producer returns undergo complete ordinary re-establishment.

===== YAML reserved metadata-sidecar decision

*Option A is selected.* In `yaml_dir`, every input file whose stem is `_meta`
(`_meta.yaml` or `_meta.yml`) is a reserved framework metadata sidecar. The YAML
backend, not Domain ingress, safe-loads at most one such file and places its
mapping value at `Frames["_meta"]` before payload-conformance ingress. A
non-mapping root or duplicate `.yaml`/`.yml` reserved sidecar is rejected at the
backend/parse boundary with a stable compatibility error. Domain ingress never
reinterprets an already-created DataFrame as metadata.

This choice is consistent with `_meta` being reserved, JSON's mapping-sidecar
interpretation, and the YAML saver's existing refusal to write an ordinary
`_meta` sheet. It does not add a YAML metadata-roundtrip promise: the current
YAML saver may continue to omit `_meta` unless persistence work separately
changes that contract.

The observable migration is that a YAML file with stem `_meta` can no longer be
addressed as an ordinary DataFrame sheet. That was not a stable roundtrip
contract because the maintained saver already skips `_meta`; consumers that
used it as ordinary data must rename the file/sheet, while consumers intending
metadata must provide a mapping compatible with the E3-accepted substrate.
E3 owns the loader conversion/rejection and MUST include release-note
documentation for the reserved-name change. No release note is created by this
design correction.

==== 12. Conformance propagation and post-ingress producers

The evaluated alternatives are:

[cols="2,3,3",options="header"]
|===
|Alternative |Assessment |Disposition

|A -- trusted-step preservation
|Efficient for reviewed built-ins, but unsafe if “built-in” or “registered” is
treated as proof without an output contract.
|Adopt only for exact reviewed bound invocation contracts.

|B -- revalidate after every step
|Simple but duplicates complete traversal after transformations already
required to preserve the grammar.
|Rejected as the permanent universal rule, but accepted as the conservative
migration behavior for every still-uncertified relevant return.

|C -- exact producer-transition contracts
|Models configuration-dependent output, controlled Intent introduction, and
the difference between reviewed behavior and arbitrary returns.
|Selected with closed uncertified default.

|D -- explicit token/type state
|Makes state machine visible but would reshape current Frames and step APIs.
|Rejected for Phase E; no evidence requires it.

|E -- arbitrary plugins outside all guarantee
|Truthful inside plugin execution but insufficient when macro flow passes the
return to later built-in steps/cleanup.
|Adopt only for calls made *inside* the plugin; returned candidates are
re-established before macro flow resumes.
|===

Producer treatment is:

[cols="3,3,5",options="header"]
|===
|Producer kind |Default treatment |Contract

|Any built-in/registered/family callable in the abstract
|Uncertified
|Name, module, registry entry, importability, family, and built-in status prove
nothing about every option combination. Callable/family review may establish
eligibility only.

|Exact reviewed bound behavior/configuration
|Preserving only for the exact closed contract it earned
|The certificate names accepted input state, closed parameters/options, output
state, metadata/structural effects, and any allowed Intent roles. Unknown
option values, nested callbacks, mutable post-binding behavior, or unreviewed
wrapper/factory composition make the invocation uncertified.

|Exact formula-helper behavior
|Intent-introducing only for reviewed
`helper_value_mode="formula"` invocation
|May create `LookupFormulaSpec` only in declared helper output columns and may
hand the result only to declared Intent-aware/transparent consumers and
supporting output adaptation. Other configurations do not inherit this
transition contract automatically.

|Framework infrastructure step
|Affected-state re-establishing when it introduces external/bootstrap/override
data; otherwise uncertified unless an exact behavior is reviewed.
|Merge-before-publish and validate the introduced portion plus affected
structural roots. It cannot claim trust merely because it is infrastructure.

|Configured dotted plugin or generic dotted callable
|Uncertified.
|Within framework-managed flow, its returned candidate MUST pass full
ordinary re-establishment before any next Domain operation, final cleanup, or
save. Any prior internal-Intent authorization ends. Domain calls made inside
the plugin remain under its own stronger caller precondition.

|Caller-supplied callable / `BoundStep` to `orchestrate`
|Uncertified unless its exact bound behavior carries a framework-reviewed
producer contract through an implementation mechanism.
|Same returned-candidate re-establishment rule. Direct Python remains trusted
runtime capability, not automatically valid output.

|Callable / `BoundStep` supplied to `run_pipeline`
|Caller-classified.
|`run_pipeline` performs no automatic transition. The caller is responsible for
the exact state accepted by each step, controlled Intent transitions, and
explicit re-establishment.
|===

“Custom output is automatically untrusted” is not the decision. Its authorship
may be fully trusted; its payload conformance is simply uncertified until
re-established. Likewise, “built-in output is automatically trusted” is not the
decision: exact behavior becomes preserving only through a reviewed closed
contract.

The applicable conformance assumption remains available only during a
*conformance interval*. This is explanatory/contractual state, not mechanically
tracked state. The framework can know that a pass succeeded, that an exact
invocation has a reviewed contract, or that an uncertified return passed
re-establishment. It cannot know or prevent retained DataFrame/nested aliases,
later caller writes, concurrent mutation, plugin closures, threads, or other
same-process writes.

Therefore no-out-of-band mutation is a caller and preserving-producer
*obligation*, not an isolation guarantee. A preserving invocation contract MUST
state that its own work does not intentionally retain or exercise a mutation
path that violates the interval, but certification does not prove absence of
all aliases in the process.

Framework-managed loaded DataFrames need not be deep-copied solely to establish
atomicity because scalar validation is read-only. Logical ownership transfers to
the macro for the duration of the call. An implementation may copy for another
documented reason, but this contract does not require a full DataFrame copy.

===== Bounded E4 migration rule

E4 defines the transition representation, exact-invocation granularity, closed
uncertified default, and a deliberately small evidence-backed initial
certificate set. The set may be zero. E4 does *not* audit every transformation
family, all 44 registry forms, or every parameter combination.

[source,text]
----
proven exact preserving invocation
  -> omit redundant full re-establishment

proven exact Intent-introducing/preserving invocation
  -> apply its named execution-state transition and role checks

anything else
  -> ordinary re-establishment of the returned candidate
  -> reject all FormulaSpec/internal Intent in that candidate
----

This conservative rule lets E5 reach the Payload-Conformance Milestone without
pretending every built-in preserves. Later family hardening may add exact
certificates as a performance optimization without changing Model D or Phase-E
completion. A failed pass still cannot roll back custom side effects or prior
successful steps.

==== 13. Operator payload-policy disposition

Global framework capability and operator policy remain architecturally
different, but Phase E has no evidenced need to expose configurable payload
narrowing:

[source,text]
----
initial Phase-E payload capability = globally supported payload grammar
----

E1 implements the global ordinary scalar grammar, not cell-category,
carrier-variant, metadata-leaf, or structural-carrier policy knobs. No current
operator requirement justifies those dimensions. In particular, carrier
variants remain admitted according to Phase D, and an independent metadata-
leaf knob must not break valid framework metadata merely because it is
configurable.

The architecture still preserves the accepted ADR rule for any *future
evidenced policy kind*: it is supplied by the trusted operator outside a
less-trusted description, fixed for the relevant conformance interval,
narrowing-only, and combined per kind. Unknown, contradictory, incomparable, or
widening requests reject. No policy can make an unsupported object, undeclared
collection, external FormulaSpec, Time, or Duration into ordinary scalar
payload. A future description may request only additional restriction for an
already-defined kind.

Trusted/less-trusted payload remains exclusively an authorship/authority
assessment. A less-trusted authored payload may become Ingress-Conformant; a
trusted authored payload may fail conformance. Both receive the same globally
supported grammar unless a separately accepted operator-policy use site
defines narrowing.

Maximum bytes/cells/text lengths, parser limits, metadata-root authorization,
filesystem capabilities, formula policy, and custom-step capability are not
added to this payload policy without their own concrete owning use sites.
Parser/resource bounds and sink capability remain separately owned.

This design does not choose payload-policy transport, CLI syntax, environment
variables, profile names, or a public policy class. E7 separately requires
operator-owned *description capability* policy because that use site is already
mandated by the accepted ADR and capability-activation evidence.

==== 14. Pipeline-description trust and capability activation

Payload-conformance ingress and pipeline-description authorization are two
coordinated but separately owned subcontracts:

[source,text]
----
description/control plane:
  parse shape -> prepare/canonicalize identifier -> combine policy -> authorize
  -> only then import/bind/acquire/invoke governed capability

payload plane:
  parse/load carrier -> structural/scalar/metadata conformance -> ordinary
  Domain or reviewed framework-Intent transition
----

Their execution order is not universally serial: current CLI and `run_app`
bind descriptions before loading payload. Therefore a later successful payload
pass cannot retroactively authorize an earlier import.

Phase E's minimum description seam is:

* an entry must state whether its description is trusted or less trusted;
* less-trusted description requests must be combined with operator policy
  outside that description;
* safe syntactic parsing, structural checks, static policy metadata lookup, and
  identifier canonicalization may occur before authorization;
* Python module import is capability activation and MUST NOT occur before an
  allow decision;
* direct Python callables and pre-bound `BoundStep` values are trusted
  programmatic capabilities, not a supported less-trusted-description format;
  and
* description authorization success does not establish payload conformance,
  and payload ingress success does not authorize the description.

Concrete description policy/allowlist/binding mechanics belong to E7 after an
*accepted* dotted-extension-surface architecture assessment supplies its per-
surface stability contract. That assessment remains open; this FTR does not
pretend its current draft is accepted. Until E7 is accepted and implemented,
`sheets-run` and `run_app` publish payload-conformance guarantees only under a
mandatory trusted-description precondition. This is a support boundary, not a
claim that less-trusted descriptions become safe after payload ingress.

===== Phase-E completion decision

*Option A is selected.* E1-E6 may reach an independently reviewed and accepted
*Phase-E Payload-Conformance Milestone* under the mandatory trusted-description
precondition. That milestone is useful but does not complete Phase E. Phase E
remains *Open* until E7 is independently accepted and its less-trusted-
description authorization contract is implemented.

While Phase E is in that intermediate state:

* current CLI/`run_app` configured execution MUST document that its description
  is trusted operator input;
* no less-trusted configured YAML protection may be advertised;
* the Domain Maintainer Contract, Phase F, and D-T3 remain blocked by the
  roadmap's Phase-E prerequisite; and
* E7 continues to depend on the accepted output of
  `FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A`, not merely its current draft.

No attempt is made to sandbox trusted Python.

==== 15. Failure atomicity

Atomicity is local to the work performed by conformance ingress and every
approved metadata/Intent delegate or transition validator:

* traversal and scalar classification are read-only;
* structural and metadata normalization are built in staged containers;
* the top-level candidate is not published to the caller, next step, cleanup,
  persistence projection, or saver until every required check succeeds;
* failure on cell N does not expose normalization performed for cells or
  metadata visited earlier;
* ingress/delegates MUST NOT mutate caller-owned Frames, DataFrames, `_meta`, or
  retained nested metadata as part of their own work; and
* no ordinary configured step or saver runs after an initial ingress failure.

This does not require transactional machinery. A staged top-level mapping plus
owned staged metadata and read-only cell traversal is sufficient under the
validate-only scalar decision. Input DataFrames need not be copied when they
are not mutated.

This is not a concurrency, alias, or ownership-isolation guarantee. The
framework does not prove that another actor did not mutate a retained DataFrame
or nested alias during the attempt, and it does not prevent later caller,
closure, thread, plugin, or other same-process mutation. No DataFrame deep copy
is required merely to pretend otherwise.

For re-establishment after an uncertified step, rejection prevents that
candidate from reaching the next ordinary Domain operation, final cleanup, or
framework saver. It cannot roll back mutations or external side effects the
custom callable already performed, nor prior successfully completed pipeline
steps, and it cannot revoke aliases retained by that callable. Plugins with such
effects remain trusted-programmatic capability and must document/own them.

==== 16. Error and diagnostic model

Boundary rejection raises exceptions; it does not emit reusable Domain
`Finding` values. Findings describe Domain semantic/invariant observations and
remain separately governed by severity policy.

The contract requires distinguishable failure kinds:

[cols="3,4",options="header"]
|===
|Failure kind |Required diagnostic context

|Unsupported scalar carrier
|Frame and positional column/row ordinal, or `ExactTable` data row/column
ordinal; constant safe detail. The rejected value is never rendered.

|Invalid structural carrier
|Top-level frame name when it is an exact validated string, carrier role, and
failed structural field/ordinal.

|Invalid metadata substrate
|Safe metadata path composed only from keys and ordinals admitted by the
accepted E3 node vocabulary; expected node kind. Delegates obey the same
rejected-value inspection rules.

|Unauthorized framework Intent carrier/role
|Frame and positional location, expected declared Intent kind/role, and
transition contract identifier. The rejected object is never rendered.

|Future evidenced payload-policy rejection
|Safe location, classified semantic category/carrier kind, and policy kind
that rejected it. No value content is required.

|Pipeline-description authorization rejection
|Description location, declarative identifier/capability kind where safely
available, and policy reason. It is a description-plane exception, not an
ingress scalar error.
|===

A typed exception hierarchy or an exception carrying a stable `kind` field is
required by contract; exact class names are an implementation choice. The
boundary may fail fast at the first deterministic error. Multi-error collection
and report/result objects are optional later enhancements.

Diagnostics MUST NOT call `repr`, `str`, equality, hashing, iteration, or NumPy
protocols on a rejected unsupported value. Frame/row/column values that have not
themselves passed a safe structural contract are reported by ordinal/role, not
by content. This restriction does not prohibit the minimum self-comparison and
hash operations required to test a candidate physical column label against the
existing addressability contract; it prohibits additional diagnostic
inspection. Metadata delegates do not gain such an exception for unsupported
leaf values.

==== 17. Downstream postconditions

Downstream entitlement depends on the lifecycle transition that established the

|===

===== B. After an exact reviewed preserving or Intent transition

An exact preserving invocation proves only the output facts named by its closed
contract. An exact Intent-introducing invocation may establish Conformant
Framework Execution Payload, which proves:

* every ordinary non-Intent cell still satisfies Scalar;
* only the named framework Intent kind appears, only in producer-declared
  frame/column roles;
* current FormulaSpec authority means `LookupFormulaSpec` produced by the exact
  reviewed formula-helper behavior, not any externally supplied or merely
  type-matching object;
* only consumers whose exact contract is Intent-aware or cell-transparent may
  receive that state; and
* output adaptation consumes the Intent only under its own adapter/sink
  capability contract.

Those facts are *PROVEN BY REVIEWED PRODUCER CONTRACT* and role validation, not
by initial ingress. Controlled carrier constructors likewise prove only their
named structural invariants. Continuing absence of out-of-band mutation is a
*CALLER/PRESERVING-PRODUCER OBLIGATION*, not a framework isolation fact.

===== C. After an uncertified producer return

The prior conformance interval and every internal-Intent authorization end.
The returned candidate may reach the next ordinary Domain operation, cleanup,
projection, or saver only after complete ordinary re-establishment succeeds.
Success proves the same facts as section 17.A and rejects all FormulaSpec/
internal Intent in the candidate. A later exact reviewed Intent producer may
introduce fresh Intent again. Re-establishment proves nothing about operations
or side effects that occurred inside the uncertified callable.

This bounded postcondition is useful enough for later family hardening to
remove arbitrary-object/callable/container defenses from ordinary scalar paths
that genuinely declare the conformance precondition. It does not authorize
removal of carrier-variant handling, Missing recognition, comparison/sort/hash
rules, family-specific label identity/role rules, FormulaSpec lifecycle checks,
or family semantics.

==== 18. Explicit downstream non-guarantees

Successful conformance establishment or a reviewed execution transition does
not prove:

* required frames or columns exist;
* FK targets/references exist or resolve;
* values in key columns, visible tuples, or Domain mappings are unique;
* grouped geometry, header depth, row keys, or reconstruction bijection is
  valid beyond generic carrier self-consistency;
* a transformation can sort, compare, hash, or serialize every admitted
  category for its own semantics;
* uniform comparison, sorting, hashing, equality, timezone, or Missing behavior
  across admitted scalar carriers;
* family configuration or every `_meta` root is semantically valid;
* metadata is authoritative merely because it has framework shape;
* cleanup has been selected or output is canonical;
* a string is safe for every sink, including XLSX formula interpretation;
* persistence roundtrip preserves carrier identity, temporal precision, or
  timezone-name identity beyond each backend's own contract;
* the pipeline description is authorized, unless the separate description
  boundary has also succeeded;
* an arbitrary trusted callable cannot misbehave or perform side effects; or
* payload or metadata resource boundedness beyond separately owned parser/
  resource contracts;
* concurrent mutation, retained-alias isolation, later same-process mutation,
  or rollback of producer/plugin effects;
* a framework-created output Intent is an ordinary scalar merely because it
  occupies a DataFrame cell;
* a reviewed producer-preservation contract prevents arbitrary same-process
  mutation outside that contractual obligation; or
* process, filesystem, network, container, or Python sandbox isolation exists.

Ingress validity is not reconstruction validity, transformation precondition,
Domain invariant validity, persistence projection, or sink safety.

==== 19. Bounded-composite extension seam

The `DeclaredComposite` branch in section 7 is intentionally empty. A future
bounded composite such as `List[Scalar]` can be added only by a separately
accepted contract that defines:

* a named composite kind distinct from arbitrary Python collection identity;
* a finite cardinality/depth/resource bound;
* the permitted scalar-leaf grammar and Missing behavior;
* an explicit carrier and ownership/copying rule;
* a schema/declaration and operator policy capability;
* ingress classification/normalization and safe path diagnostics;
* DataFrame/pandas interaction; and
* parser and persistence codecs/representations for every claimed external
  surface.

The extension must enter through Trusted Ingress and cannot make arbitrary
`list`, `tuple`, mapping, set, or object graphs valid by default. This seam does
not choose delimiter encoding, JSON encoding, Python list identity, spreadsheet
representation, or schema syntax. `List[Object]` and nested structured child
records remain `FTR-NESTED-LISTS` territory and do not use this scalar-composite
hook. FormulaSpec does not use this hook: the maintained helper path is
framework-authored output Intent under section 7's controlled execution-state
contract, not composite payload and not external formula ingress/roundtrip.

==== 20. Normative-style contract sentences for later promotion

If independently accepted, the following sentences are suitable for later
promotion into normative documentation:

* A framework-managed external entry MUST establish Ingress-Conformant Domain Payload
  before invoking an ordinary Domain operation.
* Framework-managed means that the fixed application macro flow owns the
  loader, initial Trusted Ingress, final Domain cleanup, persistence
  projection, and saver; it does not mean arbitrary executable code inside the
  flow is framework-validated while it executes.
* A preserving producer certificate applies only to one exact reviewed bound
  behavior/configuration and MUST return the execution state named by that
  contract; no callable, family, registry entry, wrapper, or built-in is
  preserving merely by identity.
* An exact reviewed Intent-introducing producer may create only its named
  framework-owned Intent in declared roles; the current FormulaSpec transition
  neither admits external FormulaSpec nor changes Scalar.
* A framework-managed flow MUST re-establish Ingress-Conformant Domain Payload for an
  uncertified producer's returned candidate before any later ordinary Domain
  operation, final cleanup, or persistence; prior internal-Intent authorization
  ends at that return.
* `run_pipeline` assumes its caller supplies the conformant execution state
  required by its first step and owns all preservation, Intent transitions, or
  re-establishment between supplied steps; `run_pipeline`
  performs no automatic Trusted Ingress.
* A documented supported direct Domain API states its local input contract and
  is not implicitly covered by framework-managed ingress.
* Arbitrary importable internals carry no framework entry, support, or stability
  guarantee.
* Successful Trusted Ingress establishes Ingress-Conformant Domain Payload, not payload
  authorship, pipeline-description authorization, Domain semantic validity, or
  sink safety.
* Trusted/less-trusted payload names authorship only: either may conform or fail
  conformance, and neither bypasses global grammar.
* Any future evidenced operator policy may narrow its globally supported kind
  but MUST NOT make an unsupported carrier valid; E1 exposes no speculative
  payload-policy matrix.
* A conformance interval is contractual/explanatory state, not a token,
  mutation detector, alias tracker, or isolation guarantee.
* A less-trusted pipeline-selected capability MUST be rejected before
  capability activation; payload ingress neither performs nor substitutes for
  that authorization.

==== 22. Pydantic disposition

No concrete Phase-E payload use site justifies a Pydantic ADR.

Scalar semantics remain project-owned and already have a bounded classifier.
DataFrame/`ExactTable` traversal is carrier-specific, and the central metadata
promise is an evidence-gated bounded structural substrate plus centrally
governed delegates. Dataclass or custom validation is sufficient for the
accepted contracts. Adopting Pydantic here would merge payload, metadata, and
description errors without solving a demonstrated problem.

A later description-plane slice may discover a concrete control/config parsing
use site. If it does, it must separately compare existing dataclass/ad-hoc
parsing, Pydantic, and another schema mechanism while keeping payload scalar
semantics and Domain Findings outside that decision. This design neither adopts
nor forbids Pydantic. No ADR stop condition is triggered now.

==== 23. Implementation slice plan (not authorized by this design)

Each slice requires the design to have passed independent review first.

===== E1 -- ordinary scalar admission and safe boundary errors

*Scope:* compose the accepted classifier with the global six-category ordinary
cell grammar and define stable failure kinds/location records. No configurable
payload-policy matrix and no orchestration wiring.

*Preconditions:* accepted Phase-D classifier and this reviewed contract.

*Acceptance criteria:* every accepted carrier/category pair is admitted; every
unsupported carrier, including external FormulaSpec, rejects without value
`repr`/conversion/protocol dispatch; no carrier is normalized.

*Test strategy:* focused unit matrix over six categories and variants, explicit
unsupported temporal/Formula/collection/opaque values, and hostile
`repr`/NumPy-protocol probes.

*Exclusions:* future operator-narrowing knobs, DataFrame traversal, metadata,
public entry wiring, description authorization, resource limits.

===== E2 -- Frames/DataFrame/ExactTable structural dispatch and atomic traversal

*Scope:* staged top-level mapping; complete positional ordinary DataFrame cells;
`ExactTable` generic self-consistency and data traversal; deterministic paths;
and the bounded distinction between external ordinary payload and declared
internal Intent roles.

*Preconditions:* E1; independently accepted compatibility evidence for current
framework-produced and supported consumer-reachable physical axes.

*Acceptance criteria:* complete ordinary-cell traversal; unknown top-level
carriers reject; current physical-column authority is enforced without a new
row-index grammar; failure leaves caller Frames/DataFrames unchanged through
ingress's own work; no DataFrame deep copy is required solely for validation;
reconstruction invariants stay local. Any narrower axis vocabulary requires a
separately reviewed compatibility/migration decision before implementation.

*Test strategy:* multiple frames/dtypes, late-cell rejection, currently valid
duplicate/odd axis compatibility cases, valid/invalid exact geometry,
unauthorized FormulaSpec, and unchanged-caller-graph assertions.

*Exclusions:* silent axis tightening, family semantic checks, grouped
reconstruction changes, generic structured-carrier registry.

===== E3 -- metadata substrate and backend metadata introduction

*Scope:* the accepted `_meta` structural contract, owned acyclic substrate,
centrally governed delegates, bootstrap/override staged validation, and the
decided reserved YAML `_meta.yaml`/`_meta.yml` parse-boundary behavior.

*Preconditions:* E1-E2; independently accepted focused census of external,
persisted, runtime-created, projected, and consumed metadata node shapes. That
evidence must accept the preferred dict/list/scalar vocabulary or replace it
with an explicit bounded vocabulary and migration treatment.

*Acceptance criteria:* supported metadata survives in an owned bounded
substrate; opaque/cyclic/invalid-root structures reject atomically; every
delegate obeys section 11 governance and its output is checked before
publication; Legend Blocks migrates under those rules; YAML reserved metadata
is converted or rejected at its backend boundary, never reinterpreted from a
DataFrame by Domain ingress; release notes cover the `_meta` sheet-name
migration; family semantics are not centralized.

*Test strategy:* external workbook/JSON/YAML metadata, bootstrap/override
candidates, deep late failure, alias/cycle cases, delegate failures, duplicate
YAML metadata spellings, non-mapping YAML roots, and no partial publication.

*Exclusions:* Pydantic, all-family semantic schemas, resource ceilings, a YAML
metadata round-trip guarantee.

===== E4 -- exact producer-transition representation and bounded certificates

*Scope:* represent ordinary-preserving, declared-Intent-introducing, and
uncertified transitions at exact bound-behavior/configuration granularity;
establish a deliberately small, possibly zero, evidence-backed initial
preserving set and the exact current FormulaSpec-authoring transition.

*Preconditions:* E1-E3; accepted step/binding call-shape evidence sufficient to
represent immutable effective configuration and nested callbacks safely.

*Acceptance criteria:* the default is closed and uncertified; no callable,
registry entry, family, wrapper, factory, or built-in inherits certification;
unknown options, mutable post-bind configuration, and uncovered callbacks stay
uncertified; each certificate names its exact input/output state and has focused
evidence; all other returned candidates are routed to re-establishment.

*Test strategy:* exact bound-invocation construction and mutation tests, the
formula-helper Intent path, a small initial certificate set, and representative
uncertified built-in/plugin/dotted/prebound forms.

*Exclusions:* auditing all registry forms, broad family hardening, plugin
sandboxing, description authorization. Later family work may add certificates
as an optimization without changing this contract.

===== E5 -- framework-managed macro wiring

*Scope:* initial ordinary conformance establishment, exact producer-state
transitions, conservative re-establishment after every still-uncertified
relevant return, controlled internal FormulaSpec lifecycle, and output
adaptation in the macro used by `sheets-run`, `run_app`, `orchestrate`/shim, and
schema maintenance.

*Preconditions:* E1-E4.

*Acceptance criteria:* all six router backend families reach initial ingress;
ordinary Domain does not run after rejection; an exact preserving certificate
alone avoids post-step traversal; an exact Intent transition alone authorizes
the declared role; every other returned candidate is re-established under the
ordinary grammar before later ordinary Domain, cleanup, projection, or save;
XLSX/ODS FormulaSpec-aware output adaptation can consume the maintained formula
helper result; rejected candidates never reach the sink.

*Test strategy:* one focused end-to-end path per materially different carrier
behavior, formula helper through XLSX/ODS adaptation, plugin/generic
dotted/prebound replacement probes, schema fixed-step path, and ordering/
atomic-save tests.

*Exclusions:* changing `run_pipeline` internals, formula sink capability policy,
parser resource limits, certification of every built-in.

===== E6 -- programmatic-surface contract and API publication

*Scope:* publish the contracts for `run_pipeline`, documented builders,
supported lower-level Domain/backend APIs, and internal/importable-only code;
provide whatever explicit conformance-establishment helper surface supported
programmatic callers actually need.

*Preconditions:* E5 behavior exists and has accepted evidence; consumer evidence
identifies the intentional public seam rather than assuming a docs-only change.

*Acceptance criteria:* consumers can determine where establishment is
automatic, which conformant execution state is a caller precondition, how an
explicit helper is obtained if supported, and which surfaces have no promise;
`run_pipeline` remains step-only with no automatic establishment; no aggregate
importability promotion occurs.

*Test strategy:* supported import/API/documentation checks and focused explicit
helper tests if that seam is selected; no unrelated direct-API rewrite.

*Exclusions:* API removal/rename, universal Domain barrel, Maintainer Contract.

===== E7 -- less-trusted description authorization (Phase-E completion slice)

*Scope:* after acceptance of
`FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A`, define and implement operator-owned
authorization for the supported declarative surface, with rejection before
import/binding/acquisition.

*Preconditions:* the still-open extension-surface assessment is independently
accepted; an independently reviewed narrow E7 design exists; operator policy
is represented for the evidenced capability kinds.

*Acceptance criteria:* supported less-trusted descriptions cannot activate a
forbidden capability; direct Python forms remain trusted-only; all four
payload/description authority combinations remain representable; payload
conformance tests remain independent.

*Test strategy:* import-observation probes, allowlist/parameter-policy
intersection, widening/unknown/contradictory rejection, and paired trusted/
less-trusted payload cases.

*Exclusions:* Python sandboxing, payload scalar changes, filesystem/sink policy
beyond capability kinds explicitly selected by E7.

E1-E6 may reach an independently accepted *Phase-E Payload-Conformance
Milestone* under a mandatory trusted-description precondition. Phase E remains
*Open* after that milestone. It becomes complete only when E7 is independently
accepted. Until then configured CLI/`run_app` execution must publish the
trusted-description precondition and must not advertise less-trusted pipeline
YAML as protected. The Domain Maintainer Contract, Phase F, and D-T3 remain
blocked on completed Phase E, not merely on the E1-E6 milestone.

|Custom/uncertified step returning an invalid ordinary candidate

==== 27. Design acceptance criteria

Independent architecture review should accept this design only if it confirms:

. all 15 accepted census questions are answered without being merged;
. the hybrid coverage model is truthful for every named entry surface;
. `run_pipeline`, supported lower-level APIs, and internals have distinct
  contracts;
. initial ingress, exact producer transitions, and uncertified-return
  re-establishment each have a short, distinct, testable postcondition;
. scalar grammar matches the accepted six categories and carriers exactly;
. validate-only scalar behavior preserves precision, timezone, and Missing
  representation;
. DataFrame, `ExactTable`, metadata, grouped/canonical carriers, declared
  framework Intent, and future carriers have distinct ownership/traversal rules;
. current physical-axis authority is preserved and any narrower vocabulary is
  gated by independently accepted compatibility evidence;
. metadata's exact node vocabulary is evidence-gated and every delegate is
  centrally governed and post-checked;
. custom producer output cannot reach later ordinary macro flow without
  preservation or re-establishment;
. producer certification is exact-bound-behavior scoped, defaults closed and
  uncertified, and does not require a repository-wide family audit;
. the maintained FormulaSpec helper path reaches capable output adaptation
  without admitting FormulaSpec at external ingress;
. payload and description trust remain independent and capability activation
  cannot precede authorization in any less-trusted-description claim;
. ingress/delegate work is non-mutating and staged before publication, while
  alias/concurrency isolation and rollback of prior effects are not promised;
. the bounded-composite seam is useful but chooses no representation;
. implementation slices are individually testable, preserve the E1-E6
  milestone/E7 completion distinction, and do not hide a giant FTR;
  and
. no runtime, ADR, Technical Model, Project Memory, guard, D-T3, or family-pilot
  authority is implied by design acceptance alone.

==== 30. Blocking-finding closure proofs

===== FormulaSpec lifecycle proof (Review 001 F1)

The maintained formula path composes without expanding external ingress:

[source,text]
----
router-loaded external payload
  -> initial ordinary ingress (FormulaSpec rejects)
  -> Ingress-Conformant Domain Payload
  -> exact reviewed add_lookup_helpers(helper_value_mode="formula") transition
  -> Conformant Framework Execution Payload
       with LookupFormulaSpec only in the declared helper-value role
  -> exact Intent-aware or Intent-transparent cleanup/projection
  -> FormulaSpec-capable XLSX/ODS output adaptation
  -> sink under its separate capability contract
----

FormulaSpec is neither Scalar nor `DeclaredComposite`. Only the exact reviewed
framework invocation may introduce the role; object shape or Python type alone
does not authorize it. If an uncertified producer intervenes, the role
authorization ends and ordinary re-establishment rejects all FormulaSpec. A
later formula helper may introduce a fresh role only through its own exact
reviewed transition. Thus the supported helper-to-renderer path remains
representable without external admission, composite abuse, re-establishment
bypass, or sink-authority collapse.

===== Bounded producer migration proof (Review 001 F2)

Phase E does not need a repository-wide producer audit:

[source,text]
----
small or zero exact proven preserving set
  + one bounded exact current Intent-introducing contract where required
  + closed uncertified default for every other bound behavior
  + ordinary re-establishment after each uncertified relevant return
  = truthful Phase-E Payload-Conformance Milestone
----

Callable/family review establishes only eligibility. Certification requires the
exact effective configuration, including covered callbacks, to have a closed
output contract. Therefore all 44 registry forms and parameter combinations do
not have to be certified before E5. The cost of the conservative initial state
is repeated traversal, not an unsound postcondition. Later family hardening may
add exact certificates as a performance optimization without changing Phase-E
semantics or becoming a Phase-E prerequisite.

This artifact remains design-only until that review completes.
