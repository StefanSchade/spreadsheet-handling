==== 1. Purpose and scope

*Central design question:*

____
What is the smallest Date/Time scalar contract the framework needs so that
ordinary structured/programmatic date values can safely cross a future
Trusted Ingress boundary without being silently stringified, numerically
reinterpreted, or made backend-specific?
____

This is not a request to design a full spreadsheet date/time system, to
mirror every Python/pandas/NumPy temporal class into a domain class, or to
start from a wrapper hierarchy. The working hypothesis this FTR tests --
stated as a hypothesis, not assumed -- is that a small canonical distinction
between *Date* and *DateTime* is sufficient. Section 7-8 evaluate that
hypothesis against current-repository evidence rather than accepting it by
default.

*In scope:* a current-state temporal-carrier inventory across every
maintained ingress/egress path; pandas/NumPy coercion findings; a Missing/NaT
interaction decision (including resolution of Independent Review 001's
deferred finding IVM-REVIEW-F7); a Date, DateTime, Time, Duration, and
timezone decision, each separately; a native-Python-vs-pandas-vs-wrapper
recommendation; comparison semantics; serialization, workbook-ingress, and
workbook-egress implications; the relationship to
`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` and to future Trusted Ingress; a
compatibility matrix; dependency-ordered implementation slices; acceptance
criteria; required executable tests; explicit non-goals; and open decisions
requiring human acceptance.

*Out of scope (this FTR does not do these; they are later, separately
authorized work):* any Python value-class implementation; any parser or
renderer change; any change to domain transformations; any CLI/runtime-policy
wiring; any registry or `_meta` schema change; Project Memory updates; a
successor/amendment ADR (this FTR only determines *whether* one will
eventually be needed -- section 17's finding is that none is required yet);
Trusted Ingress (Phase E) implementation; any Formula work of any kind.

`FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A` Slice 1 (D1-D3) has final,
independently reviewed acceptance (Review Pass 002, `e2a33b0`). Its accepted
semantic categories are *String, Boolean, Number, Missing* -- confirmed
current in `src/spreadsheet_handling/core/scalar_values.py`, re-read for this
FTR. Slice 1 deliberately did *not* establish a canonical normalized scalar

Slice 1's own docstring and FTR text (`FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A`
section 4, "Explicitly undecided") already anticipated this FTR:
`date`/`datetime`/`Timestamp` are explicitly rejected by `scalar_category`

candidate ... expected to be an *early* Phase-D follow-up slice." This FTR is
that follow-up. Formula remains a completely different kind of exclusion (not
a scalar-value candidate at all, ever) and is not reopened here.

This FTR does not modify `scalar_values.py`. All classifier behavior recorded
below (section 3's inventory table, section 6's Missing/NaT findings) was

==== 5. Pandas coercion findings [FACT]

Representative DataFrames were constructed and inspected directly (see
"Validation"). Findings, addressing the task's own central question ("can the
framework realistically promise a canonical Python carrier at every cell
while retaining normal pandas ergonomics?"):

[cols="3,3,3",options="header"]
|===
| Construction | Resulting column dtype | Scalar type at `.iloc[i]`

| Pure `datetime.date` list
| `object` (pandas does *not* promote this to `datetime64`)
| `datetime.date` (unchanged identity)

| Pure `datetime.datetime` list
| `datetime64[us]`
| `pandas.Timestamp`

| Mixed `date` + `datetime` in one column
| `object`
| Whatever each row actually was (`date` for the date row, `datetime` --
  not `Timestamp` -- for the plain-`datetime` row, confirmed by probe;
  pandas does not unify a mixed object column)

| `date` + `None`
| `object`
| `date` row unchanged; the `None` row stays a plain `None` (not `NaT`)

| `datetime` + `None`
| `datetime64[us]`
| The `None` row is silently promoted by pandas itself, at column
  construction time, to `pandas.NaT` -- *before* any framework code runs

| `pandas.to_datetime([...])` (direct construction)
| `datetime64[us]`
| `pandas.Timestamp`

| Timezone-aware `pandas.Timestamp` list
| `datetime64[us, <tz>]` (a genuinely distinct pandas extension dtype per
  timezone)
| `pandas.Timestamp` (aware, `tzinfo` preserved)
|===

*This directly answers the task's central pandas question, and confirms the
lesson the parent FTR already drew from Slice 1 must be repeated, not
re-litigated:* `ScalarCategory != canonical normalized representation`. A
"Date" payload value is not one pandas carrier shape -- it is at minimum
`datetime.date` (object dtype) *and* `pandas.Timestamp`/`datetime64[us]`
(whenever pandas' own dtype inference promotes it, including via a mixed
column or an explicit `pd.to_datetime` call). Demanding a single canonical
in-memory carrier at every cell, always, would require either fighting
pandas' own promotion behavior (rejected -- exactly the ergonomics cost
Slice 1's section 6 already rejected for the String/Boolean/Number/Missing
MVP) or accepting that classification is a *carrier-recognition* contract,
not a value-representation contract, restated below in sections 6-8.

An unexpected, concretely reproduced consequence of this asymmetry: *`date`
and `datetime`+`Missing` behave differently by construction, not by design.*
A missing value in a pure-date object column stays a plain `None`; a missing
value in a real `datetime64`-dtype column is silently rewritten to
`pandas.NaT` by pandas itself. Both are already correctly recognized as
Missing by `is_missing_carrier` today (`None` via its first branch, `NaT` via
identity) -- this is not a defect, it is evidence that the *recognition*
contract (Slice 1's own approach) already generalizes correctly across this
asymmetry without needing to know which pandas construction path produced the
missing value.

==== 6. Missing / NaT decision [RECOMMENDATION -- resolves IVM-REVIEW-F7]

*[FACT, corrected -- current state, not the original state this section was
written against]* When this section was first written, `is_missing_carrier`/
`scalar_category` classified *both* `numpy.datetime64('NaT')` *and*
`numpy.timedelta64('NaT')` as `"missing"`, purely as a side effect of the
`isinstance(value, (int, float, np.generic))` bounded-dispatch guard added by
the IVM-REVIEW-F1 fix: `np.generic` is the base class for NumPy's *entire*
scalar hierarchy, not only the numeric kinds the guard was written for, so
any NaT-valued NumPy temporal scalar reached `pandas.isna` and was recognized
as missing, while a non-NaT NumPy temporal scalar of the same type correctly
fell through to `UnsupportedScalarError`. Independent Review 001 recorded
this as Minor finding *IVM-REVIEW-F7*, explicitly deferred "into this
Date/Time discussion" -- this section is that discussion.
+
*This is no longer true for `numpy.timedelta64('NaT')`.*
`BUG-NUMPY-TIMEDELTA64-NUMBER-MISCLASSIFICATION-P4A` (fixed `022f651`,
independently reviewed and closed, archived at
`docs/cold_storage/backlog/ftrs_done/`) added an explicit `np.timedelta64`
exclusion to `is_missing_carrier`'s bounded dispatch, so
`numpy.timedelta64('NaT')` now raises `UnsupportedScalarError` like every
other `numpy.timedelta64` value -- confirmed in section 3's table. Only the
`numpy.datetime64('NaT')` half of IVM-REVIEW-F7 remains open; decision 2
below still applies to it, deferred to D-T1 as before. Decision 3 below is
retained for historical/decision-record purposes (it states the same
principle the closed BUG independently implemented) but no longer describes
outstanding D-T1 work.

*The relevant precedent already exists in the accepted contract, for a
different NumPy scalar family.* The same IVM-REVIEW-F1 fix independently
resolved an analogous case for `complex`: before the fix, a NaN-valued
`complex` misclassified as `"missing"`; after the fix, *every* `complex`
value -- NaN-valued or not -- correctly raises `UnsupportedScalarError`,
because `complex` is not one of the bounded-dispatch types
(`int`/`float`/`np.generic`)... except that `numpy.complex128` *is* a
`np.generic` subclass and was separately confirmed (Review Pass 002) to
still misclassify its NaN form as missing, for the identical reason as
`datetime64`/`timedelta64`. The review's own resolution note states the
governing principle plainly: an unsupported *category* should reject *all*
its instances uniformly, "depending only on its NaN-ness" is "an
inconsistency within the same rejected type family." That principle,
already applied to `complex128`, answers this FTR's own question by direct
analogy.

*Decision:*

. *`pandas.NaT` remains Missing, unconditionally, unchanged.* It is
  pandas' own canonical temporal-missing sentinel; there is no non-missing
  value it could otherwise represent, and it is recognized by identity, not
  by dispatching to any type-specific classification logic. No further
  action needed; this is not part of IVM-REVIEW-F7's scope and this FTR does
  not touch it.
. *`numpy.datetime64('NaT')` should classify as Missing only once
  Date/DateTime is a supported category, through an explicit,
  `datetime64`-specific branch -- not through the generic `np.generic`
  bounded dispatch.* Until that implementation slice lands, per the
  `complex128` precedent, it should raise `UnsupportedScalarError` exactly
  like every other `datetime64` value, consistent, not "missing" as a
  side-effect of an unrelated guard's breadth. This *is* IVM-REVIEW-F7's
  required fix; this FTR records the decision, the implementation is
  deferred to slice D-T1 (section 20), not performed here.
. *`numpy.timedelta64('NaT')` should raise `UnsupportedScalarError`, not
  classify as Missing, for as long as Duration remains an unsupported
  category (section 10) -- ALREADY DONE, not D-T1 scope.* The same reasoning
  applies unchanged: an unsupported category rejects all its instances,
  NaT-valued or not. `BUG-NUMPY-TIMEDELTA64-NUMBER-MISCLASSIFICATION-P4A`
  independently implemented exactly this decision (`022f651`), closed and
  archived; D-T1 does not need to perform this correction, only confirm it
  as a non-regression (section 22). If a future slice ever adds Duration
  support, that slice decides Duration's own Missing semantics at that time:
  this FTR does not pre-decide it, per the task's own instruction not to let
  NumPy's shared temporal-scalar hierarchy force Duration into the Date/Time
  MVP.
. *Complex NaN is unrelated to this FTR and is not decided or fixed here.*
  Already independently re-confirmed for this FTR (section 3): plain
  `complex` (the built-in, non-NumPy type) is not `np.generic`, never
  reaches the bounded dispatch, and is uniformly rejected, NaN or not. By
  contrast, `numpy.complex128` -- confirmed above in this section -- still
  classifies its NaN form as Missing today; it is *not* already fixed or
  already-resolved by `BUG-NUMPY-TIMEDELTA64-NUMBER-MISCLASSIFICATION-P4A`
  or by anything else. This is a separately-tracked, unrelated Minor
  documentation-and-runtime inconsistency
  (`TD64-REVIEW-F1` in
  `BUG-NUMPY-TIMEDELTA64-NUMBER-MISCLASSIFICATION-P4A_review.adoc`, and
  `DTVM-FOLLOWUP-F2` in this FTR's own
  `FTR-DATE-TIME-INTERNAL-VALUE-MODEL-P4A_review.adoc`), governed by the
  same principle stated above (an unsupported carrier family should not
  gain Missing semantics merely because one instance is NaN-like) but not
  yet brought into line with it. D-T1 neither owns nor depends on fixing
  `numpy.complex128`; nothing here reopens or resolves it, and nothing in
  Date/DateTime's own classification contract relies on it being fixed.

*Why this is the correct place to decide it, not a premature narrowing:*
IVM-REVIEW-F7's own disposition already named the trigger condition for
resolving it -- "a future slice begins wiring `is_missing_carrier` to real
ingress, *or extends the module to explicitly consider Date/Time*." This FTR
is that second trigger. Recording the decision now, ahead of the
implementation slice that applies it, keeps the fix from being invented ad
hoc mid-implementation and keeps it consistent with the already-decided
`complex128` case rather than treated as a fresh question.

==== 7. Date decision [RECOMMENDATION]

*Adopt `Date` as a supported MVP scalar category*, with native
`datetime.date` as its conceptual canonical carrier.

Evidence:

* *[FACT]* `datetime.date` is already reachable through a maintained,
  non-programmatic ingress path (YAML, section 3-4) -- this is not a
  theoretical candidate invented for symmetry with DateTime.
* *[FACT]* Pandas does not auto-promote a pure `datetime.date` column to any
  other dtype/scalar type (section 5) -- `Date` survives ordinary DataFrame
  construction as exactly the native Python type this FTR recommends
  canonical, with zero coercion cost.
* *[FACT]* Normalizing `date -> midnight datetime` is not free of semantic
  loss: it cannot be undone (a `datetime` at exactly midnight is
  indistinguishable from "this was originally date-only" once normalized),
  and the openpyxl round-trip probe (section 4) shows this loss already
  happens *silently* today, one layer below the framework's own parser, for
  any date value that reaches a spreadsheet backend by any path -- evidence
  this FTR treats as a reason to keep Date distinct at the domain-value
  level, not a reason to accept the same collapse internally too.
* *[FACT]* The roadmap's own Phase D candidate scalar list
  (`roadmap_domain_hardening_sequence.adoc`) already names `date` as a
  candidate distinct from `datetime`, independent of this FTR's own
  analysis.

*Recommendation:* `datetime.date` is Date's canonical native-Python
carrier. `pandas.Timestamp`/`datetime64`-backed values are *not* Date
carriers, even when their time-of-day happens to be midnight -- see section
8's classification-order note; a midnight `Timestamp` is a DateTime value
that happens to fall at midnight, not evidence it should be reclassified as
Date. This FTR does not invent a Date/DateTime disambiguation heuristic based
on time-of-day.

==== 8. DateTime decision [RECOMMENDATION]

*Adopt `DateTime` as a second, distinct supported MVP scalar category*, with
native `datetime.datetime` as its conceptual canonical carrier, and
`pandas.Timestamp`/`numpy.datetime64` accepted as carrier variants that
classify into it (per the same "classify without narrowing" contract Slice 1
already established for Number/Boolean's NumPy variants).

Evidence:

* *[FACT]* `datetime.datetime` and `pandas.Timestamp` are both already
  reachable through the same maintained YAML ingress path that produces
  `datetime.date` (section 3-4) -- confirmed for both the naive and the
  timezone-aware case.
* *[FACT]* Pandas *does* promote a `datetime`-bearing column to a dedicated
  `datetime64[...]` dtype with `Timestamp` scalars (section 5) -- the
  opposite of Date's behavior. This asymmetry is concrete evidence the two
  categories are not interchangeable at the pandas-ergonomics level, not
  merely at the conceptual level.
* *[FACT]* `date -> datetime` and `datetime -> date` comparisons both raise
  `TypeError` today (`'<' not supported between instances of 'datetime.date'
  and 'datetime.datetime'`, confirmed by direct probe) -- Python's own
  runtime already refuses to treat them as freely comparable. Collapsing
  them into one category would paper over a distinction the language itself
  enforces.
* *[FACT, correctness-critical for implementation]* `pandas.Timestamp`
  subclasses `datetime.datetime` (confirmed:
  `isinstance(pandas.Timestamp(...), datetime.datetime) is True`), and
  `datetime.datetime` subclasses `datetime.date` (stdlib). A future
  classifier *must* check DateTime (`datetime.datetime`/`Timestamp`) before
  Date (`datetime.date`), exactly mirroring Slice 1's existing
  Boolean-before-Number ordering rule (`bool` subclasses `int`) -- this is
  not a new kind of problem, it is the same subclass-ordering hazard Slice 1
  already solved once, applied to a second pair.

*Recommendation:* `datetime.datetime` is DateTime's canonical native-Python
carrier; `pandas.Timestamp` and `numpy.datetime64` are accepted DateTime
carrier variants, classified without being narrowed to `datetime.datetime`
(same non-normalizing posture Slice 1 already uses for NumPy numeric/boolean
variants -- see section 12). `numpy.datetime64`'s internal unit/precision
(`'D'`, `'us'`, etc.) is *not* used to infer Date-vs-DateTime intent -- doing
so would be exactly the kind of "guess a richer type from carrier internals"
heuristic the accepted contract already rejects for strings (parent FTR,
Stage C), applied instead to a NumPy dtype flag.

*[DECIDED -- no longer open, per Independent Architecture Review 001's own
additional evidence]* Every supported non-`NaT` `numpy.datetime64` value
classifies as DateTime, uniformly, regardless of unit/precision; no future
slice infers Date from `unit == "D"` or from a midnight time-of-day. The
independent review did not merely accept this FTR's stated preference, it
independently strengthened the evidence: `np.datetime64(pd.Timestamp("2026-08-09 00:00:00"), "D")`
and `np.datetime64("2026-08-09", "D")` are bit-identical once stored at day
precision -- no information about authoring intent ("this was written as a
calendar date" versus "this was a midnight `DateTime` truncated/resampled to
day granularity") survives the cast, so unit-based disambiguation is not
merely undesirable by policy, it is *not reliably possible* from the carrier
alone. The review separately confirmed pandas does not even preserve the
NumPy unit through ordinary `Series` construction (`datetime64[D]` and
`datetime64[m]` source arrays both produce a `datetime64[s]`-dtype `Series`
of `Timestamp` scalars in the installed pandas version), discarding the
original unit before any framework code runs. Semantic Date recognition from
a raw `numpy.datetime64` value, if ever wanted, requires an out-of-band
schema or producer-supplied hint, not carrier/unit inspection -- and no
current evidence calls for building that. This closes what section 24
previously listed as open decision 1.

Normalization loss, evaluated both directions per the task's instruction:

* *`date -> datetime` (implicit midnight):* lossy in the sense described in
  section 7 -- irreversible, and already an observed silent side effect of
  the XLSX carrier round trip (section 4), not a hypothetical risk.
* *`datetime -> date` (drop time-of-day):* lossy whenever the time component
  is not exactly midnight -- an ordinary, expected form of information loss,
  acceptable only as an explicit, opt-in projection a future codec/slice
  chooses deliberately, never as an implicit default coercion.

Neither direction is free; this FTR does not recommend a default automatic
normalization between the two categories in either direction.

==== 9. Time-only decision [RECOMMENDATION -- deferred]

*[FACT]* No maintained producer or consumer of a bare `datetime.time` value
was found anywhere in the repository: no parser ever constructs one (ODS's
`time-value` fallback attribute is read and immediately stringified, exactly
like every other ODS fallback attribute; XLSX has no time-specific handling
at all), and no domain transformation was found to construct or expect one.

*[FACT]* `scalar_category(datetime.time(...))` already raises
`UnsupportedScalarError` today, correctly -- not silently absorbed into
String. This is Slice 1's existing behavior, unchanged and unaffected by this
FTR.

*[FACT, new finding for this FTR]* Even independent of the internal value
model, no current serialization path can represent a bare `datetime.time` at
all: both `yaml.safe_dump` and `json.dumps` raise directly on a native
`datetime.time` object (confirmed by probe -- PyYAML's `SafeDumper` has no
`time`-only representer, unlike its `date`/`datetime` representers, which
both succeed). Adding Time support would therefore require *inventing* a
serialization contract from nothing, unlike Date/DateTime, which already have
a working YAML round trip today (modulo the DateTime-specific gap recorded in
section 14) and merely lack a JSON contract. Time is strictly more expensive
to support than Date/DateTime, not merely equally deferred by symmetry.

*Recommendation:* defer Time explicitly, not silently. If a `datetime.time`
value reaches a future Trusted Ingress boundary before Time support exists,
it must be *explicitly rejected* with a diagnostic -- which is already
`scalar_category`'s current behavior, so Phase E inherits correct behavior
for free the moment it starts calling the classifier, without needing its
own special case for Time. No maintained consumer currently needs this
changed.

==== 10. Duration / Timedelta decision [RECOMMENDATION -- deferred]

*[FACT]* No maintained producer of `datetime.timedelta`, `pandas.Timedelta`,
or `numpy.timedelta64` was found anywhere in domain transformations. The
parent FTR's Stage E already established that arithmetic reaching payload
cells (as opposed to framework-internal row/column counters) is not a
current pattern; this generalizes directly to duration arithmetic, which is
strictly a narrower case.

*[FACT, current, corrected]* `scalar_category` correctly rejects
`datetime.timedelta`, `pandas.Timedelta`, and every `numpy.timedelta64`
value (`NaT` or not) with `UnsupportedScalarError`, unaffected by this FTR.
*This section originally claimed non-`NaT` `numpy.timedelta64` was
"already correctly rejected... confirmed by probe" -- that claim was false
when written (DTVM-REVIEW-F1): it silently misclassified as `"number"`
instead. `BUG-NUMPY-TIMEDELTA64-NUMBER-MISCLASSIFICATION-P4A` (`022f651`,
independently reviewed and closed) fixed it; the statement above is now
accurate as current fact, not as a claim this FTR should have made without
evidence. See section 3's table and section 6 for the full correction.*

*Recommendation:* defer Duration entirely, and keep it *conceptually*
distinct from Date/Time even though NumPy happens to implement both temporal
scalar families under one shared `np.generic` ancestor. A duration is a
difference between two points in time, not a point in time itself --
different arithmetic (durations sum meaningfully; dates do not), different
comparison semantics, and a different eventual category boundary. IVM-REVIEW-F7
(section 6) is the concrete evidence of what happens when an implementation
detail shared between two NumPy scalar families (`np.generic`) is allowed to
blur a semantic boundary the domain model should keep separate; this FTR's
recommendation explicitly guards against repeating that shape for
Date/Time-vs-Duration specifically. NaT-shaped duration carriers are Missing
only once Duration itself is a supported category (section 6, decision 3);
until then they are simply unsupported, like every other `timedelta64` value.

==== 11. Timezone decision [DECIDED -- category membership decided; canonicalization policy remains deferred]

*[FACT]* Timezone-aware datetime values are already reachable today, through
the same maintained YAML ingress path as naive ones: `yaml.safe_load` on
`2026-08-09T10:30:00+02:00` produces an aware `datetime.datetime` directly,
and the resulting pandas column becomes a genuinely distinct extension dtype
(`datetime64[us, UTC+02:00]`) with aware `Timestamp` scalars (confirmed by
probe). This is not a hypothetical edge case reserved for a distant future
slice -- it is exactly as reachable as the naive case this FTR otherwise
recommends supporting.

*[FACT]* XLSX and ODS date cells carry no timezone concept at all, by format
design -- confirmed by probe (no `tzinfo` anywhere in either backend's native
date-cell round trip). Timezone-aware values can therefore only ever
originate from YAML or direct-Frames construction, never from a spreadsheet
backend.

*[FACT]* Naive-vs-aware comparison raises `TypeError` today
(`"can't compare offset-naive and offset-aware datetimes"`, confirmed by
probe) -- Python's own runtime already refuses to silently compare across
the naive/aware boundary. Sorting a column containing both would fail the
same way.

*[FACT]* Serialization does not introduce a *new* failure mode for
timezone-awareness specifically: the general DateTime-write gap recorded in
section 14 (a `pandas.Timestamp`-backed column crashes `yaml.safe_dump`)
reproduces identically whether the `Timestamp` is naive or aware -- the
crash is caused by `Timestamp` itself lacking a `SafeDumper` representer, not
by its timezone. A plain (non-pandas) aware `datetime.datetime` does
round-trip correctly through `yaml.safe_dump`/`safe_load` with its offset
preserved exactly (confirmed by probe) -- but every YAML-backend read/write
path in this repository goes through a `pandas.DataFrame`, which converts
that plain aware `datetime.datetime` into a `Timestamp` before any write
occurs, so the working plain-object case is not actually reachable through
the maintained backend path today.

*Decision [DECIDED -- no longer open, per Independent Architecture Review
001, narrowed to the smallest non-lossy value-model rule]:* timezone
awareness is a property of a DateTime value, not a separate scalar category.
Both naive `datetime.datetime`/`Timestamp` and timezone-aware
`datetime.datetime`/`Timestamp` classify as `DateTime`. The classifier must
not strip `tzinfo`, must not silently convert an aware value to naive, and
must not assume UTC for a naive value -- each would discard information no
current evidence says is safe to discard. The existing native behavior that
naive-vs-aware ordering/comparison raises `TypeError` (confirmed by probe
above) is preserved, not papered over; this FTR does not invent
cross-naive/aware comparison semantics.
+
*Ownership boundary, stated explicitly so a future slice does not overreach:*
this decision settles *category membership* only -- a timezone-aware value is
`DateTime`, full stop. It does *not* establish a canonical
timezone-normalization *policy*. No current evidence shows a maintained
consumer performing cross-timezone arithmetic, conversion, or comparison, so
there is no basis yet to decide whether some future boundary should normalize
to UTC, preserve the original offset, or reject mixed naive/aware datasets. A
future Phase-E ingress/policy layer, or a specific consumer with a concrete
contract, may still decide to restrict particular timezone shapes if a real
need arises -- that is a later, narrower, evidence-gated decision, not
designed or pre-empted here. This closes what section 24 previously listed as
open decision 2 at the value-model/category level; it does not open a new
policy-design task.

==== 13. Comparison semantics [RECOMMENDATION]

What a future Domain operation may safely assume, stated explicitly per the
task's own instruction not to define cross-type ordering merely because
Python/pandas happens to do something today:

[cols="3,2,4",options="header"]
|===
| Comparison | Legitimate without normalization? | Basis

| `Date` vs `Date`
| Yes
| Native `datetime.date` ordering; unaffected by anything in this FTR

| `DateTime` vs `DateTime` (both naive, or both aware with compatible offset
  handling)
| Yes
| Native `datetime.datetime`/`Timestamp` ordering; `Timestamp` and
  `datetime.datetime` already compare correctly against each other
  (confirmed by probe: `Timestamp(...) < datetime(...)` and
  `Timestamp(...) == datetime(...)` both work), because `Timestamp`
  subclasses `datetime.datetime`

| `Date` vs `DateTime`
| *No, without an explicit, chosen normalization.* Confirmed by probe:
  Python itself raises `TypeError`. This FTR does not recommend defining an
  implicit cross-category ordering; a future consumer that needs to compare
  the two must explicitly choose and apply one of section 8's two lossy
  normalization directions first.

| Naive `DateTime` vs aware `DateTime`
| No. Confirmed by probe: Python itself raises `TypeError`. This FTR
  recommends preserving that rejection rather than silently assuming a
  timezone for the naive side.

| Missing vs `Date`/`DateTime`
| Not an ordering question -- `is_missing_carrier` recognition already
  answers "is this cell missing" independent of category (section 6);
  ordering a column containing Missing values is a sorting-null-handling
  question for whatever future transformation performs the sort, not a
  value-model question this FTR needs to answer.

| Sorting a column containing both `Date` and `DateTime` values
| *No, not without normalization first.*
| Confirmed by probe: `sort_values()` on a mixed object-dtype `Series`
  containing both raises the same `TypeError` as the pairwise comparison
  above -- pandas does not paper over the underlying Python-level
  incomparability.
|===

*Recommendation:* Domain operations may assume same-category ordering is
safe (`Date`-`Date`, `DateTime`-`DateTime` with compatible
awareness/timezone), and must not assume cross-category ordering
(`Date`-`DateTime`, naive-aware) is safe without an explicit, chosen
normalization performed by the caller. No current maintained transformation
was found to perform date-based sorting or range filtering at all (the
`where:` predicate engine in `domain/_where_predicates.py` supports only
`equals`/`in`/`non_empty`/`is_null`/`not_null` -- no ordering predicate
exists today), so this FTR is not constrained by an existing consumer's
behavior; it is free to recommend the safer, non-silent default.

==== 18. Relationship to future Trusted Ingress (Phase E)

*Should Date/Time runtime support land before mandatory Trusted Ingress?*
This FTR's evidence *confirms*, rather than merely repeats, the parent FTR's
own tentative recommendation (its section 17.9, itself explicitly flagged
there as "a recommendation, not a decision"): *yes, preferably, for adoption
continuity, but not because Phase E is technically incapable of rejecting
Date/Time.*

The confirming evidence this FTR adds: Date/Time is not a hypothetical
adoption risk -- section 4 shows it is *already reachable today* through the
maintained YAML ingress path, unconditionally, for any adopter using YAML
timestamp syntax. A primitive-only Phase E slice wired ahead of this FTR's
Date/Time acceptance work would correctly reject every such value today
(`scalar_category` already raises `UnsupportedScalarError` for it, per
Slice 1) -- technically sound, per the parent FTR's own point -- but would
regress any current adopter whose YAML files already contain ordinary
calendar dates, the moment Trusted Ingress became mandatory rather than
opt-in. This FTR's own value-flow matrix (section 4) is the concrete
evidence the parent FTR's recommendation predicted but had not yet gathered.

*What Phase E still owns after Date/Time lands (unchanged in kind from the
parent FTR's own section 16/17.9 handoff, restated here for Date/Time
specifically):*

* canonical normalization application -- turning an accepted `Timestamp`/
  `numpy.datetime64` carrier into whatever the eventual
  `normalize_scalar()`-shaped primitive decides (this FTR does not build
  that primitive, per section 12);
* frame-level traversal -- calling the classifier at every real cell across
  a whole Frame, not a per-scalar concern;
* rejection policy -- what happens to a `datetime.time`/`timedelta`/
  timezone-mixed value at a real ingress point (reject with diagnostic vs.
  another bounded behavior) remains Phase E's decision, not this FTR's;
* runtime/trust policy and boundary wiring -- the ingress *mechanism*
  question (extend `INGRESS_RULES`, subphases, delegated schemas, or another
  coordinator design) remains entirely open, exactly as the parent FTR left
  it for the String/Boolean/Number/Missing case; this FTR takes no position
  for Date/Time either.

This FTR does not implement any of the above; it only sharpens the parent
FTR's already-recorded recommendation with concrete reachability evidence.

* `ScalarCategory` extended from a four-member to a six-member closed
  `Literal`: `"string", "boolean", "number", "missing", "date", "datetime"`.
  No `"time"`, `"duration"`, `"formula"`, or `"list"` member -- matching
  section 15's instruction exactly.
* `ScalarValue` extended from `str | bool | int | float | None` to
  `str | bool | int | float | datetime.date | datetime.datetime | None`.
  `datetime.date`/`datetime.datetime` were added because they play the same
  "conceptual canonical carrier" role for Date/DateTime that `int`/`float`
  already play for Number (section 12); their carrier *variants*
  (`pandas.Timestamp`, `numpy.datetime64`) were deliberately *not* added,
  for the same reason `numpy.int64`/`numpy.float64` were never added --
  consistent with the alias's own documented meaning, not a claim that every
  accepted carrier class is enumerated by it.
* `scalar_category` gained two new branches, appended after the existing
  Number branch and before the trailing `raise`:
+
[source,python]
----
if isinstance(value, (np.datetime64, datetime.datetime)):
    return "datetime"
if isinstance(value, datetime.date):
    return "date"
----
+
`datetime.datetime` and `np.datetime64` are checked together because
`np.datetime64` is unrelated to `datetime.date`/`datetime.datetime` by
inheritance (confirmed: its `__mro__` is only `(numpy.datetime64,
numpy.generic, object)`), so there is no ordering hazard between them; the
DateTime-before-Date ordering hazard is only between `datetime.datetime`
(and its subclass `pandas.Timestamp`) and `datetime.date`, and the code
above resolves it by checking the `datetime.datetime` branch first, exactly
mirroring the existing Boolean-before-Number pattern in the same function.
`pandas.Timestamp` is not named explicitly in the `isinstance` check -- it
does not need to be, since it subclasses `datetime.datetime` and is caught
by that check.
* `is_missing_carrier` gained one new explicit branch, inserted after the
  existing `np.timedelta64` exclusion and before the generic
  `np.generic`-bounded dispatch:
+
[source,python]
----
if isinstance(value, np.datetime64):
    return bool(np.isnat(value))
----
+
This closes the remaining `numpy.datetime64` half of IVM-REVIEW-F7
(section 6, decision 2): before this change, `np.datetime64('NaT')` reached
`"missing"` only as a side effect of the broad `np.generic`-bounded
`pandas.isna` dispatch (the same mechanism that, pre-D-T1, made no
distinction between "this NumPy scalar family is a supported category" and
"this NumPy scalar family merely happens to expose NaN-like behavior").
`numpy.isnat` was chosen over `pandas.isna` for this branch per the task's
own preference for "a bounded temporal-specific operation supported directly
by NumPy" -- it operates only on `datetime64`/`timedelta64` scalars, raising
`TypeError` on anything else, so no broadening of what reaches the function
occurs; the `isinstance(value, np.datetime64)` guard means it is only ever
called on a value already known to be exactly that type.
* Module docstring, `UnsupportedScalarError`'s diagnostic message, and both
  functions' own docstrings were updated to describe the new Date/DateTime
  categories and the explicit `datetime64`-NaT branch, replacing the
  now-stale "date/datetime/Timestamp is rejected" language Slice 1 had left
  in place.
