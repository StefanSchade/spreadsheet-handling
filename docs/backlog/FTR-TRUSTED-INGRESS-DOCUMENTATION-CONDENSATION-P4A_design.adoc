[[scope-control]]
==== 1. Objective and scope control

Per the task brief, the goal is a fresh competent agent being able to
understand current Trusted-Ingress architecture from Semantic Model +
Technical Model + Developer Guide + interfaces/gates + relevant ADRs + module
structure + local source comments, *without* reading the 7,661-line FTR, its
frozen E1 review ledger (7,885 lines), the E2-E7 slice reviews (13 files,
~11,000 lines combined), or the Dotted-Extension review history. See
<<fresh-agent-test>> for the operational test.

This design artifact does not: change `src/` or `tests/`; redesign E1-E7;
change public APIs; add Phase-F requirements; write a Domain Maintainer
Contract; begin D-T3; archive historical evidence; or mark documentation
closure complete. It identifies canonical content, assigns durable homes, and
sequences bounded implementation slices with review gates.

===== A. Payload language (8 invariants)

[cols="1,6,3",options="header"]
|===
| # | Invariant (paraphrase) | Evidence

| A1 | Domain has a positive internal grammar, not merely "whatever pandas
  holds": `Scalar` is String, Boolean, Number, Missing, Date, or DateTime;
  Phase E admits zero composite variants. | FTR §2/§7 (~lines 798-800)

| A2 | Composites are explicit and declared, never inferred from delimiter or
  shape -- a numeric-, boolean-, date-, formula-, SQL-, shell-, or
  HTML-looking string remains String. | FTR §7 (~lines 920-922)

| A3 | Carrier representation and semantic category are distinct axes (raw
  carrier observation vs. accepted carrier-specific substrate vs.
  pandas/NumPy carrier vs. canonical domain scalar). | `internal_value_model.adoc`
  "Semantic categories versus carrier variants" (accepted, Phase D); historical
  fuller taxonomy in ch04 concept §7

| A4 | Missing is recognition, not representation -- a bounded carrier family
  (`None`, `""`, NaN/`pandas.NA`/`NaT` variants), not a new sentinel. | `internal_value_model.adoc`
  "Missing is recognition, not representation" (accepted, Phase D)

| A5 | Successful ingress establishes a downstream assumption: ordinary Domain
  code does not defend against arbitrary external Python objects once Trusted
  Ingress has run. | FTR §2 (Ingress-Conformant Domain Payload definition)

| A6 | Visible spreadsheet payload is a string substrate by prior accepted
  decision (`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE`), not an omission this
  work reopens. | ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE; ch04 concept §1

| A7 | The framework's value proposition is a defined internal data language
  plus a reusable transformation algebra: generic transformations operate on
  the closed Domain grammar rather than defensively interpreting arbitrary
  external carriers, moving complexity to one boundary. | Synthesis from A1-A5;
  no single accepted sentence states this -- new framing content, not a restatement

| A8 | `FormulaSpec` and other framework-authored declarative output are
  Intent, not ordinary Scalar payload, and are not subject to the ingress
  scalar grammar. | ch04 concept §7 category 11; `agent_rules.adoc`
  persistence-boundary rule
|===

===== B. Ingress responsibility (6 invariants)

[cols="1,6,3",options="header"]
|===
| # | Invariant (paraphrase) | Evidence

| B1 | E1-E3 establish (and, on uncertified return, re-establish) the trusted

  acyclic metadata substrate; this is not transformation- or business-level
  validity. | FTR §2 (~lines 2197-2199); E3 design + census

| B2 | Classification order is fixed: actual-type membership is always
  checked before any value-level probe (`== ""`, `isna`, etc.) -- never falls
  back through `isinstance` after a failed exact-type check. Re-derived
  independently for both E1 scalars and E2 DataFrame/String dispatch. | FTR
  E1 §33.2 (~3877-3886); E2 §36.2 (~4246-4257)

| B3 | Ingress diagnostics are intentionally bounded/constant
  (`UnsupportedScalarError` records only "unsupported runtime type", never
  the raw value or exact type name). | FTR §33.3 (~3888-3907)

| B4 | `_meta` participates in payload-conformance ingress as an owned,
  bounded, acyclic framework substrate; root-specific authoring delegates
  are closed, centrally reviewed transitions, not dynamic extensions. | FTR

| B5 | `pipeline.run_pipeline` bypasses `domain.ingress`, the persistence
  boundary, and E4/E5 entirely -- a documented trusted-programmatic-composition

| B6 | Ingress conformance is necessary but not sufficient for family-specific

|===

===== C. Execution authority (5 invariants)

[cols="1,6,3",options="header"]
|===
| # | Invariant (paraphrase) | Evidence

| C1 | E4 certificate identity is deep-immutable at construction (single
  construction path; the earlier mutable `bind()` path was removed by
  correction) -- authority does not depend on secrecy or provenance, only on
  what constructing/using the object necessarily causes to execute. This is
  the load-bearing property behind the task brief's "Certified Invocation
  Stability" label; that exact phrase is *not* accepted terminology anywhere
  in the FTR and must not be promoted as a quoted term without the promoting
  slice re-deriving its own wording. | FTR E4 Blocking F1 and final
  self-review, §44.12 (~6491-6510)

| C2 | No callable, family, registry entry, wrapper, or built-in is preserving
  merely by identity; framework authorship or class identity alone is
  insufficient authority. | FTR §20 (~2162-2168)

| C3 | E5 wires the one coherent macro seam (`orchestrate`): classify ->
  execute -> apply; rejection blocks every later step and the saver (no
  partial output). `run_pipeline` remains byte-for-byte untouched and
  unwired. No preserving certificate was manufactured to shortcut
  re-establishment (`PRESERVING_CERTIFICATES` stays empty). | E5 review
  (~lines 6616+, 6796-6841)

| C4 | Acceptance and reachability/wiring are separate axes: an independently
  accepted ingress rule (E2's `admit_ordinary_frames`) can still be
  unreachable until a later slice explicitly wires it in. | E5 review §45.3
  (~6585-6606) -- also a maintainer-facing lesson, see Slice C

| C5 | Role-relevant effective configuration participating in a certificate's
  identity is enumerated per certificate type and consists entirely of frozen
  scalars/tuples -- there is no mutable-by-reference field an ordinary caller
  could alter post-construction. | FTR §44.7 (~6365-6422)
|===

===== D. Description authority (6 invariants)

[cols="1,6,3",options="header"]
|===
| # | Invariant (paraphrase) | Evidence

| D1 | E6 defines exactly two surface classes: framework-managed entry points
  (`orchestrate`, `run_app`, `run_schema_maintenance`, and the CLI/shim that
  reach them) that automatically establish E1-E3 conformance and apply E4/E5
  transition/authorization; and caller-precondition surfaces (`run_pipeline`,
  `build_steps_from_config`/`_yaml`, the six `make_*_step` factories, direct
  `BoundStep` composition, direct backend read/write, `domain.ingress`
  internals) where the caller owns all conformance/preservation/
  re-establishment. | E6 review §"public-contract closure table"
  (~lines 291-324); already largely reflected in `interfaces_and_gates.adoc`
  lines 42-99

| D2 | E7 uses positive/allowlist capability authorization, never a
  denylist; absence denies; an unclassified future registry entry fails
  closed. | E7 design §"trust-mode representation" (~line 1125, ~227); design
  review confirms "capability-authorization ordering for every one of the
  eight accepted surfaces" survived independent testing

| D3 | Authorization precedes import/acquisition/factory/binding/resource
  activation -- the general capability-activation timing invariant from
  `ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY` Decision 4, specialized for E7:
  denied registered steps never reach `resolve_registration`/factory/
  binding/invocation; a denied `apply_overrides` path is rejected before
  internal-target import, binding, `Path.exists`, or `open`. | ADR Decision 4;
  E7 design §7.2 (~494-502); FTR §47.4-47.5 (~7464-7488)

| D4 | Registered short-name identity differs from internal target wiring:
  once a short name and its parameters are authorized, the registration's
  internal target is trusted framework wiring and is not re-checked as a
  plugin. | FTR §47.4 (~7472-7473)

| D5 | An E7-authorized plugin is trusted same-process Python under its
  *complete current argument contract* -- E7 does not recursively inspect
  plugin arguments or infer filesystem/network/command/environment
  permissions from argument names. Not a Python sandbox. | FTR §47.5
  (~7490-7493)

| D6 | Direct Python callable targets and direct `BoundStep` composition
  remain a separate, deliberately-bypassing, trusted-programmatic-composition
  surface by design -- not a gap in the dotted-string resolver. | ch04
  concept §3.2 (confirmed still current; unaffected by E7)
|===

===== E. Resource authority (4 invariants)

[cols="1,6,3",options="header"]
|===
| # | Invariant (paraphrase) | Evidence

| E-1 | Only four resource-sensitive registered steps receive E7 resource
  semantics today: `apply_overrides`, `write_structured_yaml`,
  `write_key_value_resources`, `write_artifact_manifest`. Registry membership
  alone never grants less-trusted authorizability to a new capability. | E7
  design §7 (~467-559); FTR §47.6 (~7495-7526)

| E-2 | `apply_overrides`'s external `overrides_path` is always denied in
  less-trusted mode (must be absent or exactly `None`), rejected before any
  internal-target import, binding, `Path.exists`, or `open`. | E7 design §7.2
  (~494-502)

| E-3 | Writer authority uses an exact-root model: an output directory is
  authorized only when its canonical path equals one of that exact step's
  operator roots -- an operator root is never treated as a parent under which
  the description may choose an arbitrary second-level root. | E7 design §7
  (~467-469)

| E-4 | Artifact-manifest checksum reads require `allow_checksum_reads=True`
  as a conjunctive subpermission, separate from and in addition to manifest
  *write* authority; denial precedes any read. A live symlink-escape probe
  was independently tested against all four resource selectors. | E7 design
  §7.3 (~540-559); E7 implementation review (~522-524)
|===

===== G. Threat model (4 invariants)

[cols="1,6,3",options="header"]
|===
| # | Invariant (paraphrase) | Evidence

| G1 | Trusted runtime/operator precondition: the operator controlling the
  Python runtime, process, CLI arguments, environment, installation, and
  import path is trusted; the framework does not protect that runtime from
  its own operator. | ADR Decision 1; ch04 concept §3.3;
  `architectural_layers.adoc` lines 291-296

| G2 | Payload trust and pipeline-description trust are independent
  dimensions against that fixed precondition (ADR Decision 2), and
  output-sink capability is a third, separately-owned concern that must
  *receive* the effective policy rather than act as a fourth trust source
  (ADR Decision 5). | ADR Decisions 2, 5; `architectural_layers.adoc`
  lines 284-337

| G3 | No Python-sandboxing claim, no hostile-interpreter-compromise model,
  no generic sink/network/subprocess policy. Payload provenance never
  selects E7 authority (four-way tests keep the two dimensions independent).
  | FTR §47.9 (~7567-7589); diffuse restatements throughout the FTR (no
  single citable "Threat Model" heading exists in the FTR itself -- see
  <<doc-gaps>> item G2)

| G4 | No general hostile-concurrent-symlink-race guarantee is claimed beyond
  what was actually tested: the E7 implementation review's symlink-escape
  probe covers the four named resource selectors specifically, not a general
  filesystem-race property. Do not overclaim beyond this scope when
  promoting. | E7 implementation review (~522-524)
|===

===== H. Extensibility (5 invariants -- Developer Guide primary)

[cols="1,6,3",options="header"]
|===
| # | Invariant (paraphrase) | Evidence

| H1 | A new registered capability must not become less-trusted-authorizable
  merely by registry membership -- adding a resource-sensitive capability
  requires an explicit E7 classification decision (extending E-1's closed
  four-step enumeration is itself a reviewed architectural change). | Derived
  from E-1, D2

| H2 | Adding a new E4-certifiable producer requires establishing immutable
  effective-binding state at construction (the single-construction-path
  pattern) -- a certificate or label alone is not authority. | Derived from
  C1, C2, C5

| H3 | A new composite Domain value requires an explicit schema/codec --
  never inferred from shape or delimiters. | Derived from A2

| H4 | A new description capability or resource authority requires explicit
  review; extending E7's allowlist is architectural work, not a config
  toggle. | Derived from D2, D3, E-1

| H5 | Acceptance and wiring/reachability are separate: a newly accepted
  ingress or authorization rule must be explicitly wired into the relevant
  macro seam, not assumed automatically live. | Derived from C4 (E5's own
  lesson about E2's `admit_ordinary_frames`)
|===

Per the task brief: LangSec is an external reference frame, not the
organizing principle. Recommended placement: a short, clearly-labeled
*non-normative* "LangSec alignment" subsection at the end of the new
Technical Model material (Slice B, after categories A-G), explicitly headed

Content sketch (for the implementing slice, not final prose):

[cols="2,4",options="header"]
|===
| LangSec concept | Alignment (what the architecture already does)

| Shotgun Parsing
| The anti-pattern the architecture is designed against: E1-E3 concentrate
  parsing/classification at one owned boundary; A5 states ordinary
  downstream code does not re-defend against arbitrary external objects.

| Non-Minimalist Input Handling
| Six fixed scalar categories, zero admitted composites in Phase E (A1);
  explicit rejection of shape/delimiter inference (A2) is the discipline
  against silently accepting more than the stated grammar.

| Differing Interpretations
| The fixed classification order (B2) and the single centralized dotted-path
  resolver chokepoint (D4, D6) prevent two code paths from classifying the
  same value or the same declarative target differently.

| Incomplete Specification
| The project already practices explicit non-guarantee sections (ch04
  concept §"non-guarantees", `internal_value_model.adoc` "Non-implications")
  -- stating what is *not* specified rather than leaving it implicit. G3/G4
  continue that practice for E4-E7.

| Overloaded Fields
| The persistence-boundary Intent-vs-Resolution split (`agent_rules.adoc`)
  and the closed acyclic `_meta` substrate (B4) refuse to let one field
  carry two meanings depending on context.

| Permissive Invalid Input
| E7's fail-closed positive authorization (D2: absence denies; unclassified
  registry entries fail closed) is the direct opposite of permissively
  accepting unrecognized input.

| Input Language Complexity / formal grammar class
| Do *not* claim a Deterministic Context-Free (or any formal grammar-class)
  result. The six-category scalar grammar and the Phase E zero-composite
  rule are described informally and operationally (accepted type/carrier
  membership checks), never proven regular, context-free, or otherwise
  classified. No accepted evidence in the FTR or its reviews makes such a
  claim, and none should be introduced by this promotion.
|===

This table is a placement design, not the final subsection text; the
implementing slice should keep the eventual prose to roughly this length --
one short paragraph per row, no more.

[[parse-dont-validate]]==== 8. Parse-Don't-Validate framing

Preserve as a clearly-labeled *analogy*, not a formal equivalence claim, in
the Technical Model's B (ingress responsibility) subsection: E1-E3 read as
"external representation -> trusted Domain data language," and E4/E5 read as
"loose executable description/binding -> trusted execution/transition
state." The FTR's own vocabulary (Ingress-Conformant Domain Payload,
Conformant Framework Execution State) already expresses this without the
borrowed term; the analogy is useful shorthand for a reader who already
knows the Rust community's "Parse, Don't Validate" idea, but the promoted
text must say explicitly that this is an explanatory analogy, matching the
FTR's own restraint (it never claims formal type-level parsing).

==== 9. Economic and framework value (why, not just how)

Home: opening/motivating paragraph of the new Semantic Model subsection
(Slice A), invariant A7. The Technical Model's Slice B material should state
*how* the boundary and authority mechanisms work; the *why* -- generic
transformations operate on a closed internal language instead of
defensively interpreting arbitrary external carriers, which moves
complexity to one boundary and enables a reusable transformation algebra --
belongs once, in the Semantic Model, with the Technical Model linking back
to it rather than re-deriving the motivation. This mirrors the existing
split where Semantic Model owns "contract" and Technical Model owns
"mechanism."

Three gates, not one per paragraph and not one giant unreviewed rewrite,
