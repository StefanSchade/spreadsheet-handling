===== FTR-FK-REFERENCE-HELPER-SURFACE-CONSOLIDATION-P5 -- FK / reference helper surface consolidation

*Status:* New

*Type:* Consolidation / Design

*Area:* Pipeline / domain transformations / FK helpers / explicit lookup helpers

==== Context

The Trusted Ingress consumer smoke test (Worldbuilding `Places -> Regions`
formula-mode FK helpers, surfaced while validating the managed pipeline
against the current `core` checkout) exposed that one helper-column concept
currently has two public routes with different capabilities and lifecycle
semantics:

* `add_fk_helpers` (`domain/transformations/fk_helpers/`) -- the established
  FK-helper family. Supports relation-specific helper *output* names via
  FK-helper policy/provenance (`configure_fk_helpers` + `helper_prefix`),
  decorates the source frame in place, and supports both `values` and
  `formula` `helper_value_mode`.
* `add_lookup_helpers` (`domain/transformations/enrich_lookup/`) -- the later
  explicit lookup/enrichment route. Gained asymmetric `source_key`/
  `lookup_key` support specifically so cases such as `story_id -> stories.id`
  can be expressed without a rename/join workaround. That extension controls
  **join key identity only**. `add_lookup_helpers` has **no helper-output
  alias/prefix mapping**: projected helper columns are always named exactly
  after the lookup frame's own column names, and `enrich_lookup` explicitly
  rejects a helper name that already exists in the source frame as a
  collision (`_check_column_conflict`).

These two surfaces overlap conceptually but are **not currently drop-in
equivalents**, and the managed Trusted Ingress pipeline
(`application/managed_pipeline.py`, `classify_formula_helper_step`) currently
recognizes only the `add_lookup_helpers` formula producer, not the older
`add_fk_helpers` formula producer.

This FTR intentionally does **not** propose adding a second Trusted Ingress
certification path for the legacy `add_fk_helpers` formula producer merely to
keep both overlapping public surfaces alive. Broadening certification
opportunistically would paper over the design overlap rather than resolve
it. This is recorded as a consolidation problem, not a Trusted-Ingress
runtime defect.

==== Concrete forcing example

Worldbuilding `Places -> Regions`:

    places.region_id -> regions.id
    regions.name -> _regions_name
    regions.kind -> _regions_kind

Source frame `places` already has its own `name` and `kind` columns. This
proves bare (unprefixed) lookup helper names are insufficient in general --
not just a naming preference -- since `add_lookup_helpers` would either
silently shadow `places.name`/`places.kind` or (as implemented) correctly
raise a collision error. There is currently no way to express the desired
`_regions_name` / `_regions_kind` output names through `add_lookup_helpers`.

==== Scope (required future assessment)

* Choose ONE canonical public helper surface.
* Decide whether the established user vocabulary "FK helpers" should remain
  the public name, or whether "lookup" should be adopted as the mechanism
  name -- treat "lookup" as mechanism unless the design establishes
  otherwise.
* Support explicit asymmetric source/target keys (already proven by
  `add_lookup_helpers`'s `source_key`/`lookup_key`).
* Support explicit helper output aliases/names/prefix semantics (currently
  only `add_fk_helpers`' `helper_prefix` provides this).
* Define collision behavior (source-column shadowing) for the canonical
  surface.
* Define in-place (decorate source frame) vs separate-output-frame semantics
  -- `add_fk_helpers` does the former, `add_lookup_helpers` the latter.
* Rationalize provenance and inbound cleanup between the two families'
  differing `_meta.derived` shapes.
* Rationalize `reorder_fk_helpers` / `remove` / `apply_derived_column_policy`
  overlap with whichever surface survives.
* Remove obsolete `v2` terminology/schema sediment where no `v1` exists (see
  `FTR-FK-HELPER-POLICY-LIFECYCLE-P4A`, which already flags v1/v2 shape
  confusion under `helper_policies`).
* Define `values` vs `formula` behavior for the canonical surface.
* Define the exact `FormulaSpec` / Trusted-Ingress producer transition for
  the ONE accepted final surface (`classify_formula_helper_step` and its
  certificate/role machinery should target exactly one producer).
* Migrate maintained consumers (Worldbuilding is the known one) to the
  canonical surface.
* Deprecate/remove the redundant surface as part of an explicitly allowed
  breaking user-surface cleanup -- the current public surface is not promised
  long-term stable.

Do not propose an implementation yet; this FTR records the problem and the
required assessment only.

==== Non-Goals

* Do not decide the canonical surface in this artifact.
* Do not add a second Trusted Ingress certification path for
  `add_fk_helpers(helper_value_mode="formula")` as a substitute for this
  consolidation.
* Do not redesign the full `_meta.helper_policies` lifecycle here --
  coordinate with `FTR-FK-HELPER-POLICY-LIFECYCLE-P4A` and
  `FTR-META-LIFECYCLE-INVENTORY-P5` instead of duplicating that scope.

==== Acceptance

* A design decision exists naming exactly one canonical public helper-column
  surface, with the questions in Scope answered.
* The Worldbuilding `Places -> Regions` example is expressible on the
  canonical surface with materialized `_regions_name` / `_regions_kind`
  output names, in both `values` and `formula` modes.
* Trusted Ingress certifies exactly the canonical surface's formula producer.
* Known maintained consumers (Worldbuilding) are migrated.
* The redundant surface is deprecated or removed per the accepted breaking
  cleanup.

==== Validation

* Consumer roundtrip (XLSX and, where maintained, ODS: export -> reimport ->
  semantic diff) stays green through the migration.
* Trusted Ingress managed-pipeline tests cover the canonical surface's
  formula producer end to end (not just at the domain-function level).
