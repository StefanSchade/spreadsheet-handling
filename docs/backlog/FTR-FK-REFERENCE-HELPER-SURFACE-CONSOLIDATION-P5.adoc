===== FTR-FK-REFERENCE-HELPER-SURFACE-CONSOLIDATION-P5 -- FK / reference helper surface consolidation

*Status:* New

*Type:* Consolidation / Design

*Area:* Pipeline / domain transformations / FK helpers / explicit lookup helpers

==== Context

The Trusted Ingress consumer smoke test (Worldbuilding `Places -> Regions`
formula-mode FK helpers, surfaced while validating the managed pipeline
against the current `core` checkout) exposed that one helper-column concept
currently has two public routes with different capabilities and lifecycle
semantics:

* `add_fk_helpers` (`domain/transformations/fk_helpers/`) -- the established
  FK-helper family. Supports relation-specific helper *output* names via
  FK-helper policy/provenance (`configure_fk_helpers` + `helper_prefix`),
  decorates the source frame in place, and supports both `values` and
  `formula` `helper_value_mode`.
* `add_lookup_helpers` (`domain/transformations/enrich_lookup/`) -- the later
  explicit lookup/enrichment route. Gained asymmetric `source_key`/
  `lookup_key` support specifically so cases such as `story_id -> stories.id`
  can be expressed without a rename/join workaround. That extension controls
  **join key identity only**. `add_lookup_helpers` has **no helper-output
  alias/prefix mapping**: projected helper columns are always named exactly
  after the lookup frame's own column names, and `enrich_lookup` explicitly
  rejects a helper name that already exists in the source frame as a
  collision (`_check_column_conflict`).

These two surfaces overlap conceptually but are **not currently drop-in
equivalents**, and the managed Trusted Ingress pipeline
(`application/managed_pipeline.py`, `classify_formula_helper_step`) currently
recognizes only the `add_lookup_helpers` formula producer, not the older
`add_fk_helpers` formula producer.

This FTR intentionally does **not** propose adding a second Trusted Ingress
certification path for the legacy `add_fk_helpers` formula producer merely to
keep both overlapping public surfaces alive. Broadening certification
opportunistically would paper over the design overlap rather than resolve
it. This is recorded as a consolidation problem, not a Trusted-Ingress
runtime defect.

==== Concrete forcing example

Worldbuilding `Places -> Regions`:

    places.region_id -> regions.id
    regions.name -> _regions_name
    regions.kind -> _regions_kind

Source frame `places` already has its own `name` and `kind` columns. This
proves bare (unprefixed) lookup helper names are insufficient in general --
not just a naming preference -- since `add_lookup_helpers` would either
silently shadow `places.name`/`places.kind` or (as implemented) correctly
raise a collision error. There is currently no way to express the desired
`_regions_name` / `_regions_kind` output names through `add_lookup_helpers`.

==== Recovered surface genealogy and consolidation posture (2026-08-23)

This section records context reconstructed while closing the unrelated FK
Helper Deletion Authority subroutine (see
`docs/cold_storage/reviews/topic_reviews/fk_helper_reviews/dmc_hardening/deletion_authority/sequence_summary.adoc`),
so it is not lost before this FTR is picked up. It records evidence and a
working hypothesis; it does not decide the consolidation.

===== A. Genealogy (verified historical fact, from `git log`)

* `add_fk_helpers` is the older, established surface. FK logic exists from
  the project's early history (`ee68eac`, "tests for the foreign key logic",
  2025-09-04) and was formalized as a Domain layer in
  `FTR-FK-HELPER-REFACTOR-P3B` (`fd8afa9`, 2026-03-31) -- a P3B priority,
  markedly earlier than the P4A/P4A2/P5 priorities used for later work.
* `add_lookup_helpers`/`enrich_lookup` was introduced later, on 2026-04-27,
  by `FTR-EXPLICIT-HELPER-LOOKUP-POLICY-P4` (`8e620b4`). Its own commit
  message states its purpose was to "Replace consumer-side plugins like
  ba-config `enrich_variable_usage_matrix_helpers` with declarative YAML
  config" -- i.e. it was **not** originally conceived as an FK-helper
  alternative; it solved a different problem (replacing ad hoc
  consumer-side enrichment plugins with a declarative pipeline step).
* The asymmetric `source_key`/`lookup_key` capability that later let
  `add_lookup_helpers` cover FK-shaped cases was added afterward, by
  `FTR-XREF-LOOKUP-HELPER-SUBSTITUTION-P4A2` (`c965431`, "support asymmetric
  lookup keys"). That FTR's purpose (per
  `docs/backlog/roadmap_domain_hardening_sequence.adoc`, "Phase B") was to
  let the ten Worldbuilding matrix consumers migrate off the removed
  `project_by_role` API onto the existing explicit lookup/helper
  composition -- not to unify the FK-helper surface.
* Net verified genealogy: `add_fk_helpers` is the older, FK-relation-native
  surface. `add_lookup_helpers` grew, through independent, separately
  justified extensions, into a second surface that now overlaps
  `add_fk_helpers`' problem space without having been designed as its
  replacement. Independent prior review already recognized FK Helpers as a
  historical-sediment/problem family with overlapping surfaces (see
  `docs/cold_storage/reviews/topic_reviews/fk_helper_reviews/` and
  `docs/cold_storage/reviews/topic_reviews/meta_reviews/`).
* `SIG-ACT-CONSUMER-SMOKE-FK-HELPER-OVERLAP` (2026-08-18, this FTR's own
  origin event) is the concrete forcing case that made the overlap visible
  again: a real consumer smoke test against the current `core` checkout, not
  an inference from history alone.

===== B. Current capability asymmetry (verified from current runtime and this FTR's own Context/Concrete forcing example above)

FK helper side (`add_fk_helpers`) currently carries: FK relation-policy
integration; relation-specific helper *output* naming/prefixing
(`helper_prefix`); current FK provenance/cleanup/reorder/validation
semantics (including the deletion-authority contract closed by the
subroutine above). Lookup side (`add_lookup_helpers`/`enrich_lookup`)
currently carries: explicit asymmetric `source_key`/`lookup_key`; output-frame
selection; helper ordering; current managed-pipeline formula-producer
certification (`classify_formula_helper_step` recognizes only
`add_lookup_helpers`' formula producer, not `add_fk_helpers`'). Neither side
is a strict superset of the other today.

The Worldbuilding acceptance case above (`places.region_id -> regions.id`,
required visible helpers `_regions_name`/`_regions_kind`, with `places`
already owning its own `name`/`kind` columns) is not a preference example: it
is a proof that `add_lookup_helpers` *cannot currently* express this FK use
case, because it has no helper-output alias/prefix mapping and correctly
rejects the raw target names as a source-column collision. This is why
Worldbuilding temporarily uses `add_fk_helpers` with
`helper_value_mode: values` -- Managed Formula/Trusted Ingress currently
certifies only the Lookup route, and this FTR's own Non-Goals already reject
opportunistically certifying a second formula producer as a substitute for
consolidation.

===== C. Compatibility constraint (maintainer-provided project constraint)

There are currently no independently governed external consumers whose
compatibility needs require preserving both historical public surfaces.
Known maintained consumers (Worldbuilding) are under project-owner control
and can be migrated coherently. The consolidation target should therefore
optimize for the simplest coherent domain model, not for indefinite
preservation of both historical APIs. This is a deliberate compatibility
posture the maintainer has set for this FTR, not a claim that consumer
migration work is unnecessary -- migration is still Scope item "Migrate
maintained consumers" below.

===== D. Required consolidation method (intended decision method, not a decision)

When this FTR is implemented, the intended method is:

. inventory the complete capabilities of both surfaces;
. identify historical API sediment versus coherent domain capabilities;
. for each feature unique to either surface, decide: discard as unnecessary,
  integrate into the canonical FK-helper capability, or retain/create a
  distinct non-FK Lookup surface only if its semantics independently justify
  a separate surface;
. achieve the capability set required by maintained consumers;
. migrate maintained consumers;
. then remove/narrow the redundant public surface.

===== E. Working hypothesis -- not yet a decision

`add_fk_helpers` is currently the *likely* canonical surviving FK-helper
family, given its relation-policy integration, output-alias capability, and
deletion-authority contract now closed by the subroutine above. This is
recorded as a working hypothesis to orient future assessment, not as a
decision: no Project Memory decision record exists or should exist yet
naming `add_fk_helpers` as the winner. Any surviving `enrich_lookup` surface
must justify itself through coherent, independent domain semantics (as
Section D, step 3 requires) rather than through historical existence or
today's accidental feature asymmetry. This FTR's Scope and Acceptance
sections above, and its own Non-Goals, remain the binding requirements; this
recovered context does not loosen or replace them.

==== Scope (required future assessment)

* Choose ONE canonical public helper surface.
* Decide whether the established user vocabulary "FK helpers" should remain
  the public name, or whether "lookup" should be adopted as the mechanism
  name -- treat "lookup" as mechanism unless the design establishes
  otherwise.
* Support explicit asymmetric source/target keys (already proven by
  `add_lookup_helpers`'s `source_key`/`lookup_key`).
* Support explicit helper output aliases/names/prefix semantics (currently
  only `add_fk_helpers`' `helper_prefix` provides this).
* Define collision behavior (source-column shadowing) for the canonical
  surface.
* Define in-place (decorate source frame) vs separate-output-frame semantics
  -- `add_fk_helpers` does the former, `add_lookup_helpers` the latter.
* Rationalize provenance and inbound cleanup between the two families'
  differing `_meta.derived` shapes.
* Rationalize `reorder_fk_helpers` / `remove` / `apply_derived_column_policy`
  overlap with whichever surface survives.
* Remove obsolete `v2` terminology/schema sediment where no `v1` exists (see
  `FTR-FK-HELPER-POLICY-LIFECYCLE-P4A`, which already flags v1/v2 shape
  confusion under `helper_policies`).
* Define `values` vs `formula` behavior for the canonical surface.
* Define the exact `FormulaSpec` / Trusted-Ingress producer transition for
  the ONE accepted final surface (`classify_formula_helper_step` and its
  certificate/role machinery should target exactly one producer).
* Migrate maintained consumers (Worldbuilding is the known one) to the
  canonical surface.
* Deprecate/remove the redundant surface as part of an explicitly allowed
  breaking user-surface cleanup -- the current public surface is not promised
  long-term stable.

Do not propose an implementation yet; this FTR records the problem and the
required assessment only.

==== Non-Goals

* Do not decide the canonical surface in this artifact.
* Do not add a second Trusted Ingress certification path for
  `add_fk_helpers(helper_value_mode="formula")` as a substitute for this
  consolidation.
* Do not redesign the full `_meta.helper_policies` lifecycle here --
  coordinate with `FTR-FK-HELPER-POLICY-LIFECYCLE-P4A` and
  `FTR-META-LIFECYCLE-INVENTORY-P5` instead of duplicating that scope.

==== Acceptance

* A design decision exists naming exactly one canonical public helper-column
  surface, with the questions in Scope answered.
* The Worldbuilding `Places -> Regions` example is expressible on the
  canonical surface with materialized `_regions_name` / `_regions_kind`
  output names, in both `values` and `formula` modes.
* Trusted Ingress certifies exactly the canonical surface's formula producer.
* Known maintained consumers (Worldbuilding) are migrated.
* The redundant surface is deprecated or removed per the accepted breaking
  cleanup.

==== Validation

* Consumer roundtrip (XLSX and, where maintained, ODS: export -> reimport ->
  semantic diff) stays green through the migration.
* Trusted Ingress managed-pipeline tests cover the canonical surface's
  formula producer end to end (not just at the domain-function level).
