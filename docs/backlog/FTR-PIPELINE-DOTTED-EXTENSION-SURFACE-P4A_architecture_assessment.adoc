== 2. Current source topology

=== 2.1 Resolution and binding flow

At current HEAD, configuration-derived callable strings have one pipeline
resolution owner:
`pipeline.dotted_paths.resolve_configuration_callable`.  It parses colon or
final-dot references, rejects the blocked `spreadsheet_handling.domain.ingress`
namespace before import, imports the module, acquires the named attribute, and
checks callability.  This is a reachability and ownership guard, not an
authorization mechanism or Python sandbox.

The current flows are:

* `pipeline.build.build_step` removes the `step` selector, validates string
  parameter keys, calls `registry.resolve_registration`, injects a
  registration-owned target over any configured `target`, supplies `name`, and
  invokes the selected factory during pipeline construction.
* A registered short name is looked up in `REGISTRY`.  A `StepRegistration`
  carries its Core-owned factory and usually a string target.  A missing name
  containing a colon is instead treated as a direct factory reference and is
  resolved immediately.  A final-dot spelling is not recognized in this
  direct-factory position.
* `step: plugin` uses its `dotted` value.  Plugin resolution and callable
  acquisition happen while the `BoundStep` is constructed; invocation later
  calls `(frames, **args)` and treats `None` as pass-through.
* Generic target binders accept a string or a direct callable.  Strings pass
  through the shared checked resolver during construction.  Direct callable
  values bypass string resolution intentionally.  Builder targets are called
  at step invocation to obtain a callable; frames-first targets are captured
  in an immutable `BoundFramesTargetCall` and invoked at step execution.
* Direct `BoundStep` sequences are executed by `run_pipeline`; managed entry
  points additionally own the accepted E4--E6 ingress, boundary, role, cleanup,
  projection, and persistence semantics.
* `orchestrate` owns fixed initial-ingress, managed-step, final-cleanup,
  final-role-authorization, persistence-projection, and saver phases.
  `run_schema_maintenance` constructs a private application-owned
  `_schema_maintenance_private` `BoundStep`; it does not publish that step to
  YAML.

Direct programmatic callable values and already-created `BoundStep` objects do
not traverse the dotted resolver because no description-derived string needs
resolution.  Three other `importlib.import_module` sites are source-owned
backend lazy-load tables, not pipeline description resolution.

=== 2.2 Maintained-surface boundary

Source, tests, public imports, registry data, and application flow confirm
exactly the eight FTR-maintained surfaces: registered short name, plugin,
direct colon factory, registry-owned string target, nested configured string
target, direct Python callable target, direct `BoundStep` composition, and
framework-owned macro flow.  No ninth maintained surface was found.

The current runtime registry has 44 entries: 38 `StepRegistration` values,
all 38 with Core-owned string targets, and six bare factories.  The increase
from the FTR's dated 40/34 census is current baseline evidence.  Registry-owned
strings are not YAML occurrences.

== 4. Historical intent

[cols="2,4,4"]
|===
| Mechanism | Introduction/retention evidence | Architectural reading

| Registered names and generic binders
| Normalization work in `6f2a57b` introduced `StepRegistration`, the two generic target shapes, and direct-callable/string targets to remove bespoke pipeline factories while leaving YAML stable.  Its closed FTR preferred direct callables internally and allowed strings for lazy ownership.
| Short names are the ordinary declarative vocabulary.  Registration target strings are implementation wiring, not a second consumer request.

| Plugin
| Early pipeline support (`3c63550`) and the reviewed Wave 3r cleanup (`8b2b058`) deliberately retained the plugin protocol.  E6 later classified the dotted protocol as mechanically stable under trusted-description assumptions.  Current multi-repository adoption confirms intent.
| A supported, stable expert extension protocol exists; arbitrary YAML authorization was never implied.

| Direct colon factory
| Wave 3r explicitly retained `step: module:function`, and focused tests protect it.  It lacks maintained YAML adoption, a separately exported `StepFactory` contract, and evidence of a stronger permanent consumer promise.
| Intentional reachable compatibility, but not an ordinary or newly promoted public authoring form.

| Registry-owned string target
| Generic normalization intentionally moved Core domain callable selection into `StepRegistration.target`.  The descriptive registry calls short names public YAML steps while runtime registry binding remains source-owned.
| Trusted internal post-selection representation.  Longevity does not turn the target into consumer addressability.

| Nested configured target
| It is a consequence of the generic binders plus dynamic factory reachability and is covered by boundary/compatibility tests.  No stable guide or maintained YAML adoption establishes ordinary use.
| Conservatively retained expert compatibility, not promoted syntax.

| Direct callable target
| The generic-binder FTR explicitly supported callable targets and preferred them for internal composition.
| Deliberate trusted Python capability.  Publicness is inherited from the owning builder; internal builders are not promoted by this assessment.

| Direct `BoundStep`
| `BoundStep` is a public pipeline type and direct composition is foundational.  Accepted E6 explicitly supports `orchestrate(..., steps=...)` and lower-level `run_pipeline` with its caller precondition.
| Stable trusted programmatic composition, distinct from declarative authorization.

| Framework macro flow
| E4--E6 fixed managed phases deliberately at application boundaries; `689b446` introduced schema maintenance's private `BoundStep` composition.
| Framework lifecycle and application-private composition are intentionally owned and non-addressable, even where mechanics resemble ordinary steps.

| Resolver and blocked namespace
| Legend Correction 3 (`c0482b4`, `87c152c`) centralized resolution and blocked `domain.ingress` after a concrete ownership leak; it expressly did not settle the general extension contract.
| One technical resolver is useful, while contracts remain surface-specific.  The blocklist is not a general authorization design.
|===

The repository-wide choice is a narrow *E/D hybrid*: retain current mechanics
and make their contracts exact (E), while E7 adds operator-owned positive
authority for the declarative capability kinds it supports (the useful part of
D).  Namespace may organize an operator policy but is never evidence of trust,
publicness, or safety: external modules can be unsafe, Core modules can be
private, and re-exports cross namespaces.  Direct factories and nested targets
remain trusted-description compatibility forms rather than being promoted by
A, duplicated by B, or deprecated by C.

== 8. E7 capability, identifier, and timing handoff

The smallest useful E7 vocabulary merges surfaces only where ownership and
authorization behavior are equal:

[cols="2,3,3,4"]
|===
| Capability kind | Surfaces | Identifier / authority subset | Required timing and outcome

| Registered framework capability
| Registered short-name step
| Exact `step` name, plus the explicitly enumerated resource selectors in the final matrix.  Per-registration policy must distinguish ordinary authorized, operator-authorized-with-constraints, and unavailable-to-less-trusted use; registry membership alone is insufficient.
| Shape parsing and exact name lookup may precede policy.  Authorize before factory call, target resolution/import, binding, or invocation.

| Arbitrary plugin callable invocation
| Plugin
| Exact normalized `dotted` target; target-specific argument constraints only when positively declared by operator policy.
| Parse/canonicalize without import, combine operator policy, authorize, then and only then call `resolve_configuration_callable`.  A deny precedes import, attribute acquisition, binding, and invocation.

| Compatibility dynamic callable construction/acquisition
| Direct colon factory and nested configured target
| Outer exact colon `step` factory and, if ever supported, exact nested `target`.
| The selected architecture denies this kind to less-trusted descriptions.  Reject before importing the outer factory.  Trusted-description compatibility retains current construction order.

| Internal framework callable acquisition
| Registry-owned string target
| No new description identifier; inherit the authorized registered short name.
| Authorization has already succeeded at the short-name boundary.  Internal target resolution then proceeds and must not be blocked merely for using a dotted Core target.

| Trusted direct-Python composition
| Direct callable target and direct `BoundStep`
| Caller-supplied Python object, not description data.
| Outside E7.  Acquisition occurred in trusted Python; existing API checks and E6 preconditions apply.

| Framework lifecycle capability
| Fixed framework phases and application-private composition
| Trusted entry-point/use-case, not a phase name in YAML.
| Outside E7 and non-addressable.  E7 must not manufacture phase-selection or reordering authority.
|===

`resolve_configuration_callable` remains the single checked implementation
path for every configuration-derived dotted callable.  Direct Python objects
intentionally bypass it.  E7's policy boundary must sit before this resolver:

[source,text]
----
parse shape / canonicalize identifier
-> combine description request with operator-owned positive authority
-> authorize capability kind + exact identifier + relevant resource selectors
-> only then resolve/import/acquire
-> bind
-> invoke
----

A future package-complete architecture guard should pin resolver singularity
and the pre-resolution authorization boundary.  A post-resolution check is
architecturally invalid because module import and attribute acquisition are
already activation.  Namespace can be an operator-maintained grouping handle,
but never substitutes for positive authority or proves Python safety.

== 13. Safe interim contract

Immediately after independent acceptance of this architecture, and before any
derived work:

* All YAML/pipeline descriptions remain trusted in full: trusted to choose a
  registered step, choose arbitrary plugin/factory/nested callable code where
  reachable, and supply parameters with filesystem/resource effects.
* `step: <registered-name>` is the ordinary supported stable declarative
  vocabulary.  Registration does not yet encode permission for less-trusted
  descriptions.
* `step: plugin` with a colon or final-dot `dotted` callable is a supported
  stable expert extension protocol under the trusted-description precondition.
  The imported Python is not sandboxed.
* Implicit `step: module:function` factories and nested configured
  `target: module:function` values continue to work as expert compatibility
  surfaces for trusted descriptions.  They are not ordinary authoring forms,
  are not promoted to a stronger package API, and are not deprecated.
* A registry-owned dotted target is trusted internal wiring after short-name
  selection, not a consumer extension request.  Its dotted representation is
  replaceable while the public short-step behavior is compatibility-controlled.
* Direct Python callable targets and direct `BoundStep` composition remain
  supported trusted-programmatic forms according to their owning APIs and the
  accepted E6 split.  E7 declarative authorization does not govern them.
* Fixed framework lifecycle phases and application-owned private composition
  remain framework/application-owned, non-addressable, and non-reorderable by
  YAML.  Shared `BoundStep` mechanics do not confer consumer authority.
* Every configuration-derived dotted callable continues through
  `resolve_configuration_callable`; direct callable objects bypass it by
  design.  The resolver proves syntax, the current blocked ownership rule,
  importability, attribute existence, and callability only.  It does not prove
  authorization, safety, sandboxing, publicness, stability, or suitability for
  less-trusted input.
* Namespace checks are policy handles only.  External does not mean safe,
  Core does not mean public, and re-exporting does not confer authority.
* E7 may assume the six capability kinds and identifiers in section 8, the
  single-resolver topology, the deny posture for dynamic factory/nested forms,
  and the exclusion of trusted Python/internal lifecycle forms.  E7 must add
  an operator-owned positive decision before calling the resolver or performing
  any stronger operation; it may not pretend that the current resolver already
  supplies that decision.
