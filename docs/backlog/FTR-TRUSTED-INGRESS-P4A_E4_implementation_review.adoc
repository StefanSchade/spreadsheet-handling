== 1. Accepted E4 contract, reconstructed independently

Before inspecting the implementation, the accepted contract is restated here
in this reviewer's own words from the FTR and Review 005 (no implementation
code was open yet when this section was drafted):

E4 must provide an *implementation-local, execution/control-plane*
representation -- not payload metadata, not a runtime registry -- of exact
producer transitions for a closed, bounded role vocabulary: standalone
`LookupFormulaSpec`, transition-only `GroupedMatrix`, exactly one nested
composition `GroupedMatrix[LookupFormulaSpec@grouped-dynamic-value-cell]`,
and `ArtifactManifestSourceFrames`. Every bound invocation must classify to
either an *exact certificate* -- naming its real input/output state, provable
against actual runtime, never by nominal/identity resemblance -- or the
closed `Uncertified` default. The default is closed: no callable, registry
entry, family, wrapper, or factory identity confers certification by itself.
Preserving certificates may legitimately be an empty set. The bounded
disjoint-role locality proof must be a real semantic footprint (reads/writes/
drops), stronger than "we observed no mutation." The representation must
correctly encode forward source-retaining derivation, both reverse
`expand_grouped_xref` endpoints, the projection/adapter exit chain (including
*exact render-cell locations*, per Review 005 section 5), cleanup
termination, R1 (Scalar-safe diagnostic row-index), and M1 (artifact-manifest
role), all without wiring into E5 macro flow.

The single load-bearing acceptance criterion this review falsifies most
directly is FTR section 23's own sentence: *"the exact locality proof is
stronger than observed non-mutation and does not require a universal role
registry"* and Review 005 section 11's *"an implementation-local exact
role/transition representation."* A representation whose certificate can be
obtained for behavior the implementation never bound or never actually
computed the location of is not that.

== 4. BLOCKING F1 -- exact-bound certification is not tied to executable behavior

*Accepted criterion violated:* FTR section 23 ("no callable, registry entry,
family, wrapper, factory, or built-in inherits certification") and the
decision-table row for "Caller-supplied callable / `BoundStep`" (FTR line
~1622): certification requires *"its exact bound behavior carries a
framework-reviewed producer contract through an implementation mechanism"* --
not merely a matching descriptive label.

Every classifier in the package (`classify_formula_helper_step`,
`classify_grouped_producer_step`, `classify_expand_grouped_step`,
`classify_artifact_manifest_step`) inspects only `step.config`
(`formula_helper.py:78` etc.). None of them ever reads `step.fn`. `BoundStep`
(`pipeline/types.py:32-44`) is a frozen dataclass whose `name`/`config`/`fn`
fields are three independent values with no structural link between
`config["target"]` and what `fn` actually does -- nothing prevents
constructing one with a certifiable `config` and an unrelated `fn`.

*Counterexample A -- forged `BoundStep` (probe run against the real
implementation):*

[source,python]
----
forged = BoundStep(
    name="forged",
    config={
        "target": FORMULA_HELPER_TARGET,
        "source": "orders", "lookup": "products", "output": "orders",
        "key": "product_id", "helpers": {"fields": ["value"]},
        "missing": "empty", "helper_value_mode": "formula",
    },
    fn=lambda frames: {**frames, "PWNED": pd.DataFrame({"x": [1]})},
)
classify_formula_helper_step(forged)
# -> FormulaHelperCertificate(source='orders', lookup='products', ...)
forged(frames)
# -> {'orders': ..., 'products': ..., 'PWNED': ...}   # fn does nothing formula-related
----

The classifier returns a full `FormulaHelperCertificate` for a step whose
executable closure has no relationship whatsoever to `enrich_lookup`. This is
precisely the "prebound/caller-supplied BoundStep" case the FTR's own
decision table places on the uncertified side unless an implementation
mechanism verifies *exact bound behavior*; no such mechanism exists here.

*Counterexample B -- real registry-built step, mutated after binding (TOCTOU,
no forgery needed):*

[source,python]
----
[step] = build_steps_from_config([{
    "step": "add_lookup_helpers", "source": "orders", "lookup": "products",
    "output": "orders", "key": "product_id",
    "helpers": {"fields": ["value"]}, "missing": "empty",
    "helper_value_mode": "values",       # <- real executing closure: VALUES mode
}])
classify_formula_helper_step(step)        # Uncertified(reason='uncovered_configuration')
result0 = step(frames)                    # orders['value'] cells are plain str

step.config["helper_value_mode"] = "formula"   # single top-level dict write

classify_formula_helper_step(step)
# -> FormulaHelperCertificate(...)   # NOW CERTIFIED
result1 = step(frames)
# orders['value'] cells are STILL plain `str`, not LookupFormulaSpec
----

Root cause: `pipeline/steps.py:71-87` (`make_frames_target_step`) builds
`cfg = {"target": ..., **dict(kwargs)}` (a *new* dict, shallow-copied) but
the returned closure is `def run(fr): return fn(fr, **kwargs)` --
`pipeline/steps.py:84` -- which closes over the *original* `kwargs` object,
not `cfg`. `step.config` (== `cfg`) and the value the closure actually
executes with (`kwargs`) are two different dict objects from the moment the
step is built. A top-level key reassignment on `step.config` is therefore
purely cosmetic to execution, but *not* cosmetic to `classify_formula_helper_step`,
which re-reads `step.config` fresh every call (by design, for the opposite,
intended direction -- see FTR section 18). The result is a real,
single-threaded, no-forgery divergence between "what the certificate says
this step does" and "what it actually does when called," reachable through
the real `build_steps_from_config` → registry → `make_frames_target_step`
path with an ordinary dict mutation in between.

*Evidence-accuracy note:* FTR section 40.3 states *"callable identity is
necessary but never sufficient"* for certification. This is not what the
code does -- callable/`fn` identity is never inspected anywhere in this
package; only the `config["target"]` *label* is compared. The sentence
describes a check that does not exist.

*Test-coverage note:* `test_bound_configuration_mutation_safety.py:97-104`
proves only the *safe* direction (certified → mutate → uncertified) and its
own comment explicitly states *"[top-level reassignment] does not even
affect the actual execution closure for this binder"* -- the author was
aware of the asymmetry but the shipped test suite never exercises the
dangerous reverse direction demonstrated in Counterexample B, and
`test_uncertified_default.py` never constructs a forged `BoundStep` with a
mismatched `fn` (Counterexample A).

*Smallest bounded correction:* either (a) `BoundStep` must bind an immutable,
closure-verifiable identity between `config` and `fn` (e.g. the binder
closing over `cfg` itself instead of a separate `kwargs`, plus freezing
`cfg`/making it read-only after bind), or (b) every E4 classifier must
independently authenticate `step.fn` (e.g. via `id()`/registry-resolved
callable comparison) as well as `config`, and the FTR's "callable identity is
necessary" sentence must become true of the code. Per FTR section 45, this is
an implementation defect in how the accepted contract was encoded, not an
architecture contradiction -- Review 005's own decision-table row already
anticipated exactly this boundary.

== 5. BLOCKING F2 -- projection does not represent exact render-cell locations

*Accepted criterion violated:* Review 005 section 5 ("workbook projection and
rename rule B"): *"`grouped_matrix_to_exact_table` terminates `GroupedMatrix`
[and] relocates nested FormulaSpec to exact-table DATA LOCATIONS"* and
section 24 of the review brief: *"XLSX / ODS adapter consumes FormulaSpec...
carries exact CELL LOCATIONS."*

`projection.relocate_nested_formula_at_projection` (`projection.py:53-74`)
takes only `(nested: GroupedMatrixFormulaRole, render_frame: str)` and
returns:

[source,python]
----
return LookupFormulaSpecRole(
    frame=render_frame,
    column=source.column,      # <- projection.py:68
    ...
)
----

`source.column` is `nested.source.column` -- the *pre-grouping* flat helper's
value-column name (e.g. `"value"`), carried forward unchanged from
`compose_formula_to_grouped`. It is not derived from the actual projected
location at all. Independently reading the real projection function
(`grouped_xref/matrix.py:156-198`, `grouped_matrix_to_exact_table`) shows why
this cannot be correct: its output, `ExactTable`, has no named "column"
concept whatsoever -- `data` is row-major positional tuples
(`frame.values.tolist()`) and `header_grid` is a tuple of label rows read
from `matrix.header`; a "column name" identity does not survive projection.
The one function in this same package that *does* correctly resolve real
physical dynamic-column identity, `dynamic_column_labels`
(`grouped_matrix.py:393-408`), reads the live `GroupedHeader`/`DynamicColumn`
positions from the matrix being expanded -- exactly the mechanism
`relocate_nested_formula_at_projection` would need and does not use. The
function is not merely imprecise; it is structurally incapable of naming a
render-cell location, because it is never given the `GroupedMatrix`,
`ExactTable`, or render-plan object that location would have to be computed
from.

*Test-quality confirmation:* `test_projection_transition.py:53-64`
(`test_nested_formula_relocates_to_the_render_cell_at_projection`) hand-builds
`_source_role()` with `column="value"` and merely asserts the function
echoes that same string back -- it never runs
`grouped_matrix_to_exact_table`/`compose_workbook`/`build_render_plan` to
compare against a real projected cell location. No test in the new suite
proves correspondence between this descriptor and actual render output. This
matches the review brief's section 42 concern precisely.

*Concrete risk:* if E5 later uses this descriptor to decide which render
cell the XLSX/ODS adapter must treat as formula-bearing (its explicitly
intended purpose, per Review 005 section 5's own table), it will be told the
wrong location (a stale flat-frame column name instead of the true dynamic
render position), for every certified nested formula/grouped composition.

*Smallest bounded correction:* `relocate_nested_formula_at_projection` needs
the same kind of live-structure input `dynamic_column_labels` already uses
(the `GroupedMatrix`/`ExactTable`/render-plan object being projected) to
compute the real post-projection location, or the descriptor's `column`
field must be renamed/documented as "pre-projection provenance only," and a
separate, correctly-computed field added for the actual render-cell address
-- and E4's acceptance criteria (section 23) require the latter, since E5 is
explicitly expected to "enforce adapter consumption" from this
representation alone.

== 6. BLOCKING F3 -- disjoint-locality footprint omits declared frame-read dependencies

*Accepted criterion violated:* FTR section 10 ("its footprint proves that the
existing role location, contained payload, descriptor/provenance, and
rename/relocation identity are unaffected") and `vocabulary.py`'s own
docstring requirement that the proof be based on *"the transition's own
declared frame names... never observed runtime behaviour."*

`GroupedProducerCertificate.footprint()` (`grouped_matrix.py:130-134`) and
`ExpandGroupedCertificate.footprint()` (`grouped_matrix.py:312-323`) declare
`reads`/`writes`/`drops` built only from `relation`/`table`/`matrix` and
`output`. Both classifiers accept -- as known, reviewed configuration keys --
`source_frame` (`_CONTRACT_KNOWN_KEYS`, `_RECONSTRUCT_KNOWN_KEYS`,
`_EXPAND_KNOWN_KEYS`) and `dense_axes`/`base_relation`, but the footprint
never includes them.

Independently confirmed against the real functions: `source_frame` is a
*required* parameter of `contract_grouped_xref`, `reconstruct_grouped_matrix`,
and `expand_grouped_xref` (`grouped_xref/composites.py`), fed into
`AxisMappingIntent(source_frame=source_frame, ...)` and then genuinely read
via `frames[intent.source_frame]` inside `resolve_axis_mapping`
(`xref_axis_mapping/resolver.py:150`). A runtime probe against the real
`contract_grouped_xref` confirmed this dependency is live and load-bearing
(the call fails with `AxisMappingError: ... axis mapping source frame 'A'
row 0 ...` when frame `A`'s content does not match, proving `A`'s content is
read and validated during the transition -- not merely accepted-but-inert).

*Concrete falsification (matching the review brief's prescribed construction
exactly):*

[source,python]
----
existing = GroupedMatrixRole(frame="A", producer="contract_grouped_xref",
                              source="rel0", effect=TransitionEffect.INTRODUCE)
second_cert = GroupedProducerCertificate(
    producer="contract_grouped_xref", output="B_out", source="B_rel",
    value_column="value", drop_source=False, row_keys=("id",),
)   # relation="B_rel", output="B_out" -- both disjoint from "A"
second_cert.footprint()
# -> TransitionFootprint(reads={'B_rel'}, writes={'B_out'}, drops=set())
disjoint_grouped_introduction(existing, second_cert)
# -> existing   (claims "A" is PRESERVED / disjoint)
----

but a real invocation of this exact certificate's configuration with
`source_frame="A"` genuinely reads frame `A`'s content (confirmed above) --
a dependency the declared footprint hides entirely. The proof is not
"stronger than observed non-mutation"; on its own declared terms it is
*silent* about a real, required, classifier-accepted input.

Because reads (as opposed to writes/drops) do not themselves mutate the
existing role's frame in the current `resolve_axis_mapping` implementation,
this specific gap does not yet cause an observed runtime corruption of an
existing role -- but the FTR is explicit that the proof must not rest on
"our implementation happens not to write there today." A future
`resolve_axis_mapping` change, or a `dense_axes` shape that does write back,
would silently invalidate every locality claim this package has made, with
no test able to catch it, because the dependency was never declared. Per
finding discipline, an under-declared footprint is exactly "locality proof
is unsound."

*Smallest bounded correction:* add `source_frame` (and, for
`expand_grouped_xref`, `base_relation` if it is genuinely frame-valued -- not
independently re-verified here) to each certificate's `footprint().reads`.

== 7. IMPORTANT -- R1 scalarization only special-cases `tuple`

FTR section 23's E4 acceptance criterion states unconditionally: *"the R1
report projection emits only Scalar cells."* `_safe_row_index`
(`reference_validations.py:729-742`) is:

[source,python]
----
def _safe_row_index(row_index: Any) -> Any:
    if type(row_index) is tuple:
        return _row_index_label(row_index)
    return row_index
----

Any row-index label that is neither already an ordinary Scalar carrier nor
exactly `tuple` (a `MultiIndex` artifact) passes straight through unclassified.
Independently probed: a `pandas.Index` built from a plain hashable
non-Scalar object (a custom class instance, deliberately implementing hostile
`__str__`/`__repr__`) reaches `validate_references`'s finding output as the
*raw object itself*, not a String and not rejected:

[source,python]
----
idx = pd.Index([Hostile(), Hostile()], dtype=object)
frame = pd.DataFrame({"id": ["p1", "p1"]}, index=idx)
out = validate_references(frames, rules=[{"type": "unique", "frame": "items",
                                            "columns": ["id"]}], mode="warn")
[type(v).__name__ for v in out["validation_findings"]["row_index"]]
# -> ['Hostile', 'Hostile']   -- raw object in the report DataFrame cell
----

This is reachable under *current* physical-axis authority: E2's row-index
grammar is explicitly not yet selected (FTR section 25 defer matrix: "No
row-index grammar or scalar/tuple grammar is selected now"), so nothing in
the framework currently prevents a DataFrame with an arbitrary hashable
object index from reaching `validate_references`/`validate_graph`. No
hostile `str()`/`repr()` call is triggered by the library itself (the
existing guarded-formatting discipline inside the *tuple* branch,
`_safe_row_index_component`, is sound and correctly classifies each
component through `scalar_category` before formatting), so this is not a
Domain Boundary Robustness violation in the "executes attacker code" sense --
but it does mean R1's own unconditional "emits only Scalar cells" acceptance
criterion is false for any non-tuple, non-Scalar index label, which is a
currently reachable state, not a hypothetical one.

*Recommended correction:* classify the *whole* `row_index` (not only inside
the `tuple` branch) through the same `scalar_category` gate `finding_frame.py`
already uses for tuple components, falling back to the existing
`"<unsupported row index>"` placeholder for anything that fails it.

== 8. IMPORTANT -- M1 has no explicit consume/exit representation

FTR section 10 ("Artifact-manifest role decision") names three exit
possibilities for `ArtifactManifestSourceFramesRole`: consumption by the
manifest's own JSON/YAML writer, termination by exact whole-frame exclusion,
and deliberate rejection at an unsupported sink -- and Review 005's
twelve-flow closure item 8 lists all three explicitly as part of the
maintained flow. `artifact_manifest.py` represents only introduction
(`classify_artifact_manifest_step` / `artifact_manifest_role`, both with
`effect=TransitionEffect.INTRODUCE`); unlike `projection.py`, which gives
`GroupedMatrixRole`/`GroupedMatrixFormulaRole` an explicit, unwired
`terminate_grouped_matrix_at_projection` descriptor for their exit, there is
no analogous function for the manifest role.

In practice, whole-frame cleanup termination is already covered generically
by `roles.terminate_roles_removed_by_cleanup` (a pure frame-name
set-difference that applies to any `ControlledRole`, including this one), and
rejection at an unsupported general sink is plausibly already covered by the
existing E1 ordinary-Scalar classifier (a `list` cell fails ordinary
admission). But the fact that the JSON/YAML artifact-adapter "consume" effect
and the unsupported-sink "reject" path have no discrete E4 representation --
while the parallel FormulaSpec/GroupedMatrix exit chain received one in the
same slice -- is an asymmetry in representational completeness within E4's
own claimed scope, worth resolving before E5 needs to reconstruct that
reasoning from first principles. Not Blocking: nothing here fabricates false
role authority, and the generic mechanisms plausibly already produce correct
behavior.

=== 17.3 CRITICAL final falsification -- mutability of `BoundFramesTargetCall` itself

`BoundFramesTargetCall` has plain `__slots__` attributes with no
`__setattr__` override, no property, no frozen semantics. Nothing prevents
reassigning `target` or `kwargs` on an already-constructed, already-classified
instance -- including one obtained through the fully legitimate
`build_steps_from_config` path, not merely a hand-built one:

[source,python]
----
[step] = build_steps_from_config([{  # ordinary, framework-built, real step
    "step": "add_lookup_helpers", "source": "orders", "lookup": "products",
    "output": "orders", "key": "product_id",
    "helpers": {"fields": ["value"]}, "missing": "empty",
    "helper_value_mode": "formula",
}])
cert = classify_formula_helper_step(step)      # -> FormulaHelperCertificate(...)
type(step.fn.kwargs)                           # -> mappingproxy (item assignment IS blocked)

def malicious(frames, **kw):
    return {**frames, "PWNED": pd.DataFrame({"x": [1]})}

step.fn.target = malicious                     # <-- succeeds, no exception
step(frames)                                    # -> {'orders': ..., 'products': ..., 'PWNED': ...}
# `cert` (issued before the reassignment) still reads FormulaHelperCertificate(...)
----

The same result holds for `step.fn.kwargs = {**dict(step.fn.kwargs),
"helper_value_mode": "values"}` (whole-attribute reassignment, bypassing the
item-level `MappingProxyType` protection entirely): execution flips from
producing `LookupFormulaSpec` cells to plain `str` cells while the
already-issued certificate is unchanged. Both were independently reproduced
against a genuinely framework-built `BoundStep`, and separately against
manually-constructed `BoundFramesTargetCall` instances built with a plain
mutable `dict` (which nothing requires a caller to avoid -- the public
constructor accepts any `Mapping`).

*Root cause:* the correction proves authenticity of the pairing *at the
moment `resolve_trusted_call` runs*, but nothing makes that pairing
immutable afterward. `MappingProxyType` closes item-level mutation of a
`kwargs` mapping the *binder* chose to wrap, but the `BoundFramesTargetCall`
object holding a reference to that mapping (and to `target`) is itself an
ordinary mutable object at both the framework-built and hand-built call
sites. This is the same class of defect as the original F1 finding
(TOCTOU: a certificate is issued, then an accessible mutable surface changes
what actually executes), relocated from `BoundStep.config`/`binding` onto
`BoundFramesTargetCall.target`/`.kwargs`, not a new attack surface.

The correction's own new FTR narrative (section 42.1) states the property
established is *"obtaining and reusing that proof object is harmless
because using it necessarily runs the reviewed behavior"* and demonstrates
this only by *copying* an unmutated `BoundFramesTargetCall` into a second
`BoundStep` (`test_copying_a_genuine_binding_necessarily_executes_the
_reviewed_behavior`). No shipped test mutates `.target` or `.kwargs` on an
already-certified call object. "Reusing unmutated" and "mutating after
certification" are different properties; the correction proves the first
and the FTR's evidence conflates it with the second, which does not hold.

*E4-REVIEW-F1: NOT RESOLVED.* Per FTR section 18's own requirement
("certificate corresponds to immutable effective configuration"), the
accepted invariant is that *every* object `resolve_trusted_call` accepts
must itself be incapable of diverging from its certificate before execution
-- not merely that the framework's own binder happens to produce
well-behaved instances today.

*Smallest bounded correction:* make `BoundFramesTargetCall` genuinely
immutable after construction (e.g. `__setattr__` raising, or storing
`target`/`kwargs` behind a frozen-dataclass-style mechanism actually
enforced at the instance level, not only conventionally documented as
"should be" for `kwargs`), so identity/type checks at classification time
remain true for the lifetime of the object.

=== 18.4 CRITICAL -- direct-constructor bypass of `.bind()`

`resolve_trusted_call` accepts any object satisfying `type(step.fn) is
BoundFramesTargetCall` and `step.fn.target is expected_target` --
regardless of whether that object went through `.bind()`. The public,
`@dataclass`-generated constructor `BoundFramesTargetCall(target, kwargs)`
remains directly callable and does *not* deep-freeze `kwargs`; it only
stores whatever object it is given. `frozen=True` blocks *reassigning* the
`kwargs` attribute afterward, but does nothing to the mutable object that
attribute already points at.

[source,python]
----
mutable_kwargs = {  # exact certifiable FormulaHelper configuration
    "source": "orders", "lookup": "products", "output": "orders",
    "key": "product_id", "helpers": {"fields": ["value"]},
    "missing": "empty", "helper_value_mode": "formula",
}
call = BoundFramesTargetCall(enrich_lookup, mutable_kwargs)  # bypasses .bind()
step = BoundStep(name="manual", config={...}, fn=call)

classify_formula_helper_step(step)   # -> FormulaHelperCertificate(...)
step(frames)                          # -> orders["value"] cells are LookupFormulaSpec

mutable_kwargs["helper_value_mode"] = "values"   # caller mutates its OWN dict

step(frames)                          # -> orders["value"] cells are now plain str
# the certificate issued before the mutation is unchanged and now false
----

Two further variants independently confirmed the same divergence: (a) a
caller-held nested list inside `helpers={"fields": fields}` passed to the
direct constructor -- mutating `fields` after certification changes which
columns execution actually produces while `certificate.fields` still names
only the original set; (b) `BoundFramesTargetCall(enrich_lookup,
MappingProxyType(underlying))` -- wrapping the caller's own live `dict` in a
proxy does not freeze it; mutating `underlying` directly (not through the
proxy) after certification flips execution from formula-mode to
values-mode while the certificate is unchanged.

*E4-REVIEW-F1: NOT RESOLVED* -- the fourth consecutive disposition of the
same underlying invariant. `resolve_trusted_call` proves nothing about
objects it accepts that were not constructed via `.bind()`, and nothing
distinguishes the two at the point of classification.

*Documentation truthfulness:* FTR section 43.9 states the correction makes
"the bound executable/configuration pair... genuinely immutable after
construction." This is true only for `.bind()`-constructed instances, not
for every instance `resolve_trusted_call` actually accepts. The shipped
`test_copying_a_genuine_binding_necessarily_executes_the_reviewed_behavior`
(`test_uncertified_default.py:185-202`) constructs
`BoundFramesTargetCall(enrich_lookup, kwargs)` directly (the same bypass
above) but classifies and executes it immediately without ever mutating
`kwargs` in between, so it proves only "an unmutated direct construction is
truthful," not the docstring's broader claim (F1's actual bar) that
*obtaining* the accepted shape is harmless regardless of what the caller
does with it afterward. This is not a separate finding; it is F1's own
evidence not yet matching F1's own requirement.

*Smallest bounded correction:* per the required invariant (task section 7),
either (A) make `BoundFramesTargetCall.__new__`/`__init__` itself perform
the freeze unconditionally (so the public constructor and `.bind()` are the
same operation and no unfrozen instance can exist), or (B) give
`resolve_trusted_call` a structural way to reject a non-canonically-frozen
instance (e.g. asserting `type(call.kwargs) in (MappingProxyType,) or
call.kwargs == ()` is insufficient by itself since nested values must also
be checked recursively; freezing unconditionally at construction is the
simpler, load-bearing fix).
