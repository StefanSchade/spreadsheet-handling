== Verdict

Slice 1 is not accepted in review 002.

Correction commit `b1b8e18` does close the original arbitrary-comparator,
configured-field-alias, hostile-`str`-subclass, and over-broad exception-catch
mechanisms. The corrected ordinary paths, regression suites, and architecture
guards are green.

Independent adversarial probes nevertheless found three important contract
defects:

* diagnostics for rejected objects still call a metaclass-controlled
  `__name__` attribute and can leak `RuntimeError`;
* the accepted NumPy-integer vocabulary omits exact `numpy.longlong` and
  `numpy.ulonglong` scalars that pandas preserves on this platform; and
* `ResolvedAxisMember` retains a caller-owned tuple subclass as its `labels`,
  allowing caller behavior and later mutation to affect construction and
  inverse lookup.

The 94 focused tests do not exercise these cases. Under the requested
acceptance rule, important contract defects prevent acceptance even though all
listed test suites pass.

This verdict applies only to the internal pure model/resolver Slice 1. It does
not request or judge deferred projection, public YAML, metadata, persistence,
MultiIndex, rendering, XLSX, ODS, or grouped-header implementation.

== Exact-string and physical-label assessment

The accepted paths satisfy most of the settled string contract:

* `AxisMappingIntent`, `ResolvedAxisMember`, source keys and labels,
  `used_keys`, forward lookup, and inverse label elements require exact
  built-in `str`;
* `str` subclasses are rejected before their overridable string, hash,
  equality, comparison, or representation methods run;
* whitespace-only strings fail, while leading/trailing whitespace in an
  otherwise non-empty string remains exact data;
* accepted members contain exact built-in string leaves;
* case, delimiter text, and spelling are neither normalized nor parsed.

Configured field resolution is also correct locally. Physical-label validation
precedes matching and positional reads. An unrelated valid non-string physical
label is permitted by the shared boundary but cannot match a configured exact
string. Exact duplicate string labels fail before selection. Missing fields
produce one clear feature diagnostic.

The remaining diagnostic hole is not a string comparison. The rejection
message itself reads `type(value).__name__` in `model.py` and `resolver.py`.
Python permits a metaclass to override that class-attribute access, so the
diagnostic executes caller code before it can raise `AxisMappingError`.

== Ordering-vocabulary assessment

Configured ordering has the correct structural semantics:

* `SOURCE_ROW` is used only when explicitly selected;
* configured columns are compared in declaration order;
* canonical key is the deterministic final tie-breaker;
* each non-empty order column is homogeneous after normalization;
* different configured columns may use different supported types;
* exact built-in Python integers, including negative and arbitrarily large
  values, sort correctly;
* all eight explicitly listed NumPy widths normalize to built-in `int`;
* listed signed/unsigned boundary values normalize without overflow;
* a mixed object column containing Python `int` and listed NumPy integers
  becomes homogeneous built-in `int`;
* `bool`, `numpy.bool_`, finite/non-finite floats, `Decimal`, date, time,
  datetime, pandas timestamp, mutable values, and comparator subclasses fail
  before comparison;
* nullable integer columns accept their concrete integer scalars and reject
  `pd.NA`;
* multiple order columns, ties, empty sources, and singleton sources behave as
  specified.

The explicit NumPy type tuple is incomplete. With NumPy 2.4.4 and pandas
3.0.2 on this review platform, `np.longlong` and `np.ulonglong` are distinct
exact classes from `np.int64` and `np.uint64`. Pandas preserves both from
typed arrays, but the resolver rejects them. Other tested aliases
(`byte`, `ubyte`, `short`, `ushort`, `intc`, `uintc`, `int_`, `uint`,
`intp`, and `uintp`) resolve to one of the eight listed classes here.

Broadening to `isinstance(value, np.integer)` would not preserve the safety
contract: an independently constructed `np.int64` subclass satisfied that
check and its overridden `__int__` raised when converted. A correction should
retain exact-type membership and make the exact set complete and
platform-aware, or centralize an equivalently safe exact normalization helper.

== Configured-field identity and DRY assessment

Repository search found three distinct semantics that should not be conflated:

* `ensure_unique_physical_column_labels` validates the physical DataFrame
  boundary and deliberately permits addressable non-string labels;
* XRef matrix-axis identity validators require non-empty strings for
  carrier-stable matrix identities, while several XRef, Cell Codec, and other
  transformation field selectors intentionally retain broader physical-label
  behavior;
* Axis Mapping's configured field references have the narrower new contract:
  exact built-in string references match only exact built-in string physical
  labels.

No existing shared helper implements that third contract. Reusing either the
generic physical-label predicate or the XRef matrix-identity validator would
merge different concepts. The local `_column_positions` is used for every
Axis Mapping key, label, and order field, so no internal field-resolution drift
was found in Slice 1.

If a second transformation adopts the same exact-string field-reference
contract, the likely shared home is `domain/tabular`, next to but separate
from the physical-label and configured-declaration helpers. Current raw pandas
membership sites are a drift watch, not evidence that all of them already
share Axis Mapping's semantic contract. No DRY blocker is recorded.

== Model, immutability, and iterator assessment

The following direct-construction invariants hold:

* resolver input must be an exact `AxisMappingIntent`;
* policy must be exact `AxisOrderPolicy`;
* mapping members must be exact `ResolvedAxisMember`;
* positions must be exact built-in `int`, excluding `bool` and subclasses,
  non-negative, contiguous, and zero-based;
* label arity, duplicate keys, and duplicate complete tuples fail;
* configured field lists are copied to built-in tuples;
* member iterables are copied to a private built-in tuple;
* unordered member mappings/sets are rejected;
* derived lookup mappings have no caller-retained mutable backing dictionary;
* equality may exclude the derived maps when members are themselves stable.

The last premise is false for accepted tuple subclasses. `_resolved_labels`
checks with `isinstance(value, tuple)` and returns the caller object unchanged.
`ResolvedAxisMember` therefore retains it, `ResolvedAxisMapping` hashes it,
`labels_for_key()` returns it, and `key_for_labels()` accepts it again.
A mutable-hash tuple subclass changed same-object inverse lookup from success
to `AxisMappingError` after caller mutation. A tuple subclass whose `__len__`
raises leaked `RuntimeError` from direct member construction.

One-shot generators for mapping members and `used_keys` are materialized once.
An iterator can necessarily perform its own side effects or raise while being
consumed; the resolver's non-mutation guarantee applies to the supplied Frames
mapping, DataFrames, `_meta`, and their nested objects, not to arbitrary
iterators. No additional finding is recorded for inherent iterator
consumption.

== Exception assessment

The narrow physical-helper catch is correct and NumPy conversion/sort cannot
invoke caller comparators for the accepted exact classes. Hostile NumPy
subclasses are rejected before conversion.

The exception contract is nevertheless not complete because A-1 leaks
`RuntimeError` while constructing rejection diagnostics. The same mechanism
affects invalid Intent/member strings, source key/label values, `used_keys`,
and unsupported order values.

=== Important

A-1 -- rejection diagnostics invoke hostile type-name behavior::
`_require_non_empty_string`, `_text_value_diagnostic`, and
`_require_order_value` interpolate `type(value).__name__`. A metaclass with a
hostile `__getattribute__` caused five independently probed paths
(Intent, member, source value, used key, and order value) to raise raw
`RuntimeError`, with one hostile name access each.
+
Risk: rejected caller objects execute code and escape the promised
feature-specific diagnostic at core validation boundaries.
+
Recommended action: centralize a diagnostic-safe type description that cannot
dispatch through caller metaclass behavior, or omit the dynamic type name; add
direct and resolver regressions for every affected boundary.

A-2 -- the accepted pandas/NumPy integer vocabulary is incomplete::
The exact type tuple lists eight fixed-width classes but omits distinct exact
`numpy.longlong` and `numpy.ulonglong` classes. Pandas preserves both on this
platform, and the resolver rejects both with `AxisMappingError`.
+
Risk: two values satisfying the FTR's stated "exact NumPy integer scalars
produced by pandas" contract fail depending on dtype/platform spelling.
+
Recommended action: keep exact-type normalization but make the supported set
complete and platform-aware; add every practical signed/unsigned NumPy dtype,
aliases that are distinct on the running platform, boundary values, nullable
integer scalars, and mixed Python/NumPy integer columns. Do not replace the
check with broad `isinstance(np.integer)` without preserving subclass safety.

A-3 -- retained tuple subclasses break effective immutability::
`_resolved_labels` accepts tuple subclasses and returns them unchanged. A
caller-owned mutable-hash tuple is retained as member labels, hashed by the
derived inverse map, and returned by forward lookup. Mutating its hash state
changes later same-object inverse lookup. A hostile `__len__` also escapes
direct construction.
+
Risk: a frozen Resolution is not effectively immutable, rejected/hostile
container behavior can execute, and lookup stability depends on caller state.
+
Recommended action: establish an exact built-in tuple boundary before calling
overridable tuple methods and store only a private exact tuple; cover hostile
length/iteration/hash/equality/representation and post-construction mutation.

A-4 -- focused tests still omit required semantic adversaries::
The suite does not cover A-1 through A-3 and contains no positive tests for the
NumPy-integer support it claims.
+
Risk: a green 30-test adversarial subset and 94% coverage continue to provide
false acceptance confidence.
+
Recommended action: add focused regressions for all three findings and retain
the broader ordering matrix exercised by this review.

=== Minor

M-2 -- direct NumPy dependency is implicit::
The resolver imports NumPy directly, but the project declares only pandas as
the dependency that brings NumPy into the environment.
+
Risk: dependency ownership and compatible-version intent are implicit.
+
Recommended action: decide explicitly whether the normalizer should avoid a
direct NumPy import or whether NumPy should become a declared runtime
dependency.
