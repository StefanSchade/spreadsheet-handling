= Independent Architecture Review -- XRef Physical-Label / Trusted-Metadata Authority Decision

*Review date:* 2026-08-14

*Artifact under review:*
`docs/backlog/FTR-XREF-PHYSICAL-LABEL-METADATA-AUTHORITY-P4A.adoc`

*Authoring commit:* `f7d2c7ede676d7c50a2a7b7f8885d68ed1157469`

*Verdict:* *B. NARROW CORRECTION REQUIRED.*

The role-specific boundary is coherent and is a legitimate deliberate
revision of the published selector contract. It is not implementation-
authorizing as written: `E1-admitted Scalar` is semantic classification, not
a carrier-neutral persisted reference; the numeric example fails after actual
JSON-directory/XLSX/ODS reload; current authority layers are omitted from the
documentation transition; and the list-record consumer needs an explicit
uniqueness invariant. These are bounded corrections, not grounds to reopen
the census or global physical-label authority.

== 1. Scope and exact baseline

This review answers one question: whether the new FTR coherently and
sufficiently resolves the conflict between XRef's published broad physical-
label selector authority and Trusted-Ingress E3's bounded metadata language.
The proposal was treated as falsifiable architecture, not as a binding
conclusion from the four preceding census corrections.

The worktree was clean on `main`; `HEAD` was `f7d2c7e`. `git show f7d2c7e`
reports exactly the new FTR and `_ftrs_open.adoc`, with no runtime, test,
registry, model, guide, roadmap, or Project Memory change. Preceding review
commit `c1ec55b` changes only the census review. Current lifecycle authority
says E3-E7 remain unstarted, `TRUSTED-INGRESS-E3-CENSUS-FOLLOWUP-F1` remains
`NOT RESOLVED`, earlier `-REVIEW-F1/-F2` remain closed, and `_ftrs_open.adoc`
registers this FTR as a direct E3 prerequisite.

The complete 582-line FTR and its complete registration diff were read. This
review does not implement E3 or modify any source, test, reviewed FTR, census,
census review, model, guide, registry, roadmap, or Project Memory file.

== 2. Reconstructed authorities

=== 2.1 XRef distinguishes physical selectors from matrix-axis identities

The distinction asserted by the FTR is real and independently maintained.

`domain/tabular/physical_labels.py` defines the global physical-column
predicate as non-missing, hashable, deterministically self-comparable, unique,
and scalar-addressable. Its module and function documentation explicitly say
that physical labels need not be strings and give numeric and tuple labels as
accepted examples. `xref_crosstable/primitives.py` aliases that predicate as
XRef's accepted physical-label contract while defining matrix-axis identities
separately.

By contrast, `_ensure_column_identity_values` and
`_ensure_column_identity_list` require the roundtrip matrix-axis vocabulary to
be non-empty strings, adding uniqueness where an identity list requires it.
`expand_xref` applies that contract to the complete physical matrix header.
The resulting directional fact is important: a numeric relation-field
selector is accepted by `contract_xref`, while a rendered matrix with a
numeric header is rejected by `expand_xref`. The prior review already recorded
that asymmetry; it does not erase the broader relation/axis-source selector
contract.

The same split appears in the Technical Model (lines 98-140), Functional Model
(lines 271-309), User Guide (lines 163-215), active release notes, registry,
and runtime source. The User Guide expressly accepts a unique numeric physical
label; sparse non-string examples do not cancel that contract.

=== 2.2 Trusted-Ingress metadata grammar is bounded

The Trusted-Ingress design accepts `_meta` as an owned, bounded, acyclic
substrate and requires a compatibility census before E3 selects its exact
node vocabulary. Census section 17.4 records the preferred/accepted evidence
target:

....
root and recursive mappings: exact dict
recursive sequences:         exact list
ordinary dictionary keys:    exact str
ordinary leaves:             E1-admitted Scalar
delegates:                    closed, statically governed roles with a common
                              recursive post-check
....

The bounded roles do not authorize arbitrary Python objects. E1's semantic
vocabulary is String, Boolean, Number, Missing, Date, and DateTime. Its
recognized carrier set is broader than native Python aliases: it includes
NumPy numeric/string/boolean variants, `pandas.Timestamp`, and
`numpy.datetime64`. That classification contract explicitly does not
normalize those carriers.

=== 2.3 The authority conflict is confirmed

Current public `contract_xref` accepts `int`, `bool`, `float`, `date`,
`datetime`, NumPy/pandas scalar variants, `bytes`, `complex`, `frozenset`, and
a stable custom hashable/comparable non-tuple label when it is used as both a
relation `row_keys` selector and a dense-axis source selector. The exact label
carrier is copied into XRef metadata.

The first six semantic families may be E1 Scalar, subject to Missing and
carrier qualifications below. `bytes`, `complex`, `frozenset`, and custom
objects are not E1 leaves. Any non-string label also violates the exact-string
metadata-key rule when used as a key in runtime `row_identities`.

The conflict is therefore genuine. It cannot be resolved by another census
wording correction, by claiming unusual values were never supported, or by
widening E3 to arbitrary hashable/comparable objects.

== 3. Durable Intent and runtime Resolution trace

`expand_xref` and `contract_xref` copy `row_key_cols` to durable
`xref_crosstable.<id>.row_keys`; rediscovery, role resolution, and schema
maintenance consume it. `_axis_source_config` similarly persists physical
selectors in both `dense_axes.rows_from.key/keys` and
`columns_from.key/keys` for fresh-run re-resolution. In contrast,
`_dense_axes_meta_payload` emits `dense_axes.resolved.row_identities` keyed by
physical `row_key`; `_stored_row_identities` consumes it as a same-run
fallback, and `project_meta_to_persistable_contract` removes all `resolved`
state while preserving the three Intent paths.

JSON-directory persistence writes `_meta.yaml`; the XLSX and ODS paths encode
the projected metadata in a hidden-sheet JSON `workbook_meta_blob`. Both
spreadsheet composers call plain `json.dumps` for that blob. Readers restore
the sidecar/blob before XRef/metadata consumers run.

The FTR therefore identifies the two primary problems correctly:

. non-E1 selector values occur as durable Intent leaves; and
. non-string physical labels occur as runtime metadata dictionary keys.

One directly consequential durable copy is omitted from the FTR's seam
inventory. `contract_compact_multiaxis` and `expand_compact_multiaxis` forward
their selectors through XRef, suppress the internal temporary XRef entry, and
then persist the same original `row_keys` under
`_meta.compact_multiaxis.<id>.row_keys`. The registry calls that trace
persisted unchanged. This is not a second architecture: it inherits the same
selector rule. It is, however, an implementation, canonicalization, test, and
documentation obligation. Grouped XRef simply forwards to the XRef seam and
keeps XRef-owned metadata; no second grouped metadata authority was found.

== 4. Assessment of the role-specific architecture

The capability split is conceptually sound:

....
ordinary physical DataFrame label
    -> broad global physical-label authority

label nominated as durable XRef selector/reference
    -> broad physical-label predicate
       intersected with one bounded, carrier-neutral metadata-reference rule
....

This changes the selector-role contract without changing global DataFrame
physical-label authority. A nonconforming label may remain an ordinary column
when it is not nominated as `row_keys` or a dense-axis `key`/`keys` value.

The narrowing is legitimate architecture governance. The existing selector
contract is published and intentionally broad, so implementation must describe
the change honestly as a compatibility break. An architecture FTR may revise
that contract to obtain a bounded durable representation; it may not reclassify
the old behavior as unsupported merely because examples/tests were sparse.

The selected *boundary location* is therefore accepted in principle. The
selected *E1-Scalar vocabulary* is not evidenced as carrier-neutral and must
be corrected before the FTR authorizes implementation.

== 5. Carrier and normalization assessment

=== 5.1 `admit_ordinary_scalar` validates but does not normalize

`admit_ordinary_scalar` delegates classification to `scalar_category`, returns
the original accepted object unchanged, and preserves its identity. Its
docstring says explicitly that it does not normalize. The classifier likewise
states that NumPy/pandas variants remain those variants. Both use the safe
classify-before-inspect path claimed by the FTR; unsupported candidates are
rejected with type-only diagnostics and without their `repr`, string
conversion, hashing, equality, or iteration.

Calling this function is sufficient to establish semantic family membership.
It is not sufficient to establish the value that can be written into durable
metadata. The FTR's proposed implementation adds a check but specifies no
owned canonical-value result.

General scalar normalization remains Phase E's accepted ownership. XRef must
not invent an independent scalar normalizer. If the selector contract admits
carrier variants, Phase-E-owned normalization must produce the single
canonical selector reference before every durable/runtime copy is built, and
the XRef family must verify its category and physical-label conditions.

=== 5.2 Actual maintained-carrier results

Read-only probes placed one representative selector under `row_keys`,
`rows_from.key`, and `columns_from.key`, applied the real persistence
projection, and exercised YAML, JSON-directory sidecar, XLSX, and ODS paths.

[cols="2,2,2,4",options="header"]
|===

|native `str`, `bool`, `int`, `float`
|Roundtrips with the same native type

|Metadata alone works; physical-header identity still fails for non-strings

|native `date`, naive/aware `datetime`

|Not carrier-neutral

The data-record JSON temporal encoder and YAML temporal helper do not cure
this. They are private, persistence-local *cell-record* codecs. JSON-directory
metadata is dumped separately by PyYAML, while spreadsheet metadata uses the
plain JSON blob path. Accepted Date/DateTime work does not authorize native
temporal values in `_meta` across these carriers, and D-T3/D-T4 cannot be
assumed to do so.

=== 5.3 The published numeric example is not durable today

A real `contract_xref` probe used physical relation label integer `7` and
persisted the returned relation plus projected XRef intent. Results:

[cols="2,2,2,3",options="header"]
|===
|Carrier |Reloaded physical label |Reloaded metadata selector |Later XRef lookup

|JSON directory
|string `"7"`
|integer `7`
|Fails: configured row-key column `7` is missing

|XLSX
|string `"7"`
|integer `7`
|Same failure

|ODS
|string `"7"`
|integer `7`
|Same failure

|YAML records plus YAML metadata
|integer `7`
|integer `7`
|Passes
|===

Thus integer metadata is serializable, but the selector reference is not
carrier-neutral because the referenced physical header is not. Converting the
metadata `7` to string `"7"` would make lookup happen to work after these
carriers, but would not preserve numeric semantic identity and would collide
with a genuine string label `"7"`. That is not the architecture the FTR
selects.

On current maintained carrier evidence, the only proven all-carrier direct
selector-reference subset is exact native String, excluding the E1 Missing
category. Preserving Number or Date/DateTime would require separately
specified, type-preserving physical-header identity across frame and metadata
carriers (or a stable technical label identity). No such mechanism exists.

=== 5.4 Missing and Number semantics

The phrase `E1-admitted Scalar` accidentally includes Missing.
`admit_ordinary_scalar` accepts `None`, empty string, NaN, `pandas.NA`,
`pandas.NaT`, and `numpy.datetime64('NaT')` as Missing. Relation-frame
physical validation rejects `None`/NaN/NA/NaT, but the admission call itself
does not, and exact dense-axis/config paths cannot rely on that implication in
all direct/fallback cases. The final selector vocabulary must say
`scalar_category(value) != "missing"` (or express the equivalent closed
positive categories). Under current E1 semantics this also makes the currently
accepted empty-string physical selector a deliberate compatibility decision,
not an unnoticed String case.

Native Boolean/Number metadata preserves its JSON/YAML type, including
ordinary finite values; Python's JSON implementation also roundtrips infinity,
while NaN is Missing and must be excluded. None of that repairs physical
header type loss. Equality collisions (`1`, `True`, `1.0`) remain owned by the
existing physical-label and configured-field uniqueness/equality rules. The
FTR is correct not to invent a second equality model.

== 6. Runtime representation assessment

Conditioned on one bounded canonical selector reference, the proposed

....
[
  {"row_key": <canonical selector reference>, "value": <resolved component>},
  ...
]
....

shape is coherent and is the right existing design to reuse from census
section 19 rather than inventing a new generic pair type.

It provides fixed exact-string metadata keys, preserves physical selector
type when the canonical value itself preserves it, retains one association per
composite component, and records producer traversal in `row_keys` order.
Reconstruction by `"row_key"` value using `_values_equal` is independent of
caller order and preserves the documented same-run fallback. A missing
association can continue to raise `KeyError`; identity-tuple duplicate checks
and the existing physical-label equality owner remain unchanged.

One bounded rule is missing. A dictionary can contain at most one entry for a
given key; a list can contain two records whose `"row_key"` values compare
equal. The consumer contract must require exactly one matching record for each
requested selector and reject zero matches as missing and multiple matches as
ambiguous. It should not silently select the first. This is a family semantic
check, not a new metadata grammar or equality model.

Durable `row_keys`, dense-axis `key`/`keys`, runtime
`row_identities[*][*].row_key`, and the compact-multiaxis trace must all use
the same canonical selector-reference value. Normalizing only at the
persistence boundary would leave runtime Resolution and durable Intent in
different forms; normalizing only inside XRef would leave the compact wrapper's
durable trace in the original form.

`rows_from` and `columns_from` belong to the same selector contract. Both
persist a physical field label selected from their configured source frame;
their arity and the semantic type of their *resolved axis values* differ, but
the persisted `key`/`keys` role does not.

== 7. Documentation transition and wrapper surfaces

The FTR acknowledges a compatibility narrowing and requires release-note
treatment. That is necessary but insufficient.

The Technical Model, Functional Model, User Guide, current release notes, and
`meta_registry.yaml` all currently publish the broader physical-selector
contract. FTR section 13 assigns later Trusted-Ingress condensation as the
permanent explanatory home, but that later task cannot be the first point at
which maintained documentation becomes true. An implementing commit must
atomically update every current normative/public surface whose selector rule
is revised.

The update must preserve the global physical-label statement while qualifying
the XRef selector nomination role. It must cover direct XRef parameters and
the relevant grouped/compact forwarding wording. The `xref_crosstable`
registry entry must state the final durable selector representation; the
`compact_multiaxis` entry must no longer claim unchanged cross-carrier
serialization for an uncanonicalized forwarded selector trace. Release notes
must describe both the selector compatibility break and the runtime
`row_identities` shape change under the active unreleased section.

Later condensation may reorganize and explain that truth. It cannot defer the
truthfulness of current authority layers.

== 8. Alternatives and architecture principles

No existing stable physical-column identity was found. Position cannot serve
as identity because order is explicitly non-authoritative and same-run
composite reconstruction supports reordered `row_keys`. The live resolver used
by axis-mapping/grouped work does not persist an identity for arbitrary
physical labels.

Moving `row_keys` outside `_meta` would break XRef's persisted intent and
rediscovery model. Moving only runtime Resolution outside `_meta` is
unnecessary once fixed-key records are used and would reopen an accepted
Intent/Resolution ownership split. Widening E3 to the global hashable/
comparable physical-label predicate would admit arbitrary caller-defined
objects and destroy the bounded positive grammar. None of these alternatives
supplies a fatal objection to the role-specific boundary.

After correction it has a positive closed grammar, safe admission, one Phase-E
normalizer, no object escape hatch, and no formal LangSec or DCF claim.

== 9. Findings

=== XREF-PHYSICAL-LABEL-AUTHORITY-REVIEW-F1 -- Blocking -- the selected E1-Scalar vocabulary is neither normalized nor carrier-neutral

*Exact evidence:* `admit_ordinary_scalar` returns accepted carriers unchanged;
`scalar_values.py` explicitly reserves canonical normalization for Phase E.
Native Date/DateTime fail the plain JSON workbook metadata blob; NumPy/pandas
variants fail or narrow differently across YAML and JSON. Most decisively, a
real numeric selector roundtrip reloads physical label `7` as `"7"` in
JSON-directory, XLSX, and ODS while metadata stays integer `7`, and later XRef
lookup fails. Missing carriers are admitted by E1. Compact Multiaxis persists
another original `row_keys` copy after forwarding through XRef.

*Architectural impact:* The FTR does not define one value that can safely be
written into durable Intent, reused in runtime Resolution, reloaded from every
maintained carrier, and still identify the physical DataFrame column. The
numeric example and carrier-neutrality claims are false, and merely calling
the proposed admission function cannot authorize implementation.

*Required correction:* Replace `E1-admitted Scalar` with an exact, positive,
non-Missing selector-reference vocabulary backed by cross-carrier frame-plus-
metadata evidence. Under current carriers, exact native non-Missing String is
the only proven direct-reference subset. If the FTR elects to preserve Number,
Date, or DateTime instead, it must specify and authorize a type-preserving
physical-header/reference representation and demonstrate it across JSON/YAML,
XLSX, and ODS; metadata-only coercion is insufficient. Assign any canonical
carrier normalization to Phase E, not a second XRef normalizer, and produce the
canonical value before building XRef Intent, runtime records, or the compact
trace. Explicitly exclude Missing and test native plus NumPy/pandas carriers,
including the published numeric example after reload.

=== XREF-PHYSICAL-LABEL-AUTHORITY-REVIEW-F2 -- Blocking -- implementation may leave current published authority false

*Exact evidence:* FTR sections 9, 10, and 12 require tests and release-note
treatment but do not require the Technical Model, Functional Model, User Guide,
or relevant registry contracts to change atomically. Section 13 instead points
to later Trusted-Ingress condensation. Those current surfaces are the same
evidence by which the FTR establishes that non-string selector support is a
published contract.

*Architectural impact:* An implementation could deliberately narrow the
selector role while maintained normative/public documentation continued to
promise the old broader role. Release notes describe migration; they do not
replace current contracts. The decision is therefore not implementation-
authorizing.

*Required correction:* Make atomic implementation-time updates to every
current authority layer whose selector statement changes: Technical Model,
Functional Model, User Guide (including grouped/compact forwarding where
relevant), active release notes, and relevant `xref_crosstable`/
`compact_multiaxis` registry wording. Preserve the broad global DataFrame-label
contract and qualify only the nominated durable-selector role. Later
Trusted-Ingress condensation may reorganize this truth but must not establish
it for the first time.

=== XREF-PHYSICAL-LABEL-AUTHORITY-REVIEW-F3 -- Important -- the list-record consumer lacks an explicit ambiguity invariant

*Exact evidence:* The target representation and consumer rule say to locate a
record by `"row_key"` with `_values_equal`, and specify missing-association
failure. They do not say what happens when two list records carry equal
`"row_key"` values. The current dictionary representation makes that duplicate
association structurally impossible.

*Architectural impact:* A future implementation could silently choose the
first duplicate, making reconstruction order-dependent and weakening the
current unique association.

*Required correction:* Require exactly one `_values_equal` match for each
requested row key. Reject zero as missing and more than one as ambiguous,
without adding a new equality model. Pin composite reordered fallback,
missing, duplicate, deterministic traversal, and same-run behavior in the
implementing tests.

== 10. Verdict and lifecycle consequence

*B. NARROW CORRECTION REQUIRED.*

The role-specific selector boundary is a coherent and legitimate contract
revision, and the fixed-string-key runtime representation is conceptually
sound. The FTR must first correct its durable vocabulary/carrier proof,
normalization ownership and all-copy seam, documentation transition, and
duplicate-association rule. This verdict does not reopen global physical-label
authority or the general E3 census.

The same author may perform a narrow FTR correction, followed by a fresh-
context disposition review of F1-F3. Meanwhile the census is not corrected
again, `FOLLOWUP-F1` stays open, E3-E7 stay unstarted, and no lifecycle
curation or implementation follows.
