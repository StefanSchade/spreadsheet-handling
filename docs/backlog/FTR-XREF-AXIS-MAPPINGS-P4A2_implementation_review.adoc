== Exact scope implemented

Commit `268d413` adds one feature-local internal package:

* a frozen `AxisMappingIntent` naming the source frame, canonical key column,
  one or more ordered visible-label columns, and an explicit ordering policy;
* `AxisOrderPolicy.SOURCE_ROW`, which deliberately selects current source-row
  order, and `AxisOrderPolicy.COLUMNS`, which requires one or more configured
  order columns;
* a frozen `ResolvedAxisMember` carrying a canonical key, complete ordered
  visible-label tuple, and zero-based stable position;
* a frozen `ResolvedAxisMapping` carrying ordered members, label-level arity,
  exact key-to-tuple lookup, and exact full-tuple-to-key lookup;
* `resolve_axis_mapping`, a read-only resolver from current Frames plus Intent
  to the run-local Resolution;
* optional `used_keys` completeness validation without filtering the complete
  source mapping.

The logical model supports any positive number of label levels. One-level
labels remain one-element tuples. It never joins label levels into a string or
creates a pandas `MultiIndex`.

== Model and resolver contract

Canonical keys and complete visible-label tuples form an exact bijection.
Forward lookup accepts only an exact canonical key. Inverse lookup accepts only
a tuple with the resolved arity and exact values. Case, whitespace, delimiters,
and spelling are preserved and compared exactly; there is no normalization,
case folding, fuzzy matching, parsing, or fallback.

Canonical keys and visible labels are non-empty strings. Although the
implementation prompt asked for numeric keys if consistent with the reviewed
contract, the authoritative reviewed FTR defines canonical keys and visible
labels as non-empty strings. The implementation therefore rejects numeric keys
deliberately instead of widening the contract.

Ordering is always explicit:

* source-row order is used only when Intent selects `SOURCE_ROW`;
* configured-field order compares order columns in declaration order and adds
  the canonical key as the final deterministic tie-breaker;
* duplicate configured order-field values are therefore valid and do not
  create ambiguous positions;
* missing, non-scalar, non-reflexive, ambiguous, mixed-incomparable, or
  non-total ordering values fail before Resolution is returned.

An empty source frame with all configured columns is a valid empty bijection.
The Resolution retains label-column arity even when it has no members.

== Validation behavior

Declaration validation rejects:

* missing or empty source/key field names;
* no label columns;
* non-sequence, unordered, empty, non-string, or duplicate field
  declarations;
* an untyped ordering policy;
* order columns combined with source-row order;
* configured-column order without at least one order column.

Source/schema validation rejects:

* a missing source frame or a non-DataFrame source;
* missing key, label, or order columns;
* missing-like, duplicate, ambiguous-equality, or unhashable physical column
  labels through the shared physical-label boundary.

Complete mapping validation rejects:

* missing, empty, numeric, unhashable, ambiguous-equality, or non-scalar
  canonical keys and visible labels;
* duplicate canonical keys;
* duplicate complete visible-label tuples;
* unknown used canonical keys;
* malformed used-key values;
* missing, non-scalar, equality-ambiguous, incomparable, or non-total order
  values.

Repeated values at individual label levels are accepted when the complete
tuples differ. Configured order-field ties are accepted because canonical keys
settle them. Validation materializes and checks all source values before
hashing them into the bijection or sorting them, so malformed values receive
axis-mapping diagnostics instead of raw pandas, NumPy, or Python exceptions.

Lookup validation rejects unknown canonical keys, unknown complete tuples,
non-tuple inverse inputs, malformed label elements, and wrong tuple arity.
Visible text is never accepted as canonical identity.

== Atomicity and non-mutation evidence

The resolver reads the source with positional scalar access after validating
the complete physical-column boundary. It creates private immutable records and
returns a new immutable Resolution. It returns no Frames and writes no
metadata.

Focused tests retain references to every caller-owned DataFrame, metadata
mapping, nested list, and nested mapping. On both successful and failed
resolution they assert:

* every retained object has the same identity;
* every DataFrame has the same values, columns, index, and dtypes;
* nested metadata values remain equal;
* no output frame, `_meta` root, cleanup command, or nested object is added or
  replaced.

== Residual risks

* The typed package is intentionally internal but Python cannot technically
  prevent consumers from importing internal modules. Public naming and surface
  stability remain decisions for the gated projection slice.
* Order comparability is validated against current scalar values. A future
  public surface may need a narrower serialized order-value vocabulary, but
  Slice 1 creates no serialization contract.
* Axis projection, unknown workbook tuple policy, and structure-damage
  semantics remain unimplemented.
* Hierarchical logical header representation and lossless grouped XLSX/ODS
  carriers remain later Slice 3/4 work.
* The sibling Grouped Columns FTR still needs refinement before its
  implementation so it consumes this identity model rather than defining a
  competing one.
