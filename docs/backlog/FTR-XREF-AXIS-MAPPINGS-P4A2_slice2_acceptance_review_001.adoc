== Runtime-semantics assessment

*Correct.* Verified against `xref_axis_projection.py` and the Slice 1 resolver:

* *Outbound produces exactly one flat visible string.* The intent is built with a
  single-element `label_columns=(label_column,)`, so every resolved label tuple
  has arity one; `mapping.labels_for_key(value)[0]` unwraps it to the single
  string XRef renders as a matrix header. No tuple/MultiIndex leakage.
* *Inbound restores the exact canonical key.* Each value is wrapped as a
  one-element tuple and looked up through `key_for_labels((value,))`, which
  validates arity and returns the exact resolver key.
* *Uses the Slice 1 resolver, no duplicated mapping logic.* The module calls only
  `resolve_axis_mapping`, `labels_for_key`, `key_for_labels`, and reuses
  `AxisMappingError`/`AxisMappingIntent`/`AxisOrderPolicy`. It re-implements none
  of the exact-string / exact-tuple / safe-diagnostic / NumPy-integer contracts.
* *`contract_xref` / `expand_xref` unchanged.* The two steps are separate
  `Frames -> Frames` transformations run before/after XRef; they do not wrap it.
  Confirmed by the empty XRef diff and by the live pipeline roundtrip below.
* *Standalone vocabulary transforms.* Neither step imports or calls the XRef
  operation; they only substitute a single relation column.
* *Preservation.* `_publish` does `result = df.copy(); result[column_key] =
  new_values`, where `new_values` is positionally aligned to
  `df[column_key].tolist()`. Row order, index, non-axis columns, values, and
  frame structure are preserved; only the axis-identity column changes.
* *Coherence + no input mutation.* Input relation DataFrame is copied before
  assignment; `dict(frames)` shallow-copies the mapping. Confirmed by
  `test_inputs_are_not_mutated` and re-derived by reading `_publish`.

Live verification (public path, not only direct calls): a
`build_steps_from_config` + `run_pipeline` pipeline of `project_axis_labels ->
contract_xref -> expand_xref -> restore_axis_keys` reproduced the original
canonical relation exactly, with readable matrix headers `{story_id, Galli,
Trixi}` in between.

== Public-parameter assessment

Final public surface matches the runtime signatures, the registry entries, and
the user-guide table: `relation`, `output`, `source_frame`, `key_column`,
`label_column`, `order_policy`, `order_columns`, `column_key` (default
`"column_key"`), `drop_source`. `SOURCE_ROW` is documented (module, registry
`notes`, user guide) as relative to caller-supplied source-frame row order with

Both implementation refinements are *correct, evidence-driven refinements*:

. *`name` omitted -- correct.* XRef's `name` keys a persisted
  `_meta.xref_crosstable.<id>` config; these steps write no feature-owned
  persisted `_meta`, so a `name` function parameter would be unused and
  misleading. Critically, this does *not* break the YAML step-naming convention:
  the builder (`build_steps_from_config`) pops `name` and consumes it as the
  `BoundStep` identity via `make_frames_target_step(*, name, **kwargs)`; it is
  never forwarded to the target function. Verified live -- a spec with
  `name: my_step` bound a step named `my_step` and ran successfully with `name`
  absent from the function signature. Omitting it keeps the Python surface honest
  while preserving the YAML convention.
. *`order_policy` / `order_columns` retained but substitution-irrelevant --
  correct/harmless.* Substitution is per-value dictionary lookup and does not
  consume member order, so a roundtrip is identical under both policies
  (asserted by `test_roundtrip_result_is_order_policy_independent` and the
  parametrized roundtrip). They are forwarded to the resolver unchanged and are
  documented as substitution-irrelevant in the module, user guide, and registry.
  They are not entirely inert -- an ill-typed or absent order column can still
  fail resolution -- but that is an explicit, defaulted-off caller opt-in and
  keeps signature symmetry with the resolver for later slices. This is retained
  surface, not a contract defect (Observation O-3).

Neither refinement re-opens a settled decision.

== Losslessness assessment

Conditional bijection is stated and implemented correctly.

* Same live mapping source + configuration is the documented precondition
  (registry `inverse.reason`, user-guide "losslessness condition", release note).
* Unique canonical keys and unique complete visible labels are enforced by the
  resolver's `_ensure_bijection`; duplicate keys or duplicate labels fail before
  any output.
* Exact matching only -- resolver lookups require exact built-in non-empty
  strings; no fuzzy/case/delimiter behavior is introduced.
* Failure rather than guessing: an outbound canonical key missing from the
  source fails via `used_keys` completeness; an inbound label with no key fails
  via `key_for_labels`; an absent source frame fails via
  `_require_source_frame`.

No edit between outbound and inbound can silently mis-restore: restoration is an
exact tuple-keyed lookup that raises on any unknown label and on any duplicate in
the source. The only way to break losslessness is to change or remove the source
mapping -- which is exactly the documented "same live source" precondition and
fails loudly rather than guessing.

== Validation / diagnostic assessment

Under the accepted Domain Boundary Robustness policy (level-2 competent-user
input at the transform boundary; the resolver owns value-level validation), all
supported malformed inputs fail cleanly with `AxisMappingError` carrying
frame/column/row context:

* unknown outbound key, unknown inbound label, absent relation frame, absent
  source frame, absent axis column, duplicate keys, duplicate labels,
  empty/invalid labels, wrong arity, invalid order policy, invalid
  physical/configured column declarations -- all routed through
  `AxisMappingError` (transform ingress `_require_name` / `_order_policy` /
  `_require_relation`, or the resolver).
* output/source collisions and invalid `drop_source` combinations: the
  `drop_source and relation == output` case raises before resolution
  (`test_drop_source_requires_distinct_output`).
* No raw pandas/NumPy/metaclass exception leaks for supported malformed inputs:
  physical-label problems are caught and re-raised (`_require_relation` wraps
  `ValueError`); NaN/None/non-string axis values are described with a constant
  detail (`_unsupported_type_detail`) and never invoke caller `repr`/type/hash.

Arbitrary hostile in-process Python (level-4) is correctly out of the threat
model and is not defended beyond the resolver's narrow value contract. No genuine
explicit-guarantee violation (immutability, atomicity, exact identity,
deterministic order) was found during independent probing.

== Ownership / atomicity assessment

*Correct.*

* Caller Frames mapping not mutated: `dict(frames)` shallow copy.
* Input DataFrames not mutated: output is `df.copy()` before column assignment.
* Caller `_meta` not mutated: on the default path `_meta` is passed through by
  reference untouched; with `drop_source`, `mark_frames_for_cleanup` shallow-
  copies `_meta` and rebuilds the `pipeline_cleanup` command dict and
  `drop_frames` list before assigning, so the caller's `_meta` object is never
  written (`test_drop_source_marks_relation_without_mutating_input_meta`,
  re-derived from `pipeline_cleanup.py`).
* Build-then-publish: `new_values` is fully computed (raising on any bad
  key/label) before `_publish` creates the output frame or marks cleanup.
  Failure publishes no partial output (`test_failure_publishes_no_output_frame`).
* `drop_source=True` adds only the existing transient
  `_meta.pipeline_cleanup.drop_frames` command; cleanup marking occurs inside
  `_publish`, i.e. only after successful resolution and substitution, so no
  source is marked on failure.
* No new persisted mapping metadata: `meta_contract.reads: []`; the only write is
  the transient cleanup command; `meta_registry.yaml` unchanged.

*Output name collision (task focus).* `_publish` assigns `out[output] = result`
unconditionally. If `output` names a pre-existing unrelated frame it is silently
overwritten. This is the established, accepted behavior of the `frames_target`
model -- `contract_xref` and `expand_xref` both do `out[output] = ...`
unconditionally (their "output-name collision check" guards only *column* names,
not frame overwrites). It is therefore not a Slice-2 defect (Observation O-2).
The one collision that would corrupt the operation's own intent
(`drop_source` marking the frame you just wrote as the output) is guarded.

== `drop_source` assessment

* Valid for both directions; both call `_publish` with `drop_source`.
* The transformation is row/column preserving except for the vocabulary
  substitution, so no value-loss guard is required (documented).
* Marking the relation superseded is caller-asserted and explicit

* No source is marked on failure (marking happens only in `_publish`, after
  substitution).
* Output must be distinct (`drop_source and relation == output` fails).
* Existing cleanup conflict behavior in `pipeline_cleanup.py` remains

* Documentation and registry describe the transient `_meta.pipeline_cleanup`
  write accurately (registry `meta_contract.writes[0]` persistence `transient`;
  user-guide `drop_source` row).
