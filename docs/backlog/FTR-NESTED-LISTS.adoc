===== FTR-NESTED-LISTS -- Extract and recompose nested 1:n child tables from hierarchical JSON

*Current sequencing note:* Next program -- Phase E, last item; remains blocked
behind the model contract (Phase A), the XRef axis model, and ODS adapter
stabilization (Phases B-D). See `docs/backlog/_ftrs_open.adoc` "Next Program
Sequence".

*Purpose:*::
Enable roundtripping between hierarchical JSON structures that contain lists
and tabular frames suitable for spreadsheet or CSV representation.

*Scope:*::
Applies to adapters handling hierarchical formats (JSON, XML). Lists are
extracted into separate frames, preserving 1-to-many and nested relationships
through synthetic foreign keys.

This FTR is intentionally about the hard case:

* nested singleton objects are not the real problem and can often stay in the
  flattening / multi-header space,
* nested lists are the point where the hierarchy must be broken into multiple
  related tables.

*Solution:*::

* Introduce a transformation step `normalize_nested_lists(frames, meta)` that:
  - scans JSON-derived frames for columns containing lists of *objects*
    (structural 1:n nesting -- the hard case this FTR owns; see "Relationship
    to primitive scalar arrays" below for why a list of bare scalars is not
    automatically the same case),
  - emits new frames for each list-of-objects field (for example
    `orders.items` -> `orders__items`),
  - propagates parent identifiers into child frames to preserve referential
    integrity.
* Provide the inverse `compose_nested_lists(frames, meta)` to re-embed child
  tables into their parent JSON objects during export.
* Handle recursive/nested lists by repeating the pattern with deterministic
  naming (`__` or configurable separator).
* Capture the mapping manifest in meta for traceability.

*Relationship to primitive scalar arrays (`List[Scalar]`):*::
This FTR owns the hard structural case -- a list of *objects/records*, which
must become a child frame because each element has its own multi-field
identity. It does *not* pre-decide that a list of bare scalars (for example
`{"tags": ["a", "b", "c"]}`) must use the same child-frame representation.
`List[Scalar]` overlaps three other, currently unimplemented boundaries that
must reconcile with this FTR before primitive-list handling is implemented
here:
+
--
* the future Trusted Ingress / Minimal Internal Value Model question of
  whether a bounded composite `List[Scalar]` payload value is ever admitted
  into the internal value model (`FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A`
  section 16, "Handoff to Trusted Ingress");
* `TRANS-MERGE-LIST-TO-SEPARATED` / `TRANS-SPLIT-SEPARATED-TO-LIST`
  (`registries/domain_contracts/canonical/transformations.json`), which
  already name the compact-cell projection of a scalar list (for example
  `a/b/c`) as a candidate, not-yet-implemented transformation pair;
* Cell Codec's own explicitly deferred "repeated values of the same type
  inside a compact cell" / token-list disassembly capability
  (`docs/warm_storage/domain_reformation/slices/cell-codec-frames-meta-bridge/slice.adoc`,
  "Composition Boundary"), out of scope for its current MVP slot contract.
--
+
Until that reconciliation happens, a `List[Scalar]` value reaching this FTR's
scope should be treated as undecided, not silently routed through the
list-of-objects child-frame path merely because both are technically lists.
See `docs/cold_storage/working_context/functional_model_inquiry/future_concepts/nested_structures.adoc`
("Representation Strategy 0: Cell-Embedded List") for the existing evidence
that a delimiter-based compact notation is already a recorded candidate for
this case, alongside the extracted-child-table strategy this FTR's own
structural case uses.

*Acceptance:*::

* JSON with nested lists can be unpacked into multiple related tables and
  re-composed without information loss.
* Each emitted table includes a parent-ID column referencing the originating
  object.
* Roundtrip tests cover simple and multi-level nesting (1-to-many-to-many).
* The first implementation documents and enforces a bounded placement strategy
  rather than leaving sheet/table placement accidental.
* Config allows custom naming templates and maximum recursion depth.
