== 2. Independent durable-document ownership reconstruction

The repository's own entry points support this responsibility split:

[cols="2,5",options="header"]
|===
| Owner | Durable responsibility

| Semantic Model
| Domain vocabulary and meaning: the positive internal value language,
  semantic-category versus carrier distinction, and the semantic boundary
  between ordinary payload and framework-authored Intent. It must not own
  orchestration or capability-authorization mechanics.

| Technical Model
| Implemented mechanism and architecture: where parsed carriers become
  Ingress-Conformant Domain state, how execution authority and description
  authority are established, how controlled execution state evolves, how the
  builder/orchestrator boundary works, resource authority, and the bounded
  threat model.

| Developer Guide
| Actionable maintainer rules and checklists for extending carriers,
  composites, certifiable producers, registered capabilities, and authority
  surfaces. Project Evolution owns the short phase-level narrative.

| `interfaces_and_gates.adoc`
| Supported consumer surfaces, caller preconditions, and approval gates. It
  may summarize and link; it must not become a second architecture model.

| ADRs
| Stable decisions and rationale. The accepted runtime/policy ADR remains
  active authority for its Decisions 1--5; it is not the detailed E1--E7
  mechanism document.

| Local source comments/docstrings
| Only mechanism-local reasons that are non-obvious at the code site. They
  must remain current, but they are not a substitute for the model/guide.

| Project Memory / roadmap
| Lifecycle, posture, and navigation. Architecture prose must not migrate into
  concern events.
|===

The design's layer split is therefore sound in principle. Specific placement
results are:

* `docs/semantic_model/06_project_semantic_model.adoc` is a substantively
  appropriate home, not merely a convenient sparse file: it already owns
  first-class domain entities, transformation meaning, and semantic questions.
  Its authority banner and relationship to the Technical Model still need a
  design correction (Important I-1).
* `architectural_layers.adoc` is an acceptable primary home for a concise
  trust-boundary/authority explanation because that file already owns the
  layer map and the accepted trust/authority summary. The review does not
  require a new Technical Model file. If implementation cannot keep the
  detailed execution-state material concise, ch08 is the established
  architecture-detail fallback, but file proliferation is not required by
  this review.
* Developer Guide ch06 is the correct practical home for extension rules.
* Project Evolution ch10 is genuinely required by the existing phase/milestone
  workflow convention.
* `interfaces_and_gates.adoc` should remain the short caller-surface view and
  link to the Technical Model for rationale.

== 4. Condensation versus invention

The design generally distinguishes accepted propositions, faithful synthesis,
and derived maintainer rules honestly. G3 is a defensible synthesis if the
promoted threat-model prose remains no broader than ADR Decisions 1--5 plus
accepted E4/E5/E7 non-guarantees. The design correctly refuses Python-sandbox,
generic filesystem, generic sink, network/subprocess, and hostile-concurrent-
symlink-race claims.

`Certified Invocation Stability` does not occur in accepted governing
authority. A repository-wide exact/insensitive search found it only in the
design artifact and the review prompt context, not the accepted FTR, reviews,
ADR, permanent docs, or source. Describing the underlying immutable effective
execution snapshot is correct. Coining a name would require a deliberate new
wording decision; no name is needed.

A7 is useful new explanatory framing, not accepted historical terminology.
The evidence supports wording such as: the closed Domain language *enables*
generic transformations to rely on admitted value categories and concentrates
external-carrier handling at ingress. It does not support a formal algebraic
closure law or a product guarantee. Use `enables`/`provides a basis for`, not
`guarantees`; keep family-local preconditions explicit.

The Parse-Don't-Validate comparison is a reasonable short analogy for
external representation becoming a trusted Domain state. Its E4/E5 half must
remain explicitly analogical: certificates and controlled transitions do not
literally parse a value into a formal type. This is not a finding if kept to
one bounded explanatory paragraph.

== 5. Semantic Model placement

Slice A's subject matter is genuinely semantic/domain contract. A concise
positive language statement in `06_project_semantic_model.adoc`, with the
carrier/classifier table staying in `internal_value_model.adoc`, is the right
summary-plus-cross-link shape. FormulaSpec/Intent belongs only as a boundary
clarification: it explains why framework-authored output Intent is not a
seventh Scalar or an ordinary composite; its execution lifecycle belongs in
the Technical Model.

The current Semantic Model entry point, however, says the document is a draft
scaffold and is not yet authoritative. Slice A forbids changing any other
Semantic Model file and simultaneously proposes to make its new subsection a
canonical owner. That contradiction must be corrected (Important I-1). The
correction need not stabilize the whole Semantic Model: the entry point may
identify the accepted subsection(s) precisely while retaining draft status for
the remaining scaffold.

The design must also state the authority split explicitly: Semantic Model owns
category meaning and the positive Domain language; `internal_value_model.adoc`
owns accepted carrier variants and classifier mechanics. Leaving the latter's
current blanket `normative` language untouched while calling the former the
primary owner risks two full normative owners.

== 6. Technical Model placement and threat model

The Technical Model is the correct owner, and `architectural_layers.adoc` is
acceptable if the material is written as one coherent trust-boundary section
with links to detailed scalar and consumer-surface contracts. The resulting
text must answer, without FTR archaeology:

* where parsed external payload becomes Ingress-Conformant Domain state;
* where executable/transition authority becomes trusted;
* why config, class, factory, object, or certificate appearance is not
  authority;
* where description capability is authorized and why activation follows it;
* how builder and orchestrator responsibilities differ;
* what E7's resource authority controls; and
* which operator/runtime, plugin, filesystem, sink, and race guarantees are
  explicitly absent.

The threat-model reconstruction in G1--G4 is accurate and appropriately
narrow. In particular, E7 authorizes an allowed plugin as trusted same-process
Python under its complete current argument contract; it neither inspects those
arguments as a generic permission language nor contains arbitrary plugin
behavior. Exact-root/checksum rules are the four current E7 resource semantics,
not a general filesystem or sink policy.

The principal Technical Model defect is completeness, not the selected file:
Slice B omits category B and the inventory omits the controlled execution-state
lifecycle (Blocking B-1/B-2).

== 7. Developer Guide placement

Developer Guide ch06 is the right home for actionable H rules, and ch10's
Phase-E paragraph is required by current workflow convention. The guide should
tell a maintainer what to change and which review boundary applies, then link
to the Technical Model for the reason.

H1, H2, H4, and H5 are actionable when qualified as follows:

* every new registered step needs an explicit E7 classification decision,
  even if the result is ordinary; resource-sensitive authority additionally
  needs its resource contract;
* every new certifiable producer must snapshot/freeze all certificate-relevant
  effective binding state at the mandatory construction boundary, with no
  caller-held mutable alias able to change what executes;
* new description or resource authority is reviewed architecture, not an
  incidental registry/config edit; and
* acceptance and actual macro reachability/wiring are separate checks.

H3 is incomplete as designed. The accepted composite seam requires more than
an explicit schema/codec; see Important I-3.

== 8. Interfaces, navigation, and deduplication

The design correctly diagnoses absence as the dominant problem and selects the
right duplication pattern: one full canonical statement, short audience-
specific summaries, and links. `interfaces_and_gates.adoc` should retain its
surface matrix and caller preconditions while losing historical FTR-shaped
rationale.

Discoverability is not yet designed completely. Existing-file additions are
included automatically, but Slice C proposes a new ch06 file without naming
the required `_chapter.adoc` include. Slice E is titled navigation but only
duplicates the concept-pointer work already assigned to B and the interface
work already assigned to D. It names no include registration, glossary update,
entry-point authority note, or final stale-reference scan. See Important I-5.

The smallest correction is either:

* make Slice E a concrete navigation/consistency slice that owns all model/
  guide includes, entry-point pointers/status notes, glossary/current-term
  updates, and a stale-current-claim scan; or
* fold those exact duties into A--D and remove artificial Slice E.

No fifteen-slice decomposition is needed.

== 9. LangSec and explanatory framing

The section is correctly labeled non-normative and correctly refuses a formal
grammar-class/DCF claim. Some proposed rows nevertheless overstate or merely
associate concepts (Minor M-1):

* `Shotgun Parsing` should say centralized classification/admission, not imply
  that E1--E3 own all parsing.
* `Differing Interpretations` is not supported by the broad claim that one
  resolver makes every declarative target interpretation identical. Surface-
  specific syntax is intentionally different (for example trusted direct-
  colon factory versus plugin spellings). Narrow this to actual E1/E2
  classification order and E7 plugin canonicalization, or remove the row.
* `Overloaded Fields` mapped to Intent/Resolution plus all of `_meta` is too
  associative. Keep it only if tied to a specific accepted field contract;
  otherwise remove it.

The strongest rows (`Non-Minimalist Input Handling`, `Permissive Invalid
Input`, and bounded explicit non-guarantees) add explanatory value. A shorter
table is preferable to inventing justification for weak rows.

== 10. Historical and provisional archival disposition

The historical-only classification is substantially correct. Rejected
architectures, correction loops, test counts, commit hashes, finding ledgers,
obsolete lifecycle status, review methodology, and superseded naming belong
in evidence storage. Durable rationale is preserved by the active ADR and by
the permanent explanation of why shape/identity/config visibility do not
establish authority.

The provisional archive set is coherent:

* the giant Trusted-Ingress FTR, frozen E1 ledger, E2--E7 review chain, E3
  census/review, and E7 design/review chain are plausible historical bundles
  only after condensation and its independent review succeed;
* the runtime/policy ADR remains active;
* the Dotted-Extension FTR and accepted assessments remain active because the
  workstream has obligations beyond Trusted Ingress; and
* the actual archive/retain decision remains later.

The ch04 concept may be retained pending that decision, but the design's
pointer-only treatment is insufficient while the file remains included as an
active Technical Model concept. It contains present-tense claims that Phase E
is unstarted, mandatory ingress does not exist, E7's assessment is open, and
several mechanism questions remain undecided. See Important I-2. A prominent
document-level supersession/adoption banner plus qualification or removal of
false present-tense statements is the minimum safe demotion; archival is not
required by this review.

The later archival decision should also classify this condensation design and
its review with the registration-FTR bundle; omission from the provisional
table is non-blocking.

== 11. Slice decomposition and review cadence

The intended scale is reasonable: semantic contract; technical model;
maintainer/evolution guidance; interface alignment; navigation/consistency;
fresh-context review. Dependencies A+B, then C+D+navigation, are coherent.

Required corrections are bounded:

* Slice B must actually include category B and the missing controlled-role
  lifecycle.
* Navigation/consistency duties must become concrete rather than duplicate B/D.
* Comment/docstring work must be assigned explicitly or omitted.

The proposed cadence is otherwise sufficient. A+B introduces the high-risk
normative content and deserves its own bounded independent gate. The final
C+D+navigation review, after permanent docs are complete and incorporating a
genuinely isolated comprehension test, can satisfy the registration FTR's
independent-documentation-review gate. A full adversarial review after every
documentation commit is not required.

== 12. Fresh-agent comprehension test

The question set covers payload language, ingress, family-local validity,
execution authority, description activation, plugins, resources, layering,
and non-guarantees. It should add one direct question about the current closed
controlled-role set and what happens to roles after an uncertified return;
otherwise Blocking B-2 can pass unnoticed.

Question 4 is not a valid canary. It supplies `Certified Invocation Stability`
to the fresh agent and asks the agent to explain why the term is not accepted.
That tests compliance with design-specific prompt context, not discovery from
permanent docs, and creates pressure to mention the term permanently so the
question is answerable. See Important I-4. Ask the structural question without
the phrase; separately grep/review permanent docs to ensure the unsupported
name was not promoted.

The isolation mechanism is otherwise sound but should be operationalized
literally: start a new non-forked context with no inherited design/review
transcript; identify only Semantic Model, Technical Model, Developer Guide,
`interfaces_and_gates.adoc`, the ADR index/active ADRs, and current source as
allowed authoritative inputs; explicitly prohibit opening historical
Trusted-Ingress FTR/review/design artifacts; require source citations for each
answer; and record failures as documentation gaps, not permission to consult
history. The final reviewer may consume the fresh agent's cited result, but the
comprehension agent itself must not be the design author/reviewer context.

== 14. Findings

=== Blocking B-1 -- Slice B omits the entire ingress-responsibility category

*Observation:* The source-to-target matrix assigns B1--B6 to the Technical
Model (`architectural_layers.adoc`), but Slice B lists only C, D, E, F, and G
and explicitly says categories A/B are Slice A's job. Slice A lists only
A1--A8 and forbids changes outside its Semantic Model subsection.

*Evidence:* Design lines 617--629 assign B to the Technical Model; lines
922--930 define Slice A as A1--A8; lines 935--946 define Slice B as C--G and
exclude A/B. Current `architectural_layers.adoc` still says no mandatory
ingress owner exists.

*Risk:* A design implemented exactly as sliced would still not tell a fresh
maintainer where payload trust is established/re-established, how E1--E3
relate, why `run_pipeline` differs, or why family-local validation remains.
Fresh questions 1--3 would depend on history or stale text. This is a major
accepted responsibility with no implementation slice.

*Required correction:* Put B1--B6 in Slice B's Technical Model changes and
evidence/review gate; remove the contradictory statement that B belongs to
Slice A. No runtime change or new architecture is needed.

=== Blocking B-2 -- The 41-item inventory omits the controlled execution-state lifecycle

*Observation:* The parent FTR requires the Technical Model to own controlled
roles, exact transitions, closed composition, and ordinary re-establishment.
The design's C rows cover immutable binding, identity insufficiency, macro
wiring, reachability, and certificate fields, but never state the current
closed controlled-role set or its lifecycle.

*Evidence:* Accepted FTR sections 2, 7, 10, 12, 17, and 20 distinguish
Ingress-Conformant Domain Payload from Conformant Framework Execution State;
name FormulaSpec cell Intent, `GroupedMatrix`, and artifact-manifest roles;
forbid implicit nesting; define the one formula-in-grouped composition and
disjoint products; distinguish optional preserving certificates from required
controlled transitions; end all roles on uncertified return; reject
non-ordinary roles during ordinary re-establishment; and authorize/terminate
roles at exact exits. None is a canonical row or fresh-test question.

*Risk:* A maintainer could understand certificate immutability yet still not
understand what the certificate/transition authorizes, where non-Scalar state
may exist, how roles compose, or why an uncertified return cannot preserve a
role by identity. That fails the central E4/E5 architecture-comprehension goal.

*Required correction:* Add the smallest set of explicit execution-state
invariants covering (1) ordinary state versus controlled execution state,
(2) the current closed roles and exact composition rule, (3) certificate
versus controlled-transition authority, (4) uncertified-return role
termination plus ordinary re-establishment, and (5) exact terminal/sink exits.
Place them in Slice B and add one fresh-agent question. This is condensation of
accepted authority, not E1--E7 redesign.

=== Important I-1 -- The proposed Semantic owner still disclaims authority and overlaps the Technical owner

*Observation:* The Semantic Model entry point says it is a draft scaffold and
not authoritative, while Slice A forbids touching that entry point. At the
same time, `internal_value_model.adoc` calls itself normative for the accepted
scalar vocabulary.

*Risk:* The new subsection cannot be an unambiguous canonical owner, and the
same six categories can appear to have two normative primary homes.

*Required correction:* Let Slice A make the smallest entry-point status/
orientation edit that marks the new subsection as accepted current authority
without stabilizing unrelated draft chapters. State explicitly that Semantic
Model owns category meaning/positive language while `internal_value_model`
owns carrier variants/classifier mechanics and supplies only a linked summary
of meaning.

=== Important I-2 -- Active permanent/source alternatives remain false or dangerously plausible

*Observation:* The design limits stale corrections to two
`internal_value_model` locations and one interface sentence, and proposes only
forward pointers in the active ch04 concept. It omits stale architectural-layer
and glossary text and stale source docstrings that the fresh test is allowed
to read.

*Risk:* A fresh maintainer can reach mutually incompatible current answers
without touching historical backlog: Phase E complete versus unstarted; ingress
wired versus absent; E7 accepted versus open; deep immutable construction
versus mutable nested configuration. A pointer beside false present-tense prose
does not reliably demote the alternative.

*Required correction:* Expand the documentation-only consistency scope to the
specific current contradictions listed in section 13. Give the ch04 concept a
prominent document-level historical/supersession banner and qualify/remove
false present-tense current claims while preserving historical reasoning. Allow
comment/docstring-only source corrections where current source contradicts the
accepted architecture; prohibit runtime behavior edits.

=== Important I-3 -- H3 understates the accepted composite-extension contract

*Observation:* H3 says only that a new composite needs an explicit schema/
codec. Accepted authority requires a named bounded composite, finite depth/
cardinality/resource limits, scalar-leaf and Missing rules, explicit carrier
and ownership/copying, operator-policy capability, safe diagnostics,
DataFrame/pandas behavior, and codecs/representations for every claimed
external surface.

*Risk:* A maintainer could follow the permanent guide and introduce an
unbounded or alias-unsafe composite with one codec while believing the Trusted-
Ingress extension rule was satisfied.

*Required correction:* Expand H3/Slice C's checklist to the accepted bounded-
composite obligations. Keep it concise and link to the Technical Model; do not
design a new composite.

=== Important I-4 -- Fresh-agent question 4 leaks and incentivizes unsupported terminology

*Observation:* The test prompt itself supplies `Certified Invocation
Stability` and asks the fresh agent to explain why it is not accepted.

*Risk:* The test measures prompt leakage rather than independent discovery and
encourages permanent docs to mention a term solely to make the test answerable.
That is the exact terminology-promotion failure the design says it avoids.

*Required correction:* Ask only for the structural immutability/execution-
snapshot property and why config/certificate appearance is insufficient.
Check absence/non-promotion of the phrase separately in the final documentation
review.

=== Important I-5 -- Navigation is not an executable slice

*Observation:* Slice C's proposed new Developer Guide file is not registered in
`ch06_code_conventions/_chapter.adoc`. Slice E repeats B/D pointer edits but
does not own includes, glossary/current-term updates, model entry-point
orientation, or a stale-reference scan.

*Risk:* Correct prose may be absent from rendered entry points or difficult to
discover, and stale glossary/entry-point answers may outrank it in normal
navigation. Correct-but-undiscoverable documentation fails the parent FTR's
human-readability criterion.

*Required correction:* Make navigation/consistency concrete in Slice E or
fold exact include/glossary/entry-point/stale-scan duties into A--D and remove
Slice E. Preserve the current bounded review cadence.

=== Minor M-1 -- Three LangSec rows need narrowing or removal

See section 9. Correct `Shotgun Parsing` to classification/admission; narrow or
remove `Differing Interpretations`; remove `Overloaded Fields` unless tied to a
specific accepted field contract. Do not invent support for a weak mapping.

=== Minor M-2 -- Proposed new local comments are unowned and mostly duplicate existing explanation

The E4 construction invariant, E7 fail-closed classification, exact-root/
checksum policy, and ingress ordering already have substantial local comments
or docstrings. The design assigns no slice to source-comment edits and would
risk adding more FTR-shaped prose. Prefer correcting stale comments identified
in I-2; add a new one-line `why` comment only after showing the current code
lacks that mechanism-local reason.

=== Minor M-3 -- D6 cites provisional history instead of accepted authority

D6 is correct, but its row cites the provisional ch04 concept. Cite the
independently accepted Dotted-Extension architecture assessment and accepted
E6/E7 surface contracts instead. Keeping the Dotted-Extension workstream active
is correct.

Finding count: *2 Blocking, 5 Important, 3 Minor*.

== 15. Verdict

*B. CHANGES REQUIRED.*

The durable ownership model, the selected Semantic/Technical/Developer/
interface layers, the threat-model synthesis, the A7 explanatory direction,
the historical-only classification, the conservative Dotted-Extension/ADR
retention, and the three-gate review cadence are fundamentally sound. The
design is not ready for implementation because its own slices omit category B,
its invariant inventory omits accepted controlled execution-state authority,
and the proposed consistency/navigation work would leave active contradictory
authorities and a contaminated fresh-agent test.

Smallest correction set:

. add category B and the bounded controlled-role lifecycle to Slice B and its
  fresh test;
. resolve the Semantic Model authority/split at the entry point;
. make the current-doc/source consistency and ch04 demotion scope complete;
. restore the full accepted bounded-composite rule in H3;
. remove the unsupported term from the fresh-agent prompt; and
. make Slice E concrete navigation/consistency work or fold it into A--D.

The Minor LangSec, local-comment, and D6-citation corrections can be made in
the same documentation-only design pass without reopening architecture.

Lifecycle cleanup check: this is a design review with changes required, not a
green workstream-completion review. The registration FTR remains active;
`_ftrs_open.adoc`, Project Memory, permanent docs, and historical locations
