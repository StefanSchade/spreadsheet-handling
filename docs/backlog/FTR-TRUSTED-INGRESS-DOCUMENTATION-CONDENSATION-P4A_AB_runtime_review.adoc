== 2. Runtime counterexample and closure

=== Independent reproduction of the B-1 premise

A standalone script built an authentic bound step through
`build_steps_from_config`/`resolve_trusted_call` (not a hand-built
certificate), reproducing the exact scenario the follow-up review used: a
mutable `_MutableFill`-style object as `contract_grouped_xref`'s `fill_value`.

* Applying the exact pre-`4dabbed` `_classify_contract` body (reconstructed
  from `git show 4dabbed`'s removed/added lines, run against the *same*
  authentic `call.kwargs`) certified the configuration
  (`GroupedProducerCertificate(...)`), confirming the object identity was
  retained by reference in the frozen binding.
* Mutating the caller-held object after that certification and then invoking
  the *same real bound step* caused the mutated object to appear, by
  identity, in the produced `GroupedMatrix`'s missing cell -- an
  independently reproduced confirmation of the exact defect the follow-up
  review found.
* Running the *current* `classify_grouped_producer_step` against the
  identical authentic call returned
  `Uncertified(reason="unsupported_configuration_value", detail="fill_value")`.

*Verdict: the runtime counterexample is genuinely closed for the exact
reported configuration, independently of the new regression test.*

=== Correction review

`_unsupported_grouped_option` (`grouped_matrix.py:256`) is called from both
`_classify_contract` (with `scalar_only={"fill_value"}`, after the existing
`dense_axes` early-reject) and `_classify_reconstruct` (no scalar-only keys).
It iterates every *present* config key (already filtered to the classifier's
own known-keys vocabulary by `only_known_keys`) and requires each value to be
either `snapshot_scalar`-representable (or literally `None`, correctly
distinguishing "absent" from "unsupported" per `snapshot_scalar`'s own
documented contract) or, for non-scalar-only keys, `snapshot_string_sequence`-
representable. Both helpers use exact-type checks (`type(value) in
_SCALAR_TYPES`, exact `str`/`list`/`tuple` with exact-`str` elements), so
subclass tricks do not bypass the gate, and `snapshot_string_sequence`
returns an owned new tuple, disconnected from any caller-held list.

This is a generic, exhaustive representation-closure check applied uniformly
to every option actually present, not a per-key allowlist requiring
individual maintenance -- a structurally stronger guarantee than hand-picking
which sibling keys to re-check. `fill_value` is correctly scalar-only
(`contract_xref` writes it directly into missing cells; the family's `Any`
type hint permits no closed non-scalar representation the classifier could
safely retain). `dense_axes` remains handled by the pre-existing, unchanged
early-reject (always `Uncertified` when supplied) and is not affected by
ordering with the new check. The helper reports only the offending option
key in `detail`, never a `repr()`/introspection of the rejected object, and
performs representation checking only -- it does not reinterpret or validate
grouped-XRef semantics itself, matching its own docstring's stated scope.

*Verdict: the correction achieves the accepted E4 property for `contract_
grouped_xref` and `reconstruct_grouped_matrix` -- see finding B-2 in
section 3 for the one producer it does not cover.*

=== `_EXPAND_KNOWN_KEYS` (adjacent, same module, same FTR, NOT touched by `4dabbed`) -- Blocking B-2

The review was directed not to broaden into a repository-wide E4 audit
"unless a concrete adjacent same-class defect is found" (task section 4). One
was found, in the same file, the same producer/consumer family, and the same
live managed-execution call path.

`classify_expand_grouped_step` (`grouped_matrix.py:421`) calls
`only_known_keys(config, known=_EXPAND_KNOWN_KEYS)` but, unlike the two
producers `4dabbed` fixed, does *not* call `_unsupported_grouped_option`. It
only explicitly snapshots `matrix`, `output`, `source_frame`, `value`,
`drop_source`, and `base_relation`. The remaining eight known keys --
`row_keys`, `key_column`, `label_columns`, `column_key`, `value_columns`,
`order_policy`, `order_columns`, `xref_config_id` -- are accepted into
`ExpandGroupedCertificate`'s *governing* configuration with no shape check at
all: any object, mutable or not, is accepted.

Independent reproduction (`build_steps_from_config` -> authentic
`BoundFramesTargetCall` -> `classify_expand_grouped_step`, not a hand-built
certificate) confirmed the bug is live:

[source,text]
----
label_columns = MutableNames("group")   # a caller's own mutable custom iterable
step = build_steps_from_config([{"step": "expand_grouped_xref", ...,
                                  "label_columns": label_columns}])[0]
classify_expand_grouped_step(step)
-> ExpandGroupedCertificate(matrix='grouped', output='restored', ...)
----

`label_columns` feeds `expand_grouped_xref`'s `_build_intent(...,
label_columns=label_columns, ...)`, the same axis-mapping intent construction
whose mutation the already-accepted regression test
(`test_mutable_iterable_grouped_option_is_also_uncertified`) proved changes
role-relevant execution on the *forward* producer side. `classify_
expand_grouped_step` is not an inert accounting helper: `application/
managed_pipeline.py:297` calls it directly in the live E5 macro
controlled-role classification path, exactly parallel to
`classify_grouped_producer_step` at line 293 of the same file.

This is the same defect class as B-1 (a caller-mutable by-reference option
retained in a certified role's governing configuration, live in the managed
pipeline), in the same module, discovered by the same kind of authentic-
binding probe the task required. It survived `4dabbed` only because that
correction's scope was the two producer classifiers, not the reverse
transition's classifier.

*The smallest correction*: add the same
`unsupported = _unsupported_grouped_option(config)` / `if unsupported is not
None: return Uncertified(...)` gate to `classify_expand_grouped_step`,
mirroring `_classify_reconstruct`'s call (no key in `_EXPAND_KNOWN_KEYS`
plays `fill_value`'s content-injection role, so no `scalar_only` set is
needed). No other `_EXPAND_KNOWN_KEYS` redesign, and no change to
`ExpandGroupedCertificate`'s fields, is implied.

*This finding blocks acceptance on its own merits, independent of the
architecture-guard finding in section 8.*

=== A vs. B

Only the one raw-text assertion fails; the same test's other assertions
(`"description_authorization" not in signature.parameters`,
`"LessTrustedDescriptionAuthorization" not in source`) pass, and the sibling
`test_only_expected_runtime_modules_import_e7_authorization` test (an
AST-precise `ImportFrom` check) does not list `orchestrator.py` among E7
importers. `orchestrator.py` has no import of `description_authorization`,
no added parameter, and no policy logic -- confirmed by direct reading
(`application/orchestrator.py:102-155`).

The accepted normative rule (`architectural_layers.adoc` ~line 769,
unchanged by this review's commits) states the orchestrator "did not gain a
raw step-description surface, a policy parameter, an import responsibility,
or a provenance-inference role from description authorization" -- a
responsibility/coupling test, not a textual-mention prohibition. The single
offending sentence (`orchestrator.py:148-150`) is exactly the kind of
explanatory cross-reference F1-F3 in the original A+B review praised: it
names the parameter (`pipeline.build`'s `description_authorization`) only to
point the reader to where authorization is actually owned, and disclaims
that `orchestrate` performs it. Repo convention for this style of guard is
mixed: some guards use AST-precise import/call detection (`test_fk_helper_
primitives_consume_policy.py`'s `ImportFrom`-based checks); a few use blunt
`inspect.getsource()` substring checks, but those check call-site-shaped
tokens (`"BoundStep("`, `"orchestrate("` with parentheses, in `test_schema_
maintenance_private_step.py`) or genuinely forbidden imports/constants
(`"FK_PATTERN"`), not a plain identifier appearing only inside a
cross-reference explaining ownership elsewhere. No architecture guard in
this repository is documented as deliberately treating docstring prose as
equivalent to code coupling for this specific rule.

*Conclusion: B -- guard false positive as applied to this docstring.* The
actual architectural rule (no raw step-description surface / policy
parameter / import responsibility / provenance-inference role) is not
violated; the guard's literal substring check does not distinguish
executable coupling from an accurate documentation cross-reference.

=== Acceptance consequence

The task's acceptance rule requires the failure to be *both* outside A+B
scope *and* truly unrelated to current accepted documentation/runtime to be
excused, and explicitly rejects "the latest correction did not introduce it"
as sufficient by itself. `44c24a1` is one of the three original A+B
commits -- the failure is *inside* A+B scope regardless of the false-positive
conclusion above. This guard failure therefore blocks acceptance on its own,
independent of the B-2 finding in section 3.

*The smallest correction* is a docstring reword in `orchestrator.py:148-150`
that keeps the identical architectural explanation without spelling the
literal token `description_authorization` (for example, referring to "the
pipeline builder's own less-trusted-description authorization boundary,
`pipeline.build.build_steps_from_config`'s dedicated parameter" without using
double-backtick markup around the exact identifier). This review does not
propose loosening the guard to strip docstrings; no existing repository
convention establishes that as the intended behavior for this specific test,
and the guard has correctly caught every other case it was written for.
