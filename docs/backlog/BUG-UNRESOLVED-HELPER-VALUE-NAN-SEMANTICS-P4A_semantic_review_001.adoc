==== Q1 -- Authority: source FK authoritative, helper value derived

*Result: confirmed, no counter-example found.*

Read `domain/transformations/fk_helpers/drop.py`, `provenance.py`,
`policy.py`, and `domain/workbook_views.py` directly. Every consumer that
identifies or removes a helper column does so by *name/declared provenance*
(`_meta.derived.sheets.*.helper_columns` or the v2 relation list), never by
inspecting the helper cell's stored value. `check_helper_values`
(`domain/validations/fk_helpers.py:131`) is the one consumer that does read
the helper cell's value, and it does so specifically to detect *disagreement*
with a freshly computed target lookup (`Finding(category="value_mismatch")`)
-- a design that presupposes the helper cell is not trusted as ground truth,
not one that treats it as authoritative. No manual-edit path, re-enrichment
path, or persistence path was found that promotes the helper cell to
authoritative status. `docs/technical_model/ch04_concepts/fk_helper_metadata.adoc`
("First conservative policy") independently and explicitly documents this as
pre-existing, accepted contract, not something invented by this decision.

No maintained consumer relies on helper-cell value as authoritative state.
Not Important; no finding.

==== Q2 -- Reconstructability after real roundtrip

*Result: confirmed empirically, independently reproduced on both backends
(see Method).*

The source FK column round-trips unchanged through both XLSX and ODS (this
was already established fact from Implementation slice 1 and Review 001,
re-confirmed here). `check_unresolvable_fks`
(`domain/validations/fk_helpers.py:196`) computes
`missing = {v for v in fk_series ... if _norm(v) not in target_ids}` --
purely from the reimported source column and a freshly rebuilt target-id
set, with zero reference to the helper column. The independent probe above
confirms this holds after a *real* file write/read cycle, not merely
in-memory, on both backends.

Consistent with the task's own framing: a pipeline that reimports only the
FK-bearing frame and never loads the target frame cannot check any
cross-frame reference. That is a general property of cross-frame
validation and is correctly not treated as a defect of this BUG's
contract.

No maintained lifecycle loses the source FK or target identity needed for
the distinction. Not Important; no finding.

No finding.

==== Q4 -- Option A (distinct helper-cell carrier): rejection

*Result: rejection is justified, not merely on complexity grounds.*

Applying the task's own bar -- reject only if Option A offers no concrete
correctness property Option B lacks -- the BUG's reasoning survives: since
Q1/Q2 independently confirm the semantic information is *already* fully
recoverable from the source reference after a real roundtrip, a distinct
helper-cell sentinel would duplicate information no maintained consumer
needs duplicated. Concrete costs are identified, not asserted: a reserved
sentinel is itself an ordinary string that can collide with real domain
data (lower probability than `""`/`"nan"`, correctly not claimed as zero);
it would leak into canonical JSON on any retained-helper path as an
unexplained token to any consumer unaware of the convention; and it would
need write/read plumbing in both renderers plus survival against
spreadsheet-app autocorrect, for a property nothing currently needs. The
spreadsheet-error-token sub-option is independently correctly rejected: it
is not producible in `values` mode at all (no maintained writer emits
error tokens outside real formula evaluation), so it cannot even be a
candidate for the case this BUG covers. No concrete correctness property is
identified that Option A provides and Option B lacks.

No finding.

* *Cleanup behavior supports the conclusion:* `apply_derived_column_policy:
  drop` removes the ambiguity from canonical persistence entirely on the

==== Q6 -- Option C (no first-class internal unresolved type)

*Result: confirmed; no premature typing.*

Traced the actual control flow: `apply_fk_helpers`'s per-row loop
(`core/fk.py:327-352`) knows hit-vs-miss for exactly the one `dict.get`
call where it matters and does not persist that fact anywhere.
`check_unresolvable_fks` and `check_helper_values` each independently
*recompute* resolution state from two DataFrames on every call; no stored
intermediate value is passed between `apply_fk_helpers` and either checker.
No current consumer needs a named, persisted unresolved-state value: it
would have nowhere correct to live per the BUG's own reasoning (not the
helper column -- Option A rejected; not the source FK column, which must
stay a plain domain value for joins/display/wire format). The BUG does not
cite hypothetical future Internal Value Model work as evidence for creating
a type now -- confirmed by direct re-read of the "Option C" and
"Relationship to future Internal Value Model work" subsections, which state
the opposite: this decision does not manufacture a demonstrated need for
Phase D's type model.

No finding.

==== Q7 -- Successful-hit missing payload: boundary held

*Result: correctly kept separate, not decided by this contract.*

Read `io_backends/ods/odf_renderer.py:562-563` directly: the NaN-blind
`if value in (None, ""):` emptiness check is still present, unmodified,
exactly as the BUG describes. A genuine `numpy.nan` *stored* target payload
(reached only via direct Frame construction, not the JSON loader, which
already coerces `null` to `""` on load) is a dictionary *hit* in
`apply_fk_helpers`, returned verbatim, and is therefore not touched by this
slice's `dict.get(..., "")` miss-default. This is independently corroborated
by the maintained, passing
`TestMissingLabelField::test_missing_label_field_results_in_none_helper`
(`tests/unit/domain/transformations/test_fk_edge_cases.py:175`, re-read and
confirmed still asserts `pd.isna(...)` for that case). `check_unresolvable_fks`
correctly does not flag such a row (the key does resolve); `check_helper_values`
correctly does not flag it either (both sides of its comparison normalize
a missing carrier to `None` via its own `pd.isna`-based `_norm`). The
recommended contract does not normalize or decide this separate, narrower,
already-known ODS-renderer defect, and correctly declines to pull it into
this BUG's scope.

No finding on this BUG's own contract. The residual ODS-renderer gap
remains open as its own separate, narrower, not-yet-filed concern (see
Minor finding SEM-REVIEW-F2, recorded for traceability only -- not a
defect in *this* decision).

==== Q8 -- Current xfail disposition

*Result: disposition recommendation (retire-and-replace) is correct.*

`test_unresolved_helper_value_distinguishable_from_legitimate_empty_string`
(`tests/roundtrip/test_pathological_cell_contracts.py:275`) asserts helper-
cell inequality between an unresolved row and a resolved-empty row. Given
Q1/Q2/Q5's confirmed conclusion -- the helper cell is not the authority and
the distinction survives at the source-FK-plus-resolution level -- this
assertion targets the wrong invariant: it would only pass by implementing
the rejected Option A. The proposed replacement invariant (after a real
XLSX/ODS roundtrip, an unresolved reference and a resolved-empty value
remain distinguishable via the reimported source FK column plus a
target-frame lookup, not via helper-cell comparison) is exactly what this
review's own independent probe demonstrates holds, on both backends, with
real files. Retire-and-replace is correctly preferred over bare retirement,
since no currently maintained test proves source-plus-resolution
distinguishability survives a real roundtrip -- removing the xfail without
a replacement would be a genuine coverage regression.

No finding; recommendation confirmed sound. (Per the task's non-goals, no
test file was modified by this review.)
