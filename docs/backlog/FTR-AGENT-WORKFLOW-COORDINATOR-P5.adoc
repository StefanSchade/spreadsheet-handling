==== 1. Purpose and design inputs

V1 addresses the repeated human orchestration around bounded engineering-agent
work: preparing tasks, invoking roles, establishing actual Git truth, collecting
deterministic evidence, validating structured results, selecting only permitted
next actions, coordinating reviews/corrections, stopping for human semantic
authority, and preserving ex-post observability across autonomous Hops.

The empirical and architectural reasoning is not repeated here. Inputs are:

* `docs/warm_storage/concepts/agent_workflow_coordinator_concept_2026-08-25.adoc`
  -- non-binding evidence/hypothesis;
* `docs/warm_storage/concepts/agent_workflow_coordinator_proposed_architecture_2026-08-25.adoc`
  -- accepted formal architecture design projected into this contract;
* `docs/warm_storage/global_reviews/agent_workflow_coordinator_readiness_review_2026-08-25.adoc`
  -- finding authority for the bounded correction, not implementation authority.

If this FTR conflicts with the proposed design, readiness review must record the
conflict; implementation must not silently choose a third contract.

==== 2. V1 scope and planned placement

===== 2.1 Required V1 capability

V1 is a local, repository-native, Git-centered, policy-bounded coordinator with:

* one coordinator process, repository, worktree, active Run, and agent
  invocation at a time;
* WorkItem semantic input plus Run, Hop, and Finding operational records;
* finite validated workflow profiles and deterministic route reduction;
* one configured agent adapter plus an optional, policy-bounded supervisor role;
* Git reconciliation, fixed trusted evidence callables, structured results,
  finding convergence, autonomy budget, checkpoints, interruption/resume, and
  explicit human authority stops;
* a first routine profile, a non-production non-DMC bug-workflow fixture that
  falsifies complex-profile overfit, and, only in later Slice 5F, a DMC-shaped
  profile without DMC vocabulary in generic mechanics.

Planned implementation placement follows the proposed architecture:

* repository-local executable mechanics: `scripts/workflow_coordinator/`;
* versioned profiles, repository policy, and prompt components:
  `docs/ai_info/workflows/`;
* focused unit/integration/architecture tests under the existing `tests/`
  topology.

No coordinator code belongs under `src/spreadsheet_handling/`; it is developer
tooling, not product/runtime API. No new dependency is justified by V1 unless
the readiness review or a separately reviewed slice demonstrates necessity.

===== 2.2 Deferred capabilities

Deferred without V1 scaffolding: coordinator-created or mixed semantic commit
ownership; mandatory trailers/hooks; multiple agent providers/models and
provider-diversity policy; extraction into `tools/` or a package; automated
warm/cold run archival; quantitative trust scoring; parallel worktrees/runs;
remote/distributed execution; SonarQube implementation; semantic/vector
retrieval; web UI; autonomous/preauthorized child Runs; and `continuing`
conversation context unless a separately reviewed real adapter declares and
proves it as an optional capability.

===== 2.3 Explicit non-goals

* No workflow DSL, executable profile code, graph engine, database, event store,
  plugin manager, DI framework, queue, or distributed fault tolerance.
* No universal agent abstraction, general sandbox/security product, automatic
  workflow invention, automatic semantic acceptance, or Project Memory run
  store.
* No Domain, FK/Lookup, Trusted-Ingress, public CLI/YAML, spreadsheet, demo,
  release, or consumer behavior change.
* No real Run/Hop manifests, Git hooks, enforced trailers, live workflow agent,
  Sonar service, vector index, or external infrastructure in this drafting task.

===== 2.4 FTR sizing preflight

This is a justified FTR because it introduces architectural developer tooling
with acceptance contracts. It does not touch spreadsheet roundtrip, `_meta`,
Domain registries, XLSX/ODS parity, or current public product surfaces. The
workflow profile schema is an internal coordinator input, not the existing
public pipeline YAML surface. The five slices separate the state/reducer,
repository transaction, adapter, live invocation, and multi-Hop risks.

==== 4. Workflow profile, route, and authority contracts

===== 4.1 Profile data and route effects

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-PROFILE-01
|Human-authored WorkItem specifications, profiles, and structured repository
policy shall use strict validated YAML; natural-language prompt components are
versioned text referenced by that YAML. Machine-written transient Run state
shall use JSON. Unknown fields fail closed, and no equivalent second
human-authored serialization is provided. Phase keys are opaque to generic code.

|WFC-PROFILE-02
|Each phase shall declare role/prompt policy, explicit role/modifier and
repository-policy component selections, `durable_artifact` policy, permitted
route keys, evidence requirements, authorized scope/actions, human gates, and a
review descriptor when the phase is a review.

|WFC-PROFILE-03
|Profiles shall express only five route effects: `goto`, `complete`,
`await_human`, `suspend_for_prerequisite`, and `stop`.

|WFC-PROFILE-04
|`goto` selects one declared target phase; `complete` ends the Run without
claiming authority beyond profile policy; `await_human` records a concrete
question; `suspend_for_prerequisite` records an explicitly human-authorized child
and clears stale next action; `stop` ends autonomous progress without claiming
completion.

|WFC-PROFILE-05
|Profile data shall not contain executable code, arbitrary conditions, computed
graphs, fan-out, or user-defined loops. A loop is a finite declared route edge.

|WFC-PROFILE-06
|A profile or pinned policy mutation during a Run shall be an anomaly requiring
stop and common reconcile/resume; an agent result cannot authorize its own
profile change.
|===

===== 4.2 Routing precedence and authority

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-AUTH-01
|Routing precedence shall be: mechanical preemption, deterministic policy
reduction, optional declared supervisor judgment, then human semantic authority.

|WFC-AUTH-02
|Mechanical preemption shall stop on malformed state/result, Git anomaly,
policy mutation, budget prohibition, required evidence-provider error,
`requires_human=true`, or any non-null unresolved escalation; no supervisor may
override it. Human/escalation preemption applies regardless of outcome or valid
requested route, including `outcome=completed` with `goto`/`complete`.

|WFC-AUTH-03
|Only after mechanical preemption clears, deterministic reduction shall use the
validated routing envelope, current review authority/blocking policy, Finding
state, evidence state, budget, and current finite route table. It shall route
automatically only when policy determines a single permitted result.

|WFC-AUTH-04
|A supervisor may be invoked only at a profile-declared judgment point, shall be
read-only, consumes a Hop, receives one bounded question plus finite route keys
and compact history, and may classify/recommend, choose only one already
authorized key, or request a human.

|WFC-AUTH-05
|A supervisor shall not invent routes, mutate profile/policy, enlarge scope,
close or reopen a Finding, downgrade blocking status, accept a residual,
supersede/reclassify a Finding as an authoritative disposition, create semantic
ownership, approve public/API choices, activate any child/work item, raise review
authority, or claim project/Project-Memory decisions. Profile delegation cannot
grant these powers; the supervisor may only route to the declared gate/human.

|WFC-AUTH-06
|Human escalation shall be mandatory for new/conflicting semantic ownership or
authority, plausible public/API/compatibility choices, trust/security redesign,
capability deletion, workflow/profile redesign, unauthorized scope, unapproved
nested work, roadmap/Project Memory governance, and any undelegated decision. AI
may discover, propose, and escalate these questions, but cannot self-authorize
their disposition.
|===

==== 5. Review, Finding, and convergence contracts

===== 5.1 Review dimensions and anti-ceremony rule

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-REVIEW-01
|Every review phase shall independently declare breadth/search scope, authority,
and context policy. Breadth selects the falsification surface and grants no
authority.

|WFC-REVIEW-02
|Review authority is `advisory` or `gate`. Advisory results may add evidence or
Findings but cannot advance/complete. A gate authorizes only its declared route
under its blocking policy.

|WFC-REVIEW-03
|`fresh` context shall not reuse author conversation history and is the required
V1 baseline. `continuing` is not a V1 engine guarantee; a profile may require it
only after a separately reviewed adapter declares/proves bounded-thread support.
Context does not establish independence or authority by itself.

|WFC-REVIEW-04
|A review stage shall exist only where the profile states a distinct epistemic,
falsification, risk, or authority purpose plus trigger, blocking policy, and
exit. Availability shall never imply mandatory execution.

|WFC-REVIEW-05
|After broad review establishes a Finding set, correction/delta review normally
checks known Findings and direct regressions. New material evidence may escape
the bound; unrelated new minors shall not automatically reopen the whole work.
A resolved Finding may reopen only through WFC-FIND-03 authority and new material
evidence.
|===

===== 5.2 Finding lifecycle and convergence

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-FIND-01
|Finding state shall be exactly `open`, `resolved`, `residual`, or `superseded`.
`residual` means genuine and explicitly accepted non-blocking;
`superseded` requires successor/reclassification reference.

|WFC-FIND-02
|Agents may cite an existing ID or propose an unassigned Finding. The
coordinator allocates new IDs and rejects silent invariant/identity rewrites.

|WFC-FIND-03
|Only the current declared gate with the applicable phase/blocking-policy
authority, or human authority, may validate closure, `resolved -> open`
reopening, blocking downgrade, residual acceptance, or
supersession/reclassification. Reopening additionally requires new material
evidence; agent/supervisor reassertion alone does not change authoritative
disposition.

|WFC-FIND-04
|The coordinator shall deterministically expose Finding transitions/reopens,
commit/path and evidence changes, regression state, new material-Finding count,
route repetition, and scope/policy/baseline changes.

|WFC-FIND-05
|Material mechanism change, semantic narrowing, productive progress, goalpost
drift, lack of progress, or wrong owner/workflow are semantic classifications
for delegated supervisor or human judgment. A supervisor classification is only
a routing recommendation and never an authoritative Finding disposition. V1
shall implement no numerical convergence score.

|WFC-FIND-06
|V1 shall permit productive correction beyond three loops, stop non-progressing
loops before budget where judged, and route semantic reclassification out of
local correction. No fixed low `max_review_iterations` may be the primary rule.
|===

==== 6. Bounded autonomy and Git contracts

===== 6.1 Autonomy budget

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-AUTO-01
|Every Run shall carry positive `max_autonomous_hops=N`; architecture shall
support empirical N=1 -> 2 -> 5 -> 10 changes without model/schema redesign.

|WFC-AUTO-02
|Every invocation accepted by the agent adapter consumes one Hop whether it
succeeds, fails, or yields malformed output. Author, reviewer, correction,
re-entry assessor, curator, and supervisor invocations all count. Mechanical
reconcile/resume work does not consume a Hop. After crash recovery, absence of a
dispatch marker proves no Hop consumption; once the atomic dispatch marker
exists, acceptance that cannot be disproved is conservatively charged as one Hop
and never replayed.

|WFC-AUTO-03
|Local failure before adapter/provider acceptance, Git/evidence inspection,
prompt assembly, schema validation, deterministic routing, state/checkpoint
writing, and human actions do not consume Hops. V1 has no hidden retry.

|WFC-AUTO-04
|The coordinator shall stop before the next invocation on early-stop conditions.
At exhaustion it completes safe deterministic post-Hop work, records
`awaiting_human_budget`, renders a checkpoint, and invokes no further agent.

|WFC-AUTO-05
|Resume requires explicit maintainer action, resolved gates, verified current
HEAD/clean state, and a limit not below used Hops. Used Hops never reset within
the Run.
|===

===== 6.2 Git transaction and prospective identity

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-GIT-01
|Every Hop begins at an independently observed Git commit. Before invocation,
the coordinator verifies repository identity, expected ancestry, current HEAD,
and no tracked or non-ignored untracked changes.

|WFC-GIT-02
|After invocation, the coordinator independently observes HEAD/worktree and
computes the actual `base..head` commit range. Agent-claimed commits are hints,
never factual authority.

|WFC-GIT-03
|A successful mutating Hop shall produce 1..n atomic agent-created commits and
end clean before another Hop. Observation-only or failed Hops may have
`base==head`. The coordinator shall not synthesize semantic commits in V1.

|WFC-GIT-04
|The next Hop is prohibited after rewritten/divergent ancestry, HEAD movement
outside the invocation window, forbidden merge commit, dirty tracked/non-ignored
state, out-of-scope path, pinned policy/prompt mutation, commit safety-cap breach,
or unresolved repository/submodule/evidence identity.

|WFC-GIT-05
|Claimed/actual mismatch shall be reported and actual Git used. Mismatch becomes
blocking when coupled to hidden, divergent, out-of-scope, or policy-forbidden
change.

|WFC-GIT-06
|Ignored scratch affects cleanliness only through tracked trusted repository
policy: it may be tolerated in approved roots but must not retain secrets. A
local `.git/info/exclude` entry alone shall not establish the configured
coordinator-state-root invariant. V1 does not promise whole-filesystem
cleanliness.

|WFC-GIT-07

==== 9. Failure, suspension, resume, and trust contracts

===== 9.1 Failure and resume

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-FAIL-01
|Invocation failure or malformed structured result after adapter acceptance
consumes a Hop; coordinator reconciles Git/evidence, records diagnostic, and
stops without hidden retry or inferred route.

|WFC-FAIL-02
|A failed deterministic guard is recorded. A profile-declared failed gate may
route to correction; evidence-provider error or hard invariant stops.

|WFC-FAIL-03

|WFC-FAIL-04

require applicable explicit resume/human authority; it never replays
automatically.

|WFC-FAIL-05
|Budget exhaustion, human stop, or unclassifiable route persists
state/checkpoint and invokes no next agent.

|WFC-FAIL-06
|Every V1 prerequisite activation requires explicit maintainer authority,
creates a separate child Run, and leaves parent `suspended` with
child/suspension HEAD and no stale next action. Autonomous/preauthorized child
creation is deferred.

|WFC-FAIL-07
|Nested return shall enter the same `reconcile_required` mechanism with
`prerequisite_return` provenance, compare current Git/governing inputs/Findings
against the suspension anchor, discard stale next action, and derive currently
valid continuations. Nested work never restores stale next action; no
authoritative rebaseline counter/state machine exists.

only when the current gate/human authority possesses the same explicit operation
authority required for that disposition; `superseded` still requires
`successor_ref`. This creates no new authority. Every lifecycle operation remains
a proposal until the reducer validates it.

Only human authority or the current declared `gate` with the applicable
`finding_authority` may validate closure, `resolved -> open` reopening,
`open -> residual` acceptance/downgrade, or supersession/reclassification;
reopening also requires new material evidence and supersession requires
`successor_ref`. There is no standalone blocking-downgrade operation.
`advisory` review and ordinary work/correction phases may create open Findings
and append evidence but may not perform those disposition operations. Review
outcome or durable-artifact authority grants no additional Finding authority.

A same-state citation, regardless of whether the current phase also possesses
disposition authority, is exactly one of the following:

* an exact no-op: ID, invariant, state, blocking flag, evidence refs, disposition,
  successor ref, and authoritative attribution remain unchanged; or
* an evidence-only mutation: new schema-valid evidence refs accepted under the
  existing evidence-ref contract are appended and only the authoritative
  last-changing-Hop attribution changes.

Such a citation shall reject any attempted change to invariant/identity, state,
blocking semantics, disposition, or successor ref. `successor_ref` may be
introduced or changed only by authorized supersession/reclassification. A
citation of an already-superseded Finding shall restate the authoritative
existing `successor_ref` exactly; omission/null or replacement is neither a
no-op nor evidence-only mutation. Lifecycle change shall use its explicit
authorized operation rather than a same-state citation. These rules shall not
create a shadow status or convergence aggregate.

Run-wide completion invariant:: After Slice 5B, every supported Run reduction,
including `N=1` and profiles with no review descriptor, shall enforce:

----
route effect complete AND any authoritative Finding is open AND blocking
  -> status awaiting_human
  -> stop_reason completion_blocked_by_open_blocking_findings
  -> no applied or substitute route
----

The check occurs after any authorized Finding mutation and applies regardless of
whether the current phase is review, correction, implementation, or another
ordinary phase. It is Run-wide rather than keyed to a review descriptor because
WFC-FIND-01 defines open/blocking as authoritative Run state and WFC-PM-02 does
not permit ordinary completion to erase an unresolved blocker. Resolved,
superseded, and authorized residual/non-blocking Findings do not block.

The only executable Slice-5B review `blocking_policy` value is `blocking_only`.
It means a gate may take a declared non-terminal correction/stop route while open
blockers remain, may perform `open -> residual` only through its declared
Finding authority, and may complete only when the Run-wide invariant is
satisfied. It is not a policy language. An advisory review remains unable to
advance or complete under WFC-REVIEW-02.

Invocation outcome, artifact, Finding, route, and completion are separate
decisions (P5B-C2):: In this section, a non-terminal route is any declared route
effect other than `complete`. The `durable_artifact: required` obligation applies
to every validated result whose outcome remains eligible to reduce a route:
`completed` and `changes_required`. It does not apply to the unsuccessful
terminal outcomes `blocked` and `failed`. The WFC-OUTPUT-02 outcomes retain these
exact meanings:

* `completed`: after ordinary validation, authorized Finding proposals are
  reduced; existing CommitIntent rules apply; a `required` phase shall satisfy
  its artifact obligation before the requested declared route may reduce; and
  `complete` remains subject to the Run-wide blocker invariant.
* `changes_required`: this is a successfully executed review with a non-accepting
  verdict. Authorized Finding proposals are reduced. Only at a current declared
  review gate may CommitIntent be eligible, and then both intended and
  independently observed changed paths shall be a subset of the current phase's
  declared durable review-artifact paths. A `required` phase shall satisfy its
  artifact obligation before any route may reduce. A `changes_required` result
  in a `required` phase that is ineligible for this gate-only artifact
  CommitIntent cannot evade the declaration and fails closed as a
  required-artifact anomaly. The result may take only a declared non-terminal
  route; a `complete` request stops deterministically with
  `changes_required_cannot_complete`. The exception grants no reviewed-payload
  mutation or Finding-disposition authority. Thus a reviewer may disposition an
  existing Finding only when the gate independently declares that exact
  operation; writing or committing a report never closes a blocker.
* `blocked`: CommitIntent is forbidden. After otherwise valid and authorized
  Finding proposals are reduced, no requested autonomous route or `complete`
  applies; the Run stops `awaiting_human` with `result_blocked`. It has no
  required-artifact obligation.
* `failed`: CommitIntent is forbidden and all Finding proposals are discarded.
  No requested route or `complete` applies; a validated, correlated result stops
  `awaiting_human` with `result_failed`. It has no required-artifact obligation.
  Malformed, missing, or uncorrelated output retains the stronger existing
  uncertain-dispatch/reconciliation behavior and is not this outcome.

The runtime `changes_required` path restriction is evaluated only after the
validated result/outcome is known. Pre-dispatch validation may check static
profile, artifact, action, and scope policy but shall not predict an outcome.
The non-DMC acceptance fixture shall give each review gate artifact-only writable
scope; this fixture constraint is not a general preflight ban on wider gate scope
for other outcomes.

Durable artifacts (P5B-C8):: WFC-OUTPUT-04's `required|optional|none` phase declaration
remains authoritative. Slice 5B adds one optional strict schema-v1 WorkItem
`durable_artifacts` mapping from declared phase key to one or more normalized,
unique repository-relative paths when present. The map is WorkItem-owned pinned
input, is validated for every declared phase without route-reachability analysis,
and is projected into the operator plan rather than copied into Run state.

For `required`, the current phase shall have at least one mapped path and a
route-eligible result shall represent every required path in its trusted
CommitIntent and independently observed committed-path validation; no new result
field or `result.evidence_refs` convention is implied. At post-invocation
validation each required path shall exist as a Git-tracked versioned file at the
observed end HEAD and lie in actual committed changes. `optional` permits zero or
more mapped paths without making them a gate. `none` permits none. Every path
shall lie within both WorkItem and phase path authority and any CommitIntent and
actual mutation shall still pass all ordinary Git/scope/action checks. Declaring
a review artifact grants authority only over that artifact surface, not the
reviewed payload.

This is additive schema-v1 evolution, not a migration subsystem. The WorkItem
map and legacy repeated `--durable-artifact` argv form are mutually exclusive and
supplying both rejects deterministically. Legacy argv retains only its accepted
initial-phase/H001 meaning. If the map is absent and any non-initial phase declares
`durable_artifact: required`, canonical preflight rejects before Run creation and
adapter entry; legacy argv cannot satisfy that phase. If the map is absent, the
initial phase is `required`, and any declared route directly targets that initial
phase again, canonical preflight also rejects. This is a static direct-reference
check, not route-graph/reachability analysis.

Trusted evidence (P5B-C4/C7):: WFC-EVID-01..04 remain authoritative and production
remains bound to the fixed trusted in-code registry. Canonical preflight shall
reject before Run creation and adapter entry any evidence name selected by any
phase that is not listed in `RepositoryPolicy.evidence_states` or cannot be
resolved by the active evidence runner supplied for that Run. It validates only
selected names, not every policy-allowed name. Production uses the existing
trusted runner/registry; deterministic acceptance may use only the injected fake
runner described below. Required evidence has three route-bearing states:

* `pass` permits ordinary outcome/Finding/route reduction;
* clean `fail` is a trusted negative observation, never an agent classification;
  only a current gate ReviewDescriptor may name one existing declared `goto`
  route as `failed_evidence_route`; that route replaces the requested route after
  result/Finding-set validation. With no valid declaration, the Run stops
  `awaiting_human` with `required_evidence_failed_without_route` and no route is
  invented; and
* `error`, malformed evidence, an unresolved evidence name, or `not_run` for
  evidence required by the current phase is a mechanical hard stop and never
  follows the failed-evidence route.

`failed_evidence_route` is one additive optional schema-v1 ReviewDescriptor
field; static profile/preflight validation permits it only on a gate review,
requires the named route key to exist in that phase, and requires that route's
effect to be `goto`. It adds no route effect or migration system.

For deterministic Slice-5B acceptance only, composition may inject one local/fake
evidence-runner object with a fixed supported-name configuration. Canonical
preflight and dispatch/execution shall receive that same object/configuration.
Fake evidence names shall be disjoint from production registry names and shall
not imply a production provider can cleanly fail. Supported production entry
always uses the existing registry. No command migration, second production
registry, runtime discovery, selector, or plugin surface is authorized.

Refusal and preemption precedence (P5B-C6):: WFC-AUTH-01 remains controlling. To make
overlapping 5B refusals deterministic, apply this minimum order:

. Existing malformed/uncorrelated/uncertain dispatch, persistence, Git,
  governing-input, policy/profile, required-artifact, and trusted-evidence
  `error` anomalies retain their existing mechanical disposition; a condition
  requiring `reconcile_required` outranks an ordinary `awaiting_human` stop.
  No Finding proposals apply after such a preemption.
. Explicit `requires_human` or unresolved escalation preempts outcome routing.
. A validated `failed` outcome discards its Finding proposal set and receives its
  disposition above.
. For every other validated outcome, `scope_changed` and requested-route
  membership retain their existing deterministic guards before any clean evidence
  `fail` can replace the requested route. An advisory review's forbidden
  `complete` is refused before any later `changes_required_cannot_complete`
  handling. The entire Finding proposal set is then schema/identity/authority-
  validated atomically: one invalid delta rejects the set with no partial
  application.
. A validated `blocked` result with a valid Finding set applies that whole set
  atomically and receives `result_blocked`; it never reaches evidence-failure or
  requested-route reduction.
. For otherwise eligible `completed` or `changes_required`, the valid Finding set
  applies atomically; clean evidence `fail` may then select only the declared
  failed-evidence `goto`.
. Ordinary deterministic route reduction follows. The `changes_required`
  terminal refusal precedes the Run-wide open-blocker refusal; otherwise the
  open-blocker refusal governs `complete`.
. Budget exhaustion produces `awaiting_human_budget` only when the valid route
  would require another agent invocation. A `stop` effect or an already-terminal
  human disposition requires and consumes no further Hop.

Slice 5B adds no supervisor step; human authority remains last.
