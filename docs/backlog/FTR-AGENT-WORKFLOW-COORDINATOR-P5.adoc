==== 1. Purpose and design inputs

V1 addresses the repeated human orchestration around bounded engineering-agent
work: preparing tasks, invoking roles, establishing actual Git truth, collecting
deterministic evidence, validating structured results, selecting only permitted
next actions, coordinating reviews/corrections, stopping for human semantic
authority, and preserving ex-post observability across autonomous Hops.

The empirical and architectural reasoning is not repeated here. Inputs are:

* `docs/warm_storage/concepts/agent_workflow_coordinator_concept_2026-08-25.adoc`
  -- non-binding evidence/hypothesis;
* `docs/warm_storage/concepts/agent_workflow_coordinator_proposed_architecture_2026-08-25.adoc`
  -- accepted formal architecture design projected into this contract;
* `docs/warm_storage/global_reviews/agent_workflow_coordinator_readiness_review_2026-08-25.adoc`
  -- finding authority for the bounded correction, not implementation authority.

If this FTR conflicts with the proposed design, readiness review must record the
conflict; implementation must not silently choose a third contract.

==== 2. V1 scope and planned placement

===== 2.1 Required V1 capability

V1 is a local, repository-native, Git-centered, policy-bounded coordinator with:

* one coordinator process, repository, worktree, active Run, and agent
  invocation at a time;
* WorkItem semantic input plus Run, Hop, and Finding operational records;
* finite validated workflow profiles and deterministic route reduction;
* one configured agent adapter plus an optional, policy-bounded supervisor role;
* Git reconciliation, consumer-policy-owned named evidence commands, structured results,
  finding convergence, autonomy budget, checkpoints, interruption/resume, and
  explicit human authority stops;
* a first routine profile, a non-production non-DMC bug-workflow fixture that
  falsifies complex-profile overfit, and, only in later Slice 5F, a DMC-shaped
  profile without DMC vocabulary in generic mechanics.

Planned implementation placement follows the proposed architecture:

* repository-local executable mechanics: `scripts/workflow_coordinator/`;
* versioned profiles, repository policy, and prompt components:
  `docs/ai_info/workflows/`;
* focused unit/integration/architecture tests under the existing `tests/`
  topology.

No coordinator code belongs under `src/spreadsheet_handling/`; it is developer
tooling, not product/runtime API. No new dependency is justified by V1 unless
the readiness review or a separately reviewed slice demonstrates necessity.

===== 2.2 Deferred capabilities

Deferred without V1 scaffolding: coordinator-created or mixed semantic commit
ownership; mandatory trailers/hooks; multiple agent providers/models and
provider-diversity policy; extraction into `tools/` or a package; automated
warm/cold run archival; quantitative trust scoring; parallel worktrees/runs;
remote/distributed execution; SonarQube implementation; semantic/vector
retrieval; web UI; autonomous/preauthorized child Runs; and `continuing`
conversation context unless a separately reviewed real adapter declares and
proves it as an optional capability.

===== 2.3 Explicit non-goals

* No workflow DSL, executable profile code, graph engine, database, event store,
  plugin manager, DI framework, queue, or distributed fault tolerance.
* No universal agent abstraction, general sandbox/security product, automatic
  workflow invention, automatic semantic acceptance, or Project Memory run
  store.
* No Domain, FK/Lookup, Trusted-Ingress, public CLI/YAML, spreadsheet, demo,
  release, or consumer behavior change.
* No real Run/Hop manifests, Git hooks, enforced trailers, live workflow agent,
  Sonar service, vector index, or external infrastructure in this drafting task.

===== 2.4 FTR sizing preflight

This is a justified FTR because it introduces architectural developer tooling
with acceptance contracts. It does not touch spreadsheet roundtrip, `_meta`,
Domain registries, XLSX/ODS parity, or current public product surfaces. The
workflow profile schema is an internal coordinator input, not the existing
public pipeline YAML surface. The five slices separate the state/reducer,
repository transaction, adapter, live invocation, and multi-Hop risks.

==== 4. Workflow profile, route, and authority contracts

===== 4.1 Profile data and route effects

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-PROFILE-01
|Human-authored WorkItem specifications, profiles, and structured repository
policy shall use strict validated YAML; natural-language prompt components are
versioned text referenced by that YAML. Machine-written transient Run state
shall use JSON. Unknown fields fail closed, and no equivalent second
human-authored serialization is provided. Phase keys are opaque to generic code.

|WFC-PROFILE-02
|Each phase shall declare role/prompt policy, explicit role/modifier and
repository-policy component selections, `durable_artifact` policy, permitted
route keys, evidence requirements, authorized scope/actions, human gates, and a
review descriptor when the phase is a review.

|WFC-PROFILE-03
|Profiles shall express only five route effects: `goto`, `complete`,
`await_human`, `suspend_for_prerequisite`, and `stop`.

|WFC-PROFILE-04
|`goto` selects one declared target phase; `complete` ends the Run without
claiming authority beyond profile policy; `await_human` records a concrete
question; `suspend_for_prerequisite` records an explicitly human-authorized child
and clears stale next action; `stop` ends autonomous progress without claiming
completion.

|WFC-PROFILE-05
|Profile data shall not contain executable code, arbitrary conditions, computed
graphs, fan-out, or user-defined loops. A loop is a finite declared route edge.

|WFC-PROFILE-06
|A profile or pinned policy mutation during a Run shall be an anomaly requiring
stop and common reconcile/resume; an agent result cannot authorize its own
profile change.
|===

===== 4.2 Routing precedence and authority

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-AUTH-01
|Routing precedence shall be: mechanical preemption, deterministic policy
reduction, optional declared supervisor judgment, then human semantic authority.

|WFC-AUTH-02
|Mechanical preemption shall stop on malformed state/result, Git anomaly,
policy mutation, budget prohibition, required evidence-provider error,
`requires_human=true`, or any non-null unresolved escalation; no supervisor may
override it. Human/escalation preemption applies regardless of outcome or valid
requested route, including `outcome=completed` with `goto`/`complete`.

|WFC-AUTH-03
|Only after mechanical preemption clears, deterministic reduction shall use the
validated routing envelope, current review authority/blocking policy, Finding
state, evidence state, budget, and current finite route table. It shall route
automatically only when policy determines a single permitted result.

|WFC-AUTH-04
|A supervisor may be invoked only at a profile-declared judgment point, shall be
read-only, consumes a Hop, receives one bounded question plus finite route keys
and compact history, and may classify/recommend, choose only one already
authorized key, or request a human.

|WFC-AUTH-05
|A supervisor shall not invent routes, mutate profile/policy, enlarge scope,
close or reopen a Finding, downgrade blocking status, accept a residual,
supersede/reclassify a Finding as an authoritative disposition, create semantic
ownership, approve public/API choices, activate any child/work item, raise review
authority, or claim project/Project-Memory decisions. Profile delegation cannot
grant these powers; the supervisor may only route to the declared gate/human.

|WFC-AUTH-06
|Human escalation shall be mandatory for new/conflicting semantic ownership or
authority, plausible public/API/compatibility choices, trust/security redesign,
capability deletion, workflow/profile redesign, unauthorized scope, unapproved
nested work, roadmap/Project Memory governance, and any undelegated decision. AI
may discover, propose, and escalate these questions, but cannot self-authorize
their disposition.
|===

==== 5. Review, Finding, and convergence contracts

===== 5.1 Review dimensions and anti-ceremony rule

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-REVIEW-01
|Every review phase shall independently declare breadth/search scope, authority,
and context policy. Breadth selects the falsification surface and grants no
authority.

|WFC-REVIEW-02
|Review authority is `advisory` or `gate`. Advisory results may add evidence or
Findings but cannot advance/complete. A gate authorizes only its declared route
under its blocking policy.

|WFC-REVIEW-03
|`fresh` context shall not reuse author conversation history and is the required
V1 baseline. `continuing` is not a V1 engine guarantee; a profile may require it
only after a separately reviewed adapter declares/proves bounded-thread support.
Context does not establish independence or authority by itself.

|WFC-REVIEW-04
|A review stage shall exist only where the profile states a distinct epistemic,
falsification, risk, or authority purpose plus trigger, blocking policy, and
exit. Availability shall never imply mandatory execution.

|WFC-REVIEW-05
|After broad review establishes a Finding set, correction/delta review normally
checks known Findings and direct regressions. New material evidence may escape
the bound; unrelated new minors shall not automatically reopen the whole work.
A resolved Finding may reopen only through WFC-FIND-03 authority and new material
evidence.
|===

===== 5.2 Finding lifecycle and convergence

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-FIND-01
|Finding state shall be exactly `open`, `resolved`, `residual`, or `superseded`.
`residual` means genuine and explicitly accepted non-blocking;
`superseded` requires successor/reclassification reference.

|WFC-FIND-02
|Agents may cite an existing ID or propose an unassigned Finding. The
coordinator allocates new IDs and rejects silent invariant/identity rewrites.

|WFC-FIND-03
|Only the current declared gate with the applicable phase/blocking-policy
authority, or human authority, may validate closure, `resolved -> open`
reopening, blocking downgrade, residual acceptance, or
supersession/reclassification. Reopening additionally requires new material
evidence; agent/supervisor reassertion alone does not change authoritative
disposition.

|WFC-FIND-04
|The coordinator shall deterministically expose Finding transitions/reopens,
commit/path and evidence changes, regression state, new material-Finding count,
route repetition, and scope/policy/baseline changes.

|WFC-FIND-05
|Material mechanism change, semantic narrowing, productive progress, goalpost
drift, lack of progress, or wrong owner/workflow are semantic classifications
for delegated supervisor or human judgment. A supervisor classification is only
a routing recommendation and never an authoritative Finding disposition. V1
shall implement no numerical convergence score.

|WFC-FIND-06
|V1 shall permit productive correction beyond three loops, stop non-progressing
loops before budget where judged, and route semantic reclassification out of
local correction. No fixed low `max_review_iterations` may be the primary rule.
|===

==== 6. Bounded autonomy and Git contracts

===== 6.1 Autonomy budget

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-AUTO-01
|Every Run shall carry positive `max_autonomous_hops=N`; architecture shall
support empirical N=1 -> 2 -> 5 -> 10 changes without model/schema redesign.

|WFC-AUTO-02
|Every invocation accepted by the agent adapter consumes one Hop whether it
succeeds, fails, or yields malformed output. Author, reviewer, correction,
re-entry assessor, curator, and supervisor invocations all count. Mechanical
reconcile/resume work does not consume a Hop. After crash recovery, absence of a
dispatch marker proves no Hop consumption; once the atomic dispatch marker
exists, acceptance that cannot be disproved is conservatively charged as one Hop
and never replayed.

|WFC-AUTO-03
|Local failure before adapter/provider acceptance, Git/evidence inspection,
prompt assembly, schema validation, deterministic routing, state/checkpoint
writing, and human actions do not consume Hops. V1 has no hidden retry.

|WFC-AUTO-04
|The coordinator shall stop before the next invocation on early-stop conditions.
At exhaustion it completes safe deterministic post-Hop work, records
`awaiting_human_budget`, renders a checkpoint, and invokes no further agent.

|WFC-AUTO-05
|Resume requires explicit maintainer action, resolved gates, verified current
HEAD/clean state, and a limit not below used Hops. Used Hops never reset within
the Run.
|===

===== 6.2 Git transaction and prospective identity

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-GIT-01
|Every Hop begins at an independently observed Git commit. Before invocation,
the coordinator verifies repository identity, expected ancestry, current HEAD,
and no tracked or non-ignored untracked changes.

|WFC-GIT-02
|After invocation, the coordinator independently observes HEAD/worktree and
computes the actual `base..head` commit range. Agent-claimed commits are hints,
never factual authority.

|WFC-GIT-03
|A successful mutating Hop shall produce 1..n atomic agent-created commits and
end clean before another Hop. Observation-only or failed Hops may have
`base==head`. The coordinator shall not synthesize semantic commits in V1.

|WFC-GIT-04
|The next Hop is prohibited after rewritten/divergent ancestry, HEAD movement
outside the invocation window, forbidden merge commit, dirty tracked/non-ignored
state, out-of-scope path, pinned policy/prompt mutation, commit safety-cap breach,
or unresolved repository/submodule/evidence identity.

|WFC-GIT-05
|Claimed/actual mismatch shall be reported and actual Git used. Mismatch becomes
blocking when coupled to hidden, divergent, out-of-scope, or policy-forbidden
change.

|WFC-GIT-06
|Ignored scratch affects cleanliness only through tracked trusted repository
policy: it may be tolerated in approved roots but must not retain secrets. A
local `.git/info/exclude` entry alone shall not establish the configured
coordinator-state-root invariant. V1 does not promise whole-filesystem
cleanliness.

|WFC-GIT-07

===== 8.1 Evidence providers

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-EVID-01
|After A2, the required RepositoryPolicy v3 `evidence_commands` mapping shall be
the sole production command-definition registry. Phase `evidence` entries name

shall not define or authorize commands.

|WFC-EVID-02
|An observation shall identify provider, one of `pass`, `fail`, `error`, or
`not_run`; command name; full executed argv; authored `argv[0]` and canonical argv
digest; configured timeout; repository-root cwd policy; runtime-resolved
invocation and canonical executable paths plus the `os.stat(invocation_path)`

outcome classification; exit code or signal when applicable; stdout/stderr byte
counts and full-stream SHA-256 digests when complete streams exist (otherwise
the corresponding fields are `null`); a Coordinator-authored concise summary;
artifact ref when applicable; and whether non-empty complete stream bodies were
omitted from persistence. The old combined output `digest` is removed, not
repurposed. This changed record shape uses execution-evidence and embedded
operator-summary schema version 2.

|WFC-EVID-03
|A2 evidence execution shall use the exact policy argv with only `argv[0]`
replaced by its resolved absolute invocation path, `shell=False`,

|WFC-EVID-04
|Providers return observations and never semantic acceptance. A future

|WFC-EVID-05
|A phase evidence list shall be an ordered list of unique command names. Every
name shall exist in the admitted policy mapping; an unknown name rejects before
Run creation, state-root mutation, checkout registration, adapter construction
or entry, and provider invocation, even when an injected fake/test runner would
otherwise simulate it. An unused definition is valid but is neither
resolved nor executed. One definition may be referenced by multiple phases and
executes once whenever each such phase reaches evidence time.

|WFC-EVID-06
|The A2 executable resolver shall handle absolute `argv[0]` directly, resolve a
relative value containing `/` from repository root, and resolve a bare name
through the snapshotted effective PATH. It shall require an executable regular
file at admission and repeat resolution at execution. Symlinks are permitted;
the absolute invocation path and canonical real path are both recorded, and the
invocation path is executed. `PATH=""` is one empty entry and searches the
repository-root cwd; relative or empty entries may resolve bare names to
agent-modified repository content, which is audit disclosure, not containment.
The fingerprint uses `os.stat(invocation_path)` and follows symlinks. Admission
non-resolution is a pre-Run refusal;
later disappearance or non-executability is runtime evidence `error`.

|WFC-EVID-07
|The named environment policy shall be
`coordinator-inherited-environment-v1`: snapshot the Coordinator process
environment once during canonical preflight, set PATH to `os.defpath` only when
PATH is absent, preserve an explicitly empty PATH, and pass that unchanged
snapshot to every evidence subprocess in the Run. No virtualenv is discovered
or prepended. Persist only the policy version, PATH source, and SHA-256 of the
effective PATH; persist no environment values or environment dump.

|WFC-EVID-08
|No stdout or stderr body shall be durable A2 evidence. Each full captured byte
stream shall contribute its byte count and separate SHA-256 digest; the durable
summary shall be generated only from Coordinator outcome facts and shall not
copy command output. For a normally completed process, complete streams use
their actual count/digest and `body_omitted` is true exactly for a non-empty
stream. If a complete stream is unavailable (including resolution failure before
spawn, spawn failure, timeout, or communication/infrastructure failure), its
count, digest, and body-omitted fields are all `null`; SHA-256 of empty must not
stand in for an unavailable stream. Omission shall not change the semantic
outcome. Raw capture remains transient and receives no host-containment claim.

|WFC-EVID-09
|Exit zero is `pass`; an ordinary positive nonzero exit is `fail`; admission-
time resolution failure rejects; runtime resolution/spawn/permission failure,
timeout, signal termination, or subprocess infrastructure failure is `error`.
Timeout shall terminate and reap the direct child only and shall not retry; A2
creates no process group, tracks no descendants, and provides no process-tree
containment. Descendants may survive or retain pipes. `not_run`
remains reserved for an existing deliberately unselected diagnostic path and
shall be a hard evidence error if returned for a required phase reference.

|WFC-EVID-10
|Every command timeout shall be an integer other than boolean in
`1..COORDINATOR_HARD_MAX_EVIDENCE_TIMEOUT_SECONDS`, whose A2 value is 900.
There is no default. The implementation shall use that one named production
constant for schema validation and the runtime guard.

Action authority (hardening 2026-09-11):: `Phase.authorized_actions` and
`RepositoryPolicy.actions` are *permitted workflow effects/capabilities, not shell

only two tokens carry normative Coordinator meaning:

  Coordinator materializes as one bounded ordinary local Git commit.

other Git command; the agent remains forbidden from Git-metadata mutation, and the
sandbox is unchanged.

A trusted commit of semantic agent-created worktree mutation *requires both `edit`
and `commit` authority*: `edit` authorizes the semantic mutation and `commit`
authorizes the Coordinator to land it. The implication `edit => commit` holds for
current serialized N=1 mutating phases (an authorized mutation that is to survive
must be landed), but `commit` *does not imply `edit`* and *cannot substitute for an
absent `edit`*. The following invariants are enforced deterministically (AAH-R1
correction, 2026-09-11):

. *Phase coherence (strict serialization).* For any serialized phase, `edit` and
  `commit` form a required pair: a phase that authorizes `edit` without `commit`,
  or `commit` without `edit`, is rejected before any Run. A `durable_artifact:
  required` phase must authorize *both* `edit` and `commit`, because producing the
  required artifact exercises `edit` and landing it exercises `commit`. A genuinely
  non-mutating phase (for example `authorized_actions: [review]` with
  `durable_artifact: none`) declares neither token and remains valid. This does not
  close the otherwise-open descriptive action vocabulary.
. *Phase ⊆ policy (operator preflight).* Every profile phase's `authorized_actions`
  must be a subset of `RepositoryPolicy.actions`; the operator rejects a profile
  phase that authorizes an effect the repository policy does not permit, before
  provider execution. Because the runtime commit-authority check (below) also
  requires `commit` in the current phase, `commit` authority transitively implies
  policy `commit` authority for the operator path without carrying policy state
  into the runtime commit boundary.
. *Runtime fail-closed commit authority.* A non-null `CommitIntent` cannot cause any
  trusted Git mutation unless the current phase authorizes *both* `edit` and
  `commit`. The refusal happens before `trusted_commit()` touches Git, leaves the
  agent's worktree state observable, and enters ordinary mechanical preemption
  (human stop). HEAD does not move. A `commit`-only phase therefore cannot land an

`completed` and `changes_required`. It does not apply to the unsuccessful
terminal outcomes `blocked` and `failed`. The WFC-OUTPUT-02 outcomes retain these

  reduced; existing CommitIntent rules apply; a `required` phase shall satisfy

  `complete` remains subject to the Run-wide blocker invariant.

Path syntax:: Governance paths and WorkItem ceiling entries shall be required,
non-empty lists of unique, glob-free, normalized repository-relative POSIX
paths. A1 shall define one pure A1 path-shape predicate. A value satisfies it
when it is a non-empty stripped string; contains no `\`, absolute prefix,
empty/`.`/`..` segment, trailing or repeated slash, or glob metacharacter `*`,
`?`, `[`, or `]`; equals its `PurePosixPath(value).as_posix()` spelling; and is
not `.`. Empty, `/`, and `.` shall not represent repository root. Files and
directories are both valid lexical paths. Policy paths need not exist, because
A1 must reserve the future A3 location; selected governing inputs remain
required tracked files at pinned HEAD.

Predicate application:: The A1 path-shape predicate applies to exactly these
A1 operands: the three new RepositoryPolicy fields' path entries
(`governance_paths`, `work_item_scope_ceiling`); `WorkItem.scope` entries and
phase `authorized_scope` entries as they participate in A1 admission; the five
supplied governing-input paths; and selected component paths. Each existing
layer shall retain its own exception class (`ValidationError` in serialization,
`OperatorPreflightError` in the operator) and its established diagnostic
vocabulary; the predicate supplies the decision, not a shared exception or
message. `git_facts._normalized_path`, CommitIntent path validation, and all
trusted-commit/Hop-observation path semantics are excluded from A1 and remain
unchanged. Unselected manifest entries, durable-artifact path validation, and
other path layers are not refactored by A1.

Deliberate A1 tightening:: Current normalization does *not* reject `.`:
`operator._relative_path(".")`, `serialization._repository_path(".")`, and the
component-manifest check all accept it, and none of the current helpers rejects
glob metacharacters; `_repository_path` and the manifest check also accept
surrounding whitespace. A1 deliberately tightens these A1 operands: `.` rejects
for governance paths, WorkItem ceiling entries, WorkItem scope, and phase
`authorized_scope`; glob metacharacters and surrounding whitespace reject
wherever the A1 predicate applies. The `.` rejection is required, not cosmetic:
`git_facts` treats an authorized scope of `.` as the whole repository for
trusted commit, while `_within_scope` treats `.` lexically, so
`within(".", g)` and `within(g, ".")` are both false for every governance path
`g`. Admitting `.` would therefore let a whole-repository mutation scope pass the
governance-overlap check.

Containment relation:: A1 shall reuse the existing `_within_scope` relation:
`path` lies within `root` when the values are equal or `path` starts with
`root + "/"`. It shall not add filesystem resolution, symlink semantics, globs,
or a second path algebra. Exact duplicate governance paths reject. Distinct
governance paths also reject when either is equal to, an ancestor of, or a
descendant of the other; redundant overlapping governance roots are not a
second valid spelling. Diagnostics shall be deterministic.

`evidence_commands` shall be a required finite YAML mapping and may be empty for
a policy that authorizes no evidence command. It has no default. A command name
shall match `[a-z][a-z0-9_]{0,63}`. Mapping-key uniqueness is enforced by the
existing strict duplicate-key loader. Each value shall be a mapping with exactly
`argv` and `timeout_seconds`; unknown or missing fields reject. The following
consumer fields therefore reject rather than being ignored: `cwd`, `env`,
`shell`, `stdin`, `retries`, `user`, `PATH`, a separate executable override,
output parser/plugin, and background/detach flags.

`argv` shall be a non-empty YAML list. Every item shall be an exact string and
shall contain no NUL; no scalar coercion, trimming, expansion, interpolation,
tokenization, or shell parsing occurs. `argv[0]` shall additionally be non-empty.
Empty later arguments are valid and preserved. `timeout_seconds` shall be an
integer other than boolean in
`1..COORDINATOR_HARD_MAX_EVIDENCE_TIMEOUT_SECONDS`; the hard maximum is 900
seconds and no default exists.

Definition, reference, and result separation:: The RepositoryPolicy v3 mapping
is the sole command-definition namespace. Existing
`WorkflowProfile.phases.<phase>.evidence` remains an ordered list of names in
that mapping; it contains no argv and grants no authority independently. Each
phase list shall contain unique names. Mapping order has no execution meaning;
phase-list order is execution order. One command definition may be referenced
by multiple phases and is attempted once each time such a phase reaches evidence
execution. An unused policy definition is valid, is not resolved, and is never
executed. An `Observation` is the execution result and shall not be treated as
definition or reference authority. No second command registry exists.

Admission:: `serialization.py` owns phase-list duplicate-reference validation.
One pure cross-document check in the current operator seam shall require every
already-valid phase reference to name a policy definition. It shall return the distinct selected names in deterministic
first-reference order for preparation. The existing A1 admission remains a
separate prerequisite and is not duplicated. Canonical preflight shall then
snapshot the A2 environment policy and resolve every selected definition's
`argv[0]`. Unknown reference, malformed definition, timeout violation, or
admission-time executable non-resolution shall reject before UUID Run allocation,
`new_run()`, state-root creation or write, checkout registration, adapter
construction or entry, dispatch marker, fake executable, or provider call.
Read-only repository/Git/input inspection already owned by `_preflight()` may
precede these checks.

Environment policy:: A2 defines exactly one policy,
`coordinator-inherited-environment-v1`. During canonical preflight the
Coordinator shall copy `os.environ` once. If `PATH` is absent, it shall insert
`os.defpath` and record PATH source `os.defpath`; if PATH is present, including
an empty value, it shall preserve that exact value and record source `inherited`.
The immutable snapshot is used for both admission resolution and every evidence
subprocess in that Run. All inherited variables are passed unchanged because
current Git/tool behavior may depend on HOME, locale, temporary-directory, and
tool configuration. The policy does not claim hermeticity and shall not persist
environment values, names, secrets, or dumps. It persists only the policy
version, PATH source, and SHA-256 of the exact effective PATH encoded with
UTF-8 plus `surrogateescape`.

There is no implicit repository virtualenv discovery or insertion. An activated
virtualenv can affect inherited PATH as operator-launch context. A consumer that
requires a repository virtualenv shall name a path such as
`.venv/bin/python` explicitly in `argv[0]`; A2 neither discovers nor creates it.

Executable resolution:: Resolution is POSIX and uses the fixed repository root
and environment snapshot:

* an absolute `argv[0]` bypasses PATH;
* a relative `argv[0]` containing `/` is interpreted from repository root and
  bypasses PATH;
* a bare name is searched through the effective PATH in order; relative and
  empty PATH entries are interpreted from repository root because that is the
  fixed subprocess cwd. `PATH=""` is exactly one empty entry, so it searches
  that repository root;
* the selected path shall resolve to an existing executable regular file;
  otherwise admission rejects or, when repeated at evidence time, the
  observation is `error`;
* symlinks are permitted. The absolute selected invocation path and canonical
  real path are both recorded. The selected invocation path, not the canonical
  target spelling, replaces `argv[0]` for execution; and
* repository-local executables are permitted through an explicit relative path.
  Relative traversal and symlinks are not represented as containment or trust;
  their resulting absolute/canonical paths are recorded. Relative or empty PATH
  entries can also resolve a bare name to an executable file inside the
  repository, including agent-modified content; that is audit disclosure, not
  containment.

Resolution is performed at admission and repeated immediately before every
attempt using the same environment snapshot. A changed executable or symlink is
not rejected merely for differing from admission: commands are explicitly
allowed to execute agent-modified repository code and the host may change. The
runtime facts are recorded. Immediately before spawn, record authored `argv[0]`,
absolute invocation path, canonical real path, and the bounded stat fingerprint
`st_dev`, `st_ino`, `st_mode`, `st_size`, and `st_mtime_ns`, using
`os.stat(invocation_path)` and therefore following symlinks to fingerprint the
target represented by the invocation path at observation time. These facts and
PATH digest aid audit; they neither hash all executable/interpreter content nor
prove trustworthiness.

Execution boundary:: Actual execution occurs only at the current evidence point:
after the adapter has returned a validated candidate result and after the
Coordinator's current trusted commit/Git observation, before evidence-dependent
route reduction completes. For each phase reference the production runner shall:

* pass a sequence argv, replacing only item zero with the resolved absolute
  invocation path;
* set `shell=False`, `cwd` to the canonical repository root,
  `stdin=subprocess.DEVNULL`, and `env` to the immutable A2 snapshot;
* capture stdout and stderr separately as bytes;
* apply the definition's positive bounded timeout;
* perform no retry, fallback, shell expansion, backgrounding, or interactive
  input; and
* on timeout, terminate and reap the direct child before returning an observation.

A2 creates and manages no process group, tracks no descendant, kills no process
tree, and provides no descendant containment. Descendants may survive or retain
pipes.

Outcome taxonomy:: A successfully spawned process returning zero is `pass`. A
successfully spawned process returning an ordinary positive nonzero status is
`fail`. Runtime executable non-resolution/disappearance, permission or other
spawn failure, timeout, signal termination (negative POSIX return code), or
subprocess communication/infrastructure failure is `error`, with a stable
classification and exit code or signal where applicable. `not_run` is not a
production outcome for a required phase reference; if an injected runner returns
it, existing reducer semantics treat it as required evidence error. A diagnostic
API may retain the existing deliberately-unselected `not_run` concept, but it
shall not authorize or execute a command. No nonzero exit-code allowlist is
consumer configurable.

Output and diagnostics:: Stdout/stderr bodies are transient and shall not be
copied into Run, Hop, checkpoint, execution-evidence, operator-summary, or other
durable A2 artifacts. Each complete captured byte stream shall produce its own
byte count and SHA-256 digest; a non-empty stream records `body_omitted=true`.
The digest is over the full stream, not a decoded or truncated form. For a
normally completed process with complete streams, count and SHA-256 are present
and `body_omitted=true` exactly when the stream is non-empty. When no complete
stream is available--including admission/runtime resolution failure before spawn,
spawn failure, timeout, or subprocess communication/infrastructure failure--the
corresponding count, digest, and body-omitted facts are all `null`; an empty
digest is used only for an actually observed complete empty stream. Semantic
outcome is unaffected by omission. The durable `summary` is generated only from
Coordinator facts (`exit 0`, `exit N`, `timeout after Ns`, `terminated by signal
N`, `resolution_error:<class>`, or `spawn_error:<class>`) and never copies command
output or an environment value. Therefore A2 needs no retained-output-size hard
constant and cannot create an unbounded durable Run artifact. Existing raw
capture remains transient; A2 makes no memory, disk, or hostile-output
containment claim.

Durable facts and ownership:: The A2 observation separates:

* semantic outcome: command name and `pass|fail|error|not_run`;
* execution audit: the full executed argv (with only `argv[0]` replaced), canonical SHA-256 of

* human diagnostic: the bounded Coordinator-generated summary and terminal
  preflight diagnostics.
