==== 1. Purpose and design inputs

V1 addresses the repeated human orchestration around bounded engineering-agent
work: preparing tasks, invoking roles, establishing actual Git truth, collecting
deterministic evidence, validating structured results, selecting only permitted
next actions, coordinating reviews/corrections, stopping for human semantic
authority, and preserving ex-post observability across autonomous Hops.

The empirical and architectural reasoning is not repeated here. Inputs are:

* `docs/warm_storage/concepts/agent_workflow_coordinator_concept_2026-08-25.adoc`
  -- non-binding evidence/hypothesis;
* `docs/warm_storage/concepts/agent_workflow_coordinator_proposed_architecture_2026-08-25.adoc`
  -- accepted formal architecture design projected into this contract;
* `docs/warm_storage/global_reviews/agent_workflow_coordinator_readiness_review_2026-08-25.adoc`
  -- finding authority for the bounded correction, not implementation authority.

If this FTR conflicts with the proposed design, readiness review must record the
conflict; implementation must not silently choose a third contract.

==== 2. V1 scope and planned placement

===== 2.1 Required V1 capability

V1 is a local, repository-native, Git-centered, policy-bounded coordinator with:

* one coordinator process, repository, worktree, active Run, and agent
  invocation at a time;
* WorkItem semantic input plus Run, Hop, and Finding operational records;
* finite validated workflow profiles and deterministic route reduction;
* one configured agent adapter plus an optional, policy-bounded supervisor role;
* Git reconciliation, fixed trusted evidence callables, structured results,
  finding convergence, autonomy budget, checkpoints, interruption/resume, and
  explicit human authority stops;
* a first routine profile, a non-production non-DMC bug-workflow fixture that
  falsifies complex-profile overfit, and, only in Slice 5, a DMC-shaped profile
  without DMC vocabulary in generic mechanics.

Planned implementation placement follows the proposed architecture:

* repository-local executable mechanics: `scripts/workflow_coordinator/`;
* versioned profiles, repository policy, and prompt components:
  `docs/ai_info/workflows/`;
* focused unit/integration/architecture tests under the existing `tests/`
  topology.

No coordinator code belongs under `src/spreadsheet_handling/`; it is developer
tooling, not product/runtime API. No new dependency is justified by V1 unless
the readiness review or a separately reviewed slice demonstrates necessity.

===== 2.2 Deferred capabilities

Deferred without V1 scaffolding: coordinator-created or mixed semantic commit
ownership; mandatory trailers/hooks; multiple agent providers/models and
provider-diversity policy; extraction into `tools/` or a package; automated
warm/cold run archival; quantitative trust scoring; parallel worktrees/runs;
remote/distributed execution; SonarQube implementation; semantic/vector
retrieval; web UI; autonomous/preauthorized child Runs; and `continuing`
conversation context unless a separately reviewed real adapter declares and
proves it as an optional capability.

===== 2.3 Explicit non-goals

* No workflow DSL, executable profile code, graph engine, database, event store,
  plugin manager, DI framework, queue, or distributed fault tolerance.
* No universal agent abstraction, general sandbox/security product, automatic
  workflow invention, automatic semantic acceptance, or Project Memory run
  store.
* No Domain, FK/Lookup, Trusted-Ingress, public CLI/YAML, spreadsheet, demo,
  release, or consumer behavior change.
* No real Run/Hop manifests, Git hooks, enforced trailers, live workflow agent,
  Sonar service, vector index, or external infrastructure in this drafting task.

===== 2.4 FTR sizing preflight

This is a justified FTR because it introduces architectural developer tooling
with acceptance contracts. It does not touch spreadsheet roundtrip, `_meta`,
Domain registries, XLSX/ODS parity, or current public product surfaces. The
workflow profile schema is an internal coordinator input, not the existing
public pipeline YAML surface. The five slices separate the state/reducer,
repository transaction, adapter, live invocation, and multi-Hop risks.

These contracts become binding only after independent FTR acceptance.

===== 3.1 System boundary

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-SYS-01
|V1 shall execute serially for exactly one configured repository/worktree and
at most one active Run and one agent invocation. A suspended parent is not
active while its separate child Run executes.

|WFC-SYS-02
|Coordinator mechanics, workflow profile, repository engineering policy,
operator/Run policy, and task payload shall remain distinguishable inputs even
when implemented by a small number of modules/files.

|WFC-SYS-03
|The generic coordinator shall contain no DMC, family, cycle, slice, or
Trusted-Ingress E-phase primitive. Profiles and WorkItem labels may contain
those terms.

|WFC-SYS-04
|V1 shall remain useful with `max_autonomous_hops=1` and shall require no
future-only service or infrastructure to run.

|WFC-SYS-05
|The implementation shall stay repository-local under the planned placement
unless readiness review explicitly corrects a demonstrated placement conflict.

===== 3.2 WorkItem input, Run, Hop, and Finding

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-MODEL-01
|WorkItem shall be semantic input, not a mutable operational entity. Its compact
specification shall carry stable `work_item_id`, task/authority source, profile
reference, repository/scope, initial phase, `max_autonomous_hops`, and optional
profile labels.

|WFC-MODEL-02
|A Run shall identify one execution attempt with `run_id`, schema version,
WorkItem reference, pinned profile/policy revision, repository identity,
baseline/current observed HEAD, current phase/status, budget used/limit, compact
Hop summaries, Findings, child/suspension reference, reconcile reason/anchor,
and stop reason. Finite next route keys shall be derived from pinned profile,
current phase, and preemption state rather than persisted as independent state.

|WFC-MODEL-03
|Run state shall not duplicate full diffs, Git log, changed-file contents, or
other facts reconstructable from stored commit IDs and Git.

|WFC-MODEL-04
|A Hop shall identify one adapter-accepted invocation through run-local
`hop_id`/sequence and record role/context, start/end, independently observed
base/end commits, actual commit range, invocation/result status, Finding delta,
evidence refs, route/stop, and concise attributed rationale.

|WFC-MODEL-05
|A Finding shall have stable run-local ID, concise invariant/problem statement,
blocking flag, state, introducing/last-changing Hop, evidence refs, concise
disposition, and optional successor/external WorkItem reference. It shall not
grow assignees, due dates, comments, or general issue-tracker workflow.

|WFC-MODEL-06
|Review descriptors, observations, transition decisions, prerequisite links,
and checkpoints shall remain nested ordinary data or generated views rather
than additional operational aggregate roots.
|===

==== 4. Workflow profile, route, and authority contracts

===== 4.1 Profile data and route effects

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-PROFILE-01
|Human-authored WorkItem specifications, profiles, and structured repository
policy shall use strict validated YAML; natural-language prompt components are
versioned text referenced by that YAML. Machine-written transient Run state
shall use JSON. Unknown fields fail closed, and no equivalent second
human-authored serialization is provided. Phase keys are opaque to generic code.

|WFC-PROFILE-02
|Each phase shall declare role/prompt policy, explicit role/modifier and
repository-policy component selections, `durable_artifact` policy, permitted
route keys, evidence requirements, authorized scope/actions, human gates, and a
review descriptor when the phase is a review.

|WFC-PROFILE-03
|Profiles shall express only five route effects: `goto`, `complete`,
`await_human`, `suspend_for_prerequisite`, and `stop`.

|WFC-PROFILE-04
|`goto` selects one declared target phase; `complete` ends the Run without
claiming authority beyond profile policy; `await_human` records a concrete
question; `suspend_for_prerequisite` records an explicitly human-authorized child
and clears stale next action; `stop` ends autonomous progress without claiming
completion.

|WFC-PROFILE-05
|Profile data shall not contain executable code, arbitrary conditions, computed
graphs, fan-out, or user-defined loops. A loop is a finite declared route edge.

|WFC-PROFILE-06
|A profile or pinned policy mutation during a Run shall be an anomaly requiring
stop and common reconcile/resume; an agent result cannot authorize its own
profile change.
|===

===== 4.2 Routing precedence and authority

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-AUTH-01
|Routing precedence shall be: mechanical preemption, deterministic policy
reduction, optional declared supervisor judgment, then human semantic authority.

|WFC-AUTH-02
|Mechanical preemption shall stop on malformed state/result, Git anomaly,
policy mutation, budget prohibition, required evidence-provider error,
`requires_human=true`, or any non-null unresolved escalation; no supervisor may
override it. Human/escalation preemption applies regardless of outcome or valid
requested route, including `outcome=completed` with `goto`/`complete`.

|WFC-AUTH-03
|Only after mechanical preemption clears, deterministic reduction shall use the
validated routing envelope, current review authority/blocking policy, Finding
state, evidence state, budget, and current finite route table. It shall route
automatically only when policy determines a single permitted result.

|WFC-AUTH-04
|A supervisor may be invoked only at a profile-declared judgment point, shall be
read-only, consumes a Hop, receives one bounded question plus finite route keys
and compact history, and may classify/recommend, choose only one already
authorized key, or request a human.

|WFC-AUTH-05
|A supervisor shall not invent routes, mutate profile/policy, enlarge scope,
close or reopen a Finding, downgrade blocking status, accept a residual,
supersede/reclassify a Finding as an authoritative disposition, create semantic
ownership, approve public/API choices, activate any child/work item, raise review
authority, or claim project/Project-Memory decisions. Profile delegation cannot
grant these powers; the supervisor may only route to the declared gate/human.

|WFC-AUTH-06
|Human escalation shall be mandatory for new/conflicting semantic ownership or
authority, plausible public/API/compatibility choices, trust/security redesign,
capability deletion, workflow/profile redesign, unauthorized scope, unapproved
nested work, roadmap/Project Memory governance, and any undelegated decision. AI
may discover, propose, and escalate these questions, but cannot self-authorize
their disposition.
|===

==== 5. Review, Finding, and convergence contracts

===== 5.1 Review dimensions and anti-ceremony rule

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-REVIEW-01
|Every review phase shall independently declare breadth/search scope, authority,
and context policy. Breadth selects the falsification surface and grants no
authority.

|WFC-REVIEW-02
|Review authority is `advisory` or `gate`. Advisory results may add evidence or
Findings but cannot advance/complete. A gate authorizes only its declared route
under its blocking policy.

|WFC-REVIEW-03
|`fresh` context shall not reuse author conversation history and is the required
V1 baseline. `continuing` is not a V1 engine guarantee; a profile may require it
only after a separately reviewed adapter declares/proves bounded-thread support.
Context does not establish independence or authority by itself.

|WFC-REVIEW-04
|A review stage shall exist only where the profile states a distinct epistemic,
falsification, risk, or authority purpose plus trigger, blocking policy, and
exit. Availability shall never imply mandatory execution.

|WFC-REVIEW-05
|After broad review establishes a Finding set, correction/delta review normally
checks known Findings and direct regressions. New material evidence may escape
the bound; unrelated new minors shall not automatically reopen the whole work.
A resolved Finding may reopen only through WFC-FIND-03 authority and new material
evidence.
|===

===== 5.2 Finding lifecycle and convergence

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-FIND-01
|Finding state shall be exactly `open`, `resolved`, `residual`, or `superseded`.
`residual` means genuine and explicitly accepted non-blocking;
`superseded` requires successor/reclassification reference.

|WFC-FIND-02
|Agents may cite an existing ID or propose an unassigned Finding. The
coordinator allocates new IDs and rejects silent invariant/identity rewrites.

|WFC-FIND-03
|Only the current declared gate with the applicable phase/blocking-policy
authority, or human authority, may validate closure, `resolved -> open`
reopening, blocking downgrade, residual acceptance, or
supersession/reclassification. Reopening additionally requires new material
evidence; agent/supervisor reassertion alone does not change authoritative
disposition.

|WFC-FIND-04
|The coordinator shall deterministically expose Finding transitions/reopens,
commit/path and evidence changes, regression state, new material-Finding count,
route repetition, and scope/policy/baseline changes.

|WFC-FIND-05
|Material mechanism change, semantic narrowing, productive progress, goalpost
drift, lack of progress, or wrong owner/workflow are semantic classifications
for delegated supervisor or human judgment. A supervisor classification is only
a routing recommendation and never an authoritative Finding disposition. V1
shall implement no numerical convergence score.

|WFC-FIND-06
|V1 shall permit productive correction beyond three loops, stop non-progressing
loops before budget where judged, and route semantic reclassification out of
local correction. No fixed low `max_review_iterations` may be the primary rule.
|===

==== 6. Bounded autonomy and Git contracts

===== 6.1 Autonomy budget

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-AUTO-01
|Every Run shall carry positive `max_autonomous_hops=N`; architecture shall
support empirical N=1 -> 2 -> 5 -> 10 changes without model/schema redesign.

|WFC-AUTO-02
|Every invocation accepted by the agent adapter consumes one Hop whether it
succeeds, fails, or yields malformed output. Author, reviewer, correction,
re-entry assessor, curator, and supervisor invocations all count. Mechanical
reconcile/resume work does not consume a Hop. After crash recovery, absence of a
dispatch marker proves no Hop consumption; once the atomic dispatch marker
exists, acceptance that cannot be disproved is conservatively charged as one Hop
and never replayed.

|WFC-AUTO-03
|Local failure before adapter/provider acceptance, Git/evidence inspection,
prompt assembly, schema validation, deterministic routing, state/checkpoint
writing, and human actions do not consume Hops. V1 has no hidden retry.

|WFC-AUTO-04
|The coordinator shall stop before the next invocation on early-stop conditions.
At exhaustion it completes safe deterministic post-Hop work, records
`awaiting_human_budget`, renders a checkpoint, and invokes no further agent.

|WFC-AUTO-05
|Resume requires explicit maintainer action, resolved gates, verified current
HEAD/clean state, and a limit not below used Hops. Used Hops never reset within
the Run.
|===

===== 6.2 Git transaction and prospective identity

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-GIT-01
|Every Hop begins at an independently observed Git commit. Before invocation,
the coordinator verifies repository identity, expected ancestry, current HEAD,
and no tracked or non-ignored untracked changes.

|WFC-GIT-02
|After invocation, the coordinator independently observes HEAD/worktree and
computes the actual `base..head` commit range. Agent-claimed commits are hints,
never factual authority.

|WFC-GIT-03
|A successful mutating Hop shall produce 1..n atomic agent-created commits and
end clean before another Hop. Observation-only or failed Hops may have
`base==head`. The coordinator shall not synthesize semantic commits in V1.

|WFC-GIT-04
|The next Hop is prohibited after rewritten/divergent ancestry, HEAD movement
outside the invocation window, forbidden merge commit, dirty tracked/non-ignored
state, out-of-scope path, pinned policy/prompt mutation, commit safety-cap breach,
or unresolved repository/submodule/evidence identity.

|WFC-GIT-05
|Claimed/actual mismatch shall be reported and actual Git used. Mismatch becomes
blocking when coupled to hidden, divergent, out-of-scope, or policy-forbidden
change.

|WFC-GIT-06
|Ignored scratch affects cleanliness only through tracked trusted repository
policy: it may be tolerated in approved roots but must not retain secrets. A
local `.git/info/exclude` entry alone shall not establish the configured
coordinator-state-root invariant. V1 does not promise whole-filesystem
cleanliness.

|WFC-GIT-07
|WorkItem ID is semantic identity; Run ID is one attempt; Hop ID is invocation
identity within Run. Run evidence carries all three. No historical Hop IDs are
invented.

|WFC-GIT-08
|Workflow-produced commit subjects shall project WorkItem/Hop identity in
human-readable `git log --oneline` form compatible with Conventional Commits.
Trailers/hooks remain optional/deferred; any subject validation is coordinator
postcondition, not a Git hook.
|===

==== 7. Prompt, agent output, and repository-policy contracts

===== 7.1 Prompt composition

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-PROMPT-01
|Reusable prompt material shall be repository-local, versioned, and pinned by
path plus Git revision/content digest for the Run. Each phase shall explicitly
select the role/modifier and repository-policy components it requires; the
coordinator shall not inject all repository guidance automatically.

|WFC-PROMPT-02
|Expanded prompt order shall be: generated identity/Git/authority/output header;
selected role/persona/modifiers; selected repository engineering-policy
components; workflow/profile/phase policy; task-specific semantic payload;
bounded evidence/context; result/output contract.

|WFC-PROMPT-03
|Identity, provenance, scope, routes, process, evidence refs, and output contract
shall be structured; semantic task/reasoning remains natural-language prose.

|WFC-PROMPT-04
|V1 shall have no general template language or user-defined conditional/include
engine. What deterministic software can reliably enforce shall not exist only
as an LLM instruction. Evidence/context omitted by a bound shall be listed in an
omission/reference manifest with its retrieval path; silent truncation is
forbidden. Numeric size/diff thresholds may follow Slice-2 measurement.
|===

===== 7.2 Three output surfaces

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-OUTPUT-01
|Every accepted invocation shall produce or fail validation against a
machine-readable routing envelope containing schema version, outcome, requested
profile route, `scope_changed`, `requires_human`, optional escalation, Finding
deltas, claimed commits, evidence refs, and short summary.

|WFC-OUTPUT-02
|Outcome vocabulary shall be `completed`, `changes_required`, `blocked`, or
`failed`. Escalation classes shall include `scope`, `semantic_authority`,
`public_surface`, `trust_boundary`, `prerequisite`, and `operational` with a
concise question.

|WFC-OUTPUT-03
|A Finding delta shall contain existing/null ID, invariant, blocking flag,
proposed state, and evidence refs. Free-form prose cannot supply missing
routing-critical fields.

|WFC-OUTPUT-04
|Every phase shall declare `durable_artifact` as `required`, `optional`, or
`none`. For `required`, result validation demands an in-scope versioned artifact
reference and a successful mutating Hop commits it; for `optional`, the artifact
is permitted but not a gate; `none` creates no coordinator artifact obligation.
The agent cannot weaken the declared value. Phases with durable semantic purpose
(normally architecture/design, broad assessment, material formal review,
closure assessment, or lifecycle closure) use `required`; tiny implementation,
mechanical observation, and supervisor routing normally use `none`.

|WFC-OUTPUT-05
|Terminal output shall be concise and navigational: identities, outcome/stop,
commit/check status, human question, and artifact/checkpoint locations. Material
analysis belongs in repository artifacts, not a long terminal transcript.
|===

===== 8.2 Persistence and artifact lifecycle

[cols="1,5",options="header"]
|===
|ID |Requirement

|WFC-PERSIST-01
|V1 shall persist enough compact local state for same-checkout crash/resume:
an atomically replaced Run snapshot and atomically published correlated
dispatch/in-progress marker with base HEAD and budget reservation are the only
trusted resume anchors. Compact
Hop/result metadata, Finding state, evidence-manifest refs/digests, and generated
checkpoint remain referenced state, not repository authority.

|WFC-PERSIST-02
|Operational state shall live on persistent local storage, be unambiguously
associated with the concrete repository checkout, remain coordinator-controlled,
not contaminate repository Git state, and have its storage/correlation boundary
verified fail-closed before the first Run write and each Hop. A
repository-local root is permitted where the boundary-crossing process is
trusted not to mutate coordinator state; it must be repository-specific, ignored
by tracked repository policy, and pass Git ignore-resolution preflight (a local
exclude alone is insufficient). An external trusted checkout-associated root is
required for the writable real-agent Slice-4 boundary: it shall be
outside the agent-writable workspace, not re-exposed through writable additional
directories, and correlate coordinator-controlled state through a durable opaque
checkout identifier and trusted current checkout/Git facts. On first
registration, the coordinator records the concrete checkout's canonical path
and Git common-dir/git-dir fact as appropriate with one opaque checkout UUID;
path or association mismatch fails closed pending explicit maintainer
intervention. The UUID is not a security proof: authority also requires current
fail-closed Git/checkout and Run/Hop/HEAD correlation. No universal path,
database, repository registry service, event store, or append-only event log is
permitted.

|WFC-PERSIST-03
|Git stores durable repository history; committed design/review/assessment
artifacts store durable semantics. Run state references commits/artifacts rather
