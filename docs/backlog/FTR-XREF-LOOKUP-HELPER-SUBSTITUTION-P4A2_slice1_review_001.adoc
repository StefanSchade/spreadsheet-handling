=== 4.2 Important findings

==== XREF-S1-IMP-001 — key/helper collisions are not safely defined

Severity:: Important
Affected file / symbol::
`src/spreadsheet_handling/domain/transformations/enrich_lookup/operation.py` —
`_check_column_conflict`, `_build_helper_projection`,
`_build_formula_enrichment`, and the call path from `enrich_lookup`.
Evidence::
The asymmetric conflict guard excludes `source_key` from conflicts but does not
protect either public key role from helper projection. Direct probes using
`source_key=story_id`, `lookup_key=id` produced all of the following:

* `helpers.fields=[story_id]` in values mode renames lookup `id` to
  `story_id` beside the independently selected lookup `story_id`, then fails
  with pandas `ValueError: The column label 'story_id' is not unique`;
* `helpers.fields=[id]`, `missing=empty` silently returns only
  `[story_id, dyn]` while provenance falsely records `helper_columns=[id]`;
* the same request with `missing=fail` raises a raw pandas `KeyError` because
  the promised `id` helper is absent after rename;
* formula mode with `helpers.fields=[id]` emits an `id` output column, directly
  violating the public guarantee that the lookup-side key never leaks; and
* formula mode with `helpers.fields=[story_id]` overwrites the authoritative
  source key values with `LookupFormulaSpec` objects.

The lookup frame containing an unselected non-key `story_id` is safe, but
selecting that column or selecting the lookup key exposes the defect. These are
the requested rename-collision cases, not speculative abstractions.
Impact::
Accepted public helper-field requests can silently omit a field, publish false
provenance, leak the lookup key, destroy the source identity column, or fail
with backend-library diagnostics. This violates the Slice-1 output-key and
projection contract and makes the API unsafe for later consumer migration.
Required correction::
Define and enforce a deterministic asymmetric key/helper collision rule before
projection or formula assignment. At minimum, requested helper fields and
temporary lookup sort fields must not collapse onto the source key or expose the
lookup key; invalid combinations must raise a clear domain `ValueError` before
merge/formula construction. Preserve the authoritative source key and the
no-lookup-key-output guarantee in both values and formula modes. Add regression
tests for both key names, values/formula modes, and a lookup frame that already
contains a non-key column named like the source key.
Blocks Slice 2:: Yes.

==== XREF-S1-IMP-002 — asymmetric provenance silently disables mismatch checking

Severity:: Important
Affected file / symbol::
`src/spreadsheet_handling/domain/transformations/derived_column_policy.py` —
`_check_enrich_lookup_values` (consumer of provenance written by
`operation._write_provenance`).
Evidence::
The reader resolves only `spec.get("on")`. An asymmetric record contains
`source_key` and `lookup_key`, so `on_keys` is empty and the reader returns no
findings at lines 345–364. A direct probe enriched `story_id -> id`, edited a
materialized `title`, and invoked both public mismatch policies with the lookup
frame present:

* `warn_on_mismatch` returned zero findings and dropped `title`; and
* `fail_on_mismatch` did not raise and dropped `title`.

This is not merely the intentionally value-blind `policy: drop` path. The
registry and callable document the mismatch policies as value-checking
`enrich_lookup` helpers. The implementation artifact calls the behavior a safe
no-op, but the runtime result is silent loss of the requested check.
Impact::
The additive public asymmetric capability creates records that an existing
public policy only partially understands: helper identity/drop works, while
edited-value verification silently stops working. This is an undocumented
behavioral degradation and could allow edited derived values to pass a
`fail_on_mismatch` gate.
Required correction::
Either teach the mismatch reader to use the payload `source_key` and lookup
frame `lookup_key`, or explicitly reject mismatch policies on asymmetric
provenance with a clear diagnostic until support is implemented. It must not
silently succeed without checking. Add warn/fail tests with a changed helper,
an unchanged helper, unmatched references, and differently named keys.
Blocks Slice 2:: Yes.

==== XREF-S1-IMP-003 — explicit asymmetric mode is lost when key names are equal

Severity:: Important
Affected file / symbol::
`src/spreadsheet_handling/domain/transformations/enrich_lookup/operation.py` —
`_write_provenance`; `policy.py` — `_resolve_join_keys`.
Evidence::
The public pair accepts `source_key == lookup_key`; no confirmed contract rule
requires different strings. Nevertheless `_write_provenance` chooses the
record shape by comparing the resolved lists (`source_keys == lookup_keys`),
not by the public mode selected. A direct call with
`source_key=id, lookup_key=id` therefore writes `{"on":["id"]}` and omits both
asymmetric fields. This loses real intent: an explicit asymmetric pair ignores
a configured helper-policy `key`, while an inline symmetric form reconciles
and can conflict with that policy. The resulting provenance and downstream
mismatch behavior vary with string equality rather than selected public mode.
Impact::
Provenance cannot unambiguously distinguish an explicitly selected asymmetric
contract from legacy symmetric selection. Equality of the current labels is
not a stable substitute for mode identity, and later consumers cannot reliably
interpret the record.
Required correction::
Carry the selected public mode as part of resolved key state and write
provenance from that mode. An explicit `source_key` / `lookup_key` call must
retain the asymmetric record shape even when the strings are equal. Add direct
and YAML tests for equal names and a configured policy key.
Blocks Slice 2:: Yes.

==== XREF-S1-IMP-004 — changed asymmetric formula path has no tracked test

Severity:: Important
Affected file / symbol::
`src/spreadsheet_handling/domain/transformations/enrich_lookup/operation.py` —
`_build_formula_enrichment`; tests in
`tests/unit/domain/transformations/test_lookup_formula_mode.py` and
`tests/unit/domain/transformations/test_enrich_lookup.py`.
Evidence::
`c965431` changes formula construction from one common key to distinct
`source_key_column` and `lookup_key_column`, but every tracked formula-mode test
still uses a symmetric key. No Slice-1 test invokes asymmetric formula mode.
The independent temporary probe confirms the ordinary case currently creates
`LookupFormulaSpec(source_key_column='story_id', lookup_key_column='id')` and
renders the expected XLSX and ODS XLOOKUP ranges. That review-time evidence does
not provide regression protection, and the collision probe in IMP-001 shows
formula-only failures that the values tests cannot detect.
Impact::
A changed public path, including the distinction Slice 1 introduces, can
regress without any tracked test failing. Later slices may depend on the
general `add_lookup_helpers` contract rather than values mode alone.
Required correction::
Add an asymmetric formula test asserting both key names in the spec, source-key
preservation, absence of lookup-key leakage, helper placement, and provenance.
Add or extend one rendering test to prove the source cell and distinct lookup
key/value ranges are used after physical sheet-name resolution.
Blocks Slice 2:: Yes.

=== 4.3 Minor findings

==== XREF-S1-MIN-001 — public docs omit helper-policy key interaction

Severity:: Minor
Affected file / symbol::
`operation.enrich_lookup` docstring,
`registries/pipeline_step_registry.json` (`add_lookup_helpers` parameters),
`docs/user_guide/ch03_transformation_catalog/03_supporting_steps.adoc`, and
`docs/release_notes/release_notes.adoc`.
Evidence::
The resolver intentionally ignores only a configured helper-policy `key` when
an explicit asymmetric pair is present, while still applying policy-derived
helpers, allowed fields, order, missing mode, and value mode. A direct probe
with a conflicting policy key and `helpers=default` succeeded deterministically
using `story_id -> id`. This rule appears in an internal resolver comment and
the implementation artifact, but not in the public docstring, registry notes,
user guide, or release note. Inline symmetric keys, by contrast, are reconciled
with the policy key and may fail on conflict.
Impact::
Users cannot predict from public documentation why the same policy key is
enforced for symmetric inline parameters but ignored for the asymmetric pair.
Required correction::
Document that an explicit asymmetric pair is authoritative for key selection,
ignores the policy `key`, and continues to consume the policy's non-key helper
settings. Keep the runtime rule deterministic.
Blocks Slice 2:: No by itself.

== 5. Public API assessment

The Python signature and YAML binding accept the intended symmetric forms:
`key`, `keys`, quoted legacy `"on"`, and a policy-derived `key`. Representative
symmetric behavior is unchanged. The asymmetric pair is single-string per side,
requires both halves, and is mutually exclusive with every inline symmetric
form; there is no fallback or precedence.

Direct probes confirmed consistent diagnostics for partial pairs, blanks,
whitespace-only values, and wrong types. `None` has normal omitted-parameter
semantics: one `None` half beside a present half is diagnosed as partial; both
absent allow symmetric/policy resolution. YAML uses the same callable and the
tracked YAML success test exercises the new pair.

The configured helper-policy key is deliberately ignored in explicit
asymmetric mode while all non-key policy settings remain active. That behavior
is deterministic and suitable for an explicit key pair, subject to the public
documentation gap in MIN-001.

The registry's parameter list matches the callable signature and describes the
pair requirement and inline mutual exclusion. It correctly keeps `keys` as a
symmetric, potentially multi-column form and the asymmetric parameters as
single strings. It does not encode a machine-readable one-of constraint, but
the reviewed registry is explicitly a manual descriptive artifact, not the
runtime binder; the notes are sufficient for that artifact.

Explicit equal names are valid at the public boundary. The implementation
*should preserve that asymmetric mode selection*, because its policy-resolution
semantics and provenance contract are selected by parameter form, not by the
accidental equality of resolved labels. IMP-003 records the current failure.

== 7. Join and cardinality assessment

For ordinary asymmetric usage, source validation uses `source_key`, lookup
validation and duplicate detection use `lookup_key`, and the lookup projection
is reduced then renamed before the merge. Direct probes verified:

* reversed source order is preserved when no explicit `sort_by` is configured;
* source cardinality is preserved under a unique lookup key;
* duplicate lookup-side keys fail before merge;
* the differently named lookup key is absent from normal values output;
* `missing=fail` rejects unmatched source rows and `missing=empty` fills helper
  values with `""`;
* a lookup frame that contains an unselected, non-key column named like the
  source key does not affect the merge;
* many-to-one behavior remains enforced; and
* null/NaN key matching and subsequent blank normalization are consistent with
  the parent symmetric behavior.

Pandas merge continues to produce its established RangeIndex in values mode;
formula mode continues to preserve the copied source index. No index regression
was introduced.

The rename strategy is not safe when a selected helper is either key or when a
selected lookup column collapses onto the renamed source label. IMP-001 is the
resulting correctness finding.

== 8. Formula-mode assessment

The ordinary asymmetric formula implementation is logically correct:

* `source_key_column` is `story_id`;
* `lookup_key_column` is `id`;
* `lookup_value_column` is the selected helper;
* the source/output retains `story_id`; and
* physical sheet-name resolution remains generic.

The temporary XLSX result was
`=XLOOKUP($A2,'Entities'!$A$2:$A$3,'Entities'!$B$2:$B$3,"")`; the ODS content
used `XLOOKUP([.A2];[Entities.A2:Entities.A3];[Entities.B2:Entities.B3];"")`.
Thus both renderers use the source key cell, lookup-side key range, and lookup
value range correctly in the ordinary case. Formula missing behavior and the
single-key restriction remain unchanged.

The key/helper overwrite and leakage defects are in IMP-001. The absence of a
tracked asymmetric formula regression test is independently Important under
IMP-004. Existing symmetric formula tests remain meaningful but cannot prove
the new two-name path.

== 9. Sort and helper-field assessment

Explicit fields, policy-resolved fields, normal values mode, normal formula
mode, no-helper mode, and allowed-field checks were traced. An asymmetric
`sort_by` lookup helper (`rank`) is temporarily projected, sorts the result,
and is dropped when it was not requested as an output helper. Source row order
changes only when sorting is explicitly requested.

Passing `source_keys` to `_fields_with_sort_helpers` is semantically correct for
the output-facing join key: `sort_by=story_id` sorts the source/output key and
does not attempt to select an independent lookup non-key `story_id`. A
`sort_by=id` request is rejected because `id` is not an output column. No silent
sort-helper retention was found.

The remaining unsafe helper-field names are the two asymmetric key roles and
rename collisions described in IMP-001. The tracked Slice-1 suite does not
exercise asymmetric `sort_by` or policy-derived helper resolution; independent
probes passed, but tracked follow-up coverage should accompany the corrections.
