== Q&A

=== Q1 -- Ordinary Domain payload

ANSWER: Ordinary Domain payload is drawn from a *positive, closed* six-category
scalar grammar: String, Boolean, Number, Missing, Date, DateTime. A cell value
is admissible Domain state only if it classifies into one of these.

* *Scalar categories:* the six above; there is no seventh. Framework-authored
  Intent (`FormulaSpec`) is explicitly *not* a seventh scalar.
* *pandas storage does not make something Domain:* external representation is
  not Domain merely because a `DataFrame`/NumPy array holds it; an object-dtype
  cell holding an arbitrary Python object is not thereby admitted.
* *Composites:* the current accepted contract admits *zero* ordinary
  composite/list/mapping Scalars. A future composite is possible only through
  its own separately accepted contract; never by inference from shape or
  delimiters.
* *Carrier vs. category are distinct axes:* a `numpy.int64` classifies as
  Number while remaining a `numpy.int64`; classification labels a category, it
  does not convert/narrow/rewrap. (Carrier variants and classifier mechanics
  are owned by the Internal Scalar Value Model.)
* *Missing:* a *recognition over carriers* (`None`, `""`, bounded
  NaN/`pandas.NA`/`NaT` family), not a sentinel or wrapper; on the visible
  spreadsheet surface the missing representation stays the ordinary string
  `""`.

PRIMARY PERMANENT SOURCE: Semantic Model 06, `semantic-model-domain-scalar-language`
(canonical owner of the meaning). SUPPORTING SOURCE: Internal Scalar Value
Model (carrier variants/classifier mechanics). CONFIDENCE: *clear*.

=== Q2 -- What Trusted Ingress establishes

ANSWER: Successful Trusted Ingress establishes exactly one downstream
assumption -- *Ingress-Conformant Domain Payload*: every ordinary cell belongs
to the admitted six-category language and the framework-owned `_meta`
substrate satisfies its closed, bounded, acyclic shape. Consequently ordinary
Domain code operates on admitted Domain state and *does not need to defend, at
every consumer, against arbitrary external Python objects*.

Distinctions:

* *Payload conformance:* established (the value belongs to the admitted
  language).
* *Transformation/business validity:* NOT established -- whether an FK target
  resolves, whether a key column is unique, whether a transformation's own
  preconditions hold. "Necessary, not sufficient."
* *Local transformation preconditions:* remain each transformation's own
  responsibility.

So downstream transformations, *after admission at a managed boundary*, need
not re-defend against arbitrary external Python objects; they must still
enforce their own family/business semantics.

PRIMARY PERMANENT SOURCE: Semantic Model 06, "What successful ingress
establishes". SUPPORTING SOURCE: ch06 `trusted-ingress-establishment`
("Ingress conformance is necessary, not sufficient"). CONFIDENCE: *clear*.

=== Q3 -- Where conformance is established and re-established

ANSWER:

* *Initial establishment:* over a candidate loaded at an external/router
  boundary (or returned by uncertified code). Every ordinary cell must
  classify into the six categories; `_meta` passes the common recursive
  substrate check (a closed reviewed authoring delegate is used only where a
  root needs authoring-shape normalization first).
* *Re-establishment:* after framework-managed execution regains control from
  an *uncertified producer* (plugin callable, unreviewed wrapper,
  caller-supplied `BoundStep`), the framework MUST run a fresh
  Ingress-Conformant pass over the returned candidate before any later
  ordinary operation/cleanup/persistence. Every controlled-role authorization
  ends at that return by rule, regardless of the returned value's identity or
  provenance.
* *Framework-owned macro seam:* there is *one* macro wiring seam --
  `application.orchestrator.orchestrate` (and its small named execution
  component). Managed ingress/controlled-state enforcement is wired there and
  only there.
* *run_app and schema maintenance:* `run_app`, `run_schema_maintenance`, and
  the CLIs/shims reach the rule only by *delegating* through that one seam --
  they are reachability/coverage paths, *not* independent policy owners, and
  must not become parallel wiring locations. (This is a single policy owner,
  not three parallel owners.)

PRIMARY PERMANENT SOURCE: ch06 `trusted-ingress-establishment` +
`description-and-resource-authority` ("Framework-managed versus
caller-precondition surfaces"). SUPPORTING SOURCE: Developer Guide
`04_trusted_ingress_extension.adoc` ("Acceptance and wiring are separate
checks" -- the one macro seam). CONFIDENCE: *clear*.

=== Q4 -- Caller-precondition surfaces

ANSWER: *Caller-precondition surfaces* place all conformance, preservation,
and re-establishment responsibility on the caller; they do NOT automatically
establish Trusted Ingress:

* `run_pipeline` -- assumes the caller already supplies a conformant execution
  state for its first step; no automatic ingress; a different documented
  contract, not a lesser-trusted `orchestrate`.
* `build_steps_from_config` / `build_steps_from_yaml` -- building a step never
  establishes conformance by itself (they *do* accept opt-in
  `description_authorization`, which is a description-trust concern, not
  ingress establishment).
* Direct `BoundStep` composition -- deliberately bypassing,
  trusted-programmatic.
* Direct backend read/write -- a direct loader returns a raw carrier-level
  representation; a direct saver applies no persistence-boundary projection
  and authorizes no controlled roles.

Contrast -- *framework-managed entry points* (`orchestrate`, `run_app`,
`run_schema_maintenance`, plus CLI/compat shims) automatically establish
Domain-language conformance before any configured step and apply
controlled-role classification/transition around each step and at the sink.

*Merely building a BoundStep does NOT establish Trusted Ingress.* Explicitly
stated ("Building a step never establishes conformance by itself").

PRIMARY PERMANENT SOURCE: `interfaces_and_gates.adoc` programmatic-surface
matrix. SUPPORTING SOURCE: ch06 "Framework-managed versus caller-precondition
surfaces". CONFIDENCE: *clear*.

=== Q5 -- Executable-binding authority

ANSWER: Before an invocation may receive controlled-role certification, one
structural property must hold: *the executable target and the role-relevant
effective configuration used to classify/certify the bound call are the exact
target and configuration that will execute* -- not a description a caller could
subsequently make diverge.

* *Actual executable target + effective configuration:* a bound step's sole
  construction path creates *one authoritative effective binding snapshot*; it
  owns and freezes the supported container structure.
* *Authoritative binding snapshot / caller-held mutable aliases:* deep-immutable
  effective binding protects against mutation-through-alias; the target's
  reviewed contract stays ordinarily importable/constructible (no secrecy or
  provenance dependence) -- what establishes the property is what constructing
  and calling the object *necessarily* causes.
* *Invocation-local thaw/materialization:* invocation may materialize fresh
  local containers from that snapshot.
* *Fail-closed for certificate-relevant unsupported values:* the generic
  trusted-programmatic binder may retain an arbitrary leaf *by reference*; such
  a leaf cannot support controlled-role authority, so the step is `Uncertified`
  before any controlled role is authorized. Certification succeeds only when
  every certificate-relevant component is represented by the classifier's
  closed immutable contract.

Insufficient by themselves: a visible config value, a callable/class identity,
registry membership, framework authorship, provenance, or an object that merely
looks like a certificate.

(The canonical term used by the docs is *Executable Binding Authority*; the
phrase "Certified Invocation Stability" is not established by any permanent
document and is therefore not used.)

PRIMARY PERMANENT SOURCE: ch06 `certified-executable-binding`. CONFIDENCE:
*clear*.

=== Q6 -- Certificate versus current controlled state

ANSWER: Three questions stay distinct ("Three distinct authority questions"):

* *Certificate/binding identity* -- does this exact bound call necessarily
  execute what it claims?
* *Controlled-transition authority* -- which reviewed producer may establish
  which role, at which location?
* *Current role state* -- which values presently carry non-ordinary authority
  right now?

*Does successful classification itself mean the current payload already carries
the controlled role?* NO. Certification/classification proves only that the
exact bound invocation is *eligible and authorized* for its named reviewed
transition. The current-state descriptor/role is *published only after that
invocation executes and its exact transition is applied*. A certificate or a
successful classification is not itself proof that current payload state
already carries the role. (Two-stage relationship, never one step.)

PRIMARY PERMANENT SOURCE: ch06 `controlled-execution-state` ("Three distinct
authority questions"). SUPPORTING SOURCE: Developer Guide
`04_trusted_ingress_extension.adoc` (current-state descriptor/certificate
two-stage relationship). CONFIDENCE: *clear*.

=== Q7 -- Controlled execution state

ANSWER:

* *Current controlled semantic roles:* exactly three declared kinds --
  `LookupFormulaSpec` (introduced by
  `add_lookup_helpers(helper_value_mode="formula")`, at its declared
  helper-cell columns); `GroupedMatrix` (introduced by
  `contract_grouped_xref` / `reconstruct_grouped_matrix`, at a
  producer-declared top-level frame name -- not a cell value); and
  `ArtifactManifestSourceFrames` (introduced by `write_artifact_manifest`, at
  the `source_frames` column as a freshly-owned one-level `list[str]`). None
  is Scalar or a Domain composite.
* *Open/extensible generic algebra?* NO. The set is *closed to what accepted
  evidence has established*; it is not a public runtime role registry and not a
  general commutative role algebra. Adding a fourth role requires its own
  producer, location, consumer/exit contract, and composition rule.
* *Multiple roles coexisting:* only under one of exactly two proofs -- a
  *disjoint role product* (each later transition supplies an exact
  footprint/locality proof) or the *one admitted nested* composition,
  `GroupedMatrix` containing `LookupFormulaSpec` at grouped dynamic-value
  cells (produced only by the reviewed formula-helper-into-grouping chain).
* *Arbitrary nesting/composition:* NOT permitted -- no other nesting is
  admitted; matching class/factory/shape/key/copy proves nothing.
* *Uncertified return:* ends every controlled role by rule, regardless of the
  returned value's identity/class/provenance, and forces fresh
  re-establishment.

PRIMARY PERMANENT SOURCE: ch06 `controlled-execution-state` ("The closed
current role set", "Composition"). CONFIDENCE: *clear*.

=== Q8 -- How controlled roles terminate

ANSWER (from ch06 "Role-specific exits"; four distinct outcomes: live /
relocation-carry / pending-cleanup / consumption-termination):

* *GroupedMatrix (standalone):* role-aware transitions that never open the
  carrier (bounded workbook-view selection, whole-frame-transparent cleanup)
  carry it *live, unchanged*. `expand_grouped_xref(drop_source=false)` keeps it
  live; `drop_source=true` *terminates* the carrier's identity inside
  expansion (restored flat source handled by caller's ordinary cleanup). Only
  workbook projection (`grouped_matrix_to_exact_table`/`compose_workbook`)
  terminates it *unconditionally*.
* *FormulaSpec helper state (standalone `LookupFormulaSpec`):* stays *live* at
  its declared column through composition (no relocation needed -- already at
  final column); authorized against the exact output sink kind before the
  saver; whole-frame final cleanup is one terminal path; if it survives
  cleanup, only *consumption* by a FormulaSpec-capable maintained XLSX/ODS
  adapter is a positive terminal exit; an incapable sink is rejected before the
  saver.
* *FormulaSpec-capable XLSX/ODS consumption:* the only positive
  *consumption-termination* for a surviving FormulaSpec role; every other sink
  kind is rejected before the saver runs.
* *Nested `GroupedMatrix[LookupFormulaSpec]`:* forward grouped producer with
  `drop_source=true` marks retained source helper roles `pending_cleanup=true`
  (still *published, live* until final cleanup removes the source frame);
  `expand_grouped_xref(drop_source=false)` leaves the nested role live and
  additionally derives a new standalone role (disjoint product);
  `drop_source=true` terminates outer carrier + nested role together and
  *relocates* the FormulaSpec role to the restored flat source's dynamic
  columns with a pending-cleanup marker; if it survives to projection, the
  outer carrier terminates and the nested role *relocates* to projected
  render-cell locations, then terminates only by FormulaSpec-capable adapter
  consumption.
* *Pending cleanup:* explicitly *not* termination -- the role stays live,
  published state until the exact reviewed cleanup transition terminates it.
* *ArtifactManifestSourceFrames:* consumed only by the manifest's own JSON/YAML
  record adapter; generic ordinary Domain steps and generic sinks never receive
  it.
* *Universal rule:* an uncertified return ends every one of these roles by
  rule, regardless of which exit path was mid-way.

PRIMARY PERMANENT SOURCE: ch06 `controlled-execution-state` ("Role-specific
exits"). CONFIDENCE: *clear*.

=== Q9 -- Description authorization

ANSWER (the less-trusted pipeline-*description* boundary):

* *Opt-in?* Yes. A trusted caller supplies
  `pipeline.LessTrustedDescriptionAuthorization` (normally via its closed
  `from_mapping(...)`); failures raise `DescriptionAuthorizationError`.
* *Omission means:* the existing *trusted-description* behavior is preserved.
* *Registry membership grants permission?* NO -- authorization is
  positive/allowlist; absence denies; a future, not-yet-classified registry
  entry *fails closed* rather than inheriting authority by membership.
* *Built-in registered steps:* the *registered short name* is the authorized
  identity; once a short name and its parameters are authorized, its internal
  framework target is trusted wiring and is not separately re-checked as a
  plugin.
* *Dotted plugin targets:* authorized by their *exact canonical textual
  identity*; a differently spelled alias or re-export requires its own separate
  authorization.
* *When authorization occurs:* checked, and denial takes effect, *before*
  import, acquisition, factory resolution, binding, or resource activation --
  never imported first and checked afterward.
* *Direct callables / direct BoundStep composition:* NOT governed by this
  surface -- a separate, deliberately trusted-programmatic-composition surface
  by design, not a gap in the resolver.

PRIMARY PERMANENT SOURCE: ch06 `description-and-resource-authority`
("Description authorization"). SUPPORTING SOURCE: `interfaces_and_gates.adoc`
("Less-trusted description authorization"). CONFIDENCE: *clear*.

=== Q10 -- Plugin trust model

ANSWER: Authorizing a plugin *DOES* grant standing to run its *exact canonical
textual target* as *trusted same-process Python under its complete current
argument contract*. It *DOES NOT*:

* infer generic path, network, command, or environment permissions from plugin
  argument names/shapes (no recursive argument inspection);
* provide a Python sandbox or any same-process isolation;
* contain malicious same-process code -- `os.remove`, arbitrary
  monkeypatching, `ctypes`, interpreter compromise, and arbitrary
  filesystem/network activity remain explicitly unprotected.

*Process-level security trust vs. framework robustness:* being inside the
security-trust base (trusted operator, or authorized same-process Python) is a
*security-trust classification* granting standing to exercise process-level
capability -- it is *not* a claim that the code is correct/bug-free.
Authorized code may be accidental, sloppy, or malformed without being an
adversary; against its *output*, the framework still applies re-establishment
(uncertified/plugin return), deep-immutable binding (accidental
mutation-through-alias), and bounded ingress classification -- a
robustness/correctness posture *on top of* the security trust base, not a
second weaker security boundary, and claiming no containment of deliberately
hostile same-process code.

PRIMARY PERMANENT SOURCE: ch06 `description-and-resource-authority` +
`trust-threat-model` ("Security trust is not a correctness assumption").
SUPPORTING SOURCE: ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY Decision 1.
CONFIDENCE: *clear*.

=== Q11 -- Resource-sensitive steps

ANSWER:

* *Registry membership grants filesystem permission?* NO -- resource-sensitive
  authority is not a generic property of "being a registered step." Exactly
  *four* registered steps carry resource-sensitive semantics today:
  `apply_overrides`, `write_structured_yaml`, `write_key_value_resources`,
  `write_artifact_manifest` (a current reviewed census, not eternally closed;
  extending it is reviewed architectural work).
* *Authorization before resource activation?* Yes -- e.g. `apply_overrides`'s
  external `overrides_path` is denied before any target binding, existence
  check, or file open.
* *Exact-root/containment style:* writer authority uses an *exact-root* model
  -- an output location is authorized only when its canonical path *equals* one
  of the step's authorized operator roots; an authorized root is never treated
  as a parent under which the description may pick an arbitrary sub-location.
  `write_artifact_manifest` output is opt-in; an optional manifest path must be
  relative and contained under that same authorized root.
* *Checksum-read = write permission?* NO -- `checksum: sha256` additionally
  requires `allow_checksum_reads=True` as a *separate, conjunctive*
  subpermission, considered only after output-root/manifest-path authorization;
  denial precedes any read.
* *Generic filesystem sandbox?* NO -- no general filesystem sandbox and no
  general hostile-concurrent-symlink-race guarantee beyond what was reviewed
  for these four selectors.

*Maintainer adding a new resource-sensitive registered step:* give it its own
explicit reviewed resource-authority classification (do not inherit from
membership); preserve authorization ordering (deny before
import/acquisition/binding/resource activation); keep the fail-closed
census/guard so an unclassified entry denies; add tests proving *no* side
effect (import/resolution/binding/read/write) occurred on the denied path.

PRIMARY PERMANENT SOURCE: ch06 `description-and-resource-authority`
("Resource-sensitive capability"). SUPPORTING SOURCE: Developer Guide
`04_trusted_ingress_extension.adoc` ("Adding a new registered /
resource-sensitive step"). CONFIDENCE: *clear*.

=== Q13 -- Adding a new controlled role

ANSWER: Obligations (all required before framework-managed flow may carry it):

* *Introducing transition:* the one exact reviewed producer/transition, and no
  other (matching class/factory/shape never establishes it).
* *Location:* exact permitted location (cell/column/top-level frame name).
* *Structural contract:* the carrier's required shape/cell contract.
* *Certificate/transition/current-state relationship:* stated as the two-stage
  relationship -- certification proves only eligibility/authorization of the
  bound invocation; the current-state role publishes only *after* the
  invocation executes and its transition applies.
* *Consumers:* which transitions/adapters may read or carry it.
* *Carry/relocation:* what happens on copy/projection/relocation.
* *Termination:* the specific ending transition (not a generic "cleanup").
* *Composition:* a disjoint-product footprint proof or the one admitted
  nesting, for every already-supported role; absence of a proof means
  *unsupported* (forbidden until proven), not merely undocumented.
* *Sink behavior:* which concrete renderer/adapter may terminate by
  consumption; every other sink kind rejected before the saver.
* *Uncertified-return behavior:* ends by rule (not a per-role choice).
* *Tests/guards:* architecture guards proving all of the above.

*Ownership split:* mechanism + current role set are owned by the *Technical
Model* (ch06 `controlled-execution-state` / `certified-executable-binding`);
the *maintainer procedure/checklist* is owned by the *Developer Guide*
(`04_trusted_ingress_extension.adoc`), which links to -- and must not copy --
the canonical set.

PRIMARY PERMANENT SOURCE: Developer Guide `04_trusted_ingress_extension.adoc`
("Adding a new controlled role"). SUPPORTING SOURCE: ch06
`controlled-execution-state`. CONFIDENCE: *clear*.

=== Q14 -- Adding a future Domain composite

ANSWER: The contract must define, at minimum, all *eight* dimensions:

. a named composite kind, distinct from arbitrary Python collection identity;
. a finite cardinality/depth/resource bound;
. the permitted scalar-leaf grammar and Missing semantics for its leaves;
. an explicit carrier plus ownership/copying (alias-safety) rule;
. a schema/declaration and operator-policy capability;
. ingress classification/normalization and *bounded* safe-path diagnostics
  (never echoing raw hostile content);
. DataFrame/pandas interaction (how it behaves as a cell value under existing
  frame operations);
. codec/representation support for every claimed external surface (every
  backend that must round-trip it).

*Why an arbitrary list in an object-dtype cell is not a composite:* a list /
mapping / nested structure merely sitting in an object-dtype cell is not by
itself evidence of Domain composite status. *Why a delimiter-shaped string is
not a composite:* no delimiter/shape inference is ever acceptable -- a numeric-,
list-, or JSON-looking string stays String; a value is never promoted to a
composite because it merely looks like one. Adding a composite is a contract
extension needing its own accepted design/review, not merely a new Python type
or codec.

*Owner of semantic meaning:* the Semantic Model (Domain scalar language) --
today it admits zero composites.

PRIMARY PERMANENT SOURCE: Developer Guide `04_trusted_ingress_extension.adoc`
("Adding a future Domain composite"). SUPPORTING SOURCE: Semantic Model 06
(zero-composite rule; strings that merely look like something else); Internal
Scalar Value Model (bounded `List[Scalar]` remains an undecided candidate).
CONFIDENCE: *clear*.

=== Q15 -- Pre-ingress payload probing

ANSWER: Pipeline-level routing/policy code must not speculatively inspect
less-trusted payload before Trusted Ingress because, before admission, a
payload value may still be an arbitrary, untrusted Python object. *Even
speculative interaction* -- equality comparison, truth-value testing,
`repr`/string conversion, iteration, or hashing -- can trigger that object's
own special-method behavior before any admission check runs. This is the same
hazard the ingress classifier closes by checking *exact-type membership before
any value-level probe* and by keeping *diagnostics bounded* (never echoing a
rejected value's `repr`).

This does NOT mean ordinary Domain transformations can never read payload:
ordinary Domain transformations read *admitted* payload constantly and safely,
*after* admission. The narrow point is that a *pipeline-level routing/policy
decision* must not be the thing doing the reading beforehand.

*Documentation status:* explicitly framed as *an explanatory consequence of
existing boundary rules*, "not a new guarantee this note introduces" -- not a
new standalone security guarantee.

PRIMARY PERMANENT SOURCE: ch06 Pipeline-layer NOTE (speculative-probing),
cross-linking `trusted-ingress-establishment` (classification order + bounded
diagnostics). CONFIDENCE: *clear*.

=== Q18 -- What remains outside the guarantees

ANSWER (major non-guarantees / threat-boundary limits, consolidated):

* *Payload-language boundary vs. sandboxing:* the six-category grammar + bounded
  ingress classification is admission discipline, not a Python/process/OS/
  network sandbox of any kind.
* *Trusted same-process Python vs. hostile-code containment:* the operator, and
  authorized same-process plugin code, are inside the security-trust base; this
  grants standing, not containment -- `os.remove`, monkeypatching, `ctypes`,
  interpreter compromise, and arbitrary filesystem/network activity remain
  unprotected.
* *Trusted Ingress conformance vs. transformation/business validity:* ingress
  conformance is necessary, not sufficient; it says nothing about FK
  resolution, key uniqueness, or a transformation's own preconditions.
* *Output/resource authorization vs. general OS security:* resource semantics
  are only those explicitly reviewed for the four resource-sensitive steps
  (exact-root containment, conjunctive checksum permission); no general
  filesystem sandbox and no general symlink-race guarantee.
* *Ordinary state vs. explicitly controlled framework state:* only the closed
  three-role set is non-ordinary controlled state established by exact reviewed
  transitions; everything else must be ordinary Domain Scalar, and a value is
  never controlled by resemblance.
* Additionally: payload provenance never selects description-authorization
  authority, and description authorization never substitutes for payload
  conformance (both independence directions hold).

PRIMARY PERMANENT SOURCE: ch06 `trust-threat-model` ("Threat Model and
Non-Guarantees" + "Security trust is not a correctness assumption").
SUPPORTING SOURCE: ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY Decisions 1 & 5;
Semantic Model 06 ("necessary, not sufficient"). CONFIDENCE: *clear*.
