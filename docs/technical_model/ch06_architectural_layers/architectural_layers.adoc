=== ARCH-LAYERS — Layer Responsibilities and Boundaries

:updated: 2026-03-31
:status: post-3b

This section defines the conceptual layers of the Spreadsheet Handling architecture and their relationships.
It clarifies boundaries, dependencies, and responsibilities to ensure modularity and avoid leakage between concerns.

The layering follows a clean/hexagonal architecture mindset, with *CLI* and *I/O backends* as ports,
and *Pipeline*, *Domain*, and *Render IR* as the inner structure.

'''

==== 1) CLI Layer — Input Port

*Role:*
User- and system-facing entry point. This layer defines how the system is invoked, configured, and orchestrated from the outside.

*Responsibilities:*
- Provide a unified command-line interface (`sh` tool / `cli.py`).
- Collect configuration, input sources, and command arguments.
- Delegate execution to the **Pipeline** layer.
- Handle exit codes, logging, diagnostics, and global error handling.
- Never contain business logic or transformation rules.

*Must NOT:*
- Perform domain transformations.
- Contain serialization or deserialization logic for workbooks.
- Reference concrete I/O backends.

*Dependencies:*
→ Pipeline layer (calls into it)
← none

'''

==== 2) PIPELINE Layer -- Application / Orchestration Layer

*Role:*
Coordinates the high-level workflow. In DDD terms, this is the **Application Service Layer**.
It wires together domain operations, rendering, and persistence without embedding business rules.

The intended mental model is a parcel service that would never open the payload
to make business decisions or perform routing.

Speaking of routing, this is something we deliberately omitted. The pipeline is
a linear sequence of steps. We avoid branching or conditional execution at
present to keep things as simple as possible.

If we introduce routing and orchestration-level control metadata is ever needed in the future, it must be introduced explicitly as a separate control envelope rather than by
letting pipeline inspect workbook payload such as `_meta`.

*Responsibilities:*

- Execute user-defined or system-defined sequences of transformations (domain pipelines).
- Manage lifecycle and context for transformations (e.g., staging, logging, metrics).
- Orchestrate calls into the **Domain** layer and downstream into **Render IR** or other output ports.
- Maintain order and dependency of tasks; assemble results and errors.
- Pass configured payload from one step to the next without interpreting its
  business semantics.

*Implementation:*

The pipeline is driven by a **REGISTRY** that maps step names (strings) to factory functions.
YAML configuration declares a sequence of steps with their parameters.
`pipeline/build.py::build_steps_from_config()` resolves each step name, calls the factory with
the provided kwargs, and returns a list of `BoundStep` objects (name + config + closure).
`pipeline/execution.py::run_pipeline()` executes already-bound steps in order.
`pipeline/runner.py::run_app()` is the application-level `AppConfig` entry point.

Step factories call **core** and **domain** functions directly -- there is no intermediate
Engine mediator.  The former `Engine` class is retained as a backward-compatible shim
for legacy tests but is not used in production paths.

*Must NOT:*

- Contain domain-specific logic (e.g., how a transformation computes its output).
- Embed rendering or backend-specific logic.
- Inspect workbook payload or `_meta` in order to make feature-specific routing
  or semantic decisions.
- Drift into payload-driven routing or branching by stealth.

*Dependencies:*

* Domain (to execute transformations and apply severity policy)
* Core (for generic leaf utilities that a step may need while staying out of
  domain semantics)
* Render IR (for spreadsheet persistence)
* Directly to other I/O backends (for non-spreadsheet formats like JSON, CSV, XML)

'''

==== 3) DOMAIN Layer -- Core Model and Business Logic

*Role:*::
The heart of the system. Holds all business rules, transformation semantics, and validation logic.

*Responsibilities:*

- Define the **Domain Model**: workbook, worksheet, and transformation objects.
- Implement domain transformations (`Frames -> Frames`).
- Produce **semantic meta-information** that describes the workbook (e.g., which columns are ephemeral, linked, calculated, foreign keys, or required).
- Guarantee deterministic results for equivalent inputs.
- Contain all invariants and validation rules.

*Sub-packages:*

`transformations/`:: Header flattening/unflattening, helper reordering, and other pure data transformations.
`validations/`:: Structured validation checks that produce `Finding` objects.  The severity policy (`apply_severity_policy`) decides control flow (ignore / warn / fail) -- see <<Validation Findings and Severity Policy>>.
`meta_bootstrap.py`:: Merges meta from persistence, profiles, and CLI overrides.
`yaml_overrides.py`:: Loads and applies YAML override documents to frames.

*Must NOT:*

- Reference user interface or CLI.
- Reference spreadsheet libraries, OpenPyXL, or other persistence details.
- Know about file formats or concrete renderers.

*Dependencies:*

-> Core (pure utility functions: FK detection, indexing, DataFrame construction)
<- Pipeline orchestrates it.

'''

==== 3b) CORE Layer -- Pure Utility Functions

*Role:*::
Leaf-level library of stateless, side-effect-free functions used by both Domain and Pipeline.

*Modules:*

`fk.py`:: Wire-format and helper-column utilities (`FK_PATTERN`, `FKDef`, `build_id_value_maps`, `apply_fk_helpers`); legacy convention helpers (`build_registry`, `detect_fk_columns`) remain available but are no longer used by FK-helper primitives for relation inference.
`indexing.py`:: DataFrame column access aware of MultiIndex levels (`has_level0`, `level0_series`).
`df_build.py`:: Build MultiIndex DataFrames from flat records.
`flatten.py`:: Flatten nested JSON dicts with configurable separator.
`refs.py`:: Cell reference arithmetic for rendering.

*Dependencies:*

-> pandas (external)
<- Domain, Pipeline, IO backends

'''

==== 4) RENDER IR Layer -- Rendering Abstraction / Spreadsheet Adapter

*Role:*::
Adapter layer for spreadsheet-like backends (XLSX, ODS, OOXML).
It translates domain results and meta-information into **backend-agnostic layout directives** (RenderPlan).
This layer exists to avoid duplicating spreadsheet-specific logic across different backends.

*Responsibilities:*::
- Convert Domain Workbook + Meta into **RenderPlan** (abstract representation of layout directives).
- Express universal spreadsheet concepts: headers, filters, validations, named ranges, freeze panes, merges, styles, formula directives.
- Provide passes (RenderPasses) to enrich and normalize the RenderPlan.
- Define and maintain the **Render IR model** (WorkbookIR, SheetIR, TableBlock, DataValidationSpec, etc.).
- Ensure backend-agnostic semantics.

*Composition Flow:*::
`compose_workbook(frames, meta)` builds a naive 1-table-per-sheet `WorkbookIR`.
Passes then enrich the IR: `MetaPass` -> `ValidationPass` -> `StylePass` -> `FilterPass` -> `FreezePass`.
Finally `build_render_plan()` flattens the IR into a sequence of `RenderOp` objects.

*Must NOT:*::
- Import or reference backend APIs (OpenPyXL, odfpy, etc.).
- Write files or manage serialization formats.
- Duplicate logic that belongs to domain transformations.

*Output:*::
- **RenderPlan** (sequence of RenderOps).
  Examples: `DefineSheet`, `SetHeader`, `ApplyHeaderStyle`, `SetAutoFilter`, `AddValidation`, `MergeCells`, `WriteMeta`.

*Dependencies:*::
-> I/O Backend (via protocol or adapter)
<- Pipeline invokes it.

'''
==== 5) IO_BACKEND Layer — Output Port / Technical Persistence

*Role:*
Implements concrete persistence adapters (e.g., `.xlsx`, `.ods`, `.csv`, `.json`, `.yaml`, `.xml`).
Each backend converts abstract render or data directives into a specific file format or stream.

*Responsibilities:*
- Implement a protocol interface (e.g., `XlsxBackend.render(plan: RenderPlan, path: str)`).
- Map RenderOps to concrete APIs (OpenPyXL, odfpy, csv, JSON dumpers).
- Handle format quirks (shared strings, zip ordering, themes, data validation syntax).
- Guarantee deterministic output and normalization for tests.
- Provide backend-specific regression tests.

*Must NOT:*
- Reinterpret or change semantic meaning of RenderOps.
- Contain domain logic.
- Expose backend-specific types to upper layers.

*Dependencies:*
→ External libraries (OpenPyXL, odfpy, Python stdlib)
← Invoked by Render IR for spreadsheet outputs or by Pipeline for simpler formats (CSV, JSON, YAML).

'''

==== Layer Dependency Overview

....
CLI
 |
 v
Pipeline  --->  Domain  --->  Core  (leaf, no deps)
 |                                     ^
 +------------>  Render IR             |
                    |                  |
                    v                  |
                IO Backends  ----------+
....

*Rules:*

- **Core** has no inward dependencies -- it is the leaf layer.
- **Domain** depends only on Core.
- **Pipeline** depends on Domain and Core for step logic, and on Render IR for spreadsheet output preparation.
- **Render IR** depends only on IO Backends for final persistence (protocol boundary).
- **IO Backends** depend on Core for cell-reference math and on external libraries for format-specific serialization.
- **CLI** depends on Pipeline and Orchestrator; it never reaches into Domain or Core directly.

'''

[[validation-findings-severity]]
==== Validation Findings and Severity Policy

Validation checks in `domain/validations/` produce structured `Finding` objects instead of
raising exceptions or logging directly.  This keeps the validation functions pure and testable.

*Finding:*::
A frozen dataclass with fields: `category` (string tag like `"duplicate_id"`, `"unresolvable_fk"`,
`"unexpected_helper"`), `sheet`, `column`, `detail`, and a default `severity`.

*Severity:*::
One of `"ignore"` (silent), `"warn"` (log warning), or `"fail"` (raise `ValueError`).

*SeverityPolicy:*::
A `Dict[str, Severity]` mapping category names to a severity.
A special `"__default__"` key provides the fallback.
Example: `{"duplicate_id": "fail", "missing_helper": "ignore", "__default__": "warn"}`

*Flow:*::
. A pipeline step calls one or more pure check functions (e.g., `check_duplicate_ids`, `check_unresolvable_fks`).
. The step builds a `SeverityPolicy` from its configuration (e.g., `mode_missing_fk`, `mode_duplicate_ids`).
. `apply_severity_policy(findings, policy)` iterates over findings, logs warnings, and raises on failures.
. The validation functions themselves never log or raise -- the caller decides policy.

*Current categories:*

[cols="1,2"]
|===
| Category | Meaning

| `duplicate_id`
| A sheet contains duplicate values in the ID column.

| `unresolvable_fk`
| An FK column references an ID that does not exist in the target sheet.

| `unexpected_helper`
| A helper column (prefixed `_`) has no matching FK column.

| `missing_helper`
| An FK column's expected helper column is absent.

| `value_mismatch`
| A helper column value differs from the canonical id-label lookup.
|===

'''

[[trust-and-authority-dimensions]]
==== Trust, Authority, and Validation Responsibility

This section restates, at the layer-map level, distinctions that are already
decided architecture -- link:../ch03_architecture_decisions/ADR-DOMAIN-BOUNDARY-ROBUSTNESS.adoc[ADR-DOMAIN-BOUNDARY-ROBUSTNESS]
and link:../ch03_architecture_decisions/ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY.adoc[ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY]
own the decisions and their rationale; this section does not reopen either.

*Trust and authority are three independent dimensions, not one scalar
level* (ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY, Decisions 1-2):

[cols="1,3",options="header"]
|===
| Dimension | What it answers

| Runtime/operator trust
| A fixed precondition, not a variable one: the operator controlling the
  Python runtime, process invocation, CLI arguments, environment,
  installation, and import path is trusted. The framework does not attempt
  to protect the runtime from its own operator; same-process arbitrary
  Python execution is not sandboxed.

| Payload trust
| Is the data flowing through the pipeline trustworthy? Specialized by
  link:../ch03_architecture_decisions/ADR-DOMAIN-BOUNDARY-ROBUSTNESS.adoc[ADR-DOMAIN-BOUNDARY-ROBUSTNESS]'s
  boundary levels 2-4 (competent-user input / external application-boundary
  artifacts / arbitrary hostile in-process objects); see
  link:../ch04_concepts/domain_boundary_robustness.adoc[Domain Boundary
  Robustness] for the full boundary-level table.

| Pipeline-description trust
| Is the YAML/configuration describing *what to run* trustworthy? Independent
  of payload trust -- a pipeline can be fully trusted while its payload is
  not (the common "our pipeline, someone else's data" case), and a payload
  can be fully trusted while the pipeline that processes it is not. All four
  combinations of (trusted&#124;untrusted payload) x (trusted&#124;untrusted
  pipeline) are architecturally representable; no adopted name or profile
  implies a total ordering across the two.
|===

Security policy governing less-trusted payload or pipeline input is owned by
the trusted runtime operator and supplied *outside* the untrusted pipeline
description; an untrusted pipeline may request additional restriction, never
widen operator policy. Policy combination is per-*kind* (allowlist
intersection, numeric-ceiling minimum, permission conjunction, and so on),
not one generic "more secure" ordering, and rejects unknown, contradictory,
or widening requests rather than silently choosing a precedence rule. See
ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY Decisions 3-4 for the full
combination semantics and the capability-activation timing invariant; none
of that mechanism is re-derived here.

*Output-sink capability is a separate responsibility from payload
normalization* (ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY, Decision 5): what a
sink *does* with an already-accepted value (for example, an ordinary XLSX
payload string beginning with `=` becoming a live formula cell through the
maintained renderer) is not the same question as whether that value was
valid payload. A value is not globally invalid merely because its text
resembles code for some sink it may not even be destined for.
Security-sensitive interpretation belongs to the sink that grants the
corresponding capability. This ADR illustrates, but does not adopt a fix
for, the XLSX example above -- no formula-output policy is decided by this
section.

*Structural, ingress, and Domain-invariant validation stay distinct*
(evidence and full table:
link:../ch08_architecture_details/internal_value_model.adoc#internal-value-model-trust-authority-pointer[Internal
Scalar Value Model, "Structural, ingress, and Domain-invariant validation"]).
In short: external/description structural well-formedness (is this YAML
shape valid, independent of current data?) has diffuse current shapes in
loaders and `configure_*` paths, with no adopted centralized mechanism;
payload ingress validity (does a parsed value belong to the accepted scalar
vocabulary?) has both classification machinery and a mandatory enforcement
point -- Trusted Ingress, established at the framework-managed entry points
below (<<trusted-ingress-establishment>>); and Domain semantic/invariant
validity (does a value violate a Domain invariant given current data and
cross-references?) is enforced within Domain according to semantic locality.
Reusable cross-data/cross-reference checks use
<<validation-findings-severity,Validation Findings and Severity Policy>>;
transformation-local preconditions, reconstruction-local invariants, and
other typed-error checks remain with their responsible Domain paths. Domain
owns Domain semantics, but Domain invariant enforcement need not be
centralized in `domain/validations/`. Do not use the word "validation" for
one undifferentiated responsibility when describing or reviewing a boundary.

*Four responsibility axes, named together only for orientation* (this is an
explanatory cross-reference, not a new runtime or package layer): the
material above already separates along *description/control input*
(pipeline-description trust, above), *payload input* (payload trust, above;
the scalar category vocabulary,
link:../ch08_architecture_details/internal_value_model.adoc[Internal Scalar
Value Model]), *Domain invariants* (<<validation-findings-severity,Validation
Findings and Severity Policy>>, above, plus semantically local Domain
enforcement), and *output adaptation*
(output-sink capability, above; persistence/backend writers). Naming these
four together points to where each is already established; it does not
introduce a fifth place to look, and it authorizes no new source-tree
layering.

'''

[[trusted-ingress-establishment]]
==== Establishing and Re-establishing the Domain Scalar Language

The Semantic Model's
link:../../semantic_model/06_project_semantic_model.adoc#semantic-model-domain-scalar-language[Domain
scalar language] states what the six admitted categories *mean*. This section
owns *where* and *how* a value is admitted into that language, and what
happens after framework-managed execution has to trust code it does not
itself control.

===== Establishment

*Ingress-Conformant Domain Payload* is the postcondition established over a
candidate loaded at an external/router boundary, or returned by code the
framework does not control (an *uncertified producer*, defined below). A
payload satisfies it when every ordinary DataFrame/`ExactTable` cell
classifies into one of the six Scalar categories, and the framework-owned
`_meta` substrate, where present, satisfies its own closed, bounded, acyclic
shape through the common recursive substrate check (using a reviewed
authoring delegate only where a root needs authoring-shape normalization
first). Establishing this state is not itself family- or business-level
validation -- see "Ingress conformance is necessary, not sufficient" below.

Two structural rules govern how a value is classified, independent of which
family or feature reads the result:

* *exact-type membership precedes value-level probing.* A value's actual
  runtime type is checked against the accepted carrier set before any
  value-level test (`== ""`, `isna`, and similar) runs; classification never
  falls back to a looser `isinstance` check after an exact-type check fails.
* *diagnostics stay bounded.* Rejecting an unsupported value records only
  that it was unsupported -- never the raw value or its exact type name --
  so a pathological object cannot trigger its own `repr`, string conversion,
  comparison, hashing, or iteration merely by being rejected.

`_meta`, where present, participates in this same establishment as an owned,
bounded, acyclic framework substrate. A metadata root whose content already
satisfies the generic recursive grammar -- exact-string-keyed exact
`dict`/`list` containers with ordinary Scalar leaves, shared acyclic aliases
permitted, cycles rejected -- is admitted directly by that common recursive
check; it does not need a root-specific delegate merely to exist. A delegate
is required only for a root-specific *authoring normalization or exception*
-- authored content whose shape does not already conform to the generic
grammar and must be transformed into a conforming shape first. Delegates
are closed, centrally reviewed transitions, not a dynamically extensible
plugin surface, and every delegate's output still passes the same generic
recursive check afterward -- no delegate output is exempt by virtue of
delegate status.

===== Re-establishment after an uncertified return

Framework-managed execution sometimes hands control to code the framework
does not itself review -- a plugin callable, an unreviewed wrapper, a
caller-supplied `BoundStep`. Such a producer is *uncertified*: its returned
output is not trusted merely because it was invoked from inside a
framework-managed flow. When execution regains control after an uncertified
producer returns, the framework MUST perform a fresh Ingress-Conformant
Domain Payload pass over the returned candidate before any later ordinary
Domain operation, cleanup, or persistence. Every controlled-role
authorization the payload may have carried (<<controlled-execution-state>>)
ends at that return, by rule, regardless of the returned value's apparent
identity, class, or provenance; a plugin-produced, copied, mutated, or
same-object carrier is rejected unless it passes ordinary re-establishment.
Re-establishment proves nothing about side effects the uncertified callable
may already have performed -- it only proves that the *returned value* is,
once again, admissible Domain state.

[NOTE]
====
*Analogy, not a formal claim.* Readers already familiar with "Parse, Don't
Validate" from typed-language practice may find it a useful shorthand:
establishment reads as "external representation -> trusted Domain data
language," and the controlled-execution-state transitions in
<<controlled-execution-state>> read as "loose executable description/binding
-> trusted execution/transition state." This is an explanatory analogy
only -- not a claim of formal type-level parsing, and it does not imply a
correctness proof beyond what establishment/re-establishment actually check.
====

===== Ingress conformance is necessary, not sufficient

Ingress conformance answers one question: does this payload belong to the
admitted Domain language? It does not answer whether a transformation's own
preconditions hold, whether FK targets resolve, whether a key column is
unique, or any other family-specific semantic question. Transformations keep
their own local preconditions and contracts; conformance is a precondition
for running them safely against admitted state, not a substitute for their
own validation.

[[certified-executable-binding]]
==== Executable Binding Authority

A separate question from *what state a value carries* is *what a bound
executable step will actually execute*. Framework-managed macro flow's
controlled-role transitions (<<controlled-execution-state>>) and its
description-authorization surface (<<description-and-resource-authority>>)
both depend on one structural property: the executable target and the
role-relevant effective configuration used to classify or certify a bound
call are the exact target and configuration that will execute -- not a
description of them that a caller could subsequently make diverge.

Concretely: a bound step's effective configuration is deeply immutable once
constructed, through its sole construction path -- there is no second,
bypassable construction route. No caller-held alias to that configuration,
including a nested mutable value inside it, can alter what the certified
call actually executes, because the classifier and the executor both derive
their view from the same authoritative frozen snapshot -- the executor
materializes a fresh, invocation-local structure from it rather than
receiving the frozen snapshot object itself, but both readings describe the
same immutable configuration, so there is no separately-built view that
could diverge from it. This does not depend on secrecy or provenance: the
target and its
reviewed contract remain ordinarily importable and constructible. What
establishes the property is what constructing and calling the object
*necessarily* causes to happen, not whether a caller could theoretically
obtain the pieces.

The following are each, by themselves, *insufficient* to establish this
property:

* a visible/inspectable configuration value;
* a callable's or class's identity;
* registry membership;
* framework authorship;
* provenance (who produced the value); or
* an object that merely looks like a certificate.

None of these proves that the exact thing inspected is the exact thing that
will run. Only the deep-immutable, single-construction-path binding does.

[[controlled-execution-state]]
==== Controlled Execution State

Most framework-managed execution state is *ordinary*: every location
satisfies the Domain scalar language established above
(<<trusted-ingress-establishment>>). A small, closed set of framework-owned
values is deliberately allowed to be non-ordinary while framework-managed
execution carries them -- but only under an explicitly declared role, never
by external ingress and never by mere resemblance to a role-shaped value.

===== Ordinary state versus controlled roles

....
ConformantFrameworkExecutionState
  ::= OrdinaryStateOutsideControlledRoles + ControlledRole*
....

A `ControlledRole` is a closed descriptor: it names its kind, the exact
framework transition that may introduce it, the location it may occupy, its
structural/cell contract, which later transitions may carry or consume it,
and how it terminates. Framework authorship, a matching Python class, a
matching factory, or a matching shape never establishes a role by itself --
only the descriptor's own exact introducing transition does. A role found at
initial ingress, or surviving an uncertified return, is rejected exactly
like any other non-ordinary value.

===== The closed current role set

Exactly three controlled-role kinds are currently declared:

[cols="2,3,4",options="header"]
|===
| Role | Introduced by | Declared location

| `LookupFormulaSpec`
| The reviewed `add_lookup_helpers(helper_value_mode="formula")` invocation
| Its declared helper-cell columns

| `GroupedMatrix`
| The reviewed `contract_grouped_xref` / `reconstruct_grouped_matrix`
  invocations
| The producer-declared top-level frame name (it is not a cell value at all)

| `ArtifactManifestSourceFrames`
| The reviewed `write_artifact_manifest` invocation
| The `source_frames` column of its producer-declared output frame, as a
  freshly-owned, one-level `list[str]`
|===

None of these three is Scalar or a Domain composite. This set is closed to
what accepted evidence has established -- it is not claimed complete for
every future value; adding a fourth role requires its own producer,
location, consumer/exit contract, and composition rule before
framework-managed flow may carry it.

===== Composition

Two or more roles may coexist only under one of exactly two proofs:

* A *disjoint role product*: each later transition that could affect an
  existing role must supply an exact footprint/locality proof that the
  role's location, payload, provenance, and relocation identity are
  unaffected. Matching class, factory, shape, mapping key, copying the
  container, or an "it did not touch it" observation proves neither a
  product nor a nesting -- only an exact, transition-specific footprint
  proof does.
* The one admitted *nested* composition: `GroupedMatrix` containing
  `LookupFormulaSpec` at the grouped dynamic-value cell role, produced only
  by the reviewed formula-helper-into-grouping chain (helper formulas
  selected as a grouped `value` column). Only the dynamic cells derived from
  that exact selected source column may hold the nested role; every other
  location inside the `GroupedMatrix` remains ordinary Scalar.

This is not a general commutative role algebra, and it creates no public
runtime role registry. No other nesting is admitted.

===== Three distinct authority questions

A single "trust" word conflates three questions that stay distinct:

* *Certificate/binding identity* (<<certified-executable-binding>>) -- does
  this exact bound call necessarily execute what it claims?
* *Controlled-transition authority* -- which reviewed producer may establish
  which role, at which location?
* *Current role state* -- which values presently carry non-ordinary
  authority, right now?

An exact reviewed controlled transition establishes only its own named role,
at its own declared location, under its own closed contract. Framework
authorship or class identity alone establishes none of the three.

===== Role-specific exits

Each role's carry, relocation, termination, and sink contract is exact and
reviewed, not generic. The exits below distinguish four different outcomes a
transition may have -- a role staying live unchanged, a role deriving a
further live occurrence elsewhere while the original stays live too, a role
relocating so only the new location carries it, and a role's authority
ending -- rather than collapsing them into one word.

*`GroupedMatrix` (standalone, ordinary-valued carrier).* Introduced by
`contract_grouped_xref`/`reconstruct_grouped_matrix`. Role-aware transitions
that never open the carrier (bounded workbook-view selection,
whole-frame-transparent cleanup) carry it unchanged. `expand_grouped_xref`
does not uniformly terminate it: with `drop_source=false` the role stays
live, unchanged; with `drop_source=true` the carrier's identity ends inside
expansion, and the restored flat source frame it leaves behind is handled by
the caller's own ordinary frame-removal/cleanup. Only workbook projection
(`grouped_matrix_to_exact_table`/`compose_workbook`) terminates the role
unconditionally.

*The nested `GroupedMatrix[LookupFormulaSpec]` composition.* Established
only by the exact formula-into-grouping match (<<controlled-execution-state>>'s
composition rule): the selected source helper role derives a further live
occurrence at the grouped dynamic cells, while every retained source helper
role -- selected or not -- stays live at its original column. From there:

* `expand_grouped_xref(drop_source=false)` leaves the nested role live and
  unchanged, and additionally derives a new standalone role in the
  configured output value column -- both remain live as a disjoint product.
* `expand_grouped_xref(drop_source=true)` terminates the outer carrier and
  its nested role together, relocates the FormulaSpec role to the restored
  flat source's dynamic columns with a pending-cleanup marker, and
  additionally derives a new standalone role in the output value column.
* If a nested role survives to workbook projection instead, the outer
  carrier terminates exactly as in the standalone case above, and the nested
  FormulaSpec role relocates from its grouped dynamic cells to the
  corresponding projected render-cell locations. Only a FormulaSpec-capable
  adapter (the maintained XLSX/ODS adapters) may then terminate it by
  consumption; every other sink kind is rejected before the saver runs.

*Standalone `LookupFormulaSpec` (never grouped, or restored to standalone by
a drop-mode expansion above).* Introduced, one role per declared helper
output column, only by `add_lookup_helpers(helper_value_mode="formula")`.
It stays live at its declared column through ordinary workbook composition
-- no relocation is needed there, since it is already at its final column --
and is authorized against the exact output sink kind before the saver may
run: only a FormulaSpec-capable adapter may receive it, and any other sink
kind is rejected before saving. It terminates when the exact reviewed final
cleanup transition removes its whole containing frame.

*The manifest role* is consumed only by the manifest's own JSON/YAML record
adapter; generic ordinary Domain steps and generic sinks do not receive it.

No concrete renderer or generic sink ever receives raw controlled-role
identity directly. A "pending cleanup" marker is not termination -- a role
stays live, published execution state until the exact reviewed cleanup
transition terminates it. An uncertified return still ends every one of the
roles above by rule, exactly as stated above, regardless of which exit path
it was mid-way through.

[[description-and-resource-authority]]
==== Description and Resource Authority

Payload trust (<<trusted-ingress-establishment>>) and pipeline-*description*
trust are separate concerns, per <<trust-and-authority-dimensions>>. This
section covers how description authority and resource-sensitive capability
are established for the parts of the framework that accept a less-trusted
description of *what to run*.

===== Framework-managed versus caller-precondition surfaces

Two surface classes exist:

* *Framework-managed entry points* -- `orchestrate`, `run_app`,
  `run_schema_maintenance`, and the CLI/compatibility shims that reach them
  -- automatically establish Domain-language conformance
  (<<trusted-ingress-establishment>>) before any configured step runs, and
  apply controlled-role classification/transition around each step and at
  the final sink.
* *Caller-precondition surfaces* -- `run_pipeline`, the step builders
  (`build_steps_from_config`/`build_steps_from_yaml`, the `make_*_step`
  factories), direct `BoundStep` composition, and direct backend read/write
  -- where the caller owns all conformance, preservation, and
  re-establishment responsibility. `run_pipeline` in particular assumes its
  caller already supplies a conformant execution state for its first step;
  it performs no automatic Trusted Ingress and is not a lesser-trusted
  variant of `orchestrate` -- it is a different, documented contract. See
  `docs/ai_info/interfaces_and_gates.adoc` for the complete
  programmatic-surface matrix.

===== Description authorization

A trusted caller may opt a less-trusted pipeline *description* (dotted
plugin targets, resource-writing steps) into an explicit, positive
capability allowlist rather than trusting it wholesale:

* authorization is positive/allowlist, never a denylist -- absence denies,
  and a future, not-yet-classified registry entry fails closed rather than
  inheriting authority by registry membership alone;
* authorization is checked, and denial takes effect, *before* import,
  acquisition, factory resolution, binding, or resource activation -- a
  denied target is never imported first and checked afterward;
* the registered short name a description uses is the authorized identity;
  once a short name and its parameters are authorized, its internal
  framework target is trusted wiring and is not separately re-checked as if
  it were a plugin;
* an authorized plugin target uses its exact canonical textual identity -- a
  differently spelled alias or re-export requires its own separate
  authorization; and
* an authorized plugin is trusted same-process Python under its *complete
  current argument contract*. Authorization does not recursively inspect
  plugin arguments or infer filesystem, network, command, or environment
  permissions from argument names or shapes. It is not a Python sandbox.

Direct Python callable targets and direct `BoundStep` composition remain a
separate, deliberately trusted-programmatic-composition surface by design --
not a gap in the description-authorization resolver.

===== Resource-sensitive capability

Resource-sensitive authority is not a generic property of "being a
registered step." Today, exactly four registered steps carry
resource-sensitive authorization semantics: `apply_overrides`,
`write_structured_yaml`, `write_key_value_resources`, and
`write_artifact_manifest`. This is a current, reviewed census, not an
eternally closed list -- a future registered step does not inherit resource
authority merely by registry membership; extending this set requires its
own explicit, reviewed classification decision.

For the current four:

* `apply_overrides`'s external `overrides_path` is always denied under
  less-trusted authorization (it must be absent or `None`); denial happens
  before any target binding, existence check, or file open.
* Writer authority uses an exact-root model, applied by the same check to
  all three output-producing steps -- `write_structured_yaml`,
  `write_key_value_resources`, and `write_artifact_manifest`'s own output
  mode: an output location is authorized only when its canonical path equals
  one of that step's authorized operator roots -- an authorized root is
  never treated as a parent under which the description may pick an
  arbitrary sub-location.
* `write_artifact_manifest` specifically: manifest output is opt-in --
  omitting an output directory keeps the existing no-I/O, in-memory-only
  mode, and an authorized output directory is required before an optional
  manifest path or checksum request is considered at all. Where supplied,
  the optional manifest path must be a relative path contained under that
  same authorized root, exactly like the other two writers' paths. Only
  after output-root (and, where present, manifest-path) authorization does
  `checksum: sha256` additionally require `allow_checksum_reads=True` as a
  separate, conjunctive subpermission; denial precedes any read.

None of this claims a general filesystem sandbox or a guarantee against a
hostile concurrent symlink race beyond what was actually reviewed for these
four selectors.

[[layering-and-boundaries]]
==== Layering Under Description and Resource Authority

The layer split above (CLI / Pipeline / Domain / Core / Render IR / IO
Backend) stays intact under description and resource authority:

* The step *builder* (`build_steps_from_config`/`build_steps_from_yaml`) is
  the description-trust boundary: it applies description authorization,
  resolves and binds targets, and returns already-bound `BoundStep` objects.
* The *orchestrator* executes already-bound steps; it did not gain a raw
  step-description surface, a policy parameter, an import responsibility, or
  a provenance-inference role from description authorization. It does not
  become a description language or workflow engine.
* `run_app`'s description-authorization surface applies only to
  constructing `AppConfig.pipeline`. `AppConfig.io` remains entirely
  trusted-operator-owned and outside description authorization -- an I/O
  descriptor is never subject to the same less-trusted-plugin allowlist as a
  pipeline step.

[[trust-threat-model]]
==== Threat Model and Non-Guarantees

Consolidating the non-guarantees implied throughout this section and
<<trust-and-authority-dimensions>> into one place:

* The trusted runtime/operator precondition (<<trust-and-authority-dimensions>>)
  is not relaxed by anything above: the framework does not protect its own
  trusted runtime from its own operator.
* Payload trust and pipeline-description trust remain orthogonal;
  output-sink capability remains a third, separately owned concern that
  receives effective policy rather than acting as a fourth trust source.
* Nothing above is a Python sandbox, a hostile-interpreter-compromise model,
  or a generic network/subprocess policy.
* There is no generic filesystem sandbox; resource semantics are only those
  explicitly reviewed for the four steps named in
  <<description-and-resource-authority>>.
* No general hostile-concurrent-symlink-race guarantee is claimed beyond
  what was actually reviewed for those same four resource selectors.
* Payload provenance never selects description-authorization authority, and
  description authorization never substitutes for payload conformance --
  the two independence directions both hold.

===== Security trust is not a correctness assumption

Being inside the process-level security trust base -- the trusted operator
(above), or same-process Python an authorized plugin target is entitled to
run under its complete current argument contract -- is a *security-trust*
classification: it grants standing to exercise process-level Python
capability, with no same-process isolation guarantee. It is not a claim that
the code exercising that standing is correct, bug-free, or well-behaved.

Authorized same-process code may simply be accidental, sloppy, or malformed
without being a security adversary. Where technically enforceable, the
framework continues to apply its structural, Domain, binding-authority, and
re-establishment contracts against that code's *output*, regardless of who
or what produced it:

* re-establishment after an uncertified/plugin return
  (<<trusted-ingress-establishment>>) applies the same ordinary
  Domain-language check whether the returned candidate came from a careless
  adapter or a hostile one;
* deep-immutable effective binding (<<certified-executable-binding>>)
  protects against ordinary accidental mutation-through-alias -- a real,
  foreseeable bug class -- independent of whether that alias was ever held
  maliciously; and
* bounded ingress classification (<<trusted-ingress-establishment>>) rejects
  a malformed value regardless of which trusted or authorized actor produced
  it.

This is a robustness/correctness posture layered *on top of* the security
trust base above, not a second, weaker security boundary, and it claims no
containment of deliberately hostile same-process code: `os.remove`,
arbitrary monkeypatching, `ctypes`, interpreter compromise, and arbitrary
filesystem/network activity by an authorized plugin remain explicitly
unprotected, exactly as the non-guarantees above already state.

==== Feature Slice: FK-Helper Behavior Across Layers

This section traces the FK-helper feature through all architectural layers to illustrate
how responsibilities are distributed. Since
`FTR-FK-HELPERS-POLICY-DRIVEN-PRIMITIVES-P5` the runtime split is:
*configuration steps produce policy*; *primitive steps consume policy and
write / read derived provenance*. Primitives no longer infer relation
identity from column names.

*1. Core (`core/fk.py`):*::
Pure utility functions that operate on `Frames` (Dict of DataFrames).
`FK_PATTERN` is the cell-level wire format (`id_(<target>)`) used by the
parser / writer and by `infer_fk_relations`. `apply_fk_helpers()` adds
helper columns (label lookups) to a DataFrame given explicit `FKDef`
inputs. `build_id_value_maps()` extracts id-to-value lookup dicts per
sheet from an explicit target registry.
`build_registry()` / `detect_fk_columns()` remain available as utilities
but are no longer called from the FK-helper primitives. These functions
have no side effects and no configuration awareness.

*2. Domain -- Configuration / producers
(`domain/fk_relations.py`, `domain/helper_policies.py`):*::
Two configuration steps write the v2 relation policy under
`_meta.helper_policies.fk` (`schema_version: 2`, list of relations keyed
by `(source_frame, source_column)`).
`infer_fk_relations` scans data frames with bounded heuristics (initial
mode `naming_convention`) and emits inferred relations with
`produced_by.mode: naming_convention`. `configure_fk_helpers` takes
per-target policy from YAML, runs the transitional v1 → v2 bridge, and
emits explicit relations with `produced_by.mode: explicit`.
`apply_v2_relations` is the shared, collision-aware writer used by both
producers.

*3. Domain -- Transformation (FK-helper consumers):*::
`domain/transformations/fk_helpers/enrich.py` (`enrich_helpers`,
registered as `add_fk_helpers`) reads the v2 relation list, materializes
only the helper columns the relations declare, and writes derived helper
provenance under `_meta.derived.sheets.*.helper_columns` (entries:
`{column, fk_column, target, target_key, value_field}`). Missing policy
raises a clear error naming the producer step.
`domain/transformations/fk_helpers/drop.py` (`drop_helpers`, registered as
`remove_fk_helpers`) removes columns identified by derived provenance,
falling back to the v2 policy when provenance is absent; frames with
neither raise clearly -- there is no normal-operation classification by
column name.
`domain/transformations/helpers.py:reorder_helpers_next_to_fk`
(registered as `reorder_fk_helpers`) reads policy / provenance to find
helper columns to move next to their FK column; it does not consult
`FK_PATTERN`.

*4. Domain -- Validation (`domain/validations/fk_helpers.py`):*::
Pure check functions consume `Frames` + defaults and return `List[Finding]`.
They join helper columns against the target using `target_key` from the
v2 policy or from derived helper provenance. `validate_fk_helpers()` is
the convenience aggregator that backs the `validate_fk_helpers` step.
The functions produce findings but never log or raise -- severity is
determined by the caller.

*5. Pipeline (`pipeline/registry.py`, `pipeline/steps.py`):*::
The step registry exposes both producers and consumers as YAML-driven
steps. The architecture guard
`tests/architecture/dependency_guards/test_fk_helper_primitives_consume_policy.py`
pins the no-convention-inference contract for the primitive package.

*6. Render IR + IO Backend:*::
The rendering layer is FK-agnostic. Helper columns are regular DataFrame
columns by the time `compose_workbook()` builds the IR. Styling and
protection passes locate helper columns via the derived helper
provenance (`_derived_helper_column_names` in `rendering/passes/_base.py`),
not by column-name prefix. No FK-specific logic exists in the backend
layer.

*7. CLI:*::
The CLI passes configuration (profile defaults, YAML pipeline) to the
Orchestrator. It never references FK concepts directly.

[[configuration-step-responsibility]]
==== Configuration-Step Responsibility

The FK-helper slice above is one instance of a recurring Domain-level
responsibility split, independently evidenced across multiple transformation
families: *configuration/policy production* is a different responsibility
from *policy resolution during an operation*.

* A *configuration step* (in the sense already defined by
  link:../ch08_architecture_details/pipeline_semantics.adoc[Pipeline Step
  Semantics]'s step-category taxonomy) writes or validates explicit,
  resolved configuration into `_meta`; it is the intended place for
  heuristics and `auto` interpretation. `infer_fk_relations` and
  `configure_fk_helpers` (above) are concrete examples, alongside
  `configure_lookup_helpers`.
* *Policy resolution* is what a later primitive step does with that already-
  resolved configuration at execution time -- it reads it, it does not
  produce or heuristically infer it.

This split is real and stable enough to name, but it is not a mandated file
layout: it does not require every transformation family to expose a
`policy.py` or `configuration.py` module, and this section does not adopt
any universal package skeleton. Whether a given family's producer and
consumer responsibilities live in one module or several remains a
family-local decision.
