== Terms

The *category* column groups entries by which subsystem the term belongs to.
The *meta-system* category covers the foundation vocabulary for the meta
registry; full definitions live in
`docs/technical_model/ch05_registries/registry_semantics/`.

[cols="2,2,10", options="header"]
|===

|
term
|
category
|
explanation

|
pipeline
|
pipeline
|
User-configured sequence of frame transformations and validations. The
pipeline operates on frames and metadata; it does not own spreadsheet
rendering.

|
flow
|
render
|
Sequence of rendering steps in the Render IR layer that turns selected
frames and canonical metadata into backend-neutral render operations.

|
frame
|
data
|
Domain-level tabular data object carried in `Frames`, normally a pandas
`DataFrame` keyed by frame name. A frame is not a workbook sheet.

|
canonical tuple frame
|
data
|
Long-form source or target frame whose configured key columns identify
each semantic tuple. Matrix/crosstable views should be recomposable into
this shape.

|
matrix frame / crosstable frame
|
data
|
Domain-level pivoted frame where row identity remains in columns and a
configured matrix axis becomes payload columns. It may later be projected
to a sheet, but it is not itself a sheet.

|
discriminator
|
data
|
Configured column or value axis used to partition a canonical tuple frame
into discriminator-specific frames, for example locale, product, customer,
deployment mode, or software variant.

|
discriminator-specific frame
|
data
|
Frame produced by applying a discriminator split. It carries one configured
discriminator value implicitly through split metadata or recomposition
config.

|
matrix axis / pivot axis
|
data
|
Configured values that become columns in a matrix/crosstable frame and
become the `column_key` values again when expanded back to tuples.

|
payload value
|
data
|
Editable semantic cell value carried in the canonical tuple frame and
displayed in matrix-frame payload cells. Helper/display columns are not
payload unless explicitly configured as such.

|
workbook view
|
render
|
Rendering policy that selects, orders, names, and annotates frames for
spreadsheet projection. It belongs at the projection boundary, not inside
domain transformation semantics.

|
sheet
|
render
|
Concrete spreadsheet tab in a workbook. Sheets are render/readback
artifacts; domain transformations should refer to frames unless they are
explicitly configuring workbook projection.

|
render IR
|
render
|
Backend-neutral spreadsheet intermediate representation (`WorkbookIR`,
`SheetIR`, `TableBlock`, `RenderPlan`) used between selected frames and
concrete spreadsheet backends.

|
backend
|
render
|
I/O adapter for a concrete storage format such as JSON, CSV, XLSX, or ODS.
Spreadsheet backends render or parse through the spreadsheet contract and
Render IR.

|
original (data)
|
data
|
Data-layer status: the cell content is the authoritative source of its
information. Editing it changes the truth the system holds about the model.
See `ch05_registries/registry_semantics/01_data_and_meta.adoc`.

|
derived (data)
|
data
|
Data-layer status: the cell content is a projection or copy of information
that lives elsewhere. Editing it does not change the underlying truth — the
system either ignores the change, restores the projected value on the next
render, or treats the edit as a signal that the original source should be
reviewed. Distinct from "derived" at the meta layer; see
`ch05_registries/registry_semantics/01_data_and_meta.adoc`.

|
canonical (meta)
|
meta-system
|
Meta-layer role: a meta claim that expresses intent or property, is the
authoritative source for its information, is spreadsheet-neutral,
persistable, and lifecycle-decoupled from any single run. *Canonical*
applies only to meta claims, never to data. Full definition in
`ch05_registries/registry_semantics/02_meta_layer.adoc`.

|
derived (meta)
|
meta-system
|
Meta-layer role: the current-run realization of a canonical claim or
inferred state. Not authoritative; recomputable from canonical sources.
Examples: `__freeze`, `__autofilter`, `__style`, the
`_meta["derived"]["sheets"]` namespace. Distinct from "derived" at the data
layer.

|
operational-carrier
|
meta-system
|
Meta-layer role: the carrier-shaped representation of canonical (or
derived) meta — the form in which meta is written to a concrete backend or
read back from it. Examples: `workbook_meta_blob`, `_hidden`,
`__autofilter_ref`. Not a second canonical source.

|
model meta
|
meta-system
|
Meta classification: claims about durable structural properties of the data
— FK relationships, helper status, validation rules, feature-local intent, codec
configuration, transformation configuration. Losing model meta is a data
integrity issue. Full definition in
`ch05_registries/registry_semantics/03_meta_classification.adoc`.

|
presentation meta
|
meta-system
|
Meta classification: claims about display intent — column widths, freeze
panes, fill colors, autofilter. Persistable and roundtrip-relevant, but
distinct from model meta because the consequences of loss are aesthetic
rather than structural; conflict resolution and adapter portability
requirements are also weaker than for model meta.

|
workbook_identity meta
|
meta-system
|
Meta classification: claims about the workbook itself as a named, versioned
artifact (`version`, `author`, `exported_at`). Neither a model claim nor
display intent.

|
carrier
|
meta-system
|
The concrete backend persistence file produced or consumed by an I/O
adapter — for the current adapters, the `.xlsx` or `.ods` file itself. The
adapter's in-memory object model (openpyxl, odfpy) is not the carrier; it
is the working representation of the carrier during read or write. Full
definition in `ch05_registries/registry_semantics/04_carrier.adoc`.

|
carrier-shape
|
meta-system
|
The serialized form into which canonical meta is reduced for writing into
the carrier (or read out of it). For the current adapters this is
primarily the deterministic JSON blob in the hidden `_meta` sheet, plus
carrier-specific control flags and read-path reconstructions. The
operational-carrier layer in the meta system *is* carrier-shape; the
carrier is the file the carrier-shape gets written into.

|
contract lifecycle
|
meta-system
|
Opt-in registry-entry axis that separates current runtime truth, target
contract intent, and the temporary transition bridge between them, with
an explicit removal condition. Orthogonal to layer (`canonical` /
`derived` / `operational-carrier`), to classification (`model` /
`presentation` / `workbook_identity`), and to backend capability profiles.
Full definition in
`ch05_registries/registry_semantics/05_contract_lifecycle.adoc`.

|
transition bridge
|
meta-system
|
Temporary mechanism by which a registry entry's current and target
contract shapes coexist during a migration. Carries a structured
`status` (`none` / `planned` / `active` / `retired`), `bridge_type`,
`identity_derivation`, owning FTR id, and removal condition. Distinct
from backend capability-profile vocabulary such as
`accepted initial gap`.

|
semantic category
|
value-model
|
One of the accepted internal scalar categories -- String, Boolean, Number,
Missing, Date, DateTime (`core.scalar_values.ScalarCategory`). Not a
concrete carrier class; see *carrier variant*. Full contract in
`ch08_architecture_details/internal_value_model.adoc`.

|
carrier variant
|
value-model
|
A concrete Python/NumPy/pandas runtime type that classifies into a
semantic category without being converted to a single canonical carrier
-- for example `numpy.int64` classifies as Number while remaining a
`numpy.int64`. Carrier acceptance does not imply narrowing or
canonicalization.

|
classification
|
value-model
|
Labeling an already-in-memory value with its semantic category
(`core.scalar_values.scalar_category`) without parsing, coercing,
normalizing, or heuristically inferring semantic type from ordinary
non-missing payload content, and without mutating it. Classification does
perform bounded Missing-carrier recognition (`None`, `""`, and the supported
NaN/`NA`/`NaT` family). Distinct from *normalization*; classification exists
today, general normalization does not.

|
normalization
|
value-model
|
Converting an accepted carrier to one canonical internal representation.
No `normalize_scalar()`-shaped primitive exists anywhere in the codebase
today; general scalar normalization and type resolution were not part of
Phase E's establishment of Trusted Ingress (classification without carrier
narrowing, `ch06_architectural_layers/architectural_layers.adoc`) and remain
a separate, undecided question.

|
Missing (scalar)
|
value-model
|
Recognition, not representation: `is_missing_carrier` answers whether a
value's current carrier (`None`, `""`, or a bounded NaN/`pandas.NA`/`NaT`
family) is a missing one. Not a type or sentinel value. The
spreadsheet-visible missing representation stays the ordinary string
`""`. Distinct from *payload value* above, which is any editable semantic
cell value, missing or not.

|
payload trust
|
trust
|
Whether the data flowing through a pipeline is trustworthy -- independent
of pipeline-description trust and runtime/operator trust. Specialized by
`ADR-DOMAIN-BOUNDARY-ROBUSTNESS`'s boundary levels 2-4.

|
pipeline-description trust
|
trust
|
Whether the YAML/configuration describing what to run is trustworthy --
independent of payload trust. All four combinations of (trusted/untrusted
payload) x (trusted/untrusted pipeline) are architecturally
representable (`ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY`, Decision 2).

|
runtime/operator trust
|
trust
|
A fixed precondition, not a variable one: the operator controlling the
Python runtime, process invocation, CLI arguments, environment,
installation, and import path is trusted
(`ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY`, Decision 1). Same-process
arbitrary Python execution is not sandboxed by the framework.

|
output-sink capability
|
trust
|
What a sink does with an already-accepted value (for example, an XLSX
string beginning with `=` becoming a live formula), as a responsibility
separate from payload normalization (what a value is allowed to look
like). A value is not globally invalid merely because its text resembles
code for some sink (`ADR-TRUSTED-RUNTIME-AND-POLICY-AUTHORITY`,
Decision 5).

|
structural validation
|
validation
|
Is an external/description shape (YAML, configuration) well-formed,
independent of current data? Distinct from *payload ingress validation*
and *Domain invariant validation*. Current implementation is diffuse across
pipeline/config loaders and `configure_*` paths; no centralized structural-
validation mechanism is adopted. See
`ch08_architecture_details/internal_value_model.adoc`.

|
payload ingress validation
|
validation
|
Does an already-parsed value belong to the accepted scalar/carrier
vocabulary before it reaches ordinary Domain transformations?
`core.scalar_values.scalar_category` supplies the classification machinery
Trusted Ingress calls at its mandatory enforcement point, established and
re-established at the framework-managed entry points. See
`ch06_architectural_layers/architectural_layers.adoc`, "Establishing and
Re-establishing the Domain Scalar Language".

|
Domain invariant validation
|
validation
|
Does a value violate a Domain invariant given current data and
cross-references (for example an FK relation pointing at a nonexistent
sheet)? Domain owns the semantics, while enforcement is distributed by
semantic locality: reusable cross-data/cross-reference checks in
`domain/validations/` produce `Finding` objects decided by
`apply_severity_policy`; transformation-local preconditions,
reconstruction-local invariants, and other typed-error checks remain with
their responsible Domain paths. See the Validation Findings and Severity
Policy section of `ch06_architectural_layers/architectural_layers.adoc`.

|
configuration step
|
pipeline
|
A step (in the sense of
`ch08_architecture_details/pipeline_semantics.adoc`'s step-category
taxonomy) that writes or validates explicit, resolved configuration into
`_meta`; the intended place for heuristics and `auto` interpretation.
Configuration/policy *production* is a distinct responsibility from
policy *resolution* during a later primitive step's execution. Does not
imply every transformation family needs a dedicated `policy.py` module.

|
projection
|
transform
|
A broad existing architectural term that must be qualified where ambiguity
matters. Current qualified uses include persistence projection,
workbook/workbook-view projection, header projection, axis projection, and
IR/RenderPlan projection, among other context-specific uses. Projection does
not by itself imply reversibility. For a plain column subset in new Domain
transformation prose, prefer *extraction* or *selection* where that avoids
ambiguity; this preference neither bans nor renames existing projection uses.

|
extraction / selection
|
transform
|
Preferred vocabulary for a plain column-subset operation in new Domain
transformation prose, matching `extractions/frame_extract.py`'s own naming,
where the broad term "projection" would be ambiguous. An extraction
intentionally discards information and does not reconstruct the input
relation.

|
expand / contract
|
transform
|
Paired forward/inverse `Frames -> Frames` step vocabulary (for example
`expand_xref` / `contract_xref`, `expand_compact_multiaxis` /
`contract_compact_multiaxis`). Not every expand/contract pair is claimed
bijective in its own contract; see *bijection*.

|
reconstruction
|
transform
|
The impure, pipeline-facing reverse step that consumes externally-parsed
input (for example `reconstruct_grouped_matrix`, from a parsed
`ExactTable`). Distinct from *expand*, which denotes an ordinary
in-pipeline forward/inverse pair.

|
bijection / bijective
|
transform
|
A transform pair explicitly claimed, in its own contract, to reconstruct
the relevant information without additional assumptions (for example the
`xref_axis_mapping` resolver's ordered bijection). Do not assume every
expand/contract pair is bijective merely because the shapes look similar
-- only pairs that state the claim are bijective. See
`ch08_architecture_details/pipeline_semantics.adoc`'s "Equality and
Bijectivity" section for the full inverse-kind vocabulary
(`bijective` / `conditionally_bijective` / `relation_preserving` /
`projection_only` / `validation_only` / `extraction` / `unknown`).

|===
