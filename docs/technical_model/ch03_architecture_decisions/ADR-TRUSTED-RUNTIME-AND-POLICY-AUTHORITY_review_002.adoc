== Review 001 I-001 closure

*Prior finding:* Decision 4 required rejection before a callable, resource, or
sink capability was "resolved or invoked." The generic word "resolved"
conflated safe parsing and resource canonicalization with Python import and
capability activation. It could therefore prohibit normalization required for
a safe decision or encourage authorization against an uncanonicalized path.

*Correction:* Decision 4 now defines two normatively different phases:

* *authorization preparation* may parse declarative identifiers, structurally
  validate input, consult policy-owned static contract metadata, and
  canonicalize or otherwise normalize a resource identifier so authorization
  can be decided correctly; and
* *capability activation* includes activating, acquiring, or exercising the
  governed capability and must not occur for a forbidden capability before
  rejection.

The corrected text names untrusted-selected Python import/lookup, executable
binding or instantiation, callable invocation, external-resource acquisition/
open, and restricted sink use as activation examples. It also states that the
owning policy contract defines the safe decision inputs and activation boundary
for each capability kind, and expressly declines to prescribe a policy class,
schema, API, binding architecture, import-cache behavior, or resource-
acquisition abstraction.

*Outcome:* *Resolved.* Resulting severity: none. Acceptance impact: none.

== Corrected enforcement timing

The corrected invariant is stronger than "reject before invocation." Python
module import can execute top-level code, constructors or binding operations
can execute behavior, external resources can be acquired before later use, and
sinks can exercise capabilities without calling a pipeline step. The ADR now
requires authorization before the first capability-specific activating
operation, not merely before the final invocation or post-hoc audit.

At the same time, the invariant no longer imposes one universal sequencing
algorithm. It permits the capability-specific preparation needed to decide
policy and delegates the activation boundary to the owning policy contract.
The two examples are explicitly bounded and explanatory rather than a complete
operation taxonomy.

*Outcome:* Pass.

== Python callable example

Maintained `pipeline/dotted_paths.py` demonstrates the distinction without
being promoted into the future policy design:

. `_split_reference` parses and structurally validates the declarative dotted
  identifier.
. `_ensure_module_addressable` applies today's narrow architecture-ownership
  check.
. Only then does `importlib.import_module` import the selected module and
  `getattr` look up the callable.

Focused tests establish that forbidden framework-ingress references and
malformed references fail before import. This evidence supports the corrected
norm: parsing can precede authorization, while an untrusted-selected module
import is capability activation and must not. The ADR does not freeze this
resolver sequence, mistake the current namespace exclusion for a security
policy, or decide the open dotted-extension FTR.

*Outcome:* Pass.

== Filesystem capability example

All three maintained filesystem writers follow the evidence pattern the
correction needed to permit:

* Structured YAML resolves the configured output root, resolves each candidate
  target with `strict=False`, checks root containment, prepares all target
  paths, and only afterward creates parent directories and opens files.
* Key-Value Resource resolves the output root, renders and canonicalizes each
  candidate target, checks containment, and only afterward creates directories
  and opens the target for writing.
* Artifact Manifest canonicalizes and contains reported/manifest paths before
  any configured checksum read or manifest write; only authorized normalized
  targets reach `read_bytes`, `mkdir`, or `open`.

`Path.resolve(strict=False)` is therefore authorization preparation in these
examples. Directory creation, file read/open/write, checksum acquisition, and
sink exercise are activation/use and occur only after containment succeeds.
The ADR uses this as bounded evidence and does not universalize these helpers or
prescribe `Path.resolve` as the policy mechanism for other resource kinds.

*Outcome:* Pass.

== Decision 4 combination regression

Correction 001 changes only the timing paragraphs after the combination list.
The normative per-kind rules remain intact:

* allowlists/capability sets use intersection;
* numeric ceilings use minimum/cap;
* permissions use conjunction or capability removal;
* parameter schemas use compatible intersection;
* widening requests reject;
* unknown fields reject unless the owning policy contract defines a meaning;
  and
* contradictory or incomparable requests reject rather than use implicit
  precedence.

The correction neither adds a generic policy ordering nor weakens any rejection
rule. Authorization preparation cannot widen operator policy; it only computes
the inputs needed to apply the existing rule.

*Outcome:* Pass.
