The ADR extracts the intended five durable constraints faithfully and is
consistent with the accepted runtime-boundary and visible-cell decisions. One
normative enforcement-timing sentence is nevertheless too broad: it requires
rejection before a resource is "resolved" without distinguishing safe parsing
and normalization needed to decide authorization from capability activation.
Read literally, that rule conflicts with the maintained filesystem sinks,
whose safe containment decision necessarily canonicalizes a candidate path
before rejecting traversal. Because the ambiguity sits in the security
invariant future implementations must satisfy, it is Important and gates
acceptance.

Acceptance requires zero Blocking and zero Important findings. This review
therefore records the finding without correcting the ADR, index, accepted
concept, or any implementation artifact.

== Extraction fidelity

The extraction is narrow and faithful apart from the timing precision finding
below. It adopts exactly these five areas:

. the trusted runtime/operator precondition;
. independent payload and pipeline-description authority;
. operator-owned policy supplied outside untrusted pipeline input;
. per-policy-kind combination and rejection semantics; and
. sink-capability ownership separate from payload normalization.

The ADR does not adopt the concept's illustrative public profiles, value or
lifecycle taxonomy, concrete ingress or policy API, parser/resource limits,
FTR candidate map, `run_pipeline` behavior, dotted-extension outcome, or XLSX
formula policy. The context, alternatives, non-goals, relationship, and
consequences sections consistently preserve that narrow extraction.

*Outcome:* Pass.

== Trusted runtime and operator boundary

Decision 1 makes operator control of the Python runtime, process invocation,
CLI arguments, environment, installation, and import path a fixed precondition.
It distinguishes the framework threat model from deployment isolation, states
that same-process arbitrary Python is not sandboxed, and keeps OS/container/
network/filesystem isolation outside the framework guarantee unless deployment
infrastructure supplies it.

The statement that arbitrary trusted plugins/callables remain possible only
"wherever the chosen application contract permits them" is appropriately
qualified. It does not classify every plugin, dotted callable, or directly
composed callable as automatically trusted. This matches
ADR-DOMAIN-BOUNDARY-ROBUSTNESS's rule that local validation cannot contain
arbitrary executable Python already admitted into the process.

*Outcome:* Pass.

== Independent input authority

Decision 2 keeps payload trust and pipeline-description trust orthogonal,
rejects a scalar trust ladder, and requires all four combinations to remain
representable. It explains why the dimensions are meaningful only given the
trusted-operator precondition and does not freeze a profile name or public
representation.

*Outcome:* Pass.

== Operator-owned policy authority

Decision 3 locates authority with the trusted runtime operator and requires
policy to arrive outside the untrusted pipeline description. CLI, application
API, deployment configuration, and operator-controlled environment/service
configuration are examples only, not selected transports.

An untrusted pipeline can request a smaller surface or tighter limits but
cannot widen operator policy. Policy visibility and log visibility are
explicitly not protection. A pipeline's ability to reject itself or make a
capability unavailable through a tighter request is reduced availability, not
a transfer or weakening of authority.

*Outcome:* Pass.

== Policy combination semantics

Decision 4 correctly refuses one generic security ordering:

* allowlists/capability sets intersect;
* numeric ceilings take the minimum/cap;
* permissions conjoin or remove capability;
* parameter schemas use compatible intersection;
* widening, contradictory, and incomparable requests reject; and
* unknown fields reject unless the owning policy contract defines their
  meaning.

The separate widening-rejection rule prevents intersection/minimum from
silently discarding an attempted widening. Unknown-field rejection is a safe
fail-closed forward-compatibility posture, while the owning-contract exception
allows a future contract to define deliberate extension semantics. "Compatible
intersection" is necessarily contract-specific and is not presented as a
generic schema algorithm.

The combination rules pass. The timing sentence attached to them does not;
see I-001.

*Outcome:* Requires correction for enforcement timing only.

== Enforcement timing

The intended invariant is sound: authorization cannot be a post-hoc audit, and
an untrusted selection must not cause arbitrary module-import execution,
callable binding/instantiation with executable behavior, callable invocation,
external-resource acquisition, or sink use before policy permits that
capability.

Maintained dotted-callable code demonstrates the useful distinction.
`pipeline/dotted_paths.py` parses the reference and applies its present narrow
namespace ownership check before `importlib.import_module`; focused tests prove
forbidden and malformed references fail before import. Parsing an identifier is
therefore not the same as importing/resolving the selected Python object, and
neither is the same as binding or invoking it.

Maintained filesystem sinks demonstrate the other half of the distinction.
Their `_safe_target_path` helpers call `Path.resolve(strict=False)` to
canonicalize the candidate and then decide whether it escapes the configured
root. That normalization is required to determine authorization safely; the
file is not opened or written until after the check. The ADR's undifferentiated
"before ... resource ... is resolved" wording can prohibit this safe order or
encourage an unsafe lexical path check.

*Outcome:* Important finding I-001.

== Sink capability and payload normalization

Decision 5 correctly separates value validity from sink interpretation. It
does not globally invalidate formula-, SQL-, shell-, HTML-, or template-looking
text based only on spelling. It assigns security-sensitive interpretation to
the sink and requires the relevant effective operator policy to reach that
sink.

The XLSX statement is evidence, not policy: a focused probe through
`save_xlsx` wrote ordinary payload `=1+1`, and OpenPyXL readback with
`data_only=False` reported data type `f`; no `FormulaSpec` was involved. The
ADR explicitly declines to choose formula/literal-text behavior or claim that
`FormulaSpec` controls every formula-capable cell.

The filesystem-writer statement is also evidence, not generalization. The
three maintained registered writers use sink-local target containment. The ADR
does not invent maintained SQL, shell, or HTML sinks and does not replace
sink-local policy with generic sanitization.

*Outcome:* Pass.

== Findings

=== I-001 -- enforcement timing conflates policy-decision normalization with capability activation

*Severity:* Important.

*Exact locus:* Decision 4, lines 154--158: "Rejection of a forbidden
capability must occur before the corresponding callable, resource, or sink
capability is resolved or invoked."

*Problem:* "Resolved" is not defined and is applied uniformly to callables,
resources, and sink capabilities. The sentence does not distinguish:

* parsing and structurally validating an untrusted declarative name;
* consulting policy-owned static contract metadata;
* canonicalizing a resource identifier so policy can decide containment;
* importing and looking up an untrusted-selected Python callable;
* binding or instantiating a target where doing so can execute code;
* invoking a callable; or
* opening/acquiring a resource or exercising a sink capability.

For Python dotted targets, rejecting before import is a meaningful security
boundary because module import can execute arbitrary top-level code. For a
filesystem target, however, canonical path resolution is part of deciding
whether the target is permitted and must occur before rejection of traversal.
The current wording makes both operations simply "resolution." A future
implementation could therefore either violate the ADR while performing a safe
check or comply literally by checking an uncanonicalized path, which can weaken
containment. It also freezes one timing phrase across policy kinds even though
the ADR correctly rejects generic combination semantics elsewhere.

*Evidence:* `pipeline/dotted_paths.py` lines 31--38 parse/check the dotted
reference before `importlib.import_module`; focused plugin tests confirm
forbidden and malformed references fail before import. In contrast,
`domain/key_value_writer.py` lines 230--238 and the equivalent Structured YAML
and Artifact Manifest helpers call `Path.resolve(strict=False)` before
`is_relative_to(output_dir)` can reject an escaping resource name. Focused
writer tests confirm traversal is rejected before file use.

*Required correction:* Replace the uniform "before ... resolved" rule with a
capability-activation invariant. Permit safe parsing, structural validation,
policy-owned contract lookup, and capability-specific normalization required to
decide authorization. Require rejection before any operation that activates or
acquires the forbidden capability -- including importing untrusted-selected
code, executable binding/instantiation, callable invocation, external-resource
open/access, or sink use. State that each owning policy contract defines its
safe decision inputs and activation boundary; do not select a concrete policy
API or binding architecture.

*Gates acceptance:* Yes.

== Conclusion

The ADR is a faithful and appropriately narrow extraction of the five durable
constraints from accepted Technical Concept 001. Its trusted-operator boundary,
orthogonal input authority, out-of-band operator policy, per-kind combination
rules, sink ownership, existing-ADR relationships, and non-goals are coherent.

It cannot yet be accepted in independent review because Decision 4's security
timing rule overloads "resolved" across materially different operations and
can conflict with the safe normalization needed to authorize resources. A
narrow wording correction is sufficient; no runtime, test, FTR, BUG, concept,
index, or broader architecture change is required or authorized.
