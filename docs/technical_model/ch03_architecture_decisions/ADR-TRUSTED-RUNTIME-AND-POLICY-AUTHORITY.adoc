==== Context

link:ADR-DOMAIN-BOUNDARY-ROBUSTNESS.adoc[ADR-DOMAIN-BOUNDARY-ROBUSTNESS]
answers "how hard must a domain transformation defend against a malformed
value" for one generic caller. It does not give the project a vocabulary for
a narrower, recurring question: a pipeline author trusts their own YAML but
receives payload from outside the application boundary; or a hosting
application wants to run a pipeline written by someone else against its own
trusted data. Reviewers and workflow builders had no shared terms for "safe
against what, assuming which of these two inputs is hostile," and no stated
rule for who is allowed to decide the answer.

Technical Concept 001, *Trusted Ingress, Internal Value Model, and Runtime
Security Profiles*, was drafted to investigate this gap: a current-state
inventory of payload ingress, pipeline addressability, and output sinks; a
sketch of independent trust dimensions; an illustrative policy-representation
shape; and a sketch of the smallest plausible internal value model. It went
through three independent concept reviews (three Blocking and twelve
Important findings in Review 001, two further Important and one Minor finding
in Review 002, both corrected) and was accepted in Review 003 as a
*provisional, explanatory, non-normative, non-implementation-authorizing*
Technical Concept -- acceptance of the document's honesty and internal
consistency, not adoption of its content as architecture.

The concept's own adoption plan anticipated exactly this next step: extract
only the parts of the sketch that are stable independently of any future
implementation choice, through a narrow ADR extending
ADR-DOMAIN-BOUNDARY-ROBUSTNESS. This ADR is that step. It deliberately adopts
a small subset of the concept -- the trusted-runtime precondition, the
independence of payload and pipeline authority, operator-owned policy
authority, per-kind policy combination semantics, and the separate ownership
of output-sink capability -- and leaves everything else (profile names,
internal value taxonomy, boundary-implementation mechanism, FTR candidates)
as unadopted explanatory material.

==== Decision

[source,text]
----
The Python runtime, process invocation, CLI arguments, environment,
installation, and import path are controlled by a trusted operator.

Payload trust and pipeline-description trust are independent questions;
neither is a single scalar security level, and all four combinations of
(trusted|untrusted payload) x (trusted|untrusted pipeline) are
architecturally representable.

Security policy governing less-trusted payload or pipeline input is owned
by the trusted runtime operator and supplied outside the untrusted pipeline
description. An untrusted pipeline may only request additional
restriction, never widen operator policy.

Policy combination is per-kind, not one generic "more secure" ordering, and
rejects unknown/contradictory/incomparable/widening requests rather than
silently choosing a precedence rule.

Output-sink capability (what a sink does with an accepted value) is a
responsibility separate from payload normalization (what a value is
allowed to look like); a value is not globally invalid merely because its
text resembles code for some sink.
----

===== Decision 1 -- trusted runtime/operator precondition

The operator controlling the Python runtime, process invocation, CLI
arguments, environment, installation, and import path is trusted. This is a
normative framework assumption, not a variable condition to be relaxed by a
future feature.

Consequences of this precondition:

* the framework does not attempt to protect the runtime from its own
  operator;
* same-process arbitrary Python execution (plugins, dotted callables, direct
  programmatic composition) is not sandboxed;
* arbitrary trusted plugins/callables remain possible wherever the chosen
  application contract permits them;
* OS, container, network, and filesystem isolation are outside this
  framework-level guarantee unless separately supplied by deployment
  infrastructure the operator controls.

This is the explicit boundary of the framework's threat model, not a
weakness scheduled for a later fix. It restates, at the framework-assumption
level, what ADR-DOMAIN-BOUNDARY-ROBUSTNESS already says about hostile
in-process code: no amount of local validation changes who controls the
process.

===== Decision 2 -- independent payload and pipeline authority

The framework distinguishes two independent external-authority questions
rather than one scalar security level:

. Is the payload trusted?
. Is the pipeline description trusted?

Both questions are meaningful only once Decision 1's precondition holds. They
are orthogonal: a pipeline can be fully trusted while its payload is not (the
common "our pipeline, someone else's data" case), and a payload can be fully
trusted while the pipeline that processes it is not (someone else's pipeline
against the operator's own data). All four combinations --
trusted/trusted, untrusted-payload/trusted-pipeline,
trusted-payload/untrusted-pipeline, and untrusted/untrusted -- must remain
architecturally representable. No public profile name or policy API is
adopted by this decision; a future representation may use named convenience
profiles, explicit orthogonal fields, or a hybrid, provided every combination
stays representable and no name implies a total ordering across the two
dimensions.

===== Decision 3 -- operator-owned policy authority

Security policy governing less-trusted payload or pipeline input is owned by
the trusted runtime operator (Decision 1) and supplied *outside* the
untrusted pipeline description. Plausible future transport mechanisms
include CLI arguments, application-API parameters, deployment-owned
configuration, or operator-controlled environment/service configuration;
this ADR does not mandate CLI-only transport and does not choose among these
adapters.

An untrusted pipeline may request *additional* restriction (narrower limits,
a smaller declared functional surface) but may never widen what the operator
already restricted. The policy's protection does not depend on being hidden:
it may be fully visible and documented in the pipeline or its logs.

===== Decision 4 -- policy combination semantics

Policy combination between operator policy and pipeline requests is defined
per policy *kind*, not by one generic "more secure" ordering:

* allowlists / capability sets -> intersection of operator allowlist and
  requested subset;
* numeric ceilings -> minimum/cap of operator ceiling and requested ceiling;
* permissions -> logical conjunction, or capability removal only;
* parameter schemas -> compatible intersection;
* a pipeline request to widen a restriction -> reject;
* an unrecognized policy field -> reject, unless the owning policy contract
  explicitly defines a meaning for it;
* a contradictory or incomparable request -> reject rather than apply an
  implicit precedence rule.

A policy decision may perform safe authorization-preparation work before the
decision itself is reached: parsing a declarative identifier, structural
validation, consulting policy-owned static contract metadata, and
canonicalizing or otherwise normalizing a resource identifier so that
authorization can be decided correctly. None of that preparation activates,
acquires, or exercises the capability the policy governs, and this ADR does
not prohibit it -- normalization a correct authorization decision requires is
not itself a security violation merely because it runs before rejection.

What must not happen before rejection is *capability activation*: any
operation that activates, acquires, or exercises the governed capability
itself. This includes importing or otherwise looking up Python code selected
by an untrusted pipeline, binding or instantiating a target where
construction can execute code, invoking a callable, opening or otherwise
acquiring an external resource, and exercising a restricted sink. A forbidden
capability must be rejected before any such activating operation runs -- not
as a post-hoc audit.

The owning policy contract for each capability kind defines which operations
are safe authorization inputs and where activation begins for that kind.
These two bounded examples are explanatory, not an exhaustive operation
taxonomy: for an untrusted-selected Python callable, module import is
capability activation, because import can execute arbitrary top-level code,
so rejection must precede import -- rejecting only before invocation would
be too late. For a filesystem target, canonicalizing the candidate path is
authorization preparation, not activation; opening, reading, writing, or
otherwise using the resolved target is activation and must wait for
authorization. This ADR does not define a concrete policy class, schema, or
API, and does not prescribe binding architecture, import-caching behavior, or
resource-acquisition abstractions; it defines the capability-activation
invariant any future representation must satisfy.

===== Decision 5 -- sink capability is separately owned

Payload normalization (what a value is allowed to look like when it enters
the domain) and output-sink security (what a sink does with a value it
already accepted) are distinct responsibilities with distinct owners. A
string is not globally invalid merely because its text resembles spreadsheet
formula syntax, SQL, shell syntax, HTML, or template syntax for some sink.
Security-sensitive interpretation of an accepted value belongs to the sink
that grants the corresponding capability, and that sink must have access to
the effective operator policy (Decisions 3-4) relevant to its own capability.

Current maintained evidence illustrates the principle without this ADR
adopting a fix for any of it: an ordinary XLSX payload string beginning with
`=` currently becomes a live formula cell through the maintained renderer,
independent of the framework's `FormulaSpec` intent type; filesystem-writing
pipeline steps implement their own path-containment rules rather than a
global content filter. These examples are explanatory; this ADR does not
adopt a particular XLSX formula policy, and does not assert that the
framework maintains, or should maintain, SQL, shell, or HTML sinks it does
not currently have.

==== Rationale

* *Why a fixed trusted-runtime precondition, not a variable one.* Once
  arbitrary Python can run in-process, every special method and import path
  it controls is a potential hook; no amount of local validation changes
  who controls the process. Naming this as a precondition -- rather than
  silently assuming it or promising to eventually relax it -- lets every
  other decision in this ADR be stated honestly: they describe what varies
  *given* a trusted operator, not protection from the operator.
* *Why payload and pipeline authority must be independent, not one scalar.*
  The two motivating cases ("our pipeline, someone else's data" and
  "someone else's pipeline, our data") are common, legitimate, and require
  different protections. Collapsing them into one security level either
  over-restricts the common case or silently under-protects the other; the
  project's own concept-review history (Review 001's I-005 finding) showed
  that even a careful first attempt at naming profiles can accidentally
  hide one of the four combinations behind a name that only describes the
  other.
* *Why the operator, not the pipeline, owns policy.* A pipeline is exactly
  the artifact whose trust is in question in the untrusted-pipeline case; a
  policy an untrusted pipeline could set or widen would not be a policy at
  all. Placing authority with the always-trusted operator (Decision 1) is
  the only placement consistent with the framework's own threat model.
* *Why per-kind combination semantics, not a generic ordering.* Step
  allowlists, numeric ceilings, boolean permissions, and parameter schemas
  do not compose under one relation; a single "restricted by" ordering is
  easy to implement as precedence, which is bypassable. Stating the
  invariant per kind, and requiring rejection of anything that does not fit
  a defined kind, keeps a future implementation from silently accepting an
  unrecognized or contradictory request as if it were a narrower one.
* *Why sink capability is separate from payload normalization.* Conflating
  the two produces exactly the wrong fix: a global content filter that
  either fails to protect a genuinely code-sensitive sink (because sink
  interpretation is sink-specific) or wrongly rejects inert payload data
  that merely resembles code for some sink the value is not even destined
  for. The concept review's independently reproduced evidence (an ordinary
  XLSX string beginning with `=` becoming a live formula cell through the
  maintained renderer) shows this is not a hypothetical distinction.

==== Alternatives Considered

. *Extend ADR-DOMAIN-BOUNDARY-ROBUSTNESS's boundary levels directly instead
  of adding new dimensions.* Rejected. That ADR's four boundary levels
  describe what code *may assume* about a value's shape; they do not
  describe *who authored* the payload or the pipeline, which is the
  question this ADR answers. The two models compose (this ADR's dimensions
  specialize that ADR's levels 2 and 3) rather than substitute for each
  other.
. *Adopt the concept's illustrative profile names (`trusted`,
  `untrusted_payload`, `untrusted_pipeline`) as the public vocabulary.*
  Rejected for this ADR. The concept's own Review 001 history showed a named
  profile can silently hide a combination; adopting names now would freeze
  a vocabulary before the representation question (explicit orthogonal
  fields vs. named convenience profiles vs. a hybrid) has its own review.
  This ADR adopts the *dimensions* and the *combination invariant*, not any
  name for either.
. *Adopt a single scalar "trust level" instead of independent dimensions.*
  Rejected. It cannot represent either motivating case without either
  over-restricting or under-protecting one of them; see Rationale above.
. *Say nothing yet and wait for a runtime implementation to force the
  decision.* Rejected. The concept's own adoption plan identified this small
  subset as stable independently of implementation choice, and leaving it
  undecided would let each future FTR re-invent (and likely disagree on)
  the same trust vocabulary the concept review process already spent three
  rounds stabilizing.
. *Adopt the full concept (value model, boundary architecture, FTR
  candidate map) as this ADR's content.* Rejected. Most of that material is
  explicitly evidence and design sketch, not a decision ready for
  acceptance independent of future implementation choices; see Non-goals.

==== Non-goals

This ADR does not decide, and none of the following is authorized by it:

* public security-profile names or a public policy API;
* CLI flag syntax for any policy transport;
* a runtime `SecurityPolicy` class or any concrete policy schema;
* parser or resource limits for any format;
* the internal scalar/value type model;
* the missing/unresolved/spreadsheet-error representation (see the open
  `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`);
* the future structure or mechanism of `domain.ingress`;
* whether `pipeline.run_pipeline` remains a trusted programmatic bypass or
  gains another public boundary;
* the outcome of `FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A`'s open
  architecture assessment;
* an untrusted-pipeline allowlist implementation;
* formula or literal-text output policy for XLSX or any other sink;
* filesystem, container, or deployment-level isolation;
* process or container sandboxing of any kind;
* any concrete FTR or BUG authorization.

These remain downstream work, each requiring its own evidence and its own
separately authorized decision.

==== Relationship to other contracts

* link:ADR-DOMAIN-BOUNDARY-ROBUSTNESS.adoc[ADR-DOMAIN-BOUNDARY-ROBUSTNESS]
  remains authoritative for proportionate boundary robustness and for the
  rule that ordinary in-process validation is not a hostile-code sandbox.
  This ADR specializes that decision's threat model for the case where
  payload and pipeline authorship can vary independently; it does not
  reopen or restate the boundary levels themselves.
* link:ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE.adoc[ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE]
  is unchanged. Nothing in this ADR reopens visible spreadsheet typing, and
  Decision 5's XLSX example is illustrative evidence, not a typing or
  formula-policy decision.
* The accepted Technical Concept
  link:../ch04_concepts/trusted_ingress_and_runtime_security.adoc[Trusted
  Ingress, Internal Value Model, and Runtime Security Profiles] remains
  explanatory evidence and design context for this ADR, not itself adopted.
  This ADR adopts only Decisions 1-5 above; the concept's profile-name
  sketch, internal value/lifecycle taxonomy, boundary-implementation
  mechanics, and FTR candidate map remain provisional, explanatory, and
  non-implementation-authorizing exactly as Concept Review 003 accepted
  them -- not promoted by this ADR.

==== Consequences

* Future work proposing a security-policy representation, an
  untrusted-payload ingress boundary, or an untrusted-pipeline capability
  surface must be consistent with Decisions 1-5, but still requires its own
  FTR with its own evidence; nothing here pre-authorizes runtime work.
* A future ADR or Technical Model contract may extract further durable
  material from the accepted concept (for example the boundary-ownership
  table) once at least one implementation gives it runtime grounding, per
  the concept's own adoption plan. That extraction is not performed here.
* Project Memory curation of this decision is deferred until this ADR
  itself has passed independent review, consistent with the project's
  review-before-curation practice.
* Reviewers evaluating a future untrusted-payload or untrusted-pipeline
  proposal should cite Decisions 2-4 for the trust-dimension and
  policy-combination vocabulary, and Decision 5 to keep sink-specific fixes
  out of a generic payload-validation change.
