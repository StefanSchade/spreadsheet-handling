=== ADR-DOMAIN-BOUNDARY-ROBUSTNESS -- Domain boundaries are proportionately robust, not hostile-code sandboxes

Status: accepted
Date: 2026-07-31
Related backlog: FTR-DOMAIN-BOUNDARY-ROBUSTNESS-P4A

==== Context

Domain transformations increasingly validate pandas, NumPy, configuration,
metadata, and caller-owned Python values at their boundaries. The repository had
no shared statement of *how far* a domain boundary must defend against malformed
or hostile input, so every FTR review re-decided it independently.

`FTR-XREF-AXIS-MAPPINGS-P4A2` made the cost concrete. Three acceptance rounds on
a single internal, pure, read-only resolver escalated the applied threat model
without a shared policy: round 001 found genuine defects; round 002 escalated to
metaclass-controlled diagnostics, an incomplete exact-NumPy-integer set, and a
retained caller-owned `tuple` subclass; round 003 accepted the slice and
explicitly deferred the repo-wide question to "the planned Domain Boundary
Robustness clarification". Each round improved the code, but without a boundary a
reviewer can keep finding one more special-method hook, and a developer cannot
predict when hardening is required, sufficient, or excessive.

==== Decision

[source,text]
----
Domain boundaries robustly handle malformed and unusual values reasonably
implied by their documented pandas, NumPy, configuration, metadata, and
artifact contracts.

They do not promise containment of arbitrary hostile executable Python
behaviour already admitted into the process.
----

Validation robustness is not process isolation. A caller that can execute
arbitrary Python in the same process is already inside the runtime trust
boundary, and no amount of local defensive introspection changes that.

This is balanced by three standing qualifications:

* cheap, simplifying, *local* hardening remains desirable -- when it narrows the
  accepted vocabulary, normalizes at ingress, establishes ownership, avoids
  accidental dynamic dispatch, improves determinism, or simplifies diagnostics;
* workflow-builder responsibility does not excuse weak framework contracts
  (ambiguous behaviour, silent coercion, hidden mutation, weak diagnostics,
  undocumented assumptions, or inconsistent interpretation of a declared
  contract);
* framework responsibility does not extend to sandboxing arbitrary in-process
  code.

The normative, operational rules that follow from this decision -- boundary
levels, guarantees and non-guarantees, ownership, normalization, diagnostics,
atomicity, semantic DRY, and review classification -- live in the Technical Model
concept, not here. This ADR owns only the decision and its rationale.

==== Rationale

* *Why robustness is not isolation.* Once hostile code runs in-process, every
  special method it controls (comparison, hashing, `repr`, iteration,
  conversion, descriptors, metaclasses) is a potential hook. Chasing them with
  local validation is unbounded and cannot succeed; real protection needs a
  serialization, process, or restricted-execution boundary the workflow builder
  owns. Pretending otherwise produces defensive code that is both incomplete and
  unreadable.
* *Why competent-user responsibility stays in the model.* The framework is a
  toolkit of composable capabilities. It cannot foresee every composition or
  decide domain trust for external artifacts; the workflow builder must. This
  matches the application-boundary inquiry
  (`../../cold_storage/working_context/functional_model_inquiry/metadata_foundations/app_boundary_meta_authority.adoc`).
* *Why narrow internal representations are preferred.* Normalizing accepted
  carrier values into exact built-in representations at ingress buys stable
  equality, hashing, ordering, and effective immutability, so internal logic
  need not re-defend against the whole object model. Exact-type restrictions are
  justified by a semantic contract, not applied mechanically.
* *Why readability limits hardening.* Adversarial hardening that obscures the
  domain flow, stacks defensive fallbacks, or invents a broad generic safety
  abstraction is a maintainability cost with no matching isolation benefit. A
  reviewer must be able to follow the main transformation without metaclass
  expertise.
* *Why reviews must not silently expand the threat model.* If each feature review
  invents its own hostile-object criterion, validation semantics diverge and
  work churns. Reviews apply this shared boundary; a genuine repo-wide gap is
  escalated to a separate clarification, not embedded in one acceptance artifact.

==== Alternatives Considered

. *Treat every domain boundary as a hostile-code sandbox.* Rejected. Unbounded,
  unachievable in-process, and it buries domain logic under defensive
  introspection while still not providing isolation.
. *Rely entirely on caller responsibility.* Rejected. It would excuse ambiguous
  contracts, silent coercion, hidden mutation, and weak diagnostics -- the
  framework's own obligations.
. *Create a universal safe-value framework.* Rejected for this slice. It would
  merge distinct identity concepts (physical labels, configured field
  references, canonical identity, visible labels, ordering values, metadata
  paths) behind one abstraction without shared semantics. Extraction is gated on
  a demonstrated second consumer with a matching contract.
. *Let each feature review define its own threat model.* Rejected. It is the
  observed failure mode from the Axis Mapping rounds; it produces inconsistent
  semantics and repeated correction cycles.

==== Non-goals

* A process-isolation, sandboxing, or restricted-execution mechanism.
* A repository-wide exact-type conversion refactor or field-selection rewrite.
* A universal safe-value or broad exception-wrapper utility.
* Deciding external-artifact trust, entity lifecycle, or metadata authority --
  those remain with the application-boundary inquiry and their own modeling work.
