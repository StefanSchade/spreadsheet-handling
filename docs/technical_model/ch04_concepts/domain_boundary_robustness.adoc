== Domain Boundary Robustness

_A domain boundary is proportionately robust: it handles the malformed and
unusual values its own documented contracts imply, and it does not try to
contain arbitrary hostile Python already running in the process._

This concept is the normative owner of the operational rules. The decision and
its rationale live in
link:../ch03_architecture_decisions/ADR-DOMAIN-BOUNDARY-ROBUSTNESS.adoc[ADR-DOMAIN-BOUNDARY-ROBUSTNESS];
readable code examples live in the Developer Guide
link:../../developer_guide/ch06_code_conventions/02_domain_boundary_patterns.adoc[domain boundary patterns catalogue];
the reviewer rule lives in
link:../../ai_info/review_instructions.adoc[review_instructions.adoc]. External
application-boundary trust and metadata authority remain with the
link:../../cold_storage/working_context/functional_model_inquiry/metadata_foundations/app_boundary_meta_authority.adoc[application-boundary inquiry].

=== Why this matters

Without a shared boundary, each feature review re-decides how far validation must
go. Validation semantics then diverge, hardening churns, and defensive code
becomes unreadable. This concept fixes one boundary the whole repository reuses,
so a developer can predict when hardening is required, sufficient, or excessive.

=== Boundary levels

The framework treats input at four levels, distinguished by what it may assume.

[cols="1,3",options="header"]
|===
| Level | What it means for the code

| 1. Trusted internal values
| Produced by validated internal constructors or resolutions: narrow types,
  stable equality/hashing, effective immutability, no caller-owned mutable
  backing, explicit ownership. Internal logic *may assume* these and need not
  repeat ingress validation.

| 2. Competent-user workflow input
| Configuration, Frames, metadata, and artifacts from a competent user or a
  user-assembled workflow. May be incomplete, malformed, stale, or shaped by
  pandas/NumPy scalar/container behaviour. Ingress boundaries *must validate*
  the failure modes the capability contract implies and produce useful
  diagnostics.

| 3. External application-boundary artifacts
| Data entering from outside the managed workflow scope (Git-controlled data,
  hand-edited files, foreign spreadsheets, detached or stale `_meta`). Trust,
  bootstrap, and promotion are *application-level decisions the workflow builder
  owns*; framework-shaped metadata is not authoritative merely because it
  exists.

| 4. Arbitrary hostile in-process objects
| Objects designed to execute or disrupt through comparison, equality, hashing,
  representation, iteration, conversion, descriptors, metaclasses, or mutable
  subclass state. *Actual isolation, not local validation.* The framework may
  reject such values safely when a narrow value contract makes that natural, but
  it does not promise containment.
|===

Levels 2 and 3 overlap in practice; the load-bearing distinction is level 1
(what internal logic may assume) versus level 4 (what local validation must not
pretend to contain).

=== Normative principles

* *Validate at ingress, simplify internally.* Validate or normalize caller-owned
  values once, at the semantic boundary. Downstream code operates on narrow,
  stable values instead of re-defending against the whole object model.
* *Prefer narrow accepted representations when justified.* When subclass
  behaviour is outside the contract, exact built-in representations are
  appropriate (exact strings for stable identities, exact tuples for immutable
  compound identities, normalized built-in integers for supported NumPy integer
  scalars). Exact-type restrictions must have a semantic reason; they are not a
  default style rule.
* *Establish ownership for retained values.* When the framework keeps a
  caller-owned value beyond validation, copy or normalize it: copy accepted
  ordered containers, convert carrier scalars to canonical built-ins, build
  frozen feature-owned value objects. Do not claim effective immutability while
  retaining caller-controlled mutable or behaviourally unstable objects.
* *Normalize supported carrier types into canonical internal values.* Accept the
  documented carrier vocabulary (for example specific NumPy integer scalars) and
  convert immediately to the canonical built-in, so mixed inputs become one
  homogeneous internal type and boundary values cannot overflow.
* *Keep diagnostics deliberate and safe.* Prefer feature-specific exceptions
  carrying field/frame/row/role/config context. Do not execute caller-controlled
  behaviour merely to enrich a message; a constant detail such as
  `unsupported value type` is preferable to unsafe introspection when the
  surrounding context is already actionable.
* *Scope failure atomicity.* A validating transformation must not partially
  publish output, metadata, or caller-graph mutation before the complete
  candidate state validates. State the scope of the promise (for example Frames,
  DataFrames, `_meta`, retained nested caller values); it need not claim that
  consuming an arbitrary caller iterator has no visible effect.
* *No fake sandboxing.* Growing defensive introspection does not substitute for
  process isolation, serialization boundaries, restricted execution, or an
  explicitly trusted format. Solve hostile executable input at a real isolation
  boundary.
* *Readability is a contract quality.* Hardening is proportionate when it narrows
  vocabulary, removes ambiguous dispatch, stays behind a small well-named
  boundary helper, or simplifies the flow. Challenge it when it obscures domain
  logic, stacks fallbacks, invents a broad generic safety abstraction without a
  stable semantic contract, or defends against a threat outside the stated
  boundary.
* *Semantic DRY over syntactic DRY.* A shared helper must represent a shared
  semantic contract, not merely repeated syntax. See below.

=== Ownership, normalization, diagnostics, atomicity, and semantic DRY

These are the same principles applied to concrete decisions a boundary makes:

* *Ownership*: who may mutate a retained value after construction. Answer it by
  copying or freezing at ingress.
* *Normalization*: the single canonical internal form a boundary converts
  accepted carriers into.
* *Diagnostics*: enough semantic context to locate the fault, without running
  the rejected value's overridable behaviour.
* *Atomicity*: the explicitly scoped set of outputs and caller-graph objects that
  are never partially published on failure.
* *Semantic DRY*: extract a shared helper only when at least two genuine
  consumers need the *same* contract -- matching accepted *and* rejected
  vocabularies, matching normalization, ownership, and diagnostics, and the same
  architectural layer. These distinct concepts must not be conflated
  automatically: physical DataFrame column-label validity; configured
  field-reference identity; matrix-axis identity; canonical domain identity;
  visible presentation labels; ordering values; metadata paths. A feature-local
  helper is preferred while only one capability owns the contract.

=== Framework and workflow-builder responsibility

Both sides are load-bearing; neither excuses the other.

The *framework* provides clear capability contracts, deterministic
interpretation, deliberate validation of the failure modes its contract implies,
actionable diagnostics, documented ownership/mutation/failure behaviour, safe and
readable internal representations, and consistent architecture boundaries.

The *workflow builder* chooses and composes suitable primitives, decides trust
and authority for external data and artifacts, handles stale or foreign inputs
across the application boundary, performs application-specific validation and
promotion, and provides operational isolation where hostile *executable* input is
possible.

[IMPORTANT]
====
Workflow-builder responsibility must never excuse ambiguous behaviour, silent
coercion, hidden mutation, weak diagnostics, undocumented assumptions, or
inconsistent interpretation of a declared framework contract.
====

=== How reviews classify findings

Adversarial probes remain valid -- and their findings remain reportable -- when
they test an *explicit* guarantee:

* immutability;
* deterministic ordering;
* exact identity;
* deliberate diagnostics;
* failure atomicity;
* no mutation of the documented caller graph.

Those are correctness findings against the approved contract, not threat-model
expansion. Reviewers, however, must not silently convert arbitrary hostile
in-process behaviour into a new repository-wide release criterion. An unresolved
repo-wide gap is escalated to a separate clarification, not embedded in a single
acceptance review. The operational reviewer rule is in
link:../../ai_info/review_instructions.adoc[review_instructions.adoc].
