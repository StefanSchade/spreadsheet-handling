[[concept-trusted-ingress-and-runtime-security]]
== Trusted Ingress, Internal Value Model, and Runtime Security Profiles

_A domain boundary is proportionately robust, not a hostile-code sandbox; this
concept asks what "proportionate" means once payload trust and
pipeline-description trust are allowed to vary independently of a fixed
trusted-operator assumption, and what a closed internal value model would need
to look like to make that answerable._

Status: *provisional, explanatory, non-implementation-authorizing*. This is
Technical Concept 001 in this area. It is not an accepted architectural
decision, not an ADR, and it does not authorize any runtime change, CLI flag,
configuration key, registry entry, parser limit, or new type.

*Corrected after Independent Concept Review 002; awaiting Independent Concept
Review 003.* Review 001
(link:trusted_ingress_and_runtime_security_review_001.adoc[Independent Concept
Review 001]) returned: *Requires correction -- 3 Blocking, 12 Important, 2
Minor.* A first correction addressed every Blocking and Important finding from
Review 001. Review 002
(link:trusted_ingress_and_runtime_security_review_002.adoc[Independent Concept
Review 002]) confirmed all three Blocking findings resolved and returned:
*Requires correction -- 0 Blocking, 2 Important, 1 Minor* -- one prior
Important finding (I-003) left one stale ownership sentence uncorrected, one
prior Important finding (I-007) had a materially wrong current-state claim
about YAML missing-value normalization, and Review 002 raised one new
Important finding (N-I-001) about the retired `_meta.cell_codecs` metadata
family. This revision corrects all three by re-verifying the underlying claim
against maintained source -- not by adding disclaimers around the prior text.
Both review artifacts are unmodified, remain adjacent to this concept, and are
not included in the Technical Model chapter build (no repository convention
renders review artifacts there). Nothing in this document overrides
link:../ch03_architecture_decisions/ADR-DOMAIN-BOUNDARY-ROBUSTNESS.adoc[ADR-DOMAIN-BOUNDARY-ROBUSTNESS],
link:domain_boundary_robustness.adoc[Domain Boundary Robustness], or
link:../ch03_architecture_decisions/ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE.adoc[ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE],
all of which remain accepted authority this concept must not contradict.

This concept does not claim that the framework provides a Python sandbox, a
process-isolation mechanism, or containment of arbitrary hostile executable
Python already running in the process. See <<tirs-non-guarantees>>.

=== 1. Relationship to existing authority

link:../ch03_architecture_decisions/ADR-DOMAIN-BOUNDARY-ROBUSTNESS.adoc[ADR-DOMAIN-BOUNDARY-ROBUSTNESS]
and link:domain_boundary_robustness.adoc[Domain Boundary Robustness] are
authoritative and unchanged by this concept. Their decision, restated:

* domain boundaries robustly handle malformed and unusual values reasonably
  implied by their documented pandas, NumPy, configuration, metadata, and
  artifact contracts;
* in-process validation is not a security sandbox: the framework does not
  promise to contain arbitrary hostile executable Python already admitted
  into the process;
* framework and workflow-builder responsibility are both load-bearing and
  neither excuses the other;
* runtime hardening beyond that decision needs concrete evidence and a
  bounded, separately authorized FTR.

link:../ch03_architecture_decisions/ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE.adoc[ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE]
is equally authoritative and, per Review 001's B-002 finding, is treated here
as a *load-bearing constraint* rather than background context: visible XLSX/ODS
payload is deliberately collapsed to a string substrate at the parser boundary.
Per Review 002's N-I-001 finding, the *current mechanism* for anything layered
on top of that substrate must follow the ADR's own 2026-07-20 status note, not
its original 2026-06-05 body text: the registry-declared `_meta.cell_codecs`
metadata family the ADR originally described has since been *retired* -- it
had no runtime reader. Current Cell Codec intent lives entirely in explicit
step configuration (`codec_intent` for the position-based contract, `mode`
plus codec parameters for the historical code-row contract), confirmed by
`domain/transformations/cell_codec/frame.py`, and is itself *string-oriented*:
it moves values between compact and expanded cell representations that are
both still strings, not a typed-preservation escape hatch. Legacy
`_meta.cell_codecs` payload surviving in an old sidecar or workbook is
tolerated, inert pass-through sediment, not an active mechanism -- no
maintained code reads it. A future general opt-in typing layer (native JSON /
boolean / datetime preservation) does not exist today; it would be a *new*
explicit contract, not a revival of the retired family, and would still need
to satisfy the ADR's own revisit criteria. Nothing proposed in
<<tirs-value-model>> may be read as license to reopen the substrate itself, or
to imply that a consumer can obtain typed JSON, native booleans, or datetime
preservation today by declaring `_meta.cell_codecs` metadata. Any future
change to the substrate itself requires a successor decision under the ADR's
revisit criteria -- not an ingress or value-model FTR derived from this
concept.

This concept *specializes* the Domain Boundary Robustness decision along two
axes the ADR left open:

. it distinguishes *payload trust* and *pipeline-description trust* as
  orthogonal input-authority dimensions against a fixed trusted-runtime
  precondition, plus a separately modeled output-sink capability/exposure
  concern (<<tirs-trust-model>>), rather than one generic threat level; and
. it sketches the *smallest plausible internal value model* a boundary would
  need in order to state, precisely, which value shapes it accepts and which
  it rejects -- because "handles malformed and unusual values reasonably
  implied by contract" is only checkable against a stated contract, and that
  contract must respect the string-substrate constraint above.

It does not reopen boundary levels 1-4 from the Domain Boundary Robustness
concept; the trust dimensions in <<tirs-trust-model>> are a specialization of
level 2 (competent-user workflow input) and level 3 (external
application-boundary artifacts), read together with the toolkit/workflow-
builder responsibility split from
link:../../cold_storage/working_context/functional_model_inquiry/metadata_foundations/app_boundary_meta_authority.adoc[the
application-boundary inquiry]. Level 4 (arbitrary hostile in-process objects)
is out of scope here exactly as it is out of scope for the ADR.

This concept also relates to, and must not duplicate,
`docs/backlog/roadmap_domain_hardening_sequence.adoc` (active planning note,
2026-08-01), whose *Phase E: establish mandatory trusted ingress* already
sketches a boundary shape (bounded parser -> structural validation -> value
normalization -> trusted internal Frames -> domain pipeline) and an "inert
strings" principle (a string that resembles SQL, shell, or HTML is not
thereby dangerous; injection risk is a sink responsibility). This concept
gives that roadmap phase a fuller current-state inventory; it does not
supersede the roadmap's sequencing, which places the unresolved/missing/
error-value decision (<<tirs-nan>>) before or at the beginning of the internal
type model, which in turn precedes mandatory ingress. Where this concept and
the roadmap note differ in emphasis, the roadmap note's sequencing is treated
as authoritative planning context.

Finally, this concept must not preempt
`docs/backlog/FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A.adoc` -- an open,
unstarted architecture-assessment FTR that owns the full per-surface trust and
compatibility contract for every dotted/callable pipeline extension form,
including all eight surfaces it identifies (registered short-name steps,
plugin callables, direct colon-style factories, registry-owned string targets,
nested configured string targets, direct Python callable targets, direct
`BoundStep` composition, and framework-owned macro flow). Its own non-goals
state plainly that making plugin/factory execution safe for untrusted Python,
or creating a Python sandbox or dependency-isolation mechanism, are out of
scope for that FTR too. <<tirs-pipeline-addressability>> below describes only
the *current mechanical shape* of that surface; it does not preselect that
FTR's Options A-E and defers the audience/stability/compatibility decisions
entirely to it.

=== 2. Problem and motivation

The Domain Boundary Robustness decision answers "how hard must a domain
transformation defend against a malformed value" for one generic caller. It
does not yet give a workflow builder or a framework maintainer a vocabulary
for a question that keeps recurring in practice:

* A pipeline author trusts their own YAML but receives payload data from an
  external Git branch, a partner export, or a public upload -- how much of
  the framework's behavior can they truthfully claim as protection?
* A hosting application wants to run a pipeline written by someone else
  against its own trusted data -- what, if anything, changes about the
  framework's guarantees?
* A reviewer asked "is this safe" has no shared vocabulary for "safe against
  what, assuming which of these two inputs is hostile."

Today the honest answer to all three is narrower than a first pass at this
concept claimed: the framework normalizes exactly one external `_meta` shape
at a small number of boundaries (<<tirs-current-ingress>>), bounds ODS parser
dimensions only (<<tirs-parser-boundary>>), and blocks one specific
dotted-callable namespace from configuration addressing
(<<tirs-pipeline-addressability>>) -- and nothing more. There is no stated
trust model, no closed internal value vocabulary, no operator-facing way to
declare "run this pipeline as if the payload (or the pipeline description)
were untrusted," and at least one maintained output sink (XLSX ordinary
strings beginning with `=`) currently behaves as executable formula syntax
rather than inert text. This concept inventories the current state exactly,
sketches a trust model and illustrative policy/profile shapes, sketches the
smallest plausible internal value model consistent with the accepted
string-substrate ADR, and produces a dependency-ordered map of the narrow FTR
*decisions* that would be needed to make any of this a runtime contract --
without authorizing any of them yet.

[[tirs-string-substrate]]
===== The accepted visible-spreadsheet substrate is a hard constraint

Per ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE, four distinct concerns must stay
separate wherever this concept or a later FTR discusses "what a cell value
is":

. *Raw carrier observation* -- what OpenPyXL's `cell.data_type` or ODS's
  `office:value-type` actually reports before any framework code touches it.
. *Normalized visible spreadsheet string* -- the accepted substrate both
  parsers collapse to (`str(val)` / `str(value)`) at the table-block boundary.
  This is the *only* form visible payload takes once it reaches Frames from a
  spreadsheet carrier, by accepted decision, not by current omission.
. *Structured-backend and programmatic pandas/NumPy values* -- CSV/JSON/YAML/
  XML payload and direct-Python Frames are not subject to the spreadsheet
  substrate collapse at all; they can carry pandas dtype-inferred numerics,
  NaN, or (for direct Frames) arbitrary objects, per the rows above.
. *Opt-in domain typing (no current active mechanism for typed preservation)*
  -- typing is *not* obtained today by declaring `_meta.cell_codecs` metadata;
  that registry-declared family is retired and has no runtime reader. The
  current Cell Codec mechanism reaches this position through *explicit step
  configuration* (`decode_cell_values`/`encode_cell_values` with
  `codec_intent`, or the historical `mode` + parameters form) and is itself
  string-oriented -- it transforms between compact and expanded string cell
  representations, per ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE, not between a
  string and a native typed value. No consumer can obtain native JSON,
  boolean, or datetime preservation today by any maintained mechanism; a
  future general opt-in typing layer would be a new explicit contract, not a
  revival of the retired family.

Any internal value model this concept or a successor sketches
(<<tirs-value-model>>) must describe categories 1-4 above as they are, not
propose a canonical typed scalar that would apply uniformly across spreadsheet
and non-spreadsheet carriers. A canonical *missing/unresolved/error* value
(<<tirs-nan>>) is a narrower, additive concept and does not conflict with the
string substrate: it would still be represented as (or alongside) a string on
the spreadsheet carrier side.

Known contract gaps, stated plainly rather than fixed here:

* XLSX has no resource ceiling comparable to ODS's `ParserLimits`. This is
  not a minor asymmetry -- it means the framework's only current
  spreadsheet-parser resource guarantee is backend-specific, not a
  spreadsheet-format-neutral property.
* No payload ingress path enforces a closed scalar type set beyond the
  spreadsheet string-substrate collapse. CSV, JSON, and YAML have their own,
  not-fully-aligned, ad hoc missing-value behaviors: CSV's directory read
  path applies none (pandas default dtype inference and NaN can survive);
  JSON and YAML both coerce a pandas-recognized missing value to `""` after
  DataFrame construction, via the same `df.where(pd.notnull(df), "")` call.
  YAML's `_meta.yaml` payload is a separate problem from its missing-value
  handling: that file often never reaches ingress as mapping-shaped `_meta`
  at all, regardless of what its individual cell values normalize to (see
  the YAML row above).
* `pipeline.run_pipeline` bypasses `domain.ingress`, the persistence
  boundary, and the final-cleanup executor entirely -- all three run only
  inside `orchestrate()`. This is a documented trusted-programmatic path
  today (see the Direct Python Frames row above), not a security defect, but
  it means "ingress always runs" is not yet true of the framework as a
  whole, and this concept does not decide whether that should change
  (<<tirs-ftr-map>> candidate 9).
* Only JSON has a structured `_meta.yaml` sidecar contract. XML has none.
  YAML's same-named file is loaded as an ordinary, non-mapping sheet and so
  is invisible to the one ingress rule that exists. CSV has neither a
  sidecar nor any `_meta` round-trip at all.
* Formula content aside (<<tirs-sinks>>), XLSX/ODS parsing itself has no
  framework-level policy on embedded macros, OLE objects, or external links
  beyond whatever OpenPyXL/odfpy do by default.

==== 3.2 Pipeline ingress and addressability [[tirs-pipeline-addressability]]

The current mechanics (see `pipeline/dotted_paths.py`, `pipeline/registry.py`,
`pipeline/steps.py`, `pipeline/build.py`):

* every dotted-string resolution used by pipeline configuration --
  registered step targets, `step: plugin` + `dotted:`, direct colon-style
  `step: module:function` factories, and nested `target:` strings passed to
  generic binders -- funnels through the single function
  `resolve_configuration_callable` in `pipeline/dotted_paths.py`;
* that function's only ownership check,
  `ensure_configuration_addressable`, rejects references into
  `spreadsheet_handling.domain.ingress` (and its submodules) with a
  `ValueError`; it does not otherwise restrict which importable Python
  callable a pipeline description may name;
* direct Python callable targets and prebuilt `BoundStep` composition
  intentionally bypass this configuration-derived string classification
  entirely by design -- they are a separate, programmatic surface, not a
  gap in the string resolver;
* `tests/architecture/test_domain_ingress_boundary.py` pins this ownership
  boundary across several distinct assertions, named rather than counted to
  avoid the ambiguity Review 001 flagged in the prior draft: registry
  absence, descriptive-registry absence, unknown-short-name build rejection,
  `step: plugin` dotted resolution, direct colon-style factory resolution,
  nested `target:` string resolution, one centralized resolver ownership
  check (`test_configuration_callable_resolution_has_one_pipeline_owner`),
  and re-export absence from `orchestrator`/`meta_bootstrap`/
  `yaml_overrides`;
* declarative intent (the `step:`/`dotted:`/`target:` string in YAML) is
  therefore separated from the resolved runtime object (the imported
  Python callable) by exactly one checked chokepoint, and that chokepoint
  currently encodes one namespace exclusion, not a general trust policy.

`docs/backlog/FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A.adoc` is the open,
unstarted assessment that owns the full trust/audience/compatibility
decision for this surface, across all eight surfaces it names. It already
states, independently of this concept, that dotted-path syntax checks and
namespace ownership rules "do not make [this] a sandbox" and that making
plugin/factory execution safe for untrusted Python is an explicit non-goal.
This concept's threat-model sketch (<<tirs-trust-model>>,
<<tirs-profiles>>) is written to be consistent with that framing: any future
untrusted-pipeline enforcement would need a fundamentally different mechanism
than today's namespace exclusion -- a host-approved *allowlist* of
declarative steps, parameters, and capabilities, not a larger denylist on top
of the current resolver -- which is exactly the kind of decision that FTR,
not this concept, is scoped to make.

==== 3.3 Runtime policy inputs

CLI arguments (`cli/apps/run.py`), application-API parameters
(`orchestrate(input=..., output=..., steps=...)`), environment-derived
behavior, pipeline YAML (`io`, `pipelines`, `profiles`), and plugin
configuration are all *caller-supplied* today; none of them currently carry
a security-policy concept at all -- there is no `trust_profile` field, no
`--security-profile` flag, and no operator-policy object anywhere in the
runtime. This is consistent with this concept being pre-implementation: the
question "which layer can truthfully own a security policy" has one
uncontroversial answer given the standing assumption below, and no code yet
acts on it.

The framework-wide standing assumption, unchanged by anything in this
concept:

[IMPORTANT]
====
The operator controlling the Python runtime, process, CLI arguments,
environment, installation, and import path is trusted. The framework does
not protect that runtime from its own operator.
====

=== 4. Threat model [[tirs-trust-model]]

Review 001 correctly identified that the prior draft's "four independent
axes" conflated a fixed precondition, two genuinely variable input-authority
dimensions, and a fundamentally different kind of concern (sink exposure)
into one flat list. The corrected structure:

[cols="1,4",options="header"]
|===
| Element | What it is

| Fixed assumption: runtime/operator trust
| The runtime/operator, the Python process, the installation, the
  environment, the import path, and the out-of-band policy owner are
  trusted. This is a *precondition* for everything else in this concept, not
  a variable axis -- stated for completeness, because the two dimensions
  below are meaningless without fixing this one.

| Orthogonal input-authority dimension: pipeline-description trust
| Whether the YAML/step configuration (which steps run, in what order, with
  what dotted targets and parameters) was authored by someone the operator
  trusts to choose arbitrary Python extensions, or by someone the operator
  trusts only to choose from a host-approved declarative vocabulary.

| Orthogonal input-authority dimension: payload trust
| Whether the data and `_meta` entering through a loader originated inside
  the operator's own application scope, or crossed the application boundary
  (foreign spreadsheet, partner export, stale Git-tracked `_meta`, public
  upload).

| Separate concern: output-sink capability/exposure
| How emitted content or side effects are interpreted by whatever consumes
  a sink's output (a spreadsheet application, a filesystem, a downstream
  process), and which capabilities the effective policy grants that sink
  (e.g. which filesystem roots a writer may target, whether formula output
  is permitted). This is *not* a third authoring-trust actor equivalent to
  payload or pipeline authorship -- a plugin invocation that happens to
  write output is still pipeline execution/addressability, not a new sink
  actor. Sink exposure is per-capability and per-consumer, and it must
  receive the *effective policy* computed from the two dimensions above
  (<<tirs-boundary-architecture>>), not be treated as a fourth independent
  trust source.
|===

Payload trust and pipeline-description trust are orthogonal: a pipeline can
be fully trusted while its payload is not (the common "our pipeline, someone
else's data" case), and a payload can be fully trusted while the pipeline
that processes it is not (someone else's pipeline against the operator's own
data -- see <<tirs-profiles>>). Neither dimension, nor the sink concern, adds
up to a Python sandbox or contains already-running hostile in-process code;
that remains outside this concept's and the ADR's scope.

=== 5. Trust-profile and policy-representation sketch [[tirs-profiles]]

Review 001's I-005 finding is decisive here: naming a profile only for the
pipeline dimension (`untrusted_pipeline`) while silently also assuming an
untrusted payload hides the exact combination -- trusted payload, untrusted
pipeline -- that motivated this concept in the first place (<<tirs-trust-model>>'s
"someone else's pipeline against trusted data" case). Two representation
options are recorded, neither implemented, neither preselected:

==== Option A -- explicit orthogonal policy fields (preferred direction)

A conceptual (not implemented) policy shape with independent fields, e.g.:

[source,text]
----
payload_authority:   trusted | untrusted
pipeline_authority:  trusted | untrusted
granted_capabilities: <declarative allowlist / parameter schema / sink policy>
----

This avoids the naming trap entirely: every combination of the two
dimensions is representable without inventing a name for each corner, and
`granted_capabilities` is where sink-specific policy (<<tirs-boundary-architecture>>)
would actually live.

==== Option B -- named convenience profiles over the complete matrix

If named profiles remain useful for documentation or CLI ergonomics, every
one of the four combinations below must be representable, and no name may
imply a total ordering:

[cols="2,2,4",options="header"]
|===
| Payload | Pipeline | Illustrative name and meaning

| trusted
| trusted
| `trusted` -- ordinary operator sink policy; canonical normalization still
  applies; no claim of protection against the operator.

| untrusted
| trusted
| `untrusted_payload` -- parser and value boundaries
  (<<tirs-boundary-architecture>>) apply to the payload; the trusted
  pipeline may still use operator-approved plugins and Python extensions.

| trusted
| untrusted
| *(the previously missing combination)* -- the pipeline is restricted to a
  host-approved declarative surface, but the operator's own trusted payload
  needs no additional payload-side boundary. This is the exact case that
  motivates running "someone else's pipeline" safely.

| untrusted
| untrusted
| A genuinely combined restriction -- both the declarative-surface allowlist
  and the payload boundaries apply. This is what the prior draft's
  `untrusted_pipeline` actually meant; naming it as a combination avoids the
  ladder illusion.
|===

Whichever option (or hybrid) a later decision selects, an untrusted-pipeline
restriction is *always* an allowlist of host-approved declarative steps,
parameters, and capabilities -- never the current namespace denylist scaled
up, per <<tirs-pipeline-addressability>>. Naming, exact field shapes, and
whether Option A, Option B, or a hybrid is preferable are open questions for
review (<<tirs-open-questions>>), not decided here. Nothing above is
implemented, is a public API surface, or should be referenced as though it
were a runtime contract.

=== 6. Operator-owned policy authority

The architectural invariant this concept proposes, stated at the level of
policy *kinds* rather than one generic equation (per Review 001's I-006):

[source,text]
----
operator policy is authoritative and supplied outside untrusted pipeline input
pipeline input may only remove capabilities or tighten orderable limits

effective allowlists      = intersection(operator allowlist, requested subset)
effective numeric ceilings = minimum(operator ceiling, requested ceiling)
effective permissions      = logical conjunction / capability removal only
effective parameter schema = schema intersection

forbidden, widening, unknown, contradictory, or incomparable
pipeline requests = reject
----

A single "restricted by" ordering is not precise enough on its own: step
allowlists, numeric parser ceilings, boolean permissions, filesystem
capabilities, and formula policy do not combine the same way, and a pipeline
attempting to select a *weaker* named profile, or to submit an unrecognized
policy field, must be rejected rather than silently accepted as a narrower
request. Enforcement of this invariant must occur *before* a forbidden
callable is resolved or invoked and *before* a restricted sink capability is
used -- not as a post-hoc audit.

Whatever selection mechanism the operator uses to express policy --
CLI arguments, `orchestrate(...)` parameters, deployment-owned configuration,
or environment/service configuration the operator controls are all plausible
adapters; this concept does not require CLI-only transport -- that policy is
immutable to pipeline input. The policy may be fully visible and documented
in the pipeline or its logs; secrecy is not, and must never be treated as,
its protection mechanism. No concrete API or configuration schema is proposed
here beyond the illustrative shape above; that is implementation work for a
later FTR.

=== 7. Internal value and lifecycle categories [[tirs-value-model]]

The Domain Boundary Robustness concept's boundary levels describe what code
*may assume*; they do not yet give a name to the *shapes* a boundary would
check against. Review 001's I-007 finding showed the prior ten-category
sketch conflated data, Intent, carriers, Resolution, and executable
capability into categories that did not survive contact with the code. This
recut distinguishes categories by *role and lifecycle*, not by primitive
type, and stays consistent with the string-substrate constraint
(<<tirs-string-substrate>>). It remains explicitly not a proposal for a class
hierarchy.

[cols="2,4",options="header"]
|===
| Category | Current state and where it actually shows up

| 1. Raw carrier observation
| What a parser sees before any framework projection: OpenPyXL's
  `cell.data_type`, ODS's `office:value-type`, a `pandas.read_csv`/
  `read_json` inferred dtype, a `yaml.safe_load` scalar. No closed set today.

| 2. Accepted carrier-specific substrate value
| For spreadsheet carriers, this *is* the normalized visible string
  (<<tirs-string-substrate>>) -- an accepted, narrow, already-decided
  contract, not an open design question. For CSV, the substrate is whatever
  pandas' default dtype inference produces (category 3 below), because CSV
  is not subject to the spreadsheet collapse.

| 3. pandas/NumPy carrier value in structured/programmatic Frames
| The actual carrier behind CSV cells (pandas dtype inference on the
  directory read path, possible `NaN`), JSON cells (`dtype=str`-forced, so
  narrower, then missing coerced to `""`), YAML cells (whatever
  `pd.DataFrame(...)` infers from parsed YAML scalars for *non-missing*
  values -- pandas-recognized missing values are then coerced to `""` by the
  same `df.where(pd.notnull(df), "")` call the JSON backend uses), and any
  directly-constructed Frames. Coerced inconsistently per backend for
  non-missing values -- see <<tirs-nan>> for the concrete open instance.

| 4. Canonical domain scalar (where a family contract actually defines one)
| No framework-wide instance exists today. Individual transformation
  families may define narrower canonical scalars for their own inputs; this
  category names the pattern, it does not claim a current framework-wide
  example.

| 5. Missing value
| Represented today as `""` (JSON and YAML both apply the same
  `df.where(pd.notnull(df), "")` coercion after DataFrame construction),
  untouched pandas `NaN`/`NA` (CSV's directory read path only, which applies
  no such coercion), or an absent key. No single canonical missing-value
  token is chosen across the codebase.

| 6. Unresolved reference
| Not currently a distinct category anywhere. An FK helper that cannot
  resolve currently collapses into category 3/5 territory; see <<tirs-nan>>
  for the current, carefully-scoped evidence of what it collapses into today.

| 7. Spreadsheet or carrier error
| Not currently modeled. LibreOffice/Excel error tokens (`#NAME?`, `#N/A`)
  are read back as whatever the parser library produces (usually a string
  under the string-substrate collapse); nothing in the framework
  distinguishes "this cell holds the domain string `#N/A`" from "this cell
  holds a spreadsheet error token."

| 8. External structured metadata (before feature ingress)
| `_meta` as read from a sidecar or workbook before `domain.ingress` runs.
  Per <<tirs-current-ingress>>, only the JSON backend reliably supplies this
  as a mapping; XML never supplies it; YAML supplies a non-mapping
  `_meta.yaml` DataFrame that ingress cannot see. Currently `Any`-shaped
  except for the one root (`legend_blocks`) ingress normalizes when it is
  reachable at all.

| 9. Runtime metadata after the rules that currently exist
| `_meta` after `domain.ingress`'s one rule has run. Still `Any`-shaped in
  the type system; "after the rules that exist" is a narrower and more
  honest claim than "trusted" or "validated against a closed contract."

| 10. Persistable metadata after output projection
| `_meta` after `pipeline/persistence_boundary.py:project_meta_to_persistable_contract`
  has run, immediately before the saver. This projection is an *output*
  boundary that drops Resolution and runtime-only facets before
  serialization -- it does not construct or certify a trusted runtime
  *ingress* view; conflating the two (as the prior draft's category 7 did)
  overstates what persistence projection does.

| 11. Authored backend-neutral Intent
| A declarative value that survives a clean re-run unchanged, per
  `agent_rules.adoc`'s persistence-boundary rule: `legend_blocks[*].placement`,
  `xref_crosstable[*].dense_axes.columns_from`, `workbook_view`, and --
  confirmed by reading `core/formulas.py` -- `FormulaSpec`
  (`ListLiteralFormulaSpec`, `LookupFormulaSpec`). These are plain, frozen,
  `__post_init__`-coercing dataclasses, exported in `__all__` and directly
  constructible by any caller, not gated behind their `list_literal_formula`/
  `lookup_formula` factory-function convenience wrappers. This category
  already exists in practice; it is not new here.

| 12. Materialized Resolution and runtime-only metadata
| A value materialized from current data/layout/pipeline state on every run
  (`legend_blocks[*].resolved`, `xref_crosstable[*].dense_axes.resolved`,
  `xref_crosstable[*].column_keys`). Never persisted; the persistence
  boundary exists specifically to drop this category before any saver runs
  (see category 10's correction above for what that boundary actually is).

| 13. Controlled internal carrier
| `ExactTable` and `GroupedMatrix` are *already implemented and exercised*
  Frames-boundary carriers -- produced by workbook projection and by a
  validated feature-owned constructor respectively, with focused public
  roundtrip tests using both. They are not a hypothetical future pattern;
  this category documents what already exists, and a future internal-typing
  slice would extend the *pattern*, not invent the first instance.

| 14. Executable runtime capability
| The actual executable objects in the runtime: `pipeline.types.BoundStep.fn`
  (the callable a bound step wraps) and the resolved Python callable
  `resolve_configuration_callable` returns. These are *not* payload value
  categories -- they never appear inside Frames cell data on any documented
  path -- and must not be grouped with inert Intent objects like
  `FormulaSpec` (category 11's error in the prior draft). `FormulaSpec` is
  data describing a formula; `BoundStep.fn` is code that runs.
|===

What actual current use shows about the primitives named in the task brief:

* `None`, `bool`, `int`, `float`, `str`, `date`, `datetime` all appear as
  ordinary Python values inside `Frames`/`DataFrame` cells with no framework
  wrapper outside the spreadsheet string-substrate collapse -- pandas' own
  dtype machinery is the only thing standing between a non-spreadsheet cell
  and an arbitrary object today.
* `Decimal` does not currently appear anywhere in the read/write paths
  inspected for this concept; if a future scalar contract needs exact
  decimal arithmetic, that is new scope, not a codification of existing
  behavior.
* pandas `NA`/`NaN`/`NaT` and NumPy scalar values are the actual carriers
  behind categories 3/5 above, coerced inconsistently per backend for
  *missing* values -- CSV's directory read path retains them (no `dtype=str`,
  no post-construction coercion), while JSON and YAML both normalize a
  pandas-recognized missing value to `""` via the same
  `df.where(pd.notnull(df), "")` call. For *non-missing* rich values, YAML
  still depends on whatever `pd.DataFrame(...)` inferred from the parsed
  scalar, since that coercion only touches null cells.
* pandas `Timestamp` appears wherever a date-like column round-trips
  through pandas without an explicit cast; no canonical decision exists for
  whether a future scalar contract should retain `Timestamp` or normalize to
  `datetime.date`/`datetime.datetime`.
* Mappings and lists *do* legitimately appear in cells and metadata today
  (`_meta.legend_blocks` entries, `_meta.helper_policies.fk` relation
  lists, nested JSON produced from `MultiIndex` columns) -- these are
  places where domain code truthfully requires structured, not scalar,
  values, and a future contract must keep them as structured values rather
  than forcing scalarization. Mappings/lists are not cell scalars merely
  because pandas can hold them in an object column.
* Category 14's executable capabilities do not currently appear inside
  Frames cell data on any documented path; they appear, deliberately, as
  the resolved targets of pipeline steps. The distinction this concept draws
  is the same one `FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A` already draws:
  "importable and callable" is not "found inside untrusted payload data."
* Where existing domain code truthfully requires opaque or heterogeneous
  values (a DataFrame cell that must round-trip whatever the source
  spreadsheet contained, or `_meta` roots not yet covered by
  `domain.ingress`), `Any` currently hides a boundary that has not been
  designed yet, not a stable owned shape it would be safe to type
  immediately. The honest statement is "not yet decided," not "correctly
  left open forever."

This sketch deliberately stops here. It does not propose a scalar type
union, a `CellValue` class, or a migration plan -- that is exactly the scope
`roadmap_domain_hardening_sequence.adoc` Phase D reserves for a later,
dedicated slice, and <<tirs-nan>> is a stated prerequisite only for the
missing/unresolved/error portion of it (categories 5-7), not for categories
that are already stable in practice (11-13).

=== 8. The unresolved/missing/error dependency [[tirs-nan]]

Review 001's I-008 finding requires separating two different pieces of
evidence that the prior draft had merged into one "fully traced" narrative.
Neither is fully traced; both are read in full for this concept.

*Historical BUG evidence.* `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A`
records a reproduction at historical HEAD `8f8b519`: an FK helper whose
source key is empty (`home_place_id: ""`) reached canonical JSON as the
literal string `"nan"`. The BUG's own "Root cause sketch" section is
explicitly headed *"still to be pinned"* and records three plausible
carriers (FK helper materialization via `core/fk.py:_norm_id` returning
`None` for an empty/NaN key; a downstream stringification artifact; or
replay of already-contaminated canonical data, which the BUG separately
rules out for that specific reproduction). This concept does not claim more
certainty about the cause than the BUG itself claims.

*Current maintained xfail evidence.* `tests/roundtrip/test_pathological_cell_contracts.py`
(current file, re-read for this correction) has evolved: it now uses a
*non-empty but unresolvable* key (`ENT-MISSING`) rather than an empty source
key, and its own `reason=` string states that the current no-cleanup
reimport path observes an *ordinary empty-string* helper value -- not
`"nan"`. The test is `xfail(strict=False)`, asserting only that the helper
value must not be `"nan"` or `""`; the final representation (null,
structured finding, typed unresolved token, or another shape) remains
undecided by the BUG. The historical `"nan"` symptom and the current
empty-string symptom are both real observations, from different scenarios,
neither of which the BUG has resolved into a chosen contract.

Three contract options remain recorded in the BUG (empty/null; structured
finding via the existing `derived_column_findings` mechanism; spreadsheet-
error preservation as a partial complement) -- this concept does not choose
among them, and does not claim the root cause is pinned.

Classification for this concept's purposes, narrowed per Review 001: this
resolution is a *prerequisite only for finalizing the missing/unresolved/
error portion* of the internal value model (<<tirs-value-model>> categories
5-7) and for any ingress rule that would enforce that final semantics. It is
*not* a blocker for documenting or narrowly typing the already-stable
categories -- Intent, Resolution, and controlled carriers (categories
11-13) -- which need no missing-value decision to be described accurately.
`roadmap_domain_hardening_sequence.adoc` places this decision "before or at
the beginning of" the internal type model (Phase C, then Phase D); this
concept's narrower prerequisite claim is consistent with, and does not
contradict, that ordering.

=== 9. Boundary architecture and control flow [[tirs-boundary-architecture]]

Five separate ownership concerns remain useful, but Review 001's I-010
finding is correct that "separate owner" was previously written as though it
meant "independent of all preceding data and policy flow," which is wrong in
the relevant sense. This section keeps the five owners and adds the
distinctions the prior draft collapsed: ownership independence is not the
same thing as execution order, configuration-binding order, data flow, or
immutable effective-policy propagation.

[cols="1,3,3",options="header"]
|===
| Boundary | Owner | When it actually runs / what it actually depends on

| 1. Parser/resource
| Format-specific parser + `io_backends/parser_limits.py` (ODS only today)
| Runs at *payload load time*, before anything else in this list. Owns
  bytes/archive/dimension limits; today, only ODS dimension limits exist.

| 2. Structural/scalar ingress
| `domain/ingress/` (one rule today), plus each backend's ad hoc
  missing-value handling
| Runs immediately after load, inside `orchestrate()`, before the first
  configured step. Depends on boundary 1 having produced *some* scalar to
  normalize; does not itself establish general Frames-structure or scalar
  trust (<<tirs-current-ingress>>).

| 3. Pipeline authorization/addressability
| `pipeline/dotted_paths.py` (configuration binding/resolution)
| Often resolved *while building configuration* -- e.g. at CLI step-binding
  time, before `orchestrate()` is even called, and independent of when
  payload parsing happens. A pipeline built this way, or a directly
  constructed `BoundStep`, does not become safer merely because boundary 2
  "has run" -- direct programmatic composition can bypass boundary 3
  entirely by design (<<tirs-pipeline-addressability>>).

| 4. Domain execution
| Each transformation family, per Domain Boundary Robustness
| Runs at step-invocation time. What a family may assume depends on *which
  entry route* actually delivered its input: a family invoked via
  `orchestrate()` after boundary 2 ran gets more than one invoked via direct
  `run_pipeline` with a hand-built `BoundStep`, which gets none of boundaries
  1-3's guarantees at all.

| 5. Output sink
| Each sink-specific writer/serializer
| Runs *after* domain execution, at output time. Separately owned does not
  mean data-independent: a sink receives whatever the domain layer produced,
  and -- once any policy representation exists (<<tirs-profiles>>,
  section 6) -- it must also receive the *immutable effective policy/
  capability context* relevant to it (which filesystem roots it may target,
  whether formula output is permitted). Routing that concern through a
  global cell-content filter instead of sink-local policy would be a
  mistake this concept explicitly warns against.
|===

The project should continue to reject a universal `sanitize_everything()`
helper: parser constraints stay parser-owned, domain invariants stay
family-owned, addressability stays pipeline/application-owned, and formula/
path/serialization behavior stays sink-owned. What changes from the prior
draft is only the claim about *independence*: these are independently
*owned*, not independently *executed*, and a correct future policy-
propagation design must follow the actual binding-time/load-time/
invocation-time/output-time sequence above, not an idealized "all boundaries
run once, in this order, for every entry path" model that the direct
`run_pipeline` and direct-`BoundStep` paths already falsify.

=== 10. Existing `domain.ingress` assessment [[tirs-current-ingress]]

Read in full for this concept (`src/spreadsheet_handling/domain/ingress/`,
its architecture guard, and its integration test):

* *Current exact responsibility*: normalize `_meta.legend_blocks` from
  external list-or-mapping authoring sugar into one canonical mapping form,
  and strip a stale `resolved` Resolution facet. Nothing else.
* *Framework-owned and non-addressable*: yes, confirmed by
  `tests/architecture/test_domain_ingress_boundary.py`'s named assertions
  (<<tirs-pipeline-addressability>>).
* *External forms already canonicalized*: exactly one -- `_meta.legend_blocks`
  list form, and only when it actually reaches ingress as a mapping
  (<<tirs-current-ingress>> depends on the payload backend -- see §3.1's
  `_meta.yaml`/YAML finding). Every other `_meta` root and every
  Frames/DataFrame structural question is untouched.
* *`run_pipeline` bypasses it*: confirmed via `pipeline/execution.py`,
  which contains no call into `domain.ingress`; only `orchestrate()`,
  `bootstrap_meta`, and `apply_overrides` invoke it.
* *Does not yet establish trusted Frames generally*: it does not validate
  Frames structure, scalar values, other metadata roots, depth/size,
  callables, carrier identity, or arbitrary objects.
* *Suitable for extension as a phase, but the current mechanism is not
  pre-selected for that extension*: Review 001's I-009 finding is correct
  that one Legend Blocks rule does not prove the same flat, unphased
  `INGRESS_RULES` tuple is the necessary or sufficient architecture for
  Frames structural validation, scalar normalization/type resolution,
  heterogeneous metadata schemas, ownership establishment, diagnostics, and
  trusted-carrier construction all at once. `IngressRule` today is only a
  named `Callable[[Frames], Frames]` over `dict[str, Any]` -- credible for
  small, feature-owned metadata normalizations, not demonstrated for the
  much larger job a general trusted-ingress boundary would need to do. This
  concept therefore withdraws any claim that a future ingress slice must
  keep the current tuple shape: the *phase* (framework-owned,
  non-addressable, running at the load-time position documented in
  <<tirs-boundary-architecture>>) is worth preserving; the *mechanism*
  (one flat tuple vs. explicit subphases vs. feature-owned schema delegates
  vs. trusted-carrier construction vs. another bounded coordinator design)
  is an open decision for whichever future FTR extends it. Any such FTR
  must state, for its own slice: input authority, ownership/copying,
  ordering, diagnostics, atomicity, and the exact downstream guarantee it
  establishes.
* *Risk of becoming an unjustified central god-sanitizer*: real if a future
  slice tried to fold parser limits, scalar typing, `_meta` schema
  validation, and pipeline addressability all into one `run_domain_ingress`
  call regardless of which mechanism is chosen. Any new rule proposed under
  this concept's FTR map (<<tirs-ftr-map>>) should be evaluated against this
  risk before it is written.

This concept does not modify `domain/ingress/` in any way.

=== 11. Maintained output sinks [[tirs-sinks]]

Review 001's I-011/B-003 findings require replacing hypothetical
future-sink emphasis with an inventory of what the framework actually
writes today, and its actual current controls.

[cols="2,3,3",options="header"]
|===
| Sink | Current code-sensitive behavior | Ownership/policy implication

| XLSX
| `LookupFormulaSpec` is deliberately translated to a real XLOOKUP formula
  (`_xlsx_lookup_formula`). *But* `_xlsx_cell_value` returns every other
  value unchanged, and `_write_data_block` passes it straight to
  `ws.cell(..., value=value)`. OpenPyXL itself then classifies an ordinary
  string beginning with `=` as a formula cell. A live probe confirms this:
  writing the ordinary string `"=1+1"` through `save_xlsx` and reading it
  back with `data_only=False` reports `data_type == "f"`; `"+5"` reports
  `data_type == "s"` (ordinary string)
| *Concrete, currently unresolved formula-output policy gap.* Untrusted
  payload text can cross this sink as executable spreadsheet formula syntax
  without ever passing through `FormulaSpec`. This is sink-local, not a
  reason to censor cell scalars generally -- see <<tirs-ftr-map>> candidate
  7. `tests/architecture/formula_boundary/test_raw_formula_boundary_guards.py`
  does *not* protect against this: it is a source-code drift guard that
  keeps hardcoded backend-specific formula syntax out of generic layers of
  the codebase, unrelated to what a runtime payload string can become

| ODS
| `LookupFormulaSpec` becomes an OpenFormula lookup expression; ordinary
  values are written as `TableCell(valuetype="string"/"boolean"/"float",
  ...)` -- the ODS renderer's ordinary-value branch never reaches its
  formula branch for anything but `LookupFormulaSpec`
| Formula translation is adapter-owned and behaves *differently* from
  XLSX: an ordinary ODS string does not become a formula cell the way an
  XLSX one can. Any future cross-backend formula-output policy must account
  for this asymmetry rather than assume shared behavior

| CSV
| `_escape_csv_cell` quotes delimiter/quote/newline content; a
  formula-looking string (`"=1+1"`) is written as ordinary quoted or
  unquoted text in the `.csv` file itself
| The CSV file itself does not execute anything; downstream spreadsheet
  application interpretation of a `.csv` re-opened in Excel/Calc is an
  exposure concern for whatever opens the file, not something the CSV
  serializer can control

| JSON / YAML / XML
| Stdlib `json`, PyYAML's safe dumper, and stdlib `ElementTree` serializers
  encode structured/text content as-is
| No SQL, shell, or HTML evaluator exists anywhere in the maintained
  codebase. Keep serializer-local escaping; do not invent a global content
  filter for a sink class that does not exist yet

| Main backend output paths (all `kind`s)
| The operator/pipeline I/O descriptor (`output.path`) selects the
  destination directly; the framework does not root-contain it
| Deliberately operator/pipeline-owned capability -- this is the intended
  design (the caller chose the output location), not a gap, but it means an
  untrusted-pipeline policy must treat "which `output.path` is permitted" as
  a capability to allowlist, not assume the framework already contains it

| Registered writer: `write_structured_yaml`
| Writes one or more *declared* relative files under a resolved output
  root; `_safe_target_path` rejects absolute paths and anything that
  resolves outside the output directory (`Path.resolve(...).is_relative_to(
  output_dir)`)
| Existing, real path-containment control. For an untrusted-pipeline
  policy, the *step* and its *file-path parameters* both need allowlisting
  -- a registered step name alone is not authorization

| Registered writer: `write_key_value_resources`
| Same `_safe_target_path` containment. File path labels are rendered from
  `file_pattern` combined with payload partition-column *values*
  (`_render_pattern(file_pattern, partition_cols, group_values)`), so
  untrusted *payload* content can influence the output filename within an
  already-contained directory
| A concrete, currently-real payload-to-sink control point: path
  containment already defends the filesystem, but the *pattern* itself
  (which columns partition the output) is a pipeline-supplied parameter
  that an untrusted-pipeline policy would need to constrain

| Registered writer: `write_artifact_manifest`
| Same `_safe_target_path` containment, plus explicit rejection of
  Windows-drive and POSIX-absolute forms and `..` traversal; reads and
  checksums the files it reports and writes a YAML/JSON manifest
| Existing containment and traversal rejection; the read-then-checksum
  capability is itself policy-relevant (it can read arbitrary files under
  the configured root) independent of the write side
|===

No maintained SQL, shell, or HTML sink exists; none is invented or required
by this concept. Input normalization (what a value is allowed to look like)
and sink-specific injection protection (what a sink does with a value it
already accepted) remain different concerns with different owners --
restated correctly this time with the XLSX formula gap named as *current*
evidence rather than hidden behind a general "strings are inert" claim.

=== 12. Supported guarantees and explicit non-guarantees [[tirs-guarantees]]

==== Guarantees this concept believes are already true today, given current code

* Maintained YAML reads (`yaml_backend.py`, `json_backend.py`'s `_meta.yaml`
  sidecar, `yaml_overrides.py`) all use `yaml.safe_load`, which blocks
  PyYAML's Python-specific arbitrary/custom object constructors. This does
  *not* mean YAML input is a closed value contract: a probe confirms
  `safe_load` still resolves anchors/aliases to shared object identity and
  `!!binary` to `bytes`, and imposes no resource ceiling.
* JSON payload reads use `pandas.read_json(..., dtype=str, ...)`; combined
  with `dtype=str`, this means JSON payload cannot expose nested Python
  objects as DataFrame cell values, though it is a pandas-owned guarantee,
  not a stdlib-`json`-exclusive one.
* ODS parsing is bounded against pathological dimension declarations by
  `ParserLimits`, independent of which sheet-formatting trick produced the
  declaration. *XLSX is not currently covered by this guarantee at all.*
* The one `_meta.legend_blocks` shape ingress normalizes is deterministically
  rejected (a clear `ValueError`) when malformed, and rejection is atomic:
  the integration tests confirm no partial mutation of the caller's object
  graph on ingress failure, and no output is written when `orchestrate()`'s
  ingress call raises.
* Registered filesystem writers (`write_structured_yaml`,
  `write_key_value_resources`, `write_artifact_manifest`) all implement
  `_safe_target_path` containment against absolute paths and traversal
  outside their configured output root.

==== Explicit non-guarantees [[tirs-non-guarantees]]

* No protection from a runtime operator controlling the CLI, the Python
  process, the environment, or the import path. This is the standing
  assumption, not a gap.
* No containment of arbitrary Python plugins or dotted-callable targets
  running in the same process -- `pipeline/dotted_paths.py`'s one namespace
  exclusion is an ownership/architecture guard, explicitly not a security
  boundary, exactly as `FTR-PIPELINE-DOTTED-EXTENSION-SURFACE-P4A` already
  states for that surface.
* No general process, container, OS, or network sandboxing of any kind.
* *No XLSX resource ceiling.* Unlike ODS, XLSX parsing has no `ParserLimits`
  coverage today; a pathological XLSX input has no framework-level circuit
  breaker.
* *No guarantee that ordinary XLSX payload text is inert.* A payload string
  beginning with `=` becomes a live formula cell when written through the
  maintained XLSX renderer, independent of `FormulaSpec`. `FormulaSpec` is
  not currently the exclusive gate for XLSX formula-capable cells.
* No claim that every current or future parser or sink is protected --
  CSV/JSON/YAML/XML resource bounds and an XML entity-expansion guard do not
  currently exist. Effective XML entity protection depends on the linked
  Expat version, not on a framework-owned policy; ElementTree does not
  resolve external entities by default, but internal-entity expansion is not
  independently bounded here.
* No security-by-obscurity: a profile name or a CLI flag being undocumented
  or hard to find is never, itself, a protection.
* No claim that a dotted path passing `resolve_configuration_callable`'s
  syntax check is itself a safety property -- that is an
  architecture/ownership property, not a security property.
* No claim that the trust-profile sketch in <<tirs-profiles>> is
  implemented, load-bearing, or safe to reference as though it were a
  runtime contract.
* No claim that `run_pipeline`'s caller-constructed Frames are trusted by
  anything other than the calling code's own contract -- see §3.1's Direct
  Python Frames row.

This concept requires honest use-case assessment by whoever operates the
framework: nothing above should be read as reassurance that a use case
handling genuinely hostile payload or pipeline input is already safe.

=== 13. Current gaps (consolidated)

* No XLSX resource ceiling, unlike ODS.
* Ordinary XLSX payload strings beginning with `=` are not guaranteed inert
  -- a concrete, currently exploitable sink-local gap, not a hypothetical.
* No resource ceiling on CSV/JSON/YAML/XML input comparable to ODS's
  `ParserLimits`.
* No closed internal scalar contract for non-spreadsheet carriers; the
  unresolved/missing/error dependency (<<tirs-nan>>) is concrete evidence
  that this gap already causes an observable defect, not merely a
  theoretical one.
* `pipeline.run_pipeline` bypasses ingress, persistence-boundary
  projection, and final cleanup -- a documented trusted-programmatic path
  today, explicitly left as an open decision rather than a defect
  (<<tirs-ftr-map>> candidate 9).
* Only JSON has a working structured `_meta.yaml` sidecar contract; XML has
  none, YAML's file of the same name is not treated as structured metadata
  at all, and CSV never round-trips `_meta`.
* No operator-facing security-policy representation of any kind (no field,
  flag, or object) -- expected, since no profile is implemented, but stated
  for completeness.
* No XML entity-expansion guard beyond whatever the linked Expat version
  provides by default.
* Technical Model `ch01_structure` / `ch02_contracts` remain TBD placeholder
  chapters. This concept does not attempt to fill that backbone gap; it is
  named here only because a fuller "which chapter should eventually own
  which durable piece of this concept" answer is blocked on it.

* Candidates 1 and 2 must not merge -- the BUG has its own recorded
  acceptance criteria and release-relevance note.
* Candidates 4, 5, and 6 must not merge into one "policy" FTR --
  representation (4), payload-axis enforcement (5), and pipeline-axis
  enforcement (6) have different dependencies and different owners (6 is
  gated on an entirely separate, already-open FTR).
* Candidate 9 must not be folded into candidate 3 -- it is a standalone
  public-API decision with its own consumers, not an implementation detail
  of extending ingress.
* No "general security umbrella FTR" is proposed. Candidates 7 and 8 are
  deliberately left as independent, narrow, adapter/sink-local work items so
  no single FTR accumulates permanent ownership of unrelated parser and
  sink concerns.
* Candidate 10 is explicitly not this concept's FTR to create; it already
  belongs to the hardening roadmap.

=== 16. Open questions and stop conditions [[tirs-open-questions]]

* Option A (orthogonal policy fields) vs. Option B (named convenience
  profiles) vs. a hybrid -- <<tirs-profiles>> takes no position beyond
  requiring that all four payload/pipeline combinations be representable.
* Whether `pipeline.run_pipeline`'s bypass of ingress/persistence-boundary/
  final-cleanup should gain an opt-in boundary, remain an explicit
  documented bypass, or be split into differently-named trusted/validated
  entry points -- <<tirs-ftr-map>> candidate 9, deliberately undecided here.
* Which ingress *mechanism* (flat tuple, explicit subphases, feature-owned
  schema delegates, trusted-carrier construction, or another bounded
  coordinator design) a future trusted-payload-ingress FTR should choose --
  <<tirs-current-ingress>>, explicitly left open.
* Where exactly `roadmap_domain_hardening_sequence.adoc`'s Phase E and this
  concept's boundary architecture (<<tirs-boundary-architecture>>) should be
  merged once both have more concrete grounding -- should the roadmap note
  eventually retire in favor of Technical Model contract content, per its
  own stated retirement conditions?
* Whether a canonical missing/unresolved/error representation, once the NaN
  BUG resolves, should be spreadsheet-substrate-compatible only, or should
  also define a non-spreadsheet-carrier (CSV/JSON/YAML) canonical shape --
  not addressed by this concept's narrow prerequisite framing.
* Is a `Decimal`-carrying scalar contract actually needed by any current
  consumer, or is its absence from <<tirs-value-model>> simply because no
  current path produces one?
* Should XLSX formula-output policy (<<tirs-sinks>>, candidate 8) prefer an
  escape/literal-text convention, a `FormulaSpec`-only allowlist for what
  may become a formula, or a different mechanism -- not decided here.

Stop conditions for this concept's own scope, restated from the task
constraints it was drafted and corrected under: this document authorizes no
runtime code, no test change, no CLI flag, no configuration key, no registry
entry, no parser limit, and no new type. Any reader treating a section above
as already-accepted architecture, rather than provisional and
review-pending, is reading it incorrectly.
