== Findings

=== Blocking findings

==== B-001 -- XLSX is not protected by `ParserLimits`

*Severity:* Blocking.

*Exact locus:* Section 3.1, rows `XLSX` and `Workbook readback`; section 9.1,
`Current shape`; section 12, guarantee “XLSX/ODS parsing is bounded”; and the
section 3 introductory claim that the framework “enforces spreadsheet parser
size limits.”

*Problem:* The concept repeatedly presents a material security guarantee that
does not exist. `ParserLimits` is enforced by the ODS parser, not the XLSX
parser. The XLSX read path calls `openpyxl.load_workbook(...)`; its
`parse_workbook(...)` signature has no limits parameter, imports no
`ParserLimits`, and performs no `SpreadsheetTooLargeError` check. In
particular, the concept's 10,000,000-cell ceiling is not an XLSX guarantee.

*Evidence:* `io_backends/ods/odf_parser.py` imports `DEFAULT_LIMITS`, accepts
`limits: ParserLimits`, and calls `limits.enforce(...)` throughout repeated-row,
repeated-column, grid, and hidden-sheet parsing. No corresponding import,
parameter, call, or focused limit test exists for
`io_backends/xlsx/openpyxl_parser.py`. The only maintained tests referring to
`ParserLimits` or `SpreadsheetTooLargeError` are under
`tests/unit/io_backends/ods/test_ods_parser_repeated_cells.py`.

*Required correction:* State that current `ParserLimits` enforcement is ODS
only. Inventory the actual XLSX behavior without treating OpenPyXL's carrier
rules or worksheet maxima as the framework's row/column/cell resource policy.
Qualify workbook readback per backend. Any XLSX resource bound requires a
separately authorized and tested implementation slice.

*Gates acceptance:* Yes.

==== B-002 -- the value model contradicts the accepted visible-cell string substrate

*Severity:* Blocking.

*Exact locus:* Section 3.1, rows `XLSX`, `ODS`, and `Workbook readback`;
section 7, categories 1--3 and the primitive/carrier bullets; and section 14,
candidates 2 and 3.

*Problem:* The concept describes visible XLSX/ODS cells as OpenPyXL/odfpy
scalars with no framework normalization, then proposes a general canonical
scalar model without acknowledging the accepted architecture decision that
visible spreadsheet payload is deliberately collapsed to a string substrate.
This contradicts accepted architecture and makes the proposed internal-value
and ingress work an unsafe basis: it could silently reopen the accepted
spreadsheet carrier contract.

*Evidence:* Accepted
`ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE` states that both spreadsheet parsers
force visible payload to text at the table-block boundary. Current
`xlsx/parser_interpretation.py` appends
`str(val) if val is not None else ""`; ODS interpretation performs the same
collapse after reading `office:value-type`. `workbookir_to_frames()` then
constructs Frames from those string rows. Typed carrier observations and
programmatic/structured-data Frames are different concerns.

*Required correction:* Make the accepted string substrate an explicit
constraint. Separate at least: raw carrier observations; normalized visible
spreadsheet strings; structured-backend and programmatic pandas/NumPy values;
and opt-in domain typing. Any proposal to change the visible spreadsheet
substrate needs a successor decision under the accepted ADR's revisit gates,
not an ingress/value-model FTR implied by this concept.

*Gates acceptance:* Yes.

==== B-003 -- ordinary XLSX payload strings are not guaranteed inert

*Severity:* Blocking.

*Exact locus:* Section 9.5, statement that `FormulaSpec` is the clean formula
boundary; section 11, statement that current behavior treats SQL/shell/source/
HTML-like strings as inert and that nothing inspected executes or evaluates
based on cell content; and section 12, guarantee that formula output intent is
a closed value object rather than a free-form string at serialization.

*Problem:* The concept gives a false material sink guarantee. The current XLSX
renderer passes every ordinary non-`LookupFormulaSpec` value directly to
OpenPyXL. OpenPyXL classifies an ordinary string beginning with `=` as a formula
cell. Thus untrusted payload text can cross the maintained XLSX sink as
executable spreadsheet formula syntax without ever being represented by
`FormulaSpec`. ODS ordinary strings are emitted as `office:value-type="string"`,
so the two maintained spreadsheet sinks also differ.

*Evidence:* `_xlsx_cell_value()` returns an ordinary string unchanged and
`_write_data_block()` assigns it through `ws.cell(..., value=...)`. A focused
end-to-end probe through `save_xlsx` wrote `"=1+1"`; OpenPyXL readback with
`data_only=False` reported `data_type == "f"`. The same probe reported strings
beginning with `+`, `-`, or `@` as string cells. The ODS renderer's ordinary
value branch constructs `TableCell(valuetype="string", stringvalue=text)`;
only `LookupFormulaSpec` enters its formula branch.

*Required correction:* Withdraw the inert-string and closed-formula-boundary
guarantees. Inventory the current XLSX behavior as a concrete code-sensitive
sink and keep it separate from input scalar validity. State that any formula
output policy, literal-text escape, compatibility decision, or cross-backend
alignment requires its own evidence and authorization. Do not imply that
`FormulaSpec` already mediates every formula-capable cell.

*Gates acceptance:* Yes.

=== Important findings

==== I-001 -- the structured `_meta` and sidecar inventory is materially wrong

*Severity:* Important.

*Exact locus:* Section 3.1 rows `YAML`, `XML`, `Structured sidecars
(_meta.yaml)`, and `Application API payload paths`; section 7 category 6; and
section 13's consolidated ingress gaps.

*Problem:* The concept says structured `_meta.yaml` sidecars are read by the
JSON and XML backends and groups YAML with structured metadata ingress. Current
code has only one structured-directory `_meta.yaml` sidecar path: JSON. XML
does not read or write a sidecar. YAML glob-loads `_meta.yaml` as an ordinary
sheet/DataFrame and skips a `_meta` Frames entry on save. CSV also skips
`_meta` and has no sidecar path. Consequently `orchestrate()` invokes ingress
after these loads, but only JSON supplies a mapping-shaped `_meta` for ingress
to normalize.

*Evidence:* `json_backend.py` explicitly opens `in_dir / "_meta.yaml"` and
stores a mapping as `out["_meta"]`. `xml_backend.py` contains no YAML import or
sidecar operation. `yaml_backend.py` globs all `*.yml`/`*.yaml`, converts each
document to a DataFrame keyed by its stem, and its saver skips the `_meta` key.
`csv_backend.py` likewise skips `_meta` on save and does not read one.

*Required correction:* Inventory structured payload and metadata carriers per
backend. Distinguish JSON sidecar metadata, workbook-embedded XLSX/ODS metadata,
YAML/CSV/XML payload-only behavior, explicit override documents, and direct
programmatic `_meta`. Identify which of those forms actually reaches
`domain.ingress` as a mapping.

*Gates acceptance:* Yes.

==== I-002 -- direct Python Frames are trusted by caller contract, not by construction

*Severity:* Important.

*Exact locus:* Section 3.1, `Direct Python Frames input` row (“Fully trusted by
construction”); the following “trusted programmatic composition path” gap; and
section 13.

*Problem:* No constructor, validator, capability token, or type gate makes
caller-created Frames trusted. `run_pipeline` accepts the object graph it is
given and immediately invokes already-bound callables. A DataFrame object
column may contain arbitrary caller objects, and Frames values may also be
non-DataFrame carriers. The path can be trusted *by API contract and operator
decision*; it is not intrinsically safe or trusted by construction.

*Evidence:* `pipeline.execution.run_pipeline()` only iterates steps.
`pipeline.types.Frames` is a static alias, not runtime enforcement. The public
package re-exports `run_pipeline`. Accepted Domain Boundary Robustness places
competent-user Frames at boundary level 2 and requires capability-contract
validation of implied failures; it reserves “trusted internal values” for
validated internal constructors or resolutions.

*Required correction:* Use “trusted-by-contract direct composition path” and
state its assumptions. Do not imply controlled construction. Preserve the
separate open decision whether the public path remains an explicit bypass,
gains an opt-in boundary, or is split into clearly named trusted/validated
entry points.

*Gates acceptance:* Yes.

==== I-003 -- JSON and safe-YAML guarantees overstate the inspected mechanisms

*Severity:* Important.

*Exact locus:* Section 3.1 rows `JSON` and `YAML`; section 7 category 1 and the
mapping/list bullet; and section 12's first two guarantees.

*Problem:* The claim that JSON parsing uses the stdlib `json` module
exclusively contradicts the inventory and code: payload JSON is parsed by
`pandas.read_json`. The YAML claim is also too broad. `yaml.safe_load` blocks
Python-specific arbitrary/custom constructors and is the correct maintained
loader, but it still constructs rich standard Python graphs, including nested
lists/mappings, bytes from `!!binary`, dates, sets, aliases, and cyclic
containers. It is neither a closed cell-value contract nor a resource bound.

*Evidence:* `JSONBackend.read_multi()` calls
`pd.read_json(..., dtype=str, convert_dates=False)`; stdlib `json` is used by
writers and workbook metadata parsing, not exclusively by the JSON payload
reader. A local safe-loader probe produced `bytes` and nested-list DataFrame
cells and a self-referential list from a YAML alias. A source scan confirms all
seven maintained YAML read sites use `yaml.safe_load`; no unsafe loader was
found.

*Required correction:* Preserve the true narrow guarantee: maintained YAML
reads use `safe_load` and therefore do not enable PyYAML's Python-specific
arbitrary object constructors. Separately inventory the allowed standard
shapes, alias/cycle behavior, pandas conversion, and missing resource limits.
Describe the JSON payload path as pandas-owned and state only guarantees
supported by that path.

*Gates acceptance:* Yes.

==== I-004 -- the threat model does not have four variable independent axes

*Severity:* Important.

*Exact locus:* Section 4 heading “Four independent axes”; axis 1, which says it
is not variable; axis 4, which includes a “plugin invocation triggered by
output”; and the conclusion that axes 2--4 are independent.

*Problem:* A fixed trusted-runtime assumption is a precondition, not a variable
axis. Output-sink exposure is a per-capability/per-consumer property, not a
trust actor equivalent to payload or pipeline authorship. A plugin invocation
is pipeline execution/addressability even if it performs output, not a new sink
trust axis. Calling all four independent hides these different kinds of
concern and makes it unclear what a policy representation must carry.

*Evidence:* The concept itself says runtime/operator trust is “always trusted”
and “not a variable axis in practice.” Its three proposed profiles encode only
pipeline and payload trust and carry no sink-exposure dimension. Current code
also has sink-local differences: XLSX string/formula interpretation, ODS string
emission, serializer escaping, and filesystem-capability steps.

*Required correction:* State trusted runtime/operator control as the fixed
model assumption. Model payload trust and pipeline-description trust as
orthogonal input-authority dimensions. Model sink exposure/capabilities and
consumer interpretation separately, with explicit flow from effective policy
to each sink.

*Gates acceptance:* Yes.

==== I-005 -- `untrusted_pipeline` is a combined profile while claiming not to be a ladder

*Severity:* Important.

*Exact locus:* Section 2's motivating “someone else's pipeline against trusted
data” use case; all of section 5, especially `untrusted_pipeline`; and section
16's fourth-profile open question.

*Problem:* The profile named only for pipeline trust silently assumes both the
pipeline and payload are untrusted. The motivating trusted-payload/untrusted-
pipeline case therefore has no profile. Yet the concept then says
`untrusted_pipeline` is not a more restrictive `untrusted_payload` and that the
profiles are independent-axis combinations. The name and semantics create the
ladder the text disclaims.

*Evidence:* `untrusted_payload` means trusted pipeline plus untrusted payload;
`untrusted_pipeline` means both untrusted. No named combination represents
trusted payload plus untrusted pipeline, even though section 2 uses that exact
case to justify the concept.

*Required correction:* Prefer orthogonal policy fields/capabilities, or define
profiles only as clearly named conveniences over an explicit matrix. If the
combined profile remains, name it as combined. Include the trusted-payload/
untrusted-pipeline combination. Keep untrusted-pipeline enforcement allowlist-
or capability-based; do not present current namespace denylisting as that
policy.

*Gates acceptance:* Yes.

==== I-006 -- the monotonic policy equation is not operationally precise enough

*Severity:* Important.

*Exact locus:* Section 6, especially
`effective policy = operator policy restricted by any additional pipeline
limits` and the following “ceiling” explanation.

*Problem:* The ownership direction is sound, but “restricted by” assumes a
single ordering that the concept elsewhere denies. Step allowlists, parameter
schemas, filesystem capabilities, formula policy, numeric parser ceilings,
and boolean permissions combine differently. The text does not say what
happens for incomparable or contradictory pipeline requests, unknown fields,
or a pipeline attempt to select a weaker named profile. Without explicit
combination/rejection semantics the invariant is too easy to implement as
precedence, which would be bypassable.

*Evidence:* Current CLI, `orchestrate(...)`, and deployment configuration have
no policy object, so this is purely proposed architecture. The concept correctly
names operator-controlled CLI/API/deployment transports and correctly forbids
pipeline widening, but supplies no monotonic construction beyond prose.

*Required correction:* State the invariant per policy kind: intersection for
allowlists; minimum/capping for numeric ceilings where orderable; logical
conjunction or capability removal for permissions; schema intersection for
parameters; and rejection for unknown, contradictory, or non-orderable
requests. The operator-owned policy must be immutable to pipeline input and
failure must occur before a forbidden callable or sink capability is resolved
or invoked. No concrete public API is required at concept stage.

*Gates acceptance:* Yes.

==== I-007 -- the ten-category value model conflates data, Intent, carriers, Resolution, and executable capability

*Severity:* Important.

*Exact locus:* Section 7, especially categories 2, 7, 8, 9, and 10 and the
bullets about `FormulaSpec`, `ExactTable`, `GroupedMatrix`, arbitrary objects,
and `Any`.

*Problem:* The proposed taxonomy is not internally coherent:

* category 2 says CSV implicitly normalizes missing values to `""`, but the
  orchestrator's CSV-directory path uses `pd.read_csv` without that
  normalization and can retain pandas NaN/dtype carriers;
* category 7 describes metadata “after ingress + persistence-boundary
  projection” as trusted internal metadata, although persistence projection is
  an output projection at the end of orchestration, not the constructor of the
  runtime internal view;
* category 10 labels inert `FormulaSpec` Intent and current internal carriers as
  “Executable/runtime-owned object,” while omitting the actual executable
  `BoundStep.fn`/resolved callable capability;
* `ExactTable` and `GroupedMatrix` are already implemented and exercised
  Frames-boundary carriers, not merely possible future patterns; and
* `FormulaSpec` dataclasses are public and directly constructible, even though
  factories are the normal convenience path.

*Evidence:* `core/formulas.py` documents backend-neutral Intent.
`spreadsheet_meta_semantics.adoc` places `FormulaSpec` in IR/RenderPlan Intent.
`pipeline.types.BoundStep.fn` is the runtime callable. `ExactTable` is produced
by workbook projection and `GroupedMatrix` has a validated feature-owned
constructor; focused public roundtrip tests use both. The persistence boundary
drops Resolution and runtime-only metadata immediately before a saver; it does
not establish ingress trust.

*Required correction:* Redraw categories by role and lifecycle. Keep canonical
cell values distinct from pandas/NumPy carriers; missing, unresolved, and
spreadsheet-error states distinct; external and runtime metadata distinct from
persistable projection; authored Intent (including `FormulaSpec`) distinct from
materialized Resolution; controlled carriers distinct from scalar values; and
runtime executable capabilities/callables outside payload value categories.
No class hierarchy is required.

*Gates acceptance:* Yes.

==== I-008 -- NaN evidence and prerequisite ordering are misstated

*Severity:* Important.

*Exact locus:* Section 8's symptom/root-cause summary and classification as a
hard prerequisite; section 14 candidates 1 and 2; and the adoption sequence in
section 15.

*Problem:* The concept says the current bug path is fully traced from an empty
source key through `_norm_id`, a join NaN, and stringification to `"nan"`.
The BUG explicitly says the path is not fully pinned. The maintained xfail has
also evolved: it now uses a non-empty but unresolved key and currently observes
an ordinary empty-string helper value on a no-cleanup XLSX roundtrip. The final
contract remains undecided. The concept then makes resolution a hard blocker
for all minimal internal-value-model work, while the authoritative roadmap says
it belongs before *or at the beginning* of typing. Stable work on existing
Intent and carriers need not wait; only final missing/unresolved/error semantics
are blocked.

*Evidence:* `BUG-UNRESOLVED-HELPER-VALUE-NAN-SEMANTICS-P4A` records three
plausible carriers and requires the implementer to pin the root cause.
`tests/roundtrip/test_pathological_cell_contracts.py` uses
`ENT-MISSING`, expects a future representation other than `"nan"` or `""`, and
is marked non-strict xfail. Roadmap Phase C says the decision belongs before or
at the beginning of Phase D.

*Required correction:* Report historical BUG evidence separately from the
current xfail. Do not claim a pinned cause. Gate only the canonical
missing/unresolved/error part of the type contract and work that depends on
that decision; do not block documentation or typing of already-stable Intent,
Resolution, and carrier contracts.

*Gates acceptance:* Yes.

==== I-009 -- one flat `INGRESS_RULES` tuple is preselected beyond its evidence

*Severity:* Important.

*Exact locus:* Section 10, “Suitable for extension”; section 14 candidate 3,
which requires keeping the flat-rule architecture; and section 9.2's combined
structural/scalar boundary.

*Problem:* The current tuple is credible for an ordered set of small,
feature-owned metadata normalizations. One Legend Blocks rule does not prove
that the same unphased list is the necessary or sufficient architecture for
Frames structure, scalar normalization/type resolution, heterogeneous metadata
schemas, ownership establishment, diagnostics, and trusted-carrier creation.
The concept simultaneously warns against a god-sanitizer and mandates the
unvalidated growth mechanism.

*Evidence:* `IngressRule` is only a named `Callable[[Frames], Frames]`; the
runtime type is `dict[str, Any]`. The current rule owns one metadata root and
shares nested caller values. Roadmap Phase E explicitly separates structural
validation, value normalization/type resolution, and trusted internal Frames,
while the accepted boundary concept requires deliberate ownership,
diagnostics, and scoped atomicity.

*Required correction:* Preserve `domain.ingress` as the non-addressable phase,
not necessarily one forever-flat rule list. Let a future FTR decide whether the
coordinator retains a tuple, adds explicit subphases, delegates to feature
schemas, or constructs trusted carriers. Require each slice to state ownership,
ordering, diagnostics, atomicity, and the exact downstream guarantee.

*Gates acceptance:* Yes.

==== I-010 -- boundary independence confuses ownership with data/control flow and omits security context

*Severity:* Important.

*Exact locus:* Section 9's closing ordering paragraph; sections 9.3--9.5; and
section 11.

*Problem:* Saying the sink boundary is independent of boundaries 9.1--9.4 and
depends only on domain output is wrong in the relevant sense. Sink ownership is
separate, but a sink executes after input/domain flow and must receive the
effective operator policy/security context needed for formula, filesystem, and
other capabilities. Conversely pipeline addressability is often resolved while
building configuration, before payload parsing; it does not become safe merely
because structural ingress “has run.” Domain execution can also receive direct
programmatic `BoundStep` values for which configuration addressability never
runs.

*Evidence:* Current `orchestrate()` loads, runs domain ingress, invokes already-
bound steps, executes cleanup, projects metadata, and calls the selected saver.
CLI step binding occurs before `orchestrate()`. Direct `run_pipeline` receives
prebuilt callables. No current policy context exists, which makes the concept's
future propagation rule especially important.

*Required correction:* Distinguish ownership independence from execution and
control dependencies. Describe pipeline authorization at configuration bind/
resolution time, payload parsing/ingress at load time, domain assumptions at
step invocation, and sink enforcement at output time. Require the separately
owned sink to receive an immutable effective policy/capability context; do not
route that concern through cell sanitization.

*Gates acceptance:* Yes.

==== I-011 -- the sink assessment omits maintained filesystem capabilities and their existing controls

*Severity:* Important.

*Exact locus:* Section 9.5's statement that filesystem paths and generated
YAML/JSON/XML/CSV have no equivalent narrow contract inspected; section 11's
focus on hypothetical future SQL, shell, and template sinks; and section 14
candidate 7.

*Problem:* The concept does not audit the maintained code-sensitive sink
surface it already has. Registered pipeline steps
`write_structured_yaml`, `write_key_value_resources`, and
`write_artifact_manifest` perform filesystem writes. They already resolve an
operator/pipeline-supplied output root and reject absolute or escaping relative
targets. Key-value file patterns can derive target labels from payload columns,
so this is directly relevant to untrusted payload and pipeline policy. Main
backend output paths are operator/pipeline descriptors and are intentionally
not root-contained. These facts matter more than nonexistent SQL/shell/HTML
backends.

*Evidence:* The three domain writers implement `_safe_target_path` with
absolute-path rejection and `Path.resolve(...).is_relative_to(output_dir)`;
artifact manifests additionally normalize portable relative paths and reject
`..`. They create directories and files as runtime side effects. The registry
exposes all three as normal short-name steps. The main backend savers accept
their output path from the orchestrator descriptor.

*Required correction:* Inventory maintained sinks and existing controls:
XLSX/ODS formula interpretation, CSV/JSON/YAML/XML serialization, main backend
output paths, and the three registered filesystem writer capabilities. For an
untrusted-pipeline policy, allowlist steps *and parameters/capabilities*; a
registered name alone is not authorization. Retain sink-local escaping and path
containment rather than a global cell filter.

*Gates acceptance:* Yes.

==== I-012 -- the FTR dependency map conflates representation, enforcement, and public-entry decisions

*Severity:* Important.

*Exact locus:* Section 14 candidates 2--5 and 7, the candidate-4/5 split
rationale, and section 16's `run_pipeline` open question.

*Problem:* The map says candidate 4 is runtime policy/profile representation, then
describes the 4/5 split as “payload vs. pipeline” and “a rule added to ingress
vs. an allowlist.” Candidate 4 is not an ingress rule; candidate 3 owns payload
ingress. Representation, per-axis enforcement, and adapter propagation are
different work. The map also embeds the unresolved public
`run_pipeline` decision inside candidate 3 rather than preserving it as an
explicit independent decision, and suggests sink work should follow the value
model despite the concrete XLSX formula issue being independently actionable.

*Evidence:* The dotted-extension FTR owns the full eight-surface assessment and
precedes any untrusted-pipeline enforcement decision. Parser limits are
correctly independent. The roadmap correctly gates family hardening on
mandatory ingress. Current `run_pipeline` is a public re-export with established
programmatic consumers, so changing its boundary cannot be a subordinate
implementation detail.

*Required correction:* Recast the map as candidate decisions, not preselected
implementations: stable value semantics where actually prerequisite; payload
ingress; operator policy representation and propagation; per-axis enforcement;
dotted-surface assessment then allowlisted untrusted-pipeline capability;
independent parser work; concrete sink-local work; an explicit separate
`run_pipeline` public-contract decision; and the roadmap-owned family pilot.
Keep FTR creation just in time and do not batch-create an umbrella.

*Gates acceptance:* Yes.

=== Minor findings

==== M-001 -- XML entity-expansion wording needs runtime-version qualification

*Severity:* Minor.

*Exact locus:* Section 3.1 `XML`; sections 9.1, 12, and 13 statements that no
XML entity-expansion guard exists.

*Problem:* There is no framework-owned XML limit or explicit defused parser,
which is a true gap. The broader wording can be read as saying ElementTree/
Expat has no protection at all. Python's primary XML security documentation
makes protection depend on the linked Expat version and advises checking
`pyexpat.EXPAT_VERSION`.

*Evidence:* The review environment is Python 3.13.5 with Expat 2.7.1.
https://docs.python.org/3/library/xml.html[Python's XML security guidance]
currently warns that Expat versions below 2.7.2 may be vulnerable to entity
expansion, large-token, or disproportionate-memory attacks. ElementTree does
not expand external entities by default, but internal entities can be expanded.

*Required qualification:* Say “no framework-owned XML resource/entity policy;
effective library protection is runtime-Expat-version-dependent.” Keep document
size, nesting, and memory bounds separate from entity behavior.

*Gates acceptance:* No, not by itself.

==== M-002 -- the ingress architecture-test route count is not exact

*Severity:* Minor.

*Exact locus:* Section 10, “across five distinct addressing routes ... plus a
reexport check.”

*Problem:* The prose count compresses different assertions and omits direct
colon-style factories from its named list even though the parametrized guard
tests them. Registry absence, descriptive-registry absence, unknown short-name
build rejection, plugin dotted resolution, colon-factory resolution, nested
target resolution, centralized resolver ownership, and re-export absence are
not cleanly “five routes.”

*Evidence:* `tests/architecture/test_domain_ingress_boundary.py` parametrizes
three ingress callable strings across plugin and colon-factory routes, tests the
same three as nested targets, and has separate registry, descriptive registry,
short-name build, resolver ownership, re-export, dependency, and rule-sequence
assertions.

*Required qualification:* Describe the guarded surfaces rather than giving an
ambiguous route count.

*Gates acceptance:* No, not by itself.

| Orchestrator ingress receives sidecar mapping

| YAML directory
| `yaml_backend.load_yaml_dir` using `yaml.safe_load`
| No resource limit; pandas conversion can retain structured standard objects
  and bytes; missing -> `""`
| `_meta.yaml` is an ordinary `_meta` DataFrame; saver skips `_meta`
| Current rule ignores non-mapping `_meta`

| XML directory
| `XMLBackend.read_multi` using stdlib ElementTree
| No framework byte/depth/node limit; leaf text becomes strings; Expat security
  is runtime-version-dependent
| No sidecar read/write
| Orchestrator calls ingress, but no mapping `_meta` is loaded

| Direct Python Frames
| Public `pipeline.run_pipeline`
| No runtime type/size boundary; arbitrary caller objects and current internal
  carriers are possible
| Whatever caller supplies
| Bypasses ingress, cleanup, and persistence projection

| Direct metadata merge
| `bootstrap_meta` and `apply_overrides`
| No general schema, size, or value closure
| Runs ingress after merge; only `legend_blocks` is normalized
| Automatic for these two maintained merge calls, including when invoked as
  configured steps

| CLI/application orchestration
| `sheets-run` builds steps, then calls `application.orchestrator.orchestrate`
| Selected backend behavior; no security-profile representation
| Ingress after load, before steps; cleanup and persistence projection before saver
| Current maintained router-backed application seam
|===

This inventory distinguishes “trusted by an API/operator contract” from
“intrinsically safe.” No parsed or direct path currently establishes the closed
trusted internal value model proposed by the concept.

== Security-claim assessment

* All maintained YAML reads found by the source scan use `yaml.safe_load`.
  This blocks Python-specific arbitrary constructors; it does not close value
  shapes, prevent aliases/cycles, or impose a resource ceiling.
* JSON payload documents use pandas, not the stdlib exclusively. Current
  `dtype=str` behavior stringifies nested JSON values rather than exposing
  custom objects, but that observed behavior is not the claimed parser owner.
* ODS enforces current row/column/cell ceilings after odfpy has loaded the
  document. XLSX does not use `ParserLimits`.
* CSV, JSON, YAML, and XML have no framework-level byte, depth, row, column,
  node, text-size, or time ceiling comparable to the ODS dimension checks.
* Legend Blocks ingress is deterministic and non-mutating for its documented
  caller graph. Integration tests prove that duplicate-identity failure occurs
  before a saver and that no output directory is created.
* `FormulaSpec` is a narrow, frozen Intent representation for the formula
  cases that use it. It is not the exclusive gate for XLSX formula cells.

== Threat model

The useful core is:

* fixed assumption: the runtime/operator, installation, import path, and
  out-of-band policy owner are trusted;
* variable input authority: payload trust;
* variable input authority: pipeline-description trust; and
* separate sink capability/exposure: how emitted content or side effects are
  interpreted and which capabilities the effective policy grants.

Payload and pipeline trust are orthogonal. Sink exposure is also independently
assessed, but it is not the same kind of axis and must receive policy context.
None of these provides a Python sandbox or contains already-running hostile
in-process code.

== Profiles and policy authority

The three names in the concept are illustrative and unimplemented. They are not
an acceptable complete public taxonomy in their current semantics.

[cols="2,3,3",options="header"]
|===
| Concept name | Problem | Review direction

| `trusted`
| Can be a convenience combination, but must not mean “skip validation”
| Trusted payload + trusted pipeline, under ordinary operator sink policy

| `untrusted_payload`
| Coherent combination, once real ingress/resource contracts exist
| Trusted pipeline + untrusted payload; parser and value boundaries apply

| `untrusted_pipeline`
| Name hides that the draft also assumes untrusted payload
| Represent pipeline restriction independently; use host-approved declarative
  allowlists/capabilities and parameter schemas

| Missing combination
| Trusted payload + untrusted pipeline is a motivating use case
| Must be representable without pretending the profiles form a ladder
|===

The durable policy invariant should be stated without requiring a concrete API:

[source,text]
----
operator policy is authoritative and supplied outside untrusted pipeline input
pipeline input may only remove capabilities or tighten orderable limits
effective allowlists = intersection(operator allowlist, requested subset)
effective numeric ceilings = minimum(operator ceiling, requested ceiling)
forbidden, widening, unknown, contradictory, or incomparable requests = reject
----

CLI arguments, application API parameters, and deployment-owned configuration
are plausible operator adapters. A pipeline field is never authoritative over
them. Enforcement must precede forbidden target resolution/invocation and must
propagate to sinks.

== Internal value assessment

A corrected vocabulary need not introduce a hierarchy, but it must distinguish:

. raw carrier observations before backend projection;
. accepted carrier-specific substrate values, including the normative visible
  spreadsheet string substrate;
. pandas/NumPy carriers in CSV, structured-data, and programmatic Frames;
. canonical domain scalar values where a family contract actually defines them;
. missing, unresolved-reference, and spreadsheet-error states;
. external structured metadata before feature ingress;
. runtime metadata after the rules that currently exist;
. persistable metadata after the output projection;
. authored backend-neutral Intent, including `FormulaSpec` and persistent
  placement/axis declarations;
. materialized Resolution and runtime-only metadata;
. controlled internal carriers such as current `ExactTable` and
  `GroupedMatrix`; and
. executable runtime capabilities such as resolved callables and
  `BoundStep.fn`, which are not payload value categories.

Mappings/lists can be legitimate structured values; they are not cell scalars
merely because pandas can hold them in an object column. Formula intent is inert
until a sink translates it. A raw XLSX-leading `=` string currently reaches the
same code-sensitive sink without that Intent type, which is a separate gap.

== NaN, missing, unresolved, and error semantics

The open BUG is valid concrete evidence that the value contract is unresolved.
It does not yet establish a general representation or a fully pinned cause.
The maintained non-strict xfail currently preserves the open decision with an
unresolvable `ENT-MISSING` key and an observed empty-string helper result.

Resolution is a hard prerequisite for finalizing the missing/unresolved/error
portion of the internal value model and ingress rules that enforce it. It is not
a hard prerequisite for documenting already-stable Intent, Resolution,
spreadsheet substrate, or controlled-carrier contracts. This preserves roadmap
Phase C before/or-at-the-start-of Phase D and does not fix or pre-decide the BUG.

== Boundary architecture and `domain.ingress`

The five ownership concerns remain useful when qualified:

. Parser/resource boundary -- format adapters/raw parser stage; currently ODS
  dimension limits only.
. Structural/scalar ingress -- framework-owned domain phase; currently one
  Legend Blocks metadata normalization, not a general trusted-Frames boundary.
. Pipeline authorization/addressability -- configuration binding/resolution;
  currently a namespace ownership exclusion, not a trust policy.
. Domain execution -- feature-owned invariants; assumptions depend on the
  actual entry route and guarantees established before invocation.
. Output sink -- separately owned serializer/capability; receives domain output
  plus immutable effective policy/security context.

“Separate owner” must not be written as “independent of all preceding data and
policy flow.” The project should continue to reject a universal
`sanitize_everything()` filter. Parser constraints remain parser-owned, domain
invariants family-owned, addressability pipeline/application-owned, and
formula/path/serialization behavior sink-owned.

Current `domain.ingress` facts:

* exactly one rule normalizes `_meta.legend_blocks` list/mapping/null shape and
  strips its stale `resolved` facet;
* it is invoked after orchestrator load and after the two maintained metadata
  merge operations;
* it is absent from runtime/descriptive registries and rejected across current
  string-addressing routes;
* it does not validate Frames structure, scalar values, other metadata roots,
  depth/size, callables, carrier identity, or arbitrary objects; and
* `run_pipeline` bypasses it.

The current ordered tuple may remain as a coordinator, but future work must not
be pre-authorized to flatten every structural, scalar, metadata, and carrier
concern into that list.

== Pipeline addressability

Current string resolution is centralized correctly:

* registry-owned string targets reach generic binders and the shared resolver;
* `step: plugin` dotted strings reach it;
* direct colon-style factories reach it;
* nested string targets received by generic binders reach it; and
* direct Python callables and prebuilt `BoundStep` values intentionally bypass
  configuration-derived string classification.

`ensure_configuration_addressable` rejects only the
`spreadsheet_handling.domain.ingress` namespace and submodules. Otherwise an
importable callable is addressable. This is a useful architecture/ownership
guard and not a sandbox, allowlist, public-API promise, or semantic-safety
check.

The open dotted-extension-surface FTR remains the authority for all eight
surfaces, including registered names, plugin callables, colon factories,
registry targets, nested targets, direct callables, direct `BoundStep`
composition, and framework-owned macro flow. This review does not preselect
that FTR's Options A--E. Any future untrusted-pipeline mode is downstream and
requires an operator-approved declarative capability surface rather than a
larger denylist.

== Conclusion

The concept has valuable raw material: trusted-operator scope, orthogonal
payload and pipeline authority, operator-owned monotonic restriction, a
non-sandbox addressability distinction, separate parser/domain/sink ownership,
and just-in-time bounded follow-up work. It cannot be accepted in its current
form because it contradicts the accepted spreadsheet string substrate, claims
an XLSX resource bound that does not exist, and claims inert formula-like XLSX
payload where the maintained sink creates formula cells. The structured-meta
inventory, trust/profile model, policy-combination rule, internal categories,
NaN dependency, ingress growth mechanism, sink inventory, and FTR map also need
material correction.

Until a corrected concept receives a fresh independent review, the existing
ADR, normative Domain Boundary Robustness concept, accepted spreadsheet typing
decision, current executable contracts, dotted-extension FTR, and hardening
roadmap remain authoritative.
